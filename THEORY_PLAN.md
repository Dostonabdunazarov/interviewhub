## Ключевое решение: теория — отдельная сущность, а не вопросы

Соблазн сделать «Теорию» витриной существующих вопросов надо отвергнуть.
Вопрос — это атом с ответом, теория — связный текст, который читают подряд.
Разная модель: у вопроса `Difficulty` и `Company`, у статьи — порядок в
разделе, время чтения и «что читать дальше». Склеивать их в `Question` через
флаг `IsTheory` — путь к тому, что каталог вопросов начнёт отдавать статьи.

Связь между ними — двусторонние ссылки (этап 5), а не общая таблица.

в сайдбаре не помещается на ноутбуке и его невозможно охватить взглядом.

## Почему именно трек, а не категория вопросов

Категорий 26, и они плоские: `csharp`, `advanced-csharp`, `clr-gc`, `async`
лежат рядом как равные. Для каталога вопросов это терпимо — там фильтр.
Для чтения подряд нужна иерархия: человек учит «.NET Backend», а внутри
проходит C# → CLR → async → EF Core в осмысленном порядке.

Треки НЕ дублируют категории. Категория отвечает «к чему относится этот
вопрос», трек — «что я учу». Одна статья трека может ссылаться на вопросы
из трёх категорий.

## Что изменилось после сверки с базой

Первая версия дерева была написана по названиям категорий. Выборка
заголовков показала четыре расхождения — все в сторону «материала больше,
чем казалось»:

- **«Архитектура» распалась на два трека.** `distributed-systems` (20) и
  `system-design-senior` (20) — это не про паттерны кода, а про отказы,
  согласованность и консенсус: Raft, векторные часы, PACELC, gray failure.
  А `architecture-patterns` (16) — наоборот, чистый код: Factory, Decorator,
  SOLID. В одном треке это смешало бы «как устроена система» и «как
  написать класс».
- **`performance-profiling` (18) и `devops-senior` (18) оказались
  инструментальными,** а не теоретическими: `dotnet-trace`, дампы,
  OpenTelemetry, canary. Профилирование осталось в .NET-треке (оно про
  рантайм), инфраструктура выделена в свой трек.
- **Коллекции заслуживают своего раздела.** В `csharp` (40) заметная доля
  вопросов — `Dictionary`, `HashSet`, `List` vs `LinkedList`. В одном
  разделе с LINQ и делегатами получилось бы под 20 статей.
- **В System Design есть отдельный пласт задач-разборов** («Спроектировать
  URL shortener», «notification service», ещё около десяти). Это другой
  жанр, чем теория — вынесен в раздел `design-drills`.

Оценка выросла с ~70 до ~190 статей. Это не повод резать дерево: разделы
публикуются независимо (этап 6), а полный список нужен, чтобы статьи не
пересекались между собой.

## Куда делись `*-advanced` категории

`advanced-csharp`, `advanced-concurrency`, `advanced-aspnet`,
`advanced-postgresql`, `kafka-advanced`, `microservices-advanced`,
`system-design-senior` — это не темы, а сложность. В дереве теории они
растворяются в соответствующих разделах, а глубина передаётся через
`TheoryArticle.LevelId` и порядок статей внутри раздела.

Это ровно то, что `SEO_AND_CATEGORIES_PLAN.md` предлагает сделать с
категориями вопросов (этап 2, слияние 26 → ~15). **Теория и консолидация
категорий должны прийти к одной картине мира** — иначе в каталоге будет
`kafka-advanced`, а в теории раздел `messaging`, и связь между ними
(этап 5) придётся описывать вручную для каждой статьи.

# Модель данных

Три таблицы. `TheoryArticle` — тело, остальные две — навигация.

```csharp
// Domain/Entities/TheoryTrack.cs
public class TheoryTrack : BaseEntity, ISluggable
{
    public string Slug { get; set; } = null!;
    public string Name { get; set; } = null!;
    public string? Description { get; set; }
    public string? Icon { get; set; }   // lucide-react, как у Category
    public string? Color { get; set; }
    public int SortOrder { get; set; }
    public bool IsPublished { get; set; }
    public ICollection<TheorySection> Sections { get; set; } = [];
}

// Domain/Entities/TheorySection.cs
public class TheorySection : BaseEntity, ISluggable
{
    public string Slug { get; set; } = null!;   // уникален в пределах трека
    public string Name { get; set; } = null!;
    public string? Description { get; set; }
    public int SortOrder { get; set; }
    public Guid TrackId { get; set; }
    public TheoryTrack Track { get; set; } = null!;
    public ICollection<TheoryArticle> Articles { get; set; } = [];
}

// Domain/Entities/TheoryArticle.cs
public class TheoryArticle : BaseEntity, ISluggable
{
    public string Slug { get; set; } = null!;   // глобально уникален — он в URL
    public string Title { get; set; } = null!;

    /// <summary>Короткий анонс для карточки и meta description.</summary>
    public string? Summary { get; set; }

    /// <summary>Тело в markdown. Рендерится тем же Markdown-компонентом, что ответы.</summary>
    public string Body { get; set; } = null!;

    public int SortOrder { get; set; }
    public TheoryStatus Status { get; set; } = TheoryStatus.Draft;
```

`TheoryStatus` повторяет `QuestionStatus` (Draft/Published/Archived) —

## Решения, которые стоит зафиксировать

**Slug статьи глобально уникален.** URL `/theory/articles/{slug}` вместо
`/theory/{track}/{section}/{article}`. Причина: при переносе статьи в другой
раздел (а это будет — дерево уточняется по ходу) вложенный URL ломается и
требует редиректов. Плоский — нет. Трек и раздел живут в хлебных крошках,
а не в пути.

**Slug раздела уникален в пределах трека**, не глобально: `postgresql`
может быть и в `dotnet-backend`, и в будущем `data-engineering`.

**`ReadingMinutes` считаем на бэкенде при сохранении** — как `SearchText`
у вопроса, в `SaveChangesAsync`. 200 слов/мин, минимум 1. Клиент не должен
пересчитывать это на каждый рендер.

**Полнотекстовый поиск — сразу.** Та же generated-колонка `tsvector`, что
в [QuestionConfiguration](src/InterviewHub.Infrastructure/Persistence/Configurations/ContentConfigurations.cs#L42):
`to_tsvector('russian', Title || Summary || Body)` + GIN. Добавить потом
дороже: миграция на заполненной таблице, а сейчас она пустая.

**`Question → Category` стоит на Restrict, и `TheoryArticle → Section`
должен стоять так же.** Удаление раздела с 8 статьями не должно молча
уносить их каскадом. `TheoryArticleQuestion` — Cascade с обеих сторон,
это чистая связь.

### Сайдбар: все треки, свёрнутые

Три уровня — Трек → Раздел → Статья, — но раскрыт только путь к текущей
статье. Остальное свёрнуто, поэтому в колонке одновременно видно 6 треков
плюс разделы одного из них: порядка 15 строк, а не 190.

```
▸ .NET Backend

  ▸ Основы System Design      7
```

- **Десктоп (≥1024px):** колонка 280px слева, `sticky top-(--size-header)`,
  своя прокрутка. Контент — `max-w-3xl`, как у страницы вопроса: длинная
  строка не читается.
- **Планшет/мобильный:** сайдбар уезжает в выдвижную панель по кнопке
  «Содержание». Переиспользовать логику мобильного меню из
  [Layout.tsx](frontend/src/components/Layout.tsx) — закрывать по смене
  `location.pathname`.

- Активный пункт подсвечен как `NavLink` в хедере (`bg-surface-sunken`).
- Прокрутка к активному пункту при прямом заходе по ссылке — иначе человек
  открывает статью и не видит, где он в дереве.

**Три уровня в узкой колонке — главный риск этапа.** Отступ на каждом
уровне съедает ширину, и заголовок статьи переносится на три строки.
Поэтому: отступ не больше 12px на уровень, треки — мелким шрифтом
в верхнем регистре (это заголовки группы, а не ссылки равного веса),
статьи — обычным. Если на реальных данных всё равно тесно, первым делом
убирать отступ у уровня статей, а не уменьшать шрифт.

### Страница `/theory` — полное оглавление

Вся структура одним списком: треки, разделы, статьи. Это и витрина
(«что вообще есть»), и рабочая навигация, и SEO-узел — все ссылки раздела
в одном HTML.

У каждой статьи — время чтения и грейд:

```
Как работает GC          8 мин   middle
```

Этого metanit не делает, а у нас `ReadingMinutes` и `LevelId` уже в модели.
Человек сразу понимает объём и свой ли это уровень — при 190 статьях это
важнее, чем кажется.

Оформление: заголовок трека крупно, раздел — подзаголовком, статьи —
списком в карточке (`rounded-card border-border-subtle`), а не голыми
подчёркнутыми ссылками. Между треками — воздух, чтобы страница
просматривалась, а не читалась подряд.

**Грабли:**

- `position: sticky` не сработает без явной высоты у родителя с overflow.
- Хедер `sticky top-0 z-50`; сайдбару нужен `z-index` ниже, иначе он
  перекроет хедер при прокрутке.
- Дерево грузится асинхронно — нужен скелетон постоянной ширины, иначе
  контент прыгает вбок при загрузке.
- Состояние раскрытия держать производным от текущего URL, а не в
  `useState`: иначе переход по ссылке из текста статьи не раскроет нужную
  ветку. Ручное раскрытие — поверх этого, отдельным `Set` в состоянии.

кусков и критерий готовности каждого.

## Единица работы — раздел, не статья

Пишем **разделами целиком**, а не по статье отовсюду понемногу. Причины:

- Статьи внутри раздела ссылаются друг на друга («подробнее — в статье про
  упаковку»). Если соседа ещё нет, ссылку либо не поставишь, либо она ведёт
  в 404 до конца наполнения.
- Раздел из 6–12 статей — это ~1 день работы и законченный результат:
  его можно опубликовать и увидеть на сайте.
- Пустые разделы в сайдбар не попадают, поэтому наполовину написанный
  раздел выглядит как полноценный и вводит читателя в заблуждение сильнее,
  чем его отсутствие.

Внутри раздела порядок — по `sortOrder` из таблиц дерева: статьи читаются
подряд, и поздняя может опираться на раннюю, но не наоборот.

## Один кусок = один раздел, и вот его цикл

Повторяется для каждого раздела без изменений:

1. **Уточнить список статей** по таблице дерева. Если по ходу стало ясно,
   что тема распадается на две или, наоборот, две склеиваются — поправить
   таблицу в этом файле, а не держать расхождение в голове.
2. **Проверить утверждения про рантайм замерами** (см. шапку): консольный
   проект в scratchpad, `GC.GetAllocatedBytesForCurrentThread()`,
   BenchmarkDotNet для времени. Числа в статье — только измеренные на этой
   машине, с указанием версии .NET.
3. **Написать файлы** `content/theory/<раздел>/NN-slug.md` с фронтматтером.
   Формат — из шапки: заход без заголовка → разбор по `##` с кодом → блок
   «Что стоит ответить на собеседовании», 6–7 мин (~12 тыс. знаков).
4. **Обновить `README.md` раздела** — таблица «что куда» и список ненаписанного.
   Для нового раздела README копируется из `csharp-lang` и правится.
5. **Импорт черновиками:** `node tools/import-theory.mjs --dry-run`, затем
   без `--publish`. Вычитка владельцем — на сайте в админке, а не в markdown.
6. **Публикация:** повторный прогон с `--update --publish`. Трек включить
   переключателем «виден», если это первый опубликованный раздел трека.
7. **Отметить в этом файле** — таблица прогресса ниже и шапка «с чего начать».

Про шаг 2 стоит знать заранее: **локально Docker не установлен**, поэтому
поднять стек из `docker-compose.yml` для проверок не получится. Для замеров
это не помеха — нужен лишь консольный .NET-проект в scratchpad, но любая
проверка против БД или API идёт против прода по HTTPS.

# Что сознательно НЕ делаем

**Прогресс чтения и «пройдено».** Нужна авторизация для гостей, которой
в проекте нет (JWT только для админки). Отдельная большая задача.

**Комментарии и правки от читателей.** Модерация, спам, хранение — цена
несопоставима с пользой на текущем трафике.

**Версионирование статей.** `UpdatedAt` хватает. История правок нужна
редакции из нескольких человек, а не одному автору.

**Видео и интерактивные задачи.** Другой продукт.

# Порядок работ

| Шаг | Этап | Результат |
|---|---|---|
| 1 | Этап 1 | API отвечает, дерево пустое |
| 2 | Этап 6 частично | Наполнить `csharp-lang` — 5–8 статей, чтобы было что показать |
| 3 | Этап 2 + 3 | Сайдбар и чтение работают на реальном контенте |
| 4 | Этап 4 | Дальше наполняется через админку, а не SQL |
| 5 | — | **Слияние категорий 26 → ~15** (`SEO_AND_CATEGORIES_PLAN.md`, этап 2). Не про теорию, но должно пройти до шага 6 — см. решение 1 ниже |
| 6 | Этап 5 | Связь с каталогом |
| 7 | Этап 6 | Остальные треки в порядке из решения 2 |

Шаг 2 намеренно стоит перед вёрсткой: сайдбар на трёх фейковых пунктах
выглядит рабочим, а на 190 реальных разъезжается. Лучше увидеть это сразу.

Треки и разделы заводятся все сразу (их 6 и 32), статьи — по мере письма.
Пустые разделы в сайдбар не попадают, поэтому заранее заведённое дерево
ничего не ломает, зато `SortOrder` проставляется один раз, а не
пересчитывается при каждом добавлении.

## Принятые решения

### 1. Категории вопросов сливаем — но после этапа 3, не раньше

**Слияние безопасно.** Проверено распределение грейдов по парам категорий
(прод, 2026-09-17):

| Категория | Грейды |
|---|---|
| `csharp` | middle 40 |
| `advanced-csharp` | **senior 25** |
| `postgresql` | junior 1, middle 79 |
| `advanced-postgresql` | **senior 25** |
| `kafka` | middle 40 |
| `kafka-advanced` | **senior 20** |
| `microservices` | middle 50 |
| `microservices-advanced` | **senior 20** |
| `multithreading` | middle 40 |
| `advanced-concurrency` | **senior 20** |
| `aspnet-core` | middle 50 |
| `advanced-aspnet` | **senior 22** |

Раскол идеальный: базовые категории — 100% middle, `*-advanced` — 100%
senior. Это снимает оговорку из `SEO_AND_CATEGORIES_PLAN.md` («прочитать
по 3–5 вопросов и убедиться, что тема та же»): различие между парами
**полностью** выражено через `Level`, поэтому слияние не теряет ни бита
информации. Шаг 2 того плана («заодно проверить, что у них Level = senior»)
тоже отпадает — проверено, senior у всех.

**Но сливать нужно после этапа 3, а не до.** Причина не в данных, а в
последовательности: слияние требует бэкапа, SQL-скрипта и 301-редиректов
со старых URL (`/categories/kafka-advanced` уже в индексе после этапа 1
SEO-плана). Это самостоятельная операция со своим риском, и мешать её
с первым релизом теории незачем — теория на этапах 1–3 категорий вообще
не касается.

Крайний срок — **до этапа 5** (связь статей с вопросами). Если сливать
после, привязки к вопросам из `kafka-advanced` придётся переделывать.

Порядок: этапы 1–3 теории → слияние категорий → этап 5.

### 2. «Код и архитектура» остаётся отдельным треком, пишется последним

Оставляем как самостоятельный трек, а не растворяем в .NET.

**Почему отдельный:** SOLID, Decorator, Clean Architecture спрашивают
независимо от стека. Внутри `dotnet-backend` они оказались бы на одном
уровне с «Как работает GC» — соседство, из которого читатель делает
неверный вывод, что это .NET-специфика.

**Почему последним:** трек самый тонкий (~30 вопросов) и, в отличие от
остальных, почти не опирается на существующие ответы — их придётся писать
с нуля. При этом он наименее срочен: из 734 вопросов базы его покрывают
30, то есть 4%.

Порядок написания треков по плотности базы:
`dotnet-backend` (~290) → `distributed` (~200) → `algorithms` (~41) →
`infrastructure` (~27) → `interview` (~13) → `code-design` (~30, последним).

`interview` стоит перед `code-design` несмотря на меньший объём: 13 статей
про soft skills пишутся быстро и закрывают целый трек, а он один из шести
в сайдбаре — пустой трек там заметнее, чем недостающий раздел.
