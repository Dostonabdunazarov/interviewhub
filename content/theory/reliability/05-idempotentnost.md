Идемпотентная операция даёт тот же эффект, сколько бы раз её ни выполнили с теми же входными данными. В распределённой системе это не приятное свойство, а условие корректности: повторы неизбежны. Клиент не дождался ответа и повторил запрос, пользователь дважды нажал «Оплатить», брокер с гарантией at-least-once доставил сообщение второй раз, провайдер прислал вебхук повторно. Если операция при этом не идемпотентна, каждый такой повтор — двойной заказ или двойное списание.

## Почему повторы неизбежны

Клиент, который не получил ответ, не знает, что произошло. Запрос мог потеряться до сервера, сервер мог выполнить его и потерять ответ, а может быть, запрос всё ещё выполняется. Отличить эти случаи со стороны клиента нельзя, поэтому у него два варианта: не повторять и, возможно, потерять операцию — или повторять и, возможно, выполнить её дважды. Exactly-once доставки по сети не бывает. Бывает at-least-once плюс идемпотентная обработка, и эффект получается как от «ровно одного раза».

Важно различать эффект и ответ. Повторный `DELETE` может вернуть `404` вместо `204`, но ресурс удалён один раз. Идемпотентность — про состояние системы, а не про одинаковые байты в ответе.

## Естественная идемпотентность

Лучший вариант — спроектировать операцию так, чтобы повтор был безвреден сам по себе. По спецификации HTTP идемпотентны `GET`, `HEAD`, `PUT` и `DELETE`, а `POST` и `PATCH` — нет. Но метод говорит лишь о том, что сервер **обещал**, а реализация может это обещание нарушить. Приёмы, которые делают операцию идемпотентной по построению:

| Вместо | Делать | Почему повтор безвреден |
| --- | --- | --- |
| `POST /orders` с id на сервере | `PUT /orders/{id}` с id от клиента (UUID v7) | второй `PUT` пишет то же самое |
| `balance = balance + 100` | запись проводки с уникальным id операции | вторая вставка упадёт на уникальности |
| «перевести в Paid» | `UPDATE … SET status = 'paid' WHERE id = @id AND status = 'pending'` | второй раз условие не выполнится |
| `INSERT` | `INSERT … ON CONFLICT DO NOTHING` | upsert не создаёт дубль |
| перезапись без проверки | `If-Match` с ETag или версия строки | устаревший повтор отклоняется |

Для чтений и операций «установить состояние» этого достаточно. Для денег, заказов и внешних побочных эффектов нужен явный ключ.

## Ключ идемпотентности

Схема, которую используют платёжные API, — заголовок `Idempotency-Key` (для него есть черновик стандарта IETF). Клиент генерирует ключ один раз на намерение пользователя — при нажатии кнопки, а не при каждой попытке — и передаёт тот же ключ во всех повторах. Сервер атомарно связывает ключ с результатом операции.

```sql
CREATE TABLE idempotency_keys (
    client_id     text        NOT NULL,
    key           text        NOT NULL,
    request_hash  bytea       NOT NULL,
    status_code   int,
    response_body jsonb,
    created_at    timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (client_id, key)
);
```

Ключ уникален в паре с клиентом: иначе чужой ключ вернул бы чужой ответ. Алгоритм на сервере:

1. Посчитать хэш тела запроса и вставить строку с ключом. Уникальный индекс гарантирует, что победит ровно одна попытка.
2. Если вставка упала на уникальности — прочитать строку. Тот же хэш и есть ответ — вернуть сохранённый ответ. Тот же хэш, ответа нет — операция ещё выполняется, `409 Conflict`. Другой хэш — ключ переиспользован для другого запроса, `422`.
3. Выполнить бизнес-операцию и сохранить ответ **в той же транзакции**, что и бизнес-изменение.

В .NET с EF Core и PostgreSQL:

```csharp
app.MapPost("/payments", async (
    [FromHeader(Name = "Idempotency-Key")] string key,
    PaymentRequest req, ClaimsPrincipal user, AppDb db, CancellationToken ct) =>
{
    var clientId = user.FindFirstValue(ClaimTypes.NameIdentifier)!;
    var hash = SHA256.HashData(JsonSerializer.SerializeToUtf8Bytes(req));
    var record = new IdempotencyRecord { ClientId = clientId, Key = key, RequestHash = hash };

    await using var tx = await db.Database.BeginTransactionAsync(ct);
    db.IdempotencyKeys.Add(record);
    try
    {
        await db.SaveChangesAsync(ct);
    }
    catch (DbUpdateException e) when (e.InnerException is PostgresException { SqlState: PostgresErrorCodes.UniqueViolation })
    {
        await tx.RollbackAsync(ct);
        db.ChangeTracker.Clear();
        var saved = await db.IdempotencyKeys.AsNoTracking()
            .SingleAsync(x => x.ClientId == clientId && x.Key == key, ct);

        if (!saved.RequestHash.AsSpan().SequenceEqual(hash))
            return Results.UnprocessableEntity();
        if (saved.StatusCode is null)
            return Results.Conflict();
        return Results.Content(saved.ResponseBody, "application/json", statusCode: saved.StatusCode);
    }

    var payment = new Payment { Id = Guid.CreateVersion7(), Amount = req.Amount };
    db.Payments.Add(payment);
    record.StatusCode = StatusCodes.Status201Created;
    record.ResponseBody = JsonSerializer.Serialize(payment);
    await db.SaveChangesAsync(ct);
    await tx.CommitAsync(ct);

    return Results.Created($"/payments/{payment.Id}", payment);
});
```

Почему гонки нет. Пока первая транзакция открыта, её строка с ключом не видна другим, но уникальный индекс уже занят. Конкурентная попытка с тем же ключом повиснет на вставке, дождётся коммита первой и получит нарушение уникальности — после чего прочитает готовый ответ. Если первая транзакция откатилась, вторая просто вставит строку и выполнит операцию сама.

Две детали в коде не случайны. После ошибки в PostgreSQL транзакция переходит в состояние aborted, и любые запросы в ней падают, поэтому сначала откат, потом чтение. `ChangeTracker.Clear()` нужен, потому что неудачно добавленная сущность осталась в контексте и попала бы в следующий `SaveChanges`. Как устроены транзакции в EF Core — в статье `Транзакции и уровни изоляции`.

## Где схема ломается

- **Проверка отдельным `SELECT`.** «Прочитать, есть ли ключ, и если нет — выполнить» — классическая гонка check-then-act: два одновременных повтора оба увидят пустоту. Атомарность даёт только уникальный индекс или блокировка.
- **Ключ в Redis, данные в PostgreSQL.** `SET NX` в Redis и коммит в базе не атомарны: сбой между ними оставит ключ без результата или результат без ключа. Ключ живёт там же, где бизнес-данные.
- **Ключ генерируется не там.** Ключ, созданный на сервере или в `DelegatingHandler` ретраев заново на каждую попытку, бесполезен: повтор придёт с новым ключом. Ключ рождается у инициатора намерения.
- **Сохранение временных ошибок.** Сохранять стоит только окончательные ответы. `500` или таймаут зависимости, «приклеенный» к ключу, заблокирует операцию навсегда. Ошибку валидации сохранить можно — она не изменится.
- **Слишком короткий TTL.** Ключи должны жить дольше окна повторов клиента, включая офлайн-очереди мобильных приложений. Stripe, например, хранит ключи не меньше 24 часов. Таблицу чистят фоновой задачей, а при большом объёме партиционируют по времени и удаляют партиции целиком.

## Внешние побочные эффекты

Транзакция базы не откатит вызов платёжного шлюза. Если внутри операции есть внешний вызов, схема меняется:

1. Записать ключ со статусом «выполняется» и **закоммитить** — теперь он виден, и повтор получит `409`.
2. Вызвать внешнюю систему, передав ей собственный ключ идемпотентности. У большинства платёжных провайдеров такой параметр есть, а ключи дочерних операций выводят детерминированно: `{key}:charge`, `{key}:refund`.
3. Записать результат и пометить ключ завершённым.

Если процесс упал между шагами, ключ остаётся «выполняется». Фоновая задача находит такие зависшие операции и докатывает их, спрашивая у провайдера статус по тому же ключу. Если внешняя система ключей не поддерживает, перед повтором её спрашивают о статусе операции по нашему идентификатору, а не повторяют вслепую.

## Сообщения

Для консьюмеров идея та же, только ключ уже есть — идентификатор сообщения. В транзакции обработки сначала вставляется запись в таблицу inbox:

```sql
INSERT INTO inbox (message_id, processed_at)
VALUES (@messageId, now())
ON CONFLICT (message_id) DO NOTHING;
```

Ноль вставленных строк — сообщение уже обработано, коммитим offset и идём дальше. Если консьюмер упал после обработки, но до коммита offset, повтор отсечёт inbox. Отправляющая сторона симметрично использует outbox, чтобы запись в базу и публикация события не расходились, — об этом в разделе про микросервисы.

## Ретраи на клиенте

Идемпотентность сервера — половина дела. Стандартный resilience-обработчик в .NET повторяет запросы **любых** методов, включая `POST`, поэтому для эндпоинтов без ключа повторы небезопасных методов отключают через `DisableForUnsafeHttpMethods()` — подробности в статье `Retry, jitter и retry storm`. То же касается hedging: стандартный hedging-обработчик отправляет копию и для `POST`, и отключить это одной настройкой нельзя.

## Что стоит ответить на собеседовании

Идемпотентность — одинаковый эффект при повторном выполнении. Она обязательна, потому что клиент после таймаута не знает, выполнилась ли операция, а брокеры доставляют at-least-once. Сначала — естественная идемпотентность: `PUT` с клиентским id, установка состояния вместо инкремента, условные обновления, upsert. Для денег и создания сущностей — `Idempotency-Key`, сгенерированный клиентом один раз на намерение.

Сильный ответ опишет серверную часть: уникальный индекс по паре клиент–ключ, хэш тела для обнаружения переиспользования, сохранённый ответ для повторов, `409` на выполняющийся запрос, и всё это — в одной транзакции с бизнес-изменением, а не отдельным `SELECT` или ключом в Redis. Добавит, что внешние вызовы требуют проброса ключа и докатывания зависших операций, консьюмеры — inbox по id сообщения, а клиентские ретраи и hedging нужно согласовать с тем, какие операции сервер действительно умеет повторять.
