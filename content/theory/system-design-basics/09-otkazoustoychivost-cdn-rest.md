Три темы этой статьи всплывают почти в каждом разборе: интервьюер спрашивает «а что будет, если упадёт X?», «как отдавать картинки миллиону пользователей?» и «покажите API». Ни одна из них не требует отдельной архитектуры: отказоустойчивость — свойство всех компонентов сразу, CDN — слой перед origin, а REST API — контракт, с которого удобно начинать разбор после требований.

## Fault tolerance — свойство системы, а не компонент

Отказоустойчивость — способность продолжать корректно работать, когда часть компонентов отказала. Её не добавляют одной библиотекой, она складывается из трёх вещей: избыточности (есть чем заменить отказавшее), изоляции (сбой не распространяется) и аккуратной обработки ошибок на каждом вызове.

**Избыточность** означает, что ни у одного компонента нет единственного экземпляра. Сервисы — несколько реплик в разных зонах доступности, данные — реплицированы: PostgreSQL с автоматическим failover, Kafka с фактором репликации 3, Redis с репликами (см. `Репликация и failover`). Резерв нужен не только по числу узлов, но и по мощности. Прикидка для трёх зон: если одна выпала, оставшиеся две должны принять её трафик, то есть каждая в норме загружена не больше чем на 2/3 своей мощности — это около 50% запаса к обычной нагрузке. Система из трёх подов, каждый на 90% CPU, формально избыточна, но отказ одного из них положит остальные.

**Изоляция** — принцип bulkhead: у каждой зависимости свой пул соединений и свой лимит конкурентности. Медленный сервис рекомендаций не должен съесть все соединения и потоки, нужные для оформления заказа. Без этого частичный отказ превращается в полный: один зависший downstream исчерпывает общие ресурсы.

**Обработка ошибок на вызове** — таймауты на всё, ретраи только для идемпотентных операций и временных ошибок, с экспоненциальным backoff и jitter, и circuit breaker, который перестаёт вызывать падающую зависимость. Детали — в `Retry, jitter и retry storm`, `Timeout budget` и `Circuit breaker`; на собеседовании достаточно показать, что таймаут вызываемого меньше таймаута вызывающего, а ретраи ограничены бюджетом. В .NET это собирается Polly или `Microsoft.Extensions.Http.Resilience`:

```csharp
builder.Services.AddHttpClient<RecommendationsClient>()
    .AddStandardResilienceHandler();
```

Ретраи и повторная доставка из очередей делают **идемпотентность** обязательной: повтор платежа или создания заказа не должен давать дубль (см. `Идемпотентность`). Критичные записи надёжнее проводить через очередь с повторной обработкой и DLQ — упавший обработчик не теряет сообщение.

**Деградация** продумывается заранее для каждой зависимости:

| Зависимость упала | Поведение |
| --- | --- |
| Рекомендации | популярное из кэша |
| Redis | чтение из БД с ограничением конкурентности |
| Уведомления | заказ создаётся, письмо уходит позже |
| Платёжный провайдер | резервный провайдер или отложенная оплата |

Последний слой — защита от перегрузки: rate limiting, load shedding (быстрый 503 вместо очереди до таймаута) и приоритет критичного трафика (см. `Backpressure`).

**Проверка.** Отказоустойчивость, которую никто не проверял, — гипотеза. Chaos engineering убивает поды, вносит сетевые задержки и отключает зону — на стенде или в проде с ограниченным blast radius. Game days отрабатывают аварию с людьми и runbook, а регулярное восстановление из бэкапа подтверждает, что RPO и RTO реальны (см. `RTO/RPO и disaster recovery`).

## CDN: кэш на краю сети

CDN — сеть edge-серверов (PoP), которые держат копии контента рядом с пользователем. Запрос идёт так:

```text
клиент → DNS / anycast → ближайший PoP
  hit  → ответ из кэша edge
  miss → origin shield → origin (S3 или API) → кэш на edge → ответ
```

Организация CDN сводится к трём решениям: что кэшировать и сколько, как инвалидировать и как защитить origin.

**Что отдавать через CDN.** Идеальный случай — статика фронтенда, изображения, видеосегменты HLS/DASH. Дальше — публичные и одинаковые для всех ответы API: каталог, цены, конфигурация, с коротким TTL. Персональные ответы (`/me`, корзина) не кэшируются; через CDN их только проксируют, если нужны TLS termination и WAF на edge. Приватные файлы отдают по подписанным URL или cookie: ссылка с ограниченным сроком жизни, которую выдал бэкенд после проверки прав.

**Заголовки управляют кэшем:**

```text
app.3f9a1c.js   Cache-Control: public, max-age=31536000, immutable
index.html      Cache-Control: no-cache          + ETag
/api/catalog    Cache-Control: public, s-maxage=60, stale-while-revalidate=300
```

Ассеты с хэшем в имени кэшируются на год: новая версия получает новое имя, и инвалидация не нужна. HTML-точка входа ревалидируется по `ETag`, чтобы релиз подхватывался сразу. `s-maxage` задаёт TTL для общих кэшей отдельно от браузера, а `stale-while-revalidate` позволяет отдавать слегка устаревший ответ, пока свежий загружается в фоне.

**Cache key** должен включать только значимые параметры. Utm-метки и лишние заголовки в ключе дробят кэш на тысячи вариантов одного объекта и убивают hit ratio.

**Инвалидация.** Purge по URL или по тегу (surrogate keys) существует, но распространяется по сети от секунд до минут и обычно лимитирован. Поэтому основной механизм — версионирование URL, а purge — для исключений вроде снятого с продажи товара.

**Защита origin.** Без промежуточного слоя каждый PoP ходит за промахом в origin сам: при сотнях PoP один популярный объект после истечения TTL — это сотни одновременных запросов. Origin shield собирает промахи всех edge в один слой, request collapsing склеивает одновременные запросы к одному объекту в один (та же проблема, что в `Cache stampede`). Сам origin для статики — бакет, доступный только CDN, а не открытый в интернет.

**Почему важен hit ratio.** Прикидка: сайт отдаёт 40 Gbps статики. При hit ratio 95% origin обслуживает 40 × 0,05 = 2 Gbps, при 80% — 40 × 0,2 = 8 Gbps, вчетверо больше. Падение на 15 пунктов умножает нагрузку на origin и egress, поэтому hit ratio и трафик origin — главные метрики CDN. Попутно CDN даёт TLS и HTTP/2–3 на edge, сжатие, ресайз изображений на лету, WAF и поглощение DDoS; при очень больших объёмах используют multi-CDN.

## REST API в дизайн-секции

После требований и оценки нагрузки принято показать API — это фиксирует сценарии и сущности. Глубина здесь не нужна, нужна аккуратность.

```text
POST   /api/v1/orders                          создать, Idempotency-Key
GET    /api/v1/orders/{id}                     один заказ
GET    /api/v1/orders?status=paid&cursor=..&limit=50
PATCH  /api/v1/orders/{id}                     частичное изменение, If-Match
POST   /api/v1/orders/{id}/cancel              действие вне CRUD
GET    /api/v1/customers/{id}/orders           вложенный ресурс
```

**Ресурсы и методы.** Существительные во множественном числе, без глаголов в пути, вложенность не глубже двух уровней. GET безопасен и идемпотентен, PUT и DELETE идемпотентны, POST — нет, PATCH — не гарантированно. Действия, не укладывающиеся в CRUD, оформляют подресурсом вроде `/cancel`.

**Коды ответов.** 201 с `Location` при создании, 204 без тела, 400 — невалидный запрос, 401/403 — аутентификация и авторизация, 404, 409 — конфликт состояния, 422 — бизнес-валидация, 429 с `Retry-After`, 5xx — ошибка сервера. Ошибки — в едином формате ProblemDetails (RFC 9457, заменивший RFC 7807): `type`, `title`, `status`, `detail` и `traceId` для поиска в логах.

**Идемпотентность POST.** Клиент генерирует `Idempotency-Key`, сервер сохраняет ключ вместе с результатом первого выполнения и на повтор возвращает тот же ответ. Это связывает API с отказоустойчивостью: без ключа ретрай клиента после таймаута создаёт второй заказ.

**Пагинация.** Offset (`?page=100`) медленный на больших таблицах — `OFFSET 100000` заставляет базу прочитать и выбросить строки — и съезжает при вставках. Для лент и больших списков берут keyset: `WHERE (created_at, id) < (@ts, @id) ORDER BY created_at DESC, id DESC LIMIT 50`, а курсор отдают клиенту непрозрачной строкой. Конкурентные изменения защищают `ETag` и `If-Match`: при несовпадении версии — 412.

**Версионирование и остальное.** Версия в URL проще для кэша и отладки; аддитивные изменения не ломают клиентов, удаление и переименование полей — только в новой версии с периодом deprecation. Плюс rate limiting по клиенту, `limit` на списки, авторизация на уровне ресурса (проверка владельца, а не только роли) и контракт в OpenAPI. Подробнее — `Дизайн API и версионирование` и `Rate limiting`.

REST — не универсальный ответ: для внутренних высоконагруженных вызовов уместен gRPC, для агрегирующих экранов — GraphQL или BFF, для real-time — WebSocket или SSE. Назвать это стоит, если сценарий того требует.

## Что стоит ответить на собеседовании

Отказоустойчивость — это избыточность без единой точки отказа (реплики в нескольких зонах, репликация данных, запас мощности на потерю зоны), изоляция отказов через bulkhead, таймауты, ограниченные ретраи с jitter, circuit breaker, идемпотентность и заранее продуманная деградация. CDN кэширует статику и публичные ответы на edge: ассеты с хэшем в имени и `immutable`, API с `s-maxage`, инвалидация через версионирование URL. REST API строится от ресурсов, с правильными методами и кодами, ProblemDetails, keyset-пагинацией и `Idempotency-Key` для POST.

Сильный ответ покажет связи между темами и цифры. Запас мощности посчитан на потерю зоны, а не просто «три реплики». Ретраи без идемпотентности и бюджета названы источником дублей и retry storm. Отказоустойчивость подтверждается chaos-тестами и game days. Для CDN — объяснит, почему hit ratio с 95% до 80% вчетверо нагружает origin, и как origin shield и request collapsing защищают его от одновременных промахов. А в API — покажет, что повтор клиента после таймаута безопасен благодаря `Idempotency-Key`.
