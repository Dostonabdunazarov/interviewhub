Горизонтальное масштабирование (см. `Вертикальное и горизонтальное масштабирование`) невозможно без компонента, который решает, какой из двадцати одинаковых инстансов обработает очередной запрос. Это балансировщик нагрузки. Он распределяет запросы, перестаёт слать трафик на больные узлы и позволяет выводить узлы из работы без ошибок у клиентов. На схеме он рисуется одним прямоугольником, но за ним стоит несколько решений, о которых любят спрашивать.

## L4 и L7

Балансировщики различают по уровню модели OSI, на котором они принимают решение.

| | L4 (транспортный) | L7 (прикладной) |
| --- | --- | --- |
| Что видит | IP, порт, TCP/UDP-соединение | HTTP: путь, заголовки, cookie |
| Единица балансировки | соединение | запрос |
| Возможности | быстрое проксирование, минимум накладных расходов | маршрутизация по URL, TLS termination, ретраи, rate limiting, сжатие |
| Примеры | AWS NLB, IPVS, MetalLB | NGINX, Envoy, HAProxy, AWS ALB, Kubernetes Ingress |

L4 быстрее и проще, но слеп к содержимому: он не отличит `/api/search` от `/api/health` и не может направить их на разные пулы. L7 разбирает HTTP, а значит, может маршрутизировать по пути и заголовкам, терминировать TLS, добавлять `X-Forwarded-For` и повторять неудачные запросы на соседний бэкенд — ценой CPU и задержки на разбор.

Различие «соединение против запроса» становится критичным для долгоживущих соединений. gRPC работает поверх HTTP/2 и мультиплексирует все запросы клиента в одно соединение. L4-балансировщик распределит соединения, а не запросы, и если клиентов мало, один бэкенд получит почти всю нагрузку, пока остальные простаивают. Для gRPC нужен L7-балансировщик, понимающий HTTP/2, или балансировка на стороне клиента. Та же история с WebSocket: соединение живёт часами, и после добавления новых узлов нагрузка перераспределится только по мере переподключения клиентов.

На больших системах уровни комбинируют: L4 принимает трафик и распределяет его по пулу L7-прокси, а те уже маршрутизируют запросы по сервисам.

```text
клиенты ──► DNS ──► L4 (NLB) ──► L7 (Envoy × N) ──► orders-api × 20
                                              └──► search-api × 8
```

## Алгоритмы распределения

- **Round robin** — по кругу. Хорош, когда запросы однородны по стоимости, а узлы одинаковы по мощности.
- **Weighted round robin** — с весами: для узлов разной мощности или для канареечного релиза, когда новая версия получает 5% трафика.
- **Least connections / least requests** — выбрать узел с наименьшим числом активных запросов. Лучше при разной длительности запросов: медленный узел сам перестаёт получать новые.
- **Power of two choices** — выбрать два случайных узла и отдать запрос менее загруженному. Почти так же хорош, как least connections, но не требует глобального знания о всех узлах, поэтому хорошо работает, когда балансировщиков много. Используется, например, в Envoy.
- **Хеширование по ключу** — запрос с одним и тем же ключом (IP клиента, id сессии, id пользователя) всегда попадает на один узел. Нужен для sticky sessions и для шардированных кэшей.

Простое хеширование по модулю плохо переносит изменение числа узлов. При переходе с 4 узлов на 5 ключ остаётся на месте, только если `k mod 4 == k mod 5`, — а это лишь 4 остатка из каждых 20, то есть 80% ключей переезжает и кэши разом остывают. Consistent hashing размещает узлы и ключи на одном кольце, и при добавлении пятого узла переезжает около 1/5 ключей. Подробнее эта техника разбирается вместе с шардированием в разделе «Данные под нагрузкой».

## Health checks

Балансировщик должен знать, какие узлы здоровы. Проверки бывают двух видов:

- **активные** — периодический запрос на служебный эндпоинт вроде `/health/ready`; узел, не ответивший несколько раз подряд, выводится из ротации;
- **пассивные** (outlier detection) — балансировщик следит за реальными ответами и временно выключает узел, который отдал серию 5xx или таймаутов.

Пассивные проверки ловят то, что активные пропускают: узел отвечает на `/health` за миллисекунду, а реальные запросы обрабатывает с ошибками. Обратная ловушка — health check, который проверяет базу: при её кратковременном сбое балансировщик выкинет из ротации все узлы разом, и частичная деградация превратится в полный отказ. Как разделить liveness и readiness в ASP.NET Core — в статье `Health checks`, а почему «живой, но больной» узел опаснее мёртвого — в разделе «Надёжность».

## Конфигурация на примере NGINX

```nginx
upstream orders_api {
    least_conn;
    server 10.0.1.11:8080 max_fails=3 fail_timeout=10s;
    server 10.0.1.12:8080 max_fails=3 fail_timeout=10s;
    server 10.0.1.13:8080 max_fails=3 fail_timeout=10s weight=2;
    keepalive 64;
}

server {
    listen 443 ssl;
    server_name api.example.com;

    location / {
        proxy_pass http://orders_api;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_next_upstream error timeout;
        proxy_read_timeout 10s;
    }
}
```

Здесь видно сразу несколько решений: `least_conn` вместо round robin, пассивная проверка через `max_fails`, вдвое больший вес у мощного узла, пул keep-alive-соединений к бэкендам вместо нового TCP-рукопожатия на каждый запрос, TLS терминируется на балансировщике.

`proxy_next_upstream` — повтор на соседнем узле — заслуживает осторожности. Повтор безопасен для `GET`, но для `POST /orders` он может создать два заказа, если первый узел успел записать заказ и упал до ответа. NGINX по умолчанию не повторяет неидемпотентные методы (для этого нужен явный флаг `non_idempotent`), но другие прокси и клиентские библиотеки ведут себя по-разному. Поэтому ретраи либо ограничивают идемпотентными методами, либо делают сами операции идемпотентными по ключу — эта тема подробно разбирается в разделе «Надёжность».

Приложение за L7-балансировщиком видит IP балансировщика, а не клиента, и схему `http` вместо `https`. В ASP.NET Core это исправляет `UseForwardedHeaders` с явным списком доверенных прокси — иначе неверными окажутся логи, rate limiting по IP и генерация ссылок.

## Sticky sessions

Привязка клиента к узлу — через cookie, выставленную балансировщиком, или хеш по IP. Она упрощает жизнь stateful-приложению, которое держит сессию в памяти, но создаёт проблемы:

- нагрузка распределяется неравномерно — «тяжёлые» клиенты концентрируются на одном узле;
- при падении узла его сессии теряются;
- при добавлении узлов новые получают только новых клиентов.

Поэтому sticky sessions — скорее костыль для унаследованного кода. Правильный путь — stateless-сервис с состоянием в Redis. Оправданное применение у привязки есть там, где узел держит локальное состояние ради скорости: шардированный кэш или игровая сессия.

## Балансировщик не должен быть единой точкой отказа

Если перед двадцатью узлами стоит один NGINX, отказоустойчивость системы равна отказоустойчивости этого NGINX. Варианты:

- **пара в active-passive с общим виртуальным IP** (keepalived/VRRP): при падении активного адрес переезжает на резервный за секунды;
- **managed-балансировщик облака**, который сам по себе распределён по зонам;
- **DNS перед несколькими балансировщиками** — несколько A-записей или GeoDNS, отправляющий пользователя в ближайший регион.

DNS-балансировка грубая: клиенты и резолверы кэшируют ответ на время TTL, а иногда и дольше, поэтому быстро увести трафик с упавшего адреса не получится. Её используют на верхнем уровне — между регионами, — а внутри региона работают обычные балансировщики.

## Вывод узла из работы

При деплое или уменьшении числа узлов балансировщик должен перестать слать новые запросы на узел, но дать ему доработать текущие — это connection draining. Со стороны приложения ему помогает корректная обработка `SIGTERM`: перестать отвечать готовностью, дождаться завершения запросов и только потом выйти (см. `Graceful shutdown`). Без этого каждый деплой — это всплеск 502 у пользователей.

## Что стоит ответить на собеседовании

Балансировщик распределяет запросы между инстансами, выводит из ротации больные узлы и делает возможным горизонтальное масштабирование. L4 работает с соединениями и не видит HTTP — быстрый и простой; L7 видит запросы — умеет маршрутизировать по пути, терминировать TLS и ретраить. Алгоритмы: round robin для однородных запросов, least connections для разной длительности, power of two choices как дешёвое приближение, хеширование для привязки ключа к узлу.

Сильный ответ добавит нюансы: L4 плохо балансирует gRPC, потому что все запросы клиента идут по одному HTTP/2-соединению; health check, проверяющий общую базу, выкинет все узлы разом; ретраи на балансировщике опасны для неидемпотентных операций; sticky sessions ломают равномерность и failover; а сам балансировщик резервируют парой с общим VIP или берут managed-вариант, распределённый по зонам.
