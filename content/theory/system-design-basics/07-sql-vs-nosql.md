«SQL или NoSQL?» — один из самых частых вопросов дизайн-секции, и один из самых коварных: он провоцирует ответить предпочтением. Правильный ответ строится не от технологии, а от паттерна доступа к данным, требований к согласованности и цифр нагрузки. На практике выбор обычно звучит так: PostgreSQL по умолчанию, другое хранилище — точечно, под конкретную измеримую причину.

## Что отличает реляционную базу

SQL-базы (PostgreSQL, MySQL) хранят данные в таблицах со строгой схемой, связанных внешними ключами, и дают три вещи, ради которых их выбирают:

- **произвольные запросы** — JOIN, агрегаты, фильтры по любым колонкам, в том числе запросы, о которых при проектировании никто не думал;
- **ACID-транзакции через много строк и таблиц** — списать остаток, создать заказ и записать платёж атомарно;
- **ограничения целостности** — внешние ключи, уникальность, `CHECK`, которые база гарантирует независимо от кода.

Цена — масштабирование записи. Пишет один primary; чтение масштабируется репликами, запись — только вертикально, а дальше — шардированием, которое реляционная база сама не делает (см. `Вертикальное и горизонтальное масштабирование`).

## NoSQL — это четыре разных инструмента

Слово «NoSQL» объединяет системы с очень разными моделями, и сравнивать с SQL «NoSQL вообще» бессмысленно:

- **Key-value** (Redis, DynamoDB) — доступ строго по ключу, минимальная задержка. Кэш, сессии, счётчики, rate limiting.
- **Документные** (MongoDB) — вложенные документы с переменной структурой, выборка по полям документа.
- **Wide-column** (Cassandra, ScyllaDB) — огромная запись, данные партиционированы по ключу и отсортированы внутри партиции. Масштаб записи растёт почти линейно с числом узлов.
- **Графовые** (Neo4j) — обход связей на много шагов: «друзья друзей», рекомендации, анализ мошеннических цепочек.

Общее у большинства из них одно: они отказываются от части гарантий реляционной модели — произвольных запросов, межсущностных транзакций, строгой согласованности по умолчанию — ради горизонтального масштабирования или специфичного паттерна доступа.

## Сравнение

| | SQL | NoSQL (в целом) |
| --- | --- | --- |
| Модель | таблицы, связи, нормализация | ключ-значение, документы, колонки, граф |
| Схема | строгая, меняется миграциями | гибкая, но фактически живёт в коде |
| Запросы | произвольные, JOIN, агрегаты | по заранее спроектированному ключу |
| Транзакции | ACID через таблицы | обычно в пределах записи или партиции |
| Согласованность | строгая по умолчанию | часто настраиваемая или eventual |
| Масштаб записи | один primary, дальше шардирование вручную | встроенное партиционирование |

Строка «схема» заслуживает отдельного комментария. «Возьмём MongoDB, чтобы не думать о схеме» — анти-паттерн: схема никуда не девается, она переезжает из базы в код, и вместо одной миграции появляется код, который умеет читать все версии документа, когда-либо записанные.

## Моделирование от запроса

Принципиальная разница в том, как проектируются данные. В реляционной базе сначала моделируют сущности, а запросы пишут потом. В wide-column — наоборот: сначала перечисляют запросы, и под каждый создают свою таблицу.

```sql
CREATE TABLE messages_by_chat (
    chat_id    uuid,
    bucket     int,
    message_id timeuuid,
    sender_id  uuid,
    body       text,
    PRIMARY KEY ((chat_id, bucket), message_id)
) WITH CLUSTERING ORDER BY (message_id DESC);
```

Это CQL, язык Cassandra. Ключ партиции `(chat_id, bucket)` определяет узел, где лежат данные; `message_id` сортирует сообщения внутри партиции. Запрос «последние 50 сообщений чата» — одно чтение с одного узла. А вот запрос «все сообщения пользователя за неделю» этой таблицей не обслуживается вообще: для него нужна вторая таблица с другим ключом партиции, и приложение пишет в обе. `bucket` (например, номер месяца) нужен, чтобы партиция активного чата не росла бесконечно.

Это и есть плата за масштаб: каждый новый тип запроса — новая денормализованная таблица и двойная запись.

## Цифры, которые меняют выбор

Возьмём две системы и посчитаем их так, как это делается в статье `Оценка нагрузки и RPS`.

```text
лента с публикациями:
  20M DAU × 0.5 поста = 10M записей/день ≈ 116 в секунду, пик ≈ 350
  объём ≈ 1.8 TB/год

мессенджер:
  50M DAU × 40 сообщений = 2B записей/день ≈ 23 000 в секунду, пик ≈ 70 000
  сообщение ≈ 200 B → 400 GB/день ≈ 146 TB/год, без индексов и реплик
```

Первая система — одна PostgreSQL с репликами на годы вперёд. Вторая — 70 тысяч записей в секунду и сотни терабайт в год при простом доступе по ключу `chat_id`: одному primary это не по силам, и wide-column store с партиционированием по чату здесь естественный выбор. Обе задачи «про посты», но цифры дают разные ответы.

## Когда SQL

- важна целостность: деньги, остатки, заказы, бронирования;
- запросы заранее неизвестны или будут меняться — отчёты, админка, аналитика по ходу жизни продукта;
- нужны транзакции через несколько сущностей;
- данные помещаются в единицы терабайт — это подавляющее большинство систем.

## Когда NoSQL

- запись в десятки и сотни тысяч операций в секунду, которую один primary не вытянет;
- десятки и сотни терабайт с простым доступом по ключу — сообщения, события, телеметрия;
- явно нужна запись в нескольких регионах с высокой доступностью;
- кэш и эфемерные данные — Redis.

## Граница размыта

Современные системы давно заходят на территорию друг друга. PostgreSQL хранит документы в JSONB с индексами и закрывает многие сценарии документной базы:

```sql
CREATE TABLE products (
    id    bigint PRIMARY KEY,
    attrs jsonb  NOT NULL
);

CREATE INDEX ix_products_attrs ON products USING gin (attrs jsonb_path_ops);

SELECT id FROM products WHERE attrs @> '{"color": "red", "size": "M"}';
```

Атрибуты товаров разных категорий не влезают в одну таблицу с фиксированными колонками, но остальная модель — заказы, остатки, цены — реляционная, и всё это остаётся в одной базе с транзакциями. Про GIN-индексы подробнее — в статье `Индексы: B-tree, GIN, BRIN`.

С другой стороны, MongoDB умеет многодокументные транзакции, а распределённые SQL-базы (CockroachDB, YugabyteDB, Citus поверх PostgreSQL) дают SQL с горизонтальным масштабированием — ценой задержки на распределённых транзакциях и операционной сложности.

## Polyglot persistence

Зрелая система редко живёт на одной базе. Типичная картина:

```text
PostgreSQL     источник истины: заказы, пользователи, платежи
Redis          кэш, сессии, rate limiting
Elasticsearch  полнотекстовый поиск и фасеты
ClickHouse     аналитика по миллиардам строк
S3             файлы и медиа
Kafka          журнал событий между сервисами
```

Цена — синхронизация. Данные в производные хранилища доставляются через CDC или outbox и событийную шину, и согласованы они только в конечном счёте: поиск может несколько секунд не видеть нового товара. Как надёжно доставлять изменения — тема разделов «Микросервисы» и «Kafka и очереди», а что значит «в конечном счёте» и какие бывают модели согласованности — раздела «Согласованность».

Обратный анти-паттерн — держать в одной OLTP-базе всё подряд, включая логи и аналитические запросы, которые вытесняют рабочий набор из памяти и убивают транзакционную нагрузку.

## Что стоит ответить на собеседовании

SQL-базы дают строгую схему, произвольные запросы с JOIN и ACID-транзакции через таблицы, но запись масштабируется только вертикально и шардированием. NoSQL — это разные инструменты: key-value для доступа по ключу, документные для вложенных структур, wide-column для огромной записи с партиционированием, графовые для обходов связей; они жертвуют частью гарантий ради масштаба или специфичного доступа. Выбор определяется паттерном доступа, требованиями к согласованности и цифрами нагрузки.

Сильный ответ покажет выбор на числах: 350 записей в секунду и пара терабайт в год — PostgreSQL, 70 000 записей в секунду и сотни терабайт с доступом по одному ключу — wide-column. Объяснит, что в wide-column данные моделируют от запроса, и каждый новый запрос — новая таблица. Упомянет, что граница размыта (JSONB, распределённый SQL), и что практический дефолт — PostgreSQL как источник истины плюс специализированные хранилища точечно, с eventual consistency между ними.
