Ресурсы пода выглядят как две строчки YAML, но за ними стоят два совершенно разных механизма ядра. Память — несжимаемый ресурс: её превышение заканчивается убийством процесса. CPU — сжимаемый: превышение даёт не падение, а паузу. .NET-сервис при этом не пассивный потребитель: рантайм сам читает лимиты контейнера и по ним решает, сколько куч заводить сборщику, сколько потоков держать в пуле и какого размера может быть куча. Если лимиты и рантайм не согласованы, получаются два классических инцидента — `OOMKilled` и необъяснимые скачки латентности при низкой загрузке CPU.

## Что делают requests и limits

| Параметр | Механизм на узле | Что при превышении |
| --- | --- | --- |
| `requests.cpu` | учитывается планировщиком, вес в cgroup (`cpu.weight`) | ничего: это гарантированная доля при конкуренции |
| `limits.cpu` | квота CFS на период 100 мс (`cpu.max`) | троттлинг до конца периода |
| `requests.memory` | учитывается планировщиком и при вытеснении | под вытесняется раньше других при нехватке памяти на узле |
| `limits.memory` | `memory.max` в cgroup | OOM killer, `OOMKilled`, код выхода 137 |

Requests — это обещание планировщику: под ставится только на узел, где сумма requests помещается. Limits — потолок, который применяет ядро. Из соотношения складывается QoS-класс пода: **Guaranteed** (requests равны limits по CPU и памяти у всех контейнеров) вытесняется последним, **Burstable** — типичный выбор для API, **BestEffort** без ресурсов вообще — первый кандидат на вылет.

Рабочая схема для большинства .NET-сервисов:

```yaml
resources:
  requests:
    cpu: "500m"
    memory: "768Mi"
  limits:
    memory: "768Mi"
```

Память — request равен limit: под получает ровно то, что гарантировано, и не вытесняется из-за того, что занял больше обещанного. CPU — честный request по реальному потреблению и без limit либо с большим запасом. Почему так, видно из того, как работает каждый механизм.

## Память: куча — не весь процесс

Рантайм видит memory limit контейнера и по умолчанию отдаёт управляемой куче 75% от него — это `GCHeapHardLimit`. Оставшиеся 25% нужны всему, что живёт вне кучи: стекам потоков, коду JIT, нативным буферам Kestrel и TLS, `MemoryMappedFile`, нативным библиотекам вроде SkiaSharp и драйверов БД.

Отсюда два разных отказа, которые важно различать:

- **`OutOfMemoryException` в логах** — куча упёрлась в свой лимит раньше контейнера. Процесс жив, исключение можно поймать, дамп можно снять. Это хороший исход.
- **`OOMKilled` в `kubectl describe pod`** — ядро убило процесс по RSS всего контейнера. Никаких логов и дампов, только `Last State: Terminated, Reason: OOMKilled` и код 137.

Второй случай означает, что выросло что-то вне кучи или 25% не хватило: нативная память мимо GC (незакрытые `SslStream`, интероп), сотни потоков из-за синхронных блокировок в async-коде, второй процесс в том же контейнере, который делит лимит. Долю кучи можно сдвинуть:

```yaml
env:
  - name: DOTNET_GCHeapHardLimitPercent
    value: "0x46"
```

Числовые значения `DOTNET_GC*` рантайм читает как шестнадцатеричные, префикс `0x` необязателен. `0x46` — это 70%, а `46` без префикса тоже будет 70%, а не 46. Проверено на .NET 10: `DOTNET_GCHeapHardLimit=10000000` дало кучу ровно в 256 МБ, то есть `0x10000000` байт. Классическая ошибка — написать `70` и получить 112%.

Понижение доли кучи полезно не только для запаса: если куча упрётся в лимит раньше контейнера, вы получите `OutOfMemoryException` с дампом вместо безмолвного `OOMKilled`. Этот приём для диагностики описан в статье `Анализ дампа`.

## CPU: квота, а не ядра

`limits.cpu: 1` не означает «одно ядро». Это 100 мс процессорного времени на каждый период CFS длиной 100 мс, и тратить их можно на любом количестве ядер параллельно:

```text
limits.cpu = 1    квота 100 мс на период 100 мс
8 потоков параллельно    квота исчерпана за 12.5 мс
оставшиеся 87.5 мс    процесс не получает CPU совсем
запрос в этот момент    +87.5 мс к латентности
```

Средняя загрузка за минуту при этом может быть 30–40%, и дашборд «CPU usage» не покажет ничего подозрительного. Смотреть нужно на долю периодов, в которых процесс был заторможен:

```text
sum(rate(container_cpu_cfs_throttled_periods_total{pod=~"orders-api-.*"}[5m]))
/
sum(rate(container_cpu_cfs_periods_total{pod=~"orders-api-.*"}[5m]))
```

Для API доля выше 10–20% — сигнал, что limit мешает. Именно поэтому многие команды убирают CPU limit у латентно-чувствительных сервисов и оставляют только честный request: CPU берётся из свободного на узле, а гарантию даёт `cpu.weight`. Риск — шумные соседи, поэтому request должен отражать реальное потребление, иначе планировщик переупакует узел.

## Как .NET видит CPU

Рантайм читает квоту cgroup и выставляет `Environment.ProcessorCount` равным limit с округлением вверх: `1500m` даёт 2. От этого числа зависит многое:

- **Server GC** заводит кучу и поток сборки на каждый процессор;
- **ThreadPool** стартует с минимумом потоков, равным `ProcessorCount`;
- **параллельные сборщики** при паузе работают одновременно и сами расходуют квоту.

Ловушка — отсутствие CPU limit. Тогда квоты нет, и рантайм видит все ядра узла: на 64-ядерной машине Server GC готов завести 64 кучи в поде, рассчитанном на одно-два ядра. Сборка запускает десятки потоков разом, они съедают долю CPU, а при наличии квоты — выедают её за миллисекунды, и пауза в 5 мс растягивается на несколько периодов CFS. С .NET 9 по умолчанию включён DATAS: Server GC стартует с одной кучи и добавляет их по нагрузке, что сильно смягчает проблему, но не отменяет того, что потолок определяется размером узла, а не пода.

Поэтому без CPU limit число процессоров задают явно:

```yaml
env:
  - name: DOTNET_PROCESSOR_COUNT
    value: "2"
  - name: DOTNET_GCHeapCount
    value: "2"
```

`DOTNET_PROCESSOR_COUNT` меняет `Environment.ProcessorCount` для всего рантайма и, в отличие от настроек GC, читается как десятичное: на .NET 10 значение `10` дало ровно 10 процессоров. `DOTNET_GCHeapCount` ограничивает только кучи GC и шестнадцатеричный — `10` там означало бы 16. Для однозначности удобно держать такие значения меньше десяти.

Выбор между Server и Workstation GC в маленьком поде — отдельная развилка. При лимите в 1 CPU и меньше Server GC теряет смысл, и Workstation часто лучше по памяти и латентности; при 2–4 CPU их сравнивают нагрузочным тестом. Как работают режимы — в статье `Как работает GC`, как понять, что проблема в сборщике, — в `Диагностика высокого GC`. Переключается режим без пересборки:

```yaml
env:
  - name: DOTNET_gcServer
    value: "0"
```

## Что ещё страдает от маленького лимита

**Старт.** Первые секунды tiered compilation активно компилирует методы фоновыми потоками. При лимите в полядра старт растягивается в разы, startup-проба не успевает, и под уходит в перезапуск. Помогают ReadyToRun (`<PublishReadyToRun>true</PublishReadyToRun>`) и честный бюджет у startup-пробы — см. `Readiness vs liveness`.

**ThreadPool.** При `ProcessorCount = 1` и синхронных блокировках пул наращивает потоки медленно, и голодание пула выглядит в точности как троттлинг. Отличить их можно по метрике троттлинга и длине очереди пула.

**TLS.** Рукопожатия дорогие по CPU, и при всплеске новых соединений упираются в квоту первыми.

## Как подобрать числа

Числа не угадывают, а снимают нагрузочным тестом и из продакшена:

- **memory limit** — пиковый working set контейнера (`container_memory_working_set_bytes`) плюс 20–30% запаса;
- **CPU request** — около p90 реального потребления, чтобы планировщик раскладывал поды честно;
- **CPU limit**, если он нужен, — кратно выше request, а не 1:1, кроме случаев, когда требуется Guaranteed QoS, например для CPU Manager со static policy.

Полезно записывать в лог при старте то, что рантайм увидел на самом деле, — это снимает половину вопросов при разборе:

```csharp
var gc = GC.GetGCMemoryInfo();
logger.LogInformation(
    "server={Server} cpus={Cpus} heapLimit={HeapMb} MB",
    GCSettings.IsServerGC, Environment.ProcessorCount, gc.TotalAvailableMemoryBytes >> 20);
```

`TotalAvailableMemoryBytes` показывает именно лимит кучи с учётом контейнера и настроек, а не память узла.

И отдельно об автоскейлинге: VPA в режиме рекомендаций хорошо подсказывает requests, но одновременно с HPA по той же метрике CPU их не используют — они начинают тянуть в разные стороны.

## Что стоит ответить на собеседовании

Память несжимаемая: превышение limit — `OOMKilled`, поэтому для памяти request ставят равным limit. CPU сжимаемый: превышение limit — троттлинг квоты CFS, который даёт скачки p99 при умеренной средней загрузке, поэтому для API часто оставляют честный request без limit или с большим запасом. Троттлинг видно по `container_cpu_cfs_throttled_periods_total`, а не по графику использования CPU.

Сильный ответ свяжет это с рантаймом: куча по умолчанию получает 75% memory limit, остальное — нативной памяти, и `OutOfMemoryException` отличается от `OOMKilled` тем, где сработал лимит. `ProcessorCount` берётся из CPU limit с округлением вверх, а без limit рантайм видит все ядра узла, поэтому Server GC и ThreadPool надо ограничить через `DOTNET_PROCESSOR_COUNT` или `DOTNET_GCHeapCount`. И напомнит, что значения `DOTNET_GC*` шестнадцатеричные: 70% — это `0x46`.
