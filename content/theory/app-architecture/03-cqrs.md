«Мы используем CQRS» — одна из самых неоднозначных фраз на собеседовании. За ней может стоять что угодно: от папок `Commands` и `Queries` с MediatR над одной базой до отдельного Elasticsearch, наполняемого событиями из Kafka. Между этими вариантами — разница в сложности на порядок, и первый уточняющий вопрос интервьюера обычно «какой именно CQRS». Эта статья — про то, как отвечать на него и как решать, сколько CQRS нужно конкретному сервису.

## Команды меняют, запросы читают

Идея выросла из принципа CQS Бертрана Мейера: метод либо меняет состояние и ничего не возвращает, либо возвращает данные и ничего не меняет. CQRS (Command Query Responsibility Segregation) переносит это с уровня метода на уровень модели: **запись и чтение обслуживают разные модели**, потому что требования к ним разные.

У записи — инварианты, транзакции, проверка прав, конкурентный доступ. Ей нужна богатая модель: агрегат, который не даст отменить отгруженный заказ. У чтения — экраны, фильтры, сортировки, поиск, данные из нескольких агрегатов сразу. Ему нужны плоские DTO ровно под экран. Одна модель, растянутая в обе стороны, портится: агрегаты обрастают свойствами для отображения, а запросы списков тянут полные сущности с навигациями.

## Четыре уровня

| Уровень | Что разделено | Согласованность | Сложность |
| --- | --- | --- | --- |
| 1. Разделение кода | команды и запросы — разные обработчики, одна база, одна схема | сильная | почти бесплатно |
| 2. Разные модели, одна база | запись через агрегаты EF Core, чтение — проекции, SQL, view | сильная | умеренная |
| 3. Отдельное хранилище чтения | read-модель в Elasticsearch, Redis, отдельной базе, синхронизация событиями | eventual | высокая |
| 4. CQRS + Event Sourcing | запись — поток событий, чтение — проекции из него | eventual | максимальная |

Большинству систем хватает первых двух уровней. Скачок сложности — между вторым и третьим: там появляется асинхронная синхронизация, а с ней задержка, которую видит пользователь.

## Уровни 1–2 в коде

Команда загружает агрегат, вызывает доменный метод и сохраняет — правила проверяются только здесь:

```csharp
public sealed record CancelOrder(Guid OrderId, string Reason);

public sealed class CancelOrderHandler(ShopDbContext db)
{
    public async Task<long> HandleAsync(CancelOrder command, CancellationToken ct)
    {
        var order = await db.Orders.SingleAsync(o => o.Id == command.OrderId, ct);
        order.Cancel(command.Reason);
        await db.SaveChangesAsync(ct);
        return order.Version;
    }
}
```

Запрос не трогает агрегаты вовсе. Он собирает ровно то, что нужно экрану, тем инструментом, который удобнее, — проекцией EF или Dapper:

```csharp
public sealed record OrderListItem(Guid Id, string CustomerName, int ItemsCount, decimal Total, string Status);

public sealed class CustomerOrdersQuery(IDbConnection connection)
{
    public Task<IEnumerable<OrderListItem>> ExecuteAsync(Guid customerId, CancellationToken ct) =>
        connection.QueryAsync<OrderListItem>(new CommandDefinition("""
            SELECT o.id AS Id, c.name AS CustomerName, count(l.id)::int AS ItemsCount,
                   o.total AS Total, o.status AS Status
            FROM orders o
            JOIN customers c ON c.id = o.customer_id
            LEFT JOIN order_lines l ON l.order_id = o.id
            WHERE o.customer_id = @customerId
            GROUP BY o.id, c.name
            ORDER BY o.created_at DESC
            LIMIT 50
            """, new { customerId }, cancellationToken: ct));
}
```

Обе стороны работают с одной базой в одной транзакционной реальности: пользователь сразу видит свои изменения. Если запросов много и они тяжёлые, второй уровень расширяется без смены согласованности: view или денормализованная таблица, обновляемая в той же транзакции, что и запись. Чтение можно увести на реплику — но это уже маленький шаг к третьему уровню, потому что реплика отстаёт (см. `Репликация и failover`).

Разделение на `Commands` и `Queries` часто делают через MediatR, но это лишь способ диспетчеризации, а не сам CQRS. Обработчики можно вызывать и напрямую; риски медиатора разобраны в `Mediator и его риски`.

## Отдельное хранилище чтения

Третий уровень оправдан, когда чтению нужна другая технология или другой масштаб: полнотекстовый поиск с фасетами, ленты, дашборды, данные из нескольких сервисов в одной таблице, чтение, которое должно жить, когда запись деградировала. Схема при этом такая:

```text
команда → агрегат → PostgreSQL + outbox (одна транзакция)
                         ↓
                  издатель → Kafka → обработчик проекции → read-модель
                                                              ↑
                                                          запросы
```

Outbox нужен, чтобы событие не потерялось между коммитом и отправкой (см. `Outbox`). Обработчик проекции обязан быть идемпотентным и устойчивым к повторам и перестановкам: доставка at-least-once, и одно событие может прийти дважды. Простой способ — версия агрегата в read-модели:

```csharp
public sealed record OrderStatusChanged(Guid OrderId, long Version, string Status, DateTimeOffset OccurredAt);

public sealed class OrderListProjection(IDbConnection readDb)
{
    public Task ApplyAsync(OrderStatusChanged e, CancellationToken ct) =>
        readDb.ExecuteAsync(new CommandDefinition("""
            UPDATE order_list_view
            SET status = @Status, version = @Version, updated_at = @OccurredAt
            WHERE order_id = @OrderId AND version < @Version
            """, e, cancellationToken: ct));
}
```

Повтор и устаревшее событие просто ничего не меняют. Но условие `version <` не заметит пропуска: если событие с версией 5 потерялось, а пришло 6, проекция молча перескочит. Где это важно, проверяют строго `version = @Version - 1` и при расхождении останавливают обработку раздела и поднимают алерт.

## Что приносит третий уровень

- **Задержка.** Пользователь сохранил — и не видит изменений в списке. Это проектируется: команда возвращает новую версию, клиент обновляет экран локально или передаёт версию в запрос, а карточку «только что изменённого» читают из модели записи. Подробно — в `Read-your-writes`.
- **Расхождение навсегда.** Неправильно обработанное событие оставляет read-модель неверной, пока кто-то не заметит. Нужны сверка и инструмент повторной синхронизации.
- **Пересборка проекций.** Новое поле в read-модели требует пересчёта по всей истории. Нужен источник (лог событий или полная выгрузка) и процедура: строим новую таблицу параллельно, догоняем поток, переключаем чтение.
- **Мониторинг.** Метрика `projection_lag` — время от события до его применения — с алертом по SLO.
- **Код и отладка.** Каждый сценарий — команда, событие, проекция, запрос; вопрос «почему в списке старая цена» требует смотреть в три места.
- **Правило:** инварианты проверяются только по модели записи. Читать read-модель внутри команды нельзя — она может отставать.

## CQRS и Event Sourcing — разные вещи

Их часто называют вместе, но они независимы. CQRS без Event Sourcing — нормальная и самая частая форма: запись хранит текущее состояние, а события только синхронизируют чтение. Event Sourcing без отдельных read-моделей почти не встречается: восстанавливать состояние из событий для каждого списка слишком дорого, так что ES тянет за собой CQRS, но не наоборот. Event Sourcing нужен, когда история изменений — сама бизнес-ценность (учёт, финансы, сложные жизненные циклы), а не ради «аудита», который решается таблицей истории.

## Признаки ненужного CQRS

- read-модель — копия таблицы записи один в один;
- на каждую команду ровно один экран с теми же полями;
- нагрузка в сотни RPS, с которыми одна база с индексами справляется без усилий;
- команда тратит больше времени на синхронизацию проекций, чем на бизнес-фичи.

Практичный путь — начинать с уровней 1–2 и выносить отдельную read-модель для конкретного тяжёлого сценария, когда метрики показали проблему, а не для всего сервиса сразу.

## Что стоит ответить на собеседовании

CQRS — разделение моделей записи и чтения, потому что у них разные требования: запись защищает инварианты через агрегаты, чтение отдаёт плоские DTO под экран. Важно уточнить уровень: раздельные обработчики над одной базой почти бесплатны; разные модели в одной базе (агрегаты для команд, проекции и Dapper для запросов) дают выгоду при сильной согласованности; отдельное хранилище чтения с синхронизацией через outbox и брокер приносит eventual consistency, идемпотентные проекции, пересборку, мониторинг отставания и проектирование read-your-writes.

Сильный ответ добавит, что CQRS не равен MediatR и не требует Event Sourcing, что инварианты проверяются только по модели записи, и назовёт признаки лишнего CQRS — read-модель как копия таблицы и нагрузка, с которой справляется одна база. Начинать стоит с первых двух уровней и выносить read-модель точечно, по метрикам.
