Интерфейс на каждый класс, `BaseService<T>` «чтобы не повторяться», общий метод с шестью параметрами — всё это появляется из лучших побуждений: сделать код гибким заранее. Проблема в том, что гибкость угадывают до того, как стало известно, в какую сторону система будет меняться. Угаданная абстракция чаще мешает, чем помогает: на неё завязываются новые места, каждое добавляет условие, и через год её страшно трогать. На собеседовании этот вопрос проверяет инженерную зрелость — умение не только строить абстракции, но и отказываться от них.

## Как она выглядит

Главный критерий: хорошая абстракция **убирает знание** из вызывающего кода. Преждевременная просто добавляет слой, через который это знание всё равно приходится протаскивать. Узнаётся она по характерным признакам:

- **Одна реализация и нет второй в планах.** `INotificationSender` с единственной `EmailNotificationSender` два года подряд.
- **Интерфейс повторяет класс.** Методы один в один, включая детали технологии: `IBlobStorage.GetBlobContainer`, `IDataService.ExecuteSqlAsync`. Абстракция не скрывает, что под ней, — она просто дублирует сигнатуры.
- **Протекание деталей.** Чтобы пользоваться «хранилищем» правильно, нужно знать, что это S3 и листинг по префиксу дорогой.
- **Изменения ходят парами.** Каждая правка меняет и интерфейс, и реализацию — граница проведена не там.
- **Имя из словаря паттернов**, а не из предметной области: `IProcessor`, `IHandlerFactoryProvider`, `BaseManager<T>`.
- **«Для гибкости» без сценария.** На вопрос «какое изменение станет проще?» нет конкретного ответа.

## Флаги — следы ложного обобщения

Самый узнаваемый симптом — метод, который был общим для двух сценариев, а потом каждый новый вызывающий добавлял свой параметр:

```csharp
public static decimal CalculateFee(Order order, bool isPartner, bool isInternational,
    bool applyPromo, bool legacyRounding, FeeMode mode)
```

Внутри — ветвление по всем комбинациям, половина из которых не встречается в реальности, а `FeeMode.Default` передаёт половина вызовов просто потому, что надо что-то передать. Флаги говорят, что общего у сценариев было меньше, чем казалось. Честнее разделить метод обратно на явные и вынести только то, что действительно общее:

```csharp
public static class Fees
{
    private const decimal BaseRate = 0.03m;

    public static decimal ForCustomer(Order order) =>
        Round(order.Total * BaseRate + CrossBorderSurcharge(order));

    public static decimal ForPartner(Order order, decimal partnerRate) =>
        Round(order.Total * partnerRate);

    private static decimal CrossBorderSurcharge(Order order) =>
        order.IsInternational ? 150m : 0m;

    private static decimal Round(decimal fee) =>
        Math.Round(fee, 2, MidpointRounding.AwayFromZero);
}
```

Каждый метод читается без таблицы истинности, а изменение партнёрской комиссии не может случайно задеть клиентскую.

## Неправильная абстракция дороже дублирования

Дублирование видно и локально. Два похожих куска лежат рядом, их легко сравнить и объединить потом — когда станет понятно, что у них общее на самом деле. Неправильная абстракция распространяется: каждое новое место, которое на неё опирается, повышает цену отказа. Сэнди Метц сформулировала это как «дублирование гораздо дешевле неправильной абстракции», и типичная траектория подтверждает её почти дословно:

1. Разработчик видит повтор и выделяет общий метод.
2. Появляется сценарий «почти такой же» — добавляется параметр.
3. Следующий разработчик видит абстракцию и считает, что обязан ей пользоваться, — добавляет ещё условие.
4. Через год код понимает только автор, а изменить его боятся все.

Поэтому правильная реакция на шаге 2 — не новый флаг, а вопрос: а это всё ещё одна сущность?

## Когда абстракция окупается

Это не призыв к коду без интерфейсов. Есть места, где абстракция окупается почти всегда:

- **Граница с внешним миром**: база, сеть, брокер, сторонние SDK. Там нужна изоляция для тестов и защита от чужих изменений.
- **Недетерминированность**: время, случайность, идентификаторы. Для времени в .NET 8 есть готовый `TimeProvider` — самописный `IClock` больше не нужен:

```csharp
public sealed class OverdueChecker(TimeProvider time)
{
    public bool IsOverdue(Invoice invoice) => time.GetUtcNow() > invoice.DueAt;
}
```

- **Несколько реализаций уже сейчас**: провайдеры оплаты, стратегии доставки.
- **Контракт между командами или модулями**, которым нужна независимая эволюция.
- **Известный сценарий изменения**: «в следующем квартале подключаем второго провайдера» — причина; «вдруг когда-нибудь» — нет.

Для обобщения внутри кода работает **правило трёх**: первый раз пишем, второй — замечаем повтор и терпим, третий — обобщаем, глядя на три реальных случая, а не на один и фантазию.

## Альтернативы интерфейсу

Даже когда нужна точка подмены, интерфейс — не единственный и не всегда лучший вариант:

- **Делегат.** Если зависимость — одна операция, `Func` проще интерфейса с одной реализацией:

```csharp
public sealed class ReportExporter(Func<string, Stream, CancellationToken, Task> upload)
{
    public async Task ExportAsync(string name, byte[] content, CancellationToken ct)
    {
        using var stream = new MemoryStream(content);
        await upload($"reports/{name}", stream, ct);
    }
}
```

- **Данные вместо зависимости.** Вместо `ICurrentUser` внутри доменного метода — параметр `Guid userId`. Метод становится чистым, абстракция не нужна вовсе.
- **Конкретный класс.** Калькуляторы, валидаторы и маппинг без ввода-вывода быстрые и детерминированные; в тестах их создают настоящими.
- **Интерфейс потом.** Выделение интерфейса из класса — автоматический рефакторинг в IDE. Если через полгода понадобится вторая реализация, это займёт минуты.

Последний пункт — главный аргумент против «на всякий случай»: стоимость отложенного решения внутри одного кодового репозитория почти нулевая. Исключение — публичные API библиотек и межсервисные контракты: их изменение дорого, и там думают заранее. Но и там лучше начинать с минимального контракта и расширять его, чем угадывать максимальный.

## Как откатить лишнее обобщение

Неправильную абстракцию не чинят ещё одним параметром. Порядок обратный:

1. **Встроить её обратно** (inline) во все вызывающие места — IDE делает это механически, а тесты держат поведение.
2. **Посмотреть на конкретный код.** Ветки, которые не нужны конкретному вызову, удаляются; остаётся по-настоящему используемое.
3. **Найти реальное общее** и выделить новую, меньшую абстракцию — или оставить небольшое дублирование, если общего почти нет.

Делать это лучше инкрементально, по одному вызывающему месту, а не большим переписыванием. Похожие истории про паттерны, которые решали отсутствующую проблему, собраны в `Когда паттерн навредил`, а частный случай — generic-репозиторий над EF — в `Repository поверх ORM`. Тот же вопрос с точки зрения принципов — интерфейс ради DIP и расширяемость ради OCP без реальной причины — разобран в `Где SOLID вредит`.

## Что стоит ответить на собеседовании

Абстракция преждевременна, если у неё одна реализация без реальной причины для второй, если её форма угадана, а не выведена из нескольких случаев, и если вызывающий код из-за неё сложнее, а не проще. Признаки — интерфейс, повторяющий класс, протекание деталей, парные изменения, имена вроде `IProcessor` и параметры-флаги в «общем» методе. Неправильная абстракция дороже дублирования: дублирование локально и объединяется позже, а неправильное обобщение обрастает условиями и становится неприкасаемым.

Абстракции окупаются на границах с внешним миром (база, сеть, брокер), для недетерминированности (`TimeProvider`), при нескольких реальных реализациях и для контрактов между модулями. Внутри кода — правило трёх, делегат или конкретный класс вместо интерфейса и выделение интерфейса тогда, когда он понадобился: это рефакторинг на минуты. Лишнее обобщение откатывают через inline, а не через новый параметр.
