# Раздел «Сложность» — исходники статей

Статьи трека `Алгоритмы` (`algorithms`) → раздела `complexity`. Это первый
раздел трека. Метаданные — во фронтматтере каждого файла, тело — markdown
под ним.

## Как залить в базу

Скриптом, а не руками по одной:

```bash
node tools/import-theory.mjs --dry-run --dir content/theory/complexity

node tools/import-theory.mjs \
  --url http://localhost:5103 \
  --email admin@interview.hypex.site \
  --password 'Admin123!' \
  --dir content/theory/complexity

IH_ADMIN_PASSWORD='…' node tools/import-theory.mjs \
  --url https://interview.hypex.site \
  --email admin@hypex.site \
  --dir content/theory/complexity
```

Первая команда показывает, что будет сделано, вторая заливает локально,
третья — в прод. Пароль для прода передаётся через переменную окружения,
а не флагом: флаг виден в списке процессов и остаётся в history шелла.

**Импорт берёт один каталог за раз** и по умолчанию читает `csharp-lang`,
поэтому `--dir` обязателен — без него этот раздел просто не зальётся,
и сообщения об ошибке не будет.

По умолчанию статьи создаются **черновиками** и существующие не трогаются.
`--update` обновляет по slug, `--publish` ставит статус «Опубликована».
Привязки к вопросам импорт не стирает: при обновлении они переносятся как есть.

Метаданные берутся из фронтматтера — `title`, `slug`, `track`, `section`,
`level`, `sortOrder`, `summary`. `readingMinutes` не задаётся: его считает
`AppDbContext.SaveChangesAsync` (200 слов в минуту, минимум 1).

## Файлы и источник правды

**Источник правды — база.** Мелкие правки удобнее делать в админке
(`/admin/theory`). Если правите файл здесь — прогоните импорт с `--update`,
иначе версии разойдутся.

## Чтобы статьи стали видны гостям

Нужны **оба** условия: статус статьи `Published` и трек `IsPublished = true`.
Сидер создаёт трек `algorithms` скрытым, а это его первый раздел, поэтому
после публикации статей **трек нужно включить переключателем «виден»
в админке** — иначе опубликованные статьи гостям не покажутся.

## Раздел написан целиком

Все 3 статьи по плану (`THEORY_PLAN.md`) написаны. Источник материала —
ответы категории `algorithms` из `content/questions/algorithms.md`,
переписанные в связный текст. Числа измерены на .NET 10.0.10
(SDK 10.0.302), Windows 11, x64, Release, медиана после прогрева;
код замеров — `.claude/tempfiles/theory-algo/Lab`. Что проверялось:

- **поиск дубликатов** на худшем входе: вложенные циклы 0,33 / 31 / 4 243 мс
  на 10³ / 10⁴ / 10⁵ элементов, сортировка 0,024 / 0,59 / 6,8 мс,
  `HashSet` 0,018 / 0,11 / 1,07 мс;
- **скрытый квадрат**: `Insert(0, x)` 100 000 раз — 517 мс против 0,49 мс
  у `Add`; `s += 'a'` 100 000 раз — 3 119 мс против 0,27 мс у `StringBuilder`;
- **бинарный поиск**: 9, 19 и 29 итераций на 10³, 10⁶ и 10⁹ элементов;
  `Array.Sort` — 69 мс на миллионе, 813 мс на десяти миллионах;
- **размеры**: `object` 24 байта, `int[0]` 24, `int[1000]` 4 024,
  `List<int>(1000)` 4 056; миллион точек-классов 32 МБ против 8 МБ у структур;
  на миллионе `int` с ёмкостью `HashSet` 18,6 байта на элемент, `Dictionary`
  23,3, узлы связного списка 32;
- **скрытые аллокации**: `OrderBy().ToArray()` на миллионе `int` — 16 МБ,
  `src[1..]` — 4 МБ, `AsSpan` — 0; `List<int>` до миллиона без ёмкости
  выделил 8,4 МБ при итоговых 4,2; 10 000 конкатенаций строки — 100 МБ
  против 53 КБ;
- **сжатие памяти**: таблица `long[1001, 1001]` — 8 МБ против 16 КБ
  у двух строк; мемоизированный Фибоначчи(90) — 4,6 КБ, итеративный — 0.

**Грабля замера:** `GC.KeepAlive(значимый тип)` упаковывает аргумент
и добавляет к замеру 24 байта — поэтому у итеративного Фибоначчи
и `AsSpan` счётчик показывал 24, а не 0.

Темы, которые здесь только упоминаются, раскрываются дальше по треку:
структуры данных — `data-structures`, бинарный поиск, рекурсия
и динамическое программирование — `techniques`, разборы задач — `drills`.
