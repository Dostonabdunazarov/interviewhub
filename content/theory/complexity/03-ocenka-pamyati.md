Вопрос «а сколько памяти?» звучит на собеседовании сразу после вопроса о времени, и отвечать на него нужно так же — через Big O. Но у памяти есть вторая сторона, которую асимптотика скрывает: два решения O(n) в .NET могут отличаться по расходу в несколько раз. В этой статье — и формальная оценка, и реальные байты. Все замеры сделаны на .NET 10.0.10, x64.

## Что считается

Обычно оценивают **дополнительную память** (auxiliary space) — всё, что алгоритм выделяет сверх входа: вспомогательные коллекции, копии, таблицы, глубину стека вызовов. Сам входной массив не учитывают, если об этом не договорились отдельно. Отдельно обычно оговаривают и результат: функция, возвращающая все подмножества, обязана выделить O(2ⁿ·n) просто под ответ.

| Источник | Пример | Память |
| --- | --- | --- |
| несколько переменных | счётчики, индексы | O(1) |
| вспомогательная коллекция | множество увиденных, словарь частот | O(n) или O(k) уникальных |
| копия входа | `ToList()`, `ToArray()`, срез `a[1..]` | O(n) |
| таблица динамического программирования | `dp[n, m]` | O(n·m) |
| рекурсия | кадр стека на каждый уровень | O(глубины) |

«На месте» (in-place) называют алгоритм с O(1) дополнительной памяти: разворот массива двумя индексами, сортировка кучей. Ориентир на собеседовании — почти любое ускорение покупается памятью: множество вместо вложенного цикла, мемоизация вместо повторного счёта. Если интервьюер просит «без дополнительной памяти», он ждёт сортировки на месте, двух указателей или математического трюка.

## Рекурсия тратит стек

Рекурсивный вызов не бесплатен по памяти даже без единой аллокации: каждый уровень держит кадр стека с параметрами, локальными переменными и адресом возврата. Поэтому:

- бинарный поиск итеративно — O(1), рекурсивно — O(log n);
- обход дерева рекурсией — O(высоты), что для выродившегося дерева превращается в O(n);
- сортировка слиянием — O(n) на буфер, быстрая сортировка — O(log n) на стек в среднем и O(n) в худшем.

Стек потока ограничен — обычно это порядка мегабайта (см. `Стек и куча`), и его переполнение в .NET не перехватывается — процесс просто завершается. Как переписать рекурсию на явный стек, разбирает раздел «Приёмы».

## Сжатие таблиц и кэшей

Самый частый вопрос-продолжение: «можно ли уменьшить память?» Пример — числа Фибоначчи:

```csharp
static long FibMemo(int n, Dictionary<int, long> memo)
{
    if (n < 2) return n;
    if (memo.TryGetValue(n, out var cached)) return cached;
    return memo[n] = FibMemo(n - 1, memo) + FibMemo(n - 2, memo);
}

static long FibIter(int n)
{
    long a = 0, b = 1;
    for (int i = 0; i < n; i++)
        (a, b) = (b, a + b);
    return a;
}
```

Мемоизация даёт O(n) времени, но и O(n) памяти — на словарь и на стек рекурсии. Итеративная версия помнит только два последних значения: O(1). Замер для `n = 90`: около 4,6 КБ аллокаций у первой версии и ноль у второй.

С таблицами динамического программирования то же самое. Если строка `i` зависит только от строки `i − 1`, держать всю матрицу не нужно:

```
new long[1001, 1001]          8 016 048 байт
две строки new long[1001]        16 064 байта
```

Пятьсот раз меньше при той же асимптотике времени — O(n·m) памяти превращается в O(m).

## Сколько весят данные в .NET

Big O говорит «O(n)», но не говорит, сколько байт на элемент. Замер через `GC.GetAllocatedBytesForCurrentThread()`:

```
new object()                  24 байта
new int[0]                    24 байта
new int[10]                   64 байта
new int[1000]              4 024 байта
new long[1000]             8 024 байта
new object[1000]           8 024 байта
new List<int>(1000)        4 056 байт
```

Отсюда простая формула для массива: 24 байта служебных данных плюс `n × размер элемента` с выравниванием до 8. Массив ссылок весит 8 байт на элемент — и это только ссылки, объекты, на которые они указывают, считаются отдельно. Из чего складываются эти 24 байта, объясняет статья `Стек и куча`.

Именно здесь проявляется разница между ссылочными и значимыми типами. Миллион точек из двух `int`:

```
класс PointC[1 000 000] с объектами     31,98 МБ
record struct PointS[1 000 000]          8,00 МБ
```

Каждый объект-класс — 24 байта плюс 8 байт ссылки в массиве, итого 32 на точку. Структуры лежат в массиве подряд, по 8 байт. Асимптотика одна, расход отличается вчетверо (подробнее — `Value type и reference type: в чём разница`).

Коллекции на миллионе `int`, с заданной ёмкостью:

| Структура | Байт на элемент |
| --- | --- |
| `int[]` | 4,0 |
| `HashSet<int>` | 18,6 |
| `Dictionary<int, int>` | 23,3 |
| связный список из узлов-классов | 32,0 |

Хеш-таблица хранит на каждый элемент сохранённый хеш, индекс следующей записи и запас корзин, связный список — заголовок объекта на каждый узел. Устройство конкретных коллекций разбирают статьи `Как устроен Dictionary` и `LinkedList<T>`.

## Скрытые аллокации

Часть памяти не видна ни в Big O, ни при беглом чтении кода. Замеры на массиве из миллиона `int`:

```
src.ToList()                         4 000 056 байт
src.Where(x => x % 2 == 0).ToList()  2 000 104 байта
src.OrderBy(x => x).ToArray()       16 000 304 байта
src[1..]                             4 000 024 байта
src.AsSpan(1)                                0 байт
```

`OrderBy` выделил четыре массива размером со вход: копию элементов, ключи, перестановку индексов и сам результат. Срез через диапазон копирует, `Span` — нет (см. `Span<T> и Memory<T>`).

Рост коллекций без заданной ёмкости тоже оставляет мусор. `List<int>`, заполненный до миллиона по одному элементу, в итоге занимает 4,2 МБ, но за время роста выделил 8,4 МБ — вторая половина ушла на выброшенные промежуточные массивы.

И самый яркий пример — строки. Десять тысяч конкатенаций `s += 'a'` выделили **100 МБ**, а `StringBuilder` на ту же работу — 53 КБ. Каждая конкатенация создаёт новую строку целиком, поэтому суммарная память O(n²), хотя в любой момент жива только одна строка длины `n`.

Здесь важно различать **пиковую** память и **суммарные аллокации**. Пик у конкатенации — O(n), но нагрузка на сборщик мусора — O(n²). Для сервиса второе часто важнее: частые сборки бьют по задержкам (см. `Как работает GC`).

## Как измерить

Для быстрой проверки — разница счётчика аллоцированных байт:

```csharp
static long MeasureAllocations(Action action)
{
    action();
    long before = GC.GetAllocatedBytesForCurrentThread();
    action();
    return GC.GetAllocatedBytesForCurrentThread() - before;
}
```

Первый вызов прогревает код: JIT-компиляция и статические инициализаторы тоже выделяют память, и без прогрева они попадут в замер.

Для живого размера структуры подходит `GC.GetTotalMemory(true)` до и после создания — так получены числа в таблицах выше. Для серьёзных сравнений — BenchmarkDotNet с `[MemoryDiagnoser]` (см. `Как мерить: BenchmarkDotNet и ловушки микробенчмарков`), для работающего сервиса — профилировщик аллокаций (см. `Профилирование аллокаций`).

## Что стоит ответить на собеседовании

Память оценивают через Big O так же, как время, но считают дополнительную: вспомогательные коллекции, копии входа, таблицы и глубину рекурсии — каждый уровень вызова занимает кадр стека, поэтому рекурсивный бинарный поиск стоит O(log n) памяти, а итеративный O(1). Почти любое ускорение покупается памятью, и стандартное продолжение вопроса — сжать её: мемоизацию заменить двумя переменными, таблицу ДП — двумя строками.

Сильный ответ добавит, что асимптотика скрывает константу: в .NET массив — это 24 байта плюс элементы, `HashSet<int>` тратит около 19 байт на элемент против 4 у массива, а миллион точек-классов весит 32 МБ против 8 у структур. И разведёт пиковую память и суммарные аллокации: десять тысяч конкатенаций строки держат в памяти одну строку, но выделяют 100 МБ мусора, и именно это видит сборщик мусора.
