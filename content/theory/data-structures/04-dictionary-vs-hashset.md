`Dictionary` и `HashSet` — одна и та же хеш-таблица, только в словаре к ключу приложено значение. Сложность операций у них одинаковая, и выбор между ними — не вопрос скорости, а вопрос того, что задаче нужно знать о ключе. На алгоритмической секции это решение принимается в первые минуты почти каждой задачи, поэтому полезно иметь в голове готовые шаблоны. Устройство обеих коллекций разобрано в статьях `Как устроен Dictionary` и `HashSet<T>`; здесь — как ими решать задачи. Замеры сделаны на .NET 10.0.10.

## Правило выбора

Вопрос один: **нужно ли что-то знать о ключе, кроме того, что он есть?**

- Только факт присутствия — `HashSet<T>`: «видели ли уже», «входит ли в разрешённый список», «уникальные значения».
- Есть связанные данные — `Dictionary<TKey, TValue>`: счётчик, индекс, объект, список.

| Задача | Структура |
| --- | --- |
| убрать дубликаты, «видели ли уже» | `HashSet<T>` |
| проверка вхождения вместо `List.Contains` | `HashSet<T>` |
| пересечение, объединение, разность | `HashSet<T>` |
| подсчёт частот | `Dictionary<T, int>` |
| индекс «id → объект», кэш | `Dictionary<TKey, TValue>` |
| «значение → позиция, где его видели» | `Dictionary<T, int>` |
| группировка «ключ → элементы» | `Dictionary<TKey, List<T>>` или `ILookup` |

## Множество вместо Dictionary<T, bool>

Встречается код, где словарь используется как множество: `Dictionary<int, bool>` со значением `true` или `Dictionary<T, T>` с ключом в роли значения. Он работает, но хуже выражает намерение и тратит больше памяти. Замер на миллионе `int` без заданной ёмкости:

| Коллекция | Байт на элемент |
| --- | --- |
| `HashSet<int>` | 22,3 |
| `Dictionary<int, bool>` | 27,9 |
| `Dictionary<int, int>` | 27,9 |
| `Dictionary<int, long>` | 39,1 |

Интересная деталь: `bool` в значении стоит столько же, сколько `int`. Запись словаря выравнивается, и сэкономить на «маленьком» значении не выйдет. Множество при этом экономнее на 20% и даёт операции над множествами из коробки.

## Шаблон «видели ли уже»

`HashSet.Add` возвращает `false`, если элемент уже был, — проверка и вставка за один поиск:

```csharp
static string? FirstRepeated(IEnumerable<string> emails)
{
    var seen = new HashSet<string>(StringComparer.OrdinalIgnoreCase);
    foreach (var email in emails)
        if (!seen.Add(email))
            return email;
    return null;
}
```

Компаратор задаёт, что считать одинаковым: здесь адреса сравниваются без учёта регистра. Пара `Contains` + `Add` делает два поиска вместо одного и выдаёт, что кандидат не знает API.

## Шаблон «подсчёт частот»

Самый частый словарь на собеседовании. Способов написать его несколько, и они заметно различаются по скорости. Миллион элементов, тысяча различных значений:

```csharp
static Dictionary<int, int> CountSlow(int[] items)
{
    var counts = new Dictionary<int, int>();
    foreach (var x in items)
    {
        if (counts.ContainsKey(x)) counts[x]++;
        else counts[x] = 1;
    }
    return counts;
}

static Dictionary<int, int> CountFast(int[] items)
{
    var counts = new Dictionary<int, int>();
    foreach (var x in items)
        CollectionsMarshal.GetValueRefOrAddDefault(counts, x, out _)++;
    return counts;
}
```

| Способ | Время |
| --- | --- |
| `ContainsKey` + индексатор | 9,8 мс |
| `counts[x] = counts.GetValueOrDefault(x) + 1` | 7,8 мс |
| `CollectionsMarshal.GetValueRefOrAddDefault` | 3,5 мс |
| `items.CountBy(x => x)` (.NET 9+) | 6,5 мс |
| `items.GroupBy(x => x)` + `Count()` | 14,5 мс, 8,5 МБ аллокаций |
| массив `int[1000]` по значению | 1,0 мс |

Первый вариант делает до трёх поисков на элемент, второй — два, `GetValueRefOrAddDefault` — один: он возвращает ссылку прямо на ячейку значения, и инкремент идёт на месте. `CountBy` удобен и аллоцирует мало (около 90 КБ против 8,5 МБ у `GroupBy`, который собирает все элементы каждой группы, чтобы потом их посчитать). На собеседовании вполне достаточно второго варианта, но знание третьего — плюс.

Последняя строка таблицы — напоминание о прямой адресации: если ключи — небольшие целые числа (буквы алфавита, коды от 0 до 999), массив счётчиков быстрее любого словаря. В задачах про строки из латиницы `int[26]` — стандартный приём.

## Шаблон «индекс по ключу»

```csharp
var usersById = users.ToDictionary(u => u.Id);
foreach (var order in orders)
    if (usersById.TryGetValue(order.UserId, out var user))
        Process(order, user);
```

Один проход на построение — O(n), дальше каждый поиск O(1). Без словаря это был бы `users.First(u => u.Id == order.UserId)` внутри цикла — O(n·m), классическая причина медленного кода, который на тестовых данных работает мгновенно.

`ToDictionary` бросает `ArgumentException` на повторяющемся ключе. Если дубликаты возможны, это нужно решить явно: взять первый через `TryAdd`, последний через индексатор или сгруппировать.

## Шаблон «группировка»

Когда на ключ приходится несколько элементов:

```csharp
static Dictionary<string, List<Order>> ByCustomer(IEnumerable<Order> orders)
{
    var groups = new Dictionary<string, List<Order>>();
    foreach (var order in orders)
    {
        if (!groups.TryGetValue(order.CustomerId, out var list))
            groups[order.CustomerId] = list = [];
        list.Add(order);
    }
    return groups;
}
```

Если группы строятся один раз и дальше только читаются, короче `orders.ToLookup(o => o.CustomerId)`: `ILookup` для отсутствующего ключа возвращает пустую последовательность, а не бросает исключение. Если от группы нужна только агрегатная величина — сумма, максимум, — список вообще не нужен: `AggregateBy` (.NET 9+) или словарь с накопителем.

## Шаблон «значение → позиция»

Словарь, где ключ — значение элемента, а значение — его индекс. На этом построена задача Two Sum и множество её вариаций: проходим массив один раз и для каждого элемента спрашиваем словарь, не встречалось ли раньше нужное дополнение. Разбор — в разделе «Типовые задачи». Пересечение двух массивов с учётом и без учёта повторов там же: без повторов это множество, с повторами — словарь частот.

## Ошибки, возвращающие O(n)

**Поиск по значению.** `ContainsValue` и `Values.Contains` — линейный перебор: на словаре из тысячи элементов десять тысяч таких вызовов заняли 5,3 мс против 0,07 мс у `ContainsKey`. Если искать нужно по значению, нужен второй словарь в обратную сторону. А вот `Keys.Contains` — честная O(1), он вызывает `ContainsKey`.

**Материализация перед поиском.** `dict.Keys.ToList().Contains(x)` копирует ключи и ищет перебором — O(n) на каждый вызов.

**Изменяемый ключ.** Объект, поменявший поля после вставки, теряется в таблице — не медленно, а насовсем.

**LINQ поверх словаря.** `dict.Where(kv => kv.Key == id)` перебирает все пары, хотя ответ доступен за O(1).

## Полезное из API

- `HashSet.TryGetValue(value, out actual)` — достать уже хранящийся экземпляр, равный переданному. Полезно, чтобы хранить одну копию одинаковых объектов.
- `TryAdd`, `GetValueOrDefault`, `Remove(key, out value)` — каждый за один поиск.
- `ToHashSet()` — построить множество из последовательности одной строкой.
- `ConcurrentDictionary<T, byte>` вместо несуществующего потокобезопасного множества.
- `OrderedDictionary<TKey, TValue>` (.NET 9) — когда нужен порядок вставки.

## Что стоит ответить на собеседовании

`HashSet<T>` — когда нужен только факт присутствия: дубликаты, «видели ли уже», проверка вхождения вместо `List.Contains`, операции над множествами. `Dictionary<TKey, TValue>` — когда к ключу привязаны данные: частоты, индекс по идентификатору, группировка, «значение → позиция». Устроены они одинаково, и сложность у них одна — O(1) в среднем.

Сильный ответ покажет шаблоны без лишних поисков: `Add`, возвращающий `bool`, вместо `Contains` + `Add`; для счётчиков — `GetValueOrDefault` или `CollectionsMarshal.GetValueRefOrAddDefault`, который на .NET 10 считает частоты почти втрое быстрее пары `ContainsKey` + индексатор. Упомянет, что `Dictionary<T, bool>` вместо множества тратит на 20% больше памяти без всякой пользы, что для маленьких целых ключей массив счётчиков быстрее любого словаря, и что `ContainsValue` — это линейный перебор.
