Точные структуры из предыдущих статей платят памятью за каждый элемент: `HashSet<string>` на сто миллионов ключей — это гигабайты, точный `COUNT(DISTINCT)` по потоку событий требует помнить всё увиденное, точный p99 — хранить и сортировать каждое измерение. Когда данных больше, чем памяти, или структуру нужно гонять по сети, точность меняют на фиксированный размер с контролируемой ошибкой. Важен контракт: в какую сторону ошибается структура и что с ней можно сложить.

## Bloom filter: «точно нет» или «возможно да»

Битовый массив из `m` бит и `k` хеш-функций. Добавление ставит `k` бит, проверка смотрит, все ли `k` бит установлены. Если хоть один ноль — элемента точно не было; если все единицы — он мог быть, а мог совпасть по битам с другими. Ложноположительные ответы возможны, ложноотрицательных нет.

Размер считают от ожидаемого числа элементов `n` и допустимой доли ложных срабатываний `p`. Вероятность ошибки `p ≈ (1 − e^(−kn/m))^k`, оптимальное число хешей `k = (m/n)·ln 2`, и при нём нужно около `1,44·log₂(1/p)` бит на элемент: примерно 9,6 бита для 1% и 14,4 для 0,1%. Сто миллионов ключей при 1% укладываются примерно в 120 МБ.

```csharp
using System.IO.Hashing;
using System.Text;

public sealed class BloomFilter
{
    private readonly ulong[] _bits;
    private readonly ulong _m;
    private readonly int _k;

    public BloomFilter(long expectedItems, double falsePositiveRate)
    {
        var m = Math.Ceiling(-expectedItems * Math.Log(falsePositiveRate) / (Math.Log(2) * Math.Log(2)));
        _m = (ulong)m;
        _k = Math.Max(1, (int)Math.Round(m / expectedItems * Math.Log(2)));
        _bits = new ulong[(_m + 63) / 64];
    }

    public void Add(string key)
    {
        var (h1, h2) = Hash(key);
        for (var i = 0; i < _k; i++)
        {
            var bit = (h1 + (ulong)i * h2) % _m;
            _bits[bit >> 6] |= 1UL << (int)(bit & 63);
        }
    }

    public bool MightContain(string key)
    {
        var (h1, h2) = Hash(key);
        for (var i = 0; i < _k; i++)
        {
            var bit = (h1 + (ulong)i * h2) % _m;
            if ((_bits[bit >> 6] & (1UL << (int)(bit & 63))) == 0) return false;
        }
        return true;
    }

    private static (ulong, ulong) Hash(string key)
    {
        var h = XxHash128.HashToUInt128(Encoding.UTF8.GetBytes(key));
        return ((ulong)h, (ulong)(h >> 64) | 1);
    }
}
```

`k` независимых хешей не нужны: приём Kirsch–Mitzenmacher `g_i = h1 + i·h2` получает все позиции из одного 128-битного хеша. На миллионе ключей с `p = 1%` получается около 9,6 млн бит и `k = 7`; прогон на миллионе отсутствующих ключей дал около 1% срабатываний. `XxHash128` — из пакета `System.IO.Hashing`; `string.GetHashCode()` не подходит, потому что рандомизирован на процесс, и сохранённый или переданный другому сервису фильтр станет бессмысленным.

Ограничения: удалять нельзя (сброс бита «удалит» чужие элементы — для этого есть counting Bloom filter и cuckoo filter), а при переполнении сверх расчётного `n` ошибка растёт очень быстро. Применение в бэкенде — не ходить туда, где ключа точно нет: LSM-хранилища (RocksDB, Cassandra) держат фильтр на каждый SSTable, чтобы не читать файл с диска; перед кэшем и БД фильтр отсекает запросы к несуществующим id (cache penetration). Если ключи приходят извне, хеш нужен с секретным seed, иначе фильтр можно забить подобранными ключами.

## HyperLogLog: сколько уникальных

Элемент хешируется, первые `b` бит хеша выбирают один из `m = 2^b` регистров, а в регистре хранится максимальная позиция первой единицы в оставшихся битах. Длинная серия нулей в начале хеша — редкое событие, и чем больше уникальных элементов, тем длиннее максимальная серия. Оценка — нормированное гармоническое среднее по регистрам с поправками для малых и больших значений.

Стандартная ошибка `≈ 1,04/√m`. В Redis `m = 16384` регистров по 6 бит — около 12 КБ на ключ и ошибка порядка 0,81%, независимо от того, тысяча уникальных или миллиард:

```bash
PFADD visitors:2026-11-14:10 user:42 user:17 user:42
PFCOUNT visitors:2026-11-14:10
PFMERGE visitors:2026-11-14 visitors:2026-11-14:10 visitors:2026-11-14:11
```

Два свойства делают HLL удобным. Повторное добавление не меняет результат, поэтому at-least-once доставка не портит счёт. И объединение без потерь: поэлементный максимум регистров двух HLL — ровно HLL объединения, так что почасовые счётчики складываются в DAU и MAU, чего с готовыми числами уникальных сделать нельзя. Пересечение напрямую не считается: через `|A| + |B| − |A∪B|` ошибки складываются, и для маленьких пересечений результат бесполезен.

## Count-Min Sketch: как часто

Матрица `d × w` счётчиков и `d` хеш-функций: добавление увеличивает по одному счётчику в каждой строке, оценка берёт минимум по строкам. Коллизии только добавляют, поэтому оценка не меньше истинной, а сверху ограничена `ε·N` (где `N` — сумма всех инкрементов) с вероятностью `1 − δ` при `w = ⌈e/ε⌉`, `d = ⌈ln(1/δ)⌉`. Ошибка абсолютная и пропорциональна всему потоку: для тяжёлых элементов оценка почти точная, для редких — шум. Поэтому CMS берут для heavy hitters — горячие ключи кэша, top IP, в паре с min-кучей кандидатов размера K (сам top-K разобран в `Top K`). Скетчи с одинаковыми параметрами складываются поэлементно.

## Перцентили латентности на потоке

Точный p99 требует хранить все значения: миллиард запросов в час по 8 байт — 8 ГБ в час на сервис. Ещё хуже частая ошибка — усреднять перцентили. Перцентили не складываются: если девять подов отвечают за 50 мс, а десятый получает десятую часть трафика и отвечает за 2 с, p99 кластера — около 2 с, а среднее p99 подов — около 245 мс (цифры иллюстративные). Правильная агрегация — сложить распределения и только потом брать квантиль.

Отсюда главный критерий выбора структуры — **объединяемость**:

| Подход | Память | Ошибка | Объединение |
| --- | --- | --- | --- |
| хранить всё | O(n) | нет | конкатенация |
| гистограмма с фиксированными бакетами | число бакетов | зависит от границ | сумма счётчиков |
| логарифмические бакеты (HdrHistogram, DDSketch, OTel exponential) | фиксированная | относительная по значению | сумма счётчиков |
| t-digest | сотни центроидов | по рангу, точный на хвостах | приближённое |
| Prometheus summary | окно на процесс | по рангу | невозможно |

**Фиксированные бакеты** — модель Prometheus histogram: счётчик на интервал `le`, квантиль ищется по кумулятивной сумме, а внутри бакета `histogram_quantile` линейно интерполирует. Точность определяют границы: если SLO — 300 мс, а соседние границы 250 и 500 мс, ответ «p99 = 380 мс» почти ничего не значит. Границу ставят прямо на порог SLO — тогда доля «хороших» запросов считается точно, даже если сам перцентиль приблизителен (подробнее — `SLI и SLO`). Агрегация по кластеру — `sum by (le)` по `rate` бакетов, потом квантиль.

**Логарифмические бакеты** растут геометрически, и любое значение восстанавливается с относительной ошибкой не больше заданной: при 1% диапазон от микросекунды до часа покрывают около тысячи бакетов, и размер не зависит от числа измерений. Так устроены DDSketch и экспоненциальная гистограмма OpenTelemetry; HdrHistogram использует лог-линейную схему, где точность задаётся числом значащих цифр.

**t-digest** хранит центроиды «среднее + вес», причём у краёв распределения центроиды маленькие, почти отдельные точки, — поэтому хвосты точные. Цена — ошибка не гарантирована формулой и зависит от порядка вставки, объединение приближённое.

Две ловушки. Значения за пределами диапазона попадают в крайний бакет, и p99,9 «ровно 10 секунд» часто означает «больше 10 секунд». А нагрузочный клиент, ждущий ответа перед следующим запросом, в медленные периоды делает меньше замеров и занижает хвост — coordinated omission (см. `Нагрузочные тесты и регрессии`).

## Амортизированная O(1) и спайки латентности

Амортизированная O(1) — гарантия на сумму: n операций стоят O(n), но отдельная может стоить O(n). `List<T>.Add` раз в удвоение выделяет новый массив и копирует всё; `Dictionary` при росте выделяет массивы под простое число не меньше удвоенного размера и перекладывает все записи. `ConcurrentDictionary` при росте берёт все свои блокировки, и ждут уже все писатели. Для пакетной обработки это неважно, а в сервисе с SLO на p99 эта одна дорогая вставка внутри запроса и есть хвост.

Спайк больше, чем подсказывает Big O. Массивы от 85 000 байт идут в LOH — для `List<object>` это уже около 10 600 элементов на x64; их выделение засчитывается в бюджет gen2 и провоцирует полные сборки (см. `Диагностика высокого GC`). Новый массив обнуляется. В момент роста живы оба массива, и список на 1 ГБ кратковременно требует около 3 ГБ — в контейнере с memory limit это уже OOMKill.

Как избегать, по порядку применимости:

- **ёмкость заранее**: `new List<T>(request.Items.Count)`, `new Dictionary<K,V>(expected)`, `EnsureCapacity` — бесплатно, если размер известен;
- **структуры без копирования**: данные чанками ниже порога LOH, рост — выделение одного нового чанка;
- **переиспользование буферов**: `ArrayPool<T>.Shared`, `RecyclableMemoryStream` вместо `MemoryStream`;
- **инкрементальный рехэшинг**: две таблицы, поиск в обеих, каждая операция переносит часть корзин — так растёт словарь в Redis; в .NET из коробки такого нет;
- **рост вне горячего пути**: собрать новую структуру в фоне и атомарно подменить ссылку, для справочников — `FrozenDictionary`.

```csharp
public sealed class ChunkedList<T>
{
    private const int ChunkSize = 4096;
    private readonly List<T[]> _chunks = [];
    private int _count;

    public int Count => _count;

    public void Add(T item)
    {
        if (_count / ChunkSize == _chunks.Count)
            _chunks.Add(new T[ChunkSize]);
        _chunks[_count / ChunkSize][_count % ChunkSize] = item;
        _count++;
    }

    public T this[int index]
    {
        get
        {
            ArgumentOutOfRangeException.ThrowIfGreaterThanOrEqual((uint)index, (uint)_count, nameof(index));
            return _chunks[index / ChunkSize][index % ChunkSize];
        }
    }
}
```

4096 ссылок — 32 КБ, ниже порога LOH. Внешний список тоже растёт удвоением, но он в 4096 раз меньше и копирует только ссылки на чанки. Цена — лишняя косвенность при доступе и худшая локальность, чем у сплошного массива (см. `Массив и связный список`). Обнаруживают такие спайки по p99/p999 и максимуму, а не по среднему: большие `T[]` и `Entry[]` в событиях аллокаций `dotnet-trace`, рост LOH и частота gen2 в `dotnet-counters` (см. `Профилирование аллокаций`).

## Что стоит ответить на собеседовании

Вероятностные структуры дают фиксированную память ценой контролируемой ошибки: Bloom filter отвечает «точно нет» или «возможно да» и при 1% ошибки стоит около 10 бит на ключ, HyperLogLog оценивает число уникальных с ошибкой меньше процента на 12 КБ в Redis, Count-Min Sketch оценивает частоты сверху. Перцентили на потоке считают по гистограммам или скетчам, а амортизированная O(1) означает, что отдельная операция может стоить O(n), — это видно в p99.

Сильный ответ называет направление ошибки и объединяемость каждой структуры: HLL сливается через максимум регистров, гистограммы — суммой бакетов, а перцентили подов усреднять нельзя, и summary в Prometheus не агрегируется. Объяснит, что точность гистограммы задают границы бакетов и их ставят на порог SLO. И разберёт спайк роста коллекции целиком — копирование, LOH и gen2, двойная память, общая блокировка `ConcurrentDictionary`, — с лечением: ёмкость заранее, чанки, пулы, инкрементальный рехэшинг.
