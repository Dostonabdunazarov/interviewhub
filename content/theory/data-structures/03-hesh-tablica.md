Хеш-таблица — ответ на вопрос «как найти элемент, не перебирая остальные». Это самая полезная структура на алгоритмической секции: половина задач, где наивное решение квадратичное, решается заведением словаря или множества. Здесь — общая идея и её компромиссы, одинаковые для любого языка. Как конкретно устроены `Dictionary` и `HashSet` в .NET, разобрано в статьях `Как устроен Dictionary` и `HashSet<T>`.

## От массива к хешированию

Если ключи — небольшие целые числа, хеш-таблица не нужна: значение для ключа `k` можно хранить прямо в `array[k]`. Это **прямая адресация**, и она даёт честную O(1) на всё. Проблема в том, что ключи обычно — строки, идентификаторы или числа из огромного диапазона, и массив под все возможные ключи не поместится в память.

Хеширование решает это в два шага:

1. **Хеш-функция** превращает ключ любого типа в число.
2. Число сводится к индексу в массиве небольшого размера `m` — обычно остатком от деления: `index = hash mod m`.

Ячейки массива называют **корзинами** (buckets). Поиск, вставка и удаление сводятся к вычислению индекса и работе с одной корзиной — поэтому O(1) в среднем.

## Хорошая хеш-функция

Требования к хеш-функции:

- **детерминированность** — один и тот же ключ всегда даёт один и тот же хеш, пока лежит в таблице;
- **согласованность с равенством** — равные ключи обязаны давать равный хеш, иначе таблица их не найдёт;
- **равномерность** — разные ключи должны распределяться по корзинам как можно равномернее;
- **скорость** — хеш считается на каждой операции.

Обратное к второму пункту не требуется: разные ключи вправе давать одинаковый хеш. Как правильно реализовать эту пару методов для своего типа в C#, разобрано в статье `Equals, GetHashCode и ==: как устроено равенство`.

## Коллизии неизбежны

Коллизия — два разных ключа в одной корзине. Избежать их нельзя даже с идеальной хеш-функцией, и интуиция здесь подводит. Это **парадокс дней рождения**: в группе из 23 человек вероятность совпадения дней рождения уже больше 50%, хотя дней в году 365. В общем виде первая коллизия ожидается примерно после √m ключей, то есть в таблице на миллион корзин — уже на второй тысяче вставок.

Поэтому вопрос не в том, как избежать коллизий, а в том, как с ними жить. Подходов два.

## Метод цепочек

В каждой корзине лежит список всех записей, попавших в неё. Поиск — вычислить корзину и пройти её список, сравнивая ключи. Упрощённая реализация:

```csharp
sealed class ChainedHashTable<TKey, TValue> where TKey : notnull
{
    private List<(TKey Key, TValue Value)>?[] _buckets = new List<(TKey, TValue)>?[8];

    public int Count { get; private set; }

    private static int IndexFor(TKey key, int length) =>
        (key.GetHashCode() & int.MaxValue) % length;

    public bool TryGet(TKey key, out TValue value)
    {
        var bucket = _buckets[IndexFor(key, _buckets.Length)];
        if (bucket is not null)
            foreach (var (k, v) in bucket)
                if (EqualityComparer<TKey>.Default.Equals(k, key))
                {
                    value = v;
                    return true;
                }
        value = default!;
        return false;
    }

    public void Set(TKey key, TValue value)
    {
        var bucket = _buckets[IndexFor(key, _buckets.Length)] ??= [];
        for (int i = 0; i < bucket.Count; i++)
            if (EqualityComparer<TKey>.Default.Equals(bucket[i].Key, key))
            {
                bucket[i] = (key, value);
                return;
            }
        bucket.Add((key, value));
        if (++Count > _buckets.Length * 3 / 4) Resize();
    }

    private void Resize()
    {
        var old = _buckets;
        _buckets = new List<(TKey, TValue)>?[old.Length * 2];
        foreach (var bucket in old)
            if (bucket is not null)
                foreach (var entry in bucket)
                    (_buckets[IndexFor(entry.Key, _buckets.Length)] ??= []).Add(entry);
    }
}
```

`& int.MaxValue` отбрасывает знак: `GetHashCode` может вернуть отрицательное число, а индекс массива — нет. Цепочки просты, спокойно переносят высокое заполнение и простое удаление. Минус — отдельные списки в памяти и прыжки по ссылкам. Реализация в .NET, например, хранит цепочки не отдельными объектами, а индексами внутри одного массива записей.

## Открытая адресация

Все записи лежат прямо в массиве корзин. Если нужная ячейка занята, ищется следующая по фиксированному правилу: **линейное пробирование** берёт соседнюю, квадратичное — через растущий шаг, двойное хеширование — с шагом от второй хеш-функции. Поиск идёт по той же последовательности, пока не найдётся ключ или пустая ячейка.

Плюс — всё в одном массиве, отличная локальность. Минус — производительность резко зависит от заполнения, потому что занятые ячейки слипаются в кластеры. Замер на таблице с линейным пробированием, миллион ячеек, случайные ключи — среднее число проверенных ячеек:

| Заполнение | Найденный ключ | Отсутствующий ключ |
| --- | --- | --- |
| 50% | 1,5 | 2,5 |
| 75% | 2,5 | 8,5 |
| 90% | 5,4 | 50 |
| 95% | 10,4 | 199 |

Цифры совпадают с классической оценкой Кнута: ½(1 + 1/(1−α)) для успешного поиска и ½(1 + 1/(1−α)²) для неуспешного. Между 75% и 95% заполнения поиск отсутствующего ключа дорожает в 23 раза.

Есть и тонкость удаления: просто очистить ячейку нельзя — оборвётся цепочка пробирования, и ключи за ней «пропадут». Удалённую ячейку помечают специальной меткой (tombstone), которую поиск проходит насквозь, а вставка может переиспользовать.

## Коэффициент заполнения и рост

Отношение числа элементов к числу корзин называют **коэффициентом заполнения** (load factor, α). Средняя длина цепочки равна α, поэтому, пока он ограничен константой, операции остаются O(1). Когда порог превышен — для цепочек обычно около 0,75–1, для открытой адресации ниже, — таблица выделяет массив примерно вдвое больше и **перехеширует** все записи: индекс зависит от размера массива, поэтому каждую запись нужно положить заново.

Перехеширование стоит O(n), но, как и рост динамического массива, случается всё реже, и вставка остаётся O(1) амортизированно. Если итоговый размер известен заранее, ёмкость стоит задать при создании — промежуточных перехеширований не будет.

## Худший случай

| Операция | В среднем | В худшем |
| --- | --- | --- |
| поиск | O(1) | O(n) |
| вставка | O(1) амортизированно | O(n) |
| удаление | O(1) | O(n) |
| память | O(n) | O(n) |

Худший случай — все ключи в одной корзине. Так бывает при плохой хеш-функции (например, по одному полю с тремя возможными значениями) и при атаке: если хеш-функция предсказуема, злоумышленник может прислать тысячи ключей с одинаковым хешем и превратить каждый запрос в линейный перебор. Это называется hash flooding, и защита от него — рандомизированный хеш: в .NET хеш строки меняется от запуска к запуску процесса.

Отдельный источник ошибок — изменяемый ключ: если поле, участвующее в хеше, поменялось после вставки, запись остаётся в старой корзине и перестаёт находиться.

## Чего хеш-таблица не умеет

Хеширование намеренно разрушает порядок ключей, поэтому таблица не может:

- перечислить ключи по возрастанию;
- найти минимальный ключ или ближайший к заданному;
- ответить на запрос по диапазону «все ключи от 10 до 20».

Всё это — работа упорядоченных структур: сбалансированного дерева поиска за O(log n) или отсортированного массива с бинарным поиском (см. `Деревья и графы`).

## Что стоит ответить на собеседовании

Хеш-таблица — массив корзин и хеш-функция: ключ превращается в число, остаток от деления на размер массива даёт корзину, и операции идут с одной корзиной — O(1) в среднем. Коллизии неизбежны, разрешают их цепочками (список в каждой корзине) или открытой адресацией (поиск следующей свободной ячейки), а при превышении коэффициента заполнения таблица растёт и перехеширует все записи, сохраняя амортизированную O(1).

Сильный ответ объяснит, почему заполнение важно для открытой адресации: при 75% поиск отсутствующего ключа проверяет в среднем 8,5 ячейки, при 95% — около двухсот. Назовёт худший случай O(n) при плохом хеше или атаке подбором коллизий и защиту рандомизированным хешем. И перечислит, чего таблица не умеет — порядок, минимум, диапазоны, — за этим идут к деревьям.
