# Раздел «Типовые задачи» — исходники статей

Статьи трека `algorithms` → раздела `drills`. Метаданные — во
фронтматтере каждого файла, тело — markdown под ним.

Раздел последний в треке: каждая статья — разбор одной задачи с
собеседования в том порядке, в каком её ждут от кандидата. Условие и
уточняющие вопросы → перебор и его сложность → путь к быстрому решению →
финальный код на C# → сложность → крайние случаи и тесты → вариации,
которые интервьюер спрашивает следом → «Что стоит ответить на собеседовании».
Приёмы и структуры данных здесь не объясняются заново, а даются ссылками
на статьи разделов `complexity`, `data-structures` и `techniques`.

## Как залить в базу

Скриптом, а не руками по одной. Импорт берёт один каталог за раз,
поэтому `--dir` обязателен — без него зальётся `csharp-lang`:

```bash
node tools/import-theory.mjs --dry-run --dir content/theory/drills

node tools/import-theory.mjs \
  --url http://localhost:5103 \
  --email admin@interview.hypex.site \
  --password 'Admin123!' \
  --dir content/theory/drills

IH_ADMIN_PASSWORD='…' node tools/import-theory.mjs \
  --url https://interview.hypex.site \
  --email admin@hypex.site \
  --dir content/theory/drills
```

Пароль для прода передаётся через переменную окружения, а не флагом:
флаг виден в списке процессов и остаётся в history шелла.

По умолчанию статьи создаются **черновиками** и существующие не трогаются.
`--update` обновляет по slug, `--publish` ставит статус «Опубликована».
Привязки к вопросам импорт не стирает: при обновлении они переносятся как есть.

Метаданные берутся из фронтматтера — `title`, `slug`, `track`, `section`,
`level`, `sortOrder`, `summary`. `readingMinutes` не задаётся: его считает
`AppDbContext.SaveChangesAsync` (200 слов в минуту, минимум 1).

## Раздел написан целиком

Все 6 статей по плану (`THEORY_PLAN.md`) написаны. Весь код из статей
скомпилирован и прогнан на .NET 10 (SDK 10.0.302): каждое решение сверено
с переборной версией на тысячах случайных входов, включая пустые массивы,
дубликаты, отрицательные числа и граничные k. Код статей сверен с
протестированным построчно, без учёта отступов.

Что измерялось (Release, медиана семи прогонов):

- **Two Sum**, 10 000 элементов без подходящей пары: перебор 49,5 мс,
  словарь 0,22 мс;
- **переполнение в Two Sum**: наивная версия с `int need` на
  `[int.MinValue, int.MinValue + 4]` и `target = 4` возвращает пару,
  которой нет; версия с `long` — `null`;
- **Top K**, миллион случайных `int`, k = 10: копия + `Array.Sort` 70,3 мс,
  `OrderByDescending().Take(10)` 32,8 мс, quickselect 6,1 мс,
  min-куча 2,9 мс;
- **скобки**: `Stack<char>` на строке из 400 скобок — 456 байт аллокаций
  на вызов, стек в `Span<char>` через `stackalloc` — 0 байт;
- **слияние k массивов**, 100 × 10 000: последовательное попарное
  слияние 88,2 мс, куча 51,2 мс, склейка + `Array.Sort` 41,9 мс.

**Неожиданный результат последнего замера:** на числах в памяти сортировка
склейки обгоняет кучу, несмотря на O(N log N) против O(N log k). Это
вошло в статью как честная оговорка: ценность k-путевого слияния —
потоки и внешняя сортировка, а не массивы в памяти.
