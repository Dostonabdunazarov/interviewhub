На middle backend-собеседовании алгоритмическая часть обычно занимает 30–45 минут и содержит одну-две задачи уровня easy или medium. Экзотику не ждут: проверяют, умеет ли кандидат выбрать структуру данных, оценить сложность, написать рабочий код без IDE и пройтись по крайним случаям. Короткие задачи из этой статьи часто дают первыми — как разминку перед основной.

Разминка выглядит простой, но именно на ней видно, знает ли человек платформу: что `char` в .NET — не символ, а UTF-16 code unit, и что арифметика `int` по умолчанию молча переполняется.

## Что спрашивают и как вести себя на задаче

Почти всё покрывается десятком паттернов, и для каждого есть отдельная статья:

| Паттерн | Типичные задачи | Где подробно |
| --- | --- | --- |
| хеширование | дубликаты, анаграммы, частоты, two sum | `Хеш-таблица`, `Dictionary vs HashSet`, `Two sum` |
| два указателя | палиндром, слияние, пары в отсортированном | `Два указателя`, `Слияние отсортированных массивов` |
| скользящее окно | подстрока без повторов, сумма окна k | `Скользящее окно` |
| стек | скобки, next greater element | `Стек и очередь`, `Скобочная последовательность` |
| бинарный поиск | первая позиция, поиск по ответу | `Бинарный поиск` |
| сортировка + проход | слияние интервалов, переговорные | `Сортировки` |
| деревья и графы | обходы, острова, кратчайший путь в сетке | `Деревья и графы`, `DFS и BFS`, `Топологическая сортировка` |
| куча | top K, k-way merge | `Top K` |
| простая DP | Kadane, лестница, размен монет | `Максимальная сумма подмассива`, `Динамическое программирование` |

Устно ждут Big O по времени и памяти (`Big O`, `Оценка памяти`), устройство `Dictionary` и почему поиск в нём O(1) только в среднем, сложности операций коллекций .NET. Backend-задачи похожи на реальный код: LRU-кеш на `Dictionary` и `LinkedList`, rate limiter, дедупликация событий, top-N по логам. Красно-чёрные деревья по коду и потоки в сетях на этом уровне не спрашивают.

Порядок работы над задачей стабилен:

1. Уточнить вход: размер, пустые значения, дубликаты, отрицательные числа, алфавит, отсортированность.
2. Назвать наивное решение и его сложность.
3. Улучшить — обычно хешем, сортировкой или двумя указателями — и назвать новую сложность.
4. Написать код, проговаривая инварианты.
5. Прогнать вручную пример и крайние случаи: пустой вход, один элемент, все одинаковые, переполнение `int`.

Молчание хуже неидеального решения: интервьюер оценивает ход мысли, а помочь может только тому, кто рассуждает вслух.

## Развернуть строку

Строки в .NET неизменяемы, поэтому разворот — это создание новой строки. Каноничный вариант — массив символов и `Array.Reverse`:

```csharp
static string Reverse(string s)
{
    char[] chars = s.ToCharArray();
    Array.Reverse(chars);
    return new string(chars);
}
```

Здесь две аллокации: промежуточный массив и результат. `string.Create` даёт записать символы прямо в буфер новой строки, и аллокация остаётся одна:

```csharp
static string ReverseFast(string s) =>
    string.Create(s.Length, s, static (dst, src) =>
    {
        src.AsSpan().CopyTo(dst);
        dst.Reverse();
    });
```

`dst.Reverse()` — это `MemoryExtensions.Reverse` для `Span<char>`, разворот на месте. Если просят обойтись без библиотечных функций, то же самое делают два указателя с обменом `(a[i], a[j]) = (a[j], a[i])`, пока `i < j`. Все три варианта — O(n) времени.

Типичная ошибка — накапливать результат конкатенацией `result = c + result` в цикле. Каждая итерация копирует всю накопленную строку, итог — O(n²) времени и столько же суммарных аллокаций. LINQ `new string(s.Reverse().ToArray())` корректен и O(n), но создаёт итератор и промежуточные буферы.

### Суррогатные пары и графемы

Разворот по `char` ломает Unicode. Эмодзи `😀` занимает два `char` — суррогатную пару, — и после разворота пара переставляется в недопустимом порядке. Строка `"a😀b"` превращается в `b`, два одиночных суррогата в обратном порядке и `a`, и строгий `UTF8Encoding` на ней бросает исключение. Переход на кодовые точки через `EnumerateRunes()` чинит суррогаты, но не всё: `"café"`, записанное как `e` + комбинируемый акцент U+0301, после разворота повесит акцент на соседнюю букву, а семья `👨‍👩‍👧` из семи кодовых точек, склеенных ZWJ, распадётся.

Видимый пользователю символ — графема, или text element. С .NET 5 `StringInfo` делит строку на расширенные кластеры графем по UAX #29:

```csharp
using System.Globalization;

static string ReverseGraphemes(string s)
{
    var parts = new List<string>();
    var e = StringInfo.GetTextElementEnumerator(s);
    while (e.MoveNext()) parts.Add(e.GetTextElement());
    parts.Reverse();
    return string.Concat(parts);
}
```

Проверено на .NET 10: `"x👨‍👩‍👧y"` длиной 10 `char` и 7 рун даёт 3 графемы и разворачивается в `"y👨‍👩‍👧x"`, флаг `🇷🇺` из двух региональных индикаторов остаётся целым. Цена — подстрока на каждую графему, поэтому для ASCII-идентификаторов это избыточно. Достаточно спросить, какие данные на входе, и сказать, что для пользовательского текста разворот по `char` некорректен.

## Первый уникальный символ

Нужно вернуть индекс первого символа, который встречается в строке ровно один раз, или −1. Наивно — для каждого символа проверить остальные или сравнить `IndexOf` и `LastIndexOf`: O(n²).

Решение — два прохода. Первый считает частоты, второй идёт по строке в исходном порядке и возвращает первый символ со счётчиком 1:

```csharp
static int FirstUniqueIndex(string s)
{
    var count = new Dictionary<char, int>();
    foreach (char c in s)
        count[c] = count.GetValueOrDefault(c) + 1;
    for (int i = 0; i < s.Length; i++)
        if (count[s[i]] == 1) return i;
    return -1;
}
```

Второй проход идёт именно по строке, а не по словарю: порядок перечисления `Dictionary` не гарантирован, а нужен первый по позиции. Время O(n), память O(k), где k — число различных символов.

Если алфавит известен и мал, словарь заменяется массивом счётчиков, и хеширование исчезает:

```csharp
static int FirstUniqueIndexAscii(string s)
{
    Span<int> count = stackalloc int[26];
    foreach (char c in s) count[c - 'a']++;
    for (int i = 0; i < s.Length; i++)
        if (count[s[i] - 'a'] == 1) return i;
    return -1;
}
```

Это O(n) времени и O(1) памяти — массив фиксированного размера. Контракт жёсткий: символ вне `a–z` даст `IndexOutOfRangeException`, поэтому алфавит надо уточнить заранее. Для `"leetcode"` ответ 0, для `"loveleetcode"` — 2, для `"aabb"` и пустой строки — −1.

Уточняющие вопросы здесь те же, что в развороте: учитывать ли регистр (тогда `char.ToLowerInvariant`), что вернуть при отсутствии ответа и важны ли суррогатные пары — тогда считать руны или графемы. Однострочник `s.GroupBy(c => c).FirstOrDefault(g => g.Count() == 1)` корректен, потому что `GroupBy` сохраняет порядок первого появления ключей, но аллоцирует группы.

Частый follow-up — поток: символы приходят по одному, и после каждого нужен текущий первый уникальный. Держат счётчики и очередь кандидатов; при запросе из головы очереди выбрасывают символы со счётчиком больше 1. Каждый символ попадает в очередь и покидает её один раз, поэтому амортизированно O(1) на символ.

## Пропущенное число

В массиве из n различных чисел из диапазона `0..n` одного не хватает. Наивные варианты рабочие, но неоптимальные: отсортировать и найти первый `i`, где `a[i] != i`, — O(n log n) и порча входа; сложить всё в `HashSet` и проверить `0..n` — O(n) времени, но O(n) памяти.

Оптимальных решений два, оба O(n) времени и O(1) памяти. Первое — разница ожидаемой суммы `n·(n+1)/2` и фактической:

```csharp
static int MissingBySum(int[] nums)
{
    long n = nums.Length;
    long sum = 0;
    foreach (int x in nums) sum += x;
    return (int)(n * (n + 1) / 2 - sum);
}
```

Счёт в `long` здесь обязателен. Арифметика C# по умолчанию `unchecked`, и в `int` произведение `n·(n+1)` выходит за `int.MaxValue` начиная с n = 46 341. Проверено: на таком массиве версия на `int` вернула −2 147 467 464 вместо правильного ответа и без всякого исключения. Причина — деление: сложение и вычитание по модулю 2³² дали бы верный остаток, а `/ 2` от переполненного произведения его портит.

Второе решение — XOR. Свойства `x ^ x = 0` и `x ^ 0 = x` означают, что если проксорить все числа `0..n` и все элементы массива, каждое присутствующее число встретится дважды и обнулится, а останется пропущенное:

```csharp
static int MissingByXor(int[] nums)
{
    int result = nums.Length;
    for (int i = 0; i < nums.Length; i++)
        result ^= i ^ nums[i];
    return result;
}
```

Переполнения нет в принципе. Для `[3, 0, 1]` ответ 2, для `[0]` — 1, для `[1]` — 0. Обе версии сверены с ответом на случайных перестановках размером до 100 000, включая границу 46 341.

| Подход | Время | Память |
| --- | --- | --- |
| сортировка + поиск разрыва | O(n log n) | O(1) + память сортировки, вход меняется |
| `HashSet` | O(n) | O(n) |
| сумма в `long` | O(n) | O(1) |
| XOR | O(n) | O(1) |
| бинарный поиск, если массив отсортирован | O(log n) | O(1) |

Вариации: диапазон `1..n` — та же формула со сдвигом; пропущено два числа — сумма и сумма квадратов либо XOR с разделением по младшему установленному биту; данные — огромный файл или поток — сумма и XOR считаются за один проход без хранения.

## Что стоит ответить на собеседовании

На middle backend спрашивают хеширование, два указателя, окно, стек, бинарный поиск, BFS/DFS, сортировки и простую DP, а работу над задачей ведут по схеме: уточнить вход, назвать наивное решение и его сложность, улучшить, написать код, прогнать крайние случаи. Разворот строки — `Array.Reverse` или `string.Create` за O(n); первый уникальный символ — два прохода со словарём или массивом счётчиков, второй проход по строке; пропущенное число — сумма в `long` или XOR, O(n) и O(1).

Сильный ответ отличают знания платформы: `char` — UTF-16 code unit, и для пользовательского текста разворачивают графемы через `StringInfo`, а не `char`; второй проход идёт по строке, потому что порядок `Dictionary` не гарантирован; формула суммы в `int` молча ломается с n = 46 341, а XOR переполнению не подвержен. Плюс умение назвать неоптимальные варианты — конкатенацию за O(n²), сортировку, `HashSet` — и объяснить, чем именно они хуже.
