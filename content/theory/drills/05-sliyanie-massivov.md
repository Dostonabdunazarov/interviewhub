Слияние двух отсортированных массивов — шаг алгоритма mergesort, вынесенный в отдельную задачу. Само слияние пишется за минуту, поэтому интервьюер почти всегда идёт дальше: «а на месте, без нового массива?», «а если массивов k?», «а если они не помещаются в память?». Ниже — основное решение и ответы на эти продолжения.

## Условие и уточняющие вопросы

Даны два массива, отсортированных по возрастанию. Вернуть один отсортированный массив из всех их элементов.

Вопросы:

- **Новый массив или на месте?** Популярная постановка: у первого массива в конце есть свободное место под второй.
- **Дубликаты оставить или убрать?**
- **Важна ли стабильность** — порядок равных элементов из разных источников, если это не числа, а записи?
- **Одинаково ли направление сортировки?**
- **Данные в памяти или это потоки?**

Считаем: результат — новый массив, дубликаты сохраняются, оба массива по возрастанию.

## Решение в лоб: склеить и отсортировать

`a.Concat(b).Order().ToArray()` — правильный ответ за O((n + m) log(n + m)). Он игнорирует главное условие: данные уже упорядочены. Назвать его стоит, но как отправную точку, с которой сразу уходят к линейному слиянию.

## Идея: два указателя

Наименьший элемент результата — меньший из двух первых элементов. Следующий — меньший из двух оставшихся «голов». Значит, достаточно указателя на текущую голову каждого массива: сравниваем, меньшую записываем и сдвигаем её указатель. Когда один массив кончился, хвост другого переносится целиком. Это вариант «по двум последовательностям» из статьи `Два указателя`.

## Финальное решение

```csharp
static int[] Merge(ReadOnlySpan<int> a, ReadOnlySpan<int> b)
{
    var result = new int[a.Length + b.Length];
    int i = 0, j = 0, k = 0;
    while (i < a.Length && j < b.Length)
        result[k++] = a[i] <= b[j] ? a[i++] : b[j++];
    a[i..].CopyTo(result.AsSpan(k));
    b[j..].CopyTo(result.AsSpan(k + a.Length - i));
    return result;
}
```

Детали:

- **`<=`, а не `<`**, делает слияние стабильным: при равенстве первым идёт элемент из `a`. Для чисел это неважно, для записей с одинаковым ключом — да, и именно на этом держится стабильность mergesort.
- **Хвосты копируются через `Span.CopyTo`**, а не поэлементным циклом. Один из хвостов всегда пуст, второй переносится блоком. Индекс для `b` — это `k` плюс длина хвоста `a`, который может быть ненулевым.
- **`ReadOnlySpan<int>`** позволяет сливать части массивов без копирования, например половины в mergesort (см. `Span<T> и Memory<T>`).

## Сложность

Время O(n + m): каждый элемент записывается в результат ровно один раз, на каждом шаге одно сравнение. Память O(n + m) — под результат; дополнительной сверх него нет.

| Подход | Время | Память |
| --- | --- | --- |
| склеить и отсортировать | O((n + m) log(n + m)) | O(n + m) |
| два указателя в новый массив | O(n + m) | O(n + m) |
| на месте с конца | O(n + m) | O(1) |

## Слияние на месте

Классическая постановка: массив `a` длины `m + n`, в первых `m` ячейках — данные, в последних `n` — свободное место; `b` длины `n` надо влить в `a`.

Если заполнять с начала, запись затирает ещё не прочитанные элементы `a`. Решение — заполнять **с конца**: наибольший элемент результата — больший из последних элементов, и он идёт в последнюю ячейку, которая свободна.

```csharp
static void MergeInPlace(int[] a, int m, int[] b, int n)
{
    int i = m - 1, j = n - 1, k = m + n - 1;
    while (j >= 0)
        a[k--] = i >= 0 && a[i] > b[j] ? a[i--] : b[j--];
}
```

Цикл идёт, пока остались элементы `b`. Когда они кончились, оставшиеся элементы `a` уже стоят на своих местах — переносить их не нужно. Запись никогда не обгоняет чтение: `k` всегда не меньше `i`, потому что между ними ровно `j + 1` свободных ячеек. O(n + m) времени, O(1) дополнительной памяти.

Здесь при равенстве первым с конца берётся элемент `b` — так элементы `a` остаются левее равных им из `b`, и слияние снова стабильно.

## Крайние случаи и тесты

- Оба пустые → пустой результат.
- Один пустой → копия другого.
- Все элементы одного меньше всех элементов другого: `[5, 6]` и `[1, 2]` → `[1, 2, 5, 6]`; цикл сравнений кончается быстро, остальное — копирование хвоста.
- Дубликаты: `[1, 2, 3, 0, 0, 0]` с `m = 3` и `[2, 5, 6]` → `[1, 2, 2, 3, 5, 6]`.
- На месте при `m = 0`: `a = [0]`, `b = [1]` → `[1]` — проверка, что `i = -1` не ломает условие.
- На месте, когда весь `b` меньше `a`: `[4, 5, 6, 0, 0, 0]` и `[1, 2, 3]` → `[1, 2, 3, 4, 5, 6]`.

Все варианты статьи сверены с сортировкой склейки на трёх тысячах пар случайных отсортированных массивов, включая пустые и с повторами.

## Вариации, которые спрашивают следом

**Слить без дубликатов.** То же слияние, но значение добавляется, только если оно отличается от последнего записанного. `[1, 1, 2, 4]` и `[1, 3, 4, 4]` → `[1, 2, 3, 4]`.

**Слить потоки.** Если данные приходят как `IEnumerable<int>` и в память целиком не помещаются, те же два указателя пишутся на перечислителях:

```csharp
static IEnumerable<int> MergeStreams(IEnumerable<int> a, IEnumerable<int> b)
{
    using var ea = a.GetEnumerator();
    using var eb = b.GetEnumerator();
    bool hasA = ea.MoveNext(), hasB = eb.MoveNext();
    while (hasA && hasB)
    {
        if (ea.Current <= eb.Current)
        {
            yield return ea.Current;
            hasA = ea.MoveNext();
        }
        else
        {
            yield return eb.Current;
            hasB = eb.MoveNext();
        }
    }
    for (; hasA; hasA = ea.MoveNext()) yield return ea.Current;
    for (; hasB; hasB = eb.MoveNext()) yield return eb.Current;
}
```

Память O(1) — по одному текущему элементу из каждого источника; результат отдаётся лениво (см. `yield return и итераторы`).

**Слить k отсортированных массивов.** Последовательное попарное слияние стоит O(N·k), где N — всего элементов: первые массивы переписываются k раз. Правильный ответ — **min-куча из текущих голов**: достаём минимум, кладём следующий элемент из того же массива.

```csharp
static List<int> MergeK(int[][] arrays)
{
    var heap = new PriorityQueue<(int Array, int Index), int>(arrays.Length);
    int total = 0;
    for (int a = 0; a < arrays.Length; a++)
    {
        total += arrays[a].Length;
        if (arrays[a].Length > 0) heap.Enqueue((a, 0), arrays[a][0]);
    }

    var result = new List<int>(total);
    while (heap.TryDequeue(out var pos, out int value))
    {
        result.Add(value);
        int next = pos.Index + 1;
        if (next < arrays[pos.Array].Length)
            heap.Enqueue((pos.Array, next), arrays[pos.Array][next]);
    }
    return result;
}
```

В куче не больше k элементов, поэтому каждая операция — O(log k), итого O(N log k) времени и O(k) памяти сверх результата. Альтернатива с той же асимптотикой — сливать попарно «турниром»: массивы 1+2, 3+4 и так далее, потом результаты, всего log k уровней. Про `PriorityQueue` и почему это min-куча — в статье `Top K`.

Замер на .NET 10, 100 массивов по 10 000 случайных чисел, медиана семи прогонов:

| Подход | Время |
| --- | --- |
| последовательное попарное слияние | 88,2 мс |
| куча из голов | 51,2 мс |
| склеить всё и `Array.Sort` | 41,9 мс |

Последний результат стоит знать и честно назвать: на числах в памяти оптимизированная сортировка обгоняет кучу, несмотря на худшую асимптотику, — у кучи дорогая константа на каждую операцию. Ценность кучи в другом: ей не нужны все данные сразу. Она сливает k файлов или сетевых потоков, держа в памяти по одному элементу из каждого.

**Внешняя сортировка.** Именно так сортируют данные, которые не помещаются в память: режут на куски, каждый сортируют в памяти и пишут на диск, потом сливают k-путевым слиянием через кучу. На том же принципе построено слияние сегментов в LSM-хранилищах и сортировка в базах данных при нехватке `work_mem`.

**Слияние связных списков.** Та же логика, но без нового массива: перецепляем узлы, заведя фиктивную голову. O(1) памяти.

## Что стоит ответить на собеседовании

Назвать склейку с сортировкой как базу за O((n + m) log(n + m)) и сразу перейти к двум указателям: меньшая из двух голов идёт в результат, её указатель сдвигается, в конце переносится хвост. O(n + m) времени. Упомянуть, что `<=` делает слияние стабильным.

Сильный ответ решает вариант на месте — заполнение с конца, цикл по оставшимся элементам второго массива, O(1) памяти — и знает слияние k массивов через min-кучу за O(N log k) против O(N·k) у последовательного попарного слияния. И честно оговаривает, что на числах в памяти сортировка склейки может оказаться быстрее кучи, а настоящее применение k-путевого слияния — потоки и внешняя сортировка, где все данные сразу недоступны.
