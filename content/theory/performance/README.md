# Раздел «Производительность» — исходники статей

Статьи трека `.NET Backend` → раздела `performance`. Метаданные — во
фронтматтере каждого файла, тело — markdown под ним.

## Как залить в базу

Скриптом, а не руками по одной:

```bash
node tools/import-theory.mjs --dry-run --dir content/theory/performance

node tools/import-theory.mjs \
  --url http://localhost:5103 \
  --email admin@interview.hypex.site \
  --password 'Admin123!' \
  --dir content/theory/performance

IH_ADMIN_PASSWORD='…' node tools/import-theory.mjs \
  --url https://interview.hypex.site \
  --email admin@hypex.site \
  --dir content/theory/performance --update --publish
```

Первая команда показывает, что будет сделано, вторая заливает локально,
третья — в прод. Пароль для прода передаётся через переменную окружения,
а не флагом: флаг виден в списке процессов и остаётся в history шелла.

По умолчанию статьи создаются **черновиками** и существующие не трогаются.
`--update` обновляет по slug, `--publish` ставит статус «Опубликована».
Привязки к вопросам импорт не стирает: при обновлении они переносятся как есть.

Метаданные берутся из фронтматтера в начале каждого файла — `title`, `slug`,
`track`, `section`, `level`, `sortOrder`, `summary`. `readingMinutes` не задаётся:
его считает `AppDbContext.SaveChangesAsync` (200 слов в минуту, минимум 1).

Импорт идёт через админ-API, а не SQL: так работают валидация, генерация slug
и сброс кэша публичного дерева. После прямого INSERT статья появилась бы
на сайте только через 15 минут и с нулевым временем чтения.

## Файлы и источник правды

**Источник правды — база.** Мелкие правки удобнее делать в админке
(`/admin/theory`). Если правите файл здесь — прогоните импорт с `--update`,
иначе версии разойдутся.

Автоматического сидера, который заливал бы эти файлы при старте, нет
намеренно: он конфликтовал бы с правками из админки, то есть дал бы
два источника правды на один текст. Импорт запускается руками и осознанно.

## Чтобы статьи стали видны гостям

Нужны **оба** условия: статус статьи `Published` и трек `IsPublished = true`.
Трек `dotnet-backend` уже опубликован, так что достаточно опубликовать статьи.

**Импорт берёт один каталог за раз**, поэтому нужен `--dir` — без него
скрипт возьмёт `csharp-lang` и молча не зальёт этот раздел.

## Раздел написан целиком

Все 7 статей по плану (`THEORY_PLAN.md`) написаны. Числа измерены
на .NET 10.0.10 (SDK 10.0.302), Windows 11, AMD Ryzen 7 5800H;
BenchmarkDotNet 0.15.8, `dotnet-counters`, `dotnet-trace`, `dotnet-gcdump`
и `dotnet-dump` версии 10. Что проверялось:

- **BenchmarkDotNet**: разбор строки через `Span` вместо `Split` —
  в 3,7–4,3 раза быстрее и 0 байт против 172 байт на строку;
  `void`-метод с выброшенным `Math.Sqrt` и корень из константы дали
  0,16 и 0,11 нс с предупреждением `ZeroMeasurement` против 3,78 нс
  у честного варианта; суммирование по условию на отсортированных
  данных в 8,7 раза быстрее, чем на случайных; Debug-сборку инструмент
  отказывается запускать; `Job.WithNuGet` в 0.15.8 помечен устаревшим;
- **Stopwatch в цикле**: первые прогоны на Tier 0 в 2–3 раза медленнее
  установившихся, а прогон, в окно которого попала JIT-компиляция,
  занял 19–21 мс против 0,1–0,3 мс у соседей;
- **счётчики**: с .NET 9 `System.Runtime` отдаёт имена вида
  `dotnet.gc.pause.time`; старый `time-in-gc` показал 1% при 9% реального
  времени пауз;
- **dotnet-trace 10**: `--profile cpu-sampling` для `collect` отклоняется;
  десять секунд трассировки — 2,3 МБ по умолчанию, 2,0 МБ с `gc-collect`,
  13,3 МБ с `gc-verbose`;
- **выборка аллокаций**: 139 409 событий `AllocationTick` на 14,9 ГБ —
  в среднем около 100 КБ на событие; утечка давала меньше процента выборки;
- **цена выживаемости**: пятьдесят миллионов одинаковых аллокаций —
  0,3 с, когда объекты умирают сразу, и около 7 с, когда живут чуть дольше;
- **дамп**: `gcdump` вызывает блокирующую сборку — почти секунда на 550 МБ
  кучи; `setthread -t` в SOS 10 принимает только десятичный идентификатор.

Метрики Npgsql 10 (`db.client.connection.count`, `db.client.connection.max`)
и `SetExemplarFilter` из OpenTelemetry .NET 1.9.0 сверены с документацией,
а не измерены: локально нет PostgreSQL и коллектора.

**Грабля замера:** наивный цикл со `Stopwatch` из пяти прогонов
показывает время кода Tier 0, а не оптимизированного. Установившиеся
цифры появляются только после сотни вызовов, и даже тогда разброс
между прогонами — двукратный, поэтому без статистики BenchmarkDotNet
одиночному числу верить нельзя.
