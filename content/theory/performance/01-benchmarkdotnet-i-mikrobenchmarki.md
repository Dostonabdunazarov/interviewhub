Любая оптимизация начинается с числа «было» и заканчивается числом «стало». Если первое число получено неправильно, второе ничего не доказывает. Микробенчмарк — самый дешёвый способ получить такое число для метода и самый лёгкий способ обмануть себя: JIT, кэши процессора и сборщик мусора охотно подменяют измеряемое чем-то другим. Все числа ниже сняты на .NET 10.0.10, BenchmarkDotNet 0.15.8, AMD Ryzen 7 5800H, Windows 11.

## Почему Stopwatch в цикле врёт

Самый частый «бенчмарк» выглядит так: цикл, `Stopwatch`, вывод в консоль. Вот он на тысяче строк, которые разбираются через `Split`, — четыреста прогонов подряд в Release-сборке:

```
прогон 1:     236 мкс
прогон 2:     349 мкс
прогон 5:     350 мкс
прогон 10: 19 014 мкс
прогон 30:    222 мкс
прогон 100:   107 мкс
прогон 400:   142 мкс
```

В этих числах сразу три искажения. Первые десятки прогонов работают на коде Tier 0 — быстро скомпилированном и неоптимизированном; оптимизированная версия с Dynamic PGO появляется только после того, как метод вызван достаточно раз (подробно в статье `CLR, IL и JIT`). Поэтому «время метода» в первых прогонах вдвое-втрое хуже установившегося. Десятый прогон в 80 раз дольше соседей: в его окно попала JIT-компиляция, что подтверждает `JitInfo.GetCompiledMethodCount()` до и после замера. Наконец, установившиеся прогоны скачут от 95 до 235 мкс — без статистики непонятно, какое из этих чисел «правильное».

Поставьте в такой цикл два варианта друг за другом — второй получит фору, потому что общие методы уже прогреты.

## Что BenchmarkDotNet делает за вас

BenchmarkDotNet превращает замер в эксперимент с повторяемой процедурой:

- **отдельный процесс** на каждый бенчмарк — варианты не делят JIT-состояние, кэши и кучу;
- **пилотная стадия** подбирает число вызовов на итерацию, чтобы итерация длилась достаточно долго для точности таймера;
- **прогрев** до установившегося режима, включая переход Tier 0 → Tier 1;
- **вычитание overhead** — отдельно меряется пустой вызов с той же обвязкой;
- **статистика** — среднее, медиана, стандартное отклонение, доверительный интервал, удаление выбросов и предупреждение о многомодальном распределении;
- **валидация** — Debug-сборку он не запустит вовсе.

На Debug-сборке он печатает «Assembly … is non-optimized… Please, build it in RELEASE» и завершается без замеров.

Минимальный корректный бенчмарк сравнивает два способа достать первое число из строки вида `123;4.56;item-7`:

```csharp
[MemoryDiagnoser]
public class ParseBenchmarks
{
    private string[] _lines = default!;

    [Params(100, 10_000)]
    public int Count;

    [GlobalSetup]
    public void Setup()
    {
        var rnd = new Random(42);
        _lines = Enumerable.Range(0, Count)
            .Select(_ => $"{rnd.Next()};{rnd.NextDouble():F4};item-{rnd.Next(1000)}")
            .ToArray();
    }

    [Benchmark(Baseline = true)]
    public long Split()
    {
        long sum = 0;
        foreach (var line in _lines)
            sum += int.Parse(line.Split(';')[0]);
        return sum;
    }

    [Benchmark]
    public long Span()
    {
        long sum = 0;
        foreach (var line in _lines)
        {
            var s = line.AsSpan();
            sum += int.Parse(s[..s.IndexOf(';')]);
        }
        return sum;
    }
}
```

```bash
dotnet run -c Release -- --filter "*ParseBenchmarks*"
```

Результат:

```
| Method | Count | Mean       | StdDev    | Ratio | Gen0     | Allocated |
|------- |------ |-----------:|----------:|------:|---------:|----------:|
| Split  | 100   |   7.540 us |  1.157 us |  1.02 |   2.0447 |   17216 B |
| Span   | 100   |   1.757 us |  0.102 us |  0.24 |        - |         - |
| Split  | 10000 | 669.526 us | 64.067 us |  1.01 | 205.0781 | 1723192 B |
| Span   | 10000 | 179.477 us | 11.823 us |  0.27 |        - |         - |
```

Читать надо не только `Mean`. `Ratio` даёт выигрыш относительно baseline — примерно вчетверо. `Allocated` от `[MemoryDiagnoser]` показывает, что вариант на `Span` не аллоцирует вообще, а `Split` тратит 172 байта на строку: массив и три подстроки. `Gen0` — число сборок Gen 0 на тысячу операций. Для серверного кода эти две колонки часто важнее времени, потому что цена аллокации платится позже, в сборщике, и под нагрузкой (см. `Профилирование аллокаций`). Предупреждение «distribution is bimodal» под таблицей значит, что одно среднее плохо описывает метод, — стоит открыть гистограмму.

## Ловушки, которые обесценивают результат

**Выброшенная работа.** Метод, результат которого никуда не идёт, JIT имеет право не выполнять. Три бенчмарка вокруг `Math.Sqrt`:

```csharp
private double _x = 12345.678;

[Benchmark] public void Discarded() => Math.Sqrt(_x);
[Benchmark] public double Returned() => Math.Sqrt(_x);
[Benchmark] public double Constant() => Math.Sqrt(12345.678);
```

```
| Method    | Mean      |
|---------- |----------:|
| Discarded | 0.1636 ns |
| Returned  | 3.7829 ns |
| Constant  | 0.1071 ns |
```

`Discarded` и `Constant` получили предупреждение `ZeroMeasurement`: «The method duration is indistinguishable from the empty method duration». В первом случае JIT убрал вычисление, результат которого не используется, во втором — вычислил корень из константы при компиляции. Правило простое: возвращать результат из `[Benchmark]` — BenchmarkDotNet сам его потребит. Если результатов несколько в цикле, их передают в `Consumer.Consume`, а входные данные хранят в полях, а не в литералах.

**Подготовка внутри замера.** Генерация данных, `new List`, чтение файла в теле `[Benchmark]` измеряют подготовку, а не код. Её место — `[GlobalSetup]`. `[IterationSetup]`, который вызывается перед каждой итерацией, документация прямо не рекомендует для микробенчмарков: его стоимость и побочные эффекты портят замер операций короче примерно 100 мс.

**Слишком удобные данные.** Предсказатель ветвлений процессора выучивает повторяющийся путь, и `if` становится почти бесплатным. Суммирование элементов больше 128 в массиве из 100 000 чисел:

```
| Method | Mean      | Ratio |
|------- |----------:|------:|
| Sorted |  32.24 us |  1.01 |
| Random | 279.75 us |  8.74 |
```

Тот же код, те же числа, только отсортированные — в 8,7 раза быстрее. Бенчмарк на отсортированных или одинаковых входах измеряет лучший случай, которого в проде не будет. Данные генерируют разнообразными и с фиксированным seed, чтобы прогоны были сравнимы.

**Один размер.** Алгоритм за O(n²) может выиграть на десяти элементах и проиграть на десяти тысячах. `[Params]` с несколькими размерами, похожими на реальные, дешевле, чем ошибочный вывод.

**Шум машины.** Батарея, турбобуст, браузер, виртуалка с соседями. Сравнивают прогоны на одной машине, и разница должна быть заметно больше `StdDev`: 3% при разбросе 5% — шум.

## Что ещё умеет инструмент

- `[DisassemblyDiagnoser]` показывает машинный код: убрал ли JIT проверки границ и заинлайнил ли вызов;
- `[ThreadingDiagnoser]` и `[ExceptionDiagnoser]` считают ожидания на блокировках и исключения на операцию;
- `[EventPipeProfiler(EventPipeProfile.CpuSampling)]` снимает трассировку из процесса бенчмарка — читают её как в `dotnet-counters и dotnet-trace`;
- `[SimpleJob(RuntimeMoniker.Net80)]` или `--runtimes net8.0 net10.0` сравнивают версии рантайма в одной таблице;
- `OperationsPerInvoke` делит время на число операций внутри метода, когда одна операция короче точности обвязки;
- `--job dry` прогоняет каждый бенчмарк один раз — проверить запуск, а не мерить.

`Job.WithNuGet` для сравнения версий пакета в 0.15.8 помечен устаревшим в пользу `WithMsBuildArguments` — примеры из старых статей стоит проверять компилятором.

## Почему выигрыш не доезжает до прода

Бенчмарк меряет метод в стерильных условиях: один поток, данные в кэше L1–L2, предсказуемые ветки, почти пустая куча, профиль PGO под единственный тип. В проде всё это нарушается одновременно.

- **Кэши.** Между вызовами вашего метода чужой код вытесняет данные; таблица поиска, жившая в бенчмарке в L1, в проде даёт промахи.
- **PGO.** В бенчмарке через интерфейсный вызов проходит один тип, и JIT девиртуализирует его. В проде через тот же call site идут пять реализаций, и оптимизация срабатывает хуже.
- **GC.** Процесс бенчмарка работает с Workstation GC — это видно в строке `GC = Concurrent Workstation` его вывода, — а ASP.NET Core по умолчанию с Server GC. 200 байт на вызов в бенчмарке почти бесплатны, а в сервисе, где аллоцируют сотни потоков, — это частые сборки и продвижение объектов из долгих запросов.
- **Конкуренция.** Однопоточный бенчмарк не видит contention на блокировках, false sharing и общую пропускную способность памяти.
- **Доля в запросе.** Самая частая причина. Если запрос длится 40 мс, из которых 28 мс — база и 1 мс — бизнес-логика, то ускорение логики в десять раз даёт 39,1 мс. Закон Амдала не обойти никаким бенчмарком.

Бывает и обратное: бенчмарк показывает «одинаково по времени», а в проде выигрыш заметен. Обычно это значит, что вариант убрал аллокации, и выигрыш проявился через реже случающиеся сборки, а не через время одного вызова.

Отсюда порядок работы: сначала профиль живого сервиса находит горячий метод по inclusive time, затем бенчмарк на реальных, обезличенных данных сравнивает варианты, затем результат подтверждается метриками сервиса — p50 и p99, CPU на запрос, аллокации на запрос — в нагрузочном тесте или на canary. Если метрики сервиса не сдвинулись, оптимизацию разумно откатить ради простоты кода.

## Что стоит ответить на собеседовании

Корректный бенчмарк сравнивает варианты в Release-сборке, без отладчика, с прогревом, на разнообразных реалистичных данных из `[GlobalSetup]`, нескольких размерах через `[Params]`, и каждый результат возвращается из метода, чтобы JIT не выбросил работу. BenchmarkDotNet даёт отдельный процесс, пилотную стадию, прогрев, вычитание overhead и статистику; `[MemoryDiagnoser]` добавляет байты и сборки на операцию, которые для серверного кода важнее наносекунд.

Сильный ответ покажет ловушки на числах: в замере на .NET 10 метод с выброшенным результатом и корень из константы дали по 0,1–0,2 нс против 3,8 нс у честного варианта, а одинаковый код на отсортированных данных оказался в 8,7 раза быстрее, чем на случайных. И объяснит, почему выигрыш из бенчмарка не обязан повториться в проде: другой GC, холодные кэши, полиморфные вызовы, конкуренция и закон Амдала — поэтому бенчмарк стоит между профилем прода и проверкой метриками сервиса, а не заменяет их.
