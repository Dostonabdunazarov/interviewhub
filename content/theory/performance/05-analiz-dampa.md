Профиль аллокаций отвечает на вопрос «кто создаёт», дамп — на вопрос «кто держит». Когда память растёт и не возвращается, нужен именно второй: виновник утечки почти никогда не сам растущий тип, а корень, который его удерживает, — статический кэш, подписка на событие, таймер. Как такие утечки возникают, разобрано в статье `Утечки памяти в managed-коде`; здесь — как их находить в снимке памяти, с выводом реальных команд на .NET 10.0.10.

## Сначала — что именно растёт

Дамп кучи бесполезен, если растёт не куча. Перед снятием стоит сравнить три числа из `dotnet-counters`: размер кучи после последней сборки (`dotnet.gc.last_collection.heap.size`), закоммиченную GC память (`dotnet.gc.last_collection.memory.committed_size`) и working set процесса (`dotnet.process.memory.working_set`).

- Растёт куча — управляемая утечка, дамп поможет.
- Куча стабильна, а working set растёт — нативная память: библиотеки с нативной частью, `HttpClient` на каждый запрос, потоки со своими стеками, фрагментация `malloc`. Управляемые команды её не покажут.
- Committed заметно больше кучи — GC держит память про запас или куча фрагментирована; это не утечка.

И второе условие: рост должен быть неограниченным. Кэш, заполняющийся до лимита, и Server GC, держащий запас, дают плато; утечка — рост без плато, заканчивающийся OOMKilled.

## gcdump или полный дамп

| Инструмент | Что внутри | Цена | Когда |
| --- | --- | --- | --- |
| `dotnet-gcdump` | граф управляемых объектов | маленький файл, но полная блокирующая сборка | «какие типы растут» |
| `dotnet-dump --type Heap` | куча, потоки, стеки, модули | файл порядка размера кучи | `gcroot`, значения полей, стеки |
| `dotnet-dump --type Full` | вся память процесса | файл размером с RSS | нативные проблемы, полный разбор |

Цена `gcdump` не в размере файла, а в паузе. В трассировке GC, снятой во время его работы, видна индуцированная блокирующая Gen 2 на 908 мс при куче около 550 МБ (подробнее — в статье `Диагностика высокого GC`). Полный дамп с кучей в 215 МБ на той же машине записался за 1,7 секунды и занял 236 МБ на диске.

Есть и предел точности. На куче в 850 МБ отчёт `gcdump` показал ровно 10 000 000 объектов — круглое число, которое говорит, что снимок уже не полный. А колонка байт в текстовом отчёте по типам и на маленькой куче не совпадала с реальными размерами: у массивов `byte[200]`, каждый из которых занимает 224 байта, там стояло 24. Для количеств `gcdump` годится, для точных размеров нужен полноценный дамп.

## Шаг первый: что растёт

Утечку ищут сравнением: два-три снимка с интервалом под нагрузкой.

```bash
dotnet-gcdump collect -p 1234 -o t0.gcdump
dotnet-gcdump collect -p 1234 -o t1.gcdump
dotnet-gcdump report t1.gcdump
```

`report` даёт текстовую статистику по типам. В тестовом процессе, который складывал объекты в статический `ConcurrentDictionary`, между снимками с интервалом в двадцать секунд число `OrderDto` выросло с 98 000 до 233 900. Удобное сравнение двух снимков с разницей по числу и размеру объектов каждого типа есть в Visual Studio и PerfView — для настоящего расследования лучше они, чем текстовый отчёт.

## Шаг второй: кто держит

Для цепочки ссылок нужен полноценный дамп и SOS:

```bash
dotnet-dump collect -p 1234 --type Heap -o heap.dmp
dotnet-dump analyze heap.dmp
```

Внутри `analyze` — команды SOS. Начинают с распределения по типам:

```
> dumpheap -stat
          MT     Count   TotalSize Class Name
...
7ffcfd15a8f8   472,000  18,880,000 OrderDto
7ffcfd175ac8   472,000  22,656,000 ConcurrentDictionary<String, OrderDto>+Node
7ffcfcf2dd88 1,080,402  41,003,374 System.String
7ffcfd0335f8   472,001 105,728,024 System.Byte[]
Total 2,731,928 objects, 209,989,806 bytes
```

Сверху `Byte[]` — и это классическая ловушка. `dumpheap -stat` считает собственный размер объекта (shallow size), а не всё, что он удерживает. Массивы и строки почти всегда оказываются наверху, но это следствие: у каждого `OrderDto` есть поле `Payload` на 200 байт. Совпадение счётчиков — 472 000 `OrderDto`, столько же узлов словаря и 472 001 массив — подсказывает, кто здесь владелец.

Вторая ловушка — мёртвые объекты. Дамп снимается между сборками, и в нём лежит мусор, который ещё не собран. Ключ `-live` оставляет только достижимое:

```
> dumpheap -stat -live
7ffcfcf2dd88   945,010  36,454,656 System.String
Total 2,364,136 objects, 189,419,064 bytes
```

Сто тридцать пять тысяч строк исчезли — это был мусор от `Split` в соседнем потоке. Без `-live` их легко принять за утечку.

Дальше — адреса экземпляров и путь до корня:

```
> dumpheap -type OrderDto -short
> gcroot 021501cc0728

HandleTable:
    00000214ff3b13e8 (strong handle)
          -> 0214ffc00028  System.Object[]
          -> 021501c40388  ConcurrentDictionary<String, OrderDto>
          -> 0215071485c0  ConcurrentDictionary<String, OrderDto>+Tables
          -> 021502ca7dc8  ConcurrentDictionary<String, OrderDto>+VolatileNode[]
          -> 02150d329170  ConcurrentDictionary<String, OrderDto>+Node
          -> 021501cc0728  OrderDto
```

`System.Object[]` под strong handle — хранилище статических полей. Ответ: статический словарь без вытеснения. Одна деталь из реального вывода: SOS подписал этот словарь как `static variable: System.Threading.ExecutionContext.s_defaultFlowSuppressed` — имя статического поля в такой цепочке бывает неверным, доверять стоит типам в цепочке, а не подписи.

`gcroot` на большой куче работает долго, поэтому берут несколько случайных экземпляров, а не первый попавшийся: первый может оказаться нетипичным.

## Другие полезные команды

```
> eeheap -gc
> dumpobj 021501cc0728
> finalizequeue
> clrthreads
> setthread -t 85852
> clrstack
```

`eeheap -gc` показывает поколения, сегменты LOH и POH и общий размер кучи. `dumpobj` выводит поля объекта — например, `_size` у `List<T>`, если нужно доказать, что коллекция выросла. `finalizequeue` — объекты, ждущие финализации: если финализатор блокируется, очередь растёт и держит всё, на что ссылается. `clrthreads` даёт соответствие управляемых потоков и OS-идентификаторов; дальше `setthread` и `clrstack` показывают стек конкретного потока. В версии инструмента 10 `setthread -t` принимает OS-идентификатор в десятичном виде — шестнадцатеричный `0x14f5c` из вывода `clrthreads` отклоняется ошибкой разбора, а `85852` работает.

Фрагментация выглядит как утечка, но ею не является: крупные блоки `Free` в `dumpheap -stat` и большой Gen 2 при небольшом числе живых объектов лечатся пулами и меньшим pinning'ом (см. `LOH и фрагментация`).

## Дамп в Kubernetes

В прод-образе обычно нет SDK и shell, а инструментам нужен diagnostic socket в `/tmp` процесса и права на ptrace. Рабочих вариантов три.

**Сайдкар `dotnet-monitor`** с общим томом для сокета и HTTP API — удобнее всего для регулярной диагностики и автоматических правил вида «снять дамп, когда память превысила порог». API обязательно закрывают аутентификацией: в дампе лежат токены, строки подключения и персональные данные.

**Отладочный контейнер** через `kubectl debug --target` — даёт общее пространство процессов, но файловые системы разные, поэтому работоспособность зависит от версии инструментов и прав.

**Дамп при падении** через переменные окружения:

```yaml
env:
  - name: DOTNET_DbgEnableMiniDump
    value: "1"
  - name: DOTNET_DbgMiniDumpType
    value: "2"
  - name: DOTNET_DbgMiniDumpName
    value: /dumps/core.%e.%p.%t
```

Тип `2` — Heap. Дамп пишется при необработанном исключении, но **не при OOMKilled**: SIGKILL от ядра не оставляет процессу шанса. Чтобы получить дамп при нехватке памяти, лимит кучи (`GCHeapHardLimitPercent`) ставят ниже лимита контейнера — тогда процесс получит `OutOfMemoryException` вместо убийства — или используют триггер `dotnet-monitor`.

Подводные камни: процесс заморожен на время записи, и liveness-проба может перезапустить контейнер посреди дампа, поэтому под сначала выводят из балансировки. Full-дамп равен RSS, и запись в слой контейнера тратит `ephemeral-storage`. `emptyDir` с `medium: Memory` засчитывается в лимит памяти пода — дамп на 4 ГБ в tmpfs гарантированно закончится OOMKilled. Анализировать дамп нужно на той же ОС и архитектуре с той же версией рантайма.

## Что стоит ответить на собеседовании

Утечку ищут сравнением снимков: сначала по метрикам убеждаются, что растёт именно управляемая куча и без плато, затем два-три `gcdump` под нагрузкой показывают растущий тип, а полный дамп и `gcroot` по его экземплярам — цепочку до корня. Виновник — корень: статика, подписка на событие, таймер, кэш без лимита.

Сильный ответ назовёт ловушки чтения. `dumpheap -stat` показывает собственный размер, поэтому сверху оказываются `Byte[]` и `String` — следствия, а не причины; в демонстрации на .NET 10 массивы занимали 106 МБ, а держал их статический словарь. Без `-live` в статистику попадает несобранный мусор. `gcdump` вызывает полную блокирующую сборку — в замере почти секунду на 550 МБ кучи, — а при OOMKilled дамп при падении не пишется, и для этого лимит кучи ставят ниже лимита контейнера.
