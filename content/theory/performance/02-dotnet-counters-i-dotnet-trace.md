Когда сервис стал медленнее, первое желание — открыть код и искать «что тут тормозит». Это почти всегда дольше, чем спросить у самого рантайма. Для этого есть два инструмента, которые отвечают на разные вопросы: `dotnet-counters` показывает **что происходит** — числа по CPU, GC, пулу потоков, исключениям, а `dotnet-trace` показывает **где** — стеки и события с отметками времени. Сначала счётчики сужают гипотезу, потом трассировка находит конкретное место.

## Как они подключаются к процессу

Оба инструмента работают через EventPipe — механизм событий, встроенный в рантайм. Отладчик не подключается, процесс не останавливается. Утилита находит diagnostic port процесса (на Linux это Unix-сокет `dotnet-diagnostic-{pid}-…-socket` в `$TMPDIR`, по умолчанию `/tmp`; на Windows — именованный канал) и просит рантайм включить нужные провайдеры событий.

```bash
dotnet tool install --global dotnet-counters
dotnet tool install --global dotnet-trace
dotnet-counters ps
```

`ps` выводит управляемые процессы, к которым можно подключиться. Отсюда же следует главное ограничение в контейнере: инструменту нужен доступ к тому же `/tmp`, что у приложения. В прод-образе без SDK кладут standalone-бинарники инструментов, запускают отладочный контейнер с общим томом или ставят `dotnet-monitor` сайдкаром — подробнее об этом в статье `Анализ дампа`.

## dotnet-counters: картина целиком

Две команды: `monitor` выводит значения в консоль и обновляет их, `collect` пишет в файл для сравнения «до» и «после».

```bash
dotnet-counters monitor -p 1234 --refresh-interval 2 \
  --counters System.Runtime,Microsoft.AspNetCore.Hosting,System.Net.Http

dotnet-counters collect -p 1234 --counters System.Runtime \
  --format csv -o counters.csv --duration 00:00:05:00
```

`--duration` задаётся в формате `dd:hh:mm:ss`. Можно взять не весь провайдер, а отдельные счётчики: `System.Runtime[dotnet.gc.pause.time,dotnet.gc.collections]`.

**Имена зависят от версии рантайма.** До .NET 9 `System.Runtime` публиковал EventCounters с именами вида `time-in-gc`, `alloc-rate`, `threadpool-queue-length`. С .NET 9 появился одноимённый Meter с именами в стиле OpenTelemetry, и свежий `dotnet-counters` предпочитает его. На .NET 10.0.10 в тестовом процессе, который активно аллоцирует, вывод `collect` выглядел так (выдержка):

```
dotnet.gc.collections [gen0]                     213 / с
dotnet.gc.collections [gen1]                      65 / с
dotnet.gc.heap.total_allocated            2 316 960 120 байт / с
dotnet.gc.pause.time                            0,126 с / с
dotnet.gc.last_collection.heap.size [gen2]  383 206 888 байт
dotnet.process.cpu.time [user]                   1,906 с / с
dotnet.thread_pool.queue.length                      0
dotnet.monitor.lock_contentions                      0
```

Старые имена никуда не делись: префикс `EventCounters\System.Runtime` в `--counters` показывает их, если нужно сверить с дашбордом, построенным на старой схеме. В дашбордах Prometheus и Grafana, куда метрики уходят через OpenTelemetry, будут имена из Meter-варианта.

**Ловушка `time-in-gc`.** Старый счётчик называется «% Time in GC since last GC» — доля времени в GC с момента **предыдущей сборки**, а не за интервал. В том же процессе за одно окно в шесть секунд он показал 1%, а соседний счётчик «Time paused by GC» — 86 мс в секунду, то есть почти 9%. Для оценки нагрузки от GC надёжнее накопленное время пауз (`dotnet.gc.pause.time`), а `time-in-gc` годится разве что для тренда.

## Что смотреть первым

Счётчики нужны, чтобы различить четыре гипотезы: процесс упирается в CPU, в GC, в пул потоков или ждёт что-то внешнее.

| Картина | Скорее всего | Куда дальше |
| --- | --- | --- |
| CPU у лимита, паузы GC малы, очередь пула пуста | CPU-bound код | трассировка со стеками |
| CPU высокий, паузы GC 10% и больше, аллокации ГБ/с | давление на GC | статья `Диагностика высокого GC` |
| очередь пула растёт, число потоков растёт ступеньками | thread pool starvation | снимок стеков: `.Result`, `.Wait()`, синхронный I/O |
| CPU низкий, пул в порядке, активных запросов всё больше | ожидание зависимости | статья `База или приложение` |
| working set растёт, куча GC стабильна | неуправляемая память | статья `Анализ дампа` |

Последняя строка таблицы опирается на закон Литтла: число запросов в работе равно интенсивности, умноженной на время обработки. Если RPS прежний, а `http.server.active_requests` растёт, запросы стали дольше, и CPU-профиль этого не объяснит — процесс ждёт.

Starvation и медленная база выглядят похоже по latency, но различаются по пулу: при starvation растёт `dotnet.thread_pool.queue.length` и пул ступеньками добавляет потоки, при медленной базе очередь пустая. Механика инжекции потоков и почему `SetMinThreads` вслепую не лечит — тема раздела про многопоточность.

## dotnet-trace: где именно

`dotnet-trace collect` пишет события в файл `.nettrace`. Начиная с версии инструмента 10 без явного профиля он включает `dotnet-common` (GC, JIT, загрузка сборок, исключения, потоки — уровень Informational) и `dotnet-sampled-thread-time` — периодические снимки стеков управляемых потоков:

```bash
dotnet-trace list-profiles
dotnet-trace collect -p 1234 --duration 00:00:00:30 -o app.nettrace
```

Важная деталь для тех, кто учил по старым статьям: раньше эту роль играл профиль `cpu-sampling`, и `--profile cpu-sampling` встречается во множестве инструкций. В `dotnet-trace` 10 для команды `collect` он отклоняется с ошибкой «does not apply to `dotnet-trace collect`» — теперь это профиль `collect-linux`, который снимает CPU через `perf_events` ядра. На машине со старым инструментом команда по-прежнему работает, так что сначала стоит посмотреть `list-profiles`.

Для GC есть два профиля разной тяжести. Замер на том же процессе, по десять секунд каждый:

```
по умолчанию (dotnet-common + sampled-thread-time):   2,3 МБ
gc-collect (только сборки):                            2,0 МБ
gc-verbose (сборки + выборка аллокаций, Verbose):     13,3 МБ
```

Можно задать провайдер вручную — формат `Провайдер:ключевые_слова:уровень`. Ключевое слово `0x1` — GC, уровень `4` — Informational: только начало и конец сборок с паузами.

```bash
dotnet-trace collect -p 1234 --duration 00:00:01:00 \
  --providers Microsoft-Windows-DotNETRuntime:0x1:4
```

## Как читать трассировку

Быстрый текстовый ответ даёт сам инструмент:

```bash
dotnet-trace report app.nettrace topN -n 8
dotnet-trace report app.nettrace topN -n 8 --inclusive
```

На тестовом процессе с тремя потоками — один спит, один разбирает строки через `Split`, один ищет в `List<int>` — вершина отчёта по exclusive time была такой:

```
1. Thread.Sleep(int32)                          44,84%
2. SpanHelpers.NonPackedIndexOfValueType(...)   24,63%
3. String.SplitInternal(...)                    15,35%
```

В этих трёх строках два урока. Первый: **это время потоков, а не CPU**. Сэмплер снимает стеки всех управляемых потоков, включая спящие и ждущие, поэтому `Thread.Sleep` оказался сверху. Ждущий поток в профиле — нормально; его надо отфильтровать, а не оптимизировать. Второй: `List<T>.Contains` в отчёте нет вообще — он заинлайнен, и время записано на векторизованный поиск внутри. Метод, который вы ищете, может прятаться под чужим именем.

Для настоящего разбора трассировку открывают в PerfView или Visual Studio, а для браузера конвертируют в формат speedscope:

```bash
dotnet-trace convert app.nettrace --format Speedscope
```

Читают сверху вниз по inclusive time (какой запрос или операция дороже) и снизу вверх по exclusive (какой метод реально жжёт процессор). Сэмплер EventPipe видит только управляемые стеки: работу потоков GC и нативного кода он почти не показывает, для неё на Linux нужен `perf` с `DOTNET_PerfMapEnabled=1`.

## Как не уронить прод

EventPipe пишет события в кольцевой буфер внутри процесса (256 МБ по умолчанию, `--buffersize`); если файл не успевает записываться, события теряются, а приложение не блокируется. Опасна не сама трассировка, а её размах:

- **всегда `--duration`** — забытая сессия продолжит писать после отключения;
- **узкие провайдеры** — `Microsoft-Windows-DotNETRuntime` со всеми ключевыми словами на Verbose даёт событие на каждую аллокацию и JIT, это десятки процентов CPU;
- **`gc-verbose` — секундами**, а не минутами: даже в замере выше он в шесть раз тяжелее соседей;
- **диск** — в контейнере файл ложится в эфемерное хранилище, и kubelet может выселить под;
- **один под из N** — снимать на одном экземпляре и сравнивать его p99 с соседями во время записи.

Конвертацию и анализ лучше делать на своей машине, а не на проде: `convert` и PerfView сами по себе требуют CPU и памяти.

## Что стоит ответить на собеседовании

`dotnet-counters` и `dotnet-trace` подключаются к процессу через EventPipe, без отладчика и остановки, поэтому применимы в проде. Счётчики отвечают на вопрос «что происходит» и разделяют гипотезы: CPU-bound код, давление на GC, голодание пула потоков или ожидание внешней зависимости. Трассировка отвечает «где»: стеки и события GC с точными временами. Порядок — сначала счётчики, потом узкая трассировка с ограничением по времени.

Сильный ответ знает детали версий: с .NET 9 `System.Runtime` публикует метрики с именами `dotnet.gc.pause.time`, `dotnet.gc.collections`, `dotnet.thread_pool.queue.length`, а старый `time-in-gc` считает долю с последней сборки и скачет — в замере он показал 1% при 9% реального времени пауз. Он знает, что в `dotnet-trace` 10 `cpu-sampling` для `collect` больше не работает и заменён профилями `dotnet-common` и `dotnet-sampled-thread-time`, а сэмплер показывает время потоков, включая ждущие, и не видит нативный код и работу GC.
