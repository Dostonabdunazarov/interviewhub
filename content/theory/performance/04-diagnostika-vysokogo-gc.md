Высокое время в GC означает, что заметная доля процессора и пауз приложения уходит на сборки, а не на полезную работу. Начинать с переписывания кода — ошибка: сначала нужно понять, **почему** сборщик работает так часто или так долго. Причин три — объём аллокаций, выживаемость объектов и нехватка памяти, — и лечатся они по-разному: кодом, временем жизни объектов или конфигурацией. Механику сборок, поколений и LOH раздел про CLR уже разобрал (`Как работает GC`, `Поколения Gen 0–2`), здесь — как это диагностировать.

## Как читать метрику

Первый сигнал обычно приходит со счётчиков. Как показано в статье `dotnet-counters и dotnet-trace`, старый `time-in-gc` считает долю с момента предыдущей сборки и скачет, поэтому опираться стоит на `dotnet.gc.pause.time` — накопленное время пауз за интервал. Ориентиры для сервиса: до 5% — нормально, 10–20% — стоит разобраться, больше — GC определяет производительность. Для batch-процесса 10% может быть нормой, для API с SLA в 50 мс — нет.

Само по себе число мало что доказывает. Проблема подтверждается **корреляцией**: всплески p99 совпадают по времени с паузами, а CPU, упёршийся в лимит, заметно тратится на сборки. На дашборде рядом должны стоять задержки запросов, время пауз, число сборок по поколениям, CPU и троттлинг контейнера.

## Классифицировать сборки

Следующий шаг — трассировка только с событиями GC. Она дешёвая и даёт по каждой сборке поколение, тип, причину и длительность паузы:

```bash
dotnet-trace collect -p 1234 --profile gc-collect --duration 00:00:02:00
```

В PerfView это отчёт GCStats, программно — `TraceEvent`. Десять секунд трассировки тестового процесса на .NET 10.0.10, аллоцирующего около 1,5 ГБ/с короткоживущих строк, разобранные по группам:

```
gen0  AllocSmall  1734 сборки  медиана 0,24 мс  макс 6,53 мс
gen1  AllocSmall    73 сборки  медиана 0,60 мс  макс 3,11 мс
сумма пауз 501 мс за 10 052 мс
```

Почти две сотни сборок в секунду — и это здоровая картина: Gen 0 стоит доли миллисекунды, потому что почти ничего не выживает, суммарно 5% времени. Частые Gen 0 с короткими паузами — нормальная жизнь .NET-сервиса.

На что смотреть в отчёте:

- **Поколения.** Много Gen 1 и Gen 2 — объекты выживают, это дороже, чем много Gen 0.
- **Тип Gen 2.** Фоновая (background) сборка почти не останавливает приложение; блокирующая, особенно с уплотнением, — длинная пауза.
- **Promoted bytes.** Сколько переживает каждую сборку. Высокое продвижение из Gen 0 — признак объектов «средней жизни».
- **Причина.** `AllocSmall` — исчерпан бюджет Gen 0, обычный случай. `AllocLarge` — бюджет LOH, то есть большие массивы. `LowMemory` — процесс у лимита памяти, GC работает агрессивно, и это проблема лимитов, а не кода. `Induced` — кто-то вызвал `GC.Collect`.

Про `Induced` стоит помнить, что вызвать его может и диагностика. В той же трассировке, снятой во время `dotnet-gcdump collect`, появилась одна строка:

```
gen2  NonConcurrentGC  Induced  1 сборка  пауза 907,91 мс
```

Куча была около 550 МБ, и снимок кучи остановил процесс почти на секунду. Это не повод отказываться от `gcdump`, но повод не снимать его на нагруженном экземпляре в балансировке.

## Выживаемость дороже объёма

Почему продвижение важнее числа аллокаций, видно на простом замере. Пятьдесят миллионов массивов по 64 байта, Workstation GC, .NET 10.0.10. В первом варианте массив сразу становится мусором, во втором он кладётся в кольцевой буфер на миллион элементов и умирает, прожив чуть дольше, чем нужно для пары сборок:

```csharp
for (int i = 0; i < total; i++)
{
    var o = new byte[64];
    if (ring > 0) buf[i % ring] = o;
}
```

```
сразу мусор:       0,3–0,5 с   паузы 9–15 мс      526 сборок Gen 0
живёт в буфере:    6,2–7,8 с   паузы 2,8–3,4 с    597 сборок, все Gen 1+, 71 Gen 2
```

Аллокаций одинаково, а работы в 15–20 раз больше, паузы — в двести. Это и есть mid-life crisis: объекты переживают Gen 0, их копируют и продвигают, они доживают до Gen 2 и умирают там, где сборка дороже всего. В реальном сервисе такие объекты — кэш на минуту, буферизованные тела запросов, данные долгих запросов, большие графы сущностей с отслеживанием изменений.

Отсюда вывод для лечения: при высокой выживаемости уменьшать надо **время жизни**, а не количество аллокаций. Профиль аллокаций из статьи `Профилирование аллокаций` в этом случае покажет не то, что нужно.

## Отсечь конфигурацию

Прежде чем трогать код, стоит убедиться, что GC не борется с окружением:

| Симптом | Что проверить |
| --- | --- |
| `LowMemory`, частые Gen 2, контейнер у лимита | лимит памяти мал для нагрузки; куча по умолчанию получает 75% лимита контейнера |
| Workstation GC на многоядерном сервере | `<ServerGarbageCollection>true</ServerGarbageCollection>`; в ASP.NET Core включено по умолчанию |
| Server GC в поде с одним-двумя CPU | Workstation может оказаться лучше; с .NET 9 DATAS смягчает проблему |
| `Induced` в причинах | вызовы `GC.Collect` в коде и библиотеках |
| длинные блокирующие Gen 2 | не выключен ли `ConcurrentGarbageCollection` |

DATAS (Dynamic Adaptation To Application Sizes) с .NET 9 включён по умолчанию для Server GC: процесс стартует с одной кучи и добавляет их по нагрузке, вместо того чтобы сразу завести кучу на каждое ядро. Без CPU-лимита рантайм видит все ядра ноды, и число куч определяется размером машины, а не пода.

Для переменных окружения есть классическая грабля: числовые значения `DOTNET_GC*` рантайм читает как шестнадцатеричные. `DOTNET_GCHeapCount=10` — это шестнадцать куч, а 60% для `DOTNET_GCHeapHardLimitPercent` записывается как `0x3C`.

Посмотреть, что получилось, можно из самого процесса:

```csharp
var info = GC.GetGCMemoryInfo();
Console.WriteLine($"server={GCSettings.IsServerGC} cpus={Environment.ProcessorCount}");
Console.WriteLine($"available={info.TotalAvailableMemoryBytes >> 20} MB");
Console.WriteLine($"pause={info.PauseTimePercentage:F1}% promoted={info.PromotedBytes >> 20} MB");
```

## Работать с кодом по данным

Когда конфигурация в порядке, выбор зависит от того, что показала классификация:

- **Высокая скорость аллокаций** — топ аллоцирующих стеков по выборке и приёмы из `Снижение аллокаций`.
- **Высокая выживаемость** — искать, что держит объекты дольше запроса: буферизацию, кэши без ограничения размера, `DbContext` с тысячами отслеживаемых сущностей, очереди в памяти.
- **Причина `AllocLarge`** — массивы и строки от 85 000 байт: пулы (`ArrayPool<T>`, `RecyclableMemoryStream`) и стриминг вместо материализации.

Типичный пример последнего — чтение большого ответа через строку:

```csharp
await using var stream = await response.Content.ReadAsStreamAsync(ct);
var page = await JsonSerializer.DeserializeAsync<OrderPage>(stream, JsonOptions, ct);
```

Вариант с `ReadAsStringAsync` создаёт строку на десятки мегабайт прямо в LOH и ещё раз копирует данные из UTF-8 в UTF-16.

Эффект проверяют по тем же метрикам «до» и «после»: аллокации на запрос, частота Gen 2, время пауз, p99. Снижение времени в GC с 25% до 5% обычно сразу видно и по задержкам, и по CPU.

## Чего не делать

Не вызывать `GC.Collect()` «чтобы освободить память» — он старит живые объекты и добавляет длинную блокирующую паузу. Не выключать concurrent GC без замера. Не включать `GCSettings.LatencyMode = SustainedLowLatency` как универсальное лекарство и не крутить размер Gen 0 наугад. Всё это сдвигает проблему, а не решает её.

## Что стоит ответить на собеседовании

Высокое время в GC — симптом, у которого три возможные причины: слишком много аллокаций, слишком долго живущие объекты или нехватка памяти. Диагностика идёт от метрики пауз к трассировке `gc-collect` и отчёту GCStats, где у каждой сборки видны поколение, тип, причина и пауза. `LowMemory` указывает на лимиты, `Induced` — на явный `GC.Collect`, `AllocLarge` — на LOH, а много Gen 1 и Gen 2 — на выживаемость.

Сильный ответ покажет, что выживаемость дороже объёма: в замере на .NET 10 одинаковые пятьдесят миллионов аллокаций стоили 0,3 секунды, когда объекты умирали сразу, и около семи, когда жили чуть дольше, — с паузами в три секунды вместо десятка миллисекунд. Он сначала отсечёт конфигурацию (Server или Workstation, DATAS, лимит контейнера, шестнадцатеричные значения в переменных `DOTNET_GC*`), а потом будет лечить код по данным и проверять результат по p99, а не только по байтам.
