`List<T>` внутри — обычный массив. Вся разница между ними в том, что список умеет расти, и за это умение приходится платить копированием. Понимание механики роста объясняет и совет задавать `capacity`, и то, почему вставка в начало дорогая, и когда стоит взять голый массив.

## Массив: фиксированный размер

Размер массива задаётся при создании и не меняется никогда:

```csharp
int[] numbers = new int[100];
numbers[0] = 1;
// numbers.Add(...) — такого метода нет
```

«Увеличить» массив можно только создав новый и скопировав — этим и занимается `Array.Resize`, несмотря на название:

```csharp
Array.Resize(ref numbers, 200);   // на самом деле новый массив + копирование
```

Массив — единственный объект в куче, элементы лежат подряд. Для значимых типов это даёт отличную локальность: процессор читает соседние элементы пачками в кэш (см. `Стек и куча`).

Многомерные варианты тоже стоит различать:

```csharp
int[,] matrix = new int[10, 10];     // прямоугольный: один объект, 100 элементов подряд
int[][] jagged = new int[10][];      // зубчатый: 11 объектов, строки могут быть разной длины
```

Прямоугольный компактнее, зубчатый быстрее по индексу (у него проще арифметика адреса) и допускает разную длину строк.

## List: массив, который умеет расти

`List<T>` хранит внутренний массив и число занятых элементов. Когда место кончается, он **создаёт новый массив вдвое больше и копирует туда всё**.

Проверено на .NET 10 — как растёт `Capacity` при добавлении 1000 элементов по одному:

```
4, 8, 16, 32, 64, 128, 256, 512, 1024
перевыделений: 9
```

Первое добавление даёт ёмкость 4, дальше — удвоение. Девять перевыделений и девять копирований, чтобы дойти до тысячи.

Удвоение выбрано не случайно: оно даёт **амортизированную O(1)** на добавление. Отдельные операции дорогие (копирование всего массива), но редкие, и в среднем на элемент приходится константа.

## Зачем задавать capacity

Если итоговый размер известен заранее, его стоит указать сразу. Замер на .NET 10, 100 добавлений:

```
new List<int>() без capacity, 100 Add   1184 байта
new List<int>(100), 100 Add              456 байт
```

Разница в 2,6 раза — это выброшенные промежуточные массивы (4, 8, 16, 32, 64 элемента), каждый из которых стал мусором сразу после копирования.

```csharp
var list = new List<int>(expectedCount);      // одна аллокация вместо девяти
```

На больших объёмах эффект заметнее, и там же появляется второй довод: массив на 85 000 байт и больше уезжает в LOH (см. `LOH и фрагментация`), а при удвоении легко проскочить границу незаметно.

Если размер известен только приблизительно — лучше задать с запасом, чем не задавать вовсе. Лишняя память дешевле серии копирований.

Обратная операция тоже существует: `TrimExcess()` ужимает внутренний массив до фактического размера, когда список перестал расти и будет долго жить.

## Доступ по индексу: разницы почти нет

Расхожее «массив быстрее списка» стоит проверить. Миллион обращений по индексу, .NET 10:

```
array[i] в цикле                 7,55 мс
list[i] в цикле                  6,42 мс
IList<int>[i] (через интерфейс)  6,98 мс
```

Разница в пределах погрешности: индексатор `List<T>` — тонкая обёртка, и JIT её встраивает (см. `CLR, IL и JIT`). Выбирать список ради удобства — нормально, потери по скорости доступа нет.

А вот перечисление отличается:

```
foreach по int[]                          0 байт
foreach по List<int> (struct enumerator)  0 байт
foreach по IEnumerable<int> (боксинг)    18,84 байта на элемент
```

Ноль у первых двух: у `List<T>` энумератор — структура, и `foreach` по переменной конкретного типа её не упаковывает. Стоит объявить переменную как `IEnumerable<T>` — и появляются аллокации. Это та же ловушка, что в статье `LINQ и отложенное выполнение`.

## Где список действительно дорог

**Вставка и удаление не в конце.** Элементы приходится сдвигать:

```
List.Insert(0, x)   5,50 мс на 10 000 операций
List.Add(x)         3,70 мс на 10 000 операций
```

На списке из сотни элементов разница невелика, но она растёт линейно с размером: вставка в начало списка из миллиона элементов сдвигает миллион элементов. Если вставки в начало — частая операция, нужна другая структура (см. `LinkedList<T>` и `Выбор коллекции под задачу`).

**`Remove(item)`** сначала ищет элемент линейным перебором, потом сдвигает хвост — то есть O(n) дважды.

**Удаление в цикле** по индексам вперёд пропускает элементы, потому что после удаления всё сдвигается. Правильные варианты:

```csharp
// Идти с конца
for (int i = list.Count - 1; i >= 0; i--)
    if (ShouldRemove(list[i])) list.RemoveAt(i);

// Или одним вызовом
list.RemoveAll(ShouldRemove);
```

`RemoveAll` к тому же эффективнее: он сдвигает всё за один проход, а не на каждое удаление.

## Сколько занимает элемент

Замер на миллионе элементов, .NET 10:

```
List<int> на 1 000 000:  3829 КБ = 3,9 байта на элемент
```

То есть практически ровно `sizeof(int)`: накладные расходы самого списка (заголовок объекта, поля, заголовок массива) размазываются в ничто на большом объёме. Для сравнения, `LinkedList<int>` на том же объёме даёт 48 байт на элемент — в 12 раз больше.

## Что выбрать

**`List<T>`** — по умолчанию. Подходит почти всегда, и оптимизировать стоит только по факту замера.

**`T[]`** — когда размер фиксирован и известен, когда важна максимальная плотность данных, при работе с API, требующими массив, и в многомерных вычислениях.

**`ReadOnlyCollection<T>` / `IReadOnlyList<T>`** — когда коллекцию отдают наружу и менять её нельзя. Важная деталь: возврат `List<T>` из свойства позволяет вызывающему менять внутреннее состояние вашего объекта.

```csharp
public IReadOnlyList<Order> Orders => _orders;   // менять нельзя
```

**`Span<T>` / `Memory<T>`** — для работы с участком массива без копирования (см. `Span<T> и Memory<T>`).

**Коллекционные выражения** (C# 12) работают для обоих и выбирают эффективный способ построения:

```csharp
int[] arr = [1, 2, 3];
List<int> list = [1, 2, 3, .. other];
```

## Что стоит ответить на собеседовании

`List<T>` — обёртка над массивом с автоматическим ростом: при нехватке места создаётся массив вдвое больше и всё копируется. Удвоение даёт амортизированную O(1) на добавление, но каждое перевыделение — это копирование и мусор: 100 добавлений без `capacity` стоят 1184 байта против 456 с заданной ёмкостью (замер на .NET 10, девять перевыделений по пути).

Сильный ответ уточнит, что по скорости доступа по индексу разницы с массивом практически нет — индексатор встраивается JIT-ом, — а реальная цена списка в операциях не с конца: `Insert(0, x)` и `Remove` сдвигают элементы и работают за O(n). И добавит про `foreach`: у `List<T>` энумератор структурный и перечисление бесплатно, но через переменную типа `IEnumerable<T>` он упаковывается и начинает аллоцировать.
