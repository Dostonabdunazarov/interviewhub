`Dictionary<TKey, TValue>` даёт поиск по ключу за O(1) — при условии, что ключи правильно считают хеш. Внутри это массив корзин, и всё поведение словаря, включая неприятное, объясняется этим устройством.

## Устройство

Два массива:

```csharp
int[] _buckets;         // индексы: по хешу → с какой записи начинать
Entry[] _entries;       // сами записи

struct Entry
{
    public uint hashCode;   // сохранённый хеш ключа
    public int next;        // индекс следующей записи в той же корзине, -1 — конец
    public TKey key;
    public TValue value;
}
```

Поиск по ключу:

1. Посчитать `key.GetHashCode()`.
2. Взять остаток от деления на число корзин — получить номер корзины.
3. Пройти по цепочке записей этой корзины, сравнивая **сначала сохранённый хеш** (дёшево), и только при совпадении — `Equals` (дорого).

Сохранённый `hashCode` в записи — важная оптимизация: большинство несовпадений отсеивается сравнением двух чисел, не доходя до `Equals`.

Вставка добавляет запись в `_entries` и вставляет её в начало цепочки нужной корзины. Удаление помечает запись свободной и кладёт её в список свободных мест для переиспользования.

## Коллизии и рост

Две разные записи могут попасть в одну корзину — это коллизия, и она нормальна. Пока цепочки короткие, поиск остаётся почти константным.

Число корзин — **простое число**, и растёт оно тоже по простым. Проверено на .NET 10:

```
рост ёмкости Dictionary до 1000: 3, 7, 17, 37, 89, 197, 431, 919, 1931
```

Простое число берётся, чтобы остаток от деления равномернее распределял даже плохо распределённые хеши. При росте все записи **перераспределяются** по новым корзинам — это полное перехеширование, дорогая операция.

Отсюда тот же совет, что и для списка, только цена ошибки выше:

```
new Dictionary<int,string>() + 100 Add       10 192 байта
new Dictionary<int,string>(100) + 100 Add     3 128 байт
```

Более чем втрое. Задавайте `capacity`, когда знаете примерный размер.

## Чем грозит плохой GetHashCode

Если все ключи дают один хеш, все записи попадают в одну корзину, и цепочка превращается в линейный список. Поиск деградирует из O(1) в **O(n)**.

Замер на .NET 10, 100 000 поисков, `GetHashCode()` возвращает константу:

```
GetHashCode() => 1 (константа)   104,46 мс
нормальный хеш                     9,55 мс
разница: в 11 раз
```

Но важнее не сам множитель, а то, как он зависит от размера коллекции:

```
  100 элементов:   2,44 мс на 20 000 поисков
  500 элементов:  10,77 мс
 1000 элементов:  21,41 мс
 2000 элементов:  40,67 мс
```

Время растёт **линейно с числом элементов** — это и есть выродившийся словарь. На сотне записей проблему не заметить, на десятках тысяч сервис встанет. Поэтому правило из статьи `Equals, GetHashCode и ==` — не формальность: хеш должен различать объекты.

Худший случай эксплуатируют намеренно: hash-flooding, когда атакующий шлёт ключи с одинаковым хешом, чтобы уронить производительность. Для строковых ключей .NET по умолчанию использует **рандомизированное хеширование** — хеш строки различается между запусками процесса. Отсюда важное следствие: **хеш строки нельзя сохранять между запусками** и нельзя использовать как стабильный идентификатор.

## Порядок перечисления не определён

Словарь не гарантирует порядок. Проверено:

```
порядок перечисления: zebra, apple, mango, banana
после Remove("mango") + Add("cherry"): zebra, apple, cherry, banana
```

Новый ключ встал **на место удалённого**, а не в конец — сработал список свободных мест. Порядок выглядит как «порядок вставки», пока не было удалений, и это самая коварная часть: код, случайно полагающийся на порядок, работает месяцами, а ломается после добавления одного `Remove`.

Если порядок нужен — берите структуру, которая его гарантирует: `SortedDictionary`, `List<KeyValuePair<,>>` или явную сортировку при перечислении.

## Компараторы и строковые ключи

Для строковых ключей компаратор стоит задавать явно:

```csharp
new Dictionary<string, int>(StringComparer.Ordinal);            // быстрее всего
new Dictionary<string, int>(StringComparer.OrdinalIgnoreCase);  // без учёта регистра
```

Замеры, 500 000 поисков:

```
Ordinal      13,25 мс
по умолчанию 13,15 мс
IgnoreCase   16,99 мс
```

По умолчанию для строк и так используется порядковое сравнение, поэтому первые две строки совпадают. `OrdinalIgnoreCase` дороже примерно на четверть — это честная цена за нормализацию регистра, и она всё равно выгоднее, чем `ToLower()` на каждом обращении (лишняя строка плюс зависимость от культуры, см. `Строки и StringBuilder`).

Главное — **не использовать культурное сравнение для технических ключей**: результат будет зависеть от локали сервера.

Для своего типа-ключа можно передать компаратор вместо переопределения `Equals`/`GetHashCode`:

```csharp
new Dictionary<Point, string>(new PointComparer());
```

И напоминание из статьи про равенство: структура-ключ без `IEquatable<T>` стоит 72 байта мусора на каждый `TryGetValue` из-за упаковки.

## Ключ должен быть неизменяемым

Если поле, участвующее в хеше, поменялось после вставки, запись теряется: она лежит в корзине, посчитанной по старому хешу.

```csharp
var key = new MutableKey { Value = 1 };
dict[key] = "данные";
key.Value = 2;
dict.ContainsKey(key);   // false — хотя это тот же объект
```

Правило: ключ либо неизменяемый тип (`string`, `int`, `Guid`, `record` без изменяемых полей), либо изменяемый объект, чьи хеш-поля после вставки никто не трогает.

## Потребление памяти

```
Dictionary<int,int> на 1 000 000: 22 708 КБ = 23,3 байта на элемент
List<int> на 1 000 000:            3 829 КБ =  3,9 байта на элемент
```

Почти в шесть раз больше на элемент: запись хранит хеш (4 байта), ссылку на следующую (4), ключ и значение, плюс массив корзин и запас ёмкости. Это нормальная плата за O(1)-поиск, но её стоит учитывать, когда элементов миллионы.

## Полезные приёмы

```csharp
// Одна операция вместо двух поисков
if (dict.TryGetValue(key, out var value)) { }

// Добавить, только если нет
dict.TryAdd(key, value);

// Значение по умолчанию без исключения
var v = dict.GetValueOrDefault(key, fallback);

// Ссылка на значение — изменение на месте, без второго поиска
ref var slot = ref CollectionsMarshal.GetValueRefOrAddDefault(dict, key, out bool exists);
slot++;
```

Последний приём из `CollectionsMarshal` полезен для счётчиков: классическое `dict[key] = dict.GetValueOrDefault(key) + 1` делает два поиска, а этот — один.

Индексатор и `Add` различаются: `dict[key] = v` перезаписывает молча, `dict.Add(key, v)` бросает исключение при дубликате. Выбирайте осознанно.

## Что стоит ответить на собеседовании

`Dictionary` — массив корзин плюс массив записей: по хешу ключа вычисляется номер корзины, внутри неё записи связаны в цепочку, и сравнение идёт сначала по сохранённому хешу, а уже потом через `Equals`. Число корзин — простое число, при исчерпании ёмкости происходит рост с полным перехешированием, поэтому задавать `capacity` заметно выгоднее: 100 вставок стоят 3128 байт против 10 192 без него.

Сильный ответ объяснит деградацию: одинаковый хеш у всех ключей складывает их в одну корзину и превращает поиск в линейный — на .NET 10 это 11-кратное замедление на тысяче элементов, причём время растёт пропорционально их количеству. И добавит, что порядок перечисления не определён и после удаления новый ключ занимает освободившееся место в середине, а хеш строки рандомизирован между запусками процесса, поэтому сохранять его или считать стабильным идентификатором нельзя.
