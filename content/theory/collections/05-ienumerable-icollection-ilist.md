Интерфейсы коллекций образуют лестницу: каждый следующий добавляет возможности к предыдущему. Выбор правильной ступеньки для параметра и возвращаемого значения — обычный вопрос на собеседовании и ежедневное решение в коде.

## Лестница

```
IEnumerable<T>          перечислить
  └ ICollection<T>      + Count, Add, Remove, Contains
      └ IList<T>        + индексатор, Insert, RemoveAt
```

И отдельная ветка только для чтения:

```
IReadOnlyCollection<T>  Count + перечисление
  └ IReadOnlyList<T>    + индексатор по чтению
```

**`IEnumerable<T>`** — минимум: только обход вперёд, по одному элементу.

```csharp
public interface IEnumerable<out T> : IEnumerable
{
    IEnumerator<T> GetEnumerator();
}
```

Ни размера, ни индекса, ни изменения. Зато он ковариантен (`out T`) — `IEnumerable<string>` можно передать как `IEnumerable<object>` (см. `Ковариантность и контравариантность`) — и может представлять поток, который вычисляется на ходу или бесконечен.

**`ICollection<T>`** добавляет `Count`, `Add`, `Remove`, `Contains`, `Clear` и `IsReadOnly`. Появляется известный размер — значит, коллекция конечна и уже существует.

**`IList<T>`** добавляет доступ по индексу и вставку/удаление по позиции. Появляется порядок.

**`IReadOnlyList<T>`** — индексатор и `Count`, но без изменения. Ковариантен, в отличие от `IList<T>`, и это важное практическое отличие: `IReadOnlyList<string>` присваивается `IReadOnlyList<object>`, а `IList<string>` — нет.

## Что принимать параметром

Правило — **самый слабый интерфейс, которого хватает**. Метод, которому нужно только перечислить, должен принимать `IEnumerable<T>`: тогда ему можно передать список, массив, множество и результат LINQ-запроса.

```csharp
// Хорошо: примет что угодно перечисляемое
decimal Total(IEnumerable<Order> orders) => orders.Sum(o => o.Amount);

// Плохо: заставляет вызывающего делать ToList()
decimal Total(List<Order> orders) => orders.Sum(o => o.Amount);
```

Но у этого правила есть важная оговорка, о которой часто забывают.

**Если метод перечисляет аргумент дважды — `IEnumerable<T>` опасен.** Переданный запрос выполнится дважды (см. `LINQ и отложенное выполнение`), а одноразовая последовательность во второй раз окажется пустой:

```csharp
// Ловушка: два прохода по возможно-ленивой последовательности
decimal Average(IEnumerable<Order> orders)
{
    if (!orders.Any()) return 0;             // проход 1
    return orders.Sum(o => o.Amount) / orders.Count();  // проходы 2 и 3
}
```

Здесь честнее попросить материализованную коллекцию:

```csharp
decimal Average(IReadOnlyCollection<Order> orders)   // Count бесплатен, повторный обход безопасен
```

Сигнатура становится документацией: «мне нужна готовая коллекция, а не ленивый запрос».

## Что возвращать

Здесь правило обратное — **возвращать нужно достаточно конкретный тип**, чтобы вызывающий мог с ним работать, но не раскрывающий внутренности.

**`IEnumerable<T>` как результат — частый источник проблем.** Он не говорит, выполнен ли запрос:

```csharp
public IEnumerable<Order> GetOrders() => _db.Orders.Where(o => o.IsActive);
```

Вызывающий не знает, что каждое перечисление — поход в базу, а после закрытия контекста он получит `ObjectDisposedException`. Об этом же — в статье `IEnumerable vs IQueryable`.

**`IReadOnlyList<T>` — обычно лучший выбор** для результата: говорит «коллекция готова, порядок есть, менять нельзя».

```csharp
public IReadOnlyList<Order> GetOrders() => _orders.ToList();
```

**`List<T>` наружу возвращать не стоит**, особенно из свойства: вызывающий сможет менять внутреннее состояние вашего объекта.

```csharp
// Плохо: чужой код может сделать Orders.Clear()
public List<Order> Orders => _orders;

// Хорошо
public IReadOnlyList<Order> Orders => _orders;
```

Тонкость: `IReadOnlyList<T>` защищает от изменения **через этот интерфейс**, но не делает коллекцию неизменяемой — обладатель исходного `List<T>` по-прежнему может её менять, а вызывающий может привести тип обратно. Настоящая неизменяемость — это `ImmutableArray<T>`/`ImmutableList<T>` или `ReadOnlyCollection<T>` как обёртка:

```csharp
public IReadOnlyList<Order> Orders => _orders.AsReadOnly();
```

## Перечисление и его цена

`foreach` не требует интерфейса вовсе — компилятору достаточно метода `GetEnumerator()` с нужной формой (как и `await` не требует интерфейса, см. `State machine`). Благодаря этому `List<T>` отдаёт структурный энумератор, и перечисление не аллоцирует.

Но стоит объявить переменную интерфейсом — и энумератор упакуется:

```
foreach по List<int>                      0 байт
foreach по IEnumerable<int>              18,84 байта на элемент
```

Поэтому в горячем коде тип переменной не стоит поднимать до интерфейса без нужды. В обычном коде разница несущественна.

Доступ по индексу через интерфейс почти бесплатен — замер показал 6,98 мс против 6,42 мс у `List<int>` на миллион операций, то есть разница в пределах погрешности.

## Проверка возможностей в рантайме

`ICollection<T>.IsReadOnly` существует, потому что интерфейс реализуют и неизменяемые коллекции: массив как `IList<T>` бросит исключение на `Add`. Это классический пример нарушения принципа подстановки Лисков в самой платформе — тип реализует интерфейс, но не поддерживает его контракт.

```csharp
IList<int> list = new[] { 1, 2, 3 };
list[0] = 42;      // работает
list.Add(4);       // NotSupportedException
```

LINQ пользуется проверками типов для быстрых путей: `Count()` для `ICollection<T>` берёт `Count` вместо перечисления, `ElementAt` для `IList<T>` — индексатор. Отсюда и совет возвращать материализованную коллекцию: она позволяет этим оптимизациям сработать.

## Необобщённые версии

`IEnumerable`, `ICollection`, `IList` без параметра типа остались с .NET 1.0. Работают через `object`, то есть упаковывают значимые типы, и типобезопасности не дают. В новом коде не нужны; встречаются только при взаимодействии со старым API.

## Короткая памятка

| Задача | Тип |
| --- | --- |
| Параметр, один проход | `IEnumerable<T>` |
| Параметр, несколько проходов или нужен `Count` | `IReadOnlyCollection<T>` |
| Параметр, нужен доступ по индексу | `IReadOnlyList<T>` |
| Параметр, метод пополняет коллекцию | `ICollection<T>` |
| Результат метода | `IReadOnlyList<T>` (материализованный) |
| Свойство-коллекция | `IReadOnlyList<T>` |
| Ленивый поток, который так и задуман | `IEnumerable<T>` + имя, говорящее об этом |
| Асинхронный поток | `IAsyncEnumerable<T>` |

## Что стоит ответить на собеседовании

Интерфейсы образуют иерархию: `IEnumerable<T>` даёт только перечисление, `ICollection<T>` добавляет `Count` и изменение, `IList<T>` — доступ по индексу; параллельно есть ветка только для чтения с `IReadOnlyCollection<T>` и `IReadOnlyList<T>`. Для параметра берут самый слабый достаточный интерфейс, чтобы метод принимал и список, и массив, и результат запроса.

Сильный ответ назовёт исключение из этого правила: если метод проходит по аргументу дважды, `IEnumerable<T>` опасен — ленивый запрос выполнится повторно, — и честнее принимать `IReadOnlyCollection<T>`. И добавит про возврат: `IEnumerable<T>` как результат скрывает, выполнен ли запрос, и приводит к обращениям к базе из чужого кода, поэтому возвращать лучше материализованный `IReadOnlyList<T>`, а `List<T>` из свойства отдавать не стоит — вызывающий сможет менять внутреннее состояние объекта.
