Эта статья собирает раздел воедино: какая коллекция под какую задачу, с измеренными числами вместо общих слов. Правило, которое стоит держать в голове с самого начала: **по умолчанию `List<T>` и `Dictionary<TKey,TValue>`**, а всё остальное — под конкретную задачу и желательно после замера.

## Сложности операций

| Коллекция | Доступ по индексу | Поиск значения | Вставка в конец | Вставка в середину | Удаление |
| --- | --- | --- | --- | --- | --- |
| `T[]` | O(1) | O(n) | — | — | — |
| `List<T>` | O(1) | O(n) | O(1)* | O(n) | O(n) |
| `LinkedList<T>` | — | O(n) | O(1) | O(1)** | O(1)** |
| `Dictionary<K,V>` | — | O(1)*** | O(1)* | — | O(1) |
| `HashSet<T>` | — | O(1)*** | O(1)* | — | O(1) |
| `SortedDictionary<K,V>` | — | O(log n) | O(log n) | — | O(log n) |
| `SortedList<K,V>` | O(1) | O(log n) | O(n) | O(n) | O(n) |
| `Queue<T>` / `Stack<T>` | — | O(n) | O(1)* | — | O(1) |

\* амортизированно: изредка происходит перевыделение с копированием
\*\* при наличии узла; поиск узла — O(n)
\*\*\* при хорошем хеше; при плохом деградирует до O(n)

Числа из замеров на .NET 10, чтобы таблица не была абстрактной:

```
поиск в коллекции из 1000, 100 000 операций:
  List.Contains          9,95 мс
  Dictionary/HashSet     1,29 мс

поиск, 1 000 000 операций:
  Dictionary          14,32 мс
  FrozenDictionary    13,65 мс
  SortedDictionary    22,96 мс
```

## Выбор по задаче

**Просто хранить и перебирать** → `List<T>`. Задавайте `capacity`, если размер известен.

**Искать по ключу** → `Dictionary<TKey, TValue>`.

**Проверять вхождение, хранить уникальные** → `HashSet<T>`.

**Очередь задач (FIFO)** → `Queue<T>`. Внутри кольцевой массив, дёшево и компактно.

**Стек (LIFO)** → `Stack<T>`.

**Всегда брать минимальный/максимальный** → `PriorityQueue<TElement, TPriority>` (с .NET 6):

```csharp
var pq = new PriorityQueue<Job, int>();
pq.Enqueue(job, priority);
var next = pq.Dequeue();     // всегда с наименьшим приоритетом
```

**Хранить в отсортированном виде** → `SortedDictionary` (дерево, быстрая вставка) или `SortedList` (два массива, компактнее и быстрее по индексу, но вставка O(n)). Для набора без значений — `SortedSet<T>` с диапазонными запросами через `GetViewBetween`.

**Много значений на один ключ** → `ILookup` из `ToLookup()` для готовых данных или `Dictionary<K, List<V>>`, если нужно пополнять.

**Двусторонняя очередь, вставки по узлам** → `LinkedList<T>`, помня про 48 байт на элемент (см. `LinkedList<T>`).

## Неизменяемые и замороженные

**`ImmutableArray<T>` / `ImmutableList<T>`** — настоящая неизменяемость: любая «модификация» возвращает новую коллекцию. Безопасны для многопоточного чтения без блокировок. Цена видна в замере:

```
ImmutableDictionary.TryGetValue   141,86 мс на 1 000 000
Dictionary.TryGetValue             14,32 мс
```

В десять раз медленнее, потому что внутри дерево, а не хеш-таблица. Берите их, когда важна именно неизменяемость структуры, а не скорость чтения. `ImmutableArray<T>` при этом читается так же быстро, как массив, — дорого обходится только изменение.

**`FrozenDictionary<K,V>` / `FrozenSet<T>`** (с .NET 8) — для случая «построили один раз, дальше только читаем». При создании тратится время на подбор оптимальной раскладки, зато чтение быстрее обычного словаря:

```
FrozenDictionary   13,65 мс
Dictionary         14,32 мс
```

Выигрыш на целочисленных ключах скромный, на строковых заметнее. Идеальный случай — справочники и конфигурация, загруженные на старте:

```csharp
static readonly FrozenDictionary<string, Handler> Handlers =
    BuildHandlers().ToFrozenDictionary(StringComparer.OrdinalIgnoreCase);
```

Строить `Frozen`-коллекцию в цикле или на каждый запрос нельзя — создание дороже обычного словаря.

## Потокобезопасные

Обычные коллекции **не потокобезопасны**, и одновременная запись из двух потоков портит внутренние структуры — вплоть до зацикливания при чтении.

**`ConcurrentDictionary<K,V>`** — основной рабочий вариант:

```
ConcurrentDictionary.TryGetValue   36,86 мс на 1 000 000
Dictionary.TryGetValue             14,32 мс
```

Примерно вдвое-втрое дороже на чтение — честная цена за безопасность. Важная тонкость: `GetOrAdd` **не гарантирует**, что фабрика вызовется один раз, — при гонке её могут выполнить несколько потоков, хотя сохранится только одно значение. Если создание дорогое или с побочным эффектом, оборачивайте в `Lazy<T>`:

```csharp
var value = _cache.GetOrAdd(key, k => new Lazy<Data>(() => Load(k))).Value;
```

**`ConcurrentQueue<T>` / `ConcurrentStack<T>` / `ConcurrentBag<T>`** — очередь, стек и неупорядоченная сумка для сценария «много производителей».

**`BlockingCollection<T>`** — производитель-потребитель с ограничением размера и блокировкой.

**`Channel<T>`** — современная замена `BlockingCollection` для асинхронного кода, работает с `await` и `IAsyncEnumerable` (см. `IAsyncEnumerable`):

```csharp
var channel = Channel.CreateBounded<Message>(capacity: 100);
await channel.Writer.WriteAsync(message);
await foreach (var m in channel.Reader.ReadAllAsync(token)) { }
```

**Множества в многопоточном коде**: готового `ConcurrentHashSet` нет, используют `ConcurrentDictionary<T, byte>`.

Отдельно стоит помнить: если коллекция только читается после инициализации, потокобезопасный вариант не нужен — достаточно не менять её после публикации, а ещё лучше взять `Frozen` или `Immutable`.

## Типовые ошибки выбора

**`List.Contains` в цикле.** Классическая O(n²), которая незаметна на тестовых данных и убивает продакшен. Лечится `HashSet`.

**`Dictionary` без `capacity` при известном размере** — лишние перехеширования: 10 192 байта против 3128 на сотне вставок.

**Структура-ключ без `IEquatable<T>`** — упаковка на каждом поиске, 72 байта мусора (см. `Equals, GetHashCode и ==`).

**Плохой `GetHashCode`** — деградация до линейного поиска: 11-кратное замедление на тысяче элементов, растущее вместе с их числом.

**`ConcurrentDictionary` там, где нет конкуренции** — лишние накладные расходы ради безопасности, которая не нужна.

**Обычная коллекция там, где конкуренция есть** — редкие, невоспроизводимые баги.

**`LinkedList` «потому что вставка O(1)»** — без ссылок на узлы преимущества нет, а память в 12 раз больше.

**`ImmutableList` в горячем чтении** — в десять раз медленнее словаря.

**Изменение коллекции во время `foreach`** — `InvalidOperationException`. Собирайте изменения отдельно или идите по индексам с конца.

## Порядок принятия решения

1. **Как ищем?** По ключу — словарь. По индексу — список. Всё подряд — любая.
2. **Нужна ли уникальность?** Да — множество.
3. **Нужен ли порядок?** Порядок вставки — список. Сортировка — `Sorted*`. Не нужен — хеш-коллекции.
4. **Меняется ли после создания?** Нет — `Frozen`/`Immutable`.
5. **Есть ли конкуренция?** Да — `Concurrent*` или `Channel`.
6. **Известен ли размер?** Да — задайте `capacity`.

Если после этого осталось несколько вариантов — берите более простой и замерьте, когда и если станет узким местом.

## Что стоит ответить на собеседовании

Выбор определяется главной операцией: поиск по ключу — `Dictionary` (O(1) против O(n) у `List.Contains`, на тысяче элементов это 1,29 мс против 9,95 на 100 000 проверок), уникальность — `HashSet`, порядок вставки и доступ по индексу — `List`, FIFO/LIFO — `Queue`/`Stack`, «взять минимальный» — `PriorityQueue`. По умолчанию `List` и `Dictionary`, остальное — под конкретную задачу.

Сильный ответ добавит слой поверх: `FrozenDictionary` для справочников, которые строятся один раз и дальше только читаются; `Immutable*` — когда нужна именно неизменяемость, с оговоркой, что чтение у `ImmutableDictionary` примерно в десять раз медленнее обычного; `ConcurrentDictionary` при реальной конкуренции, с памяткой, что его `GetOrAdd` может выполнить фабрику несколько раз, и потому дорогое создание заворачивают в `Lazy<T>`.
