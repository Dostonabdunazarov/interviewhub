`LinkedList<T>` — двусвязный список: каждый элемент лежит в отдельном узле со ссылками на соседей. В учебниках он подаётся как структура с дешёвой вставкой, и это правда. На практике он почти всегда проигрывает `List<T>` — и полезно понимать, почему.

## Устройство

```csharp
public sealed class LinkedListNode<T>
{
    public T Value;
    public LinkedListNode<T>? Next;
    public LinkedListNode<T>? Previous;
    public LinkedList<T>? List;
}
```

Каждый элемент — **отдельный объект в куче**, разбросанный по памяти. Сам список хранит только ссылку на первый узел и счётчик.

Отсюда все свойства: вставка и удаление по известному узлу переставляют пару ссылок и не двигают остальные элементы, зато доступа по индексу нет вовсе, а элементы лежат не подряд.

## Честная цена

Замеры на .NET 10 сразу показывают масштаб платы.

**Память на элемент:**

```
List<int> на 1 000 000:        3 829 КБ =  3,9 байта на элемент
LinkedList<int> на 1 000 000: 46 857 КБ = 48,0 байта на элемент
```

В **12 раз** больше. Считается это просто: узел — объект с заголовком (16 байт), значением и двумя ссылками по 8 байт (см. `Стек и куча`), плюс сама ссылка на узел.

**Создание:**

```
LinkedList<int>, 100 AddLast   4840 байт
List<int>, 100 Add             1184 байта
```

Каждый `AddLast` — это аллокация узла, то есть работа для сборщика мусора на каждый элемент, а не одно перевыделение массива на десяток добавлений.

**Обход:**

```
LinkedList: foreach по 1000    146,57 мс на 10 000 обходов
List: foreach по 1000          115,64 мс
```

Список быстрее, хотя алгоритмически обе операции O(n). Причина — локальность: элементы `List<T>` лежат подряд и читаются процессором пачками в кэш, а узлы связного списка раскиданы по куче, и каждый переход по ссылке рискует промахнуться мимо кэша.

## Где он действительно быстр

Единственное настоящее преимущество — вставка и удаление **по уже имеющемуся узлу**:

```
LinkedList.AddAfter(узел)   5,58 мс на 100 000 операций
```

Это честная O(1), не зависящая от размера списка. У `List<T>` вставка в середину сдвигает хвост, то есть O(n).

Ключевое слово — «по имеющемуся узлу». Если узел надо сначала **найти**, преимущество исчезает: поиск в связном списке линейный, и суммарно получается та же O(n), только с худшей локальностью.

```csharp
// O(1) — узел уже есть
list.AddAfter(node, newValue);
list.Remove(node);

// O(n) — сначала поиск
var node = list.Find(value);   // перебор
list.AddAfter(node, newValue);
```

Поэтому `LinkedList` окупается только там, где ссылки на узлы **хранятся отдельно** и вставки/удаления происходят часто.

## Канонический пример: LRU-кэш

Классическое применение, где связный список на месте, — кэш с вытеснением давно не использованных. Нужны две операции: найти элемент за O(1) и переместить его в начало за O(1).

```csharp
public sealed class LruCache<TKey, TValue> where TKey : notnull
{
    readonly int _capacity;
    readonly Dictionary<TKey, LinkedListNode<(TKey Key, TValue Value)>> _map;
    readonly LinkedList<(TKey Key, TValue Value)> _order = new();

    public LruCache(int capacity)
    {
        _capacity = capacity;
        _map = new Dictionary<TKey, LinkedListNode<(TKey, TValue)>>(capacity);
    }

    public bool TryGet(TKey key, out TValue value)
    {
        if (!_map.TryGetValue(key, out var node)) { value = default!; return false; }

        _order.Remove(node);            // O(1): узел на руках
        _order.AddFirst(node);          // O(1): переиспользуем тот же узел
        value = node.Value.Value;
        return true;
    }

    public void Add(TKey key, TValue value)
    {
        if (_map.Count >= _capacity)
        {
            var oldest = _order.Last!;  // O(1)
            _order.RemoveLast();
            _map.Remove(oldest.Value.Key);
        }
        _map[key] = _order.AddFirst((key, value));
    }
}
```

Работает это именно потому, что словарь хранит **узлы**, а не значения: перемещение в начало не требует поиска. Ни `List`, ни `Queue` так не умеют — у них удаление из середины сдвигает элементы.

Заметьте деталь: `_order.Remove(node)` и `AddFirst(node)` переиспользуют существующий узел, не аллоцируя новый.

## Чего у него нет

**Доступа по индексу.** Ни `list[5]`, ни `IList<T>`. Есть только `First`, `Last` и обход по ссылкам.

**Сортировки на месте.** `List.Sort()` есть, у связного списка — нет.

**`Span<T>`, `AsSpan`, `CollectionsMarshal`** — всё, что требует непрерывной памяти, неприменимо.

**Эффективного LINQ.** Операторы работают, но каждый обход — прыжки по указателям.

## Альтернативы, которые обычно лучше

**Очередь с двух концов** — `Queue<T>` (FIFO) и `Stack<T>` (LIFO) внутри кольцевые массивы, они быстрее и компактнее:

```
Queue: 100 Enqueue+Dequeue   1192 байта
Stack: 100 Push+Pop          1184 байта
LinkedList: 100 AddLast      4840 байт
```

**Приоритетная очередь** — `PriorityQueue<TElement, TPriority>` (с .NET 6) для «взять минимальный».

**Много вставок в начало** — иногда проще собрать список в обратном порядке и один раз развернуть.

**Частое удаление из середины по условию** — `List.RemoveAll` делает это за один проход, что на практике быстрее связного списка из-за локальности.

## Когда всё-таки брать

Список получается коротким:

- нужны ссылки на узлы и вставка/удаление по ним (LRU и подобные структуры);
- реализуется алгоритм, где узлы перемещаются между списками;
- элементы очень большие, и копирование при сдвиге действительно дороже прыжков по ссылкам;
- нужен стабильный «адрес» элемента: узел не меняется при изменении списка, в отличие от индекса.

Во всех остальных случаях разумная позиция — брать `List<T>`, а `LinkedList<T>` доставать только под конкретную задачу с измеренной выгодой.

## Что стоит ответить на собеседовании

`LinkedList<T>` — двусвязный список из отдельных узлов: вставка и удаление по уже имеющемуся узлу стоят O(1), но доступа по индексу нет, а поиск линейный. На практике он почти всегда проигрывает `List<T>`, потому что каждый узел — объект в куче: на .NET 10 это 48 байт на элемент против 3,9 у списка, аллокация на каждое добавление и худшая локальность — обход 1000 элементов вышел медленнее списка (146 мс против 115 на 10 000 повторов), хотя обе операции O(n).

Сильный ответ уточнит, что теоретическое преимущество реализуется только когда узел уже на руках: если его нужно найти, поиск съедает выигрыш. И приведёт канонический случай — LRU-кэш, где `Dictionary` хранит именно узлы, благодаря чему перемещение элемента в начало списка обходится без поиска.
