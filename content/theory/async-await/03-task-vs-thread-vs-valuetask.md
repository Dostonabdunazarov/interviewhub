`Thread`, `Task` и `ValueTask` часто ставят в один ряд, хотя это сущности разного уровня. `Thread` — поток операционной системы. `Task` — **обещание результата**, которое может вообще не потребовать потока. `ValueTask` — способ не платить за это обещание, когда результат уже есть.

## Thread: дорогой ресурс ОС

`Thread` — обёртка над потоком операционной системы. Создание стоит дорого: ядру нужно завести структуры планирования и **зарезервировать стек — около 1,5 МБ адресного пространства по умолчанию** (см. `Стек и куча`).

```csharp
var thread = new Thread(() => DoWork());
thread.Start();
thread.Join();
```

Замер на .NET 10 — 200 живых потоков:

```
managed-память: +48 КБ
адресное пространство: ~300 МБ (по 1,5 МБ стека на поток)
```

Managed-память почти не растёт, и это обманчиво: в профилировщике кучи такие потоки почти не видны, а адресное пространство и планировщик ОС нагружены всерьёз. Тысяча потоков — полтора гигабайта зарезервированного адресного пространства плюс постоянные переключения контекста.

Прямой `new Thread` сегодня нужен редко. Оправданные случаи: долгоживущий фоновый цикл на всё время работы процесса, поток с нестандартным размером стека или приоритетом, COM-совместимость с `SetApartmentState`. Для всего остального есть пул.

## Пул потоков

Пул переиспользует потоки: задача становится в очередь, свободный поток её берёт, по завершении возвращается в пул. Создавать и уничтожать потоки не приходится.

```csharp
await Task.Run(() => HeavyCalculation());
```

Пул растёт не мгновенно — он добавляет потоки постепенно, оценивая пропускную способность. В замере `ThreadPool.GetMinThreads` дал **16** (по числу ядер), и именно постепенный рост объясняет неожиданный на первый взгляд результат:

```
1000 x new Thread(Sleep 10):            138 мс
1000 x Task.Run(Sleep 10) (блокировка):  970 мс
1000 x Task.Delay(10) (без блокировки):   15 мс
```

`Task.Run` **проиграл** прямому созданию потоков в семь раз. Это не аргумент в пользу `new Thread` — это демонстрация того, что **блокировать потоки пула нельзя**. Тысяча заблокированных задач исчерпала пул, и он медленно добавлял потоки по мере необходимости. Третья строка показывает, как должно быть: то же количество ожиданий без блокировки — 15 мс.

Вывод, который стоит запомнить: пул рассчитан на **короткие неблокирующие** задачи. Блокировка его потока — это отъём ресурса у всего приложения, и типовой способ устроить голодание пула (см. `Дедлоки на .Result`).

## Task: обещание, а не поток

Главное заблуждение: «`Task` — это поток» или «`Task` выполняется в фоне». `Task` — **объект-обещание**: он описывает операцию, которая когда-нибудь завершится результатом или ошибкой. Потока за ним может не быть вовсе.

Два принципиально разных источника задач:

```csharp
// 1. Задача, выполняемая на потоке пула — здесь поток нужен
Task<int> compute = Task.Run(() => Calculate());

// 2. Задача ввода-вывода — потока нет, ждёт порт завершения ОС
Task<string> download = httpClient.GetStringAsync(url);
```

Во втором случае, пока идёт запрос, **ни один поток не занят**. Именно поэтому асинхронный сервис держит тысячи одновременных соединений на десятке потоков.

Полезные состояния и члены:

```csharp
task.Status;          // Created, Running, RanToCompletion, Faulted, Canceled
task.IsCompleted;     // завершена любым образом (в т. ч. с ошибкой)
task.IsCompletedSuccessfully;
task.Exception;       // AggregateException, если упала
```

Готовые задачи без аллокаций для быстрых путей:

```csharp
Task.CompletedTask;          // 0 байт — закэширован
Task.FromResult(value);      // 72 байта на .NET 10
Task.FromException(ex);
Task.FromCanceled(token);
```

`Task` **неизменяем и одноразов по смыслу**: его можно ждать сколько угодно раз, и все ожидающие получат тот же результат. Это отличает его от `ValueTask`.

## ValueTask: когда результат обычно уже есть

`Task` — класс, то есть объект в куче. Если метод почти всегда возвращает результат синхронно (значение в кэше, данные в буфере), аллокация на каждый вызов становится заметной.

`ValueTask<T>` — **структура**, которая хранит либо готовое значение, либо ссылку на настоящую задачу, если пришлось ждать:

```csharp
public ValueTask<User> GetUserAsync(int id)
{
    if (_cache.TryGetValue(id, out var user))
        return new ValueTask<User>(user);        // без аллокации

    return new ValueTask<User>(LoadFromDbAsync(id));  // обычный Task внутри
}
```

Замер подтверждает выигрыш на быстром пути — и, что важно, показывает его границу:

```
async ValueTask, завершается синхронно   0 байт
async Task, завершается синхронно        0 байт
```

Оба нуля. Компилятор и рантайм уже оптимизируют синхронное завершение `async Task` (см. `State machine`), поэтому **`ValueTask` не даёт автоматического выигрыша**. Он выигрывает там, где `Task` пришлось бы создавать явно — как в примере выше с кэшем, где альтернативой был бы `Task.FromResult` с его 72 байтами.

### Ограничения ValueTask

За экономию приходится соблюдать правила, которых у `Task` нет:

**Ждать можно только один раз.** Повторный `await` того же `ValueTask` — неопределённое поведение: внутренний объект мог быть уже переиспользован пулом.

```csharp
var vt = GetUserAsync(1);
var a = await vt;
var b = await vt;        // так нельзя
```

**Нельзя ждать несколькими потребителями и нельзя хранить.** Если результат нужен дважды или его надо положить в поле — превращайте в `Task`:

```csharp
Task<User> task = GetUserAsync(1).AsTask();   // теперь можно ждать сколько угодно
```

**Нельзя передавать в `WhenAll`/`WhenAny`** напрямую — они работают с `Task`.

**Не годится для блокирующего ожидания** — `.Result` на незавершённом `ValueTask` некорректен.

Рекомендация платформы прямая: **по умолчанию возвращайте `Task`**, а `ValueTask` — только когда профилировщик показал проблему и метод действительно чаще завершается синхронно. Цена ошибки (незаметное двойное ожидание) выше экономии.

Для методов без результата есть `ValueTask` без параметра типа, но выигрыш там ещё меньше: `Task.CompletedTask` и так бесплатен.

## Что выбрать

| Нужно | Берите |
| --- | --- |
| Дождаться ввода-вывода | `Task` из асинхронного API, без `Task.Run` |
| Выполнить вычисление, не блокируя текущий поток | `Task.Run` |
| Вернуть результат из горячего метода с кэшем | `ValueTask<T>` |
| Долгоживущий фоновый цикл | `Thread` c `IsBackground`, либо `BackgroundService` |
| Периодическая работа в сервисе | `BackgroundService` / `PeriodicTimer` |
| Тяжёлая параллельная обработка коллекции | `Parallel.ForEachAsync` |

Отдельно про `Task.Run`: он нужен, чтобы **снять вычисление с текущего потока**, и не нужен вокруг того, что уже асинхронно. Оборачивать `await Task.Run(() => _http.GetAsync(url))` — значит занять поток пула ожиданием, которое и так потока не требовало.

Есть и уточнение для долгих задач: если работа действительно длинная, стоит сказать об этом явно, чтобы не занимать поток пула надолго:

```csharp
Task.Factory.StartNew(LongLoop, TaskCreationOptions.LongRunning);
```

Такая задача получит отдельный поток, а не поток пула.

## Что стоит ответить на собеседовании

`Thread` — поток операционной системы: дорогой ресурс, резервирующий около мегабайта под стек, поэтому прямое создание оправдано лишь для долгоживущих фоновых циклов и особых настроек. `Task` — не поток, а обещание результата: для операций ввода-вывода за ним не стоит никакого потока, ожидание обслуживают порты завершения ОС, и именно поэтому сервис держит тысячи соединений на десятке потоков.

Сильный ответ добавит, что пул рассчитан на короткие неблокирующие задачи и растёт постепенно: в замере на .NET 10 тысяча блокирующих `Task.Run` заняла 970 мс против 15 мс у той же тысячи неблокирующих ожиданий — то есть блокировка потока пула вредит всему приложению. И объяснит `ValueTask` как структуру для случая «результат обычно уже готов», с ограничениями: ждать один раз, не хранить, не передавать в `WhenAll`, а при необходимости переводить в `Task` через `AsTask()` — по умолчанию же возвращать `Task`.
