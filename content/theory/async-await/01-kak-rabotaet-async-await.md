`async/await` — не про то, чтобы выполнять код в другом потоке. Это про то, чтобы **не занимать поток, пока идёт ожидание**. Разница принципиальная, и большая часть ошибок с асинхронностью растёт из первого понимания вместо второго.

## Задача, которую решает асинхронность

Типичный запрос к веб-сервису: принять HTTP, сходить в базу, вызвать соседний сервис, сложить ответ. Почти всё время здесь — ожидание чужого ответа, а не вычисления.

Синхронный код на таком ожидании **блокирует поток**: поток стоит в ядре, ничего не делает и при этом занят. Тысяча одновременных запросов — тысяча занятых потоков, каждый со своим стеком (см. `Стек и куча`: 1 МБ адресного пространства на поток по умолчанию).

Асинхронный код на время ожидания **освобождает поток** — тот возвращается в пул и обслуживает другие запросы. Когда ответ придёт, выполнение продолжится, возможно, уже на другом потоке.

Разница измерима. Тысяча операций по 10 мс, .NET 10:

```
1000 x new Thread(Sleep 10):            138 мс
1000 x Task.Run(Sleep 10) (блокировка):  970 мс
1000 x Task.Delay(10) (без блокировки):   15 мс
```

Последняя строка — та же тысяча ожиданий, но ни один поток не заблокирован: пул успевает обслужить всё за 15 мс. Первые две блокируют потоки и платят за это либо созданием тысячи потоков, либо ожиданием, пока пул разрастётся.

## Что делает await

`await` **не блокирует** и **не создаёт поток**. Он делает следующее:

1. Проверяет, не завершена ли операция уже. Если да — выполнение идёт дальше синхронно, без всяких переключений.
2. Если нет — **возвращает управление вызывающему**. Метод приостанавливается, поток свободен.
3. Регистрирует продолжение (остаток метода) как колбэк на завершение операции.
4. Когда операция завершится, продолжение ставится в очередь на выполнение.

Ключевое здесь — пункт 2. Встретив `await`, метод **возвращает** в вызывающий код незавершённую `Task`, а не ждёт. Вызывающий волен делать что-то ещё или, в свою очередь, сделать `await`.

Проверка про потоки на .NET 10:

```
до await:          поток 7
после Task.Yield:  поток 6
после Task.Delay:  поток 6
```

Продолжение выполнилось **на другом потоке** — это нормально и ожидаемо. Никакой гарантии «тот же поток» в консольном приложении и ASP.NET Core нет, и полагаться на неё нельзя. Почему в UI-приложениях иначе — в статье `SynchronizationContext`.

## async не означает «параллельно»

Самое частое заблуждение. `async` описывает, **как метод ждёт**, а не **сколько всего выполняется одновременно**.

```csharp
// Последовательно: каждый await ждёт завершения предыдущего
await LoadUserAsync();      // 200 мс
await LoadOrdersAsync();    // 200 мс
await LoadSettingsAsync();  // 200 мс
// итого ~600 мс
```

Замер: **641 мс**. Хотя все три метода асинхронные, они выполняются один за другим — `await` на то и `await`, чтобы дождаться.

Чтобы операции шли одновременно, их надо **запустить, а потом ждать**:

```csharp
var userTask = LoadUserAsync();
var ordersTask = LoadOrdersAsync();
var settingsTask = LoadSettingsAsync();

await Task.WhenAll(userTask, ordersTask, settingsTask);
// итого ~200 мс
```

Замер: **214 мс**, втрое быстрее. Задачи запущены до первого `await`, поэтому выполняются внахлёст. Подробнее про `WhenAll` и его подвохи с исключениями — в отдельной статье.

Оговорка: так можно только если операции независимы. Если вторая использует результат первой, последовательность обязательна — и это нормально.

## Асинхронность ввода-вывода не занимает поток вообще

Для настоящих операций ввода-вывода (диск, сеть, база) ожидание не занимает **никакого** потока. Операционная система умеет уведомлять о завершении через порты завершения (IOCP на Windows, epoll на Linux); .NET регистрирует операцию и отпускает поток до прихода уведомления.

Это и объясняет 15 мс на тысячу `Task.Delay` — таймер не требует потока, пока тикает.

Отсюда важное разделение:

- **ввод-вывод** (`HttpClient`, `SqlConnection`, файлы, `Task.Delay`) — асинхронность выигрывает всегда, поток не занят;
- **вычисления** (разбор, математика, сжатие) — асинхронность сама по себе не ускоряет: работа всё равно занимает поток. Её выносят в пул через `Task.Run`, чтобы не блокировать текущий, — но суммарной работы меньше не становится.

Поэтому `Task.Run` вокруг асинхронного ввода-вывода — почти всегда ошибка: операция и так не занимала поток, а `Task.Run` заставляет занять.

## Сколько стоит async

Расхожее «async дорогой» стоит проверить. Замеры на .NET 10, байт на вызов:

```
Task.FromResult(42)                        72 байта
async Task, завершается синхронно           0 байт
async ValueTask, завершается синхронно      0 байт
Task.CompletedTask                          0 байт
async Task с реальным await Task.Yield()   14 байт
```

Результат противоречит интуиции: `async`-метод, завершившийся синхронно, не аллоцирует **ничего**, а `Task.FromResult` стоит 72 байта. Причина — оптимизации рантайма: для завершённого `Task` без результата возвращается закэшированный экземпляр, а машина состояний остаётся структурой на стеке, пока не понадобится реальная приостановка.

Платить приходится только за **настоящую** приостановку — когда `await` действительно ждёт: тогда машина состояний переезжает в кучу. На фоне сетевого запроса в десятки миллисекунд эти байты незаметны.

Практический вывод: `async` не нужно избегать из соображений производительности. Его стоит избегать там, где он бессмысленен, — например, `async`-обёртка над методом, который ничего не ждёт.

## Что генерирует компилятор

`async`-метод компилятор переписывает в **машину состояний** — примерно как итератор из статьи `yield return и итераторы`, только с продолжениями вместо `MoveNext`.

```csharp
async Task<int> LoadAsync()
{
    var data = await FetchAsync();   // точка приостановки
    return data.Length;
}
```

Превращается в структуру с полем состояния, полями под локальные переменные и методом `MoveNext`, где тело разрезано по точкам `await`. Подробно устройство разбирается в статье `State machine`.

Два следствия, полезных сразу:

**Локальные переменные переживают `await`** — они стали полями машины состояний. Поэтому писать асинхронный код можно обычным образом, с циклами и `try/catch`.

**`return` внутри `async`-метода не возвращает значение вызывающему напрямую**, а помещает его в `Task`. Вызывающий получит `Task<int>`, а число — только после `await`.

## Правила, которые снимают большинство проблем

**Асинхронность заразна: `async` до самого верха.** Если метод внизу стал асинхронным, вызывающие тоже должны стать. Попытка «остановить заразу» через `.Result` или `.Wait()` приводит либо к дедлоку, либо к голоданию пула — об этом статья `Дедлоки на .Result`.

**Возвращайте `Task`, а не `void`.** Исключение — обработчики событий; почему так, разбирается в статье `async void`.

**Именуйте асинхронные методы суффиксом `Async`.** Соглашение платформы, и оно помогает заметить незаваченный вызов.

**Не оборачивайте ввод-вывод в `Task.Run`.** Он уже асинхронный.

## Что стоит ответить на собеседовании

`async/await` — способ не занимать поток на время ожидания, а не способ выполнить код параллельно. Встретив `await`, метод возвращает управление вызывающему и регистрирует остаток тела как продолжение; поток уходит в пул и обслуживает другие задачи, а после завершения операции выполнение продолжается — возможно, уже на другом потоке.

Сильный ответ отделит асинхронность от параллелизма на примере: три `await` подряд выполняются последовательно (замер на .NET 10 — 641 мс), и чтобы получить одновременность, задачи надо запустить до ожидания и собрать через `WhenAll` (214 мс). И добавит, что для настоящего ввода-вывода ожидание не занимает потока вообще благодаря портам завершения ОС, поэтому `Task.Run` вокруг асинхронного вызова только вредит, а сам `async` при синхронном завершении не аллоцирует ничего — дороже оказывается `Task.FromResult` (72 байта против нуля).
