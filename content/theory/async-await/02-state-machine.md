`async` — синтаксический сахар. Компилятор переписывает метод в **машину состояний**: структуру с полем текущего шага и методом `MoveNext`, где тело разрезано по точкам `await`. Знать её устройство полезно не ради эрудиции: из него напрямую следуют и цена асинхронности, и вид стектрейсов, и правила про `ValueTask`.

## Во что превращается метод

Исходник:

```csharp
async Task<int> LoadAsync(string url)
{
    var response = await _http.GetStringAsync(url);
    var parsed = Parse(response);
    return parsed.Length;
}
```

Компилятор порождает примерно такое (упрощённо, реальные имена содержат непроизносимые символы вроде `<LoadAsync>d__3`):

```csharp
struct LoadAsyncStateMachine : IAsyncStateMachine
{
    public int State;                                  // -1 = не начат, 0 = ждём первый await
    public AsyncTaskMethodBuilder<int> Builder;        // кто строит Task для вызывающего
    public string Url;                                 // параметр стал полем
    public MyClass This;                               // и захваченный this

    string _response;                                  // локальные переменные — тоже поля
    TaskAwaiter<string> _awaiter;                      // чем мы ждём

    public void MoveNext()
    {
        try
        {
            if (State != 0)
            {
                _awaiter = This._http.GetStringAsync(Url).GetAwaiter();
                if (!_awaiter.IsCompleted)             // ещё не готово?
                {
                    State = 0;
                    Builder.AwaitUnsafeOnCompleted(ref _awaiter, ref this);
                    return;                            // ВЫХОД из метода, поток свободен
                }
            }
            else
            {
                State = -1;
            }

            _response = _awaiter.GetResult();          // сюда возвращаемся после ожидания
            var parsed = Parse(_response);
            Builder.SetResult(parsed.Length);          // результат кладём в Task
        }
        catch (Exception ex)
        {
            Builder.SetException(ex);                  // исключение — тоже в Task
        }
    }
}
```

А сам метод превращается в короткую заглушку: создать машину, отдать её билдеру, вернуть `Builder.Task`.

Читать это стоит так. **`return` в середине `MoveNext` — и есть освобождение потока.** Метод буквально выходит, оставив продолжение зарегистрированным. Когда операция завершится, `MoveNext` вызовут снова, и он по значению `State` попадёт в нужное место.

## Три участника

**State machine** хранит состояние: где остановились, чему равны локальные переменные. Именно поэтому локальные переменные переживают `await` — они стали полями.

**Builder** (`AsyncTaskMethodBuilder`) отвечает за `Task`, который видит вызывающий: создаёт его, проставляет результат через `SetResult`, ошибку — через `SetException`. Для `ValueTask` билдер свой, для `async void` — `AsyncVoidMethodBuilder`, и различия между ними объясняют поведение этих форм.

**Awaiter** — то, что умеет ждать. `await` работает не с `Task` как таковым, а с любым типом, у которого есть метод `GetAwaiter()`, возвращающий нечто с тремя членами:

```csharp
bool IsCompleted { get; }
void OnCompleted(Action continuation);
T GetResult();
```

Это **паттерн, а не интерфейс** — компилятор ищет члены по имени. Отсюда и возможность ждать `Task`, `ValueTask`, `Task.Yield()`, `IAsyncEnumerable` и даже собственные типы: достаточно написать `GetAwaiter()`, в том числе методом расширения.

## Почему быстрый путь бесплатен

Проверка `if (!_awaiter.IsCompleted)` — ключевая оптимизация. Если результат уже готов (данные в буфере, значение в кэше, `Task.CompletedTask`), продолжение не регистрируется, и метод **доходит до конца синхронно**, ни разу не выйдя.

В этом случае машина состояний так и остаётся **структурой на стеке**. Отсюда замеры из статьи `Как работает async/await`:

```
async Task, завершается синхронно           0 байт
async ValueTask, завершается синхронно      0 байт
async Task с реальным await Task.Yield()   14 байт
Task.FromResult(42)                        72 байта
```

Ноль — это и есть быстрый путь: аллоцировать нечего. Как только ожидание настоящее, структуру приходится **упаковать в кучу** (иначе она умрёт вместе с кадром стека), и тогда появляются аллокации: сама машина, объект `Task` и делегат продолжения.

Практический вывод: **асинхронный метод, который обычно завершается синхронно, почти бесплатен**. Это же обоснование `ValueTask` — о нём в статье `Task vs Thread vs ValueTask`.

## Что это объясняет на практике

**Стектрейсы выглядят странно.** В трассировке видно `MoveNext()` вместо имени вашего метода, а вызывающего может не быть вовсе — он давно вернулся. Начиная с .NET Core 2.1 рантайм склеивает асинхронные стектрейсы, поэтому картина стала читаемой, но `MoveNext` в кадрах — норма, а не признак поломки.

**Исключение не вылетает из метода, а попадает в `Task`.** Видно по `catch` в `MoveNext`: ошибка отдаётся через `Builder.SetException`. Поэтому `try/catch` вокруг **вызова** без `await` ничего не поймает:

```csharp
try { DoAsync(); }            // Task создан, исключение внутри него
catch (Exception) { }         // сюда не попадёт

try { await DoAsync(); }      // а так поймает
catch (Exception) { }
```

**Исключения до первого `await` тоже откладываются.** В отличие от итераторов (см. `yield return и итераторы`), где тело не выполняется вовсе, здесь тело начинает выполняться сразу — но проверка аргументов всё равно вернётся вызывающему не броском, а через `Task`. Поэтому для быстрой валидации применяют тот же приём: синхронный метод-обёртка плюс приватный `async`.

```csharp
public Task<int> LoadAsync(string url)
{
    ArgumentException.ThrowIfNullOrEmpty(url);   // бросит сразу, при вызове
    return LoadCoreAsync(url);

    async Task<int> LoadCoreAsync(string u) { /* ... */ }
}
```

**`async` нельзя применить к конструктору, свойству и `lock`.** Конструктор обязан вернуть объект, а не `Task`; в `lock` нельзя ждать, потому что продолжение может прийти на другом потоке, а монитор привязан к потоку-владельцу. Для асинхронной синхронизации есть `SemaphoreSlim.WaitAsync` — это тема раздела про многопоточность.

**`ref` и `out` параметры запрещены** — их негде хранить в полях машины состояний. Ровно та же причина, что у итераторов.

## Посмотреть своими глазами

Полезная привычка при разборе непонятного поведения — заглянуть в сгенерированный код. Быстрее всего через sharplab.io: вставить метод, выбрать «Results: C#» и увидеть развёрнутую машину состояний. Локально то же покажут ILSpy или dotPeek.

Особенно наглядно это на `foreach`, `await foreach` и `try/finally` внутри `async` — видно, во что превращается `finally`, почему он честно выполняется после ожидания и откуда берутся дополнительные поля.

## Что стоит ответить на собеседовании

Компилятор превращает `async`-метод в машину состояний: структуру с полем состояния, полями под параметры и локальные переменные и методом `MoveNext`, где тело разрезано по точкам `await`. На каждом `await` проверяется, не готов ли результат; если нет — регистрируется продолжение, и `MoveNext` **возвращает управление**, освобождая поток. Работают три участника: машина состояний, билдер (он создаёт `Task` и кладёт туда результат или исключение) и awaiter — причём `await` опирается на паттерн `GetAwaiter()`/`IsCompleted`/`GetResult`, а не на интерфейс, поэтому ждать можно и свои типы.

Сильный ответ добавит, что при синхронном завершении машина остаётся структурой на стеке и аллокаций нет вовсе (0 байт на .NET 10 — дешевле, чем `Task.FromResult` с его 72 байтами), а в кучу она переезжает только при настоящей приостановке. И объяснит через `Builder.SetException`, почему исключение не вылетает из асинхронного метода, а оседает в `Task`: `try/catch` вокруг вызова без `await` его не поймает.
