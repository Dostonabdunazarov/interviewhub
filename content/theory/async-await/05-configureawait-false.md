`ConfigureAwait(false)` говорит одну вещь: «после ожидания возвращаться в захваченный контекст не нужно, продолжай где угодно». Всё остальное — следствия. Вызов окружён мифами («ускоряет», «делает код параллельным», «нужен всегда»), поэтому полезно разобраться, что он делает буквально.

## Что происходит буквально

По умолчанию `await` захватывает `SynchronizationContext.Current` и после завершения операции возвращает продолжение туда (см. `SynchronizationContext`). `ConfigureAwait(false)` отменяет этот захват — продолжение выполняется на том потоке, который освободился, обычно на потоке пула.

Проверено на .NET 10 с установленным контекстом:

```
после await без ConfigureAwait:  контекст SingleThreadContext
после ConfigureAwait(false):     контекст null
```

Технически `ConfigureAwait` возвращает не `Task`, а `ConfiguredTaskAwaitable` — другой awaiter, чей `OnCompleted` не обращается к контексту. Отсюда следует мелочь, которая иногда удивляет: результат `ConfigureAwait` нельзя сохранить в переменную типа `Task` и нельзя передать в `WhenAll`; это модификатор ожидания, а не задачи.

```csharp
await Task.WhenAll(t1, t2).ConfigureAwait(false);   // правильно: настраиваем ожидание
```

## Что он НЕ делает

Три заблуждения, которые стоит развести сразу.

**Не делает код параллельным.** Порядок выполнения не меняется: `await` по-прежнему ждёт завершения.

**Не ускоряет саму операцию.** Экономится только переключение на контекст — доли микросекунды. Если контекста нет, не экономится ничего.

**Не защищает от дедлока в общем случае.** Он снимает конкретный сценарий — блокировку под однопоточным контекстом, — но блокирующий вызов остаётся плохой идеей и без контекста: он занимает поток пула (см. `Дедлоки на .Result`).

## Где он обязателен

**В библиотеках.** Главный и по сути единственный безусловный случай. Библиотека не знает, кто её вызовет: консоль, веб-сервис или WPF-приложение. Если вызовут из UI-потока, каждое ожидание внутри библиотеки будет гонять продолжение через очередь сообщений окна — лишняя работа, а при блокировке вызывающим — дедлок.

```csharp
public async Task<Data> LoadAsync(string url)
{
    var json = await _http.GetStringAsync(url).ConfigureAwait(false);
    var parsed = await ParseAsync(json).ConfigureAwait(false);
    return parsed;
}
```

Правило внутри библиотеки: **на каждом `await`**. Пропущенный вызов в середине цепочки возвращает контекст обратно, и дальше он снова захватывается.

**В коде, который может быть вызван из UI.** Общие сборки в решении, где есть и веб, и десктоп, — тот же случай.

## Где он бесполезен

**В ASP.NET Core.** Контекста нет, `SynchronizationContext.Current` равен `null`, захватывать нечего. `ConfigureAwait(false)` в контроллере или сервисе ничего не меняет — это шум, ухудшающий читаемость.

Именно поэтому в современных шаблонах и в коде самого ASP.NET Core его не пишут. Если проект перешёл с .NET Framework и код усыпан этими вызовами, их можно спокойно убирать — но только убедившись, что сборка не переиспользуется UI-приложением.

**В консольных приложениях и фоновых сервисах.** Контекста тоже нет.

**После последнего `await` в методе**, если дальше ничего нет. Продолжения, которое волновало бы, попросту не осталось.

## Где его писать НЕЛЬЗЯ

**В UI-обработчиках, если после `await` вы трогаете интерфейс:**

```csharp
private async void Button_Click(object sender, EventArgs e)
{
    var data = await LoadAsync();                        // без ConfigureAwait — правильно
    label.Text = data;                                   // мы в UI-потоке, всё законно

    var other = await LoadAsync().ConfigureAwait(false); // а так — ошибка
    label.Text = other;   // InvalidOperationException: не тот поток
}
```

Правильный приём для UI — тяжёлую работу целиком вынести в `Task.Run`, а внутри неё уже не заботиться о контексте:

```csharp
var result = await Task.Run(async () =>
{
    return await ProcessAsync().ConfigureAwait(false);
});
label.Text = result;      // вернулись в UI-поток
```

## ConfigureAwait(true) и другие опции

`ConfigureAwait(true)` — поведение по умолчанию, писать его явно смысла нет.

В .NET 8 появился более выразительный вариант с флагами:

```csharp
await task.ConfigureAwait(ConfigureAwaitOptions.None);                   // = false
await task.ConfigureAwait(ConfigureAwaitOptions.ContinueOnCapturedContext); // = true
await task.ConfigureAwait(ConfigureAwaitOptions.SuppressThrowing);       // не бросать исключение
await task.ConfigureAwait(ConfigureAwaitOptions.ForceYielding);          // всегда приостанавливаться
```

`SuppressThrowing` полезен, когда результат не важен и исключение обрабатывать не нужно, — заменяет обёртку `try { await t; } catch { }`. `ForceYielding` пригождается, чтобы гарантированно вернуть управление вызывающему даже на быстром пути.

Важно: у `ValueTask` тоже есть `ConfigureAwait`, и правила те же.

## Как не писать его руками

Вместо того чтобы расставлять вызовы вручную по всей библиотеке, можно включить анализатор:

```xml
<PropertyGroup>
  <AnalysisMode>Recommended</AnalysisMode>
</PropertyGroup>
```

Правило **CA2007** («Do not directly await a Task») подсветит места без `ConfigureAwait`. В приложениях на ASP.NET Core его наоборот отключают, чтобы не засорять код:

```xml
<NoWarn>$(NoWarn);CA2007</NoWarn>
```

Есть и радикальный приём для библиотек — задать поведение на уровне сборки через `Task.ConfigureAwait`-обёртки или собственный awaiter, но на практике проще довериться анализатору.

## Короткая памятка

| Где | Писать? |
| --- | --- |
| Библиотека, переиспользуемый код | **Да, на каждом `await`** |
| ASP.NET Core: контроллеры, сервисы | Нет, контекста нет |
| Консоль, `BackgroundService` | Нет |
| UI-обработчик, дальше работа с интерфейсом | **Нет, сломает** |
| Внутри `Task.Run` в UI-приложении | Да |

## Что стоит ответить на собеседовании

`ConfigureAwait(false)` отключает захват контекста синхронизации: продолжение после `await` выполняется на освободившемся потоке пула, а не возвращается в UI-поток или контекст запроса. Он не ускоряет операцию, не делает код параллельным и не меняет порядок выполнения — экономит только переключение.

Сильный ответ назовёт границы применимости: обязателен в библиотеках, где неизвестно, кто вызовет, и на каждом `await`, потому что пропуск в середине цепочки возвращает захват; бесполезен в ASP.NET Core, где контекста нет вовсе (`SynchronizationContext.Current == null`), и вреден в UI-обработчике, после которого код трогает элементы управления, — там он даст исключение о работе не из того потока.
