После `await` выполнение иногда продолжается на том же потоке, а иногда на другом. Решает это `SynchronizationContext` — абстракция «куда доставить продолжение». Понимание её устройства сразу объясняет и дедлоки на `.Result`, и смысл `ConfigureAwait(false)`, и почему один и тот же код ведёт себя по-разному в WinForms и в веб-сервисе.

## Что это такое

`SynchronizationContext` — класс с одним по-настоящему важным методом:

```csharp
public virtual void Post(SendOrPostCallback d, object? state);   // асинхронно
public virtual void Send(SendOrPostCallback d, object? state);   // синхронно
```

Смысл — «выполни этот колбэк там, где положено». Что значит «где положено», решает конкретная реализация.

Механика `await` такова: перед приостановкой он **захватывает текущий контекст** (`SynchronizationContext.Current`), а когда операция завершится, отдаёт продолжение этому контексту через `Post`. Если контекста нет — продолжение просто ставится в пул потоков.

Отсюда всё поведение.

## Где контекст есть, а где нет

**WinForms и WPF — есть.** У UI-потока свой контекст, чей `Post` ставит колбэк в очередь сообщений окна. Благодаря этому после `await` можно спокойно трогать элементы управления:

```csharp
private async void Button_Click(object sender, EventArgs e)
{
    var data = await LoadAsync();     // ушли ждать, UI не заморожен
    label.Text = data;                // вернулись в UI-поток — это законно
}
```

Без контекста такая строка упала бы: у WinForms и WPF жёсткое правило — элементы управления трогает только создавший их поток.

**Старый ASP.NET (.NET Framework) — есть.** `AspNetSynchronizationContext` возвращал продолжение в контекст запроса, где жили `HttpContext.Current`, культура и идентификация пользователя. Он же разрешал обрабатывать запрос **только одному потоку одновременно** — и именно это делало дедлоки на `.Result` массовой проблемой.

**ASP.NET Core — нет.** Контекст убрали намеренно. Проверено на .NET 10 в консоли, где картина та же:

```
SynchronizationContext.Current = null
```

`HttpContext` в ASP.NET Core передаётся через `IHttpContextAccessor` поверх `AsyncLocal`, а не через контекст синхронизации, поэтому возвращать продолжение в какой-то особый поток не требуется.

**Консольные приложения и сервисы — нет.** Продолжения идут в пул.

## Что это меняет на практике

Проверка разницы с собственным контекстом (.NET 10):

```
поставили свой контекст:         SingleThreadContext
после await без ConfigureAwait:  SingleThreadContext   ← вернулись в контекст
после ConfigureAwait(false):     null                  ← остались в пуле
```

Три следствия, которые важно понимать.

**Захват контекста стоит денег.** Возврат продолжения через `Post` — это постановка в очередь и переключение потока. В UI-приложении цена оправдана, в библиотеке на горячем пути — нет; отсюда `ConfigureAwait(false)`, которому посвящена отдельная статья.

**Контекст может быть однопоточным, и это опасно в сочетании с блокировкой.** Если единственный поток контекста заблокирован на `.Result`, доставить ему продолжение невозможно — получается дедлок. Проверено экспериментом в статье `Дедлоки на .Result`: без `ConfigureAwait(false)` зависает намертво, с ним завершается за 59 мс.

**В ASP.NET Core этой проблемы нет.** Раз контекста нет, классический дедлок на `.Result` в веб-сервисе не воспроизводится. Это **не** означает, что `.Result` там безопасен: блокировка потока пула остаётся и приводит к голоданию под нагрузкой — другой механизм, тот же печальный итог.

## Связанные механизмы, которые путают с контекстом

**`ExecutionContext`** — другая сущность, и её часто смешивают с `SynchronizationContext`. Она переносит через `await` «окружение» логической операции: `AsyncLocal<T>`, идентификацию, культуру. Переносится **всегда**, и `ConfigureAwait(false)` на неё не влияет — поэтому `IHttpContextAccessor` продолжает работать после любого `await`.

**`TaskScheduler`** решает, где выполнять `Task`, а не куда доставить продолжение `await`. По умолчанию — пул потоков.

Разделение простое: `ExecutionContext` — **что** окружает выполнение, `SynchronizationContext` — **где** оно продолжится, `TaskScheduler` — **кто** его запустит.

## Как написать свой контекст

Практически это нужно редко — разве что для однопоточного цикла обработки или для тестов, — но понимание устройства закрывает тему:

```csharp
class SingleThreadContext : SynchronizationContext
{
    readonly BlockingCollection<(SendOrPostCallback cb, object? st)> _queue = new();

    public override void Post(SendOrPostCallback d, object? state) => _queue.Add((d, state));

    public void RunLoop()
    {
        SetSynchronizationContext(this);
        foreach (var (cb, state) in _queue.GetConsumingEnumerable())
            cb(state);         // всё исполняется на одном потоке
    }
}
```

Именно такой контекст использовался для воспроизведения дедлока: поток одновременно качает очередь и блокируется на результате — доставить продолжение становится некому.

Установка и снятие:

```csharp
var previous = SynchronizationContext.Current;
SynchronizationContext.SetSynchronizationContext(myContext);
try { /* ... */ }
finally { SynchronizationContext.SetSynchronizationContext(previous); }
```

## Практические правила

**В библиотеке — `ConfigureAwait(false)` везде.** Библиотека не знает, в каком приложении её вызовут, и не должна зависеть от наличия контекста.

**В коде приложения на ASP.NET Core — можно не писать.** Контекста нет, эффекта тоже; добавлять его везде — лишний шум. Исключение — код, который может быть переиспользован в UI-приложении.

**В UI-обработчиках — не писать**, если после `await` нужно трогать интерфейс. А тяжёлую работу внутри выносить в `Task.Run` и уже там ставить `ConfigureAwait(false)`.

**Никогда не блокироваться под контекстом.** `.Result`, `.Wait()`, `GetAwaiter().GetResult()` в UI-обработчике — прямой путь к зависанию приложения.

## Что стоит ответить на собеседовании

`SynchronizationContext` — абстракция «куда доставить продолжение после `await`». Перед приостановкой `await` захватывает текущий контекст и по завершении операции отдаёт ему продолжение через `Post`; если контекста нет, продолжение выполняется на потоке пула. В WinForms и WPF контекст возвращает выполнение в UI-поток, в старом ASP.NET — в контекст запроса, причём однопоточно.

Сильный ответ отметит, что в ASP.NET Core контекста нет намеренно — проверяется как `SynchronizationContext.Current == null`, — поэтому классический дедлок на `.Result` там не воспроизводится, но блокировка потока пула всё равно ведёт к голоданию под нагрузкой. И разведёт `SynchronizationContext` с `ExecutionContext`: первый определяет, где продолжится выполнение, и отключается через `ConfigureAwait(false)`, а второй переносит `AsyncLocal`, культуру и идентификацию, передаётся всегда и от `ConfigureAwait` не зависит — благодаря чему `IHttpContextAccessor` работает после любого `await`.
