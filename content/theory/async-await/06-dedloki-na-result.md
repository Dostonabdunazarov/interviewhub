Классическая ошибка: асинхронный метод вызывают синхронно через `.Result` или `.Wait()`, и приложение зависает намертво. Механизм у этого зависания простой и полностью объясняется через `SynchronizationContext`. Проверим его экспериментом, а не пересказом.

## Воспроизведение

Соберём условия: однопоточный контекст (как в WinForms, WPF и старом ASP.NET) и блокирующее ожидание на том же потоке.

```csharp
static async Task<int> GetValueAsync()
{
    await Task.Delay(50);
    return 42;
}

// На потоке с однопоточным контекстом:
var task = GetValueAsync();
bool ok = task.Wait(1200);      // блокируем поток
```

Результат на .NET 10:

```
t.Wait() без ConfigureAwait                ЗАВИСЛО на 1209 мс — ДЕДЛОК
t.Wait() с ConfigureAwait(false) внутри    завершилось за 59 мс, результат 42
```

Дедлок настоящий, воспроизводится стабильно. Разберём, почему.

## Механизм

Шаг за шагом:

1. Поток с контекстом вызывает `GetValueAsync()` и получает незавершённую задачу.
2. Внутри метода `await Task.Delay(50)` **захватывает контекст** и регистрирует продолжение — «остаток метода доставить в этот контекст».
3. Поток доходит до `task.Wait()` и **блокируется**, ожидая завершения задачи.
4. Через 50 мс таймер срабатывает, и продолжение отдаётся контексту через `Post`.
5. Но исполнять продолжения в этом контексте может **только тот самый поток** — а он стоит на шаге 3.

Круг замкнулся: задача не завершится, пока не выполнится продолжение; продолжение не выполнится, пока занят поток; поток занят ожиданием задачи.

Важная деталь: дедлок возникает не из-за `async` и не из-за `Task`. Он возникает из-за **сочетания** однопоточного контекста и блокирующего ожидания. Убрать любое из двух — и его нет, что и подтверждает вторая строка замера: `ConfigureAwait(false)` снимает захват контекста, продолжение выполняется на потоке пула, задача завершается, `Wait` разблокируется за 59 мс.

## Все три формы одинаково опасны

```csharp
var result = GetValueAsync().Result;              // блокирует
GetValueAsync().Wait();                           // блокирует
var r = GetValueAsync().GetAwaiter().GetResult(); // тоже блокирует
```

Разница между ними только в упаковке исключений — проверено:

```
.Result бросил: AggregateException, внутри InvalidOperationException
await бросил:   InvalidOperationException
```

`GetAwaiter().GetResult()` бросает исходное исключение без обёртки `AggregateException`, поэтому его иногда предпочитают, — но **дедлок он даёт ровно такой же**. Выбор между ними не решает проблему, а лишь делает стектрейс чище.

## В ASP.NET Core дедлока нет, но блокировать нельзя

В ASP.NET Core контекст убран, поэтому описанный дедлок там **не воспроизводится**. Это регулярно порождает вывод «значит, `.Result` можно» — вывод неверный.

Блокирующий вызов занимает **поток пула**, и под нагрузкой это приводит к голоданию (thread pool starvation). Замер на .NET 10, 50 задач по 100 мс:

```
50 задач блокируют поток пула:  749 мс, потоков стало 51
50 задач через await:           109 мс, потоков 51
```

Семикратная разница на пустом месте. Пул начинал с 16 потоков (по числу ядер) и был вынужден добавлять новые — а добавляет он их неспешно, примерно по одному-два в секунду после исчерпания минимума. В реальном сервисе картина выглядит так: при росте нагрузки время ответа внезапно увеличивается в разы, процессор при этом недогружен, а число потоков растёт. Классическая диагностическая картина голодания пула.

То есть в ASP.NET Core `.Result` не вешает приложение мгновенно — он делает хуже постепенно и под нагрузкой, что отлаживать неприятнее.

## Что делать вместо

**Сделать вызывающий метод асинхронным.** Правильный ответ в 95% случаев — «async до самого верха»:

```csharp
// Плохо
public User GetUser(int id) => _repo.GetUserAsync(id).Result;

// Хорошо
public Task<User> GetUserAsync(int id) => _repo.GetUserAsync(id);
```

ASP.NET Core, современные тестовые фреймворки, `BackgroundService`, `Main` — всё это умеет асинхронные точки входа, так что доводить `async` до верха почти всегда возможно:

```csharp
static async Task Main(string[] args) { await RunAsync(); }
```

**Если точка входа синхронна и переделать нельзя** — блокируйте **один раз на самом верху**, где контекста уже нет:

```csharp
// Точка входа legacy-кода
public void Execute() => ExecuteAsync().GetAwaiter().GetResult();
```

Это допустимо именно наверху: там нет контекста, в который надо возвращаться, и нет потока пула, который отнимается у обработки запросов.

**Для вызова асинхронного кода из конструктора или свойства** — не блокируйте, а поменяйте дизайн: асинхронная фабрика вместо конструктора, метод `InitializeAsync`, ленивое `AsyncLazy`:

```csharp
public sealed class Service
{
    readonly Lazy<Task<Config>> _config;
    public Service(IConfigLoader loader) => _config = new(() => loader.LoadAsync());
    public async Task<string> GetNameAsync() => (await _config.Value).Name;
}
```

**Никогда не блокируйтесь под контекстом** — в UI-обработчике, в старом ASP.NET, внутри библиотеки, которую могут вызвать из UI.

## Как поймать заранее

**Анализаторы.** Правило **CA2012** ругается на неправильное использование `ValueTask`, а набор [Microsoft.VisualStudio.Threading.Analyzers](https://www.nuget.org/packages/Microsoft.VisualStudio.Threading.Analyzers) содержит **VSTHRD002** — «избегайте синхронных ожиданий» — и ловит именно этот случай.

**Диагностика на живом сервисе.** Признаки голодания пула: время ответа растёт, процессор недогружен, число потоков ползёт вверх. Смотреть через счётчики:

```bash
dotnet-counters monitor -p <pid> --counters System.Runtime[threadpool-thread-count,threadpool-queue-length]
```

Растущая длина очереди пула при низком CPU — почти наверняка блокирующие вызовы.

## Что стоит ответить на собеседовании

Дедлок возникает из сочетания однопоточного контекста синхронизации и блокирующего ожидания: `await` внутри метода захватывает контекст и после завершения операции отдаёт продолжение ему, но единственный поток этого контекста заблокирован на `.Result`, поэтому продолжение не выполнится, а задача не завершится. Проверяется экспериментом: под таким контекстом вызов зависает, а с `ConfigureAwait(false)` внутри завершается за 59 мс.

Сильный ответ добавит, что в ASP.NET Core контекста нет и классический дедлок не воспроизводится, но блокировать всё равно нельзя — поток пула занимается впустую, и под нагрузкой наступает голодание: в замере на .NET 10 пятьдесят блокирующих задач отработали за 749 мс против 109 мс у тех же задач с `await`. И назовёт правильное лечение — «async до самого верха», а блокирующий вызов допустим лишь однократно в синхронной точке входа, где контекста уже нет.
