Рекурсия делает код коротким там, где сама задача рекурсивна: дерево, вложенный JSON, перебор вариантов. Цена — стек вызовов. Каждый вызов занимает на нём кадр, стек у потока фиксированного размера, и когда он кончается, .NET не бросает обычное исключение, а **завершает процесс**. На собеседовании ждут не определения рекурсии, а понимания этой цены: сколько вызовов помещается, что происходит при переполнении и как от него защищаться.

## Идея

Рекурсивная функция решает задачу, вызывая себя на меньшей подзадаче того же вида. Корректная рекурсия состоит из двух частей:

- **базовый случай** — ответ известен сразу, без вызова;
- **шаг** — вызов на входе, который гарантированно ближе к базовому случаю.

```csharp
static int Height(TreeNode? node)
{
    if (node is null) return 0;
    return 1 + Math.Max(Height(node.Left), Height(node.Right));
}
```

Пустое дерево имеет высоту 0, непустое — на единицу больше самого высокого поддерева. Код повторяет определение почти дословно, и в этом сила рекурсии.

## Как узнать задачу

Рекурсия естественна, когда данные или пространство решений устроены как дерево:

- деревья и графы — обходы, высота, проверка дерева поиска (см. `DFS и BFS`);
- «разделяй и властвуй» — сортировка слиянием, быстрая сортировка, бинарный поиск;
- перебор с возвратом (backtracking) — подмножества, перестановки, расстановки;
- вложенные структуры — разбор выражений, JSON, XML, каталогов;
- задачи с перекрывающимися подзадачами — это уже динамическое программирование, следующая статья.

## Как оценивать сложность

Время — число вызовов, умноженное на работу внутри одного вызова. Память — **максимальная глубина**, а не число вызовов: кадры живут только пока вызов не вернулся.

| Пример | Вызовов | Время | Стек |
| --- | --- | --- | --- |
| факториал `n * F(n - 1)` | n | O(n) | O(n) |
| бинарный поиск | log n | O(log n) | O(log n) |
| обход дерева | n | O(n) | O(h), h — высота |
| наивный Фибоначчи | ~2ⁿ | O(2ⁿ) | O(n) |
| все подмножества | 2ⁿ⁺¹ | O(2ⁿ · n) с копированием | O(n) |

Глубину часто забывают: рекурсивный обход дерева «не использует дополнительной памяти», но тратит O(h) стека, а на вырожденном дереве h = n. Подробнее о том, как считать память, — в `Оценка памяти`.

## Шаблон: перебор с возвратом

Рекурсия, которую стоит знать наизусть, — backtracking: выбрать, углубиться, отменить выбор.

```csharp
static void Subsets(int[] nums, int i, List<int> current, List<List<int>> result)
{
    if (i == nums.Length)
    {
        result.Add([.. current]);
        return;
    }
    Subsets(nums, i + 1, current, result);
    current.Add(nums[i]);
    Subsets(nums, i + 1, current, result);
    current.RemoveAt(current.Count - 1);
}
```

Для `[1, 2, 3]` получаем 8 подмножеств. Две детали: в результат кладётся **копия** `current` — иначе все восемь элементов ответа окажутся одним и тем же списком, который в конце пуст; и после второго вызова выбор отменяется, чтобы вызывающий уровень увидел `current` в исходном состоянии. Глубина здесь всего n, а время определяется размером ответа.

## Сколько вызовов помещается

Замерено на .NET 10.0.10, Windows 11 x64. Размер стека считывался через `GetCurrentThreadStackLimits`:

```
главный поток              1536 КБ
new Thread()               1536 КБ
поток пула (Task.Run)      1536 КБ
new Thread(work, 64 МБ)   65536 КБ
```

Итого полтора мегабайта на поток по умолчанию. Глубина, на которой процесс падал, зависит от размера кадра:

```
длина списка  n => 1 + Length(n.Next), Release   ~31 700
то же, Debug                                       ~19 000
Height по вырожденному дереву, Release             ~23 900
рекурсивный DFS из статьи DFS и BFS, Release       ~10 600
5 параметров + stackalloc на 64 байта              ~7 400
простая рекурсия в потоке со стеком 64 МБ        ~1 013 000
```

Главный вывод — порядок: **десятки тысяч**, а не миллионы. Список из ста тысяч элементов, дерево, построенное из уже отсортированных ключей без балансировки, цепочка зависимостей длиной в десять тысяч — и рекурсивный код падает. Точное число зависит от параметров, локальных переменных, режима сборки, версии JIT и ОС, поэтому проектировать «впритык» нельзя. На Linux размер стека главного потока задаёт `ulimit -s`, и цифры будут другими — их нужно мерить там, где код работает.

## Почему StackOverflow не ловится

Переполнение стека в .NET не обрабатывается: `try/catch` вокруг рекурсивного вызова не срабатывает, блоки `finally` не выполняются, процесс завершается. В замере с `catch (Exception)` вывод был один и тот же:

```
Stack overflow.
Repeated 19266 times:
--------------------------------
   at P.Crash(Int32)
```

Код завершения — `0xC00000FD`, системный `STATUS_STACK_OVERFLOW`. Для веб-сервиса это значит, что один запрос роняет все остальные, которые обрабатывал процесс. Отсюда и угроза отказа в обслуживании: если глубина рекурсии зависит от входных данных, атакующему достаточно прислать JSON с вложенностью в сто тысяч уровней.

## Хвостовая рекурсия не спасает

Хвостовой вызов — когда рекурсивный вызов последнее действие функции, и кадр можно переиспользовать:

```csharp
static long SumTail(int n, long acc) => n == 0 ? acc : SumTail(n - 1, acc + n);
```

Компилятор C# не превращает такую рекурсию в цикл. JIT иногда превращает — и именно «иногда» тут ключевое. Release-сборка на .NET 10 с настройками по умолчанию упала на `SumTail(100000, 0)` примерно на 32 000 вызовах: глубокая рекурсия выполняется в неоптимизированном коде первого уровня многоуровневой компиляции, где хвостовых вызовов нет. Та же сборка с `DOTNET_TieredCompilation=0` досчитала `SumTail(10000000, 0)` до `50000005000000`. Поведение зависит от настроек рантайма, поэтому опираться на него нельзя.

## Как защититься

**1. Переписать итеративно** с явным стеком в куче — самый надёжный вариант:

```csharp
static int HeightIterative(TreeNode? root)
{
    if (root is null) return 0;
    var stack = new Stack<(TreeNode Node, int Depth)>();
    stack.Push((root, 1));
    int max = 0;
    while (stack.Count > 0)
    {
        var (node, depth) = stack.Pop();
        max = Math.Max(max, depth);
        if (node.Left is not null) stack.Push((node.Left, depth + 1));
        if (node.Right is not null) stack.Push((node.Right, depth + 1));
    }
    return max;
}
```

На вырожденном дереве из миллиона узлов эта версия вернула 1 000 000, а рекурсивная упала на 24 тысячах.

**2. Ограничить глубину явно**, если вход приходит извне. Так делают парсеры: у `System.Text.Json` лимит вложенности по умолчанию — 64. Проверено: 64 вложенных массива разбираются, на 65-м — `JsonException` с текстом «The maximum configured depth of 64 has been exceeded». Своё ограничение — счётчик в параметре и понятная ошибка:

```csharp
static int HeightGuarded(TreeNode? node, int depth = 0)
{
    if (node is null) return 0;
    if (depth >= 1000) throw new InvalidOperationException("Слишком глубокое дерево");
    return 1 + Math.Max(HeightGuarded(node.Left, depth + 1), HeightGuarded(node.Right, depth + 1));
}
```

**3. Проверять запас стека.** `RuntimeHelpers.EnsureSufficientExecutionStack()` бросает `InsufficientExecutionStackException`, когда стек почти исчерпан, — и это обычное исключение, его можно поймать. `TryEnsureSufficientExecutionStack()` возвращает `bool`. Так защищаются компилятор Roslyn и компиляция деревьев выражений. В замере вызов в начале рекурсивного `Height` превратил падение процесса на дереве из миллиона узлов в перехватываемое исключение; минимальная рекурсия с проверкой остановилась на глубине около 30 000 — проверка оставляет запас.

**4. Поток с большим стеком** — `new Thread(work, maxStackSize: 256 * 1024 * 1024)`. С ним рекурсивный `Height` прошёл дерево из миллиона узлов. Это костыль для офлайн-расчётов: в обработчике запроса создавать поток ради стека — плохая идея, а потоки пула всё равно получают стандартный размер.

**5. Уменьшить глубину алгоритмически.** В быстрой сортировке рекурсивно обрабатывают меньшую часть, а большую — циклом: глубина становится O(log n) даже в худшем случае. `Array.Sort` в .NET вдобавок переключается на пирамидальную сортировку при слишком глубокой рекурсии.

## Типичные ошибки

- **Нет базового случая** или шаг не приближает к нему — бесконечная рекурсия и падение процесса.
- **Рекурсия по данным извне** без ограничения глубины.
- **Копия забыта в backtracking** — в ответе один и тот же изменяемый список.
- **Повторяющиеся подзадачи без кэша** — экспоненциальное время там, где хватило бы линейного; это тема `Динамическое программирование`.
- **Память не учтена** в оценке: O(глубины) стека — тоже память.
- **Расчёт на хвостовую оптимизацию** — в C# она не гарантирована.

## Что стоит ответить на собеседовании

Рекурсия — функция, вызывающая себя на меньшей подзадаче, с базовым случаем и шагом, который к нему приближает. Время — число вызовов на работу в вызове, память — максимальная глубина: обход дерева тратит O(h) стека, на вырожденном дереве это O(n).

Главная практическая опасность — переполнение стека. По умолчанию у потока на .NET 10 под Windows полтора мегабайта стека, это десятки тысяч вызовов: в замере простая рекурсия по списку падала на ~32 тысячах, рекурсивный DFS — на ~10 тысячах. `StackOverflow` не перехватывается: `catch` и `finally` не срабатывают, процесс завершается с `0xC00000FD`, и для сервиса это отказ всех запросов сразу. Хвостовая рекурсия в C# не гарантирована. Защита — итеративная версия с `Stack<T>` для данных извне, явный лимит глубины, как `MaxDepth = 64` в `System.Text.Json`, и `RuntimeHelpers.EnsureSufficientExecutionStack()`, которое превращает переполнение в обычное исключение.
