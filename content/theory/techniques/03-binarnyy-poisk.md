Идея бинарного поиска умещается в одну фразу: сравнить искомое с серединой и отбросить половину, где его быть не может. Написать его без ошибки с первого раза сложнее, чем кажется: перепутанные границы дают бесконечный цикл или пропущенный элемент. Надёжный способ — думать не о «середине», а об **инварианте**: что гарантированно верно про `lo` и `hi` на каждой итерации.

## Идея

Каждое сравнение делит диапазон пополам. После k шагов остаётся n / 2ᵏ элементов, и до одного доходим за log₂ n шагов: миллион элементов — 20 сравнений, миллиард — 30. Время O(log n), память O(1) в итеративной версии.

Два требования, без которых приём не работает:

- **данные упорядочены** — или, шире, условие монотонно: до некоторой точки «нет», после — «да»;
- **доступ по индексу за O(1)** — на связном списке дойти до середины уже стоит O(n).

## Как узнать задачу

- массив **отсортирован**, а от решения ждут лучше O(n);
- нужна **первая или последняя** позиция, где выполняется условие, точка вставки, число элементов меньше x;
- просят найти **минимальное значение параметра**, при котором что-то «помещается» или «успевает», и проверку для фиксированного значения легко написать — это поиск по ответу;
- массив «почти» отсортирован — например, циклически сдвинут.

## Классический поиск: закрытый интервал

```csharp
static int IndexOf(int[] a, int target)
{
    int lo = 0, hi = a.Length - 1;
    while (lo <= hi)
    {
        int mid = lo + (hi - lo) / 2;
        if (a[mid] == target) return mid;
        if (a[mid] < target) lo = mid + 1;
        else hi = mid - 1;
    }
    return -1;
}
```

Инвариант: если элемент есть, он лежит в `[lo, hi]` — **оба края включены**. Отсюда всё остальное. Пока интервал непуст, то есть `lo <= hi`, продолжаем. `mid` уже проверен, поэтому новые границы — `mid + 1` и `mid - 1`, без него. Пустой массив работает сам: `hi = -1`, цикл не выполняется ни разу.

## Lower bound: полуоткрытый интервал

На практике чаще нужен не «какой-нибудь индекс равного», а **первая позиция, где `a[i] >= target`**. Это lower bound: первое вхождение дубликата, точка вставки, начало диапазона.

```csharp
static int LowerBound(int[] a, int target)
{
    int lo = 0, hi = a.Length;
    while (lo < hi)
    {
        int mid = lo + (hi - lo) / 2;
        if (a[mid] < target) lo = mid + 1;
        else hi = mid;
    }
    return lo;
}
```

Инвариант другой: ответ лежит в `[lo, hi)`, и `hi = a.Length` — законный ответ «все элементы меньше». Цикл идёт, пока `lo < hi`. Если `a[mid] >= target`, сам `mid` может быть ответом, поэтому `hi = mid`, а не `mid - 1`. Если меньше — `mid` точно не ответ, `lo = mid + 1`. Цикл завершается всегда: `mid` строго меньше `hi`, и каждая ветка сужает интервал.

Upper bound — первая позиция, где `a[i] > target`, — отличается одним символом: `a[mid] <= target`. Вместе они дают диапазон равных:

```csharp
static (int First, int Last) Range(int[] a, int target)
{
    int first = LowerBound(a, target);
    if (first == a.Length || a[first] != target) return (-1, -1);
    return (first, UpperBound(a, target) - 1);
}
```

Для `[1, 3, 3, 3, 5, 8, 13]` и 3 получаем `(1, 3)`, для 4 — `(-1, -1)`. Число вхождений — `UpperBound - LowerBound`, за O(log n) вместо прохода по всем дубликатам.

Главное правило: **не смешивать два стиля**. `lo <= hi` идёт в паре с `hi = mid - 1`, `lo < hi` — с `hi = mid`. Смесь `lo <= hi` и `hi = mid` зацикливается, когда `lo == hi`.

## Что возвращает Array.BinarySearch

В .NET бинарный поиск есть готовый: `Array.BinarySearch`, `List<T>.BinarySearch`, `MemoryExtensions.BinarySearch` для `Span<T>`. Если элемент не найден, возвращается **отрицательное число** — побитовое дополнение точки вставки:

```csharp
var list = new List<int> { 1, 3, 5 };
int i = list.BinarySearch(4);
if (i < 0) list.Insert(~i, 4);
```

Список становится `[1, 3, 4, 5]`. Проверено на .NET 10: поиск 4 в `[1, 3, 3, 3, 5, 8, 13]` дал −5, а `~(-5)` — 4, ровно lower bound. Проверка `i == -1` вместо `i < 0` — частая ошибка: отрицательных значений много.

С дубликатами готовый метод возвращает индекс **какого-то** из равных. На `[1, 2, 2, 2, 2, 2, 3]` поиск 2 вернул 3 — середину, а не первое вхождение. Если нужно первое, пишите lower bound сами.

## Поиск по ответу

Самое полезное применение — когда массива нет вовсе. Пусть есть монотонная функция `ok(x)`: для малых x она ложна, начиная с некоторого — истинна. Тогда минимальный подходящий x ищется тем же lower bound, только по диапазону значений:

```csharp
static int FirstTrue(int lo, int hi, Func<int, bool> ok)
{
    while (lo < hi)
    {
        int mid = lo + (hi - lo) / 2;
        if (ok(mid)) hi = mid;
        else lo = mid + 1;
    }
    return lo;
}
```

Задача: есть грузы в фиксированном порядке, их надо развезти за `days` дней; какая минимальная грузоподъёмность нужна? Проверить конкретную грузоподъёмность легко — жадно набирать груз на день, пока влезает. И проверка монотонна: если хватает 15, хватит и 16.

```csharp
static int MinCapacity(int[] weights, int days)
{
    bool Fits(int capacity)
    {
        int used = 1, load = 0;
        foreach (int w in weights)
        {
            if (load + w > capacity)
            {
                used++;
                load = 0;
            }
            load += w;
        }
        return used <= days;
    }

    return FirstTrue(weights.Max(), weights.Sum(), Fits);
}
```

Нижняя граница — самый тяжёлый груз (меньше не поднять), верхняя — сумма всех (увезти за один день). Для грузов 1…10 и 5 дней ответ 15. Сложность — O(n · log(сумма)): логарифм диапазона проверок, каждая за O(n). Та же схема решает «минимальную скорость, чтобы успеть», «максимальное расстояние между объектами» и подбор таймаута по логам.

## Сдвинутый массив

Отсортированный массив, циклически сдвинутый: `[4, 5, 6, 7, 0, 1, 2]`. Целиком он не монотонен, но **одна из половин** относительно `mid` всегда отсортирована. Определяем какая, проверяем, лежит ли цель в её пределах, и отбрасываем другую:

```csharp
static int SearchRotated(int[] a, int target)
{
    int lo = 0, hi = a.Length - 1;
    while (lo <= hi)
    {
        int mid = lo + (hi - lo) / 2;
        if (a[mid] == target) return mid;
        if (a[lo] <= a[mid])
        {
            if (a[lo] <= target && target < a[mid]) hi = mid - 1;
            else lo = mid + 1;
        }
        else
        {
            if (a[mid] < target && target <= a[hi]) lo = mid + 1;
            else hi = mid - 1;
        }
    }
    return -1;
}
```

Поиск 0 возвращает 4, поиск 3 — −1. Код рассчитан на уникальные элементы. С дубликатами нельзя понять, какая половина отсортирована: на `[1, 3, 1, 1, 1]` поиск 3 вернул −1. Исправленная версия при `a[lo] == a[mid]` просто сдвигает `lo` на единицу, и худший случай становится O(n).

## Сложность

| | Время | Память |
| --- | --- | --- |
| итеративный поиск | O(log n) | O(1) |
| рекурсивный | O(log n) | O(log n) на стек |
| поиск по ответу | O(log D · стоимость проверки) | как у проверки |
| сортировка + k поисков | O(n log n + k log n) | зависит от сортировки |

Для одного поиска по неотсортированным данным сортировать невыгодно: O(n log n) хуже линейного прохода. Окупается, когда поисков много. Если нужны и частые вставки, и поиск, отсортированный массив не подходит — вставка в него O(n); тогда `SortedSet<T>` или `SortedDictionary<TKey, TValue>` с O(log n) на всё (подробнее — в `Деревья и графы`). Против хеш-таблицы бинарный поиск проигрывает в точном поиске, но умеет то, чего хеш не может: ближайший элемент, границы и диапазоны.

## Типичные ошибки

- **`(lo + hi) / 2`** — переполнение. При `lo = 1 500 000 000` и `hi = 2 000 000 000` выражение даёт −397 483 648. Правильно — `lo + (hi - lo) / 2`; в `SpanHelpers.BinarySearch` из исходников .NET середину считают через `uint`, где сумма не переполняется.
- **Смешение стилей границ** — бесконечный цикл или пропущенный элемент.
- **Немонотонная проверка** в поиске по ответу — алгоритм «находит» что-то, но не минимум.
- **Поиск в неотсортированных данных** — неверный ответ без исключения.
- **`BinarySearch(...) == -1`** вместо `< 0`.
- **Ожидать первое вхождение** от `Array.BinarySearch` при дубликатах.

## Что стоит ответить на собеседовании

Бинарный поиск работает на упорядоченных данных с доступом по индексу: сравниваем с серединой и отбрасываем половину, время O(log n), память O(1) итеративно. Корректность держится на инварианте: закрытый интервал `[lo, hi]` идёт с `lo <= hi` и `hi = mid - 1`, полуоткрытый `[lo, hi)` — с `lo < hi` и `hi = mid`; середину считают как `lo + (hi - lo) / 2`, чтобы не переполнить `int`.

Сильный ответ называет lower bound как основной рабочий вариант — первое вхождение, точка вставки, диапазон равных, — и поиск по ответу по монотонной проверке, например минимальная грузоподъёмность. Про .NET: `Array.BinarySearch` возвращает `~точку_вставки` при промахе и произвольный из равных при дубликатах. Про ограничения: на одиночный поиск сортировать невыгодно, а для частых вставок нужно дерево.
