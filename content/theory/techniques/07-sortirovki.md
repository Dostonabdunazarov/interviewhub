Свою сортировку в продакшене почти никто не пишет: в .NET есть `Array.Sort` и `OrderBy`. Но на сортировках удобно проверить сразу анализ сложности, рекурсию, устойчивость и понимание того, что стоит за стандартной библиотекой. А задача «отсортировать файл больше оперативной памяти» — вполне практическая.

## Bubble sort: эталон O(n²)

Пузырёк многократно проходит по массиву и меняет местами соседей, стоящих не по порядку. После каждого прохода самый большой из оставшихся элементов «всплывает» в конец, поэтому следующий проход на один элемент короче.

```csharp
static void BubbleSort(int[] a)
{
    for (int end = a.Length - 1; end > 0; end--)
    {
        bool swapped = false;
        for (int i = 0; i < end; i++)
        {
            if (a[i] > a[i + 1])
            {
                (a[i], a[i + 1]) = (a[i + 1], a[i]);
                swapped = true;
            }
        }
        if (!swapped) break;
    }
}
```

На `[5, 1, 4, 2]` первый проход даёт `[1, 4, 2, 5]`, второй — `[1, 2, 4, 5]`, третий проходит без обменов, и флаг `swapped` завершает работу. Средний и худший случай — O(n²) сравнений и обменов, лучший (уже отсортированный вход) благодаря раннему выходу — O(n). Память O(1), сортировка устойчива: строгое `>` не переставляет равные элементы.

Ценность пузырька — учебная. Из квадратичных на практике выигрывает сортировка вставками: меньше записей, быстра на маленьких и почти отсортированных массивах — её `Array.Sort` и применяет к коротким участкам.

## Quicksort: вся работа в разбиении

Quicksort выбирает опорный элемент, переставляет массив так, чтобы слева оказались элементы меньше опорного, справа — не меньше (partition), и рекурсивно сортирует обе части. Склеивать ничего не нужно: после разбиения опорный уже на своём окончательном месте, сортировка идёт на месте.

```csharp
static void QuickSort(int[] a, int lo, int hi)
{
    while (lo < hi)
    {
        int p = Partition(a, lo, hi);
        if (p - lo < hi - p) { QuickSort(a, lo, p - 1); lo = p + 1; }
        else { QuickSort(a, p + 1, hi); hi = p - 1; }
    }
}

static int Partition(int[] a, int lo, int hi)
{
    int r = Random.Shared.Next(lo, hi + 1);
    (a[r], a[hi]) = (a[hi], a[r]);
    int pivot = a[hi], i = lo;
    for (int j = lo; j < hi; j++)
        if (a[j] < pivot) { (a[i], a[j]) = (a[j], a[i]); i++; }
    (a[i], a[hi]) = (a[hi], a[i]);
    return i;
}
```

Это **схема Ломуто**: опорный уводится в конец, индекс `i` отмечает границу «меньших», в конце опорный встаёт на позицию `i`. Две детали делают код рабочим. Рекурсия идёт только в меньшую часть, а большая обрабатывается циклом — так глубина стека не превышает O(log n) при любом разбиении. И опорный выбирается случайно.

**Откуда O(n²).** Если опорный каждый раз оказывается минимальным или максимальным, разбиение даёт части 0 и n − 1: n уровней по O(n). Классика — первый или последний элемент как опорный на уже отсортированном массиве, то есть ровно на тех данных, что часто приходят из базы. Защиты две: случайный опорный (плохой случай остаётся, но перестаёт зависеть от входа) и медиана трёх — первого, среднего и последнего.

Второй источник деградации — **много одинаковых ключей**. Ломуто отправляет все равные опорному в одну часть, и массив из одинаковых чисел снова сортируется за O(n²). Помогает схема Хоара или трёхпутевое разбиение (`<`, `==`, `>`, «голландский флаг»).

```csharp
static void QuickSortHoare(int[] a, int lo, int hi)
{
    if (lo >= hi) return;
    int pivot = a[lo + (hi - lo) / 2];
    int i = lo - 1, j = hi + 1;
    while (true)
    {
        do i++; while (a[i] < pivot);
        do j--; while (a[j] > pivot);
        if (i >= j) break;
        (a[i], a[j]) = (a[j], a[i]);
    }
    QuickSortHoare(a, lo, j);
    QuickSortHoare(a, j + 1, hi);
}
```

У Хоара два указателя идут навстречу (см. `Два указателя`) и останавливаются на элементах, **равных** опорному, поэтому дубликаты делятся между частями поровну. Обменов меньше, чем у Ломуто, но опорный не обязан оказаться на позиции `j`, и рекурсия идёт по `[lo, j]` и `[j + 1, hi]` — перепутать границы здесь проще всего.

Quicksort **неустойчив**: дальние обмены переставляют равные элементы. Зато он не аллоцирует, внутренний цикл предельно прост, доступ к памяти локален — поэтому на массивах в памяти он обычно быстрее конкурентов.

## Mergesort: работа в слиянии

Mergesort делит массив пополам, рекурсивно сортирует половины и сливает их, каждый раз забирая меньший из двух текущих элементов.

```csharp
static void MergeSort(int[] a)
{
    var buf = new int[a.Length];
    Sort(a, buf, 0, a.Length);

    static void Sort(int[] a, int[] buf, int lo, int hi)
    {
        if (hi - lo < 2) return;
        int mid = lo + (hi - lo) / 2;
        Sort(a, buf, lo, mid);
        Sort(a, buf, mid, hi);
        int i = lo, j = mid, k = lo;
        while (i < mid && j < hi)
            buf[k++] = a[j] < a[i] ? a[j++] : a[i++];
        while (i < mid) buf[k++] = a[i++];
        while (j < hi) buf[k++] = a[j++];
        Array.Copy(buf, lo, a, lo, hi - lo);
    }
}
```

Глубина всегда log n, каждый уровень — O(n), поэтому O(n log n) **гарантированно**, независимо от входа. Устойчивость обеспечивает одно условие: при равенстве берётся элемент из левой половины (`a[j] < a[i]`, а не `<=`). Цена — буфер O(n) и копирование на каждом уровне. Буфер аллоцируется один раз на весь вызов, а не на каждое слияние — иначе сортировка превращается в генератор мусора для GC.

Для **связного списка** mergesort идеален: слияние перевешивает указатели без буфера, а произвольный доступ, нужный quicksort, у списка как раз отсутствует. И он же основа внешней сортировки: слияние читает входы строго последовательно, что и нужно диску.

## Quicksort против mergesort

Оба — «разделяй и властвуй» со средним O(n log n), но quicksort работает **до** рекурсии (разбиение), а mergesort — **после** (слияние). Из этого следует всё остальное:

| | Quicksort | Mergesort |
| --- | --- | --- |
| худший случай | O(n²) | O(n log n) |
| доп. память | O(log n) стек | O(n) буфер |
| устойчивость | нет | да |
| массивы в памяти | обычно быстрее | копирование в буфер |
| списки, внешняя сортировка | не подходит | стандартный выбор |

Массив примитивов, устойчивость не важна, память дорога — quicksort, точнее его гибрид. Нужна устойчивость (многоуровневая сортировка) или гарантия от специально подобранного входа — mergesort, Timsort или heapsort.

## Что делает .NET

`Array.Sort`, `List<T>.Sort` и `Span<T>.Sort` реализуют **introsort**: quicksort с медианой трёх, участки до 16 элементов досортировываются вставками, а когда глубина рекурсии превышает порог порядка 2·log₂ n, участок уходит в heapsort. Так худший случай ограничен O(n log n), а память — O(log n). Результат **неустойчив**.

`Enumerable.OrderBy` и `ThenBy` **устойчивы** — это гарантия документации: заказы, отсортированные `OrderBy(o => o.Customer)`, внутри одного клиента сохранят исходный порядок, а у `Array.Sort` по тому же ключу он не определён. Чтобы получить устойчивость без LINQ, сортируют пары `(key, index)` и при равных ключах сравнивают индекс.

## Данные больше памяти: внешняя сортировка

Классика — **external merge sort** в две фазы.

1. **Формирование ранов.** Читаем вход, пока не исчерпан бюджет памяти, сортируем `Array.Sort` и пишем во временный файл. Получается R ≈ N / M отсортированных ранов, где N — объём данных, M — бюджет.
2. **k-way merge.** Открываем все раны, кладём первую строку каждого в min-кучу, извлекаем минимум, пишем в выход и подкладываем следующую строку из того же рана. Время O(N log R), память — по буферу на ран.

```csharp
var heap = new PriorityQueue<int, string>(readers.Length, StringComparer.Ordinal);
for (int i = 0; i < readers.Length; i++)
    if (await readers[i].ReadLineAsync(ct) is { } first) heap.Enqueue(i, first);

string? previous = null;
while (heap.TryDequeue(out int run, out string? line))
{
    if (!distinct || !string.Equals(previous, line, StringComparison.Ordinal))
    {
        await writer.WriteLineAsync(line.AsMemory(), ct);
        previous = line;
    }
    if (await readers[run].ReadLineAsync(ct) is { } next) heap.Enqueue(run, next);
}
```

**Дедупликация** достаётся бесплатно: на выходе слияния одинаковые строки идут подряд, достаточно сравнить с предыдущей. Важно, чтобы раны сортировались и сливались **одним и тем же компаратором**: раны с `CurrentCulture` и слияние через `Ordinal` дадут «почти отсортированный» выход с пропущенными дубликатами. Для машинных данных почти всегда нужен `Ordinal`. Кучевое слияние неустойчиво; если важен порядок равных, приоритетом делают `(key, runIndex)`.

Бюджет считают в объектах, а не в байтах файла: строка в .NET — заголовок, длина и 2 байта на символ UTF-16 плюс ссылка в массиве, так что короткие ASCII-строки в памяти занимают в разы больше, чем на диске (см. `Оценка памяти`). Если ранов тысячи, сливают в несколько проходов: их ⌈log_F R⌉, где F — fan-in. Временные файлы удаляют в `finally` и не кладут на `tmpfs`, который сам живёт в RAM.

**Хеш-партиционирование** — путь для дедупликации без сортировки. Первый проход раскладывает записи по P файлам по `hash(key) % P`, где P подобран так, чтобы партиция с запасом влезала в память. Второй проход читает каждую партицию в `HashSet<string>` и пишет уникальные. Одинаковые ключи гарантированно оказываются в одном файле, поэтому глобальная задача сводится к локальной: ровно два прохода по диску, партиции обрабатываются параллельно, но порядок на выходе произвольный. Риск — перекос: горячий ключ или плохой хеш, и одна партиция не влезает — её разбивают повторно с другим seed. Тот же приём использует hash join в СУБД при нехватке памяти.

Для разовой задачи свой код не нужен: `LC_ALL=C sort -u big.txt -o out.txt` делает ровно это — раны во временных файлах и слияние, а `LC_ALL=C` включает побайтовое сравнение вместо локали. PostgreSQL сам уходит во внешнюю сортировку, когда не хватает `work_mem`. Свой код оправдан в регулярном пайплайне, где нужны контроль памяти, отмена и метрики.

## Что стоит ответить на собеседовании

Пузырёк — обмен соседей, O(n²), ранний выход по флагу даёт O(n) на отсортированном входе; знают его ради анализа сложности, а из квадратичных на практике берут вставки. Quicksort работает в разбиении, на месте, в среднем O(n log n), но неустойчив и при неудачном опорном деградирует до O(n²) — лечится случайным опорным или медианой трёх, а дубликаты — схемой Хоара или трёхпутевым разбиением. Mergesort работает в слиянии, гарантирует O(n log n) и устойчивость ценой O(n) памяти, хорош для списков и внешней сортировки.

Сильный ответ показывает знание реальности: в .NET `Array.Sort` — introsort (quicksort + heapsort при глубокой рекурсии + вставки на мелких участках), неустойчив, а `OrderBy` устойчив; рекурсия в меньшую часть держит стек в O(log n). Для данных больше памяти — раны плюс k-way merge через `PriorityQueue` с дедупликацией на слиянии, или хеш-партиционирование в два прохода с риском перекоса; узкое место там диск, а не CPU, и для разовой задачи хватает `sort -u`.
