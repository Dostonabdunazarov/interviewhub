Хороший HTTP API предсказуем: клиент по методу понимает, можно ли повторить запрос, по коду — что пошло не так, по телу ошибки — что именно. Эти соглашения важны не ради эстетики. На них полагаются ретраи, кэши, балансировщики и мониторинг, и API, который их нарушает, ломает инфраструктуру вокруг себя. Версионирование — продолжение той же темы: как менять контракт и не ломать тех, кто на него уже опирается.

## Ресурсы и методы

REST по Филдингу с гипермедиа почти никто не реализует. Большинство API — второй уровень модели зрелости Ричардсона: ресурсы плюс правильные методы и коды, и этого достаточно.

```http
GET    /orders?status=paid      список
GET    /orders/42               один ресурс
POST   /orders                  создать → 201 Created + Location: /orders/42
PUT    /orders/42               полная замена
PATCH  /orders/42               частичное изменение
DELETE /orders/42               удалить → 204 No Content
POST   /orders/42/cancellation  действие, выраженное как ресурс
```

В URI — существительные, а не глаголы: `/orders/42/cancellation` вместо `/cancelOrder?id=42`.

Семантика методов задана RFC 9110:

| Метод | Safe | Идемпотентен |
| --- | --- | --- |
| `GET`, `HEAD`, `OPTIONS` | да | да |
| `PUT`, `DELETE` | нет | да |
| `POST` | нет | нет |
| `PATCH` | нет | не гарантирована |

Идемпотентность — про **состояние сервера, а не про ответ**. Первый `DELETE /orders/42` вернёт `204`, второй — `404`, но состояние одинаковое: заказа нет. Это корректно.

Реализация обязана соответствовать контракту. `PUT`, который внутри делает `balance += amount`, нарушает семантику: клиент с ретраями, считающий `PUT` безопасным для повтора, зачислит деньги дважды.

## Коды ответа

Первая цифра задаёт класс, и для клиентов это важнее конкретного числа: на 4xx повтор без изменений не поможет, на 5xx — может. Поэтому ретрай-политики повторяют 5xx, 408 и 429, но не остальные 4xx.

Пары, которые путают чаще всего:

- **`401` и `403`** — не аутентифицирован против нет прав; подробно в статье `Аутентификация и JWT`. Вернуть `404` вместо `403`, чтобы не раскрывать существование ресурса, — допустимый приём.
- **`400` и `422`** — синтаксически неверный запрос против нарушенного бизнес-правила. ASP.NET Core на ошибки валидации по умолчанию отдаёт `400`. Граница спорная, важна единообразность.
- **`502`, `503`, `504`** — прокси получил плохой ответ, сервис временно недоступен, прокси не дождался ответа.

Отдельная ошибка — `200` с `{"success": false}`: мониторинг и ретраи смотрят на код и видят успех.

## ProblemDetails

Стандартный формат тела ошибки — RFC 9457, тип `application/problem+json`. Поля `type`, `title`, `status`, `detail`, `instance`, всё остальное — расширения. В ASP.NET Core его включает одна строка:

```csharp
builder.Services.AddProblemDetails();

app.UseExceptionHandler();
app.UseStatusCodePages();
```

Проверено на .NET 10, Production-окружение:

```
GET /nf    (Results.NotFound() без тела) → 404 application/problem+json
           {"type":"https://tools.ietf.org/html/rfc9110#section-15.5.5","title":"Not Found","status":404,"traceId":"..."}
GET /boom  (throw new InvalidOperationException("secret detail")) → 500
           {"title":"An error occurred while processing your request.","status":500,"traceId":"..."}
```

Пустой 404 получил тело благодаря `UseStatusCodePages`, а необработанное исключение — благодаря `UseExceptionHandler`. Текст исключения в ответ не попал, зато есть `traceId`, по которому ошибку находят в логах и трейсах. Детали и стек допустимы только в Development.

Явно ошибка возвращается через `TypedResults.Problem` или `ControllerBase.Problem()`:

```csharp
return TypedResults.Problem(
    title: "Недостаточно средств",
    statusCode: StatusCodes.Status422UnprocessableEntity,
    type: "https://example.com/problems/insufficient-funds");
```

Поле `type` — часть контракта: клиенты ветвятся по нему, а не по тексту `title`. Менять его — такое же breaking change, как переименовать поле. Ошибки валидации, бизнес-ошибки и 500 должны иметь один формат, иначе клиенту приходится разбирать три разных тела.

## Идемпотентный POST

Клиент отправил `POST /payments`, ответ потерялся по таймауту. Он не знает, прошёл ли платёж, и повторяет запрос. Без защиты — двойное списание. Стандартное решение — заголовок `Idempotency-Key`: клиент генерирует ключ, сервер сохраняет результат первой обработки и на повтор отдаёт его же.

```csharp
app.MapPost("/payments", async (
    [FromHeader(Name = "Idempotency-Key")] Guid key,
    CreatePayment cmd, AppDbContext db, CancellationToken ct) =>
{
    var existing = await db.IdempotencyRecords.FindAsync([key], ct);
    if (existing is not null)
        return existing.RequestHash == cmd.Hash()
            ? Results.Json(existing.Response, statusCode: existing.StatusCode)
            : Results.UnprocessableEntity();

    var payment = Payment.Create(cmd);
    db.Payments.Add(payment);
    db.IdempotencyRecords.Add(new IdempotencyRecord(key, cmd.Hash(), 201, payment.ToDto()));
    await db.SaveChangesAsync(ct);

    return Results.Created($"/payments/{payment.Id}", payment.ToDto());
});
```

Ключевые детали: **уникальный индекс** на ключ — единственная защита от гонки двух одновременных повторов; запись ключа и бизнес-изменение — в одной транзакции; тот же ключ с другим телом — ошибка клиента. Если в домене уже есть естественный ключ — номер заказа из внешней системы, ID события из очереди, — хватит уникального ограничения и `INSERT ... ON CONFLICT DO NOTHING`.

## Rate limiting

С .NET 7 ограничение частоты встроено: политики регистрируются в `AddRateLimiter`, включаются `UseRateLimiter` и привязываются к endpoint'ам через `RequireRateLimiting`. Алгоритмы — fixed window, sliding window, token bucket и concurrency limiter.

Одна деталь стоит отдельного упоминания. Проверено на .NET 10, политика на один запрос в минуту без дополнительных настроек:

```
GET /rl → 200
GET /rl → 503 Service Unavailable
```

По умолчанию отказ — **`503`**, а не `429`. Клиент воспримет это как падение сервиса и начнёт ретраить, усиливая нагрузку. `RejectionStatusCode = 429` и заголовок `Retry-After` в `OnRejected` нужно выставлять явно. И помнить, что счётчики живут в памяти процесса: при трёх репликах лимит «100 в минуту» превращается в «до 300».

## Что ломает клиентов

Прежде чем думать о механике версий, стоит понять, когда новая версия вообще нужна. Большинство изменений можно сделать обратно совместимыми:

| Совместимо | Ломает клиентов |
| --- | --- |
| новое необязательное поле в ответе | удаление или переименование поля |
| новый endpoint | смена типа поля |
| новый необязательный параметр | новый обязательный параметр или поле запроса |
| ослабление валидации | ужесточение валидации |
| | смена семантики поля или статус-кода |
| | новое значение enum для клиентов со строгой десериализацией |
| | `null` там, где его раньше не было |

Последние две строки самые коварные: формально схема только расширилась, но строгий клиент падает.

Приёмы, позволяющие не плодить версии:

- **Tolerant reader** — документировать, что клиенты обязаны игнорировать неизвестные поля и быть готовы к новым значениям enum.
- **Expand–contract** — чтобы переименовать `name` в `fullName`, сначала отдают и принимают оба поля, помечают старое deprecated, ждут, пока трафик со старым полем исчезнет, и только потом удаляют.
- **Расширяемые структуры** — объект `"price": {"amount": 10, "currency": "EUR"}` вместо числа там, где возможен рост.

От случайных breaking changes защищает сравнение OpenAPI-спецификации, сгенерированной на сборке (с .NET 9 — встроенный `Microsoft.AspNetCore.OpenApi`), с опубликованной.

## Asp.Versioning

Когда breaking change неизбежен, новая версия выходит рядом со старой. Стандартная библиотека — `Asp.Versioning`: пакет `Asp.Versioning.Http` для Minimal API, `Asp.Versioning.Mvc` для контроллеров.

```csharp
builder.Services.AddApiVersioning(o =>
{
    o.DefaultApiVersion = new ApiVersion(1);
    o.ReportApiVersions = true;
});

var orders = app.NewVersionedApi("Orders");

var v1 = orders.MapGroup("/api/v{version:apiVersion}/orders").HasApiVersion(1.0);
v1.MapGet("/{id}", (int id) => new OrderV1(id, "pending"));

var v2 = orders.MapGroup("/api/v{version:apiVersion}/orders").HasApiVersion(2.0);
v2.MapGet("/{id}", (int id) => new OrderV2(id, new Status("pending", DateTime.UtcNow)));
```

Версию можно передавать сегментом URL, query-параметром, заголовком или в media type. Чаще всего выбирают URL: он виден в логах, кэшируется и понятен гейтвеям. Поведение при неверной версии зависит от способа — проверено на .NET 10 с `Asp.Versioning` 10.0:

```
GET /api/v1/ping              → 200, api-supported-versions: 1.0, 2.0
GET /api/v3/ping              → 404 Not Found
GET /qv?api-version=3.0       → 400, code: UnsupportedApiVersion
GET /qv                       → 400, code: ApiVersionUnspecified
```

С URL-сегментом несуществующая версия — это несуществующий путь, отсюда 404. С query-параметром библиотека отвечает осмысленным 400 в формате ProblemDetails. Запрос без версии отклоняется, пока не включён `AssumeDefaultVersionWhenUnspecified`. Заголовок `api-supported-versions` добавляется благодаря `ReportApiVersions` и показывает клиенту, какие версии живы.

Версия не должна размножать бизнес-логику. Домен один, версии отличаются только DTO и маппингом на границе API.

## Жизненный цикл версии

1. Новая версия выходит рядом со старой, обе обслуживаются одним приложением.
2. Старая помечается устаревшей: `[ApiVersion(1.0, Deprecated = true)]` даёт заголовок `api-deprecated-versions`, а заголовки `Deprecation` и `Sunset` сообщают дату отключения и ссылку на гайд миграции.
3. Трафик по версиям и по клиентам измеряется — вы знаете, кого предупреждать лично.
4. После даты — сначала временные периоды отказов, чтобы забывшие клиенты заметили, затем `410 Gone`.

## Что стоит ответить на собеседовании

HTTP API строится вокруг ресурсов и семантики методов: `GET`, `PUT`, `DELETE` идемпотентны, `POST` — нет, и идемпотентность касается состояния сервера, а не кода ответа. Ошибки отдаются кодами нужного класса — 4xx не ретраят, 5xx можно, — в едином формате ProblemDetails, который в ASP.NET Core включают `AddProblemDetails`, `UseExceptionHandler` и `UseStatusCodePages`. `POST` делают идемпотентным через `Idempotency-Key` с уникальным индексом и записью в одной транзакции с бизнес-изменением.

Сильный ответ про версионирование начнётся с того, что большинство изменений делают обратно совместимыми без новой версии, а breaking change — это удаление и переименование полей, смена типа, новые обязательные поля, неожиданный `null` или значение enum. Новая мажорная версия живёт рядом со старой через `Asp.Versioning`, с общим доменом и разными DTO, а старая выводится по объявленному графику с заголовками `Deprecation` и `Sunset`. И добавит практическую деталь: встроенный rate limiter по умолчанию отказывает кодом `503`, а не `429`, и это нужно настраивать явно.
