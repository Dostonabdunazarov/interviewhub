Логи — главный источник правды, когда в проде что-то пошло не так, и одновременно одна из самых недооценённых статей расходов. Код пишет в абстракцию `ILogger`, а дальше сообщение проходит фильтрацию, уходит в один или несколько провайдеров, сериализуется, едет по сети и индексируется в хранилище. На каждом шаге можно потерять либо полезность лога, либо производительность сервиса.

Эта статья — про модель `Microsoft.Extensions.Logging` и про то, как писать логи так, чтобы ими можно было пользоваться и чтобы они не тормозили запросы.

## Модель: логгер, фабрика, провайдер

Код получает логгер через DI и пишет в него:

```csharp
public sealed class OrderService(ILogger<OrderService> logger)
{
    public void Place(Order order)
    {
        logger.LogInformation("Order {OrderId} placed by {UserId}", order.Id, order.UserId);
    }
}
```

За этим стоят три роли:

| Тип | Роль |
| --- | --- |
| `ILogger<T>` | логгер с категорией, равной полному имени типа `T` |
| `ILoggerFactory` | создаёт логгеры с произвольной категорией: `CreateLogger("Payments")` |
| `ILoggerProvider` | приёмник: консоль, Debug, EventSource, OpenTelemetry, Serilog |

Один вызов `LogInformation` уходит во **все** провайдеры, которые пропустили его по фильтру. `WebApplication.CreateBuilder` по умолчанию подключает Console, Debug и EventSource, на Windows ещё EventLog. Набор меняют через `builder.Logging`: `ClearProviders()`, `AddJsonConsole()`, `AddOpenTelemetry(...)`.

Уровни идут по возрастанию важности: `Trace`, `Debug`, `Information`, `Warning`, `Error`, `Critical`; `None` выключает категорию целиком. Исключение передают отдельным аргументом — `logger.LogError(ex, "Payment {PaymentId} failed", id)`, а не через `ex.Message` в тексте: так провайдер сохранит тип и стектрейс как поля.

## Категории и фильтрация

Категория — строка, по которой фильтруют. Для `ILogger<T>` это имя типа с пространством имён, поэтому фильтры пишутся по префиксам:

```json
"Logging": {
  "LogLevel": {
    "Default": "Information",
    "Microsoft.AspNetCore": "Warning",
    "Microsoft.EntityFrameworkCore.Database.Command": "Information"
  },
  "Console": {
    "LogLevel": { "Default": "Warning" }
  }
}
```

Правила выбора: из подходящих правил побеждает самый длинный совпавший префикс категории, а секция конкретного провайдера (`Console`) важнее общей `LogLevel`. В примере фреймворк ASP.NET Core пишет только предупреждения, SQL-команды EF Core видны, а консоль поверх всего пропускает лишь `Warning` и выше.

То же можно задать кодом — `builder.Logging.AddFilter("Microsoft.AspNetCore", LogLevel.Warning)` или `SetMinimumLevel(...)`. Конфигурация удобнее: при изменении `appsettings.json` или другого источника с перезагрузкой фильтры перечитываются без рестарта, и Debug для одной категории можно включить на время разбора инцидента. Как устроены источники и перезагрузка — в статье `Конфигурация и options`.

## Structured logging

Шаблон сообщения в `ILogger` — не формат-строка, а описание события. Именованные плейсхолдеры становятся полями:

```csharp
logger.LogInformation("Order {OrderId} processed in {ElapsedMs} ms", order.Id, sw.ElapsedMilliseconds);
logger.LogInformation($"Order {order.Id} processed in {sw.ElapsedMilliseconds} ms");
```

Первый вызов отдаёт провайдеру шаблон и пары «имя — значение». JSON-приёмник сохранит `MessageTemplate`, `OrderId: 42`, `ElapsedMs: 118` и `TraceId` текущей активности. Второй — готовую строку: поля исчезли, искать придётся регуляркой, а каждый экземпляр события выглядит как уникальный шаблон, что ломает группировку в хранилище.

Что даёт структура: фильтр `OrderId = 42` без полнотекстового поиска, агрегации вроде среднего `ElapsedMs` по эндпоинту, группировка всех экземпляров одного события и корреляция с трейсами по `TraceId` и `SpanId`.

Правила шаблонов, о которых спрашивают:

- плейсхолдеры сопоставляются с аргументами **по позиции**, а не по имени — переставили аргументы, и поля перепутались молча;
- имена полей — PascalCase и одинаковые по всему коду: `UserId`, а не где-то `userId`, а где-то `User`, иначе запросы к хранилищу перестают находить события;
- `{@Order}` — синтаксис деструктуризации Serilog; стандартные провайдеры объект просто приведут к строке;
- идентификатор в тексте вместо плейсхолдера даёт ту же высокую кардинальность шаблонов, что и интерполяция.

Для консоли в контейнере есть встроенный `AddJsonConsole()`; дальше логи собирает агент на ноде и отправляет в Seq, Elasticsearch, Loki или OpenTelemetry Collector.

## Scopes

Контекст, общий для группы сообщений — correlation id, тенант, номер заказа, — не передают в каждый вызов, а открывают scope:

```csharp
using (logger.BeginScope(new Dictionary<string, object> { ["OrderId"] = order.Id, ["TenantId"] = tenant }))
{
    logger.LogInformation("Pricing started");
    await pricing.CalculateAsync(order, ct);
    logger.LogInformation("Pricing finished");
}
```

Все сообщения внутри блока, включая записанные другими классами ниже по стеку вызовов, получат эти поля. Scope течёт через `await`, поскольку хранится в `AsyncLocal`. Словарь `string → object` — общепринятая форма, которую провайдеры разворачивают в отдельные поля; строковый шаблон `BeginScope("Order {OrderId}", id)` тоже работает. Важно, что провайдер должен уметь показывать scopes: у консольного форматтера это включается опцией `IncludeScopes`, у OpenTelemetry — одноимённой опцией `OpenTelemetryLoggerOptions`. Типичное место для scope — middleware, как `CorrelationIdMiddleware` в статье `Pipeline и middleware`.

## Serilog и OpenTelemetry

Serilog и NLog подключаются как провайдеры `ILogger`, поэтому код приложения от выбора библиотеки не зависит. Serilog берут ради enrichers, деструктуризации и большого набора sink'ов. Альтернатива — экспорт через OpenTelemetry: `builder.Logging.AddOpenTelemetry(o => o.AddOtlpExporter())`, после чего логи идут в Collector вместе с трейсами и метриками и связываются с ними по `TraceId`. Детали — в статьях `OpenTelemetry в .NET` и `Логи, метрики, трассировки`.

## Сколько стоит вызов

Стоимость логирования складывается из трёх частей: работа на вызывающем потоке, доставка в sink и обратное давление, когда sink не успевает.

**Аргументы на выключенном уровне.** Методы `LogDebug`, `LogInformation` и остальные принимают `params object?[]`. Вызов `logger.LogDebug("Order {Id} total {Total}", id, total)` при уровне `Information` ничего не пишет, но массив уже аллоцирован, а `long` и `decimal` упакованы — проверка уровня происходит внутри, после вызова. На горячем пути это тысячи лишних аллокаций в секунду. Интерполяция хуже: строка форматируется всегда.

**Дорогие аргументы.** `JsonSerializer.Serialize(request)` в списке аргументов выполняется до любой проверки. Такие вызовы оборачивают в `if (logger.IsEnabled(LogLevel.Debug))`. Ручная проверка спасает от вычислений на выключенном уровне, но не от боксинга на включённом.

**Source generator.** Атрибут `[LoggerMessage]` (с .NET 6) генерирует метод, который сначала проверяет `IsEnabled`, а затем передаёт аргументы строго типизированно, без `object[]` и упаковки; шаблон разбирается на этапе компиляции:

```csharp
public static partial class OrderLog
{
    [LoggerMessage(EventId = 1001, Level = LogLevel.Debug, Message = "Order {OrderId} priced at {Total}")]
    public static partial void OrderPriced(this ILogger logger, long orderId, decimal total);

    [LoggerMessage(EventId = 1002, Level = LogLevel.Warning, Message = "Provider {Provider} responded in {ElapsedMs} ms")]
    public static partial void SlowPayment(this ILogger logger, string provider, double elapsedMs);
}

logger.OrderPriced(order.Id, order.Total);
```

Бонус — каталог событий с `EventId` в одном месте и единые имена полей. Анализатор CA1848 подсвечивает вызовы `LogXxx`, которые стоит перевести на `LoggerMessage`. До генератора то же делали вручную через `LoggerMessage.Define`.

**Scopes на каждый запрос.** Словарь в `BeginScope` и провайдер, который собирает все активные scopes в каждое событие, — заметная доля аллокаций в профиле.

## Синхронные sink'и и обратное давление

Провайдер вызывается на потоке запроса. Если он пишет синхронно в медленный приёмник, запросы ждут логирование. Консольный провайдер пишет в очередь и выводит из отдельного потока, но очередь ограничена, и при переполнении поток запроса либо ждёт, либо сообщения отбрасываются — это настраивается в `ConsoleLoggerOptions`. В контейнере stdout — это pipe: если Fluent Bit или Vector не успевают его вычитывать, запись блокируется. Файловый sink с `flush` на каждое сообщение упирается в диск.

Общее правило для любого асинхронного sink'а: ограниченная очередь и явная политика переполнения — отбрасывать `Debug` и `Information`, но не ошибки. Неограниченный буфер под нагрузкой становится утечкой памяти, а при падении процесса буфер теряется, поэтому на остановке его сбрасывают — см. `Graceful shutdown`.

## Объём, уровни и сэмплирование

Двадцать строк на запрос при 5 000 RPS — 100 000 событий в секунду. Это CPU на сериализацию, сеть и индексация в хранилище, которая нередко стоит дороже самого сервиса. Каждое поле индексируется, поэтому высококардинальные поля дорожают быстрее остальных.

Что делают на практике:

- **уровни по категориям**: `Microsoft.AspNetCore` и `Microsoft.EntityFrameworkCore` на `Warning`, свой код на `Information`, `Debug` — точечно и временно;
- **не дублировать метрики и трейсы**: «запрос начат», «запрос завершён за N мс» — это span и гистограмма, а не две строки лога; встроенные сообщения хостинга о каждом запросе в проде обычно гасят фильтром;
- **логировать исключение один раз** там, где его обрабатывают, а не на каждом уровне стека с пятью копиями стектрейса;
- **сэмплирование и rate limiting** повторяющихся событий: упавшая зависимость рождает одну и ту же ошибку тысячи раз в секунду; в пакетах `Microsoft.Extensions.Telemetry` из репозитория dotnet/extensions есть сэмплирование и буферизация логов;
- **stdout в компактном формате** и сбор агентом на ноде дешевле, чем отправка по сети из процесса.

Измеряют цену так: профиль CPU и аллокаций под нагрузкой с долей `Microsoft.Extensions.Logging`, `FormattedLogValues` и сериализатора sink'а, затем тот же нагрузочный тест с уровнем `Warning`. Разница в RPS, p99 и CPU на запрос — это и есть стоимость логирования.

## PII и секреты

Логи читает больше людей, чем базу, хранятся они дольше, а удалить из них данные по запросу пользователя почти невозможно. Не логируют пароли, токены, заголовок `Authorization`, cookies, номера карт и персональные данные. Самые частые утечки — логирование тел запросов и ответов целиком, включая `UseHttpLogging` с телами, и объект запроса, сериализованный в аргумент. Для полей, которые нужны в маскированном виде, есть редактирование через `Microsoft.Extensions.Compliance.Redaction`. Аудит — отдельный поток событий с другими гарантиями доставки и хранения, а не `LogInformation`.

## Что стоит ответить на собеседовании

Код пишет в `ILogger<T>`, категория которого — имя типа; `ILoggerFactory` создаёт логгеры с произвольной категорией, а провайдеры решают, куда уходят сообщения. Фильтрация задаётся в секции `Logging` конфигурации по уровню и префиксу категории: побеждает самый длинный префикс, настройки провайдера важнее общих. Шаблоны с именованными плейсхолдерами дают structured logging — поля, по которым можно искать и агрегировать; интерполяция превращает событие в строку. Контекст для группы сообщений добавляют через `BeginScope`, исключение передают отдельным аргументом.

Сильный ответ покажет понимание цены: `params object[]` и боксинг аргументов даже на выключенном уровне, поэтому на горячем пути — `[LoggerMessage]` с проверкой `IsEnabled` и без упаковки; синхронный или переполненный sink тормозит запросы, а асинхронной доставке нужна ограниченная очередь с политикой сброса. И назовёт, что делать с объёмом: уровни по категориям, длительности в метриках и трейсах вместо логов, одно логирование исключения, сэмплирование повторяющихся ошибок, никаких PII и секретов в полях.
