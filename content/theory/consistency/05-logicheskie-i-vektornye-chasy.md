Когда два события произошли на разных машинах, вопрос «что было раньше» по системным часам не решается: часы расходятся, прыгают и врут, это тема статьи `Почему нельзя верить часам`. Но часто нужен не момент времени, а **порядок**: могла ли запись B знать о записи A, или они сделаны независимо и одна должна не затереть другую, а стать конфликтом. Логические часы отвечают именно на этот вопрос и не опираются на физическое время вовсе. На собеседовании их спрашивают на уровне «объясните разницу между Лэмпортом и векторными часами и зачем они в репликации».

## Happened-before

Лесли Лэмпорт в статье 1978 года «Time, Clocks, and the Ordering of Events in a Distributed System» определил отношение «произошло раньше» (→) без всякого времени:

- A → B, если A и B — события одного процесса и A случилось раньше по его ходу выполнения;
- A → B, если A — отправка сообщения, а B — его получение;
- транзитивность: из A → B и B → C следует A → C.

Если ни A → B, ни B → A, события **конкурентны**: ни одно не могло повлиять на другое. Конкурентность здесь — не «одновременность по часам», а отсутствие причинной цепочки. Две записи с разницей в минуту конкурентны, если между узлами за эту минуту не прошло ни одного сообщения.

```text
P1:  a ──── b(send m) ─────────────── c
                 \
P2:  d ────────── e(recv m) ── f
P3:  g ──────────────────────────── h

a → b → e → f        b → c
d → e                g, h конкурентны со всем на P1 и P2
c ∥ f                c и f конкурентны: пути между ними нет
```

## Часы Лэмпорта

Каждый процесс хранит целочисленный счётчик:

1. перед каждым локальным событием — увеличить счётчик;
2. при отправке — положить текущее значение в сообщение;
3. при получении — `counter = max(counter, received) + 1`.

Гарантия ровно одна: **если A → B, то L(A) < L(B)**. Обратное неверно: из L(A) < L(B) не следует, что A причина B, — события могли быть конкурентными, а номера сложились так случайно. Если к счётчику добавить идентификатор узла и сравнивать пары `(counter, nodeId)`, получится **полный порядок** всех событий, согласованный с причинностью. Лэмпорт использовал его для распределённого взаимного исключения: все узлы обрабатывают запросы в одном и том же порядке меток.

Полного порядка хватает, когда нужно лишь, чтобы все узлы детерминированно выбрали одного победителя. Но для репликации этого мало. Две независимые записи одного ключа получат разные метки, одна из них «победит» — и конфликт, который надо было показать пользователю или слить, исчезнет молча. Last-write-wins по меткам Лэмпорта лучше, чем по wall clock, потому что не зависит от расхождения часов, но конкурентные записи теряет точно так же.

## Векторные часы

Векторные часы (независимо описаны Фиджем и Маттерном в 1988 году) различают «раньше» и «конкурентно». Каждый процесс хранит вектор счётчиков — по компоненте на каждый процесс:

1. при локальном событии увеличивает свою компоненту;
2. при отправке прикладывает весь вектор;
3. при получении берёт поэлементный максимум со своим вектором и увеличивает свою компоненту.

Сравнение: если каждая компонента V(A) не больше соответствующей у V(B) и векторы не равны, то A → B. Если в одних компонентах больше A, а в других B — события конкурентны. Это уже точная характеристика причинности в обе стороны, чего часы Лэмпорта не дают.

```csharp
public enum Causality { Equal, Before, After, Concurrent }

public static Causality Compare(
    IReadOnlyDictionary<string, long> a,
    IReadOnlyDictionary<string, long> b)
{
    var less = false;
    var greater = false;

    foreach (var node in a.Keys.Union(b.Keys))
    {
        var x = a.GetValueOrDefault(node);
        var y = b.GetValueOrDefault(node);
        if (x < y) less = true;
        if (x > y) greater = true;
    }

    return (less, greater) switch
    {
        (false, false) => Causality.Equal,
        (true, false) => Causality.Before,
        (false, true) => Causality.After,
        _ => Causality.Concurrent,
    };
}
```

## Version vectors в репликации

На практике в хранилищах используют близкий родственник — **version vector**: счётчики ведутся не по процессам-клиентам, а по репликам, и прикладываются к версии значения. Реплика, получив две версии ключа, решает:

| Сравнение векторов | Что делать |
| --- | --- |
| одна версия «раньше» другой | старую выбросить, она уже учтена в новой |
| равны | это одна и та же версия |
| конкурентны | конфликт: сохранить обе (siblings) и слить |

Так работала корзина Amazon Dynamo из статьи `Модели согласованности`: клиент при чтении получал все конкурентные версии вместе с их контекстом, приложение сливало их и записывало результат с объединённым вектором. Riak перенёс эту модель в продукт и позже перешёл на dotted version vectors — они точнее отличают действительно конкурентные записи от тех, что пришли через одну реплику, и не раздувают число siblings.

Схема write-path выглядит так: клиент читает значение вместе с вектором, меняет и пишет обратно, приложив прочитанный вектор. Сервер понимает, какие версии новая запись «видела» и заменяет, а какие — нет и с ними конкурентна.

## Ограничения

- **Размер.** Вектор растёт с числом участников. По репликам это терпимо, по клиентам — нет. Усечение старых компонент экономит место, но может превратить «раньше» в ложный конфликт.
- **Конфликт обнаружен, но не разрешён.** Векторные часы говорят, что две версии конкурентны, а что с ними делать — решает приложение или CRDT. CRDT обычно обходятся без вектора на каждое значение: их операции коммутативны, и реплики сходятся при любом порядке доставки.
- **Нет связи с реальным временем.** Запрос «события за последний час» по логическим часам не построить, и линеаризуемости они не дают: причинный порядок слабее порядка реального времени, это разница между причинной моделью и линеаризуемостью.

## Гибридные логические часы

HLC (Кулкарни и соавторы, 2014) объединяют оба мира. Метка — пара: физическая часть, близкая к wall clock, и логический счётчик. При локальном событии и при получении сообщения физическая часть берётся как максимум из своих часов и пришедшей метки, а счётчик различает события с одинаковой физической частью. В итоге метки монотонны, согласованы с причинностью, как у Лэмпорта, и при этом остаются близки к реальному времени — по ним можно делать снимки «на момент T».

HLC используют CockroachDB и YugabyteDB для MVCC-меток транзакций; MongoDB для causal consistency в сессиях использует cluster time, построенный на похожей идее. Важная оговорка: HLC не избавляет от требований к часам. CockroachDB рассчитывает на ограниченное расхождение часов узлов и останавливает узел, если его отклонение превысило допустимый максимум.

## Та же идея в повседневной разработке

Логические часы — это не экзотика из статей, а принцип «порядок задаёт счётчик единственного писателя, а не часы»:

- **LSN в PostgreSQL** — позиция в журнале; на ней построен токен из статьи `Read-your-writes`;
- **offset в партиции Kafka** — порядок событий внутри партиции, у которой один лидер;
- **`rowversion`, `xmin`, ETag** — версия объекта для оптимистичной конкуренции, см. `Оптимистичная блокировка`;
- **терм в Raft и эпоха лидера** — монотонный номер, по которому отличают актуального лидера от устаревшего, см. `Консенсус и Raft` и `Выбор лидера`;
- **sequence или identity в базе** — если порядок нужен в пределах одной базы, она сама и есть единственный писатель.

Вывод для дизайна: если нужен порядок, ищите место, где у данных один писатель, и берите его счётчик. Метка `created_at` из кода приложения для упорядочивания событий с разных узлов не годится.

## Что стоит ответить на собеседовании

Логические часы упорядочивают события по причинности, а не по физическому времени. Отношение happened-before Лэмпорта: события одного процесса по порядку, отправка раньше получения, транзитивность; всё остальное — конкурентно. Часы Лэмпорта — один счётчик с правилом `max + 1` при получении; гарантируют, что причина получает меньшую метку, но по меткам нельзя отличить причину от конкурентного события. С идентификатором узла дают полный порядок, которого хватает, чтобы все выбрали одного победителя.

Векторные часы хранят счётчик на каждого участника и точно различают «раньше» и «конкурентно». В репликации их вариант — version vectors по репликам: если версии конкурентны, это конфликт, который сохраняют и сливают, как корзина в Dynamo. Сильный ответ назовёт цену — размер вектора, — то, что разрешение конфликта остаётся задачей приложения или CRDT, и гибридные логические часы, которые дают причинно согласованные метки, близкие к реальному времени, но всё равно требуют ограниченного расхождения часов. И приведёт бытовые примеры той же идеи: LSN, offset в Kafka, ETag и `rowversion`.
