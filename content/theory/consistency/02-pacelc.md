CAP говорит только о моменте, когда сеть уже разделилась. Но разделения редки, а система работает каждую секунду — и всё это время платит за согласованность задержкой. PACELC, предложенный Дэниелом Абади, делает этот повседневный компромисс явным. На собеседовании его спрашивают как продолжение разговора о CAP, и сильный ответ здесь отличается от слабого тем, что кандидат может объяснить, откуда берутся миллисекунды и где ими управлять в настройках конкретной базы. Сама CAP разобрана в статье `CAP на самом деле`.

## Формулировка

Абади изложил идею в блоге в 2010 году и затем в статье «Consistency Tradeoffs in Modern Distributed Database System Design» в IEEE Computer (2012). Название читается как условие:

```text
if Partition:   выбираем между Availability и Consistency
Else:           выбираем между Latency      и Consistency
```

Первая половина — та же CAP. Вторая — вклад Абади: даже при идеально работающей сети нельзя одновременно получить минимальную задержку и строгую согласованность реплицированных данных. И если разделение — событие раз в месяц, то задержка — налог на каждый запрос.

## Откуда компромисс без всяких сбоев

Чтобы запись пережила падение узла и была видна при чтении с другой реплики, её нужно доставить на другие узлы **до** ответа клиенту. Это минимум один сетевой круг до самой медленной реплики из тех, кого ждём, плюс запись на диск там.

```text
клиент ──► лидер ──► реплики ──fsync──► подтверждение ──► лидер ──► клиент
                 └───────── round-trip + fsync ─────────┘

в одной зоне доступности       доли миллисекунды
между зонами одного региона    около миллисекунды и больше
между регионами                десятки миллисекунд, через океан — около сотни
```

Альтернатива — ответить сразу после локальной записи и реплицировать асинхронно. Тогда задержка минимальна, но чтение с другой реплики может не увидеть запись, а падение лидера до отправки её потеряет. Ровно этот выбор — L или C — и есть вторая половина PACELC.

Важная деталь: ожидание определяется не средней, а **самой медленной** репликой из тех, чьего ответа ждём. Поэтому строгая согласованность бьёт прежде всего по хвостам: p99 записи — это p99 худшего участника кворума. Ожидание «любых двух из трёх» вместо «всех трёх» как раз срезает этот хвост.

## Классификация систем

Абади классифицировал системы по паре выборов. Упрощённо, по его статье:

| Система (в настройках по умолчанию) | При разделении | Иначе |
| --- | --- | --- |
| Dynamo, Cassandra, Riak | A | L |
| VoltDB/H-Store, Megastore, BigTable/HBase | C | C |
| PNUTS (Yahoo) | C | L |
| MongoDB (по оценке в статье 2012 года) | A | C |

PA/EL — отвечаем локально, реплицируем асинхронно, в разделении продолжаем принимать запись. PC/EC — каждая запись ждёт подтверждения, в разделении меньшинство отказывает. PNUTS интересен как промежуточный вариант: запись идёт через «мастер записи» для каждого ключа, а чтение — с локальной реплики и может быть устаревшим.

Как и с CAP, классификация описывает поведение по умолчанию, а не неотъемлемое свойство продукта. Большинство современных баз дают выбрать позицию на каждый запрос.

## Тот же выбор в настройках

**Cassandra** задаёт consistency level на запрос: `ONE` — EL в чистом виде, `LOCAL_QUORUM` — согласованность внутри одного дата-центра с задержкой внутри него же, `EACH_QUORUM` и `ALL` — ближе к EC с межрегиональной задержкой.

**PostgreSQL** делает то же через `synchronous_commit`, и его можно менять на уровне транзакции:

| Значение | Когда `COMMIT` возвращает управление |
| --- | --- |
| `off` | до локального сброса WAL на диск, при крэше можно потерять последние транзакции |
| `local` | после локального сброса, реплики не ждём |
| `remote_write` | синхронная реплика получила WAL и передала ОС, без fsync |
| `on` | синхронная реплика сбросила WAL на диск |
| `remote_apply` | синхронная реплика применила изменения, чтение с неё увидит запись |

Значения после `local` действуют, только если задан `synchronous_standby_names`. Кворумная форма `ANY 1 (replica_a, replica_b)` ждёт любую одну из двух и убирает зависимость от одной медленной реплики. Подробности механики — в статье `Репликация` раздела PostgreSQL.

```sql
BEGIN;
SET LOCAL synchronous_commit = 'remote_apply';
UPDATE accounts SET balance = balance - 100 WHERE id = 42;
COMMIT;

BEGIN;
SET LOCAL synchronous_commit = 'local';
INSERT INTO page_views (user_id, url, viewed_at) VALUES (7, '/catalog', now());
COMMIT;
```

Списание денег ждёт, пока реплика применит изменения; запись просмотра страницы не ждёт никого — потерять пару таких строк при аварии допустимо. В одной базе и даже в одном запросе к API получаются две разные точки на оси L–C.

**Kafka** выражает выбор через `acks` продюсера: `acks=1` отвечает после записи на лидере партиции, `acks=all` — после записи на всех синхронных репликах, причём `min.insync.replicas` задаёт, сколько их должно быть, чтобы запись вообще принималась. Это уже и P-, и E-половина сразу: при нехватке синхронных реплик запись отвергается.

## Почему задержка важна не меньше согласованности

Соблазн «включим строгую согласованность везде, на всякий случай» разбивается о три эффекта.

- **Пропускная способность.** Если запрос держит соединение из пула 80 мс вместо 5, при том же размере пула через него пройдёт в 16 раз меньше запросов. По закону Литтла (см. `Оценка нагрузки и RPS`) рост времени обслуживания — это рост числа одновременно занятых ресурсов.
- **Сложение в цепочках.** Запрос пользователя проходит через несколько сервисов, и задержки каждого складываются, а синхронная запись в нескольких из них множит межзонные круги.
- **Хвосты при fan-out.** Если запрос опрашивает 10 узлов и ждёт всех, вероятность, что хотя бы один ответит медленнее своего p99, около 1 − 0.99¹⁰ ≈ 10%. Чем больше участников в синхронном пути, тем чаще пользователь видит худший случай.

Отсюда практическое правило: строгая согласованность — для данных, где ошибка стоит денег или нарушает инвариант, задержка — для всего остального.

## Как это выглядит в дизайне

- **Делить данные по требованиям.** Деньги, остатки, уникальные имена — EC. Ленты, счётчики просмотров, рекомендации — EL.
- **Геораспределение через домашний регион.** Пользователь пишет в свой регион, где синхронность дешёвая; синхронная запись во все регионы стоит десятков миллисекунд на каждую операцию.
- **Явно ограничивать устаревание.** «Реплика с лагом больше N секунд выводится из пула чтения» превращает размытое «eventual» в измеримую гарантию.
- **Помнить о Spanner.** Google Spanner даёт внешнюю согласованность глобально, но платит за неё ожиданием: перед подтверждением коммита он выжидает неопределённость часов TrueTime (commit wait) плюс межрегиональный кворум Paxos. Это PC/EC с честно оплаченной задержкой — подробнее в статье `Почему нельзя верить часам`.

## Что стоит ответить на собеседовании

PACELC Абади дополняет CAP: при разделении выбираем между доступностью и согласованностью, а в остальное время — между задержкой и согласованностью. Второй компромисс важнее на практике, потому что разделения редки, а задержку платит каждый запрос: чтобы запись была видна на других репликах и пережила падение узла, нужно дождаться их подтверждения — круг по сети плюс fsync у самой медленной из ожидаемых реплик.

Сильный ответ приведёт классификацию — Dynamo и Cassandra PA/EL, VoltDB и HBase PC/EC, PNUTS PC/EL — и тут же оговорится, что это поведение по умолчанию, а выбор делается на запрос: consistency level в Cassandra, `acks` в Kafka, `synchronous_commit` в PostgreSQL, который можно поставить в `remote_apply` для платежа и в `local` для лога просмотров в одной базе. И объяснит, почему задержка — не мелочь: она снижает пропускную способность пула, складывается в цепочках и усиливает хвосты при fan-out.
