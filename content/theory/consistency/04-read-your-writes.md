Пользователь меняет имя в профиле, жмёт «Сохранить», страница перезагружается — и показывает старое имя. Через секунду, после ещё одного обновления, всё в порядке. Это нарушение read-your-writes: самая заметная пользователю аномалия асинхронной репликации и самая частая причина тикетов «данные не сохраняются». Гарантия скромная — клиент после успешной записи видит её в своих последующих чтениях, — но обеспечить её в системе с репликами чтения сложнее, чем кажется. Это одна из сессионных гарантий из статьи `Модели согласованности`.

## Откуда берётся аномалия

При асинхронной репликации primary подтверждает коммит, не дожидаясь реплик, а реплика применяет журнал с задержкой — лагом.

```text
t=0     POST /profile   → primary: UPDATE users SET name='Анна'   COMMIT ok
t=5ms   GET  /profile   → replica-2: лаг 40 мс, ещё name='Аня'     ← старое
t=60ms  GET  /profile   → replica-1: name='Анна'                   ← новое
```

Лаг в спокойном режиме — миллисекунды, но под массовой записью, при долгом запросе на реплике или сетевых проблемах он вырастает до секунд и минут. Поэтому «лаг маленький, пользователь не успеет» — не решение: однажды успеет. Как устроены реплики и почему лаг неизбежен — в статье `Репликация и failover`.

Read-your-writes **ничего не обещает другим клиентам**. Соседний пользователь может видеть старое имя ещё секунду — это допустимо. Гарантия касается только автора изменения, и именно поэтому её можно обеспечить дешевле, чем линеаризуемость.

## Способ 1: читать своё с primary

Самое простое правило: то, что пользователь мог изменить сам, — профиль, настройки, собственные заказы, корзину — читаем с primary; чужие данные и каталог — с реплик. Надёжно и не требует инфраструктуры, но держится на дисциплине: каждый новый эндпоинт надо отнести к правильной категории. И если «своих» данных много, выгода от реплик исчезает.

## Способ 2: окно после записи

После записи ставим в cookie или сессию метку времени, и в течение N секунд все чтения этого пользователя идут на primary.

```csharp
public sealed class ReadRoutingMiddleware(RequestDelegate next)
{
    private static readonly TimeSpan Window = TimeSpan.FromSeconds(5);

    public async Task InvokeAsync(HttpContext ctx, DbRouter router)
    {
        if (HttpMethods.IsGet(ctx.Request.Method)
            && ctx.Request.Cookies.TryGetValue("lw", out var raw)
            && long.TryParse(raw, out var ticks)
            && DateTimeOffset.UtcNow - new DateTimeOffset(ticks, TimeSpan.Zero) < Window)
        {
            router.ForcePrimary();
        }

        await next(ctx);

        if (!HttpMethods.IsGet(ctx.Request.Method) && ctx.Response.StatusCode < 400)
            ctx.Response.Cookies.Append("lw", DateTimeOffset.UtcNow.UtcTicks.ToString());
    }
}
```

Дёшево, но это эвристика: окно выбирается «больше типичного лага», а при всплеске лага до 30 секунд пользователь снова увидит прошлое. Есть и тонкость: cookie выставляется после `next`, а к этому моменту ответ может быть уже начат — в реальном коде её ставят через `OnStarting`.

## Способ 3: токен позиции в журнале

Точный способ — запомнить позицию журнала после своего коммита и читать с реплики, только если она эту позицию уже применила. В PostgreSQL позиция — LSN:

```sql
SELECT pg_current_wal_lsn();

SELECT pg_last_wal_replay_lsn() >= '3/7A0012C8'::pg_lsn;
```

Первый запрос выполняется на primary сразу после `COMMIT` — он вернёт позицию не меньше позиции вашей записи, этого достаточно. Второй — на реплике перед чтением. Токен уезжает к клиенту в cookie или заголовке и возвращается с каждым запросом:

```csharp
public async Task<NpgsqlDataSource> ChooseAsync(string? minLsn, CancellationToken ct)
{
    if (minLsn is null)
        return _replica;

    await using var cmd = _replica.CreateCommand(
        "SELECT pg_last_wal_replay_lsn() >= @lsn::pg_lsn");
    cmd.Parameters.AddWithValue("lsn", minLsn);

    var caughtUp = await cmd.ExecuteScalarAsync(ct) is true;
    return caughtUp ? _replica : _primary;
}
```

Если реплика отстаёт, можно не сразу уходить на primary, а подождать 50–100 мс и проверить ещё раз — так primary не получит всплеск чтений, когда лаг подрос у всех реплик сразу. Идея общая для любых хранилищ: MongoDB делает то же через causally consistent sessions и `afterClusterTime`, в CQRS роль LSN играет версия проекции.

## Способ 4: ждать применения на репликах

`synchronous_commit = remote_apply` заставляет `COMMIT` ждать, пока синхронные реплики **применят** изменения — тогда чтение с них гарантированно увидит запись. Это переносит цену с чтения на запись: каждый коммит ждёт сетевой круг и применение, а отказ синхронной реплики тормозит запись. И работает только для реплик из `synchronous_standby_names` — если чтение может уйти на асинхронную реплику пула, гарантии нет. Компромисс между задержкой и согласованностью подробно — в статье `PACELC`.

## Способ 5: липкость к реплике

Привязка пользователя к одной реплике — по хешу идентификатора или sticky-сессии на балансировщике — даёт **monotonic reads**: время для пользователя не идёт назад, потому что одна реплика применяет журнал последовательно. Но read-your-writes она не даёт: запись ушла на primary, а «своя» реплика всё ещё может отставать. Липкость часто путают с решением, и это хороший вопрос-ловушка на собеседовании.

| Способ | Даёт RYW | Цена |
| --- | --- | --- |
| Своё с primary | да | дисциплина, нагрузка на primary |
| Окно после записи | обычно | эвристика, ломается при всплеске лага |
| Токен LSN | да | запрос к реплике, передача токена |
| `remote_apply` | для синхронных реплик | задержка каждого коммита |
| Липкость к реплике | нет, только monotonic reads | ребалансировка при отказе реплики |

## Маршрутизация в Npgsql

Multi-host строка подключения решает вопрос «куда слать», но не вопрос лага:

```csharp
var multi = new NpgsqlDataSourceBuilder(
        "Host=pg-1,pg-2,pg-3;Database=app;Username=app;Load Balance Hosts=true")
    .BuildMultiHost();

var primary = multi.WithTargetSession(TargetSessionAttributes.Primary);
var replica = multi.WithTargetSession(TargetSessionAttributes.PreferStandby);
```

Поверх этого всё равно нужна одна из стратегий выше.

## Где гарантию ломают

- **Кэш.** Если чтение после записи идёт из Redis, а инвалидация асинхронная — по событию или по TTL, — read-your-writes нарушает уже кэш, а не реплика. Инвалидировать ключ нужно в том же запросе, что делал запись. Стратегии — в статье `Кэширование`.
- **Фоновые обработчики.** Событие из outbox может прийти консьюмеру раньше, чем реплика догонит primary, и консьюмер, читающий с реплики, не найдёт только что созданную сущность. Либо передавайте нужные данные в самом событии, либо LSN, либо читайте в обработчике с primary.
- **Второе устройство.** Cookie-токен живёт в одном браузере. Чтобы «изменил на телефоне — вижу на ноутбуке», токен хранится на сервере по `userId`, например в Redis.
- **Failover.** После переключения на новую primary LSN старой линии времени может оказаться несравнимым с позициями новой. При ошибке проверки безопаснее читать с primary.
- **Мониторинг лага.** На primary — `replay_lag` в `pg_stat_replication`, на реплике — `now() - pg_last_xact_replay_timestamp()`. Реплику с лагом выше порога стоит выводить из пула чтения.

## Что делать в интерфейсе

Часть задачи решается на клиенте: после успешного сохранения интерфейс показывает значение, которое пользователь только что ввёл, не перечитывая его с сервера (оптимистичное обновление). Ответ на `POST` или `PUT` может вернуть итоговое состояние ресурса — тогда клиенту не нужно сразу делать `GET`. Это не отменяет серверную гарантию для других вкладок и устройств, но убирает самую частую жалобу.

## Что стоит ответить на собеседовании

Read-your-writes — гарантия, что клиент после успешной записи видит её в своих чтениях; другим клиентам она ничего не обещает. Нарушает её лаг асинхронной репликации: запись ушла на primary, чтение — на отстающую реплику.

Способы — от простого к точному: читать «своё» с primary; окно после записи, в течение которого чтения идут на primary; токен позиции журнала — LSN после коммита, и чтение с реплики, только если она его применила; `remote_apply` для синхронных реплик ценой задержки коммита. Сильный ответ отметит, что липкость к реплике даёт monotonic reads, а не read-your-writes, и назовёт места, где гарантия ломается помимо реплик: асинхронная инвалидация кэша, консьюмеры событий, читающие с реплики, второе устройство пользователя и failover.
