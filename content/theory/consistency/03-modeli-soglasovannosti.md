Модель согласованности — это контракт между хранилищем и клиентом: какие значения может вернуть чтение с учётом уже выполненных записей. «Сильная» и «слабая» — слишком грубое деление: между ними лежит несколько моделей с точными определениями, и каждая разрешает свой набор аномалий. На собеседовании ждут, что кандидат назовёт модели, нарисует историю операций, которая одну нарушает, а другую нет, и не перепутает линеаризуемость с сериализуемостью. Уровни изоляции транзакций в одной базе — отдельная тема, она разобрана в статье `Уровни изоляции`.

## Линеаризуемость

Самая сильная модель для отдельного объекта (Херлихи и Винг, 1990). Каждая операция выглядит так, будто она атомарно выполнилась в какой-то момент между вызовом и ответом, и этот порядок согласован с **реальным временем**: если операция A завершилась до начала B, то B видит результат A. Проще: система ведёт себя так, будто копия данных одна.

```text
время ─────────────────────────────────────────────────►
клиент A:  [ write x=1 ]
клиент B:                  [ read x → 1 ]    обязано вернуть 1
клиент C:        [ read x → 0 или 1 ]        пересекается с записью: допустимо оба
клиент D:                       [ read x → 0 ]  НАРУШЕНИЕ: после B, которое уже видело 1
```

Последняя строка — классическая аномалия: если одно чтение уже вернуло новое значение, никакое более позднее не может вернуть старое. Линеаризуемость нужна там, где решение принимается на основании «единственной правды»: захват блокировки, выбор лидера, уникальность имени, проверка баланса. Цена — координация на каждой операции через лидера или кворум и недоступность при потере кворума, как требует `CAP на самом деле`.

Ещё одно полезное свойство — композиционность: если каждый объект по отдельности линеаризуем, то и система из них линеаризуема. Последовательная согласованность этим свойством не обладает.

## Последовательная согласованность

Модель Лэмпорта (1979): все операции выстроены в **один общий порядок**, одинаковый для всех наблюдателей, и в нём сохраняется порядок операций каждого клиента. Связи с реальным временем нет: операция, завершившаяся раньше, может оказаться в общем порядке позже.

```text
клиент A:  write x=1                   (завершилась в 10:00:00)
клиент B:                read x → 0   (началась в 10:00:01)
```

Для линеаризуемости это нарушение, для последовательной согласованности — нет: общий порядок «read B, write A» существует и не противоречит порядку внутри каждого клиента. Цена почти та же, что у линеаризуемости — все должны договориться об одном порядке, — поэтому в распределённых хранилищах она встречается редко; зато она важна в моделях памяти процессоров и языков.

## Причинная согласованность

Ослабляет требование общего порядка: согласованно упорядочены только **причинно связанные** операции. Если операция B могла зависеть от A — клиент прочитал A и затем записал B, или A и B выполнены одним клиентом подряд, — все узлы увидят A раньше B. Независимые (конкурентные) операции разные узлы могут увидеть в разном порядке.

```text
Алиса:  пишет пост «Потеряла кольцо»
Алиса:  пишет пост «Нашлось!»
Боб:    читает «Нашлось!» → комментирует «Ура!»

причинная модель: никто не увидит «Ура!» раньше «Нашлось!»
                  и «Нашлось!» раньше «Потеряла кольцо»
eventual:         кто-то может увидеть «Ура!» под первым постом
```

Причинная согласованность интересна тем, что это, по результату Махаджана, Алвиси и Далина (2011, с оговорками о точной формулировке модели), сильнейшая модель, которую можно обеспечить, оставаясь доступным при разделении сети. Цена — отслеживание зависимостей: версии, векторные часы или токены «я видел состояние не раньше X». Механизмы разобраны в статье `Логические и векторные часы`.

## Сессионные гарантии

Четыре гарантии, сформулированные для системы Bayou (Терри и соавторы, 1994), обещают порядок **в рамках одного клиента**, ничего не говоря о других:

| Гарантия | Обещание клиенту |
| --- | --- |
| Read-your-writes | после своей записи я вижу её во всех последующих чтениях |
| Monotonic reads | однажды увидев версию, я не увижу более старую |
| Monotonic writes | мои записи применяются в том порядке, в котором я их сделал |
| Writes-follow-reads | моя запись, сделанная после чтения, упорядочена после прочитанного |

Вместе они дают причинную согласованность для одного клиента. Обеспечиваются привязкой клиента к реплике или токеном версии, который клиент носит с собой. Самая заметная пользователю — первая; ей посвящена статья `Read-your-writes`.

## Eventual consistency

Обещание одно: если новые записи прекратятся, реплики **когда-нибудь** сойдутся к одному значению. Ни сколько ждать, ни что вернёт чтение в промежутке, модель не говорит. Почти бесплатна по задержке и доступности, но все аномалии видны пользователю: устаревшие данные, «прыжки назад», потерянные записи при наивном разрешении конфликтов.

Без механизма сходимости eventual consistency не работает. Варианты — last-write-wins (одна из конкурентных записей тихо пропадает), хранение конфликтующих версий с слиянием в приложении, CRDT. Последние дают **strong eventual consistency**: реплики, получившие одинаковый набор обновлений, находятся в одинаковом состоянии без всякой координации.

## Линеаризуемость и сериализуемость — не одно и то же

Самая частая путаница на собеседовании.

| | Линеаризуемость | Сериализуемость |
| --- | --- | --- |
| О чём | отдельные операции над одним объектом | транзакции над многими объектами |
| Обещание | порядок согласован с реальным временем | результат как при некотором последовательном выполнении |
| Реальное время | учитывает | не учитывает: порядок может быть любым |
| Откуда | распределённые системы, модели памяти | базы данных, теория транзакций |

Сериализуемая база может выстроить транзакции в порядке, который противоречит реальному времени: транзакция, начавшаяся после коммита другой, вправе «оказаться» перед ней, если результат эквивалентен какому-то последовательному порядку. Комбинация обоих свойств называется **strict serializability**; её дают Spanner (под именем external consistency) и обычно однонодовая база с двухфазной блокировкой. Snapshot isolation не даёт ни того ни другого: write skew возможен, хотя каждое отдельное чтение видит согласованный снимок.

## Кворум ещё не линеаризуемость

Распространённая ошибка — считать, что W + R > N делает хранилище линеаризуемым. Пересечение кворумов гарантирует, что чтение «заденет» узел с последней записью, но:

- запись, упавшая посередине, оказалась на одном узле из трёх; одно чтение кворумом её увидит, следующее — нет, это нарушение линеаризуемости;
- конкурентные записи, разрешаемые по времени, теряют одну из них;
- sloppy quorum с hinted handoff пишет на «чужие» узлы, и пересечения нет.

Чтобы кворумные чтения стали линеаризуемыми, читатель должен дописать увиденное значение на отстающие реплики до ответа (read repair в синхронном режиме), а для compare-and-set нужен консенсус. Детали кворумов в репликации — в статье `Репликация и failover`.

## Как выбрать модель: корзина

Модель выбирается под операцию, а не под систему. Корзину интернет-магазина видит один человек, поэтому линеаризуемость между всеми пользователями ей не нужна, а аномалии, которые раздражают, — сессионные:

- добавил товар, обновил страницу, а его нет — нарушен read-your-writes;
- товар появился и снова исчез на следующем запросе к другой реплике — нарушены monotonic reads;
- корзину одновременно правили с телефона и ноутбука — конфликт, который нужно слить, а не «последний победил».

Amazon Dynamo решал это так: запись в корзину принимается всегда, конфликтующие версии хранятся параллельно, при чтении приложение сливает их объединением. Известная аномалия — «воскрешение» удалённого товара, если удаление было в одной ветке, а добавление в другой; её устраняет CRDT типа OR-Set.

Для типового .NET-магазина проще: корзина — документ в одном лидере, изменения — с оптимистичной версией, чтобы два устройства не затирали друг друга (см. `Оптимистичная блокировка`):

```csharp
var rows = await db.Carts
    .Where(c => c.UserId == userId && c.Version == expectedVersion)
    .ExecuteUpdateAsync(s => s
        .SetProperty(c => c.Items, merged)
        .SetProperty(c => c.Version, expectedVersion + 1), ct);

if (rows == 0)
    return Results.Conflict();
```

А оформление заказа — уже линеаризуемые операции: резерв остатка условным `UPDATE`, фиксация цены, идемпотентный ключ платежа.

## Что стоит ответить на собеседовании

Модель согласованности — контракт о том, что может вернуть чтение. От сильной к слабой: линеаризуемость — одна копия, порядок согласован с реальным временем; последовательная — общий порядок без привязки ко времени; причинная — согласованно упорядочены только связанные операции; сессионные гарантии — порядок для одного клиента; eventual — реплики когда-нибудь сойдутся, если записи прекратятся.

Сильный ответ отделит линеаризуемость (одна операция, реальное время) от сериализуемости (транзакции, любой эквивалентный порядок) и назовёт их сочетание strict serializability. Объяснит, что кворум W + R > N сам по себе не даёт линеаризуемости, что причинная модель — сильнейшая из совместимых с доступностью при разделении, а eventual consistency без механизма разрешения конфликтов означает потерю записей. И покажет выбор по операциям: корзине хватит сессионных гарантий и слияния, а резерв остатков и оплата требуют линеаризуемости.
