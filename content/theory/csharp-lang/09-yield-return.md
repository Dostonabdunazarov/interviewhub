`yield return` позволяет написать метод, который возвращает последовательность, не собирая её в коллекцию. Выглядит как обычный метод с циклом, но выполняется совершенно иначе: тело замирает после каждого `yield` и продолжается, когда запросят следующий элемент. За этим стоит генерация целого класса компилятором, и знать, какого именно, полезно — из его устройства следуют все особенности итераторов.

## Что происходит при вызове

Метод с `yield return` при вызове **не выполняет ни строчки своего тела**. Он создаёт объект и возвращает его:

```csharp
static IEnumerable<int> Numbers(int n)
{
    Console.WriteLine("начали");
    for (int i = 0; i < n; i++)
        yield return i;
}

var seq = Numbers(3);        // ничего не напечаталось
foreach (var x in seq) { }   // вот теперь "начали"
```

Компилятор переписывает метод в класс — конечный автомат с полем `<>1__state`, полями под локальные переменные и параметры и методом `MoveNext()`, где тело разрезано на куски по точкам `yield`. Каждый `yield return` — это «сохранить состояние, вернуть значение, выйти»; следующий `MoveNext()` возвращается ровно в эту точку.

Забавная деталь, которую видно в замере: сгенерированный класс реализует **и** `IEnumerable<T>`, **и** `IEnumerator<T>` одновременно — проверено, `Numbers(1) is IEnumerator` даёт `true`. Это экономия: при первом `GetEnumerator()` возвращается сам объект, а не новый, и аллокация одна вместо двух.

## Сколько это стоит

Замеры на .NET 10, последовательность из 10 элементов:

```
вызов итератора без перечисления                40 байт
итератор, перечисление 10 элементов             40 байт
List<int> на 10 элементов + foreach             96 байт
```

Читать так. 40 байт — это сам объект state machine, и он **не зависит от числа элементов**: перечисление десяти элементов не добавило ни байта, потому что элементы отдаются по одному и нигде не накапливаются. Список на те же десять элементов стоит 96 байт — объект `List` плюс массив под элементы — и растёт линейно.

Отсюда главный практический вывод: **итератор выигрывает тем сильнее, чем больше последовательность и чем меньше её нужно целиком**. На десяти элементах разница копеечная, на миллионе — это выбор между постоянной памятью и массивом на миллион элементов.

Второй вывод обратный: если результат всё равно материализуют в список сразу после вызова, итератор добавляет 40 байт и слой косвенности без всякой пользы. Тогда честнее вернуть `List<T>`.

## Ленивость и её последствия

Итератор — источник той самой ленивости, про которую написано в статье `LINQ и отложенное выполнение`. Все ленивые операторы LINQ внутри устроены именно так.

**Перечислить дважды — выполнить дважды.** Проверено: один и тот же объект итератора дал `3` и `3` на двух `Count()`, то есть тело отработало два раза. Сохранённая переменная — это не результат, а рецепт.

**Бесконечная последовательность — нормальный код**, потому что элементы вычисляются по требованию:

```csharp
static IEnumerable<int> Naturals()
{
    for (int i = 0; ; i++) yield return i;
}

Naturals().Where(x => x % 7 == 0).Take(5).ToList();   // завершится
```

**Ресурсы освобождаются правильно.** `foreach` вызывает `Dispose()` у энумератора, а сгенерированный автомат исполняет в этот момент блоки `finally`, до которых дошло выполнение. Поэтому `using` внутри итератора работает даже при досрочном выходе:

```csharp
static IEnumerable<string> ReadLines(string path)
{
    using var reader = new StreamReader(path);   // закроется корректно
    string? line;
    while ((line = reader.ReadLine()) is not null)
        yield return line;
}

foreach (var line in ReadLines(path))
{
    if (line.StartsWith("#")) break;   // выход на первой строке — файл закрыт
}
```

Это, кстати, канонический пример пользы `yield`: файл на гигабайт читается построчно при постоянном расходе памяти, а вызывающий видит обычный `IEnumerable<string>`.

## Отложенная проверка аргументов — главная ловушка

Раз тело не выполняется при вызове, то и проверки аргументов в нём тоже не выполняются:

```csharp
static IEnumerable<int> Take(int[] source, int count)
{
    ArgumentNullException.ThrowIfNull(source);   // выполнится НЕ при вызове
    for (int i = 0; i < count; i++)
        yield return source[i];
}

var seq = Take(null!, 5);   // исключения нет
seq.Count();                // вот здесь ArgumentNullException
```

Исключение прилетает в месте перечисления, где стек вызовов уже никак не указывает на настоящего виновника. Отлаживать такое неприятно.

Лечится разделением на два метода: обычный с проверками и приватный итератор.

```csharp
static IEnumerable<int> Take(int[] source, int count)
{
    ArgumentNullException.ThrowIfNull(source);
    ArgumentOutOfRangeException.ThrowIfNegative(count);
    return Iterator(source, count);

    static IEnumerable<int> Iterator(int[] source, int count)
    {
        for (int i = 0; i < count; i++)
            yield return source[i];
    }
}
```

Проверено: в таком виде `ArgumentNullException` бросается **сразу при вызове**. Внешний метод не содержит `yield`, поэтому выполняется обычным образом, а итератор создаётся только после успешных проверок. Так устроены все методы в `System.Linq` — там это тот же приём.

## Ограничения

В методе с `yield` нельзя:

- использовать `ref`, `out` и `in`-параметры — их негде хранить в полях state machine;
- писать `yield return` внутри блока `try` **с** `catch` (с одним `finally` — можно);
- применять `yield` в `unsafe`-контексте и в лямбдах (в локальных функциях — можно).

Есть и `yield break` — досрочное завершение последовательности:

```csharp
static IEnumerable<string> ReadUntilEmpty(TextReader reader)
{
    while (true)
    {
        var line = reader.ReadLine();
        if (string.IsNullOrEmpty(line)) yield break;
        yield return line;
    }
}
```

## Асинхронный вариант

Для потока данных, который приходит с задержками — из сети, из базы, из очереди, — есть `IAsyncEnumerable<T>`:

```csharp
static async IAsyncEnumerable<string> ReadLinesAsync(string path)
{
    using var reader = new StreamReader(path);
    while (await reader.ReadLineAsync() is string line)
        yield return line;
}

await foreach (var line in ReadLinesAsync(path))
    Process(line);
```

Компилятор генерирует такой же автомат, только совмещённый с автоматом `async`. Подробности — в разделе про асинхронность; здесь важно, что `await foreach` — это тот же итератор, просто умеющий ждать.

## Когда yield не нужен

**Коллекция уже в памяти.** `foreach (var x in list) yield return x;` — бессмысленная обёртка: 40 лишних байт и медленнее. Верните сам список.

**Результат всегда материализуют.** Если у всех вызывающих сразу `.ToList()`, итератор только мешает.

**Нужен `Count` или доступ по индексу.** У `IEnumerable<T>` их нет; вызов `Count()` перечислит всё заново.

**Источник нельзя перечитать.** Итератор над сетевым потоком отработает один раз, а второе перечисление молча даст пустую последовательность или упадёт. Такие последовательности лучше материализовать сразу или явно документировать как одноразовые.

## Что стоит ответить на собеседовании

Метод с `yield return` компилятор превращает в класс — конечный автомат, реализующий `IEnumerator<T>`. Вызов метода не выполняет тело, а создаёт этот объект; тело продвигается на один шаг при каждом `MoveNext()` и замирает на очередном `yield`. Отсюда ленивость, возможность бесконечных последовательностей и постоянный расход памяти независимо от длины последовательности — на .NET 10 это 40 байт на итератор против 96 у списка из десяти элементов.

Сильный ответ добавит про отложенную проверку аргументов: `ArgumentNullException` из тела итератора прилетит не при вызове метода, а при первом перечислении, поэтому проверки выносят в обычный метод-обёртку, а `yield` оставляют в приватном. И упомянет, что `foreach` вызывает `Dispose` у энумератора, благодаря чему `using` внутри итератора корректно закрывает файл даже при выходе через `break`.
