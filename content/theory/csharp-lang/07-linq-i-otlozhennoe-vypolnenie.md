Главное, что нужно знать про LINQ, — вызов `Where` ничего не фильтрует. Он строит объект, который **умеет** фильтровать, и ждёт, пока его начнут перечислять. Это называется отложенным (ленивым) выполнением, и почти все неожиданности с LINQ объясняются именно им.

## Запрос не выполняется, пока его не перечислят

Проверим прямо: посчитаем, сколько раз вызвался предикат.

```csharp
int[] arr = Enumerable.Range(0, 100).ToArray();
int calls = 0;

var query = arr.Where(x => { calls++; return x > 50; });
// calls == 0 — предикат не вызывался ни разу

query.Count();   // calls == 100
query.Count();   // calls == 200
```

Замер на .NET 10 подтверждает: после объявления `Where` — ноль вызовов, после первого `Count()` — сто, после второго — двести. Запрос выполнился **дважды**, потому что `query` — не результат, а рецепт.

Отсюда два следствия, которые в реальном коде дают баги.

**Запрос видит данные на момент перечисления, а не объявления:**

```csharp
var list = new List<int> { 1, 2, 3 };
var evens = list.Where(x => x % 2 == 0);

list.Add(4);
evens.Count();      // 2 — четвёрка попала в результат
```

**Двойное перечисление удваивает работу.** Безобидно для массива в памяти, дорого для запроса к БД и катастрофично для потока, который читается один раз:

```csharp
var users = repository.GetActive();          // IEnumerable, запрос к БД
if (users.Any())                             // запрос №1
    foreach (var u in users) Process(u);     // запрос №2
```

Лечится материализацией: `.ToList()` один раз, дальше работа со списком. Правило простое — **если результат нужен больше одного раза, материализуйте его**. Анализаторы (в том числе ReSharper) умеют ловить `PossibleMultipleEnumeration`, и этому предупреждению стоит верить.

## Какие операторы откладывают, а какие выполняют

Делятся на две группы по возвращаемому типу — это надёжный признак.

**Откладывают** (возвращают `IEnumerable<T>`): `Where`, `Select`, `SelectMany`, `Take`, `Skip`, `Distinct`, `Concat`, `Zip`, `Cast`, `OfType`, `Reverse`, `GroupBy`, `OrderBy`.

**Выполняют немедленно** (возвращают значение или коллекцию): `ToList`, `ToArray`, `ToDictionary`, `ToHashSet`, `Count`, `Sum`, `Min`, `Max`, `Average`, `First`, `FirstOrDefault`, `Single`, `Any`, `All`, `Contains`, `ElementAt`, `Aggregate`.

Два оператора стоят особняком. `OrderBy` формально ленив — он возвращает `IEnumerable<T>`, — но при первом же обращении к элементу вынужден прочитать и отсортировать **весь** источник: иначе он не знает, какой элемент первый. Поэтому `OrderBy(...).First()` в замере стоит 120 байт против нуля у `Min()`:

```
arr.OrderBy(x => x).First()     120 байт
arr.Min()                         0 байт
```

За первым элементом отсортированной последовательности лучше идти через `Min`/`MaxBy`, а не через сортировку целиком.

`GroupBy` ведёт себя так же: чтобы отдать первую группу, нужно увидеть все элементы.

## Как ленивость экономит работу

Обратная сторона: ленивые операторы тянут элементы по одному и останавливаются, как только результата достаточно.

```csharp
var first = hugeCollection
    .Where(x => Expensive(x))
    .Select(x => Transform(x))
    .First();
```

`Expensive` и `Transform` вызовутся ровно столько раз, сколько нужно, чтобы найти первый подходящий элемент, а не для всей коллекции. Перепишите это с `.ToList()` в середине — и потеряете всю экономию.

Особенно наглядно с бесконечными последовательностями: ленивость позволяет им вообще существовать.

```csharp
static IEnumerable<int> Naturals()
{
    for (int i = 0; ; i++) yield return i;
}

Naturals().Where(x => x % 7 == 0).Take(5).ToList();   // завершится
```

Как устроены такие генераторы — в статье `yield return`.

Из этого же следует правило порядка операторов: **фильтруйте раньше, проецируйте позже**. `Where(...).Select(...)` вызовет проекцию только для прошедших фильтр, `Select(...).Where(...)` — для всех.

## Сколько LINQ стоит по памяти

Каждый оператор в цепочке — это объект-итератор плюс делегат. Замеры на .NET 10, массив из 100 элементов:

```
Where().Select() без перечисления              104 байта
Where().Select().Count(), 100 элементов        104 байта
эквивалентный foreach, 100 элементов             0 байт
arr.Any(x => x > 5)                              0 байт
arr.Count()                                      0 байт
arr.ToList()                                   456 байт
```

104 байта — это цена **построения** цепочки, и она не зависит от числа элементов: перечисление ста элементов не добавило ничего сверху. Для запроса, который обрабатывает сотни элементов, накладные расходы теряются на фоне полезной работы. Для запроса из двух элементов внутри цикла на миллион итераций — нет.

Ноль у `Any` и `Count` — это оптимизации самого LINQ: лямбда без захвата кэшируется (см. `Делегаты и события`), а `Count()` для массива берёт `Length` напрямую, не перечисляя.

Отдельно стоит знать про перечисление через интерфейс:

```
foreach по List<int>                              0 байт
foreach по List<int> через IEnumerable<int>      40 байт
```

У `List<T>` энумератор — структура, и `foreach` по переменной типа `List<T>` работает без аллокаций. Стоит объявить переменную как `IEnumerable<int>` — и энумератор упаковывается, давая 40 байт на каждое перечисление. Поэтому в горячем коде тип переменной лучше не обобщать до интерфейса без нужды. Про упаковку — в статье `Упаковка и распаковка`.

Практический вывод не «не используйте LINQ». Читаемость почти всегда важнее сотни байт. Заменять LINQ ручным циклом стоит там, где профилировщик показал проблему: горячий путь, вызываемый десятки тысяч раз в секунду.

## Синтаксис запросов и методов

Две формы записи, компилируются в одно и то же:

```csharp
// Синтаксис запросов
var q = from u in users
        where u.IsActive
        orderby u.Name
        select u.Email;

// Синтаксис методов — то же самое
var q = users.Where(u => u.IsActive).OrderBy(u => u.Name).Select(u => u.Email);
```

Компилятор переписывает первую форму во вторую, так что разницы в производительности нет. Синтаксис запросов выигрывает в двух случаях — соединения (`join`) и промежуточные переменные (`let`), — в остальном методы компактнее, и в проектах чаще пишут их.

## Частые ошибки

**`Count() > 0` вместо `Any()`.** `Count()` перечисляет всё, `Any()` останавливается на первом элементе. Для `List` разницы нет (есть быстрый путь по `Count`), для ленивого запроса — большая.

**`First()` там, где нужен `FirstOrDefault()`.** `First` на пустой последовательности бросает `InvalidOperationException`. Осознанный выбор: `First` — когда пусто означает ошибку, `FirstOrDefault` — когда это допустимо.

**`Single()` ради «первого».** `Single` перечисляет дальше найденного, проверяя, что элемент один. Если нужен просто первый — это `First`.

**Побочные эффекты в `Select`.** Из-за ленивости они случаются в непредсказуемый момент или несколько раз. Для действий есть `foreach`.

**`.ToList()` в середине цепочки «на всякий случай».** Материализует промежуточный результат целиком и убивает ленивость. Осмысленно только если промежуточный результат нужен несколько раз.

## Что стоит ответить на собеседовании

Большинство операторов LINQ ленивы: `Where` и `Select` возвращают объект-итератор и не выполняют ничего, пока последовательность не начнут перечислять. Выполнение запускают операторы, возвращающие конкретное значение или коллекцию, — `ToList`, `Count`, `First`, `Any`. Отсюда двойное перечисление: перечислить запрос дважды — выполнить его дважды, что для запроса к БД означает два похода в базу.

Сильный ответ добавит границы. `OrderBy` и `GroupBy` формально ленивы, но читают источник целиком при первом же обращении. Цена LINQ — около сотни байт на построение цепочки независимо от размера данных, то есть проблема не в объёме, а в частоте вызова. И упомянет `foreach` по переменной типа `IEnumerable<T>` вместо конкретного `List<T>` — упаковка энумератора, 40 байт на каждое перечисление на .NET 10.
