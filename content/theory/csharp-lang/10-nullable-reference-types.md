Nullable reference types — механизм, при котором компилятор отслеживает, может ли ссылка быть `null`, и предупреждает о разыменовании без проверки. Ключевое, что нужно понимать: это **исключительно проверка времени компиляции**. В рантайме не меняется ничего, и `string?` — не отдельный тип.

## Ничего нового в рантайме

Проверим утверждение напрямую:

```csharp
typeof(string) == typeof(string?)   // true — это один и тот же тип
```

Компилятор не создаёт нового типа. Вместо этого он расставляет в метаданных атрибуты. Реальная картина из рефлексии на .NET 10:

```
поле string? MaybeNull   → атрибут NullableAttribute(2)
поле string  NotNull     → атрибутов нет
параметр string? opt     → NullableAttribute
тип целиком              → NullableContextAttribute, NullableAttribute
```

Цифра `2` в `NullableAttribute` означает «допускает null», `1` — «не допускает». `NullableContextAttribute` на типе задаёт значение по умолчанию для всех членов, чтобы не повторять атрибут на каждом поле. Прочитать всё это удобнее через `NullabilityInfoContext`, а не разбирая атрибуты руками:

```csharp
var info = new NullabilityInfoContext().Create(field);
info.WriteState;   // Nullable или NotNull
```

Из «это только метаданные» следуют три вещи, про которые спрашивают.

**Никаких проверок в рантайме не добавляется.** Метод `string Take(string s)` спокойно принимает `null`, если его туда передать, — проверено, исключения не было. `string` без вопросительного знака — это обещание, а не гарантия.

**Обещание можно нарушить снаружи.** Код без включённых NRT, старая библиотека, десериализация JSON, рефлексия, EF Core, заполняющий свойства, — всё это кладёт `null` в non-nullable свойство, и компилятор об этом не узнает.

**`default` не спрашивает разрешения:**

```csharp
struct Holder { public string Name; }
default(Holder).Name is null      // true — поле не-nullable, а там null

var arr = new string[3];
arr[0] is null                    // true — массив ссылок создан пустым
```

Поэтому NRT — не замена валидации на границах приложения. Данные, пришедшие снаружи, всё равно нужно проверять.

## Что компилятор всё-таки делает

Внутри проекта с включёнными NRT компилятор ведёт **анализ потока** — отслеживает, откуда значение пришло и проверяли ли его:

```csharp
void Handle(string? input)
{
    Console.WriteLine(input.Length);   // CS8602: возможно разыменование null

    if (input is null) return;
    Console.WriteLine(input.Length);   // ок: после проверки состояние «не null»
}
```

Анализ понимает `is null`, `is not null`, `== null`, `!= null`, сравнение с `string.IsNullOrEmpty` (через атрибуты в BCL), присваивание непустого значения и раннее возвращение. Это и есть основная польза: он ловит именно те места, где о проверке забыли.

Полезные предупреждения, которые стоит знать в лицо:

- **CS8602** — разыменование того, что может быть `null`;
- **CS8618** — non-nullable поле или свойство не инициализировано в конструкторе;
- **CS8625** — присваивание литерала `null` в non-nullable;
- **CS8600** — преобразование `null`-значения в non-nullable тип.

## Оператор `!` и когда он уместен

`!` (null-forgiving) говорит компилятору «я знаю лучше» и гасит предупреждение. Он не делает **ничего** в рантайме — не проверяет, не бросает:

```csharp
string value = MayReturnNull()!;   // предупреждения нет, null попасть может
```

Оправданных применений немного:

```csharp
// 1. Внешняя проверка, которую анализ не видит
if (!dict.TryGetValue(key, out var item)) throw new KeyNotFoundException();
Process(item!);

// 2. Тесты, где null передаётся намеренно
Assert.Throws<ArgumentNullException>(() => service.Handle(null!));

// 3. Поле, которое заполняет фреймворк после конструктора
```

Во всех остальных случаях `!` — способ спрятать проблему, а не решить её. Хороший признак: если `!` в коде больше десятка, аннотации проставлены неверно.

Для случая с полем, которое заполняет фреймворк, есть более честные инструменты, чем `= null!`:

```csharp
public class UserDto
{
    public required string Name { get; init; }      // компилятор требует задать при создании
    public string Email { get; init; } = "";        // безопасное значение по умолчанию
    public string? MiddleName { get; init; }        // честно необязательное
}
```

`required` (C# 11) — обычно лучший ответ на CS8618: он переносит требование на вызывающего, не обманывая анализ.

## Атрибуты для нестандартных контрактов

Когда сигнатура не выражает договорённость, её уточняют атрибутами из `System.Diagnostics.CodeAnalysis`. Компилятор их учитывает:

```csharp
// Если вернулось true — value точно не null
bool TryGet(string key, [NotNullWhen(true)] out string? value);

// Вернёт null, только если аргумент был null
[return: NotNullIfNotNull(nameof(input))]
string? Normalize(string? input);

// Аргумент может быть null, но после вызова считается не-null
void ThrowIfNull([NotNull] object? arg);

// Метод не возвращает управление — код после него недостижим
[DoesNotReturn]
void Fail(string message) => throw new InvalidOperationException(message);
```

`NotNullWhen(true)` — самый полезный из них: именно благодаря ему `dictionary.TryGetValue` и `int.TryParse` не требуют `!` после успешной проверки. Свои `Try`-методы стоит размечать так же.

## Как включать в существующем проекте

Включается в csproj, и на большом проекте это сразу сотни предупреждений:

```xml
<PropertyGroup>
  <Nullable>enable</Nullable>
</PropertyGroup>
```

Разумный порядок миграции — не «включить везде и чинить месяц», а по частям:

**Новые проекты — сразу `enable`.** В шаблонах .NET он включён по умолчанию.

**Старые — включать по файлам** директивой, чиня по одному модулю за раз:

```csharp
#nullable enable
// этот файл проверяется
```

**Полезный промежуточный режим — `annotations`:** аннотации разрешены и попадают в метаданные, но предупреждения не выдаются. Позволяет расставить `?` по публичному API, не воюя с предупреждениями внутри.

```xml
<Nullable>annotations</Nullable>
```

**На финише — предупреждения в ошибки**, иначе они накапливаются и перестают читаться:

```xml
<WarningsAsErrors>Nullable</WarningsAsErrors>
```

Порядок работы внутри проекта тоже важен: сначала размечается публичный API (сигнатуры методов, DTO), потом внутренности. Обратный порядок заставляет переделывать — внутренние решения зависят от контракта, а не наоборот.

## Отличие от Nullable&lt;T&gt;

Похожий синтаксис, совершенно разная природа — это частый вопрос:

```csharp
int? a = null;      // Nullable<int> — настоящая структура с HasValue и Value
string? b = null;   // тот же string, просто помеченный атрибутом
```

`int?` — реальный тип (`System.Nullable<int>`), существующий с .NET 2.0, занимающий больше места, чем `int`, и имеющий свою семантику: `HasValue`, `GetValueOrDefault()`, особое поведение при упаковке (упакованный `int?` со значением `null` — это просто `null`, см. `Упаковка и распаковка`).

`string?` — ничего из этого. Никакой обёртки, никакого `HasValue`, размер тот же. Отсюда и разница в возможностях: `int?` гарантирует, что без проверки значение не достать, а `string?` — лишь предупреждает.

В обобщённом коде это даёт известную путаницу: `T?` для `T : struct` и `T?` для `T : class` — разные вещи, и без ограничения компилятор не знает, какую имеют в виду.

## Что стоит ответить на собеседовании

NRT — статический анализ, а не изменение системы типов: `typeof(string?) == typeof(string)`, а вопросительный знак превращается в `NullableAttribute` в метаданных. В рантайме не появляется ни одной проверки, поэтому `null` спокойно попадает в non-nullable параметр из кода без NRT, из десериализации, из EF или через `default`.

Сильный ответ добавит про `!`: он гасит предупреждение и не делает ничего больше, а массовое его применение означает неправильно расставленные аннотации — для незаполненных свойств есть `required`, для `Try`-методов `[NotNullWhen(true)]`. И про миграцию: включать по файлам директивой `#nullable enable` или через промежуточный режим `annotations`, начиная с публичного API.
