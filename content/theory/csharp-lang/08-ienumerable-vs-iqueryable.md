Оба интерфейса выглядят одинаково: `Where`, `Select`, `OrderBy` есть и там, и там. Разница в том, **что хранит цепочка**. `IEnumerable<T>` хранит скомпилированные делегаты и выполняет их в вашем процессе. `IQueryable<T>` хранит дерево выражений — описание запроса, которое провайдер умеет перевести на другой язык, обычно в SQL. Перепутать их — способ незаметно вытащить из базы всю таблицу.

## Два разных `Where`

Расширяющие методы объявлены в разных классах и принимают разные аргументы:

```csharp
// System.Linq.Enumerable
static IEnumerable<T> Where<T>(this IEnumerable<T> source, Func<T, bool> predicate);

// System.Linq.Queryable
static IQueryable<T> Where<T>(this IQueryable<T> source, Expression<Func<T, bool>> predicate);
```

`Func<T, bool>` — готовый к вызову делегат, чёрный ящик: его можно только выполнить. `Expression<Func<T, bool>>` — **дерево** того же выражения: объект, который можно обойти и разобрать на части.

```csharp
Expression<Func<int, bool>> expr = x => x > 5;
// expr.Body — BinaryExpression, NodeType = GreaterThan
// expr.Body.Left — параметр x, expr.Body.Right — константа 5
```

Именно поэтому EF Core умеет превратить `Where(u => u.Age > 18)` в `WHERE age > 18`: он читает дерево и генерирует SQL. Делегат разобрать нельзя — только вызвать.

Посмотреть дерево можно и без базы, у `AsQueryable`:

```csharp
IQueryable<int> q = arr.AsQueryable().Where(x => x > 5).Select(x => x * 2);
q.Expression.ToString();
// System.Int32[].Where(x => (x > 5)).Select(x => (x * 2))
```

Цепочка не выполнена — она **описана**. Выполнит её `q.Provider`, когда запрос начнут перечислять.

Дерево выражений можно скомпилировать в делегат вручную, но это дорого — 4,2 КБ и заметное время на .NET 10:

```
Expression.Compile()                  ~4240 байт на вызов
вызов скомпилированного делегата           0 байт
```

Отсюда правило: если компилируете выражения в рантайме, результат надо кэшировать, а не компилировать на каждый запрос.

## Где выполняется фильтр

Практическая разница ровно в этом. Один и тот же код даёт два совершенно разных сценария:

```csharp
// IQueryable: фильтр уезжает в SQL
IQueryable<User> query = db.Users;
var adults = query.Where(u => u.Age > 18).ToList();
// SELECT * FROM users WHERE age > 18  — из базы приехали только взрослые

// IEnumerable: фильтр выполняется в памяти приложения
IEnumerable<User> users = db.Users;
var adults = users.Where(u => u.Age > 18).ToList();
// SELECT * FROM users  — приехали ВСЕ, отфильтровали уже у себя
```

Второй вариант на таблице в миллион строк вытянет миллион строк по сети, создаст миллион объектов и выбросит почти все. При этом код выглядит идентично, ошибка не проявляется ни в компиляции, ни в тестах на трёх записях — только под нагрузкой.

Момент, где `IQueryable` превращается в `IEnumerable`, — это **любое приведение к `IEnumerable<T>`**, и происходит оно тише всего в трёх местах:

```csharp
// 1. Тип переменной или возвращаемого значения
IEnumerable<User> users = db.Users;          // дальше всё в памяти

// 2. Явный AsEnumerable()
db.Users.AsEnumerable().Where(...)           // осознанный переход

// 3. Оператор, которого нет в SQL
db.Users.Where(u => MyCheck(u.Name))         // упадёт или уедет в память
```

Третий случай стоит разобрать. EF Core не знает, как перевести ваш метод `MyCheck` в SQL. Раньше он молча выполнял такие куски на клиенте, и это давало ровно ту утечку производительности, о которой речь; начиная с EF Core 3.0 он **бросает исключение** вместо тихого переключения — это одно из лучших изменений в его истории. Хотите на клиенте — напишите `AsEnumerable()` явно, чтобы намерение было видно в коде.

## Правильный порядок: сузить в базе, доработать в памяти

Комбинировать оба мира нормально, важен порядок:

```csharp
var report = db.Orders
    .Where(o => o.CreatedAt >= from && o.Status == OrderStatus.Paid)  // SQL
    .Select(o => new { o.Id, o.Total, o.CustomerId })                 // SQL: только нужные колонки
    .AsEnumerable()                                                   // граница, явная
    .Select(o => new OrderRow(o.Id, FormatMoney(o.Total)))            // C#: свой метод можно
    .ToList();
```

Всё, что сужает объём данных — фильтры, сортировка, пагинация, агрегаты, — должно остаться до `AsEnumerable()`. После неё — форматирование и всё, что SQL не умеет.

Проекция в `Select` до границы важна не меньше фильтра: без неё EF вытащит все колонки сущности, включая тяжёлые текстовые поля, которые отчёту не нужны.

## Что ещё умеет только IQueryable

Раз запрос — дерево, его можно собирать по частям, и это штатный способ сделать динамическую фильтрацию без склейки SQL строками:

```csharp
IQueryable<User> query = db.Users;

if (!string.IsNullOrEmpty(filter.Name))
    query = query.Where(u => u.Name.Contains(filter.Name));

if (filter.MinAge is int minAge)
    query = query.Where(u => u.Age >= minAge);

var page = await query
    .OrderBy(u => u.Id)
    .Skip(filter.Skip).Take(filter.Take)
    .ToListAsync();
```

Ни одного обращения к базе до `ToListAsync` — уйдёт **один** запрос со всеми условиями сразу и с `LIMIT`/`OFFSET`. С `IEnumerable` то же самое означало бы вытащить таблицу и страницу резать в памяти.

## Что возвращать из репозитория

Типовой вопрос на собеседовании, и ответ у него не односложный — это выбор между двумя рисками.

**Вернуть `IQueryable<T>`** — значит отдать наружу незавершённый запрос. Вызывающий может дописать условия, и это гибко; но он же может перечислить его после закрытия `DbContext` и получить `ObjectDisposedException`, а детали хранилища (что это вообще EF) протекают в слой выше.

**Вернуть `IEnumerable<T>`** — обманчиво: тип говорит «коллекция», а под ним может лежать неисполненный запрос с теми же проблемами, только теперь ещё и невидимыми.

**Вернуть `List<T>` или `IReadOnlyList<T>`** — значит запрос уже выполнен, границы честные, сюрпризов нет. Цена — репозиторию нужен метод под каждый сценарий выборки.

Практика, которая обычно оказывается рабочей: репозиторий возвращает **материализованный** результат (`IReadOnlyList<T>`), а параметры фильтрации и пагинации принимает аргументами. `IQueryable` наружу отдают осознанно и только внутри одного слоя — например, когда поверх строится общий механизм фильтрации в том же проекте.

## Мелочи, о которых спрашивают

`IQueryable<T>` **наследует** `IEnumerable<T>` — проверено, `q is IEnumerable<int>` даёт `true`. Поэтому `foreach` по `IQueryable` работает: он просто заставляет провайдер выполнить запрос.

Ленивость у обоих, но разной природы: `IEnumerable` откладывает **вызов делегатов**, `IQueryable` откладывает **поход в базу**. Двойное перечисление (см. `LINQ и отложенное выполнение`) для `IQueryable` означает два SQL-запроса.

`AsQueryable()` на списке в памяти не делает его «умнее»: провайдер там `EnumerableQuery`, который просто компилирует дерево обратно в делегаты. Метод нужен для единообразия сигнатур и в тестах.

## Что стоит ответить на собеседовании

`IEnumerable<T>` работает с делегатами и выполняет запрос в памяти процесса; `IQueryable<T>` хранит дерево выражений, которое провайдер переводит в SQL и выполняет на стороне базы. Разница проявляется в моменте, когда цепочка приводится к `IEnumerable<T>`: всё, что написано после этого, выполнится на клиенте — с `Where` после такого приведения база отдаст таблицу целиком.

Сильный ответ добавит, что граница часто возникает неявно — от типа переменной или возвращаемого значения репозитория, — и что с EF Core 3.0 непереводимое выражение не уезжает на клиента молча, а бросает исключение. И скажет про порядок: всё, что сужает выборку — фильтры, пагинация, проекция колонок, — должно быть до `AsEnumerable()`, а форматирование — после.
