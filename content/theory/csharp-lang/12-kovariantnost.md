Вопрос звучит так: если `string` — это `object`, то является ли `List<string>` списком `object`? Ответ — нет, и причина показательна. Вариантность определяет, когда обобщённый тип с одним параметром можно использовать вместо такого же с другим параметром, и ключ к ней — направление, в котором данные ходят.

## Три варианта поведения

**Ковариантность** (`out`) — сохраняет направление наследования. `IEnumerable<string>` можно присвоить `IEnumerable<object>`, потому что из последовательности строк можно только **читать**, а любая прочитанная строка — это `object`.

**Контравариантность** (`in`) — обращает направление. `IComparer<object>` можно присвоить `IComparer<string>`, потому что в компаратор значения только **передают**, а компаратор, умеющий сравнивать любые `object`, справится и со строками.

**Инвариантность** — присваивание запрещено в обе стороны. Так ведёт себя всё, что и читает, и пишет.

Проверено на .NET 10:

```
IEnumerable<string> -> IEnumerable<object>   можно (ковариантность)
IReadOnlyList<string> -> IReadOnlyList<object> можно
IComparer<object> -> IComparer<string>       можно (контравариантность)
Func<string> -> Func<object>                 можно
Action<object> -> Action<string>             можно
List<string> -> IList<object>                НЕЛЬЗЯ (IList<T> инвариантен)
IEnumerable<int> -> IEnumerable<object>      НЕЛЬЗЯ (значимый тип)
Task<string> -> Task<object>                 НЕЛЬЗЯ (Task<T> инвариантен)
```

## Почему IList инвариантен

Мысленный эксперимент, объясняющий всё. Допустим, компилятор разрешил бы присваивание:

```csharp
List<string> strings = new() { "a" };
IList<object> objects = strings;   // если бы это было можно...
objects.Add(42);                   // ...то сюда мы положили бы int
string s = strings[0];             // ...и прочитали бы его как string
```

Последняя строка — катастрофа: в списке строк лежит число. Чтобы этого не случилось, присваивание запрещено на этапе компиляции. У `IList<T>` есть и `Add(T)`, и индексатор — параметр `T` стоит и на входе, и на выходе, а значит, безопасной вариантности не существует.

`IEnumerable<T>` же объявлен так:

```csharp
public interface IEnumerable<out T> : IEnumerable
{
    IEnumerator<T> GetEnumerator();
}
```

`out T` — обещание, что `T` встречается **только в позиции результата**. Положить туда ничего нельзя, поэтому проблемы из примера не возникает. Компилятор это обещание проверяет: попытка объявить `void Add(T item)` в интерфейсе с `out T` не скомпилируется.

Симметрично для `in`:

```csharp
public interface IComparer<in T>
{
    int Compare(T? x, T? y);   // T только в параметрах
}
```

Отсюда простая мнемоника: **`out` — то, что тип отдаёт, `in` — то, что тип принимает**. У `Func<in T, out TResult>` они стоят ровно на своих местах, у `Action<in T>` — только `in`.

## Ковариантность массивов — историческая ошибка

Массивы ковариантны с первой версии .NET, и это **небезопасно**:

```csharp
string[] strings = { "a", "b" };
object[] objects = strings;     // компилируется
objects[0] = 42;                // ArrayTypeMismatchException в рантайме
```

Проверено — исключение действительно летит. Ровно тот случай, который для `IList<T>` запрещён компилятором, здесь разрешён, а проверка перенесена в рантайм: каждая запись в массив проверяет, что тип значения подходит реальному типу массива.

Сделано это было ради совместимости с Java до появления обобщений в .NET 2.0 — методам вроде `Array.Sort(object[])` нужно было работать с любыми массивами. Сегодня это признанная ошибка дизайна, но убрать её нельзя.

Цена проверки в обычном коде незаметна — в замерах и запись в `object[]`, и запись в `string[]` дали ноль аллокаций, — но проверка типа при каждой записи в ссылочный массив всё же выполняется, и JIT может её убрать только там, где видит точный тип массива.

Практический вывод: **не передавайте `T[]` туда, где ожидается `object[]`**, если принимающий код пишет в массив. Для передачи «только на чтение» есть `IReadOnlyList<T>` — он ковариантен по-настоящему, без проверок в рантайме.

Массивы значимых типов не ковариантны вовсе — `int[]` в `object[]` не приводится (проверено, `InvalidCastException`), потому что представление элементов в памяти разное.

## Почему значимые типы не участвуют

`IEnumerable<int>` нельзя присвоить `IEnumerable<object>` — проверено, нельзя. Причина не в правилах вариантности, а в представлении данных.

Вариантность работает через **ссылочное преобразование**: ссылка на `string` и ссылка на `object` — это одинаковые машинные слова, их можно трактовать по-разному без изменения битов. `int` же лежит в памяти как четыре байта значения, и чтобы увидеть его как `object`, нужна **упаковка** — создание объекта в куче (см. `Упаковка и распаковка`). Это не преобразование ссылки, а копирование данных, и бесплатно оно происходить не может.

Поэтому в ограничениях к вариантности всегда указывается: параметр типа должен быть ссылочным.

## Как объявить своё

`out` и `in` пишутся у параметра типа при объявлении интерфейса или делегата. Для классов вариантность **не поддерживается** вообще — это частый вопрос с подвохом.

```csharp
// Ковариантный: T только возвращается
public interface IRepository<out T>
{
    T? GetById(int id);
    IReadOnlyList<T> GetAll();
    // void Add(T item);  — не скомпилируется
}

// Контравариантный: T только принимается
public interface IValidator<in T>
{
    bool IsValid(T item);
}
```

Что это даёт на практике:

```csharp
IRepository<Manager> managers = new ManagerRepository();
IRepository<Employee> employees = managers;     // читать менеджеров как сотрудников — можно

IValidator<Employee> anyEmployee = new EmployeeValidator();
IValidator<Manager> managerCheck = anyEmployee;  // валидатор сотрудников проверит и менеджера
```

Есть ограничения на то, где параметр может встречаться. `out T` нельзя использовать в параметре метода, а `in T` — в возвращаемом значении; `in T` также нельзя использовать как ограничение обобщённого метода. Компилятор проверяет это строго, и сообщение об ошибке обычно прямо называет нарушенную позицию.

Исключение, которое стоит помнить: `out T` **можно** использовать в ковариантной позиции внутри другого обобщённого типа — например, вернуть `IEnumerable<T>`, потому что он сам ковариантен. Именно поэтому `IReadOnlyList<out T>` работает.

## Почему Task&lt;T&gt; инвариантен

Вопрос на внимательность: `Task<T>` только отдаёт результат, почему же он не ковариантен?

Потому что `Task<T>` — **класс**, а не интерфейс, а классы вариантность не поддерживают в принципе. Проверено: `Task<string>` в `Task<object>` не приводится. Обходят это преобразованием результата:

```csharp
async Task<object> Wrap(Task<string> task) => await task;
```

Та же причина у `List<T>`: даже если бы у него не было `Add`, класс всё равно остался бы инвариантным. Поэтому в публичных API типы-возвращаемые значения лучше объявлять интерфейсами (`IReadOnlyList<T>`), а не классами — так вызывающий получает вариантность.

## Что стоит ответить на собеседовании

Ковариантность (`out`) сохраняет направление наследования и разрешена там, где параметр типа только возвращается: `IEnumerable<string>` присваивается `IEnumerable<object>`, потому что из последовательности можно лишь читать. Контравариантность (`in`) обращает направление и разрешена там, где параметр только принимается: `IComparer<object>` подходит вместо `IComparer<string>`. Если параметр стоит и на входе, и на выходе — как `T` у `IList<T>` с его `Add` и индексатором, — тип инвариантен, иначе в список строк можно было бы положить число.

Сильный ответ добавит три границы. Вариантность работает только у интерфейсов и делегатов, но не у классов, — поэтому `Task<string>` не приводится к `Task<object>`. Она требует ссылочных типов, потому что опирается на преобразование ссылки, а `int` в `object` — это упаковка. И упомянет ковариантность массивов как историческую ошибку: `string[]` присваивается `object[]`, а запись чужого типа падает `ArrayTypeMismatchException` уже в рантайме.
