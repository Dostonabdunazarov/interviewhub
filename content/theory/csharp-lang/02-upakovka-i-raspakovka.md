Упаковка — это мост между двумя мирами типов из предыдущей статьи. Значимые типы и ссылочные устроены по-разному, но иногда значимый тип нужно передать туда, где ждут ссылку на объект. Тогда CLR заворачивает значение в объект — и это стоит денег.

## Что происходит

Упаковка (boxing) — размещение значения значимого типа в куче внутри объекта-обёртки. Распаковка (unboxing) — извлечение значения обратно.

```csharp
int number = 42;
object boxed = number;      // упаковка: аллокация в куче
int back = (int)boxed;      // распаковка: копирование значения обратно
```

Упакованный объект — полноценный обитатель кучи: у него есть заголовок с указателем на таблицу методов и полем для синхронизации, он живёт до сборки мусора и учитывается в поколениях.

Важно, что **упаковка копирует**. Упакованный объект не связан с исходной переменной:

```csharp
int original = 42;
object boxed = original;
original = 100;
// (int)boxed по-прежнему 42
```

Это прямое следствие семантики значимых типов: значение скопировалось в новое место, дальнейшие изменения оригинала его не касаются.

## Сколько это стоит

Цена упаковки складывается из трёх частей, и аллокация — не самая неприятная.

**Аллокация.** Упакованный `int` занимает в куче заметно больше четырёх байт: к значению добавляются заголовок объекта и указатель на таблицу методов, плюс выравнивание. На 64-битной платформе упакованный `int` обходится примерно в 24 байта — в шесть раз больше самого значения.

**Давление на сборщик мусора.** Каждая упаковка — новый объект в Gen 0. Сама по себе аллокация в .NET дёшева, это фактически сдвиг указателя. Дорого то, что происходит потом: чем больше объектов создаётся, тем чаще запускается сборка. В горячем цикле упаковка превращается в поток мусора.

**Косвенность при чтении.** Чтобы добраться до значения, процессору нужно пройти по ссылке — а упакованные объекты разбросаны по куче и плохо ложатся в кэш. Для массива из миллиона `object`, где на самом деле лежат числа, это заметно сильнее, чем стоимость самих аллокаций.

## Где упаковка случается незаметно

Явное `object boxed = number` в реальном коде встречается редко. Проблема в том, что упаковка происходит сама, и увидеть её в исходнике трудно.

### Приведение к интерфейсу

Структура может реализовать интерфейс, но интерфейс — ссылочный тип. Приведение упаковывает:

```csharp
struct Point : IComparable<Point>
{
    public int X;
    public int CompareTo(Point other) => X.CompareTo(other.X);
}

Point p = new() { X = 1 };
IComparable<Point> cmp = p;   // упаковка
```

Здесь же прячется важное исключение. Когда структура передаётся в обобщённый метод с ограничением `where T : IComparable<T>`, упаковки **не происходит**: CLR создаёт отдельную специализацию обобщённого кода под каждый значимый тип, и вызов идёт напрямую. Именно поэтому `List<int>` не упаковывает элементы, а `ArrayList` упаковывает каждый.

```csharp
// Упаковки нет: обобщённый код специализируется под int
static int Max<T>(T a, T b) where T : IComparable<T> =>
    a.CompareTo(b) >= 0 ? 0 : 1;
```

### Необобщённые коллекции и API

`ArrayList`, `Hashtable`, необобщённый `IEnumerable` хранят `object`. Любое значение при добавлении упаковывается:

```csharp
var list = new ArrayList();
list.Add(42);              // упаковка
int value = (int)list[0];  // распаковка
```

Это основная причина, по которой необобщённые коллекции считаются устаревшими с выходом дженериков в .NET 2.0.

### Строковая интерполяция и форматирование

Классический источник незаметной упаковки — передача значений в методы с параметром `params object[]`:

```csharp
// Каждое значение упаковывается — params object[]
string.Format("{0} из {1}", done, total);
Console.WriteLine("Готово: {0}", count);
```

Со строковой интерполяцией в современном C# ситуация лучше. Начиная с C# 10 компилятор использует `DefaultInterpolatedStringHandler`, который принимает значение через обобщённый метод и умеет форматировать его без упаковки:

```csharp
// Упаковки нет в C# 10 и новее
string message = $"{done} из {total}";
```

Но если тип не реализует `ISpanFormattable`, упаковка внутри всё же случится. Для встроенных числовых типов, `DateTime` и `Guid` это не так — они его реализуют.

### Structural equality без переопределения

Если у структуры не переопределён `Equals(object)`, вызов базовой реализации упакует аргумент:

```csharp
struct Point { public int X, Y; }

var a = new Point { X = 1 };
var b = new Point { X = 1 };
bool eq = a.Equals(b);   // Equals(object) — b упаковывается
```

Лечится реализацией `IEquatable<T>`: компилятор выберет перегрузку `Equals(Point)`, и упаковки не будет. Это одна из причин, по которой у структур принято реализовывать `IEquatable<T>` вместе с переопределением `Equals` и `GetHashCode`.

### Enum в качестве ключа или аргумента

`enum` — значимый тип, и на нём легко наткнуться на упаковку:

```csharp
// Упаковка при каждом вызове: Enum.HasFlag принимает Enum
if (permissions.HasFlag(Permission.Write)) { }

// Без упаковки — побитовая проверка
if ((permissions & Permission.Write) != 0) { }
```

`Enum.HasFlag` упаковывает и аргумент, и сам флаг. На .NET 10 это легко измерить: сто тысяч вызовов дают около 4,8 МБ аллокаций — то есть 48 байт на вызов, две упаковки. Побитовая проверка не аллокирует ничего.

## Как увидеть упаковку

Глазами по коду упаковку искать тяжело. Есть три надёжных способа.

**Промежуточный язык.** В IL упаковка видна как инструкция `box`, распаковка — `unbox.any`. Посмотреть IL можно в SharpLab, ILSpy или dotPeek. Для спорного участка это самый прямой ответ.

**Анализаторы.** Есть специализированные анализаторы Roslyn, которые подсвечивают упаковку прямо в редакторе — например, `ClrHeapAllocationAnalyzer`. Полезно на горячем коде, шумно на обычном.

**Профилировщик аллокаций.** Если упаковка реально вредит, она видна как множество мелких объектов типа `System.Int32` в куче. Инструменты и подход разбираются в разделе про производительность.

## Когда на это стоит обращать внимание

Почти никогда — и это важная часть ответа.

Одна упаковка стоит десятки наносекунд. В коде, который обрабатывает HTTP-запрос и ходит в базу, упаковка теряется на фоне всего остального: запрос к PostgreSQL занимает миллисекунды, то есть в десятки тысяч раз дольше. Переписывать читаемый код ради устранения упаковки в таком месте — потеря времени.

Упаковка становится проблемой в узком наборе случаев:

- **горячий цикл** на миллионы итераций;
- **сериализация и парсинг** больших объёмов данных;
- **код с жёсткими требованиями к задержке**, где важен не средний отклик, а хвост распределения: лишний мусор означает лишние паузы сборщика;
- **библиотечный код**, который вызывают из чужих горячих циклов.

Правильный порядок действий — сначала измерить, потом чинить. Если профилировщик показал, что аллокации действительно давят на сборщик, упаковка — один из первых кандидатов на устранение. Если не показал, стоит оставить код читаемым.

## Что стоит ответить на собеседовании

Упаковка — это размещение значения значимого типа в куче внутри объекта-обёртки, распаковка — обратное извлечение. Она копирует значение, поэтому упакованный объект не связан с оригиналом.

Стоит назвать типичные места, где она случается незаметно: приведение структуры к интерфейсу, необобщённые коллекции, `params object[]` в форматировании, `Equals(object)` без `IEquatable<T>`. И добавить, что в обобщённом коде с ограничением по интерфейсу упаковки нет — CLR специализирует код под каждый значимый тип.

Хороший ответ заканчивается оговоркой про меру: упаковка важна в горячем коде и не важна в обычном, и начинать надо с измерения, а не с переписывания.
