Четыре темы этой статьи объединяет одно: в каждой есть вопрос «что решается при компиляции, а что в рантайме». `const` вшивается в вызывающий код, `new` выбирается по типу переменной, extension-метод превращается в обычный статический вызов, а `in` может незаметно скопировать структуру. На собеседовании спрашивают именно эти места, а не синтаксис.

## ref, out и in: один механизм, три контракта

Все три модификатора передают адрес переменной, а не её значение. В IL это один и тот же управляемый указатель; `out` отличается только атрибутом, поэтому перегрузки, различающиеся лишь `ref` и `out`, запрещены. Разница — в правилах, которые проверяет компилятор:

- `ref` — переменная должна быть инициализирована до вызова, метод может читать и писать;
- `out` — инициализация на входе не нужна, но метод обязан присвоить значение до возврата и не может читать параметр до присваивания;
- `in` — только чтение; смысл в том, чтобы не копировать большую структуру.

```csharp
static void Swap<T>(ref T a, ref T b) => (a, b) = (b, a);

if (int.TryParse("42", out var n)) Console.WriteLine(n);

static double Length(in Vector3 v) => Math.Sqrt(v.X * v.X + v.Y * v.Y + v.Z * v.Z);
```

Для ссылочного типа `ref` — это ссылка на ссылку. Без `ref` метод может менять содержимое объекта, но `list = new List<int>()` внутри метода снаружи не видно; с `ref` переприсвоение доходит до вызывающего.

Главный подвох `in` — **защитная копия**. Компилятор обязан гарантировать, что `in`-параметр не изменится, а про метод не-`readonly` структуры он не знает, меняет ли тот состояние. Поэтому перед каждым таким вызовом он копирует структуру во временную переменную:

```csharp
struct Counter { public int Value; public void Inc() => Value++; }

static void Bump(in Counter c) => c.Inc();

var c = new Counter();
Bump(in c);
Console.WriteLine(c.Value);
```

Проверено на .NET 10: выводится `0` — `Inc` отработал на копии. Выигрыш от передачи по ссылке исчезает, поэтому `in` имеет смысл с `readonly struct` или `readonly`-методами. Для маленьких структур вроде `int` или `DateTime` передача по значению дешевле — `in` лишь добавляет косвенность.

В месте вызова `in` можно не писать, и тогда для литерала компилятор создаст временную переменную. C# 12 добавил `ref readonly`-параметры: тот же контракт, но вызывающий обязан передать именно переменную.

Ссылка может указывать на стек, поэтому `ref`, `out` и `in` нельзя объявлять у `async`-методов и итераторов и нельзя захватить в лямбду. C# 13 разрешил `ref`-локальные переменные в async-методах, если они не живут через `await`. `ref`-возвраты, `ref struct` и `scoped` — в `Span<T> и Memory<T>`. В прикладном коде `out` уместен в паттерне `TryXxx`, а вместо нескольких `out` лучше вернуть кортеж или record.

## const, readonly и static readonly

`const` — константа времени компиляции. Допустимы только примитивы, `decimal`, `string`, enum и `null` для ссылочных типов; она неявно статическая. Только `const` можно использовать в `case`, аргументах атрибутов и значениях параметров по умолчанию.

`readonly` — поле экземпляра, присваиваемое при объявлении или в конструкторе. `static readonly` — одно поле на тип, вычисляется в рантайме при инициализации типа и может быть любого типа:

```csharp
public class HttpSettings
{
    public const int MaxRetries = 3;
    public static readonly TimeSpan Timeout = TimeSpan.FromSeconds(30);
    private readonly ILogger _logger;

    public HttpSettings(ILogger logger) => _logger = logger;
}
```

`TimeSpan.FromSeconds(30)` — вызов метода, поэтому `const` здесь невозможен.

**Версионирование — главная ловушка `const`.** Значение подставляется литералом в IL сборки-потребителя. Если библиотека поменяла `public const int ProtocolVersion` с `1` на `2`, неперекомпилированный потребитель продолжит видеть `1` — в его коде нет ссылки на поле, есть только число. `static readonly` читается из поля в рантайме. Поэтому публичные значения, которые могут измениться, объявляют `static readonly`, а `const` оставляют для действительно неизменного и для `private`/`internal`.

**`readonly` защищает поле, а не объект.** `readonly List<int> _items` нельзя переприсвоить, но `_items.Add(1)` работает. Для структуры иначе: у `readonly`-поля типа struct нельзя менять поля, а вызов не-`readonly` метода порождает ту же защитную копию, что и с `in`.

**Скорость.** Когда метод перекомпилируется на оптимизированном уровне tiered compilation, тип уже инициализирован, и JIT может считать `static readonly`-поле примитивного типа константой: `if (Settings.FeatureEnabled)` сворачивается вместе с мёртвой веткой. Разница с `const` в скорости пренебрежима — выбирать стоит по семантике.

С C# 10 `const string` можно собрать интерполяцией из констант: `const string Url = $"{Base}/api";`. Исключение в инициализаторе `static readonly` превращается в `TypeInitializationException`, и тип остаётся непригодным до конца жизни процесса.

## virtual, override и new

В C# методы по умолчанию невиртуальные — в отличие от Java. `virtual` разрешает переопределение, `override` переопределяет, `new` скрывает:

```csharp
class Base
{
    public virtual string Who() => "Base";
    public string Hello() => "Base.Hello";
}

class Derived : Base
{
    public override string Who() => "Derived";
    public new string Hello() => "Derived.Hello";
}

Base b = new Derived();
b.Who();
b.Hello();
((Derived)b).Hello();
```

Проверено: `b.Who()` даёт `"Derived"`, `b.Hello()` — `"Base.Hello"`, после приведения — `"Derived.Hello"`. Механизм — таблица виртуальных методов типа. `override` записывает свою реализацию в тот же слот, что и базовый `virtual`, поэтому вызов через любую ссылку находит её. `new` создаёт новый член, а старый слот остаётся с базовой реализацией; какой из них вызвать, решает компилятор по статическому типу переменной.

Без `new` компилятор выдаст предупреждение CS0108 и всё равно скроет член: `new` лишь делает намерение явным. Оправдан он редко — когда базовый класс из чужой библиотеки в новой версии добавил член с тем же именем. В своём коде скрытие — источник багов.

Детали, которые проверяют:

- `sealed override` запрещает дальнейшее переопределение в наследниках;
- `abstract` — неявно виртуальный член без реализации, наследник обязан сделать `override`;
- сигнатура и доступность `override` совпадают с базовыми, но с C# 9 разрешены ковариантные возвращаемые типы: `override Derived Clone()`;
- `base.Who()` вызывает реализацию родителя невиртуально.

**Виртуальный вызов в конструкторе.** Конструктор базового класса выполняется раньше тела конструктора наследника, но объект уже имеет итоговый тип, поэтому виртуальный вызов попадёт в `override` наследника:

```csharp
class A { public A() => Init(); protected virtual void Init() { } }

class B : A
{
    private string _name;
    public B() => _name = "b";
    protected override void Init() => Console.WriteLine(_name.Length);
}
```

`new B()` падает с NullReferenceException: тело конструктора `B` ещё не выполнялось. Инициализатор поля (`private string _name = "b";`) выполняется до базового конструктора и спас бы пример, но полагаться на это хрупко — виртуальные методы из конструктора не вызывают.

**Производительность.** Виртуальный вызов — косвенный переход, который JIT в общем случае не инлайнит. Для `sealed`-классов и при известном точном типе JIT девиртуализирует вызов, а динамическая PGO, включённая по умолчанию с .NET 8, девиртуализирует горячие мономорфные вызовы с проверкой типа. Подробнее — в `CLR, IL и JIT`.

## Extension methods

Extension-метод — статический метод статического класса с `this` перед первым параметром. Вызов `text.IsBlank()` компилятор переписывает в `StringExtensions.IsBlank(text)`: тип не меняется, доступа к приватным членам нет.

```csharp
public static class StringExtensions
{
    public static bool IsBlank(this string? s) => string.IsNullOrWhiteSpace(s);
}

string? name = null;
name.IsBlank();
```

Последняя строка возвращает `true` и не падает: это обычный статический вызов с `null` в аргументе. Если расширение не рассчитано на `null`, проверять аргумент надо самому.

**Выбор метода — статический.** Сначала компилятор ищет подходящий экземплярный метод и только если его нет — extension-методы в подключённых через `using` пространствах имён, начиная с ближайшего. Отсюда следствия:

- экземплярный метод с подходящей сигнатурой всегда побеждает: если в новой версии библиотеки у типа появится свой `Truncate`, ваш extension молча перестанет вызываться;
- без нужного `using` метод исчезает — поэтому пакеты кладут методы регистрации в namespace `Microsoft.Extensions.DependencyInjection`;
- два подходящих расширения из разных namespace дают ошибку неоднозначности;
- полиморфизма нет: при перегрузках для `Base` и `Derived` вызов на переменной типа `Base`, в которой лежит `Derived`, выберет версию для `Base`;
- через `dynamic` extension-методы не вызываются.

На расширениях построены LINQ (см. `IEnumerable vs IQueryable`), регистрация сервисов и fluent-API. Главная ценность — добавить поведение интерфейсу сразу для всех реализаций. Для структур есть `this ref`: расширение меняет значение без копии.

**C# 14 — extension members.** Новые блоки `extension` позволяют объявлять не только методы, но и свойства, а также статические члены, которые вызываются через сам расширяемый тип:

```csharp
public static class EnumerableExtensions
{
    extension<T>(IEnumerable<T> source)
    {
        public bool IsEmpty => !source.Any();
    }

    extension(TimeSpan)
    {
        public static TimeSpan TwoMinutes => TimeSpan.FromMinutes(2);
    }
}

new List<int>().IsEmpty;
TimeSpan.TwoMinutes;
```

Проверено на .NET 10. Старые `this`-методы продолжают работать, а природа не меняется: это статический код без доступа к состоянию объекта. Если нужен доступ к внутреннему состоянию или полиморфизм — это метод класса.

## Что стоит ответить на собеседовании

`ref`, `out` и `in` передают адрес переменной и различаются контрактом инициализации и записи; `in` с не-`readonly` структурой делает защитную копию и теряет смысл. `const` подставляется литералом в вызывающую сборку, поэтому публичные изменяемые значения объявляют `static readonly`; `readonly` защищает поле, а не объект. `override` замещает слот в таблице виртуальных методов и работает через ссылку базового типа, `new` скрывает член, и вызов определяется типом переменной. Extension-метод — статический метод, который компилятор подставляет вместо вызова «на экземпляре».

Сильный ответ покажет, что за каждым модификатором стоит граница между компиляцией и рантаймом: перекомпиляция потребителя после смены `const`, JIT, сворачивающий `static readonly` в константу, девиртуализация `sealed` и PGO, NRE от виртуального вызова в базовом конструкторе, экземплярный метод, молча вытесняющий extension, и вызов расширения на `null` без исключения. Плюс знание, что C# 12 добавил `ref readonly`-параметры, а C# 14 — extension-свойства и статические extension-члены.
