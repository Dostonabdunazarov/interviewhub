Делегат — типизированная ссылка на метод: переменная, в которую можно положить метод и вызвать его позже. На делегатах держатся события, колбэки, LINQ и вся подписочная механика в .NET. Событие же — не отдельная сущность, а делегат с ограниченным доступом, и понимание этой разницы — типовой вопрос на собеседовании.

## Делегат — это класс

Объявление делегата компилируется в класс, унаследованный от `MulticastDelegate`, с полями «на каком объекте» и «какой метод»:

```csharp
delegate int Transform(int x);     // превращается в класс Transform : MulticastDelegate

Transform t = x => x * 2;
int result = t(5);                 // 10
```

Свои объявления `delegate` сегодня почти не нужны — в BCL есть готовые обобщённые типы:

```csharp
Func<int, int> f = x => x * 2;         // принимает int, возвращает int
Func<int, string, bool> g = (i, s) => s.Length == i;  // последний параметр — результат
Action<string> log = s => Console.WriteLine(s);        // ничего не возвращает
Predicate<int> isEven = x => x % 2 == 0;               // Func<int, bool> под другим именем
```

Собственный `delegate` оправдан в двух случаях: когда нужны `ref`/`out`-параметры (`Func` их не умеет) и когда имя типа несёт смысл — `Transform` читается лучше, чем `Func<int, int>` в публичном API.

## Сколько стоит делегат

Создание делегата — это аллокация объекта, но компилятор кое-что кэширует. Замеры на .NET 10, байт на одно создание с вызовом:

```
лямбда без захвата (кэшируется компилятором)        0 байт
лямбда с захватом локальной переменной               0 байт
лямбда с захватом параметра итерации                88 байт
static-лямбда, значение через аргумент               0 байт
метод-группа экземпляра (Action a = inst.Do)        64 байта
метод-группа статического метода                     0 байт
```

Читать это надо так. Лямбда **без захвата** компилируется в статический метод, делегат для него создаётся один раз и кладётся в кэш-поле — отсюда ноль. Лямбда, **захватывающая переменную**, требует объекта замыкания, в который эта переменная переносится; если захваченное значение меняется на каждой итерации, замыкание создаётся заново — те самые 88 байт. Ноль во второй строке — тот же кэш: захваченная переменная не менялась, замыкание создалось один раз.

Ключевой практический вывод: **лишнее — не лямбды, а захват изменяющегося состояния в горячем цикле**. Лечится либо `static`-лямбдой с передачей значения аргументом (для этого у многих API есть перегрузка со `state`), либо выносом делегата из цикла.

```csharp
// 88 байт на итерацию: замыкание пересоздаётся
for (int i = 0; i < n; i++)
    Run(() => Handle(i));

// 0 байт: значение приходит аргументом, замыкания нет
for (int i = 0; i < n; i++)
    Run(static s => Handle(s), i);
```

Отдельная строчка про метод-группы: `Action a = inst.Do` стоит 64 байта каждый раз, потому что делегат хранит ссылку на конкретный экземпляр и кэшировать его нельзя. Для статического метода с C# 11 компилятор делегат кэширует, и цена нулевая.

## Multicast: несколько методов в одном делегате

Любой делегат может хранить список методов. `+=` добавляет, `-=` убирает:

```csharp
Action pipeline = () => Console.Write("a");
pipeline += () => Console.Write("b");
pipeline += () => Console.Write("c");

pipeline();                         // abc — по порядку подписки
pipeline.GetInvocationList().Length; // 3
```

Делегаты **неизменяемы**: `+=` не меняет существующий объект, а создаёт новый список и присваивает переменной. Из этого следуют две вещи.

**Возвращаемое значение теряется.** Если делегат что-то возвращает, вызов multicast отдаёт результат только **последнего** метода, остальные молча выброшены:

```csharp
Func<int> calc = () => 1;
calc += () => 2;
calc += () => 3;
calc();                 // 3 — первые два результата потеряны
```

Поэтому multicast имеет смысл только для `Action`-подобных делегатов. Если нужны все результаты — перебирать `GetInvocationList()` вручную (это, кстати, 48 байт на вызов: метод создаёт новый массив).

**Исключение обрывает цепочку.** Если второй из трёх подписчиков бросит, третий не выполнится, а исключение уйдёт наверх вызывающему:

```csharp
foreach (var handler in pipeline.GetInvocationList().Cast<Action>())
{
    try { handler(); }
    catch (Exception ex) { logger.LogError(ex, "подписчик упал"); }
}
```

Так делают, когда подписчики независимы и падение одного не должно влиять на остальных.

Сам по себе вызов multicast бесплатен по памяти — в замерах ноль байт на вызов трёх подписчиков. Платить приходится только за построение списка и за `GetInvocationList`.

## Событие = делегат + ограничение доступа

Событие — это синтаксический сахар над полем-делегатом, который запрещает снаружи всё, кроме подписки и отписки:

```csharp
public class Order
{
    public event EventHandler<OrderPaidEventArgs>? Paid;

    public void Pay()
    {
        // ...
        Paid?.Invoke(this, new OrderPaidEventArgs(Id));
    }
}
```

Что именно даёт `event` по сравнению с публичным полем `public EventHandler? Paid;`:

- снаружи доступны **только** `+=` и `-=`; присвоить `Paid = null` и стереть чужие подписки нельзя;
- **вызвать** событие может только сам класс — подписчик не может изобразить его срабатывание;
- у события можно написать свои `add`/`remove` — например, хранить подписчиков в другой структуре.

Компилятор превращает `event` в приватное поле плюс два метода `add_Paid`/`remove_Paid`. Внутри класса имя события означает поле, снаружи — только аксессоры.

Про вызов: `Paid?.Invoke(...)` вместо `Paid(...)` обязателен, потому что **у события без подписчиков поле равно `null`**, а не пустому списку. Проверено: `?.Invoke` на событии без подписчиков проходит без NRE. Классический совет из старых книг — копировать делегат в локальную переменную перед проверкой, чтобы подписчик не успел отписаться между проверкой и вызовом, — `?.` делает ровно это, читая поле один раз.

Соглашение по сигнатуре — `(object? sender, TEventArgs e)`, для аргументов наследник `EventArgs`. Своё определение `delegate` для событий сейчас почти не пишут: `EventHandler<T>` покрывает случай.

## Главная ловушка: события держат подписчиков

Подписка — это ссылка **от источника события к подписчику**. Пока источник жив, все подписчики недостижимы для сборщика:

```csharp
public class Widget
{
    public Widget(NotificationService service)
    {
        service.Received += OnReceived;   // service теперь держит this
    }

    void OnReceived(object? s, EventArgs e) { }
}
```

Если `NotificationService` живёт всё время работы приложения (синглтон в DI), то каждый созданный `Widget` останется в памяти навсегда, даже когда на него больше никто не ссылается. Это самая частая утечка памяти в .NET и любимый вопрос на собеседованиях.

Лечится отпиской. Явно:

```csharp
public sealed class Widget : IDisposable
{
    readonly NotificationService _service;

    public Widget(NotificationService service)
    {
        _service = service;
        _service.Received += OnReceived;
    }

    public void Dispose() => _service.Received -= OnReceived;
}
```

Здесь важна деталь: отписаться можно **только тем же делегатом**. `-=` сравнивает делегаты по цели и методу, поэтому метод-группа `OnReceived` отписывается корректно, а лямбда — нет:

```csharp
service.Received += (s, e) => Handle();   // подписались
service.Received -= (s, e) => Handle();   // НЕ отписались: это другой объект
```

Если подписка лямбдой всё-таки нужна, делегат надо сохранить в поле и отписываться им же.

Альтернативы в современном коде: `IObservable<T>`/Rx с его `IDisposable` на подписку, каналы (`System.Threading.Channels`) для потока сообщений и слабые подписки — но для внутрипроцессных уведомлений обычное событие с честным `Dispose` остаётся нормальным решением.

## Ковариантность делегатов

Делегаты поддерживают вариантность: `Func<T>` ковариантен по результату, `Action<T>` контравариантен по параметру. Проверено на .NET 10:

```csharp
Func<string> fs = () => "a";
Func<object> fo = fs;        // можно: строку всегда можно вернуть как object

Action<object> ao = o => { };
Action<string> as_ = ao;     // можно: обработчик object справится со строкой
```

Подробнее, почему это безопасно именно в таком направлении, — в статье `Ковариантность и контравариантность`.

## Что стоит ответить на собеседовании

Делегат — типизированная ссылка на метод, компилируемая в класс от `MulticastDelegate`, и в нём может лежать список методов. Событие — не отдельный механизм, а делегат, у которого снаружи доступны только `+=` и `-=`: вызвать его или обнулить может только объявивший класс.

Сильный ответ добавит две вещи. Первая — утечка через события: подписка держит подписчика ссылкой от источника, и при долгоживущем источнике подписчики не собираются, а отписаться лямбдой, которой подписался, невозможно. Вторая — про цену: лямбда без захвата кэшируется и стоит ноль, а захват меняющейся переменной создаёт замыкание на каждой итерации (88 байт на .NET 10), что лечится `static`-лямбдой с передачей состояния аргументом.
