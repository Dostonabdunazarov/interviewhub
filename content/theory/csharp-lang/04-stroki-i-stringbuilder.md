`string` — ссылочный тип, который ведёт себя как значимый: сравнивается по содержимому и не меняется после создания. Из этой неизменяемости следует и удобство строк, и главная ловушка производительности, ради которой существует `StringBuilder`.

## Неизменяемость и её последствия

Объект `string` нельзя изменить после создания. Всё, что выглядит как изменение, создаёт новую строку:

```csharp
string s = "привет";
s = s.ToUpper();          // новая строка, старая осталась в куче
s += " мир";              // ещё одна новая строка
```

Ни `ToUpper`, ни `Replace`, ни `Trim`, ни `Substring` не меняют исходную строку — все они возвращают новую. Забытый результат — распространённая ошибка:

```csharp
string name = "  Иван  ";
name.Trim();              // результат выброшен, name не изменился
name = name.Trim();       // так правильно
```

Неизменяемость даёт три вещи. Строку **безопасно передавать** в чужой код: его нельзя заставить увидеть изменение. Строка **потокобезопасна** по чтению без всякой синхронизации. И строку можно **кэшировать по содержимому**, чем CLR и пользуется.

## Интернирование

Строковые литералы из исходного кода попадают в пул интернирования — общую таблицу, где каждое уникальное содержимое хранится один раз.

```csharp
string a = "привет";
string b = "привет";
ReferenceEquals(a, b);    // true — это один объект
```

Строки, собранные во время выполнения, в пул не попадают:

```csharp
string c = "при" + Console.ReadLine();  // вычисляется в рантайме
ReferenceEquals(a, c);    // false, даже если содержимое совпало
```

Конкатенация литералов — исключение: `"при" + "вет"` компилятор сворачивает в единственный литерал ещё на этапе компиляции, и он интернируется.

Практический вывод: **никогда не сравнивайте строки через `ReferenceEquals` или приведение к `object`**. Результат будет зависеть от того, попала строка в пул или нет.

```csharp
object x = "привет";
object y = new string("привет".ToCharArray());
x == y;                   // false — сравниваются ссылки!
(string)x == (string)y;   // true — сравнивается содержимое
```

Оператор `==` для `string` перегружен и сравнивает содержимое. Но если операнды приведены к `object`, компилятор выберет сравнение ссылок — вот почему упомянутая ловушка встречается в вопросах на собеседованиях.

`string.Intern` позволяет добавить строку в пул вручную. Пользоваться этим стоит осторожно: интернированные строки живут до конца работы процесса и не собираются сборщиком мусора, поэтому интернирование пользовательского ввода — способ устроить утечку памяти.

## Почему конкатенация в цикле — проблема

Каждая операция `+=` создаёт новую строку и копирует в неё всё содержимое предыдущей. В цикле это даёт квадратичную сложность:

```csharp
// Так делать не надо
string result = "";
for (int i = 0; i < 10_000; i++)
    result += i;          // на каждой итерации копируется весь result
```

На тысяче итераций разница ещё терпима, на десятках тысяч — уже секунды и десятки мегабайт мусора. Скопированные промежуточные строки немедленно становятся недостижимыми и нагружают сборщик.

`StringBuilder` решает это буфером: он хранит символы в изменяемом массиве и достраивает его по мере надобности, а строку создаёт один раз в конце.

```csharp
var sb = new StringBuilder();
for (int i = 0; i < 10_000; i++)
    sb.Append(i);
string result = sb.ToString();   // единственная аллокация строки
```

Если итоговый размер примерно известен, его стоит задать сразу — это избавит от перевыделений буфера:

```csharp
var sb = new StringBuilder(capacity: 4096);
```

## Когда StringBuilder не нужен

Обратная ошибка встречается не реже: `StringBuilder` ради склейки трёх строк. Он сам по себе объект с внутренним буфером, и на коротких склейках проигрывает.

**Несколько строк подряд компилятор оптимизирует сам.** Конкатенация в одном выражении разворачивается в вызов `string.Concat`, который считает итоговую длину и делает одну аллокацию:

```csharp
// Один вызов string.Concat, одна аллокация — StringBuilder тут лишний
string full = firstName + " " + lastName + ", " + city;
```

**Интерполяция не хуже.** В современном C# `$"..."` использует `DefaultInterpolatedStringHandler`, который пишет в арендованный буфер и тоже делает одну аллокацию результата:

```csharp
string full = $"{firstName} {lastName}, {city}";
```

**Для массива строк есть `string.Join`.** Он эффективнее ручного цикла с `StringBuilder` и читается лучше:

```csharp
string csv = string.Join(", ", names);
```

Практическое правило: `StringBuilder` нужен, когда число операций заранее неизвестно — то есть в цикле или при построении текста по условиям. Для фиксированного набора кусков достаточно интерполяции.

## Сравнение строк: какой способ выбрать

Сравнение строк — место, где по умолчанию легко получить неправильное поведение или лишние расходы.

```csharp
// Порядковое сравнение: побайтовое, быстрое, предсказуемое
string.Equals(a, b, StringComparison.Ordinal);
string.Equals(a, b, StringComparison.OrdinalIgnoreCase);

// Культурное: учитывает правила языка, медленнее
string.Equals(a, b, StringComparison.CurrentCulture);
```

Правило простое: **для идентификаторов, ключей, имён файлов, заголовков HTTP и прочих технических строк используйте `Ordinal`**. Культурное сравнение нужно только там, где результат видит пользователь, — сортировка списка имён на экране.

Разница не только в скорости. Культурное сравнение даёт неочевидные результаты, зависящие от настроек системы: классический пример — турецкая локаль, где `"I".ToLower()` даёт не `"i"`, а `"ı"`, из-за чего регистронезависимое сравнение идентификаторов ломается. Именно поэтому `ToLower()` перед сравнением — плохая практика вдвойне: он ещё и создаёт лишнюю строку.

```csharp
// Так не надо: лишняя аллокация плюс зависимость от культуры
if (input.ToLower() == "admin") { }

// Так правильно
if (string.Equals(input, "admin", StringComparison.OrdinalIgnoreCase)) { }
```

Для проверки на пустоту есть готовые методы, и `IsNullOrWhiteSpace` обычно ближе к тому, что имеется в виду:

```csharp
string.IsNullOrEmpty(s);        // null или ""
string.IsNullOrWhiteSpace(s);   // null, "" или только пробелы
```

## Как избежать аллокаций при разборе строк

Когда строку нужно не собрать, а разобрать, промежуточные подстроки становятся основным источником мусора. `Substring` и `Split` создают новые строки — а `Span<char>` позволяет смотреть на участок существующей строки без копирования:

```csharp
ReadOnlySpan<char> span = line.AsSpan();
int comma = span.IndexOf(',');

ReadOnlySpan<char> key = span[..comma];      // без аллокации
ReadOnlySpan<char> value = span[(comma + 1)..];

if (int.TryParse(value, out int number)) { }  // парсинг прямо из span
```

Это уже тема раздела про CLR и память — там `Span<T>` разбирается подробно. Здесь достаточно знать, что для разбора больших объёмов текста существует способ не создавать подстроки вовсе.

## Что стоит ответить на собеседовании

`string` — ссылочный тип, неизменяемый, с перегруженным `==`, который сравнивает содержимое. Любая операция «изменения» создаёт новую строку, поэтому конкатенация в цикле даёт квадратичную сложность и много мусора — для этого случая есть `StringBuilder` с изменяемым буфером.

Сильный ответ добавит границу применимости: для нескольких кусков в одном выражении `StringBuilder` не нужен, компилятор свернёт это в `string.Concat` или интерполяцию с одной аллокацией. И упомянет `StringComparison.Ordinal` как правильный выбор для технических строк вместо `ToLower()` перед сравнением.
