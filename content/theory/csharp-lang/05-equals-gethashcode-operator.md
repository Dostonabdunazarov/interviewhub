В C# есть три разных способа спросить «равны ли эти два объекта», и они не связаны между собой: виртуальный `Equals`, `GetHashCode` и оператор `==`. Можно переопределить один и забыть про второй — компилятор не остановит, а коллекции начнут вести себя странно. Разбираемся, кто из них когда вызывается и какой контракт между ними обязателен.

## Три механизма, которые легко перепутать

`object.Equals(object)` — виртуальный метод. Его вызывают коллекции, LINQ и всё, что работает с объектами через базовый тип. Именно он определяет равенство «по-настоящему».

`object.GetHashCode()` — тоже виртуальный, возвращает `int`. Хеш-таблицы используют его, чтобы понять, **в какую корзину** класть объект, и только потом внутри корзины зовут `Equals`.

`==` — статический оператор, не виртуальный. Он выбирается **компилятором по типу переменной**, а не по типу объекта в рантайме. Это и есть источник главной ловушки:

```csharp
object a = new string("привет".ToCharArray());
object b = new string("привет".ToCharArray());

a == b;                  // false — оператор object, сравнение ссылок
a.Equals(b);             // true  — виртуальный Equals строки
((string)a) == ((string)b); // true — оператор string
```

Объекты одни и те же, ответы разные. `Equals` виртуален и всегда доберётся до реализации `string`, а `==` компилятор выбрал по статическому типу `object`. В `Строки и StringBuilder` эта ловушка упоминалась — здесь видно, откуда она берётся.

По умолчанию для классов все три сравнивают ссылки: два объекта равны, только если это один объект. Для структур по умолчанию сравнивается содержимое, а `==` вообще не определён — попытка написать `p1 == p2` для своей структуры не скомпилируется, пока оператор не будет объявлен.

## Контракт GetHashCode

Правило одно, и оно односторонее:

> Если `a.Equals(b)`, то `a.GetHashCode() == b.GetHashCode()`.

Обратное неверно: у разных объектов хеши **могут** совпасть, это называется коллизией, и она нормальна. `Dictionary` разберётся, вызвав `Equals` внутри корзины.

Отсюда следуют правила, которые в коде нарушают чаще всего:

**Переопределяя `Equals`, обязательно переопределяйте `GetHashCode`.** Иначе два «равных» объекта дадут разные хеши, попадут в разные корзины, и `Dictionary` просто не найдёт то, что вы туда положили. Компилятор выдаст на это предупреждение CS0659 — его нельзя игнорировать.

**Хеш должен считаться только по тем полям, что участвуют в `Equals`.** Лишнее поле в хеше — те же разные корзины у равных объектов.

**Поля в хеше должны быть неизменяемыми.** Мутация поля после того, как объект стал ключом, теряет его окончательно:

```csharp
var key = new MutableKey { Value = 1 };
var set = new HashSet<MutableKey> { key };
key.Value = 2;
set.Contains(key);       // false — хотя это тот самый объект
```

Проверено на .NET 10: объект остался в наборе, но лежит в корзине, посчитанной по старому хешу, и найти его теперь нельзя ничем, кроме полного перебора.

Считать хеш руками через `x ^ y` не нужно — есть `HashCode.Combine`, который делает это правильно и устойчиво к перестановкам:

```csharp
public override int GetHashCode() => HashCode.Combine(X, Y);
```

## Реализация для класса

Канонический вид — с `IEquatable<T>` для типизированного сравнения без приведений:

```csharp
public sealed class Money : IEquatable<Money>
{
    public decimal Amount { get; }
    public string Currency { get; }

    public bool Equals(Money? other) =>
        other is not null &&
        Amount == other.Amount &&
        Currency == other.Currency;

    public override bool Equals(object? obj) => Equals(obj as Money);

    public override int GetHashCode() => HashCode.Combine(Amount, Currency);

    public static bool operator ==(Money? a, Money? b) =>
        a is null ? b is null : a.Equals(b);

    public static bool operator !=(Money? a, Money? b) => !(a == b);
}
```

Три детали, из-за которых такой код чаще всего ломается. `operator ==` **нельзя** реализовать как `a.Equals(b)` — на `null` слева это NullReferenceException, поэтому проверка через `is null` (не через `==`, иначе получится бесконечная рекурсия). `operator !=` требуется объявить, если объявлен `==`, — компилятор этого требует. И класс лучше делать `sealed`: в наследнике `Equals` начнёт сравнивать только базовые поля, и объекты разных типов окажутся «равны».

## Структуры: почему по умолчанию медленно

Для структур `ValueType.Equals` и `ValueType.GetHashCode` работают из коробки и сравнивают поля. Но реализация универсальная и платит за это двумя способами.

Во-первых, `Equals(object)` принимает `object` — значит, структуру нужно **упаковать**. Замеры на .NET 10:

```
struct без override: Equals(object)              48 байт на вызов
struct с ref-полем без override: Equals(object)  80 байт на вызов
struct с override Equals(object)                 24 байта на вызов
struct с IEquatable<T>.Equals(T)                  0 байт
```

Во-вторых, если у структуры есть ссылочные поля, `ValueType.Equals` не может сравнить память побайтово и уходит в рефлексию по полям — отсюда 80 байт вместо 48.

Реальная цена видна на `Dictionary`:

```
Dictionary<struct без override>.TryGetValue    72 байта на вызов
Dictionary<struct с override>.TryGetValue       0 байт
```

72 байта мусора на каждый поиск по словарю — этого достаточно, чтобы горячий путь начал заметно нагружать сборщик. Поэтому **любая структура, которая может стать ключом словаря или элементом `HashSet`, обязана реализовать `IEquatable<T>` и переопределить `Equals`/`GetHashCode`**.

Интересно, что `List<T>.Contains` в том же замере дал ноль байт в обоих случаях: `EqualityComparer<T>.Default` для структуры JIT девиртуализует, и упаковки не происходит. То есть проблема не «структуры всегда медленно сравниваются», а конкретно путь через `Equals(object)` в хеш-таблицах.

Полный вид для структуры:

```csharp
public readonly struct Point : IEquatable<Point>
{
    public int X { get; init; }
    public int Y { get; init; }

    public bool Equals(Point other) => X == other.X && Y == other.Y;
    public override bool Equals(object? obj) => obj is Point p && Equals(p);
    public override int GetHashCode() => HashCode.Combine(X, Y);

    public static bool operator ==(Point a, Point b) => a.Equals(b);
    public static bool operator !=(Point a, Point b) => !a.Equals(b);
}
```

Тут `Equals(object?)` нужен как заглушка для старого кода, а работать будет типизированный.

## record: всё это уже написано

`record` и `record struct` генерируют весь набор сами — `Equals`, `GetHashCode`, `IEquatable<T>`, `==` и `!=`, всё по содержимому:

```csharp
record PointRecord(int X, int Y);

var a = new PointRecord(1, 2);
var b = new PointRecord(1, 2);
a == b;                            // true
a.GetHashCode() == b.GetHashCode(); // true
```

Проверено — работает, и `record struct Equals(T)` не аллоцирует. Это самый весомый практический довод за `record` для типов-значений в домене: ручная реализация занимает 20 строк, в которых легко ошибиться, а сгенерированная всегда согласована. Подробнее о выборе между `class`, `struct` и `record` — в статье `class, struct и record`.

Одна тонкость: у `record` класса сравнение включает **проверку типа**, а не `GetType() == typeof(...)` в наивном виде. Наследник `record`-а не будет равен базовому, даже если поля совпадают, — это правильное поведение, которого в рукописном коде обычно не хватает.

## Когда сравнение по содержимому — ошибка

Не всякий тип должен сравниваться по полям. У сущности с идентификатором равенство определяется идентификатором, а не совпадением всех полей:

```csharp
public sealed class User : IEquatable<User>
{
    public Guid Id { get; }
    public string Name { get; set; } = "";

    // Два пользователя равны, если это один пользователь —
    // даже если имя успели поменять
    public bool Equals(User? other) => other is not null && Id == other.Id;
    public override bool Equals(object? o) => Equals(o as User);
    public override int GetHashCode() => Id.GetHashCode();
}
```

Это ровно тот случай, когда `record` для сущности — плохая идея: он сравнил бы и `Name`, и пользователь после переименования перестал бы быть равен себе прежнему. Правило: **`record` — для значений, ручное равенство по `Id` — для сущностей, ссылочное равенство по умолчанию — для сервисов и всего, у чего нет содержимого**.

## Что стоит ответить на собеседовании

`Equals` виртуален и выбирается по типу объекта, `==` статичен и выбирается компилятором по типу переменной — отсюда классическая разница в поведении при приведении строк к `object`. `GetHashCode` связан с `Equals` односторонним контрактом: равные объекты обязаны давать равный хеш, обратное не требуется, а поля в хеше должны быть неизменяемыми, иначе объект теряется в словаре.

Сильный ответ добавит про структуры: реализация по умолчанию работает через упаковку и, при наличии ссылочных полей, через рефлексию — на .NET 10 это 48–80 байт на сравнение и 72 байта на каждый `Dictionary.TryGetValue`. Поэтому структуре-ключу нужен `IEquatable<T>`. И упомянет, что `record` генерирует весь набор корректно, но подходит именно значениям: для сущности с `Id` равенство по всем полям — ошибка.
