Pattern matching — способ одним выражением проверить форму значения и достать из него части. Начиналось с `is Type x` в C# 7 и за несколько версий выросло в самостоятельный язык образцов, который заменяет цепочки `if` и вызовы `as` с проверкой на `null`. Разбираемся, какие образцы бывают, во что они компилируются и где ими лучше не увлекаться.

## Образец типа: замена as + проверке

Исходная форма, ради которой всё начиналось:

```csharp
// Было
var user = obj as User;
if (user != null && user.IsActive) { }

// Стало
if (obj is User { IsActive: true } user) { }
```

Переменная `user` объявляется прямо в условии и видна дальше в той ветке, где проверка прошла. Компилятор понимает её область видимости точно: в `else` она недоступна, а после `if (obj is not User u) return;` — наоборот, доступна до конца метода.

Отрицание пишется через `is not`, и это читается лучше, чем `!(obj is User)`:

```csharp
if (obj is not User user) return;
// здесь user гарантированно есть
```

## Полный набор образцов

**Константный** — сравнение со значением:

```csharp
if (code is 404) { }
if (name is "admin") { }
if (status is OrderStatus.Paid) { }
```

**Реляционный** (C# 9) — сравнение с порядком:

```csharp
var category = age switch
{
    < 0 => "некорректный",
    < 18 => "несовершеннолетний",
    < 65 => "взрослый",
    _ => "пенсионер"
};
```

**Логический** — `and`, `or`, `not`, комбинируются с любыми другими:

```csharp
if (c is >= 'a' and <= 'z') { }
if (status is OrderStatus.Cancelled or OrderStatus.Refunded) { }
if (obj is not null) { }
```

**Свойственный** — проверка полей и свойств, в том числе вложенных:

```csharp
if (order is { Customer.Country: "RU", Total: > 10_000 })
    ApplyDomesticDiscount(order);
```

Обратите внимание на `Customer.Country` — вложенный доступ прямо в образце (C# 10). Он безопасен: если `Customer` равен `null`, образец просто не совпадёт, NRE не будет. Это одно из лучших применений паттернов — цепочка проверок на `null` схлопывается в одну строку.

**Деконструкции** — для типов с `Deconstruct` (в том числе всех позиционных `record`):

```csharp
record Point(int X, int Y);

static int Quadrant(Point p) => p switch
{
    (> 0, > 0) => 1,
    (< 0, > 0) => 2,
    (< 0, < 0) => 3,
    _ => 4
};
```

**Списочный** (C# 11) — сопоставление с формой коллекции:

```csharp
int[] seq = { 1, 2, 3, 4 };

seq is [1, .., 4]            // true: начинается на 1, кончается на 4
seq is [var first, ..]       // достать первый элемент
seq is []                    // пустая
seq is [_, _]                // ровно два элемента
```

Проверено на .NET 10 — `[1, .., 4]` даёт `true`. Удобно для разбора аргументов командной строки и коротких массивов.

**`var`-образец** — совпадает всегда, нужен чтобы дать имя промежуточному значению:

```csharp
if (GetConfig() is var config && config.Timeout > 0) { }
```

## switch expression

Выражение, а не оператор: возвращает значение, требует исчерпывающего покрытия и не нуждается в `break`.

```csharp
decimal CalculateFee(Payment payment) => payment switch
{
    { Method: PaymentMethod.Card, Amount: > 100_000 } => payment.Amount * 0.01m,
    { Method: PaymentMethod.Card } => payment.Amount * 0.02m,
    { Method: PaymentMethod.Cash } => 0m,
    null => throw new ArgumentNullException(nameof(payment)),
    _ => throw new NotSupportedException($"метод {payment.Method}")
};
```

Три вещи, которые важно понимать.

**Порядок важен.** Ветки проверяются сверху вниз, первая совпавшая выигрывает. Если поменять две первые строки местами, ветка с суммой станет недостижимой — компилятор на это предупредит (CS8510).

**Исчерпывающность проверяется.** Если ни одна ветка не совпала и нет `_`, в рантайме летит `SwitchExpressionException`. Компилятор предупреждает (CS8509), когда видит непокрытые случаи, — но для `enum` он честно считает возможными и значения, которых в перечислении нет, поэтому `_` обычно нужен всё равно.

**`when` добавляет произвольное условие**, когда образцов не хватает:

```csharp
var result = value switch
{
    int n when n == Magic => "магическое",
    int n => $"число {n}",
    _ => "не число"
};
```

## Сколько это стоит

Приятная новость: почти ничего. Замеры на .NET 10:

```
is int i (распаковка)                     0 байт
switch по типу object                     0 байт
деконструкция record в switch             0 байт
switch expression по int                  0 байт
```

Образцы компилируются в обычные проверки типа, сравнения и вызовы `Deconstruct` — никаких обёрток. Распаковка (`is int i` для `object`) тоже бесплатна: упаковка стоила памяти при создании, а чтение значения обратно аллокаций не требует (см. `Упаковка и распаковка`).

Более того, компилятор **оптимизирует** сопоставление: для набора констант он строит переход по таблице или бинарный поиск вместо последовательных сравнений. Поэтому `switch` по строкам с десятком веток быстрее цепочки `if`, а не медленнее.

Единственное, за что можно заплатить, — деконструкция типа, чей `Deconstruct` сам по себе что-то аллоцирует, и `when` с дорогим выражением, вычисляемым для нескольких веток подряд.

## Тонкости про null

Здесь легко ошибиться, и это любят спрашивать:

```csharp
object? x = null;

x is object    // false — образец типа НЕ совпадает с null
x is null      // true
x is not null  // false
```

`is object` не совпадает с `null` — это выделяет его из старого `x != null` и делает `is not null` самой надёжной проверкой: она не зависит от перегрузок `==`, которые пользовательский тип может определить как угодно.

Для структуры проверка на `null` бессмысленна, и компилятор об этом скажет: `point is not null` для не-nullable структуры — всегда `true`.

В `switch` ветка `null` обязана быть явной, `_` её тоже покроет, а вот образец типа — нет:

```csharp
string Describe(object? o) => o switch
{
    null => "ничего",          // без этой ветки null уйдёт в _
    int => "число",
    string => "строка",
    _ => "что-то ещё"
};
```

## Когда паттерны вредят

Механизм затягивает, и есть два типичных перебора.

**Слишком длинное сопоставление вместо полиморфизма.** Если `switch` по типу разросся до десятка веток и при добавлении нового типа его надо править, — это нарушение принципа открытости-закрытости, которое лечится виртуальным методом:

```csharp
// Пахнет: каждый новый тип фигуры требует правки здесь
double Area(Shape s) => s switch
{
    Circle c => Math.PI * c.R * c.R,
    Square sq => sq.Side * sq.Side,
    Rectangle r => r.W * r.H,
    // ...ещё восемь
};
```

Оговорка: если иерархия типов **закрыта** и меняется редко (варианты ответа, состояния конечного автомата), `switch` как раз лучше — вся логика в одном месте, а не размазана по классам. Граница проходит по тому, что меняется чаще: типы или операции над ними.

**Слишком плотный образец.** Вот это формально корректно, но прочесть с первого раза нельзя:

```csharp
if (o is Order { Items: [{ Product.Category: "electronics" }, ..], Customer: { IsVip: true } c }
    && c.Orders is { Count: > 5 })
```

Практическое правило — один образец должен помещаться в строку и читаться вслух. Если не помещается, разложите на две проверки или вынесите в метод с говорящим именем.

## Что стоит ответить на собеседовании

Pattern matching — это проверка формы значения с одновременным извлечением частей: образцы типа, константные, реляционные, логические (`and`/`or`/`not`), свойственные, деконструкции и списочные. `switch expression` возвращает значение, проверяет ветки по порядку сверху вниз и требует исчерпывающего покрытия — иначе `SwitchExpressionException` в рантайме.

Сильный ответ добавит, что всё это чистый синтаксический сахар: образцы компилируются в обычные проверки типа и сравнения, аллокаций нет (проверено на .NET 10 — ноль байт, включая деконструкцию `record`), а для набора констант компилятор строит таблицу переходов. И назовёт границу применимости: `switch` по типу хорош для закрытой иерархии, а для растущей он превращается в место, которое правят при каждом новом типе, — там нужен полиморфизм.
