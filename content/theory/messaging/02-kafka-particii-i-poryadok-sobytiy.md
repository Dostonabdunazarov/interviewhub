Kafka гарантирует порядок только внутри одной партиции. Это короткое правило порождает половину вопросов на собеседовании: как сделать, чтобы события одного заказа шли по порядку, что будет при добавлении партиций, почему lag растёт только на одной из них и можно ли обрабатывать партицию в несколько потоков. Ответы на все эти вопросы начинаются с того, как запись попадает в партицию.

## Как producer выбирает партицию

- **Ключ задан** — партиция вычисляется как хеш ключа по модулю числа партиций. Одинаковый ключ всегда попадает в одну партицию, пока число партиций не меняется.
- **Ключа нет** — клиент распределяет записи сам. Java-клиент с версии 3.3 заполняет батч в одну партицию и потом переключается на другую (KIP-794), чтобы батчи были крупнее.
- **Партиция указана явно** или подключён свой partitioner — полный контроль и вся ответственность.

У .NET есть ловушка. Confluent.Kafka работает поверх librdkafka, а её партиционер по умолчанию — `consistent_random` на CRC32. Java-клиент использует murmur2. Если в один топик пишут и Java-, и .NET-сервисы, один и тот же ключ окажется в разных партициях, и порядок по нему сломается без единой ошибки в логах. Лечится выравниванием алгоритма:

```csharp
var config = new ProducerConfig
{
    BootstrapServers = "kafka:9092",
    Partitioner = Partitioner.Murmur2Random,
    EnableIdempotence = true
};
```

`Murmur2Random` хеширует ключ так же, как Java-клиент, а сообщения без ключа раскладывает случайно.

## Почему нет глобального порядка

Партиции — независимые логи со своими лидерами, часто на разных брокерах. Глобальный порядок потребовал бы одной точки, через которую проходят все записи топика, а это уничтожило бы горизонтальное масштабирование, ради которого партиции существуют. Сообщение, записанное в P1 позже, вполне может быть обработано раньше сообщения из P0: их читают разные consumer'ы с разной скоростью.

Сортировать события разных партиций по timestamp тоже ненадёжно. По умолчанию это `CreateTime`, который ставит producer, а часы разных машин расходятся — почему, разобрано в статье `Почему нельзя верить часам`.

На практике глобальный порядок почти никогда не нужен. Нужен порядок внутри сущности, и сильный ход на собеседовании — переспросить, порядок *чего* требуется.

| Требование | Решение | Цена |
| --- | --- | --- |
| Порядок событий одной сущности | ключ = id сущности | стандартный путь |
| Порядок внутри агрегата | ключ = id агрегата: `accountId`, а не `transactionId` | риск горячих ключей |
| Строгий порядок всего потока | топик с одной партицией | пропускная способность одного consumer'а |
| Порядок между разными ключами | буферизация и сортировка на consumer'е по sequence | задержка, окно ожидания |

## Три условия сохранения порядка

Порядок должен пережить весь путь сообщения, и сломать его может любое звено.

**1. Один ключ для связанных событий.** `OrderCreated`, `OrderPaid`, `OrderShipped` с ключом `orderId` попадают в одну партицию. Ключ должен быть не мельче единицы, внутри которой нужен порядок.

**2. Producer не переставляет записи при ретраях.** Producer держит несколько запросов в полёте. Если батч 1 упал с временной ошибкой, а батч 2 уже записан, ретрай батча 1 окажется после батча 2. Idempotent producer это исключает: брокер проверяет sequence number каждого батча и не примет запись с «дыркой», а клиент переотправит батчи в правильном порядке. Работает это при `max.in.flight.requests.per.connection` не больше 5. Без идемпотентности порядок сохраняется только при одном запросе в полёте. В Java-клиенте идемпотентность включена по умолчанию с Kafka 3.0, в librdkafka — нет, её включают явно.

**3. Consumer обрабатывает записи партиции последовательно.** Если после `Consume` раскидать сообщения по `Task.Run`, Kafka честно отдаст их по порядку, а приложение тут же его потеряет.

## Где порядок теряется незаметно

- **Увеличение числа партиций.** Хеш по модулю меняется, новые события ключа уходят в другую партицию, пока старые ещё не дочитаны.
- **Retry-топик.** Упавшее событие обработается позже следующих за ним — об этом подробно в статье `Обработка ошибок и DLQ`.
- **Несколько producer'ов на один ключ.** Между ними Kafka порядок не определяет: кто первым дошёл до лидера, тот и раньше. Надёжнее один источник событий на сущность — например, outbox её сервиса, публикуемый последовательно.
- **Разные партиционеры** в Java- и .NET-сервисах.

Последний рубеж защиты — версия в самом событии. Даже при всех мерах возможны ручные реплеи и redrive из DLQ, поэтому приёмник применяет только более новое состояние:

```sql
UPDATE orders
SET status = @status, version = @version
WHERE id = @id AND version < @version;
```

Устаревшее событие просто ничего не меняет. Тот же приём делает обработку идемпотентной, о чём — в статье `Идемпотентность`.

## Горячие ключи

Хеширование распределяет ключи равномерно, но не нагрузку. Если 40% трафика даёт один крупный клиент, а ключ — `customerId`, одна партиция перегружена, её consumer загружен на 100%, остальные простаивают. Добавление consumer'ов и партиций не поможет: горячий ключ всё равно попадает в одну партицию.

Симптомы видны в выводе группы — lag сосредоточен в одной партиции:

```bash
kafka-consumer-groups.sh --bootstrap-server kafka:9092 --describe --group billing
```

```text
TOPIC   PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG
orders  0          10500           10520           20
orders  1          8000            52000           44000
orders  2          9900            9930            30
```

Что делать:

- **Уточнить ключ.** Если порядок нужен по заказу, а ключом был `customerId`, переход на `orderId` снимает перекос.
- **Посолить ключ** — `customerId + ":" + (orderId % 8)`: нагрузка клиента делится на 8 партиций, порядок остаётся внутри каждой «соли».
- **Вынести крупного клиента** в отдельный топик со своим пулом consumer'ов.
- **Проверить, что дело в ключах**, а не в лидерах: иногда лидеры партиций скучены на одном брокере, и это лечится переизбранием предпочтительных лидеров.

Низкая кардинальность — та же болезнь в другой форме: `tenantId` из 20 значений на 48 партиций оставит больше половины партиций пустыми.

## Сколько партиций заводить

Число партиций — потолок параллелизма одной consumer group. Ориентир — целевой поток, делённый на пропускную способность одного consumer'а, с запасом на рост на год-два. Удобны числа вроде 12, 24, 48: они делятся на много вариантов числа экземпляров.

«Побольше на всякий случай» не бесплатно: каждая партиция — файлы и дескрипторы на брокерах, память в клиентах, время на выбор лидеров при сбое и на ребалансировку группы. KRaft поднял потолок числа партиций в кластере, но не отменил его.

## Изменение числа партиций

Уменьшить число партиций нельзя — только создать новый топик и перенести данные. Увеличить можно одной командой, и данные при этом не переезжают:

```bash
kafka-topics.sh --bootstrap-server kafka:9092 --alter --topic orders --partitions 24
```

Опасность в другом. Ключ `order-42` жил в партиции 3, а теперь пишется в 17. В партиции 3 ещё лежат его необработанные события, а новые уже могут обработать раньше. Producer'ы узнают о новых партициях при обновлении метаданных, по умолчанию раз в 5 минут, так что какое-то время экземпляры пишут по разным формулам. А у consumer group нет committed offset'а для новых партиций: при `auto.offset.reset=latest` записи, попавшие туда до назначения, будут пропущены.

| Ситуация | Подход |
| --- | --- |
| Ключей нет или порядок не важен | `--alter`, у consumer'ов `auto.offset.reset=earliest` |
| Порядок важен, пауза допустима | остановить producer'ов, дождаться нулевого lag, расширить, запустить |
| Порядок важен, остановка невозможна | новый топик, перекладка, переключение consumer'ов после вычитки старого |
| Обработчик защищён версиями | расширить и положиться на проверку `version` |

Для compacted-топиков и Kafka Streams расширение особенно опасно: состояние и co-partitioning завязаны на число партиций, и там обычно идут через новый топик.

## Параллельная обработка внутри партиции

Когда consumer'ов уже столько же, сколько партиций, параллелизм поднимают внутри consumer'а — но по ключам, а не по сообщениям. Один поток читает и раздаёт записи воркерам по стабильному хешу ключа: один ключ — всегда один воркер, разные ключи обрабатываются параллельно. Канал к воркеру делают ограниченным `Channel<T>`, чтобы получить backpressure.

Вторая половина задачи — offset'ы. Сообщения 10, 11 и 12 ушли разным воркерам, 11 и 12 готовы, 10 ещё в работе. Коммитить 13 нельзя: при падении сообщение 10 потеряется. Коммитят offset первого незавершённого сообщения, а 11 и 12 после рестарта обработаются повторно — значит, обработчик обязан быть идемпотентным. В Java это готовая библиотека Confluent Parallel Consumer, в .NET обычно пишут своё или берут KafkaFlow с распределением воркеров по ключу. `string.GetHashCode()` для выбора воркера между процессами не годится — он рандомизирован, нужен детерминированный хеш.

## Что стоит ответить на собеседовании

Порядок в Kafka есть только внутри партиции, глобального нет и не будет — это цена масштабирования. Связанные события пишут с одним ключом, ключ выбирают по единице, внутри которой нужен порядок. Порядок держится на трёх условиях: один ключ, idempotent producer (иначе ретраи переставят батчи) и последовательная обработка партиции на consumer'е.

Сильный ответ перечислит, где порядок теряется незаметно: увеличение числа партиций, retry-топики, несколько producer'ов на ключ, разные партиционеры в Java и .NET. Добавит, что горячий ключ не лечится добавлением consumer'ов, а только сменой или солением ключа, что партиции нельзя уменьшить, а при увеличении нужен `earliest` и план для порядка, и что последний рубеж — версия события, по которой приёмник отбрасывает устаревшее.
