В RabbitMQ неудачное сообщение можно отклонить, и брокер сам переложит его в dead letter exchange. В Kafka такого нет: сообщение нельзя «вернуть в очередь», можно только не сдвигать offset или переопубликовать его в другой топик. Поэтому повторы и DLQ в Kafka — это архитектура приложения, а не настройка брокера. На собеседовании здесь проверяют три вещи: умеешь ли ты отличить плохое сообщение от сломанной зависимости, не блокируешь ли партицию и что делаешь с порядком.

## Почему одна ошибка останавливает партицию

Consumer читает партицию строго по порядку и коммитит один offset. Если обработчик бросает исключение, а приложение не сдвигает offset — или процесс падает и рестартует, — следующий запуск прочитает то же сообщение снова.

Такое сообщение называют **poison message**: битый JSON, неизвестная версия схемы, значение, на котором обработчик падает с `NullReferenceException`. Повтор ему не поможет никогда. Временная ошибка — таймаут базы, `503` от соседнего сервиса — наоборот, может пройти со второй попытки. Отсюда главное решение — классификация.

| Тип | Примеры | Реакция |
| --- | --- | --- |
| Неисправимая | ошибка десериализации, валидации, нарушение инварианта | сразу в DLT, без повторов |
| Временная | таймаут, `503`, deadlock в базе | повторы с backoff, потом retry-топик |
| Системная | база лежит целиком | остановить или поставить на паузу consumer'а |

Последняя строка — частая ошибка. Если база недоступна, все сообщения падают одинаково, и наивный обработчик за час аварии отправит в DLT весь поток. Признак системного сбоя — ошибки идут подряд по многим сообщениям, а не по одному. Тут нужен circuit breaker, а не dead letter: если доля сообщений, ушедших в DLT за минуту, больше порога, consumer останавливают. Как устроен breaker — в статье `Circuit breaker`.

## Десериализация внутри try

Если десериализатор указан в `ConsumerBuilder`, ошибка формата прилетит как `ConsumeException` ещё до кода обработчика. Надёжнее читать байты и десериализовать самостоятельно — тогда исходное сообщение всегда доступно для отправки в DLT байт в байт.

```csharp
var config = new ConsumerConfig
{
    BootstrapServers = "kafka:9092",
    GroupId = "billing",
    EnableAutoCommit = true,
    EnableAutoOffsetStore = false,
    MaxPollIntervalMs = 300_000
};

using var consumer = new ConsumerBuilder<byte[], byte[]>(config).Build();
consumer.Subscribe("orders");

while (!ct.IsCancellationRequested)
{
    var cr = consumer.Consume(ct);
    try
    {
        var evt = JsonSerializer.Deserialize<OrderEvent>(cr.Message.Value)
            ?? throw new InvalidDataException("Пустое событие");
        await retryPipeline.ExecuteAsync(token => handler.HandleAsync(evt, token), ct);
    }
    catch (Exception ex) when (IsTransient(ex))
    {
        await ForwardAsync(cr, "orders.retry.1m", attempt: 1, ex, ct);
    }
    catch (Exception ex) when (ex is not OperationCanceledException)
    {
        await ForwardAsync(cr, "orders.dlt", attempt: 0, ex, ct);
    }
    consumer.StoreOffset(cr);
}
```

Здесь два уровня повторов. `retryPipeline` — короткие локальные повторы через Polly: три попытки с экспоненциальной задержкой и jitter, в сумме около секунды. Они отсекают большинство мимолётных сбоев без лишней инфраструктуры, но партиция всё это время стоит. Суммарное время попыток должно быть далеко от `max.poll.interval.ms`, иначе consumer выпадет из группы и сообщение обработает другой экземпляр. Как не превратить повторы в retry storm — в статье `Retry, jitter и retry storm`.

Offset сдвигается во всех ветках, но только после того, как `ForwardAsync` дождался подтверждения записи в другой топик. Если DLT недоступен, лучше остановиться, чем сдвинуть offset и потерять сообщение.

## Retry-топики с задержкой

Ждать в основном consumer'е через `Task.Delay` нельзя: 30 секунд ожидания одного сообщения — 30 секунд простоя для всех ключей партиции, а задержка дольше `max.poll.interval.ms` выбьет consumer'а из группы. Долгие повторы выносят в отдельные топики с фиксированной задержкой:

```text
orders ─fail─► orders.retry.10s ─fail─► orders.retry.1m ─fail─► orders.retry.10m ─fail─► orders.dlt
```

Сообщение копируется в следующий топик с исходным ключом и заголовками: номер попытки, исходные топик, партиция и offset, текст ошибки и время, раньше которого его не обрабатывать. Задержка внутри одного топика одинаковая, поэтому сообщения в нём упорядочены по времени готовности: если голова партиции ещё не созрела, остальные тоже нет, и ждать нужно только её.

Consumer retry-топика ждёт через `Pause`, а не блокирует poll-цикл:

```csharp
var cr = consumer.Consume(TimeSpan.FromMilliseconds(100));
if (cr is null)
{
    ResumeDuePartitions(consumer);
    continue;
}

var dueAt = ReadDueAt(cr.Message.Headers);
if (dueAt > DateTimeOffset.UtcNow)
{
    consumer.Pause(new[] { cr.TopicPartition });
    consumer.Seek(cr.TopicPartitionOffset);
    ScheduleResume(cr.TopicPartition, dueAt);
    continue;
}
```

`Consume` продолжают вызывать и во время паузы — так consumer остаётся в группе. `Pause`, `Resume` и `Seek` вызываются из потока poll-цикла: consumer в Confluent.Kafka не потокобезопасен.

Готовой реализации в Confluent.Kafka нет. В Java это `@RetryableTopic` в Spring Kafka, в .NET — middleware KafkaFlow или MassTransit Rider, либо своя схема по образцу выше.

## Dead letter topic

DLT — топик, куда попадают сообщения, которые не удалось обработать после всех попыток или которые заведомо не обработать. Он позволяет не останавливать основной поток и не терять проблемное сообщение.

Что в него класть: исходные ключ и значение байт в байт, не пересериализованные, и заголовки с диагностикой.

```csharp
var headers = new Headers
{
    { "dlt-original-topic", Encoding.UTF8.GetBytes(cr.Topic) },
    { "dlt-original-partition", Encoding.UTF8.GetBytes(cr.Partition.Value.ToString()) },
    { "dlt-original-offset", Encoding.UTF8.GetBytes(cr.Offset.Value.ToString()) },
    { "dlt-exception", Encoding.UTF8.GetBytes(ex.GetType().FullName ?? "unknown") },
    { "dlt-reason", Encoding.UTF8.GetBytes(ex.Message) },
    { "dlt-failed-at", Encoding.UTF8.GetBytes(DateTimeOffset.UtcNow.ToString("O")) }
};

await dltProducer.ProduceAsync("orders.dlt",
    new Message<byte[], byte[]> { Key = cr.Message.Key, Value = cr.Message.Value, Headers = headers },
    ct);
```

Ключ сохраняют исходный, чтобы при переигрывании сообщение попало в ту же партицию.

Жизненный цикл DLT важнее самого топика:

- **алерт** на появление сообщений — DLT, в который никто не смотрит, превращается в тихую потерю данных;
- **инструмент разбора**: просмотр, фильтр по причине, поиск по ключу;
- **redrive** — после исправления бага сообщения переотправляют в исходный топик; обработчик обязан быть идемпотентным, о чём — в статье `Идемпотентность`;
- **retention** у DLT больше, чем у основного топика, чтобы успеть разобраться.

Если сообщение валит процесс целиком — например, OOM на огромном payload'е, — обработчик не успевает его классифицировать. Лечение — ограничение размера до десериализации, а аварийная мера — ручной сдвиг offset'а остановленной группы:

```bash
kafka-consumer-groups.sh --bootstrap-server kafka:9092 --group billing \
  --topic orders:3 --reset-offsets --shift-by 1 --execute
```

## Порядок по ключу

И retry-топик, и DLT нарушают порядок. Пока `OrderCreated` заказа 42 ждёт в retry, `OrderPaid` того же заказа уже обработан из основного топика — и, скорее всего, упал или дал неконсистентное состояние. Варианты по строгости:

| Подход | Порядок | Цена |
| --- | --- | --- |
| Принять нарушение | нет | годится для независимых событий: уведомления, метрики |
| Версии в событиях | восстанавливается на приёмнике | устаревшее отбрасывается, пропущенное нужно дождаться |
| «Парковка» ключа | сохраняется | реестр ключей в ретрае, все следующие события ключа идут следом в retry |
| Блокирующий повтор на месте | сохраняется | партиция стоит, пока сообщение не пройдёт |

Последний вариант — тоже решение. Для операций по счёту, где цена неконсистентности выше цены простоя, осознанно остановить партицию и позвать человека бывает правильнее, чем обработать события не по порядку. Подробнее о порядке — в статье `Партиции и порядок событий`.

## Чем отличается RabbitMQ

| | Kafka | RabbitMQ |
| --- | --- | --- |
| Кто перекладывает в DLQ | приложение | брокер: `nack` без requeue, TTL, переполнение очереди |
| Лимит попыток | считает приложение в заголовках | `x-delivery-limit` в quorum-очередях |
| Задержка повтора | retry-топики и `Pause` | TTL плюс dead letter exchange |
| Блокировка | одно сообщение держит партицию | неудачное сообщение не мешает остальным |

В Kafka Connect DLQ есть из коробки (`errors.deadletterqueue.topic.name`), а share groups из Kafka 4.x ведут счётчик попыток доставки на каждую запись и после лимита перестают её выдавать — это шаг Kafka к очередной семантике, но для обычных consumer group всё по-прежнему строится в приложении.

Профилактика дешевле лечения: Schema Registry с проверкой совместимости, контрактные тесты, валидация на входе.

## Что стоит ответить на собеседовании

Встроенного retry для consumer'а в Kafka нет: сообщение нельзя вернуть в очередь, можно только не сдвигать offset или переопубликовать. Поэтому сначала классифицируют ошибку: неисправимая сразу идёт в DLT, временная получает несколько быстрых локальных повторов, потом retry-топик с задержкой, а системная — авария базы — останавливает consumer'а, а не заливает DLT.

Сильный ответ покажет детали: десериализация внутри try на `byte[]`, offset сдвигается только после подтверждённой записи в DLT, задержка в retry-топике делается через `Pause` и `Seek` без блокировки poll-цикла и без выхода за `max.poll.interval.ms`, в DLT кладут исходные байты, ключ и диагностику в заголовках, на DLT есть алерт и процесс redrive. И обязательно скажет, что retry и DLT ломают порядок по ключу, предложив версии, парковку ключа или осознанную остановку партиции.
