Принципы ООП обычно спрашивают первыми, и обычно на них отвечают определениями из учебника: «инкапсуляция — это сокрытие». Такой ответ засчитывают, но не выделяют. Интервьюер ждёт другого — понимания, от какой проблемы защищает каждый принцип и чем он оборачивается, если применить его не к месту. К трём принципам из заголовка часто добавляют четвёртый — абстракцию, и её тоже стоит уметь отличить от инкапсуляции.

## Инкапсуляция — это инварианты, а не private-поля

Формальное определение — «скрыть данные и дать доступ через методы». Но класс, у которого каждое поле закрыто и открыто через `{ get; set; }`, формально инкапсулирован, а по сути — нет:

```csharp
public class Order
{
    public OrderStatus Status { get; set; }
    public List<OrderLine> Lines { get; set; } = [];
    public decimal Total { get; set; }
}
```

Любой код может добавить строку в оплаченный заказ, забыть пересчитать `Total` или подменить список целиком. Правила заказа живут не в заказе, а размазаны по сервисам, которые его меняют, — это называют анемичной моделью.

Настоящая инкапсуляция — гарантия, что объект **нельзя перевести в некорректное состояние** снаружи:

```csharp
public sealed class Order
{
    private readonly List<OrderLine> _lines = [];

    public OrderStatus Status { get; private set; } = OrderStatus.Draft;
    public IReadOnlyList<OrderLine> Lines => _lines.AsReadOnly();
    public decimal Total => _lines.Sum(l => l.Price * l.Quantity);

    public void AddLine(string sku, decimal price, int quantity)
    {
        if (Status != OrderStatus.Draft)
            throw new InvalidOperationException("Оплаченный заказ менять нельзя.");
        if (quantity <= 0)
            throw new ArgumentOutOfRangeException(nameof(quantity));

        _lines.Add(new OrderLine(sku, price, quantity));
    }

    public void MarkPaid()
    {
        if (_lines.Count == 0)
            throw new InvalidOperationException("Пустой заказ нельзя оплатить.");
        Status = OrderStatus.Paid;
    }
}
```

Здесь важны три детали. Сеттер `Status` закрыт, и статус меняется только через `MarkPaid`, где проверено правило. `Total` вычисляется, а не хранится, — рассинхронизироваться нечему. Наружу отдаётся `AsReadOnly()`, а не сам список: если вернуть `_lines` как `IReadOnlyList<OrderLine>`, вызывающий код может привести его обратно к `List<OrderLine>` и изменить.

Отсюда практический вопрос на ревью: «какие правила этот класс гарантирует сам?». Если ответ «никаких, их проверяет сервис», инкапсуляции нет, сколько бы `private` ни стояло.

## Абстракция — «что», а не «как»

Абстракцию часто смешивают с инкапсуляцией, но они отвечают на разные вопросы. Инкапсуляция — как защищено устройство объекта. Абстракция — какой контракт видит клиент и какие детали ему не нужны.

Хрестоматийный пример из BCL — `Stream`. Код, принимающий `Stream`, читает байты и не знает, файл это, сокет или память. В C# абстракцию выражают через `interface` и `abstract class`; разница между ними в том, что интерфейс — контракт без состояния, которых класс может реализовать сколько угодно, а абстрактный класс — частичная реализация с полями и конструктором, и базовый класс у типа один.

## Наследование — самая сильная связь

Наследник видит `protected`-члены базового класса и зависит не только от его контракта, но и от устройства: какой метод вызывает какой, в каком порядке. Это называют проблемой **хрупкого базового класса**:

```csharp
public class Notifier
{
    public virtual void Send(string to, string text) => Console.WriteLine($"{to}: {text}");

    public virtual void SendMany(IEnumerable<string> recipients, string text)
    {
        foreach (var to in recipients)
            Send(to, text);
    }
}

public class CountingNotifier : Notifier
{
    public int Sent { get; private set; }

    public override void Send(string to, string text)
    {
        Sent++;
        base.Send(to, text);
    }

    public override void SendMany(IEnumerable<string> recipients, string text)
    {
        var list = recipients.ToList();
        Sent += list.Count;
        base.SendMany(list, text);
    }
}
```

Отправка трёх писем через `SendMany` даст `Sent == 6`: базовый `SendMany` вызывает виртуальный `Send`, и счётчик срабатывает дважды. Чтобы написать наследника правильно, нужно знать внутреннюю реализацию базы. А если автор базового класса перепишет `SendMany` на пакетный API без вызова `Send`, счётчик молча начнёт считать иначе — хотя контракт не менялся.

Композиция этой проблемы не имеет: обёртка видит только публичный контракт и ничего не знает о том, как реализация вызывает сама себя. Подробно этот приём разобран в статье `Decorator vs наследование`.

Ещё одна ловушка наследования — **виртуальный вызов в конструкторе**. Конструктор базы, вызвавший `virtual`-метод, попадёт в `override` наследника до того, как отработал конструктор наследника, и поля наследника, присваиваемые в его конструкторе, будут ещё не заполнены.

Отсюда два правила. Наследоваться — когда есть настоящее отношение «является» и наследник подставляется вместо базы без сюрпризов (это принцип Лисков, ему посвящена статья `Нарушение LSP на реальном коде`). И объявлять классы `sealed` по умолчанию: открытый для наследования класс — это обещание поддерживать его внутренние вызовы как контракт. Бонусом JIT девиртуализирует вызовы методов `sealed`-класса.

## Полиморфизм: три вида

На вопрос «что такое полиморфизм» почти всегда отвечают про `virtual`/`override`. Это один вид из трёх.

**Полиморфизм подтипов** — выбор реализации по фактическому типу объекта во время выполнения, через таблицу виртуальных методов. Работает для `virtual`/`override` и интерфейсов:

```csharp
public abstract class Shape
{
    public abstract double Area();
}

public sealed class Circle(double r) : Shape
{
    public override double Area() => Math.PI * r * r;
}

public sealed class Rect(double w, double h) : Shape
{
    public override double Area() => w * h;
}

public static class Shapes
{
    public static double TotalArea(IEnumerable<Shape> shapes) => shapes.Sum(s => s.Area());
}
```

`TotalArea` не знает, какие фигуры существуют, и не меняется при добавлении новой.

**Параметрический полиморфизм** — обобщения. `List<T>` один и тот же код для любого `T`. Ограничения вида `where T : IComparable<T>` дают полиморфизм без виртуальных вызовов и без упаковки значимых типов. Отдельная тема — когда `IEnumerable<string>` можно передать вместо `IEnumerable<object>`; это разобрано в статье `Ковариантность и контравариантность`.

**Ad hoc-полиморфизм** — перегрузка методов и операторов. Какая перегрузка вызовется, решает компилятор по статическим типам аргументов.

Различие между выбором «во время выполнения» и «во время компиляции» хорошо видно на `new` против `override`:

```csharp
public class Base
{
    public virtual string Who() => "Base";
    public string Hello() => "Base.Hello";
}

public class Derived : Base
{
    public override string Who() => "Derived";
    public new string Hello() => "Derived.Hello";
}

public static class Demo
{
    public static void Run()
    {
        Base b = new Derived();
        Console.WriteLine(b.Who());
        Console.WriteLine(b.Hello());
    }
}
```

Напечатается `Derived` и `Base.Hello`. `override` занимает тот же слот в таблице виртуальных методов, и вызов через ссылку на базу находит новую реализацию. `new` создаёт новый член, который виден только через ссылку типа `Derived`, — поведение зависит от того, через какую переменную вызвали, и это источник багов.

## Полиморфизм или switch по типу

Альтернатива виртуальному методу — pattern matching по закрытому набору типов:

```csharp
public static class Geometry
{
    public static double Area(Shape shape) => shape switch
    {
        Circle c => c.Area(),
        Rect r => r.Area(),
        _ => throw new ArgumentException($"Неизвестная фигура {shape.GetType().Name}")
    };
}
```

Это не анти-паттерн, а другой компромисс. Виртуальный метод делает дешёвым добавление нового **типа**: новый класс, ни одной правки в старом коде. `switch` делает дешёвым добавление новой **операции**: ещё одна функция, иерархия не меняется. Если иерархия стабильна, а операций над ней много (расчёт, сериализация, отображение), `switch` по типу честнее, чем десяток виртуальных методов в базовом классе. Подробнее о выборе — в статье `Strategy vs switch`.

## Что стоит ответить на собеседовании

Инкапсуляция — не `private`-поля, а гарантия инвариантов: объект нельзя перевести в некорректное состояние снаружи; класс со свойствами `{ get; set; }` на каждом поле инкапсуляции не даёт. Абстракция — контракт «что делает», инкапсуляция — защита «как устроено». Наследование — самая сильная связь между типами: наследник зависит от внутренних вызовов базы, отсюда хрупкий базовый класс, совет предпочитать композицию и `sealed` по умолчанию. Полиморфизм бывает трёх видов: подтипов (`virtual`, интерфейсы — выбор во время выполнения), параметрический (generics) и ad hoc (перегрузка — выбор при компиляции).

Сильный ответ покажет разницу `override` и `new` на примере, назовёт ловушку виртуального вызова в конструкторе и объяснит, когда `switch` по закрытой иерархии лучше виртуального метода.
