Вопрос «где SOLID вредит» задают senior-кандидатам почти всегда, и ответ «нигде, это лучшие практики» — плохой. SOLID помогает там, где есть реальная изменчивость: несколько реализаций, разные причины изменений, граница с инфраструктурой. Применённый превентивно — к коду, который не меняется и у которого одна реализация, — он даёт не гибкость, а косвенность: чтобы понять три строки логики, читатель прыгает по пяти файлам.

## Как выглядит переусердствование

Задача — проверить заказ перед оформлением: не пустой, сумма положительная, адрес доставки указан. Вот как это выглядит в проекте, где SOLID превратился в ритуал:

```csharp
public interface IOrderValidationRule
{
    ValidationResult Validate(OrderDraft order);
}

public interface IOrderValidationRuleProvider
{
    IEnumerable<IOrderValidationRule> GetRules();
}

public interface IOrderValidator
{
    ValidationResult Validate(OrderDraft order);
}

public interface IOrderValidatorFactory
{
    IOrderValidator Create();
}

public sealed class NotEmptyRule : IOrderValidationRule
{
    public ValidationResult Validate(OrderDraft order) =>
        order.Lines.Count > 0 ? ValidationResult.Ok : ValidationResult.Fail("empty");
}
```

Плюс ещё два класса правил, провайдер, валидатор, фабрика, шесть регистраций в DI и по моку на каждый интерфейс в тестах. Формально соблюдено всё: каждое правило — отдельная ответственность, новое правило добавляется без правки валидатора, все зависимости через абстракции. Фактически за два года правил так и осталось три, а их полный список нельзя увидеть, не открыв семь файлов.

То же самое без церемоний:

```csharp
public static class OrderDraftValidation
{
    public static IReadOnlyList<string> Validate(OrderDraft order)
    {
        var errors = new List<string>();
        if (order.Lines.Count == 0) errors.Add("empty");
        if (order.Lines.Sum(l => l.Price * l.Quantity) <= 0) errors.Add("zero_total");
        if (string.IsNullOrWhiteSpace(order.ShippingAddress)) errors.Add("no_address");
        return errors;
    }
}
```

Все правила на одном экране, тест — таблица входов и ожидаемых ошибок, никаких моков. Если правил станет тридцать и их начнут включать по конфигурации, тогда и стоит выделять `IOrderValidationRule` — по факту, а не на всякий случай.

## Принцип за принципом: где окупается, где нет

| Принцип | Окупается | Превращается в церемонию |
| --- | --- | --- |
| SRP | класс правят разные люди по разным причинам | «один метод — один класс», десяток классов по 15 строк, которые всегда меняются вместе |
| OCP | плагины, провайдеры оплаты, правила, которые добавляются регулярно | точка расширения «на будущее», где за годы не появилось второго варианта |
| LSP | любая иерархия и любой интерфейс с несколькими реализациями | — нарушение LSP всегда баг, «лишнего» соблюдения не бывает |
| ISP | клиенты используют разные части большого интерфейса | интерфейс на каждый метод, класс реализует восемь мини-интерфейсов |
| DIP | граница с БД, сетью, брокером, временем, сторонними SDK | `IOrderMapper` с одной реализацией, которую никто не подменяет |

LSP выделяется: у него нет цены, потому что он не про добавление абстракций, а про честность тех, что уже есть. Остальные четыре добавляют типы и косвенность, и их стоимость нужно сравнивать с выгодой.

## SRP — не «маленькие классы»

Самое частое искажение — читать SRP как требование дробить. Мерило — причина изменения, а не размер. Класс на 300 строк, который целиком описывает расчёт тарифа и меняется только по запросу тарифной команды, — одна ответственность. Пять классов по 60 строк, каждый из которых приходится открывать при любой правке тарифа, — одна ответственность, размазанная по пяти местам. Связность (cohesion) важнее количества файлов: то, что меняется вместе, должно лежать вместе.

## DIP — не «интерфейс на каждый класс»

Принцип требует, чтобы политика не зависела от деталей. Он не требует интерфейса для каждого сервиса. Внедрение конкретного класса через конструктор — тоже внедрение зависимости, и для чистой логики этого достаточно:

```csharp
public sealed class DiscountPolicy
{
    public decimal Apply(decimal subtotal, CustomerTier tier) => tier switch
    {
        CustomerTier.Gold => subtotal * 0.9m,
        _ => subtotal
    };
}

public interface IExchangeRates
{
    Task<decimal> GetRateAsync(string from, string to, CancellationToken ct);
}

public sealed class Checkout(DiscountPolicy discounts, IExchangeRates rates, TimeProvider time)
{
    public async Task<decimal> TotalAsync(decimal subtotal, CustomerTier tier, string currency, CancellationToken ct)
    {
        var rate = await rates.GetRateAsync("RUB", currency, ct);
        return Math.Round(discounts.Apply(subtotal, tier) * rate, 2);
    }
}
```

`DiscountPolicy` — конкретный класс: быстрый, детерминированный, в тестах создаётся настоящим. `IExchangeRates` — интерфейс, потому что за ним сеть. `TimeProvider` уже абстракция из BCL, свой `IClock` писать не нужно. Интерфейсов ровно столько, сколько настоящих границ.

Если зависимость — одна функция, интерфейс тоже не обязателен: `Func<string, string, CancellationToken, Task<decimal>>` или делегат с осмысленным именем выражают её проще. Про стоимость и особенности делегатов — в статье `Делегаты и события`.

## OCP и YAGNI

Открытость для расширения требует угадать, **где** будет расширение. Угадывают плохо: точку расширения закладывают по оси, которая никогда не меняется, а реальные изменения приходят с другой стороны и ломают выстроенную абстракцию. Отсюда прагматичное правило: первый вариант пишется прямо, второй — замечается, на третьем выделяется абстракция, когда уже видно, что у вариантов действительно общее.

Стоимость отложенного решения в .NET-проекте мала. Выделить интерфейс из класса, заменить тип параметра в конструкторе и строку регистрации — рефакторинг на минуты с помощью IDE. Поддерживать лишнюю абстракцию годами дороже. Исключение — публичные API библиотек и межсервисные контракты: там изменение стоит дорого, и думать заранее оправдано.

## Тесты, которые проверяют моки

Отдельный вред — тесты, ради которых и создавались интерфейсы:

```csharp
public sealed class OrderServiceTests
{
    [Fact]
    public void Calls_validator_then_repository()
    {
        var validator = new SpyValidator();
        var repository = new SpyRepository();
        var service = new OrderService(validator, repository);

        service.Place(new OrderDraft([], "Москва"));

        Assert.True(validator.Called);
        Assert.True(repository.Saved);
    }
}
```

Тест проверяет, что один метод вызвал другой, — то есть повторяет реализацию. При любом рефакторинге он ломается, а настоящую ошибку — неправильное правило валидации или неверный SQL — не ловит. Логику лучше тестировать на настоящих объектах, границы с внешним миром — фейками (in-memory реализациями) и интеграционными тестами с настоящей базой.

## Признаки, что SOLID применён без пользы

- интерфейс с одной реализацией, который лежит рядом с ней, повторяет её методы и никогда не подменяется;
- переход «к реализации» нужен на каждом шаге, а логика размазана по классам по 10 строк;
- добавление одного поля требует правки DTO, маппера, интерфейса, реализации, валидатора и фабрики;
- классы названы по паттернам (`Manager`, `Provider`, `Factory`), а не по смыслу предметной области;
- на вопрос «какое изменение станет проще благодаря этой абстракции?» нет конкретного ответа.

Последний пункт — самый полезный инструмент на ревью: спросить про конкретный сценарий изменения. Если его нет, абстракция может подождать. Как распознавать преждевременные абстракции вообще, а не только связанные с SOLID, — тема раздела «Архитектура приложения».

## Что стоит ответить на собеседовании

SOLID окупается на реальных швах: несколько реализаций, граница с базой, сетью и временем, код, который меняют разные люди по разным причинам. Применённый превентивно, он даёт интерфейс на каждый класс, косвенность вместо гибкости и тесты, проверяющие вызовы моков. SRP — про причины изменений, а не про размер класса; DIP — не «интерфейс на всё»: конкретный класс через конструктор тоже инверсия для чистой логики, а для одной функции хватит делегата. LSP — исключение: его нарушение всегда баг.

Сильный ответ приведёт пример из своего опыта, назовёт правило трёх и аргумент о стоимости: ввести абстракцию позже — минуты, поддерживать лишнюю — годы.
