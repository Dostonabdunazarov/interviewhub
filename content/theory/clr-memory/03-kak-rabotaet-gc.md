Сборщик мусора освобождает память объектов, до которых больше нельзя добраться из работающей программы. Ключевое слово — «нельзя добраться»: GC не считает ссылки и не знает, «нужен» ли объект. Он строит граф достижимости от корней и всё, что в него не попало, считает мусором.

## Три фазы

**Пометка (mark).** Сборщик берёт набор корней и обходит граф ссылок, помечая каждый достижимый объект. Корни — это то, что заведомо живо: локальные переменные и аргументы в кадрах стека всех потоков, регистры процессора, статические поля, закреплённые дескрипторы (GC handles) и очередь финализации. Подробнее — в статье `GC Root и WeakReference`.

**Очистка (sweep).** Всё непомеченное объявляется свободным. Обратите внимание на асимметрию: работа сборщика пропорциональна количеству **живых** объектов, а не мусора. Куча, где почти всё умерло, собирается быстро — это фундамент, на котором стоит вся схема поколений.

**Уплотнение (compact).** Выжившие объекты сдвигаются к началу, чтобы свободная память шла одним непрерывным куском, а ссылки на перемещённые объекты исправляются. Благодаря этому выделение новой памяти — просто сдвиг указателя, а куча не фрагментируется.

Уплотнение происходит не всегда: для большой кучи объектов (LOH) оно по умолчанию отключено, потому что копировать мегабайтные массивы дорого. Отсюда фрагментация, о которой — в статье `LOH и фрагментация`.

## Пауза и её цена

Чтобы обойти граф и подвинуть объекты, сборщику нужно, чтобы граф не менялся. Поэтому управляемые потоки на время работы GC **останавливаются** — это и есть «stop the world».

Останавливаются они не мгновенно, а в **безопасных точках** (safe points), где JIT знает расположение всех ссылок: вызовы методов, переходы в циклах. Именно поэтому длинный цикл без вызовов может ненадолго задержать сборку.

Замер цены на .NET 10, Workstation GC, почти пустая куча:

```
100 x GC.Collect(0):   2,4 мс   (0,024 мс на сборку)
100 x GC.Collect(2):  11,5 мс   (0,115 мс на сборку)
```

Полная сборка вышла примерно в пять раз дороже сборки молодого поколения — и это на практически пустой куче. В реальном сервисе с гигабайтами живых объектов разрыв кратно больше: Gen 0 остаётся долями миллисекунды, а полная сборка доходит до сотен миллисекунд. Отсюда главная идея настройки: **полных сборок должно быть как можно меньше**.

## Workstation и Server GC

Два режима, и выбор между ними — самая действенная настройка GC.

**Workstation GC** — одна куча, сборка в основном на том потоке, который запросил память. Оптимизирован под короткие паузы и малый расход памяти. По умолчанию в консольных и десктопных приложениях.

**Server GC** — **отдельная куча и отдельный поток сборщика на каждое ядро**. Сборка идёт параллельно, пропускная способность выше в разы, но памяти расходуется больше (каждая куча имеет свой бюджет), а отдельная пауза может быть длиннее. По умолчанию в ASP.NET Core.

```xml
<PropertyGroup>
  <ServerGarbageCollection>true</ServerGarbageCollection>
  <ConcurrentGarbageCollection>true</ConcurrentGarbageCollection>
</PropertyGroup>
```

Проверить текущий режим можно из кода — `GCSettings.IsServerGC`; в моём консольном замере он ожидаемо `False`.

Важная практическая деталь для контейнеров: Server GC создаёт кучи по числу **доступных** ядер, и в контейнере с лимитом CPU это может оказаться число ядер хоста, если лимиты не выставлены корректно. Результат — десятки куч и неожиданный расход памяти в маленьком поде. Начиная с .NET Core 3.0 рантайм учитывает cgroup-лимиты, но проверять `Environment.ProcessorCount` внутри контейнера всё равно стоит.

## Фоновая сборка

Полная сборка (Gen 2) может идти **параллельно с работой приложения** — это background GC, включённый по умолчанию. Большая часть работы делается без остановки потоков, а короткие паузы нужны лишь в начале и в конце.

Есть и режимы задержки для особых случаев:

```csharp
GCSettings.LatencyMode = GCLatencyMode.SustainedLowLatency;
```

А для участков, где пауза недопустима совсем, — попытка договориться заранее:

```csharp
if (GC.TryStartNoGCRegion(totalSize: 100_000_000))
{
    try { /* критичный участок */ }
    finally { GC.EndNoGCRegion(); }
}
```

Рантайм резервирует память заранее и обещает не собирать, пока она не кончится. Инструмент для торговых систем и обработки реального времени, а не для обычного веб-сервиса.

## Почему GC.Collect() вызывать не надо

Соблазн «подчистить память вручную» возникает регулярно, и почти всегда это ухудшение:

**Сборщик лучше знает момент.** Он настраивает пороги по наблюдаемому поведению приложения. Ручной вызов сбивает эту статистику.

**Вы форсируете полную сборку** — самую дорогую, останавливая все потоки.

**Вы состариваете мусор.** Это неочевидный и самый вредный эффект: объекты, пережившие вызванную вами сборку, переезжают в старшее поколение, где собираются реже. То есть попытка освободить память делает так, что мусор живёт **дольше**. Механика — в статье `Поколения Gen 0–2`.

Оправданных случаев ровно два: замеры в бенчмарках (зафиксировать состояние до измерения) и точка, где заведомо умер большой объём долгоживущих данных — например, выгрузили из памяти кэш на гигабайт. Во втором случае осмысленна и форма с уплотнением LOH:

```csharp
GCSettings.LargeObjectHeapCompactionMode = GCLargeObjectHeapCompactionMode.CompactOnce;
GC.Collect();
```

Во всех остальных ситуациях правильная реакция на «много памяти» — не звать сборщик, а меньше аллоцировать (см. `Снижение аллокаций`).

## Что смотреть при проблемах

Счётчики, доступные прямо из кода:

```csharp
GC.CollectionCount(0);            // сколько было сборок каждого поколения
GC.GetTotalMemory(forceFullCollection: false);
GC.GetTotalAllocatedBytes();      // сколько всего выделено за жизнь процесса
var info = GC.GetGCMemoryInfo();  // размер кучи, поколение последней сборки, паузы
```

Диагностический признак проблемы — не размер кучи сам по себе, а **соотношение сборок**. Здоровая картина: Gen 0 много, Gen 1 заметно меньше, Gen 2 единицы. Если счётчик Gen 2 растёт сопоставимо с Gen 0, значит, объекты массово доживают до старшего поколения — это либо утечка, либо слишком большие короткоживущие объекты.

Инструменты: `dotnet-counters` для наблюдения в реальном времени, `dotnet-gcdump` для снимка кучи, `dotnet-trace` для детального разбора пауз.

## Что стоит ответить на собеседовании

GC работает по схеме mark-sweep-compact: помечает достижимые от корней объекты, освобождает остальное и уплотняет выживших, исправляя ссылки. Корни — стеки потоков, статические поля, регистры и дескрипторы. Работа пропорциональна количеству живых объектов, а не мусора, поэтому куча, где почти всё умерло, собирается дёшево.

Сильный ответ добавит, что на время сборки управляемые потоки останавливаются в безопасных точках, что Server GC даёт кучу и поток сборщика на ядро ради пропускной способности (и по умолчанию включён в ASP.NET Core), а полная сборка на порядок дороже молодой — на .NET 10 это 0,115 мс против 0,024 мс даже на пустой куче. И объяснит, почему `GC.Collect()` вреден: он форсирует самую дорогую сборку и **состаривает** переживший её мусор, отправляя его в поколение, которое собирают реже.
