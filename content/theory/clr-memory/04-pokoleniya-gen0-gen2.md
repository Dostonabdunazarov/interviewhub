Деление кучи на поколения — главная оптимизация сборщика мусора, и вся она держится на одном наблюдении о том, как программы используют память. Понимание этой схемы объясняет и почему короткоживущие объекты почти бесплатны, и почему `GC.Collect()` делает хуже.

## Гипотеза о поколениях

Два эмпирических факта, верных почти для любой программы:

1. **Большинство объектов умирает молодыми.** Промежуточные результаты, аргументы, локальные списки, DTO одного запроса — всё это живёт доли миллисекунды.
2. **Чем дольше объект прожил, тем вероятнее проживёт ещё.** Кэши, конфигурация, синглтоны, пул соединений живут столько же, сколько процесс.

Отсюда вывод: проверять всю кучу целиком — расточительно. Гораздо выгоднее часто проверять молодых, где почти все мертвы, и редко — старых, где почти все живы.

Куча делится на три поколения:

- **Gen 0** — только что созданные объекты. Маленькое (сотни килобайт — единицы мегабайт), собирается часто.
- **Gen 1** — пережившие одну сборку. Буфер между молодыми и старыми.
- **Gen 2** — долгожители. Сюда же попадает всё крупное. Собирается редко, полная сборка — самая дорогая.

`GC.MaxGeneration` возвращает `2` — больше поколений в .NET нет.

## Как объект стареет

Объект **переходит в следующее поколение, только если переживёт сборку своего**. Проверено на .NET 10:

```csharp
var obj = new byte[100];
GC.GetGeneration(obj);   // 0 — только что создан

GC.Collect(0);
GC.GetGeneration(obj);   // 1 — пережил сборку Gen 0

GC.Collect(1);
GC.GetGeneration(obj);   // 2 — пережил сборку Gen 1

GC.Collect(2);
GC.GetGeneration(obj);   // 2 — дальше некуда
```

Важно, что сборка поколения **включает все младшие**: Gen 1 собирает Gen 0 и Gen 1, Gen 2 — всё. Обратное неверно, и это ключ ко всей схеме: сборка Gen 0 **не смотрит** на Gen 1 и Gen 2, поэтому она дешёвая независимо от того, сколько памяти занимает приложение.

Сборка Gen 0 запускается, когда исчерпан бюджет поколения — не по таймеру и не по общему объёму кучи. Бюджет рантайм подбирает сам, ориентируясь на размер кэша процессора и на то, сколько объектов обычно выживает.

Цена разницы видна в замере даже на пустой куче:

```
100 x GC.Collect(0):   2,4 мс
100 x GC.Collect(2):  11,5 мс
```

В реальном приложении с большой живой кучей разрыв на порядки: Gen 0 остаётся в долях миллисекунды, а Gen 2 растёт вместе с объёмом живых данных.

## Барьер записи и карточная таблица

Возникает законный вопрос: если сборка Gen 0 не смотрит на Gen 2, как она узнает, что старый объект ссылается на молодой? Такая ссылка делает молодой объект живым, но корней в стеке у него нет.

```csharp
static List<Order> cache = new();   // объект в Gen 2

void Handle()
{
    var order = new Order();        // объект в Gen 0
    cache.Add(order);               // ссылка из Gen 2 в Gen 0
}
```

Решение — **барьер записи** (write barrier): при записи ссылки в поле объекта JIT вставляет несколько дополнительных инструкций, помечающих соответствующий участок памяти в **карточной таблице** (card table) как «здесь могла появиться ссылка на молодого». При сборке Gen 0 сборщик просматривает только помеченные участки старых поколений, а не всю старую кучу.

Из этого следуют две практические вещи. Во-первых, запись ссылочного поля объективно дороже записи `int` — за неё платят барьером. Во-вторых, **массив структур без ссылок не требует барьеров вовсе**, что добавляет аргумент к совету из статьи `Стек и куча` про массивы значимых типов в горячем коде.

## Почему GC.Collect() состаривает мусор

Теперь механика вреда, упомянутого в статье `Как работает GC`, становится видна:

```csharp
var temp = new byte[1000];   // Gen 0, умрёт через миллисекунду
GC.Collect();                // но сборка случилась ПРЯМО СЕЙЧАС
// temp ещё достижим → переживает сборку → уезжает в Gen 1
```

Объект, который спокойно умер бы в Gen 0 и обошёлся почти бесплатно, теперь в Gen 1, а при повторе — в Gen 2, где его соберут нескоро. Ручная сборка не ускоряет освобождение памяти, а **замедляет** его для всего, что в этот момент ещё живо.

Тот же эффект возникает и без `GC.Collect()` — если объект живёт достаточно долго, чтобы застать сборку. Отсюда классическая проблема сервисов: объект, который должен был умереть в Gen 0, доживает до Gen 2, потому что его держит что-то долгоживущее.

## Промежуточное поколение долгоживущих объектов

Частный случай, который стоит знать, потому что он ломает интуицию: в веб-сервисе объект запроса живёт «недолго» по меркам человека, но под нагрузкой сборки Gen 0 случаются **чаще**, чем обрабатывается один запрос. В результате объекты одного запроса переживают одну-две сборки и уезжают в Gen 2.

Картину видно по счётчикам: `GC.CollectionCount(2)` растёт вместе с нагрузкой. Лечение — не настройка GC, а сокращение объёма и времени жизни аллокаций на путь запроса: пулы буферов, `Span<T>` вместо подстрок, отказ от лишних промежуточных коллекций. Всё это — тема статьи `Снижение аллокаций`.

## Отдельно: большие объекты

Объект от **85 000 байт** попадает не в Gen 0, а сразу в **Gen 2** — на большую кучу объектов. Проверено точно на границе:

```
массив 84 000 байт: Gen 0
массив 85 000 байт: Gen 2
массив 90 000 байт: Gen 2
массив 1 000 000 байт: Gen 2
```

То есть чуть более крупный буфер попадает в поколение, которое собирается на порядки реже, и освобождается сильно позже. Подробности и что с этим делать — в статье `LOH и фрагментация`.

## Что смотреть в диагностике

Здоровое соотношение — много сборок Gen 0, заметно меньше Gen 1, единицы Gen 2:

```csharp
GC.CollectionCount(0);   // должно быть много
GC.CollectionCount(1);   // меньше
GC.CollectionCount(2);   // мало и растёт медленно
```

Если Gen 2 растёт сопоставимо с Gen 0 — объекты массово доживают до старости. Причины по частоте: утечка (см. `Утечки памяти в managed-коде`), большие объекты, слишком долгая жизнь объектов запроса.

В моём тестовом прогоне счётчики оказались `Gen0=34, Gen1=30, Gen2=29` — картина нездоровая ровно потому, что замер сам вызывал `GC.Collect()` принудительно. Ровно тот случай, когда ручные сборки превращают все поколения в одно.

## Что стоит ответить на собеседовании

Куча делится на три поколения по гипотезе: большинство объектов умирает молодыми, а долгоживущие живут дальше. Gen 0 маленький и собирается часто, Gen 2 — редко. Объект переходит в следующее поколение, только пережив сборку своего; сборка старшего поколения включает младшие, а младшего — не затрагивает старшие, поэтому Gen 0 дёшев независимо от общего размера кучи.

Сильный ответ объяснит, как сборка Gen 0 узнаёт про ссылки из старых объектов: барьер записи помечает участки в карточной таблице, и сборщик просматривает только их — платой за это является чуть более дорогая запись ссылочных полей. И добавит про состаривание: объект, переживший лишнюю сборку, уезжает в старшее поколение, поэтому `GC.Collect()` продлевает жизнь мусору, а объекты веб-запроса под нагрузкой нередко доживают до Gen 2 просто потому, что сборки Gen 0 случаются чаще, чем завершается запрос.
