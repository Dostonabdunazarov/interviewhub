Эта статья собирает воедино то, что разбиралось в разделе по частям: аллокация сама по себе дёшева, дорога **последующая сборка**. Снижение аллокаций — это не микрооптимизация ради красивых чисел, а способ сократить частоту сборок и их влияние на задержки. Но берутся за него только тогда, когда есть подтверждение, что проблема именно здесь.

## Сначала — измерить

Правило, без которого дальше читать бессмысленно: **оптимизировать без профилировщика нельзя**. Интуиция об узких местах ошибается почти всегда, а код, переписанный «на всякий случай», становится хуже без выигрыша.

Признаки, что аллокации действительно мешают:

- высокий процент времени в GC (`dotnet-counters`, счётчик `time-in-gc` — тревожно от 10%);
- растущий `gen-2-gc-count` — объекты доживают до старости (см. `Поколения Gen 0–2`);
- всплески задержек, совпадающие со сборками, в трассировке.

Порядок инструментов: `dotnet-counters` для картины в целом → `dotnet-trace` или PerfView для профиля аллокаций → BenchmarkDotNet с `[MemoryDiagnoser]` для конкретного участка.

```csharp
[MemoryDiagnoser]
public class ParseBenchmark
{
    [Benchmark] public int Old() => ParseWithSubstring(Line);
    [Benchmark] public int New() => ParseWithSpan(Line);
}
```

Для быстрой проверки одного утверждения хватает и простого замера, которым сделаны все числа этого раздела:

```csharp
GC.Collect(); GC.WaitForPendingFinalizers(); GC.Collect();
long before = GC.GetAllocatedBytesForCurrentThread();
// измеряемый код
long allocated = GC.GetAllocatedBytesForCurrentThread() - before;
```

С обязательным прогревом до замера — иначе измеряется JIT (см. `CLR, IL и JIT`).

## Приёмы, дающие наибольший эффект

По убыванию отдачи, с измеренными числами на .NET 10.

**1. Пул буферов вместо создания.** Самый крупный выигрыш в коде, работающем с массивами:

```
ArrayPool Rent+Return 1024:    0,01 байта
new byte[1024]:             1048,00 байта
```

Стократ и больше — потому что массив переиспользуется, а не создаётся заново. Детали и правила — в статье `LOH и фрагментация`. Для объектов посложнее есть `ObjectPool<T>` из `Microsoft.Extensions.ObjectPool`, полезный для `StringBuilder` и тяжёлых парсеров.

**2. `Span<T>` вместо подстрок.**

```
line.Substring(0, 3):   32 байта
line.AsSpan(0, 3):       0 байт
line.Split(';'):       128 байт
```

Разбор текста через окна вместо копий — тема статьи `Span<T> и Memory<T>`.

**3. `stackalloc` для маленьких буферов.**

```
stackalloc byte[128]:   0 байт
new byte[128]:        152 байта
```

С оговорками про размер и циклы из статьи `Стек и куча`.

**4. Структуры вместо классов для мелких значений.** Класс с одним-двумя полями стоит 24 байта в куче; структура в локальной переменной — ноль. Массив структур ещё и даёт локальность. Границы применимости — в статье `class, struct и record`.

**5. Правильная работа со строками.**

```
string.Concat 3 строк:               32 байта
StringBuilder 3 Append + ToString:  136 байт
```

Показательно, что `StringBuilder` на коротких склейках **проигрывает** в четыре раза: он сам объект с буфером. Он нужен для неизвестного числа операций, а не для трёх (см. `Строки и StringBuilder`).

**6. Задавать вместимость коллекций.** `List<T>` и `Dictionary` растут удвоением, и каждый рост — новый массив плюс копирование:

```csharp
var list = new List<int>(expectedCount);         // одна аллокация вместо log₂(n)
var dict = new Dictionary<int, string>(capacity: 1000);
```

## Скрытые источники мусора

Места, где аллокации возникают незаметно — по ним стоит пройтись при разборе профиля.

**Упаковка.** Структура, попавшая в `object`, интерфейс или несогласованный обобщённый параметр (см. `Упаковка и распаковка`). Проверенный в прошлом разделе пример: `Dictionary` со структурным ключом без `IEquatable<T>` — 72 байта на каждый поиск.

**Замыкания с захватом.** 88 байт на итерацию при захвате меняющейся переменной, ноль — у `static`-лямбды с передачей состояния аргументом (см. `Делегаты и события`).

**Энумератор через интерфейс.** `foreach` по переменной типа `IEnumerable<T>` вместо `List<T>` упаковывает структурный энумератор — 40 байт на перечисление (см. `LINQ и отложенное выполнение`).

**Цепочки LINQ в горячем коде.** Около 104 байт на построение цепочки независимо от объёма данных: проблема не в размере коллекции, а в частоте вызова.

**`params` и интерполяция в логировании.** Вызов логгера создаёт массив аргументов **даже если уровень выключен**:

```csharp
_logger.LogDebug($"обработано {count} записей");     // строка собирается всегда
_logger.LogDebug("обработано {Count} записей", count); // отложено до проверки уровня
```

Вторая форма — не только про структурированные логи, но и про мусор: строка не форматируется, если уровень отключён.

**`async` на горячем пути.** Каждый `await`, который реально ждёт, создаёт объект состояния. Для методов, часто завершающихся синхронно, есть `ValueTask` — подробности в разделе про асинхронность.

**`ToList()` и `ToArray()` без нужды.** Материализация промежуточного результата, который тут же перечисляется один раз.

## Чего делать не надо

**Не переписывать всё подряд.** Код, оптимизированный без замера, обычно хуже читается и не быстрее. Аллокации в коде, выполняющемся раз в минуту, не имеют значения — даже если их тысячи.

**Не звать `GC.Collect()`.** Он состаривает мусор и делает хуже (см. `Как работает GC`).

**Не путать аллокации с производительностью.** Ноль аллокаций через десять строк работы со `Span` может проигрывать одной аллокации с простым кодом — измерять надо время, а не только байты.

**Не превращать структуры в универсальное лекарство.** Большая структура копируется при каждой передаче; передача её по значению в цикле дороже одной аллокации класса.

**Не жертвовать корректностью.** Переиспользование буфера, который ещё читает другой поток, — источник ошибок, которые ищут неделями.

Разумная граница: аллокации стоит убирать на пути, который выполняется **тысячи раз в секунду**, и там, где профилировщик показал заметное время в GC. Всё остальное — преждевременная оптимизация.

## Порядок работы

Сложившаяся последовательность, которой стоит держаться:

1. **Зафиксировать цель** — конкретную метрику: задержка p99, пропускная способность, потребление памяти. Без неё непонятно, когда останавливаться.
2. **Замерить базу** — BenchmarkDotNet или нагрузочный тест с текущими числами.
3. **Найти главный источник** по профилю аллокаций — обычно это один-два места, дающие большую часть мусора.
4. **Исправить одно место** и перемерить. Именно одно: несколько правок сразу не дают понять, что помогло.
5. **Проверить, что стало лучше по целевой метрике**, а не только по байтам.
6. **Остановиться, когда цель достигнута.** Дальше выигрыш падает, а сложность растёт.

## Что стоит ответить на собеседовании

Аллокация в .NET дёшева — это сдвиг указателя; дорога последующая сборка, поэтому цель снижения аллокаций в том, чтобы реже запускать GC и не давать объектам доживать до старших поколений. Браться за это стоит по данным профилировщика: высокий процент времени в GC и рост числа полных сборок, а не по ощущениям.

Сильный ответ назовёт приёмы с порядком эффекта: пул буферов вместо создания массивов (на .NET 10 это 0,01 байта против 1048 на операцию), `Span<T>` вместо подстрок (0 против 32), `stackalloc` для маленьких буферов, структуры для мелких значений и заданная заранее вместимость коллекций. И перечислит скрытые источники — упаковку, замыкания с захватом, упакованный энумератор при `foreach` через `IEnumerable<T>`, цепочки LINQ в горячем коде и интерполяцию в вызове логгера, которая форматирует строку даже при выключенном уровне.
