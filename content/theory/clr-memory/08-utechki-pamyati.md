«В .NET утечек не бывает, есть же сборщик» — заблуждение, которое разваливается на первом же продакшене. GC освобождает **недостижимые** объекты; если объект достижим, но уже не нужен, он останется в памяти навсегда. Это и есть managed-утечка: не потерянный указатель, как в C++, а забытая ссылка.

## Статические коллекции

Самая частая причина. Статическое поле — корень, живущий всё время процесса (см. `GC Root и WeakReference`), поэтому всё, что в него положили, живёт столько же.

```csharp
static readonly Dictionary<int, byte[]> Cache = new();

void Handle(int id)
{
    Cache[id] = LoadData(id);   // кто это удалит?
}
```

Замер на .NET 10 показывает, что сборщик здесь бессилен:

```
словарь 10 000 x 1000 байт:  +10 470 КБ, живы после полной сборки
после Clear():                −2 КБ
```

Десять мегабайт не освобождаются никакой сборкой, пока ссылки лежат в словаре, и возвращаются мгновенно после `Clear()`. Сборщик работает правильно — ошибка в коде.

Лечение — не «не использовать кэш», а **задавать границы**: ограничение размера и вытеснение. `IMemoryCache` умеет и то, и другое:

```csharp
_cache.Set(key, value, new MemoryCacheEntryOptions
{
    Size = 1,
    AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(10)
});
```

С обязательным `SizeLimit` при регистрации — без него ограничение не работает, и `IMemoryCache` превращается в тот же бесконечный словарь.

Признак, по которому подозревают эту утечку: память растёт монотонно и не падает после полных сборок, а в дампе видна большая коллекция, висящая на статическом поле.

## События

Вторая по частоте и более коварная, потому что ссылка неочевидна: подписка создаёт ссылку **от источника события к подписчику**, а не наоборот.

```csharp
class Subscriber
{
    public Subscriber(EventSource source)
    {
        source.Fired += OnFired;   // source теперь держит this
    }
    void OnFired(object? s, EventArgs e) { }
}
```

Замер — десять тысяч подписчиков, каждый вышел из области видимости сразу после создания:

```
10 000 подписчиков вышли из области видимости:  +6 143 КБ
подписчиков у события осталось:                 10 000
```

Шесть мегабайт живут после полной сборки, потому что долгоживущий источник держит всех. В реальном приложении на месте источника обычно синглтон из DI, а на месте подписчика — компонент со временем жизни запроса.

Лечение — симметричная отписка, обычно через `IDisposable`:

```csharp
public sealed class Subscriber : IDisposable
{
    readonly EventSource _source;

    public Subscriber(EventSource source)
    {
        _source = source;
        _source.Fired += OnFired;
    }

    public void Dispose() => _source.Fired -= OnFired;
    void OnFired(object? s, EventArgs e) { }
}
```

И напоминание из статьи `Делегаты и события`: отписаться можно **только тем же делегатом**, поэтому подписка лямбдой требует сохранить делегат в поле, иначе `-=` молча ничего не сделает.

## Таймеры и фоновые задачи

Работающий таймер удерживается рантаймом и держит свой колбэк вместе со всем захваченным:

```csharp
class Service
{
    Timer? _timer;

    public void Start() =>
        _timer = new Timer(_ => Poll(), null, 0, 1000);   // держит this

    // без Dispose таймер и Service живут вечно
}
```

`System.Threading.Timer` требует `Dispose`; его отсутствие — утечка и самого сервиса, и всего, на что он ссылается. То же касается незавершённых `Task` с бесконечным циклом, подписок Rx и `CancellationTokenSource`, в который зарегистрировали колбэк:

```csharp
// Регистрация в долгоживущем токене держит колбэк
var registration = longLivedToken.Register(() => Cleanup());
registration.Dispose();   // обязательно, если сам объект короткоживущий
```

## Замыкания

Замыкание захватывает не значение, а **переменную** — и вместе с ней весь объект, которому она принадлежит:

```csharp
class Handler
{
    byte[] _bigBuffer = new byte[10_000_000];

    public Action Create()
    {
        int id = _id;
        return () => Console.WriteLine(id);   // захватывает this, а не только id!
    }
}
```

Если лямбда обращается к полю или методу экземпляра, компилятор захватывает `this` целиком, и десятимегабайтный буфер живёт столько же, сколько делегат. Лечится копированием нужного значения в локальную переменную и `static`-лямбдой:

```csharp
public Action Create()
{
    int id = _id;
    return static () => { };   // или лямбда, использующая только локальные копии
}
```

Ровно этот же механизм объясняет и аллокации замыканий из статьи `Делегаты и события`.

## Ещё несколько источников

**`HttpClient` в `using`.** Парадоксальная, но классическая ошибка: создание `HttpClient` на каждый запрос исчерпывает сокеты (они остаются в состоянии `TIME_WAIT`). Правильно — `IHttpClientFactory` или один долгоживущий экземпляр.

**Неверное время жизни в DI.** Scoped-сервис, внедрённый в singleton, живёт вечно вместе с ним — это captive dependency. Встроенный контейнер ловит часть таких случаев при `ValidateScopes`, но не все.

**Строки в пуле интернирования.** `string.Intern` на пользовательском вводе — память, которая не вернётся никогда (см. `Строки и StringBuilder`).

**Незакрытые `Stream` и соединения.** Утечка не столько памяти, сколько дескрипторов и соединений в пуле, но проявляется похоже — см. `IDisposable, using и финализаторы`.

**Фрагментация LOH** — не утечка в строгом смысле, но выглядит так же: память растёт и не возвращается (см. `LOH и фрагментация`).

## Как искать

Порядок действий, который работает:

**1. Подтвердить, что это утечка.** Память, растущая под нагрузкой, — норма; утечка — это память, которая **не возвращается после полной сборки** в состоянии покоя. Смотреть по `GC.GetTotalMemory(forceFullCollection: true)` или по счётчикам.

**2. Снять два дампа** — с интервалом под нагрузкой:

```bash
dotnet-gcdump collect -p <pid> -o before.gcdump
# нагрузка
dotnet-gcdump collect -p <pid> -o after.gcdump
```

**3. Сравнить и найти растущий тип.** Инструменты (Visual Studio, PerfView, dotMemory) показывают разницу по типам: что выросло в количестве и объёме.

**4. Найти цепочку от корня** — путь удержания (path to root). Это главный шаг: он прямо называет виновника. Статическое поле, список подписчиков события, таймер — цепочка сразу покажет, какой именно.

**5. Разорвать цепочку** и проверить повтором замера.

Для наблюдения в реальном времени удобны счётчики:

```bash
dotnet-counters monitor -p <pid> --counters System.Runtime
```

Смотреть стоит на `gc-heap-size` вместе с `gen-2-gc-count`: рост первого при работающем втором — признак настоящей утечки.

## Что стоит ответить на собеседовании

В .NET утечка — это не потерянная память, а лишняя достижимость: объект не нужен, но на него есть цепочка ссылок от корня, и сборщик обязан его сохранить. Классические источники — статические коллекции без ограничения размера, подписки на события долгоживущих источников без отписки, таймеры и фоновые задачи без `Dispose`, а также замыкания, захватывающие `this` целиком.

Сильный ответ приведёт механику событий: подписка создаёт ссылку от источника к подписчику, поэтому singleton-источник удерживает все короткоживущие компоненты (в замере на .NET 10 — 6 МБ на десять тысяч подписчиков, переживших полную сборку), а отписаться лямбдой, которой подписался, невозможно. И опишет порядок поиска: убедиться, что память не возвращается после полной сборки, сравнить два gcdump-а, найти выросший тип и посмотреть у него путь до корня — именно цепочка удержания называет виновника.
