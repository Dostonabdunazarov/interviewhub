В .NET память делится на стек и управляемую кучу. Распространённая формулировка «значимые типы живут на стеке, ссылочные — в куче» удобна как первое приближение, но неверна: структура внутри класса лежит в куче, а ссылка на объект — на стеке. Правильный критерий — не тип, а **время жизни**.

## Стек

Стек — область памяти потока, растущая и сжимающаяся по мере вызовов. Каждый вызов метода кладёт кадр (frame) с аргументами, локальными переменными и адресом возврата; выход из метода снимает кадр целиком, сдвигая указатель.

Отсюда свойства стека: выделение стоит одну инструкцию (сдвиг указателя), освобождение — тоже, память не фрагментируется, а данные лежат плотно и попадают в кэш процессора. Сборщик мусора стеком не занимается вовсе.

Ограничения тоже вытекают из устройства. Размер фиксирован — **около 1,5 МБ на поток по умолчанию** (замер на .NET 10, Windows x64; на Linux размер стека главного потока задаёт `ulimit -s`); превышение даёт `StackOverflowException`, которое нельзя поймать `catch` и которое немедленно завершает процесс. И время жизни жёстко привязано к методу: то, что на стеке, не переживёт возврата.

Проверка глубины рекурсии — классический способ упереться в это ограничение; именно поэтому глубоко рекурсивные алгоритмы переписывают на цикл с явным стеком.

## Куча

Управляемая куча — общая для всего процесса область, где живут объекты, чьё время жизни не связано с методом. Выделение здесь тоже дёшево: аллокатор в большинстве случаев просто сдвигает указатель на свободное место, потому что куча поколений уплотняется и свободное место идёт непрерывно.

Дорого другое — **освобождение**. Никто не знает, когда объект перестал быть нужен, поэтому этим занимается сборщик мусора, а его работа требует пауз. Подробно — в статье `Как работает GC`.

## Сколько весит объект

Замеры на .NET 10, x64, через `GC.GetAllocatedBytesForCurrentThread()`:

```
new object()                     24 байта (с поправкой на кэширование)
class с одним int полем          24 байта
class с двумя int полями         24 байта
class с одним ref полем          24 байта
new byte[0]                      24 байта
new byte[1]                      32 байта
new byte[8]                      32 байта
new int[10]                      64 байта
строка из 10 символов            48 байт
строка из 100 символов          224 байта
```

Числа объясняются устройством объекта в куче на 64 бита:

- **8 байт** — заголовок объекта (object header, он же sync block index): используется для блокировки через `lock`, хеш-кода по умолчанию и служебных флагов;
- **8 байт** — указатель на таблицу методов (method table pointer): по нему рантайм узнаёт тип объекта, находит виртуальные методы и работает `is`/`as`;
- **дальше поля**, выровненные по 8 байт;
- минимальный размер объекта — **24 байта**, даже если полей нет вовсе.

Поэтому класс с одним `int` и класс с двумя `int` весят одинаково: 16 байт служебных данных плюс 8 байт под поля, в которые два `int` помещаются целиком. Третий `int` добавил бы ещё 8.

У массива добавляется 8 байт под длину, отсюда 24 байта у пустого. А строка из 10 символов — это 16 служебных + 4 длина + 20 байт данных (UTF-16, два байта на символ) с выравниванием, итого 48.

Практический вывод: **мелкие объекты почти целиком состоят из накладных расходов**. Миллион объектов с одним `int` — это 24 МБ, из которых полезны 4. Когда таких объектов много, разница между `class` и `struct` перестаёт быть вкусовой (см. `class, struct и record`).

## Что на самом деле где лежит

Правило: **объект живёт там, где живёт то, что им владеет**.

```csharp
class Order
{
    public int Id;              // в куче, внутри объекта Order
    public DateTime Created;    // структура, но тоже в куче — она поле класса
    public Customer Customer;   // ссылка в куче, сам Customer — отдельный объект в куче
}

void Process()
{
    int local = 5;              // на стеке
    DateTime d = DateTime.Now;  // структура на стеке
    Order order = new Order();  // ссылка на стеке, объект в куче
}
```

Структура — поле класса, элемент массива, захваченная замыканием переменная или упакованное значение — во всех этих случаях она в куче. Поэтому утверждение «struct не нагружает GC» верно только для локальных переменных и параметров.

И обратное уточнение: даже локальная структура не обязана быть на стеке. JIT свободно держит её **в регистрах**, если она мала и не берётся по ссылке, — это быстрее любой памяти.

Тут же — важная тонкость с массивами. Массив структур хранит значения подряд, одним блоком:

```csharp
Point[] points = new Point[1000];   // 1000 структур внутри одного объекта
Point?[] boxed = new Point?[1000];  // иначе
PointClass[] objs = new PointClass[1000]; // 1000 ссылок + 1000 отдельных объектов
```

Первый вариант — один объект в куче и отличная локальность: элементы лежат рядом и читаются кэшем процессора пачками. Третий — тысяча объектов, разбросанных по куче, плюс тысяча ссылок. Для больших массивов данных это разница в разы, и именно она стоит за советом использовать структуры в числодробилках.

## stackalloc

Можно попросить память на стеке явно:

```csharp
Span<byte> buffer = stackalloc byte[128];
buffer[0] = 1;
```

Замер подтверждает — ноль байт в куче против 152 байт у `new byte[128]`. Освобождения не нужно: кадр снимется вместе с методом.

Ограничения жёсткие, и их стоит помнить:

- **размер должен быть маленьким и ограниченным**. `stackalloc` на пользовательский ввод — готовое переполнение стека. Практический порог — сотни байт, максимум килобайт;
- **нельзя в цикле**: память не освобождается до выхода из метода, и цикл на тысячу итераций съест стек;
- результат нельзя вернуть из метода — `Span<T>` этого просто не позволит (см. `Span<T> и Memory<T>`).

Типовой безопасный шаблон — маленький буфер на стеке, большой из пула:

```csharp
Span<byte> buffer = length <= 256
    ? stackalloc byte[256]
    : new byte[length];
```

## Стек и потоки

У каждого потока свой стек, поэтому локальные переменные потокобезопасны по определению: другой поток до них не дотянется. Куча же общая, и любой объект, доступный двум потокам, требует синхронизации.

Из этого следует и цена потока: **около 1,5 МБ адресного пространства на стек** (физическая память выделяется по мере использования). Десять тысяч потоков — это пятнадцать гигабайт адресного пространства, и это одна из причин, по которым асинхронность в .NET сделана не через «поток на запрос». Подробнее — в разделе про асинхронность.

## Что стоит ответить на собеседовании

Стек — память потока с кадром на каждый вызов: выделение и освобождение стоят сдвига указателя, но размер ограничен (около 1,5 МБ по умолчанию), а данные не переживают возврата из метода. Куча — общая память процесса для объектов с произвольным временем жизни; выделение тоже дёшево, а освобождение требует работы сборщика.

Сильный ответ поправит формулировку «значимые типы на стеке»: место определяется не типом, а владельцем — структура в поле класса, в массиве или в замыкании лежит в куче, а локальная структура может вообще не попасть в память и остаться в регистрах. И приведёт устройство объекта: 8 байт заголовка плюс 8 байт указателя на таблицу методов, минимум 24 байта, из-за чего класс с одним `int` весит столько же, сколько с двумя, а миллион мелких объектов — это в основном накладные расходы.
