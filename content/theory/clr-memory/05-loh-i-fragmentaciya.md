Объекты от 85 000 байт живут отдельно — на большой куче объектов (Large Object Heap, LOH). У неё другие правила: она не уплотняется и собирается только при полной сборке. Из этих двух особенностей вырастает специфический класс проблем, вплоть до `OutOfMemoryException` при гигабайтах свободной памяти.

## Граница — 85 000 байт

Проверено на .NET 10 прямо на границе:

```
массив 84 000 байт: Gen 0
массив 85 000 байт: Gen 2
массив 90 000 байт: Gen 2
массив 1 000 000 байт: Gen 2
```

Порог — константа рантайма, историческая и не круглая: 85 000 байт, а не 85 КБ и не 64 КБ. Переводя в элементы массива:

- `byte[]` — примерно **85 000** элементов;
- `int[]` — примерно **21 250** (по 4 байта);
- `string` — около **42 500** символов (UTF-16, по 2 байта);
- массив ссылок или `long[]` — около **10 600** (по 8 байт на x64).

Последнее особенно легко упустить: `List<T>` ссылочных типов уезжает на LOH уже на десяти с небольшим тысячах элементов.

Исключение — массивы `double`: для них на 32-битных системах порог ниже (1000 элементов), это оптимизация выравнивания.

## Два следствия, из которых всё вытекает

**LOH собирается только при сборке Gen 2.** Большой объект формально сразу в Gen 2 (что и показывает замер), а значит, освободится лишь при полной сборке — самой редкой и самой дорогой. Короткоживущий большой буфер занимает память сильно дольше, чем маленький.

**LOH не уплотняется.** Копировать мегабайтные объекты дорого, поэтому по умолчанию сборщик оставляет выжившие на местах и лишь ведёт список свободных промежутков. Новые объекты размещаются в подходящую по размеру дыру — как в обычном неуправляемом аллокаторе, со всеми его недостатками.

## Как возникает OutOfMemory при свободной памяти

Классический сценарий фрагментации:

```
LOH:  [500 КБ][ свободно 200 КБ ][800 КБ][ свободно 300 КБ ][600 КБ]
```

Свободно 500 КБ, но **непрерывным куском — максимум 300**. Запрос на массив в 400 КБ не выполнится, хотя памяти достаточно. В 64-битном процессе это редкость, а вот в 32-битном (или в контейнере с жёстким лимитом) — вполне реальный путь к `OutOfMemoryException` при, казалось бы, свободной памяти.

Типичная причина — циклическое создание больших буферов разного размера:

```csharp
// Плохо: каждый ответ — новый большой массив своего размера
while (true)
{
    var buffer = new byte[response.ContentLength];  // 90 КБ, 150 КБ, 120 КБ...
    Process(buffer);
}
```

Дыры от освобождённых буферов не совпадают по размеру с новыми запросами, и куча медленно расползается.

## Что с этим делать

**Пулить буферы вместо создания.** Основной приём, и он же самый эффективный. `ArrayPool<T>` держит набор массивов и выдаёт их во временное пользование — замер на .NET 10 показателен:

```
ArrayPool Rent+Return 1024:    0,01 байта на вызов
new byte[1024]:             1048,00 байта на вызов
```

Практически ноль против килобайта на каждую операцию. Шаблон использования:

```csharp
byte[] buffer = ArrayPool<byte>.Shared.Rent(size);
try
{
    // ВАЖНО: массив может быть БОЛЬШЕ запрошенного
    Process(buffer.AsSpan(0, size));
}
finally
{
    ArrayPool<byte>.Shared.Return(buffer);
}
```

Три правила, которые нарушают чаще всего: `Rent` возвращает массив **не меньше** запрошенного, но обычно больше — работать надо через `Span` нужной длины, а не по `buffer.Length`; возврат обязателен даже при исключении, отсюда `try/finally`; после `Return` массив трогать нельзя, его уже мог получить другой код. Если в буфере были чувствительные данные, есть `Return(buffer, clearArray: true)`.

**Выбирать размеры буферов одинаковыми.** Если пулинг невозможен, фиксированный размер (скажем, всегда 128 КБ) оставляет дыры, в которые точно поместится следующий запрос. Фрагментация возникает от разнородности, а не от размера.

**Держать большие объекты ниже порога.** Иногда буфер в 100 КБ можно разбить на два по 50 и остаться в обычной куче, где работает уплотнение. Особенно это касается `List<T>`, который удваивает внутренний массив: предсказать переход границы сложно, поэтому длинным спискам стоит задавать вместимость сразу.

**Потоковая обработка вместо целого файла.** Чтение файла целиком в `byte[]` — гарантированный LOH и частая причина проблем. Построчное или поблочное чтение через `Stream` держит память постоянной независимо от размера файла.

## Принудительное уплотнение

Если фрагментация уже случилась, LOH можно уплотнить вручную — это единственный способ:

```csharp
GCSettings.LargeObjectHeapCompactionMode = GCLargeObjectHeapCompactionMode.CompactOnce;
GC.Collect();
```

Настройка действует **один раз** и сбрасывается после сборки. Операция очень дорогая: полная сборка с перемещением больших объектов и исправлением всех ссылок, паузы в сотни миллисекунд.

Уместно в редких точках жизненного цикла — после выгрузки крупного кэша, между этапами пакетной обработки, — и категорически не на пути запроса. Это ровно тот случай из статьи `Как работает GC`, когда ручная сборка оправдана.

Есть и настройка на уровне приложения, включающая LOH в обычные сборки Gen 2 чаще:

```xml
<ServerGarbageCollection>true</ServerGarbageCollection>
```

Server GC сам по себе обычно улучшает ситуацию с большими объектами за счёт параллельной сборки, но памяти потребляет больше.

## Диагностика

Признаки проблемы с LOH:

- растёт `GC.CollectionCount(2)` — большие объекты вынуждают полные сборки;
- размер кучи заметно больше суммы живых объектов в дампе — это и есть дыры;
- `OutOfMemoryException` при видимой свободной памяти.

Смотреть стоит через `dotnet-gcdump` (снимок с разбивкой по кучам) или `dotnet-counters` со счётчиком `gen-2-gc-count`. В дампе LOH видна отдельной кучей, и её размер сравнивают с объёмом живых больших объектов: разница — фрагментация.

## Что стоит ответить на собеседовании

Объекты от 85 000 байт попадают на большую кучу объектов, которая относится к Gen 2 и собирается только при полной сборке, а по умолчанию ещё и не уплотняется. Отсюда фрагментация: свободная память есть, но разрозненными кусками, и запрос на крупный непрерывный блок может не выполниться — вплоть до `OutOfMemoryException` при свободной памяти.

Сильный ответ переведёт порог в элементы (`int[]` уезжает на LOH примерно с 21 тысячи элементов, массив ссылок — с 10 тысяч, так что до порога проще добраться, чем кажется) и назовёт лечение: `ArrayPool<T>` вместо создания буферов — в замере на .NET 10 это 0,01 байта против 1048 на операцию, — одинаковые размеры буферов вместо произвольных и потоковая обработка вместо чтения файла целиком. И упомянет `LargeObjectHeapCompactionMode.CompactOnce` как разовое дорогое лечение уже возникшей фрагментации.
