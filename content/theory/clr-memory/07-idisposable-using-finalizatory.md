Сборщик мусора управляет памятью — и только ею. Файловые дескрипторы, сокеты, соединения с базой, блокировки и неуправляемые буферы он освобождать не умеет и не должен. Для них существует `IDisposable`, а финализатор — страховка на случай, если про `Dispose` забыли. Разница между этими двумя механизмами и их правильное сочетание — стандартный вопрос на собеседовании.

## Два вида ресурсов

**Управляемая память** освобождается сборщиком в произвольный момент после того, как объект стал недостижим. Ждать этого момента можно сколько угодно — он наступит, когда рантайм сочтёт нужным.

**Неуправляемые ресурсы** такой роскоши не допускают. Открытый файл держит дескриптор операционной системы, соединение с базой занимает место в пуле, а незакрытый сокет — порт. Их лимиты гораздо жёстче памяти: дескрипторы кончатся раньше, чем гигабайты. Поэтому освобождать их нужно **детерминированно** — в известный момент, а не когда-нибудь.

Именно это и означает `IDisposable`: «у меня есть что освободить, и сделать это надо явно».

## using

Синтаксис, гарантирующий вызов `Dispose` даже при исключении:

```csharp
using (var stream = new FileStream(path, FileMode.Open))
{
    Read(stream);
}   // Dispose вызовется здесь в любом случае
```

Компилятор разворачивает это в `try/finally`, поэтому исключение внутри блока файл не оставит открытым.

Начиная с C# 8 есть форма без блока — ресурс освобождается в конце области видимости:

```csharp
void Process(string path)
{
    using var stream = new FileStream(path, FileMode.Open);
    Read(stream);
}   // Dispose здесь
```

Для асинхронного освобождения — `IAsyncDisposable` и `await using`, это важно для сетевых ресурсов, где закрытие требует ввода-вывода:

```csharp
await using var connection = new SqlConnection(cs);
```

Правило простое: **если тип реализует `IDisposable`, его использование должно быть обёрнуто в `using`** — либо объект должен явно принадлежать кому-то другому, кто позаботится о `Dispose` (например, DI-контейнеру).

Отдельная типовая ошибка — `using` на объекте, которым вы не владеете. `HttpClient` из `IHttpClientFactory` или соединение, переданное аргументом, освобождать не надо: владелец другой.

## Канонический Dispose pattern

Полный шаблон для класса, который владеет и неуправляемым, и управляемыми ресурсами:

```csharp
public class ResourceHolder : IDisposable
{
    IntPtr _handle;            // неуправляемый ресурс
    FileStream? _stream;       // управляемый, сам IDisposable
    bool _disposed;

    public void Dispose()
    {
        Dispose(disposing: true);
        GC.SuppressFinalize(this);
    }

    protected virtual void Dispose(bool disposing)
    {
        if (_disposed) return;

        if (disposing)
        {
            // вызвано явно: управляемые объекты ещё живы, их можно трогать
            _stream?.Dispose();
        }

        // в обоих случаях: освобождаем неуправляемое
        if (_handle != IntPtr.Zero)
        {
            ReleaseHandle(_handle);
            _handle = IntPtr.Zero;
        }

        _disposed = true;
    }

    ~ResourceHolder() => Dispose(disposing: false);
}
```

Смысл каждой детали:

**Параметр `disposing`** различает два пути вызова. При явном `Dispose()` управляемые объекты гарантированно живы, и их можно освобождать. Из финализатора — **нельзя**: порядок финализации не определён, и `_stream` может быть уже финализирован. Обращение к нему оттуда — ошибка.

**`GC.SuppressFinalize(this)`** снимает объект с очереди финализации, раз ресурсы уже освобождены. Без этого объект зря переживёт лишнюю сборку.

**Флаг `_disposed`** делает повторный `Dispose` безопасным — по контракту он обязан быть идемпотентным.

**`Dispose` не должен бросать исключений.** Он часто вызывается из `finally` во время обработки другого исключения, и своё исключение затрёт исходное.

## Сколько стоит финализатор

Финализатор — не бесплатная страховка. Замеры на .NET 10 показывают механику точно:

```
создано 1000 объектов с финализатором, сразу:   финализировано 0
после GC.Collect():                              финализировано 0
после WaitForPendingFinalizers():                финализировано 1000
с SuppressFinalize:                              финализировано 0 из 1000
```

Читать так. При **создании** объект с финализатором регистрируется в очереди финализации — это уже дополнительная работа. При сборке он оказывается недостижим, но **не освобождается**: вместо этого его переносят в очередь готовых к финализации, а это делает его снова достижимым (очередь — корень, см. `GC Root и WeakReference`). Финализатор выполняется **отдельным потоком** асинхронно, и только следующая сборка освобождает память.

Отсюда главные факты для собеседования: объекту с финализатором нужно **минимум две сборки**, он гарантированно **переживает первую** и уезжает в старшее поколение (что показал и замер с поколениями), а момент вызова финализатора не определён — он может не выполниться вовсе при завершении процесса.

Отдельно стоит отметить, что аллокация объекта с финализатором и без него одинакова (24 байта) — цена не в памяти объекта, а в его времени жизни и в работе потока финализации.

`GC.SuppressFinalize` убирает всё это: проверено — 0 финализаций из 1000. Поэтому он обязателен в `Dispose`.

## Финализатор нужен реже, чем кажется

Главный современный тезис: **если класс не владеет неуправляемым ресурсом напрямую, финализатор не нужен**.

Класс, у которого поля — обычные `IDisposable` (`FileStream`, `HttpClient`, `SqlConnection`), должен просто реализовать `IDisposable` без финализатора:

```csharp
public sealed class Repository : IDisposable
{
    readonly SqlConnection _connection;

    public Repository(string cs) => _connection = new SqlConnection(cs);

    public void Dispose() => _connection.Dispose();
}
```

Финализатор здесь был бы вреден: он ничего не может сделать правильно (трогать `_connection` из финализатора нельзя), но продлевает жизнь объекту на лишнюю сборку. `sealed` заодно позволяет обойтись без виртуального `Dispose(bool)`.

А для прямого владения дескриптором есть готовые базовые классы, снимающие проблему целиком:

```csharp
public sealed class MyHandle : SafeHandleZeroOrMinusOneIsInvalid
{
    public MyHandle() : base(ownsHandle: true) { }
    protected override bool ReleaseHandle() => CloseHandle(handle);
}
```

`SafeHandle` устойчив к прерываниям потока, корректно работает при взаимодействии с неуправляемым кодом и уже содержит правильную финализацию. Рекомендация современного .NET — **использовать `SafeHandle` вместо собственных финализаторов**.

## Частые ошибки

**Забыли `using`.** Самая частая. Ловится анализатором CA2000 и просто вниманием к типам, реализующим `IDisposable`.

**`Dispose` не идемпотентен** — второй вызов падает. Флаг `_disposed` обязателен.

**Освобождение чужого объекта.** Особенно с внедрёнными зависимостями: если объект пришёл из DI со временем жизни singleton, его `Dispose` — не ваша задача.

**Финализатор ради памяти.** Освобождать управляемую память в финализаторе бессмысленно — этим занимается GC.

**Долгая или блокирующая работа в финализаторе.** Поток финализации один; заблокировав его, вы остановите финализацию всех объектов в процессе.

## Что стоит ответить на собеседовании

GC управляет только памятью, поэтому для файлов, сокетов и соединений есть `IDisposable` с детерминированным освобождением, а `using` разворачивается в `try/finally` и гарантирует вызов даже при исключении. Финализатор — страховка на случай забытого `Dispose`, и в `Dispose` обязателен `GC.SuppressFinalize`, чтобы её снять.

Сильный ответ опишет цену финализатора по механике: объект регистрируется в очереди при создании, при сборке не освобождается, а переносится в очередь готовых к финализации — то есть снова становится достижимым, — финализатор выполняется отдельным потоком асинхронно, и память освобождает только следующая сборка. Итого минимум две сборки и гарантированный переезд в старшее поколение (проверено на .NET 10). И добавит главный практический вывод: финализатор нужен только при прямом владении неуправляемым ресурсом, а в этом случае правильнее взять `SafeHandle`.
