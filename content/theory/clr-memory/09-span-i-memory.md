`Span<T>` — представление участка непрерывной памяти: массива, строки, стекового буфера или неуправляемого блока. Он не владеет данными и ничего не копирует — только смотрит. Появившись в .NET Core 2.1, он изменил то, как в платформе пишут разбор данных: вместо создания подстрок и подмассивов стало принято передавать окна в уже существующую память.

## Проблема, которую он решает

Классический разбор строки создаёт мусор на каждом шаге:

```csharp
string line = "key=value;other=thing";
string key = line.Substring(0, 3);     // новая строка в куче
string[] parts = line.Split(';');      // массив + строка на каждую часть
```

Замер на .NET 10:

```
line.Substring(0, 3)     32 байта
line.Split(';')         128 байт
line.AsSpan(0, 3)         0 байт
```

`AsSpan` бесплатен, потому что не создаёт ничего: он лишь запоминает указатель и длину. Для разбора миллиона строк это разница между сотней мегабайт мусора и нулём.

Важно, что и парсинг умеет работать со `Span` напрямую:

```
int.Parse(строка)     0 байт
int.Parse(span)       0 байт
```

Оба нуля здесь не случайны: числовые парсеры в современном .NET не аллоцируют, и работать они умеют с любым из двух представлений. Значит, цепочку «взять подстроку → распарсить» можно целиком перевести на `Span`.

## Как выглядит переписанный разбор

Было — три аллокации на строку:

```csharp
static (string Key, int Value) Parse(string line)
{
    var parts = line.Split('=');
    return (parts[0], int.Parse(parts[1]));
}
```

Стало — ни одной, если ключ тоже можно оставить окном:

```csharp
static (ReadOnlySpan<char> Key, int Value) Parse(ReadOnlySpan<char> line)
{
    int eq = line.IndexOf('=');
    return (line[..eq], int.Parse(line[(eq + 1)..]));
}
```

Срез `line[..eq]` — не копия, а новый `Span`, указывающий внутрь исходных данных. Поэтому операции нарезки бесплатны, сколько бы их ни было.

Для перебора разделителей без `Split` есть штатный приём:

```csharp
ReadOnlySpan<char> rest = line;
while (!rest.IsEmpty)
{
    int idx = rest.IndexOf(';');
    ReadOnlySpan<char> item = idx < 0 ? rest : rest[..idx];
    Handle(item);
    rest = idx < 0 ? default : rest[(idx + 1)..];
}
```

## Почему Span — ref struct

`Span<T>` объявлен как `ref struct`, и это влечёт жёсткие ограничения, которые на собеседованиях спрашивают чаще всего:

- **нельзя положить в поле класса** (только в поле другого `ref struct`);
- **нельзя упаковать** — ни в `object`, ни в интерфейс, ни в `dynamic`;
- **нельзя использовать в обобщённых типах** как аргумент типа: `List<Span<char>>` не скомпилируется;
- **нельзя захватить в лямбду** или в итератор;
- **нельзя использовать в `async`-методе** через `await`.

Причина одна: `ref struct` гарантированно живёт **только на стеке**. Если бы `Span` мог попасть в кучу, он мог бы пережить память, на которую указывает, — например, стековый буфер из `stackalloc`, кадр которого давно снят. Тогда чтение через него означало бы обращение к чужой памяти, а это ровно та ошибка, от которой .NET защищает по определению.

Ограничение на `async` — следствие того же: состояние `async`-метода сохраняется в объекте в куче, а `Span` туда попасть не может.

## Memory<T> — когда нужно хранить

`Memory<T>` решает ровно ту задачу, которую `Span` решать не вправе: это **обычная структура**, которую можно положить в поле, передать в `async`-метод и захватить в лямбду.

```csharp
class Buffer
{
    Memory<byte> _data;                      // так можно
    // Span<byte> _span;                     // а так нет

    public async Task WriteAsync(Stream s) =>
        await s.WriteAsync(_data);           // Memory работает с async
}
```

Платой за это является косвенность: работать с данными напрямую `Memory` не умеет, для доступа нужно получить `Span`:

```csharp
Memory<byte> memory = buffer.AsMemory();
Span<byte> span = memory.Span;               // вот теперь можно читать и писать
span[0] = 1;
```

Отсюда практическое разделение ролей: **`Memory<T>` — для хранения и передачи через асинхронные границы, `Span<T>` — для работы в пределах синхронного метода**. Типичный асинхронный код выглядит так:

```csharp
async Task ProcessAsync(Memory<byte> data)
{
    await ReadIntoAsync(data);
    Parse(data.Span);          // синхронный разбор — уже через Span
}
```

Полезно помнить и про `ReadOnlySpan<T>`/`ReadOnlyMemory<T>`: строка превращается именно в `ReadOnlySpan<char>`, потому что строки неизменяемы. Для API, который только читает, правильный тип параметра — `ReadOnlySpan<T>`: он принимает и массив, и строку, и стековый буфер.

## Откуда берутся Span-ы

```csharp
Span<byte> fromArray = new byte[100];
Span<byte> fromStack = stackalloc byte[128];        // 0 байт в куче
ReadOnlySpan<char> fromString = "текст".AsSpan();
Span<byte> slice = fromArray.AsSpan(10, 20);
unsafe { Span<byte> fromPointer = new Span<byte>(ptr, length); }
```

Связка со `stackalloc` особенно удачна: буфер на стеке без аллокаций, а работа с ним — через безопасный `Span` с проверкой границ, а не через указатель (см. `Стек и куча`). Ограничения на размер те же — сотни байт, не в цикле.

Для буферов побольше — пул, тоже отдающий `Span`:

```csharp
byte[] rented = ArrayPool<byte>.Shared.Rent(size);
try
{
    Span<byte> buffer = rented.AsSpan(0, size);   // именно нужная длина!
    Fill(buffer);
}
finally
{
    ArrayPool<byte>.Shared.Return(rented);
}
```

## Чего Span не делает

Стоит помнить границы применимости, иначе легко переусердствовать.

**Он не ускоряет вычисления сам по себе** — он убирает аллокации. Если узкое место в другом, выигрыша не будет.

**Он не продлевает жизнь данным.** `Span` на массив не мешает собрать массив, если больше ссылок нет; обычно это неважно, потому что `Span` живёт в пределах метода.

**Он не годится для API, хранящего данные.** Метод, который принимает `ReadOnlySpan<char>` и сохраняет его в поле, написать нельзя — и правильно: сохранять нужно копию (`ToString()`, `ToArray()`) или `Memory<T>`.

**Он усложняет код.** Переписывать на `Span` весь разбор подряд не стоит — только горячие пути, подтверждённые профилировщиком. В остальных местах `Substring` читается лучше.

## Что стоит ответить на собеседовании

`Span<T>` — структура из указателя и длины, дающая доступ к участку чужой непрерывной памяти без копирования: срез строки или массива через него стоит ноль байт против 32 у `Substring` на .NET 10. Он работает одинаково с массивом, строкой, стековым буфером и неуправляемой памятью, поэтому API, принимающий `ReadOnlySpan<T>`, принимает их все.

Сильный ответ объяснит, почему `Span` — `ref struct`: он обязан жить только на стеке, иначе мог бы пережить память, на которую указывает (например, буфер `stackalloc`). Отсюда запреты — нельзя в поле класса, нельзя упаковать, нельзя в обобщённый аргумент и нельзя в `async`-метод, потому что состояние такого метода сохраняется в куче. И назовёт `Memory<T>` как решение для хранения и асинхронных границ, из которого `Span` получают уже внутри синхронного метода через свойство `.Span`.
