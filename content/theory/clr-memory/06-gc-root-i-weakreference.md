Объект жив ровно до тех пор, пока до него можно добраться от корня. Не «пока на него есть ссылки» — циклические ссылки между двумя мёртвыми объектами не спасают ни один из них, — а именно **достижим от корня**. Разобраться, что такое корень, полезно вдвойне: это и ответ на вопрос о работе GC, и инструмент поиска утечек.

## Что считается корнем

Корень — место, про которое рантайм знает, что оно заведомо живо. Полный список:

**Локальные переменные и аргументы** в кадрах стека всех потоков, а также значения в регистрах процессора. JIT ведёт таблицу, по которой в каждой безопасной точке известно, где лежат ссылки.

**Статические поля.** Живут всё время существования домена приложения — то есть обычно всё время процесса. Отсюда статический список, который никто не чистит, — самая частая утечка в .NET.

**Дескрипторы GC (GC handles).** Закреплённые (`GCHandle` с `Pinned`), используемые для взаимодействия с неуправляемым кодом, и обычные сильные дескрипторы.

**Очередь финализации.** Объект с неисполненным финализатором жив, даже если недостижим иначе, — см. `IDisposable, using и финализаторы`.

**Стек и регистры неуправляемого кода**, если туда передавались ссылки.

Всё остальное живо только транзитивно: через поля живых объектов. Отсюда правило поиска утечки — искать не «кто ссылается», а **цепочку от корня**. Инструменты (`dotnet-gcdump`, Visual Studio, dotMemory) показывают её именно так, и вопрос «кто держит этот объект» на собеседовании подразумевает этот же ответ.

Циклы для сборщика не проблема:

```csharp
class Node { public Node? Other; }

var a = new Node();
var b = new Node();
a.Other = b;
b.Other = a;     // взаимные ссылки
a = b = null;    // от корней недостижимы — оба будут собраны
```

Это принципиальное отличие от подсчёта ссылок (как в COM или Python), где такой цикл течёт и требует слабых ссылок.

## Локальная переменная — тоже корень, но ненадолго

Тонкость, которая в Release-сборке ломает интуицию: JIT считает переменную живой **до последнего использования**, а не до конца метода.

```csharp
void Process()
{
    var data = new Payload();
    Use(data);
    // data больше не используется — объект уже может быть собран,
    // хотя переменная формально в области видимости
    DoSomethingLong();
}
```

При замерах для этой статьи я на это наткнулся напрямую: слабая ссылка на объект, созданный в теле метода, упорно оставалась живой, пока объект не был вынесен в отдельный метод. То есть отличие не в сборщике, а в том, что переменная-корень ещё жила в кадре.

Если объект обязан дожить до конкретной строки (обычно из-за неуправляемого ресурса, на который смотрит нативный код), есть явный способ:

```csharp
GC.KeepAlive(handle);   // ничего не делает, но считается использованием
```

## Слабые ссылки

`WeakReference<T>` позволяет ссылаться на объект, **не делая его достижимым**. Сборщик такую ссылку не считает и при сборке обнуляет.

```csharp
var weak = new WeakReference<Payload>(payload);

if (weak.TryGetTarget(out var target))
    Use(target);         // объект ещё жив
else
    Recreate();          // уже собран
```

Проверено на .NET 10: после того как единственная сильная ссылка ушла (объект создавался в отдельном методе), из 100 слабых ссылок живыми остались **0**, а `TryGetTarget` честно вернул `false` с `null` в `out`.

Пользоваться надо только через `TryGetTarget`: проверка `IsAlive` с последующим чтением `Target` — гонка, объект может быть собран между этими двумя обращениями. `TryGetTarget` атомарно захватывает сильную ссылку.

Стоит слабая ссылка недорого — 24 байта, как обычный объект, — но она не бесплатна, и миллион слабых ссылок на мелкие объекты смысла не имеет.

## Короткие и длинные

У неуниверсальной `WeakReference` есть параметр, о котором спрашивают редко, но он показателен:

```csharp
new WeakReference(obj, trackResurrection: false);  // короткая
new WeakReference(obj, trackResurrection: true);   // длинная
```

**Короткая** обнуляется, как только объект признан недостижимым. **Длинная** продолжает отдавать объект, пока не отработал его финализатор, — то есть видит объект в «зомби»-состоянии между попаданием в очередь финализации и настоящим освобождением.

Замер это показывает точно:

```
после Collect (объект в очереди финализации):  short=False, long=True
после финализации и второй сборки:             short=False, long=False
```

Практически длинная ссылка нужна крайне редко — в основном чтобы наблюдать воскрешение объекта. Почти всегда правильный выбор — короткая, а `WeakReference<T>` (обобщённая) именно такая.

## Кэш на слабых ссылках

Основной практический сценарий: кэш, который не должен мешать сборщику освобождать память под нагрузкой.

```csharp
class WeakCache<TKey, TValue> where TValue : class where TKey : notnull
{
    readonly Dictionary<TKey, WeakReference<TValue>> _items = new();

    public bool TryGet(TKey key, out TValue? value)
    {
        value = null;
        if (!_items.TryGetValue(key, out var weak)) return false;
        if (weak.TryGetTarget(out value)) return true;

        _items.Remove(key);   // ссылка обнулилась — чистим запись
        return false;
    }

    public void Set(TKey key, TValue value) => _items[key] = new(value);
}
```

Замер показал, что механизм работает: из 1000 значений в таком кэше после сборки выжило **1**, а память вернулась. Но он же показывает подвох — **словарь и сами объекты `WeakReference` никуда не делись**. Записи с обнулёнными ссылками остаются и продолжают занимать место, поэтому чистка обязательна: либо лениво при обращении (как выше), либо периодически.

Честная оценка применимости: для большинства задач `IMemoryCache` с явным ограничением размера и вытеснением предсказуемее. Слабый кэш хорош там, где объекты дорого создавать, но нельзя оценить, сколько их поместится, — например, кэш распарсенных документов разного размера.

## ConditionalWeakTable

Когда нужно **привязать данные к чужому объекту**, не продлевая ему жизнь, есть специальный тип:

```csharp
static readonly ConditionalWeakTable<Order, Metadata> _meta = new();

_meta.Add(order, new Metadata());
if (_meta.TryGetValue(order, out var m)) { }
```

Отличие от словаря со слабыми ключами принципиальное: таблица держит значение ровно столько, сколько жив **ключ**, и при этом значение может ссылаться на ключ без образования утечки — рантайм разрывает такую зависимость сам. Замер: после сборки ключей в таблице осталось **0 записей**, чистить её вручную не требуется.

Именно на этом механизме реализованы вложенные данные компилятором и рантаймом — например, привязка состояния к объектам, которые нельзя менять.

## Что стоит ответить на собеседовании

Объект жив, пока достижим от корня; корни — это локальные переменные и регистры в кадрах стека всех потоков, статические поля, дескрипторы GC и очередь финализации. Поэтому циклические ссылки между недостижимыми объектами не мешают их собрать — в отличие от систем с подсчётом ссылок, — а поиск утечки сводится к поиску цепочки от корня, что и показывают профилировщики.

Сильный ответ добавит, что в Release-сборке локальная переменная перестаёт быть корнем после последнего использования, а не в конце метода (отсюда `GC.KeepAlive` для объектов, на которые смотрит неуправляемый код). И объяснит слабые ссылки: `WeakReference<T>` не удерживает объект и обнуляется при сборке, читать её нужно через `TryGetTarget` во избежание гонки, а для привязки данных к чужому объекту есть `ConditionalWeakTable`, которая держит значение ровно столько, сколько жив ключ, и самоочищается.
