Статья `CLR, IL и JIT` описывает JIT как чёрный ящик. На уровне senior этого мало: один метод за время жизни процесса может существовать в нескольких версиях машинного кода, а решения об инлайнинге, девиртуализации и размещении объектов JIT принимает по наблюдаемому профилю. Отсюда расхождения между бенчмарком и продом и аллокации, которые то есть, то нет.

Вторая половина — про обратную сторону: что происходит, когда программист сам берёт на себя гарантии рантайма через указатели, `fixed` и закрепление объектов.

## Tiered compilation и Dynamic PGO

При первом вызове метод компилируется в **Tier 0** — быстро, почти без оптимизаций, без инлайнинга. Рантайм считает вызовы; после примерно 30 вызовов (и паузы, в которую не появляются новые Tier 0 методы) метод ставится в фоновую очередь на перекомпиляцию в **Tier 1** с полной оптимизацией, и вызовы переключаются на новую версию через заглушку.

С .NET 8 по умолчанию включён **Dynamic PGO**. Горячие методы сначала проходят через *instrumented Tier 0*: код собирает профиль — какие типы реально приходят в виртуальные и интерфейсные вызовы, какие ветки выполняются. Tier 1 строится уже по этому профилю: например, если за `IShape` в 99% случаев стоит `Circle`, JIT вставляет проверку типа и прямой инлайненный вызов `Circle.Area` (guarded devirtualization), оставляя виртуальный вызов только как запасной путь.

Атрибут `[MethodImpl(MethodImplOptions.AggressiveOptimization)]` заставляет компилировать метод сразу оптимизированно, минуя tiering, — и тем самым **лишает его PGO**. Использовать его «для скорости» обычно ошибка.

## OSR: метод, который вызван один раз

Tiering переключает версии только на границе вызова. Это ломается на методах с долгим циклом:

```csharp
static void Main()
{
    long sum = 0;
    for (int i = 0; i < 1_000_000_000; i++)
        sum += Compute(i);
    Console.WriteLine(sum);
}
```

`Main` вызывается один раз, счётчик до порога не дойдёт, и весь миллиард итераций прошёл бы в Tier 0. То же касается `while (true)` в фоновых воркерах. Раньше рантайм выбирал меньшее зло: методы с циклами компилировались сразу оптимизированно (`QuickJitForLoops = false`) — цикл быстрый, но старт медленнее и профиля нет.

**OSR** (On-Stack Replacement) решает это так: в Tier 0 версию в заголовки циклов вставляются *patchpoint*'ы со счётчиком итераций. Когда счётчик превышает порог, JIT компилирует оптимизированную **OSR-версию**, точка входа которой — этот patchpoint. Она подхватывает текущий кадр стека Tier 0 и продолжает цикл с той же итерации. Следующие вызовы метода идут обычным путём через Tier 1.

OSR и `QuickJitForLoops` включены по умолчанию с .NET 7 на x64 и Arm64. В выводе `DOTNET_JitDisasmSummary=1` это видно как `Tier1-OSR @0x14` — смещение patchpoint'а в IL.

OSR-код наследует раскладку кадра Tier 0 и не идентичен Tier 1, поэтому самописный замер цикла внутри `Main` показывает OSR-код, а BenchmarkDotNet, вызывающий метод многократно, — Tier 1. Обратного перехода из оптимизированного кода в Tier 0, как деоптимизация в JVM, в .NET нет.

## Инлайнинг и почему бенчмарк врёт

Решение об инлайнинге JIT принимает **для каждого места вызова отдельно**: по размеру IL вызываемого метода, оставшемуся бюджету роста вызывающего, константности аргументов и профилю. Мешают инлайнингу виртуальные вызовы без девиртуализации, вызовы через делегат, рекурсия, большой IL, атрибут `NoInlining`. `AggressiveInlining` снимает эвристику размера, но не делает невозможное возможным.

Из этого следует типичная ловушка: метод в бенчмарке быстрее, чем в проде. Причины складываются:

- **константы** — `Parse("42")` после инлайнинга частично сворачивается при компиляции, а в проде строка приходит из сети;
- **мономорфный профиль** — в бенчмарке за интерфейсом один тип, в проде пять, и guarded devirtualization промахивается;
- **бюджет инлайнинга** — в крошечном методе бенчмарка его хватает, в большом продовом методе нет;
- **tier** — редкий продовый путь может работать в Tier 0 или в ReadyToRun-коде с ограниченным межсборочным инлайнингом;
- **мёртвый код** — неиспользованный результат JIT выбрасывает; BenchmarkDotNet потребляет возвращаемое значение, самописный цикл часто нет.

Проверять надо машинный код, а не догадки:

```csharp
[DisassemblyDiagnoser(maxDepth: 2)]
public class ParseBench
{
    private string _input = "42";
    [Benchmark] public int Parse() => Parser.Parse(_input);
}
```

Строка в поле, а не литералом — чтобы не измерять свёртку констант. В работающем приложении то же даёт `DOTNET_JitDisasm="Parser:Parse"` (в release-рантайме с .NET 7) и `DOTNET_JitDisasmSummary=1` для списка методов с их tier. Смотреть нужно Tier 1 версию вызывающего метода: есть ли в ней `call`. Полезные эксперименты — `DOTNET_TieredPGO=0`, бенчмарк с массивом разных реализаций интерфейса, `NoInlining` для оценки вклада инлайнинга. Подробнее о методике — `Как мерить: BenchmarkDotNet`.

## Escape analysis: что есть на самом деле

Escape analysis доказывает, что объект не покидает метод: ссылку не записали в поле или массив, не вернули, не передали в неинлайненный вызов. Такой объект можно разместить в кадре стека. В .NET это появилось только недавно, и замер подтверждает границы (аллокации на вызов после прогрева, Release, вызывающие методы помечены `NoInlining`):

```csharp
sealed class Pt { public int X, Y; }

static int Obj(int a) { var p = new Pt { X = a, Y = a }; return p.X + p.Y; }
static int Arr(int a) { var x = new[] { a, a + 1, a + 2 }; return x[0] + x[1] + x[2]; }
static int Del(int a) { Func<int, int> f = y => y + a; return f(1); }
static int Esc(int a) { var p = new Pt { X = a }; _keep = p; return p.X; }
```

```
            .NET 8   .NET 9   .NET 10
Obj           24        0        0
Arr           40       40        0
Del           88       88       24
Esc           24       24       24
```

.NET 9 научился класть на стек небольшие объекты классов, .NET 10 — небольшие массивы и делегаты. В `Del` на .NET 10 из кучи ушёл только делегат; объект замыкания с полем `a` по-прежнему аллоцируется. `Esc` сохраняет ссылку в статическое поле — объект «убегает», и никакая версия его не уберёт.

Это **оптимизация, а не контракт**. Её нет в Tier 0, она зависит от инлайнинга (добавили логирование в вызываемый метод — он перестал инлайниться, аллокация вернулась), её не будет для объектов, живущих через `await` или захваченных замыканием. Если аллокация в горячем пути важна, её убирают явно — структурой, `stackalloc`, статической лямбдой, пулом (см. `Снижение аллокаций`), а escape analysis считают бонусом для обычного кода.

## unsafe: какие гарантии снимаются

Указатели в `unsafe`-блоке отключают сразу несколько механизмов рантайма:

- **проверку границ** — запись за конец буфера портит соседний объект вместо `IndexOutOfRangeException`;
- **типобезопасность и верифицируемость** — `*(long*)p` читает любые байты как что угодно;
- **отслеживание GC** — сырой указатель GC не видит: объект может переехать при уплотнении или быть собран;
- **инициализацию** — память из `NativeMemory.Alloc` или под `SkipLocalsInit` содержит мусор.

Ошибка проявляется не там, где сделана: `AccessViolationException`, который в .NET Core роняет процесс, падение внутри GC на следующей сборке или тихо неверные данные.

Оправдан `unsafe` в двух случаях: interop, где указатели — часть контракта native-API (включая `delegate* unmanaged<...>` для колбэков без делегата), и измеренный горячий путь в низкоуровневых библиотеках — парсерах, сериализаторах, кодеках. Почти всегда есть безопасная альтернатива: `Span<T>` со `stackalloc`, `MemoryMarshal.Cast` и `MemoryMarshal.Read<T>`, `BinaryPrimitives`, `Vector128<T>`, `LibraryImport` для P/Invoke. JIT убирает проверки границ в каноническом `for (int i = 0; i < span.Length; i++)`, так что выигрыш от указателей часто нулевой.

Промежуточный вариант — `Unsafe.Add`, `Unsafe.As`, `MemoryMarshal.GetArrayDataReference`. Они не требуют `AllowUnsafeBlocks` и работают через `ref`, который GC отслеживает при перемещении, поэтому закрепление не нужно, но проверки границ и типов отключают так же. Правило общее: изолировать опасный код в маленьком типе с безопасным API, проверять аргументы на входе и держать рядом бенчмарк — если unsafe-версия не быстрее, её удаляют.

## Закреплённые объекты

Уплотняющий GC двигает объекты и переписывает managed-ссылки на них. Адрес, отданный в native-код, ОС для асинхронного ввода-вывода или в сырой указатель, GC переписать не может — поэтому объект **закрепляют** (pinning):

```csharp
fixed (byte* p = buffer)
    NativeRead(p, buffer.Length);

var handle = GCHandle.Alloc(buffer, GCHandleType.Pinned);
try { Use(handle.AddrOfPinnedObject()); }
finally { handle.Free(); }

byte[] ioBuffer = GC.AllocateArray<byte>(64 * 1024, pinned: true);
```

`fixed` закрепляет на время блока и почти бесплатен: локальная помечается как pinned в GC info, и это имеет значение, только если сборка случилась внутри блока. `GCHandle` закрепляет на произвольное время, и забытый `Free` — одновременно утечка и фрагментация. Для API на `Memory<T>` есть `Pin()`, а P/Invoke-маршалер сам закрепляет blittable-массивы и строки на время вызова.

Вред закрепления — **фрагментация**: GC не может сдвинуть закреплённый объект и сдвинуть к нему соседей, вокруг остаются дыры. Хуже всего долго закреплённые буферы в Gen 0 — эфемерная куча перестаёт нормально уплотняться. Поэтому с .NET 5 есть **POH** (Pinned Object Heap): отдельная куча для объектов, закреплённых навсегда, которая не мешает уплотнению остальных. Долгоживущие буферы для I/O и interop выделяют там или берут из пула. Диагностика — `poh-size` в `dotnet-counters`, `gchandles` и `dumpheap -stat` с множеством `Free`-блоков в `dotnet-dump` (см. `LOH и фрагментация`, `Анализ дампа`).

## Что стоит ответить на собеседовании

Метод сначала компилируется в Tier 0 без оптимизаций, после примерно 30 вызовов перекомпилируется в Tier 1, а с .NET 8 Dynamic PGO по умолчанию собирает профиль, по которому Tier 1 девиртуализует и инлайнит горячие вызовы. Метод с долгим циклом, вызванный один раз, застрял бы в Tier 0 — OSR переводит его на оптимизированную версию посреди цикла через patchpoint. `unsafe` снимает проверку границ, типобезопасность и отслеживание указателей GC, а закрепление объектов фрагментирует кучу, для долгих случаев есть POH.

Сильный ответ объяснит, почему бенчмарк и прод видят разный машинный код (константы, мономорфный профиль, бюджет инлайнинга, tier) и как это проверить через `DisassemblyDiagnoser` и `DOTNET_JitDisasm`. Он точно скажет, что умеет escape analysis: объекты классов на стеке с .NET 9, массивы и делегаты с .NET 10, но не замыкания и не «убегающие» объекты — и что это хрупкая оптимизация, а не гарантия. И назовёт `Span<T>`, `MemoryMarshal` и `Unsafe` как способ получить скорость без сырых указателей и без пиннинга.
