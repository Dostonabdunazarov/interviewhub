Кэш — промежуточный слой быстрого хранилища между потребителем и медленным или дорогим источником. Он отдаёт частые результаты без обращения к источнику, снижая задержку и нагрузку, а платят за это тем, что данные могут быть устаревшими. Кэш легко добавить и трудно сделать правильно: почти все проблемы с ним — не про скорость, а про согласованность с источником и про то, что происходит, когда кэша вдруг нет.

## Уровни кэширования

Кэш живёт на каждом уровне пути запроса, и выбор уровня важнее выбора технологии.

| Уровень | Что кэширует | Инструмент |
| --- | --- | --- |
| Клиент | статику, ответы API | `Cache-Control`, `ETag` |
| CDN | статику, медиа, публичные ответы | Cloudflare, CloudFront |
| Reverse proxy | HTTP-ответы | NGINX, Varnish, Output Caching в ASP.NET Core |
| Процесс | справочники, конфигурацию | `IMemoryCache` |
| Распределённый | сущности, результаты запросов | Redis, Memcached |
| База | страницы данных | `shared_buffers`, page cache ОС |

Чем ближе к клиенту, тем дешевле попадание, но тем сложнее инвалидация: ответ, закэшированный в браузере на час, отозвать нельзя. Кэш в процессе обходится без сетевого хопа — наносекунды против сотен микросекунд у Redis, — но у каждого пода своя копия, и после изменения данных поды какое-то время отдают разное. Распределённый кэш общий для всех инстансов, зато добавляет сетевой вызов и ещё один компонент, который может упасть.

## Стратегии чтения и записи

**Cache-aside** — самый распространённый вариант. Приложение читает из кэша, при промахе идёт в базу и кладёт результат в кэш. Кэш ничего не знает об источнике.

```csharp
public async Task<Product?> GetAsync(long id, CancellationToken ct)
{
    var key = $"product:{id}";
    var cached = await _redis.StringGetAsync(key);
    if (cached.HasValue)
        return JsonSerializer.Deserialize<Product>(cached.ToString());

    var product = await _db.Products.AsNoTracking().FirstOrDefaultAsync(p => p.Id == id, ct);
    if (product is not null)
        await _redis.StringSetAsync(key, JsonSerializer.Serialize(product), TimeSpan.FromMinutes(5));
    return product;
}
```

**Read-through** — то же самое, но загрузку делает сам кэш-слой по заданной функции. С точки зрения кода это `GetOrCreate`: вызывающая сторона не видит промаха.

**Write-through** — запись идёт в кэш и в базу синхронно, кэш всегда свежий, но запись медленнее и в кэш попадает всё записанное, в том числе то, что никто не прочитает.

**Write-behind** — запись в кэш, а в базу асинхронно пачками. Очень быстро, но при падении кэша незаписанное теряется, поэтому годится только для данных, потерю которых можно пережить, например счётчиков просмотров.

## Инвалидация и гонка

Есть два способа поддерживать кэш согласованным с базой: ограничить время жизни (TTL) и сбрасывать ключ при изменении. На практике используют оба: сброс при записи плюс TTL как страховка на случай, если сброс потерялся.

При сбросе ключ надо **удалять, а не перезаписывать** новым значением. Перезапись даёт гонку двух писателей: первый обновил базу, второй обновил базу, второй записал кэш, первый записал кэш — и в кэше навсегда (до TTL) осталось старое значение. Удаление этой гонки не имеет: следующий читатель загрузит актуальное.

Но и у удаления есть своя, более редкая гонка с читателем:

```text
reader: промах, SELECT → старое значение
writer: UPDATE в базе
writer: DEL product:42
reader: SET product:42 = старое значение
```

Читатель загрузил данные до записи, а положил в кэш после удаления. Окно узкое, потому что чтение из базы обычно быстрее записи, но под нагрузкой оно срабатывает. Помогают короткий TTL, повторное удаление через небольшую задержку после записи или версия в значении: в кэш кладётся `{version, data}`, и запись с меньшей версией отвергается. Удалять ключ нужно после коммита транзакции, а не внутри неё, иначе читатель успеет загрузить ещё не изменённые данные.

В системе из многих сервисов надёжнее всего инвалидировать из потока изменений базы: CDC публикует изменённые строки в Kafka, отдельный потребитель удаляет ключи. Тогда сброс не зависит от того, не забыл ли разработчик вызвать его в очередном месте записи.

## Что кэшировать и под каким ключом

Кэш окупается на данных с высоким отношением чтений к записям и допустимой устарелостью: каталог, профили, справочники, результаты тяжёлых агрегатов. Не кэшируют то, что используется для принятия решения с деньгами: баланс перед списанием и цену в момент оплаты берут из базы.

Ключ должен включать всё, от чего зависит значение: `product:{id}:{lang}:{currency}`, иначе пользователи увидят чужую локаль. Полезно добавить в префикс версию формата (`v2:product:42`): после изменения схемы сериализации новая версия кода просто не увидит старых значений.

Промах по несуществующему ключу тоже стоит кэшировать. Иначе запросы к отсутствующему товару каждый раз доходят до базы, и этим пользуются как атакой — это называют cache penetration. Короткий TTL для «пустого» значения решает проблему.

## Вытеснение в Redis

Когда память кончается, Redis действует по `maxmemory-policy`. Значение по умолчанию — `noeviction`: при достижении лимита команды записи начинают возвращать ошибку. Для кэша это почти всегда неправильно.

```text
CONFIG SET maxmemory 8gb
CONFIG SET maxmemory-policy allkeys-lfu
```

`allkeys-lru` вытесняет давно не использованные ключи, `allkeys-lfu` — редко используемые и лучше держит стабильно популярное; варианты `volatile-*` трогают только ключи с TTL, что подходит, если в том же инстансе лежат данные без срока жизни. LRU и LFU в Redis приблизительные: решение принимается по выборке ключей (`maxmemory-samples`, по умолчанию 5), а не по точному глобальному порядку.

Отдельно о размере значений. Redis выполняет команды в одном потоке, и ключ на десятки мегабайт или `KEYS *` блокирует всех остальных клиентов. Большие объекты дробят на части, а для обхода ключей используют `SCAN`.

## Hit ratio — главная метрика

Эффект кэша считается одной формулой: до базы доходит доля промахов. При 10 000 RPS и hit ratio 95% база получает 500 RPS. Если hit ratio упал до 80%, база получает уже 2 000 — вчетверо больше при том же трафике. Поэтому алерт на падение hit ratio важнее алерта на падение отдельного узла кэша, а кэш с hit ratio около 50% почти бесполезен: он добавляет сетевой круг к каждому запросу и снимает с базы лишь половину нагрузки.

## Когда кэша нет

Самое опасное свойство кэша — система привыкает к нему. База, рассчитанная на 5% промахов, внезапно получает 100% трафика: после падения Redis, после рестарта с пустой памятью, после деплоя, сменившего формат ключей. Это проектируют заранее.

- **Короткие таймауты к кэшу**: 50–200 мс. Ждать кэш дольше, чем отвечает база, бессмысленно. В `StackExchange.Redis` по умолчанию 5 секунд, и это нужно менять.
- **Приложение стартует без кэша**: `abortConnect=false`, Redis не входит в liveness-проверку.
- **Circuit breaker** к кэшу, чтобы после серии ошибок сразу идти по резервному пути (статья `Circuit breaker`).
- **Ограничение конкурентности** запросов в базу, которые обычно закрывал кэш, чтобы она деградировала, а не падала.
- **Двухуровневый кэш**: даже несколько секунд локального кэша на поде снимают основную нагрузку от горячих ключей.

В .NET двухуровневую схему даёт `HybridCache` (пакет `Microsoft.Extensions.Caching.Hybrid`, появился вместе с .NET 9): L1 в памяти процесса, L2 в любом `IDistributedCache`, например Redis, плюс защита от одновременной загрузки одного ключа внутри процесса и инвалидация по тегам.

```csharp
var product = await _cache.GetOrCreateAsync(
    $"product:{id}",
    async ct => await _db.Products.AsNoTracking().FirstOrDefaultAsync(p => p.Id == id, ct),
    new HybridCacheEntryOptions
    {
        Expiration = TimeSpan.FromMinutes(5),
        LocalCacheExpiration = TimeSpan.FromSeconds(30)
    },
    tags: ["catalog"],
    cancellationToken: ct);
```

Одновременная загрузка популярного ключа сотнями запросов — отдельная проблема со своими решениями, ей посвящена следующая статья, `Cache stampede`.

## Что стоит ответить на собеседовании

Кэш — слой быстрого хранилища перед медленным источником, и уровень важнее технологии: клиент и CDN дёшевы, но плохо инвалидируются, кэш в процессе быстрее всего, но у каждого пода своя копия, распределённый общий, но добавляет сетевой вызов и точку отказа. Основная стратегия — cache-aside, write-through держит кэш свежим ценой медленной записи, write-behind быстр, но теряет данные.

Сильный ответ объяснит инвалидацию: TTL плюс удаление после коммита, удалять, а не перезаписывать, чтобы не получить гонку писателей, а остаточную гонку с читателем закрывать коротким TTL или версиями; в системе из многих сервисов — инвалидация из CDC. Назовёт hit ratio главной метрикой, `maxmemory-policy` с вытеснением вместо `noeviction` по умолчанию и кэширование пустых ответов. И скажет, что система должна переживать отсутствие кэша: короткие таймауты, circuit breaker, лимит конкурентности к базе и двухуровневый кэш вроде `HybridCache`.
