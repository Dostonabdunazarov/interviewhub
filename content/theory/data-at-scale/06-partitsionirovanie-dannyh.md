Слово «партиция» означает разное в зависимости от системы, и на собеседовании это источник путаницы. В PostgreSQL партиция — секция таблицы на том же сервере. В Kafka — упорядоченный лог внутри топика и единица параллелизма. В Cassandra и DynamoDB — группа строк с одинаковым ключом, которая целиком живёт на одном узле. В литературе по распределённым системам «партиционирование» часто вообще синоним шардирования. Общее у всех значений одно: данные делят по ключу на части, которые можно хранить, обслуживать и удалять независимо. Механика секций одной базы разобрана в статье `Партиционирование` раздела PostgreSQL; здесь — о том, как ключ партиции определяет поведение системы из многих узлов.

## Три способа делить данные

**Горизонтально** — разные строки в разных частях: по дате, по хешу ключа, по тенанту. Это то, что обычно имеют в виду, и это основа и секций, и шардов.

**Вертикально** — разные колонки в разных таблицах или хранилищах. Узкие горячие поля заказа (статус, сумма, даты) лежат в одной таблице, а большой JSON с деталями доставки — в другой, или вообще в объектном хранилище. Горячая таблица становится меньше, больше строк помещается в память, а широкие поля читаются только по требованию.

**Функционально** — разные домены в разных базах: заказы, каталог, пользователи. Аналитика уходит в колоночное хранилище через поток изменений, полнотекстовый поиск — в поисковый движок. Это самый дешёвый способ снять нагрузку с основной базы и обычно предшествует шардированию: часто после него шардировать уже не нужно.

## Ключ партиции — граница запроса и порядка

В системах, которые распределяют данные по узлам, ключ партиции задаёт два свойства сразу. Во-первых, запрос с этим ключом идёт на один узел, а без него — на все. Во-вторых, внутри партиции данные упорядочены, а между партициями порядка нет.

В Cassandra первичный ключ состоит из ключа партиции и кластеризующих колонок. Первый определяет узел, вторые — порядок строк внутри партиции.

```sql
CREATE TABLE sensor_readings (
    sensor_id   uuid,
    day         date,
    ts          timestamp,
    value       double,
    PRIMARY KEY ((sensor_id, day), ts)
) WITH CLUSTERING ORDER BY (ts DESC);

SELECT ts, value FROM sensor_readings
WHERE sensor_id = 6f1c2a9e-0b7d-4c43-9a51-2d3f6e8b7c10 AND day = '2026-10-06'
LIMIT 100;
```

Двойные скобки делают ключом партиции пару «датчик плюс день», а `ts` сортирует показания внутри неё. Запрос «последние сто показаний датчика за сегодня» читает одну партицию последовательно — это самый быстрый путь в Cassandra. Запрос «все датчики со значением выше порога» по такой схеме не выполнить эффективно вовсе: модель данных в таких системах строится от запросов, и под другой запрос заводят другую таблицу.

DynamoDB устроен так же: partition key определяет партицию, sort key — порядок внутри неё. Kafka — тоже: ключ сообщения хешируется в номер партиции, и порядок гарантирован только для событий с одним ключом. Подробно про Kafka — в статье `Партиции и порядок событий`.

## Раздутые партиции

Если ключ партиции — только `sensor_id`, партиция растёт бесконечно: каждое показание датчика за всю его жизнь лежит в одной партиции на одном наборе реплик. Такие партиции медленно читаются, тяжело уплотняются и неравномерно распределяют диск. В Cassandra ориентир — держать партицию в пределах сотни мегабайт, а лучше заметно меньше.

Лечение — добавить в ключ временное ведро, как `day` в примере выше. Размер ведра подбирают по объёму: день для датчика, пишущего раз в секунду, час для потока в тысячи событий в секунду. Цена — запрос за длинный период теперь читает несколько партиций, и приложение собирает их само.

## Горячие партиции

Обратная проблема — партиция нормального размера, на которую приходится непропорциональная доля нагрузки: популярный товар, знаменитость в соцсети, крупный тенант. Все запросы к ней идут на одни и те же узлы, а остальные простаивают. В DynamoDB у одной партиции есть собственный потолок пропускной способности, и упираются именно в него, даже если суммарной ёмкости таблицы хватает с запасом.

Решение для записи — искусственный суффикс, который размазывает один логический ключ по нескольким партициям:

```csharp
public static string WriteKey(string itemId) =>
    $"{itemId}#{Random.Shared.Next(16)}";

public static IEnumerable<string> ReadKeys(string itemId) =>
    Enumerable.Range(0, 16).Select(i => $"{itemId}#{i}");
```

Запись идёт в одну из 16 партиций, чтение собирает все 16 и агрегирует. Так считают лайки и просмотры у горячих объектов. Дробить стоит только известные горячие ключи: для остальных это шестнадцатикратное удорожание чтения без пользы. Горячее чтение обычно проще снять кэшем.

С монотонными ключами горячей становится последняя партиция: если ключ — время, вся текущая запись идёт в одно место. Для секций в одной базе это нормально и даже хорошо, а для распределённой системы означает, что вся запись приходится на один узел. Поэтому в распределённых хранилищах время ставят в кластеризующую часть, а ключом партиции делают что-то с высокой кардинальностью.

## Вторичные индексы

Когда данные разделены по одному ключу, а искать нужно по другому, есть два варианта индекса, и оба с компромиссом.

| | Локальный | Глобальный |
| --- | --- | --- |
| Где лежит | в каждой партиции, только по её строкам | отдельно, разделён по индексируемому полю |
| Запись | затрагивает одну партицию | затрагивает партицию данных и партицию индекса |
| Чтение по индексу | обход всех партиций | одна партиция индекса |
| Согласованность | синхронная | обычно асинхронная |

Локальный индекс дёшев при записи, но запрос по нему превращается в scatter-gather по всем узлам. Глобальный быстр при чтении, но обновляется асинхронно, и только что записанная строка может какое-то время не находиться. В DynamoDB это прямо отражено в API: local secondary index живёт в той же партиции и создаётся вместе с таблицей, а global secondary index — отдельная структура с собственным ключом и согласованностью «в конечном счёте». Та же развилка возникает при самостоятельном шардировании: таблица `email → user_id`, разделённая по email и наполняемая из потока изменений, — это глобальный индекс, собранный руками.

## Партиции и жизненный цикл данных

Разделение по времени нужно не только для скорости запросов, но и для управления данными. Свежие партиции — горячие, к ним идут почти все запросы; старые читают редко. Это позволяет держать разные части на разных носителях и удалять устаревшее целой партицией, а не построчно.

В ClickHouse ключ партиционирования задаётся отдельно от ключа сортировки, и его назначение — именно управление данными:

```sql
CREATE TABLE events
(
    event_time DateTime,
    user_id    UInt64,
    type       LowCardinality(String)
)
ENGINE = MergeTree
PARTITION BY toYYYYMM(event_time)
ORDER BY (user_id, event_time)
TTL event_time + INTERVAL 12 MONTH;
```

Партиция — месяц, старые строки удаляет TTL при фоновых слияниях, а с настройкой `ttl_only_drop_parts` — целыми кусками данных. Документация ClickHouse прямо предостерегает от слишком мелкого партиционирования: тысячи партиций замедляют вставку и слияния, а скорости запросов не добавляют — для этого служит ключ сортировки. Та же логика работает в PostgreSQL и в объектных хранилищах с раскладкой файлов по датам: партиция — единица хранения и удаления, а не индекс.

## Число партиций и перебалансировка

Количество партиций выбирают с запасом, потому что менять его дорого. Если ключ хешируется в номер партиции, увеличение их числа перекладывает большую часть ключей: в Kafka после добавления партиций события одного ключа начинают попадать в новую партицию, и порядок между старыми и новыми событиями этого ключа теряется. Поэтому распределённые хранилища используют одну из трёх схем: фиксированное число партиций намного больше числа узлов, которые переезжают целиком (Redis Cluster, Citus); динамическое деление разросшихся партиций (HBase, chunk'и MongoDB); число партиций, пропорциональное числу узлов, через виртуальные узлы на кольце (Cassandra). Как переносить партиции между узлами под нагрузкой — в статье `Решардинг без простоя`.

## Что стоит ответить на собеседовании

Партиционирование — деление данных по ключу на независимые части, и сначала стоит уточнить, о какой системе речь: секции таблицы в PostgreSQL на одном сервере, партиции Kafka как единица порядка и параллелизма или партиции Cassandra и DynamoDB, распределённые по узлам. Делить можно горизонтально, вертикально и функционально, и функциональное разделение по доменам часто снимает необходимость шардировать.

Сильный ответ объяснит, что ключ партиции одновременно задаёт маршрут запроса и границу порядка, поэтому модель данных строят от запросов. Назовёт две болезни: раздутые партиции лечат временным ведром в ключе, горячие — суффиксом для записи и кэшем для чтения, а монотонный ключ партиции в распределённой системе сводит всю запись к одному узлу. Сравнит локальные вторичные индексы, дешёвые при записи, но требующие обхода всех партиций, с глобальными, быстрыми при чтении, но асинхронными. И скажет, что число партиций выбирают с запасом: изменить его при хешировании — значит перераспределить ключи и потерять порядок.
