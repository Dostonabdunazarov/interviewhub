Cache stampede, он же dogpile или thundering herd, случается, когда ключ, который читают тысячи раз в секунду, исчезает из кэша, и все эти запросы одновременно идут пересчитывать значение в базу. Кэш при этом исправен, и база тоже — до того момента, пока на неё не обрушится несколько тысяч одинаковых тяжёлых запросов. Защита строится на трёх идеях: пересчитывает кто-то один, остальные тем временем получают устаревшее значение, а самые популярные ключи вообще не должны исчезать внезапно.

## Масштаб проблемы

Пусть ключ читают 20 000 раз в секунду, а пересчёт занимает 200 мс. Пока первый запрос считает значение, придут ещё 20 000 × 0,2 = 4 000 запросов, и каждый из них тоже увидит промах и тоже пойдёт в базу. Четыре тысячи одинаковых агрегатов замедляют базу, пересчёт идёт уже не 200 мс, а секунду, за это время приходят новые — положительная обратная связь, которая заканчивается падением.

```text
t=0       ключ истёк
t=0..200  4 000 промахов → 4 000 одинаковых SELECT
t=200..   база перегружена, пересчёт 1 с, промахов уже 20 000
```

Важно, что для этого не нужен отказ кэша: достаточно штатного истечения TTL у одного горячего ключа.

## Три похожие проблемы

Stampede часто путают с двумя соседними проблемами, и у каждой своё лечение.

| Проблема | Что происходит | Основная защита |
| --- | --- | --- |
| Stampede | истёк один горячий ключ | один пересчитывает, остальные ждут или берут устаревшее |
| Лавина (avalanche) | одновременно истекло много ключей или упал кэш | джиттер TTL, прогрев, защита базы |
| Проникновение (penetration) | запросы к несуществующим ключам | кэширование пустого ответа, фильтр Блума |

Ниже — защита от первой, но джиттер из второй строки обязателен в любом случае.

## Объединение запросов внутри процесса

Первый рубеж — не пускать в базу больше одного запроса с одного пода. Сотни конкурентных запросов на одном инстансе ждут одну и ту же задачу загрузки.

```csharp
public sealed class Coalescer<T>
{
    private readonly ConcurrentDictionary<string, Lazy<Task<T>>> _inflight = new();

    public async Task<T> RunAsync(string key, Func<Task<T>> load)
    {
        var lazy = _inflight.GetOrAdd(key, _ => new Lazy<Task<T>>(load));
        try
        {
            return await lazy.Value;
        }
        finally
        {
            _inflight.TryRemove(new KeyValuePair<string, Lazy<Task<T>>>(key, lazy));
        }
    }
}
```

`Lazy` нужен потому, что `GetOrAdd` может вызвать фабрику несколько раз при гонке, а запускать загрузку должен ровно один вызов. Удаление по паре ключ-значение гарантирует, что мы не удалим чужую, более новую загрузку. На практике писать это руками не нужно: `HybridCache.GetOrCreateAsync` из .NET 9 делает то же из коробки. Но у объединения внутри процесса есть потолок: при 100 подах в базу всё равно уйдёт 100 запросов, а не один.

## Распределённый lease

Чтобы пересчитывал один запрос на весь кластер, нужен общий замок с ограниченным временем жизни — lease. Получивший его пересчитывает значение, остальные ждут короткое время или отдают устаревшее.

```text
SET lock:product:42 9f3c… NX PX 5000
```

`NX` — записать, только если ключа нет; `PX 5000` — удалить через пять секунд, даже если держатель упал. Снимать lease можно только своим токеном, иначе процесс, у которого lease уже истёк, удалит чужой:

```csharp
var token = Guid.NewGuid().ToString("N");
var lockKey = $"lock:{key}";

if (await _db.StringSetAsync(lockKey, token, TimeSpan.FromSeconds(5), When.NotExists))
{
    try
    {
        var fresh = await _load();
        await _db.StringSetAsync(key, Serialize(fresh), TimeSpan.FromMinutes(10));
        return fresh;
    }
    finally
    {
        await _db.ScriptEvaluateAsync(
            "if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) end return 0",
            new RedisKey[] { lockKey },
            new RedisValue[] { token });
    }
}

return await WaitForValueOrStaleAsync(key);
```

Проверка и удаление выполняются одним Lua-скриптом, потому что пара `GET` и `DEL` неатомарна. Здесь lease — оптимизация, а не гарантия корректности: если он истёк во время долгого пересчёта, в базу придут два запроса вместо одного, и это допустимо. Для задач, где два исполнителя недопустимы, нужен fencing-токен, это тема статьи `Распределённые блокировки`. Facebook решал ту же проблему механизмом leases в memcache: при промахе сервер выдаёт токен на пересчёт только одному клиенту, остальным предлагает немного подождать.

## Soft и hard TTL

Lease решает, кто пересчитывает, но остальным всё ещё приходится ждать. Схема stale-while-revalidate убирает ожидание: значение хранится дольше, чем считается свежим.

```text
value + fresh_until (soft, 60 с) ; TTL ключа в Redis (hard, 10 мин)

now < fresh_until           → отдать
fresh_until ≤ now < hard    → отдать устаревшее + один фоновый пересчёт под lease
ключа нет                   → синхронный пересчёт под lease
```

Пользователи почти никогда не ждут, а база получает один запрос на ключ. Цена — короткое время пользователи видят старые данные. Для карточки товара это нормально, для цены в момент оплаты — нет, её берут из базы. Та же схема даёт stale-if-error: если пересчёт упал, отдаётся устаревшее значение вместо ошибки.

## Вероятностное раннее обновление

Алгоритм XFetch обходится без замков вовсе. Каждый запрос с небольшой вероятностью, растущей по мере приближения к истечению, сам пересчитывает значение заранее. Значение обновляют, если

```text
now − Δ · β · ln(rand()) ≥ expiry
```

где Δ — время последнего пересчёта, β — коэффициент агрессивности, обычно 1, а `rand()` — равномерное число из (0, 1]. Логарифм отрицателен, поэтому левая часть — это текущее время плюс случайный сдвиг вперёд, пропорциональный стоимости пересчёта. Дорогие ключи начинают обновляться раньше, дешёвые — почти в момент истечения, и в среднем ключ обновляет один запрос незадолго до того, как он пропадёт. Достоинство — никакой координации; недостаток — надо хранить рядом со значением Δ и время истечения.

## Инвалидация без исчезновения ключа

Stampede провоцирует не только TTL, но и инвалидация: изменили популярный товар, удалили ключ — и тысячи запросов разом получили промах. Для горячих ключей потребитель события об изменении не удаляет ключ, а пересчитывает и записывает новое значение или сдвигает `fresh_until` в прошлое, чтобы сработала схема soft TTL. Ключ не исчезает ни на мгновение.

Это не противоречит правилу «удалять, а не перезаписывать» из статьи `Кэширование`: там речь о конкурентных писателях из кода приложения, а здесь перезапись делает один потребитель потока изменений по порядку событий, и гонки писателей нет.

## Джиттер и прогрев

Значения, записанные одновременно, одновременно и истекают: после деплоя, прогрева или восстановления кэша тысячи ключей с одинаковым TTL умрут в одну секунду. Это уже лавина, и защита от неё — случайный разброс времени жизни.

```csharp
var ttl = TimeSpan.FromSeconds(540 + Random.Shared.NextDouble() * 120);
```

Здесь TTL равномерно распределён в диапазоне от 540 до 660 секунд. Для заранее известных топ-ключей можно пойти дальше и вообще не давать им истекать: фоновая задача обновляет их по расписанию.

## Последний рубеж — база

Все механизмы выше могут не сработать: lease упал вместе с Redis, ключей слишком много. Поэтому сама база защищена отдельно: лимит конкурентности на пересчёты данного типа (bulkhead), circuit breaker на тяжёлые запросы, отдача устаревшего при ошибке. Цель — чтобы при худшем сценарии часть пользователей увидела старые данные или отказ, а не легла вся система.

## Что выбрать

| Ситуация | Решение |
| --- | --- |
| Умеренная нагрузка, несколько подов | объединение запросов внутри процесса |
| Горячие ключи, много подов | soft и hard TTL плюс распределённый lease |
| Устаревшее отдавать нельзя | lease плюс ожидание результата с таймаутом |
| Известные топ-ключи | фоновое обновление, ключ без истечения |
| Пересчёт дорогой, координация нежелательна | XFetch |

## Что стоит ответить на собеседовании

Cache stampede — одновременный промах тысяч запросов по одному истёкшему горячему ключу, который превращает штатное истечение TTL в перегрузку базы с положительной обратной связью. Сильный ответ сразу считает масштаб: RPS ключа, умноженный на время пересчёта, — столько одинаковых запросов придёт в базу.

Защита многослойная: объединение запросов внутри процесса снижает нагрузку до числа подов; распределённый lease через `SET NX PX` со снятием своим токеном через Lua сводит её к одному запросу; soft и hard TTL позволяют отдавать устаревшее, пока идёт фоновый пересчёт; XFetch обновляет ключ заранее без координации. Горячие ключи при изменении перезаписывают, а не удаляют, TTL разбрасывают джиттером, а базу защищают лимитом конкурентности. И отличает stampede от лавины, когда истекает много ключей разом, и от проникновения, когда запрашивают несуществующее.
