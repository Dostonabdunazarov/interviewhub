Деплой — это доставка нового кода на серверы, релиз — момент, когда пользователи начинают им пользоваться. Feature flag разводит эти события: код раскатывается выключенным, включается для сотрудников, затем для процента пользователей, а при проблеме выключается за секунды изменением конфигурации, без отката и без пайплайна. Инфраструктурный canary (см. `Rolling, blue-green, canary`) ограничивает радиус поражения по подам, флаг — по пользователям и сегментам, и часто это дешевле.

Цена — ветвления в коде, комбинации состояний, которые надо тестировать, и флаги, которые никто не удаляет. На собеседовании senior-уровня спрашивают как раз про цену: как устроена оценка флага, что будет, если сервис флагов недоступен, и как через год не обнаружить в коде двести флагов с неизвестным назначением.

## Типы флагов

| Тип | Пример | Срок жизни | Кто переключает |
| --- | --- | --- | --- |
| release | новый чекаут | дни–недели, до 100% и удаления | команда |
| experiment | вариант цены в A/B-тесте | длительность эксперимента | продукт |
| ops / kill switch | отключить рекомендации под нагрузкой | постоянно | дежурный |
| permission | функция тарифа Enterprise | постоянно | бизнес-логика |

Тип определяет, как с флагом обращаться. Release-флаг временный и должен быть удалён после раскатки на 100%. Experiment привязан к эксперименту и требует стабильного распределения пользователей по вариантам. Kill switch живёт постоянно, переключается дежурным без деплоя и по умолчанию включён: выключение — это деградация. Permission-флаг — по сути часть бизнес-модели, и ему место скорее в системе прав, чем в платформе флагов.

Частая проблема — смешение типов: release-флаг «временно» оставляют как аварийный выключатель, и через год никто не знает, можно ли его удалить и что сломается при выключении.

## Microsoft.FeatureManagement

Библиотека строит флаги поверх `IConfiguration`: значение флага — это либо `true`/`false`, либо список фильтров, и флаг включён, если сработал хотя бы один. Встроенные фильтры — `Microsoft.Percentage`, `Microsoft.TimeWindow` и `Microsoft.Targeting`:

```json
"FeatureManagement": {
  "Recommendations": true,
  "BlackFridayBanner": {
    "EnabledFor": [
      {
        "Name": "Microsoft.TimeWindow",
        "Parameters": {
          "Start": "Fri, 27 Nov 2026 00:00:00 GMT",
          "End": "Mon, 30 Nov 2026 23:59:59 GMT"
        }
      }
    ]
  },
  "NewCheckout": {
    "EnabledFor": [
      {
        "Name": "Microsoft.Targeting",
        "Parameters": {
          "Audience": {
            "Users": [ "qa-user-1" ],
            "Groups": [ { "Name": "employees", "RolloutPercentage": 100 } ],
            "DefaultRolloutPercentage": 5
          }
        }
      }
    ]
  }
}
```

Разница между процентным фильтром и таргетингом важна. `Microsoft.Percentage` бросает монетку при каждой оценке, поэтому один пользователь может получить новый чекаут на одном запросе и старый на следующем. Таргетинг считает процент по хэшу идентификатора пользователя и имени флага: пользователь стабильно попадает в один вариант, а при росте процента с 5 до 25 уже включённые остаются включёнными. Для всего, что видит человек, нужен таргетинг.

Таргетингу нужен контекст — кто пользователь и в каких он группах:

```csharp
builder.Services.AddHttpContextAccessor();
builder.Services.AddFeatureManagement()
    .WithTargeting<UserTargetingContextAccessor>();

app.MapPost("/checkout", async (IFeatureManagerSnapshot features, CheckoutRequest req) =>
    await features.IsEnabledAsync(Flags.NewCheckout)
        ? await NewCheckout.Handle(req)
        : await LegacyCheckout.Handle(req));

sealed class UserTargetingContextAccessor(IHttpContextAccessor http) : ITargetingContextAccessor
{
    public ValueTask<TargetingContext> GetContextAsync()
    {
        var user = http.HttpContext?.User;
        return ValueTask.FromResult(new TargetingContext
        {
            UserId = user?.FindFirst("sub")?.Value,
            Groups = user?.FindAll("groups").Select(c => c.Value).ToList() ?? []
        });
    }
}
```

`IFeatureManagerSnapshot` фиксирует значение флага на время запроса: если конфигурация обновится посреди обработки, запрос всё равно пройдёт одной веткой. Для MVC есть атрибут `[FeatureGate]`, для Razor — тег-хелпер `<feature>`. Свои фильтры пишутся через `IFeatureFilter`, например «включено для тенантов из списка».

## Где хранить и как доставлять

**appsettings и ConfigMap.** Достаточно для старта, но переключение — это деплой или обновление конфигурации, а не секундная операция. Для kill switch такого мало.

**Azure App Configuration.** Флаги хранятся централизованно, провайдер конфигурации периодически их перечитывает, а middleware инициирует обновление по запросам:

```csharp
builder.Configuration.AddAzureAppConfiguration(o => o
    .Connect(new Uri(endpoint), new DefaultAzureCredential())
    .UseFeatureFlags(ff => ff.SetRefreshInterval(TimeSpan.FromSeconds(30))));
builder.Services.AddAzureAppConfiguration();

app.UseAzureAppConfiguration();
```

**Внешние платформы** — LaunchDarkly, Unleash, flagd, Flagsmith. Они дают UI, аудит, сегменты, эксперименты и стриминг обновлений. Чтобы не привязывать код к вендору, используют **OpenFeature** — вендор-нейтральный SDK, где платформа подключается провайдером, а код видит только `client.GetBooleanValueAsync("new-checkout", false, context)`.

Независимо от хранилища к системе флагов есть требования:

- **Оценка локальная.** SDK держит правила в памяти и получает обновления стримингом или поллингом. Сетевой вызов на каждую проверку — латентность и новая точка отказа на горячем пути.
- **Безопасное значение по умолчанию.** Если платформа недоступна при старте, используется default из кода: для release-флага «выключено», для kill switch — «функция работает».
- **Аудит и права.** Переключение флага в проде — изменение продакшена: кто, когда, с какого значения на какое, с уведомлением в канал инцидентов.
- **Наблюдаемость.** Значение флага пишется атрибутом в трассировку и логи — в OpenTelemetry для этого есть семантические соглашения `feature_flag.*`. Иначе при всплеске ошибок не видно, что падает только новый вариант.
- **Кэш.** Если ответ зависит от флага, флаг или вариант должен входить в ключ кэша, иначе пользователь из контрольной группы получит закэшированный ответ нового варианта.

## Согласованность в распределённой системе

Обновление флага доходит до подов и сервисов с разницей в секунды, а в пределах интервала опроса — и дольше. Если `orders` и `billing` независимо оценивают один флаг, на одном и том же запросе они могут принять разные решения: заказ оформлен по новым правилам, а счёт выставлен по старым. Решение принимают один раз на входе и передают дальше — заголовком или через baggage, — а нижестоящие сервисы доверяют переданному варианту.

С асинхронным обменом хуже: событие, ушедшее в Kafka с новым полем, флагом не отзывается. Формат сообщения версионируют явно, а консьюмер должен понимать обе версии до того, как продюсер включит новую.

## Флаги и миграции БД

Флаг не откатывает схему. Новый код за выключенным флагом всё равно работает с той же базой, поэтому схема меняется по expand/contract (см. `Миграции БД при нескольких репликах`), а флаг управляет переключением поведения между шагами:

1. Expand: добавить колонку или таблицу, старый код её не замечает.
2. Двойная запись: оба пути пишут и в старую, и в новую структуру.
3. Флаг переключает чтение на новую структуру — сначала для части пользователей; откат — выключить флаг.
4. Когда флаг на 100% и стабилен, убрать старый путь вместе с флагом, затем contract — удалить старую колонку.

Старую колонку нельзя удалять, пока в коде есть ветка, которая её читает, даже если флаг выключен везде: выключенный флаг — это всё ещё код, который можно включить.

## Тестирование комбинаций

N независимых флагов дают 2^N состояний, проверить все нельзя. Работающая практика: тесты прогоняются для текущего прод-состояния и для следующего планируемого (флаг включён), флаги не вкладываются друг в друга, а в тестах значения задаются явно, а не наследуются из общего окружения:

```csharp
var factory = new WebApplicationFactory<Program>().WithWebHostBuilder(b =>
    b.ConfigureAppConfiguration((_, cfg) => cfg.AddInMemoryCollection(new Dictionary<string, string?>
    {
        [$"FeatureManagement:{Flags.NewCheckout}"] = "true"
    })));
```

Тест с параметром `[InlineData(true)] [InlineData(false)]` для каждого release-флага покрывает обе ветки, пока флаг жив, и удаляется вместе с ним.

## Технический долг

Каждый флаг — две ветки кода, которые нужно поддерживать и понимать. Без дисциплины флаги копятся, и удалить их становится страшно. Работающий набор мер:

- у каждого флага есть тип, владелец и дата удаления; задача на удаление заводится вместе с задачей на функцию, и удаление флага — часть её definition of done;
- флаги объявлены в одном месте, а не строками по коду — тогда реестр можно проверить в CI;
- проверка в CI падает, если release-флаг пережил свою дату;
- метрика оценок: флаг две недели на 100% везде — кандидат на удаление, флаг без оценок — мёртвый код. Платформы умеют это сами: Unleash помечает флаги как потенциально устаревшие по типу и возрасту, LaunchDarkly показывает ссылки на флаг в коде и неиспользуемые флаги;
- имена флагов никогда не переиспользуются.

```csharp
public static class Flags
{
    [Flag(Owner = "checkout-team", RemoveBy = "2026-12-15")]
    public const string NewCheckout = "NewCheckout";
}

[Fact]
public void ReleaseFlagsAreNotExpired()
{
    var expired = typeof(Flags).GetFields()
        .Select(f => (f.Name, Meta: f.GetCustomAttribute<FlagAttribute>()!))
        .Where(x => DateOnly.Parse(x.Meta.RemoveBy) < DateOnly.FromDateTime(DateTime.UtcNow))
        .Select(x => $"{x.Name} ({x.Meta.Owner})");
    Assert.Empty(expired);
}
```

Последний пункт списка — не формальность. В 2012 году Knight Capital при деплое переиспользовал старый флаг; на одном сервере новый код не установился, и флаг включил давно мёртвую торговую логику. За 45 минут компания потеряла около 440 млн долларов.

## Что стоит ответить на собеседовании

Feature flag отделяет деплой от релиза: код раскатывается выключенным, включается для сотрудников, затем для процента пользователей, а выключается без отката. Флаги бывают release, experiment, ops/kill switch и permission, и у них разный срок жизни и владелец. В .NET это `Microsoft.FeatureManagement` с фильтрами процента, временного окна и таргетинга, где таргетинг даёт стабильное распределение по хэшу пользователя; для переключения без рестарта — Azure App Configuration или внешняя платформа через OpenFeature.

Сильный ответ добавит требования к системе флагов: локальная оценка, безопасный default при недоступности платформы, аудит переключений, значение флага в трассировке и в ключе кэша. Скажет, что флаг не решает: не откатывает схему, поэтому миграции идут по expand/contract, и не даёт согласованности между сервисами — решение принимают на входе и передают дальше. И опишет борьбу с долгом: владелец и дата удаления у каждого флага, проверка в CI, метрики устаревших флагов и запрет на переиспользование имён — с Knight Capital как аргументом.
