Пайплайн обычно описывают как цепочку «собрать, протестировать, задеплоить», но на собеседовании senior-уровня интересует другое: что гарантирует, что в прод попало ровно то, что протестировали, и как быстро вернуть предыдущую версию, когда что-то пошло не так. Быстрый откат не появляется в момент инцидента — его закладывают в устройство пайплайна заранее: неизменяемый артефакт, декларативный деплой с историей и схема БД, совместимая с прошлой версией кода.

## Стадии

```text
commit
  → restore, build, unit-тесты
  → интеграционные тесты (Testcontainers)
  → образ: тег = git sha, push в registry
  → сканирование, SBOM, подпись
  → деплой в dev → smoke и e2e
  → продвижение в staging того же digest → нагрузочный smoke
  → продвижение в prod: rolling или canary с проверкой метрик
  → при деградации: автоматический откат на предыдущий digest
```

Порядок подчинён одной идее — падать как можно раньше и дешевле. Unit-тесты отрабатывают за секунды и не требуют инфраструктуры. Интеграционные тесты поднимают настоящий PostgreSQL или Kafka в контейнере через Testcontainers: моки репозиториев не поймают ни ошибку в SQL, ни несовместимую миграцию. Там же применяют миграции к пустой базе и проверяют, что в модели нет изменений без миграции — подробности в статье `Миграции БД при нескольких репликах`.

## Build once, deploy many

Образ собирается **один раз** и дальше продвигается по окружениям без изменений. Пересборка «для прода» из того же коммита даёт другой артефакт: могли обновиться базовый образ, транзитивные пакеты, сам SDK. Тогда протестирован один бинарник, а в проде работает другой.

Отсюда два правила:

- **Идентификатор версии — digest**, а не тег. `orders-api@sha256:5f1c…` однозначно указывает на содержимое, а тег можно перезаписать. Теги вроде `latest` или `prod` для деплоя не годятся вовсе: откатиться «на прошлый latest» невозможно, потому что его уже нет. В registry включают неизменяемые теги.
- **Конфигурация окружения — снаружи образа.** Строки подключения, адреса, флаги приходят из Helm values, ConfigMap и менеджера секретов. Образ, внутри которого лежит `appsettings.Production.json` с адресом базы, нельзя продвинуть из staging в prod — его придётся пересобрать.

## Пайплайн на GitHub Actions

Сборка публикует образ и передаёт дальше digest, а не тег:

```yaml
jobs:
  build:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
    outputs:
      digest: ${{ steps.push.outputs.digest }}
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-dotnet@v4
        with:
          dotnet-version: "10.0.x"
      - run: dotnet test -c Release
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - uses: docker/setup-buildx-action@v3
      - id: push
        uses: docker/build-push-action@v6
        with:
          push: true
          tags: ghcr.io/acme/orders-api:${{ github.sha }}

  deploy-prod:
    needs: build
    runs-on: ubuntu-latest
    environment: production
    steps:
      - uses: actions/checkout@v4
      - run: ./deploy.sh "${{ needs.build.outputs.digest }}"
```

`environment: production` даёт ручное подтверждение, свои секреты окружения и историю деплоев. Кэш слоёв и порядок `COPY`, от которых зависит скорость шага сборки, разобраны в статье `Минимальный образ .NET`.

## Деплой через Helm

Push-модель: CI сам применяет изменения к кластеру.

```bash
helm upgrade --install orders-api ./charts/orders-api \
  --namespace orders \
  --values values-prod.yaml \
  --set image.digest="$IMAGE_DIGEST" \
  --rollback-on-failure --wait --timeout 10m
```

`--rollback-on-failure` (в Helm 3 он назывался `--atomic`, старое имя в Helm 4 работает с предупреждением) откатывает релиз, если ресурсы не стали готовыми за `--timeout`. Каждый релиз — ревизия, и ручной откат делается одной командой:

```bash
helm history orders-api -n orders
helm rollback orders-api 41 -n orders
```

Ограничение Helm — он смотрит только на готовность ресурсов, то есть на readiness подов. Под, который отвечает `200` на пробу и `500` на каждый пятый запрос, Helm считает успешным. Анализ по метрикам — ошибкам и латентности — делают Argo Rollouts, Flagger или отдельный шаг пайплайна после деплоя (см. `Rolling, blue-green, canary`).

## GitOps

Pull-модель: желаемое состояние кластера лежит в git-репозитории окружений, а контроллер внутри кластера (Argo CD, Flux) приводит кластер к нему. CI ничего не применяет — он только коммитит новый digest:

```yaml
image:
  repository: ghcr.io/acme/orders-api
  digest: sha256:5f1c...
```

Что это даёт:

- **аудит** — каждое изменение прода — это коммит с автором и ревью;
- **откат тем же механизмом** — `git revert` коммита с digest, и контроллер вернёт прошлую версию;
- **безопасность** — у CI нет доступа к кластеру вообще, только право писать в репозиторий окружений;
- **дрейф виден** — ручная правка в кластере отображается как расхождение с git.

Обратная сторона — ловушка на инциденте: `kubectl rollout undo` в GitOps-кластере контроллер отменит при следующей синхронизации, потому что в git по-прежнему записана новая версия. Откатываться нужно через git, и это должно быть в runbook.

## Безопасность самого пайплайна

Пайплайн, который умеет деплоить в прод, — привлекательная цель. Минимальный набор мер:

- **без долгоживущих ключей** — доступ к облаку и registry через OIDC-федерацию: раннер получает короткоживущий токен на конкретный репозиторий и окружение;
- **сканирование** образа и зависимостей (Trivy, Grype, `dotnet list package --vulnerable`) с порогом, который ломает сборку;
- **SBOM и подпись** — cosign подписывает образ, admission-контроллер в кластере не пустит неподписанный;
- **минимальные права** — раннер, собирающий PR из форков, не видит секретов окружений;
- **поиск секретов** в коде — gitleaks или встроенное сканирование платформы, подробнее в статье `Секреты и ротация`.

## Откат как отрепетированная операция

Откатиться на предыдущий digest технически можно всегда. Сломать систему он может по трём причинам, и все три решаются до инцидента:

- **несовместимая миграция** — старый код не работает с новой схемой. Лечится правилом expand → contract: каждая миграция совместима с предыдущей версией кода;
- **несовместимые контракты** — новая версия уже отправила в Kafka сообщения формата, который старая не читает. Контракты версионируют с совместимостью в обе стороны (см. `Версионирование контрактов`);
- **данные в новом формате** — их откат образа не вернёт; здесь поможет только исправление вперёд.

Рискованные функции отделяют от деплоя флагами: код раскатывается выключенным, а «откат» — это выключение флага за секунды, без пайплайна. Сам откат репетируют: откат в staging как обязательный шаг релиза или регулярные учения. Непроверенный откат в момент инцидента оказывается ещё одним непроверенным деплоем.

Качество процесса меряют четырьмя метриками DORA: частота деплоев, время от коммита до прода, доля неудачных изменений и время восстановления. Хороший откат напрямую сокращает последнее.

## Что стоит ответить на собеседовании

Пайплайн: сборка и unit-тесты, интеграционные тесты на настоящей инфраструктуре в Testcontainers, образ с тегом git sha, сканирование и подпись, затем продвижение по окружениям. Главный принцип — build once, deploy many: образ собирается один раз и продвигается по digest, а конфигурация окружения живёт вне образа, поэтому в проде работает ровно то, что протестировали.

Сильный ответ сравнит push-деплой через Helm с `--rollback-on-failure` и GitOps, где откат — это `git revert`, а ручной `rollout undo` будет отменён контроллером. Объяснит, что Helm проверяет только readiness, а не ошибки и латентность. И скажет, что быстрый откат обеспечивается заранее: совместимыми миграциями и контрактами, флагами для рискованных функций и репетициями отката, а не командой, которую вспоминают на инциденте.
