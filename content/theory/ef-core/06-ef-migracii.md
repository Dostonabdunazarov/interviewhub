Миграции EF Core версионируют схему базы вместе с кодом: каждое изменение модели — новая сущность, колонка, индекс — оформляется как класс с методами `Up()` и `Down()`, лежит в репозитории, проходит ревью и применяется к базе по порядку. Механика простая, а проблемы начинаются в двух местах: когда сгенерированную миграцию не читают, и когда её применяют к живой базе под нагрузкой. Про сам процесс выкатки и порядок релизов подробнее в разделе про доставку; здесь — то, что относится к EF.

## Как миграция вычисляется

```bash
dotnet ef migrations add AddSku
dotnet ef database update
```

На `migrations add` EF собирает проект, создаёт `DbContext` (через `IDesignTimeDbContextFactory` или хост приложения) и строит текущую модель: конвенции, атрибуты, `OnModelCreating`. Затем `IMigrationsModelDiffer` сравнивает её **не с базой, а со снимком** — файлом `AppDbContextModelSnapshot.cs`, где записана модель на момент последней миграции. Разница превращается в список операций (`AddColumn`, `CreateIndex`, `RenameColumn`…), и генерируются три файла: сама миграция, её `.Designer.cs` с моделью на этот момент и обновлённый snapshot.

Из этого следуют два правила. База при генерации вообще не нужна, и если кто-то поменял схему руками, EF об этом не узнает. А snapshot — общий файл для всей команды: две ветки, каждая со своей миграцией, при слиянии дают конфликт в нём. Разрешают его, удаляя свою миграцию и генерируя её заново поверх чужой, а не правкой snapshot руками.

## Что генерирует Npgsql

Дифф двух версий модели, прогнанный через `IMigrationsModelDiffer` и SQL-генератор Npgsql-провайдера EF Core 10. Было: `Product { Id, Name, Price }`. Стало: `Name` переименовано в `Title`, добавлены `Sku` (обязательная строка), `CategoryId` (nullable), уникальный индекс по `Sku` и `[Timestamp] uint Version`:

```sql
ALTER TABLE "Products" RENAME COLUMN "Name" TO "Title";
ALTER TABLE "Products" ADD "CategoryId" integer;
ALTER TABLE "Products" ADD "Sku" text NOT NULL DEFAULT '';
CREATE INDEX "IX_Products_CategoryId" ON "Products" ("CategoryId");
CREATE UNIQUE INDEX CONCURRENTLY "IX_Products_Sku" ON "Products" ("Sku");
```

Несколько вещей, которые здесь стоит заметить:

- **Обязательная колонка получила `DEFAULT ''`.** Иначе `NOT NULL` нельзя было бы добавить к таблице с данными. Но пустая строка — это значение по умолчанию для C#, а не для бизнеса: уникальный индекс по `Sku` на таблице с двумя товарами упадёт на дубликате `''`.
- **Для `xmin` операция в списке есть, а SQL нет** — системная колонка уже существует (см. `Оптимистичная блокировка`).
- **Индекс по внешнему ключу** `CategoryId` создан по соглашению. PostgreSQL сам индексы на FK не создаёт, EF — создаёт.
- **`CONCURRENTLY`** появился из-за `IsCreatedConcurrently()` в модели, и эта команда помечена как выполняемая вне транзакции — о причинах ниже.

## Когда переименование становится потерей данных

Распространённое утверждение «EF не распознаёт переименование и делает `DROP` + `ADD`» верно не всегда. Проверено на том же диффере:

```
Name → Title, тип тот же             RENAME COLUMN "Name" TO "Title"
Name → Title и Price → Cost          два RENAME COLUMN
Name → Title плюс HasMaxLength(200)  DROP COLUMN "Name";
                                     ADD "Title" character varying(200) NOT NULL DEFAULT ''
```

Простое переименование свойства EF сопоставляет по совпадающей структуре колонки и генерирует `RENAME`. Но стоит в той же миграции поменять тип или длину — сопоставления не будет, и данные колонки будут удалены без вопросов. CLI предупреждает строкой «An operation was scaffolded that may result in the loss of data», которую легко пропустить в выводе.

Правило из этого простое: **сгенерированную миграцию читают, как любой другой код**. Опасное место правят руками — `RenameColumn`, затем `AlterColumn` отдельной операцией, а перенос данных пишут через `migrationBuilder.Sql(…)`. И переименование с изменением типа лучше делать двумя миграциями.

Второе правило: **уже применённую миграцию не редактируют.** Где-то она уже записана в историю как выполненная, и правка до этой базы никогда не доедет. Исправление — новой миграцией.

## __EFMigrationsHistory

О том, что уже применено, EF узнаёт из таблицы в самой базе. Её DDL у Npgsql:

```sql
CREATE TABLE IF NOT EXISTS "__EFMigrationsHistory" (
    "MigrationId" character varying(150) NOT NULL,
    "ProductVersion" character varying(32) NOT NULL,
    CONSTRAINT "PK___EFMigrationsHistory" PRIMARY KEY ("MigrationId")
);
```

`database update` читает список применённых миграций, находит неприменённые (идентификатор начинается с временной метки, отсюда порядок), переводит их операции в SQL и выполняет, записывая каждую в историю. DDL в PostgreSQL транзакционный, так что неудачная миграция откатывается целиком — с исключением для операций, которые в транзакции выполнить нельзя.

## Как применять в проде

| Способ | Плюсы | Минусы |
| --- | --- | --- |
| `dotnet ef migrations script --idempotent` | SQL можно прочитать, отдать DBA, применить любым инструментом | отдельный шаг в пайплайне |
| `dotnet ef migrations bundle` | самодостаточный исполняемый файл, без SDK и исходников | тот же отдельный шаг, но проще в CI/CD |
| `db.Database.MigrateAsync()` на старте | ничего настраивать не надо | права на DDL у приложения, долгая миграция блокирует старт, несколько реплик стартуют одновременно |

Идемпотентный скрипт оборачивает каждую миграцию проверкой по истории. Так выглядит запись одной миграции у Npgsql:

```sql
DO $EF$
BEGIN
    IF NOT EXISTS(SELECT 1 FROM "__EFMigrationsHistory" WHERE "MigrationId" = '20260901120000_AddSku') THEN
    INSERT INTO "__EFMigrationsHistory" ("MigrationId", "ProductVersion")
    VALUES ('20260901120000_AddSku', '10.0.4');
    END IF;
END $EF$;
```

Такой скрипт можно прогнать на базе в любом состоянии: уже применённое пропустится.

`MigrateAsync` на старте в EF Core 9 стал безопаснее: он берёт блокировку на уровне базы, и параллельно стартующие реплики не будут применять одно и то же одновременно. Ещё два изменения EF 9, которые ломают старый код: `Migrate` бросает исключение, если в модели есть изменения без миграции (`PendingModelChangesWarning`), и бросает `MigrationsUserTransactionWarning`, если его вызвали внутри своей транзакции — старый приём «обернуть `MigrateAsync` в транзакцию и execution strategy» больше не работает. Но даже с блокировкой отдельный шаг деплоя надёжнее: приложению не нужны права на DDL, а упавшая миграция не превращается в упавший сервис.

Отдельно о `EnsureCreated()`: он создаёт схему по текущей модели **в обход миграций** и не пишет историю. Для тестов это удобно, но вызов `EnsureCreated` перед `Migrate` на одной базе ломает миграции.

## Миграция под нагрузкой

Миграция и новый код выкатываются не атомарно: какое-то время старая версия приложения работает с новой схемой, или наоборот. Отсюда приём expand → migrate → contract:

1. **Expand.** Добавить новое, не ломая старое: новую колонку nullable или с default, новую таблицу.
2. **Migrate.** Выкатить код, который пишет в обе схемы, перенести данные пачками.
3. **Contract.** Отдельным релизом, когда старый код уже нигде не работает, — удалить старую колонку и ужесточить ограничения.

Переименование колонки при этом — тоже три шага, а не один `RENAME`: старая версия приложения, которая ещё обслуживает запросы во время выкатки, обращается к старому имени.

Второй источник проблем — блокировки. `ALTER TABLE` берёт `ACCESS EXCLUSIVE` lock, и даже быстрая операция встанет в очередь за долгим запросом, а за ней встанут все остальные запросы к таблице (см. `Блокировки и deadlock`). Обычный `CREATE INDEX` на большой таблице блокирует запись на всё время построения. Для этого в Npgsql есть `IsCreatedConcurrently()`, а вручную — так:

```csharp
migrationBuilder.Sql(
    "CREATE INDEX CONCURRENTLY \"IX_Orders_CreatedAt\" ON \"Orders\" (\"CreatedAt\");",
    suppressTransaction: true);
```

`CONCURRENTLY` не блокирует запись, но не может выполняться внутри транзакции — отсюда `suppressTransaction`. Обратная сторона: если такая миграция упадёт посередине, частичный откат не случится, и останется невалидный индекс, который нужно удалить руками.

## Down, сидинг и альтернативы

`Down()` генерируется всегда, но в проде почти не используется: откат схемы после того, как новые данные уже записаны, сам по себе рискован. Откатываются обычно новой миграцией вперёд.

Справочные данные можно положить в миграции через `HasData` — тогда они становятся частью диффа. В EF Core 9 появились `UseSeeding`/`UseAsyncSeeding` для начальных данных, которые не должны жить в миграциях.

И миграции EF — не единственный путь. Команды с DBA часто ведут схему в Flyway, Liquibase или DbUp, а EF только маппит существующую схему (`dotnet ef dbcontext scaffold`). Это нормальный выбор, если схема важнее модели и её меняют не только из этого сервиса.

## Что стоит ответить на собеседовании

`migrations add` сравнивает текущую модель не с базой, а со снимком модели из `ModelSnapshot` и генерирует операции; `database update` читает `__EFMigrationsHistory`, применяет недостающие миграции по порядку и записывает каждую в историю. Сгенерированную миграцию нужно читать: простое переименование свойства EF 10 превращает в `RENAME COLUMN`, но переименование вместе со сменой типа даёт `DROP COLUMN` + `ADD COLUMN`, то есть потерю данных, а обязательная колонка добавляется с `DEFAULT ''`.

Сильный ответ расскажет про применение в проде — идемпотентный скрипт или bundle отдельным шагом деплоя вместо `Migrate()` на старте, хотя с EF 9 он берёт блокировку от параллельных реплик и падает на неучтённых изменениях модели. И про zero-downtime: схема и код выкатываются не атомарно, поэтому опасные изменения делают через expand → migrate → contract, а индексы на больших таблицах строят `CONCURRENTLY` вне транзакции.
