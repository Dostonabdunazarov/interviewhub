Предыдущие статьи раздела описывали EF Core изнутри: трекер, загрузку связей, трансляцию, транзакции. Эта — о границах. ORM хорош для того, для чего создан: загрузить агрегат, поменять, сохранить одной транзакцией, не написав ни строки SQL. Но есть задачи, где абстракция стоит дороже, чем даёт, — тяжёлое чтение, сложный SQL, массовые операции, горячий путь с жёсткой latency. Зрелый ответ на собеседовании — не «EF медленный» и не «Dapper не нужен», а понимание, где проходит граница и что есть между ними.

## Во что обходится EF

Чтобы отделить накладные расходы EF от работы базы, замер сделан на SQLite in-memory — там почти нет сети и диска. .NET 10.0.10, EF Core 10.0.4, медиана из семи прогонов:

```
20 000 строк, три колонки:
  ADO.NET DataReader вручную     14,9 мс    3 708 КБ
  EF AsNoTracking                22,7 мс    7 516 КБ
  EF Database.SqlQuery<T>        23,6 мс    6 739 КБ
  EF с трекингом                103,5 мс   24 624 КБ

1000 запросов по первичному ключу:
  ADO.NET                        22,6 мс      992 КБ
  EF AsNoTracking                94,3 мс    7 852 КБ
  EF.CompileQuery                51,7 мс    2 717 КБ
```

Из этих чисел видно, куда уходят деньги. Материализация большого результата без трекинга дороже ручного кода в полтора раза — заметно, но не драматично. С трекингом — уже в семь раз дороже ручного кода и в четыре с половиной раза дороже того же EF без трекинга, и это первое, что стоит убрать (см. `ChangeTracker`). А на коротком запросе EF добавляет около 70 мкс и 8 КБ аллокаций на вызов: построение дерева, вычисление ключа кэша, создание команды. Compiled query срезает эту часть почти вдвое.

Теперь контекст. Запрос по ключу к PostgreSQL по сети — это сотни микросекунд roundtrip'а. На обычном API 70 мкс поверх них — шум. На эндпоинте, который делает десять таких запросов на каждый из тысяч RPS, — уже процессор, который можно не покупать. **Решение о переходе на что-то другое принимают по профилю, а не по таблице из статьи.**

## Что сделать до того, как уходить с EF

Большинство «EF тормозит» лечится внутри EF:

- `AsNoTracking()` или проекция в DTO для всего, что только читается;
- убрать N+1 и лишние `Include` (см. `Загрузка связей и N+1`);
- `ExecuteUpdateAsync`/`ExecuteDeleteAsync` (EF Core 7+) вместо загрузки сущностей ради массового изменения;
- `AddDbContextPool` — переиспользование экземпляров контекста и меньше аллокаций на запрос;
- compiled query для горячих запросов фиксированной формы;
- `dotnet ef dbcontext optimize` (compiled model), если медленный именно старт на модели из сотен сущностей.

`ExecuteUpdate` здесь особенно важен, потому что закрывает целый класс задач, ради которых раньше писали SQL:

```csharp
await db.Orders
    .Where(o => o.CreatedAt < cutoff)
    .ExecuteDeleteAsync(ct);
```

```sql
DELETE FROM "Orders" AS o
WHERE o."CreatedAt" < @cutoff
```

Одна команда вместо загрузки тысяч сущностей и тысяч `DELETE`. В EF Core 10 сеттеры `ExecuteUpdateAsync` стали обычной лямбдой, а не деревом выражений, так что условные обновления пишутся через `if` внутри неё. Цена — обход трекера: уже загруженные сущности об изменении не узнают, токены версий не проверяются, а отложенного Unit of Work здесь нет — команда выполняется сразу.

## SQL, который LINQ не выражает

Есть конструкции, которых в LINQ нет или которые EF переводит плохо: рекурсивные CTE, `LATERAL`, `DISTINCT ON`, `GROUPING SETS`, большая часть оконных функций, `INSERT … ON CONFLICT` (upsert), полнотекстовый поиск с ранжированием, подсказки планировщику. Писать их через LINQ — либо невозможно, либо получается запрос, который нельзя прочитать и который даёт непредсказуемый SQL.

Первый шаг — raw SQL внутри EF, без смены инструмента:

```csharp
var tree = await db.Database
    .SqlQuery<CategoryNode>($"""
        WITH RECURSIVE t AS (
            SELECT "Id", "ParentId", "Name", 0 AS "Depth"
            FROM "Categories" WHERE "Id" = {rootId}
            UNION ALL
            SELECT c."Id", c."ParentId", c."Name", t."Depth" + 1
            FROM "Categories" c JOIN t ON c."ParentId" = t."Id"
        )
        SELECT * FROM t
        """)
    .ToListAsync(ct);
```

`Database.SqlQuery<T>` с EF Core 8 материализует произвольные немапленные типы, а не только скаляры; в замере выше он стоит столько же, сколько обычный запрос без трекинга. Для сущностей есть `DbSet<T>.FromSql`, поверх которого работает LINQ — EF оборачивает ваш SQL в подзапрос (см. `Трансляция IQueryable в SQL`). Для команд — `Database.ExecuteSqlAsync`, который возвращает число затронутых строк.

## Raw SQL и инъекции

Все три метода принимают `FormattableString`, и интерполяция в них **не склейка строк**: EF видит отдельно шаблон и аргументы и превращает каждый аргумент в `DbParameter`. Проверено на `FromSql`: `{min}` в тексте превратился в `@p0`, значение ушло отдельно.

```csharp
db.Products.FromSql($"SELECT * FROM \"Products\" WHERE \"Name\" = {name}");
db.Products.FromSqlRaw($"SELECT * FROM \"Products\" WHERE \"Name\" = '{name}'");
```

Первая строка безопасна. Вторая — SQL-инъекция: интерполяция выполнилась до вызова, и в `FromSqlRaw` пришла готовая строка со значением внутри. Код отличается тремя буквами, а поведение противоположное; на ревью это проверяют специально. `FromSqlRaw` нужен только для SQL, собранного динамически, и тогда значения передают позиционными параметрами (`{0}`), а имена колонок и направление сортировки выбирают из белого списка в коде — параметром их не передать.

С Dapper та же ловушка ещё коварнее: `conn.QueryAsync($"… {x}")` принимает обычную `string`, и интерполяция там всегда склейка. Значения — только через `@name` и объект параметров.

## Когда брать Dapper

Dapper — тонкая обёртка над ADO.NET: выполняет ваш SQL и маппит строки в объекты кэшированным материализатором. Его берут, когда SQL важнее модели:

- отчёты, аналитика и read-модели (сторона чтения в CQRS), где результат — плоские DTO;
- legacy-схема, хранимые функции, представления, которые дорого описывать в модели EF;
- горячие пути чтения, где профилирование показало оверхед EF;
- команда хорошо знает PostgreSQL и хочет видеть в коде ровно тот запрос, что попадёт в `EXPLAIN`.

Остаются на EF там, где богатая доменная модель, агрегаты меняются и сохраняются целиком, много CRUD, нужны миграции, токены версий, глобальные фильтры (soft delete, multi-tenancy) и рефакторинг, который ловит компилятор, а не тесты. Цена Dapper — ровно то, что EF делает сам: `INSERT` и `UPDATE` руками, связи — через multi-mapping или два запроса со склейкой в словаре, ошибки в именах колонок — только в рантайме.

Частый зрелый вариант — **оба в одном сервисе**: EF для записи, Dapper для тяжёлого чтения, на одном соединении и в одной транзакции:

```csharp
await using var tx = await db.Database.BeginTransactionAsync(ct);
db.Orders.Add(order);
await db.SaveChangesAsync(ct);

var conn = db.Database.GetDbConnection();
var stats = await conn.QueryAsync<OrderStat>(new CommandDefinition(
    "SELECT customer_id AS CustomerId, sum(total) AS Total FROM orders WHERE created_at >= @from GROUP BY customer_id",
    new { from = since }, transaction: tx.GetDbTransaction(), cancellationToken: ct));

await tx.CommitAsync(ct);
```

## Массовая загрузка

`AddRange` + `SaveChanges` для сотен тысяч строк — неподходящий инструмент даже с пачками и `ChangeTracker.Clear()`: каждая строка проходит трекер, а в базу идут `INSERT`, пусть и пакетами. В PostgreSQL для этого есть `COPY`, а в Npgsql — бинарный импорт:

```csharp
await using var conn = await dataSource.OpenConnectionAsync(ct);
await using var writer = await conn.BeginBinaryImportAsync(
    "COPY products (name, price) FROM STDIN (FORMAT BINARY)", ct);

foreach (var p in rows)
{
    await writer.StartRowAsync(ct);
    await writer.WriteAsync(p.Name, NpgsqlDbType.Text, ct);
    await writer.WriteAsync(p.Price, NpgsqlDbType.Numeric, ct);
}
await writer.CompleteAsync(ct);
```

Без `CompleteAsync` импорт откатится. Для upsert больших объёмов обычный приём — `COPY` во временную таблицу и затем `INSERT … SELECT … ON CONFLICT DO UPDATE` одной командой. Сторонние bulk-библиотеки для EF делают по сути то же самое.

## Generic-репозиторий поверх DbContext

Отдельный случай «ORM мешает» создают сами разработчики: оборачивают `DbContext` в `IRepository<T>` с `GetById`, `GetAll`, `Add`, `Update`. `DbSet<T>` уже репозиторий, а `DbContext` — Unit of Work, и обёртка поверх них обычно теряет больше, чем даёт:

- пропадают проекции, `Include`, `AsNoTracking`, `AsSplitQuery`, пагинация — либо интерфейс раздувается до копии `IQueryable`, либо всё делается через `GetAll()` и LINQ в памяти;
- `Save()` в каждом репозитории ломает атомарность операции над несколькими сущностями;
- возврат `IQueryable<T>` наружу делает абстракцию декоративной (см. `IEnumerable vs IQueryable`);
- «чтобы можно было сменить ORM» на практике почти не случается.

Оправдан репозиторий **агрегата** в DDD-стиле — `IOrderRepository.GetAsync(OrderId)` гарантирует, что заказ загружается целиком со строками, — или когда слой приложения не должен ссылаться на EF. Чтение при этом идёт напрямую через `DbContext` с проекциями или через Dapper.

И про тесты: InMemory-провайдер ведёт себя не как PostgreSQL — у него нет транзакций, ограничений и настоящей трансляции SQL. Запросы проверяют интеграционными тестами на реальной базе в контейнере, а не моками репозитория.

## Что стоит ответить на собеседовании

EF — выбор по умолчанию для бизнес-логики с доменной моделью и CRUD, а граница проходит там, где SQL важнее модели. Оверхед реальный, но разный: на SQLite in-memory без трекинга материализация 20 000 строк стоила 22,7 мс против 14,9 у ручного `DataReader`, с трекингом — 103,5 мс, а короткий запрос по ключу добавил около 70 мкс и 8 КБ на вызов, которые compiled query срезает вдвое. Поэтому сначала — `AsNoTracking`, проекции, `ExecuteUpdate`/`ExecuteDelete`, пулинг контекста и compiled queries, и только по профилю — смена инструмента.

Сильный ответ назовёт конкретные случаи: рекурсивные CTE, `LATERAL`, upsert и оконные функции — через `SqlQuery<T>` или Dapper; массовая загрузка — через `COPY`; и предупредит, что `FromSql($"…")` параметризует значения, а `FromSqlRaw($"…")` и интерполяция в Dapper — это SQL-инъекция. И скажет, что EF и Dapper прекрасно живут в одном сервисе на общей транзакции, а generic-репозиторий поверх `DbContext` чаще отнимает возможности EF, чем изолирует от него.
