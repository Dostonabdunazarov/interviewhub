`DbContext` — это не просто способ отправить SQL. Каждая сущность, которую вернул обычный запрос, регистрируется в **change tracker**: контекст запоминает её ключ, исходные значения свойств и состояние. Когда вы вызываете `SaveChanges()`, EF сравнивает текущие значения с запомненными и сам решает, какие `INSERT`, `UPDATE` и `DELETE` выполнить. Почти всё неожиданное поведение EF Core — от «изменения не сохранились» до «запрос вернул старые данные» — объясняется устройством трекера.

## Что хранит трекер

На каждую отслеживаемую сущность трекер держит запись (`EntityEntry`) из трёх частей:

- **ключ** — по нему работает identity map: одна строка таблицы соответствует одному объекту в контексте;
- **snapshot исходных значений** — копия свойств на момент загрузки, с ней потом сравниваются текущие;
- **состояние** — `EntityState`, от которого зависит, какая команда уйдёт в базу.

| Состояние | Откуда берётся | Что будет при `SaveChanges` |
| --- | --- | --- |
| `Detached` | объект создан через `new` или пришёл из `AsNoTracking()` | ничего, контекст о нём не знает |
| `Unchanged` | загружен запросом, `Attach` | ничего |
| `Added` | `Add`, новый объект в графе отслеживаемой сущности | `INSERT` |
| `Modified` | изменилось свойство, `Update` | `UPDATE` изменённых колонок |
| `Deleted` | `Remove` | `DELETE` |

Состояния — это не флажки, которые ставит программист, а результат работы трекера. Например, `Remove` для объекта, который был только что добавлен и ещё не сохранён, переводит его не в `Deleted`, а сразу в `Detached`: удалять из базы нечего. Это проверено на EF Core 10.

## Как обнаруживаются изменения

По умолчанию EF использует **snapshot tracking**: свойства — обычные автосвойства, и присваивание `user.Email = …` никак не сообщает контексту об изменении. Разницу находит метод `DetectChanges`, который проходит по всем отслеживаемым сущностям и сравнивает их со снимками.

```csharp
var c = await db.Customers.FirstAsync(x => x.Id == 1);
db.Entry(c).State;                                   // Unchanged

c.Email = "new@mail";
db.Entry(c).State;                                   // Modified
db.Entry(c).Property(x => x.Email).IsModified;       // true
db.Entry(c).Property(x => x.Name).IsModified;        // false
```

Вызывать `DetectChanges` руками почти никогда не нужно: его автоматически вызывают `SaveChanges`, `Entry()`, `ChangeTracker.Entries()`, `HasChanges()` и ряд других API. Именно поэтому во втором `Entry(c).State` уже стоит `Modified`.

Для отладки удобен `ChangeTracker.DebugView.LongView` — так выглядит его реальный вывод после изменения:

```
Customer {Id: 1} Modified
    Id: 1 PK
    Email: 'new@mail' Modified Originally 'c1@mail'
    Name: 'C1'
  Orders: []
```

При сохранении в `UPDATE` попадает только изменённая колонка. SQL, который сгенерировал Npgsql-провайдер EF Core 10:

```sql
UPDATE "Customers" SET "Email" = @p0
WHERE "Id" = @p1;
```

Две детали, которые проверяются за минуту. Если присвоить свойству то же значение, что было, сущность остаётся `Unchanged` — сравниваются значения, а не факт присваивания. А если выключить `ChangeTracker.AutoDetectChangesEnabled`, изменение не будет найдено вовсе: состояние останется `Unchanged`, а `SaveChanges` вернёт 0 сохранённых строк. Выключать автообнаружение имеет смысл только вместе с явным вызовом `DetectChanges()` перед сохранением.

## Во что обходится DetectChanges

Полный проход по всем сущностям означает, что цена `DetectChanges` растёт линейно с размером трекера. Замер на .NET 10.0.10 и EF Core 10.0.4, сущность с тремя свойствами, медиана из семи серий:

```
   100 сущностей в трекере    0,027 мс на вызов
 1 000 сущностей              0,278 мс
10 000 сущностей              2,792 мс
20 000 сущностей              5,592 мс
```

Сам по себе один вызов недорог. Проблема появляется, когда контекст живёт долго и копит сущности, а `DetectChanges` вызывается часто — например, `SaveChanges` после каждой вставки в цикле импорта. Тогда каждая итерация проходит по всему, что накопилось, и импорт становится квадратичным.

Лечится это тремя способами, по возрастанию радикальности:

```csharp
foreach (var chunk in rows.Chunk(1000))
{
    db.AddRange(chunk);
    await db.SaveChangesAsync();
    db.ChangeTracker.Clear();
}
```

Пачки с `ChangeTracker.Clear()` (EF Core 5+) или новый контекст на каждую пачку; `AutoDetectChangesEnabled = false` на время массовой вставки; для сотен тысяч строк — вообще не трекер, а `COPY` (об этом в статье `Когда ORM мешает`).

## Identity resolution: почему повторный запрос не обновляет объект

Трекер — это ещё и identity map. Если запрос вернул строку, ключ которой уже отслеживается, EF **не создаёт новый объект и не перезаписывает старый**, а возвращает тот, что уже есть. Проверка:

```csharp
var a = await db.Customers.FirstAsync(x => x.Id == 3);
a.Name = "changed in memory";

await db.Database.ExecuteSqlAsync($"UPDATE Customers SET Email = 'db@mail' WHERE Id = 3");

var b = await db.Customers.FirstAsync(x => x.Id == 3);
// ReferenceEquals(a, b) == true
// b.Name  == "changed in memory"
// b.Email == "c3@mail" — новое значение из базы не применилось
```

Второй `SELECT` реально ушёл в базу и вернул `db@mail`, но объект остался прежним целиком — не только изменённое в памяти свойство «победило», но и нетронутое `Email` не обновилось. Отсюда классический баг долгоживущего контекста: данные «застывают» на момент первой загрузки.

Чтобы получить актуальные значения, есть `AsNoTracking()` (новый объект с данными из базы) или `db.Entry(a).ReloadAsync()`, который перечитывает строку и сбрасывает изменения в памяти.

`FindAsync(id)` использует identity map ещё активнее: сначала ищет сущность в трекере и, если нашёл, **вообще не идёт в базу** — в логе после него не появилось ни одной команды. `FirstOrDefaultAsync(x => x.Id == id)` всегда делает запрос, но умеет `Include` и произвольные условия.

## Tracking и no-tracking

Трекинг стоит памяти и времени. Замер: 20 000 строк из таблицы с тремя колонками, SQLite in-memory, .NET 10, медиана из пяти прогонов:

```
ToList(), tracking         53–77 мс   25 191 КБ
AsNoTracking().ToList()    14–18 мс    8 075 КБ
Select(c => new { … })     10–17 мс    6 357 КБ
```

Разброс по времени между запусками заметный, а память стабильна: отслеживание утроило аллокации — на каждую строку создаются запись трекера, snapshot и элемент identity map. SQL при этом одинаковый во всех трёх случаях: `AsNoTracking()` экономит работу приложения, а не базы, и медленный из-за отсутствия индекса запрос не ускорит.

Правило практическое: всё, что только читается, — `AsNoTracking()` или проекция в DTO. Проекции в анонимный тип или record не отслеживаются вообще — трекать там нечего, — но если в проекции лежит сама сущность (`new { Order = o, … }`), она будет отслеживаться. Для read-heavy контекста можно поменять умолчание через `UseQueryTrackingBehavior(QueryTrackingBehavior.NoTracking)` и включать трекинг точечно через `AsTracking()`.

У `AsNoTracking()` есть побочный эффект: без identity map одинаковые строки становятся разными объектами. Пять заказов одного клиента с `Include(o => o.Customer)`:

```
AsNoTracking()                          5 разных объектов Customer
AsNoTrackingWithIdentityResolution()    1 объект Customer
```

Второй вариант строит identity map только на время одного запроса и не регистрирует сущности в контексте — компромисс для больших графов, где один и тот же «справочник» повторяется сотни раз.

## Отсоединённые сущности: Update, Attach и SetValues

В веб-API сущность часто приходит из запроса клиента, а не из базы, и контекст о ней не знает. Есть три способа сказать ему, что делать, и они генерируют разный SQL:

```csharp
db.Update(dto);
// UPDATE "Customers" SET "Email" = @p0, "Name" = @p1 WHERE "Id" = @p2

db.Attach(dto);
db.Entry(dto).Property(x => x.Email).IsModified = true;
// UPDATE "Customers" SET "Email" = @p0 WHERE "Id" = @p1

var entity = await db.Customers.FirstAsync(x => x.Id == dto.Id);
db.Entry(entity).CurrentValues.SetValues(dto);
// SELECT … ; UPDATE "Customers" SET "Email" = @p0 WHERE "Id" = @p1
```

`Update` помечает **все** свойства изменёнными — без запроса к базе, но с перезаписью каждой колонки, включая те, что клиент не присылал и которые могли поменять другие. `Attach` с точечным `IsModified` обновляет только указанное. `SetValues` на загруженной сущности стоит лишнего `SELECT`, зато обновит ровно те поля, значения которых действительно отличаются, и даёт место для проверки прав и инвариантов.

Самая частая ошибка здесь — попытка присоединить второй объект с ключом, который уже отслеживается:

```
InvalidOperationException: The instance of entity type 'Customer' cannot be tracked
because another instance with the same key value for {'Id'} is already being tracked.
```

Обычно это значит, что в том же контексте сущность уже загружалась ранее — проверкой существования или в другом сервисе того же HTTP-запроса. Решение — работать с загруженным экземпляром через `SetValues`, а не присоединять копию.

## Время жизни контекста

Из устройства трекера следуют правила, которые спрашивают на собеседовании:

- **Контекст — единица работы, а не кэш.** В ASP.NET Core он регистрируется как scoped: один экземпляр на HTTP-запрос. Singleton-контекст или контекст на всю жизнь фонового воркера копит сущности, замедляет `DetectChanges` и отдаёт застывшие данные.
- **Контекст не потокобезопасен.** Две одновременные операции на одном экземпляре дают `InvalidOperationException: A second operation was started on this context instance before a previous operation completed`. Для параллельной работы нужен отдельный контекст на задачу, их удобно брать из `IDbContextFactory<T>`.
- **В `BackgroundService` контекст берут из scope** (`IServiceScopeFactory`) или фабрики, а не внедряют в конструктор синглтона.
- **`ExecuteUpdate`/`ExecuteDelete` трекер обходят.** Они сразу выполняют SQL, и уже загруженные сущности о сделанном изменении не узнают — это та же история с identity map, только наоборот.

## Что стоит ответить на собеседовании

Change tracker хранит для каждой загруженной сущности ключ, snapshot исходных значений и состояние (`Unchanged`, `Added`, `Modified`, `Deleted`, `Detached`). `SaveChanges` вызывает `DetectChanges`, который сравнивает текущие значения со снимками и формирует `UPDATE` только по изменённым колонкам. Проход идёт по всем отслеживаемым сущностям, поэтому цена линейна: на .NET 10 это около 0,28 мс на тысячу сущностей и 5,6 мс на двадцать тысяч, — и долгоживущий контекст со `SaveChanges` в цикле превращает импорт в квадратичный.

Сильный ответ добавит про identity map: повторный запрос того же ключа вернёт уже отслеживаемый объект и не обновит его значения из базы, а `Find` может не пойти в базу вовсе. Скажет, что `AsNoTracking()` втрое снижает аллокации на чтении, но SQL не меняет, и что для отсоединённых сущностей `Update` перезаписывает все колонки, а `Attach` с `IsModified` или `SetValues` — только нужные.
