Сервис должен сделать две вещи: изменить свою базу и сообщить об этом остальным через брокер. Общей транзакции у базы и брокера нет, и любой порядок двух вызовов оставляет окно, в котором падение процесса разводит их навсегда. Эта проблема называется dual write, и transactional outbox — стандартный ответ на неё. На собеседовании ждут не название паттерна, а объяснение, где именно теряется событие, почему ретрай не помогает и почему после outbox доставка всё равно at-least-once.

## Где теряется событие

Наивный код выглядит безобидно:

```csharp
await db.SaveChangesAsync(ct);
await bus.Publish(new OrderPlaced(order.Id), ct);
```

Между двумя строками процесс может упасть: под убили при деплое, закончилась память, брокер недоступен. Заказ есть, события нет — сага не стартует, письмо не уйдёт, склад не узнает. Поменять порядок не помогает: событие опубликовано, а `SaveChangesAsync` упал на нарушении ограничения — подписчики обрабатывают заказ, которого не существует. Ретрай вокруг `Publish` спасает от недоступности брокера, но не от падения процесса. Обернуть оба вызова в `try` и «откатить второе при ошибке первого» тоже нельзя: проблема не в исключении, а в падении между двумя **успешными** коммитами, которое никакой `catch` не поймает.

Как выбрать между блокирующим 2PC и этими альтернативами, разобрано в статье `Почему 2PC проблематичен`. Здесь достаточно того, что большинство брокеров в распределённой транзакции участвовать не умеют.

## Идея: одна локальная транзакция

Событие пишется не в брокер, а в таблицу `outbox` той же базы, той же транзакцией, что и бизнес-данные. Либо сохранилось всё, либо ничего. Отдельный процесс — relay — читает таблицу и публикует события в брокер:

```text
транзакция: INSERT orders + INSERT outbox  →  COMMIT
relay:      SELECT из outbox → publish → ждать подтверждения → отметить
```

```sql
CREATE TABLE outbox (
    id           uuid        PRIMARY KEY,
    aggregate_id uuid        NOT NULL,
    type         text        NOT NULL,
    payload      jsonb       NOT NULL,
    created_at   timestamptz NOT NULL DEFAULT now(),
    sent_at      timestamptz
);

CREATE INDEX outbox_unsent ON outbox (created_at) WHERE sent_at IS NULL;
```

В EF Core запись в outbox — обычная сущность, которую добавляют в тот же `SaveChanges` (почему этого достаточно, без явной транзакции, — в статье `Транзакции и уровни изоляции`):

```csharp
order.MarkPaid();
db.Outbox.Add(new OutboxEntry
{
    Id = Guid.NewGuid(),
    AggregateId = order.Id,
    Type = nameof(OrderPaid),
    Payload = JsonSerializer.Serialize(new OrderPaid(order.Id, order.Total, order.Currency)),
});
await db.SaveChangesAsync(ct);
```

`Id` записи становится идентификатором события, и он рождается один раз вместе с бизнес-изменением. Это важно для получателя: повтор публикации придёт с тем же id, и дедупликация сработает.

## Почему всё равно at-least-once

Relay опубликовал событие, брокер подтвердил, а relay упал до того, как записал `sent_at`. После рестарта он отправит событие ещё раз. Outbox гарантирует, что событие **не потеряется**, но не то, что оно придёт **один раз**. Поэтому outbox всегда идёт в паре с идемпотентным получателем — inbox по id сообщения или естественной идемпотентностью операции (см. `Идемпотентность` и `Exactly-once на практике`).

Второе следствие — задержка. Событие появляется в брокере после коммита плюс интервал опроса или лаг CDC. Прочитать свою запись через события сразу не получится.

## Polling publisher

Самый простой relay — фоновый сервис, который опрашивает таблицу. Чтобы несколько экземпляров не публиковали одно и то же, в PostgreSQL используют `FOR UPDATE SKIP LOCKED`:

```sql
SELECT id, aggregate_id, type, payload
FROM outbox
WHERE sent_at IS NULL
ORDER BY created_at
LIMIT 100
FOR UPDATE SKIP LOCKED;
```

Строки, заблокированные другим экземпляром, пропускаются, а не ждут. Отметку `sent_at` ставят только после подтверждения брокера — для Kafka это delivery report с `acks=all`. Опрос раз в 100–500 мс даёт приемлемую задержку и постоянную, но небольшую нагрузку на базу.

## CDC

Альтернатива — change data capture: Debezium читает журнал базы (WAL в PostgreSQL через логический replication slot) и публикует вставки в outbox в Kafka. У Debezium для этого есть готовое преобразование Outbox Event Router: оно берёт тип события, ключ и payload из колонок outbox-таблицы.

| | Polling | CDC |
| --- | --- | --- |
| задержка | интервал опроса | доли секунды |
| нагрузка на базу | постоянные запросы и очистка | чтение журнала |
| порядок | нужно обеспечивать самому | порядок коммитов |
| инфраструктура | ничего нового | Kafka Connect, replication slot |

У CDC своя эксплуатационная цена: replication slot удерживает WAL, пока коннектор его не прочитал. Остановившийся коннектор может заполнить диск primary — слот нужно мониторить. И CDC стоит делать именно из outbox-таблицы, а не из бизнес-таблиц: иначе наружу утекает внутренняя схема базы, и любое переименование колонки ломает подписчиков.

## Порядок событий

Если подписчику важен порядок событий одного агрегата — `OrderPlaced` раньше `OrderCancelled`, — параллельный relay может его нарушить: два экземпляра с `SKIP LOCKED` взяли соседние пачки и опубликовали их в разном темпе. Варианты:

- **один активный relay** — через выбор лидера или advisory lock (см. `Выбор лидера`);
- **распределение по агрегату** — экземпляр обрабатывает только свой диапазон хэшей `aggregate_id`;
- **ключ сообщения = `aggregate_id`** — в Kafka это кладёт события агрегата в одну партицию, где порядок сохраняется, при условии что сам relay публикует их последовательно, а producer идемпотентен.

## MassTransit

В .NET outbox редко пишут вручную. MassTransit умеет транзакционный outbox поверх EF Core:

```csharp
builder.Services.AddMassTransit(x =>
{
    x.AddEntityFrameworkOutbox<OrdersDbContext>(o =>
    {
        o.UsePostgres();
        o.QueryDelay = TimeSpan.FromSeconds(1);
        o.UseBusOutbox();
    });

    x.UsingRabbitMq((ctx, cfg) => cfg.ConfigureEndpoints(ctx));
});
```

```csharp
protected override void OnModelCreating(ModelBuilder modelBuilder)
{
    modelBuilder.AddTransactionalOutboxEntities();
}
```

С `UseBusOutbox` вызов `IPublishEndpoint.Publish` в scope с `DbContext` не отправляет сообщение, а добавляет его в таблицу `OutboxMessage`; оно сохраняется тем же `SaveChangesAsync`, что и бизнес-данные, а фоновый delivery service доставляет его в брокер. `AddTransactionalOutboxEntities` добавляет в модель три таблицы — `InboxState`, `OutboxState` и `OutboxMessage`, — и их нужно провести миграцией. На стороне получения тот же механизм включается для endpoint через `UseEntityFrameworkOutbox<OrdersDbContext>(context)`: он дедуплицирует входящие сообщения по `InboxState` и складывает исходящие из консьюмера в outbox.

## Эксплуатация

- **Рост таблицы.** Отправленные записи удаляют фоновой задачей; при большом потоке таблицу партиционируют по времени и удаляют партиции целиком. Без очистки опрос деградирует, а vacuum не успевает.
- **Ядовитая запись.** Событие, которое не сериализуется или превышает лимит размера сообщения брокера, блокирует очередь relay. Нужны счётчик попыток и отдельный статус, чтобы пропустить запись и поднять алерт.
- **Брокер лёг.** Это достоинство: заказы оформляются, события копятся в базе и уйдут позже. Сервис больше не зависит от доступности брокера на критическом пути.
- **Метрики.** Число неотправленных записей и возраст самой старой — лучший сигнал, что relay встал.
- **Версия payload.** В таблице лежит уже сериализованный контракт. Если формат события меняется, старые записи должны оставаться читаемыми (см. `Версионирование контрактов`).

## Что стоит ответить на собеседовании

Outbox решает dual write: изменить базу и опубликовать событие атомарно нельзя, и падение между двумя вызовами теряет событие или публикует несуществующее. Событие пишется в таблицу outbox той же локальной транзакцией, что и данные, а relay публикует его и отмечает отправленным. Доставка становится at-least-once: при падении relay между публикацией и отметкой событие уйдёт повторно, поэтому получатель идемпотентен, а id события рождается вместе с записью.

Сильный ответ сравнит polling с `FOR UPDATE SKIP LOCKED` и CDC через Debezium (задержка против инфраструктуры и replication slot), объяснит, как сохранить порядок событий агрегата, назовёт MassTransit EF Core outbox и эксплуатационные детали: очистку таблицы, ядовитые записи, метрику возраста старейшей неотправленной записи и то, что outbox развязывает доступность сервиса и брокера.
