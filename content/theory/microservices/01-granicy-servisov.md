Почти все боли микросервисной архитектуры — распределённые транзакции, цепочки синхронных вызовов, согласованные релизы пяти сервисов — следствие одной ошибки: неправильно проведённой границы. Сервисы, которые постоянно меняются вместе и не могут ответить на запрос без соседа, — это монолит, разрезанный сетью. На собеседовании вопрос «как вы делили систему на сервисы» проверяет, умеет ли кандидат объяснить, по какому принципу проходит граница и как понять, что она проведена неверно.

## Граница по бизнесу, а не по слою

Хорошая граница — та, при которой типичное изменение требований затрагивает один сервис, а сервис выполняет свою основную работу, не делая синхронных вызовов к соседям. Отсюда два классических антипримера:

- **по техническим слоям** — `ApiGateway`, `BusinessLogicService`, `DataAccessService`: любая фича проходит через все три, и релизить их приходится вместе;
- **по таблицам** — `CustomerService`, `ProductService`, `OrderService` как CRUD над сущностями: поведения в них нет, правила живут в «оркестраторах» сверху, и каждый сценарий превращается в серию сетевых вызовов.

Правильная нарезка идёт по бизнес-возможностям — тому, что организация умеет делать: каталог, ценообразование, заказы, оплата, склад, доставка. Каждая такая возможность имеет своих экспертов, свои правила и свои данные.

## Bounded context: одна сущность — разные модели

Инструмент для поиска границ дал DDD. Bounded context — граница, внутри которой модель и язык однозначны. За границей то же слово может значить другое, и это нормально. «Товар» в интернет-магазине:

```text
каталог        название, описание, фото, характеристики
склад          SKU, остаток, ячейка хранения, вес
цены           базовая цена, скидки, акции
доставка       габариты, хрупкость
```

Одна «универсальная» сущность `Product` со всеми полями становится классом, который боятся трогать все команды: у каждой свои правила валидации и свой смысл полей. Вместо этого у каждого контекста своя модель, а общим остаётся только идентификатор:

```csharp
public sealed class Customer
{
    public CustomerId Id { get; }
    public CustomerTier Tier { get; private set; }
    public Money CreditLimit { get; private set; }
}

public sealed record Recipient(CustomerId Id, string Name, Address Address, PhoneNumber Phone);

public sealed record Payer(CustomerId Id, string TaxId, PaymentTerms Terms);
```

Первый класс — «клиент» в продажах, второй — «получатель» в доставке, третий — «плательщик» в биллинге. У них разные инварианты: для продаж клиент без адреса валиден, для доставки нет. Разные жизненные циклы: клиент, заблокированный в продажах, всё равно должен получить уже оплаченный заказ.

Bounded context — естественный кандидат на границу сервиса. Один контекст может быть реализован несколькими деплойными единицами, но один сервис не должен смешивать несколько контекстов — иначе модели снова сольются.

## Агрегат — граница транзакции

Внутри контекста DDD выделяет агрегаты — группы объектов, которые должны меняться атомарно ради инварианта. «Сумма резервов не больше остатка» проверяется в одной транзакции, значит, резервы и остаток лежат в одном агрегате, в одной базе и в одном сервисе.

Это главное практическое правило: **агрегат нельзя разрезать между сервисами**. Инвариант, растянутый через сеть, превращается либо в распределённую транзакцию (почему это плохо, разобрано в статье `Почему 2PC проблематичен`), либо в сагу с eventual consistency (см. `Saga`). Если бизнес не согласен, что «резерв может на секунду превысить остаток», граница проведена неверно.

## Как искать границы на практике

- **Event Storming.** С экспертами выписывают доменные события на временной линии: «Заказ оформлен», «Оплата получена», «Товар отгружен». Вокруг ключевых событий меняется язык, ответственные люди и данные — там стык контекстов.
- **Язык.** Где эксперты спорят о значении термина или используют разные слова для одного и того же, проходит граница.
- **Автономия решений.** Сервис должен принимать решения по своим данным. Если для проверки «можно ли оформить заказ» нужно синхронно спросить троих соседей, данные лежат не там.
- **Команды.** Закон Конвея работает в обе стороны: система повторяет структуру коммуникаций. Контекст, которым владеют три команды, не станет независимым сервисом.
- **Поддомены.** Generic-части — авторизация, рассылки, биллинг — часто выгоднее купить или взять готовыми, чем писать свой сервис.

## Владение данными

У каждого сервиса своя база, и чужие таблицы он не читает. Общая база — самая быстрая дорога к распределённому монолиту: схему нельзя поменять, не согласовав с соседями, а тяжёлый запрос одного сервиса тормозит всех.

У каждого факта один владелец. Остальные хранят копии нужных им полей, обновляемые событиями. Сервис заказов держит у себя название и цену товара **на момент заказа** — это не дублирование по недосмотру, а осознанная цена автономии:

```sql
CREATE TABLE order_lines (
    order_id     uuid           NOT NULL,
    product_id   uuid           NOT NULL,
    product_name text           NOT NULL,
    unit_price   numeric(12, 2) NOT NULL,
    quantity     int            NOT NULL,
    PRIMARY KEY (order_id, product_id)
);
```

События при этом несут бизнес-факт, а не снимок таблицы: `CustomerRelocated { CustomerId, NewAddress }` вместо `CustomerUpdated` с шестьюдесятью полями. Снимок всей сущности означает, что сервисы делят модель, а не обмениваются фактами. Для интеграции с legacy-системой или внешним API на входе ставят anti-corruption layer — переводчик, который не даёт чужой модели проникнуть в свою.

## Признаки ошибочной границы

Об ошибке говорят не диаграммы, а поведение системы. Признаки, которые можно измерить:

- **change coupling** — по истории git сервисы A и B меняются в одних и тех же PR в большинстве случаев;
- **deployment coupling** — релиз требует выкатить несколько сервисов в определённом порядке;
- **chatty-взаимодействие** — один пользовательский запрос порождает десятки синхронных вызовов соседа, и без него сервис бесполезен;
- **компенсации в каждом втором потоке** — саги нужны для обычных сценариев, а не для редких бизнес-исключений;
- **общая таблица или общая доменная библиотека** — модели двух сервисов на самом деле одна модель;
- **сервис-«бог»** — к нему обращаются все, и он меняется в каждой фиче.

Набор этих признаков называют распределённым монолитом: все недостатки монолита (связанность, совместные релизы) плюс все недостатки распределённой системы (сеть, частичные отказы, eventual consistency) — и ни одного преимущества.

## Начинать с крупного

Разрезать крупный сервис позже проще, чем склеивать мелкие, успевшие обрасти своими базами и контрактами. Поэтому разумный старт — модульный монолит: модули по bounded context, у каждого своя схема в базе, межмодульные вызовы только через публичный интерфейс. Когда граница подтверждена реальной историей изменений и появилась причина выделить модуль — отдельное масштабирование, своя команда, другой темп релизов, — его выносят в сервис, переключая трафик постепенно (strangler fig).

Склеить два сильно связанных сервиса обратно — нормальное инженерное решение, а не поражение. Объединение обычно дешевле, чем вечная координация релизов и компенсаций.

## Что стоит ответить на собеседовании

Границы проводят по бизнес-возможностям и bounded context, а не по техническим слоям или таблицам. Внутри контекста модель и язык однозначны, поэтому одна сущность — клиент, товар — выглядит в разных сервисах по-разному, и общим остаётся только идентификатор. Агрегат — граница атомарного инварианта, его нельзя резать между сервисами. У каждого сервиса своя база и у каждого факта один владелец; остальные держат копии, обновляемые событиями.

Сильный ответ назовёт измеримые признаки ошибки — change coupling и совместные релизы, chatty-вызовы, компенсации в обычных сценариях, общие таблицы и доменные библиотеки — и предложит начинать с крупных контекстов или модульного монолита, выделяя сервисы, когда граница подтверждена историей изменений.
