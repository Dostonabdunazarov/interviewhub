Микросервисы — не способ сделать код чище, а ответ на организационную проблему: много команд мешают друг другу в одном релизе, а части системы требуют разного масштаба и разной доступности. Платят за это сетью вместо вызовов методов, eventual consistency вместо ACID и обязательной платформой. На собеседовании senior-уровня вопрос «как бы вы распилили монолит» проверяет не знание паттернов, а умение сначала спросить «зачем», потом идти маленькими обратимыми шагами и не забыть про данные.

## Что делает сервис микросервисом

Микросервисная архитектура — набор независимо развёртываемых сервисов, каждый из которых отвечает за одну бизнес-возможность, владеет своими данными и общается с остальными только через явные контракты: HTTP, gRPC, сообщения. Отличают её от «монолита, порезанного на проекты» три проверяемых признака:

- **независимый деплой** — сервис выкатывается, не трогая соседей. Если релиз требует синхронно обновить пять сервисов в определённом порядке, это распределённый монолит;
- **своя база** — чужие таблицы никто не читает, данные идут через API или события;
- **одна команда владеет сервисом целиком** — код, деплой, мониторинг, дежурства.

Здесь работает закон Конвея: система повторяет структуру коммуникаций организации. Сервис трёх команд не будет независимым, а одна команда с десятью сервисами получит всю цену распределённости без выигрыша в автономии.

## Монолит против микросервисов честно

| | Монолит | Микросервисы |
| --- | --- | --- |
| вызов между модулями | in-process, не падает | сеть: задержка, таймаут, частичный отказ |
| транзакции | ACID в одной базе | saga, outbox, eventual consistency |
| перенос границы | рефакторинг в IDE | смена контрактов и версионирование |
| масштабирование | всё приложение целиком | каждый сервис по своей нагрузке |
| изоляция отказов | утечка памяти роняет всё | отказ локализуется при таймаутах и circuit breaker |
| релизы | общая очередь | независимые |

Промежуточный и часто лучший вариант — **модульный монолит**. Один деплой, но модули выделены по bounded context: у каждого своя схема в базе, общение только через публичный интерфейс или in-process события, а запрет прямых ссылок проверяется архитектурными тестами:

```csharp
[Fact]
public void Billing_does_not_reference_Orders_internals()
{
    var result = Types.InAssembly(typeof(BillingModule).Assembly)
        .ShouldNot()
        .HaveDependencyOn("Shop.Orders.Domain")
        .GetResult();

    Assert.True(result.IsSuccessful);
}
```

Это даёт большую часть пользы от правильных границ без сетевой сложности, а модуль с подтверждённой границей потом выносится в сервис почти механически. За распил говорят очередь команд на общий релиз, другой профиль нагрузки или отдельный compliance-контур; против — одна команда, неустоявшийся домен, нет автодеплоя и наблюдаемости.

## План распила

**Цель и метрики.** «Перейти на микросервисы» — не цель. Цель — «команда платежей релизится независимо, а сейчас ждёт общий релиз раз в две недели». Lead time изменений, частота деплоев, MTTR и стоимость инфраструктуры показывают, помогает ли распил, и дают критерий остановки: часть монолита разумно оставить монолитом навсегда.

**Карта связей.** Bounded context через event storming, граф зависимостей в коде, а главное — кто какие таблицы пишет и читает: связанность по данным почти всегда сильнее, чем по коду. История git показывает hotspots — модули, которые меняются чаще всего.

**Модульность внутри.** Границы, которые не удаётся удержать в одном процессе, через сеть станут только хуже. Нередко на этом шаге решается половина проблем.

**Платформа до первого сервиса.** CI/CD, шаблон сервиса, логи, метрики и трассировка (см. `OpenTelemetry в .NET`), брокер, подход к контрактам. Иначе первый же сервис станет источником инцидентов, диагностировать которые нечем.

**Первый кандидат** — модуль с наименьшей связанностью по данным и наибольшей частотой изменений или отдельной причиной масштабирования: уведомления, поиск, генерация документов, интеграция с партнёром. Плохие кандидаты — ядро, от которого зависят все (заказы, пользователи), и модуль без владельца. «Край» системы даёт быструю победу и опыт; ядро разбирают, когда практики отлажены.

Big bang rewrite не работает: месяцы без ценности, новая система догоняет меняющуюся старую, а переключение в один день — огромный риск.

## Strangler fig: фасад перед монолитом

Перед монолитом ставят маршрутизирующий слой, который сначала всё отправляет в монолит. Затем функции по одной переписываются в новых сервисах, маршрут для них переключается, старый код удаляется. Любой шаг обратим возвратом маршрута, а монолит работает всё время миграции.

В .NET фасадом удобно делать YARP. Маршруты с меньшим `Order` проверяются первыми, поэтому новый сервис получает только запросы с пометкой канарейки, а остальное уходит в монолит:

```json
{
  "ReverseProxy": {
    "Routes": {
      "invoices-new": {
        "ClusterId": "invoices",
        "Order": 1,
        "Match": {
          "Path": "/api/invoices/{**rest}",
          "Methods": [ "GET" ],
          "Headers": [ { "Name": "X-Canary", "Values": [ "1" ] } ]
        }
      },
      "legacy": {
        "ClusterId": "monolith",
        "Order": 100,
        "Match": { "Path": "{**catch-all}" }
      }
    },
    "Clusters": {
      "invoices": { "Destinations": { "d1": { "Address": "http://invoices/" } } },
      "monolith": { "Destinations": { "d1": { "Address": "http://legacy/" } } }
    }
  }
}
```

Взвешенного разделения трафика между кластерами в YARP из коробки нет, поэтому долю задают своим middleware до маршрутизации. Решение принимается по стабильному хешу тенанта, а не случайно: один клиент всегда попадает в одну реализацию.

```csharp
var app = builder.Build();

app.Use(async (ctx, next) =>
{
    ctx.Request.Headers.Remove("X-Canary");
    var percent = ctx.RequestServices
        .GetRequiredService<IOptionsMonitor<CanaryOptions>>().CurrentValue.InvoicesPercent;
    var tenant = ctx.Request.Headers["X-Tenant"].ToString();
    var bucket = XxHash32.HashToUInt32(Encoding.UTF8.GetBytes(tenant)) % 100;
    if (bucket < percent)
        ctx.Request.Headers["X-Canary"] = "1";
    await next();
});

app.UseRouting();
app.MapReverseProxy();
app.Run();
```

`string.GetHashCode` здесь не подходит: он рандомизирован между процессами, и экземпляры прокси раскидали бы одного тенанта по разным реализациям. Входящий `X-Canary` удаляют, чтобы клиент не мог выбрать маршрут сам.

Сначала переключают чтения, потом запись; внутренние пользователи → пилотный тенант → 5% → 50% → 100%. Для записи липкость обязательна, иначе данные одной сущности разъедутся по двум хранилищам. Критерий шага — ошибки и latency новой реализации против старой.

**Shadow traffic** для чтений снижает риск ещё до канарейки: запрос зеркалируется в новый сервис, ответы сравниваются, но пользователю отдаётся ответ монолита. Встроенного зеркалирования в YARP нет — его делают своим middleware либо средствами Envoy, nginx или service mesh. Зеркалируют только безопасные запросы: копия `POST` выполнит операцию дважды.

Внутренние вызовы монолита переключают через branch by abstraction: за интерфейсом `IInvoiceService` либо локальная реализация, либо HTTP-клиент к сервису, выбор — feature flag. Прокси становится критичной точкой: несколько экземпляров, минимум логики, свои таймауты на маршрут.

## Разделение общей базы

Самая частая ошибка — вынести код, а базу оставить общей: любая миграция схемы снова требует согласования всех. Делят поэтапно, и каждый шаг обратим.

**Инвентаризация.** Кто читает и пишет каждую таблицу: поиск по коду, `pg_stat_statements`, а также отчёты и ETL, которые ходят в базу напрямую, — их забывают чаще всего. Транзакции, пересекающие будущую границу, нужно найти здесь: они станут сагами (см. `Saga`), и это меняет бизнес-процесс.

**Логическое разделение.** Таблицы будущего сервиса переезжают в свою схему, у модуля свой пользователь БД с правами только на неё — нарушения видны сразу:

```sql
CREATE SCHEMA invoicing;
ALTER TABLE public.invoices SET SCHEMA invoicing;
CREATE ROLE invoicing_app LOGIN;
GRANT USAGE ON SCHEMA invoicing TO invoicing_app;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA invoicing TO invoicing_app;
REVOKE ALL ON ALL TABLES IN SCHEMA invoicing FROM monolith_app;
```

Чужой SQL с join на `invoices` переписывают на вызов модуля, а старому коду на переходный период дают read-only view с ограниченным набором полей — это уже контракт, а не доступ к внутренностям.

**Разрыв связей.** Foreign key на таблицу другого владельца удаляют, ссылочную целостность обеспечивают приложением и событиями (`CustomerDeleted` обрабатывается подписчиком). Join заменяют API-вызовом для единичных объектов, локальной read-only копией нужных полей по событиям для списков и фильтрации или composition на уровне BFF. Отчёты переводят в аналитическое хранилище, наполняемое через CDC. Таблицу, которую пишут несколько модулей, делят по контекстам: `customers` превращается в профиль, кредитные условия и адреса доставки.

**Физический перенос.** Начальная выгрузка в базу сервиса, затем CDC (Debezium или логическая репликация PostgreSQL) догоняет изменения, пока сервис только читает. Сверка — число строк и контрольные суммы по диапазонам. Потом переключают чтение, затем запись.

**Смена владельца записи** — критичный момент. Соблазн — двойная запись: код пишет и в старую таблицу, и в новую базу (или в базу и в брокер). Между двумя записями нет общей транзакции, поэтому падение процесса, таймаут или ретрай после второй записи оставляют хранилища в разном состоянии, а порядок параллельных обновлений в двух местах может различаться. Безопасная последовательность: сервис пишет в свою базу и публикует события через `Outbox`, монолит подписывается и обновляет свою копию для кода, который ещё читает напрямую, а когда прямых чтений не осталось, копию удаляют. На время стабилизации держат обратную синхронизацию для отката. Идентификаторы генерирует сервис — UUID вместо общей sequence, чтобы не было конфликтов при двусторонней синхронизации.

Таблицы и старый код в монолите удаляют последними, после аудита, подтвердившего, что к ним никто не обращается. Без этого шага остаются два источника правды и вечная миграция.

## Что стоит ответить на собеседовании

Микросервисы — независимо развёртываемые сервисы со своими данными, границами по бизнес-возможностям и одной командой-владельцем; они решают проблему масштабирования команд и разных требований к частям системы ценой сети, eventual consistency и обязательной платформы. Модульный монолит часто даёт большую часть пользы без этой цены. Распил начинают с цели и метрик, модульности внутри монолита и платформы, затем выделяют слабо связанный по данным модуль через strangler fig: фасад вроде YARP, постепенное переключение маршрутов, удаление старого кода.

Сильный ответ покажет обратимость каждого шага: shadow traffic для чтений, канарейка по стабильному хешу тенанта с липкостью для записи, branch by abstraction для внутренних вызовов. И подробно разберёт данные: инвентаризация, включая отчёты и ETL, отдельная схема и права, замена join и foreign key на API и копии по событиям, CDC с проверкой, перенос записи через outbox вместо двойной записи, обратная синхронизация для отката и удаление таблиц только после аудита.
