«У нас в Kafka включён exactly-once» — одна из самых частых неточностей на собеседованиях. Отправитель в ненадёжной сети не может отличить потерю сообщения от потери подтверждения, поэтому выбирает между «не повторять» и «повторять». Ровно одной доставки протокол не даёт. Зато можно добиться, чтобы **эффект** был ровно один: сообщение придёт дважды, а результат в базе — один. Этот раздел про то, как это собирается на практике и где кончаются гарантии брокера.

## Доставка и эффект

Отправитель послал сообщение и не получил подтверждения. Возможно, сообщение потерялось. Возможно, оно обработано, а потерялось подтверждение. Спросить «дошло ли» бесполезно — ответ тоже может потеряться. Это задача двух генералов, и у неё нет решения. Отсюда три семантики:

- **at-most-once** — не повторять: дублей нет, потери возможны;
- **at-least-once** — повторять до подтверждения: потерь нет, дубли возможны;
- **exactly-once эффект** — at-least-once доставка плюс обработка, превращающая дубль в no-op.

Формула, которую стоит произнести на собеседовании: **exactly-once = at-least-once + идемпотентность**. Любая система, заявляющая exactly-once, обеспечивает его внутри своей границы за счёт дедупликации и транзакций, но не для побочных эффектов снаружи.

## Где коммитить offset

У консьюмера семантику определяет момент, когда он сообщает брокеру «обработано». Закоммитил offset до обработки и упал — сообщение потеряно, это at-most-once. Обработал и упал до коммита — сообщение придёт снова, это at-least-once:

```csharp
var consumer = new ConsumerBuilder<string, string>(new ConsumerConfig
{
    BootstrapServers = "kafka:9092",
    GroupId = "billing",
    EnableAutoCommit = false,
    AutoOffsetReset = AutoOffsetReset.Earliest
}).Build();

consumer.Subscribe("payments");

while (!ct.IsCancellationRequested)
{
    var result = consumer.Consume(ct);
    await HandleAsync(result.Message, ct);
    consumer.Commit(result);
}
```

Дубли здесь неизбежны: падение между `HandleAsync` и `Commit`, rebalance группы, повторная публикация отправителем после сбоя relay outbox. Задача — сделать так, чтобы `HandleAsync` при повторе ничего не менял. Синхронный `Commit` на каждое сообщение медленный, поэтому в реальном коде коммитят пачками, но принцип тот же: сначала эффект, потом offset. Подробно о гарантиях доставки Kafka — в разделе «Kafka и очереди».

## Способ 1. Inbox

Идентификатор сообщения записывается в таблицу inbox **в той же транзакции**, что и бизнес-изменение, а уникальный индекс отсекает повтор:

```csharp
await using var tx = await db.Database.BeginTransactionAsync(ct);

var inserted = await db.Database.ExecuteSqlAsync($"""
    INSERT INTO inbox (consumer, message_id)
    VALUES ('billing', {message.Id})
    ON CONFLICT DO NOTHING
    """, ct);

if (inserted == 1)
{
    await ApplyPaymentAsync(message, ct);
    await db.SaveChangesAsync(ct);
}

await tx.CommitAsync(ct);
```

Ноль вставленных строк — сообщение уже обработано, и коммит offset его просто пропускает. Два экземпляра, получившие одно сообщение одновременно, упираются в уникальный индекс: второй `INSERT` ждёт коммита первого и получает ноль. Детали — ключ, хранение, очистка — в статье `Идемпотентность`. Здесь важны три условия:

- **одна транзакция** — отметка в Redis и данные в PostgreSQL снова дают dual write;
- **стабильный id от отправителя** — рождённый вместе с событием, например id записи outbox, а не сгенерированный при каждой отправке;
- **срок хранения больше окна повторов** — retention топика, время жизни DLQ, ручной replay.

## Способ 2. Естественная идемпотентность

Часто таблица inbox не нужна, потому что операция повторяема сама по себе:

- установка конечного состояния вместо инкремента: `SET status = 'paid'`, а не `balance = balance + 100`;
- условное обновление по версии: `UPDATE ... WHERE id = @id AND version < @version` — устаревший или повторный апдейт ничего не меняет;
- бизнес-ключ с уникальным ограничением: один платёж на `order_id`, повторная вставка падает на конфликте.

## Способ 3. Offset в базе

Если результат обработки пишется только в базу, offset можно хранить там же, в той же транзакции, а брокеру не доверять вовсе. При назначении партиций консьюмер встаёт на offset из базы:

```csharp
var consumer = new ConsumerBuilder<string, string>(config)
    .SetPartitionsAssignedHandler((c, partitions) =>
        partitions.Select(tp => new TopicPartitionOffset(tp, offsets.Load(tp))))
    .Build();
```

```sql
UPDATE consumer_offsets
SET next_offset = @offset + 1
WHERE group_id = 'billing' AND topic = @topic AND partition = @partition;
```

Обновление offset и бизнес-изменение коммитятся вместе. После падения консьюмер продолжит ровно с того места, до которого результат зафиксирован, — это честный exactly-once для эффекта в базе без всякой дедупликации.

## Способ 4. Транзакции Kafka

Для конвейеров «прочитать из Kafka → обработать → записать в Kafka» у Kafka есть собственный exactly-once. Он складывается из трёх механизмов:

| Механизм | Что убирает |
| --- | --- |
| идемпотентный producer: producer id и sequence number на партицию | дубли от ретраев producer'а |
| транзакции с `transactional.id` | частичную запись; атомарно фиксирует выход и offset входа |
| `isolation.level=read_committed` у читателей | чтение незакоммиченных и отменённых записей |

```csharp
using var producer = new ProducerBuilder<string, string>(new ProducerConfig
{
    BootstrapServers = "kafka:9092",
    TransactionalId = $"invoicer-{instanceId}",
    EnableIdempotence = true
}).Build();

producer.InitTransactions(TimeSpan.FromSeconds(30));

var result = consumer.Consume(ct);
producer.BeginTransaction();
producer.Produce("invoices", new Message<string, string>
{
    Key = result.Message.Key,
    Value = BuildInvoice(result.Message.Value)
});
producer.SendOffsetsToTransaction(
    [new TopicPartitionOffset(result.TopicPartition, result.Offset + 1)],
    consumer.ConsumerGroupMetadata,
    TimeSpan.FromSeconds(30));
producer.CommitTransaction();
```

Консьюмеры ниже по потоку читают с `IsolationLevel = IsolationLevel.ReadCommitted`. Если процесс упал до `CommitTransaction`, транзакция отменится, offset не сдвинется, и новый владелец партиции обработает то же сообщение заново. Для выходного топика это невидимо: отменённые записи `read_committed`-читатели пропускают. Но HTTP-вызов, письмо или `INSERT` в базу из этого обработчика выполнятся повторно.

## Цена транзакций Kafka

- **Задержка.** `read_committed`-читатель видит данные только после коммита, поэтому транзакции делают на пачку, и размер пачки добавляется к задержке.
- **Пропускная способность.** Каждая транзакция — запросы к transaction coordinator и маркеры во все затронутые партиции. Транзакция на одно сообщение, как в примере выше, убивает throughput.
- **Зависшая транзакция** задерживает всех `read_committed`-читателей партиции до коммита или `transaction.timeout.ms`.
- **Обработка ошибок.** Fenced producer — фатально, его пересоздают; abortable-ошибка требует `AbortTransaction` и отката консьюмера к закоммиченным offset, иначе он пропустит сообщения отменённой транзакции.

## Kafka и база не коммитятся вместе

Транзакция Kafka и транзакция базы — две независимые транзакции в двух системах. В каком порядке их ни коммить, остаётся окно:

| Порядок | Падение между коммитами |
| --- | --- |
| сначала база, потом Kafka | offset не сдвинут, сообщение обработают снова — повторная запись в базу |
| сначала Kafka, потом база | событие ушло, offset сдвинут, а изменение в базе потеряно |

Поэтому для связки с базой транзакции Kafka не используют. Вход в базу — inbox или offset в базе. Выход из базы в Kafka — outbox (см. `Outbox`). «Прочитал, записал в базу, опубликовал» — offset или inbox плюс запись в outbox в одной транзакции базы.

## Внешние побочные эффекты

Самое трудное место — вызов, который не откатывается вместе с транзакцией:

- **ключ идемпотентности** — платёжные провайдеры принимают его, и повтор с тем же ключом вернёт исходный результат. Ключ выводят детерминированно из id сообщения;
- **спросить, а не повторять** — если ключей нет, сначала записать намерение со статусом, при повторе запросить у внешней системы статус по своему идентификатору;
- **принять редкий дубль** — для писем и пушей дубль обычно дешевле потери, и хватает дедупликации на стороне отправки.

## Типичные ошибки

- коммит offset или ack до коммита базы — тихая потеря сообщений;
- дедупликация в памяти процесса — не переживает рестарт и не работает на нескольких экземплярах;
- новый id при каждой отправке — повтор становится «новым» сообщением;
- уверенность, что транзакции Kafka защищают запись во внешнюю базу.

## Что стоит ответить на собеседовании

Exactly-once доставку по ненадёжной сети гарантировать нельзя — это задача двух генералов. Достижим exactly-once эффект: at-least-once доставка плюс обработка, превращающая дубль в no-op. Способы: inbox с уникальным индексом по id сообщения в одной транзакции с изменением, естественная идемпотентность (конечное состояние, версия, бизнес-ключ), хранение offset в базе вместе с результатом.

Сильный ответ уточнит, что exactly-once в Kafka — это идемпотентный producer, транзакции, атомарно фиксирующие выход и offset входа, и `read_committed`, и что гарантия заканчивается на границе Kafka: побочные эффекты обработчика повторяются, а с транзакцией базы транзакция Kafka не коммитится атомарно. Назовёт цену — задержку, throughput, зависшие транзакции — и предложит для связки с базой outbox и inbox, а для внешних API — детерминированный ключ идемпотентности.
