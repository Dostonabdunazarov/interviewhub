Оформление заказа затрагивает склад, платежи и доставку — три сервиса с тремя базами. Общей транзакции между ними нет, и делать её через two-phase commit не стоит (почему — в статье `Почему 2PC проблематичен`). Сага — это бизнес-процесс, разбитый на цепочку локальных транзакций: каждый шаг атомарно меняет данные своего сервиса и сообщает о результате, а при неудаче уже сделанные шаги отменяются компенсирующими действиями. Атомарность «всё или ничего» заменяется на «всё или аккуратно отменено», а изоляция пропадает совсем — и именно это интервьюер хочет услышать.

## Фундамент: без него сага зависает

Любая реализация держится на трёх вещах:

- **локальная транзакция плюс outbox на каждом шаге** — изменение и сообщение о нём фиксируются вместе. Если сервис изменил базу, а событие потерялось, сага зависнет навсегда (см. `Outbox`);
- **идемпотентные обработчики** — сообщения приходят повторно, и повторный `ReserveStock` не должен резервировать дважды (см. `Идемпотентность`);
- **correlation id** — каждый экземпляр саги однозначно определяется, обычно идентификатором заказа.

## Типы шагов и pivot

Дизайн саги начинается с классификации шагов:

| Тип | Пример | Как обращаться |
| --- | --- | --- |
| compensatable | резерв товара, hold денег на карте | есть обратная операция: снять резерв, void |
| pivot | capture платежа, передача курьеру | точка невозврата: после неё только вперёд |
| retriable | начисление бонусов, письмо | должен завершиться, повторяется до успеха |

Порядок шагов — главный рычаг. Рискованные и необратимые действия ставят как можно позже, а до pivot делают только то, что легко отменить. Поэтому деньги не списывают, а **блокируют** (authorize), товар не списывают, а **резервируют**, и только когда всё сошлось, выполняют capture и отгрузку. Письмо «заказ оформлен» отправляют по событию `OrderConfirmed`, а не после первого шага.

## Хореография

В хореографии центрального участника нет. Каждый сервис слушает события и публикует свои:

```text
Orders     → OrderSubmitted
Inventory  ← OrderSubmitted   → StockReserved | StockRejected
Payments   ← StockReserved    → PaymentAuthorized | PaymentFailed
Inventory  ← PaymentFailed    → StockReleased
Orders     ← PaymentAuthorized → заказ подтверждён
Orders     ← PaymentFailed     → заказ отменён
```

Кода мало, единой точки отказа нет, сервисы связаны только событиями. Но процесс нигде не описан целиком: чтобы понять, где застрял заказ 42, нужно собирать трассы и логи нескольких сервисов. Никто не замечает, что ответ не пришёл, если специально не написать «сторожа». Изменение процесса — правка нескольких сервисов разных команд, а при росте числа участников появляются циклы событий.

## Оркестрация на MassTransit

В оркестрации процессом управляет отдельный компонент — state machine, которая хранит состояние экземпляра и рассылает команды. В MassTransit это `MassTransitStateMachine`:

```csharp
public sealed class OrderState : SagaStateMachineInstance
{
    public Guid CorrelationId { get; set; }
    public string CurrentState { get; set; } = null!;
    public Guid? PaymentTimeoutTokenId { get; set; }
}

public sealed class OrderStateMachine : MassTransitStateMachine<OrderState>
{
    public State Reserving { get; private set; } = null!;
    public State Paying { get; private set; } = null!;

    public Event<OrderSubmitted> Submitted { get; private set; } = null!;
    public Event<StockReserved> Reserved { get; private set; } = null!;
    public Event<PaymentAuthorized> Authorized { get; private set; } = null!;
    public Event<PaymentFailed> Failed { get; private set; } = null!;
    public Schedule<OrderState, PaymentTimeoutExpired> PaymentTimeout { get; private set; } = null!;

    public OrderStateMachine()
    {
        InstanceState(x => x.CurrentState);

        Event(() => Submitted, e => e.CorrelateById(m => m.Message.OrderId));
        Event(() => Reserved, e => e.CorrelateById(m => m.Message.OrderId));
        Event(() => Authorized, e => e.CorrelateById(m => m.Message.OrderId));
        Event(() => Failed, e => e.CorrelateById(m => m.Message.OrderId));

        Schedule(() => PaymentTimeout, x => x.PaymentTimeoutTokenId, s =>
        {
            s.Delay = TimeSpan.FromMinutes(15);
            s.Received = r => r.CorrelateById(m => m.Message.OrderId);
        });

        Initially(
            When(Submitted)
                .Publish(ctx => new ReserveStock(ctx.Saga.CorrelationId))
                .TransitionTo(Reserving));

        During(Reserving,
            When(Reserved)
                .Publish(ctx => new AuthorizePayment(ctx.Saga.CorrelationId))
                .Schedule(PaymentTimeout, ctx => new PaymentTimeoutExpired(ctx.Saga.CorrelationId))
                .TransitionTo(Paying));

        During(Paying,
            When(Authorized)
                .Unschedule(PaymentTimeout)
                .Publish(ctx => new ConfirmOrder(ctx.Saga.CorrelationId))
                .Finalize(),
            When(Failed)
                .Unschedule(PaymentTimeout)
                .Publish(ctx => new ReleaseStock(ctx.Saga.CorrelationId))
                .Publish(ctx => new CancelOrder(ctx.Saga.CorrelationId))
                .Finalize(),
            When(PaymentTimeout.Received)
                .Publish(ctx => new ReleaseStock(ctx.Saga.CorrelationId))
                .Publish(ctx => new CancelOrder(ctx.Saga.CorrelationId))
                .Finalize());
    }
}
```

Состояние хранится в базе. Два события одного заказа могут прийти параллельно, поэтому репозиторию включают оптимистичную конкурентность (у строки состояния в маппинге настраивают токен конкурентности, в PostgreSQL обычно `xmin`), а сообщения из саги отправляют через транзакционный outbox — тогда смена состояния и исходящие команды фиксируются одной транзакцией:

```csharp
x.AddSagaStateMachine<OrderStateMachine, OrderState>()
    .EntityFrameworkRepository(r =>
    {
        r.ConcurrencyMode = ConcurrencyMode.Optimistic;
        r.ExistingDbContext<OrdersDbContext>();
        r.UsePostgres();
    });
```

`Schedule` требует настроенного планировщика сообщений — встроенной отложенной доставки брокера или внешнего. Таймаут — то, чего в хореографии нет по умолчанию: если платёж не ответил за 15 минут, оркестратор сам запускает компенсацию. Для процессов длиной в дни и недели со сложной логикой повторов смотрят на workflow-движки вроде Temporal.

| Вопрос | Хореография | Оркестрация |
| --- | --- | --- |
| где застрял заказ 42 | трассы и логи нескольких сервисов | одна строка в таблице состояния |
| кто замечает, что ответа нет | никто без «сторожа» | таймаут в state machine |
| изменение процесса | несколько сервисов, согласованный релиз | один оркестратор |
| тестирование | только интеграционно | state machine тестируется изолированно |
| связанность | только через события | оркестратор знает всех участников |

Хореография хороша для коротких реакций на события между доменами, оркестрация — когда у процесса есть бизнес-владелец, SLA, ветвления и компенсации.

## Компенсация — не откат

Компенсация — новая бизнес-операция, которая семантически отменяет эффект: списание не «откатывают», а делают refund; проводку не удаляют, а сторнируют; письмо не отзывают, а отправляют уточнение. В истории заказа остаются и действие, и отмена — бухгалтерия так работает веками. Требования к компенсации:

- **идемпотентна** — `ReleaseStock` может прийти дважды;
- **работает от текущего состояния** — за время саги остаток могли изменить другие заказы, поэтому компенсация резерва — «вернуть N», а не «восстановить прежнее значение»;
- **переживает гонку с прямым шагом** — компенсация может обогнать сам шаг, если тот ещё ретраится. Участник запоминает «отменено» и отклоняет запоздавший `ReserveStock`;
- **не может упасть окончательно** — ретраится с backoff, а исчерпав попытки, переводит сагу в состояние «требует внимания» и создаёт задачу оператору. Ручная обработка — часть дизайна, а не авария.

## Нет изоляции

Промежуточные состояния саги видны всем. Пока заказ в `Paying`, другой процесс может его изменить, а отчёт — посчитать товар проданным. Классические аномалии — потерянные обновления и грязные чтения, только растянутые на минуты. Контрмеры:

- **семантическая блокировка** — статус `Pending` запрещает конфликтующие операции над заказом, пока сага не завершится;
- **коммутативные операции** — резерв и снятие резерва как `+N` и `−N` дают верный итог в любом порядке;
- **перечитать перед pivot** — проверить цену и остаток непосредственно перед capture;
- **версии** — обновление с проверкой версии (см. `Оптимистичная блокировка`) отбрасывает действие, основанное на устаревших данных.

## Наблюдаемость

У оркестратора естественные метрики: число экземпляров в каждом состоянии, возраст самых старых незавершённых, доля компенсаций. Рост доли компенсаций часто первым показывает проблему у участника — раньше, чем его собственные алерты.

## Что стоит ответить на собеседовании

Сага — цепочка локальных транзакций, каждая с outbox, с компенсирующими действиями при неудаче. Она даёт eventual consistency без распределённых блокировок, но не даёт изоляции. Шаги делятся на compensatable, pivot и retriable; необратимое ставят как можно позже, деньги сначала блокируют и списывают только после pivot. Хореография — сервисы реагируют на события друг друга, просто, но процесс нигде не виден; оркестрация — state machine с состоянием в базе и таймаутами, процесс в одном месте.

Сильный ответ добавит, что компенсация — семантическая отмена, а не откат: идемпотентная, от текущего состояния, устойчивая к обгону прямого шага, с ручной обработкой как последним шагом. И назовёт защиту от отсутствия изоляции: семантические блокировки, коммутативные операции, перечитывание перед pivot и проверку версий.
