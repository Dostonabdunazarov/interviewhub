Внутреннее API — такой же публичный контракт, как внешнее, только его потребители сидят в соседних командах и деплоятся по своему графику. Если контракт повторяет схему базы, течёт внутренними сущностями и ломается при добавлении поля, независимого деплоя не будет: каждый релиз превратится в согласование. Поэтому две темы идут вместе — как спроектировать контракт, чтобы он переживал изменения, и как проверить, что изменение в сервисе A не сломало сервис B, не поднимая всю систему.

## Операции, а не таблицы

Контракт описывает бизнес-возможности сервиса. `POST /orders/{id}/cancel` лучше, чем `PATCH /orders/{id}` с `{ "status": 5 }`: допустимые переходы и инварианты остаются внутри сервиса, клиенту не нужно знать, что из `Shipped` отменить нельзя. Ресурсный стиль хорош для чтения и простых коллекций, а действия с правилами честнее выражать RPC-подобными операциями.

Наружу отдают отдельные DTO, а не EF-сущности — новая колонка в таблице не должна менять контракт. Операции делают крупными: если экран требует десяти вызовов одного сервиса, API слишком «болтливое», и каждая сетевая поездка добавляет задержку и точку отказа. Отдельный анти-паттерн — общий NuGet-пакет с доменными моделями для всех сервисов: он незаметно связывает релизы так же, как общая база (см. `Границы сервисов`).

## REST или gRPC внутри

| | REST + OpenAPI | gRPC |
| --- | --- | --- |
| контракт | спецификация, часто генерируется из кода | `.proto` — первичный источник |
| формат | JSON, читается глазами | protobuf, компактнее и быстрее сериализуется |
| клиенты | генерация по OpenAPI или ручной `HttpClient` | генерируются из `.proto` |
| стриминг | нет (SSE/WebSocket отдельно) | серверный, клиентский, двунаправленный |
| отладка, gateway | curl, любые прокси | нужен HTTP/2 и инструменты вроде grpcurl |

Типичный выбор — gRPC для плотного трафика «сервис-сервис», REST для всего, что проходит через gateway или нужно внешним клиентам. В обоих случаях контракт — артефакт в репозитории: изменения проходят ревью, а CI проверяет их на breaking changes (`buf breaking` для protobuf, сравнение OpenAPI-спецификаций для REST). Правила эволюции — только добавлять поля, не делать новые поля обязательными, клиенты игнорируют незнакомое — разобраны в `Версионирование контрактов`.

## Команды и события

Не каждое взаимодействие должно быть вызовом. Команда (`ReserveStock`) адресована одному владельцу, сформулирована в повелительном наклонении и может быть отклонена — отправитель ждёт результат. Событие (`OrderPlaced`) — свершившийся факт: издатель не знает подписчиков, и отказ подписчика его не ломает. Если сервису нужен ответ прямо сейчас — синхронный запрос; если он лишь сообщает, что что-то произошло, — событие. Цепочка `A → B → C → D` складывает задержки и перемножает вероятности отказа, а данные, которые сервис запрашивает в каждом запросе, лучше держать локальной копией, обновляемой событиями. Подробнее — `Синхронное vs асинхронное взаимодействие`.

## Идемпотентность и пагинация

Клиент повторяет запрос после таймаута, не зная, дошёл ли первый. Для операций с побочными эффектами это значит дубль платежа. Защита — ключ идемпотентности: клиент генерирует его один раз на бизнес-операцию и передаёт в заголовке `Idempotency-Key`, сервер сохраняет ключ вместе с хешем запроса и ответом. Повтор с тем же ключом возвращает сохранённый ответ, тот же ключ с другим телом — ошибка. Ключ и результат пишутся в одной транзакции с бизнес-изменением, иначе гонка двух параллельных повторов всё равно даст дубль. Детали — в `Идемпотентность`.

Любой список ограничен: внутренний клиент тоже может попросить миллион строк. Offset-пагинация проста, но деградирует на глубоких страницах и пропускает или дублирует строки при вставках. Для лент и выгрузок используют keyset: клиент получает непрозрачный курсор и передаёт его в следующий запрос: `GET /orders?limit=100&after=<cursor>`.

## Ошибки и таймауты

Единый формат ошибок — `ProblemDetails` (RFC 9457, заменил RFC 7807). В ASP.NET Core его включают через `AddProblemDetails()`, а из эндпоинта возвращают `TypedResults.Problem`:

```csharp
builder.Services.AddProblemDetails();

app.MapPost("/orders/{id:guid}/cancel", async (Guid id, OrderService orders) =>
{
    var result = await orders.CancelAsync(id);
    return result switch
    {
        CancelResult.Ok => Results.NoContent(),
        CancelResult.NotFound => Results.NotFound(),
        CancelResult.AlreadyShipped => TypedResults.Problem(
            statusCode: StatusCodes.Status409Conflict,
            title: "Order already shipped",
            type: "https://errors.example.com/orders/already-shipped"),
        _ => throw new UnreachableException()
    };
});
```

Код статуса — часть контракта, потому что по нему клиент решает, повторять ли. 400, 404, 409, 422 — повтор не поможет; 429, 503 и таймаут — можно повторить с backoff, уважая `Retry-After` (см. `Retry, jitter и retry storm`). Поле `type` даёт клиенту стабильный машинный идентификатор ошибки вместо разбора текста.

Таймауты задаёт вызывающая сторона, и они обязаны быть. У `HttpClient` по умолчанию 100 секунд — для внутреннего вызова это почти бесконечность; у gRPC-вызова без явного дедлайна ограничения нет вовсе. Таймаут каждого шага должен укладываться в бюджет вызывающего: бессмысленно ждать соседа 30 секунд, если клиент уже ушёл через 5. В gRPC дедлайн передаётся по цепочке — в ASP.NET Core это включается через `EnableCallContextPropagation()` на клиенте из `AddGrpcClient`, и нижний сервис видит, сколько времени осталось. Для HTTP используют резилиентность из `HttpClient` и `Circuit breaker`.

## Пирамида для микросервисов

Пирамида сохраняется, но центр тяжести смещается: основная масса — быстрые тесты внутри сервиса, совместимость между сервисами проверяют контрактами, а e2e остаётся тонкая верхушка.

| Уровень | Что проверяет | Инструменты |
| --- | --- | --- |
| юнит | доменная логика, агрегаты, расчёты | xUnit, без инфраструктуры |
| компонентный | сервис целиком: HTTP → логика → реальная БД и брокер, соседи — заглушки | `WebApplicationFactory`, Testcontainers, WireMock.Net |
| контрактный | запросы потребителя совпадают с тем, что умеет провайдер | PactNet, проверка схем в CI |
| e2e | критичный сценарий через несколько реальных сервисов | стенд, .NET Aspire, Playwright |

Юнит-тесты дешёвы и проверяют правила — переходы статусов, расчёт цены, инварианты агрегата. Но ошибки маппинга, миграций, сериализации и регистрации в DI они не видят: всё это замокано.

## Компонентные тесты с Testcontainers

Рабочая лошадка — тест сервиса целиком через `WebApplicationFactory<Program>`: настоящий конвейер ASP.NET Core в памяти, настоящая PostgreSQL в контейнере, внешние HTTP-зависимости на WireMock.Net. EF Core InMemory вместо базы не подходит: он не проверяет транзакции, ограничения, SQL-специфику и миграции.

```csharp
public sealed class OrdersApiFactory : WebApplicationFactory<Program>, IAsyncLifetime
{
    private readonly PostgreSqlContainer _db = new PostgreSqlBuilder()
        .WithImage("postgres:16-alpine")
        .Build();

    public WireMockServer Payments { get; } = WireMockServer.Start();

    protected override void ConfigureWebHost(IWebHostBuilder builder)
    {
        builder.UseSetting("ConnectionStrings:Orders", _db.GetConnectionString());
        builder.UseSetting("Services:Payments", Payments.Url);
    }

    public Task InitializeAsync() => _db.StartAsync();

    async Task IAsyncLifetime.DisposeAsync()
    {
        Payments.Stop();
        await _db.DisposeAsync();
        await base.DisposeAsync();
    }
}

public sealed class PlaceOrderTests(OrdersApiFactory factory) : IClassFixture<OrdersApiFactory>
{
    [Fact]
    public async Task Payment_unavailable_returns_503_problem()
    {
        factory.Payments
            .Given(Request.Create().WithPath("/payments").UsingPost())
            .RespondWith(Response.Create().WithStatusCode(503).WithDelay(TimeSpan.FromSeconds(1)));

        var resp = await factory.CreateClient()
            .PostAsJsonAsync("/orders", new { ProductId = 1, Qty = 2 });

        Assert.Equal(HttpStatusCode.ServiceUnavailable, resp.StatusCode);
        Assert.Equal("application/problem+json", resp.Content.Headers.ContentType?.MediaType);
    }
}
```

WireMock удобен именно для отказов: задержка, 503, обрыв соединения — поведение, которое на живом стенде воспроизвести почти невозможно. Kafka поднимается так же — `KafkaBuilder` из Testcontainers.Kafka, адрес через `GetBootstrapAddress()`. С реальным брокером проверяют, что событие публикуется с нужным ключом и схемой и что консьюмер идемпотентен на повторной доставке; для MassTransit есть `ITestHarness` с проверками `Published<T>()` и `Consumed<T>()`. Контейнер делят между тестами класса, а данные изолируют уникальными идентификаторами или очисткой (Respawn).

## Контрактные тесты

Компонентный тест провайдера не знает, как его вызывают потребители, а тест потребителя проверяет поведение против заглушки, которую написал он сам. Разрыв закрывают consumer-driven контракты. Потребитель в своём тесте описывает ожидаемое взаимодействие, Pact поднимает по нему мок-сервер и сохраняет контракт в файл:

```csharp
var pact = Pact.V4("Orders", "Payments", new PactConfig()).WithHttpInteractions();

pact.UponReceiving("authorize payment")
    .Given("customer 42 has enough funds")
    .WithRequest(HttpMethod.Post, "/payments")
    .WithJsonBody(new { orderId = "o-1", amount = 100.0m })
    .WillRespond()
    .WithStatus(HttpStatusCode.Created)
    .WithJsonBody(new { paymentId = Match.Type("p-1"), status = "Authorized" });

await pact.VerifyAsync(async ctx =>
{
    var client = new PaymentsClient(new HttpClient { BaseAddress = ctx.MockServerUri });
    var result = await client.AuthorizeAsync("o-1", 100m);
    Assert.Equal("Authorized", result.Status);
});
```

Контракт публикуется в Pact Broker, а CI провайдера проигрывает все контракты потребителей против настоящего сервиса через `PactVerifier`; `Given` соответствует provider state — данным, которые провайдер готовит перед проверкой. Перед деплоем `can-i-deploy` отвечает, совместима ли эта версия с тем, что сейчас в проде. Так провайдер узнаёт, какие поля реально используются, и может удалить остальные. Для асинхронных взаимодействий у Pact есть message-контракты; более лёгкая альтернатива — проверка совместимости схем в Schema Registry и `buf breaking`.

## E2E и проверки в проде

E2E держат для пары критичных сценариев вроде «оформить и оплатить заказ». Они медленные, нестабильные, по падению сложно понять виноватого, и они возвращают связанность релизов: «нельзя выкатывать, пока e2e не зелёные у всех».

Часть уверенности переносят в прод. Canary-релиз отдаёт новой версии малую долю трафика и откатывается автоматически по метрикам ошибок и латентности; синтетические проверки регулярно проходят ключевой сценарий тестовым пользователем; smoke-тесты запускаются сразу после деплоя. Без нормальной наблюдаемости это не работает (см. `Логи, метрики, трассировки`).

## Что стоит ответить на собеседовании

API между сервисами описывает бизнес-операции, а не таблицы: отдельные DTO, крупные вызовы, ключ идемпотентности на операциях с побочными эффектами, пагинация на всех списках, единый формат ошибок `ProblemDetails` с кодами, по которым клиент понимает, можно ли повторять, обязательные таймауты. Контракт меняется только обратно совместимо и хранится как артефакт — `.proto` или OpenAPI с проверкой breaking changes в CI. Тестируют слоями: много юнитов, компонентные тесты через `WebApplicationFactory` с реальной базой в Testcontainers и заглушками соседей в WireMock.Net, контрактные тесты и минимум e2e.

Сильный ответ объяснит, чем команда отличается от события и почему цепочки синхронных вызовов опасны, расскажет про бюджет таймаутов и передачу дедлайна в gRPC и про хранение ключа идемпотентности в одной транзакции с изменением. На вопрос «как проверить, что изменение в A не сломало B без всей системы» он ответит consumer-driven контрактами с Pact Broker и `can-i-deploy`, а e2e оставит для пары критичных сценариев, дополнив их canary-релизами и синтетическими проверками в проде.
