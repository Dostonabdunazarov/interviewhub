Главное обещание микросервисов — независимый деплой. Оно держится ровно до первого изменения контракта, которое требует выкатить провайдера и всех потребителей одновременно. Версионирование контрактов — это набор правил, позволяющих менять API и события по одному сервису за раз. Про механику версий REST API — URL, заголовки, `Asp.Versioning`, заголовки `Deprecation` и `Sunset` — рассказано в статье `Дизайн API и версионирование`. Здесь — то, что специфично для общения сервисов: совместимость в обе стороны, protobuf, события в брокере и автоматическая проверка контрактов.

## Что такое контракт

Контракт — не всё, что провайдер отдаёт, а то, на что потребители реально опираются: имена и типы полей, обязательность, допустимые значения, статус-коды и — самое коварное — смысл. Поле `total`, которое вчера включало НДС, а сегодня нет, проходит любую проверку схемы и ломает бухгалтерию.

Отсюда два правила, на которых держится всё остальное:

- **провайдер** в рамках версии делает только обратно совместимые изменения: добавляет необязательное, не удаляет, не переименовывает, не меняет тип и смысл;
- **потребитель** пишется как tolerant reader: игнорирует незнакомые поля, не падает на неизвестном значении enum и читает только то, что ему нужно.

Ломающее изменение — это новая версия, которая живёт рядом со старой, пока все потребители не перейдут.

## Backward, forward и порядок деплоя

Совместимость бывает в две стороны, и от неё зависит, кого выкатывать первым:

| Совместимость | Что означает | Кого обновлять первым |
| --- | --- | --- |
| backward | новый читатель понимает данные, записанные по старой схеме | потребителей |
| forward | старый читатель понимает данные, записанные по новой схеме | провайдера |
| full | обе сразу | в любом порядке |

Для синхронного API обычно нужна backward-совместимость сервера по запросам и forward-совместимость клиентов по ответам: новый сервер принимает старые запросы, старые клиенты переживают новые поля в ответе. Для событий картина сложнее: в топике одновременно лежат сообщения разных версий, и читать их будут и старые, и новые подписчики.

## Protobuf и gRPC

В protobuf поля идентифицируются номерами, а не именами, и это определяет правила эволюции:

```protobuf
syntax = "proto3";

package shop.orders.v1;

message OrderPlaced {
  reserved 3;
  reserved "discount";

  string order_id = 1;
  int64 total_minor = 2;
  string currency = 4;
  OrderChannel channel = 5;
}

enum OrderChannel {
  ORDER_CHANNEL_UNSPECIFIED = 0;
  ORDER_CHANNEL_WEB = 1;
  ORDER_CHANNEL_MOBILE = 2;
}
```

- **добавить поле с новым номером** — совместимо: старый код его не знает и пропускает, а в proto3 отсутствующее поле читается значением по умолчанию;
- **удалить поле** — можно, но номер и имя помечают `reserved`, чтобы их никогда не переиспользовали. Иначе старый клиент прочитает новое поле как старое с другим смыслом;
- **переименовать** — для бинарного формата безопасно, но ломает JSON-представление и JSON transcoding;
- **сменить тип или номер** — ломает;
- **enum** начинают с нулевого значения `UNSPECIFIED` — это значение получит читатель, если поле не задано.

Для несовместимых изменений заводят новый пакет `shop.orders.v2` и обслуживают обе версии сервиса параллельно. Проверку в CI делает `buf breaking`: он сравнивает `.proto` с предыдущей версией и падает на ломающих изменениях.

## Почему события труднее

У REST API видно, кто его вызывает: логи, метрики по client id. У событий так не получается:

- **подписчиков не видно** — издатель не знает, кто читает топик и какие поля ему важны;
- **старые сообщения живут долго** — в топике, в retry-очередях, в DLQ, в outbox-таблице. Новая версия подписчика при replay обязана прочитать и их;
- **нет параллельного эндпоинта** — нельзя «оставить v1 по старому адресу», сообщение уже записано.

Поэтому для событий правила строже. Событие несёт бизнес-факт с минимумом полей — `OrderShipped { OrderId, ShippedAt, Carrier }`, а не снимок всей сущности: меньше поверхность контракта, меньше поводов его ломать. Интеграционные события отделяют от внутренних доменных, чтобы внутреннюю модель можно было менять свободно. Типичные причины будущих ломающих изменений закрывают сразу: сумма — вместе с валютой, время — в UTC, идентификаторы — строками или UUID. В каждом событии есть id для дедупликации, время возникновения и тип с версией.

## Schema Registry

В Kafka контракт событий обычно держат в Schema Registry. Схема (Avro, Protobuf или JSON Schema) регистрируется для subject, а режим совместимости проверяет каждую новую версию при регистрации — несовместимую схему зарегистрировать не получится, и producer не сможет публиковать сообщения по ней. Пример совместимого изменения Avro — новое поле с значением по умолчанию:

```json
{
  "type": "record",
  "name": "OrderPlaced",
  "namespace": "shop.orders",
  "fields": [
    { "name": "orderId", "type": "string" },
    { "name": "totalMinor", "type": "long" },
    { "name": "currency", "type": "string", "default": "EUR" }
  ]
}
```

Режимы отвечают на вопрос «с чем сравнивать»: `BACKWARD` (по умолчанию) — новая схема читает данные предыдущей, значит, сначала обновляют потребителей; `FORWARD` — старая схема читает данные новой, сначала обновляют producer; `FULL` — и то и другое. Варианты `_TRANSITIVE` сравнивают не с последней версией, а со всеми предыдущими — это важно, если в топике лежат сообщения многих версий. В Avro поле без значения по умолчанию добавить backward-совместимо нельзя: новый читатель не знает, что подставить для старых записей.

Схема не ловит смену смысла. «Сумма теперь без НДС» проходит любой режим — от этого защищает только ревью и новое поле с новым именем, например `totalExclVat`.

## Tolerant reader в .NET

Потребитель не должен быть строже, чем нужно. В System.Text.Json неизвестные свойства по умолчанию пропускаются — главное не включить обратное:

```csharp
public sealed record OrderPlaced(
    Guid OrderId,
    long TotalMinor,
    string? Currency,
    string? Channel);

var options = new JsonSerializerOptions(JsonSerializerDefaults.Web)
{
    UnmappedMemberHandling = JsonUnmappedMemberHandling.Skip
};

var channel = message.Channel switch
{
    "web" => OrderChannel.Web,
    "mobile" => OrderChannel.Mobile,
    _ => OrderChannel.Unknown
};
```

`JsonUnmappedMemberHandling.Disallow` превращает каждое новое поле у провайдера в падение потребителя. Канал здесь сознательно прочитан строкой: `JsonStringEnumConverter` бросает исключение на незнакомом значении, и добавление нового канала у провайдера уронило бы обработку событий. Для enum, которые будут расширяться, надёжнее строка и маппинг с веткой по умолчанию.

## Ломающее изменение события

Когда без новой версии не обойтись, её выводят так же, как версию API, только медленнее:

1. Провайдер публикует v2 рядом с v1 — обе записи кладутся в outbox одной транзакцией, либо v1 строится адаптером из v2 (см. `Outbox`).
2. Подписчики по одному переходят на v2. Подписываться нужно на одну версию: читая обе, подписчик обработает факт дважды.
3. Провайдер следит, кто ещё читает v1, — по consumer group на старом топике или по реестру потребителей.
4. Когда v1 никто не читает, её публикацию прекращают, а топик удаляют после истечения retention.

Альтернатива для подписчика — upcasting: при чтении старое сообщение преобразуется в текущую модель, и бизнес-код работает только с последней версией. Так поступают с историей, которую нельзя переписать, например в event sourcing.

## Contract testing

Diff схем ловит удаление поля и смену типа, но не знает, кто какие поля читает. Consumer-driven contracts закрывают этот пробел. В подходе Pact потребитель в своих тестах описывает запросы и минимально нужный ему ответ, результат публикуется в брокер контрактов, а провайдер в своём CI проигрывает контракты всех потребителей против себя. Перед деплоем проверка `can-i-deploy` отвечает, совместима ли эта версия с версиями соседей, которые сейчас в окружении. Для событий есть message pacts — тот же подход для асинхронных контрактов.

Плюс подхода — провайдер знает, какие поля реально используются, и может удалить то, что никто не читает. Типичные ошибки: контракт описывает весь ответ, а не нужную потребителю часть, точные значения вместо проверки типов и формата, и `can-i-deploy`, не встроенный в пайплайн. Общая NuGet-библиотека с DTO провайдера контрактом не является: она связывает релизы и не показывает, что потребитель на самом деле читает.

## Что стоит ответить на собеседовании

Цель версионирования — сохранить независимый деплой. В рамках версии провайдер делает только совместимые изменения — добавляет необязательное, не удаляет, не меняет тип и смысл, — а потребитель пишется как tolerant reader. Ломающее изменение — новая версия рядом со старой, переход потребителей и удаление старой по метрикам использования. Backward-совместимость означает «сначала обновить потребителей», forward — «сначала провайдера».

Сильный ответ назовёт правила protobuf (номера полей, `reserved`, новый пакет для v2), объяснит, почему события версионировать труднее — подписчики не видны, старые сообщения лежат в топике и DLQ, — расскажет про Schema Registry с режимами `BACKWARD`, `FORWARD`, `FULL` и транзитивными вариантами, про ловушку строгих enum в System.Text.Json, и добавит, что смену смысла не ловит никакая схема — только новое поле и consumer-driven contract testing.
