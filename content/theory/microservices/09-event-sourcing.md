В обычной системе база хранит текущее состояние: строка `accounts` с полем `balance = 700`. Как баланс стал таким, знают только логи, если повезло. Event sourcing переворачивает модель: хранится не состояние, а последовательность фактов — `AccountOpened`, `MoneyDeposited 1000`, `MoneyWithdrawn 300`, — а состояние вычисляется сверткой этих событий. История становится источником истины, а текущее значение — производной от неё.

На собеседовании тема проверяет не знание определения, а трезвость: понимает ли кандидат, сколько стоит паттерн в эксплуатации, где он окупается и как жить с историей, которую нельзя переписать.

## Состояние как свёртка событий

Единица хранения — поток (stream) событий одного агрегата: все события счёта 42 лежат в потоке `account-42` в строгом порядке, у каждого свой номер версии. Чтобы выполнить команду, агрегат восстанавливают: читают поток и применяют события по порядку.

```csharp
public sealed class Account
{
    public Guid Id { get; private set; }
    public decimal Balance { get; private set; }
    public bool Closed { get; private set; }
    public long Version { get; private set; }

    public void Apply(AccountOpened e) { Id = e.AccountId; Version++; }
    public void Apply(MoneyDeposited e) { Balance += e.Amount; Version++; }
    public void Apply(MoneyWithdrawn e) { Balance -= e.Amount; Version++; }
    public void Apply(AccountClosed e) { Closed = true; Version++; }

    public MoneyWithdrawn Withdraw(decimal amount)
    {
        if (Closed) throw new DomainException("Счёт закрыт");
        if (amount > Balance) throw new DomainException("Недостаточно средств");
        return new MoneyWithdrawn(Id, amount, DateTimeOffset.UtcNow);
    }
}
```

Разделение важное: метод команды (`Withdraw`) проверяет инварианты и возвращает событие, а `Apply` только меняет состояние и никогда не бросает исключений — иначе старая история, записанная по прежним правилам, перестанет загружаться. Решение принимается один раз, при записи; при чтении событие — уже свершившийся факт. И событие несёт бизнес-смысл: `AccountUpdated { все поля }` — это CRUD в форме событий, по такой истории на вопрос «почему» не ответить.

## Event store и оптимистичная конкуренция

Хранилище событий — append-only журнал. Простейшая реализация на PostgreSQL — одна таблица с уникальным ключом по потоку и версии:

```sql
CREATE TABLE events (
    global_position bigserial   PRIMARY KEY,
    stream_id       text        NOT NULL,
    version         bigint      NOT NULL,
    event_type      text        NOT NULL,
    data            jsonb       NOT NULL,
    metadata        jsonb       NOT NULL,
    created_at      timestamptz NOT NULL DEFAULT now(),
    UNIQUE (stream_id, version)
);
```

Запись идёт с ожидаемой версией: команда загрузила счёт версии 7 и пишет событие с версией 8. Если параллельная команда успела записать свою восьмую версию, уникальный ключ отклонит вставку, и команду повторяют на свежем состоянии. Это та же оптимистичная блокировка, что и с токеном конкурентности в EF Core (см. `Оптимистичная блокировка`), только версия — естественная часть модели, а не служебная колонка.

`global_position` нужна для проекций: по ней подписчик читает все события всех потоков в порядке записи и запоминает, где остановился. При этом `bigserial` в PostgreSQL выдаёт номера в порядке вставки, а не фиксации транзакций, поэтому наивный читатель «всё, что больше последней позиции» может пропустить событие из транзакции, закоммиченной позже. Готовые хранилища решают это за вас — ещё один довод не писать event store с нуля для серьёзной нагрузки.

Конкуренция работает только в пределах потока. Инвариант между агрегатами — «email уникален среди всех клиентов» — через версию не проверить, а проверка по проекции подвержена гонке, потому что проекция отстаёт. Обычное решение — отдельная таблица резервирования уникальных значений с уникальным индексом, которую обновляют в той же транзакции, что и запись события.

## Снапшоты

У счёта с десятью тысячами операций восстановление при каждой команде — чтение десяти тысяч событий. Снапшот — сериализованное состояние агрегата на версии N: загрузка берёт последний снапшот и доигрывает только события после него.

Снапшот — кэш, а не источник истины: при изменении формы состояния его не мигрируют, а пересоздают из событий. Очень длинный поток — часто сигнал пересмотреть границу: счёт можно разбить на периоды, где новый поток начинается с переноса остатка.

## Проекции и read models

Из потока событий удобно восстановить один агрегат, но нельзя сделать запрос «все заказы в статусе `Shipped` за неделю». Для чтения строят проекции: обработчики, которые подписаны на события и поддерживают денормализованные таблицы под конкретные запросы. Это и есть связка с CQRS — модель записи и модели чтения разделены (уровни CQRS разобраны в статье `CQRS`; там же — что CQRS прекрасно живёт без event sourcing).

Проекции бывают синхронными (в транзакции записи события) и асинхронными (догоняют журнал в фоне). Асинхронные — норма, поэтому read model отстаёт: заказ сохранён, а в списке его ещё нет. Это учитывают в UX и мониторят лаг проекции, как лаг консьюмера.

Главное преимущество — проекцию можно построить заново по всей истории. Появился новый отчёт — пишут новую проекцию и прогоняют через неё журнал с начала. Поменялась логика существующей — строят новую версию в отдельную таблицу, догоняют, переключают чтение (blue/green) и удаляют старую.

## Когда event sourcing действительно нужен

Паттерн окупается, когда история — сама ценность для бизнеса, а не побочный продукт:

- **аудит как требование домена** — финансы, учёт, страхование: нужно доказуемо показать, как получено каждое значение, и записи по закону неизменяемы;
- **временные запросы** — «какой был кредитный лимит на момент сделки», «каким был полис на дату страхового случая», причём с юридической значимостью;
- **новые представления по всей истории** — аналитика регулярно спрашивает то, о чём не думали при проектировании: «сколько заказов отменили после смены адреса»;
- **сложные доменные процессы** — длинные жизненные циклы со множеством переходов, где явные события описывают поведение понятнее, чем мутации полей.

И даже тогда — в одном-двух bounded context, а не во всей системе. Event sourcing для «Счетов» не означает event sourcing для каталога и профиля пользователя.

## Почему его часто внедряют зря

| Мотивация | Что дешевле |
| --- | --- |
| «нужен аудит» | таблица истории, temporal tables, CDC в хранилище логов |
| «нужно публиковать события другим сервисам» | обычное состояние плюс `Outbox` |
| «хотим CQRS» | CQRS без event sourcing |
| «модно, масштабируется» | ES сам по себе ничего не ускоряет |

А сложность остаётся навсегда:

- **eventual consistency на чтении** — любой поиск и список идут через проекции, которые надо строить, мониторить и пересобирать;
- **исправление ошибок** — неверное значение нельзя поправить `UPDATE`, нужно корректирующее событие и, возможно, пересборка проекций;
- **эволюция схемы** — история неизменяема, а модель меняется (следующий раздел);
- **GDPR** — право на удаление конфликтует с неизменяемым журналом. Персональные данные выносят из событий в отдельное хранилище по ссылке либо шифруют ключом на субъекта и при удалении уничтожают ключ (crypto-shredding);
- **команда** — ошибки моделирования событий исправлять дорого, и нужны люди, понимающие паттерн.

Отдельная частая ошибка — публиковать внутренние события потока наружу как контракт. Тогда любое изменение модели агрегата ломает подписчиков. Внутренние события — деталь реализации сервиса; наружу через outbox уходят интеграционные события со своим версионированием (см. `Версионирование контрактов`).

## Эволюция схемы при неизменяемой истории

Сохранённые события не переписывают — меняют то, как их читают. Цель: агрегат и проекции знают одну актуальную форму события, а зоопарк версий живёт в одном слое десериализации. Инструменты по возрастанию цены.

**Слабая схема и толерантный ридер** — для аддитивных изменений. Новое поле опционально и имеет разумное значение по умолчанию, неизвестные поля при чтении игнорируются:

```csharp
public sealed record OrderPlaced(
    Guid OrderId,
    Guid CustomerId,
    decimal Total,
    string Currency = "RUB");
```

Старые события без `Currency` прочитаются с default. Удалить поле, сменить тип или смысл так нельзя: `Total` не может тихо начать означать сумму без НДС.

**Upcasting** — для структурных изменений. Между хранилищем и агрегатом стоит преобразователь, который поднимает старую версию до новой при чтении:

```csharp
public sealed record OrderPlacedV1(Guid OrderId, Guid CustomerId, decimal Total);
public sealed record OrderPlaced(Guid OrderId, Guid CustomerId, Money Total, string Channel);

public static class OrderUpcasters
{
    public static object Upcast(object e) => e switch
    {
        OrderPlacedV1 v1 => new OrderPlaced(
            v1.OrderId, v1.CustomerId, new Money(v1.Total, "RUB"), Channel: "web"),
        _ => e
    };
}
```

Upcaster'ы выстраивают цепочкой V1 → V2 → V3, каждый знает только шаг к следующей версии. Тип события в хранилище фиксируется строкой (`order-placed.v1`), а не именем CLR-класса: иначе переименование namespace сломает чтение всей истории. Набор сериализованных событий всех версий держат как тестовые фикстуры с проверкой «каждую версию можно прочитать».

**Новый тип события** — когда изменился смысл, а не форма. Раньше `OrderPlaced` означал «оформлен и оплачен», теперь оплата — отдельный шаг. Заводят новые события `OrderPlaced` и `OrderPaid`, а старое продолжают обрабатывать как два факта сразу. Это честнее, чем подделывать историю upcaster'ом, выдавая старые записи за новые факты.

**Copy-and-transform** — крайний случай: накопилось много версий или нужно поменять границы потоков, например разделить агрегат. Историю один раз читают, преобразуют и пишут в новое хранилище; новый store догоняет старый, затем запись переключается. Дорого, зато очищает код от легаси-версий.

Чего нельзя никогда — `UPDATE` событий в таблице: это уничтожает доверие к истории и расходится с построенными проекциями.

## Инструменты в .NET

- **Marten** — event store поверх PostgreSQL: потоки, оптимистичная конкуренция, inline- и асинхронные проекции, снапшоты, upcasting. Естественный выбор, если PostgreSQL уже в стеке.
- **EventStoreDB** (теперь KurrentDB) — специализированная база событий: запись с ожидаемой ревизией потока, подписки на отдельные потоки и на весь журнал.
- **Своя таблица в PostgreSQL** — для простых случаев, с оговоркой про глобальную позицию, описанной выше.

Kafka на роль event store агрегатов не годится: в ней нет записи с ожидаемой версией потока и дешёвого чтения одного агрегата.

## Что стоит ответить на собеседовании

Event sourcing хранит не состояние, а поток событий агрегата; состояние восстанавливается свёрткой, при необходимости от снапшота. Запись — append с ожидаемой версией потока, то есть оптимистичная конкуренция. Чтение — через проекции, которые строятся асинхронно и потому отстают; их можно пересобрать по всей истории. Оправдан там, где история — бизнес-ценность: аудит как требование, временные запросы, новые представления по старым данным, сложные процессы, — и обычно в одном bounded context, а не во всей системе.

Сильный ответ трезво назовёт цену: eventual consistency на чтении, исправление ошибок корректирующими событиями, конфликт с GDPR и crypto-shredding, внутренние события как не-контракт. И объяснит эволюцию схемы без переписывания истории: слабая схема для новых полей, upcasting при чтении цепочкой версий, новые типы событий при смене смысла, copy-and-transform как крайняя мера, — а также почему аудит, публикация событий и CQRS сами по себе не повод внедрять event sourcing.
