Сервисы общаются двумя способами: синхронно — запрос по сети и ожидание ответа, и асинхронно — сообщение в брокер, которое получатель обработает, когда сможет. В реальной системе есть оба, и вопрос на собеседовании не «что лучше», а «что выбрать здесь и чем за это заплатить». Главное различие — временная связанность: при синхронном вызове оба сервиса должны быть живы одновременно, при асинхронном — нет.

## Не путать с async/await

`await httpClient.GetAsync(...)` не блокирует поток, но архитектурно это синхронное взаимодействие: вызывающий ждёт ответа и без него не продолжит. `async/await` — про потоки внутри процесса, «синхронно/асинхронно» в архитектуре — про то, ждёт ли отправитель получателя. Кандидат, который на вопрос о взаимодействии сервисов начинает рассказывать про `Task`, сразу теряет очки.

## Синхронная цепочка: доступность и задержка

Синхронный вызов прост: ответ сразу, данные свежие, ошибка видна вызывающему, отладка понятна. Проблемы начинаются в цепочках. Если запрос проходит A → B → C → D и каждый доступен на 99,9%, доступность операции — произведение:

```text
0.999 × 0.999 × 0.999 × 0.999 ≈ 0.996   →  99.6%
99.9%  — 43 минуты простоя в месяц
99.6%  — почти 3 часа
```

Задержка складывается, а хвосты задержки — хуже, чем складываются: p99 цепочки определяется худшим звеном. Пики нагрузки синхронный вызов передаёт вниз без сглаживания. Поэтому каждый синхронный вызов обвешан защитой: таймаут с общим бюджетом на цепочку (см. `Timeout budget`), ограниченные ретраи с jitter (`Retry, jitter и retry storm`), circuit breaker (`Circuit breaker`). Длинная синхронная цепочка — часто признак неверных границ (см. `Границы сервисов`).

## REST и gRPC

Для синхронных вызовов между сервисами используют REST/JSON или gRPC. REST универсален, читается глазами, кэшируется HTTP-инфраструктурой и подходит для публичных API. gRPC — строгий контракт в `.proto`, бинарный Protobuf, HTTP/2 с мультиплексированием и стриминг; он быстрее и удобнее для частых внутренних вызовов.

У gRPC есть deadline — абсолютный момент, до которого вызов должен завершиться. Он передаётся по цепочке, и нижестоящий сервис знает, сколько времени у него осталось:

```csharp
builder.Services
    .AddGrpcClient<Inventory.InventoryClient>(o =>
        o.Address = new Uri("https://inventory"))
    .EnableCallContextPropagation();

var reply = await inventory.ReserveAsync(
    new ReserveRequest { Sku = "A-42", Qty = 1 },
    deadline: DateTime.UtcNow.AddSeconds(2),
    cancellationToken: ct);
```

`EnableCallContextPropagation` из пакета `Grpc.AspNetCore.Server.ClientFactory` берёт deadline и отмену входящего gRPC-вызова и передаёт их в исходящий. Частая ловушка gRPC — балансировка: HTTP/2 держит одно долгоживущее соединение, и L4-балансировщик отправит весь трафик клиента на один под. Нужна L7-балансировка (Envoy, service mesh) или клиентская (см. `Балансировщики`).

## Асинхронно: команды, события, request-reply

Асинхронное сообщение бывает трёх видов, и путать их — частая ошибка дизайна:

- **команда** — `ReserveStock`: просьба сделать, адресована конкретному получателю, может быть отклонена;
- **событие** — `OrderPlaced`: факт, который уже произошёл, в прошедшем времени; издатель не знает подписчиков и не ждёт от них ничего;
- **асинхронный request-reply** — запрос в очередь, ответ в отдельную очередь по correlation id.

Брокер даёт развязку по времени (получатель лежит — сообщения подождут), сглаживание пиков (очередь работает буфером, см. `Backpressure`) и расширяемость: новый подписчик на `OrderPlaced` появляется без изменения издателя.

Платить приходится сложностью. Доставка at-least-once — значит дубли и идемпотентные обработчики (`Идемпотентность`). Порядок сообщений гарантирован в лучшем случае внутри партиции. Нужны dead letter queue для «ядовитых» сообщений, сквозная трассировка через брокер и мониторинг лага. Данные становятся согласованными в конечном счёте: пользователь создал заказ, а список заказов, собранный по событиям, его ещё не показывает (см. `Read-your-writes`). И отдельная проблема — атомарно изменить базу и отправить сообщение, которую решает `Outbox`.

## Смешанные цепочки

Две комбинации встречаются часто и обе требуют осторожности. Первая — **sync over async**: HTTP-обработчик кладёт запрос в очередь и держит соединение, пока ответ не придёт в reply-очередь. Получается худшее из двух миров: пользователь всё равно ждёт, соединение и поток заняты, а при медленном потребителе таймаут HTTP наступит раньше, чем ответ, и результат придётся куда-то девать. Если ответ нужен сразу — честный синхронный вызов, если нет — `202` и статус.

Вторая — синхронный вызов внутри обработчика сообщения. Консьюмер `OrderPlaced` идёт по HTTP в сервис цен, тот лежит, обработчик падает, брокер доставляет сообщение снова — и сотни повторов превращаются в retry storm на уже больной сервис. Ретраи консьюмера ограничивают и разносят во времени, а сообщения, которые так и не обработались, уводят в DLQ, а не крутят бесконечно.

## Гибрид: 202 Accepted

Самая частая схема в реальных системах — принять команду синхронно, а исполнить асинхронно. API проверяет запрос, сохраняет его и сразу отвечает `202 Accepted` с адресом, где смотреть статус:

```csharp
app.MapPost("/orders", async (PlaceOrder cmd, OrdersDbContext db,
    IPublishEndpoint bus, CancellationToken ct) =>
{
    var order = Order.Create(cmd);
    db.Orders.Add(order);
    await bus.Publish(new OrderPlaced(order.Id, order.Total), ct);
    await db.SaveChangesAsync(ct);
    return Results.Accepted($"/orders/{order.Id}", new { order.Id, order.Status });
});
```

При включённом транзакционном outbox MassTransit `Publish` не уходит в брокер сразу, а сохраняется тем же `SaveChangesAsync`, что и заказ, — подробности в статье `Outbox`. Дальше резерв, оплата и доставка идут событиями, а клиент узнаёт результат опросом статуса, через webhook или push по SignalR. Пользователь получает ответ за десятки миллисекунд, а падение платёжного сервиса не роняет оформление заказа.

## Убрать синхронный вызов совсем

Многие синхронные вызовы — это чтение чужих данных: «как называется товар», «какой у клиента тариф». Их можно заменить локальной копией, которую владелец обновляет событиями:

```csharp
public sealed class ProductRenamedConsumer(OrdersDbContext db) : IConsumer<ProductRenamed>
{
    public async Task Consume(ConsumeContext<ProductRenamed> context)
    {
        var m = context.Message;
        await db.ProductCopies
            .Where(p => p.Id == m.ProductId && p.Version < m.Version)
            .ExecuteUpdateAsync(s => s
                .SetProperty(p => p.Name, m.Name)
                .SetProperty(p => p.Version, m.Version));
    }
}
```

Условие по версии делает обработку идемпотентной и защищает от устаревшего события, пришедшего позже нового. Копия может отставать на секунды — это нужно явно согласовать с бизнесом. Для цены в корзине такое отставание допустимо, для остатка при списании денег — нет, и там остаётся синхронная проверка у владельца.

## Как выбирать

| Сценарий | Способ |
| --- | --- |
| пользователю нужен ответ сейчас: цена, права, валидация | синхронно |
| сообщить другим о факте: заказ создан | событие |
| долгий процесс с несколькими участниками | асинхронно + сага |
| сгладить пиковую нагрузку, медленный внешний партнёр | очередь |
| часто читаемые чужие данные | локальная копия по событиям |

Правило большого пальца: синхронно — чтение и то, без чего нельзя ответить пользователю; асинхронно — всё, что может случиться чуть позже. Чем меньше синхронных зависимостей на критическом пути, тем меньше сервис зависит от доступности соседей.

## Что стоит ответить на собеседовании

Синхронное взаимодействие — HTTP или gRPC, вызывающий ждёт ответа. Просто и даёт свежие данные, но создаёт временную связанность: доступности в цепочке перемножаются (четыре сервиса по 99,9% — 99,6%), задержки складываются, а каждый вызов требует таймаута, ретраев и circuit breaker. Асинхронное — сообщения через брокер: развязка по времени, буфер для пиков и расширяемость, но eventual consistency, дубли, порядок и DLQ. И это не про `async/await`.

Сильный ответ различит команды и события, назовёт гибрид «принять синхронно, ответить 202, исполнить событиями», расскажет про deadline и балансировку gRPC, предложит заменить синхронное чтение чужих данных локальной копией по событиям и упомянет, что атомарную публикацию после изменения базы даёт outbox.
