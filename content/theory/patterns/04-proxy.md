Proxy — объект, который реализует тот же интерфейс, что и реальный объект, и стоит между ним и клиентом. Структурно это ровно то же, что декоратор: тот же интерфейс плюс ссылка на другой объект. Поэтому главный вопрос на собеседовании — «чем Proxy отличается от Decorator», и ответ лежит не в коде, а в намерении.

## Decorator добавляет, Proxy управляет доступом

**Decorator** расширяет поведение объекта, который уже есть: добавляет кэш, метрики, ретраи. Декораторы рассчитаны на композицию, их собирают в цепочку при старте приложения, и обёрнутый объект передаётся снаружи.

**Proxy** контролирует доступ к объекту: решает, когда его создать, можно ли к нему обратиться, где он физически находится. Прокси обычно один, клиент о нём не знает, а реальный объект прокси часто создаёт или получает сам.

| | Decorator | Proxy |
| --- | --- | --- |
| Цель | добавить поведение | управлять доступом к субъекту |
| Кто создаёт обёрнутый объект | передают снаружи | часто сам прокси — лениво или удалённо |
| Сколько обёрток | цепочка — норма | обычно одна |
| Знает ли клиент | цепочку собирают осознанно | клиент не должен замечать прокси |
| Примеры | метрики, логирование, ретраи | ленивая загрузка, удалённый вызов, проверка прав |

Граница размыта: кэширующая обёртка — это и декоратор (добавляет кэш), и caching proxy (ограничивает обращения к дорогому объекту). В таких случаях важнее назвать класс по смыслу — `CachedProductCatalog`, — чем спорить о классификации. Про декораторы подробно — в статье `Decorator vs наследование`.

## Виртуальный прокси: создать, когда понадобится

Генератор отчётов при создании загружает шаблоны и шрифты — это секунды и десятки мегабайт. Большинство запросов к сервису отчёт не строят, но сервис зависит от генератора через конструктор:

```csharp
public interface IReportGenerator
{
    Task<byte[]> BuildAsync(ReportRequest request, CancellationToken ct);
}

public sealed class LazyReportGenerator(Func<IReportGenerator> factory) : IReportGenerator
{
    private readonly Lazy<IReportGenerator> _real = new(factory);

    public Task<byte[]> BuildAsync(ReportRequest request, CancellationToken ct) =>
        _real.Value.BuildAsync(request, ct);
}
```

Прокси решает, когда создать тяжёлый объект, а клиент работает с `IReportGenerator` как обычно. `Lazy<T>` по умолчанию потокобезопасен: при одновременных первых обращениях фабрика выполнится один раз.

Самый известный виртуальный прокси в .NET — ленивая загрузка EF Core через `UseLazyLoadingProxies`. EF генерирует во время выполнения наследника сущности, который при первом обращении к `order.Customer` выполняет запрос к базе. Отсюда требование объявлять навигации `virtual`, а классы сущностей не делать `sealed` — прокси переопределяет геттеры, — и главная ловушка: цикл по заказам с обращением к `order.Customer` превращается в N+1 запросов, хотя в коде не видно ни одного. Замер этого эффекта — в статье `Загрузка связей и N+1`.

## Удалённый прокси: сеть под видом вызова метода

Сгенерированный клиент gRPC или клиент Refit — удалённые прокси. Вы вызываете метод, а прокси сериализует аргументы, отправляет запрос и десериализует ответ.

Удобство здесь же становится опасностью. Вызов `await client.GetUserAsync(id)` выглядит так же, как обращение к локальному объекту, но под ним сеть: задержка в десятки миллисекунд, таймауты, частичные отказы, повторы. Прокси прячет то, что прятать нельзя. Поэтому удалённым прокси нужны явные таймауты, политика ретраев только для идемпотентных операций и имена, из которых видно, что это клиент внешней системы.

## Защитный прокси: проверка прав

```csharp
public interface IDocumentStore
{
    Task<Document?> GetAsync(Guid id, CancellationToken ct);
    Task DeleteAsync(Guid id, CancellationToken ct);
}

public sealed class AuthorizedDocumentStore(IDocumentStore inner, ICurrentUser user) : IDocumentStore
{
    public Task<Document?> GetAsync(Guid id, CancellationToken ct) => inner.GetAsync(id, ct);

    public Task DeleteAsync(Guid id, CancellationToken ct) =>
        user.IsInRole("admin")
            ? inner.DeleteAsync(id, ct)
            : throw new UnauthorizedAccessException("Удалять документы может только администратор.");
}
```

Структурно — декоратор. По намерению — прокси: он не добавляет функциональность, а решает, пустить ли вызов к реальному объекту. В веб-приложении такие проверки чаще живут в политиках авторизации и фильтрах на границе запроса, но защитный прокси полезен, когда к одному хранилищу ходят из разных точек входа — HTTP, консьюмеров, фоновых задач.

## Умная ссылка: пул соединений

Знакомый всем пример — пул соединений ADO.NET. `NpgsqlConnection` или `SqlConnection`, которые вы создаёте и закрываете, — лёгкие объекты над физическим соединением из пула. `Dispose` не разрывает TCP-соединение, а возвращает его в пул; следующий `Open` получит то же физическое соединение. Клиент работает с объектом так, будто владеет соединением целиком, а прокси управляет доступом к дорогому ресурсу.

## Динамические прокси

Писать прокси руками для каждого интерфейса утомительно. Динамические прокси генерируют класс-обёртку во время выполнения, а всю логику перехвата пишут один раз.

**`DispatchProxy`** встроен в .NET. Все вызовы методов интерфейса приходят в один метод `Invoke`:

```csharp
public class LoggingProxy<T> : DispatchProxy where T : class
{
    private T _target = default!;
    private ILogger _logger = default!;

    public static T Wrap(T target, ILogger logger)
    {
        var proxy = Create<T, LoggingProxy<T>>();
        var self = (LoggingProxy<T>)(object)proxy;
        self._target = target;
        self._logger = logger;
        return proxy;
    }

    protected override object? Invoke(MethodInfo? targetMethod, object?[]? args)
    {
        _logger.LogInformation("Вызов {Type}.{Method}", typeof(T).Name, targetMethod!.Name);
        try
        {
            return targetMethod.Invoke(_target, args);
        }
        catch (TargetInvocationException ex) when (ex.InnerException is not null)
        {
            ExceptionDispatchInfo.Throw(ex.InnerException);
            throw;
        }
    }
}
```

Ограничения видны сразу. `DispatchProxy` работает только с интерфейсами. Вызов идёт через рефлексию, и исключение цели приходит обёрнутым в `TargetInvocationException` — его нужно разворачивать, иначе вызывающий код получит не тот тип исключения. А для асинхронных методов `Invoke` возвращает `Task` сразу: чтобы записать время выполнения или результат, нужно дождаться задачи, а это уже заметно больше кода.

**Castle DynamicProxy** — библиотека на том же принципе с более богатыми возможностями: прокси для интерфейсов и для классов с виртуальными методами, цепочки перехватчиков:

```csharp
public sealed class TimingInterceptor(ILogger logger) : IInterceptor
{
    public void Intercept(IInvocation invocation)
    {
        var started = Stopwatch.GetTimestamp();
        invocation.Proceed();
        logger.LogInformation("{Method}: {Elapsed}",
            invocation.Method.Name, Stopwatch.GetElapsedTime(started));
    }
}

public static class Proxies
{
    private static readonly ProxyGenerator Generator = new();

    public static IReportGenerator WithTiming(IReportGenerator target, ILogger logger) =>
        Generator.CreateInterfaceProxyWithTarget(target, new TimingInterceptor(logger));
}
```

На Castle DynamicProxy построены Moq и NSubstitute — каждый мок в тесте это динамический прокси, — а также ленивые прокси EF Core. Тот же недостаток с асинхронностью есть и здесь: для `async`-метода `Proceed` возвращает управление, когда задача ещё не завершена, и время в примере выше будет временем до первого `await`.

## Цена прозрачности

Ценность прокси в том, что клиент его не замечает. Опасность — ровно в том же. Ленивая загрузка превращает обращение к свойству в запрос к базе, удалённый прокси — вызов метода в сетевой запрос, динамический перехватчик — любой вызов в нечто, чего нет в исходниках. Поэтому разумные правила такие:

- прокси, меняющий стоимость операции (сеть, база), должен быть виден хотя бы по имени типа или регистрации;
- динамические прокси — для действительно сквозных задач, где ручные обёртки невыносимы, а не как замена обычным декораторам;
- для AOT и горячих путей ручная обёртка предпочтительнее: генерация типов во время выполнения и вызов через рефлексию плохо совместимы с Native AOT и стоят дороже прямого вызова.

## Что стоит ответить на собеседовании

Proxy и Decorator структурно одинаковы, различаются намерением: декоратор добавляет поведение и собирается в цепочки, прокси управляет доступом — откладывает создание, проверяет права, скрывает удалённость — и для клиента прозрачен. Виды прокси: виртуальный (`Lazy<T>`, ленивые навигации EF Core), удалённый (клиенты gRPC и Refit), защитный, умная ссылка (соединение из пула). Динамические прокси — `DispatchProxy` (только интерфейсы) и Castle DynamicProxy, на котором работают Moq и NSubstitute.

Сильный ответ назовёт цену прозрачности: ленивая загрузка прячет N+1, удалённый прокси прячет сеть, а перехват асинхронных методов в динамических прокси требует отдельной работы.
