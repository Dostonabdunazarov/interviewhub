Strategy — паттерн, в котором семейство взаимозаменяемых алгоритмов вынесено за общий интерфейс, а клиент выбирает или получает нужный. В учебниках он подаётся как способ «избавиться от switch», и на собеседовании это ловушка: кандидат, который заменил бы любой `switch` на иерархию классов, выдаёт отсутствие опыта. Правильный ответ — это компромисс, и у `switch` в нём есть своя сторона.

## Когда switch — правильный выбор

Стоимость доставки зависит от способа и веса. Набор способов меняется раз в год, и всё правило — это таблица:

```csharp
public enum ShippingMethod { Pickup, Courier, Post }

public sealed record Shipment(ShippingMethod Method, decimal WeightKg);

public static class Shipping
{
    public static decimal Cost(Shipment s) => s switch
    {
        { Method: ShippingMethod.Pickup } => 0m,
        { Method: ShippingMethod.Courier, WeightKg: <= 5 } => 300m,
        { Method: ShippingMethod.Courier } => 300m + (s.WeightKg - 5) * 40m,
        { Method: ShippingMethod.Post } => 250m + s.WeightKg * 25m,
        _ => throw new UnreachableException($"Неизвестный способ {s.Method}")
    };
}
```

Вся логика на одном экране, тест — таблица входов и ожидаемых сумм, добавить вариант — одна строка. Если переписать это на Strategy, получится интерфейс, три класса по три строки, регистрации в DI и класс-диспетчер — а прочитать правило целиком станет невозможно без пяти открытых файлов.

Ветка `_ => throw` здесь нужна. Для `enum` компилятор не может доказать полноту: в переменную `ShippingMethod` можно положить `(ShippingMethod)42`, поэтому без «прочего» случая выражение `switch` выдаст предупреждение о неполноте, а при добавлении нового значения в enum ошибкой компиляции ничего не подсветится. `UnreachableException` из .NET 7 явно говорит, что сюда попадать не должны.

## Когда нужна Strategy

Совсем другая картина — платёжные провайдеры:

```csharp
public interface IPaymentProvider
{
    string Code { get; }
    Task<PaymentResult> ChargeAsync(PaymentRequest request, CancellationToken ct);
    Task RefundAsync(string paymentId, decimal amount, CancellationToken ct);
}

public sealed class PaymentRouter(IEnumerable<IPaymentProvider> providers)
{
    private readonly Dictionary<string, IPaymentProvider> _byCode =
        providers.ToDictionary(p => p.Code, StringComparer.OrdinalIgnoreCase);

    public IPaymentProvider Resolve(string code) =>
        _byCode.TryGetValue(code, out var provider)
            ? provider
            : throw new NotSupportedException($"Способ оплаты {code} не подключён.");
}

public static class PaymentRegistration
{
    public static IServiceCollection AddPayments(this IServiceCollection services)
    {
        services.AddScoped<IPaymentProvider, CardProvider>();
        services.AddScoped<IPaymentProvider, SbpProvider>();
        services.AddScoped<PaymentRouter>();
        return services;
    }
}
```

Здесь каждый пункт таблицы выше перевёрнут:

- **У вариантов свои зависимости.** У каждого провайдера свой `HttpClient`, настройки, ретраи и маппинг ошибок. В одном `switch` все эти зависимости собрались бы в один класс.
- **Над вариантами несколько операций.** `Charge` и `Refund` — это два параллельных `switch`, которые нужно держать синхронными. Забыли ветку во втором — возврат не работает для нового провайдера.
- **Варианты добавляются независимо.** Новый провайдер — новый класс и регистрация, `PaymentRouter` не меняется.
- **Выбор зависит от конфигурации.** Провайдер можно включить фича-флагом на одном окружении и тестировать изолированно.

Внедрение `IEnumerable<IPaymentProvider>` — штатная возможность контейнера: он отдаёт все регистрации интерфейса. Начиная с .NET 8 для выбора по ключу есть и keyed services — `AddKeyedScoped<IPaymentProvider, CardProvider>("card")` и `GetRequiredKeyedService`. Подробнее о регистрациях — в статье `DI и жизненные циклы`.

## Середина: словарь делегатов

Между `switch` и полноценной Strategy есть промежуточная ступень — когда варианты различаются одной функцией без зависимостей, но набор должен расширяться без правки диспетчера:

```csharp
public static class Rounding
{
    private static readonly Dictionary<string, Func<decimal, decimal>> Rules = new()
    {
        ["bank"] = x => Math.Round(x, 2, MidpointRounding.ToEven),
        ["up"] = x => Math.Ceiling(x * 100) / 100,
        ["cash"] = x => Math.Round(x * 2, MidpointRounding.AwayFromZero) / 2
    };

    public static decimal Apply(string rule, decimal amount) =>
        Rules.TryGetValue(rule, out var round)
            ? round(amount)
            : throw new ArgumentException($"Неизвестное правило {rule}", nameof(rule));
}
```

Это та же Strategy, только стратегия — делегат, а не класс. Подходит, когда ключ приходит из конфигурации или данных, а сам алгоритм — однострочник. Как только у функции появляются зависимости или вторая операция, делегат перерастает в интерфейс.

## Критерии выбора

| Вопрос | `switch` | Strategy |
| --- | --- | --- |
| Набор вариантов | закрыт, меняется редко | растёт |
| Логика ветки | несколько строк | классы, зависимости, состояние |
| Операций над вариантами | одна | несколько (`Charge`, `Refund`) |
| Сколько мест выбирает по типу | одно | несколько одинаковых `switch` — сигнал к Strategy |
| Выбор во время выполнения | по данным | по конфигурации, фича-флагу |
| Кто добавляет варианты | та же команда в том же файле | разные команды, плагины |

Самый надёжный сигнал — повторение. Один `switch` по `PaymentMethod` — нормально. Тот же `switch` в пяти классах — это уже размазанная по коду иерархия, которую забудут обновить в одном из мест.

## Expression problem

За выбором стоит фундаментальный компромисс, у которого есть имя — expression problem. Есть типы (варианты) и операции над ними, и легко расширять можно только по одной оси:

- **`switch` по закрытому набору** делает дешёвым добавление новой **операции**: ещё одна функция со своим `switch`, существующий код не трогается. Добавить новый **вариант** дорого — нужно найти и обновить все `switch`.
- **Strategy и полиморфизм** — наоборот: новый вариант — новый класс, а новая операция — правка интерфейса и всех реализаций.

Отсюда практическое правило: выбирайте то, что делает дешёвым **более частое** изменение. Платёжные провайдеры добавляются чаще, чем операции над ними, — Strategy. Типы документов в бухгалтерии стабильны, а отчётов и проверок над ними всё больше — `switch` или pattern matching. Это тот же компромисс, что виртуальный метод против `switch` по иерархии в статье `Инкапсуляция, наследование, полиморфизм`.

## Опасности обеих сторон

**У `switch`:** одинаковые `switch` по одному enum в десяти местах; забытая ветка при добавлении значения; ветки, разросшиеся до сотни строк с зависимостями, которые нужны только одной из них.

**У Strategy:** интерфейс ради двух вариантов по три строки; «стратегии», которым на самом деле нужны разные входные данные, из-за чего общий контракт раздувается параметрами, которые половина реализаций игнорирует; непрозрачный выбор — чтобы узнать, какая реализация сработает, нужно найти регистрацию в DI.

## Strategy и State

Близкий паттерн, который часто путают, — State. Структура та же — интерфейс и реализации, — но различается, **кто меняет** текущую реализацию. В Strategy её выбирает клиент или конфигурация, и выбор не меняется в ходе работы. В State объект сам переключает своё состояние: заказ в состоянии «оплачен» при отгрузке переходит в «отгружен», и следующая операция уже вызывается у другого объекта состояния.

## Что стоит ответить на собеседовании

`switch` лучше, когда набор вариантов закрыт, ветки короткие, операция одна и всё решение видно на одном экране; полноту для enum компилятор не гарантирует, поэтому нужна ветка `_ => throw`. Strategy лучше, когда варианты добавляются независимо, у каждого свои зависимости, над вариантами несколько операций, выбор идёт по конфигурации. Посередине — словарь делегатов. Сигнал к переходу — одинаковые `switch` по одному enum в нескольких местах.

Сильный ответ назовёт expression problem: `switch` дешёв для новых операций, полиморфизм — для новых вариантов, и выбирать стоит по тому, что меняется чаще.
