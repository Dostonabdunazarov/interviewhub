Под словом «медиатор» в .NET-проектах почти всегда понимают не паттерн из книги GoF, а библиотеку MediatR и её подражателей: контроллер отправляет команду, библиотека находит обработчик и прогоняет вызов через конвейер. Это полезный инструмент с узнаваемым сценарием деградации, и на senior-собеседовании спрашивают именно о нём: что даёт, во что превращается и как это предотвратить.

## Два разных паттерна под одним именем

**Классический Mediator** из GoF убирает прямые связи между множеством объектов-коллег. Вместо того чтобы каждый знал о каждом, все общаются через посредника, который знает правила координации. Учебный пример — форма: выбор способа доставки блокирует поле адреса, ввод промокода пересчитывает итог, итог включает кнопку оплаты. Без посредника каждый элемент держит ссылки на остальные, и связей становится N×N. С посредником каждый элемент знает только его.

**Диспетчер запросов** в стиле MediatR решает другую задачу. Он не координирует коллег, а маршрутизирует: по типу запроса находит единственный обработчик и вызывает его. По сути это in-process шина команд с конвейером. Различие стоит назвать на собеседовании явно — его спрашивают как проверку, понимает ли кандидат, что использует.

## Что даёт диспетчер

```csharp
public sealed record PlaceOrder(int CustomerId, IReadOnlyList<int> ProductIds) : IRequest<int>;

public sealed class PlaceOrderHandler(AppDbContext db) : IRequestHandler<PlaceOrder, int>
{
    public async Task<int> Handle(PlaceOrder request, CancellationToken ct)
    {
        var order = new Order(request.CustomerId, request.ProductIds);
        db.Orders.Add(order);
        await db.SaveChangesAsync(ct);
        return order.Id;
    }
}

public sealed class LoggingBehavior<TRequest, TResponse>(ILogger<LoggingBehavior<TRequest, TResponse>> logger)
    : IPipelineBehavior<TRequest, TResponse>
    where TRequest : notnull
{
    public async Task<TResponse> Handle(
        TRequest request, RequestHandlerDelegate<TResponse> next, CancellationToken ct)
    {
        var started = Stopwatch.GetTimestamp();
        var response = await next(ct);
        logger.LogInformation("{Request} за {Elapsed}",
            typeof(TRequest).Name, Stopwatch.GetElapsedTime(started));
        return response;
    }
}
```

Три реальных выигрыша:

- **Класс на сценарий.** `PlaceOrderHandler` с двумя зависимостями вместо `OrderService` на сорок методов с пятнадцатью. Каждый сценарий читается и тестируется отдельно.
- **Сквозная функциональность в одном месте.** Логирование, валидация, транзакция, метрики — в pipeline behaviors, а не копипастой в каждом обработчике. Behavior — это декоратор вокруг обработчика, только регистрируется для всех запросов сразу.
- **Тонкие точки входа.** Эндпоинт только превращает HTTP-запрос в команду и отправляет её.

## Как он превращается в свалку

**Обработчик вызывает обработчик.** Внутри `PlaceOrderHandler` появляется `await mediator.Send(new GetCustomerQuery(id))`. Зависимость стала невидимой: по конструктору видно только `IMediator`, «перейти к определению» ведёт в интерфейс библиотеки, а чтобы понять, что делает класс, нужно искать обработчики по типам запросов. Хуже того, вложенный `Send` снова проходит **все** behaviors: двойное логирование, повторная валидация и — самое опасное — вложенная транзакция, если транзакция сделана behavior'ом.

**Notifications как скрытая шина событий.** `Publish` уведомления выглядит как публикация события, но по умолчанию обработчики вызываются последовательно, в том же процессе, в той же транзакции и в том же запросе. Упавший обработчик ломает основной сценарий, медленный — задерживает ответ. Со стороны это похоже на событийную архитектуру, но без её главного свойства — надёжной доставки независимо от основного сценария.

**Медиатор ради медиатора.** `GetUserByIdQuery`, `GetUserByIdQueryHandler` и `GetUserByIdQueryValidator` — три файла ради `db.Users.FindAsync(id)`. Если у сценария нет ни сквозной логики, ни своих зависимостей, прямой вызов проще.

**Behaviors с бизнес-логикой.** Проверка прав на конкретную сущность, обогащение запроса данными из базы, кэширование с ключами по имени типа — всё это поведение, которое не видно при чтении обработчика. Новичок читает код, а происходит что-то ещё.

**Стоимость.** Разрешение обработчика из контейнера, аллокации на каждый вызов, длинные стеки в профилировщике и трассировке. Обычно некритично, но на горячем пути заметно.

## Правила, которые удерживают от деградации

1. **`Send` только в точках входа.** Эндпоинты, консьюмеры сообщений, фоновые задачи. Внутри логики — обычные зависимости через конструктор.
2. **Общая логика — в обычных классах**, которые внедряются в несколько обработчиков, а не в «обработчиках, которые вызывают обработчики».
3. **Behaviors — только для действительно сквозных задач**, их немного, порядок регистрации явный и описан.
4. **События между модулями — через outbox и брокер** или через явный механизм доменных событий с понятной семантикой транзакции, а не через `INotification`.

## Можно без библиотеки

Все выигрыши диспетчера достигаются обычными средствами: обработчик — обычный класс за обобщённым интерфейсом, сквозная функциональность — декораторы, точка входа получает обработчик из DI напрямую:

```csharp
public interface ICommandHandler<TCommand, TResult>
{
    Task<TResult> HandleAsync(TCommand command, CancellationToken ct);
}

public sealed class LoggingCommandHandler<TCommand, TResult>(
    ICommandHandler<TCommand, TResult> inner,
    ILogger<LoggingCommandHandler<TCommand, TResult>> logger) : ICommandHandler<TCommand, TResult>
{
    public async Task<TResult> HandleAsync(TCommand command, CancellationToken ct)
    {
        var started = Stopwatch.GetTimestamp();
        var result = await inner.HandleAsync(command, ct);
        logger.LogInformation("{Command} за {Elapsed}",
            typeof(TCommand).Name, Stopwatch.GetElapsedTime(started));
        return result;
    }
}

public static class OrderEndpoints
{
    public static void MapOrders(this WebApplication app) =>
        app.MapPost("/orders", (PlaceOrderCommand command,
            ICommandHandler<PlaceOrderCommand, int> handler, CancellationToken ct) =>
            handler.HandleAsync(command, ct));
}
```

Декоратор регистрируется для всех обработчиков одной строкой Scrutor — `Decorate(typeof(ICommandHandler<,>), typeof(LoggingCommandHandler<,>))`, — как в статье `Decorator vs наследование`. Разница с библиотекой в главном: зависимость эндпоинта от конкретного обработчика видна в сигнатуре, и «перейти к реализации» ведёт туда, куда нужно.

Есть и практический довод. Начиная с версии 13, вышедшей в 2025 году, MediatR распространяется по двойной лицензии: коммерческая с ключом и бесплатный уровень для небольших организаций; без ключа библиотека работает, но пишет предупреждение в лог. Точные условия стоит сверять на сайте проекта перед обновлением. Версии до 13-й остаются под Apache 2.0, поэтому часть команд закрепилась на 12-й, часть перешла на собственный тонкий диспетчер или на аналоги с генерацией кода, у которых нет разрешения обработчиков через рефлексию.

## Где Mediator уместен

- в большом приложении с десятками сценариев, где класс на сценарий и единый конвейер окупаются;
- когда сквозная функциональность действительно одинакова для всех команд — валидация, аудит, метрики;
- в vertical slice архитектуре, где фича — это запрос, обработчик и эндпоинт в одной папке.

И не уместен в маленьком сервисе с пятью эндпоинтами, где он добавляет слой без выигрыша. Как устроить приложение вокруг команд и запросов, и чем это отличается от CQRS, — тема раздела «Архитектура приложения».

## Что стоит ответить на собеседовании

Классический Mediator координирует взаимодействие объектов-коллег, убирая связи «каждый с каждым»; MediatR — другое: in-process диспетчер, который по типу запроса находит обработчик и прогоняет его через pipeline behaviors. Выигрыш — класс на сценарий, сквозная логика в одном месте, тонкие эндпоинты. Свалкой он становится, когда обработчики вызывают друг друга через `Send` (невидимые зависимости, повторный проход по behaviors, вложенные транзакции), когда `Publish` используют как шину событий и когда в behaviors уезжает бизнес-логика.

Сильный ответ назовёт правило «`Send` только в точках входа» и покажет, что те же выигрыши дают обычные обработчики с декораторами, без библиотеки и её лицензионных условий.
