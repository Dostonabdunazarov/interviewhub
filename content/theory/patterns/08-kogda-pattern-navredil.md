«Приведите пример, где паттерн навредил проекту» — вопрос не на знание каталога, а на зрелость. Интервьюер проверяет, отличает ли кандидат паттерн от проблемы, которую тот решает, умеет ли измерить последствия и выйти из неудачного решения без большого переписывания. Ответ «у нас такого не было» звучит как отсутствие опыта, а ответ «паттерны — зло» — как обида на прошлый проект.

## Почему паттерн вредит

Паттерн — это решение типовой проблемы, и у него всегда есть цена: лишний уровень косвенности, дополнительные типы, правила, которые нужно знать. Когда проблема есть, цена окупается. Когда её нет, остаётся только цена. Почти все истории о вреде сводятся к трём механизмам:

- **решение отсутствующей проблемы.** Второй реализации интерфейса нет и не будет, смена хранилища не планируется, вариантов алгоритма два и они не меняются, — а инфраструктура под них уже построена;
- **закрытый доступ к возможностям.** Обёртка прячет то, что было нужно: проекции и массовые операции ORM, отмену, потоковую обработку, настройки клиента;
- **невидимое поведение.** Вызов уходит через диспетчер, прокси или базовый класс, и по коду метода уже нельзя понять, что произойдёт.

Общая версия этой мысли — про любые обобщения, а не только про паттерны — разобрана в `Преждевременные абстракции`. Здесь речь о том, как превратить её в конкретную историю.

## Формат истории

Хороший ответ — короткий кейс из пяти частей, и интервьюер ждёт именно их:

1. **Контекст:** что за система, какой масштаб, какая команда.
2. **Решение:** какой паттерн ввели и какую проблему им собирались решить.
3. **Последствия:** что пошло не так, желательно с числами, а не «было некрасиво».
4. **Выход:** как исправили — постепенно, под защитой тестов.
5. **Вывод:** что изменили в процессе, чтобы не повторить.

## Пример: репозиторий и спецификации поверх EF Core

Самая частая реальная история — generic-репозиторий, Unit of Work и спецификации над EF Core, введённые «для чистой архитектуры». Механика того, почему такая обёртка теряет возможности EF, разобрана в `Repository поверх ORM`; здесь — как это выглядит в виде рассказа.

**Контекст.** Сервис каталога и заказов, несколько десятков сущностей, команда из шести человек. На старте решили: доступ к данным только через `IRepository<T>` и `IUnitOfWork`, сложные выборки — через спецификации, `DbContext` вне инфраструктурного проекта запрещён.

**Последствия.** Через год спецификации выглядели так:

```csharp
public sealed class OrdersForCustomerSpec : Specification<Order>
{
    public OrdersForCustomerSpec(int customerId, bool withLines, bool withAddress, bool asNoTracking)
    {
        Criteria = o => o.CustomerId == customerId;
        if (withLines) Includes.Add(o => o.Lines);
        if (withAddress) Includes.Add(o => o.ShippingAddress);
        AsNoTracking = asNoTracking;
    }
}
```

Каждый флаг — след задачи, которой абстракция не выдержала. Проекции в неё не помещались, и экран списка тянул заказы со строками и адресами ради пяти колонок. `SaveChangesAsync` вызывался и в репозиториях, и в `UnitOfWork`, и в одном сценарии половина изменений сохранялась до исключения. Пакетное обновление цен шло через загрузку всех товаров, потому что `ExecuteUpdateAsync` в интерфейс не вписывался. Тесты на моках не ловили ошибки трансляции LINQ в SQL, а новая выборка требовала спецификации, метода в интерфейсе и реализации.

**Выход.** Не переписывание, а серия маленьких шагов: сначала интеграционные тесты на реальной базе для ключевых сценариев; затем чтения переведены на прямые запросы через `DbContext` с проекциями; для агрегата заказа на стороне записи оставлен репозиторий с методами по сценариям — там граница была осмысленной; `SaveChanges` перенесён в одно место, в обработчик команды. Generic-интерфейс удалили последним, когда на него не осталось ссылок.

**Вывод.** Решения такого масштаба теперь фиксируются в ADR — с альтернативами и условием, при котором решение пересматривают (см. `Документирование решений (ADR)`).

Числа в рассказе должны быть вашими. Если точных нет, лучше назвать порядок и источник («время ответа списка упало с секунд до сотен миллисекунд по метрикам APM»), чем придумывать.

## Другие типичные истории

**Singleton со статическим состоянием.** Курсы валют держали в статическом классе, «чтобы не тянуть через DI»:

```csharp
public static class CurrencyRates
{
    private static readonly Dictionary<string, decimal> Rates = new();

    public static decimal Get(string currency) => Rates[currency];

    public static void Refresh(IReadOnlyDictionary<string, decimal> fresh)
    {
        Rates.Clear();
        foreach (var (code, rate) in fresh)
            Rates[code] = rate;
    }
}
```

`Dictionary` не потокобезопасен для одновременной записи и чтения, и фоновое обновление под нагрузкой иногда портило его внутреннее состояние. Между `Clear` и заполнением запросы получали `KeyNotFoundException`. Тесты, менявшие курсы, влияли друг на друга, а при параллельном запуске падали случайно. Зависимость не была видна ни в одном конструкторе. Исправление — обычный сервис, зарегистрированный в DI как singleton, который атомарно подменяет неизменяемый снимок:

```csharp
public sealed class CurrencyRateProvider
{
    private volatile IReadOnlyDictionary<string, decimal> rates = new Dictionary<string, decimal>();

    public decimal Get(string currency) => rates[currency];

    public void Refresh(IReadOnlyDictionary<string, decimal> fresh) =>
        rates = new Dictionary<string, decimal>(fresh);
}
```

Читатели видят либо старый снимок целиком, либо новый целиком, а в тестах у каждого свой экземпляр. Проблема была не в одиночке как таковой — время жизни singleton в DI нормально, — а в глобальном изменяемом состоянии.

**Mediator везде.** Обработчики вызывали обработчики через `Send`, зависимости стали невидимыми, вложенный вызов повторно проходил конвейер и открывал вложенную транзакцию. Подробно — в `Mediator и его риски`.

**Базовый класс вместо композиции.** `BaseService<T>` с десятком виртуальных методов, которые наследники переопределяли выборочно. Любое изменение базы ломало кого-то из наследников, а чтобы понять поведение одного сервиса, нужно было читать всю цепочку. Как это раскладывается на декораторы — в `Decorator vs наследование`.

**Observer без отписки.** Короткоживущий объект подписывался на событие долгоживущего, например scoped-сервис на событие singleton'а, и не отписывался. Издатель держал ссылку на подписчика, тот — на свой `DbContext`, и память росла с каждым запросом, а обработчики вызывались на уже освобождённых объектах.

**Strategy и фабрика на два варианта** там, где хватало `switch` на четыре строки, — см. `Strategy vs switch` и `Factory`. На уровне архитектуры — event sourcing в CRUD-домене и микросервисы у команды из пяти человек; такие истории стоит рассказывать, только если вы участвовали в решении.

## Как распознать заранее

- паттерн назван раньше проблемы: «сделаем через стратегию», а какие варианты будут меняться — неизвестно;
- у интерфейса одна реализация и нет реалистичного сценария для второй;
- типы названы по словарю паттернов, а не по предметной области: `IProcessorFactoryProvider`, `BaseManager<T>`;
- довод «на будущее» или «так правильно» вместо конкретного требования;
- стоимость типовой задачи растёт: новая выборка или новый сценарий требуют правок в нескольких слоях;
- в абстракции появляются флаги и параметры, которые использует один вызывающий.

## Что хотят услышать

- **паттерн отделён от проблемы:** вы объясняете, какую проблему он решал бы и почему её не было;
- **последствия измеримы:** время ответа, число файлов на задачу, инциденты, а не вкусовщина;
- **выход инкрементальный:** сначала тесты, потом по одному вызывающему месту, удаление абстракции последним шагом;
- **вывод процессный:** ADR, ревью архитектурных решений, критерий пересмотра;
- **баланс:** вы не против паттернов вообще и можете назвать тот, что окупился, — например, адаптер вокруг платёжного провайдера, который позволил сменить провайдера за спринт, или декоратор с повторами вокруг нестабильного клиента.

## Что стоит ответить на собеседовании

Паттерн вредит, когда решает отсутствующую проблему: цена косвенности остаётся, а выигрыша нет. Типичные механизмы — закрытый доступ к нужным возможностям, невидимое поведение и рост стоимости каждой задачи. Самый частый пример — generic-репозиторий, Unit of Work и спецификации поверх EF Core: потеря проекций и массовых операций, размытые транзакции, тесты на моках, которые не ловят ошибки SQL. Другие — статический singleton с изменяемым состоянием, Mediator с вызовами обработчиков из обработчиков, базовый класс вместо композиции, подписка без отписки.

Сильный ответ — конкретная история в формате «контекст, решение, измеримые последствия, постепенный выход, процессный вывод», рассказанная без обиды на паттерны и с примером паттерна, который окупился.
