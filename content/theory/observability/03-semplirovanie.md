Трассировка пишется на каждый запрос, и каждый запрос порождает десятки span'ов. Сервис на 2 000 RPS с 30 span'ами на запрос — это 60 000 span'ов в секунду, около 5 млрд в сутки, и хранение такого объёма часто стоит дороже самого сервиса. Поэтому трейсы почти всегда сэмплируют — сохраняют только часть. Вопрос не в том, сэмплировать ли, а в том, как выбрать часть так, чтобы в ней остались именно те трейсы, которые понадобятся при разборе: ошибки, медленные запросы, редкие сценарии.

## Head sampling: решение в начале

При head sampling решение принимается в момент создания корневого span'а, когда о запросе ещё ничего не известно, и передаётся дальше флагом `sampled` в заголовке `traceparent`. Все сервисы по цепочке уважают решение вызывающего, поэтому трейс либо сохраняется целиком, либо не сохраняется вовсе.

```csharp
builder.Services.AddOpenTelemetry()
    .WithTracing(t => t
        .SetSampler(new ParentBasedSampler(new TraceIdRatioBasedSampler(0.25)))
        .AddAspNetCoreInstrumentation()
        .AddHttpClientInstrumentation());
```

`TraceIdRatioBasedSampler` решает по самому `trace_id`, а не по случайному числу: разные сервисы с одинаковым коэффициентом примут одинаковое решение для одного трейса. `ParentBasedSampler` применяет внутренний sampler только к корневым span'ам, а для остальных следует флагу родителя. Без него каждый сервис решал бы сам, и в хранилище оказывались бы «дырявые» трейсы без середины.

С версии 1.8 SDK тот же sampler можно задать переменными окружения, не меняя код:

```yaml
env:
  - name: OTEL_TRACES_SAMPLER
    value: parentbased_traceidratio
  - name: OTEL_TRACES_SAMPLER_ARG
    value: "0.25"
```

Отброшенный трейс не бесплатен, но почти: span всё равно создаётся, чтобы передать контекст и флаг дальше, но с `Recorded == false` и `IsAllDataRequested == false` — атрибуты не собираются, экспорт не происходит.

**Почему head sampling теряет редкие ошибки.** Решение принимается вслепую. Пусть сервис обрабатывает 50 RPS, ошибается в 0,1% запросов, а сэмплирование — 1%. Ошибок 0,05 в секунду, из них сохранится 0,0005 в секунду — один трейс с ошибкой примерно в 33 минуты. Именно тот трейс, который нужен для разбора, скорее всего не сохранится. С медленными запросами то же самое: хвост p99 — это 1% запросов, и при сэмплировании 1% от него остаётся сотая доля.

## Tail sampling: решение после завершения

При tail sampling приложение отправляет все span'ы, Collector собирает их по `trace_id`, ждёт завершения трейса и только тогда решает, сохранять ли его. Теперь решение принимается по фактам: была ли ошибка, сколько длился запрос, какой это маршрут.

```yaml
processors:
  tail_sampling:
    decision_wait: 10s
    num_traces: 50000
    expected_new_traces_per_sec: 2000
    policies:
      - name: errors
        type: status_code
        status_code:
          status_codes: [ERROR]
      - name: slow
        type: latency
        latency:
          threshold_ms: 1000
      - name: checkout
        type: string_attribute
        string_attribute:
          key: http.route
          values: [/api/orders/checkout]
      - name: baseline
        type: probabilistic
        probabilistic:
          sampling_percentage: 2
```

Политики верхнего уровня объединяются по «или»: трейс сохраняется, если подошёл под любую. Здесь сохраняются все ошибки, все запросы дольше секунды, весь чекаут и 2% остального. Для сложных условий есть политика `and`, для отбрасывания — `drop` (например, всё по маршрутам проб), а `composite` делит общий лимит span'ов в секунду между подполитиками, чтобы шторм ошибок не съел весь бюджет хранения.

## Цена tail sampling

**Все span'ы трейса должны попасть в один экземпляр Collector.** Если Collector'ов несколько и span'ы распределяются между ними случайно, каждый увидит обрывок трейса и примет своё решение. Поэтому схему делают двухуровневой: первый слой принимает данные от приложений и с экспортёром `load_balancing` раскладывает span'ы по второму слою по хешу `trace_id`, а второй слой уже делает tail sampling.

```yaml
exporters:
  load_balancing:
    routing_key: traceID
    protocol:
      otlp:
        tls:
          insecure: true
    resolver:
      k8s:
        service: otel-sampler-headless.observability
```

Старое имя экспортёра — `loadbalancing`, оно осталось устаревшим псевдонимом. При изменении числа реплик второго слоя часть трейсов на время переезжает на другой экземпляр и может быть разрезана — масштабировать этот слой лучше спокойно, а не резкими скачками.

**Память.** Collector держит в памяти все span'ы за `decision_wait`. При 2 000 новых трейсов в секунду и ожидании 10 секунд в буфере одновременно около 20 000 трейсов; при 30 span'ах на трейс это 600 000 span'ов, то есть порядка сотен мегабайт на экземпляр. `num_traces` ограничивает буфер; если он меньше реального потока, старые трейсы вытесняются раньше решения. Его ставят с запасом относительно `expected_new_traces_per_sec × decision_wait` и следят за метриками самого процессора.

**Долгие трейсы.** Если запрос длится дольше `decision_wait` — асинхронная обработка, долгий отчёт, — решение принимается по неполным данным. Поздние span'ы получают решение из кэша решений, если он включён (`decision_cache`), иначе обрабатываются как новый трейс.

**Трафик от приложения.** Приложение отправляет 100% span'ов, а это сеть и CPU на сериализацию. Частый компромисс — head sampling с высоким коэффициентом в SDK, например 25–50%, плюс tail sampling в Collector. Но тогда tail sampling выбирает только из того, что пропустил head: ошибка в отброшенных 50% не сохранится никогда.

## Как не потерять редкое

**Метрики не сэмплируются.** Доля ошибок и гистограммы задержки считаются SDK по всем запросам, сэмплирование трейсов на них не влияет. Это главный аргумент, почему алерты строят на метриках, а не на трейсах. Если же метрики получают из span'ов в Collector — коннектором spanmetrics, — его ставят до сэмплирования, иначе числа будут занижены в сто раз.

**Логи ошибок пишутся всегда** и содержат `trace_id`. Даже если трейс не сохранился, по этому идентификатору находятся логи запроса во всех сервисах.

**Exemplars** ссылаются только на сохранённые трейсы, поэтому с head sampling 1% у хвоста гистограммы их почти не будет. Tail sampling с политикой по задержке делает переход «от всплеска p99 к трейсу» рабочим — подробнее в статье `Что делать с p99`.

**Принудительное сэмплирование.** Для отладки конкретного клиента или запроса удобен собственный sampler, который по признаку, известному при старте span'а, возвращает `RecordAndSample`, а в остальных случаях передаёт решение обычному:

```csharp
public sealed class ForceSampleSampler(Sampler inner) : Sampler
{
    public override SamplingResult ShouldSample(in SamplingParameters p)
    {
        if (p.Tags is not null)
        {
            foreach (var tag in p.Tags)
            {
                if (tag.Key == "app.force_sample" && tag.Value is true)
                {
                    return new SamplingResult(SamplingDecision.RecordAndSample);
                }
            }
        }
        return inner.ShouldSample(p);
    }
}
```

Его оборачивают в `ParentBasedSampler`, чтобы не ломать решения вызывающих. Фильтровать пробы и служебные маршруты надёжнее фильтром инструментации ASP.NET Core, а не sampler'ом: к моменту сэмплирования атрибуты HTTP-запроса могут быть ещё не заполнены.

**Разные ставки для разных маршрутов.** Платёж сэмплируется на 100%, каталог — на 1%. В tail sampling это отдельные политики, в head sampling — собственный sampler по имени операции.

## Сэмплирование логов

Логи тоже можно сэмплировать, но по другим правилам. Ошибки и предупреждения не сэмплируют никогда — их мало, и каждая важна. Сэмплируют поток однотипных информационных событий и повторяющиеся сообщения: одна и та же ошибка десять тысяч раз в секунду при падении зависимости забьёт и CPU, и хранилище, хотя для разбора хватит первых сотен. Удобная практика — сохранять все логи тех запросов, чей трейс сохранён, и только ошибки для остальных.

## Что стоит ответить на собеседовании

Сэмплирование нужно, потому что трейс пишется на каждый запрос и полное хранение слишком дорого. Head sampling решает в начале запроса по `trace_id` и передаёт решение флагом в `traceparent` — дёшево, трейсы целые, но выбор слепой: при 1% теряется 99% ошибок. Tail sampling решает в Collector после завершения трейса и сохраняет все ошибки и медленные запросы плюс небольшую долю остальных.

Сильный ответ назовёт `ParentBasedSampler` с `TraceIdRatioBasedSampler` и объяснит, зачем уважать решение родителя. Опишет цену tail sampling: двухуровневую схему с `load_balancing` по `trace_id`, буфер в памяти на `decision_wait`, неполные решения для долгих трейсов. И покажет, как не терять редкое: метрики считаются по всем запросам и не зависят от сэмплирования, логи ошибок пишутся всегда с `trace_id`, spanmetrics ставится до сэмплирования, критичные маршруты сэмплируются полностью.
