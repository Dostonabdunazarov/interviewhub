PostgreSQL обслуживает каждое соединение отдельным процессом. Открыть соединение дорого, держать тысячи соединений дорого вдвойне, поэтому между приложением и базой почти всегда стоит пул: в драйвере, во внешнем прокси или в обоих местах сразу. Сам PostgreSQL встроенного пула не имеет и о пулах ничего не знает — для него это обычные долгоживущие сессии.

Ошибки здесь проявляются не в тестах, а на проде: при автоскейлинге, деплое, пиковой нагрузке.

## Почему соединение дорогое

Установка соединения — это TCP-рукопожатие, TLS, аутентификация SCRAM в несколько round trip, затем postmaster делает `fork` нового backend-процесса, и тот прогревает кэши системного каталога. Итог — единицы, а с TLS и сетью десятки миллисекунд, тогда как простой запрос по индексу выполняется за доли миллисекунды. Без пула накладные расходы доминируют.

Держать соединения тоже не бесплатно. Каждый backend — это мегабайты собственной памяти, плюс `work_mem` (по умолчанию 4 МБ) на каждую операцию сортировки или хеширования в запросе, а таких операций в одном плане может быть несколько. Много соединений замедляют сервер даже в простое: растёт стоимость построения снимка, который перебирает активные бэкенды, и конкуренция за разделяемые структуры.

Отсюда `max_connections` по умолчанию 100, и поднимать его до тысяч — плохая идея. База реально выполняет параллельно столько запросов, сколько у неё ядер и дисковых очередей. Ориентир для активных соединений — порядка «ядра × 2–4»; всё сверх этого должно ждать в очереди пула, а не толкаться внутри сервера. Несколько слотов из `max_connections` зарезервированы для суперпользователя (`superuser_reserved_connections`, по умолчанию 3), с PG 16 можно выделить резерв и для ролей с `pg_use_reserved_connections`.

## Пул Npgsql

В Npgsql пул включён по умолчанию. `Open()` берёт физическое соединение из пула или открывает новое, `Close()`/`Dispose()` возвращает его обратно. Пул один на каждую уникальную строку подключения либо на один `NpgsqlDataSource`. Строки, отличающиеся хоть одним символом, например разным `Application Name`, создают разные пулы, и пулинг теряет смысл.

```csharp
var dataSource = NpgsqlDataSource.Create(
    "Host=db;Database=app;Username=app;Password=...;" +
    "Maximum Pool Size=30;Minimum Pool Size=5;Timeout=15;" +
    "Connection Idle Lifetime=300;Application Name=orders-api");

await using var conn = await dataSource.OpenConnectionAsync();
await using var cmd = new NpgsqlCommand("SELECT now()", conn);
var ts = await cmd.ExecuteScalarAsync();
```

| Параметр | По умолчанию | Смысл |
| --- | --- | --- |
| `Pooling` | `true` | включение пула |
| `Maximum Pool Size` | 100 | предел соединений в пуле |
| `Minimum Pool Size` | 0 | сколько держать открытыми всегда |
| `Timeout` | 15 с | ожидание свободного соединения и установки нового |
| `Connection Idle Lifetime` | 300 с | когда закрывать простаивающие сверх минимума |
| `Connection Pruning Interval` | 10 с | как часто проверять простаивающие |
| `Connection Lifetime` | 0 | максимальный возраст соединения, 0 — без ограничения |

`NpgsqlDataSource` (Npgsql 7+) — рекомендуемая точка входа: один объект на приложение, регистрируется через `AddNpgsqlDataSource`, владеет пулом, маппингом типов и логированием. Им же пользуются EF Core и Dapper.

Перед повторной выдачей соединения Npgsql сбрасывает сессионное состояние через `DISCARD ALL`: параметры `SET`, временные таблицы, сессионные advisory locks. `Connection Lifetime` полезен, когда за базой балансировщик или после failover нужно постепенно перераспределить соединения.

## Исчерпание пула

Когда все `Maximum Pool Size` соединений заняты, следующий `Open()` ждёт до `Timeout`, а затем падает с `The connection pool has been exhausted`. Увеличить лимит — почти всегда неверный первый шаг: исчерпание — симптом. Типичные причины:

- **утечка** — соединение или `DbDataReader` не освобождены, нет `await using`;
- **долгие транзакции** — внутри транзакции идёт HTTP-вызов или ожидание очереди, соединение простаивает занятым;
- **sync-over-async** — `.Result` под нагрузкой вызывает голодание thread pool, и соединения возвращаются с задержкой;
- **неограниченный параллелизм** — `Task.WhenAll` на 500 задач, каждая со своим контекстом;
- **медленные запросы** под нагрузкой — каждое соединение занято дольше, пропускная способность пула падает.

Диагностика с двух сторон. В приложении — метрики Npgsql через `System.Diagnostics.Metrics`: занятые и свободные соединения, время ожидания. На сервере — `pg_stat_activity`:

```sql
SELECT application_name, state, count(*),
       max(now() - state_change) AS longest
FROM pg_stat_activity
WHERE backend_type = 'client backend'
GROUP BY 1, 2 ORDER BY 3 DESC;
```

Много `idle in transaction` — приложение не закрывает транзакции; это ещё и удержание горизонта vacuum, см. статью `MVCC и vacuum`.

## EF Core и пул соединений

EF Core сам пулом соединений не управляет: он работает через `NpgsqlConnection`, а пулинг делает драйвер. Соединение открывается непосредственно перед операцией и возвращается сразу после неё, поэтому даже долгоживущий `DbContext` не держит физическое соединение между запросами.

| Ситуация | Соединение занято |
| --- | --- |
| `ToListAsync`, `SaveChangesAsync`, `ExecuteUpdateAsync` | на время операции |
| `await foreach`, `AsAsyncEnumerable` | пока идёт перечисление |
| `BeginTransactionAsync` | до `Commit`/`Rollback`/`Dispose` |
| `Database.OpenConnectionAsync()` | до закрытия или `Dispose` контекста |
| между запросами | нет |

`AddDbContextPool` — другой уровень. Он переиспользует **объекты** `DbContext` вместе с внутренними сервисами (по умолчанию до 1024 экземпляров), экономя аллокации и инициализацию на каждый запрос. К числу соединений с базой он отношения не имеет: `poolSize: 1024` не означает 1024 соединения. Ограничение — контекст не должен хранить собственное состояние в полях, например tenant id. Подробнее — в будущей статье раздела EF Core.

```csharp
builder.Services.AddNpgsqlDataSource(connectionString);
builder.Services.AddDbContextPool<AppDbContext>((sp, o) =>
    o.UseNpgsql(sp.GetRequiredService<NpgsqlDataSource>()));
```

## Считаем соединения на кластер

Пул драйвера живёт внутри процесса. Каждый под приложения — свой пул, и в сумме:

```text
Σ (max_replicas × Maximum Pool Size) по всем сервисам + фоновые задачи + миграции + админ ≤ max_connections − резерв
```

Брать нужно не текущее число реплик, а максимум автоскейлера и учитывать rolling-деплой, при котором старые и новые поды живут одновременно. Пример: 20 подов × 100 по умолчанию = 2000 соединений при `max_connections = 100`. Варианты решения: уменьшить `Maximum Pool Size` до 5–10 на под, ограничить реплики или поставить внешний пулер, который сведёт тысячи клиентских соединений к десяткам серверных.

## PgBouncer и режимы

PgBouncer — лёгкий однопоточный прокси, который держит небольшой пул серверных соединений на пару «база/пользователь» и раздаёт его клиентам. Режим определяет, на сколько серверное соединение закрепляется за клиентом:

| `pool_mode` | Закреплено на | Что даёт |
| --- | --- | --- |
| `session` (по умолчанию) | всю клиентскую сессию | работает всё, экономия только на установке соединения |
| `transaction` | одну транзакцию | основной выигрыш, сессионное состояние не гарантировано |
| `statement` | один оператор | многооператорные транзакции запрещены |

```ini
[databases]
app = host=10.0.0.5 port=5432 dbname=app

[pgbouncer]
listen_port = 6432
pool_mode = transaction
auth_type = scram-sha-256
max_client_conn = 5000
default_pool_size = 40
max_db_connections = 60
reserve_pool_size = 5
max_prepared_statements = 200
```

`default_pool_size` по умолчанию 20, `max_client_conn` — 100, его почти всегда поднимают. Серверный пул подбирают по ресурсам базы, а не по числу клиентов. Кроме экономии, PgBouncer гасит шторм подключений при одновременном рестарте подов и умеет `PAUSE`/`RESUME` для обслуживания и переключения мастера. Ожидание переезжает из базы в PgBouncer, поэтому мониторят `SHOW POOLS`: `cl_waiting` и `maxwait`.

## Что ломает transaction mode

Следующая транзакция клиента может попасть на другое серверное соединение, а на «его» соединение — чужая транзакция. Всё, что опирается на состояние сессии, становится ненадёжным:

- **сессионный `SET`** (`search_path`, `statement_timeout`, `TimeZone`) применится к случайному соединению и протечёт к чужим клиентам. Замена — `SET LOCAL` внутри транзакции или `ALTER ROLE ... SET`;
- **сессионные advisory locks** (`pg_advisory_lock`) останутся на серверном соединении, снять их «тем же» клиентом нельзя. Замена — `pg_advisory_xact_lock`, см. статью `Блокировки и deadlock`;
- **`LISTEN`** — уведомления придут в соединение, которое уже отдано другому. Для подписки нужно прямое соединение к базе;
- **временные таблицы**, живущие дольше транзакции, и курсоры `WITH HOLD`. Безопасны только `ON COMMIT DROP`;
- **подготовленные выражения**: SQL-команда `PREPARE` не работает. Протокольные prepared statements PgBouncer поддерживает с версии 1.21 при `max_prepared_statements > 0` — он сам отслеживает их и подготавливает на нужном серверном соединении. На более старых версиях auto-prepare в драйвере нужно выключать;
- **логика на `pg_backend_pid()`** и `set_config(..., false)` — неустойчива.

Долгие транзакции и `idle in transaction` в этом режиме особенно вредны: они держат соединение из маленького серверного пула, и остальные клиенты встают в очередь.

## Npgsql за PgBouncer

Пул Npgsql оставляют включённым: он экономит соединения до PgBouncer, а PgBouncer — до базы. Под transaction mode строку подключения настраивают так:

```text
Host=pgbouncer;Port=6432;Database=app;Username=app;Password=...;
Maximum Pool Size=20;No Reset On Close=true;Max Auto Prepare=0
```

`No Reset On Close=true` отключает `DISCARD ALL` при возврате в пул: в transaction mode он ушёл бы на случайное серверное соединение и только добавил бы лишний round trip. `Max Auto Prepare` по умолчанию 0; включать автоподготовку и явный `Prepare()` можно только при PgBouncer 1.21+ с `max_prepared_statements`. Для миграций, `LISTEN`, долгих сессионных операций и `pg_dump` заводят отдельную строку подключения напрямую к PostgreSQL.

## Где ставить пулер

- **Sidecar в поде** — экономит установку соединений, но не агрегирует поды: N подов всё равно дают N серверных пулов. Полезен мало.
- **Отдельный сервис** — несколько экземпляров PgBouncer за балансировщиком. Каждый держит свой серверный пул, поэтому итог — экземпляры × `default_pool_size`, и это тоже должно влезть в `max_connections`. Однопоточность обходят несколькими процессами с `so_reuseport` или многопоточными альтернативами — Odyssey, PgCat.
- **На хосте базы** — минимум сетевых переходов, но пулер делит ресурсы с PostgreSQL и переключается вместе с ним при failover.
- **Managed** — RDS Proxy, встроенный PgBouncer в Azure Database for PostgreSQL Flexible Server, Supavisor. Меньше эксплуатации, но свои ограничения на закрепление сессии, их читают в документации провайдера.

## Что стоит ответить на собеседовании

Соединение с PostgreSQL дорогое: процесс на каждое соединение, аутентификация и TLS, мегабайты памяти, а сотни активных соединений деградируют сервер, поэтому `max_connections` по умолчанию 100. Npgsql держит пул на каждую строку подключения или `NpgsqlDataSource` — до 100 соединений, ожидание 15 секунд, затем исключение об исчерпании, которое обычно означает утечку или долгие транзакции. EF Core берёт соединение из пула драйвера на время операции, а `AddDbContextPool` переиспользует объекты контекста, а не соединения.

Сильный ответ посчитает соединения: максимум реплик × `Maximum Pool Size` по всем сервисам с учётом деплоя должен влезать в `max_connections`, и объяснит, когда нужен PgBouncer. Различит режимы `session`, `transaction`, `statement` и перечислит, что ломает transaction mode: сессионные `SET`, advisory locks, `LISTEN`, временные таблицы, `PREPARE` и protocol prepared statements до PgBouncer 1.21. Назовёт настройки Npgsql под пулер — `No Reset On Close`, `Max Auto Prepare`, прямое соединение для миграций — и скажет, что размер серверного пула выбирают по ядрам базы, а не по числу клиентов.
