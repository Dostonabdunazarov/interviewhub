Партиционирование разбивает одну большую логическую таблицу на несколько физических таблиц-секций по значению ключа. Приложение работает с родительской таблицей как с обычной, PostgreSQL сам направляет строки в нужную секцию, а при чтении отсекает лишние. Главный выигрыш обычно не в скорости запросов, как принято думать, а в обслуживании: удаление старых данных, vacuum и индексы работают по частям.

## Три способа разбиения

Декларативное партиционирование появилось в PG 10, и с тех пор почти каждая версия его улучшала.

```sql
CREATE TABLE events (
    id bigint GENERATED ALWAYS AS IDENTITY,
    created_at timestamptz NOT NULL,
    tenant_id int NOT NULL,
    payload jsonb,
    PRIMARY KEY (id, created_at)
) PARTITION BY RANGE (created_at);

CREATE TABLE events_2025_05 PARTITION OF events
    FOR VALUES FROM ('2025-05-01') TO ('2025-06-01');
CREATE TABLE events_2025_06 PARTITION OF events
    FOR VALUES FROM ('2025-06-01') TO ('2025-07-01');
CREATE TABLE events_default PARTITION OF events DEFAULT;
```

| Тип | Пример | Где полезен |
| --- | --- | --- |
| `RANGE` | по месяцам `created_at` | логи, события, история; удаление старого |
| `LIST` | по `region` или крупным `tenant_id` | явные группы значений |
| `HASH` (PG 11+) | `MODULUS 8, REMAINDER n` по `tenant_id` | равномерное распределение без естественного диапазона |

Верхняя граница `RANGE` не включается: строка с `2025-06-01 00:00` попадёт в июньскую секцию. Секции можно разбивать дальше — например, по месяцам, а внутри по хешу. `DEFAULT`-секция принимает строки, которым не нашлось места; без неё такая вставка падает с ошибкой.

Индекс, созданный на родительской таблице (PG 11+), автоматически создаётся на каждой секции, включая будущие. Но физически это отдельные индексы — глобального индекса по всем секциям в PostgreSQL нет.

## Partition pruning

Отсечение секций — то, ради чего ключ партиционирования должен быть в запросах:

```sql
EXPLAIN SELECT * FROM events WHERE created_at >= '2025-06-10';
```

```text
Append
  ->  Seq Scan on events_2025_06
        Filter: (created_at >= '2025-06-10 00:00:00+00'::timestamptz)
  ->  Seq Scan on events_default
        Filter: (created_at >= '2025-06-10 00:00:00+00'::timestamptz)
```

Вывод иллюстративный. Майская секция не читается вовсе, а `DEFAULT` попадает в план, потому что про её содержимое PostgreSQL ничего не знает.

Отсечение бывает двух видов. **На этапе планирования** — когда значение известно сразу, как литерал выше. **На этапе выполнения** (PG 11+) — когда значение приходит параметром generic-плана или из подзапроса; в плане это видно как `Subplans Removed: N`. Второй вид работает, но план всё равно строится по всем секциям, и время планирования не экономится. Как устроены generic-планы — в статье `EXPLAIN и план запроса`.

Pruning срабатывает, только если условие сравнивает саму колонку ключа: `created_at >= $1` подходит, `date_trunc('day', created_at) = $1` — нет. Это то же правило, что и для индексов из статьи `Индексы: B-tree, GIN, BRIN`.

## Что даёт партиционирование

**Дешёвое удаление старых данных.** `DELETE` миллионов строк — это часы работы, гигабайты WAL, отставание реплик и мёртвые версии для vacuum. Удаление секции — операция с метаданными:

```sql
ALTER TABLE events DETACH PARTITION events_2024_01 CONCURRENTLY;
DROP TABLE events_2024_01;
```

`DETACH ... CONCURRENTLY` (PG 14+) не блокирует запросы к родителю надолго, но не работает внутри транзакции.

**Обслуживание по частям.** Vacuum, `REINDEX` и построение индекса по терабайтной таблице идут сутками; по секциям — порциями и параллельно. Старые секции, которые больше не меняются, можно один раз заморозить `VACUUM FREEZE` и больше не трогать — заодно снимается риск wraparound из статьи `MVCC и vacuum`.

**Горячие и холодные данные.** Запись и чтение идут в последние секции, их индексы помещаются в память. Старые секции можно вынести на дешёвый диск через tablespace.

**Массовая загрузка.** Загрузить данные в отдельную таблицу, построить на ней индексы и подключить через `ATTACH PARTITION`.

## Ограничения

- **PK и уникальные ограничения обязаны включать ключ партиционирования.** Глобальной уникальности по `id` нет: при разбиении по дате `UNIQUE (email)` невозможен, а PK становится составным `(id, created_at)`, и внешние ключи на такую таблицу ссылаются по обеим колонкам.
- **Запрос без ключа идёт во все секции.** Точечный поиск по `id` при ключе `created_at` проверит индекс каждой секции — при сотне секций это сто спусков вместо одного.
- **`UPDATE` ключа** переносит строку в другую секцию (PG 11+), фактически это `DELETE` и `INSERT`.
- **Секции нужно создавать заранее.** Иначе в новом месяце строки уйдут в `DEFAULT` или вставка упадёт. Обычно это делает расширение `pg_partman` или фоновая задача.
- **`DEFAULT`-секция мешает.** При `ATTACH` новой секции PostgreSQL проверяет, нет ли в `DEFAULT` подходящих строк, и сканирует её.
- **`CREATE INDEX CONCURRENTLY` на родителе не поддерживается** (в PG 15–17). Порядок обхода: `CREATE INDEX ... ON ONLY events` (создаётся невалидным, без построения), затем `CREATE INDEX CONCURRENTLY` на каждой секции и `ALTER INDEX ... ATTACH PARTITION` — когда подключены все, родительский индекс становится валидным.

**Сколько секций.** Десятки и сотни — нормально, тысячи — уже риск. Растёт время планирования запросов без pruning, память на соединение под кэш метаданных и число блокировок: запрос, который не отсёк секции, берёт `ACCESS SHARE` на каждую секцию и её индексы, и под нагрузкой это упирается в lock manager и `max_locks_per_transaction`. Размер секции — ориентир от единиц до десятков гигабайт.

## Выбор ключа

Ключ выбирают по двум вопросам: **по какому полю фильтруют почти все критичные запросы** и **по какому полю данные живут и удаляются**. Идеальный ключ отвечает на оба — для событийных данных это время, для мультитенантных систем — тенант.

| Данные | Ключ |
| --- | --- |
| События, логи, метрики, история | `RANGE (created_at)` по дню, неделе или месяцу |
| SaaS с крупными тенантами | `LIST` или `HASH (tenant_id)` |
| Равномерно размазать запись без естественного диапазона | `HASH` |

Что бывает при неудачном выборе:

- **нет pruning** — разбили по `created_at`, а главный запрос `WHERE user_id = ?`; запросы стали **медленнее**, чем до партиционирования;
- **перекос** — `LIST (country)`, где 80% строк в одной стране: одна секция огромна, все проблемы большой таблицы остались;
- **слишком мелкие секции** — дневные по 10 МБ дают тысячи таблиц без выигрыша;
- **изменяемый ключ** — каждое его обновление переносит строку между секциями.

Проверяют выбор до миграции: топ запросов из `pg_stat_statements` должен содержать условие на ключ в пригодной для pruning форме, а распределение строк по будущим секциям — быть ровным. Исправить ключ потом можно только полной переливкой таблицы.

## Перевод живой таблицы без простоя

Превратить обычную таблицу в партиционированную через `ALTER TABLE` нельзя. Для разбиения по времени работает приём «старая таблица становится секцией». Сначала, не блокируя запись, готовят ограничения:

```sql
CREATE UNIQUE INDEX CONCURRENTLY orders_id_created_uq ON orders (id, created_at);

ALTER TABLE orders ADD CONSTRAINT orders_legacy_range
  CHECK (created_at IS NOT NULL AND created_at < '2025-07-01') NOT VALID;
ALTER TABLE orders VALIDATE CONSTRAINT orders_legacy_range;
```

`VALIDATE` сканирует таблицу под `SHARE UPDATE EXCLUSIVE`, запись при этом идёт. Затем одна короткая транзакция с `lock_timeout`: переименовать `orders` в `orders_legacy`, создать партиционированную `orders`, подключить старую таблицу секцией `FROM (MINVALUE) TO ('2025-07-01')` и создать секцию на следующий месяц. Валидный `CHECK` доказывает границу, поэтому `ATTACH PARTITION` не сканирует таблицу, а PK на родителе подхватывает уже построенный уникальный индекс. Старые данные потом уходят по retention целиком.

Если нужен другой ключ, делают фоновую переливку: новая таблица, триггер для двойной записи, бэкфилл батчами, сверка и короткое переключение переименованием. В обоих случаях отдельно продумывают внешние ключи, последовательности, зависимые view и создание будущих секций.

## Партиционирование и шардирование

Все секции живут на одном сервере и делят его CPU, память и диск. Партиционирование не масштабирует запись за пределы одной машины — это задача шардирования: Citus или разнесение данных на уровне приложения. Как выбирать ключ шардирования и переживать решардинг, разбирается в треке про распределённые системы, в разделе «Данные под нагрузкой».

Прежде чем партиционировать, стоит проверить более дешёвые альтернативы: частичные индексы под горячие данные, BRIN по времени, архивную таблицу или вынос аналитики в колоночное хранилище.

## Что стоит ответить на собеседовании

Партиционирование делит таблицу на секции по `RANGE`, `LIST` или `HASH`; приложение работает с родителем, а PostgreSQL отсекает лишние секции на этапе планирования или, для параметров, на этапе выполнения. Главный выигрыш — удаление старых данных через `DETACH` и `DROP` вместо многочасового `DELETE` и обслуживание по частям; ускорение запросов вторично и бывает только при условии на ключ.

Сильный ответ назовёт ограничения: PK и уникальные ограничения обязаны включать ключ, глобальных индексов нет, запрос без ключа идёт во все секции, секции нужно создавать заранее, а тысячи секций бьют по планированию и блокировкам. Объяснит, как выбирать ключ — по фильтрам горячих запросов и жизненному циклу данных — и что бывает при ошибке. И отличит партиционирование от шардирования: секции живут на одном сервере.
