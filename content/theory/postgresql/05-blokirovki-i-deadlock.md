MVCC избавляет читателей от ожидания писателей, но не отменяет блокировки совсем. Два `UPDATE` одной строки выстраиваются в очередь, `ALTER TABLE` ждёт всех, кто читает таблицу, а неудачный порядок захвата строк приводит к deadlock. В PostgreSQL два уровня тяжеловесных блокировок — на таблицу и на строку, — и устроены они по-разному.

## Блокировки таблиц

Блокировку на таблицу берёт **каждая** команда, даже обычный `SELECT`. Режимов восемь, но большинство совместимы между собой, и проблемы создают в основном DDL.

| Режим | Кто берёт |
| --- | --- |
| `ACCESS SHARE` | `SELECT` |
| `ROW SHARE` | `SELECT ... FOR UPDATE` / `FOR SHARE` |
| `ROW EXCLUSIVE` | `INSERT`, `UPDATE`, `DELETE`, `MERGE` |
| `SHARE UPDATE EXCLUSIVE` | `VACUUM`, `ANALYZE`, `CREATE INDEX CONCURRENTLY` |
| `SHARE` | `CREATE INDEX` без `CONCURRENTLY` |
| `SHARE ROW EXCLUSIVE` | `CREATE TRIGGER`, добавление внешнего ключа |
| `EXCLUSIVE` | `REFRESH MATERIALIZED VIEW CONCURRENTLY` |
| `ACCESS EXCLUSIVE` | `DROP`, `TRUNCATE`, большинство `ALTER TABLE`, `VACUUM FULL` |

Главные конфликты стоит знать наизусть. Чтение (`ACCESS SHARE`) конфликтует **только** с `ACCESS EXCLUSIVE`. Запись (`ROW EXCLUSIVE`) не конфликтует сама с собой — параллельные `INSERT` и `UPDATE` в одну таблицу на уровне таблицы друг другу не мешают. Обычный `CREATE INDEX` (`SHARE`) блокирует запись, но не чтение. `ACCESS EXCLUSIVE` блокирует всё.

## Очередь блокировок: как быстрый ALTER вешает прод

Самая дорогая ловушка в эксплуатации. Запросы встают в очередь, и новый запрос не может обогнать ждущий конфликтующий:

```text
T1: BEGIN; SELECT ... FROM orders;        держит ACCESS SHARE, транзакция висит
T2: ALTER TABLE orders ADD COLUMN x int;  ждёт ACCESS EXCLUSIVE за T1
T3..Tn: SELECT ... FROM orders;            ждут за T2
```

`ALTER TABLE ADD COLUMN` сам по себе меняет только метаданные и выполнился бы за миллисекунды. Но он ждёт долгую транзакцию T1, а все остальные запросы к таблице, даже чтения, ждут его. Пул соединений исчерпывается за секунды, сервис лежит. Защита — `lock_timeout` в каждой миграции:

```sql
SET lock_timeout = '3s';
ALTER TABLE orders ADD COLUMN note text;
```

При таймауте миграция падает с ошибкой и повторяется позже, а продакшен продолжает работать.

## Блокировки строк

Строку блокируют `UPDATE`, `DELETE` и `SELECT ... FOR ...`. Обычный `SELECT` блокировок строк не берёт и не ждёт. Режимов четыре, от сильного к слабому:

| Режим | Кто берёт | С чем конфликтует |
| --- | --- | --- |
| `FOR UPDATE` | `DELETE`, `UPDATE` ключевых колонок, явный запрос | со всеми |
| `FOR NO KEY UPDATE` | обычный `UPDATE` | со всеми, кроме `FOR KEY SHARE` |
| `FOR SHARE` | явный запрос | с `FOR NO KEY UPDATE` и `FOR UPDATE` |
| `FOR KEY SHARE` | проверка внешнего ключа на родительской строке | только с `FOR UPDATE` |

Разделение на «key» и «no key» нужно, чтобы вставка дочерней строки, которая берёт `FOR KEY SHARE` на родителя, не блокировала обычные обновления родителя, не меняющие ключ.

Блокировка строки держится **до конца транзакции**. Хранится она не в общей таблице блокировок в памяти, а прямо в заголовке версии строки — в `xmax` и флагах. Поэтому число заблокированных строк не ограничено, `SELECT ... FOR UPDATE` пишет на страницу и порождает WAL, а в `pg_locks` такие блокировки не видны, пока их никто не ждёт. Ожидающий виден как ждущий завершения транзакции-держателя (`transactionid`).

Два модификатора меняют поведение ожидания. `NOWAIT` сразу возвращает ошибку `55P03`, если строка занята. `SKIP LOCKED` пропускает занятые строки — на этом в PostgreSQL строят очередь задач для нескольких воркеров:

```sql
UPDATE jobs SET status = 'running', worker = @worker
WHERE id IN (
  SELECT id FROM jobs
  WHERE status = 'queued'
  ORDER BY id
  LIMIT 10
  FOR UPDATE SKIP LOCKED
)
RETURNING *;
```

Каждый воркер берёт свою десятку, не дожидаясь чужих. В запросе с `JOIN` `FOR UPDATE` блокирует строки всех таблиц; ограничить можно через `FOR UPDATE OF jobs`.

## Как возникает deadlock

Deadlock — цикл ожиданий: T1 держит A и ждёт B, T2 держит B и ждёт A. Классика — встречные переводы:

```text
T1: UPDATE accounts SET balance = balance - 10 WHERE id = 1;
T2: UPDATE accounts SET balance = balance - 10 WHERE id = 2;
T1: UPDATE accounts SET balance = balance + 10 WHERE id = 2;   ждёт T2
T2: UPDATE accounts SET balance = balance + 10 WHERE id = 1;   ждёт T1
```

Проверка на цикл не выполняется на каждое ожидание — это дорого. Процесс, который ждёт блокировку дольше `deadlock_timeout` (по умолчанию 1 с), запускает поиск цикла в графе ожиданий. Найдя цикл, PostgreSQL откатывает одну из транзакций, обычно ту, что выполнила проверку:

```text
ERROR:  deadlock detected
DETAIL:  Process 4120 waits for ShareLock on transaction 9081; blocked by process 4133.
         Process 4133 waits for ShareLock on transaction 9080; blocked by process 4120.
SQLSTATE: 40P01
```

`ShareLock on transaction` — так выглядит ожидание строки: процесс ждёт завершения транзакции, которая её держит. Общая теория взаимоблокировок — та же, что для `lock` в многопоточном коде; здесь важно, где разный порядок появляется неявно:

- **массовый `UPDATE` без порядка** — две сессии проходят пересекающиеся наборы строк в порядке своих планов, одна Seq Scan, другая по индексу;
- **внешние ключи** — транзакция вставляет детей (берёт `FOR KEY SHARE` на родителя), потом обновляет родителя; встречная такая же ждёт её, она ждёт встречную;
- **повышение блокировки** — две транзакции взяли `FOR SHARE` на одну строку, затем обе пытаются её обновить;
- **вставки с одинаковыми уникальными ключами** в разном порядке;
- **триггеры и каскады**, порядок блокировок которых не виден в коде приложения;
- **ORM** — `SaveChanges` отправляет команды в порядке, который выбирает сам.

## Как предотвратить

Главное правило — **один детерминированный порядок захвата**. Если все блокируют строки по возрастанию ключа, цикл невозможен:

```sql
BEGIN;
SELECT id FROM accounts WHERE id IN (@from, @to) ORDER BY id FOR UPDATE;
UPDATE accounts SET balance = balance - @amount WHERE id = @from;
UPDATE accounts SET balance = balance + @amount WHERE id = @to;
COMMIT;
```

`UPDATE` не поддерживает `ORDER BY`, поэтому для массовых изменений порядок задают отдельной блокировкой в CTE с `ORDER BY id FOR UPDATE`. Остальное: сначала блокировать родителя, потом детей; сразу брать сильную блокировку (`FOR UPDATE`, а не `FOR SHARE` с последующим `UPDATE`); держать транзакции короткими; для горячих счётчиков использовать атомарный `UPDATE ... SET x = x + 1`.

Даже при аккуратном порядке deadlock возможен в редких сочетаниях, поэтому транзакцию с `40P01` повторяют целиком, как и `40001` из статьи `Уровни изоляции`. Но частые deadlock — признак ошибки в порядке, который нужно исправить, а не спрятать за ретраями. Увеличивать `deadlock_timeout` бесполезно: deadlock будут находиться позже, а транзакции дольше висеть.

## Пессимистичная или оптимистичная

`SELECT ... FOR UPDATE` уместен, когда конфликты частые, а операция короткая и целиком внутри одной транзакции: конкуренты ждут вместо того, чтобы падать и повторять. Оптимистичная блокировка — проверка версии при записи — когда конфликты редкие или между чтением и записью проходит время вне транзакции, как при редактировании формы:

```sql
UPDATE documents SET body = @body, version = version + 1
WHERE id = @id AND version = @expected;
```

Ноль затронутых строк — документ успели изменить. В EF Core это concurrency token, а в Npgsql удобно маппить свойство на системную колонку `xmin`, которая меняется при каждом обновлении строки; конфликт выбрасывает `DbUpdateConcurrencyException`. Часто лучше обоих — атомарный условный `UPDATE stock SET qty = qty - 2 WHERE sku = @sku AND qty >= 2`: ни отдельного чтения, ни ретраев.

## Как найти держателя блокировки

Цель — корень цепочки ожиданий: процесс, который сам ничего не ждёт, но блокирует других.

```sql
SELECT pid, pg_blocking_pids(pid) AS blocked_by, state,
       now() - xact_start AS xact_age, wait_event_type, wait_event,
       left(query, 80) AS query
FROM pg_stat_activity
WHERE cardinality(pg_blocking_pids(pid)) > 0
   OR pid IN (SELECT unnest(pg_blocking_pids(pid)) FROM pg_stat_activity)
ORDER BY xact_start;
```

Частая картина — корень в состоянии `idle in transaction` с большим `xact_age`. Колонка `query` показывает его **последний** запрос, а блокировку мог взять любой из предыдущих. Это приложение, которое открыло транзакцию и не закрыло её: забытый `Commit`, внешний HTTP-вызов внутри транзакции, исключение без `Dispose`. `pg_cancel_backend(pid)` отменяет текущий запрос и для `idle in transaction` бесполезен; `pg_terminate_backend(pid)` закрывает соединение и откатывает транзакцию.

Для истории, а не только текущего момента, включают `log_lock_waits = on` — в лог попадает каждое ожидание дольше `deadlock_timeout` с держателем и очередью. При самом deadlock в лог сервера пишутся тексты запросов всех участников, чего нет в ошибке на клиенте. Счётчик `pg_stat_database.deadlocks` показывает, растёт ли проблема.

## Что стоит ответить на собеседовании

В PostgreSQL блокировки двух уровней. Блокировку таблицы берёт любая команда, но чтение конфликтует только с `ACCESS EXCLUSIVE`, который берут `DROP`, `TRUNCATE` и большинство `ALTER TABLE`. Блокировки строк берут `UPDATE`, `DELETE` и `SELECT ... FOR UPDATE`; хранятся они в заголовке строки и держатся до конца транзакции, а обычный `SELECT` их не ждёт. Deadlock — цикл ожиданий; его ищут после `deadlock_timeout` в 1 секунду и откатывают одну транзакцию с `40P01`.

Сильный ответ объяснит очередь блокировок — быстрый `ALTER TABLE` за долгой транзакцией вешает все запросы к таблице, поэтому в миграциях обязателен `lock_timeout`. Назовёт главную профилактику deadlock — единый порядок захвата строк, например `ORDER BY id FOR UPDATE`, — и неявные источники разного порядка: массовые `UPDATE`, внешние ключи, повышение блокировки. Покажет `SKIP LOCKED` для очередей, выбор между `FOR UPDATE` и оптимистичной проверкой версии и как через `pg_blocking_pids` найти держателя, который часто оказывается `idle in transaction`.
