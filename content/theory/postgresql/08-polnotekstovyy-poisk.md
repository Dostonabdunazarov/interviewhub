`LIKE '%индекс%'` — плохой поиск по тексту. Он не находит «индексы» и «индексами», не умеет ранжировать результаты и обычным B-tree не ускоряется. В PostgreSQL есть встроенный полнотекстовый поиск: текст превращается в набор нормализованных слов, запрос — в логическое выражение над ними, а GIN-индекс находит совпадения без прохода по всей таблице. Для поиска по каталогу, статьям или тикетам этого обычно хватает без отдельного поискового движка.

## tsvector и tsquery

Два типа данных лежат в основе всего. `tsvector` — документ, разобранный на **лексемы**: слова, приведённые к нормальной форме, с позициями в тексте. Стоп-слова вроде предлогов и союзов отбрасываются.

```sql
SELECT to_tsvector('russian', 'Индексы ускоряют поиск, а поиск без индекса медленный');
```

```text
'индекс':1,7 'медлен':8 'поиск':3,5 'ускоря':2
```

Вывод показан примерно: точные основы зависят от словаря. Видно главное — «Индексы» и «индекса» свелись к одной лексеме, у каждой лексемы сохранились позиции, а «а» и «без» выброшены как стоп-слова, хотя свои позиции они заняли.

`tsquery` — запрос: лексемы, соединённые операторами `&` (и), `|` (или), `!` (не) и `<->` (следует за). Совпадение проверяет оператор `@@`:

```sql
SELECT to_tsvector('russian', 'Индексы ускоряют поиск')
       @@ to_tsquery('russian', 'индекс & поиск');
```

Запрос тоже проходит нормализацию, поэтому «индекс» в запросе совпадает с «Индексы» в тексте.

## Конфигурации и словари

Первый аргумент — **конфигурация** поиска (`regconfig`): она определяет парсер, словари и стоп-слова. `russian` использует стеммер Snowball, который отрезает окончания. Это быстро и не требует словаря, но иногда склеивает разные слова или не склеивает формы одного. `simple` только приводит к нижнему регистру — подходит для артикулов, кодов, имён собственных. Для текстов вперемешку с английскими терминами часто строят свою конфигурацию на основе `russian` с английским стеммером для латиницы; расширение `unaccent` убирает диакритику.

Конфигурацию стоит **всегда указывать явно**. Форма `to_tsvector(text)` без неё берёт `default_text_search_config` из настроек сервера и поэтому помечена `STABLE`, а не `IMMUTABLE` — по ней нельзя построить индекс. Двухаргументная `to_tsvector('russian', body)` — `IMMUTABLE`, и именно она идёт в индекс. Если в таблице тексты на разных языках, конфигурацию можно хранить в колонке типа `regconfig` и передавать её первым аргументом.

## Как превращать ввод пользователя в запрос

`to_tsquery` требует синтаксиса с операторами: строка `индекс поиск` без `&` — ошибка. Пользовательский ввод в неё передавать нельзя. Для этого есть три другие функции:

| Функция | Что делает с `быстрый поиск` |
| --- | --- |
| `plainto_tsquery` | `'быстр' & 'поиск'` — все слова через «и» |
| `phraseto_tsquery` | `'быстр' <-> 'поиск'` — слова подряд, как фраза |
| `websearch_to_tsquery` (PG 11+) | синтаксис поисковиков: кавычки для фразы, `or`, минус для исключения |

`websearch_to_tsquery('russian', '"полнотекстовый поиск" -elasticsearch')` превратит фразу в кавычках в `<->`, а слово с минусом — в `!`. Она никогда не падает на некорректном вводе, поэтому для поисковой строки на сайте это выбор по умолчанию.

## Индекс: выражение или generated-колонка

Без индекса `@@` вычисляет `to_tsvector` для каждой строки таблицы — это Seq Scan с разбором всего текста. Индекс — GIN, инвертированный, из статьи `Индексы: B-tree, GIN, BRIN`: для каждой лексемы он хранит список строк.

Индекс можно построить по выражению:

```sql
CREATE INDEX articles_fts_idx ON articles
USING gin (to_tsvector('russian', title || ' ' || body));
```

Но тогда запрос обязан повторить выражение посимвольно, иначе индекс не подойдёт, а для ранжирования `to_tsvector` всё равно будет вычисляться заново. Удобнее хранимая generated-колонка (PG 12+):

```sql
ALTER TABLE articles ADD COLUMN search tsvector
GENERATED ALWAYS AS (
    setweight(to_tsvector('russian', coalesce(title, '')), 'A') ||
    setweight(to_tsvector('russian', coalesce(body, '')), 'B')
) STORED;

CREATE INDEX articles_search_idx ON articles USING gin (search);
```

`coalesce` нужен потому, что конкатенация с `NULL` даёт `NULL`, и статья без тела выпала бы из поиска целиком. `setweight` помечает лексемы заголовка весом `A`, тела — `B`; это пригодится для ранжирования. Колонка занимает место в таблице, зато выражение видно в схеме, а запросы простые:

```sql
SELECT id, title
FROM articles
WHERE search @@ websearch_to_tsquery('russian', @term);
```

В плане GIN, как всегда, выглядит как `Bitmap Index Scan` под `Bitmap Heap Scan`. Цена индекса — запись: документ из тысячи различных слов даёт тысячу записей в индексе, и часто обновляемые длинные тексты заметно нагружают таблицу. Механизм pending list, который это смягчает, разобран там же, в статье про индексы.

## EF Core и Npgsql

Провайдер Npgsql поддерживает всё это из LINQ. Generated-колонка и индекс задаются в конфигурации модели:

```csharp
builder.HasGeneratedTsVectorColumn(a => a.Search, "russian", a => new { a.Title, a.Body })
       .HasIndex(a => a.Search)
       .HasMethod("GIN");
```

Запрос транслируется в `@@` с `websearch_to_tsquery`, а ранжирование — в `ts_rank`:

```csharp
var query = EF.Functions.WebSearchToTsQuery("russian", term);

var hits = await db.Articles
    .Where(a => a.Search.Matches(query))
    .OrderByDescending(a => a.Search.Rank(query))
    .Take(20)
    .Select(a => new { a.Id, a.Title })
    .ToListAsync(ct);
```

`HasGeneratedTsVectorColumn` не поддерживает веса; если они нужны, колонку описывают через `HasComputedColumnSql(..., stored: true)` с SQL из предыдущего раздела. Как LINQ превращается в SQL, разбирается в статье `IEnumerable vs IQueryable`.

## Ранжирование и подсветка

`ts_rank` считает релевантность по частоте совпавших лексем и их весам, `ts_rank_cd` дополнительно учитывает близость совпадений друг к другу. Веса по умолчанию — `{0.1, 0.2, 0.4, 1.0}` для `D`, `C`, `B`, `A`, так что совпадение в заголовке весит больше, чем в теле. Третий аргумент — нормализация по длине документа, иначе длинные тексты выигрывают просто количеством слов.

Важное ограничение: индекс находит совпадения, но **не сортирует** по рангу. `ts_rank` вычисляется для каждой найденной строки, и запрос по частому слову, которое есть в половине таблицы, ранжирует полтаблицы. Отсюда приёмы: требовать все слова (`&`, а не `|`), ограничивать выборку дополнительными фильтрами, а для тяжёлых случаев — расширение RUM, которое хранит в индексе позиции и умеет отдавать результат в порядке релевантности.

`ts_headline` строит фрагмент с подсвеченными совпадениями. Он заново разбирает исходный текст и индексом не ускоряется, поэтому его вызывают только для итоговых 20 строк страницы — во внешнем запросе поверх `LIMIT`, — а не для всей выборки.

## Триграммы: опечатки и подстроки

Полнотекстовый поиск работает со словами целиком. Опечатку «индкес» или подстроку внутри артикула он не найдёт. Для этого есть расширение `pg_trgm`: строка режется на тройки символов, и похожесть считается по доле общих троек.

```sql
CREATE EXTENSION pg_trgm;
CREATE INDEX products_name_trgm ON products USING gin (name gin_trgm_ops);

SELECT name FROM products WHERE name ILIKE '%ксиом%';
SELECT name, similarity(name, 'айфон') AS sim
FROM products WHERE name % 'айфон' ORDER BY sim DESC LIMIT 10;
```

Триграммный GIN ускоряет `LIKE` и `ILIKE` с `%` с обеих сторон, регулярные выражения и оператор похожести `%` (порог по умолчанию — 0.3, `pg_trgm.similarity_threshold`). Частая связка: полнотекстовый поиск по описаниям плюс триграммы по названиям для подсказок и исправления опечаток. На строках короче трёх символов триграммы бесполезны.

## Ограничения и когда уходить в поисковый движок

У `tsvector` есть жёсткие пределы: размер меньше 1 МБ, позиции больше 16 383 обрезаются, не больше 256 позиций на лексему. Для статей и описаний товаров это не заметно, для книг целиком — заметно.

Встроенного поиска хватает, пока нужен поиск по словам с морфологией, фильтры из той же базы и транзакционная согласованность: документ виден в поиске сразу после коммита, без отдельной синхронизации. Elasticsearch или OpenSearch оправданы, когда нужны развитая морфология и синонимы, фасеты по миллионам документов, нечёткий поиск с тонкой настройкой релевантности или горизонтальное масштабирование поиска отдельно от базы. Платой становится отдельная система и её синхронизация с базой — обычно через outbox или CDC, которые разбираются в треке про распределённые системы.

## Что стоит ответить на собеседовании

Полнотекстовый поиск в PostgreSQL строится на `tsvector` — документе, разобранном на нормализованные лексемы с позициями, — и `tsquery` — логическом выражении над лексемами; совпадение проверяет `@@`. Нормализацию задаёт конфигурация вроде `russian` со стеммером Snowball, и указывать её нужно явно, потому что только двухаргументная `to_tsvector` иммутабельна и годится для индекса. Ускоряет поиск GIN-индекс, удобнее всего — по хранимой generated-колонке с весами для заголовка и тела.

Сильный ответ добавит, что пользовательский ввод передают через `websearch_to_tsquery`, а не `to_tsquery`, что индекс не сортирует по рангу и `ts_rank` считается для каждой найденной строки, а `ts_headline` вызывают только для итоговой страницы. Отличит полнотекстовый поиск от триграмм `pg_trgm`, которые нужны для опечаток и `LIKE '%...%'`. И назовёт границу: встроенного поиска хватает, пока важны морфология, фильтры и согласованность с базой; за синонимами, фасетами и масштабированием поиска идут в Elasticsearch.
