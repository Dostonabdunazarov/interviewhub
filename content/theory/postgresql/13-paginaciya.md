Отдать список по страницам можно двумя способами. `LIMIT/OFFSET` отвечает на вопрос «покажи страницу номер N», keyset-пагинация (её же называют seek или cursor pagination) — на вопрос «покажи строки после последней, которую я видел». Первый прост и позволяет прыгнуть на любую страницу, но дорожает с каждой страницей и сбивается при вставках. Второй работает за одинаковое время на любой глубине, но умеет только «вперёд» и «назад».

## OFFSET/LIMIT и почему он деградирует

```sql
SELECT id, title, created_at
FROM posts
WHERE status = 'published'
ORDER BY created_at DESC, id DESC
LIMIT 20 OFFSET 40;
```

Семантика `OFFSET` — «сформировать результат и выбросить первые N строк». PostgreSQL не умеет перепрыгнуть N записей в B-tree: в индексе нет счётчиков позиций, а видимость каждой строки нужно проверять отдельно, потому что индекс её не хранит (подробнее — в статье `MVCC и vacuum`). Поэтому `OFFSET 500000` честно читает и отбрасывает полмиллиона строк, и в плане это видно по числу строк под узлом `Limit`:

```text
Limit  (actual time=180.3..180.4 rows=50 loops=1)
  ->  Index Scan using events_pkey on events  (actual rows=500050 loops=1)
```

Вывод иллюстративный, но пропорция характерная: работа растёт линейно с номером страницы. Если подходящего индекса под `ORDER BY` нет, всё ещё хуже — перед отбрасыванием нужна сортировка всей выборки, хотя бы top-N.

Вторая проблема — стабильность. Между запросом второй и третьей страницы в начало ленты добавилась запись — все строки сдвинулись на одну, и последняя строка второй страницы придёт повторно. Удаление даёт обратный эффект: одна строка пропадёт незамеченной. Для админки с номерами страниц это терпимо, для ленты и API — нет.

## Keyset-пагинация

Вместо номера страницы клиент передаёт значение ключа сортировки последней полученной строки, и запрос продолжает с него:

```sql
SELECT * FROM events WHERE id > 500123 ORDER BY id LIMIT 50;
```

```text
Limit  (actual time=0.03..0.09 rows=50 loops=1)
  ->  Index Scan using events_pkey on events  (actual rows=50 loops=1)
        Index Cond: (id > 500123)
```

Один спуск по B-tree до нужного места и 50 записей по листьям — стоимость не зависит от того, тысячная это страница или первая. Вставки и удаления выше курсора на следующую страницу не влияют: граница задана значением, а не позицией.

Цена — нет перехода на произвольную страницу и нет «всего страниц». Это ограничение интерфейса, а не реализации, поэтому типичный компромисс для UI — keyset для «далее/назад» и бесконечного скролла, а номера страниц только на первых десятках с запретом уходить глубже.

## Составной ключ и сравнение кортежей

Сортировать ленту по одному `created_at` нельзя: время не уникально, и строки с одинаковой меткой на границе страниц потеряются или задвоятся. Ключ должен быть детерминированным — последняя колонка уникальна, обычно это `id`. Условие продолжения для `(created_at, id)` удобно писать через сравнение кортежей (row value comparison):

```sql
CREATE INDEX posts_published_feed_idx
    ON posts (created_at DESC, id DESC)
    WHERE status = 'published';

SELECT id, title, created_at
FROM posts
WHERE status = 'published'
  AND (created_at, id) < (@last_created_at, @last_id)
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

`(a, b) < (x, y)` в SQL означает лексикографическое сравнение: `a < x` или `a = x AND b < y`. Важно, что PostgreSQL умеет использовать такое условие как `Index Cond` составного B-tree-индекса, то есть начинать скан прямо с нужной позиции. Индекс здесь частичный под фильтр `status = 'published'`; направления `DESC` можно было не указывать — B-tree читается в обе стороны, — но колонки и их взаимный порядок обязаны совпадать с `ORDER BY`. Подробнее о правиле ведущего префикса — в статье `Индексы: B-tree, GIN, BRIN`.

Сравнение кортежей работает, только когда все колонки сортируются в одну сторону. Для смешанного порядка, например `price ASC, id DESC`, пишут развёрнутое условие:

```sql
WHERE price >= @last_price
  AND (price > @last_price OR (price = @last_price AND id < @last_id))
ORDER BY price ASC, id DESC
LIMIT 20;
```

Первая строка логически избыточна, но даёт планировщику диапазон для `Index Cond`. Без неё `OR` попадает в `Filter`, и скан идёт с начала индекса, отбрасывая всё до курсора, — та же деградация, что у `OFFSET`. Индекс для такого запроса должен быть построен со смешанными направлениями: `(price ASC, id DESC)`.

Ещё две ловушки. Nullable-колонка в ключе: `NULL` не сравнивается через `<`, и такие строки выпадут из выдачи, если не задать `NULLS FIRST/LAST` и не обработать их отдельной веткой условия; проще сделать колонку `NOT NULL`. Страница «назад»: условие и направление сортировки инвертируют (`>` и `ORDER BY ... ASC`), а полученные строки переворачивают в приложении.

## Стабильность сортировки

`ORDER BY` по неуникальному набору колонок не гарантирует порядок строк с равными ключами — он зависит от плана, и два одинаковых запроса могут вернуть равные строки в разном порядке. Для `OFFSET` это значит дубли и пропуски даже без конкурентных вставок, для keyset — потерю строк на границе. `LIMIT` без `ORDER BY` вообще не определяет, какие строки вернутся. Правило одно для обоих подходов: последним в `ORDER BY` всегда стоит уникальный ключ.

## Курсор в API

Наружу курсор отдают непрозрачным токеном: значения ключа последней строки сериализуют и кодируют в base64. Клиент не разбирает токен и не собирает его сам — это позволяет менять ключ сортировки, не ломая контракт. Если в курсор кладут что-то кроме значений сортировки, его подписывают HMAC, чтобы клиент не подменил содержимое. Вместе с ключом стоит хранить параметры сортировки и фильтра: курсор, полученный для `sort=price`, не должен приниматься для `sort=date`.

```csharp
public sealed record FeedCursor(DateTime CreatedAt, long Id);

static string Encode(FeedCursor c) =>
    Convert.ToBase64String(JsonSerializer.SerializeToUtf8Bytes(c));

static FeedCursor Decode(string token) =>
    JsonSerializer.Deserialize<FeedCursor>(Convert.FromBase64String(token))!;
```

Метку времени сериализуют с полной точностью. `timestamptz` хранит микросекунды; если курсор округлит их до секунд или миллисекунд, сравнение `<` на границе пропустит или повторит строки.

Признак «есть следующая страница» не требует подсчёта: запрашивают `LIMIT 21`, отдают 20, а наличие 21-й строки означает, что продолжение есть.

## Total count и его цена

«Всего 1 284 312 записей, страница 3 из 64 216» выглядит безобидно, но `count(*)` по большой выборке — полный проход по подходящим строкам: в PostgreSQL нет хранимого счётчика строк, потому что при MVCC у каждой транзакции своё множество видимых версий. Index Only Scan помогает только на провакуумированных страницах. Вариант `count(*) OVER ()` в том же запросе не дешевле — окну нужно досчитать всю выборку, прежде чем отдать первую строку.

Варианты по убыванию честности:

- не показывать общее число, только «ещё есть» через `LIMIT n + 1`;
- точное число до порога: `SELECT count(*) FROM (SELECT 1 FROM ... LIMIT 10001) s` и вывод «больше 10 000»;
- оценка планировщика: `pg_class.reltuples` для всей таблицы или `rows` из `EXPLAIN` для запроса с фильтром — дёшево, но неточно;
- счётчик, который поддерживает приложение или триггер, либо кэш с периодическим пересчётом.

## Keyset в EF Core

Сравнение кортежей в LINQ не выражается, поэтому в общем виде пишут развёрнутое условие:

```csharp
var query = db.Posts
    .Where(p => p.Status == PostStatus.Published);

if (cursor is not null)
{
    query = query.Where(p =>
        p.CreatedAt < cursor.CreatedAt ||
        (p.CreatedAt == cursor.CreatedAt && p.Id < cursor.Id));
}

var page = await query
    .OrderByDescending(p => p.CreatedAt)
    .ThenByDescending(p => p.Id)
    .Take(pageSize + 1)
    .AsNoTracking()
    .ToListAsync(ct);

var hasNext = page.Count > pageSize;
if (hasNext) page.RemoveAt(pageSize);
```

Такой `OR` переходит в SQL как есть, и для однонаправленной сортировки его стоит проверить в `EXPLAIN`: если условие ушло в `Filter`, добавляют избыточное `p.CreatedAt <= cursor.CreatedAt`, как в SQL-примере выше. Провайдер Npgsql умеет транслировать сравнение кортежей через `EF.Functions.LessThan(ValueTuple.Create(...), ValueTuple.Create(...))` в `(a, b) < (x, y)`. Есть и готовые библиотеки вроде `MR.EntityFrameworkCore.KeysetPagination`. Что EF Core делает с LINQ до SQL, разобрано в статье `IEnumerable vs IQueryable` раздела про язык.

## Большие таблицы: выборка батчами

Фоновые задачи — бэкфилл, реиндексация в поисковый движок, выгрузка событий в брокер — обходят таблицу целиком, и `OFFSET` там особенно вреден: каждый следующий батч дороже предыдущего, а параллельные вставки сдвигают окно. Правильный паттерн — keyset по первичному ключу с сохранением чекпоинта:

```sql
SELECT id, payload
FROM events
WHERE id > @last_id
ORDER BY id
LIMIT 1000;
```

После обработки батча последний `id` записывают в таблицу прогресса, и при падении задача продолжает с него, а не с нуля. Каждый батч — короткий запрос и короткая транзакция.

Альтернатива — серверный курсор (`DECLARE ... CURSOR` внутри транзакции) или потоковое чтение одного большого `SELECT` через `NpgsqlDataReader` либо `AsAsyncEnumerable()` в EF Core. Это удобно и не держит всё в памяти, но означает одну транзакцию на всё время выгрузки. Её снимок удерживает горизонт видимости, vacuum не может удалить мёртвые версии строк во всей базе, и на часовой выгрузке горячие таблицы начинают пухнуть. Для обходов на минуты и часы батчи с чекпоинтом надёжнее.

Тот же принцип для изменений: обновлять и удалять пачками по несколько тысяч строк с коммитом после каждой, а не одним `UPDATE` на сотни миллионов. Блокировки остаются короткими, vacuum успевает чистить, реплики не отстают, прерванную операцию можно продолжить. В EF Core для этого подходит `ExecuteUpdateAsync` или `ExecuteDeleteAsync` по диапазону ключей. Остальное про жизнь с большими таблицами — индексы под каждый частый запрос, настройку autovacuum, `CREATE INDEX CONCURRENTLY` и разбиение на части — см. в статьях `Индексы: B-tree, GIN, BRIN`, `MVCC и vacuum` и `Партиционирование`.

## Что стоит ответить на собеседовании

`OFFSET N` заставляет PostgreSQL прочитать и выбросить N строк, поэтому время растёт с номером страницы, а вставки между запросами дают дубли и пропуски. Keyset-пагинация продолжает со значения ключа последней строки: `WHERE (created_at, id) < (@x, @y) ORDER BY created_at DESC, id DESC LIMIT 20` с индексом `(created_at, id)` читает ровно одну страницу на любой глубине и стабильна при вставках, но не умеет переходить на страницу N. Ключ сортировки обязан быть уникальным, для этого добавляют `id` как tie-breaker.

Сильный ответ добавит детали: сравнение кортежей работает только при одном направлении сортировки, при смешанном нужно развёрнутое условие с избыточным диапазоном, иначе индекс не сузит скан; nullable-колонки в ключе ломают сравнение; курсор в API делают непрозрачным токеном с полной точностью времени; точный `count(*)` дорог из-за MVCC и заменяется на `LIMIT n + 1`, порог или оценку. И про большие таблицы: выгрузки и бэкфиллы идут keyset-батчами по `id` с чекпоинтом и короткими транзакциями, а не через `OFFSET` или одну многочасовую транзакцию, удерживающую vacuum.
