PostgreSQL хранит на сервере не только данные, но и код: функции, процедуры и представления. Для .NET-разработчика это обычно не место для бизнес-логики, а инфраструктура — триггеры, индексы по выражению, пакетные миграции данных, отчётные витрины. На собеседовании проверяют, понимает ли кандидат, как этот код влияет на план, транзакции и сопровождение.

Термин «хранимая процедура» коварен: до PG 11 процедур не было, и так называли функции. Привычка из SQL Server, где процедура возвращает result set и служит API к базе, в PostgreSQL не переносится.

## Функция: значение внутри выражения

Функция принимает аргументы и возвращает значение: скаляр, составной тип, набор строк (`SETOF`, `RETURNS TABLE`) или `void`. Главное её свойство — она вызывается внутри SQL-выражения: в `SELECT`, `WHERE`, `DEFAULT`, `CHECK`, в определении индекса, как триггер.

```sql
CREATE FUNCTION recent_orders(p_customer bigint, p_limit int)
RETURNS TABLE (id bigint, created_at timestamptz, total numeric)
LANGUAGE sql STABLE
AS $$
    SELECT id, created_at, total FROM orders
    WHERE customer_id = p_customer
    ORDER BY created_at DESC
    LIMIT p_limit
$$;

SELECT * FROM recent_orders(42, 10);
```

Функция всегда выполняется в транзакции вызывающего оператора. `COMMIT` внутри неё невозможен, а ошибка откатывает весь оператор, из которого её вызвали.

## SQL против PL/pgSQL

Язык функции определяет, что сможет сделать планировщик. Простую функцию на `LANGUAGE sql` из одного `SELECT` он может **инлайнить**: подставить тело в вызывающий запрос и оптимизировать как подзапрос — с проталкиванием условий, индексами и нормальными оценками строк. Табличная функция для этого должна быть `STABLE` или `IMMUTABLE` и без `SECURITY DEFINER`. Вызов `recent_orders(42, 10)` превращается в обычный запрос по индексу `(customer_id, created_at)`.

PL/pgSQL не инлайнится никогда — для планировщика это чёрный ящик с числом строк из атрибута `ROWS` (по умолчанию 1000 для set-returning функций), из-за чего соединение с ней легко получает неверный метод. Запросы внутри PL/pgSQL кэшируют планы в сессии и могут перейти на generic-план, как описано в статье `EXPLAIN и план запроса`; динамический `EXECUTE` планируется каждый раз. Правило: функции, которые только возвращают данные, пишут на `LANGUAGE sql`, а PL/pgSQL берут, когда нужны переменные, ветвление, циклы, исключения или динамический SQL. С PG 14 у SQL-функций есть тело `BEGIN ATOMIC ... END`: оно разбирается при создании, и зависимости от таблиц отслеживаются.

## Категория изменчивости и план

Каждая функция помечена одной из трёх категорий, и это обещание планировщику, которое он не проверяет.

| Категория | Обещание | Что разрешает планировщику |
| --- | --- | --- |
| `VOLATILE` (по умолчанию) | может менять данные, результат может различаться при каждом вызове | ничего: вызов для каждой строки |
| `STABLE` | не пишет, результат постоянен в пределах одного оператора | использовать результат как ключ индексного поиска |
| `IMMUTABLE` | результат зависит только от аргументов, всегда | вычислить при планировании, использовать в индексе по выражению |

`now()` — `STABLE`, поэтому в `WHERE created_at > now() - interval '1 day'` значение вычисляется один раз и становится `Index Cond`. Обёртка над ним в собственной функции без пометки получит `VOLATILE`, условие уйдёт в `Filter`, и индекс не сработает — частая причина Seq Scan.

Ошибка в обратную сторону опаснее. Если функция, объявленная `IMMUTABLE`, читает таблицу или зависит от `TimeZone`, индекс по выражению построится, но после изменения данных или настроек начнёт возвращать неверные результаты. Корректный пример:

```sql
CREATE FUNCTION normalize_phone(text) RETURNS text
LANGUAGE sql IMMUTABLE PARALLEL SAFE
AS $$ SELECT regexp_replace($1, '\D', '', 'g') $$;

CREATE INDEX customers_phone_norm_idx ON customers (normalize_phone(phone));
```

По умолчанию функция ещё и `PARALLEL UNSAFE`: её появление в запросе отключает параллельный план целиком, поэтому чистые функции помечают `PARALLEL SAFE`. `SECURITY DEFINER` выполняет функцию с правами владельца и без `SET search_path` в определении становится дырой: вызывающий подменит объекты через свою схему.

## Процедура: транзакции внутри

Процедура (`CREATE PROCEDURE`, PG 11+) вызывается только отдельной командой `CALL`, не участвует в выражениях и не возвращает набор строк — результат можно получить через параметры `INOUT`, а с PG 14 и `OUT`, одной строкой. Зато она умеет то, чего не умеет функция: выполнять `COMMIT` и `ROLLBACK` по ходу работы. После `COMMIT` автоматически начинается новая транзакция.

```sql
CREATE PROCEDURE backfill_status(batch int DEFAULT 10000)
LANGUAGE plpgsql AS $$
DECLARE last_id bigint := 0; max_id bigint;
BEGIN
    SELECT max(id) INTO max_id FROM orders;
    WHILE last_id < max_id LOOP
        UPDATE orders SET status_v2 = status
        WHERE id > last_id AND id <= last_id + batch;
        last_id := last_id + batch;
        COMMIT;
    END LOOP;
END $$;

CALL backfill_status(5000);
```

Каждая пачка фиксируется отдельно: блокировки отпускаются, vacuum может чистить обработанную часть, сбой на середине не откатывает сделанное. В функции это была бы одна транзакция на всю таблицу — с блокировками до конца и раздуванием из статьи `MVCC и vacuum`.

`COMMIT` в процедуре работает, только если `CALL` выполнен вне явного блока транзакции, иначе — ошибка `invalid transaction termination`. Нельзя коммитить внутри блока с `EXCEPTION`, а процедура с `SECURITY DEFINER` или `SET`-параметрами в определении транзакциями не управляет. Для .NET это значит: никакого `BeginTransaction` вокруг вызова, а из миграции EF Core, которая по умолчанию транзакционна, — только с `suppressTransaction: true`.

```csharp
await using var cmd = new NpgsqlCommand("CALL backfill_status($1)", conn);
cmd.Parameters.AddWithValue(5000);
await cmd.ExecuteNonQueryAsync();
```

Итог сравнения: нужно значение в запросе, индексе, ограничении или триггере — функция; долгая операция с промежуточными фиксациями — процедура. Триггеры всегда используют функции с `RETURNS trigger`; `EXECUTE PROCEDURE` в `CREATE TRIGGER` — исторический синоним `EXECUTE FUNCTION`. Volatility, `PARALLEL` и инлайнинг к процедурам неприменимы.

## Когда логику оправдано держать в базе

PL/pgSQL уместен, когда процедурный код должен быть рядом с данными и задача не решается одним запросом: триггеры (`updated_at`, аудит, денормализованные счётчики), пакетная обработка с коммитами из `pg_cron` или миграции, цепочка зависимых запросов, где важно убрать round trip-ы и укоротить транзакцию, обслуживание через динамический SQL — создание партиций, массовые `ALTER` — с `format('%I')` и `USING` вместо конкатенации.

Для бизнес-логики .NET-команды это обычно плохой выбор. Код в базе труднее тестировать и отлаживать: его нет в стеке исключения, точку останова не поставить, версия меняется только миграцией, а откат релиза приложения не откатывает функцию. Логика расползается между C# и SQL. Частые анти-паттерны: цикл `FOR r IN SELECT ... LOOP UPDATE ... WHERE id = r.id` — тот же N+1 внутри сервера вместо одного `UPDATE ... FROM`; блок `BEGIN ... EXCEPTION` в цикле — каждый вход создаёт подтранзакцию, что заметно тормозит на миллионе строк. Разумный компромисс: триггеры и инфраструктурные процедуры — в PL/pgSQL, функции чтения — на `LANGUAGE sql`, бизнес-правила — в сервисах.

## Представление: сохранённый запрос

Обычный `VIEW` хранит только текст запроса. При обращении планировщик раскрывает его как подзапрос и оптимизирует вместе с внешним запросом, проталкивая условия внутрь:

```sql
CREATE VIEW active_customers AS
SELECT id, name, email FROM customers WHERE deleted_at IS NULL;

SELECT * FROM active_customers WHERE id = 42;
```

Это выполнится как запрос к `customers` с обоими условиями и индексом по `id`, так что представление само по себе запрос не ускоряет и не замедляет. Исключение — агрегаты, `DISTINCT`, оконные функции или `LIMIT` внутри: не всякое внешнее условие проходит сквозь них (подробнее — в статье `Подзапросы и CTE`).

Представления скрывают сложные соединения за стабильным контрактом, дают доступ к части данных вместо таблицы (`security_barrier`, а с PG 15 — `security_invoker`, чтобы права проверялись у вызывающего) и сохраняют совместимость при рефакторинге схемы. Простые представления над одной таблицей автоматически обновляемые: через них работают `INSERT`, `UPDATE`, `DELETE`.

## Материализованное представление: сохранённый результат

`MATERIALIZED VIEW` выполняет запрос и сохраняет результат на диск как таблицу. Чтение идёт из снимка, на который можно строить собственные индексы, а данные обновляются только явной командой.

```sql
CREATE MATERIALIZED VIEW daily_sales AS
SELECT date_trunc('day', created_at) AS day, product_id,
       sum(qty) AS qty, sum(total) AS revenue
FROM orders
WHERE status = 'paid'
GROUP BY 1, 2;

CREATE UNIQUE INDEX daily_sales_day_product_uq ON daily_sales (day, product_id);

REFRESH MATERIALIZED VIEW CONCURRENTLY daily_sales;
```

Обычный `REFRESH` пересчитывает содержимое целиком под `ACCESS EXCLUSIVE` — все чтения ждут. `REFRESH ... CONCURRENTLY` берёт только `EXCLUSIVE`: чтения идут по старым данным, ждёт лишь параллельный refresh. Он считает результат во временную таблицу, сравнивает со старым и применяет разницу, а строки сопоставляет по уникальному индексу — только по колонкам, без выражений и `WHERE`. Без такого индекса команда падает с ошибкой; ещё одно условие — представление уже заполнено. При больших изменениях `CONCURRENTLY` медленнее обычного и оставляет мёртвые строки для vacuum.

Автоматического и инкрементального обновления в ядре нет: refresh запускают по расписанию (`pg_cron`, фоновая задача приложения), и он пересчитывает всё. Агрегат за всю историю, обновляемый раз в пять минут, однажды начнёт считаться дольше пяти минут. Время последнего обновления в каталогах не хранится — его пишут в отдельную таблицу. В EF Core такое представление мапят как keyless-сущность через `ToView("daily_sales")`, а создают и обновляют сырым SQL.

## View или materialized view

Решает требование к актуальности. Нужны строго свежие данные — обычное представление, а ускорять при необходимости индексы базовых таблиц. Допустима задержка в минуты или часы при тяжёлом запросе — материализованное с регулярным `REFRESH CONCURRENTLY`. Нужны и свежесть, и скорость на больших объёмах — таблица-агрегат, которую инкрементально обновляют триггеры или обработчик событий.

## Что стоит ответить на собеседовании

Функция возвращает значение и вызывается внутри SQL-выражения, всегда в транзакции вызывающего; процедура (PG 11+) вызывается через `CALL` и может делать `COMMIT` внутри, если её не вызвали в явной транзакции. Категория изменчивости — обещание планировщику: `VOLATILE` по умолчанию вызывается на каждую строку и не годится для индексного поиска, `STABLE` можно использовать как ключ индекса, `IMMUTABLE` — в индексе по выражению. Обычное представление — сохранённый запрос, который раскрывается в вызывающий и сам по себе ничего не ускоряет; материализованное — сохранённый результат со своими индексами, актуальный на момент последнего `REFRESH`.

Сильный ответ объяснит, что SQL-функции инлайнятся, а PL/pgSQL — чёрный ящик с `ROWS 1000` и кэшем планов, чем опасна ложная пометка `IMMUTABLE` и почему функция без пометки ломает индекс. Покажет пакетную процедуру с коммитами и предупредит про `BeginTransaction` и транзакционные миграции EF Core. Назовёт требование уникального индекса для `REFRESH CONCURRENTLY` и разницу блокировок. И обозначит позицию: PL/pgSQL — для триггеров, обслуживания и пакетных операций, а бизнес-логика живёт в приложении, где её можно тестировать и откатывать вместе с релизом.
