`jsonb` превращает PostgreSQL в гибрид реляционной и документной базы: рядом с типизированными колонками лежит документ произвольной структуры, к которому можно строить запросы и индексы. На собеседовании проверяют три вещи: разницу между `json` и `jsonb`, какой индекс обслужит конкретный запрос и какова цена — от переписывания всего документа при обновлении одного ключа до отсутствия статистики по полям.

## json и jsonb

`json` хранит документ как текст ровно в том виде, в каком он пришёл, и разбирает его при каждом обращении. `jsonb` разбирает документ один раз при записи и хранит бинарное дерево: пробелы отбрасываются, ключи сортируются, из дубликатов остаётся последний.

```sql
SELECT '{"b": 1, "a": 2, "a": 3}'::json;
SELECT '{"b": 1, "a": 2, "a": 3}'::jsonb;
```

Первый запрос вернёт строку как есть, второй — `{"a": 3, "b": 1}`. Запись в `jsonb` чуть дороже из-за парсинга, зато чтение и операторы быстрее, и только у `jsonb` есть операторы содержания и существования ключа, GIN-индексы и равенство: у `json` нет оператора `=`, поэтому по нему не работают `DISTINCT`, `GROUP BY` и уникальность. Числа `jsonb` хранит как `numeric` — без потери точности, `1.00` остаётся `1.00`, но при сравнении равно `1.0`.

`json` оправдан, когда нужно сохранить исходный текст байт в байт: например, тело webhook-а для проверки подписи — переставленные ключи её сломают. Но и тогда часто выбирают `text` для сырого тела плюс `jsonb` для запросов. Во всех остальных случаях берут `jsonb`.

## Операторы

```sql
CREATE TABLE events (
    id bigserial PRIMARY KEY,
    type text NOT NULL,
    payload jsonb NOT NULL
);

SELECT payload -> 'items' -> 0          AS first_item,
       payload ->> 'order_id'           AS order_id_text,
       payload #>> '{items,0,sku}'      AS first_sku
FROM events
WHERE payload @> '{"source": "web"}'
  AND payload ? 'promo';
```

`->` возвращает значение по ключу или индексу массива как `jsonb`, `->>` — как `text`; `#>` и `#>>` делают то же по пути. `@>` проверяет, что левый документ содержит правый: `'{"items": [{"sku": "A1"}]}'` найдёт заказ, где среди позиций есть `A1`, независимо от остальных полей. `?`, `?|`, `?&` проверяют наличие ключа верхнего уровня — одного, любого из списка или всех. Для изменения есть `||` (слияние верхнего уровня), `-` и `#-` (удаление ключа и пути) и `jsonb_set`; с PG 14 работает подписка `payload['status']`, в том числе в `UPDATE ... SET payload['status'] = '"paid"'`.

Типовые ловушки. `->>` всегда даёт `text`, поэтому сравнение чисел и дат требует явного приведения: `(payload ->> 'qty')::int > 1`, иначе `'10' < '9'`. Даты внутри JSON — просто строки. JSON `null` не равен SQL `NULL`: `'{"a": null}'::jsonb -> 'a'` вернёт значение `null` типа `jsonb`, а `->>` — SQL `NULL`, и `payload ? 'a'` при этом истинно.

Структуру документа можно частично защитить ограничениями: `CHECK (payload ? 'order_id')`, `CHECK (jsonb_typeof(payload -> 'items') = 'array')`. С PG 16 есть предикат `IS JSON OBJECT`, но схему JSON целиком ядро не проверяет.

## jsonpath

С PG 12 поддерживается язык путей SQL/JSON. Он полезен, когда условие касается элементов вложенного массива и через `@>` не выражается — например, сравнение, а не равенство:

```sql
SELECT id FROM events
WHERE payload @? '$.items[*] ? (@.qty > 1)';

SELECT jsonb_path_query(payload, '$.items[*].sku') FROM events WHERE id = 1;
```

`@?` проверяет, что путь вернул хотя бы один элемент, `@@` — что предикат пути истинен; функции `jsonb_path_exists` и `jsonb_path_query` делают то же с параметрами. Оба оператора поддерживаются GIN-индексом, но индекс помогает только с той частью пути, которая сводится к проверке ключей и равенств; условие `@.qty > 1` всё равно проверяется перечитыванием строки. С PG 17 добавились стандартные `JSON_TABLE`, `JSON_VALUE`, `JSON_QUERY` и `JSON_EXISTS`: `JSON_TABLE` разворачивает массив документа в строки с типизированными колонками.

## Индексы: GIN по документу или B-tree по ключу

Выбор индекса определяется формой запросов, а не типом колонки. Вариантов три.

```sql
CREATE INDEX events_payload_gin ON events USING gin (payload);

CREATE INDEX events_payload_path_gin ON events USING gin (payload jsonb_path_ops);

CREATE INDEX events_order_id_idx ON events (((payload ->> 'order_id')::bigint));
ANALYZE events;
```

GIN с классом `jsonb_ops` (по умолчанию) индексирует каждый ключ и каждое значение отдельно и поддерживает `@>`, `?`, `?|`, `?&`, `@?`, `@@`. GIN с `jsonb_path_ops` хранит хеш всего пути от корня до значения: индекс заметно меньше и точнее на `@>`, но операторы существования ключа `?`, `?|`, `?&` не поддерживает. Если запросы — только `@>` и jsonpath, лучше `jsonb_path_ops`. Как устроен GIN, почему он работает только через Bitmap Scan и чем платит на записи — в статье `Индексы: B-tree, GIN, BRIN`.

Главная ловушка — GIN не обслуживает `->>` с `=`:

```sql
SELECT * FROM events WHERE payload ->> 'type' = 'order_created';
```

Такое условие не входит ни в один из классов операторов GIN, и индекс по `payload` будет проигнорирован. Решения два: переписать на `payload @> '{"type": "order_created"}'` или создать B-tree по выражению `(payload ->> 'type')`. B-tree по выражению — правильный выбор, когда фильтруют по одному-двум известным полям на равенство, диапазон или сортируют: он компактнее GIN, умеет порядок и `LIMIT`. Выражение в запросе должно совпадать с индексом структурно, вплоть до приведения типа, а функция должна быть `IMMUTABLE`. Приведение `text` к `bigint` подходит, к `timestamptz` — нет: результат зависит от часового пояса сессии, и такой индекс создать нельзя.

После создания индекса по выражению нужен `ANALYZE`: только тогда у планировщика появляется статистика по значениям выражения. Без неё условия по ключам JSON оцениваются захардкоженными селективностями, и ошибка оценки ломает план так, как описано в статье `EXPLAIN и план запроса`. Если поле стало важным для запросов, надёжнее вынести его в настоящую колонку, не меняя код записи, — через `GENERATED ALWAYS AS ((payload ->> 'order_id')::bigint) STORED` (PG 12+; виртуальные generated-колонки появились только в PG 18).

## GiST: индекс для данных без линейного порядка

На этом месте часто спрашивают про GiST — для сравнения с GIN и B-tree. GiST (Generalized Search Tree) — сбалансированное дерево, во внутренних узлах которого лежат не отсортированные ключи, а ограничивающие предикаты: например, прямоугольник, покрывающий все объекты поддерева. Поддеревья могут перекрываться, поэтому поиск иногда спускается в несколько ветвей. Отвечает GiST не на «равно или больше», а на «пересекается», «содержит», «ближайший к».

```sql
CREATE EXTENSION btree_gist;

ALTER TABLE bookings
ADD CONSTRAINT bookings_no_overlap
EXCLUDE USING gist (room_id WITH =, during WITH &&);
```

Типичные применения: диапазоны (`tstzrange`, `daterange` с операторами `&&`, `@>`, `<@`), exclusion constraints вроде «брони одной комнаты не пересекаются по времени» — проверка атомарна при конкурентных вставках, чего на уровне приложения надёжно не добиться, — KNN-поиск `ORDER BY location <-> point(...) LIMIT 10` без сортировки всей таблицы, геометрия PostGIS. `btree_gist` нужен, чтобы включить в индекс скалярную колонку с `=`. GiST бывает lossy и перепроверяет строки в heap; для полнотекстового поиска и триграмм он меньше GIN, но медленнее на чтение. Для `jsonb` встроенного класса операторов GiST нет — документы индексируют GIN или B-tree по выражению.

## Цена обновления: вся строка и TOAST

Документ в `jsonb` — одно значение, и изменить один ключ «на месте» нельзя. `jsonb_set` строит новый документ целиком, а MVCC создаёт новую версию всей строки; старая остаётся до vacuum, подробнее — в статье `MVCC и vacuum`. Если документ больше примерно 2 КБ, он уходит в TOAST: сжимается и режется на куски в отдельной таблице. Тогда каждое обновление счётчика внутри документа в 50 КБ заново сжимает и записывает 50 КБ в TOAST и порождает соответствующий объём WAL.

Есть и косвенная цена. GIN по `payload` означает, что любое изменение документа меняет индексированную колонку, и обновление не может быть HOT: в индексы пишутся новые записи. Чтение тоже не бесплатно — выборка одного ключа из TOAST-документа требует достать и распаковать его целиком.

Практический вывод: часто меняющиеся поля — статусы, счётчики, даты последнего изменения — держат в обычных колонках, а в `jsonb` оставляют то, что пишется один раз и читается целиком.

## Когда JSONB, а когда колонки

`jsonb` уместен для атрибутов с переменной структурой (характеристики товаров разных категорий), сырых payload-ов внешних систем и событий, настроек и метаданных, по которым редко фильтруют. Колонки нужны всему, по чему фильтруют, соединяют и сортируют: у них есть типы, `NOT NULL`, `CHECK`, внешние ключи и полноценная статистика. Внешний ключ на значение внутри JSON не поставить, и данные со ссылочной целостностью в документ не кладут. Если один и тот же ключ `->>` повторяется в `WHERE`, `JOIN` и `ORDER BY` — это колонка, спрятанная в документ.

## EF Core и Npgsql

В EF Core документ мапится через owned-типы и `ToJson()`; в провайдере Npgsql это поддерживается с версии 8 и заменило старый способ — POCO-свойство с `[Column(TypeName = "jsonb")]`. Для слабо типизированных данных можно маппить свойство на `JsonDocument` или `string`.

```csharp
modelBuilder.Entity<Order>()
    .OwnsOne(o => o.Details, d =>
    {
        d.ToJson();
        d.OwnsMany(x => x.Items);
    });

var paid = await db.Orders
    .Where(o => o.Details.Status == "paid")
    .ToListAsync();
```

LINQ по свойству документа транслируется в выражение с `->>` и сравнением, а не в `@>`, поэтому GIN по колонке такому запросу не поможет — нужен B-tree по тому же выражению, которое генерирует провайдер. Индекс по выражению создают в миграции через `migrationBuilder.Sql(...)`, предварительно посмотрев SQL через `ToQueryString()` или логи. На уровне ADO.NET Npgsql с версии 8 требует явного `EnableDynamicJson()` на `NpgsqlDataSourceBuilder`, чтобы сериализовать произвольные POCO в `jsonb` через System.Text.Json.

## Что стоит ответить на собеседовании

`jsonb` хранит JSON в разобранном бинарном виде: без пробелов, с отсортированными ключами и без дубликатов, и поэтому быстрее на чтение, поддерживает `@>`, `?`, jsonpath, равенство и GIN-индексы; `json` хранит исходный текст и нужен, только когда важен текст байт в байт. Для произвольных фильтров по документу используют GIN — `jsonb_ops`, если нужен `?`, и более компактный `jsonb_path_ops`, если хватает `@>`; для конкретного поля — B-tree по выражению. Часто фильтруемые и связанные внешними ключами данные держат в колонках.

Сильный ответ объяснит, почему GIN не помогает `payload ->> 'status' = 'x'` и как это проявляется в EF Core, зачем `ANALYZE` после индекса по выражению и почему `::timestamptz` в нём запрещён, что обновление одного ключа переписывает всю строку и TOAST-документ, порождает WAL и при GIN-индексе лишает обновление HOT. И сможет отличить GIN от GiST: первый — инвертированный индекс по элементам составного значения, второй — дерево ограничивающих предикатов для диапазонов, геометрии, KNN и exclusion constraints.
