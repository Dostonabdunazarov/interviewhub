Уровень изоляции отвечает на вопрос, что транзакция видит из работы параллельных транзакций. Стандарт SQL описывает четыре уровня через запрещённые аномалии, но в PostgreSQL их реализация опирается на MVCC и снимки, поэтому поведение отличается и от стандарта, и от других СУБД. По умолчанию в PostgreSQL — **Read Committed**, а реально различных уровней три: Read Uncommitted ведёт себя как Read Committed.

## Аномалии и таблица уровней

Четыре классические аномалии:

- **dirty read** — видны незакоммиченные изменения другой транзакции;
- **non-repeatable read** — повторное чтение той же строки вернуло другое значение, потому что её изменили и закоммитили;
- **phantom read** — повторный запрос с тем же условием вернул другой набор строк, потому что подходящие строки вставили или удалили;
- **serialization anomaly** — результат параллельных транзакций не совпадает ни с одним последовательным порядком их выполнения.

| Уровень | Dirty read | Non-repeatable read | Phantom read | Serialization anomaly |
| --- | --- | --- | --- | --- |
| Read Uncommitted | стандарт допускает, в PG нет | возможно | возможно | возможно |
| Read Committed | нет | возможно | возможно | возможно |
| Repeatable Read | нет | нет | стандарт допускает, в PG нет | возможно |
| Serializable | нет | нет | нет | нет |

Dirty read в PostgreSQL невозможен в принципе: незакоммиченная версия строки лежит в таблице, но правила видимости из статьи `MVCC и vacuum` её не показывают никому, кроме автора. Специально нарушать собственную модель ради «грязного» чтения смысла нет — читатели и так не ждут писателей. Аналога `WITH (NOLOCK)` из SQL Server нет и не нужно.

Уровень задаётся на транзакцию или по умолчанию для базы:

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;
SHOW transaction_isolation;
ALTER DATABASE app SET default_transaction_isolation = 'repeatable read';
```

В Npgsql это `connection.BeginTransaction(IsolationLevel.RepeatableRead)`, в EF Core — `Database.BeginTransaction(IsolationLevel.Serializable)`. Как EF Core управляет транзакциями вокруг `SaveChanges`, разбирается в разделе про EF Core.

## Read Committed: снимок на каждый оператор

На Read Committed каждый **оператор** берёт свежий снимок и видит всё, что закоммичено до его начала. Два одинаковых `SELECT` в одной транзакции могут вернуть разное — это разрешённый non-repeatable read.

Интереснее, что происходит при конфликте записи:

```sql
UPDATE accounts SET balance = balance - 100
WHERE id = 1 AND balance >= 100;
```

1. Оператор находит строку по своему снимку.
2. Если её уже меняет другая транзакция — ждёт её завершения.
3. Если та откатилась — работает со старой версией.
4. Если закоммитилась — берёт **новую версию** строки, заново проверяет `WHERE` и, если условие всё ещё выполняется, обновляет её.

Этот механизм повторной проверки (EvalPlanQual) делает атомарные операции безопасными: списания не теряются, баланс не уходит в минус. Подвох в том, что перепроверяется только сама обновляемая строка — подзапросы и соединения по новому снимку не перевычисляются, и сложный `UPDATE ... FROM` при конкурентных изменениях может дать неочевидный результат.

Где Read Committed подводит — read-modify-write в коде приложения:

```csharp
var balance = await db.QuerySingleAsync<decimal>("SELECT balance FROM accounts WHERE id = 1");
await db.ExecuteAsync("UPDATE accounts SET balance = @b WHERE id = 1", new { b = balance - 100 });
```

Две параллельные операции прочитают одно и то же значение и запишут одно и то же. Одно списание пропало — это **lost update**. Решения на Read Committed: перенести вычисление в SQL (`SET balance = balance - 100`), взять `SELECT ... FOR UPDATE` перед изменением или проверять версию при записи — оптимистичная блокировка, в PostgreSQL для неё удобна системная колонка `xmin`. Подробнее о блокировках — в статье `Блокировки и deadlock`.

## Repeatable Read: снимок на всю транзакцию

На Repeatable Read все запросы транзакции видят **один снимок** — взятый на **первом операторе**, а не на `BEGIN`. Это snapshot isolation, и он строже стандарта: фантомов тоже нет, потому что новые строки в старый снимок не попадают.

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT count(*) FROM orders WHERE status = 'new';
SELECT count(*) FROM orders WHERE status = 'new';
COMMIT;
```

Оба запроса вернут одно и то же, даже если заказы вставляют параллельно.

Конфликт записи здесь разрешается иначе. Переключиться на новую версию строки, как на Read Committed, нельзя — это нарушило бы снимок. Поэтому транзакция, которая пытается изменить строку, изменённую после её снимка уже закоммиченной транзакцией, получает ошибку:

```text
ERROR:  could not serialize access due to concurrent update
SQLSTATE: 40001
```

Следствие: lost update невозможен, но приложение **обязано** повторять транзакцию при `40001`. Повторять нужно всю транзакцию с перечитыванием данных, а не последний оператор.

Это заметное отличие от MySQL InnoDB, где Repeatable Read — уровень по умолчанию, а `UPDATE` работает с последней закоммиченной версией без ошибки, так что lost update там возможен без `FOR UPDATE`.

## Write skew: чего Repeatable Read не ловит

Write skew — аномалия, где каждая транзакция по отдельности корректна, но вместе они нарушают инвариант. Шаблон: прочитать набор строк, проверить условие и записать **в другую** строку.

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT count(*) FROM doctors WHERE on_call;
UPDATE doctors SET on_call = false WHERE id = 1;
COMMIT;
```

Правило «на дежурстве хотя бы один врач». Две транзакции одновременно видят двух дежурных, каждая снимает своего — дежурных ноль. Конфликта записи нет: изменены разные строки. Та же картина у «не больше трёх активных заказов на клиента», «переговорка свободна в это время», «логин свободен» без уникального индекса.

Закрыть write skew без Serializable можно так:

- **ограничение в схеме** — уникальный, в том числе частичный, индекс или exclusion constraint для интервалов; самый надёжный вариант;
- **материализовать конфликт** — заставить транзакции писать в одну строку: `SELECT ... FROM customers WHERE id = 5 FOR UPDATE` сериализует все операции по клиенту;
- **advisory lock** по ключу инварианта: `pg_advisory_xact_lock(5)`.

Блокировка прочитанных строк через `FOR UPDATE` работает только для существующих строк: вставляемый фантом заблокировать нельзя, его ещё нет.

## Serializable: SSI

Serializable гарантирует, что результат совпадает с каким-то последовательным порядком выполнения. В PostgreSQL он реализован как Serializable Snapshot Isolation: снимок как на Repeatable Read плюс отслеживание зависимостей чтения-записи. На прочитанное ставятся предикатные блокировки `SIReadLock` — они ничего не блокируют, только запоминают «эта транзакция это читала». Когда складывается опасная структура зависимостей, одна из транзакций получает:

```text
ERROR:  could not serialize access due to read/write dependencies among transactions
```

Пример с врачами на Serializable безопасен: одна из двух транзакций откатится. Правила работы с этим уровнем:

- **ретраи обязательны**, и их больше, чем на Repeatable Read: SSI консервативен и бывает ложно положительным, особенно когда запросы читают через Seq Scan и блокировка ставится на всю таблицу;
- **все участники должны работать на Serializable** — транзакция на Read Committed проскальзывает мимо проверки;
- **транзакции должны быть короткими**;
- для долгих отчётов есть `SERIALIZABLE READ ONLY DEFERRABLE`: транзакция дожидается безопасного снимка и потом выполняется без риска отката.

## Ретраи в .NET

Ошибки `40001` (serialization failure) и `40P01` (deadlock) — штатное поведение, а не авария. В Npgsql они приходят как `PostgresException` с `SqlState`, и для них `IsTransient` равно `true`. Повторять нужно всю бизнес-операцию:

```csharp
for (var attempt = 1; ; attempt++)
{
    try
    {
        await using var tx = await conn.BeginTransactionAsync(IsolationLevel.Serializable, ct);
        await TransferAsync(conn, tx, from, to, amount, ct);
        await tx.CommitAsync(ct);
        return;
    }
    catch (PostgresException ex) when (ex.SqlState is "40001" or "40P01" && attempt < 5)
    {
        await Task.Delay(Random.Shared.Next(10, 50) * attempt, ct);
    }
}
```

Задержка с джиттером не даёт двум конфликтующим транзакциям снова столкнуться в ту же миллисекунду. В EF Core то же делает execution strategy (`EnableRetryOnFailure`), но с ручной транзакцией её нужно явно оборачивать в `strategy.ExecuteAsync`.

## Как выбирать

- **Read Committed** — дефолт для OLTP. Гонки закрываются атомарными `UPDATE ... SET x = x - 1 WHERE x >= 1`, уникальными ограничениями и точечными `FOR UPDATE`. Ретраи нужны только на deadlock.
- **Repeatable Read** — согласованная картина из нескольких запросов: отчёты, выгрузки (так работает `pg_dump`), защита от lost update без явных блокировок — при наличии ретраев.
- **Serializable** — сложные инварианты между строками и таблицами, которые хрупко закрывать руками. Цена — откаты под конкуренцией.

Общий минус более строгих уровней — длинный снимок держит горизонт vacuum, и под нагрузкой записи это bloat.

## Что стоит ответить на собеседовании

В PostgreSQL по умолчанию Read Committed: снимок на каждый оператор, повторное чтение может вернуть новое значение, а конфликтующий `UPDATE` ждёт и перепроверяет условие на новой версии строки. Repeatable Read — снимок на первом операторе транзакции, без неповторяющихся и фантомных чтений, конфликт записи даёт `40001`. Serializable — SSI поверх того же снимка с отслеживанием зависимостей чтения-записи. Dirty read невозможен ни на одном уровне благодаря MVCC.

Сильный ответ разберёт lost update при read-modify-write в коде и способы закрыть его на Read Committed, покажет write skew как аномалию, которую Repeatable Read пропускает, и предложит защиту: ограничение в схеме, блокировку родительской строки или Serializable. И подчеркнёт, что на уровнях выше Read Committed ретрай всей транзакции по `40001` — обязательная часть кода, а не обработка редкой ошибки.
