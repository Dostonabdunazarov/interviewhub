Индекс в PostgreSQL — отдельная структура рядом с таблицей, которая по значению ключа находит адреса строк. Встроенных типов шесть: B-tree, Hash, GiST, SP-GiST, GIN и BRIN. На собеседовании почти всегда спрашивают про три из них — B-tree как индекс по умолчанию, GIN для «составных» значений и BRIN для огромных таблиц, — и про то, почему подходящий на вид индекс не используется.

## Что индекс хранит и чем за него платят

Таблица в PostgreSQL называется heap: строки лежат в 8-килобайтных страницах без какого-либо порядка. Индекс хранит пары «ключ → TID», где TID (`ctid`) — физический адрес строки: номер страницы и позиция на ней. Найдя TID, PostgreSQL всё равно идёт в heap — не только за остальными колонками, но и чтобы проверить, видна ли эта версия строки текущей транзакции. Индекс видимость не хранит; почему так — в статье `MVCC и vacuum`.

Цена индекса — запись. Каждый `INSERT` добавляет запись во все индексы таблицы, а `UPDATE`, который не попал под HOT-оптимизацию, создаёт новую версию строки и тоже новые записи во всех индексах. Десять индексов на горячей таблице — это десятикратное усиление записи, больше WAL и больше работы для vacuum. Поэтому лишний индекс — не бесплатная страховка, а постоянный налог.

## B-tree: индекс по умолчанию

`CREATE INDEX` без `USING` строит B-tree — сбалансированное дерево с отсортированными ключами. Корень, внутренние страницы, листья; листья связаны в список, поэтому диапазон читается подряд без повторного спуска. Ветвление — сотни ключей на страницу, так что таблица в сотни миллионов строк укладывается в три-четыре уровня, а верхние почти всегда в кэше.

Отсортированность определяет всё, что B-tree умеет: равенство, диапазоны (`<`, `>`, `BETWEEN`), `IN`, префиксный `LIKE 'abc%'`, `ORDER BY` без отдельной сортировки, `MIN`/`MAX` и уникальность — `UNIQUE` поддерживает только B-tree. Индекс читается и в обратную сторону, так что для `ORDER BY created_at DESC` отдельный `DESC`-индекс не нужен.

```sql
CREATE INDEX orders_created_at_idx ON orders (created_at);

EXPLAIN SELECT * FROM orders
WHERE created_at >= now() - interval '1 day'
ORDER BY created_at;
```

```text
Index Scan using orders_created_at_idx on orders
  Index Cond: (created_at >= (now() - '1 day'::interval))
```

Здесь и дальше вывод `EXPLAIN` иллюстративный: стоимости и имена зависят от данных и версии. Важно, что узла `Sort` нет — строки пришли из индекса уже упорядоченными.

С PG 13 B-tree умеет дедупликацию: одинаковые ключи хранятся один раз со списком TID, и индексы по колонкам с малым числом значений стали заметно меньше. Ограничение размера ключа — около трети страницы, примерно 2,7 КБ, поэтому длинный текст целиком в B-tree не кладут.

## Составной индекс и правило ведущего префикса

Индекс `(a, b, c)` упорядочен лексикографически: сначала по `a`, внутри равных `a` — по `b`. Отсюда правило ведущего префикса:

| Условие | Как работает индекс `(a, b, c)` |
| --- | --- |
| `a = ?` | сужает поиск |
| `a = ? AND b = ?` | сужает поиск по обеим колонкам |
| `a = ? AND b > ?` | диапазон внутри одного `a` |
| `a = ? ORDER BY b` | отдаёт строки уже отсортированными |
| `b = ?` | плохо: подходящие записи разбросаны по всему индексу |
| `a > ? AND b = ?` | `b` проверяется фильтром, а не сужает диапазон |

Практическое правило порядка колонок: **сначала колонки с равенством, потом одна колонка с диапазоном или сортировкой**. Для «последних 20 заказов клиента» индекс `(customer_id, created_at)` даёт один спуск и 20 записей по листьям, а `(created_at, customer_id)` заставит перебрать заказы всех клиентов. Миф «самую селективную колонку — первой» для равенств почти не важен; важнее, какие ещё запросы сможет обслужить общий префикс. Отдельный индекс `(a)` рядом с `(a, b)` обычно лишний.

В PG 18 появился skip scan, который частично снимает ограничение при малом числе различных значений ведущей колонки. На 15–17 его нет, и рассчитывать на него не стоит.

## Частичный, по выражению, покрывающий

Поверх любого метода работают три модификатора, и они решают больше задач, чем выбор самого метода.

**Частичный индекс** строится только по строкам, подходящим под условие. Очередь из 50 тысяч `pending` среди 100 миллионов заказов получает крошечный индекс:

```sql
CREATE INDEX orders_pending_idx ON orders (created_at)
WHERE status = 'pending';

CREATE UNIQUE INDEX users_email_active_uq ON users (lower(email))
WHERE deleted_at IS NULL;
```

Второй пример выражает «один активный пользователь на email», чего обычным `UNIQUE` не сделать. Подвох: планировщик использует частичный индекс, только если может доказать, что условие запроса влечёт предикат индекса. `WHERE status = $1` в generic-плане такого доказательства не даёт — значение предиката лучше держать литералом.

**Индекс по выражению** хранит результат функции: `lower(email)`, `(payload->>'order_id')`. Выражение в запросе должно совпадать с выражением индекса структурно, а функция должна быть `IMMUTABLE`. Поэтому `created_at::date` над `timestamptz` проиндексировать нельзя — результат зависит от часового пояса сессии. После создания такого индекса нужен `ANALYZE`, иначе статистики по выражению нет.

**Покрывающий индекс** добавляет неключевые колонки в листья через `INCLUDE`, чтобы запрос мог обойтись без heap — это Index Only Scan:

```sql
CREATE INDEX orders_customer_total_idx ON orders (customer_id) INCLUDE (total);
```

Но Index Only Scan пропускает heap только для страниц, отмеченных all-visible в visibility map. Если таблица часто обновляется, а vacuum отстаёт, в плане растёт `Heap Fetches`, и выигрыш исчезает.

## GIN: инвертированный индекс

B-tree отвечает на вопрос «где строка с этим значением». GIN (Generalized Inverted Index) отвечает на обратный: «в каких строках встречается этот элемент». Как предметный указатель в книге — слово и список страниц. Внутри это B-tree по элементам, у каждого элемента — список TID. Подходит для значений, у которых много элементов: `jsonb`, массивы, `tsvector` для полнотекстового поиска, триграммы.

```sql
CREATE INDEX docs_payload_gin ON docs USING gin (payload jsonb_path_ops);
SELECT * FROM docs WHERE payload @> '{"status": "active"}';

CREATE INDEX posts_tags_gin ON posts USING gin (tags);
SELECT * FROM posts WHERE tags @> ARRAY['postgres'];

CREATE EXTENSION pg_trgm;
CREATE INDEX users_name_trgm ON users USING gin (name gin_trgm_ops);
SELECT * FROM users WHERE name ILIKE '%петров%';
```

Какие операторы поддерживаются, решает operator class. Для `jsonb` по умолчанию берётся `jsonb_ops`: он поддерживает и `@>`, и проверку наличия ключа `?`, но больше по размеру. `jsonb_path_ops` заметно меньше и быстрее на `@>`, но `?` не умеет. Частая ошибка — ждать от GIN помощи в `payload->>'status' = 'x'`: этот оператор GIN не обслуживает, нужен `@>` или отдельный B-tree по выражению.

У GIN нет обычного Index Scan, Index Only Scan и сортировки: в плане он всегда выглядит как `Bitmap Index Scan` под `Bitmap Heap Scan`. Главная его цена — запись: строка с 50 тегами порождает 50 записей в индексе. Чтобы смягчить это, по умолчанию включён `fastupdate`: новые элементы копятся в pending list (до `gin_pending_list_limit`, по умолчанию 4 МБ) и вливаются в дерево при vacuum или переполнении. Поиск обязан просматривать и этот список, а вставка, на которой список переполнился, получает всплеск задержки. Если это мешает, индекс создают с `fastupdate = off`.

## BRIN: сводка по диапазонам блоков

BRIN (Block Range Index) не хранит ссылку на каждую строку. Для каждого диапазона блоков — по умолчанию 128 страниц — он хранит сводку, обычно минимум и максимум колонки. Поиск отбирает диапазоны, чей `[min, max]` пересекается с условием, и читает их целиком, перепроверяя строки. Индекс получается в сотни и тысячи раз меньше B-tree.

```sql
CREATE INDEX events_created_brin ON events USING brin (created_at);
```

```text
Bitmap Heap Scan on events
  Recheck Cond: (created_at >= '2025-05-01' AND created_at < '2025-05-02')
  Rows Removed by Index Recheck: 18430
  Heap Blocks: lossy=1280
  ->  Bitmap Index Scan on events_created_brin
```

`lossy` здесь норма: индекс указывает на блоки, а не на строки. BRIN работает, только когда значения колонки коррелируют с физическим порядком строк, — в append-only таблицах логов, событий, метрик, где строки вставляются по времени. Проверить можно по `pg_stats.correlation`: близко к 1 или −1 — подходит, около нуля — бесполезен. Ломают BRIN обновления и вставки в освободившееся после `DELETE` место: старые даты перемешиваются с новыми. Новые диапазоны суммаризирует vacuum, а не вставка; параметр `autosummarize` по умолчанию выключен. С PG 14 есть классы `minmax_multi` (устойчивее к выбросам) и `bloom`.

## Остальные типы коротко

**Hash** — только равенство; с PG 10 журналируется в WAL и безопасен, но выигрывает у B-tree редко. **GiST** — для данных без линейного порядка: диапазоны (`&&`), геометрия, KNN-поиск «ближайшие к точке» и exclusion constraints вроде «брони одной комнаты не пересекаются по времени». **SP-GiST** — для неперекрывающихся разбиений: точки, `inet`, префиксы.

Создавать индекс на работающей большой таблице нужно через `CREATE INDEX CONCURRENTLY`: обычный `CREATE INDEX` берёт блокировку `SHARE` и останавливает запись на всё время построения. У `CONCURRENTLY` свои правила — нельзя внутри транзакции (в миграциях EF Core нужен `suppressTransaction: true`), а при сбое остаётся `INVALID`-индекс, который не читается, но обновляется. Подробнее о блокировках — в статье `Блокировки и deadlock`.

## Что стоит ответить на собеседовании

Индекс хранит ключ и адрес строки в heap, но не видимость, поэтому PostgreSQL почти всегда идёт в таблицу проверить версию строки; исключение — Index Only Scan по all-visible страницам. B-tree — отсортированное дерево для равенства, диапазонов, сортировки и уникальности; составной индекс работает по правилу ведущего префикса, и колонки равенства ставят перед колонкой диапазона. GIN — инвертированный индекс для `jsonb`, массивов, полнотекстового поиска и триграмм: дешёв на чтение «содержит», дорог на запись и работает только через bitmap. BRIN хранит min/max по диапазонам блоков, крошечный и полезен только при физической корреляции данных с порядком вставки.

Сильный ответ добавит цену индексов — усиление записи и потерю HOT-обновлений, — назовёт частичные, функциональные и покрывающие индексы как инструмент точнее выбора метода и объяснит типичные причины, по которым индекс не используется: функция над колонкой, неведущая колонка составного индекса, параметр против предиката частичного индекса, низкая селективность. Как это увидеть в плане — в статье `EXPLAIN и план запроса`.
