Сервис заказов — задача не про нагрузку, а про границы ответственности. Он владеет жизненным циклом заказа: создаёт его из корзины, фиксирует цены, ведёт статусы и сообщает оплате, складу и доставке о том, что произошло. Интервьюер проверяет три вещи: не создаётся ли второй заказ при повторном клике, как заказ договаривается со складом и оплатой без распределённой транзакции и что происходит, когда падает PostgreSQL, Redis или Kafka. Шаги разбора — как в `Как проходить дизайн-секцию`.

## Требования

Функциональные:

- создать заказ из корзины;
- получить заказ и историю заказов пользователя;
- отменить заказ;
- менять статус по событиям оплаты, склада и доставки.

Нефункциональные:

- заказ не теряется и не дублируется при повторном нажатии;
- создание быстрее 300 мс на p99;
- доступность 99.95%;
- история смены статусов хранится для поддержки и аудита.

Каталог, поиск, корзину и сам платёжный шлюз вслух выносим за скоуп: это соседние сервисы, с которыми заказ общается.

## Оценка нагрузки

Допущение — 1 млн заказов в день, история читается в 10–20 раз чаще, чем создаются заказы.

```text
запись:   1M / 86 400 ≈ 12 заказов/с, пик ×10 ≈ 120/с
чтение:   120 × 10–20 ≈ 1 200–2 400 RPS, берём ~2 000
объём:    ~2 KB на заказ с позициями → 2 GB/день ≈ 730 GB/год
```

Вывод из цифр: одна PostgreSQL с репликами держит это годами, шардирование на старте не нужно. Узкое место — не запись заказов, а чтение каталога и корзины, которое идёт вокруг. Методика — в `Оценка нагрузки и RPS`.

## API

```text
POST /api/orders
Idempotency-Key: 6f1c...e2
{ "cartId": "c-771", "addressId": "a-12", "paymentMethod": "card" }
→ 201 { "orderId": "...", "status": "pending" }

GET  /api/orders/{id}
GET  /api/orders?cursor=...&limit=20
POST /api/orders/{id}/cancel
```

Ключ идемпотентности генерирует клиент один раз на попытку оформления. Повтор с тем же ключом не создаёт новый заказ, а возвращает уже созданный. Ответ создания — не финальный статус, а `pending`: оплата и резерв идут дальше асинхронно. История — с курсорной пагинацией по `(created_at, id)`, а не `offset`, который на глубоких страницах заставляет базу читать и отбрасывать строки. Общие правила — в `Дизайн API и версионирование`.

## Модель данных

```sql
create table orders (
    id               uuid primary key,
    user_id          bigint not null,
    status           text not null,
    total_amount     bigint not null,
    currency         char(3) not null,
    idempotency_key  text not null unique,
    version          int not null default 0,
    created_at       timestamptz not null default now(),
    updated_at       timestamptz not null default now()
);

create index orders_user_history on orders (user_id, created_at desc);

create table order_items (
    order_id    uuid not null,
    product_id  bigint not null,
    qty         int not null,
    unit_price  bigint not null
);

create table order_status_history (
    order_id     uuid not null,
    from_status  text,
    to_status    text not null,
    reason       text,
    at           timestamptz not null default now()
);

create table outbox (
    id            bigint generated always as identity primary key,
    aggregate_id  uuid not null,
    type          text not null,
    payload       jsonb not null,
    created_at    timestamptz not null default now(),
    published_at  timestamptz
);
```

Цена копируется в `order_items` на момент оформления. Если брать её из каталога при чтении, старый заказ «подорожает» вслед за прайсом. Суммы — целые в копейках.

Статусы — машина состояний, разрешённые переходы описаны в коде:

```text
pending ──► reserved ──► paid ──► assembled ──► delivered
   │            │          │
   └────────────┴──────────┴──► cancelled
```

Переход делается условным `UPDATE ... where id = @id and status = @expected`. Ноль обновлённых строк значит, что статус уже изменил кто-то другой или переход недопустим. Событие «оплачено» для отменённого заказа не применяется молча, а запускает возврат денег. Каждый переход пишется в `order_status_history` той же транзакцией.

## Архитектура

```text
клиент ──► API Gateway ──► Order API ──► PostgreSQL primary (orders, items, history, outbox)
                              │   │                 │
              Cart, Pricing ◄─┘   └─► Redis          ▼ outbox relay / Debezium
              (синхронно)       (rate limit,     Kafka: orders.events (key = order_id)
                                 кэш)                   │
                                     ┌──────────────────┼───────────────┬───────────────┐
                                     ▼                  ▼               ▼               ▼
                                 Inventory           Payment         Delivery     Notifications
```

Синхронно при создании вызываются только проверки, без которых заказ бессмыслен: актуальная цена и наличие. Всё остальное идёт событиями.

## Склад и оплата через сагу

Заказ, резерв склада и платёж живут в разных сервисах и разных базах, поэтому одной транзакции у них нет. Оформление — сага:

```text
OrderCreated ──► Inventory: резерв ──► StockReserved ──► Payment: оплата ──► OrderPaid
                     │                                      │
                     └─► StockFailed ──► заказ cancelled     └─► PaymentFailed ──► снять резерв, cancelled
```

Каждый шаг имеет компенсацию: не прошла оплата — снять резерв и отменить заказ. Пользователь сначала видит «заказ принят, ожидает оплаты», зато падение склада или платёжного провайдера не ломает приём заказов. Оркестратор на стороне сервиса заказов удобно сделать на MassTransit state machine — шаги и компенсации видны в одном месте. Устройство саги и выбор между оркестрацией и хореографией — в `Saga`, платёжная сторона — в `Обработка платежей`.

## События через outbox

Публиковать в Kafka напрямую после `COMMIT` — это dual write: процесс упал между коммитом и публикацией, и событие потеряно навсегда. Поэтому заказ и строка в `outbox` пишутся одной транзакцией, а отдельный relay (фоновый `BackgroundService` с опросом или Debezium через CDC) читает outbox и публикует. Подробно — в `Outbox`.

Настройки, которые стоит назвать: продюсер с `acks=all` и `enable.idempotence=true`, топик с `replication.factor=3` и `min.insync.replicas=2`. Ключ партиции — `order_id`, тогда события одного заказа приходят по порядку. Число партиций — прикидка от пика: 2 000 событий в секунду при ~200 в секунду на партицию у консьюмера с походом в базу дают минимум 10, берём 24–32 с запасом, потому что увеличение числа партиций потом ломает соответствие ключа партиции.

Relay доставляет at-least-once, поэтому консьюмеры идемпотентны: таблица `inbox(event_id primary key)` в той же транзакции, что и изменение данных, или идемпотентная операция вроде условного перехода статуса. Offset коммитится после обработки, `enable.auto.commit=false`. Временные ошибки — ретрай с backoff, постоянные — в retry-топики и затем в DLQ; ретрай в отдельном топике нарушает порядок по ключу, что закрывается проверкой версии заказа. Детали — в `Обработка ошибок и DLQ` и `Exactly-once на практике`.

## Redis: что кэшировать, а что нет

Redis здесь — производный слой, а не хранилище:

- **кэш каталога и цен** — cache-aside с TTL; при изменении цены событие из Kafka удаляет ключ. Удалять, а не перезаписывать: два параллельных обновления могут записать значения в обратном порядке;
- **корзина** — до оформления это черновик, потеря которого неприятна, но не критична;
- **rate limit** на создание заказов — `INCR` плюс `EXPIRE`, при потере данных лимиты просто сбрасываются;
- **кэш последних заказов** пользователя — «мои заказы» не требуют строгой свежести.

Не кэшируем то, на чём принимается решение: статус заказа при переходах, остатки при резерве и итоговую цену при оформлении — всё это читается из источника истины. Стратегии — в `Кэширование` и `Rate limiting`.

## Чтение истории и масштабирование

История читается с реплик по индексу `(user_id, created_at desc)`; отставание реплики на доли секунды допустимо, но собственный только что созданный заказ пользователь должен видеть — его можно читать с primary короткое время после создания. Таблица растёт на 730 GB в год, поэтому `orders` партиционируется по `created_at` помесячно, а старые партиции уходят в архив. Если рост окажется на порядки выше оценки, следующий шаг — шардирование по `user_id`: история пользователя тогда живёт на одном шарде. Но это не первый шаг. Подробнее — в `Партиционирование` и `Шардирование и выбор ключа`.

## Узкие места и отказы

**PostgreSQL недоступна.** Это единственная действительно критичная зависимость: создавать заказы нельзя, API отвечает 503. Карточки товаров продолжают отдаваться из кэша. Заказ нельзя принять «на веру» без записи. Переключение — в `Репликация и failover`.

**Redis недоступен.** Все чтения каталога идут в базу — с лимитом конкурентности, чтобы не положить реплики; rate limit временно работает в памяти процесса. Заказы продолжают создаваться.

**Kafka недоступна.** События не уходят, но outbox копит строки в PostgreSQL, и после восстановления relay догоняет. Приём заказов продолжается; задерживаются резерв, оплата и уведомления. Надо следить за размером outbox и consumer lag.

**Повисшая сага.** Заказ застрял в `pending` или `reserved` — фоновая задача по таймауту запускает компенсацию и снимает резерв.

## Что уточнить у интервьюера

- можно ли подтверждать заказ асинхронно или нужен мгновенный финальный статус;
- резервировать товар при создании заказа или при оплате;
- нужна ли частичная отмена и частичная доставка;
- один склад или несколько, и кто выбирает склад.

Если нагрузка действительно 200 записей в секунду, честно сказать: можно начать с одной PostgreSQL, outbox с polling и `IMemoryCache`, а Redis и Kafka добавлять, когда появится конкретный потребитель или нагрузка. Три технологии — это три кластера в эксплуатации.

## Что стоит ответить на собеседовании

Базовый ответ: около 120 заказов в секунду в пике и 730 GB в год — это одна PostgreSQL с репликами. Заказ создаётся с ключом идемпотентности и уникальным индексом, цены копируются в позиции, статусы — машина состояний с условным `UPDATE` и историей переходов. Резерв склада и оплата идут сагой с компенсациями, события публикуются через outbox в Kafka с ключом `order_id`, Redis держит кэш каталога, корзину и rate limit.

Сильный ответ объяснит, почему прямая публикация в Kafka — это dual write, разделит, что кэшировать можно, а что нельзя, потому что на этом принимается решение, и пройдётся по отказам: без PostgreSQL заказы не принимаются, без Redis растёт нагрузка на базу, без Kafka заказы принимаются, а события копятся в outbox. Плюс назовёт момент, когда понадобится партиционирование по времени и шардирование по `user_id`, и почему не сразу.
