Платёжная задача на собеседовании почти никогда не про нагрузку: сотня платежей в секунду — скромная цифра для любой базы. Она про корректность в условиях, когда сеть ненадёжна, а внешний провайдер отвечает секундами и иногда не отвечает вовсе. Интервьюер ждёт одной формулировки: «списать ровно один раз» по сети гарантировать нельзя, но можно добиться эффекта ровно одного списания — идемпотентностью на каждом шаге, явным состоянием «исход неизвестен» и сверкой, которая ловит то, что пропустили все остальные уровни.

## Требования

Функциональные:

- оплатить заказ с подтверждением 3-D Secure, несколько провайдеров эквайринга;
- двухфазная оплата: заморозить деньги при заказе, списать при отгрузке;
- полный и частичный возврат, статус платежа и события о его изменении.

Нефункциональные:

- ни одного двойного списания и ни одного «потерянного» платежа;
- аудит каждого движения денег, исправления — только новыми записями;
- данные карт у нас не хранятся: ввод карты — на платёжной форме провайдера, мы получаем токен, и основная часть требований PCI DSS остаётся на провайдере;
- доступность 99.95% — это 21.6 минуты простоя в месяц;
- подтверждённая запись о платеже не теряется при падении базы — RPO = 0.

## Оценка нагрузки

```text
платежей в день       1M  → 1M / 86 400 ≈ 12/с
пик распродажи        ×20 ≈ 230/с
событий на платёж     ~5 (создан, отправлен, 3DS, авторизован, списан)
хранение              ~2 KB с событиями → 2 GB/день ≈ 730 GB/год
время ответа провайдера  1–5 с

запросов к провайдерам одновременно (закон Литтла): 230 × 3 с ≈ 700
```

Последняя строка — самая важная: в пике в полёте около 700 вызовов. Код с потоком на вызов здесь не выживет, а HTTP-пул к провайдеру должен вмещать эти сотни соединений. Объём же — 730 GB в год — помещается в одну PostgreSQL. Узкое место — не база, а задержка и доступность провайдера.

## API

```text
POST /v1/payments
Idempotency-Key: order:8812:attempt:1
{ "orderId": "8812", "amount": 129900, "currency": "RUB",
  "method": { "type": "card", "token": "tok_..." }, "returnUrl": "https://shop/..." }
→ 201 { "paymentId": "...", "status": "requires_action", "actionUrl": "https://3ds/..." }

GET  /v1/payments/{id}
POST /v1/payments/{id}/capture         Idempotency-Key: capture:{paymentId}
POST /v1/payments/{id}/refunds         Idempotency-Key: refund:{refundRequestId}
POST /v1/webhooks/{provider}
```

Суммы — целые числа в минимальных единицах валюты (копейках), никогда не `float` и не `double`: двоичная дробь не представляет 0.1 точно, и ошибки округления в деньгах недопустимы.

## Модель данных

```sql
create table payments (
    id                   uuid primary key,
    order_id             text not null,
    attempt              int not null,
    amount               bigint not null,
    currency             char(3) not null,
    status               text not null,
    provider             text not null,
    provider_payment_id  text,
    idempotency_key      text not null unique,
    created_at           timestamptz not null default now(),
    updated_at           timestamptz not null default now()
);

create unique index payments_one_active_per_order
    on payments (order_id) where status not in ('declined', 'failed', 'canceled');

create table payment_events (
    payment_id         uuid not null,
    type               text not null,
    provider_event_id  text unique,
    raw                jsonb not null,
    received_at        timestamptz not null default now()
);

create table ledger_entries (
    id          bigint generated always as identity primary key,
    payment_id  uuid not null,
    operation   text not null,
    account     text not null,
    debit       bigint not null default 0,
    credit      bigint not null default 0,
    created_at  timestamptz not null default now(),
    unique (payment_id, operation, account)
);
```

Каждое ограничение здесь — уровень защиты от дубля. Частичный уникальный индекс не даст создать второй активный платёж на заказ, сколько бы раз ни пришёл запрос. `idempotency_key` не даст создать тот же платёж дважды. `provider_event_id` отбросит повторно доставленный вебхук. Уникальность проводки по `(payment_id, operation, account)` не даст дважды записать одно и то же списание, даже если код по ошибке попытается.

## Где рождаются дубли

```text
клиент ──двойной клик──► Order ──ретрай HTTP──► Payment ──таймаут, ретрай──► провайдер
                                                   ▲
                    повторная доставка вебхука ────┤
                    воркер восстановления ─────────┤
                    переключение на другого провайдера
```

Каждая стрелка — место, где операция может прийти дважды, и защита нужна на каждой.

## Машина состояний с неизвестным исходом

```text
created ──► sending ──► authorized ──► captured ──► refunded
               │  ▲
               │  └── requires_action (3DS)
               ├──► declined       определённый отказ, можно новую попытку
               └──► unknown        таймаут, 5xx, обрыв
                       └──► запрос статуса у провайдера ──► authorized | declined
```

Три правила делают её безопасной.

**Состояние `sending` фиксируется до вызова провайдера.** Если процесс упал сразу после вызова, после рестарта мы видим `sending` и знаем, что списание могло состояться. Без этой записи платёж выглядел бы как не начатый, и повтор с новым ключом списал бы деньги второй раз.

**Таймаут — это не отказ.** Из `sending` и `unknown` разрешено только выяснение статуса у провайдера по нашему идентификатору или повтор с тем же ключом идемпотентности. Новый ключ или новый провайдер для платежа в `unknown` запрещены.

**Переходы — условным `UPDATE`.** Вебхук и воркер восстановления могут прийти одновременно, и выиграть должен ровно один:

```sql
update payments
set status = 'authorized', provider_payment_id = @providerPaymentId, updated_at = now()
where id = @id and status in ('sending', 'unknown', 'requires_action');
```

Если строк обновлено ноль, переход уже сделан кем-то другим или недопустим — например, «успех» пришёл для отменённого платежа. Такие случаи не применяются молча, а уходят в автоматический возврат или ручной разбор. Подробнее о гонках при параллельных обновлениях — в `Оптимистичная блокировка`.

## Идемпотентность на каждом уровне

- **Order → Payment.** Ключ `order:{id}:attempt:{n}` сохраняется вместе с хэшем тела запроса и ответом в одной транзакции с созданием платежа. Повтор с тем же ключом возвращает сохранённый ответ; тот же ключ с другим телом — ошибка 422.
- **Payment → провайдер.** Наш ключ передаётся в механизм идемпотентности провайдера — у крупных провайдеров это заголовок вида `Idempotency-Key`. Повтор с тем же ключом провайдер не исполняет, а возвращает результат первой попытки. Нужно знать, сколько провайдер хранит ключи, и не ретраить дольше этого срока.
- **Провайдер → Payment.** Вебхуки дедуплицируются по `provider_event_id`, а их обработка — идемпотентный переход состояния.
- **Payment → остальные сервисы.** События уходят в Kafka через outbox, потребители защищаются inbox-таблицей обработанных сообщений.

Общий разбор приёма — в `Идемпотентность`, почему брокер не даёт exactly-once из коробки — в `Exactly-once на практике`.

## High-level схема

```text
Order Service ──► Payment API ──► PostgreSQL: payments, payment_events, ledger, outbox
                       │                 primary ═══ синхронная реплика в другой зоне
                       ├──► адаптер провайдера A ──► эквайринг A
                       ├──► адаптер провайдера B ──► эквайринг B
                       │         ▲ webhooks
                       └──► outbox relay ──► Kafka: payment-events ──► Order, Notifications, Accounting

Recovery worker:  платежи в sending/unknown дольше N секунд → запрос статуса
Reconciliation:   реестры провайдеров ⇄ ledger, ежедневно и почти в реальном времени
```

Создание платежа не ждёт финального исхода: ответ — текущий статус и ссылка на 3-D Secure, итог приходит событием. Синхронное ожидание провайдера при его сбоях порождает повторные нажатия и дубли.

Order и Payment не связаны распределённой транзакцией. Оформление заказа — сага: заказ создан, платёж авторизован, товар зарезервирован, а при сбое шага — компенсации вроде отмены авторизации. Почему не 2PC — в `Почему 2PC проблематичен`, устройство саги — в `Saga`.

## Журнал двойной записи

Баланс и отчёты считаются из неизменяемого журнала проводок, а не из поля `status`. Каждая операция — набор проводок, где сумма дебетов равна сумме кредитов:

```text
capture 1 299.00   дебет  расчёты с провайдером     129900
                   кредит обязательства перед продавцом 129900
refund    300.00   дебет  обязательства перед продавцом  30000
                   кредит расчёты с провайдером      30000
```

Поле `operation` — идентификатор конкретной операции: `capture`, `refund:{refundId}`. Поэтому два разных возврата по одному платежу записываются, а повтор одного и того же упирается в уникальный ключ. Строки не обновляются и не удаляются; ошибка исправляется сторнирующей проводкой, а частичный возврат считается от записанных проводок — вернуть больше списанного нельзя.

## Сверка — последний рубеж

Некоторые случаи видно только со стороны провайдера: провайдер без идемпотентности, потерянный вебхук, ручная операция в его кабинете. Поэтому по ежедневному реестру и через API почти в реальном времени операции провайдера сравниваются с нашим журналом. Два списания на один заказ — автоматический возврат лишнего и алерт. Списание без платежа у нас — привязка к заказу или возврат. У нас `declined`, у провайдера списано — исправление статуса.

## Отказы и выбор согласованности

**Провайдер деградирует.** На каждого провайдера — отдельный пул соединений и circuit breaker, чтобы медленный провайдер A не съел ресурсы вызовов к B. Новые платежи переключаются на резервного провайдера, но только новые: платёж в `unknown` у A никогда не отправляется к B. Подробно — в `Circuit breaker`.

**База недоступна.** Платёж нельзя принять «на веру» без записи — это сознательный выбор согласованности вместо доступности: лучше отказать в оплате на минуту, чем списать деньги без следа. Обоснование в терминах CAP — в `CAP на самом деле`. Синхронная реплика в другой зоне даёт RPO = 0 ценой нескольких миллисекунд на каждую запись; переключение — в `Репликация и failover`.

## Компромиссы

- асинхронный исход усложняет UX — «платёж обрабатывается», — но убирает дубли от повторных нажатий;
- синхронная репликация добавляет задержку записи, зато подтверждённый платёж не теряется;
- сверка — отдельная система с ручным разбором, но без неё гарантия однократного списания остаётся обещанием.

## Что стоит ответить на собеседовании

Начните с честной формулировки: exactly-once по сети недостижим, достижим эффект однократного списания. Его дают уникальные ограничения в базе — один активный платёж на заказ, ключ идемпотентности, дедупликация вебхуков, уникальная проводка, — ключ идемпотентности, переданный провайдеру, и машина состояний, в которой `sending` записывается до вызова, а таймаут ведёт в `unknown` и опрос статуса, а не в повтор с новым ключом.

Сильный ответ добавит оценку через закон Литтла — около 700 одновременных вызовов провайдера в пике, — журнал двойной записи вместо изменяемого баланса, сагу вместо распределённой транзакции, синхронную реплику ради RPO = 0 и сверку с провайдером, которая находит и автоматически возвращает дубли, пропущенные всеми предыдущими уровнями.
