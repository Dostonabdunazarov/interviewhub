Цифры в этой задаче считаются за пять минут, а проваливаются на слове «без дублей». Ровно один раз по сети доставить нельзя, и интервьюер ждёт, что кандидат скажет это сам и соберёт эффективно ровно один раз: at-least-once на каждом звене плюс идемпотентный приёмник. Вторая ловушка — считать «без потерь» свойством Kafka. Это свойство всей цепочки, и рвётся она в скучных местах: в буфере памяти gateway или в автокоммите offset.

## Требования

Функционально: принять поток событий от источников, сохранить сырые события для аналитики и переобработки, отдать их потоковым обработчикам. Нефункционально:

- 1 млн событий в секунду, средний размер 1 KB;
- подтверждённое источнику событие не теряется, в том числе при потере зоны;
- каждое событие учтено в приёмнике один раз, задержка до хранилища — секунды;
- порядок нужен только в пределах источника: глобальный порядок означает одну партицию, то есть отказ от масштабирования.

## Оценка нагрузки

Это прикидки на допущениях выше; их надо назвать и попросить подтвердить.

```text
поток:        1M/с × 1 KB              = 1 GB/с сырых данных
сжатие:       zstd/lz4 на батчах ≈ ×4  → ~250 MB/с на запись в лог
репликация:   RF=3                     → ~750 MB/с записи на диски кластера,
                                         из них ~500 MB/с межброкерного трафика
retention:    250 MB/с × 86 400 с      ≈ 21.6 TB × 3 реплики ≈ 65 TB за сутки
чтение:       3 группы консьюмеров × 250 MB/с = 750 MB/с исходящего трафика
брокеры:      ~100–150 MB/с входящих на брокер с учётом репликации → 9–12 брокеров
партиции:     консьюмер тянет ~5–10k событий/с на партицию → 100–200, берём 256–512
```

Сеть и диск важнее CPU: брокеры — с NVMe и сетью 25 Гбит, и запас нужен на восстановление, когда заменённый брокер догоняет реплики поверх рабочего трафика. Батчинг обязателен на каждом шаге — сжатие работает на батчах. Партиции берут с запасом сразу: их число — потолок параллелизма, а добавление позже меняет отображение ключей и ломает порядок по ключу. Длинный хвост хранения — в tiered storage, а не на брокерах.

## API

```text
POST /v1/events
  [{ "eventId": "...", "sourceId": "dev-42", "seq": 1017, "ts": "...", "type": "...", "payload": {...} }, ...]
  → 200 { "accepted": [...], "rejected": [{ "eventId": "...", "reason": "schema" }] }
  → 503 Retry-After: 2
```

Приём батчами: по сотне событий — это 10 000 запросов в секунду вместо миллиона. `eventId` генерирует источник: только так повтор после таймаута узнаётся как тот же event. Монотонный `seq` позволяет доказать потерю по дырке в последовательности. Ответ 200 значит «записано на реплики Kafka», а не «принято в память».

## Данные

Ключ партиции — `sourceId`: порядок в пределах источника и ровное распределение, пока источников много. Ключ дедупликации — `eventId`, это другая роль. Главная угроза — перекос: тенант с 10% потока даёт своей партиции 100 000 событий в секунду при потолке консьюмера 5–10 тысяч. Решение — соль в ключе крупных источников (`sourceId#0..7`) ценой порядка внутри них или отдельный топик. Подробно — в `Партиции и порядок событий`.

## Архитектура

```text
источники ──► LB ──► ingest gateway (stateless) ──► Kafka: events (3 AZ, RF=3, min.insync=2)
 локальный буфер     валидация, батчинг              │
 + retry по eventId  200 только после acks=all       ├──► потоковая обработка ──► Kafka: aggregates
                                                     ├──► sink ──► объектное хранилище (сырые, долго)
                                                     └──► sink ──► ClickHouse (аналитика)
```

Источник удаляет событие только после 200. Gateway без состояния ждёт подтверждения Kafka; отвечать 200 из буфера памяти нельзя — рестарт пода потеряет события. Kafka недоступна — 503, источник повторит.

**Продюсер:**

```csharp
var config = new ProducerConfig
{
    Acks = Acks.All,
    EnableIdempotence = true,
    LingerMs = 10,
    BatchSize = 1_000_000,
    CompressionType = CompressionType.Zstd
};
```

`acks=all` ждёт реплики из ISR, идемпотентность убирает дубли от внутренних ретраев — но только в пределах сессии продюсера. Упал под gateway после записи, но до ответа — источник повторит, новый продюсер запишет событие второй раз, и этот дубль ловится только по `eventId` в приёмнике. См. `Продюсер Kafka`.

Kafka: RF=3, `min.insync.replicas=2`, реплики по зонам через rack awareness, `unclean.leader.election.enable=false`. Подтверждение означает page cache реплик, а не fsync: защита держится на том, что три зоны не теряют питание одновременно.

## Без дублей: эффективно ровно один раз

Консьюмер коммитит offset вручную после записи в приёмник. Упал между ними — батч придёт снова. Дубли at-least-once неизбежны (`Гарантии доставки`); их делают безвредными, и инструмент зависит от приёмника — общий принцип в `Идемпотентность`.

**Kafka → Kafka.** Read-process-write закрывается транзакциями Kafka: выход и offset входа коммитятся атомарно, читатели результата работают с `isolation.level=read_committed`. Внешние эффекты — база, HTTP — транзакция не покрывает.

**OLTP-база** — upsert по уникальному ключу:

```sql
insert into events (event_id, source_id, ts, payload)
select * from unnest(@ids, @sources, @ts, @payloads)
on conflict (event_id) do nothing;
```

**ClickHouse** — батч-вставки по 10–50 тысяч строк: это десятки вставок в секунду на кластер, мелкие он переносит плохо. `ReplacingMergeTree` по `event_id` схлопывает дубли только при фоновых слияниях; до них запросы видят дубли без `FINAL` или агрегации по ключу. Дедупликация вставок по токену батча (`insert_deduplication_token`) отбрасывает повтор, если токен детерминирован — например, `(topic, partition, startOffset)`. По умолчанию она включена для Replicated*-таблиц; для обычного `MergeTree` нужно задать `non_replicated_deduplication_window`. Тот же приём для объектного хранилища: имя файла от этой тройки, повтор перезаписывает тот же файл.

**Окно дедупликации** — если upsert недоступен. Хранить все `eventId` нельзя: час потока — 3.6 млрд ключей по 16 байт, около 58 GB. Окно ограничивают горизонтом повторов в минуты, а состояние держат по партициям: дубль источника приходит в ту же партицию, к тому же консьюмеру. Окно уже задержки повтора — поздний дубль пройдёт. См. `Exactly-once на практике`.

## Backpressure и мониторинг

Kafka — буфер на часы: консьюмеры тянут сами, медленный приёмник копит lag, а не роняет приём. Retention должен быть заметно больше допустимого отставания, иначе события удалятся непрочитанными — потеря без единой ошибки. На входе при росте задержки записи или заполненном буфере продюсера gateway отвечает 503 с `Retry-After`, источники копят у себя. См. `Backpressure`.

Мониторинг: consumer lag в секундах, а не в сообщениях; under-replicated и under-min-ISR партиции; задержка `acks=all` и доля 503. И сквозная сверка — счётчики по источнику и часу на входе и в каждом приёмнике с алертом на расхождение. Без неё «без потерь» — обещание, а не измерение.

## Отказы

**Брокер или зона.** Лидерство переходит к репликам из ISR, в партиции остаются две реплики, `min.insync.replicas=2` выполнен — запись идёт, продюсер ретраит без дублей. Если осталась одна реплика, запись с `acks=all` отклоняется: недоступность вместо риска потери, а выключенный unclean election не даёт отстающей реплике стать лидером.

**Консьюмер.** Ребаланс, обработка с последнего закоммиченного offset, повтор части батча поглощает приёмник. На сотнях партиций нужны cooperative sticky assignor и static membership, чтобы рестарт пода не останавливал группу. См. `Консьюмер под нагрузкой`.

**Ядовитое событие** после N попыток уходит в DLQ с причиной и алертом, не блокируя партицию, см. `Обработка ошибок и DLQ`. **Недоступный приёмник** — offset не коммитится, данные ждут в Kafka, а на догонку нужен запас мощности.

## Что уточнить у интервьюера

Размер событий и профиль пиков; с какого момента считается «без потерь» — с подтверждения или с возникновения события на устройстве; допустимый lag и срок хранения; где нужен порядок; есть ли крупные тенанты; умеют ли приёмники upsert.

## Что стоит ответить на собеседовании

Начните с цифр: 1 GB/с сырых данных, около 250 MB/с после сжатия, 750 MB/с записи на диски с RF=3, 65 TB за сутки, порядка десятка брокеров и 256–512 партиций. Затем цепочка: источник с `eventId` и локальным буфером, gateway отвечает 200 только после `acks=all`, продюсер идемпотентен, Kafka с RF=3 и `min.insync.replicas=2` по трём зонам, консьюмер коммитит offset после записи, приёмник идемпотентен. Гарантия — at-least-once плюс дедупликация, то есть эффективно ровно один раз.

Сильный ответ назовёт границы каждой гарантии: идемпотентность продюсера живёт в пределах сессии, транзакции Kafka не покрывают внешние эффекты, `ReplacingMergeTree` схлопывает дубли только при слияниях, подтверждение Kafka — это page cache, а не fsync. Добавит перекос ключей с конкретным решением, lag в секундах против retention и сквозную сверку счётчиков как доказательство, что потерь действительно нет.
