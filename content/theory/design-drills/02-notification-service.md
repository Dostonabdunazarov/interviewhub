Сервис уведомлений выглядит как простой конвейер «получили событие — отправили письмо», но на собеседовании его выбирают за то, что в нём сходятся почти все темы надёжности: асинхронная обработка, идемпотентность, ретраи, внешние провайдеры с лимитами и отказами, изоляция нагрузки. Главная мысль, к которой стоит прийти: приоритеты здесь — это изоляция ресурсов, а не сортировка одной очереди. Маркетинговая рассылка на десять миллионов адресов физически не должна иметь возможности задержать код входа.

## Требования

Функциональные:

- другие сервисы отправляют запрос «уведомить пользователя о событии X»;
- сервис сам выбирает каналы — push, email, SMS, in-app — по настройкам пользователя, рендерит шаблон с локализацией;
- настройки пользователя: отписки по типам, тихие часы;
- история доставок и in-app лента.

Нефункциональные — по классам, потому что у разных уведомлений разные цены ошибки:

| Класс | Примеры | Доставка p99 | При перегрузке |
| --- | --- | --- | --- |
| P0 | код входа, сброс пароля, вход с нового устройства | < 5 с | не задерживается никогда |
| P1 | заказ оплачен, курьер в пути | < 1 мин | задерживается, но не теряется |
| P2 | маркетинг, дайджесты | часы | ставится на паузу первым |

Общие свойства: принятое уведомление не теряется; повтор запроса не даёт второго SMS — оно стоит денег и раздражает; просроченное уведомление не доставляется вовсе — код входа, пришедший через 20 минут, бесполезен.

## Оценка нагрузки

```text
всего                100M уведомлений/день
P0    2M/день   → 2M / 86 400  ≈ 23/с,   пик ×10 ≈ 230/с
P1   30M/день   → 30M / 86 400 ≈ 350/с,  пик ×5  ≈ 1 750/с
P2   68M/день   → кампаниями: 10M за час ≈ 2 800/с

суммарный пик        ≈ 230 + 1 750 + 2 800 ≈ 4 800/с
журнал доставок      100M × 1 KB = 100 GB/день, 90 дней хранения ≈ 9 TB
```

Пять тысяч сообщений в секунду — немного для Kafka и воркеров. Настоящее ограничение в другом: SMS-провайдер даёт порядка сотен сообщений в секунду на аккаунт, push-сервисы и почтовые провайдеры тоже ограничивают скорость. Узкое место системы — чужие лимиты, и вся архитектура строится вокруг того, как их делить. А 9 TB журнала за 90 дней — повод не держать его в основной PostgreSQL без партиций: журнал режется по дням, старые партиции удаляются целиком, или журнал уходит в ClickHouse.

## API

```text
POST /v1/notifications
Idempotency-Key: order-8812:shipped
{
  "userId": 42,
  "type": "order_shipped",
  "priority": "P1",
  "data": { "orderId": 8812, "eta": "2026-10-08" },
  "expiresAt": "2026-10-07T18:00:00Z"
}
→ 202 { "notificationId": "..." }

GET /v1/notifications/{id}             → статусы по каналам
GET /v1/users/{id}/inbox?cursor=       → in-app лента
PUT /v1/users/{id}/preferences
```

Ответ `202`, а не `200`: сервис гарантирует, что принял заявку, но не что отправил. Ключ идемпотентности формирует продюсер из смысла события — `order-8812:shipped`, `login:{sessionId}:otp`, — тогда повторная публикация того же события даёт тот же ключ.

## Модель данных

```sql
create table notifications (
    id               uuid primary key,
    idempotency_key  text not null unique,
    user_id          bigint not null,
    type             text not null,
    priority         smallint not null,
    payload          jsonb not null,
    expires_at       timestamptz,
    created_at       timestamptz not null default now()
);

create table deliveries (
    notification_id      uuid not null,
    channel              text not null,
    status               text not null,
    provider             text,
    provider_message_id  text,
    attempts             int not null default 0,
    updated_at           timestamptz not null default now(),
    primary key (notification_id, channel)
);

create table user_preferences (user_id bigint, type text, channel text, enabled boolean,
                               primary key (user_id, type, channel));
create table device_tokens (user_id bigint, token text primary key, platform text);
create table templates (type text, channel text, locale text, version int, body text,
                        primary key (type, channel, locale, version));
```

Первичный ключ `deliveries` по паре «уведомление, канал» — это и есть защита от второй отправки по тому же каналу: строка одна, и её статус проверяется перед вызовом провайдера.

## High-level схема

```text
сервисы ──► Notification API ──► PostgreSQL (notifications + outbox) ──► Kafka: notif.p0 | notif.p1 | notif.p2
                                                                                │         │         │
                                                                          Dispatcher P0  P1        P2
                                                         настройки, тихие часы, шаблон, выбор каналов
                                                                                │
                                                        Kafka: send.sms.p0, send.push.p1, send.email.p2 ...
                                                                                │
                                         Channel senders ──► rate limiter (Redis) ──► провайдеры A / B
                                                                                │
                                              Delivery tracker ◄── webhooks статусов от провайдеров
```

Путь одного уведомления: API в одной транзакции пишет строку в `notifications` и запись в outbox, отвечает `202`; релей публикует её в топик своего класса. Dispatcher класса читает настройки пользователя, отбрасывает отключённые каналы, откладывает уведомление на конец тихих часов, рендерит шаблон и раскладывает по топикам каналов. Sender канала берёт токен из лимитера, проверяет статус доставки, вызывает провайдера и записывает результат. Финальный статус — «доставлено», «не доставлено» — приходит позже вебхуком провайдера.

Outbox здесь нужен, чтобы недоступность Kafka не превращалась в потерю заявок: API продолжает принимать их в PostgreSQL, а релей дошлёт, когда брокер вернётся. Сам паттерн — в статье `Outbox`. Ключ партиции во всех топиках — `user_id`: уведомления одного пользователя обрабатываются по порядку, и на этом же ключе удобно ограничивать частоту — не больше N маркетинговых сообщений в день одному человеку.

## Почему не одна очередь с приоритетами

Kafka не умеет приоритеты внутри топика. RabbitMQ умеет (`x-max-priority`), но это не решает проблему: если все воркеры заняты долгими вызовами провайдера по P2, сообщение P0 первым в очереди всё равно ждёт свободного воркера. Изоляцию дают только отдельные топики, отдельные consumer groups и пулы воркеров на каждый класс и отдельные доли лимитов провайдера. P0-путь мал по объёму, поэтому его масштабируют с запасом ×3 от пика — это дёшево.

## Лимиты провайдеров

Допустим, SMS-аккаунт даёт 300 сообщений в секунду. Его делят иерархическим token bucket в Redis:

```text
P0   гарантированно до 120/с, может забирать свободные токены остальных
P1   до 180/с
P2   только остаток, и только пока свободных токенов больше порога
```

Часто P2 вообще уводят на отдельный аккаунт или отдельного провайдера: маркетинговые рассылки портят репутацию отправителя, и делить её с кодами входа опасно. Если токенов нет, sender не крутится в цикле, а приостанавливает потребление партиции — это backpressure на уровне Kafka, подробнее в `Backpressure`.

## Ретраи, дубли и неизвестный исход

Ошибки провайдера делятся на два вида. Постоянные — невалидный номер, ответ push-сервиса о незарегистрированном токене — не ретраятся: токен сразу удаляется из `device_tokens`, иначе бесполезные попытки копятся. Временные — 5xx, таймаут, 429 — повторяются с экспоненциальной задержкой и джиттером, после N попыток сообщение уходит в DLQ. Почему без джиттера ретраи добивают провайдера — в `Retry, jitter и retry storm`, устройство DLQ — в `Обработка ошибок и DLQ`.

Самое тонкое место — таймаут после вызова провайдера. Мы не знаем, ушло ли SMS. Порядок действий такой:

1. записать `status = 'sending'` до вызова провайдера;
2. вызвать провайдера, передав `notification_id` как его ключ идемпотентности, если провайдер это поддерживает;
3. записать `sent` и `provider_message_id`.

Если процесс упал между вторым и третьим шагом, после рестарта мы видим `sending` и знаем, что вызов мог состояться. Дальше — либо запрос статуса у провайдера, либо осознанный повтор. Без идемпотентности на стороне провайдера окно для дубля остаётся, и это нужно честно сказать: at-least-once в очередях плюс дедупликация дают «почти exactly-once». Для кода входа дубль приемлем, для платного маркетингового SMS лучше потерять сообщение, чем отправить дважды. Общая теория — в `Идемпотентность`.

## Отказ провайдера и fallback

На каждый критичный канал — минимум два провайдера. Sender считает долю ошибок и латентность каждого в скользящем окне, circuit breaker при деградации переводит трафик на резервного — подробно в `Circuit breaker`. Для P0 допустим hedging: если провайдер не подтвердил приём за 3 секунды, отправить через второго, ценой редкого двойного кода.

Fallback между каналами зависит от класса. Push не доставлен, потому что у пользователя нет токена, — для P0 отправляем SMS. Почтовый провайдер лёг — для P1 ждём и повторяем, а не заменяем письмо на SMS: это в разы дороже.

## Сроки жизни и перегрузка

У каждого уведомления есть `expires_at`: код входа — 5 минут, «курьер подъезжает» — 30 минут. Просроченные выбрасываются при отправке. Без этого после часовой аварии провайдера пользователи получат лавину устаревших сообщений, а свежие коды встанут в очередь за ними.

Перегрузку решают по метрике отставания в секундах для каждого класса, а не по числу сообщений в топике. Растёт отставание P1 — автоматически ставятся на паузу кампании P2. Критическая перегрузка — P2 откладывается целиком. Это и есть load shedding по приоритету.

## Наблюдаемость

Метрики — время от приёма до подтверждения провайдером по классам и каналам, доля доставленных по отчётам провайдеров, стоимость по провайдерам. Для P0 полезна синтетика: раз в минуту отправлять код на тестовые номера через каждого провайдера и мерить время доставки. Так о проблеме провайдера узнают раньше пользователей.

## Компромиссы

- резерв мощности и квот под P0 простаивает большую часть времени, а маркетинг идёт медленнее;
- hedging и fallback повышают доставляемость критичных сообщений ценой стоимости и редких дублей — для P0 обмен правильный, для P2 нет;
- асинхронный приём через outbox и Kafka даёт устойчивость к отказам, но продюсер узнаёт о результате только из статуса или события.

## Что стоит ответить на собеседовании

Начните с классов: коды входа, транзакционные и маркетинговые уведомления имеют разные SLO и разную цену ошибки. Нагрузка — около 5 000 сообщений в секунду в пике, что несложно для Kafka; настоящий предел — лимиты провайдеров в сотни SMS в секунду. Архитектура — приём с ключом идемпотентности через outbox, отдельные топики, consumer groups и доли лимитов на каждый класс, отдельные очереди на каналы, чтобы падение SMS-шлюза не задерживало email.

Сильный ответ объяснит, почему приоритетная очередь не даёт изоляции, разберёт неизвестный исход вызова провайдера через статус `sending` и честно скажет, что без идемпотентности провайдера дубль исключить нельзя. Добавит TTL сообщений, чтобы после аварии не слать устаревшие коды, и load shedding по отставанию: при перегрузке первым останавливается маркетинг.
