В задаче про отслеживание посылок нагрузка обманчиво мала: 10 миллионов событий в день — это чуть больше сотни в секунду. Сложность не в объёме, а в характере потока. Событий десятки видов из десятка источников — сканеры складов, приложения курьеров, внешние перевозчики со своими кодами статусов. Приходят они пачками, с опозданием, не по порядку и иногда дважды. А читают результат и люди, и интернет-магазины, которые без присмотра превращают трекинг в генератор опросов. Хороший ответ строится вокруг этих свойств потока, а не вокруг RPS.

## Требования

Функциональные:

- приём событий: API для сканеров и курьеров, вебхуки перевозчиков, опрос перевозчиков без вебхуков, файлы реестров;
- страница трекинга по номеру: текущий статус, ожидаемая дата и хронология;
- уведомления покупателю о значимых сменах статуса;
- подписка интернет-магазинов на изменения статусов их посылок.

Нефункциональные:

- принятое событие не теряется;
- дубли событий не создают лишних записей и лишних SMS;
- статус на странице обновляется в пределах минуты;
- хронология и текущий статус корректны даже при опоздавших событиях.

## Оценка нагрузки

```text
событий            10M/день → 10M / 86 400 ≈ 116/с
всплески           реестры перевозчиков и смены сортировки, пик ×20 ≈ 2 300/с
событий на посылку ~8 → 10M / 8 ≈ 1.25M новых посылок в день
активных посылок   в пути в среднем 5 дней → 1.25M × 5 ≈ 6M

хранение           500 B на событие → 5 GB/день ≈ 1.8 TB/год, с индексами ≈ 3.6 TB
горячие 90 дней    450 GB сырых ≈ 0.9 TB с индексами

чтение людьми      10 проверок на посылку → 12.5M/день ≈ 145 RPS, вечерний пик ×5 ≈ 720 RPS
опрос магазинами   6M активных × раз в 15 минут = 6M × 96 = 576M/день ≈ 6 700 RPS
```

Последняя строка решает архитектуру. Если магазины опрашивают API по всем активным посылкам, они создают в 46 раз больше нагрузки, чем все покупатели вместе, и почти все их запросы возвращают «ничего не изменилось». Значит, магазинам нужны вебхуки — 116 событий в секунду вместо 6 700 запросов, — а опрос остаётся с жёстким rate limit. Всё остальное — запись около сотни событий в секунду со всплесками в тысячи и несколько сотен чтений — укладывается в одну PostgreSQL, если всплески сгладить очередью.

## API

```text
POST /v1/events                          пачка событий от сканеров и курьеров → 202
POST /v1/carriers/{carrier}/webhook      → 202
GET  /v1/parcels/{trackingNo}
  → 200 { "status": "out_for_delivery", "statusAt": "...", "eta": "2026-10-08",
          "events": [ { "status": "...", "location": "...", "occurredAt": "..." } ] }
POST /v1/subscriptions
  { "merchantId": 15, "url": "https://shop/hooks/tracking", "statuses": ["delivered", "returned"] }
```

Приём отвечает `202` после записи в Kafka: событие сохранено надёжно, но ещё не обработано. Публичная страница не показывает адрес и имя получателя — только город и этап; иначе перебор трек-номеров становится утечкой персональных данных. По той же причине — rate limit на чтение по IP.

## Модель данных

```sql
create table parcels (
    tracking_no    text primary key,
    merchant_id    bigint not null,
    carrier        text not null,
    status         text not null,
    status_rank    smallint not null,
    status_at      timestamptz not null,
    eta            date,
    last_event_at  timestamptz,
    version        int not null default 0
);

create table tracking_events (
    tracking_no      text not null,
    occurred_at      timestamptz not null,
    received_at      timestamptz not null default now(),
    status           text not null,
    location         text,
    source           text not null,
    source_event_id  text not null,
    raw              jsonb,
    unique (source, source_event_id, occurred_at)
) partition by range (occurred_at);

create index on tracking_events (tracking_no, occurred_at);
```

Здесь есть ловушка PostgreSQL, которую полезно назвать вслух: уникальный индекс на партиционированной таблице обязан включать ключ партиционирования. Поэтому `unique (source, source_event_id)` без даты создать нельзя. Включить `occurred_at` безопасно: дубль — это повторная доставка того же события, и время в нём то же. Партиции по месяцу `occurred_at`; опоздавшее событие просто попадает в свою, уже существующую партицию. Старые партиции через 90 дней отсоединяются и выгружаются в Parquet на S3. Механика — в `Партиционирование`.

Текущий статус хранится отдельно от истории — это денормализация, но страница трекинга становится одним чтением по первичному ключу плюс последние события по индексу.

## High-level схема

```text
сканеры, курьеры ──► Ingest API ────────┐
перевозчики: webhooks ──────────────────┤
перевозчики: polling ───────────────────┼──► Kafka: tracking.raw (key = tracking_no)
реестры SFTP / S3 ──► parser ───────────┘               │
                                                         ▼
                                   Normalizer: маппинг кодов, валидация, дедупликация
                                                         │
                                         Kafka: tracking.events (key = tracking_no)
                     ┌───────────────────────────┬──────┴──────────────┬────────────────────┐
                     ▼                           ▼                     ▼                    ▼
             State builder              запись истории         подписки магазинов     уведомления
             parcels + Redis            tracking_events        webhooks с HMAC        покупателям
                     │
клиент ──► CDN (TTL 30–60 с) ──► Tracking API ──► Redis ──miss──► PostgreSQL
```

Путь события: Ingest проверяет только формат, пишет в Kafka с `acks=all` и отвечает. Normalizer переводит код перевозчика во внутренний статус и отбрасывает дубли. State builder обновляет `parcels`, сбрасывает ключ в Redis и публикует смену статуса, на которую подписаны вебхуки магазинов и уведомления. Сырой топик хранится 7 дней и дублируется в S3: если маппинг кодов оказался ошибочным, события можно переобработать.

## Порядок и конкурентность

Ключ партиции во всех топиках — трек-номер. Все события одной посылки попадают в одну партицию и обрабатываются одним консьюмером последовательно, поэтому обновлению `parcels` не нужны блокировки, а гонка «два события одной посылки на двух подах» невозможна по построению. Параллелизм — между посылками: 24–48 партиций с запасом. Почему порядок есть только внутри партиции — в `Партиции и порядок событий`.

## Дубли и опоздавшие события

**Дедупликация.** У источников со своими идентификаторами — уникальный ключ `(source, source_event_id, occurred_at)` и вставка с `on conflict do nothing`. У источников без идентификаторов `source_event_id` — детерминированный хэш от трек-номера, кода статуса, места и времени. Дедупликация живёт в базе, а не в памяти консьюмера, чтобы переживать рестарты и перебалансировку.

**Опоздавшие события.** Хронология сортируется по `occurred_at` — когда событие случилось, — а не по времени получения. Текущий статус не равен «последнему пришедшему»: опоздавшее «принято на сортировке» не должно откатить уже показанное «вручено». Поэтому у статусов есть ранг этапа, а финальные статусы терминальны:

```sql
update parcels
set status = @status, status_rank = @rank, status_at = @occurredAt, version = version + 1
where tracking_no = @trackingNo
  and status not in ('delivered', 'returned')
  and (status_rank < @rank or (status_rank = @rank and status_at < @occurredAt));
```

Исключения вроде возврата после «в пути» описываются явными переходами с более высоким рангом, а не обходом правила.

**Неизвестные коды.** У каждого перевозчика десятки собственных статусов, они маппятся на 8–10 внутренних. Неизвестный код сохраняется как сырое событие, статус не меняется, а рост доли нераспознанных событий — алерт.

## Опрос перевозчиков

Если опрашивать каждую из 6 млн активных посылок раз в час, получится 6M / 3 600 ≈ 1 700 запросов в секунду к чужим API — больше, чем они позволят. Поэтому опрашивают только перевозчиков без вебхуков, только незавершённые посылки и с частотой по стадии: «в пути между городами» — раз в несколько часов, «передано курьеру» — чаще. Лимиты каждого перевозчика соблюдаются отдельным token bucket.

## Раздача и уведомления

Страница трекинга кэшируется на CDN по трек-номеру на 30–60 секунд — требование «в пределах минуты» это позволяет, а нагрузка на API падает в разы. Магазины получают вебхуки по своим посылкам: подпись HMAC, ретраи с экспоненциальной задержкой, отдельная очередь недоставленных на каждого получателя, чтобы один лежащий магазин не задерживал остальных.

Покупателю уведомления уходят только на значимые переходы — «передано курьеру», «ждёт в пункте выдачи», — с дедупликацией по `(tracking_no, status)`: дубль события не должен дать дубль SMS. Сами уведомления отправляет отдельный сервис, разобранный в `Notification service`.

## Отказы

Kafka поглощает и всплески, и недоступность базы: при падении PostgreSQL приём продолжает работать, отставание консьюмеров растёт и разбирается после восстановления. Если сломался маппинг, State builder пересобирает `parcels` повторным чтением событий — это возможно, потому что история неизменяема, а текущий статус из неё выводится. Посылка без событий дольше нормы для своего этапа — проактивный алерт «возможно, потерялась».

## Рост ×10

100 млн событий в день — около 1 160 в секунду в среднем и 50 GB в сутки — всё ещё по силам PostgreSQL с партициями, но запас тает. Естественный следующий шаг — хранилище с ключом партиции по трек-номеру и сортировкой по времени, например Cassandra или ScyllaDB: доступ всегда по одной посылке, а запись хорошо масштабируется горизонтально. Обсуждение — в `SQL vs NoSQL`.

## Компромиссы

- текущий статус отдельно от истории — денормализация, требующая аккуратного порядка обработки, но делающая чтение тривиальным;
- свежесть 30–60 секунд вместо реального времени снижает нагрузку в разы и незаметна для трекинга;
- вебхуки для магазинов требуют ретраев, подписи и учёта недоставленных, но убирают 98% бесполезных запросов;
- асинхронный приём через Kafka даёт устойчивость к всплескам ценой задержки между сканированием и отображением.

## Что стоит ответить на собеседовании

Начните с оценки: 116 событий в секунду в среднем и тысячи во всплесках, несколько сотен чтений от покупателей и 6 700 запросов, если магазины опрашивают API, — поэтому магазинам вебхуки. Приём тонкий: валидация и запись в Kafka с ключом по трек-номеру; дальше нормализация кодов, дедупликация уникальным ключом в базе и текущий статус, вычисляемый из истории.

Сильный ответ разберёт опоздавшие события — хронология по `occurred_at`, ранги этапов и терминальные статусы вместо «последнее пришедшее побеждает», — объяснит, почему ключ партиции по трек-номеру снимает гонки без блокировок, и назовёт ловушку уникального индекса на партиционированной таблице. Добавит переобработку из сырого топика и S3 как страховку от ошибок маппинга и кэш страницы на минуту как самый дешёвый способ выдержать вечерний пик.
