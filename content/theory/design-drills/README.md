# Раздел «Разбор задач» — исходники статей

Статьи трека `Распределённые системы` (`distributed`) → раздела
`design-drills`. Это последний раздел трека: полные разборы типовых задач
дизайн-секции. Метаданные — во фронтматтере каждого файла, тело — markdown
под ним.

## Как залить в базу

Скриптом, а не руками по одной:

```bash
node tools/import-theory.mjs --dry-run --dir content/theory/design-drills

node tools/import-theory.mjs \
  --url http://localhost:5103 \
  --email admin@interview.hypex.site \
  --password 'Admin123!' \
  --dir content/theory/design-drills

IH_ADMIN_PASSWORD='…' node tools/import-theory.mjs \
  --url https://interview.hypex.site \
  --email admin@hypex.site \
  --dir content/theory/design-drills
```

Первая команда показывает, что будет сделано, вторая заливает локально,
третья — в прод. Пароль для прода передаётся через переменную окружения,
а не флагом: флаг виден в списке процессов и остаётся в history шелла.

**Импорт берёт один каталог за раз** и по умолчанию читает `csharp-lang`,
поэтому `--dir` обязателен — без него этот раздел просто не зальётся,
и сообщения об ошибке не будет.

По умолчанию статьи создаются **черновиками** и существующие не трогаются.
`--update` обновляет по slug, `--publish` ставит статус «Опубликована».
Привязки к вопросам импорт не стирает: при обновлении они переносятся как есть.

Метаданные берутся из фронтматтера в начале каждого файла — `title`, `slug`,
`track`, `section`, `level`, `sortOrder`, `summary`. `readingMinutes` не задаётся:
его считает `AppDbContext.SaveChangesAsync` (200 слов в минуту, минимум 1).

## Файлы и источник правды

(`/admin/theory`). Если правите файл здесь — прогоните импорт с `--update`,
иначе версии разойдутся.

## Чтобы статьи стали видны гостям

Нужны **оба** условия: статус статьи `Published` и трек `IsPublished = true`.
Если трек `distributed` к моменту импорта ещё скрыт, после публикации статей
его нужно включить переключателем «виден» в админке — сидер создаёт
треки скрытыми.

## Раздел написан целиком

Все 6 статей по плану (`THEORY_PLAN.md`) написаны. Источник материала —
ответы «Спроектировать …» и «Спроектируйте …» из
`content/questions/system-design.md`, переписанные в связные разборы.

Каждый разбор идёт по шагам из статьи «Как проходить дизайн-секцию»:
требования → оценка нагрузки → API → модель данных → high-level схема →
углубление в узкие места → компромиссы. Механизмы, которые уже разобраны
в других разделах трека, не объясняются заново, а даются ссылкой на статью
по точному заголовку: кэширование и шардирование — `data-at-scale`, ретраи,
идемпотентность и circuit breaker — `reliability`, CAP и read-your-writes —
`consistency`, outbox и саги — `microservices`, партиции и DLQ — `messaging`.

Замеров в этом разделе нет: числа — оценки на собеседовании. Арифметика
перепроверена:

- **URL shortener**: 100M ссылок в месяц ≈ 39 записей/с, редиректов
  ≈ 3 860/с и ≈ 19 300 в пике; 6 млрд ссылок за 5 лет — 3 TB;
  62^7 ≈ 3.52 трлн, заполненность 0.17%;
- **уведомления**: 100M в день, пик ≈ 230 + 1 750 + 2 800 ≈ 4 800/с;
  журнал 100 GB в день, 9 TB за 90 дней;
- **файлы**: 1 TB входящих в день, 365 TB в год; 5 TB скачиваний в день
  ≈ 58 MB/s ≈ 460 Mbps, пик ≈ 1.4 Gbps; erasure coding 8+3 — 1.375×,
  5 PB данных ≈ 6.9 PB сырой ёмкости против 15 PB при тройной репликации;
- **платежи**: 1M в день ≈ 12/с, пик ×20 ≈ 230/с; по закону Литтла
  230 × 3 с ≈ 700 одновременных вызовов провайдера; 99.95% — 21.6 мин в месяц;
- **посылки**: 10M событий в день ≈ 116/с; чтение покупателями ≈ 145 RPS,
  опрос магазинами 6M × 96 = 576M в день ≈ 6 700 RPS — в 46 раз больше;
- **100 000 RPS**: 77 подов при утилизации 65%, 90 — чтобы пережить потерю
  зоны; 270 000 ops/s Redis — 12 шардов; 15.5 TB горячих данных — 8 шардов
  PostgreSQL; 0.99^10 ≈ 0.904.

Мощности узлов (RPS на под, транзакции на шард PostgreSQL, ops/s Redis,
лимиты SMS-провайдеров) даны как порядки и в тексте помечены «замерить».
