Сокращатель ссылок — самая частая первая задача на секции System Design, и именно поэтому на ней легко провалиться: кандидат за две минуты рисует «API → база» и не знает, о чём говорить оставшиеся сорок. На деле в задаче три настоящих вопроса — как генерировать короткие коды без коллизий и угадываемости, как отдавать редиректы за миллисекунды при перекосе чтения к записи 100:1 и как собирать статистику, не замедляя редирект. Ниже разбор идёт ровно по шагам из статьи `Как проходить дизайн-секцию`.

## Требования

Функциональные — три сценария, остальное вслух за скоуп:

- создать короткую ссылку для длинного URL, опционально со своим alias и сроком жизни;
- перейти по короткой ссылке и получить редирект;
- посмотреть статистику переходов по своей ссылке.

Нефункциональные — цифрами:

- редирект быстрый: p99 < 20 мс на стороне сервиса;
- доступность редиректа выше, чем создания: ссылка из разосланного письма, которая не открывается, хуже, чем минутная невозможность создать новую — целимся в 99.99% для редиректа и 99.9% для создания;
- коды не перебираются подряд: по `aZ3kP9q` нельзя угадать соседние ссылки;
- статистика может отставать на минуты.

Последний пункт важен: он сразу разрешает вынести учёт кликов из синхронного пути.

## Оценка нагрузки

Допущения проговариваем и просим подтвердить: 100 млн новых ссылок в месяц, на одну создание приходится 100 переходов, хранение 5 лет.

```text
запись:  100M / 30 дней     ≈ 3.33M/день → 3.33M / 86 400 ≈ 39 RPS, пик ×3 ≈ 120 RPS
чтение:  3.33M × 100        ≈ 333M/день  → 333M / 86 400  ≈ 3 860 RPS, пик ×5 ≈ 19 300 RPS

ссылок за 5 лет:  100M × 60 = 6 млрд
хранение:         6 млрд × 500 B = 3 TB, × 1.5 на индексы ≈ 4.5 TB, × 2 с репликой ≈ 9 TB
трафик:           19 300 × 0.5 KB ≈ 9.7 MB/s ≈ 77 Mbps
```

Пиковый коэффициент для чтения взят выше обычного: ссылки массово рассылают, и одна рассылка даёт всплеск переходов в первые минуты. Выводы из цифр: запись ничтожна, трафик ничтожен, а 20 000 редиректов в секунду — это задача кэша, а не базы. Как получать такие цифры — в статье `Оценка нагрузки и RPS`.

Отдельно — длина кода. В алфавите base62 (`0-9A-Za-z`) 62 символа:

```text
62^6 ≈ 56.8 млрд       — запас над 6 млрд всего в 9.5 раза
62^7 ≈ 3.52 трлн       — заполненность через 5 лет 6 / 3 520 ≈ 0.17%
62^8 ≈ 218 трлн        — заполненность ≈ 0.003%
```

Семь символов — разумный выбор: короткие ссылки и запас почти в 600 раз.

## API

```text
POST /api/links
  { "url": "https://...", "alias": null, "expiresAt": null }
  → 201 { "code": "aZ3kP9q", "shortUrl": "https://sho.rt/aZ3kP9q" }

GET  /{code}                       → 302 Location: https://...   | 404 | 410
GET  /api/links/{code}/stats?from=&to=&groupBy=day
DELETE /api/links/{code}           → 204
```

Редирект живёт на корне домена отдельно от `/api` — это два разных сервиса с разными требованиями к доступности, и их удобно масштабировать и деплоить независимо.

Код ответа редиректа — решение с ценой. `301` (или `308`) браузер кэширует надолго: повторные переходы вообще не доходят до сервиса, но теряется статистика и возможность поменять или отозвать ссылку. `302` (или `307`) каждый раз приходит к нам. Если статистика — функциональное требование, выбор `302`, и это стоит сказать вслух.

## Модель данных

Доступ только по ключу, транзакций между ссылками нет, объём — единицы терабайт. Это одинаково хорошо ложится и на PostgreSQL, и на key-value хранилища вроде DynamoDB или Cassandra; по умолчанию берём PostgreSQL, потому что он уже есть в стеке и 4.5 TB для него — не предел.

```sql
create table links (
    code        text primary key,
    long_url    text not null,
    owner_id    bigint,
    created_at  timestamptz not null default now(),
    expires_at  timestamptz
);

create index links_owner on links (owner_id, created_at desc);
```

Статистика в эту таблицу не пишется: счётчик `clicks` в строке ссылки превратил бы каждый редирект в `UPDATE` одной и той же горячей строки.

## Генерация кода

Это главная тема задачи, и её стоит разобрать сравнением вариантов.

| Способ | Плюсы | Минусы |
| --- | --- | --- |
| Хэш URL, первые 7 символов base62 | один URL — один код | коллизии разных URL, всё равно нужна проверка |
| Глобальный счётчик → base62 | без коллизий, коротко | коды идут подряд и перебираются; счётчик — точка синхронизации |
| Диапазоны ID: инстанс берёт блок из sequence | без коллизий и без координации на каждый запрос | коды подряд, если не перемешать; остаток блока теряется при рестарте |
| Случайный код + уникальный ключ | неугадываемо, проще всего | изредка коллизия, нужен повтор вставки |

Для нашей заполненности практичен случайный код. Вероятность попасть в занятый код равна доле занятых — через 5 лет это 0.17%, то есть одна повторная попытка примерно на 600 вставок. Генерировать нужно криптографически стойким генератором, а не `Random`, иначе коды станут предсказуемы:

```csharp
const string Alphabet = "0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz";

static string NewCode() => RandomNumberGenerator.GetString(Alphabet, 7);
```

Вставка — с `on conflict do nothing returning code`: если строка не вернулась, генерируем новый код и пробуем ещё раз, максимум несколько попыток. Тот же уникальный ключ закрывает пользовательские alias: занятый alias — это просто конфликт, после которого API отвечает 409. Отдельно держим список зарезервированных слов (`api`, `admin`, `login`), чтобы alias не перекрыл служебные пути.

Если интервьюер просит гарантию без повторов вообще, ответ — диапазоны ID с перемешиванием: инстанс забирает из sequence блок по 10 000 номеров, а номер перед кодированием в base62 проходит через обратимую перестановку (например, небольшой шифр Фейстеля с секретным ключом). Коллизий нет по построению, соседние номера дают несвязанные коды, а база видит одно обращение на 10 000 ссылок.

## High-level схема

```text
                ┌────────────► Redirect API (N подов) ──► локальный кэш ──► Redis ──miss──► PostgreSQL replica
клиент ──► LB ──┤                     │
                │                     └──► канал в памяти ──► Kafka: clicks ──► агрегатор ──► ClickHouse
                └────────────► Links API ──────────────────────────────────────────────────► PostgreSQL primary
```

Путь редиректа: запрос попадает на любой под Redirect API, тот ищет код в локальном кэше процесса, затем в Redis, при промахе — в реплике PostgreSQL, кладёт результат в Redis и отвечает `302`. Событие клика ставится в ограниченную очередь в памяти и уходит в Kafka фоновым отправщиком; ответ его не ждёт.

## Кэш редиректов

Ссылки неизменяемы, поэтому кэш здесь почти идеальный: инвалидировать нечего, кроме удаления и истечения. Рабочий набор невелик — если активны 20 млн ссылок по 500 B, это 10 GB, что помещается в один Redis с репликой. Ожидаемый hit rate выше 90%, и тогда в базу на пике идёт около 1 900 запросов в секунду — пара реплик справится с запасом.

Три детали, которые отличают сильный ответ:

- **отрицательное кэширование.** Перебор несуществующих кодов иначе целиком уходит в базу; ответ «нет такого кода» кладём в кэш на минуту;
- **TTL не дольше `expires_at`**, а при удалении ссылки ключ удаляется из Redis явно;
- **горячая ссылка** из массовой рассылки даёт тысячи запросов в секунду в один ключ Redis — её снимает локальный кэш процесса на несколько секунд.

Истечение ссылки проверяется при чтении — поле уже загружено, проверка бесплатна, — а физическое удаление старых строк делает фоновая задача пачками. Стратегии и вытеснение подробно — в `Кэширование`, одновременный промах по популярному ключу — в `Cache stampede`.

## Статистика без замедления редиректа

Синхронная запись клика в базу удвоила бы время редиректа и превратила бы чтение в запись. Поэтому клики уходят в Kafka асинхронно, ключ партиции — код ссылки, а агрегатор пачками раскладывает их по минутным счётчикам в ClickHouse. Поток небольшой: 333 млн событий в день по 200 B — около 67 GB в сутки до сжатия.

Важно сформулировать, какие гарантии нужны. Потерять несколько кликов при падении пода допустимо, а замедлить или сломать редирект из-за недоступности Kafka — нет. Значит, очередь в памяти ограничена, при её переполнении события отбрасываются с метрикой, а продюсер не блокирует обработку запроса. Это сознательный выбор доступности редиректа против полноты статистики; подробнее о гарантиях — в `Гарантии доставки`.

## Узкие места и отказы

**Падение primary.** Создание ссылок недоступно до failover, но редиректы продолжают работать из кэша и реплик — именно поэтому пути разделены. Как проходит переключение — в `Репликация и failover`.

**Падение Redis.** Весь поток редиректов идёт в базу: 19 300 запросов в секунду на пару реплик — это уже риск. Защита — локальный кэш процесса, лимит конкурентности на походы в базу и резерв реплик под такой сценарий.

**Рост ×10.** 40 млрд ссылок за 5 лет — это 20 TB сырых данных, и тут уместно шардирование по хэшу кода: все запросы идут по ключу, кросс-шардовых запросов нет, ключ идеален. Разбор выбора ключа — в `Шардирование и выбор ключа`.

**Злоупотребления.** Сокращатель — любимый инструмент фишинга. Rate limit на создание по пользователю и IP, проверка URL по спискам вредоносных доменов при создании и периодически — для старых ссылок, возможность заблокировать код.

## Компромиссы

- `302` вместо `301` — точная статистика ценой нагрузки на каждый переход;
- случайные коды — неугадываемость ценой редких повторных вставок;
- асинхронные клики — быстрый редирект ценой возможной потери части событий и задержки статистики;
- PostgreSQL вместо key-value хранилища — знакомый стек и запас до десятков терабайт ценой ручного шардирования, если рост превысит оценку.

## Что стоит ответить на собеседовании

Начните с цифр: 40 записей и около 20 000 редиректов в секунду в пике, 6 млрд ссылок и 3 TB за пять лет. Из них следует, что это read-heavy key-value задача, где базу защищает кэш, а запись тривиальна. Код — 7 символов base62, 3.5 трлн комбинаций; генерация — случайный код через `RandomNumberGenerator` с повтором при конфликте уникального ключа или блоки ID из sequence с обратимым перемешиванием, если нужна гарантия без повторов.

Сильный ответ разделит редирект и создание по доступности, объяснит выбор `302` ради статистики, вынесет клики в Kafka без влияния на редирект, добавит отрицательное кэширование против перебора и назовёт момент, когда понадобится шардирование по хэшу кода, — и почему для этой задачи ключ шардирования очевиден.
