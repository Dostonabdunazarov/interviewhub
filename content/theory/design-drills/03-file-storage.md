Задача «спроектируйте Google Drive» или «сервис хранения файлов» проверяет одну ключевую мысль: метаданные и содержимое — разные данные с разными требованиями, и хранить их нужно по-разному. Имя файла, папка, владелец, права и версии — маленькие связные записи, которые читаются и меняются транзакционно. Байты файла — большие неизменяемые объекты, которые нужно надёжно хранить и быстро раздавать. Вторая мысль следует из оценки трафика: содержимое файлов не должно проходить через серверы API вообще.

## Требования

Функциональные:

- загрузка файлов до 5 GB, с докачкой после обрыва;
- скачивание, папки, переименование и перемещение;
- шаринг конкретным пользователям и по публичной ссылке;
- версии и корзина с восстановлением.

Нефункциональные:

- файл, получивший подтверждение загрузки, не теряется — это главное свойство;
- скорость скачивания не ограничена мощностью API-серверов;
- файл не раздаётся публично, пока не проверен антивирусом;
- метаданные согласованы: пользователь не видит файл, которого нет, и место в хранилище не занимают объекты, о которых никто не знает.

Синхронизацию папок с десктоп-клиентом и совместное редактирование документов сразу выносим за скоуп — это отдельные большие задачи.

## Оценка нагрузки

```text
DAU                     1M
загрузок в день         2 на пользователя, средний файл 500 KB
скачиваний              в 5 раз больше загрузок

загрузки:   2M/день  → 2M / 86 400  ≈ 23/с,  пик ×3 ≈ 70/с
скачивания: 10M/день → 10M / 86 400 ≈ 116/с, пик ×3 ≈ 350/с

входящие байты:   2M × 500 KB = 1 TB/день  → ≈ 365 TB/год
исходящий трафик: 5 TB/день → 5 TB / 86 400 ≈ 58 MB/s ≈ 460 Mbps, пик ×3 ≈ 1.4 Gbps
метаданные:       ~1 KB на файл × 730M файлов/год ≈ 730 GB/год
```

Цифры дают три вывода. Запросов мало — сотни в секунду, это одна PostgreSQL и пара подов API. Байтов много — 365 TB в год, это объектное хранилище, а не диски серверов. Трафик скачивания в пике — полтора гигабита, и гнать его через API означает держать флот серверов только ради перекладывания байтов из S3 в сокет. Отсюда главное архитектурное решение: клиент загружает и скачивает напрямую из хранилища по подписанным ссылкам, а API выдаёт разрешения и ведёт учёт.

## API

```text
POST /v1/uploads
  { "name": "report.pdf", "size": 734003200, "contentType": "application/pdf",
    "folderId": "...", "sha256": "..." }
  → 201 { "fileId": "...", "uploadId": "...", "partSize": 67108864,
          "parts": [ { "number": 1, "url": "https://s3/...signed" }, ... ] }

POST /v1/uploads/{fileId}/complete
  { "parts": [ { "number": 1, "etag": "..." }, ... ] }
  → 200 { "status": "processing" }

GET    /v1/files/{fileId}/download     → 302 Location: presigned GET
GET    /v1/folders/{folderId}/items?cursor=
POST   /v1/files/{fileId}/shares        { "userId": 7, "permission": "read" } | { "public": true }
DELETE /v1/files/{fileId}               → в корзину
```

Файл в 700 MB при части 64 MB режется на 11 частей, каждая грузится отдельным PUT по своей подписанной ссылке и при обрыве повторяется только она. У S3 часть должна быть от 5 MB до 5 GB, частей не больше 10 000 — для файлов до 5 GB с частями по 64 MB это максимум 80 частей.

## Модель данных

```sql
create table files (
    id               uuid primary key,
    owner_id         bigint not null,
    folder_id        uuid,
    name             text not null,
    size             bigint not null,
    content_type     text,
    sha256           text,
    status           text not null,
    current_version  int not null default 1,
    deleted_at       timestamptz,
    created_at       timestamptz not null default now()
);

create unique index files_name_in_folder
    on files (owner_id, folder_id, name) where deleted_at is null;

create table file_versions (
    file_id      uuid not null references files (id),
    version      int not null,
    storage_key  text not null,
    size         bigint not null,
    created_at   timestamptz not null default now(),
    primary key (file_id, version)
);

create table shares (
    file_id      uuid not null references files (id),
    grantee_id   bigint,
    token        text unique,
    permission   text not null,
    expires_at   timestamptz
);
```

`storage_key` — сгенерированный путь вида `{owner_shard}/{yyyy}/{mm}/{uuid}`, а не имя файла. Поэтому переименование и перемещение меняют одну строку метаданных и не трогают объект, а два файла с одинаковым именем не конфликтуют в хранилище. Частичный уникальный индекс запрещает два одноимённых файла в папке, но не мешает файлу в корзине.

## High-level схема

```text
клиент ──1. POST /uploads──► File API ──► PostgreSQL: files(status = pending)
   │                            └──────► S3 CreateMultipartUpload, подписанные URL частей
   ├──2. PUT части ──────────────────────────────────────────────► S3
   └──3. complete ──────────► File API ──► S3 CompleteMultipartUpload
                                  │        files.status = processing
                                  └──► outbox ──► Kafka: file-uploaded
                                                     ├──► антивирус ──► status = ready | blocked
                                                     ├──► превью и миниатюры
                                                     └──► извлечение текста для поиска

скачивание: клиент ──► File API (проверка прав) ──► 302 на presigned GET или подписанный URL CDN
```

## Согласованность метаданных и объекта

Метаданные и объект живут в разных системах, и общей транзакции между PostgreSQL и S3 нет. Поэтому согласованность строится на статусах и уборке, а не на атомарности:

- строка создаётся в статусе `pending` до загрузки — у каждого объекта в S3 заранее есть владелец в базе;
- пользователь видит файл только после `complete`, а публично раздаётся только в `ready`;
- фоновая задача удаляет `pending` старше суток вместе с их незавершёнными загрузками, а lifecycle-правило бакета обрывает незавершённые multipart через сутки — иначе неподтверждённые части молча копятся и стоят денег;
- периодическая сверка находит объекты без строк и строки без объектов.

`complete` должен быть идемпотентным: клиент мог не получить ответ и повторить запрос. Повтор для файла уже в `processing` или `ready` просто возвращает текущий статус. Почему это обязательно для любой операции, которую клиент может повторить, — в `Идемпотентность`.

Публикация события `file-uploaded` идёт через outbox в той же транзакции, что и смена статуса, — иначе при сбое между коммитом и отправкой файл навсегда останется непроверенным. Паттерн разобран в `Outbox`.

## Скачивание и шаринг

API проверяет права — владелец, явный доступ в `shares` или действующий публичный токен — и отвечает редиректом на presigned GET с коротким сроком жизни. Подписанную ссылку нельзя отозвать до истечения, поэтому срок — минуты, а не дни: после отзыва доступа скачивание по старой ссылке ещё возможно, но недолго.

Популярные публичные файлы раздаются через CDN с подписанными URL. Для видео и больших файлов CDN и S3 поддерживают range-запросы, так что докачка скачивания работает без участия API.

## Версии, корзина и квоты

Новая версия — новый объект и новая строка в `file_versions`; `current_version` переключается транзакционно. Удаление — сначала мягкое: `deleted_at`, 30 дней корзины, затем фоновая задача удаляет объекты всех версий. Квота пользователя — счётчик `used_bytes`, который увеличивается в той же транзакции, что и перевод файла из `pending`, а проверяется при выдаче ссылок на загрузку, а не после неё.

## Дедупликация

Соблазн — хранить объекты по хэшу содержимого: одинаковые файлы занимают место один раз, а повторная загрузка того же файла мгновенна. Цена заметная: удаление требует подсчёта ссылок, шифрование ключом конкретного пользователя становится невозможным, а мгновенная загрузка раскрывает, что такой файл уже есть у кого-то другого. Поэтому дедупликацию, если делают, ограничивают одним пользователем или тенантом.

## Масштабирование

API stateless и масштабируется подами, S3 масштабируется сам. Метаданные — 730 GB в год — первые годы живут в одной PostgreSQL с репликой. При росте их шардируют по `owner_id`: почти все запросы — «файлы этого пользователя в этой папке», и они остаются внутри шарда. Неудобны только запросы «расшаренные мне файлы», которые смотрят на чужих владельцев, — для них держат отдельную проекцию по `grantee_id`. Выбор ключа подробно — в `Шардирование и выбор ключа`.

## Что меняется на петабайтах

Если хранилище вырастает до 5 PB, на первый план выходят экономика и долговечность:

- **классы хранения.** Большинство обращений приходится на свежие файлы; lifecycle-правила переводят старые объекты в более дешёвые классы. У холодных классов есть плата за извлечение и минимальный срок хранения, поэтому переводят по статистике обращений, а не просто всё старше 30 дней;
- **своё хранилище вместо облака.** Ceph или MinIO с erasure coding 8+3 переживают потерю трёх дисков при избыточности 11/8 ≈ 1.375 — 5 PB данных занимают около 6.9 PB сырой ёмкости вместо 15 PB при тройной репликации. Цена — эксплуатация и CPU при восстановлении;
- **метаданные.** 2.5 млрд файлов по 1 KB — 2.5 TB, уже уверенно шардированная база;
- **удаление по требованию.** Удалить нужно все версии, реплики и кэш CDN; распространённый приём — crypto-shredding, когда данные пользователя шифруются его ключом и удаление ключа делает нечитаемыми все копии.

Репликация бакетов в другой регион и защита от удаления через versioning — часть плана восстановления, разобранного в `RTO/RPO и disaster recovery`.

## Компромиссы

- presigned URL снимают трафик с API, но их нельзя отозвать до истечения;
- асинхронная обработка делает загрузку быстрой, но файл недоступен публично, пока не проверен;
- статусы и уборка вместо распределённой транзакции дают простую систему ценой временных «сирот», которые чистит фон;
- дедупликация экономит место ценой сложности удаления и утечки факта существования файла.

## Что стоит ответить на собеседовании

Разделите данные: метаданные — в PostgreSQL, байты — в S3. Оценка даёт сотни запросов в секунду, но терабайт входящих данных в день и полтора гигабита исходящего трафика в пике, поэтому байты идут мимо API: загрузка — multipart по presigned URL с повтором отдельных частей, скачивание — редиректом на подписанную ссылку или CDN.

Сильный ответ объяснит согласованность без общей транзакции: строка `pending` до загрузки, идемпотентный `complete`, событие через outbox, уборка незавершённых загрузок и сверка. Назовёт цену presigned URL — их нельзя отозвать, поэтому срок короткий — и ключ шардирования метаданных по владельцу с отдельной проекцией для расшаренных файлов. На петабайтах добавит классы хранения и erasure coding как способ платить 1.4×, а не 3× за долговечность.
