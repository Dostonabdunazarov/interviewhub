Все примитивы из предыдущих статей — `lock`, `Monitor`, `Mutex`, `ReaderWriterLockSlim` — защищают **поток**: владелец блокировки — конкретный поток ОС, и только он может её освободить. В асинхронном коде единица работы другая — **логическая операция**, которая после каждого `await` может продолжиться на другом потоке пула. Поэтому для неё нужны другие инструменты: блокировка без владельца, ожидание без потока и контекст, который переезжает вместе с операцией.

## Почему lock не подходит

`await` внутри `lock` запрещён компилятором — ошибка CS1996 (см. `lock и Monitor`). Если бы его разрешили, сломалось бы три вещи:

1. **Освобождение не тем потоком.** Продолжение после `await` выполняется на другом потоке, `Monitor.Exit` бросает `SynchronizationLockException`, а блокировка остаётся захваченной навсегда. Ровно это получится, если обойти запрет ручными `Monitor.Enter`/`Exit`.
2. **Тихое нарушение исключения.** Если продолжение попало на тот же поток, хуже: за время `await` поток вернулся в пул и выполнял чужие задачи. `Monitor` реентерабелен, и любая из них, дойдя до того же `lock`, войдёт внутрь, хотя логический владелец ещё не закончил.
3. **Блокировка на время I/O.** Все, кто пришёл к секции, стоят на заблокированных потоках, пока длится сетевой вызов.

`System.Threading.Lock` из .NET 9 проблему не решает: `await` под ним запрещён так же, а `Lock.Scope` — `ref struct`, его нельзя пронести через `await`.

Часто блокировка через `await` не нужна: I/O выносят наружу, а под `lock` оставляют короткую работу с памятью:

```csharp
var data = await LoadAsync(ct);
lock (_gate)
{
    _cache = data;
}
```

Асинхронная блокировка нужна, когда сама асинхронная операция должна быть внутри критической секции: «проверить токен, если протух — обновить», чтобы сотня запросов не обновляла его одновременно.

## SemaphoreSlim как асинхронная блокировка

Стандартный ответ — `SemaphoreSlim(1, 1)`. У семафора нет владельца, поэтому `Release` можно вызвать с любого потока, а `WaitAsync` ждёт задачей, не занимая поток:

```csharp
private readonly SemaphoreSlim _gate = new(1, 1);

public async Task<Token> GetTokenAsync(CancellationToken ct)
{
    await _gate.WaitAsync(ct);
    try
    {
        if (_token is { IsExpired: false }) return _token;
        _token = await _auth.RefreshAsync(ct);
        return _token;
    }
    finally
    {
        _gate.Release();
    }
}
```

**`WaitAsync` стоит до `try`, а не внутри.** Если ожидание отменили, захвата не было. Проверено на .NET 10: отменённый `WaitAsync` бросает `OperationCanceledException`, и `CurrentCount` остаётся 0 — слот по-прежнему у того, кто внутри. Если бы `WaitAsync` стоял внутри `try`, `finally` выполнил бы `Release` за чужой захват, и в секции оказалось бы два участника.

Свойства, проверенные на .NET 10:

```
свободный WaitAsync                       0 байт аллокаций, завершается синхронно
WaitAsync(50 мс) по таймауту              возвращает false, не бросает
повторный WaitAsync в той же операции     висит — самоблокировка
порядок входа 20 ожидающих                0, 1, 2 … 19 во всех трёх прогонах
```

**Нет реентерабельности.** Метод под блокировкой, вызвавший другой метод, который берёт ту же блокировку, ждёт сам себя вечно. Узнать владельца нельзя — его нет, — а флаг «я уже внутри» в `AsyncLocal` протекает в дочерние задачи и превращает реентерабельность в дыру во взаимном исключении. Правильное решение — разделить методы: публичные берут блокировку, внутренние предполагают, что она уже взята, и сами её не трогают.

**Порядок.** На практике асинхронные ожидающие входят по очереди, но документация FIFO не обещает — строить на этом логику нельзя.

**`maxCount` обязателен.** Без него лишний `Release` тихо расширит лимит (см. `Mutex, Semaphore и ReaderWriterLockSlim`).

## Wait или WaitAsync

Синхронный `Wait` на том же семафоре блокирует поток пула на всё время ожидания. Пока ожидающих мало, разница не видна. Семафор, однако, обычно стоит перед узким местом — базой, внешним API, — где при деградации очередь растёт. Замер на .NET 10: двести задач через одну блокировку `SemaphoreSlim(1, 1)`, внутри — `await Task.Delay(1)`:

```
WaitAsync     3 048 мс    потоков пула максимум  14
Wait         79 687 мс    потоков пула максимум 108
```

В 26 раз медленнее при той же работе. С `Wait` почти все потоки пула стоят на семафоре, а продолжению `await Task.Delay(1)` у владельца блокировки — тому самому, после которого он вызовет `Release`, — тоже нужен поток пула. Его нет, пул добавляет по потоку в полсекунды-секунду, и вся очередь движется со скоростью роста пула. Это ThreadPool starvation в чистом виде (см. `Процессы, потоки и ThreadPool`), и страдает весь процесс, включая эндпоинты, которые этот семафор вообще не трогают.

С `WaitAsync` двести ожидающих — двести небольших объектов в очереди семафора, и ни одного потока.

## Обёртка с using

Чтобы не писать `try/finally` вручную и не ошибиться с порядком, блокировку заворачивают в `IDisposable`:

```csharp
public sealed class AsyncLock
{
    private readonly SemaphoreSlim _semaphore = new(1, 1);

    public async ValueTask<Releaser> LockAsync(CancellationToken ct = default)
    {
        await _semaphore.WaitAsync(ct).ConfigureAwait(false);
        return new Releaser(_semaphore);
    }

    public readonly struct Releaser(SemaphoreSlim semaphore) : IDisposable
    {
        public void Dispose() => semaphore?.Release();
    }
}

using (await _lock.LockAsync(ct))
{
    await RefreshCacheAsync(ct);
}
```

Захват происходит до входа в `using`: отменённое ожидание не создаст `Releaser`, и лишнего `Release` не будет. `ConfigureAwait(false)` нужен для вызова из кода с `SynchronizationContext` (см. `ConfigureAwait(false)`). Слабое место — двойной `Dispose`; если это риск, `Releaser` делают классом с флагом через `Interlocked.Exchange`.

## Блокировка по ключу

Частая задача — «одна операция на пользователя» или «один пересчёт на документ», при этом разные ключи не должны мешать друг другу. Наивное решение — `ConcurrentDictionary<string, SemaphoreSlim>` и `GetOrAdd`. Оно растёт без предела: по семафору на каждый ключ за всю жизнь процесса. А удалять семафор из словаря без учёта ссылок опасно: другой поток может как раз ждать удаляемый экземпляр, а следующий пришедший создаст новый — и в секции окажутся двое.

Корректная схема — словарь под коротким синхронным `lock` с **подсчётом ссылок**: при входе счётчик ключа увеличивается, при выходе уменьшается, и запись удаляется, когда он дошёл до нуля. Внутри `lock` нет `await`, поэтому он здесь уместен. Готовая реализация — библиотека `AsyncKeyedLock`.

## Другие инструменты

| Задача | Инструмент |
| --- | --- |
| взаимное исключение вокруг async-кода | `SemaphoreSlim(1, 1)` |
| не больше N одновременных операций | `SemaphoreSlim(N, N)` или `ConcurrencyLimiter` с ограниченной очередью |
| асинхронно инициализировать один раз | `Lazy<Task<T>>` |
| обработать коллекцию с лимитом | `Parallel.ForEachAsync` с `MaxDegreeOfParallelism` |
| сложное состояние с разными операциями | один потребитель команд из `Channel<T>` |
| асинхронный reader-writer | `AsyncReaderWriterLock` из Nito.AsyncEx или Microsoft.VisualStudio.Threading |
| несколько экземпляров сервиса | распределённая блокировка или констрейнт в базе |

`Lazy<Task<T>>` закрывает однократную инициализацию без блокировки: все получают одну задачу. Упавшую задачу сбрасывают, иначе ошибка закэшируется.

`ConcurrencyLimiter` из `System.Threading.RateLimiting` — семафор с **ограниченной очередью**. У `SemaphoreSlim` очередь ожидающих не ограничена: при долгой деградации ресурса задачи копятся без предела. Лимитер с `QueueLimit` отказывает сразу, когда очередь полна, — это backpressure, а не бесконечное ожидание (см. `Channel<T>`).

## Своя блокировка на TaskCompletionSource

Если пишете примитив сами, `TaskCompletionSource` создают с `TaskCreationOptions.RunContinuationsAsynchronously`. Иначе `SetResult` в `Release` выполнит продолжение следующего ожидающего синхронно, прямо внутри `Release`, — в чужом потоке и, возможно, под чужой блокировкой, что ведёт к deadlock.

## AsyncLocal и ThreadLocal

Вторая половина темы — данные, привязанные к операции. `ThreadLocal<T>` и `[ThreadStatic]` хранят значение **на поток ОС**. `AsyncLocal<T>` хранит его в `ExecutionContext`, который захватывается при `await`, `Task.Run` и постановке в пул и восстанавливается там, где выполнение продолжилось.

Замер на .NET 10: тысяча одновременных операций, каждая записывает свой номер в `ThreadLocal` и `AsyncLocal`, делает `await Task.Delay` и читает обратно. Три прогона:

```
ThreadLocal после await:   своё значение 1–3,   чужое 997–999,   пустое 0
AsyncLocal после await:    неверных 0
```

Почти каждая операция прочитала из `ThreadLocal` **номер другой операции**: продолжение попало на поток пула, где до этого побывала чужая операция. Не `null`, а правдоподобное чужое значение — худший вид ошибки. Пользователь, tenant, correlation id в `ThreadLocal` в веб-сервисе означают утечку данных между запросами. Для контекста операции — только `AsyncLocal`; на нём построены `IHttpContextAccessor`, `Activity.Current` и scope логгера.

`ThreadLocal` остаётся правильным выбором для того, что принадлежит именно потоку: кэш буферов, локальное состояние в `Parallel.For`.

Особенности `AsyncLocal`, проверенные на .NET 10:

- **значение течёт только вниз.** Async-метод, изменивший значение, после возврата вызывающему не меняет его у вызывающего: после `await Inner()`, где `Inner` записал `"inner"`, снаружи осталось `"outer"`. Передать что-то наверх можно только через изменяемый объект-холдер в `AsyncLocal`;
- **течёт в фоновые задачи.** `Task.Run`, запущенный внутри запроса, видит его значение — 42 в замере — и держит ссылки на контекст запроса после его завершения. Долгоживущие фоновые циклы запускают под `ExecutionContext.SuppressFlow()`: там же `Task.Run` увидел значение по умолчанию;
- **не бесплатен**: каждая запись создаёт новый `ExecutionContext`.

## Что стоит ответить на собеседовании

`lock`, `Monitor`, `Mutex` и `ReaderWriterLockSlim` привязаны к потоку-владельцу, а асинхронная операция после `await` продолжается на другом потоке, поэтому `await` внутри `lock` — ошибка CS1996. Асинхронная блокировка строится на примитиве без владельца — `SemaphoreSlim(1, 1)` с `WaitAsync` до `try` и `Release` в `finally`. Он не реентерабелен (повторный `WaitAsync` в той же операции висит), FIFO не обещает и при свободном слоте не аллоцирует. Блокирующий `Wait` вместо `WaitAsync` — прямой путь к голоданию пула: на .NET 10 двести задач через блокировку прошли за 3 секунды с `WaitAsync` и за 80 секунд со 108 потоками пула с `Wait`.

Сильный ответ добавит обёртку с `using`, блокировку по ключу со счётчиком ссылок, `Lazy<Task<T>>` для однократной инициализации, `ConcurrencyLimiter` с ограниченной очередью и `RunContinuationsAsynchronously` для своих примитивов. И объяснит разницу `AsyncLocal` и `ThreadLocal`: в замере 997 из 1000 операций прочитали из `ThreadLocal` значение чужой операции, а `AsyncLocal` не ошибся ни разу; при этом `AsyncLocal` течёт только вниз и утекает в фоновые задачи, если не подавить поток через `SuppressFlow`.
