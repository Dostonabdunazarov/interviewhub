`lock` закрывает самый частый сценарий — один поток в секции, внутри одного процесса. Остальные примитивы появляются, когда нужно что-то сверх этого: синхронизировать несколько процессов, пустить в секцию не одного, а N участников, или разрешить читателям работать одновременно. У каждого своя цена, и выбор «на всякий случай» обычно оборачивается замедлением на порядки.

## Mutex: блокировка уровня ОС

`Mutex` — примитив взаимного исключения на объекте ядра операционной системы. Его главное отличие от `lock` — он может быть **именованным** и тогда работает между процессами. Классический сценарий — единственный экземпляр приложения:

```csharp
using var mutex = new Mutex(initiallyOwned: false, name: @"Global\MyApp.SingleInstance");

if (!mutex.WaitOne(TimeSpan.Zero))
{
    Console.WriteLine("Уже запущено");
    return;
}
try
{
    RunApp();
}
finally
{
    mutex.ReleaseMutex();
}
```

В Windows префикс `Global\` делает мьютекс видимым во всех сессиях, `Local\` (по умолчанию) — только в текущей. В .NET Core на Linux и macOS именованные мьютексы тоже поддерживаются — рантайм реализует их сам, и видны они только другим .NET-процессам.

Свойства, проверенные на .NET 10:

- **привязан к потоку**: `ReleaseMutex` из чужого потока бросает `ApplicationException`;
- **реентерабелен**: владелец может захватить повторно, но и освободить должен столько же раз;
- **abandoned mutex**: если поток-владелец завершился, не освободив мьютекс, следующий `WaitOne` получает владение, но бросает `AbandonedMutexException`. Это сигнал, что защищаемые данные могли остаться в неконсистентном состоянии;
- наследник `WaitHandle` — можно ждать вместе с другими хендлами через `WaitHandle.WaitAny`/`WaitAll`.

**Цена.** Каждый `WaitOne` и `ReleaseMutex` — системный вызов, даже без конкуренции. BenchmarkDotNet, .NET 10, один поток:

```
lock (object)                 5,6 нс
Mutex.WaitOne + ReleaseMutex  820 нс
```

Почти в 150 раз дороже. Поэтому `Mutex` как внутрипроцессная блокировка — пустая трата: его берут только тогда, когда нужна синхронизация процессов на одной машине — единственный экземпляр утилиты, два процесса, пишущие в один файл. Для нескольких машин или подов в Kubernetes не подходит ни `lock`, ни `Mutex`: нужна распределённая блокировка или уникальный констрейнт в базе.

С `await` мьютекс несовместим так же, как `lock`: после `await` продолжение окажется на другом потоке, и `ReleaseMutex` бросит исключение.

## Семафор: N участников вместо одного

Семафор пропускает в секцию не больше N участников одновременно. Внутри — счётчик свободных слотов: `Wait` уменьшает его или ждёт, если он равен нулю, `Release` увеличивает. Мьютекс пускает одного, семафор — N.

```csharp
private static readonly SemaphoreSlim _slots = new(initialCount: 10, maxCount: 10);

public async Task<string> CallAsync(string url, CancellationToken ct)
{
    await _slots.WaitAsync(ct);
    try
    {
        return await _http.GetStringAsync(url, ct);
    }
    finally
    {
        _slots.Release();
    }
}
```

Не больше десяти запросов к внешнему сервису одновременно — типичное применение. Другие: пул из N соединений или лицензий, и асинхронный мьютекс `SemaphoreSlim(1, 1)`.

**Ключевое свойство — у семафора нет владельца.** `Release` может вызвать любой поток, в том числе продолжение после `await` на другом потоке. Именно поэтому `SemaphoreSlim` — стандартная асинхронная замена `lock`. Обратная сторона — нет реентерабельности и нет защиты от ошибок подсчёта. Проверено на .NET 10:

```
повторный Wait(100) в том же потоке при счётчике 0:   false — ждёт сам себя
лишний Release при maxCount = 1:                      SemaphoreFullException
два лишних Release без maxCount:                      CurrentCount = 3
```

Последняя строка — самая опасная: без `maxCount` лишний `Release` тихо увеличивает число слотов, и ограничение перестаёт работать. Отсюда два правила: **всегда задавать `maxCount`** и **вызывать `Release` в `finally`**, иначе исключение «потеряет» слот, и со временем семафор заблокирует всех.

## Semaphore и SemaphoreSlim

| | `Semaphore` | `SemaphoreSlim` |
| --- | --- | --- |
| Реализация | объект ядра ОС | управляемый код в CLR |
| Межпроцессный | да, если именованный (только Windows) | нет |
| Асинхронное ожидание | нет | `WaitAsync(timeout, ct)` |
| Отмена | нет | `CancellationToken` в `Wait` и `WaitAsync` |
| Текущий счётчик | не узнать | `CurrentCount` |
| Цена без конкуренции | системный вызов | атомарная операция |

Без конкуренции `SemaphoreSlim.Wait` + `Release` стоит 17,8 нс (BenchmarkDotNet, .NET 10) — втрое дороже `lock`, но несопоставимо дешевле объекта ядра. Свободный `WaitAsync` завершается синхронно и не аллоцирует ничего (`GC.GetAllocatedBytesForCurrentThread` даёт 0 байт); ждущий — около 88 байт на объект ожидания вместо целого потока.

`Semaphore` нужен, только если нужно ограничить число **процессов** на машине. На Linux и macOS именованные семафоры не поддерживаются — конструктор с именем бросает `PlatformNotSupportedException`; межпроцессно там работает только именованный `Mutex`.

Почему в серверном коде нужен именно `WaitAsync`, а не `Wait`, и во сколько раз это меняет поведение под нагрузкой, — в статье `Асинхронная синхронизация`.

## ReaderWriterLockSlim

Блокировка, которая разрешает **много одновременных читателей или одного писателя**:

```csharp
private readonly ReaderWriterLockSlim _rw = new();
private readonly Dictionary<string, Config> _map = new();

public Config? Get(string key)
{
    _rw.EnterReadLock();
    try { return _map.GetValueOrDefault(key); }
    finally { _rw.ExitReadLock(); }
}

public void Set(string key, Config value)
{
    _rw.EnterWriteLock();
    try { _map[key] = value; }
    finally { _rw.ExitWriteLock(); }
}
```

Три режима:

| Режим | Совместим с | Назначение |
| --- | --- | --- |
| Read | другими Read и одним Upgradeable | только чтение |
| Upgradeable read | Read, но не с другим Upgradeable | прочитать и, возможно, перейти в Write |
| Write | ни с чем | изменение |

Upgradeable нужен для «проверил — при необходимости изменил» без отпускания блокировки. Держать его может только один поток: если бы двое одновременно повышались до записи, каждый ждал бы, пока другой отпустит чтение, — deadlock.

**Писатели не голодают:** пока писатель ждёт, новые читатели не допускаются.

**Рекурсия запрещена по умолчанию** (`LockRecursionPolicy.NoRecursion`). Проверено: повторный `EnterReadLock` в том же потоке и `EnterWriteLock` под удержанным чтением бросают `LockRecursionException` — сознательное решение, рекурсия в таких блокировках легко ведёт к deadlock. Как и `lock`, примитив привязан к потоку и с `await` не работает.

## Когда ReaderWriterLockSlim быстрее lock

Интуиция подсказывает, что для «читают часто, пишут редко» он всегда лучше. Замер говорит иначе. Шестнадцать потоков только читают из словаря на 1000 элементов, .NET 10, медиана пяти прогонов:

```
короткое чтение (один поиск в словаре), 500 000 на поток
  lock                    468 мс
  ReaderWriterLockSlim    441 мс

длинное чтение (поиск + 200 вычислений), 50 000 на поток
  lock                   1436 мс
  ReaderWriterLockSlim    159 мс
```

На коротком чтении разницы нет: сама блокировка дороже работы внутри (без конкуренции чтение под `ReaderWriterLockSlim` стоит 9,4 нс против 5,6 у `lock`), а её внутреннее состояние — та же общая кэш-линия, за которую бьются все шестнадцать ядер. На длинном чтении читатели действительно работают параллельно, и выигрыш девятикратный.

Правило: `ReaderWriterLockSlim` окупается, когда чтение **длинное** и чтений **намного больше**, чем записей. Решение принимают по замеру, а не по названию. Старый `ReaderWriterLock` (без Slim) в новом коде не используют.

Часто лучше обойтись без блокировки вовсе:

- `ConcurrentDictionary` — чтение без блокировок (см. `Конкурентные коллекции`);
- **неизменяемый снимок с заменой ссылки**: читатели берут текущий `FrozenDictionary`, писатель строит новый и публикует одной записью ссылки. Для редко меняющейся конфигурации — идеальный вариант.

```csharp
private FrozenDictionary<string, Config> _snapshot = FrozenDictionary<string, Config>.Empty;

public Config? Get(string key) => Volatile.Read(ref _snapshot).GetValueOrDefault(key);

public void Reload(IEnumerable<Config> items) =>
    Volatile.Write(ref _snapshot, items.ToFrozenDictionary(c => c.Key));
```

## Что выбрать

| Задача | Примитив |
| --- | --- |
| защитить состояние внутри процесса | `lock` |
| то же, но внутри нужен `await` | `SemaphoreSlim(1, 1)` |
| не больше N одновременных операций | `SemaphoreSlim(N, N)` |
| единственный экземпляр процесса на машине | именованный `Mutex` |
| длинные чтения, редкие записи | `ReaderWriterLockSlim` или снимок |
| несколько машин | распределённая блокировка, констрейнт в БД |

## Что стоит ответить на собеседовании

`Mutex` — объект ядра ОС: может быть именованным и синхронизировать процессы, привязан к потоку-владельцу и сообщает о брошенном владельцем мьютексе через `AbandonedMutexException`. Цена — системный вызов на каждый захват: на .NET 10 820 нс против 5,6 нс у `lock`, поэтому внутри процесса его не используют. Семафор пропускает N участников, у него нет владельца, поэтому `Release` можно вызвать с любого потока, и `SemaphoreSlim(1, 1)` с `WaitAsync` служит асинхронной блокировкой; `Semaphore` — объект ядра для межпроцессного случая, только в Windows.

Сильный ответ предупредит, что `SemaphoreSlim` не реентерабелен и без `maxCount` лишний `Release` тихо расширяет лимит. И про `ReaderWriterLockSlim` скажет, что он выигрывает только на длинных чтениях: в замере с шестнадцатью читателями короткий поиск в словаре под ним не быстрее `lock`, а длинное чтение — в девять раз быстрее. Для read-mostly данных часто лучше неизменяемый снимок с атомарной заменой ссылки.
