Гонка портит данные. Второй класс отказов — потеря прогресса: исключений нет, а работа не делается. Различают три вида: **deadlock** — потоки ждут друг друга вечно, **livelock** — потоки активно работают, но откатывают друг друга, **starvation** — система работает, но отдельный поток или задача не получает ресурс. Их путают, а лечатся они по-разному.

## Deadlock

Взаимная блокировка — два или больше потоков, каждый держит ресурс, нужный другому, и ждёт ресурс, который держит другой:

```csharp
object a = new(), b = new();

var t1 = new Thread(() => { lock (a) { Thread.Sleep(100); lock (b) { } } });
var t2 = new Thread(() => { lock (b) { Thread.Sleep(100); lock (a) { } } });
```

Замер на .NET 10: через три секунды оба потока в состоянии `WaitSleepJoin`, и за следующую секунду процесс потратил **0 мс** процессорного времени. Это главный признак deadlock в продакшене: запросы не завершаются, процесс жив, а CPU почти нулевой — потоки спят, а не работают.

CLR, в отличие от СУБД, циклы ожидания не ищет и не разрывает: `lock` ждёт вечно. PostgreSQL обнаружит, что две транзакции ждут друг друга, и откатит одну с ошибкой `deadlock detected` (см. `Блокировки и deadlock`). В памяти процесса этого не сделает никто.

## Условия Коффмана

Deadlock возможен, только когда выполнены все четыре условия одновременно. Разрушьте любое — и взаимная блокировка невозможна по построению:

| Условие | Смысл | Как разрушить |
| --- | --- | --- |
| Mutual exclusion | ресурсом владеет один | неизменяемые данные, lock-free структуры |
| Hold and wait | держу один ресурс и жду другой | одна блокировка вместо нескольких |
| No preemption | ресурс нельзя отобрать | таймаут с откатом захваченного |
| Circular wait | цикл в графе ожиданий | единый порядок захвата |

Практически работает в основном последнее — порядок захвата.

## Единый порядок захвата

Классика на собеседовании — перевод между счетами:

```csharp
void Transfer(Account from, Account to, decimal amount)
{
    lock (from.Sync)
    lock (to.Sync)
    {
        from.Balance -= amount;
        to.Balance += amount;
    }
}
```

Перевод A→B блокирует сначала A, встречный B→A — сначала B, и оба ждут вторую блокировку. Замер на .NET 10: два потока, по миллиону встречных переводов, три прогона:

```
порядок по Id        2 млн переводов за 87–151 мс
наивный порядок      зависли после 6, 1 583 и 2 953 переводов
```

Исправление — захватывать блокировки в порядке, который не зависит от направления:

```csharp
void Transfer(Account from, Account to, decimal amount)
{
    var (first, second) = from.Id < to.Id ? (from, to) : (to, from);
    lock (first.Sync)
    lock (second.Sync)
    {
        from.Balance -= amount;
        to.Balance += amount;
    }
}
```

Порядок может задавать идентификатор или уровень в иерархии — важно, чтобы он соблюдался везде. В базе тот же приём: обновлять строки в порядке первичного ключа.

Часто ещё проще — **одна блокировка** на оба объекта. Конкуренция чуть выше, зато deadlock невозможен. Мелкозернистые блокировки вводят, когда замер показал узкое место, а не заранее.

## Где deadlock прячется в .NET

**Чужой код под блокировкой.** Порядок захвата никто явно не нарушал, он «размазан» по компонентам: под своей блокировкой код поднимает событие, обработчик вызывает другой компонент, тот берёт свою блокировку, а в другом потоке ждёт первую. Правило из статьи `lock и Monitor`: под `lock` скопировать состояние, выйти и только потом вызывать обработчики.

```csharp
EventHandler? handler;
lock (_sync)
{
    _state = newState;
    handler = Changed;
}
handler?.Invoke(this, EventArgs.Empty);
```

**Sync-over-async.** `.Result` или `.Wait()` в потоке с однопоточным `SynchronizationContext`: продолжение `await` ждёт этот поток, а поток ждёт продолжения. Ресурс здесь — единственный поток контекста. Разбор с замерами — в статье `Дедлоки на .Result`.

**Самоблокировка на асинхронном примитиве.** `SemaphoreSlim` не реентерабелен: метод под `await _gate.WaitAsync()` вызывает другой метод, который ждёт тот же `_gate`. Проверено на .NET 10 — повторный `WaitAsync` в той же операции висит, пока первый захват не освобождён (подробнее — в статье `Асинхронная синхронизация`).

**Смешанный цикл.** Код держит `lock` в памяти и ждёт строку в базе, которую держит транзакция, ожидающая этот же `lock`. СУБД видит только свою половину цикла — обнаружить его не может никто.

## Таймаут — не лечение

Кажется, что захват с таймаутом решает проблему: не дождался — отпустил своё. Тот же встречный сценарий с `Monitor.TryEnter(second, 500 мс)`:

```
поток 1: False   поток 2: False   619 мс
```

Вечного зависания нет, но и работа не сделана: **оба** потока отказались одновременно. Таймаут разрушает условие «no preemption» лишь мягко: он превращает невидимое зависание в видимую ошибку, которую можно залогировать и повторить с паузой. Сам по себе он дизайн не исправляет — и, повторённый без паузы, ведёт прямо к livelock.

## Livelock

Потоки не заблокированы, активно работают, но не продвигаются: каждый реагирует на действие другого и откатывает своё — как двое в коридоре, синхронно уступающие друг другу дорогу.

В коде это «вежливый» захват двух блокировок:

```csharp
void DoWork(object first, object second)
{
    while (true)
    {
        lock (first)
        {
            if (Monitor.TryEnter(second))
            {
                try { Work(); return; }
                finally { Monitor.Exit(second); }
            }
        }
    }
}
```

Один поток вызывает `DoWork(a, b)`, другой — `DoWork(b, a)`. Deadlock убран — никто не ждёт вечно, — но в худшем случае оба потока в одном ритме берут свою блокировку, не получают чужую, отпускают и повторяют. Чистый livelock на реальном железе редок: планировщик и разные тайминги ядер ломают синхронный ритм. Но его зародыш — холостые попытки — виден в замере. .NET 10, два потока по 200 000 операций:

```
откат без паузы              37–61 мс, неудачных попыток 307 000–596 000
откат со случайной паузой    17–22 мс, неудачных попыток  15 000–19 000
```

Без паузы на каждую успешную операцию приходится до полутора неудачных. Случайная пауза (`Thread.SpinWait` на случайное число итераций) разбивает синхронность: неудачных попыток в 17–36 раз меньше, и работа идёт в 2–3 раза быстрее, хотя потоки «тратят время» на ожидание.

Где livelock встречается на практике:

- **ретраи без jitter** — сотни клиентов получили ошибку в один момент и повторяют через одинаковое время, снова перегружая сервис (см. `Retry, jitter и retry storm`);
- **CAS-циклы под сильной конкуренцией** — отдельный поток раз за разом проигрывает `CompareExchange` (см. `Interlocked и атомарность`);
- **оптимистичные транзакции** и **«отравленные» сообщения**, которые бесконечно возвращаются в очередь.

Лечение одно и то же: **случайная задержка и экспоненциальный backoff**, ограничение числа попыток с переходом на пессимистичную блокировку или на ошибку, dead-letter очередь для сообщений, а лучше — единый порядок, при котором откат не нужен вовсе.

## Starvation

Голодание — система в целом продвигается, но отдельный поток или задача долго или бесконечно не получает ресурс, потому что он постоянно достаётся другим.

**ThreadPool starvation** — самый частый случай в .NET. Потоки пула заняты блокирующим ожиданием, новые задачи и продолжения `await` стоят в очереди, а пул добавляет потоки по одному в полсекунды-секунду. Эксперимент с замерами — в статье `Процессы, потоки и ThreadPool`, а как блокирующий `SemaphoreSlim.Wait` превращает 3 секунды работы в 80 — в статье `Асинхронная синхронизация`.

**Писатели в reader-writer блокировке.** Если читатели идут непрерывным потоком, писатель может не дождаться момента без читателей. `ReaderWriterLockSlim` это предотвращает: пока писатель ждёт, новые читатели не допускаются (см. `Mutex, Semaphore и ReaderWriterLockSlim`).

**Несправедливые блокировки.** `Monitor` не обещает FIFO: поток, только что освободивший блокировку, может сразу захватить её снова, пока разбуженный ждущий ещё просыпается. На практике распределение обычно ровное — четыре потока, плотно захватывающие один `lock` в течение секунды, на .NET 10 получили от 221 до 283 тысяч захватов каждый, — но гарантии нет, и при неравных условиях (разная длина работы вне секции, разные приоритеты) отдельный поток может проигрывать долго.

**Тяжёлые и лёгкие задачи в одной очереди.** Долгие операции задерживают короткие; лечится отдельными очередями и лимитами (bulkhead) для разных классов работы.

## Как отличить

| | Кто страдает | CPU | Стеки потоков |
| --- | --- | --- | --- |
| Deadlock | участники цикла, навсегда | около нуля | стоят в `Monitor.Enter`, `WaitOne`, `.Result` |
| Livelock | участники, крутятся без толку | высокий | постоянно меняются, а счётчики завершённых операций не растут |
| Starvation | отдельные потоки или задачи | любой | у остальных работа идёт; при голодании пула — растущая очередь |

Инструменты:

- **дамп процесса**: `dotnet-dump collect -p <pid>`, затем в `dotnet-dump analyze` команды `syncblk` (кто какой `Monitor` держит и сколько потоков ждёт) и `clrstack -all` (на чём стоит каждый поток). Подробнее — в статье `Анализ дампа`;
- **`dotnet-counters`**: `threadpool-queue-length` и рост `threadpool-thread-count` ступенькой при низком CPU — голодание пула; быстро растущий `monitor-lock-contention-count` — борьба за блокировку (см. `dotnet-counters и dotnet-trace`);
- **стресс-тест с таймаутом на весь тест**: зависание превращается в упавший тест, а не в вечный прогон CI.

## Чего не делать

Не лечить deadlock через `ThreadPool.SetMinThreads`, `Thread.Sleep` «чтобы успело» или перезапуск по расписанию — это прячет проблему до следующего всплеска. Защита строится в дизайне: единый порядок захвата, короткие секции без чужого кода, никакого синхронного ожидания асинхронного кода, а где возможно — один владелец данных и очередь к нему (см. `Channel<T>`). Нет блокировок — нет deadlock.

## Что стоит ответить на собеседовании

Deadlock — потоки вечно ждут ресурсы друг друга; он возможен только при четырёх условиях Коффмана, и на практике его разрушают единым порядком захвата: на .NET 10 встречные переводы с наивным порядком блокировок зависали после нескольких тысяч операций, с порядком по Id выполнили два миллиона за 87–151 мс. Признак в продакшене — процесс жив, запросы висят, CPU около нуля; диагностика — дамп и `syncblk`/`clrstack -all`. CLR, в отличие от СУБД, deadlock не обнаруживает.

Сильный ответ назовёт неочевидные источники — чужой код под блокировкой, sync-over-async, повторный `WaitAsync` на нереентерабельном `SemaphoreSlim` — и объяснит, что таймаут не лечит: оба потока с `TryEnter` отказались одновременно, а повтор без паузы даёт livelock. Livelock — активная работа без прогресса, лечится случайной паузой и backoff: в замере неудачных попыток стало в 17–36 раз меньше. Starvation — отдельные участники не получают ресурс; в .NET это прежде всего голодание пула потоков от блокирующего ожидания.
