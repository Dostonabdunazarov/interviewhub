Обычные коллекции BCL безопасны для одновременного чтения, но не для записи. Пространство имён `System.Collections.Concurrent` даёт коллекции, которые можно одновременно читать и менять из многих потоков без внешнего `lock`. Важно понимать, что именно они гарантируют: каждая операция атомарна, но комбинация операций — нет, а за потокобезопасность платят памятью и однопоточной скоростью.

## Что бывает с Dictionary под гонкой

Шестнадцать потоков одновременно пишут по сто тысяч разных ключей в один `Dictionary<int, int>`. .NET 10, пять прогонов:

```
Count = 100 335 из 1 600 000   InvalidOperationException: concurrent update ... corrupted its state
Count =     796                ArgumentException: Destination array was not long enough
Count =      13                ArgumentException: Source array was not long enough
Count =      24                IndexOutOfRangeException
Count =     175                IndexOutOfRangeException
```

Все пять прогонов упали, каждый раз по-разному, и словарь потерял от 94 до 99,999% данных. Гонка ломает внутреннюю структуру — корзины, цепочки, счётчики (см. `Как устроен Dictionary`); исторически это давало и вечный цикл в поиске на 100% CPU. Современный `Dictionary` иногда распознаёт повреждение и бросает `InvalidOperationException`, но это диагностика, а не защита.

Тот же объём через `ConcurrentDictionary` — ровно 1 600 000 элементов.

## Что есть в System.Collections.Concurrent

| Коллекция | Модель | Когда использовать |
| --- | --- | --- |
| `ConcurrentDictionary<K, V>` | ключ-значение, чтение без блокировок | общий кэш, реестр |
| `ConcurrentQueue<T>` | FIFO, lock-free | очередь работ, буфер сообщений |
| `ConcurrentStack<T>` | LIFO, lock-free | пул объектов, где важен LIFO |
| `ConcurrentBag<T>` | без порядка, локальный список на поток | поток сам кладёт и сам забирает |
| `BlockingCollection<T>` | обёртка с лимитом и блокирующим ожиданием | синхронный producer-consumer |

Общий стиль API — методы `Try*`: `TryAdd`, `TryDequeue`, `TryPop`, `TryTake`, `TryRemove`, `TryUpdate`. Они объединяют проверку и действие в одну атомарную операцию. Проверять `Count > 0` перед извлечением бессмысленно — это check-then-act из статьи `Race condition`:

```csharp
while (queue.TryDequeue(out var job))
    Process(job);
```

Потокобезопасного `List<T>` с доступом по индексу в BCL нет намеренно: «элемент номер пять» теряет смысл, если параллельно кто-то вставляет в начало.

## Как устроен ConcurrentDictionary

- **Чтение без блокировок.** `TryGetValue`, индексатор на чтение и `ContainsKey` не берут lock. Каждая запись — отдельный объект-узел. Значение, которое можно записать атомарно (ссылку, `int`), писатель меняет прямо в узле, а остальное — `decimal`, `Guid`, большую структуру — заменяет вместе с узлом. Поэтому читатель без блокировки видит либо старое значение, либо новое, но не «половину».
- **Запись с lock striping.** Массив блокировок, каждая защищает свою группу корзин. Два потока, пишущие в разные группы, друг другу не мешают. Число блокировок по умолчанию связано с числом процессоров.
- **Рост таблицы** захватывает все блокировки сразу — редкое, но дорогое событие. Если размер известен, его задают в конструкторе.

Замер на .NET 10, шестнадцать потоков по миллиону операций, медиана пяти прогонов:

```
только чтение         Dictionary + lock          839 мс
                      ConcurrentDictionary        14 мс
                      Dictionary без lock         16 мс
90% чтений, 10% записей
                      Dictionary + lock          910 мс
                      ConcurrentDictionary        38 мс
```

На чтении `ConcurrentDictionary` работает со скоростью обычного словаря без синхронизации и в 60 раз быстрее словаря под общим `lock`, где шестнадцать ядер выстраиваются в очередь к одной блокировке. С десятью процентами записей разрыв двадцатикратный.

## Цена потокобезопасности

Узел на каждую запись и массив блокировок стоят памяти, а однопоточная вставка проходит через захват блокировки:

```
миллион int → int          Dictionary     ConcurrentDictionary
память                     27,9 байта     51,2 байта на элемент
вставка в одном потоке     15–26 мс       195–226 мс
```

Почти вдвое больше памяти и на порядок медленнее вставка в одном потоке. Отсюда первое правило: `ConcurrentDictionary` берут, когда к словарю действительно обращаются многие потоки, а не «на всякий случай».

Второе — **операции над всей коллекцией дорогие**. `Count`, `Keys`, `Values`, `ToArray` захватывают все блокировки, `Keys` и `Values` ещё и копируют содержимое. На словаре из ста тысяч элементов без какой-либо конкуренции:

```
Count                   около 0,5 мкс   (у Dictionary — 5 нс)
IsEmpty                 34 нс
Keys                    400 КБ аллокаций за один вызов
```

`Count` в горячем пути под нагрузкой превращает lock-free словарь в словарь с глобальной блокировкой. Нужен размер — ведите отдельный счётчик через `Interlocked`, нужна проверка на пустоту — `IsEmpty`. Перечисление `foreach` блокировок не берёт и не бросает исключение при параллельных изменениях, но и снимком не является: оно может увидеть часть изменений. Нужен снимок — `ToArray()`, понимая его цену.

## GetOrAdd вызывает фабрику несколько раз

```csharp
var value = cache.GetOrAdd(key, k => LoadFromDb(k));
```

Фабрика выполняется **вне блокировки**. Если ключа нет и шестнадцать потоков пришли одновременно, все шестнадцать вызовут фабрику, в словарь попадёт одно значение, и все получат именно его. Замер на .NET 10, шестнадцать потоков стартуют через `Barrier`, фабрика работает 50 мс:

```
GetOrAdd:          фабрика вызвана 16 раз в каждом из пяти прогонов, результат у всех один
GetOrAdd + Lazy:   фабрика вызвана 1 раз
```

Под блокировкой фабрику не вызывают намеренно: медленная фабрика заблокировала бы все ключи своей группы. Это безвредно, если фабрика дешёвая и чистая. Опасно, если она ходит в базу (cache stampede, см. `Cache stampede`), открывает соединение, которое проигравшие никто не закроет, или имеет побочные эффекты. То же касается `updateValueFactory` в `AddOrUpdate`: при конфликте она вызывается повторно.

Решение — хранить `Lazy<T>`: лишний `Lazy` создать дёшево, он ничего не делает до обращения к `Value`, а в словарь попадает один экземпляр.

```csharp
private readonly ConcurrentDictionary<string, Lazy<Task<Config>>> _cache = new();

public Task<Config> GetAsync(string key) =>
    _cache.GetOrAdd(key, static k => new Lazy<Task<Config>>(() => LoadAsync(k))).Value;
```

Режим по умолчанию у `Lazy<T>` — `ExecutionAndPublication`, фабрика внутри выполнится ровно один раз. Подвох — **исключения кэшируются**: упавшая загрузка будет отдавать ту же ошибку вечно, поэтому при ошибке элемент удаляют через `TryRemove(KeyValuePair)` — удаляется только этот экземпляр, а не значение, которое успел положить другой поток. И гарантия «один раз» действует только внутри процесса.

## Горячий ключ

Lock striping помогает, когда записи распределены по ключам. Если все пишут в **один** ключ, они бьются за одну блокировку, а `AddOrUpdate` под конфликтом ещё и повторяет вычисление. Шестнадцать потоков по 500 000 инкрементов, .NET 10:

```
AddOrUpdate в один ключ                    1514 мс
Dictionary + lock, тот же ключ              340 мс
AddOrUpdate, у каждого потока свой ключ     139 мс
GetOrAdd(Counter) + Interlocked             136 мс
```

На горячем ключе `ConcurrentDictionary` вчетверо **медленнее** обычного словаря под `lock`. Лечится изменяемым значением: словарь пишется только при первом появлении ключа, а дальше — атомарная операция над полем объекта, без блокировок словаря:

```csharp
sealed class Counter { public long Value; }

private readonly ConcurrentDictionary<string, Counter> _hits = new();

public void Hit(string page) =>
    Interlocked.Increment(ref _hits.GetOrAdd(page, static _ => new Counter()).Value);
```

Одиннадцатикратное ускорение. Для метрик ещё лучше локальное накопление со слиянием, как в статье `Interlocked и атомарность`.

Мутировать объект-значение внутри `AddOrUpdate` — `(_, list) => { list.Add(x); return list; }` — нельзя: словарь защищает свою структуру, а не ваш `List<T>`.

## ConcurrentQueue, ConcurrentStack, ConcurrentBag

`ConcurrentQueue<T>` — lock-free очередь из сегментов-массивов, `ConcurrentStack<T>` — lock-free связный список на CAS. `ConcurrentBag<T>` устроен иначе: у каждого потока свой локальный список, и `TryTake` сначала берёт из своего, а у чужих **крадёт** только когда свой пуст. Поэтому он хорош в одном сценарии и посредственен в другом. .NET 10, медиана пяти прогонов:

```
8 производителей + 8 потребителей по 1 млн
  Queue + lock                 1891 мс
  ConcurrentQueue              1260 мс
  ConcurrentBag                1842 мс

16 потоков, каждый кладёт и сам забирает по 1 млн
  ConcurrentQueue              3511 мс
  ConcurrentBag                 736 мс
```

Когда одни пишут, а другие читают, `ConcurrentBag` постоянно крадёт и работает как очередь под `lock`. Когда поток забирает свои же элементы — например, пул переиспользуемых объектов, — он почти не синхронизируется и впятеро быстрее очереди. Порядка у него нет.

## BlockingCollection

Обёртка над `ConcurrentQueue<T>` (или другой `IProducerConsumerCollection<T>`) с лимитом ёмкости и ожиданием в `Take` и `Add`. Ожидание **блокирует поток**: 32 вызова `Take()` на пустой коллекции из задач пула подняли число потоков пула на .NET 10 с 7 до 20. В асинхронном коде её место занимает `Channel<T>` — те же 32 ожидающих `ReadAsync` не заняли ни одного потока (подробности — в статье `Channel<T>`).

## Неизменяемые коллекции

Для данных, которые читают все, а меняют редко, лучший вариант — без синхронизации на чтении. `FrozenDictionary` и `FrozenSet` (.NET 8) строятся дорого, а читаются быстро — для справочников. `ImmutableDictionary` и `ImmutableList` при изменении возвращают новую коллекцию с общими частями старой — удобны для снимков, но читаются медленнее.

Сама коллекция потокобезопасна, а поле с «текущей версией» — нет: его публикуют через `Volatile.Write` или `Interlocked.Exchange`, а «прочитал — дополнил — записал» делают методами `ImmutableInterlocked` (пример — в статье `Mutex, Semaphore и ReaderWriterLockSlim`).

## Что стоит ответить на собеседовании

`Dictionary` при параллельной записи не просто теряет значения, а портит внутреннюю структуру: на .NET 10 шестнадцать потоков уронили его во всех пяти прогонах тремя разными исключениями и потеряли почти все данные. `ConcurrentDictionary` читает без блокировок, а пишет под блокировками на группы корзин; на чтении с шестнадцатью потоками он в 60 раз быстрее словаря под общим `lock`. Цена — почти вдвое больше памяти, на порядок медленнее однопоточная вставка и дорогие `Count`, `Keys` и `ToArray`, которые захватывают все блокировки.

Сильный ответ объяснит, что `GetOrAdd` вызывает фабрику вне блокировки — в замере шестнадцать потоков вызвали её шестнадцать раз — и что лечится это `Lazy<T>` в качестве значения с удалением при ошибке. Покажет, что на горячем ключе `AddOrUpdate` вчетверо медленнее `lock`, а `GetOrAdd` объекта-счётчика с `Interlocked` — в одиннадцать раз быстрее. Различит `ConcurrentQueue` и `ConcurrentBag` по сценарию и скажет, что `BlockingCollection` в async-коде заменяет `Channel<T>`.
