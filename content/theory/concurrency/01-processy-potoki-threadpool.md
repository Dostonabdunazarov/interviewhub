Почти всё, что в .NET выполняется «параллельно», выполняется на потоках пула: продолжения после `await`, `Task.Run`, обработка запросов в ASP.NET Core, таймеры. Чтобы понимать, почему сервис внезапно перестаёт отвечать при почти нулевой загрузке CPU, нужно знать три вещи: что такое поток, сколько он стоит и по каким правилам пул решает, сколько потоков держать.

## Процесс и поток

**Процесс** — контейнер ресурсов: изолированное адресное пространство, дескрипторы файлов и сокетов, токен безопасности. **Поток** — единица выполнения внутри процесса: свой указатель инструкций, свои регистры и свой стек, но общая с остальными потоками память.

| | Процесс | Поток |
| --- | --- | --- |
| Адресное пространство | своё, изолированное | общее с другими потоками процесса |
| Обмен данными | pipes, сокеты, shared memory | общие объекты в куче плюс синхронизация |
| Переключение | дороже: смена таблиц страниц | дешевле: адресное пространство то же |
| Падение | не затрагивает другие процессы | необработанное исключение роняет весь процесс |

Из таблицы следуют два практических вывода. Первый: всё, что лежит в куче, и все статические поля видны всем потокам сразу, поэтому любой объект, к которому обращаются из двух потоков, требует синхронизации. Локальные переменные метода лежат на стеке потока и принадлежат только ему (см. `Стек и куча`). Второй: **процесс — граница отказа, поток — нет.** Необработанное исключение в любом потоке, включая потоки пула, завершает процесс. Ненадёжный код — плагины, нативные библиотеки — изолируют отдельным процессом.

В .NET Framework внутри процесса существовали AppDomain — лёгкая изоляция без отдельного процесса. В .NET Core и новее создать дополнительный AppDomain нельзя; для загрузки и выгрузки сборок есть `AssemblyLoadContext`, но изоляции падений он не даёт.

## Thread: обёртка над потоком ОС

`System.Threading.Thread` — это один поток операционной системы, один к одному:

```csharp
var worker = new Thread(() => Console.WriteLine("работаю"))
{
    IsBackground = true,
    Name = "worker"
};
worker.Start();
worker.Join();
```

**Foreground и background.** Процесс живёт, пока жив хотя бы один foreground-поток. Background-потоки обрываются при выходе из процесса, и их блоки `finally` не выполняются. Главный поток — foreground, все потоки пула — background. Проверено на .NET 10:

```
main:        IsThreadPoolThread=False  IsBackground=False
поток пула:  IsBackground=True
```

**Остановить поток снаружи нельзя.** `Thread.Abort` в .NET Core и новее бросает `PlatformNotSupportedException`. Остановка только кооперативная — через `CancellationToken` (см. `CancellationToken и таймауты`).

## Сколько стоит поток

Создание потока — системный вызов, резервирование адресного пространства под стек (порядка мегабайта, резервируется, а не выделяется сразу), регистрация в CLR. Замер на .NET 10, Ryzen 7 5800H:

```
1000 × new Thread + Start + Join            168–235 мс
1000 × ThreadPool.QueueUserWorkItem + ожидание   1,0–5,3 мс
```

Порядка 170 микросекунд на поток против пары микросекунд на постановку работы в уже готовый поток пула — разница больше чем в сто раз. Плюс к этому каждый живой поток занимает стек, а переключение контекста между потоками стоит микросекунды и выбивает кэши процессора.

Отсюда базовое правило: **короткую работу не запускают в новом потоке, её отдают пулу**. А ожидание I/O вообще не должно занимать поток: для этого есть `async/await` (см. `Как работает async/await`).

`new Thread` оправдан в немногих случаях: долгоживущий цикл, который блокируется (чтение из нативного API, старый синхронный драйвер), нужен STA-апартамент для COM, особый приоритет или имя потока для диагностики. Для «долгой задачи» есть и `Task.Factory.StartNew(work, TaskCreationOptions.LongRunning)` — он тоже создаёт отдельный поток вне пула. С async-делегатом `LongRunning` бессмысленен: поток освободится на первом же `await`.

## Как устроен ThreadPool

Пул — общий на процесс набор рабочих потоков, которые берут задачи из очередей. Очередей несколько:

```
Глобальная очередь (FIFO)  ← Task.Run и QueueUserWorkItem из потоков вне пула
        │
 ┌──────┼──────────┬───────────┐
Worker 1    Worker 2    Worker 3
[локальная] [локальная] [локальная]  ← задачи, созданные внутри этого worker'а
```

- Задача, запущенная **из потока пула**, попадает в локальную очередь этого потока.
- Владелец берёт задачи из своей очереди с «горячего» конца (LIFO): только что созданная задача работает с данными, которые ещё лежат в кэше.
- Поток без работы сначала смотрит в глобальную очередь, затем **крадёт** задачу у соседа с противоположного конца его очереди (work stealing) — так владелец и вор реже конфликтуют.

Начиная с .NET 6 пул реализован на C# одинаково на всех платформах. Ожидание I/O рабочих потоков не занимает: завершение операции приходит через IOCP в Windows или epoll/kqueue в Unix, и в пул ставится только продолжение.

## Сколько потоков держит пул

Здесь кроется главная особенность пула, которую нужно знать наизусть. Минимум по умолчанию равен числу логических процессоров:

```
ThreadPool.GetMinThreads:  worker=16, io=1     (16 логических ядер)
ThreadPool.GetMaxThreads:  worker=32767, io=1000
```

До минимума потоки создаются **сразу**, по требованию. Выше минимума работают два механизма: **hill climbing** периодически меняет число потоков и смотрит на пропускную способность, а **детектор голодания** добавляет поток, если очередь не пуста, а задачи не завершаются. Оба осторожны: пул рассчитан на короткие CPU-задачи, и лишние потоки только мешали бы.

Что это значит на практике, видно в эксперименте: 64 задачи, каждая блокирует поток на 5 секунд (`Thread.Sleep`), и сразу за ними — одна пустая задача. .NET 10:

```
    2 мс: потоков=1   в очереди=63
   26 мс: потоков=16  в очереди=49
 1023 мс: потоков=17
 1531 мс: потоков=18
 2549 мс: потоков=19
 3568 мс: потоков=20
 4077 мс: потоков=21  в очереди=44
пустая задача за 5 секунд так и не выполнилась
```

Шестнадцать потоков появились мгновенно, дальше — по одному раз в полсекунды-секунду. Пустая задача, которой нужна была одна микросекунда процессорного времени, простояла в очереди больше пяти секунд, потому что все потоки спали.

Это и есть **ThreadPool starvation**: CPU почти не загружен, а приложение не отвечает. В веб-сервисе вместо `Thread.Sleep` обычно стоит `.Result` или `.Wait()` над асинхронным методом, синхронный I/O или блокирующий `SemaphoreSlim.Wait()`. Продолжению той самой асинхронной операции, которую ждёт заблокированный поток, тоже нужен поток пула — и его нет. Подробный разбор с замерами — в статье `Дедлоки на .Result`.

## Правила работы с пулом

| Сценарий | Что использовать |
| --- | --- |
| короткое CPU-вычисление | `Task.Run`, `Parallel.For` |
| ожидание I/O | `async/await` — поток не нужен вовсе |
| бесконечный блокирующий цикл | отдельный поток: `new Thread` или `LongRunning` |
| много независимых блокирующих вызовов | переписать на async; временно — ограничить их число |

**Не блокировать потоки пула.** Это главное правило, всё остальное — следствия.

**`SetMinThreads` — пластырь, а не лечение.** `ThreadPool.SetMinThreads(200, 200)` поднимает порог мгновенного создания потоков, и сервис при всплеске оживает. Но причина — блокирующий код — остаётся, а двести потоков стоят памяти и переключений контекста. Это допустимо как аварийная мера на время исправления.

**`[ThreadStatic]` и `ThreadLocal<T>` переживают задачу.** Поток пула после задачи возвращается за следующей, и значение, оставленное одной задачей, увидит другая. В асинхронном коде для контекста операции нужен `AsyncLocal<T>` — о разнице в статье `Асинхронная синхронизация`.

**Диагностика.** `dotnet-counters monitor -p <pid> --counters System.Runtime` показывает `threadpool-thread-count` и `threadpool-queue-length`. Число потоков, растущее ступенькой при низком CPU, и очередь, которая не опустошается, — характерная картина голодания.

## Что стоит ответить на собеседовании

Процесс — изолированное адресное пространство и граница отказа, поток — единица выполнения внутри процесса со своим стеком и общей кучей; необработанное исключение в любом потоке роняет весь процесс. Создавать поток дорого: на .NET 10 тысяча `new Thread` с запуском и ожиданием занимает около 170 мс против пары миллисекунд на ту же тысячу задач в пуле, поэтому короткую работу отдают `ThreadPool`, а ожидание I/O делают через `async/await`, не занимая поток вовсе.

Сильный ответ объяснит устройство пула: глобальная очередь, локальные очереди у каждого рабочего потока, work stealing, минимум потоков по числу ядер. И главное — что выше минимума пул добавляет потоки медленно, примерно по одному в полсекунды-секунду: в эксперименте с 64 заблокированными задачами пустая задача не выполнилась за пять секунд. Отсюда ThreadPool starvation при `.Result` и синхронном I/O, и `SetMinThreads` маскирует её, а не лечит.
