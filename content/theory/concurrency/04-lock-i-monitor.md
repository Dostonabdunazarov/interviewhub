`lock` — основной инструмент взаимного исключения в C#: блок кода для одного и того же объекта блокировки выполняет не больше одного потока одновременно. Он прост в использовании, но за ним стоит механизм CLR — `Monitor`, — и понимание этого механизма объясняет и цену блокировки, и её ограничения, и то, почему в .NET 9 появился отдельный тип `Lock`.

## Во что компилируется lock

Для обычного объекта компилятор разворачивает `lock` в `Monitor.Enter`/`Monitor.Exit` внутри `try/finally`:

```csharp
lock (_sync)
{
    _items.Add(item);
}

bool lockTaken = false;
try
{
    Monitor.Enter(_sync, ref lockTaken);
    _items.Add(item);
}
finally
{
    if (lockTaken) Monitor.Exit(_sync);
}
```

Нижний фрагмент — то, во что превращается верхний. `finally` гарантирует освобождение блокировки при исключении. Перегрузка с `ref bool lockTaken` нужна, чтобы исключение, возникшее прямо во время захвата, не привело ни к вечно захваченной блокировке, ни к лишнему `Exit`.

## Свойства блокировки

**Реентерабельность.** Поток, уже держащий блокировку, может войти повторно — `Monitor` ведёт счётчик рекурсии. Проверено для обоих вариантов на .NET 10: `lock (o) lock (o) { }` и то же для `Lock` проходят без зависания.

**Привязка к потоку.** Освободить блокировку может только поток-владелец. `Monitor.Exit` из чужого потока бросает `SynchronizationLockException`, `Lock.Exit` — тоже (проверено).

**Барьер памяти.** Вход и выход работают как полные барьеры: всё, что поток записал внутри секции, увидит следующий владелец. Поэтому код, где каждое обращение к общим данным идёт под одной блокировкой, не нуждается ни в `volatile`, ни в ручных барьерах (см. `volatile и барьеры памяти`).

**Нет таймаута.** `lock` ждёт вечно. Захват с таймаутом — через `Monitor.TryEnter(obj, timeout, ref taken)` или `Lock.TryEnter(timeout)`.

**Только внутри процесса.** Между процессами нужен `Mutex`, между машинами — распределённая блокировка (см. `Mutex, Semaphore и ReaderWriterLockSlim`).

## Как Monitor устроен внутри

У каждого объекта в куче есть заголовок. При захвате без конкуренции CLR записывает в него идентификатор потока-владельца и счётчик рекурсии одной атомарной операцией — это **thin lock**. Если возникает конкуренция или заголовок уже занят (например, там сохранён хеш-код объекта), блокировка «раздувается» до **sync block** — записи в отдельной таблице с полноценной очередью ожидающих и событием ядра.

Путь захвата при конкуренции:

1. несколько коротких итераций активного ожидания (spin) — вдруг владелец сейчас выйдет;
2. не вышел — поток засыпает на объекте ядра: системный вызов и переключение контекста;
3. при `Exit` владелец будит одного из ожидающих.

Поэтому короткие секции без конкуренции почти бесплатны, а под конкуренцией цена растёт на порядки. Замер BenchmarkDotNet на .NET 10, один поток, без конкуренции:

```
++_counter без синхронизации     0,19 нс
lock (object)                    5,59 нс
lock (Lock)                      4,89 нс
```

Аллокаций нет ни в одном варианте. Теперь шестнадцать потоков, по два миллиона инкрементов общего счётчика каждый (медиана пяти прогонов):

```
lock (object)                         2553 мс
lock (Lock)                           3085 мс
тот же объём в одном потоке с lock     406–446 мс
локальный счётчик + одно сложение        2,9 мс
```

Шестнадцать ядер под общей блокировкой работают **в шесть раз медленнее одного потока**: секция сериализует их, а сверху добавляются spin, засыпания, пробуждения и пересылка кэш-линии с состоянием блокировки между ядрами. Это и есть lock contention. Счётчик `Monitor.LockContentionCount` за пять прогонов по 200 тысяч захватов на поток вырос на 4941 — столько раз поток не смог захватить блокировку сразу. Тот же показатель есть в `dotnet-counters` как `monitor-lock-contention-count`.

Вывод: блокировка дешёвая, пока за неё не борются. Под конкуренцией помогает не смена примитива, а уменьшение общего состояния — короткие секции, шардирование, локальное накопление.

## System.Threading.Lock (.NET 9)

В .NET 9 и C# 13 появился отдельный тип блокировки:

```csharp
private readonly Lock _gate = new();

lock (_gate)
{
    _balance -= amount;
}
```

Если выражение в `lock` имеет тип `Lock`, компилятор генерирует не `Monitor`, а `using (_gate.EnterScope())`. Блокировка живёт в полях самого объекта `Lock` и не трогает заголовок и таблицу sync block. Объект стоит 40 байт против 24 у `new object()` (замер на .NET 10).

Выигрыш скромный: в замере выше без конкуренции `Lock` быстрее на 0,7 нс, под сильной конкуренцией преимущества нет. Главная ценность — явность: тип поля сразу говорит, что это блокировка, а API `TryEnter(timeout)` и `IsHeldByCurrentThread` встроены. Для нового кода рекомендуют именно его.

Ловушка — приведение к `object`:

```csharp
object o = _gate;
lock (o) { }
```

Компилятор выдаёт предупреждение CS9216 и откатывается к `Monitor`. Это **другая** блокировка, несовместимая с `lock (_gate)`: два участка кода, захватывающие «один и тот же» объект разными способами, друг друга не исключают.

## Что блокировать

Только reference type: для значимого типа `lock` не скомпилируется, а `Monitor.Enter(int)` каждый раз упакует новый объект (см. `Упаковка и распаковка`), и `Exit` получит другой объект с исключением. Правило — закрытое `readonly`-поле:

- не `this` — его может заблокировать внешний код и устроить deadlock;
- не `typeof(Foo)` — один объект на весь процесс;
- не строку — интернированные строки общие для всех сборок.

Один объект блокировки — на один инвариант, и все обращения к защищаемым данным, включая чтение, идут через него.

## Wait и Pulse

Кроме взаимного исключения, `Monitor` реализует условные переменные — ожидание, пока выполнится условие:

```csharp
public void Produce(Job job)
{
    lock (_sync)
    {
        _queue.Enqueue(job);
        Monitor.Pulse(_sync);
    }
}

public Job Consume()
{
    lock (_sync)
    {
        while (_queue.Count == 0)
            Monitor.Wait(_sync);
        return _queue.Dequeue();
    }
}
```

`Wait` атомарно освобождает блокировку и засыпает, после пробуждения снова её захватывает. `Pulse` переводит одного ждущего в очередь на захват, но продолжит он только после выхода текущего владельца. Условие проверяется в `while`, а не в `if`: между `Pulse` и повторным захватом другой поток мог забрать элемент. `Wait` и `Pulse` без владения блокировкой бросают `SynchronizationLockException`.

У `Lock` методов `Wait`/`Pulse` нет. Сегодня producer-consumer обычно пишут не на условных переменных, а на `Channel<T>` (см. статью `Channel<T>`) или `BlockingCollection<T>`.

## lock и await

`await` внутри `lock` запрещён компилятором — ошибка CS1996 «Cannot await in the body of a lock statement», и для `Lock` тоже. Причина в привязке к потоку: после `await` продолжение может выполниться на другом потоке пула, и освобождать блокировку будет не владелец. Обходить запрет ручными `Monitor.Enter`/`Exit` нельзя: получите `SynchronizationLockException` и вечно захваченную блокировку.

`lock` до или после `await` в том же методе — нормально, если сама секция синхронная:

```csharp
var data = await LoadAsync(ct);
lock (_gate)
{
    _cache = data;
}
```

Если асинхронная операция должна быть внутри критической секции, нужен примитив без владельца — `SemaphoreSlim` с `WaitAsync`. Этому посвящена статья `Асинхронная синхронизация`.

## Правила хорошей критической секции

- **Короткая.** Внутри только работа с общим состоянием; вычисления, логирование, I/O и аллокации — снаружи.
- **Без чужого кода.** Событие, колбэк, виртуальный метод под блокировкой могут взять другую блокировку — прямой путь к deadlock. Под `lock` копируют нужное состояние, выходят и только потом вызывают обработчики.
- **Check-then-act целиком внутри.** Проверка и действие под одним захватом.
- **Ссылки на защищённые данные не уходят наружу.** Возвращать внутренний `List<T>` из-под `lock` — значит дать изменять его без блокировки; наружу отдают копию или неизменяемый снимок.

## Что стоит ответить на собеседовании

`lock` — синтаксис C#, который для обычного объекта разворачивается в `Monitor.Enter(obj, ref taken)` и `Monitor.Exit` в `finally`. Блокировка реентерабельна, привязана к потоку-владельцу, работает как полный барьер памяти и действует только внутри процесса. Без конкуренции это thin lock в заголовке объекта и одна атомарная операция — на .NET 10 около 5 нс; при конкуренции блокировка раздувается до sync block, потоки крутятся, засыпают и просыпаются, и шестнадцать потоков на общем `lock` работают в шесть раз медленнее одного.

Сильный ответ расскажет про `System.Threading.Lock` из .NET 9: `lock` по нему компилируется в `EnterScope()`, не использует заголовок объекта, а приведение к `object` молча возвращает `Monitor` с предупреждением CS9216. Объяснит, почему нельзя блокировать `this`, `typeof` и строки, зачем `Wait` проверяют в `while`, и почему `await` внутри `lock` — ошибка CS1996: продолжение может выполниться на другом потоке, а освободить `Monitor` может только владелец.
