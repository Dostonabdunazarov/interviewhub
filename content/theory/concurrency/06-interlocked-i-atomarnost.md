Атомарная операция для других потоков выглядит неделимой: они видят состояние либо до неё, либо после, но никогда промежуточное. Часть операций атомарна в .NET сама по себе, часть становится атомарной через `Interlocked`, а всё остальное требует блокировки. Граница между этими тремя группами — частый вопрос на собеседовании.

## Что атомарно само по себе

Спецификация CLI (ECMA-335) гарантирует атомарность чтения и записи для правильно выровненных значений размером не больше указателя:

| Операция | Атомарна? |
| --- | --- |
| чтение/запись `int`, `bool`, `char`, `float`, ссылки | да |
| чтение/запись `long`, `double` в 64-битном процессе | да на практике: выровнены и равны размеру указателя |
| чтение/запись `long`, `double` в 32-битном процессе | **нет** |
| чтение/запись `decimal`, `Guid`, своей структуры | **нет** |
| `x++`, `x += y` | **нет**: чтение, изменение, запись |
| `if (x == null) x = new()` | **нет**: проверка и действие разделены |

Неатомарная запись структуры даёт **torn read** — «разорванное» значение:

```csharp
struct Range { public long Start, End; }
private Range _range;
```

Если один поток присваивает `_range = new Range { Start = 10, End = 20 }`, другой может прочитать `Start = 10` и `End = 0`: половину нового значения и половину старого. Исправление — либо `lock`, либо неизменяемый **класс** вместо структуры: запись ссылки атомарна, и читатель увидит либо старый объект целиком, либо новый целиком.

Атомарность не означает видимость и порядок. Атомарная запись `int` гарантирует, что никто не увидит «половину» числа, но не гарантирует, когда и в каком порядке относительно других записей её увидит другой поток. Это отдельная тема — `volatile и барьеры памяти`.

## Interlocked

Статический класс с атомарными операциями над одной переменной:

| Метод | Что делает |
| --- | --- |
| `Increment`, `Decrement` | ±1, возвращает новое значение |
| `Add` | прибавляет, возвращает новое значение |
| `Exchange` | записывает новое, возвращает старое |
| `CompareExchange(ref x, value, comparand)` | записывает `value`, только если `x == comparand`; возвращает старое |
| `Read(ref long)` | атомарное чтение 64-битного значения в 32-битном процессе |
| `And`, `Or` | атомарные побитовые операции (.NET 5+) |

С .NET 9 `Exchange` и `CompareExchange` работают и с `byte`, `short`, перечислениями — проверено компиляцией на .NET 10.

На x86/x64 эти операции компилируются в инструкции с префиксом `lock` (`lock xadd`, `lock cmpxchg`), на ARM64 — в атомарные инструкции LSE (`ldadd`, `cas`) или в цикл load-exclusive/store-exclusive на процессорах без LSE. Процессор удерживает кэш-линию в эксклюзивном владении на время операции, и никакой другой поток не вклинится между чтением и записью. Кроме того, каждая операция `Interlocked` — **полный барьер памяти**.

```csharp
private long _requests;

public void OnRequest() => Interlocked.Increment(ref _requests);
public long Snapshot() => Interlocked.Read(ref _requests);
```

## Сколько стоит атомарность

В одном потоке `Interlocked.Increment` стоит около 2–2,5 нс против долей наносекунды у обычного `++` (замер Stopwatch на 32 млн операций, .NET 10, Ryzen 7 5800H). Это дёшево. Проблемы начинаются, когда в одну переменную пишут много ядер. Шестнадцать потоков по два миллиона инкрементов одного счётчика, медиана пяти прогонов:

```
Interlocked.Increment, общий счётчик     457 мс
те же 32 млн в одном потоке             70–85 мс
lock (object), общий счётчик            2553 мс
локальный счётчик + один Interlocked.Add   2,9 мс
```

Шестнадцать ядер с атомарным счётчиком в пять-шесть раз **медленнее одного**: каждое ядро должно забрать кэш-линию со счётчиком себе, и линия непрерывно пересылается между ядрами. Это не ошибка корректности — результат верный, — а предел масштабирования. `Interlocked` в пять раз быстрее `lock` под той же нагрузкой, но оба упираются в одну и ту же кэш-линию.

Лечится это не выбором примитива, а **шардированием**: каждый поток копит своё значение и сливает его один раз. Последняя строка — то же количество работы за 2,9 мс. У `Parallel.For` для этого есть перегрузка с `localInit`/`localFinally`:

```csharp
long total = 0;
Parallel.ForEach(items,
    () => 0L,
    (item, _, local) => local + Weight(item),
    local => Interlocked.Add(ref total, local));
```

## False sharing

Шардирование работает, только если шарды лежат в **разных** кэш-линиях. Протокол когерентности кэшей оперирует линиями по 64 байта, и если два ядра пишут в соседние, логически независимые переменные одной линии, линия ходит между ними так же, как при общем счётчике.

Восемь потоков, каждый сто миллионов раз пишет в **свой** элемент массива. .NET 10, три прогона:

```
соседние long в одном массиве     3240–6219 мс
каждый счётчик в своих 128 байтах   299–312 мс
разница                           ×10–21
```

Гонок нет, результат правильный, а работа в десять-двадцать раз медленнее. Исправление — паддинг:

```csharp
[StructLayout(LayoutKind.Explicit, Size = 128)]
struct PaddedLong
{
    [FieldOffset(0)] public long Value;
}

var counters = new PaddedLong[Environment.ProcessorCount];
```

128 байт, а не 64: соседние линии часто подкачиваются парами, а на части ARM-процессоров, включая Apple M-серии, сама линия 128 байт. False sharing не виден в коде — только в замере, где добавление потоков замедляет работу. BCL борется с ним сама: например, `ConcurrentQueue<T>` разносит индексы головы и хвоста паддингом.

## CAS-цикл

`CompareExchange` — основа любого lock-free кода. Любую операцию над одной переменной можно сделать атомарной циклом «прочитал — вычислил — записал, если никто не изменил»:

```csharp
static void UpdateMax(ref int target, int value)
{
    int current = Volatile.Read(ref target);
    while (value > current)
    {
        int seen = Interlocked.CompareExchange(ref target, value, current);
        if (seen == current) break;
        current = seen;
    }
}
```

Ключевая деталь — `CompareExchange` возвращает **фактическое** значение ячейки, и его нужно использовать для следующей попытки. Типичная ошибка — прочитать значение один раз до цикла и сравнивать с ним вечно:

```csharp
long current = _value;
while (Interlocked.CompareExchange(ref _value, current + 1, current) != current) { }
```

Если хоть раз кто-то изменил `_value`, `current` устарел навсегда, и цикл не завершится.

Второе ограничение — гарантия прогресса. Lock-free означает, что **кто-то** продвигается, а не что продвинется конкретный поток: под сильной конкуренцией отдельный поток может проигрывать CAS очень долго. Поэтому вычисление между чтением и CAS держат минимальным, а при неудаче делают паузу через `SpinWait`. Для простого инкремента CAS не нужен вовсе — `Interlocked.Increment` и `Add` выполняются одной инструкцией без повторов.

## ABA

CAS сравнивает значение, а не историю. Если поток прочитал `A`, другой поменял его на `B` и обратно на `A`, CAS первого пройдёт, хотя структура уже другая. Классическая жертва — lock-free стек: узел снят, переиспользован и снова положен на вершину, а «устаревший» поток ставит вершиной узел, который давно не в стеке.

В .NET для ссылок проблему во многом снимает GC: пока поток держит ссылку на узел, узел не будет собран и выделен заново по тому же адресу. ABA возвращается, как только узлы начинают **переиспользовать через пул** или вместо ссылок хранят индексы в массиве. Тогда рядом со значением хранят счётчик версий и сравнивают пару одним CAS по `long`. Для обычного числового счётчика ABA не проблема: число и есть всё состояние.

Главный вывод из ABA — не писать самописные lock-free структуры. `ConcurrentStack<T>` и `ConcurrentQueue<T>` уже содержат выверенные алгоритмы.

## Interlocked или lock

| Задача | Выбор |
| --- | --- |
| счётчик, метрика | `Interlocked.Increment` / `Add` |
| «запустить один раз» | `Interlocked.CompareExchange(ref _state, 1, 0) == 0` |
| публикация нового неизменяемого снимка | `Interlocked.Exchange` или `Volatile.Write` ссылки |
| два поля меняются вместе | `lock` |
| check-then-act над коллекцией | `lock` или атомарный метод concurrent-коллекции |

Две атомарные операции подряд не атомарны вместе:

```csharp
Interlocked.Add(ref _total, amount);
Interlocked.Increment(ref _count);
```

Между ними другой поток прочитает несогласованную пару и посчитает неверное среднее. Инвариант «`_total` и `_count` согласованы» охватывает две переменные — его защищает только `lock` или неизменяемый объект с обоими полями, заменяемый одним `CompareExchange` ссылки.

Практическое правило: начинать с `lock` — его корректность проще проверить. Переходить на `Interlocked`, когда состояние естественно сводится к одной переменной или замер показал конкуренцию на блокировке.

## Что стоит ответить на собеседовании

Атомарны сами по себе чтение и запись выровненных значений не больше указателя и ссылок; `long` в 32-битном процессе, `decimal` и структуры могут читаться «разорванными», а `x++` — всегда три операции. `Interlocked` делает атомарной одну операцию над одной переменной: на x64 это инструкции с префиксом `lock`, на ARM64 — атомики LSE, и каждая операция — полный барьер. Всё, что сложнее, строится CAS-циклом на `CompareExchange`, где важно брать для следующей попытки значение, которое вернул CAS.

Сильный ответ покажет пределы: шестнадцать потоков с `Interlocked.Increment` на одном счётчике на .NET 10 работают в пять-шесть раз медленнее одного потока из-за пересылки кэш-линии, а локальное накопление с одним слиянием делает ту же работу за 2,9 мс. Упомянет false sharing — соседние счётчики разных потоков замедлили работу в 10–21 раз, паддинг до 128 байт это убрал, — ABA-проблему и то, что инвариант из нескольких полей защищает только `lock`.
