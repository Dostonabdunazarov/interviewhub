Атомарность отвечает на вопрос, увидит ли другой поток значение целиком. Модель памяти отвечает на два других: **когда** он его увидит и **в каком порядке** относительно остальных записей. Ответ «сразу и в порядке строк кода» неверен: и JIT, и процессор переставляют обращения к памяти ради скорости. Пока код синхронизируется через `lock`, `Interlocked` и `Task`, это незаметно; флаг на обычном поле или самописная ленивая инициализация ломаются, причём по-разному на разном железе.

## Что гарантирует модель памяти

Базовая модель описана в ECMA-335 (раздел I.12.6) и намеренно слабая. CoreCLR даёт гарантии сильнее, и они записаны в документе `docs/design/specs/Memory-model.md` репозитория dotnet/runtime. Опираться стоит на них, а не на «у меня на x64 работает».

Гарантировано:

- **однопоточная согласованность** и **атомарность** выровненных обращений не больше указателя (см. `Interlocked и атомарность`);
- **volatile-чтение — acquire, volatile-запись — release**;
- **полный барьер** у всех методов `Interlocked`, `Thread.MemoryBarrier`, входа и выхода из `lock`;
- **зависимые чтения упорядочены**: прочитав ссылку и затем поле через неё, второе чтение не «обгонит» первое;
- **безопасная публикация объекта**: CoreCLR записывает ссылку на объект в кучу с release-семантикой, и другой поток не увидит объект с незаполненными полями. ECMA-335 этого не требует.

Не гарантировано всё остальное: в какой момент обычная запись одного потока станет видна другому и в каком порядке относительно других обычных записей.

## Acquire и release

Два слова, без которых тема не объясняется:

| Семантика | Что запрещает | В .NET |
| --- | --- | --- |
| acquire (при чтении) | переносить **последующие** операции выше этого чтения | `Volatile.Read`, чтение `volatile`-поля |
| release (при записи) | переносить **предыдущие** операции ниже этой записи | `Volatile.Write`, запись `volatile`-поля |
| полный барьер | любые перестановки через точку | `Interlocked.*`, `Thread.MemoryBarrier()`, `lock` |

Рассуждать надо не о «свежести», а о **парах синхронизации**: release-запись в одном потоке и acquire-чтение того же места в другом. Если чтение увидело значение, записанное release-записью, читателю видно всё, что писатель сделал до неё. Классический паттерн публикации:

```csharp
private int _data;
private bool _ready;

void Producer()
{
    _data = 42;
    Volatile.Write(ref _ready, true);
}

void Consumer()
{
    if (Volatile.Read(ref _ready))
        Console.WriteLine(_data);
}
```

Если `Consumer` увидел `true`, он гарантированно напечатает 42. Без `Volatile` гарантии нет: запись флага может стать видна раньше записи данных, а чтение данных — выполниться раньше чтения флага.

## Источник первый: JIT

JIT вправе считать, что поле меняет только текущий поток, и вынести чтение из цикла:

```csharp
private static bool _stop;

static void Worker()
{
    long n = 0;
    while (!_stop) n++;
}
```

Цикл компилируется как «прочитать `_stop` один раз и крутиться вечно». Проверено на .NET 10, Release: поток крутится секунду, затем главный поток выставляет флаг и ждёт две секунды.

```
обычное поле:   НЕ остановился за 2 с
volatile поле:  остановился
Volatile.Read:  остановился
```

Это единственный механизм, который даёт «вечно устаревшее» значение, и он чисто программный: кэши процессоров когерентны, и запись рано или поздно увидят все ядра — если код её перечитывает. `volatile` и `Volatile.Read` запрещают выносить такие чтения. В Debug баг не воспроизводится: JIT там не оптимизирует. А для флага остановки в прикладном коде правильный ответ вообще `CancellationToken` (см. `CancellationToken и таймауты`).

## Источник второй: процессор

Процессор выполняет инструкции не строго по порядку и складывает записи в **store buffer**, откуда они уходят в кэш позже. Что именно разрешено переставлять, зависит от архитектуры:

| Пара операций с разными адресами | x86/x64 (TSO) | ARM64 |
| --- | --- | --- |
| чтение → чтение | не переставляются | переставляются |
| запись → запись | не переставляются | переставляются |
| чтение → запись | не переставляются | переставляются |
| запись → чтение | **переставляются** | переставляются |
| зависимые чтения | упорядочены | упорядочены |

На x86 любая обычная загрузка уже имеет семантику acquire, а любое сохранение — release. Поэтому там volatile-обращения компилируются в обычные `mov` — проверено дизассемблером JIT на .NET 10, x64:

```
Volatile.Read(ref F)       mov  eax, dword ptr [F]
Volatile.Write(ref F, v)   mov  dword ptr [F], ecx
Thread.MemoryBarrier()     lock or dword ptr [rsp], 0
Interlocked.Exchange       xchg dword ptr [F], ecx
```

И по замеру BenchmarkDotNet volatile-чтение стоит те же 0,28 нс, что и обычное: на x64 его цена — только запрещённые оптимизации JIT. На ARM64 обычные `ldr`/`str` никакого порядка не дают, и JIT по документации runtime выдаёт для volatile-обращений `ldar`/`stlr` (на новых ядрах — `ldapr`), а для полного барьера — `dmb ish`. Это дороже обычных инструкций, но дешевле полного барьера; на ARM мы это не замеряли.

## Почему код с x86 ломается на ARM

Пример публикации выше без `Volatile`:

```csharp
_data = 42;
_ready = true;

if (_ready)
    Console.WriteLine(_data);
```

На x64 он почти всегда работает: процессор не переставляет запись-запись и чтение-чтение, а JIT в таком простом коде обычно ничего не трогает. На ARM64 ломаются обе стороны: писатель может сделать запись флага видимой раньше данных, читатель — прочитать `_data` спекулятивно раньше `_ready`. Напечатается 0.

Код был корректен не по модели памяти .NET, а по случайности железа. С серверами на Graviton и Ampere и Apple Silicon у разработчиков это перестало быть теорией: типичные жертвы переезда — самописные флаги, ленивая инициализация без `Lazy<T>`, spin-ожидание на обычном поле.

## Чего volatile не даёт

**Атомарности.** `volatile int _count; _count++` — по-прежнему чтение и запись, между которыми вклинится другой поток. Нужен `Interlocked.Increment`.

**Порядка «запись, затем чтение другой переменной».** Это единственная перестановка, которую делает даже x86, и volatile от неё не защищает. Протокол «выставил свой флаг — проверил чужой» (алгоритмы Деккера и Петерсона):

```csharp
x = 1;
r1 = y;

y = 1;
r2 = x;
```

Первые две строки выполняет один поток, вторые — другой. Интуитивно хотя бы один должен увидеть единицу. Замер на .NET 10, x64, 200 000 одновременных стартов через `Barrier`:

```
обычные поля            r1 == 0 && r2 == 0 в   459 прогонах
Volatile.Write/Read     r1 == 0 && r2 == 0 в 3 541 прогоне
Interlocked.Exchange    r1 == 0 && r2 == 0 в     0
Thread.MemoryBarrier    r1 == 0 && r2 == 0 в     0
```

Оба потока прочитали ноль: каждая запись ещё сидела в store buffer своего ядра, когда чтение уже выполнилось. `Volatile` не помог — release-запись и следующее acquire-чтение **другого** адреса переставлять разрешено. Помогает только полный барьер: `Interlocked.Exchange(ref x, 1)` вместо записи или `Thread.MemoryBarrier()` между записью и чтением.

## volatile-поле или Volatile.Read/Write

Модификатор и методы дают одну и ту же семантику, разница в охвате:

| | поле `volatile` | `Volatile.Read/Write` |
| --- | --- | --- |
| где действует | на каждое обращение к полю | только в точке вызова |
| типы | ссылки, `int` и меньше, `float`, `nint`, enum на их основе; **не** `long`/`double` | все примитивы, включая `long` и `double`, ссылки |
| видимость намерения | неявна | явна |

Современная рекомендация — методы: видно, какое обращение требует семантики, и нет соблазна написать `_count++` по volatile-полю в уверенности, что оно атомарно. Передача volatile-поля по `ref` даёт предупреждение CS0420; для `Interlocked` компилятор делает исключение (проверено на .NET 10 SDK).

## Двойная проверка блокировки

Самая известная ловушка, где всё это сходится:

```csharp
private static Config? _instance;
private static readonly Lock _gate = new();

public static Config Instance
{
    get
    {
        var local = Volatile.Read(ref _instance);
        if (local is not null) return local;
        lock (_gate)
        {
            local = _instance;
            if (local is null)
            {
                local = new Config();
                Volatile.Write(ref _instance, local);
            }
            return local;
        }
    }
}
```

Без `Volatile` по ECMA-335 читатель мог бы увидеть ссылку раньше полей объекта. В CoreCLR публикация ссылки и так имеет release-семантику, поэтому вариант без `Volatile` на нём работает. Но писать его незачем: `Lazy<T>` и `LazyInitializer.EnsureInitialized` делают то же правильно на любой реализации, а для статики хватает поля с инициализатором — статический конструктор выполняется один раз.

## Где барьеры уже стоят

Ручные барьеры в прикладном коде почти никогда не нужны, потому что их ставят примитивы:

- `lock`, `Monitor`, `System.Threading.Lock` — вход и выход;
- все методы `Interlocked`;
- `Thread.Start` и `Join`;
- запуск `Task`, её завершение и `await`: всё, что сделано до `Task.Run`, видно внутри, а всё, что сделано в задаче, видно после `await`;
- `SemaphoreSlim`, `ManualResetEventSlim`, `Barrier`, concurrent-коллекции и `Channel<T>`.

Например, результат, записанный в обычное поле внутри `Task.Run`, после `await` той задачи читается без всяких `volatile`. Ручные `Volatile.*` нужны для публикации снимка или флага, полный барьер — для «записал своё, проверил чужое», а всё остальное — забота тех, кто пишет сами примитивы и lock-free структуры.

## Что стоит ответить на собеседовании

Модель памяти .NET гарантирует атомарность выровненных обращений, однопоточную согласованность, acquire для volatile-чтения, release для volatile-записи и полный барьер у `Interlocked` и `lock`; порядок и момент видимости обычных записей не гарантированы. Переставляют обращения и JIT, и процессор. JIT выносит чтение поля из цикла — на .NET 10 цикл `while (!_stop)` на обычном поле в Release не остановился, с `volatile` и `Volatile.Read` остановился. Процессор x86 переставляет только запись с последующим чтением, ARM64 — почти всё, поэтому публикация «данные, затем флаг» без `Volatile` на x86 работает случайно, а на ARM ломается.

Сильный ответ объяснит, что `volatile` даёт порядок, но не атомарность и не порядок store→load: в замере на x64 протокол Деккера на `Volatile.Write/Read` провалился в 3541 случае из 200 000, а с `Interlocked.Exchange` и `Thread.MemoryBarrier` — ни разу. Покажет, что на x64 volatile-обращения — это обычные `mov`, а барьер — `lock or`. И скажет главное: в прикладном коде ручные барьеры не нужны, их уже ставят `lock`, `Interlocked`, `Task`/`await` и concurrent-коллекции; флаг остановки — это `CancellationToken`, ленивая инициализация — `Lazy<T>`.
