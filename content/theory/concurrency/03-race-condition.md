Race condition (состояние гонки) — ошибка, при которой результат зависит от того, в каком порядке и с каким наложением выполнились операции нескольких потоков. Это самый частый и самый неприятный дефект многопоточного кода: он не воспроизводится на машине разработчика, проходит тесты и вылезает под нагрузкой в продакшене.

## Классика: count++

```csharp
int counter = 0;
Parallel.For(0, 1_000_000, _ => counter++);
Console.WriteLine(counter);
```

Пять запусков на .NET 10, 16 логических ядер:

```
counter++:              252 814 | 209 952 | 107 779 | 109 575 | 88 866
Interlocked.Increment:  1 000 000 во всех пяти
```

Потеряно от 75 до 91% инкрементов. Причина в том, что `counter++` — не одна операция, а три: прочитать значение, прибавить единицу, записать обратно.

```
Поток A:  read 42 ── add ──────────── write 43
Поток B:       read 42 ── add ── write 43
```

Оба потока прочитали 42, оба записали 43 — один инкремент исчез. Чем больше ядер и чем плотнее цикл, тем больше таких наложений: здесь шестнадцать потоков бьют в одну ячейку, и большая часть записей перетирает друг друга.

Исправление для одной переменной — атомарная операция `Interlocked.Increment(ref counter)`, которая выполняет все три шага неделимо (подробнее — в статье `Interlocked и атомарность`).

## Виды гонок

**Read-modify-write.** `count++`, `total += x`, `flags |= mask` — чтение и запись разнесены, между ними вклинивается другой поток.

**Check-then-act.** Проверка и действие — две операции, и условие может перестать быть верным между ними:

```csharp
if (_balance >= amount)
    _balance -= amount;
```

Эксперимент: баланс 100, восемь потоков стартуют одновременно через `Barrier` и пытаются списать по 100. Между проверкой и списанием — несколько десятков холостых итераций, имитирующих работу:

```
успешных списаний: 1, баланс 0
успешных списаний: 2, баланс −100
успешных списаний: 3, баланс −200
```

Корректный результат получился только в одном прогоне из трёх. Сюда же относятся `if (!dict.ContainsKey(k)) dict.Add(k, v)` и ленивая инициализация без синхронизации: два потока видят `null` и оба создают объект.

**Гонки на публикации.** Один поток заполняет данные и выставляет флаг «готово», другой читает флаг и данные. Без барьеров памяти читатель может увидеть флаг раньше данных — эта гонка зависит от модели памяти и процессора и разобрана в статье `volatile и барьеры памяти`.

## Коллекции под гонкой

Обычные коллекции BCL не потокобезопасны при записи, и гонка в них портит внутреннюю структуру, а не одно значение. Миллион `List<T>.Add` из `Parallel.For`, три прогона на .NET 10:

```
List.Add параллельно: Count = 71 743 из 1 000 000
List.Add параллельно: Count = 106 130
List.Add параллельно: ArgumentException: Source array was not long enough
```

В одних прогонах элементы молча теряются, в других список падает посреди роста внутреннего массива. С `Dictionary` хуже: при параллельной записи он бросает `IndexOutOfRangeException` и теряет почти всё содержимое (замеры — в статье `Конкурентные коллекции`).

Одновременное **чтение** из `List<T>` и `Dictionary` безопасно, если никто не пишет. Это документированный контракт: статические члены типов BCL потокобезопасны, экземплярные — нет, кроме специально оговорённых случаев.

## Data race и race condition

Термины близкие, но не одинаковые.

**Data race** — одновременный доступ к одной ячейке памяти из нескольких потоков без синхронизации, хотя бы один доступ — запись. Это свойство уровня памяти.

**Race condition** — логическая ошибка порядка. Она возможна и без data race: каждая операция по отдельности синхронизирована, но их комбинация — нет.

```csharp
var cache = new ConcurrentDictionary<string, Data>();

if (!cache.ContainsKey(key))
    cache[key] = Load(key);

var value = cache.GetOrAdd(key, Load);
```

В первом варианте обе операции `ConcurrentDictionary` атомарны и data race нет, но между `ContainsKey` и записью другой поток успеет сделать то же самое — `Load` выполнится дважды, второе значение перезапишет первое. Второй вариант — одна атомарная операция. То же с `if (queue.Count > 0) queue.Dequeue()`: правильно `TryDequeue`.

Это главная ловушка понятия «потокобезопасный тип»: **потокобезопасные операции не складываются в потокобезопасную комбинацию.** Гарантия всегда относится к контракту — каким операциям и в каком сочетании можно доверять.

## Как устранять

От простого к сложному:

| Ситуация | Решение |
| --- | --- |
| состояние можно не делить | локальные данные на поток или запрос, слияние в конце |
| данные читают все, меняют редко | неизменяемый объект и атомарная замена ссылки |
| одна переменная | `Interlocked.Increment`, `Add`, `CompareExchange` |
| check-then-act над коллекцией | атомарные методы: `GetOrAdd`, `AddOrUpdate`, `TryAdd`, `TryDequeue` |
| несколько связанных полей | `lock` вокруг всего инварианта |
| ленивая инициализация | `Lazy<T>`, `LazyInitializer.EnsureInitialized` |

Лучшая синхронизация — та, которой нет. Если потоки не делят изменяемое состояние, гонке негде случиться: неизменяемые объекты (`record` с `init`-свойствами, `ImmutableArray<T>`, `string`) можно читать из любых потоков без блокировок, а изменение — это новый объект (см. `class, struct и record`).

Для исправленного примера со списанием достаточно поместить проверку и действие под одну блокировку:

```csharp
private readonly Lock _gate = new();
private decimal _balance;

public bool TryWithdraw(decimal amount)
{
    lock (_gate)
    {
        if (_balance < amount) return false;
        _balance -= amount;
        return true;
    }
}
```

Важно, что **все** обращения к `_balance`, включая чтение, идут под тем же `_gate`. Одно «просто чтение» без блокировки — и инвариант снова не защищён.

## Почему гонку трудно найти

Гонка требует, чтобы два потока попали в узкое окно времени. На машине разработчика мало ядер и мало нагрузки, в Debug другие тайминги, а JIT в Release выполняет оптимизации, которые меняют картину. В продакшене под нагрузкой то же окно попадается раз в сутки. Тест «запустил десять раз — прошло» ничего не доказывает.

Приёмы, которые превращают «раз в сутки» в «каждый прогон»:

- **одновременный старт** через `Barrier` или `ManualResetEventSlim`: без него потоки часто стартуют по очереди и не пересекаются;
- **тысячи итераций**, потоков больше, чем ядер, сборка в Release;
- **расширение окна гонки** — тестовый шов, вставляющий задержку между проверкой и действием;
- **прогон на ARM64**: слабая модель памяти проявляет ошибки упорядочивания, скрытые на x86;
- **систематический перебор чередований** — Microsoft Coyote берёт планирование задач под контроль и воспроизводит найденный баг по сохранённому трейсу.

Аналога ThreadSanitizer, автоматически находящего data race в управляемом коде, в .NET нет. Поэтому основной вес ложится на дизайн и ревью: общее изменяемое поле без синхронизации, check-then-act, чтение вне `lock`, мутабельное `static`-состояние — первые подозреваемые.

## Что стоит ответить на собеседовании

Race condition — ошибка, при которой результат зависит от порядка и наложения операций нескольких потоков. Классический пример — `count++`: это чтение, сложение и запись, и на .NET 10 миллион инкрементов из `Parallel.For` дают от 89 до 253 тысяч. Виды гонок — read-modify-write, check-then-act и гонки на публикации; исправляются атомарными операциями `Interlocked`, атомарными методами коллекций, `lock` вокруг всего инварианта, а лучше всего — отказом от общего изменяемого состояния.

Сильный ответ различит data race и race condition и покажет, что потокобезопасные операции не дают потокобезопасной комбинации: `ContainsKey` плюс индексатор у `ConcurrentDictionary` всё равно гонка, нужен `GetOrAdd`. И объяснит, как ловить редкую гонку: одновременный старт через `Barrier`, тысячи итераций в Release, расширение окна, прогон на ARM64 и Coyote, — потому что ThreadSanitizer для .NET нет.
