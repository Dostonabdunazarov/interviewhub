## Что такое Big O?

```yaml
category: algorithms
level: middle
difficulty: 2
slug: algorithms-chto-takoe-big-o
tags: complexity
```

Big O — это асимптотическая верхняя оценка того, как растёт время работы (или память) алгоритма при росте размера входа `n`. Она отвечает не на вопрос «сколько миллисекунд», а на вопрос «во сколько раз станет медленнее, если данных станет в 10 раз больше».

**Что отбрасывается:**

- **Константы.** `3n + 100` и `n` — оба O(n). Константа зависит от железа, JIT и кэшей, а форма роста — нет.
- **Младшие слагаемые.** `n² + n log n + n` — это O(n²): при большом `n` доминирует старший член.
- **Основание логарифма.** `log₂ n` и `log₁₀ n` отличаются в константу раз, поэтому пишут просто O(log n).

**Родственные обозначения**, которые иногда спрашивают:

| Обозначение | Смысл |
| --- | --- |
| O(f) | растёт не быстрее f (верхняя граница) |
| Ω(f) | растёт не медленнее f (нижняя граница) |
| Θ(f) | растёт ровно как f (и сверху, и снизу) |

В разговоре «O(n)» обычно подразумевают именно Θ — точную оценку.

**Худший, средний, амортизированный случай.** Это разные вещи, и их важно называть явно:

- `Dictionary.TryGetValue` — O(1) в среднем, O(n) в худшем (все ключи в одной корзине);
- quicksort — O(n log n) в среднем, O(n²) в худшем;
- `List<T>.Add` — O(1) амортизированно: изредка массив копируется за O(n), но в пересчёте на одну операцию выходит константа.

**Чего Big O не говорит.** Для маленьких `n` алгоритм O(n²) с хорошей локальностью может обогнать O(n log n): именно поэтому `Array.Sort` для участков до 16 элементов переключается на сортировку вставками. Линейный проход по массиву бывает быстрее поиска в `Dictionary` на 5–10 элементах. Big O — инструмент для выбора подхода при росте данных, а не замена профилированию.

## Как оценить сложность алгоритма?

```yaml
category: algorithms
level: middle
difficulty: 3
slug: algorithms-kak-ocenit-slozhnost-algoritma
tags: complexity
```

Нужно посчитать, сколько раз выполняется самая «тяжёлая» операция в зависимости от размера входа, и оставить только старший член. На практике это сводится к нескольким правилам для циклов, вызовов и рекурсии.

**Базовые правила:**

- **Последовательные блоки складываются**, остаётся максимум: O(n) + O(n²) = O(n²).
- **Вложенные циклы перемножаются**: цикл по `n` внутри цикла по `m` — O(n·m).
- **Цикл, где шаг делит/умножает счётчик** (`i *= 2`, `hi = mid`) — O(log n).
- **Вызов метода внутри цикла** — умножайте на его сложность. Это самая частая ловушка.

```csharp
// Выглядит как O(n), на деле O(n²): Contains у List — линейный поиск
foreach (var x in items)
    if (!result.Contains(x)) result.Add(x);

// O(n): HashSet.Add — O(1) в среднем
var seen = new HashSet<int>();
foreach (var x in items) seen.Add(x);
```

**Скрытые затраты в .NET**, которые стоит видеть в коде:

| Операция | Сложность |
| --- | --- |
| `list.Insert(0, x)`, `list.RemoveAt(0)` | O(n) — сдвиг массива |
| `list.Contains`, `IndexOf`, `Remove(x)` | O(n) |
| `string +=` в цикле | O(n²) суммарно — каждый раз новая строка |
| `enumerable.Count()` на не-коллекции | O(n) |
| `ToList()`, `ToArray()`, `OrderBy` | O(n) / O(n log n) и аллокация |
| `ElementAt(i)` на `IEnumerable` | O(i) |

**Рекурсия** оценивается через рекуррентное соотношение:

- `T(n) = T(n/2) + O(1)` → O(log n) (бинарный поиск);
- `T(n) = 2T(n/2) + O(n)` → O(n log n) (mergesort);
- `T(n) = T(n-1) + T(n-2)` → O(2ⁿ) (наивный Фибоначчи);
- в общем виде — дерево вызовов: число узлов × работа в узле. Для деления пополам работает мастер-теорема.

**Амортизированный анализ.** Если дорогая операция случается редко (перевыделение в `List<T>` при удвоении), считаем суммарную стоимость серии операций и делим на их число: n добавлений стоят O(n), значит одно — O(1).

**Несколько входов — несколько переменных.** Если на вход два массива, пишите O(n + m) или O(n·m), а не «O(n)». Интервьюеры это замечают.

**Память** оценивается так же: дополнительные коллекции, копии и глубина стека рекурсии.

## Что такое O(1), O(log n), O(n), O(n log n), O(n²)?

```yaml
category: algorithms
level: middle
difficulty: 2
slug: algorithms-chto-takoe-o-1-o-log-n-o-n-o-n-log-n-o-n
tags: complexity
```

Это основные классы роста — от «не зависит от размера входа» до «растёт квадратично». Полезно знать и типичные примеры каждого, и порядок чисел при `n = 1 000 000`.

| Класс | Название | Операций при n = 10⁶ | Типичный пример |
| --- | --- | --- | --- |
| O(1) | константа | 1 | `array[i]`, `Dictionary` get/set, `Stack.Push` |
| O(log n) | логарифм | ~20 | бинарный поиск, `SortedSet.Add`, операции кучи |
| O(n) | линейная | 10⁶ | один проход, `List.Contains`, `Sum()` |
| O(n log n) | линейно-логарифмическая | ~2·10⁷ | `Array.Sort`, `OrderBy`, mergesort |
| O(n²) | квадратичная | 10¹² | вложенные циклы, bubble sort, `Contains` в цикле |

**O(1)** — количество шагов не зависит от `n`. Не значит «быстро»: хеширование длинной строки тоже O(1) относительно числа элементов, но не бесплатно.

**O(log n)** — на каждом шаге задача уменьшается в константу раз. Удвоение данных добавляет один шаг: миллиард элементов — около 30 сравнений.

**O(n)** — каждый элемент обрабатывается константное число раз. Нижняя граница для любой задачи, где нужно посмотреть все данные (найти максимум, посчитать сумму).

**O(n log n)** — обычно «разделяй и властвуй»: log n уровней, на каждом O(n) работы. Это доказанная нижняя граница для сортировки сравнениями.

**O(n²)** — каждую пару элементов. На 10⁴ элементов ещё терпимо (10⁸ операций — доли секунды), на 10⁶ — уже часы.

**Бывают и другие:** O(n + m) (граф: вершины + рёбра), O(2ⁿ) (перебор подмножеств), O(n!) (перебор перестановок), O(√n) (проверка на простоту).

**Правило для собеседования:** увидев решение O(n²), спросите себя, нельзя ли сделать O(n log n) сортировкой или O(n) хеш-таблицей — чаще всего можно, ценой O(n) памяти.

## Сложность поиска в `Dictionary`?

```yaml
category: algorithms
level: middle
difficulty: 3
slug: algorithms-slozhnost-poiska-v-dictionary
tags: collections, complexity
```

Поиск по ключу в `Dictionary<TKey, TValue>` — **O(1) в среднем** и **O(n) в худшем случае**, когда много ключей попадает в одну корзину. Поиск по значению (`ContainsValue`) всегда O(n) — это полный перебор.

**Как устроен поиск:**

1. Вычисляется `comparer.GetHashCode(key)`.
2. По хешу берётся номер корзины: остаток от деления на размер массива корзин (он — простое число).
3. Из корзины начинается цепочка записей в массиве `_entries`; для каждой сравнивается **сначала сохранённый хеш**, и только при совпадении — `Equals`.

Пока хеш-функция хорошо распределяет ключи и цепочки короткие, шагов константное число.

| Операция | Средний случай | Худший случай |
| --- | --- | --- |
| `TryGetValue`, `ContainsKey`, индексатор | O(1) | O(n) |
| `Add`, `this[key] = v` | O(1) амортизированно | O(n) (рост + перехеширование или коллизии) |
| `Remove` | O(1) | O(n) |
| `ContainsValue` | O(n) | O(n) |
| перечисление | O(n) | O(n) |

**Откуда берётся худший случай:**

- плохой `GetHashCode` — например, константа или хеш только по одному полю с малым разбросом значений: словарь превращается в связный список;
- изменяемый ключ: объект поменяли после добавления, хеш другой — запись «потерялась» (это уже не про скорость, а про корректность);
- для строковых ключей .NET по умолчанию использует рандомизированный хеш, что защищает от атак подбором коллизий.

**Цена O(1) не нулевая.** Каждый поиск — вызов `GetHashCode` (для строки — проход по всем символам) и минимум один `Equals`. Для 3–5 элементов линейный поиск по массиву может оказаться быстрее. Для неизменяемых справочников, которые много читают, есть `FrozenDictionary` (.NET 8), который тратит время при создании на подбор оптимальной раскладки и быстрее на чтение.

**Сравнение с альтернативами:** `SortedDictionary` (красно-чёрное дерево) и `SortedList` (бинарный поиск по массиву) дают O(log n) на поиск, зато хранят ключи упорядоченно.

## Сложность поиска в `List`?

```yaml
category: algorithms
level: middle
difficulty: 3
slug: algorithms-slozhnost-poiska-v-list
tags: complexity
```

Доступ по индексу `list[i]` — **O(1)**, потому что внутри `List<T>` — обычный массив. Поиск по значению (`Contains`, `IndexOf`, `Find`, `Remove(item)`) — **O(n)**: список ничего не знает о порядке элементов и перебирает их подряд.

| Операция | Сложность | Комментарий |
| --- | --- | --- |
| `list[i]` | O(1) | адресная арифметика по массиву |
| `Contains`, `IndexOf`, `LastIndexOf` | O(n) | сравнение через `EqualityComparer<T>.Default` |
| `Find`, `FindIndex`, `Exists` | O(n) | предикат на каждый элемент |
| `BinarySearch` | O(log n) | **только если список отсортирован** тем же компаратором |
| `Any(x => ...)`, `FirstOrDefault` (LINQ) | O(n) | то же самое плюс делегат |

**Когда это становится проблемой.** Один `Contains` на тысячу элементов — ничто. Но `Contains` внутри цикла по другой коллекции даёт O(n·m):

```csharp
// O(n·m)
var common = orders.Where(o => vipIds.Contains(o.CustomerId)).ToList();

// O(n + m): один раз строим HashSet
var vip = vipIds.ToHashSet();
var common2 = orders.Where(o => vip.Contains(o.CustomerId)).ToList();
```

**Варианты ускорения:**

- много поисков по значению → `HashSet<T>` или `Dictionary<TKey, T>` (O(1) в среднем);
- нужен и порядок, и быстрый поиск → отсортировать один раз (O(n log n)) и дальше `BinarySearch` (O(log n)), либо `SortedSet<T>`;
- мало элементов (единицы–десятки) → оставить `List`: линейный проход по массиву с хорошей локальностью кэша очень быстрый.

**Нюанс для value types.** `Contains` для `List<int>` и других примитивов в современных .NET векторизован (сравнивает сразу несколько элементов через SIMD), поэтому константа маленькая — но асимптотика всё равно линейная.

**Нюанс для своих типов.** Для классов `Contains` без переопределённого `Equals` сравнивает ссылки, а не содержимое — частая причина «не находит, хотя объект такой же».

## Сложность добавления элемента в `List`?

```yaml
category: algorithms
level: middle
difficulty: 3
slug: algorithms-slozhnost-dobavleniya-elementa-v-list
tags: complexity
```

`Add` в конец — **O(1) амортизированно**: обычно элемент просто пишется в свободную ячейку массива, но когда место кончается, создаётся массив вдвое больше и всё копируется за O(n). Вставка в середину или начало (`Insert`) — **O(n)** всегда, потому что хвост сдвигается.

**Как растёт ёмкость.** Первое добавление в пустой список создаёт массив на 4 элемента, дальше — удвоение: 4, 8, 16, 32, … До 1000 элементов — девять перевыделений.

**Почему амортизированно O(1).** При удвоении суммарная стоимость копирований для n добавлений: n/2 + n/4 + n/8 + … < n. Значит, n операций `Add` стоят O(n), а одна — O(1) в среднем по серии. При этом **отдельный** `Add`, попавший на перевыделение, стоит O(n) — это важно для задач с жёсткой латентностью.

| Операция | Сложность |
| --- | --- |
| `Add(x)` | O(1) амортизированно, O(n) в худшем |
| `AddRange(collection)` | O(k), если коллекция — `ICollection<T>` (одно перевыделение); иначе поэлементно |
| `Insert(0, x)` / `Insert(i, x)` | O(n − i) — сдвиг хвоста через `Array.Copy` |
| `RemoveAt(Count - 1)` | O(1) |
| `RemoveAt(0)` | O(n) |

**Практические выводы:**

- **Знаете размер — задайте `capacity`.** `new List<T>(expected)` убирает все промежуточные перевыделения и мусор от выброшенных массивов.
- **Нужна вставка в начало** — возьмите `Queue<T>`/`Stack<T>` или `LinkedList<T>`, а не `Insert(0, …)` в цикле (это O(n²) на серию).
- **Удаление в цикле по индексу** — идите с конца или используйте `RemoveAll(predicate)`, который делает один проход за O(n).
- Список не уменьшается сам после удаления элементов; `TrimExcess()` освобождает лишнюю ёмкость.

**Для сравнения:** `LinkedList<T>.AddFirst/AddLast` — честное O(1) без амортизации, но с аллокацией узла на каждый элемент и плохой локальностью. На практике `List<T>` почти всегда быстрее.

## Как работает binary search?

```yaml
category: algorithms
level: middle
difficulty: 3
slug: algorithms-kak-rabotaet-binary-search
tags: complexity
```

Бинарный поиск работает на **отсортированном** массиве: сравниваем искомое значение с серединой диапазона и отбрасываем ту половину, где его быть не может. Повторяем, пока диапазон не опустеет или элемент не найдётся.

```csharp
static int BinarySearch(int[] a, int target)
{
    int lo = 0, hi = a.Length - 1;          // ищем в [lo, hi]
    while (lo <= hi)
    {
        int mid = lo + (hi - lo) / 2;        // без переполнения
        if (a[mid] == target) return mid;
        if (a[mid] < target) lo = mid + 1;
        else hi = mid - 1;
    }
    return ~lo;                               // как в .NET: побитовое дополнение точки вставки
}
```

**Типичные ошибки:**

- `(lo + hi) / 2` переполняется при больших индексах — пишите `lo + (hi - lo) / 2` или `(int)((uint)lo + (uint)hi >> 1)`, как в исходниках .NET;
- путаница границ: при полуинтервале `[lo, hi)` условие `lo < hi` и `hi = mid`, при закрытом `[lo, hi]` — `lo <= hi` и `hi = mid - 1`. Смешение даёт бесконечный цикл или пропуск элемента;
- поиск на неотсортированных данных — результат просто неверный, без исключения.

**Вариант «найти первую позицию, где условие истинно»** (lower bound) — самый полезный на практике: первое вхождение дубликата, точка вставки, поиск по ответу.

```csharp
// первый индекс, где a[i] >= target (или a.Length)
static int LowerBound(int[] a, int target)
{
    int lo = 0, hi = a.Length;               // [lo, hi)
    while (lo < hi)
    {
        int mid = lo + (hi - lo) / 2;
        if (a[mid] < target) lo = mid + 1; else hi = mid;
    }
    return lo;
}
```

**В .NET готовое:** `Array.BinarySearch`, `List<T>.BinarySearch`, `MemoryExtensions.BinarySearch` для `Span<T>`/`ReadOnlySpan<T>`. Если элемент не найден, возвращается **отрицательное** число — побитовое дополнение индекса, куда его надо вставить: `int i = list.BinarySearch(x); if (i < 0) list.Insert(~i, x);`. При дубликатах возвращается индекс *какого-то* из равных, не обязательно первого.

**Где применяется помимо массивов:** поиск по ответу (минимальная скорость, при которой успеваем, — если проверка монотонна), `git bisect`, поиск в B-деревьях индексов БД, `SortedList<TKey, TValue>` внутри.

## Какая сложность binary search?

```yaml
category: algorithms
level: middle
difficulty: 3
slug: algorithms-kakaya-slozhnost-binary-search
tags: complexity
```

**O(log n) по времени и O(1) по памяти** в итеративной версии. Каждое сравнение делит диапазон пополам, поэтому после k шагов остаётся n / 2ᵏ элементов, и до одного элемента доходим за k = log₂ n шагов.

| n | Максимум сравнений |
| --- | --- |
| 1 000 | 10 |
| 1 000 000 | 20 |
| 1 000 000 000 | 30 |

**Разбивка по случаям:**

| Случай | Время |
| --- | --- |
| лучший (элемент ровно в середине) | O(1) |
| средний и худший | O(log n) |
| память, итеративно | O(1) |
| память, рекурсивно | O(log n) — глубина стека |

Рекуррентно: `T(n) = T(n/2) + O(1)` → O(log n).

**Важные оговорки, которые ждут на собеседовании:**

- **Нужна сортировка.** Если данные не отсортированы, сначала сортировка за O(n log n). Для одного поиска это хуже линейного O(n). Бинарный поиск окупается, когда поисков много: k поисков стоят O(n log n + k log n) против O(k·n).
- **Нужен произвольный доступ за O(1).** На связном списке бинарный поиск бессмыслен: дойти до середины — уже O(n).
- **Сравнение не всегда O(1).** Для строк сравнение стоит O(длины), итого O(L · log n).
- **Вставка в отсортированный массив остаётся O(n)** — найти место можно за log n, но сдвиг элементов линейный. Если нужны и частые вставки, и поиск, берите сбалансированное дерево: `SortedSet<T>` / `SortedDictionary<TKey, TValue>` (красно-чёрное дерево, O(log n) на всё).

**Сравнение с хешированием:** `HashSet.Contains` — O(1) в среднем, но бинарный поиск умеет то, чего хеш-таблица не может: найти ближайший элемент, нижнюю/верхнюю границу, диапазон `[a, b]`.

## Как работает bubble sort?

```yaml
category: algorithms
level: middle
difficulty: 3
slug: algorithms-kak-rabotaet-bubble-sort
tags: complexity
```

Пузырьковая сортировка многократно проходит по массиву и меняет местами соседние элементы, стоящие в неправильном порядке. После каждого прохода самый большой из оставшихся элементов «всплывает» в конец, поэтому следующий проход можно делать на один элемент короче.

```csharp
static void BubbleSort(int[] a)
{
    for (int end = a.Length - 1; end > 0; end--)
    {
        bool swapped = false;
        for (int i = 0; i < end; i++)
        {
            if (a[i] > a[i + 1])
            {
                (a[i], a[i + 1]) = (a[i + 1], a[i]);
                swapped = true;
            }
        }
        if (!swapped) break;      // проход без обменов — массив уже отсортирован
    }
}
```

Пример на `[5, 1, 4, 2]`: первый проход → `[1, 4, 2, 5]` (пятёрка всплыла), второй → `[1, 2, 4, 5]`, третий проход без обменов — выход.

| Характеристика | Значение |
| --- | --- |
| худший и средний случай | O(n²) сравнений и обменов |
| лучший случай (уже отсортирован, с флагом `swapped`) | O(n) |
| дополнительная память | O(1), сортирует на месте |
| стабильность | стабильна — равные элементы не меняются местами (строгое `>`) |

**Зачем её знать, если она медленная:**

- как базовый пример O(n²) и анализа сложности;
- чтобы объяснить оптимизации: ранний выход по флагу, сокращение границы прохода, «шейкерная» сортировка в обе стороны;
- чтобы сравнить со вставками: у обеих O(n²), но **insertion sort** на практике заметно быстрее (меньше записей) и хороша на почти отсортированных и маленьких массивах — поэтому именно её, а не пузырёк, использует `Array.Sort` для коротких участков (до 16 элементов).

**В продакшене не используется.** В .NET есть `Array.Sort` / `List<T>.Sort` (introsort, O(n log n)) и `OrderBy` (стабильная, O(n log n)) — писать свою сортировку почти никогда не нужно.

## Как работает quicksort?

```yaml
category: algorithms
level: middle
difficulty: 3
slug: algorithms-kak-rabotaet-quicksort
tags: complexity
```

Quicksort выбирает опорный элемент (pivot), переставляет массив так, чтобы слева оказались элементы меньше опорного, а справа — больше (partition), и рекурсивно сортирует обе части. Вся работа делается при разбиении, «склеивать» результат не нужно — сортировка идёт на месте.

```csharp
static void QuickSort(int[] a) => QuickSort(a, 0, a.Length - 1);

static void QuickSort(int[] a, int lo, int hi)
{
    while (lo < hi)
    {
        int p = Partition(a, lo, hi);
        // рекурсия в меньшую часть, цикл по большей — стек не глубже O(log n)
        if (p - lo < hi - p) { QuickSort(a, lo, p - 1); lo = p + 1; }
        else                 { QuickSort(a, p + 1, hi); hi = p - 1; }
    }
}

// Схема Ломуто; pivot — средний элемент, переносим его в конец
static int Partition(int[] a, int lo, int hi)
{
    int mid = lo + (hi - lo) / 2;
    (a[mid], a[hi]) = (a[hi], a[mid]);
    int pivot = a[hi], i = lo;
    for (int j = lo; j < hi; j++)
        if (a[j] < pivot) { (a[i], a[j]) = (a[j], a[i]); i++; }
    (a[i], a[hi]) = (a[hi], a[i]);   // pivot на своё окончательное место
    return i;
}
```

| Характеристика | Значение |
| --- | --- |
| средний случай | O(n log n) |
| худший случай | O(n²) — pivot всё время минимальный или максимальный |
| память | O(log n) на стек (с рекурсией в меньшую часть) |
| стабильность | нестабильна |

**Откуда O(n²).** Если опорный элемент каждый раз оказывается крайним, разбиение даёт части размером 0 и n−1, и глубина рекурсии становится n. Классический случай — первый/последний элемент как pivot на уже отсортированном массиве. Защита: случайный pivot или медиана трёх (первый, средний, последний).

**Много одинаковых элементов** тоже бьют по Ломуто. Решение — трёхпутевое разбиение (Dutch national flag: `< pivot`, `== pivot`, `> pivot`) или схема Хоара.

**Как это сделано в .NET.** `Array.Sort`, `List<T>.Sort` и `Span<T>.Sort` используют **introsort**: quicksort с медианой трёх, на участках до 16 элементов — сортировка вставками, а если глубина рекурсии превышает ~2·log₂ n — переключение на heapsort. Так гарантируется O(n log n) в худшем случае. Результат нестабилен; если нужна стабильность — `OrderBy`.

**Почему quicksort быстрый на практике:** последовательный доступ к памяти, работа на месте без аллокаций, маленькая константа внутреннего цикла.

## Как работает mergesort?

```yaml
category: algorithms
level: middle
difficulty: 3
slug: algorithms-kak-rabotaet-mergesort
tags: complexity
```

Mergesort делит массив пополам, рекурсивно сортирует обе половины и **сливает** две отсортированные половины в одну за линейное время. Основная работа — в слиянии, само деление тривиально.

```csharp
static void MergeSort(int[] a)
{
    var buf = new int[a.Length];           // один буфер на всю сортировку
    Sort(a, buf, 0, a.Length);
}

static void Sort(int[] a, int[] buf, int lo, int hi)   // [lo, hi)
{
    if (hi - lo < 2) return;
    int mid = lo + (hi - lo) / 2;
    Sort(a, buf, lo, mid);
    Sort(a, buf, mid, hi);
    Merge(a, buf, lo, mid, hi);
}

static void Merge(int[] a, int[] buf, int lo, int mid, int hi)
{
    int i = lo, j = mid, k = lo;
    while (i < mid && j < hi)
        buf[k++] = a[i] <= a[j] ? a[i++] : a[j++];   // <= сохраняет стабильность
    while (i < mid) buf[k++] = a[i++];
    while (j < hi)  buf[k++] = a[j++];
    Array.Copy(buf, lo, a, lo, hi - lo);
}
```

| Характеристика | Значение |
| --- | --- |
| время — лучший, средний, худший | O(n log n) всегда |
| дополнительная память | O(n) на буфер + O(log n) стек |
| стабильность | стабильна (при `<=` в слиянии) |

**Почему O(n log n).** Уровней деления — log₂ n, на каждом уровне все слияния вместе обрабатывают n элементов. Рекуррентно `T(n) = 2T(n/2) + O(n)`.

**Где mergesort выигрывает:**

- **нужна стабильность** — порядок равных элементов сохраняется (сортировка сначала по дате, потом по имени);
- **гарантия худшего случая** — нет вырождения, как у quicksort;
- **связные списки** — слияние делается перестановкой указателей, без буфера, и не нужен произвольный доступ;
- **внешняя сортировка** — данные не помещаются в память: сортируем куски, пишем на диск, потом сливаем k-путевым слиянием. Так работают сортировки в СУБД и `sort` в Unix.

**Оптимизации:** сортировка вставками для маленьких кусков, пропуск слияния, если `a[mid - 1] <= a[mid]` (половины уже по порядку), bottom-up вариант без рекурсии. На этих идеях построен **Timsort** (Python, Java для объектов).

**В .NET.** `Array.Sort` — не mergesort, а нестабильный introsort. Стабильную сортировку даёт LINQ `OrderBy`/`ThenBy`: он сортирует массив индексов и при равенстве ключей сравнивает исходные позиции.

## Чем quicksort отличается от mergesort?

```yaml
category: algorithms
level: middle
difficulty: 3
slug: algorithms-chem-quicksort-otlichaetsya-ot-mergesort
tags: complexity
```

Оба алгоритма — «разделяй и властвуй» со средней сложностью O(n log n), но работу делают в разных местах: quicksort — **при разбиении** (до рекурсии), mergesort — **при слиянии** (после рекурсии). Отсюда все остальные различия.

| | Quicksort | Mergesort |
| --- | --- | --- |
| средний случай | O(n log n) | O(n log n) |
| худший случай | O(n²) | O(n log n) |
| дополнительная память | O(log n) стек, на месте | O(n) буфер |
| стабильность | нет | да |
| доступ к памяти | произвольный внутри подмассива, но локальный | последовательный |
| связные списки | неудобен | отлично подходит, без буфера |
| внешняя сортировка (диск) | не подходит | стандартный выбор |
| скорость на практике (массивы в памяти) | обычно быстрее | медленнее из-за копирования в буфер |

**Почему quicksort обычно быстрее в памяти:** не аллоцирует, внутренний цикл очень простой, хорошо работает с кэшем процессора. Mergesort на каждом уровне копирует все данные в буфер и обратно.

**Почему у quicksort плохой худший случай:** качество зависит от pivot. Неудачный выбор на отсортированных данных или множество дубликатов даёт O(n²) и глубокую рекурсию. Лечится случайным pivot, медианой трёх, трёхпутевым разбиением — и, радикально, introsort.

**Когда выбирать какой:**

- массив примитивов, стабильность не важна, память дорога → quicksort (точнее introsort);
- нужна стабильность (многоуровневая сортировка) → mergesort / Timsort;
- нужна гарантия O(n log n) (защита от специально подобранных входов) → mergesort или heapsort;
- связный список или данные больше оперативной памяти → mergesort.

**Как это в .NET:**

- `Array.Sort`, `List<T>.Sort`, `Span<T>.Sort` — **introsort** (quicksort + heapsort при глубокой рекурсии + insertion sort на мелких участках), нестабильный, O(n log n) в худшем;
- `Enumerable.OrderBy` / `ThenBy` — **стабильная** сортировка: при равных ключах сохраняется исходный порядок (реализация на quicksort по индексам с дотяжкой сравнения по позиции);
- для стабильности через `Array.Sort` можно сортировать пары `(key, index)`.

**Что хорошо сказать в конце:** в стандартных библиотеках почти всегда гибриды — introsort (.NET, C++ `std::sort`) или Timsort (Python, Java для объектов), а не «чистые» учебные версии.

## Что такое stack?

```yaml
category: algorithms
level: middle
difficulty: 2
slug: algorithms-chto-takoe-stack
tags: data-structures
```

Стек — структура данных LIFO (last in, first out): последним положили — первым достали. Работать можно только с вершиной: положить (`Push`), снять (`Pop`), посмотреть без снятия (`Peek`).

```csharp
var stack = new Stack<int>();
stack.Push(1);
stack.Push(2);
stack.Push(3);

stack.Peek();                        // 3, остаётся в стеке
stack.Pop();                         // 3
stack.TryPop(out var top);           // true, top == 2 — без исключения на пустом стеке
stack.Count;                         // 1
```

| Операция | Сложность |
| --- | --- |
| `Push` | O(1) амортизированно (рост массива — O(n)) |
| `Pop`, `Peek`, `TryPop`, `TryPeek` | O(1) |
| `Contains` | O(n) |
| перечисление | O(n), от вершины к низу |

**Как устроен `Stack<T>` в .NET.** Это массив плюс индекс вершины. `Push` пишет в следующую ячейку, при нехватке места массив удваивается — как у `List<T>`. `Pop` на пустом стеке бросает `InvalidOperationException`, поэтому в коде без гарантий удобнее `TryPop`. Потокобезопасная версия — `ConcurrentStack<T>` (lock-free).

**Где применяется:**

- **стек вызовов** — каждый вызов метода кладёт кадр с локальными переменными и адресом возврата; отсюда `StackOverflowException` при бесконечной рекурсии;
- **проверка скобок** и разбор выражений (алгоритм сортировочной станции, вычисление обратной польской записи);
- **итеративный DFS** и замена рекурсии явным стеком, когда глубина может быть большой;
- **undo/redo** в редакторах, история навигации «назад»;
- **монотонный стек** — задачи вида «следующий больший элемент», «дневные температуры», максимальный прямоугольник в гистограмме за O(n).

**Не путать** стек как структуру данных с областью памяти «стек потока», где живут кадры методов и локальные value types. Связь есть (кадры организованы именно по принципу LIFO), но `Stack<T>` — это обычный объект в куче.

**Реализовать самому** можно на массиве (как в .NET) или на односвязном списке с добавлением в голову — оба варианта дают O(1) на операцию; массив быстрее из-за локальности и отсутствия аллокаций на каждый элемент.

## Что такое queue?

```yaml
category: algorithms
level: middle
difficulty: 2
slug: algorithms-chto-takoe-queue
tags: data-structures
```

Очередь — структура данных FIFO (first in, first out): элементы добавляются в конец и извлекаются из начала, в порядке поступления. Основные операции — `Enqueue`, `Dequeue`, `Peek`.

```csharp
var queue = new Queue<string>();
queue.Enqueue("a");
queue.Enqueue("b");

queue.Peek();                          // "a"
queue.Dequeue();                       // "a"
queue.TryDequeue(out var next);        // true, next == "b"
```

| Операция | Сложность |
| --- | --- |
| `Enqueue` | O(1) амортизированно |
| `Dequeue`, `Peek`, `TryDequeue` | O(1) |
| `Contains` | O(n) |

**Как устроен `Queue<T>`.** Это **кольцевой буфер** на массиве с индексами головы и хвоста. При извлечении элементы не сдвигаются — просто двигается голова; индексы «заворачиваются» на начало массива. Когда буфер заполнен, массив увеличивается вдвое, элементы копируются по порядку. Именно поэтому очередь на `List<T>` с `RemoveAt(0)` — плохая идея: каждое извлечение O(n).

**Разновидности очередей в .NET:**

| Тип | Когда нужен |
| --- | --- |
| `Queue<T>` | однопоточная FIFO |
| `ConcurrentQueue<T>` | несколько потоков, lock-free |
| `Channel<T>` (`System.Threading.Channels`) | producer/consumer с `async`, ограничением ёмкости и backpressure |
| `BlockingCollection<T>` | producer/consumer с блокирующим ожиданием (старый API) |
| `PriorityQueue<TElement, TPriority>` | извлечение по приоритету, а не по порядку (.NET 6+, min-куча) |

**Где применяется:**

- **BFS** — обход графа по уровням, кратчайший путь в невзвешенном графе;
- **буферизация и конвейеры** — очередь задач, фоновые воркеры, `Channel<T>` между producer и consumer;
- **планировщики** — пул потоков .NET внутри держит очереди рабочих элементов;
- **скользящее окно** — хранение последних k событий, rate limiting;
- **брокеры сообщений** (RabbitMQ, Azure Service Bus) — та же идея на уровне системы.

**Дек (deque)** — очередь с двух сторон. Отдельного `Deque<T>` в .NET нет; для задач вроде «максимум в скользящем окне» используют `LinkedList<T>` или собственный кольцевой буфер.

## Что такое linked list?

```yaml
category: algorithms
level: middle
difficulty: 2
slug: algorithms-chto-takoe-linked-list
tags: data-structures
```

Связный список — последовательность узлов, где каждый узел хранит значение и ссылку на следующий (в двусвязном — ещё и на предыдущий). Элементы не лежат в памяти подряд, поэтому вставка и удаление по известному узлу — O(1), а доступ по индексу — O(n).

```csharp
var list = new LinkedList<int>();
var node = list.AddLast(1);        // возвращает LinkedListNode<int>
list.AddLast(3);
list.AddAfter(node, 2);            // O(1): 1 → 2 → 3
list.AddFirst(0);                  // O(1): 0 → 1 → 2 → 3
list.Remove(node);                 // O(1) по узлу: 0 → 2 → 3
list.Remove(3);                    // O(n) по значению — сначала поиск
```

| Операция | `LinkedList<T>` | `List<T>` |
| --- | --- | --- |
| доступ по индексу | O(n) (индексатора нет) | O(1) |
| добавление в начало | O(1) | O(n) |
| добавление в конец | O(1) | O(1) амортизированно |
| вставка/удаление по известному узлу | O(1) | O(n) (сдвиг) |
| поиск по значению | O(n) | O(n) |
| память на элемент | узел-объект: значение + 3 ссылки + заголовок | только значение |

**`LinkedList<T>` в .NET** — двусвязный и внутренне кольцевой: голова ссылается на хвост. Каждый узел — отдельный объект `LinkedListNode<T>` со ссылками `Next`, `Previous`, `List` и значением.

**Почему на практике он редко выигрывает:**

- **аллокация на каждый элемент** — нагрузка на GC;
- **плохая локальность** — узлы разбросаны по куче, каждый переход по ссылке — вероятный промах кэша; проход по `List<T>` в разы быстрее;
- **память** — для `LinkedList<int>` около 48 байт на элемент против 4 у `List<int>`;
- «O(1) вставка» верна, только если узел уже есть; если его надо найти — это всё равно O(n).

**Где он действительно нужен:**

- **LRU-кэш** — `Dictionary<key, LinkedListNode>` + список: перенос в начало и удаление из хвоста за O(1);
- очередь/дек с частыми вставками и удалениями с обоих концов и из середины по ссылке;
- задачи на собеседовании: разворот списка, поиск цикла (Флойд, «черепаха и заяц»), середина списка двумя указателями, слияние двух отсортированных списков.

```csharp
// Классика: разворот односвязного списка, O(n) время, O(1) память
static Node? Reverse(Node? head)
{
    Node? prev = null;
    while (head is not null)
    {
        var next = head.Next;
        head.Next = prev;       // разворачиваем ссылку
        prev = head;
        head = next;
    }
    return prev;
}
class Node(int value) { public int Value = value; public Node? Next; }
```

## Что такое hash table?

```yaml
category: algorithms
level: middle
difficulty: 2
slug: algorithms-chto-takoe-hash-table
tags: data-structures
```

Хеш-таблица хранит пары «ключ — значение» в массиве корзин: по ключу вычисляется хеш, по хешу — номер корзины, и туда кладётся запись. Поэтому вставка, поиск и удаление по ключу занимают **O(1) в среднем** — не нужно перебирать элементы.

**Три составляющих:**

1. **Хеш-функция** — превращает ключ в число. Равные ключи обязаны давать равный хеш; разные — желательно разный и равномерно распределённый.
2. **Разрешение коллизий** — разные ключи могут попасть в одну корзину:
   - **цепочки (separate chaining)** — в корзине список записей. Так устроены `Dictionary` и `HashSet` в .NET (цепочки через индексы внутри массива записей, без отдельных объектов-узлов);
   - **открытая адресация** — при занятой ячейке ищем следующую по правилу (линейное/квадратичное пробирование). Так устроен старый `Hashtable` (двойное хеширование) и многие реализации в других языках.
3. **Рост (rehashing)** — когда элементов становится слишком много относительно корзин (load factor), массив увеличивается и все записи перераскладываются. В .NET размер — простое число, примерно вдвое больше предыдущего.

| Операция | Средний случай | Худший случай |
| --- | --- | --- |
| вставка | O(1) амортизированно | O(n) |
| поиск | O(1) | O(n) |
| удаление | O(1) | O(n) |
| память | O(n) | O(n) |

Худший случай — все ключи в одной корзине: плохой хеш или специально подобранные ключи (hash flooding). Для строк .NET по умолчанию использует рандомизированный хеш, чтобы такую атаку было сложно провести.

**Контракт `GetHashCode` / `Equals` для своих ключей:**

- если `a.Equals(b)`, то `a.GetHashCode() == b.GetHashCode()` — обязательно;
- обратное не обязательно (это и есть коллизия);
- хеш не должен меняться, пока объект лежит в таблице — ключ лучше делать неизменяемым;
- удобнее всего `record`/`record struct` или `HashCode.Combine(a, b)`.

**Реализации в .NET:**

| Тип | Что это |
| --- | --- |
| `Dictionary<TKey, TValue>` | основная хеш-таблица ключ → значение |
| `HashSet<T>` | только ключи, множество |
| `ConcurrentDictionary<TKey, TValue>` | потокобезопасная, с блокировками по сегментам |
| `FrozenDictionary` / `FrozenSet` | неизменяемые, оптимизированы под чтение (.NET 8) |
| `Hashtable` | необобщённая, устаревшая, боксинг |

**Чего хеш-таблица не умеет:** хранить порядок (порядок перечисления `Dictionary` не гарантирован), искать диапазоны и ближайшие ключи. Для этого — `SortedDictionary`/`SortedSet` за O(log n).

## Как найти дубликаты в массиве?

```yaml
category: algorithms
level: middle
difficulty: 3
slug: algorithms-kak-naiti-dublikaty-v-massive
tags: sql
```

Стандартное решение — один проход с `HashSet<T>`: если `Add` вернул `false`, элемент уже встречался. Это O(n) по времени и O(n) по памяти. Альтернативы — сортировка (O(n log n), O(1) доп. памяти) или трюки для специальных ограничений на значения.

```csharp
// Все значения, встречающиеся больше одного раза (каждое — один раз в результате)
static List<int> FindDuplicates(int[] nums)
{
    var seen = new HashSet<int>();
    var dups = new HashSet<int>();
    foreach (var x in nums)
        if (!seen.Add(x)) dups.Add(x);
    return [.. dups];
}

// Есть ли вообще дубликат — можно выйти сразу
static bool ContainsDuplicate(int[] nums)
{
    var seen = new HashSet<int>(nums.Length);
    foreach (var x in nums)
        if (!seen.Add(x)) return true;
    return false;
}
```

**Варианты и их цена:**

| Подход | Время | Память | Когда |
| --- | --- | --- | --- |
| `HashSet` | O(n) | O(n) | по умолчанию |
| `Dictionary<T, int>` со счётчиками | O(n) | O(n) | нужно число повторений |
| сортировка + сравнение соседей | O(n log n) | O(1)*, но меняет массив | нельзя тратить память |
| два вложенных цикла | O(n²) | O(1) | только как стартовая мысль |
| знак по индексу / цикл Флойда | O(n) | O(1) | значения в диапазоне `1..n` |

\* `Array.Sort` сортирует на месте; если массив менять нельзя — придётся копировать.

**LINQ-вариант** — короткий и читаемый, но с аллокациями группировки:

```csharp
var dups = nums.GroupBy(x => x)
               .Where(g => g.Count() > 1)
               .Select(g => g.Key);
// со счётчиками: .ToDictionary(g => g.Key, g => g.Count())
// .NET 9: nums.CountBy(x => x).Where(p => p.Value > 1)
```

**Специальный случай «значения от 1 до n»** (LeetCode 442): отмечаем посещение знаком элемента по индексу `|x| - 1`. Если там уже отрицательное число — дубликат. O(n) времени, O(1) памяти, но массив портится.

**Для своих типов** не забудьте про `Equals`/`GetHashCode` или передайте `IEqualityComparer<T>` в конструктор `HashSet` — иначе объекты сравниваются по ссылке.

**Тот же вопрос в SQL** (отсюда тег): `SELECT email, COUNT(*) FROM users GROUP BY email HAVING COUNT(*) > 1`. Чтобы получить сами строки-дубликаты — оконная функция `ROW_NUMBER() OVER (PARTITION BY email ORDER BY id)` и фильтр `> 1`; это же используется для удаления дублей с сохранением одной записи.

## Как найти первый уникальный символ в строке?

```yaml
category: algorithms
level: middle
difficulty: 3
slug: algorithms-kak-naiti-pervyi-unikalnyi-simvol-v-stroke
```

Два прохода: в первом считаем, сколько раз встречается каждый символ, во втором идём по строке **в исходном порядке** и возвращаем первый символ со счётчиком 1. Время O(n), память O(k), где k — размер алфавита.

```csharp
// Для строчной латиницы (как в LeetCode 387): массив вместо словаря
static int FirstUniqCharIndex(string s)
{
    Span<int> count = stackalloc int[26];
    foreach (var c in s) count[c - 'a']++;
    for (int i = 0; i < s.Length; i++)
        if (count[s[i] - 'a'] == 1) return i;
    return -1;
}

// Для произвольных символов — Dictionary
static char? FirstUniqChar(string s)
{
    var count = new Dictionary<char, int>();
    foreach (var c in s)
        count[c] = count.GetValueOrDefault(c) + 1;
    foreach (var c in s)
        if (count[c] == 1) return c;
    return null;
}
```

**Почему второй проход по строке, а не по словарю.** Порядок перечисления `Dictionary` не гарантирован, а нужен именно *первый* по позиции в строке. Второй проход по строке — O(n) и даёт правильный порядок.

**Сложность:**

| Вариант | Время | Память |
| --- | --- | --- |
| массив счётчиков на 26 / 128 / 65536 | O(n) | O(1) — фиксированный размер |
| `Dictionary<char, int>` | O(n) | O(k) различных символов |
| `s.IndexOf(c) == s.LastIndexOf(c)` для каждого символа | O(n²) | O(1) |

**Уточняющие вопросы, которые стоит задать:**

- какой алфавит — только `a–z` или любой Unicode? От этого зависит, массив или словарь;
- учитывать ли регистр (`'A'` и `'a'` — один символ?) — тогда `char.ToLowerInvariant`;
- что вернуть, если уникального нет: `-1`, `null`, исключение;
- **суррогатные пары и эмодзи.** `char` в .NET — это UTF-16 code unit, и `"😀"` состоит из двух `char`. Если важны настоящие символы, итерируйте `s.EnumerateRunes()` (кодовые точки) или `StringInfo` (графемы).

**Потоковый вариант** — символы приходят по одному, и после каждого нужно отвечать «какой сейчас первый уникальный»: держим счётчики + очередь кандидатов; при запросе выбрасываем из головы очереди символы, чей счётчик стал > 1. Амортизированно O(1) на символ.

**LINQ-однострочник** для разговора: `s.GroupBy(c => c).FirstOrDefault(g => g.Count() == 1)?.Key` — работает, потому что `GroupBy` сохраняет порядок первого появления ключа, но аллоцирует группы на каждый символ.

## Как проверить, является ли строка palindrome?

```yaml
category: algorithms
level: middle
difficulty: 3
slug: algorithms-kak-proverit-yavlyaetsya-li-stroka-palindrome
```

Два указателя с концов строки идут навстречу друг другу и сравнивают символы; при первом несовпадении — не палиндром, встретились — палиндром. O(n) времени и O(1) памяти, без создания перевёрнутой копии.

```csharp
static bool IsPalindrome(string s)
{
    int i = 0, j = s.Length - 1;
    while (i < j)
        if (s[i++] != s[j--]) return false;
    return true;
}
```

**Типичная постановка (LeetCode 125):** игнорировать регистр и всё, кроме букв и цифр — `"A man, a plan, a canal: Panama"` должна считаться палиндромом.

```csharp
static bool IsPalindromeLoose(string s)
{
    int i = 0, j = s.Length - 1;
    while (i < j)
    {
        if (!char.IsLetterOrDigit(s[i])) { i++; continue; }
        if (!char.IsLetterOrDigit(s[j])) { j--; continue; }
        if (char.ToLowerInvariant(s[i]) != char.ToLowerInvariant(s[j])) return false;
        i++; j--;
    }
    return true;
}
```

**Сравнение подходов:**

| Подход | Время | Память |
| --- | --- | --- |
| два указателя | O(n) | O(1) |
| `s.SequenceEqual(s.Reverse())` | O(n) | O(n) + аллокации LINQ |
| очистить строку, развернуть, сравнить | O(n) | O(n) |
| рекурсия `s[0] == s[^1] && IsPal(s[1..^1])` | O(n²) из-за копий подстрок | O(n²) |

Два указателя проверяют только половину строки и не аллоцируют — именно это ждут на собеседовании. Рекурсию с `Substring`/диапазонами лучше не предлагать: каждый срез создаёт новую строку.

**Крайние случаи:** пустая строка и строка из одного символа — палиндромы; `null` — решить явно (исключение или `false`); строка только из знаков препинания в «мягкой» версии — палиндром.

**Unicode.** Посимвольное сравнение `char` ломается на суррогатных парах (эмодзи, редкие иероглифы) и на комбинируемых символах (`é` как `e` + ударение). Для честной проверки нужна нормализация (`s.Normalize()`) и сравнение по графемам (`StringInfo`). Обычно достаточно упомянуть это как оговорку.

**Смежные задачи:** палиндром при удалении не более одного символа (при несовпадении пробуем пропустить левый или правый — O(n)), самая длинная палиндромная подстрока (расширение от центра, O(n²)), палиндромное число без перевода в строку (разворачиваем половину числа).

## Как развернуть строку?

```yaml
category: algorithms
level: middle
difficulty: 3
slug: algorithms-kak-razvernut-stroku
```

Строки в .NET неизменяемы, поэтому «развернуть» — значит создать новую строку с символами в обратном порядке. Самый эффективный способ — `string.Create` или `char[]` + `Array.Reverse`: O(n) времени, одна аллокация результата.

```csharp
// Классика: массив символов + Array.Reverse
static string Reverse(string s)
{
    var chars = s.ToCharArray();
    Array.Reverse(chars);
    return new string(chars);
}

// Без промежуточного массива: пишем сразу в буфер новой строки
static string ReverseFast(string s) =>
    string.Create(s.Length, s, (span, src) =>
    {
        src.AsSpan().CopyTo(span);
        span.Reverse();
    });
```

**Вручную двумя указателями** — если просят «без встроенных функций»:

```csharp
static void ReverseInPlace(char[] a)
{
    for (int i = 0, j = a.Length - 1; i < j; i++, j--)
        (a[i], a[j]) = (a[j], a[i]);
}
```

**Сравнение способов:**

| Способ | Время | Аллокации |
| --- | --- | --- |
| `string.Create` + `Span.Reverse` | O(n) | только результат |
| `ToCharArray` + `Array.Reverse` + `new string` | O(n) | массив + результат |
| `new string(s.Reverse().ToArray())` | O(n) | итератор, буферы LINQ, результат — медленнее |
| `StringBuilder`, добавляя с конца | O(n) | буфер + результат |
| `result = c + result` в цикле | **O(n²)** | новая строка на каждом шаге |

Последний вариант — классическая ошибка: каждая конкатенация копирует всю накопленную строку.

**Подводный камень — Unicode.** Разворот по `char` ломает суррогатные пары: эмодзи `"😀"` — это два `char`, и после разворота получится невалидная строка. Также разрываются комбинируемые символы (`e` + `◌́`). Корректный разворот по графемам:

```csharp
using System.Globalization;

static string ReverseGraphemes(string s)
{
    var e = StringInfo.GetTextElementEnumerator(s);
    var parts = new List<string>();
    while (e.MoveNext()) parts.Add(e.GetTextElement());
    parts.Reverse();
    return string.Concat(parts);
}
```

Упомянуть это на собеседовании — хороший плюс, даже если писать не просят.

**Смежные задачи:** развернуть порядок слов (`"hello world"` → `"world hello"`: разворот всей строки, затем каждого слова, или `string.Join(' ', s.Split(' ', StringSplitOptions.RemoveEmptyEntries).Reverse())`), развернуть число, развернуть связный список.

## Как найти два числа с заданной суммой?

```yaml
category: algorithms
level: middle
difficulty: 3
slug: algorithms-kak-naiti-dva-chisla-s-zadannoi-summoi
```

Это задача Two Sum. Для произвольного массива — один проход со словарём «значение → индекс»: для каждого `x` проверяем, видели ли мы уже `target - x`. O(n) времени, O(n) памяти. Если массив отсортирован — два указателя с концов, O(n) времени и O(1) памяти.

```csharp
// Неотсортированный массив: вернуть индексы двух элементов
static (int, int)? TwoSum(int[] nums, int target)
{
    var seen = new Dictionary<int, int>();          // значение → индекс
    for (int i = 0; i < nums.Length; i++)
    {
        int need = target - nums[i];
        if (seen.TryGetValue(need, out int j)) return (j, i);
        seen[nums[i]] = i;                           // добавляем ПОСЛЕ проверки
    }
    return null;
}
```

Порядок «сначала проверить, потом добавить» важен: так элемент не сложится сам с собой (`target = 6`, `nums = [3, ...]`), а пара `[3, 3]` при этом находится корректно.

```csharp
// Отсортированный массив: два указателя
static (int, int)? TwoSumSorted(int[] a, int target)
{
    int l = 0, r = a.Length - 1;
    while (l < r)
    {
        long sum = (long)a[l] + a[r];                 // защита от переполнения
        if (sum == target) return (l, r);
        if (sum < target) l++; else r--;
    }
    return null;
}
```

**Почему два указателя корректны:** если сумма мала, увеличить её можно только сдвинув левый указатель вправо (правый уже максимален для текущего левого); если велика — сдвигаем правый влево. Ни одна подходящая пара не пропускается.

| Подход | Время | Память |
| --- | --- | --- |
| перебор всех пар | O(n²) | O(1) |
| словарь, один проход | O(n) | O(n) |
| сортировка + два указателя | O(n log n) | O(n) при сохранении индексов, O(1) если нужны только значения |
| массив уже отсортирован | O(n) | O(1) |
| бинарный поиск `target - x` для каждого x | O(n log n) | O(1) |

**Уточняющие вопросы:** вернуть индексы или значения? Одну пару или все? Могут ли быть дубликаты? Отсортирован ли массив? Что вернуть, если пары нет? Возможно ли переполнение `int`?

**Все уникальные пары значений:** сортировка + два указателя с пропуском одинаковых соседей, либо `HashSet` для увиденных и `HashSet` для найденных пар.

**Развитие темы:** 3Sum — сортировка и для каждого элемента Two Sum двумя указателями, O(n²); 4Sum — O(n³); Two Sum в BST — обход in-order даёт отсортированную последовательность.

## Что такое Two Pointers?

```yaml
category: algorithms
level: middle
difficulty: 2
slug: algorithms-chto-takoe-two-pointers
tags: complexity
```

Two Pointers — приём, при котором по массиву или строке одновременно движутся два индекса, и на каждом шаге по простому правилу сдвигается один из них. Это превращает перебор пар O(n²) в один проход O(n) с O(1) памяти.

**Три основных варианта:**

| Вариант | Как движутся | Примеры задач |
| --- | --- | --- |
| навстречу друг другу | с концов к центру | палиндром, Two Sum в отсортированном массиве, контейнер с максимумом воды, разворот |
| в одном направлении (быстрый/медленный) | `read` идёт всегда, `write` — по условию | удаление дубликатов на месте, сдвиг нулей в конец, фильтрация массива |
| по двум массивам | по индексу в каждом | слияние отсортированных массивов, пересечение, сравнение версий |

Отдельно стоит **«черепаха и заяц»** на связных списках: один указатель шагает на 1, другой на 2. Так находят середину списка и цикл (алгоритм Флойда).

**Пример «read/write»: удалить дубликаты из отсортированного массива на месте** (LeetCode 26):

```csharp
static int RemoveDuplicates(int[] a)
{
    if (a.Length == 0) return 0;
    int write = 1;
    for (int read = 1; read < a.Length; read++)
        if (a[read] != a[write - 1])
            a[write++] = a[read];
    return write;              // новая длина; a[0..write) — уникальные элементы
}
```

**Пример «навстречу»: максимальная площадь «контейнера с водой»** (LeetCode 11) — двигаем тот указатель, чья стенка ниже: от более высокой стенки площадь при сужении не вырастет.

```csharp
static long MaxArea(int[] h)
{
    int l = 0, r = h.Length - 1;
    long best = 0;
    while (l < r)
    {
        best = Math.Max(best, (long)Math.Min(h[l], h[r]) * (r - l));
        if (h[l] < h[r]) l++; else r--;
    }
    return best;
}
```

**Когда приём применим.** Нужна монотонность: должно быть понятно, какой указатель двигать, и что сдвинутая позиция больше не понадобится. Чаще всего это обеспечивает **сортировка** — поэтому многие задачи решаются так: отсортировать за O(n log n), затем два указателя за O(n) (например, 3Sum за O(n²) вместо O(n³)).

**Связь со Sliding Window.** Скользящее окно — частный случай двух указателей в одном направлении, где интересует отрезок между ними (сумма, набор символов).

**Сложность:** каждый указатель проходит массив не больше одного раза → O(n) времени, O(1) дополнительной памяти.

## Что такое Sliding Window?

```yaml
category: algorithms
level: middle
difficulty: 2
slug: algorithms-chto-takoe-sliding-window
tags: complexity
```

Sliding Window — приём для задач о непрерывных подмассивах и подстроках: поддерживаем «окно» `[left, right]` и при сдвиге **инкрементально** обновляем его состояние (сумму, счётчики символов), а не пересчитываем заново. Так O(n·k) или O(n²) превращается в O(n).

**Окно фиксированного размера** — максимальная сумма k подряд идущих элементов:

```csharp
static long MaxSumOfK(int[] a, int k)
{
    long sum = 0;
    for (int i = 0; i < k; i++) sum += a[i];
    long best = sum;
    for (int i = k; i < a.Length; i++)
    {
        sum += a[i] - a[i - k];      // вошёл новый, вышел старый
        best = Math.Max(best, sum);
    }
    return best;
}
```

**Окно переменного размера** — правая граница расширяет окно, левая сжимает, пока условие нарушено. Классика — самая длинная подстрока без повторяющихся символов (LeetCode 3):

```csharp
static int LongestUniqueSubstring(string s)
{
    var lastIndex = new Dictionary<char, int>();
    int best = 0, left = 0;
    for (int right = 0; right < s.Length; right++)
    {
        if (lastIndex.TryGetValue(s[right], out int prev) && prev >= left)
            left = prev + 1;                      // перепрыгиваем повтор
        lastIndex[s[right]] = right;
        best = Math.Max(best, right - left + 1);
    }
    return best;
}
```

**Общий шаблон переменного окна:**

1. сдвигаем `right`, добавляем элемент в состояние;
2. `while` окно невалидно — удаляем `a[left]` из состояния и сдвигаем `left`;
3. обновляем ответ.

Каждый элемент добавляется и удаляется не больше одного раза, поэтому даже с вложенным `while` сложность **O(n)**.

**Типичные задачи:**

- максимум/среднее в окне размера k;
- самая длинная подстрока без повторов / с не более чем k различными символами;
- минимальный подмассив с суммой ≥ S (только для неотрицательных чисел);
- минимальная подстрока, содержащая все символы шаблона;
- поиск анаграмм шаблона в строке (фиксированное окно + счётчики);
- максимум в каждом окне — окно + монотонный дек, O(n).

**Когда приём не работает.** Нужна монотонность: расширение окна должно только «ухудшать» условие, а сжатие — «улучшать». С отрицательными числами сумма окна немонотонна — для «подмассива с суммой ровно K» нужны префиксные суммы + `Dictionary`, а не окно.

**В бэкенде** та же идея — rate limiting со скользящим окном, скользящие метрики (запросы за последние 60 секунд), обычно с `Queue<T>` временных меток.

## Как найти максимальную сумму подмассива?

```yaml
category: algorithms
level: middle
difficulty: 3
slug: algorithms-kak-naiti-maksimalnuyu-summu-podmassiva
```

Алгоритм Кадане: идём по массиву и для каждой позиции держим лучшую сумму подмассива, **заканчивающегося** в ней. Она равна либо текущему элементу (начать заново), либо текущему элементу плюс лучшая сумма на предыдущей позиции. Ответ — максимум по всем позициям. O(n) времени, O(1) памяти.

```csharp
static long MaxSubArray(int[] a)
{
    if (a.Length == 0) throw new ArgumentException("Массив пуст", nameof(a));

    long current = a[0], best = a[0];
    for (int i = 1; i < a.Length; i++)
    {
        current = Math.Max(a[i], current + a[i]);   // продолжить или начать заново
        best = Math.Max(best, current);
    }
    return best;
}
```

Пример: `[-2, 1, -3, 4, -1, 2, 1, -5, 4]` → `current` по шагам: −2, 1, −2, 4, 3, 5, 6, 1, 5; ответ **6** (подмассив `[4, -1, 2, 1]`).

**Интуиция.** Если накопленная сумма стала отрицательной, она только ухудшит любой следующий подмассив — её выгоднее отбросить. Это динамическое программирование с состоянием размера O(1): `dp[i] = max(a[i], dp[i-1] + a[i])`.

**Если нужны границы подмассива:**

```csharp
static (long Sum, int Start, int End) MaxSubArrayRange(int[] a)
{
    long current = a[0], best = a[0];
    int start = 0, bestStart = 0, bestEnd = 0;
    for (int i = 1; i < a.Length; i++)
    {
        if (current + a[i] < a[i]) { current = a[i]; start = i; }
        else current += a[i];

        if (current > best) { best = current; bestStart = start; bestEnd = i; }
    }
    return (best, bestStart, bestEnd);
}
```

**Сравнение подходов:**

| Подход | Время | Память |
| --- | --- | --- |
| перебор всех подмассивов с пересчётом суммы | O(n³) | O(1) |
| перебор с накопительной суммой | O(n²) | O(1) |
| разделяй и властвуй | O(n log n) | O(log n) |
| Кадане | O(n) | O(1) |

**Крайние случаи:**

- **все числа отрицательные** — ответ равен максимальному элементу. Частая ошибка — инициализировать `best = 0`: тогда вернётся 0, что соответствует пустому подмассиву. Уточните, разрешён ли пустой подмассив;
- переполнение — сумма `int` может не влезть в `int`, поэтому `long`;
- пустой массив — решить явно.

**Вариации:** максимальное произведение подмассива (держим и максимум, и минимум — минус на минус), максимальная сумма в кольцевом массиве (max(Кадане, общая сумма − минимальный подмассив)), лучшее время купить/продать акцию — тот же Кадане по разностям соседних дней.

## Как найти пересечение двух массивов?

```yaml
category: algorithms
level: middle
difficulty: 3
slug: algorithms-kak-naiti-peresechenie-dvuh-massivov
```

Строим `HashSet` из одного массива и проходим по второму, отбирая элементы, которые есть в множестве. Это O(n + m) времени и O(min(n, m)) памяти, если множество строить из меньшего массива. Для отсортированных массивов — два указателя за O(n + m) и O(1) памяти.

Сначала уточните, что значит «пересечение»: **уникальные** общие значения (`[1,2,2,1] ∩ [2,2] = [2]`) или **с учётом кратности** (`= [2, 2]`).

```csharp
// Уникальные общие значения (LeetCode 349)
static int[] Intersection(int[] a, int[] b)
{
    if (a.Length > b.Length) (a, b) = (b, a);       // множество — из меньшего
    var set = new HashSet<int>(a);
    var result = new HashSet<int>();
    foreach (var x in b)
        if (set.Contains(x)) result.Add(x);
    return [.. result];
}

// С учётом кратности (LeetCode 350)
static List<int> IntersectionWithCounts(int[] a, int[] b)
{
    var count = new Dictionary<int, int>();
    foreach (var x in a) count[x] = count.GetValueOrDefault(x) + 1;

    var result = new List<int>();
    foreach (var x in b)
        if (count.TryGetValue(x, out int c) && c > 0)
        {
            result.Add(x);
            count[x] = c - 1;
        }
    return result;
}
```

**Отсортированные массивы — два указателя:**

```csharp
static List<int> IntersectSorted(int[] a, int[] b)
{
    var result = new List<int>();
    int i = 0, j = 0;
    while (i < a.Length && j < b.Length)
    {
        if (a[i] < b[j]) i++;
        else if (a[i] > b[j]) j++;
        else { result.Add(a[i]); i++; j++; }         // с кратностью
    }
    return result;
}
```

**Встроенные средства .NET:**

- `a.Intersect(b)` — LINQ, уникальные значения, внутри строит множество из `b`, порядок — как в `a`;
- `set.IntersectWith(other)` — изменяет сам `HashSet` на месте;
- `IntersectBy(keys, selector)` (.NET 6) — пересечение по ключу для объектов.

| Подход | Время | Память |
| --- | --- | --- |
| вложенные циклы | O(n·m) | O(1) |
| `HashSet` | O(n + m) | O(min(n, m)) |
| сортировка обоих + два указателя | O(n log n + m log m) | O(1)* |
| уже отсортированы | O(n + m) | O(1) |
| один маленький, другой огромный и отсортирован | O(k log n) бинарным поиском | O(1) |

\* не считая результата и копий, если исходные массивы менять нельзя.

**Follow-up с собеседований:** второй массив не помещается в память (читаем его потоком, а меньший держим в `HashSet`/словаре; если оба огромные — внешняя сортировка и слияние); пересечение k массивов (счётчики или последовательное `IntersectWith`); пересечение по полю объектов (`IEqualityComparer<T>` или `IntersectBy`).

## Как объединить два отсортированных массива?

```yaml
category: algorithms
level: middle
difficulty: 3
slug: algorithms-kak-obedinit-dva-otsortirovannyh-massiva
```

Два указателя — по одному на каждый массив: сравниваем текущие элементы, меньший пишем в результат и сдвигаем его указатель; когда один массив кончился, дописываем хвост другого. Это шаг слияния из mergesort: O(n + m) времени и O(n + m) памяти под результат.

```csharp
static int[] Merge(int[] a, int[] b)
{
    var result = new int[a.Length + b.Length];
    int i = 0, j = 0, k = 0;
    while (i < a.Length && j < b.Length)
        result[k++] = a[i] <= b[j] ? a[i++] : b[j++];   // <= — стабильность
    while (i < a.Length) result[k++] = a[i++];
    while (j < b.Length) result[k++] = b[j++];
    return result;
}
```

**Вариант на месте (LeetCode 88):** первый массив имеет длину `m + n`, в конце — свободное место под второй. Заполняем **с конца**, чтобы не затереть ещё не обработанные элементы:

```csharp
static void MergeInPlace(int[] a, int m, int[] b, int n)
{
    int i = m - 1, j = n - 1, k = m + n - 1;
    while (j >= 0)                                   // пока есть элементы b
        a[k--] = i >= 0 && a[i] > b[j] ? a[i--] : b[j--];
    // остаток a уже на своих местах
}
```

Здесь O(n + m) времени и O(1) дополнительной памяти. Цикл идёт по `j`, потому что оставшиеся элементы `a` и так стоят где нужно.

**Почему не `a.Concat(b).OrderBy(x => x)`:** это O((n + m) log(n + m)) — сортировка игнорирует то, что данные уже упорядочены. Работает, но на собеседовании ждут линейное слияние.

| Подход | Время | Память |
| --- | --- | --- |
| склеить и отсортировать | O((n+m) log(n+m)) | O(n + m) |
| два указателя в новый массив | O(n + m) | O(n + m) |
| на месте с конца | O(n + m) | O(1) |

**Крайние случаи:** один или оба массива пустые, все элементы одного меньше всех элементов другого, дубликаты (оставлять или убирать — уточнить), разные направления сортировки.

**Follow-up: слить k отсортированных массивов или списков.** Наивно сливать попарно — O(N·k). Правильно — **min-куча** из текущих головных элементов: достаём минимум, кладём следующий элемент из того же массива. O(N log k), где N — всего элементов.

```csharp
static List<int> MergeK(int[][] arrays)
{
    var heap = new PriorityQueue<(int Arr, int Idx), int>();
    for (int a = 0; a < arrays.Length; a++)
        if (arrays[a].Length > 0) heap.Enqueue((a, 0), arrays[a][0]);

    var result = new List<int>();
    while (heap.TryDequeue(out var pos, out int value))
    {
        result.Add(value);
        int next = pos.Idx + 1;
        if (next < arrays[pos.Arr].Length)
            heap.Enqueue((pos.Arr, next), arrays[pos.Arr][next]);
    }
    return result;
}
```

Та же идея лежит в основе внешней сортировки и слияния сегментов в LSM-хранилищах.

## Как найти пропущенное число?

```yaml
category: algorithms
level: middle
difficulty: 3
slug: algorithms-kak-naiti-propuschennoe-chislo
```

Классическая постановка: в массиве из `n` различных чисел от `0` до `n` одно пропущено. Решение — сравнить ожидаемую сумму `n·(n+1)/2` с фактической; разница и есть пропущенное число. Альтернатива без риска переполнения — XOR всех индексов и значений. Оба способа — O(n) времени и O(1) памяти.

```csharp
// Через сумму: long, чтобы не переполниться
static int MissingNumber(int[] nums)
{
    long n = nums.Length;
    long expected = n * (n + 1) / 2;
    long actual = 0;
    foreach (var x in nums) actual += x;
    return (int)(expected - actual);
}

// Через XOR: x ^ x = 0, x ^ 0 = x — парные числа взаимно уничтожаются
static int MissingNumberXor(int[] nums)
{
    int result = nums.Length;
    for (int i = 0; i < nums.Length; i++)
        result ^= i ^ nums[i];
    return result;
}
```

Пример: `[3, 0, 1]`, n = 3 → ожидаемая сумма 6, фактическая 4, пропущено **2**.

**Почему XOR работает.** XOR всех чисел от 0 до n, «проксоренный» со всеми элементами массива: каждое присутствующее число встречается дважды и обнуляется, остаётся только пропущенное. Переполнения нет в принципе.

| Подход | Время | Память | Замечание |
| --- | --- | --- | --- |
| сортировка + поиск разрыва | O(n log n) | O(1)* | меняет массив |
| `HashSet` всех чисел, затем проверка 0..n | O(n) | O(n) | универсально |
| сумма | O(n) | O(1) | следить за переполнением |
| XOR | O(n) | O(1) | без переполнения |
| бинарный поиск (массив отсортирован) | O(log n) | O(1) | ищем первый `i`, где `a[i] != i` |

\* плюс память самой сортировки.

**Про переполнение.** Если считать формулу в `int`, произведение `n·(n+1)` перестаёт помещаться уже при n ≈ 46 341. Считайте в `long` или используйте XOR. В C# арифметика по умолчанию `unchecked` — переполнение не бросит исключение, а тихо даст неверный результат.

**Вариации:**

- **диапазон `1..n`** — та же формула с поправкой;
- **пропущено два числа** — сумма и сумма квадратов (система из двух уравнений) или XOR с разделением по младшему установленному биту;
- **есть дубликаты и пропуски, значения в `1..n`** — пометка знаком по индексу, O(n) и O(1);
- **первое пропущенное положительное** в произвольном массиве (LeetCode 41) — расстановка каждого числа `x` на позицию `x − 1` обменами, затем проход; O(n) и O(1);
- **данные — поток или огромный файл** — сумма/XOR считаются в один проход, всё в памяти держать не нужно.

## Как проверить корректность скобок?

```yaml
category: algorithms
level: middle
difficulty: 3
slug: algorithms-kak-proverit-korrektnost-skobok
```

Используем стек: открывающую скобку кладём в стек, на закрывающей проверяем, что стек не пуст и на вершине лежит парная открывающая, и снимаем её. В конце строка корректна, только если стек пуст. O(n) времени, O(n) памяти в худшем случае.

```csharp
static bool IsValid(string s)
{
    var stack = new Stack<char>();
    foreach (var c in s)
    {
        switch (c)
        {
            case '(' or '[' or '{':
                stack.Push(c);
                break;
            case ')' or ']' or '}':
                char expected = c switch { ')' => '(', ']' => '[', _ => '{' };
                if (!stack.TryPop(out var top) || top != expected) return false;
                break;
            // остальные символы игнорируем
        }
    }
    return stack.Count == 0;
}
```

**Три способа ошибиться, которые ловит алгоритм:**

| Строка | Почему некорректна | Что срабатывает |
| --- | --- | --- |
| `"(]"` | не та пара | `top != expected` |
| `"())"` | лишняя закрывающая | стек пуст при `TryPop` |
| `"(()"` | незакрытая открывающая | `stack.Count != 0` в конце |
| `"([)]"` | неправильная вложенность | на `)` вершина — `[` |

Последний пример — причина, почему не работает простой подсчёт количества каждого вида скобок.

**Один вид скобок — достаточно счётчика**, стек не нужен: O(1) памяти.

```csharp
static bool IsValidParens(string s)
{
    int depth = 0;
    foreach (var c in s)
    {
        if (c == '(') depth++;
        else if (c == ')' && --depth < 0) return false;   // закрыли больше, чем открыли
    }
    return depth == 0;
}
```

**Оптимизации и детали:**

- **ранний выход по длине**: если в строке только скобки и длина нечётная — сразу `false`;
- в .NET `Stack<char>` — массив, аллокация одна (плюс рост); для горячего пути можно взять `char[]`/`stackalloc` с индексом вершины, если длина строки ограничена;
- `TryPop` избавляет от проверки `Count` и исключения `InvalidOperationException` на пустом стеке.

**Уточняющие вопросы:** какие виды скобок; есть ли в строке другие символы; нужно ли вернуть позицию первой ошибки (тогда храним в стеке индексы, а не символы).

**Вариации:**

- минимальное число скобок, которое нужно удалить/добавить, чтобы строка стала корректной — счётчики «не закрытых» и «лишних закрывающих»;
- сгенерировать все корректные последовательности из n пар — бэктрекинг (число вариантов — n-е число Каталана);
- самая длинная корректная подстрока — стек индексов, O(n).

**Где это в реальной жизни:** парсеры и лексеры (JSON, выражения), подсветка парных скобок в IDE, валидация шаблонов — всё это тот же стек.

## Как реализовать LRU Cache?

```yaml
category: algorithms
level: middle
difficulty: 4
slug: algorithms-kak-realizovat-lru-cache
tags: caching, data-structures
```

LRU (Least Recently Used) — кэш фиксированной ёмкости, который при переполнении вытесняет элемент, к которому дольше всего не обращались. Классическая реализация — **хеш-таблица + двусвязный список**: словарь даёт поиск узла за O(1), список хранит порядок использования и позволяет переставить узел в начало или удалить хвост за O(1).

```csharp
public sealed class LruCache<TKey, TValue> where TKey : notnull
{
    private readonly int _capacity;
    private readonly Dictionary<TKey, LinkedListNode<(TKey Key, TValue Value)>> _map;
    private readonly LinkedList<(TKey Key, TValue Value)> _order = new(); // голова — самый свежий

    public LruCache(int capacity)
    {
        ArgumentOutOfRangeException.ThrowIfNegativeOrZero(capacity);
        _capacity = capacity;
        _map = new Dictionary<TKey, LinkedListNode<(TKey, TValue)>>(capacity);
    }

    public bool TryGet(TKey key, out TValue value)
    {
        if (_map.TryGetValue(key, out var node))
        {
            _order.Remove(node);        // O(1): удаление по узлу
            _order.AddFirst(node);      // помечаем как недавно использованный
            value = node.Value.Value;
            return true;
        }
        value = default!;
        return false;
    }

    public void Put(TKey key, TValue value)
    {
        if (_map.TryGetValue(key, out var node))
        {
            node.Value = (key, value);
            _order.Remove(node);
            _order.AddFirst(node);
            return;
        }

        if (_map.Count == _capacity)
        {
            var lru = _order.Last!;     // самый давно использованный
            _order.RemoveLast();
            _map.Remove(lru.Value.Key); // ключ в узле нужен именно для этого
        }

        _map[key] = _order.AddFirst((key, value));
    }
}
```

**Сложность:** `TryGet` и `Put` — O(1) в среднем (амортизированный O(1) словаря плюс O(1) операции со списком). Память — O(capacity).

**Ключевые детали, которые проверяют:**

- **ключ хранится в узле списка** — иначе при вытеснении хвоста не понять, какую запись удалить из словаря;
- **чтение тоже меняет порядок** — `Get` это «использование», а не только `Put`;
- **обновление существующего ключа** не должно вытеснять другой элемент;
- `LinkedList<T>.Remove(node)` + `AddFirst(node)` переиспользуют тот же узел — без новой аллокации.

**Почему не другие структуры:**

| Вариант | Проблема |
| --- | --- |
| `Dictionary` + `List<TKey>` | перенос в начало и удаление из середины — O(n) |
| `Dictionary` + метка времени | вытеснение требует поиска минимума — O(n) |
| `SortedDictionary` по времени | O(log n) на операцию |
| `OrderedDictionary` | удаление из середины — O(n) |

**Потокобезопасность.** Эта реализация не потокобезопасна: даже `TryGet` меняет список. Простейшее решение — `lock` вокруг обоих методов. `ConcurrentDictionary` сам по себе не поможет, потому что порядок в списке тоже нужно менять атомарно. Под высокой конкуренцией используют шардирование (несколько кэшей по хешу ключа) или приближённые алгоритмы.

**В продакшене .NET** свою реализацию обычно не пишут: `MemoryCache` (`Microsoft.Extensions.Caching.Memory`) поддерживает `SizeLimit`, приоритеты и истечение по времени (если новая запись не влезает в лимит, она не добавляется, а кэш запускает компактирование: сначала просроченные, затем по приоритету и давности обращения — это не строгий LRU), для распределённого кэша — Redis с политикой `allkeys-lru`. Реализацию руками спрашивают, чтобы проверить понимание комбинирования структур данных.

**Родственные политики:** LFU (вытеснять самый редко используемый — словарь + частоты + списки по частотам), TTL, 2Q/ARC, W-TinyLFU (используется в Caffeine для Java и во многих современных кэшах).

## Как найти top K элементов?

```yaml
category: algorithms
level: middle
difficulty: 3
slug: algorithms-kak-naiti-top-k-elementov
```

Оптимальное универсальное решение — **min-куча размера k**: проходим по данным, кладём элемент в кучу, а если она стала больше k — выкидываем минимум. В конце в куче ровно k наибольших. Это O(n log k) времени и O(k) памяти, и работает даже на потоке, который не помещается в память.

```csharp
// k наибольших элементов
static int[] TopK(IEnumerable<int> source, int k)
{
    if (k <= 0) return [];
    var heap = new PriorityQueue<int, int>(k);       // min-куча: приоритет = значение
    foreach (var x in source)
    {
        if (heap.Count < k) heap.Enqueue(x, x);
        else if (x > heap.Peek()) heap.EnqueueDequeue(x, x);  // вытеснить текущий минимум
    }
    var result = new int[heap.Count];
    for (int i = result.Length - 1; i >= 0; i--) result[i] = heap.Dequeue();
    return result;                                    // по убыванию
}
```

`PriorityQueue<TElement, TPriority>` в .NET 6+ — это **min-куча** (4-арная, на массиве): `Dequeue` возвращает элемент с наименьшим приоритетом. `EnqueueDequeue` делает вставку и извлечение за одну операцию просеивания. Для k наименьших нужна max-куча — передайте компаратор `Comparer<int>.Create((a, b) => b.CompareTo(a))`.

**Top K самых частых элементов** (LeetCode 347) — сначала частоты, потом та же куча по частоте:

```csharp
static int[] TopKFrequent(int[] nums, int k)
{
    var freq = new Dictionary<int, int>();
    foreach (var x in nums) freq[x] = freq.GetValueOrDefault(x) + 1;

    var heap = new PriorityQueue<int, int>();         // приоритет = частота
    foreach (var (value, count) in freq)
    {
        heap.Enqueue(value, count);
        if (heap.Count > k) heap.Dequeue();           // выкинуть самый редкий
    }
    return [.. heap.UnorderedItems.Select(e => e.Element)];
}
```

**Сравнение подходов:**

| Подход | Время | Память | Когда |
| --- | --- | --- | --- |
| полная сортировка, взять k | O(n log n) | O(n) | просто, k ~ n, данные небольшие |
| LINQ `OrderByDescending().Take(k)` | O(n log n) худший* | O(n) | читаемо, для не горячего кода |
| min-куча размера k | O(n log k) | O(k) | k ≪ n, поток данных |
| quickselect | O(n) в среднем, O(n²) худший | O(1) на месте | нужен результат без порядка, массив можно менять |
| bucket sort по частоте | O(n) | O(n) | top K частых, частоты ограничены n |

\* в современных .NET цепочка `OrderBy(...).Take(k)` оптимизирована и не сортирует весь массив полностью, но всё равно материализует источник целиком.

**Quickselect** — partition из quicksort, но рекурсия только в ту половину, где лежит k-я позиция: n + n/2 + n/4 + … = O(n) в среднем.

**Крайние случаи:** `k <= 0`, `k >= n` (вернуть всё), дубликаты значений, равные частоты (нужен ли детерминированный порядок — тогда добавить тай-брейк в приоритет).

**В распределённых системах** (топ запросов по логам): каждый узел считает локальный top-K кучей, затем результаты сливаются; для приблизительного подсчёта частот в потоке — Count-Min Sketch, Space-Saving.

## Когда использовать `Dictionary`, а когда `HashSet`?

```yaml
category: algorithms
level: middle
difficulty: 3
slug: algorithms-kogda-ispolzovat-dictionary-a-kogda-hashset
tags: collections
```

`HashSet<T>` — когда нужно только знать, **есть ли элемент** (множество уникальных значений). `Dictionary<TKey, TValue>` — когда по ключу нужно **получить связанные данные**: счётчик, объект, индекс. Внутри они устроены одинаково (хеш-таблица с цепочками), и сложность операций совпадает — O(1) в среднем.

| Задача | Выбор |
| --- | --- |
| убрать дубликаты, «видели ли уже» | `HashSet<T>` |
| быстрая проверка вхождения вместо `List.Contains` | `HashSet<T>` |
| пересечение, объединение, разность множеств | `HashSet<T>` (`IntersectWith`, `UnionWith`, `ExceptWith`) |
| подсчёт частот | `Dictionary<T, int>` |
| кэш / индекс «id → объект» | `Dictionary<TKey, TValue>` |
| Two Sum: «значение → индекс» | `Dictionary<int, int>` |
| группировка «ключ → список» | `Dictionary<TKey, List<T>>` |

```csharp
// HashSet: только факт присутствия
var seen = new HashSet<string>(StringComparer.OrdinalIgnoreCase);
if (!seen.Add(email)) Console.WriteLine($"Дубликат: {email}");

// Dictionary: ключ → данные
var usersById = users.ToDictionary(u => u.Id);
if (usersById.TryGetValue(order.UserId, out var user)) { /* ... */ }
```

**Антипаттерн — `Dictionary<T, bool>` или `Dictionary<T, T>` вместо множества.** Работает, но хранит лишнее значение на каждую запись и хуже выражает намерение. `HashSet<T>` экономнее по памяти и даёт операции над множествами.

**Полезные детали API:**

- `HashSet.Add` возвращает `bool` — проверка и вставка за один поиск, без отдельного `Contains`;
- `Dictionary.TryAdd`, `TryGetValue`, `GetValueOrDefault` — избегайте пары `ContainsKey` + индексатор (двойной поиск);
- `CollectionsMarshal.GetValueRefOrAddDefault(dict, key, out _)` — ссылка на значение, чтобы инкрементировать счётчик за один поиск в горячем коде;
- `HashSet.TryGetValue(equalValue, out actual)` — достать уже хранящийся экземпляр (интернирование объектов);
- оба принимают `IEqualityComparer<T>` — например, `StringComparer.OrdinalIgnoreCase`.

**Ограничения обоих:** порядок перечисления не гарантирован, ключи должны корректно реализовывать `Equals`/`GetHashCode` и не меняться после добавления, `null` как ключ в `Dictionary` недопустим.

**Смежные варианты:**

| Нужно дополнительно | Тип |
| --- | --- |
| упорядоченность, диапазоны | `SortedSet<T>` / `SortedDictionary<TKey, TValue>` — O(log n) |
| многопоточность | `ConcurrentDictionary<TKey, TValue>` (готового `ConcurrentHashSet` нет — используют `ConcurrentDictionary<T, byte>`) |
| неизменяемый справочник, только чтение | `FrozenSet<T>` / `FrozenDictionary<TKey, TValue>` |
| порядок вставки | `OrderedDictionary<TKey, TValue>` (.NET 9) |

## Как оценить память, которую использует алгоритм?

```yaml
category: algorithms
level: middle
difficulty: 3
slug: algorithms-kak-ocenit-pamyat-kotoruyu-ispolzuet-algoritm
```

Память оценивают так же, как время, — через Big O, но считают **дополнительную** память (auxiliary space): новые коллекции, копии данных и глубину стека рекурсии. Сам входной массив обычно не учитывается, если об этом не договорились отдельно.

**Что увеличивает память:**

| Источник | Пример | Память |
| --- | --- | --- |
| несколько переменных | счётчики, указатели | O(1) |
| вспомогательная коллекция | `HashSet` увиденных, `Dictionary` частот | O(n) или O(k) уникальных |
| копия входа | `ToList()`, `ToArray()`, `Substring`, срез массива `a[1..]` | O(n) |
| матрица / таблица DP | `dp[n, m]` | O(n·m), часто сжимается до O(m) |
| **рекурсия** | каждый вызов — кадр стека | O(глубины) |
| результат | вернуть все подмножества | O(2ⁿ·n) — обычно указывают отдельно |

**Примеры:**

- бинарный поиск итеративно — O(1), рекурсивно — O(log n) за счёт стека;
- mergesort — O(n) буфер; quicksort — O(log n) стек (O(n) в худшем без оптимизации);
- DFS по графу — O(V) на `visited` плюс O(V) стек в худшем случае (граф-цепочка);
- Фибоначчи с мемоизацией — O(n) кэш и O(n) стек; итеративно с двумя переменными — O(1).

**Скрытые аллокации в C#,** которые не видны в Big O, но влияют на реальный расход:

- `string` неизменяемы: `s += c` в цикле даёт O(n²) суммарных аллокаций — используйте `StringBuilder`;
- LINQ создаёт итераторы и замыкания; `ToList()`/`OrderBy()` материализуют весь источник;
- боксинг value types при приведении к `object` или необобщённому интерфейсу;
- рост `List<T>`/`Dictionary` удвоением оставляет мусор — задавайте `capacity`;
- `Substring`/`Split` копируют — `Span<T>`/`ReadOnlySpan<char>` позволяют работать со срезами без аллокаций;
- `stackalloc` — буфер на стеке для небольших фиксированных размеров.

**Константа тоже важна.** `LinkedList<int>` и `List<int>` оба O(n), но первый тратит около 48 байт на элемент против 4 у второго. `Dictionary<int, int>` — примерно в 5–6 раз больше памяти на элемент, чем массив пар: хеш, индекс следующей записи, ключ, значение и запас ёмкости.

**Как измерить на практике:**

- **BenchmarkDotNet** с `[MemoryDiagnoser]` — аллокации на операцию и сборки мусора по поколениям;
- `GC.GetAllocatedBytesForCurrentThread()` до и после — быстрая проверка в тесте;
- `dotnet-counters` — GC heap size и частота сборок в работающем приложении;
- `dotnet-gcdump`/`dotnet-dump` и профилировщики (Visual Studio, dotMemory) — кто держит память.

**Компромисс время/память.** Большинство ускорений покупаются памятью: `HashSet` вместо вложенного цикла, мемоизация, префиксные суммы. Если память ограничена — сортировка на месте и два указателя, потоковая обработка вместо материализации.

## Что такое recursion?

```yaml
category: algorithms
level: middle
difficulty: 2
slug: algorithms-chto-takoe-recursion
tags: complexity
```

Рекурсия — это когда функция решает задачу, вызывая саму себя на меньшей подзадаче того же вида. Любая корректная рекурсия состоит из **базового случая** (где ответ известен сразу) и **рекурсивного шага**, который гарантированно приближает вход к базовому случаю.

```csharp
// Высота бинарного дерева: естественно рекурсивная задача
int Height(TreeNode? node)
{
    if (node is null) return 0;                         // базовый случай
    return 1 + Math.Max(Height(node.Left), Height(node.Right)); // шаг
}
```

**Как это работает.** Каждый вызов получает свой кадр на стеке вызовов: параметры, локальные переменные, адрес возврата. Вызовы «спускаются» до базового случая, затем результаты собираются при раскрутке стека. Поэтому рекурсия всегда стоит памяти — O(глубины рекурсии), даже если явных коллекций нет.

**Как оценить сложность.** Время = число вызовов × работа в одном вызове, память = максимальная глубина:

| Пример | Вызовов | Время | Память (стек) |
| --- | --- | --- | --- |
| факториал `n * F(n-1)` | n | O(n) | O(n) |
| бинарный поиск | log n | O(log n) | O(log n) |
| обход дерева | n узлов | O(n) | O(h), h — высота |
| наивный Фибоначчи `F(n-1) + F(n-2)` | ~2ⁿ | O(2ⁿ) | O(n) |

**Где рекурсия уместна:** деревья и графы (DFS), «разделяй и властвуй» (mergesort, quicksort), перебор с возвратом (перестановки, подмножества), разбор вложенных структур (JSON, выражения). Там рекурсивный код короче и ближе к определению задачи.

**Мемоизация.** Если подзадачи повторяются, как в Фибоначчи, кэш результатов превращает экспоненту в линию — это top-down динамическое программирование:

```csharp
long Fib(int n, Dictionary<int, long> memo)
{
    if (n < 2) return n;
    if (memo.TryGetValue(n, out var v)) return v;
    return memo[n] = Fib(n - 1, memo) + Fib(n - 2, memo);
}
```

**Типичные ошибки:**

- нет базового случая или шаг не уменьшает вход → бесконечная рекурсия и `StackOverflowException`;
- экспоненциальное время из-за повторных подзадач без мемоизации;
- большая глубина на реальных данных (список из 10⁶ узлов, вырожденное дерево) — стек кончается.

**Хвостовая рекурсия.** Если рекурсивный вызов — последнее действие функции, его можно заменить прыжком без нового кадра. Компилятор C# такой оптимизации не гарантирует (JIT иногда делает её сам, но полагаться на это нельзя), поэтому при потенциально большой глубине рекурсию переписывают в цикл с явным `Stack<T>`/`Queue<T>`.

## Какие проблемы могут возникнуть при глубокой рекурсии?

```yaml
category: algorithms
level: middle
difficulty: 3
slug: algorithms-kakie-problemy-mogut-vozniknut-pri-glubokoi-rekursii
tags: complexity
```

Главная проблема — переполнение стека: у каждого потока стек фиксированного размера (порядка 1 МБ по умолчанию), и при глубине в десятки–сотни тысяч вызовов он заканчивается. В .NET `StackOverflowException` нельзя перехватить — процесс аварийно завершается целиком. Вторичные проблемы — лишняя память, экспоненциальное время и плохо предсказуемая производительность.

**Почему именно падение процесса.** Начиная с .NET 2.0 CLR не даёт обработать переполнение стека: `try/catch` не сработает, `finally` не выполнятся, веб-сервер потеряет все текущие запросы. Поэтому рекурсия по недоверенным данным — это ещё и вектор DoS: достаточно прислать JSON или XML с вложенностью 100 000.

**Сколько вызовов помещается** — зависит от размера кадра (параметры, локальные переменные, `stackalloc`), режима сборки и платформы. Ориентир — от нескольких тысяч до ~100 тысяч вызовов. Точное число не гарантировано, поэтому проектировать «на грани» нельзя.

**Как защититься:**

1. **Переписать итеративно** с явным стеком в куче — самый надёжный вариант, память ограничена только кучей:

```csharp
int MaxDepth(TreeNode? root)
{
    if (root is null) return 0;
    var stack = new Stack<(TreeNode Node, int Depth)>();
    stack.Push((root, 1));
    int max = 0;
    while (stack.Count > 0)
    {
        var (node, depth) = stack.Pop();
        max = Math.Max(max, depth);
        if (node.Left is not null)  stack.Push((node.Left, depth + 1));
        if (node.Right is not null) stack.Push((node.Right, depth + 1));
    }
    return max;
}
```

2. **Ограничить глубину явно** — счётчик уровня и понятная ошибка при превышении. Так делают парсеры: у `System.Text.Json` `MaxDepth` по умолчанию 64.
3. **Проверять запас стека**: `RuntimeHelpers.EnsureSufficientExecutionStack()` бросает перехватываемое `InsufficientExecutionStackException`, а `TryEnsureSufficientExecutionStack()` возвращает `bool`. Этим пользуются компиляторы выражений и Roslyn.
4. **Запустить в потоке с большим стеком** — `new Thread(work, maxStackSize: 64 * 1024 * 1024)`. Это костыль для оффлайн-расчётов, не для обработки запросов.
5. **Уменьшить глубину алгоритмически**: в quicksort рекурсивно обрабатывать меньшую часть, а большую — циклом, тогда глубина O(log n) даже в худшем случае.

**Другие проблемы глубокой рекурсии:**

- **Память O(глубины)** — её часто забывают при оценке сложности: рекурсивный DFS по графу-цепочке тратит O(V) стека.
- **Экспоненциальное время** из-за повторяющихся подзадач — лечится мемоизацией или переходом к bottom-up DP.
- **Накладные расходы на вызов**: пролог/эпилог, отсутствие инлайнинга рекурсивных методов — итеративная версия обычно быстрее на константу.
- **Хвостовые вызовы не гарантированы.** C#-компилятор не эмитит префикс `tail.`, поэтому надеяться, что «хвостовая рекурсия не растит стек», нельзя.
- **async-рекурсия** не спасает: пока `await` завершается синхронно, продолжения выполняются на том же стеке, а при реальной асинхронности каждый уровень аллоцирует state machine в куче.

**На собеседовании** хороший ответ: назвать StackOverflow и то, что его нельзя поймать, затем показать итеративную версию и упомянуть ограничение глубины для входных данных извне.

## Что такое BFS?

```yaml
category: algorithms
level: middle
difficulty: 2
slug: algorithms-chto-takoe-bfs
tags: complexity
```

BFS (Breadth-First Search, поиск в ширину) — обход графа или дерева «волнами»: сначала все вершины на расстоянии 1 от старта, потом на расстоянии 2 и так далее. Реализуется через очередь (FIFO), и благодаря этому порядку в невзвешенном графе BFS находит кратчайший путь по числу рёбер.

**Алгоритм:**

1. положить старт в очередь и пометить как посещённый;
2. пока очередь не пуста — достать вершину, для каждого непосещённого соседа: пометить, записать расстояние/родителя, положить в очередь.

```csharp
// Кратчайшее число шагов от start до target; -1, если недостижимо
int ShortestPath(Dictionary<int, List<int>> graph, int start, int target)
{
    var dist = new Dictionary<int, int> { [start] = 0 };
    var queue = new Queue<int>();
    queue.Enqueue(start);

    while (queue.Count > 0)
    {
        var v = queue.Dequeue();
        if (v == target) return dist[v];
        foreach (var next in graph.GetValueOrDefault(v, []))
        {
            if (dist.TryAdd(next, dist[v] + 1))   // TryAdd == «ещё не посещён»
                queue.Enqueue(next);
        }
    }
    return -1;
}
```

**Почему путь кратчайший.** Очередь гарантирует, что все вершины уровня k обрабатываются раньше любой вершины уровня k + 1. Значит, в момент первого обнаружения вершины до неё уже найден путь минимальной длины — более короткого позже не появится.

**Сложность:** время O(V + E) — каждая вершина попадает в очередь один раз, каждое ребро просматривается один раз (ориентированный граф) или два (неориентированный). Память O(V) на `visited` и очередь; для дерева — O(ширины самого широкого уровня).

**Обход по уровням.** Если нужен номер уровня или группировка (level order traversal дерева), фиксируйте размер очереди перед обработкой уровня:

```csharp
while (queue.Count > 0)
{
    int levelSize = queue.Count;
    for (int i = 0; i < levelSize; i++) { /* Dequeue и добавить детей */ }
    level++;
}
```

**Частые ошибки:**

- **помечать вершину при извлечении, а не при добавлении** — одна вершина попадёт в очередь многократно, в плотном графе это O(V²) операций и лишняя память;
- забыть `visited` в графе с циклами — бесконечный цикл (в дереве `visited` не нужен);
- применять BFS к **взвешенному** графу — он минимизирует число рёбер, а не сумму весов; там нужен Dijkstra (или 0-1 BFS с деком, если веса только 0 и 1);
- на сетке (`grid[r][c]`) — забыть проверку границ и препятствий перед добавлением соседа.

**Чтобы восстановить сам путь,** храните `parent[next] = v`, после нахождения цели пройдите от неё к старту по родителям и разверните список.

## Что такое DFS?

```yaml
category: algorithms
level: middle
difficulty: 2
slug: algorithms-chto-takoe-dfs
tags: complexity
```

DFS (Depth-First Search, поиск в глубину) — обход, который идёт по одной ветке как можно глубже, пока не упрётся в тупик, затем откатывается назад и пробует следующую ветку. Реализуется рекурсией (стек вызовов) или явным `Stack<T>`.

```csharp
// Рекурсивный DFS: посетить все вершины, достижимые из v
void Dfs(Dictionary<int, List<int>> graph, int v, HashSet<int> visited)
{
    if (!visited.Add(v)) return;           // уже были здесь
    // pre-order: обработать v до потомков
    foreach (var next in graph.GetValueOrDefault(v, []))
        Dfs(graph, next, visited);
    // post-order: обработать v после всех потомков
}
```

**Итеративная версия** — когда глубина может быть большой и есть риск переполнить стек:

```csharp
var visited = new HashSet<int>();
var stack = new Stack<int>();
stack.Push(start);
while (stack.Count > 0)
{
    var v = stack.Pop();
    if (!visited.Add(v)) continue;          // помечаем при извлечении
    foreach (var next in graph.GetValueOrDefault(v, []))
        if (!visited.Contains(next)) stack.Push(next);
}
```

Порядок посещения у неё отличается от рекурсивной (соседи снимаются со стека в обратном порядке), а post-order так просто не получить — нужен стек с состоянием «вершина + индекс следующего соседа» или повторное помещение вершины с флагом «дети обработаны».

**Сложность:** время O(V + E), память O(V) на `visited` плюс O(глубины) на стек — в худшем случае (граф-цепочка) тоже O(V). Для дерева — O(h), где h — высота: O(log n) для сбалансированного, O(n) для вырожденного.

**Pre-order и post-order** — главное, что даёт DFS помимо самого обхода:

- **pre-order** — копирование/сериализация дерева, вывод структуры каталогов;
- **in-order** в BST — ключи в отсортированном порядке;
- **post-order** — размеры поддеревьев, освобождение ресурсов снизу вверх, **топологическая сортировка** (вершины в порядке завершения, затем разворот).

**Что решают DFS-ом:**

- компоненты связности, «количество островов» на сетке, flood fill;
- поиск цикла: в ориентированном графе — три цвета (белый/серый/чёрный), ребро в серую вершину означает цикл;
- топологическая сортировка зависимостей (порядок сборки проектов, миграций);
- перебор с возвратом (backtracking): перестановки, подмножества, судоку;
- задачи на деревьях: высота, сумма пути, LCA, проверка BST;
- продвинутое: мосты и точки сочленения, сильно связные компоненты (Tarjan, Kosaraju).

**Подводные камни:** рекурсия на больших входах (10⁵+ вершин в цепочке) грозит `StackOverflowException`, который в .NET не перехватывается; без `visited` в графе с циклами — бесконечная рекурсия; DFS **не** находит кратчайший путь — первый найденный путь может быть сколь угодно длинным.

## Чем BFS отличается от DFS?

```yaml
category: algorithms
level: middle
difficulty: 3
slug: algorithms-chem-bfs-otlichaetsya-ot-dfs
tags: complexity
```

Оба алгоритма обходят все достижимые вершины за O(V + E), но в разном порядке: BFS идёт уровнями от старта через очередь, DFS уходит вглубь одной ветки через стек или рекурсию. Из порядка следует главное практическое различие: BFS даёт кратчайший путь в невзвешенном графе, DFS — нет, зато DFS естественно даёт pre/post-order, на которых строятся топосортировка, поиск циклов и backtracking.

| | BFS | DFS |
| --- | --- | --- |
| Структура | очередь (FIFO) | стек (LIFO) или рекурсия |
| Порядок | по расстоянию от старта | по веткам, с откатом |
| Кратчайший путь (без весов) | да | нет |
| Время | O(V + E) | O(V + E) |
| Память | O(ширины уровня), до O(V) | O(глубины), до O(V) |
| Огромный/бесконечный граф | находит близкие цели | может уйти в бесконечную ветку |
| Типичные задачи | минимум шагов, уровни дерева, ближайший объект | топосортировка, циклы, компоненты, перебор |

**Структурно это один алгоритм.** Если в итеративном обходе заменить `Queue<T>` на `Stack<T>`, BFS превращается в вариант DFS. Всё различие — в том, какую из найденных, но ещё не обработанных вершин брать следующей: самую раннюю или самую свежую.

**Память — тонкий момент.** Асимптотически оба O(V), но на практике всё решает форма графа:

- **широкое неглубокое дерево** (у узла тысячи детей): очередь BFS держит целый уровень — много; стек DFS — мало;
- **глубокая цепочка**: BFS держит 1–2 вершины, DFS — всю глубину, и рекурсивный вариант может переполнить стек;
- полное бинарное дерево из n узлов: BFS в пике держит последний уровень ≈ n/2 узлов, DFS — log n.

**Когда цель близко, а граф большой,** BFS найдёт её, просмотрев только ближайшие уровни, а DFS может долго исследовать огромную ветку в другом направлении. Если же нужно обойти всё или просто проверить достижимость, разницы по времени нет, и рекурсивный DFS короче в записи.

**Гибрид — Iterative Deepening DFS (IDDFS):** DFS с ограничением глубины 1, 2, 3, … Находит кратчайший по числу рёбер путь, как BFS, а памяти тратит как DFS. Применяется в поиске по играм и в больших пространствах состояний, где уровень BFS не помещается в память.

**Для взвешенных графов** не подходит ни тот, ни другой: кратчайший путь ищет Dijkstra (по сути BFS с приоритетной очередью вместо обычной) или Bellman–Ford при отрицательных весах.

**Короткий ответ для собеседования:** «очередь против стека; BFS — кратчайший путь и уровни, DFS — полный перебор, топосортировка, циклы; время одинаковое, память зависит от ширины против глубины».

## Когда использовать BFS?

```yaml
category: algorithms
level: middle
difficulty: 3
slug: algorithms-kogda-ispolzovat-bfs
tags: complexity
```

BFS выбирают, когда важно **расстояние**: минимальное число шагов, ближайший объект, обработка по уровням. Сигнал в условии задачи — слова «минимальное количество ходов/преобразований», «кратчайший путь» при одинаковой цене шага, «на каком уровне», «ближайший».

**Типичные сценарии:**

| Задача | Почему BFS |
| --- | --- |
| кратчайший путь в лабиринте/сетке | все шаги стоят одинаково |
| word ladder, ходы коня, минимум операций над числом | вершины — состояния, рёбра — допустимые переходы |
| level order обход дерева, «правый вид», среднее по уровням | нужен порядок по уровням |
| степень связи в соцсети («друзья друзей» до 2-го круга) | расстояние ограничено k |
| краулер с лимитом глубины, распространение по сети | идём волнами от источника |
| проверка двудольности графа | раскраска по чётности уровня |
| топосортировка по Кану | очередь вершин с нулевой входящей степенью |

**Multi-source BFS** — стартуем сразу из всех источников, положив их в очередь с расстоянием 0. Так за один проход O(V + E) считается расстояние до ближайшего источника для каждой клетки: «гниющие апельсины», «расстояние до ближайшего нуля», «ближайший склад»:

```csharp
int[][] DistanceToNearest(int[][] grid)   // 1 — источник, 0 — пустая клетка
{
    int rows = grid.Length, cols = grid[0].Length;
    var dist = new int[rows][];
    var q = new Queue<(int R, int C)>();
    for (int r = 0; r < rows; r++)
    {
        dist[r] = new int[cols];
        Array.Fill(dist[r], -1);
        for (int c = 0; c < cols; c++)
            if (grid[r][c] == 1) { dist[r][c] = 0; q.Enqueue((r, c)); }
    }

    (int, int)[] dirs = [(1, 0), (-1, 0), (0, 1), (0, -1)];
    while (q.Count > 0)
    {
        var (r, c) = q.Dequeue();
        foreach (var (dr, dc) in dirs)
        {
            int nr = r + dr, nc = c + dc;
            if (nr < 0 || nc < 0 || nr >= rows || nc >= cols || dist[nr][nc] != -1) continue;
            dist[nr][nc] = dist[r][c] + 1;
            q.Enqueue((nr, nc));
        }
    }
    return dist;                           // -1 — недостижимо
}
```

Время и память O(rows · cols). Запуск отдельного BFS из каждого источника дал бы O(k · rows · cols).

**Когда BFS не подходит:**

- **рёбра с разными весами** → Dijkstra (`PriorityQueue<TElement, TPriority>` в .NET); веса 0/1 → 0-1 BFS с деком (в .NET готового дека нет — `LinkedList<T>` или свой кольцевой буфер);
- **нужен полный перебор** или путь любой длины — DFS проще и экономнее по памяти на широких графах;
- **очень широкий граф** (большой коэффициент ветвления): уровень не помещается в память — IDDFS или двунаправленный BFS.

**Оптимизация — двунаправленный BFS:** волны от старта и от цели навстречу друг другу. При ветвлении b и расстоянии d просматривается порядка 2·b^(d/2) вершин вместо b^d. Классический приём для word ladder.

**Пограничные случаи:** старт совпадает с целью (ответ 0), цель недостижима (-1 или `null`), старт или цель — препятствие, пустой граф.

## Когда использовать DFS?

```yaml
category: algorithms
level: middle
difficulty: 3
slug: algorithms-kogda-ispolzovat-dfs
tags: complexity
```

DFS выбирают, когда нужно **исследовать структуру целиком** или **перебрать варианты**: связность, циклы, порядок зависимостей, все пути/комбинации, агрегаты по поддеревьям. Кратчайший путь ему не нужен, а порядок «зашёл — вышел» (pre/post-order) как раз полезен.

**Типичные сценарии:**

| Задача | Почему DFS |
| --- | --- |
| количество островов, компоненты связности, flood fill | достаточно обойти всё достижимое |
| цикл в графе зависимостей | «серая» вершина на текущем пути = цикл |
| топологическая сортировка | порядок завершения вершин (post-order) |
| перестановки, подмножества, комбинации, N ферзей, судоку | backtracking: выбрать → углубиться → отменить выбор |
| высота дерева, диаметр, сумма пути, проверка BST, LCA | ответ узла собирается из ответов детей |
| существует ли путь между A и B | неважно, какой он длины |
| мосты, точки сочленения, SCC (Tarjan) | нужны времена входа/выхода DFS |
| top-down DP (мемоизированная рекурсия) | DFS по графу подзадач |

**Пример — поиск цикла и топосортировка за один проход** (порядок сборки проектов):

```csharp
// null, если в зависимостях есть цикл
List<int>? TopoSort(int n, List<int>[] deps)
{
    var state = new byte[n];      // 0 — не посещён, 1 — на текущем пути, 2 — готов
    var order = new List<int>(n);

    bool Visit(int v)
    {
        if (state[v] == 1) return false;       // вернулись в вершину текущего пути — цикл
        if (state[v] == 2) return true;
        state[v] = 1;
        foreach (var d in deps[v])
            if (!Visit(d)) return false;
        state[v] = 2;
        order.Add(v);                          // post-order: зависимости уже добавлены
        return true;
    }

    for (int v = 0; v < n; v++)
        if (!Visit(v)) return null;
    return order;                              // сначала зависимости, потом зависящие
}
```

Время O(V + E), память O(V). Двух состояний (visited/не visited) для ориентированного графа недостаточно: вершина, посещённая через другую ветку, — это не цикл.

**Backtracking** — тот же DFS по дереву решений:

```csharp
void Subsets(int[] nums, int i, List<int> cur, List<List<int>> res)
{
    if (i == nums.Length) { res.Add([.. cur]); return; }
    Subsets(nums, i + 1, cur, res);            // не берём nums[i]
    cur.Add(nums[i]);
    Subsets(nums, i + 1, cur, res);            // берём
    cur.RemoveAt(cur.Count - 1);               // откат выбора
}
```

Здесь время O(2ⁿ · n) определяется размером ответа, а стек — всего O(n).

**Когда DFS не подходит или опасен:**

- нужен **минимум шагов** → BFS;
- **глубина может быть огромной** (цепочка из 10⁵–10⁶ вершин, вырожденное дерево) → итеративный DFS с явным `Stack<T>`, иначе `StackOverflowException`;
- **бесконечное или очень глубокое пространство состояний** → DFS может никогда не вернуться; нужен лимит глубины или IDDFS.

**Выбор на практике:** если обе стратегии подходят (подсчёт островов, проверка достижимости), берут то, что короче написать без ошибок, — обычно рекурсивный DFS, — и упоминают риск глубины.

## Какие алгоритмы обычно спрашивают на Middle backend interview?

```yaml
category: algorithms
level: middle
difficulty: 3
slug: algorithms-kakie-algoritmy-obychno-sprashivayut-na-middle-backend-interview
```

На Middle backend-собеседовании обычно дают 1–2 задачи уровня easy/medium на 30–45 минут. Проверяют не знание экзотических алгоритмов, а умение выбрать структуру данных, оценить сложность, написать рабочий код без подсказок IDE и разобрать граничные случаи. Почти всё покрывается десятком паттернов.

**Что спрашивают чаще всего:**

| Паттерн | Типичные задачи | Ключевая идея |
| --- | --- | --- |
| хеширование | дубликаты, two sum, анаграммы, первый уникальный символ, частоты | `Dictionary`/`HashSet` → O(n) вместо O(n²) |
| два указателя | палиндром, слияние отсортированных массивов, пары в отсортированном массиве | движемся с двух концов или двумя скоростями |
| скользящее окно | самая длинная подстрока без повторов, максимальная сумма окна k | расширяем правую границу, сжимаем левую |
| стек | корректность скобок, next greater element, вычисление выражений | LIFO и монотонный стек |
| бинарный поиск | поиск в отсортированном массиве, первая позиция, «поиск по ответу» | инвариант `lo`/`hi`, O(log n) |
| сортировка + проход | слияние интервалов, встречи в переговорных | сортировка задаёт порядок, дальше O(n) |
| деревья | обходы, высота, проверка BST, LCA, level order | рекурсивный DFS, BFS по уровням |
| графы | острова, кратчайший путь в сетке, топосортировка | BFS/DFS, `visited` |
| куча | top K, k-й наибольший, слияние k отсортированных списков | `PriorityQueue` размера k → O(n log k) |
| связный список | разворот, поиск цикла, середина списка | указатели, fast/slow |
| простая DP | лестница, максимальная сумма подмассива (Kadane), размен монет | подзадачи + таблица, сжатие памяти |

**Теория, которую ждут устно:**

- Big O по времени и памяти, амортизированная сложность `List<T>.Add`;
- как устроены `Dictionary`/`HashSet` (бакеты, коллизии, требования к `GetHashCode`), почему O(1) в среднем;
- сложности основных операций коллекций .NET: `List`, `LinkedList`, `Queue`, `Stack`, `SortedDictionary`, `PriorityQueue`;
- quicksort против mergesort, стабильность сортировки, что использует `Array.Sort` (introsort);
- рекурсия и её риски.

**Backend-флейвор** — задачи, похожие на реальный код:

- **LRU cache** на `Dictionary` + `LinkedList` с O(1) на операцию;
- **rate limiter** (фиксированное/скользящее окно, token bucket);
- дедупликация и группировка событий, подсчёт top-N по логам;
- слияние отсортированных потоков (k-way merge) и пагинация по курсору;
- разбор строк: парсинг логов, валидация, простой шаблонизатор.

**Что обычно не спрашивают на Middle:** красно-чёрные деревья по коду, сложные DP на отрезках, потоки в сетях, суффиксные структуры. Dijkstra и trie встречаются, но скорее как «расскажите идею».

**Как проходить задачу:**

1. уточнить вход: размеры, пустые значения, дубликаты, отрицательные числа, отсортированность;
2. проговорить наивное решение и его сложность;
3. улучшить (обычно хешем, сортировкой или двумя указателями) и назвать новую сложность;
4. написать код, проговаривая инварианты;
5. прогнать вручную на маленьком примере и граничных случаях: пустой вход, один элемент, все одинаковые, переполнение `int`.
