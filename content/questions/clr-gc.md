## Что такое CLR?

```yaml
category: clr-gc
level: middle
difficulty: 2
slug: clr-gc-chto-takoe-clr
tags: clr
```

CLR (Common Language Runtime) — среда выполнения .NET: она загружает сборки, превращает IL в машинный код, управляет памятью и потоками, обеспечивает типобезопасность и обработку исключений. C#-программа исполняется не «голой» на процессоре, а внутри CLR — поэтому код и называют managed.

**Из чего состоит и что делает:**

| Подсистема | Ответственность |
| --- | --- |
| Loader / type system | загрузка сборок, построение `MethodTable` для каждого типа, проверка метаданных |
| JIT (RyuJIT) | компиляция IL в машинный код при первом вызове метода, tiered compilation, PGO |
| GC | выделение памяти в managed-куче и автоматическое освобождение недостижимых объектов |
| Исключения | двухпроходная обработка: поиск `catch`, затем раскрутка стека с `finally` |
| Потоки и синхронизация | управляемые потоки, `ThreadPool`, `Monitor`, safe points для GC |
| Interop | P/Invoke, COM, маршалинг между managed и native |
| Безопасность типов | проверка приведений, bounds checks массивов, запрет произвольной арифметики указателей вне `unsafe` |

**Как это выглядит на практике.** `dotnet app.dll` запускает хост (`dotnet.exe` / apphost), тот находит нужную версию рантайма (`hostfxr` → `hostpolicy`) и загружает `coreclr`. Дальше CLR читает метаданные сборки, находит `Main`, JIT компилирует его — и программа поехала.

```csharp
Console.WriteLine(Environment.Version);                  // версия рантайма, например 10.0.x
Console.WriteLine(System.Runtime.InteropServices.RuntimeInformation.FrameworkDescription); // ".NET 10.0.x"
```

**Связь с CLI и CTS.** CLR — это реализация стандарта ECMA-335 (CLI). Стандарт описывает общую систему типов (CTS) и IL, благодаря чему C#, F# и VB.NET компилируются в один формат и свободно используют типы друг друга.

**Реализации.** Сейчас основная — CoreCLR (.NET 5+, кроссплатформенная). Исторически был CLR в .NET Framework (только Windows), для мобильных и WebAssembly используется Mono. NativeAOT — это тот же рантайм, но без JIT: код компилируется заранее, а в бинарник вшивается урезанный рантайм с GC.

**Что спрашивают дальше:** чем managed-код отличается от unmanaged, как устроен JIT и tiered compilation, как работает GC, что такое BCL (библиотека классов — это не CLR, а код поверх него).

## Что происходит с C# кодом от компиляции до выполнения?

```yaml
category: clr-gc
level: middle
difficulty: 3
slug: clr-gc-chto-proishodit-s-c-kodom-ot-kompilyacii-do-vypolneniya
```

Компилятор Roslyn превращает C# в IL и метаданные внутри сборки (`.dll`), а при запуске CLR загружает сборку и JIT-компилирует IL в машинный код метод за методом, в момент первого вызова. Машинный код появляется только на целевой машине, в рантайме.

**По шагам:**

1. **Компиляция (`dotnet build`).** Roslyn разбирает исходники, проверяет типы, раскрывает синтаксический сахар (`async`, `foreach`, `using`, лямбды, record'ы превращаются в обычные классы и методы) и генерирует IL + метаданные + манифест в PE-файл.
2. **Запуск.** Хост (`dotnet` или apphost) по `runtimeconfig.json` выбирает версию рантайма и загружает CoreCLR.
3. **Загрузка.** Assembly loader читает метаданные, по мере надобности подгружает зависимые сборки, строит `MethodTable` для используемых типов. Статические конструкторы выполняются лениво — при первом обращении к типу.
4. **JIT.** Каждый метод изначально указывает на заглушку (prestub). При первом вызове JIT компилирует IL в машинный код, заглушка подменяется адресом готового кода, повторные вызовы идут напрямую.
5. **Tiered compilation.** Сначала метод компилируется быстро и без оптимизаций (Tier 0). Если его вызывают часто, в фоне он перекомпилируется с полными оптимизациями (Tier 1), с учётом собранного профиля (Dynamic PGO, включён по умолчанию с .NET 8).
6. **Выполнение.** Машинный код работает под присмотром CLR: GC выделяет и собирает память, исключения разбираются рантаймом, в safe points потоки могут быть остановлены для сборки мусора.

```csharp
int Sum(int[] a) { var s = 0; foreach (var x in a) s += x; return s; }
// IL (фрагмент): ldloc.0 / ldloc.2 / ldelem.i4 / add / stloc.0 ...
// машинный код появится только при первом вызове Sum
```

**Альтернативы JIT на старте:**

- **ReadyToRun** — IL плюс заранее скомпилированный машинный код в той же сборке; JIT подключается для горячих методов (Tier 1) и того, что не удалось прекомпилировать.
- **NativeAOT** — весь код компилируется в нативный бинарник при публикации, JIT в рантайме нет вообще.

**Типичные вопросы дальше:** почему первый запрос к сервису медленный (JIT, загрузка типов, статические конструкторы, прогрев кэшей), зачем в IL нужны метаданные (рефлексия, проверка типов, сериализация), что делает `dotnet publish -p:PublishReadyToRun=true`.

## Что такое IL?

```yaml
category: clr-gc
level: middle
difficulty: 2
slug: clr-gc-chto-takoe-il
tags: clr
```

IL (Intermediate Language, он же CIL или MSIL) — промежуточный байткод, в который компилируются все .NET-языки. Он не зависит от процессора и ОС: одна и та же `.dll` работает на x64, ARM64, Windows и Linux, потому что в машинный код её превращает JIT уже на месте.

**Как устроен.** IL — стековая машина: инструкции кладут значения на стек вычислений и снимают их оттуда. Регистров нет, их распределяет JIT.

```csharp
static int Add(int a, int b) => a + b;
```

```text
.method static int32 Add(int32 a, int32 b)
{
  ldarg.0    // положить a на стек
  ldarg.1    // положить b
  add        // снять два, положить сумму
  ret
}
```

**Что ещё лежит рядом с IL в сборке — метаданные.** Таблицы типов, методов, полей, атрибутов, ссылок на другие сборки. Именно метаданные делают возможными рефлексию, `typeof`, сериализацию, проверку типов при загрузке и межъязыковое взаимодействие. IL без метаданных бессмыслен: инструкция `call` ссылается на токен метода в таблице.

**Особенности IL, которые полезно знать:**

- **Он высокоуровневый и типизированный.** Есть инструкции `newobj`, `box`, `unbox.any`, `callvirt`, `castclass`, `isinst` — IL знает про объекты, виртуальные вызовы и исключения, в отличие от ассемблера.
- **Он богаче C#.** Некоторые вещи возможны в IL, но не выражаются в C# напрямую (например, фильтры исключений существовали в IL задолго до `catch when`).
- **Его легко декомпилировать.** ILSpy, dnSpy, dotPeek восстанавливают почти исходный C#. Поэтому секреты в коде не хранят, а для защиты используют обфускаторы.
- **Сахар раскрыт.** В IL уже нет `async`/`await`, `using`, лямбд — только сгенерированные классы и state machine. Смотреть IL полезно, чтобы понять, где появляются `box` или скрытые аллокации.

**Где посмотреть:** sharplab.io (C# → IL → JIT asm), ILSpy, `ildasm`.

**Что спрашивают дальше:** чем IL отличается от байткода Java (идеологически близко, но IL изначально проектировался под JIT, а не интерпретацию), что такое `callvirt` и почему C# использует его даже для невиртуальных методов (заодно проверка на `null`).

## Что такое JIT?

```yaml
category: clr-gc
level: middle
difficulty: 2
slug: clr-gc-chto-takoe-jit
tags: clr
```

JIT (Just-In-Time) — компилятор внутри CLR, который превращает IL в машинный код во время выполнения, при первом вызове метода. В .NET это RyuJIT. Скомпилированный код кэшируется в памяти процесса, и повторные вызовы идут уже напрямую.

**Механика первого вызова.** У каждого метода сначала есть только заглушка (prestub). Первый вызов попадает в неё → CLR вызывает JIT → получается машинный код → адрес в таблице методов подменяется, и больше JIT для этого метода (на этом уровне) не вызывается.

**Почему JIT, а не сразу машинный код:**

- **Переносимость.** Одна сборка для всех платформ.
- **Оптимизация под конкретную машину.** JIT знает реальный CPU и использует AVX2/AVX-512, если они есть (`Vector<T>`, `Vector256` получают правильную ширину).
- **Оптимизация под реальные данные.** `static readonly` поля к моменту Tier 1 уже инициализированы и сворачиваются в константы, ветки по ним вырезаются; Dynamic PGO видит, какие типы реально приходят в интерфейсный вызов, и девиртуализирует его.

**Tiered compilation** (включена по умолчанию):

| Уровень | Что это | Зачем |
| --- | --- | --- |
| Tier 0 | быстрая компиляция без оптимизаций | быстрый старт |
| Tier 0 instrumented | Tier 0 + сбор профиля | данные для PGO |
| Tier 1 | полная оптимизация с учётом профиля | пиковая производительность |

Метод, вызванный достаточно много раз, перекомпилируется в Tier 1 в фоновом потоке. Для долгих циклов в Tier 0-коде есть OSR — переход на оптимизированную версию прямо посреди выполнения метода.

**Цена JIT:**

- время старта — первые запросы к сервису заметно медленнее;
- память под сгенерированный код и структуры JIT;
- на платформах, где генерация кода в рантайме запрещена (iOS), JIT недоступен.

**Альтернативы:** ReadyToRun (прекомпилированный код в сборке, JIT догоняет горячие методы) и NativeAOT (JIT нет совсем, старт быстрый, но нет Dynamic PGO и ограничена рефлексия).

```csharp
// посмотреть, что сгенерировал JIT (работает на релизном рантайме с .NET 7)
// DOTNET_JitDisasm="Sum" dotnet run -c Release
```

**Что спрашивают дальше:** что такое инлайнинг и когда JIT его не делает, почему бенчмарк без прогрева врёт, как ускорить холодный старт.

## Чем managed memory отличается от unmanaged memory?

```yaml
category: clr-gc
level: middle
difficulty: 3
slug: clr-gc-chem-managed-memory-otlichaetsya-ot-unmanaged-memory
tags: memory
```

Managed memory — память, которой распоряжается CLR: объекты в managed-куче выделяет и освобождает GC, он же может их перемещать. Unmanaged memory — всё, что выделено в обход GC (native-аллокатор, ОС, сторонние библиотеки): рантайм о ней ничего не знает, и освобождать её обязан код.

| | Managed | Unmanaged |
| --- | --- | --- |
| Кто выделяет | CLR (`new`) | ОС, `malloc`, `NativeMemory.Alloc`, `Marshal.AllocHGlobal`, native-библиотеки |
| Кто освобождает | GC, автоматически | код явно: `Free`, `CloseHandle`, `Dispose` |
| Перемещение | GC может двигать объекты при уплотнении | адрес стабилен |
| Типобезопасность | да, bounds checks, проверки приведений | нет, ошибка = порча памяти |
| Видимость в `dotnet-counters` | GC heap size | не видна как heap, только в общем RSS |
| Типичные ошибки | удержание ссылок (логические утечки) | утечки, use-after-free, double free |

**Что относится к unmanaged в реальном .NET-приложении:**

- файловые и сокетные дескрипторы, мьютексы, соединения в native-драйверах;
- буферы native-библиотек (SkiaSharp, SQLite, ONNX, libz);
- память, выделенная через `NativeMemory` / `Marshal.AllocHGlobal`;
- стеки потоков, JIT-код, внутренние структуры самого рантайма.

**Как их связывают.** Managed-объект часто лишь «обёртка» над unmanaged-ресурсом. GC видит маленький объект в 24 байта и не знает, что за ним стоит мегабайтный native-буфер. Поэтому:

```csharp
IntPtr p = Marshal.AllocHGlobal(1_000_000);
GC.AddMemoryPressure(1_000_000);          // подсказать GC реальную «цену» обёртки
try { /* ... */ }
finally
{
    Marshal.FreeHGlobal(p);
    GC.RemoveMemoryPressure(1_000_000);
}
```

Правильный паттерн — `SafeHandle` (гарантированное освобождение даже при аварийном сценарии) плюс `IDisposable` для детерминированного освобождения через `using`.

**Граница при interop.** Передавая managed-массив в native-код, его нужно закрепить (`fixed`, `GCHandle.Alloc(..., Pinned)`), иначе GC может его переместить посреди native-вызова. P/Invoke-маршалер пиннит аргументы на время вызова сам, но если native-код сохраняет указатель на потом — пиннинг ваша забота.

**Практический вывод:** если процесс потребляет гораздо больше, чем показывает GC heap, ищите unmanaged: native-библиотеки, неосвобождённые handle'ы, фрагментацию native-аллокатора.

## Как работает Garbage Collector?

```yaml
category: clr-gc
level: middle
difficulty: 3
slug: clr-gc-kak-rabotaet-garbage-collector
tags: memory
```

GC в .NET — трассирующий, поколенческий, уплотняющий сборщик. Он не считает ссылки, а периодически обходит граф объектов от корней, помечает всё достижимое, а остальное считает мусором; выжившие объекты сдвигает друг к другу, чтобы память оставалась непрерывной.

**Выделение.** Managed-куча — это непрерывные участки, и `new` для маленького объекта — просто сдвиг указателя в allocation context текущего потока (bump pointer). Поэтому аллокация в .NET очень дешёвая; дорого не выделение, а последующая сборка.

**Когда запускается сборка:**

- исчерпан бюджет аллокаций Gen 0 (самый частый триггер);
- превышен бюджет LOH или Gen 1/Gen 2;
- ОС сообщила о нехватке памяти (low memory notification), достигнут hard limit в контейнере;
- явный `GC.Collect()`.

**Фазы сборки:**

1. **Suspend.** Управляемые потоки останавливаются в safe points (stop-the-world).
2. **Mark.** От корней (локальные переменные и регистры активных методов, статические поля, GC handles, очередь финализации) обходится граф, достижимые объекты помечаются. Для сборки младшего поколения ссылки из старших берутся из card table, которую поддерживает write barrier.
3. **Plan / Sweep или Compact.** GC решает, уплотнять ли поколение. При уплотнении живые объекты копируются вплотную, при sweep — мёртвые участки становятся free list.
4. **Relocate.** Все ссылки на перемещённые объекты переписываются.
5. **Resume.** Потоки продолжают работу.

```csharp
var before = GC.CollectionCount(0);
for (int i = 0; i < 1_000_000; i++) _ = new byte[100];
Console.WriteLine(GC.CollectionCount(0) - before); // десятки-сотни сборок Gen 0
```

**Поколения.** Куча делится на Gen 0, Gen 1, Gen 2 плюс LOH (объекты от 85 000 байт) и POH (pinned object heap, с .NET 5). Большинство объектов умирает в Gen 0, поэтому частые дешёвые сборки молодых и редкие полные сборки дают лучший баланс.

**Режимы.** Workstation / Server (один или несколько хипов и GC-потоков), background GC для Gen 2 — пометка идёт параллельно с работой приложения, stop-the-world только на короткие фазы.

**Практические следствия:**

- паузы пропорциональны объёму **живых** объектов, а не мусора: мёртвые объекты GC вообще не трогает;
- много короткоживущих мелких объектов — нормально; плохо, когда они доживают до Gen 2;
- GC освобождает только managed-память; файлы, сокеты и native-буферы — через `Dispose`;
- `GC.Collect()` вручную почти всегда вредит.

**Что спрашивают дальше:** что такое GC roots, как GC находит ссылки из Gen 2 в Gen 0, чем Server GC отличается от Workstation, как устроены финализаторы.

## Что такое Gen 0, Gen 1 и Gen 2?

```yaml
category: clr-gc
level: middle
difficulty: 2
slug: clr-gc-chto-takoe-gen-0-gen-1-i-gen-2
tags: memory
```

Это три поколения managed-кучи, по которым GC раскладывает объекты в зависимости от возраста — сколько сборок они пережили. Gen 0 — новые объекты, Gen 1 — пережившие одну сборку, Gen 2 — долгожители. Молодые поколения собираются часто и дёшево, старшее — редко и дорого.

| | Gen 0 | Gen 1 | Gen 2 |
| --- | --- | --- | --- |
| Кто там живёт | только что созданные объекты | пережившие одну сборку | пережившие ещё одну, плюс LOH |
| Частота сборок | очень часто | реже | редко |
| Цена сборки | доли миллисекунды | небольшая | зависит от объёма живой кучи, может быть большой |
| Типичное содержимое | DTO запроса, строки, временные списки | «застрявшие» объекты, буфер | кэши, синглтоны, статика, пулы |

```csharp
var o = new object();
Console.WriteLine(GC.GetGeneration(o)); // 0
GC.Collect(0);
Console.WriteLine(GC.GetGeneration(o)); // 1 — пережил сборку Gen 0
GC.Collect(1);
Console.WriteLine(GC.GetGeneration(o)); // 2
Console.WriteLine(GC.MaxGeneration);    // 2 — больше поколений нет
```

**Ключевые правила:**

- **Сборка поколения включает все младшие.** Gen 1 GC собирает Gen 0 и Gen 1, Gen 2 GC (full GC) — всю кучу, включая LOH.
- **Сборка Gen 0 не смотрит на старшие поколения** — поэтому она дешёвая независимо от размера приложения. Ссылки из Gen 2 на молодые объекты она находит через card table, которую помечает write barrier при записи ссылочного поля.
- **Gen 0 и Gen 1 называют эфемерными.** Их сборка всегда блокирующая, но короткая.
- **Gen 1 — буфер.** Он отсеивает объекты, которые просто оказались живы в момент сборки Gen 0, но скоро умрут, чтобы они не засоряли Gen 2.

**Большие объекты** (от 85 000 байт) пропускают Gen 0 и сразу считаются частью Gen 2 — `GC.GetGeneration` для них возвращает 2.

**Здоровая картина в метриках:** сборок Gen 0 много, Gen 1 на порядок меньше, Gen 2 — единицы. Если Gen 2 растёт почти так же быстро, как Gen 0, объекты массово доживают до старости: утечка, большие буферы или слишком долгое удержание объектов запроса.

```csharp
Console.WriteLine($"{GC.CollectionCount(0)} / {GC.CollectionCount(1)} / {GC.CollectionCount(2)}");
```

**Что спрашивают дальше:** почему поколений именно три и зачем вообще поколения, что такое write barrier, почему `GC.Collect()` «состаривает» объекты.

## Почему в .NET используется поколенческий GC?

```yaml
category: clr-gc
level: middle
difficulty: 3
slug: clr-gc-pochemu-v-net-ispolzuetsya-pokolencheskii-gc
tags: memory
```

Потому что он опирается на эмпирическую «гипотезу о поколениях»: большинство объектов умирает молодыми, а переживший несколько сборок объект, скорее всего, проживёт долго. Значит, выгодно часто проверять маленькую область молодых объектов, где почти всё мусор, и редко — большую область старых, где почти всё живо.

**Откуда выигрыш.** Цена трассирующей сборки пропорциональна объёму **живых** объектов, которые надо обойти и, возможно, скопировать. Мёртвые объекты GC не трогает вовсе.

- В Gen 0 после сборки выживает малая доля объектов — обход и копирование почти бесплатны, а освобождается весь бюджет разом.
- Если бы каждая сборка обходила всю кучу, сервис с 4 ГБ кэша платил бы за обход этих 4 ГБ при каждой нехватке памяти под DTO запроса.

```csharp
// типичный веб-запрос: всё это умрёт через миллисекунды
var dto = await JsonSerializer.DeserializeAsync<OrderDto>(body);
var errors = new List<string>();
var key = $"order:{dto.Id}";
```

**Что это даёт на практике:**

| Без поколений | С поколениями |
| --- | --- |
| каждая сборка обходит всю кучу | обычная сборка обходит только Gen 0 (часто — единицы МБ) |
| пауза растёт с размером кэшей | пауза Gen 0 почти не зависит от размера кучи |
| уплотнение всей кучи | уплотняется в основном молодая область |

**Цена подхода.**

- **Write barrier.** Сборка Gen 0 не обходит Gen 2, но должна знать о ссылках «старый → молодой». Поэтому каждая запись ссылки в поле объекта сопровождается барьером, который помечает участок в card table. Запись ссылочного поля чуть дороже записи `int`.
- **Преждевременное старение.** Объект, живой в момент сборки, переезжает в старшее поколение, даже если умрёт через миг. Под нагрузкой объекты долгого запроса могут доехать до Gen 2 и освобождаться только при полной сборке («mid-life crisis»).
- **Гипотеза не всегда верна.** Кэш с постоянной ротацией (объекты живут минуты и умирают) — худший случай: они успевают попасть в Gen 2 и создают дорогие полные сборки.

**Выводы для кода:**

- короткоживущие мелкие аллокации — это нормально, GC для них и оптимизирован;
- плохо средне-живущее: объекты, которые держат дольше, чем нужно (буферы в полях, кэши без лимита, замыкания в долгоживущих подписках);
- не вызывать `GC.Collect()` — он переводит живые временные объекты в старшие поколения.

**Что спрашивают дальше:** как работает card table, почему поколений три, а не два, что такое «mid-life crisis» и как его увидеть в метриках (рост `gen-2-gc-count`).

## Что такое Large Object Heap (LOH)?

```yaml
category: clr-gc
level: middle
difficulty: 2
slug: clr-gc-chto-takoe-large-object-heap-loh
tags: memory
```

LOH (Large Object Heap) — отдельная область managed-кучи для объектов размером от 85 000 байт. Такие объекты сразу относятся к Gen 2, собираются только при полной сборке и по умолчанию не уплотняются — копировать мегабайтные массивы слишком дорого.

```csharp
Console.WriteLine(GC.GetGeneration(new byte[84_000])); // 0
Console.WriteLine(GC.GetGeneration(new byte[85_000])); // 2 — LOH
```

**Порог в элементах** (размер считается вместе с заголовком объекта):

| Тип | Примерно на LOH начиная с |
| --- | --- |
| `byte[]` | ~85 000 элементов |
| `int[]` | ~21 250 |
| `string` | ~42 500 символов (UTF-16) |
| `object[]`, `long[]` на x64 | ~10 600 |

Последнее легко упустить: внутренний массив `List<T>` со ссылочными элементами уезжает на LOH уже на десяти с небольшим тысячах элементов, а при росте `List<T>` удваивает массив — промежуточные копии тоже становятся большими объектами.

**Чем LOH отличается от обычной кучи:**

- **Сборка только в Gen 2.** Короткоживущий большой буфер освободится лишь при полной сборке. Превышение бюджета LOH само по себе запускает Gen 2 GC — много больших аллокаций ведут к частым полным сборкам.
- **Нет уплотнения по умолчанию.** Освобождённые места становятся free list, новые объекты кладутся в подходящую дыру. Отсюда фрагментация.
- **Обнуление.** Большой массив нужно обнулить при выделении — это тоже заметная работа.

**Проблемы, которые LOH создаёт:**

- частые Gen 2 из-за буферов под каждый запрос;
- фрагментация: суммарно свободно много, но крупного непрерывного куска нет;
- рост памяти процесса, который не уходит после пика.

**Что делать:**

- пулить буферы (`ArrayPool<T>.Shared`, `RecyclableMemoryStream`);
- обрабатывать потоками, а не читать файл/ответ целиком в `byte[]`;
- задавать `List<T>` вместимость заранее, если размер известен;
- в крайнем случае — разовое уплотнение:

```csharp
GCSettings.LargeObjectHeapCompactionMode = GCLargeObjectHeapCompactionMode.CompactOnce;
GC.Collect(); // дорогая полная сборка, только в «тихой» точке
```

**Рядом стоит POH** (Pinned Object Heap, с .NET 5) — отдельная куча для объектов, которые должны быть закреплены навсегда (`GC.AllocateArray<T>(n, pinned: true)`), чтобы они не мешали уплотнению обычной кучи.

**Что спрашивают дальше:** почему именно 85 000, как диагностировать фрагментацию LOH (`dotnet-gcdump`, счётчики `loh-size`, `gen-2-gc-count`), как устроен `ArrayPool`.

## Когда объект попадает в Gen 1 или Gen 2?

```yaml
category: clr-gc
level: middle
difficulty: 3
slug: clr-gc-kogda-obekt-popadaet-v-gen-1-ili-gen-2
tags: memory
```

Объект переходит в следующее поколение, когда переживает сборку своего поколения: выжил в сборке Gen 0 — стал Gen 1, выжил в сборке Gen 1 — стал Gen 2. Исключение — большие объекты от 85 000 байт: они сразу оказываются в Gen 2 (на LOH). Возраст объекта измеряется не временем, а числом пережитых сборок.

```csharp
var order = new Order();
GC.GetGeneration(order);   // 0
GC.Collect(0);
GC.GetGeneration(order);   // 1 — был достижим во время сборки Gen 0
GC.Collect(1);
GC.GetGeneration(order);   // 2
GC.Collect(2);
GC.GetGeneration(order);   // 2 — дальше некуда
```

**Что значит «пережил».** В момент сборки объект был достижим от корней: на него ссылалась локальная переменная активного метода, статическое поле, другой живой объект, GC handle или очередь финализации. Неважно, что через микросекунду ссылка пропадёт — решение принимается в момент сборки.

**Ситуации, когда объекты попадают в Gen 2, хотя «должны» были умереть молодыми:**

- **Долгий запрос под нагрузкой.** При высоком allocation rate сборки Gen 0 идут чаще, чем завершается один запрос. Объекты запроса переживают две сборки и оседают в Gen 2.
- **`await` посреди работы.** Состояние async-метода (state machine, захваченные переменные, буферы) живёт в куче всё время ожидания I/O и успевает состариться.
- **Кэши с ротацией.** `MemoryCache` с TTL в минуты: объекты гарантированно доживают до Gen 2 и умирают там, провоцируя дорогие полные сборки.
- **Финализатор.** Объект с финализатором после смерти ставится в очередь f-reachable и переживает как минимум ещё одну сборку, поднимаясь в поколении вместе со всем графом, на который ссылается.
- **Ручной `GC.Collect()`.** Всё живое в этот момент искусственно состаривается.
- **Большой размер.** Буфер от 85 000 байт — сразу Gen 2.

**Почему это важно.** Объект в Gen 2 освобождается только полной сборкой — самой дорогой. Много «средне-живущих» объектов = частые Gen 2 и рост памяти.

**Как увидеть:** соотношение `GC.CollectionCount(0/1/2)` или счётчики `gen-0-gc-count`, `gen-1-gc-count`, `gen-2-gc-count` в `dotnet-counters`; в трассе `dotnet-trace` — события promoted bytes по поколениям.

**Как лечить:** сокращать время жизни и объём аллокаций на пути запроса — пулы буферов, `Span<T>` вместо промежуточных строк и массивов, не держать временные данные в полях долгоживущих объектов.

## Как GC определяет, какие объекты больше не нужны?

```yaml
category: clr-gc
level: middle
difficulty: 3
slug: clr-gc-kak-gc-opredelyaet-kakie-obekty-bolshe-ne-nuzhny
tags: memory
```

По достижимости: GC начинает с корней (GC roots) и рекурсивно обходит все ссылки, помечая встреченные объекты живыми. Всё, до чего обход не дошёл, — мусор. «Не нужен» для GC значит «недостижим», а не «больше не используется по смыслу».

**Что считается корнями:**

- локальные переменные и аргументы активных методов — в стеке и регистрах всех потоков;
- статические поля загруженных типов;
- GC handles: `GCHandle` (Normal, Pinned), внутренние handles рантайма;
- очередь финализации (f-reachable queue) — объекты, ожидающие выполнения финализатора;
- ссылки, удерживаемые interop-кодом (например, COM или маршалинг делегатов).

**Как GC знает, где в объекте ссылки.** У каждого объекта есть указатель на `MethodTable`, а в ней — GC-описание: по каким смещениям лежат ссылочные поля. Поэтому обход точный (precise): GC не угадывает, похоже ли число на адрес, а точно знает, какие слоты — ссылки. Для стека JIT генерирует GC info: в каждой safe point известно, какие слоты и регистры содержат живые ссылки.

**Важная тонкость — «живость» локальной переменной.** В оптимизированном коде JIT считает переменную мёртвой после её последнего использования, а не в конце метода:

```csharp
void Work()
{
    var big = new byte[100_000_000];
    Use(big);
    // здесь big уже не корень в Release-сборке —
    // GC может собрать массив, пока идёт LongOperation
    LongOperation();
}
```

В Debug-сборке и под отладчиком время жизни продлевается до конца метода — поэтому поведение памяти в Debug и Release отличается. Если объект нужно гарантированно продержать до точки, используют `GC.KeepAlive(obj)`.

**Обход при сборке поколения.** Сборка Gen 0 не обходит Gen 2 целиком. Ссылки из старших поколений в молодые GC берёт из card table — её помечает write barrier при каждой записи ссылки в поле.

**Что из этого следует:**

- циклические ссылки не проблема: если на цикл нет ссылок от корней, он целиком мусор;
- утечка в .NET — это объект, который по-прежнему достижим (событие, статика, кэш), хотя логически не нужен;
- понять, почему объект жив, можно командой `gcroot` в `dotnet-dump analyze` или в dotMemory / Visual Studio — они показывают цепочку от корня.

**Что спрашивают дальше:** есть ли в .NET подсчёт ссылок (нет), что происходит с объектом с финализатором, как работает `WeakReference`.

## Может ли GC удалить объекты, которые ссылаются друг на друга?

```yaml
category: clr-gc
level: middle
difficulty: 3
slug: clr-gc-mozhet-li-gc-udalit-obekty-kotorye-ssylayutsya-drug-na-druga
tags: memory
```

Да. GC в .NET трассирующий: он определяет живость по достижимости от корней, а не по числу ссылок на объект. Если на группу объектов, ссылающихся друг на друга, нет пути от корней, вся группа — мусор, и цикл ей не помогает.

```csharp
class Node { public Node? Next; }

void Make()
{
    var a = new Node();
    var b = new Node();
    a.Next = b;
    b.Next = a;   // цикл a ↔ b
}                 // после выхода ни a, ни b не достижимы от корней

Make();
GC.Collect();     // оба объекта соберутся
```

Проверить можно через `WeakReference`: после сборки `TryGetTarget` для обоих объектов вернёт `false`.

**Почему в других системах циклы — проблема.** При подсчёте ссылок (COM, `shared_ptr` в C++, Swift ARC, частично CPython) объект освобождается, когда счётчик падает до нуля. В цикле счётчики никогда не обнуляются, поэтому там нужны weak-ссылки или отдельный сборщик циклов. В .NET счётчиков нет, и этот класс утечек отсутствует.

| | Подсчёт ссылок | Трассирующий GC (.NET) |
| --- | --- | --- |
| Когда освобождается | счётчик = 0, сразу | при сборке, если недостижим |
| Циклы | утекают без weak-ссылок | собираются |
| Детерминированность | да | нет |
| Цена | инкремент/декремент на каждое присваивание | паузы на сборку, write barrier |

**Где циклы всё же «утекают» в .NET:**

- **Цикл достижим.** Если хотя бы один объект цикла доступен от корня (статическое поле, синглтон, подписка на событие), живой будет весь граф. Родитель и дочерние узлы UI-дерева, ссылающиеся друг на друга, собираются, только пока никто снаружи их не держит.
- **Граница с COM/native.** RCW и CCW при interop с COM используют подсчёт ссылок на стороне COM. Цикл, проходящий через COM-объект, GC сам разорвать не может.
- **Финализаторы в цикле.** Объекты соберутся, но только со второго захода, после выполнения финализаторов, и порядок финализации внутри цикла не определён — финализатор не должен обращаться к другим финализируемым объектам.

**Практический вывод:** специально разрывать двунаправленные ссылки (`parent.Children` ↔ `child.Parent`) ради GC не нужно. Искать надо внешнюю ссылку, которая держит граф живым, — её покажет `gcroot`.

## Что такое GC Root?

```yaml
category: clr-gc
level: middle
difficulty: 2
slug: clr-gc-chto-takoe-gc-root
tags: memory
```

GC root — ссылка, которая считается живой сама по себе, без проверки: с корней GC начинает обход графа объектов. Объект жив, если до него есть цепочка ссылок от какого-нибудь корня; если такой цепочки нет — он мусор.

**Виды корней:**

| Корень | Пример | Как долго держит |
| --- | --- | --- |
| Локальные переменные и аргументы | `var list = new List<int>();` в выполняющемся методе | до последнего использования (в Release) |
| Регистры CPU | временные значения в оптимизированном коде | пока нужны JIT |
| Статические поля | `static readonly Dictionary<...> Cache` | всё время жизни типа, фактически процесса |
| GC handles | `GCHandle.Alloc(obj)`, pinned handles, handles внутри рантайма | до `handle.Free()` |
| Очередь финализации (f-reachable) | объект, ждущий выполнения `~Finalizer()` | до выполнения финализатора |
| Thread-static | `[ThreadStatic]`, `ThreadLocal<T>` | пока жив поток / объект `ThreadLocal` |

**Корни не только в вашем коде.** Таймер, запущенный `System.Threading.Timer`, держится рантаймом; подписка на событие статического объекта — это ссылка от статики на ваш обработчик; незавершённая `Task`, ожидающая сигнала, держится тем, кто её завершит.

```csharp
public class Page
{
    public Page() => AppEvents.Changed += OnChanged; // static event
    void OnChanged(object? s, EventArgs e) { }
}
// цепочка: static AppEvents.Changed → delegate → Page
// страница никогда не соберётся, пока не отпишется
```

**Живость локальных переменных.** JIT для каждой safe point записывает, какие слоты стека и регистры содержат живые ссылки. В Release-коде переменная перестаёт быть корнем сразу после последнего использования. В Debug время жизни растягивается до конца метода — одна из причин, почему профилировать память надо на Release.

**Зачем это знать на практике.** Почти любая утечка памяти в .NET сводится к вопросу «какой корень держит объект». Инструменты отвечают на него напрямую:

```text
dotnet-dump analyze core.dmp
> dumpheap -stat              # какие типы занимают память
> dumpheap -mt <MethodTable>  # конкретные экземпляры
> gcroot <address>            # цепочка от корня до объекта
```

В dotMemory и Visual Studio то же самое называется «retention path» / «paths to root».

**Что спрашивают дальше:** почему циклические ссылки не мешают сборке, что делает `GC.KeepAlive`, чем strong handle отличается от weak (`WeakReference` — это weak handle, он не является корнем).

## Что такое memory leak в .NET?

```yaml
category: clr-gc
level: middle
difficulty: 2
slug: clr-gc-chto-takoe-memory-leak-v-net
tags: memory
```

Memory leak в .NET — ситуация, когда память растёт и не освобождается, потому что объекты остаются достижимыми, хотя логически уже не нужны, или потому что unmanaged-ресурсы не были освобождены. GC собирает только недостижимое: если что-то держит ссылку, объект будет жить вечно.

**Два класса утечек:**

| | Managed (логическая) | Unmanaged |
| --- | --- | --- |
| Суть | ссылку держат дольше, чем нужно | native-память или handle не освобождены |
| Видна в GC heap | да, heap растёт | нет, растёт RSS процесса |
| Как искать | `dotnet-gcdump`, `dotnet-dump` + `gcroot` | счётчики handles, native-профилировщики |

**Типичные причины managed-утечек:**

- **События.** Подписка на событие долгоживущего объекта без отписки: издатель держит делегат, делегат — подписчика.
- **Статические коллекции и кэши без ограничений.** `static Dictionary`, в который только добавляют.
- **Замыкания.** Лямбда в долгоживущем колбэке захватывает `this` или большой объект.
- **Таймеры.** Незадиспоженный `System.Threading.Timer` / `PeriodicTimer` держит свой колбэк.
- **DI.** Scoped- или transient-объект, захваченный синглтоном (captive dependency); transient `IDisposable` из корневого провайдера, которые контейнер запоминает до своего освобождения.
- **Незавершённые `Task` / `TaskCompletionSource`,** на которые навешены продолжения.

```csharp
public sealed class Subscriber
{
    private readonly byte[] _data = new byte[10_000_000];
    public Subscriber(Publisher p) => p.Tick += OnTick;   // утечка, если Publisher живёт дольше
    private void OnTick(object? s, EventArgs e) { }
}
```

**Unmanaged-утечки:** не вызван `Dispose` у `FileStream`, `SqlConnection`, `Bitmap`, объектов native-библиотек; `Marshal.AllocHGlobal` без `FreeHGlobal`; `GCHandle.Alloc` без `Free`. Финализатор может когда-нибудь это исправить, но «когда-нибудь» может не наступить до падения.

**Что утечкой не является:**

- память не вернулась ОС сразу после пика — GC держит committed-сегменты про запас, это нормально;
- рост до стабильного уровня после прогрева (JIT, кэши, пулы);
- большой Gen 2, который стабилен под нагрузкой.

Признак настоящей утечки — **монотонный** рост размера кучи после полных сборок при постоянной нагрузке.

**Как искать:** сравнить два снимка кучи (`dotnet-gcdump collect` с интервалом), найти типы, число экземпляров которых растёт, и через `gcroot` / retention path увидеть, кто их держит.

## Может ли managed-приложение иметь memory leak?

```yaml
category: clr-gc
level: middle
difficulty: 3
slug: clr-gc-mozhet-li-managed-prilozhenie-imet-memory-leak
tags: memory
```

Да. GC гарантирует только одно: недостижимые объекты будут собраны. Он не знает, нужен ли объект по смыслу, поэтому всё, на что осталась ссылка, живёт, — и не управляет unmanaged-ресурсами, которые приложение забыло освободить. Утечки в .NET другие, чем в C++, но они есть.

**Чего GC действительно избавляет:** забытого `free`, double free, use-after-free, утечек из-за циклических ссылок. Этот класс ошибок в managed-коде отсутствует.

**Что остаётся — пять типовых сценариев из практики:**

1. **Подписки на события.** `publisher.Event += handler` создаёт ссылку издатель → подписчик. Если издатель — синглтон или статика, подписчик никогда не соберётся.
2. **Неограниченные кэши.** `ConcurrentDictionary` как кэш без вытеснения; `MemoryCache` без `SizeLimit`; кэш с ключом, который каждый раз уникален (например, по полному URL с query).
3. **Captive dependency в DI.** Синглтон, захвативший `DbContext` или scoped-сервис, — scoped-объект с его графом живёт до конца процесса.
4. **Долгоживущие делегаты и таймеры.** Замыкание захватило `this` или большой буфер; `Timer` без `Dispose`; `CancellationToken.Register` без `Dispose` регистрации на долгоживущем токене.
5. **Unmanaged-ресурсы.** Незакрытые потоки, соединения, `HttpResponseMessage`, объекты SkiaSharp/ImageSharp, `GCHandle` без `Free`.

```csharp
// классика: токен живёт весь процесс, регистрации копятся
_appStopping.Register(() => _session.Close());   // на каждый запрос — навсегда

// правильно: освобождать регистрацию
using var reg = _appStopping.Register(() => _session.Close());
```

**Неочевидные случаи:**

- **Генерация кода в рантайме.** Динамические сборки, `Expression.Compile()` / `new Regex(..., RegexOptions.Compiled)` в цикле, `XmlSerializer` с нестандартным конструктором — каждый вызов создаёт новый код, и старый может не выгружаться.
- **`AssemblyLoadContext` плагинов**, который не выгружается из-за одной оставшейся ссылки.
- **`ThreadLocal<T>` / `[ThreadStatic]`** на потоках пула, которые живут весь процесс.
- **Фрагментация**, особенно LOH: объём живых данных стабилен, но занятая память растёт.

**Как отличить утечку от нормального поведения:** GC не обязан сразу отдавать память ОС, а сервис после старта набирает кэши и JIT-код. Утечка — это рост кучи **после полных сборок** при стабильной нагрузке, без выхода на плато.

**Как искать:** `dotnet-counters` (растёт ли `gc-heap-size` и `gen-2-gc-count`), два снимка `dotnet-gcdump` для сравнения по типам, `dotnet-dump analyze` + `gcroot`, чтобы увидеть корень. Если GC heap стабилен, а RSS растёт, — ищите в unmanaged.

## Что такое `IDisposable`?

```yaml
category: clr-gc
level: middle
difficulty: 2
slug: clr-gc-chto-takoe-idisposable
```

`IDisposable` — интерфейс с одним методом `Dispose()`, который означает «у этого объекта есть ресурс, который нужно освободить явно и детерминированно». GC освобождает только managed-память и в непредсказуемый момент; файлы, сокеты, соединения с БД, блокировки и native-буферы освобождает `Dispose`.

```csharp
public interface IDisposable
{
    void Dispose();
}

public interface IAsyncDisposable      // для асинхронного освобождения (с .NET Core 3.0)
{
    ValueTask DisposeAsync();
}
```

**Какие ресурсы за этим стоят:**

- unmanaged: файловые дескрипторы, сокеты, handles ОС, native-память (`FileStream`, `Socket`, `SafeHandle`);
- ограниченные managed-ресурсы: соединение из пула (`SqlConnection`, `NpgsqlConnection`), семафор, подписка, таймер;
- «логическое» завершение: `Activity`, `IDisposable`-scope логгера, откат транзакции при выходе без `Commit`.

**Использование — через `using`:**

```csharp
using var conn = new NpgsqlConnection(cs);   // Dispose в конце области видимости
await conn.OpenAsync();

await using var stream = File.OpenRead(path); // DisposeAsync для асинхронного освобождения
```

`using` разворачивается в `try/finally`, поэтому `Dispose` вызовется и при исключении.

**Правила хорошей реализации:**

- `Dispose` должен быть **идемпотентным** — повторный вызов не бросает исключение;
- после `Dispose` остальные методы бросают `ObjectDisposedException` (`ObjectDisposedException.ThrowIf(_disposed, this)`);
- класс, владеющий полем-`IDisposable`, сам реализует `IDisposable` и освобождает это поле;
- финализатор добавляют **только** если класс напрямую владеет unmanaged-хэндлом, и то лучше обернуть хэндл в `SafeHandle`;
- `sealed`-класс обходится простым `Dispose()`, для наследуемого — паттерн `protected virtual void Dispose(bool disposing)`.

**Правило владения.** Освобождает тот, кто создал. Если объект получен из DI-контейнера, `Dispose` вызовет контейнер при завершении scope — вручную его звать не нужно.

**Частые ошибки на собеседовании и в коде:**

- думать, что `Dispose` освобождает память объекта — нет, память освободит GC позже;
- создавать `HttpClient` в `using` на каждый запрос — исчерпание сокетов; нужен `IHttpClientFactory` или долгоживущий экземпляр;
- возвращать из метода объект, созданный в `using`, — он придёт уже освобождённым.

## Зачем нужен `Dispose()`?

```yaml
category: clr-gc
level: middle
difficulty: 3
slug: clr-gc-zachem-nuzhen-dispose
tags: memory
```

`Dispose()` нужен, чтобы освободить ресурс сразу, когда он больше не нужен, а не когда-нибудь потом. GC не детерминирован и видит только managed-память: он не знает, что маленький объект `FileStream` держит файловый дескриптор, а `DbConnection` — одно из ограниченного числа соединений в пуле.

**Что будет без `Dispose`:**

| Ресурс | Последствие, если не освобождать |
| --- | --- |
| `FileStream` | файл остаётся заблокированным, данные в буфере могут не записаться |
| `SqlConnection` / `NpgsqlConnection` | соединение не возвращается в пул → timeout при получении нового под нагрузкой |
| `Socket`, `HttpResponseMessage` | исчерпание сокетов/соединений |
| `Timer` | колбэк продолжает срабатывать, держит объекты живыми |
| `SemaphoreSlim`, `CancellationTokenSource` с таймаутом | держатся внутренние таймеры и wait handles |
| native-объекты (SkiaSharp, ONNX) | рост native-памяти, невидимый GC |

**Почему нельзя положиться на финализатор.** Финализатор сработает только после того, как GC соберёт объект, — а это может быть через секунды, минуты или никогда, если памяти много. Пул соединений кончится раньше. Кроме того, финализация удлиняет жизнь объекта минимум на одну сборку и выполняется в одном служебном потоке.

```csharp
// плохо: соединение вернётся в пул, только когда GC доберётся до объекта
var conn = new NpgsqlConnection(cs);
await conn.OpenAsync();
return await conn.ExecuteScalarAsync<int>("select 1");

// хорошо: вернётся в пул на выходе из метода, даже при исключении
await using var conn = new NpgsqlConnection(cs);
await conn.OpenAsync();
return await conn.ExecuteScalarAsync<int>("select 1");
```

**Что `Dispose` делает и чего не делает:**

- освобождает или возвращает ресурс (закрывает handle, сбрасывает буфер, возвращает соединение в пул);
- обычно вызывает `GC.SuppressFinalize(this)`, если у класса есть финализатор, — объект не попадёт в очередь финализации;
- **не освобождает память самого объекта** — это по-прежнему работа GC;
- не обнуляет ссылки на объект — после `Dispose` объект жив, но пользоваться им нельзя.

**Практические правила:**

- видите `IDisposable` у объекта, который вы создали, — оборачивайте в `using`/`await using`;
- если класс хранит `IDisposable` в поле и владеет им — реализуйте `IDisposable` сами;
- для асинхронных ресурсов (`Stream` с флашем, `DbConnection`) предпочитайте `DisposeAsync`;
- не диспозьте то, чем не владеете: объекты из DI, общий `HttpClient`, поток, переданный с `leaveOpen: true`.

Анализаторы `CA2000` (объект не освобождён) и `CA1816` (корректный вызов `SuppressFinalize`) ловят большинство таких ошибок на этапе сборки.

## Как работает `using`?

```yaml
category: clr-gc
level: middle
difficulty: 3
slug: clr-gc-kak-rabotaet-using
```

`using` — синтаксический сахар, который компилятор разворачивает в `try/finally` с вызовом `Dispose()` в `finally`. Благодаря этому ресурс освобождается при любом выходе из блока: обычном, через `return`, `break` или исключение.

```csharp
using (var stream = File.OpenRead(path))
{
    Process(stream);
}
```

Компилятор генерирует примерно:

```csharp
var stream = File.OpenRead(path);
try
{
    Process(stream);
}
finally
{
    if (stream != null) ((IDisposable)stream).Dispose();
}
```

Для значимых типов проверки на `null` нет, а вызов идёт без boxing (constrained call).

**Формы `using`:**

| Форма | Когда вызывается `Dispose` |
| --- | --- |
| `using (var x = ...) { }` | в конце блока |
| `using var x = ...;` (C# 8) | в конце охватывающей области видимости (метода, блока) |
| `await using var x = ...;` | `await x.DisposeAsync()` в конце области |
| несколько `using var` подряд | в обратном порядке объявления |

```csharp
async Task CopyAsync(string from, string to)
{
    await using var src = File.OpenRead(from);
    await using var dst = File.Create(to);
    await src.CopyToAsync(dst);
}   // сначала dst.DisposeAsync(), потом src.DisposeAsync()
```

**Детали, которые спрашивают:**

- **Переменная `using` — readonly.** Её нельзя переприсвоить внутри блока, иначе освободился бы не тот объект.
- **Паттерн-based `Dispose`.** Для `ref struct` (например, собственных обёрток над `Span`) достаточно публичного метода `Dispose()` без реализации интерфейса — `ref struct` до C# 13 вообще не могли реализовывать интерфейсы.
- **`await using`** работает с `IAsyncDisposable`; если тип реализует только `IDisposable`, `await using` не скомпилируется.
- **Исключение в `Dispose`** перекроет исключение из тела блока — поэтому `Dispose` не должен бросать.
- **Исключение в конструкторе/фабрике** — `Dispose` не вызовется, объекта ещё нет. Если класс в конструкторе создаёт несколько ресурсов, он сам должен освободить уже созданные при ошибке.

**Частые ошибки:**

```csharp
// объект вернётся уже освобождённым
Stream Open() { using var s = File.OpenRead(path); return s; }

// using var держит соединение до конца большого метода, а не до конца работы с ним
using var conn = await OpenAsync();
var data = await conn.QueryAsync(...);
await SlowProcessingAsync(data);   // соединение всё ещё занято
```

Во втором случае лучше блочная форма `using (...) { }` или отдельный метод — время удержания ресурса станет явным.

## Чем `Dispose()` отличается от finalizer?

```yaml
category: clr-gc
level: middle
difficulty: 3
slug: clr-gc-chem-dispose-otlichaetsya-ot-finalizer
tags: memory
```

`Dispose()` вызывает ваш код явно и в известный момент — это основной способ освободить ресурс. Финализатор вызывает GC сам, в неизвестный момент после того, как объект стал недостижим, — это страховка на случай, если `Dispose` забыли вызвать. Первый детерминированный и дешёвый, второй недетерминированный и дорогой.

| | `Dispose()` | Финализатор `~T()` |
| --- | --- | --- |
| Кто вызывает | код, обычно через `using` | GC, в выделенном finalizer thread |
| Когда | сразу, когда ресурс не нужен | после сборки, когда-нибудь — или никогда до завершения процесса |
| Порядок | контролируете вы | не определён, даже между связанными объектами |
| Доступ к другим объектам | можно обращаться к полям-`IDisposable` | нельзя полагаться на другие финализируемые объекты — они могут быть уже финализированы |
| Цена | обычный вызов метода | дороже аллокация, объект переживает лишнюю сборку, нагрузка на один поток |
| Исключение | обычное исключение | необработанное исключение в финализаторе роняет процесс |
| Что освобождать | managed и unmanaged ресурсы | только unmanaged |

**Как они работают вместе — классический паттерн:**

```csharp
public class NativeBuffer : IDisposable
{
    private IntPtr _ptr = Marshal.AllocHGlobal(4096);
    private bool _disposed;

    public void Dispose()
    {
        Dispose(disposing: true);
        GC.SuppressFinalize(this);          // финализатор больше не нужен
    }

    protected virtual void Dispose(bool disposing)
    {
        if (_disposed) return;
        if (disposing)
        {
            // освобождать managed-поля (другие IDisposable) — только здесь
        }
        Marshal.FreeHGlobal(_ptr);          // unmanaged — в обоих случаях
        _ptr = IntPtr.Zero;
        _disposed = true;
    }

    ~NativeBuffer() => Dispose(disposing: false);
}
```

Флаг `disposing` разделяет два пути: при вызове из финализатора managed-поля трогать нельзя — они могли быть уже собраны или финализированы.

**Почему финализатор дорогой.** Объект с финализатором при создании регистрируется в finalization queue. Когда он становится недостижим, GC не освобождает его, а переносит в f-reachable queue — это корень, и объект вместе со всем графом переживает сборку и поднимается в следующее поколение. Память освободится только на следующей сборке после выполнения финализатора. `GC.SuppressFinalize` в `Dispose` снимает объект с этой очереди.

**Современная практика.** Писать финализаторы самому почти никогда не нужно: unmanaged-хэндл заворачивают в `SafeHandle` (у него критический финализатор уже есть), а свой класс реализует только `Dispose`. Если у класса нет прямого unmanaged-ресурса, финализатора быть не должно.

## Что такое finalizer?

```yaml
category: clr-gc
level: middle
difficulty: 2
slug: clr-gc-chto-takoe-finalizer
tags: memory
```

Финализатор — специальный метод `~ClassName()`, который GC вызывает перед освобождением памяти объекта, если тот стал недостижим. Компилятор превращает его в переопределение `Object.Finalize()`. Назначение — последний шанс освободить unmanaged-ресурс, если `Dispose` не был вызван.

```csharp
class FileWrapper
{
    private IntPtr _handle;
    ~FileWrapper()               // компилируется в protected override void Finalize()
    {                            //   { try { ... } finally { base.Finalize(); } }
        CloseHandle(_handle);
    }
}
```

**Жизненный цикл финализируемого объекта:**

1. При создании объект регистрируется в **finalization queue** — аллокация чуть дороже обычной.
2. Объект становится недостижим. Во время сборки GC видит его в finalization queue и переносит в **f-reachable queue**. Эта очередь — GC root, поэтому объект и всё, на что он ссылается, **выживает** и повышается в поколении.
3. Выделенный **finalizer thread** забирает объекты из f-reachable queue и вызывает `Finalize()`.
4. На **следующей** сборке соответствующего поколения объект уже никем не удерживается и освобождается окончательно.

Итог: память объекта с финализатором освобождается минимум через две сборки, а если он успел попасть в Gen 2 — через две полные сборки.

**Ограничения и опасности:**

- **Время вызова не определено.** Может пройти сколько угодно времени; при завершении процесса в .NET Core/.NET 5+ финализаторы вообще не запускаются.
- **Порядок не определён.** Финализатор не должен обращаться к другим финализируемым объектам — они могли быть уже финализированы.
- **Один поток.** Медленный или заблокированный финализатор тормозит финализацию всех остальных объектов — очередь растёт, память течёт.
- **Необработанное исключение** в финализаторе завершает процесс.
- **Воскрешение.** Финализатор может сохранить `this` в статическое поле — объект снова станет достижимым. Это законно, но почти всегда ошибка.
- **Частично сконструированный объект.** Если конструктор бросил исключение, финализатор всё равно вызовется — поля могут быть не инициализированы.

**Управление:**

```csharp
GC.SuppressFinalize(this);        // в Dispose: финализатор не нужен
GC.ReRegisterForFinalize(this);   // вернуть в очередь (редко)
GC.WaitForPendingFinalizers();    // дождаться выполнения очереди (тесты, диагностика)
```

**На практике** финализаторы в прикладном коде почти не пишут: для unmanaged-хэндлов есть `SafeHandle`, у которого надёжный финализатор уже реализован. Счётчик растущей очереди финализации — `dotnet-counters`, событие `FinalizeObject` в трассе или `finalizequeue` в `dotnet-dump analyze`.

## Когда нужно использовать finalizer?

```yaml
category: clr-gc
level: middle
difficulty: 3
slug: clr-gc-kogda-nuzhno-ispolzovat-finalizer
tags: memory
```

Почти никогда. Финализатор оправдан только тогда, когда класс **напрямую** владеет unmanaged-ресурсом (сырой `IntPtr`-хэндл, native-память) и нужна страховка на случай, если потребитель забудет вызвать `Dispose`. Но и в этом случае правильнее обернуть хэндл в `SafeHandle` — финализатор у него уже есть, и писать свой не придётся.

**Дерево решений:**

| Ситуация | Нужен финализатор? |
| --- | --- |
| Класс держит только managed-объекты, в том числе `IDisposable` (`Stream`, `DbConnection`) | нет — у них свои механизмы освобождения, достаточно `Dispose` |
| Класс держит `SafeHandle` | нет — финализатор есть у `SafeHandle` |
| Класс держит сырой `IntPtr` на native-ресурс | да, если не можете заменить на `SafeHandle` |
| Нужно «гарантированно что-то сделать при сборке» (логирование, метрики) | нет — ненадёжно и дорого |
| Хочется отследить незакрытые объекты в Debug | допустимо: финализатор только под `#if DEBUG`, который пишет предупреждение |

**Почему `SafeHandle` лучше собственного финализатора:**

```csharp
sealed class MyHandle : SafeHandleZeroOrMinusOneIsInvalid
{
    public MyHandle() : base(ownsHandle: true) { }
    protected override bool ReleaseHandle() => NativeMethods.Close(handle);
}

public sealed class Device : IDisposable
{
    private readonly MyHandle _handle = NativeMethods.Open();
    public void Dispose() => _handle.Dispose();   // свой финализатор не нужен
}
```

- **Критическая финализация.** `SafeHandle` наследует `CriticalFinalizerObject`: его финализатор выполняется после обычных, поэтому обычные финализаторы ещё могут пользоваться хэндлом.
- **Защита от гонки с GC.** P/Invoke-маршалер увеличивает счётчик ссылок `SafeHandle` на время native-вызова — хэндл не закроется посреди вызова, даже если объект-владелец стал недостижим. С сырым `IntPtr` этот сценарий реален и лечится только `GC.KeepAlive`.
- **Защита от recycle-атак.** Хэндл закрывается ровно один раз.
- **Маленький объект.** Финализируемым становится только крошечный `SafeHandle`, а не ваш большой класс со всем графом.

**Если свой финализатор всё-таки нужен:**

- делайте его минимальным: освобождение unmanaged и ничего больше;
- не обращайтесь к другим managed-объектам и не бросайте исключения;
- вызывайте `GC.SuppressFinalize(this)` в `Dispose`;
- используйте паттерн `Dispose(bool disposing)`.

**Чего не делать:** добавлять финализатор «на всякий случай» классу без unmanaged-ресурсов. Это замедляет каждую аллокацию, продлевает жизнь объекта на сборку и нагружает единственный finalizer thread — при большом потоке таких объектов очередь финализации растёт быстрее, чем обрабатывается, и память течёт.

## Что такое `WeakReference`?

```yaml
category: clr-gc
level: middle
difficulty: 2
slug: clr-gc-chto-takoe-weakreference
tags: memory
```

`WeakReference` / `WeakReference<T>` — ссылка на объект, которая не мешает GC его собрать. Пока на объект есть обычные (сильные) ссылки, через слабую можно его получить; когда сильных ссылок не остаётся, GC собирает объект, а слабая ссылка начинает возвращать «пусто».

```csharp
var weak = new WeakReference<byte[]>(new byte[1000]);

if (weak.TryGetTarget(out var data))
    Console.WriteLine(data.Length);    // объект ещё жив — теперь есть сильная ссылка data
else
    Console.WriteLine("собран");

GC.Collect();
Console.WriteLine(weak.TryGetTarget(out _)); // скорее всего False
```

**Как устроено.** `WeakReference` — обёртка над weak GC handle. Такой handle не является корнем: при пометке GC его игнорирует, а после сборки обнуляет, если цель умерла. Сам объект `WeakReference` — обычный managed-объект со своей аллокацией и финализатором, который освобождает handle.

**Short и long weak reference:**

| | Short (по умолчанию) | Long (`trackResurrection: true`) |
| --- | --- | --- |
| Обнуляется | как только объект стал недостижим | только после финализации |
| Видит воскрешённые объекты | нет | да |

Long-ссылки нужны крайне редко.

**Где применяют:**

- **Кэши, которые можно потерять** — например, кэш распарсенных документов: пока объект где-то используется, вернём его, иначе пересоздадим. Но как основной кэш это плохо: объект может умереть при первой же сборке Gen 0, hit rate непредсказуем. Для кэшей лучше `MemoryCache` с лимитом размера.
- **Weak events** — издатель держит подписчиков слабо, чтобы подписка не продлевала им жизнь (так сделаны WPF `WeakEventManager` и некоторые messenger'ы в MVVM).
- **Диагностика и тесты утечек** — проверить, что объект собрался:

```csharp
[MethodImpl(MethodImplOptions.NoInlining)]
static WeakReference Create() => new(new Page());

var wr = Create();
GC.Collect(); GC.WaitForPendingFinalizers(); GC.Collect();
Assert.False(wr.IsAlive);   // страница не утекла
```

`NoInlining` нужен, чтобы локальная переменная с сильной ссылкой не осталась в кадре теста.

**Подводные камни:**

- **Гонка.** `IsAlive == true` ничего не гарантирует на следующей строке. Всегда получайте цель через `TryGetTarget` в локальную переменную и работайте с ней.
- **Стоимость.** Каждая слабая ссылка — аллокация, handle и работа для GC. Миллион `WeakReference` — заметная нагрузка.
- **Альтернатива для «прикреплённых» данных** — `ConditionalWeakTable<TKey, TValue>`: связывает значение с ключом, не продлевая жизнь ключа; значение живёт, пока жив ключ.

## Что такое allocation?

```yaml
category: clr-gc
level: middle
difficulty: 2
slug: clr-gc-chto-takoe-allocation
tags: memory
```

Allocation (аллокация) — выделение памяти под новый объект в managed-куче: `new` для класса, массива, строки, делегата, а также скрытые выделения вроде boxing, замыканий и state machine `async`-метода. Сама аллокация в .NET дешёвая, но каждый выделенный байт приближает следующую сборку мусора — поэтому в горячем коде считают именно их.

**Как выделяется маленький объект.** У каждого потока есть allocation context — кусок Gen 0, выданный ему заранее. `new` сдвигает указатель на размер объекта (bump pointer), записывает заголовок и указатель на `MethodTable`. Никаких поисков свободного места и блокировок. Когда кусок кончается, поток берёт новый; когда исчерпан весь бюджет Gen 0 — запускается сборка.

**Что стоит за объектом:**

| Что | Размер на x64 |
| --- | --- |
| заголовок объекта (object header) | 8 байт |
| указатель на `MethodTable` | 8 байт |
| минимальный объект (`new object()`) | 24 байта |
| массив | заголовок + `MethodTable` + длина + элементы |

**Явные и скрытые аллокации:**

```csharp
var list = new List<int>();         // явная: объект List + позже внутренний массив
string s = $"id={id}";              // строка
object o = 42;                      // boxing
Func<int> f = () => id;             // замыкание (display class) + делегат
IEnumerable<int> q = arr.Where(x => x > 0); // итератор LINQ
await SomethingAsync();             // state machine, если метод реально ушёл в ожидание
params int[] args                   // массив при каждом вызове
```

**Где память выделяется не в Gen 0:**

- объекты от 85 000 байт — на LOH (сразу Gen 2);
- `GC.AllocateArray<T>(n, pinned: true)` — на POH;
- `stackalloc` — на стеке, GC не участвует;
- `NativeMemory.Alloc` — unmanaged.

**Как измерить:**

```csharp
long before = GC.GetAllocatedBytesForCurrentThread();
DoWork();
long allocated = GC.GetAllocatedBytesForCurrentThread() - before;
```

Для бенчмарков — `[MemoryDiagnoser]` в BenchmarkDotNet (колонка `Allocated`), для сервиса — счётчик `alloc-rate` в `dotnet-counters`, для поиска источников — трасса `dotnet-trace` с событиями `AllocationTick` или профилировщик аллокаций в Visual Studio / dotMemory.

**Почему аллокации важны, если они дешёвые.** Частота сборок Gen 0 прямо пропорциональна скорости аллокаций. Больше аллокаций → больше пауз, больше шансов, что объекты доживут до Gen 1/Gen 2, больше CPU на GC. В коде, который выполняется миллионы раз в секунду, лишние 40 байт на вызов превращаются в десятки мегабайт в секунду.

## Как уменьшить количество аллокаций?

```yaml
category: clr-gc
level: middle
difficulty: 3
slug: clr-gc-kak-umenshit-kolichestvo-allokacii
tags: memory
```

Сначала измерить, где аллокации реально происходят, а затем убрать самые массовые: заменить временные объекты значимыми типами и `Span<T>`, переиспользовать буферы через пулы, убрать скрытые аллокации (boxing, замыкания, LINQ, `params`, интерполяцию строк в логах). Оптимизировать стоит горячий путь, а не весь код подряд.

**Приёмы по частоте пользы:**

| Проблема | Решение |
| --- | --- |
| временный `byte[]`/`char[]` под каждый вызов | `ArrayPool<T>.Shared`, `stackalloc` для малых размеров |
| `Substring`, `Split`, `string.Concat` при разборе | `ReadOnlySpan<char>`, `MemoryExtensions.Split`, `span.Slice` |
| `List<T>` растёт с перевыделениями | задать `capacity` заранее |
| boxing через `object` или интерфейс | дженерики с `where T : struct`, `IEquatable<T>` |
| лямбда захватывает переменные | `static`-лямбды, перегрузки с `state`-аргументом |
| LINQ в горячем цикле | обычный `foreach`/`for` |
| `params object[]` | перегрузки с фиксированными аргументами, `params ReadOnlySpan<T>` (C# 13) |
| `Task<T>` при синхронном завершении | `ValueTask<T>` |
| строки в логах при выключенном уровне | `[LoggerMessage]` source generator |
| маленькие неизменяемые объекты | `readonly struct` / `record struct` |

**Примеры:**

```csharp
// до: Split создаёт массив и строку на каждый элемент
foreach (var part in line.Split(','))
    sum += int.Parse(part);

// после: ноль аллокаций
foreach (var range in line.AsSpan().Split(','))
    sum += int.Parse(line.AsSpan(range));
```

```csharp
// лямбда захватывает threshold → display class + делегат на каждый вызов
items.Where(x => x > threshold);

// static-лямбда не может захватывать — компилятор гарантирует отсутствие замыкания
cache.GetOrAdd(key, static (k, arg) => Create(k, arg), threshold);
```

```csharp
[LoggerMessage(Level = LogLevel.Debug, Message = "Order {Id} processed")]
static partial void LogProcessed(ILogger logger, int id);   // без boxing и форматирования, если Debug выключен
```

**Кэширование результатов.** Неизменяемые объекты можно создать один раз: `static readonly` массивы, `Array.Empty<T>()`, кэш `JsonSerializerOptions` (создание новых опций на каждый вызов — известная ловушка), `SearchValues<T>` для поиска символов, `FrozenDictionary` для справочников.

**Порядок работы:**

1. Измерить: `dotnet-counters` (`alloc-rate`, частота Gen 0), трасса аллокаций, BenchmarkDotNet с `[MemoryDiagnoser]`.
2. Найти 2–3 точки, дающие большую часть байтов.
3. Переписать их и перемерить.

**Чего не делать:** превращать всё в структуры (большие структуры копируются и могут быть медленнее), пулить мелкие объекты (пул дороже Gen 0-аллокации), жертвовать читаемостью в коде, который вызывается раз в минуту.

## Что такое boxing allocation?

```yaml
category: clr-gc
level: middle
difficulty: 2
slug: clr-gc-chto-takoe-boxing-allocation
tags: memory, boxing
```

Boxing allocation — аллокация в куче, которая происходит при упаковке значимого типа: когда `int`, `struct` или `enum` приводится к `object`, к интерфейсу или к `Enum`/`ValueType`, CLR создаёт в куче объект-«коробку» и копирует туда значение. Каждый такой объект — отдельная работа для GC.

```csharp
int x = 42;
object o = x;        // box: новый объект 24 байта на x64, копия значения
int y = (int)o;      // unbox: проверка типа + копирование обратно, без аллокации
```

В IL это видно явно: инструкция `box`. Коробка — полноценный объект с заголовком и `MethodTable`, поэтому `int` в 4 байта превращается в 24 байта кучи.

**Где boxing прячется:**

| Код | Почему boxing |
| --- | --- |
| `ArrayList`, `Hashtable`, `List<object>` | хранят `object` |
| `string.Format("{0}", id)`, `Console.WriteLine("{0}", x)` | параметры `object` |
| `logger.LogInformation("Id {Id}", id)` | `params object?[]` — массив и коробка на каждый аргумент |
| `IComparable c = myStruct;` | приведение к интерфейсу |
| `struct` без переопределённых `Equals`/`GetHashCode` как ключ словаря | базовый `ValueType.Equals` работает через рефлексию и boxing |
| `enumValue.HasFlag(flag)` в старых версиях | параметр `Enum`, в современных JIT оптимизирует |
| `foreach` по `IEnumerable<T>` у структурного энумератора | энумератор-структура боксится при приведении к интерфейсу |
| лямбда/делегат, захватывающий struct | struct копируется в display class (это не boxing, но тоже аллокация) |

**Как избежать:**

- **Дженерики.** `List<int>`, `Dictionary<int, T>` работают без упаковки: JIT генерирует отдельный код для каждого значимого типа.
- **Ограничения** `where T : struct, IEquatable<T>` — вызов метода интерфейса через ограничение идёт по constrained call без boxing.
- **Реализовать `IEquatable<T>`** и переопределить `GetHashCode` у структур-ключей; `record struct` делает это сам.
- **Интерполяция строк.** `$"id={id}"` в современном C# идёт через `DefaultInterpolatedStringHandler` и не боксит `int`, в отличие от `string.Format`.
- **`[LoggerMessage]`** вместо `logger.LogX("...", args)` — строго типизированные параметры без `object[]`.

**Оптимизации JIT.** Современный JIT умеет убирать часть упаковок: `box` + немедленный `unbox`, вызов `HasFlag`, проверки `typeof(T) == typeof(int)` в дженериках. В .NET 9–10 JIT также может размещать коробку на стеке, если она не покидает метод (escape analysis). Но полагаться на это в публичном API нельзя — ориентир остаётся «не боксить в горячем пути».

**Как найти:** `box` в IL (sharplab.io, ILSpy), аллокации `System.Int32`/ваших структур в профилировщике памяти, анализатор Roslynator/Heap Allocation Viewer в IDE.

## Как можно диагностировать проблемы с памятью?

```yaml
category: clr-gc
level: middle
difficulty: 3
slug: clr-gc-kak-mozhno-diagnostirovat-problemy-s-pamyatyu
```

Идти от общего к частному: сначала метриками понять, что растёт (managed-куча, частота сборок или общая память процесса), затем снять снимок кучи или трассу аллокаций и найти конкретные типы и цепочки ссылок, которые их держат. Для .NET это набор `dotnet-counters` → `dotnet-gcdump` / `dotnet-dump` → `dotnet-trace`, плюс профилировщики.

**Шаг 1 — метрики в реальном времени:**

```bash
dotnet-counters monitor -p <pid> --counters System.Runtime
```

| Что смотреть | О чём говорит |
| --- | --- |
| `gc-heap-size` | размер managed-кучи; монотонный рост после Gen 2 = утечка |
| `alloc-rate` | сколько байт в секунду выделяется — давление на GC |
| `gen-0/1/2-gc-count` | много Gen 2 — объекты доживают до старости или много LOH |
| `time-in-gc` | доля времени в GC; стабильно больше ~10% — повод разбираться |
| `loh-size`, `poh-size` | большие и закреплённые объекты |
| `working-set` | вся память процесса; сильно больше heap → unmanaged |

В .NET 8+ те же данные доступны как метрики `System.Runtime` через OpenTelemetry — в проде их обычно смотрят в Prometheus/Grafana.

**Шаг 2 — что лежит в куче:**

```bash
dotnet-gcdump collect -p <pid>     # лёгкий снимок: типы, количество, размеры, связи
dotnet-dump collect -p <pid>       # полный дамп процесса
dotnet-dump analyze dump.dmp
> dumpheap -stat                    # топ типов по занимаемой памяти
> gcroot <address>                  # почему объект жив
> eeheap -gc                        # размеры поколений и сегментов
> finalizequeue                     # что ждёт финализации
```

Главный приём для утечек — **сравнить два снимка** через интервал под нагрузкой (Visual Studio, PerfView, dotMemory умеют diff): растущие по количеству типы и есть кандидаты.

**Шаг 3 — кто выделяет:**

```bash
dotnet-trace collect -p <pid> --profile gc-verbose
```

Трасса содержит события GC (паузы, причины, поколения) и `AllocationTick` — выборку аллокаций со стеками. Открывается в PerfView, Visual Studio, SpeedScope. Отсюда видно, какой метод генерирует основной поток байтов.

**Для разработки:**

- BenchmarkDotNet с `[MemoryDiagnoser]` — аллокации на операцию;
- `GC.GetAllocatedBytesForCurrentThread()` в тестах;
- Visual Studio Diagnostic Tools, JetBrains dotMemory / dotTrace.

**Типичные картины и вывод:**

- heap растёт и не падает после полных сборок → managed-утечка, ищите корень через `gcroot`;
- heap стабилен, частые Gen 0, высокий `time-in-gc` → много временных аллокаций в горячем пути;
- много Gen 2 и большой `loh-size` → большие буферы, нужен пул или стриминг;
- `working-set` намного больше heap → unmanaged: native-библиотеки, handles, фрагментация native-аллокатора.

Все инструменты `dotnet-*` работают и в Linux-контейнерах; для pod'ов их кладут в образ или запускают в sidecar с общим `/tmp` (там лежит diagnostics IPC socket).

## Что такое `GC.Collect()` и почему обычно не стоит вызывать его вручную?

```yaml
category: clr-gc
level: middle
difficulty: 4
slug: clr-gc-chto-takoe-gc-collect-i-pochemu-obychno-ne-stoit-vyzyvat-ego-vruchnuyu
tags: memory
```

`GC.Collect()` принудительно запускает сборку мусора — по умолчанию полную, блокирующую, всех поколений, включая LOH. Вызывать его вручную обычно вредно: GC сам выбирает момент и объём сборки по собственной статистике, а ручной вызов стоит дорого, останавливает потоки и искусственно состаривает живые объекты.

**Перегрузки:**

```csharp
GC.Collect();                                     // = Collect(2, Forced, blocking: true)
GC.Collect(0);                                    // только Gen 0
GC.Collect(2, GCCollectionMode.Optimized);        // GC сам решит, стоит ли
GC.Collect(2, GCCollectionMode.Forced, blocking: false); // попросить background GC
GC.Collect(2, GCCollectionMode.Forced, blocking: true, compacting: true);
```

**Почему это плохо:**

1. **Пауза.** Полная блокирующая сборка обходит всю живую кучу. На сервисе с гигабайтами живых объектов это сотни миллисекунд stop-the-world — все запросы в этот момент стоят.
2. **Состаривание.** Всё, что живо в момент вызова (объекты текущих запросов, временные буферы), переживает сборку и переезжает в Gen 1/Gen 2. Мусор, который бесплатно умер бы в Gen 0, теперь будет ждать полной сборки.
3. **Сбитая самонастройка.** GC подбирает бюджеты поколений по наблюдаемой выживаемости. Ручные сборки искажают статистику, и бюджеты становятся хуже.
4. **Не лечит причину.** Если память растёт, значит, объекты достижимы — `GC.Collect` их не освободит. Если недостижимы — GC и так их соберёт, когда понадобится память.
5. **Не освобождает unmanaged.** Файлы и соединения закрывает `Dispose`, а не сборка.

Частый антипаттерн — `GC.Collect()` в фоновом таймере «чтобы память не росла». Результат — регулярные паузы и та же память, потому что GC всё равно держит committed-сегменты про запас.

**Когда вызов оправдан:**

- **Тесты и бенчмарки** — привести кучу в известное состояние, проверить отсутствие утечки через `WeakReference`:
  ```csharp
  GC.Collect(); GC.WaitForPendingFinalizers(); GC.Collect();
  ```
- **Редкие границы фаз**, после которых много памяти гарантированно освободилось, а пауза не мешает: выгрузили крупный кэш, закончили загрузку при старте, между этапами batch-процесса, приложение ушло в фон.
- **Разовое уплотнение LOH** вместе с `GCSettings.LargeObjectHeapCompactionMode = CompactOnce`.

**Что использовать вместо:**

- уменьшать аллокации и время жизни объектов;
- `GC.TryStartNoGCRegion(size)` — для короткого критичного по latency участка;
- `GCSettings.LatencyMode = GCLatencyMode.SustainedLowLatency` — избегать блокирующих полных сборок на время чувствительной фазы;
- конфигурацию GC (`GCConserveMemory`, `GCHeapHardLimit`, режим Server/Workstation), если проблема в объёме памяти процесса.

**Что спрашивают дальше:** что такое `GCCollectionMode.Optimized`, почему после `GC.Collect()` память процесса может не уменьшиться (GC не обязан сразу возвращать память ОС), как проверить, что объект действительно собран.

## Что такое Server GC и Workstation GC?

```yaml
category: clr-gc
level: middle
difficulty: 2
slug: clr-gc-chto-takoe-server-gc-i-workstation-gc
tags: memory
```

Это два режима работы сборщика мусора. Workstation GC — одна куча, сборка выполняется на потоке, который её вызвал; экономит память и CPU, рассчитан на десктоп и небольшие процессы. Server GC — отдельная куча и отдельный поток GC на каждое логическое ядро, сборка идёт параллельно; даёт максимальную пропускную способность ценой заметно большей памяти.

| | Workstation | Server |
| --- | --- | --- |
| Кучи | одна | по одной на ядро (или меньше, см. DATAS) |
| Кто собирает | поток, вызвавший GC | выделенные потоки GC с высоким приоритетом |
| Бюджет Gen 0 | небольшой | большой, на каждую кучу свой |
| Память процесса | меньше | в разы больше |
| По умолчанию | консоль, десктоп, сервисы | ASP.NET Core (`Microsoft.NET.Sdk.Web`) |

**Как включить:**

```xml
<PropertyGroup>
  <ServerGarbageCollection>true</ServerGarbageCollection>
  <ConcurrentGarbageCollection>true</ConcurrentGarbageCollection>
</PropertyGroup>
```

То же самое — `System.GC.Server` в `runtimeconfig.json` или переменная окружения `DOTNET_gcServer=1`. Проверить в рантайме: `GCSettings.IsServerGC`. На машине с одним логическим процессором Server GC недоступен, и рантайм использует Workstation.

**Background GC ортогонален режиму.** Флаг `ConcurrentGarbageCollection` (по умолчанию включён) разрешает собирать Gen 2 в фоне параллельно с работой приложения — и в Workstation, и в Server. Выключают его редко: ради экономии потока и памяти в очень маленьких процессах.

**DATAS (.NET 9+).** Классическая проблема Server GC — на 32-ядерной машине процесс заводит 32 кучи, даже если нагрузка маленькая. DATAS (Dynamic Adaptation To Application Sizes) начинает с одной кучи и добавляет или убирает кучи по нагрузке. В .NET 8 его включали вручную, с .NET 9 он включён по умолчанию для Server GC; выключается `<GarbageCollectionAdaptationMode>0</GarbageCollectionAdaptationMode>`.

**Как выбирать:** веб-сервис с высокой нагрузкой — Server; много небольших процессов на одной машине, CLI-утилиты, десктоп, pod с маленьким лимитом памяти — Workstation или Server с ограниченным `GCHeapCount`. Решение подтверждают замером: пропускная способность, p99 latency и потребление памяти.

**Что спрашивают дальше:** почему процесс с Server GC «съедает» больше памяти, как Server GC ведёт себя в контейнере с лимитом CPU, что такое background GC.

## Что такое pinned object?

```yaml
category: clr-gc
level: middle
difficulty: 2
slug: clr-gc-chto-takoe-pinned-object
tags: memory
```

Pinned (закреплённый) объект — объект в managed-куче, который GC пообещал не перемещать при уплотнении. Закрепление нужно, когда адрес объекта передан туда, где GC его не отследит: в native-код, драйвер, ОС для асинхронного ввода-вывода или в сырой указатель в `unsafe`-коде.

**Зачем это вообще нужно.** Уплотняющий GC двигает живые объекты и переписывает все managed-ссылки на них. Native-код держит голый адрес — если массив переедет, функция на C будет писать в чужую память.

**Способы закрепить:**

```csharp
// 1. fixed — на время блока, самый дешёвый способ
fixed (byte* p = buffer)
{
    NativeRead(p, buffer.Length);
}

// 2. GCHandle — на произвольное время, освобождать обязательно
var handle = GCHandle.Alloc(buffer, GCHandleType.Pinned);
try { IntPtr addr = handle.AddrOfPinnedObject(); /* ... */ }
finally { handle.Free(); }

// 3. Memory<T>.Pin() — для API на Memory<T>
using MemoryHandle mh = memory.Pin();

// 4. Сразу в Pinned Object Heap (.NET 5+)
byte[] ioBuffer = GC.AllocateArray<byte>(64 * 1024, pinned: true);
```

Кроме того, P/Invoke-маршалер сам закрепляет blittable-массивы и строки на время вызова — явно ничего делать не нужно, пока native-код не сохраняет указатель после возврата.

**Чем закрепление вредно.** Закреплённый объект — камень посреди кучи. GC не может сдвинуть его и не может сдвинуть к нему соседей, поэтому вокруг остаются дыры — фрагментация. Особенно плохо, когда в Gen 0 много долго закреплённых буферов: эфемерная куча перестаёт нормально уплотняться, растёт память, GC вынужден оставлять целые участки в младших поколениях.

**Правила:**

- закреплять как можно короче — `fixed` предпочтительнее `GCHandle`;
- долгоживущие буферы для I/O и interop выделять в POH или пулить: POH отделён от обычной кучи и не мешает её уплотнению;
- не забывать `handle.Free()` — забытый pinned-handle одновременно и утечка, и источник фрагментации;
- `fixed` почти бесплатен, если GC за время блока не случился: локальная переменная просто помечена как pinned в GC info.

**Диагностика:** `dotnet-counters` показывает `poh-size`, событие `GCHeapStats` в трассе `dotnet-trace` — число закреплённых объектов на момент сборки; в `dotnet-dump` — `gchandles` (сколько pinned-handle'ов) и `dumpheap -stat` с большим количеством `Free`-блоков.

**Что спрашивают дальше:** что такое POH, как pinning связан с фрагментацией, почему `Socket` и `FileStream` внутри используют закреплённые буферы.

## Что такое fragmentation в памяти?

```yaml
category: clr-gc
level: middle
difficulty: 2
slug: clr-gc-chto-takoe-fragmentation-v-pamyati
tags: memory
```

Фрагментация — ситуация, когда свободная память есть, но она разбита на мелкие несмежные куски между живыми объектами. Суммарно свободно много, а выделить крупный непрерывный блок нельзя, и процесс держит больше памяти, чем реально использует.

```text
[A][free 8K][B][free 4K][C][free 16K][D]   → свободно 28K,
                                              но массив на 20K не влезет
```

**Откуда берётся в .NET:**

- **LOH не уплотняется по умолчанию.** Большие объекты освобождаются, на их месте остаются дыры, новые большие объекты разного размера туда не всегда помещаются.
- **Pinned-объекты.** GC не может сдвинуть закреплённый буфер, поэтому его соседи тоже остаются на местах, а вокруг образуются промежутки.
- **Sweep вместо compact.** Background GC для Gen 2 только помечает мёртвые объекты как свободные (free list), а не сдвигает живые. Уплотнение делает лишь блокирующая сборка, и GC решает, делать ли его, по оценке выгоды.
- **Native-куча.** `malloc` в native-библиотеках и `Marshal.AllocHGlobal` фрагментируются по своим законам, GC тут не помогает.

**Почему SOH обычно не страдает.** Малая куча уплотняется: живые объекты сдвигаются друг к другу, свободное место становится одним блоком, а выделение — простым сдвигом указателя. Поэтому основные проблемы — LOH, pinning и native-память.

**Как увидеть:**

```csharp
var info = GC.GetGCMemoryInfo();
Console.WriteLine($"Fragmented: {info.FragmentedBytes / 1024 / 1024} MB");
Console.WriteLine($"Heap:       {info.HeapSizeBytes / 1024 / 1024} MB");

// по поколениям: 0,1,2 — SOH, 3 — LOH, 4 — POH
var loh = info.GenerationInfo[3];
Console.WriteLine($"LOH fragmentation: {loh.FragmentationAfterBytes}");
```

В дампе (`dotnet-dump analyze`) фрагментацию видно как много объектов типа `Free` в `dumpheap -stat`. Счётчик `gc-fragmentation` в `dotnet-counters` показывает её долю в процентах.

**Как бороться:**

- пулить большие буферы (`ArrayPool<T>`, `RecyclableMemoryStream`) — один и тот же массив переиспользуется, дыр не появляется;
- не читать крупные данные целиком — стримить кусками меньше 85 000 байт;
- закреплять ненадолго, долгоживущие I/O-буферы держать в POH;
- при необходимости разрешить разовое уплотнение LOH через `GCSettings.LargeObjectHeapCompactionMode`.

С регионами (.NET 7+) ситуация лучше: полностью освободившийся регион возвращается в общий пул и может быть отдан ОС, так что фрагментация не так долго удерживает память.

**Что спрашивают дальше:** почему LOH не уплотняется, как pinning создаёт фрагментацию, как отличить фрагментацию от утечки (при утечке растёт число живых объектов, при фрагментации — доля `Free`).

## Как работает Tiered Compilation и почему первые вызовы метода могут быть медленнее в разы?

```yaml
category: clr-gc
level: senior
difficulty: 4
slug: advanced-csharp-kak-rabotaet-tiered-compilation-i-pochemu-pervye-vyzovy-metoda-mogut-b
tags: jit, performance
```

Tiered Compilation — схема, при которой JIT компилирует метод несколько раз: сначала быстро и без оптимизаций (Tier 0), а если метод оказался горячим — повторно, с полной оптимизацией (Tier 1). Первые вызовы медленнее по двум причинам: они платят за саму JIT-компиляцию и выполняются неоптимизированным Tier 0 кодом, который бывает в разы медленнее итогового.

**Жизненный цикл метода в .NET 8+:**

```text
первый вызов ─► Tier 0 (или готовый ReadyToRun-код)
               │ ~30 вызовов + пауза в активности Tier 0 (~100 мс)
               ▼
            Tier 0 instrumented — собирает профиль (Dynamic PGO)
               │ ещё порция вызовов
               ▼
            Tier 1 — полная оптимизация с учётом профиля,
                     компилируется в фоновом потоке, вызовы переключаются на него
```

Для кода из ReadyToRun-образа путь похожий: предкомпилированный код → при горячести инструментированная версия → Tier 1.

**Чем Tier 0 хуже:**

- нет инлайнинга — каждый геттер и `Span<T>.this[]` становится настоящим вызовом;
- локальные переменные живут в стеке, а не в регистрах;
- не удаляются проверки границ, не разворачиваются циклы, нет девиртуализации;
- `static readonly` поля читаются из памяти, а в Tier 1 класс уже проинициализирован, и JIT подставляет их как константы, вырезая мёртвые ветки.

**Почему так сделано.** Большинство методов при старте выполняются один-два раза (конфигурация, DI, регистрация маршрутов). Полная оптимизация каждого из них тратила бы время старта впустую. Tiering экономит старт, а горячие методы в итоге получают код даже лучше, чем при старом «сразу оптимизировать»: Dynamic PGO знает реальные типы и ветки и делает guarded devirtualization, раскладку горячих блоков, инлайнинг по профилю.

**Практические последствия:**

- **Холодный старт и первые запросы** медленнее — отсюда warm-up перед вводом инстанса в балансировщик.
- **Бенчмарки без прогрева лгут.** BenchmarkDotNet делает прогрев и дожидается Tier 1, самописный `Stopwatch` на десяти вызовах — нет.
- **Методы с циклами** стартуют в Tier 0 и переходят на оптимизированный код через OSR прямо внутри цикла.

**Рычаги управления:**

| Настройка | Эффект |
| --- | --- |
| `<TieredCompilation>false</TieredCompilation>` | сразу полная оптимизация, без PGO; старт медленнее |
| `<TieredPGO>false</TieredPGO>` | tiering остаётся, профиль не собирается |
| `<TieredCompilationQuickJitForLoops>false</...>` | методы с циклами сразу компилируются оптимизированно |
| `[MethodImpl(MethodImplOptions.AggressiveOptimization)]` | метод минует tiering — но и PGO для него нет |
| `<PublishReadyToRun>true</PublishReadyToRun>` | первый вызов идёт по готовому коду, без JIT |

`AggressiveOptimization` часто ставят «для скорости» и получают обратный эффект: без профиля JIT не девиртуализирует интерфейсные вызовы, и стационарная производительность падает.

**Как увидеть уровни:** `DOTNET_JitStdOutFile` + `DOTNET_JitDisasmSummary=1` печатает каждый скомпилированный метод с его tier; события JIT видны в `dotnet-trace` и PerfView.

**Что спрашивают дальше:** что такое OSR, как ReadyToRun сочетается с tiering, почему `AggressiveOptimization` может замедлить код, зачем прогрев в Kubernetes readiness-пробе.

## Что такое OSR (On-Stack Replacement) и какую проблему Tiered Compilation он решает?

```yaml
category: clr-gc
level: senior
difficulty: 5
slug: advanced-csharp-chto-takoe-osr-on-stack-replacement-i-kakuyu-problemu-tiered-compilati
tags: jit, performance
```

OSR (On-Stack Replacement) — механизм, который позволяет перевести метод с неоптимизированного Tier 0 кода на оптимизированный прямо посреди выполнения, не дожидаясь следующего вызова. Он решает проблему методов с долгими циклами: tiering переключает версию метода только на границе вызова, и метод, вызванный один раз, но крутящий цикл миллиард итераций, навсегда застрял бы в медленном Tier 0.

**Проблема без OSR:**

```csharp
static void Main()
{
    long sum = 0;
    for (int i = 0; i < 1_000_000_000; i++)   // Main вызывается один раз —
        sum += Compute(i);                     // счётчик вызовов до 30 не дойдёт
    Console.WriteLine(sum);
}
```

До .NET 7 у рантайма было два плохих варианта:

- **`QuickJitForLoops = false`** (дефолт в старых версиях) — методы с циклами сразу компилировались с полной оптимизацией. Цикл быстрый, но старт медленнее, а PGO для таких методов нет вовсе.
- **`QuickJitForLoops = true`** без OSR — метод с циклом компилировался в Tier 0 и оставался в нём до конца работы цикла. Для `Main`, фоновых воркеров с `while (true)` и одноразовых batch-методов это означало медленный код на всё время жизни.

**Как работает OSR:**

1. JIT компилирует метод с циклом в Tier 0 и вставляет в заголовки циклов *patchpoint* — счётчик итераций.
2. Когда счётчик превышает порог, рантайм просит JIT скомпилировать **OSR-версию** метода: оптимизированный код, чья точка входа — именно этот patchpoint, а не начало метода.
3. OSR-код получает текущий Tier 0 кадр стека как есть: читает локальные переменные из его слотов и продолжает цикл с той же итерации.
4. Следующие вызовы метода идут обычным путём: Tier 0 → по счётчику вызовов → полноценный Tier 1.

Это видно в выводе JIT:

```text
JIT compiled P:M(...) [Instrumented Tier0, IL size=155, code size=638]
JIT compiled P:M(...) [Tier1-OSR @0x14 with Synthesized PGO, IL size=155, code size=2212]
```

`@0x14` — IL-смещение patchpoint'а, с которого начинается OSR-версия. С .NET 8 методы с циклами сразу компилируются как *Instrumented Tier0*, чтобы к моменту OSR у JIT уже был профиль.

**Статус по версиям:** OSR и `QuickJitForLoops` включены по умолчанию с .NET 7 на x64 и Arm64. Это одна из причин, почему Dynamic PGO по умолчанию (.NET 8) заметно помог: методы с циклами тоже стали получать профиль.

**Ограничения, о которых стоит знать:**

- **OSR-код не идентичен Tier 1.** Он унаследовал раскладку Tier 0 кадра, часть локальных живёт в памяти старого кадра, вход в середину метода мешает части оптимизаций. Обычно он близок к Tier 1, но в микробенчмарках разница бывает видна.
- **Переключение не мгновенное** — первые итерации цикла, до срабатывания patchpoint'а, всё равно идут в Tier 0.
- **Не каждый метод подходит.** Для части методов (исторически — например, с `localloc`, то есть `stackalloc` переменного размера) OSR не поддерживался, и JIT компилировал их сразу оптимизированно.

**Практическое следствие для бенчмарков.** Если меряете один вызов долгого метода, часть времени он проведёт в Tier 0, а остальную — в OSR-версии, а не в том Tier 1, который увидит прод при многократных вызовах. BenchmarkDotNet вызывает метод многократно и выдаёт стационарное значение; самописные замеры цикла внутри `Main` показывают OSR-код.

**Как отключить для эксперимента:** `DOTNET_TC_QuickJitForLoops=0` — методы с циклами сразу компилируются оптимизированно, OSR им не нужен. В проде трогать не нужно.

**Что спрашивают дальше:** как tiering переключает версии метода (через precode/stub и backpatching вызовов), почему `AggressiveOptimization` отключает PGO, чем OSR в .NET отличается от деоптимизации в JVM (в .NET нет обратного перехода из оптимизированного кода в Tier 0).

## Как ReadyToRun и NativeAOT влияют на время старта, пиковую производительность и размер образа?

```yaml
category: clr-gc
level: senior
difficulty: 4
slug: advanced-csharp-kak-readytorun-i-nativeaot-vliyayut-na-vremya-starta-pikovuyu-proizvod
tags: jit, performance
```

Оба убирают JIT с пути старта, но по-разному. ReadyToRun кладёт в сборку заранее скомпилированный код рядом с IL: старт быстрее, а горячие методы JIT всё равно перекомпилирует в Tier 1, так что пиковая производительность остаётся как у обычного JIT. NativeAOT компилирует всё приложение в один native-бинарник без JIT: самый быстрый старт и малая память, но без Tier 1 и Dynamic PGO, с ограничениями на рефлексию и динамический код.

| | JIT | ReadyToRun | NativeAOT |
| --- | --- | --- | --- |
| Старт | медленный: JIT каждого метода | быстрее, JIT только для того, чего нет в образе | самый быстрый, JIT нет |
| Пиковая производительность | высокая, Tier 1 + Dynamic PGO | та же: горячие методы перекомпилируются | хорошая, но без PGO по реальной нагрузке |
| Размер | только IL | IL + native, сборки в 2–3 раза больше | один файл, trimming выкидывает неиспользуемое |
| Нужен рантайм | да | да | нет, рантайм вшит в бинарник |
| Совместимость | полная | полная | нет `Reflection.Emit`, динамической загрузки сборок, требуется trim-safe код |

**ReadyToRun:**

```xml
<PublishReadyToRun>true</PublishReadyToRun>
<RuntimeIdentifier>linux-x64</RuntimeIdentifier>
```

- Код компилируется под конкретную платформу и консервативный набор инструкций, без знания реального CPU и без профиля. Поэтому R2R-код — это стартовая ступень tiering'а: горячие методы проходят инструментирование и перекомпилируются в Tier 1.
- Кросс-сборочный инлайнинг ограничен «version bubble»: код из вашей сборки не может заинлайнить метод из NuGet-пакета, который может обновиться отдельно. Composite R2R (`PublishReadyToRunComposite`) объединяет сборки в один bubble.
- Если R2R-код не подходит (другая версия зависимости, generic-инстанциация, которой нет в образе), рантайм молча откатывается на JIT. Именно так поставляется сама BCL — она уже R2R.

**NativeAOT:**

```xml
<PublishAot>true</PublishAot>
<OptimizationPreference>Speed</OptimizationPreference> <!-- или Size -->
```

- Всё компилируется заранее, включая инстанциации generic'ов, которые компилятор смог увидеть статически. `MakeGenericType` с неизвестными типами, `Assembly.LoadFrom`, `Reflection.Emit` не работают; сериализация и DI должны быть на source generators.
- Нет tiering: код один раз оптимизирован компилятором, без знаний о реальных типах. Там, где JIT-версия выигрывает за счёт guarded devirtualization, `static readonly` как констант и инструкций конкретного CPU, NativeAOT может уступать в стационарной пропускной способности. Где-то он, наоборот, быстрее за счёт whole-program анализа. Итог зависит от кода — мерить.
- Выигрыш: старт в десятки миллисекунд, меньше working set (нет JIT, метаданных для него, IL), маленький образ контейнера без .NET runtime.
- Предупреждения trimming/AOT (`IL2026`, `IL3050`) — это не шум, а места, которые сломаются в рантайме.

**Когда что выбирать:**

- **Долгоживущий веб-сервис** — обычный JIT, иногда с R2R ради быстрого прогрева после деплоя и автомасштабирования.
- **Serverless, CLI-утилиты, sidecar'ы, масштабирование с нуля** — NativeAOT: старт и память важнее последних процентов throughput.
- **Десктоп** — R2R для отзывчивого старта без потери совместимости.

**Что спрашивают дальше:** почему R2R-сборка больше обычной, что такое version bubble, какие библиотеки несовместимы с NativeAOT и как это найти до продакшена (`<IsAotCompatible>`, анализаторы), чем trimming отличается от AOT.

## Почему в бенчмарке метод может быть быстрее, чем в проде, из-за инлайнинга — и как это проверить?

```yaml
category: clr-gc
level: senior
difficulty: 5
slug: advanced-csharp-pochemu-v-benchmarke-metod-mozhet-byt-bystree-chem-v-prode-iz-za-inlai
tags: jit, profiling
```

Решение об инлайнинге JIT принимает для каждого места вызова отдельно, с учётом контекста и профиля. В бенчмарке метод вызывается из маленького цикла с константными аргументами и одним типом — JIT инлайнит его, сворачивает константы, девиртуализирует и выкидывает лишнее. В проде тот же метод вызывается из большого метода, с разными типами и данными, и инлайнинг либо не происходит, либо даёт меньше. Проверяют это дизассемблером JIT, а не догадками.

**Почему результаты расходятся:**

- **Константы.** `Parse("42")` в бенчмарке после инлайнинга может частично посчитаться на этапе компиляции. В проде строка приходит из сети.
- **Мономорфный профиль.** Dynamic PGO видит, что за `IShape` всегда `Circle`, и делает guarded devirtualization с инлайнингом `Circle.Area`. В проде там пять реализаций вперемешку — проверка типа промахивается, вызов остаётся виртуальным.
- **Бюджет инлайнинга вызывающего метода.** У JIT есть лимиты на рост кода. В крошечном методе бенчмарка бюджета хватает, в большом продовом методе с десятком вызовов — нет.
- **Tier.** BenchmarkDotNet меряет Tier 1 после прогрева. Редко вызываемый продовый путь может работать в Tier 0, где инлайнинга нет вообще, или в R2R-коде с ограниченным кросс-сборочным инлайнингом.
- **Мёртвый код.** Если результат не используется, JIT может выбросить вычисление целиком. BenchmarkDotNet защищается, потребляя возвращаемое значение, — самописный бенчмарк часто нет.
- **Кэши CPU и branch predictor.** Горячий цикл на одних данных — идеальные условия, которых в проде нет. Это уже не про инлайнинг, но искажает результат в ту же сторону.

**Как проверить, что происходит на самом деле:**

```csharp
[DisassemblyDiagnoser(maxDepth: 2)]
[MemoryDiagnoser]
public class ParseBench
{
    private string _input = "42";                // поле, а не литерал: без свёртки констант

    [Benchmark] public int Parse() => Parser.Parse(_input);
}
```

`DisassemblyDiagnoser` показывает итоговый машинный код бенчмарка: видно, остался ли `call Parser.Parse` или тело встроено.

Для реального приложения — дизассемблер JIT через переменные окружения (работает в release-рантайме с .NET 7):

```bash
DOTNET_JitDisasmSummary=1 DOTNET_JitStdOutFile=jit.txt dotnet app.dll   # какие методы в каком tier
DOTNET_JitDisasm="Parser:Parse" dotnet app.dll                           # asm конкретного метода
```

В выводе `JitDisasm` для вызывающего метода видно, есть ли `call` на интересующий метод. Важно смотреть именно Tier 1 версию вызывающего метода, а не Tier 0.

**Эксперименты:**

- `[MethodImpl(MethodImplOptions.NoInlining)]` на методе — сравнить с бенчмарком без него, чтобы понять, сколько давал инлайнинг;
- `[MethodImpl(MethodImplOptions.AggressiveInlining)]` — снять эвристику размера (JIT всё равно откажется, если инлайнинг невозможен);
- бенчмарк с полиморфными данными — массив разных реализаций интерфейса вместо одной;
- `DOTNET_TieredPGO=0` — увидеть, сколько выигрыша было от профиля.

**Что мешает инлайнингу:** виртуальные и интерфейсные вызовы без девиртуализации, большой IL, `NoInlining`, вызов через делегат, рекурсия, пересечение границы version bubble в R2R. Исключения в методе — классический стопор, хотя в новых версиях JIT ограничения постепенно ослабляют.

**Что спрашивают дальше:** что такое guarded devirtualization, почему `sealed` помогает JIT, как профилировать прод (`dotnet-trace`, PerfView), чтобы проверить, что горячий путь совпадает с бенчмарком.

## Что такое escape analysis и стековая аллокация в .NET, и на что реально можно рассчитывать?

```yaml
category: clr-gc
level: senior
difficulty: 5
slug: advanced-csharp-chto-takoe-escape-analysis-i-stekovaya-allokaciya-v-net-i-na-chto-real
tags: allocations, jit
```

Escape analysis — анализ JIT, который доказывает, что объект не «убегает» из метода: ссылка на него не сохраняется в поле, не возвращается, не передаётся в неинлайненный вызов. Такой объект можно разместить в кадре стека вместо кучи — без аллокации и без работы для GC. В .NET это появилось реально только в последних версиях: .NET 9 научился стековой аллокации небольших объектов классов, .NET 10 расширил её на небольшие массивы и делегаты. Рассчитывать можно на простые локальные случаи в оптимизированном коде, а не на «JIT уберёт все аллокации».

**Что видно на практике** (аллокации на вызов после прогрева, Release):

```csharp
sealed class Pt { public int X, Y; }

static int Obj(int a) { var p = new Pt { X = a, Y = a }; return p.X + p.Y; }
static int Arr(int a) { var x = new[] { a, a + 1, a + 2 }; return x[0] + x[1] + x[2]; }
static int Del(int a) { Func<int, int> f = y => y + a; return f(1); }
```

| | .NET 8 | .NET 9 | .NET 10 |
| --- | --- | --- | --- |
| `Obj` — объект класса | 24 B | 0 | 0 |
| `Arr` — массив из трёх `int` | 40 B | 40 B | 0 |
| `Del` — лямбда с захватом | 88 B | 88 B | 24 B |

В последней строке .NET 10 убрал из кучи делегат, но объект замыкания (display class с полем `a`) всё ещё аллоцируется.

**Отдельная история — удаление боксинга.** Паттерны вроде `object o = x; o.GetHashCode()` JIT давно умеет превращать в вызов без упаковки — это не escape analysis в общем виде, а локальная оптимизация `box` + вызов.

**Почему объект «убегает» — и аллокация остаётся:**

- ссылку записали в поле, статическое поле, массив или вернули из метода;
- объект передан в метод, который не заинлайнился, — JIT не видит, что метод с ним делает;
- объект захвачен замыканием или живёт через `await` (переезжает в state machine в куче);
- размер больше лимита для стека, или массив переменной длины;
- аллокация внутри цикла, где каждая итерация требовала бы нового слота (ограничения здесь постепенно ослабляют).

**Ограничения, которые важны:**

- **Только оптимизированный код.** Tier 0 не делает escape analysis — первые вызовы аллоцируют как обычно. В бенчмарках без прогрева вы увидите аллокации.
- **Зависит от инлайнинга.** Добавили в вызываемый метод логирование, он перестал инлайниться — аллокация вернулась. Оптимизация хрупкая и ничем не гарантирована: это деталь реализации JIT, а не контракт языка.
- **NativeAOT** использует тот же JIT-бэкенд (RyuJIT), так что возможности похожие, но без PGO часть инлайнинга, открывающего escape analysis, может не случиться.

**На что опираться в коде.** Если аллокация в горячем пути важна, не надейтесь на JIT — уберите её явно:

- `struct` / `readonly struct` вместо маленького класса;
- `Span<T>` + `stackalloc` вместо временного массива;
- статическая лямбда (`static x => ...`) или передача состояния параметром вместо захвата;
- `ArrayPool<T>` для буферов переменного размера.

Escape analysis — приятный бонус для кода, который пишется «как обычно», а проверять результат нужно `[MemoryDiagnoser]` в BenchmarkDotNet или `GC.GetAllocatedBytesForCurrentThread()` на прогретом коде.

**Сравнение с JVM:** HotSpot давно делает escape analysis со scalar replacement — объект вообще разбирается на отдельные локальные значения. В .NET это направление развивается последние релизы, так что вопрос «почему C# полагается на struct» исторически отвечается именно этим.

**Что спрашивают дальше:** почему замыкания всё равно аллоцируют, чем stack allocation отличается от `struct`, как проверить аллокации в Tier 1.

## Как найти и убрать аллокации в горячем пути, если профилировщик показывает высокий Gen 0?

```yaml
category: clr-gc
level: senior
difficulty: 4
slug: advanced-csharp-kak-naiti-i-ubrat-allokacii-v-goryachem-puti-esli-profilirovschik-poka
tags: allocations, profiling
```

Высокая частота Gen 0 сама по себе означает одно: приложение много аллоцирует. Порядок действий — подтвердить, что это действительно проблема (время в GC, паузы, CPU), найти по трассе аллокаций конкретные стеки и типы, дающие основной поток байтов, и убирать их по одному, проверяя эффект бенчмарком.

**Шаг 1 — убедиться, что это узкое место.** Gen 0 дешёвый: если `time-in-gc` 1–2%, а p99 в норме, оптимизировать нечего. Сигналы, что пора: `time-in-gc` стабильно выше ~5–10%, `alloc-rate` в сотни МБ/с, паузы коррелируют со всплесками latency, растёт `gen-1`/`gen-2` — временные объекты не успевают умереть.

```bash
dotnet-counters monitor -p <pid> --counters System.Runtime
```

**Шаг 2 — кто аллоцирует:**

```bash
dotnet-trace collect -p <pid> --profile gc-verbose --duration 00:00:30
```

Трасса содержит `GCAllocationTick` — событие примерно на каждые 100 КБ аллокаций с типом и стеком. В PerfView («GC Heap Alloc Ignore Free») или Visual Studio (.NET Object Allocation Tracking) это превращается в дерево: какой метод выделил сколько байт каких типов. Альтернатива — dotMemory / dotTrace в режиме allocation.

**Шаг 3 — узнать типичных виновников:**

| Что в трассе | Откуда | Чем заменить |
| --- | --- | --- |
| `String`, `Char[]` | конкатенация, `Substring`, `ToString`, `string.Format` | `Span<char>`, `string.Create`, `TryFormat`, кэш строк |
| `<>c__DisplayClass` | лямбда с захватом переменных | статическая лямбда, передача state параметром |
| `Func<...>`, `Action` | создание делегата в каждом вызове | кэшировать делегат в `static readonly` поле |
| упакованный `Int32`, `Enumerator` | боксинг, `foreach` по интерфейсу | generic-ограничения, конкретный тип коллекции |
| `WhereSelectEnumerableIterator` и т. п. | LINQ в горячем цикле | обычный цикл |
| `Object[]` | `params object[]`, логирование | перегрузки, `LoggerMessage` source generator |
| `Byte[]` | буферы на запрос | `ArrayPool<T>.Shared`, `stackalloc` для малых |
| `AsyncStateMachineBox`, `Task` | async, который часто завершается асинхронно | `ValueTask`, синхронный быстрый путь |
| `List<T>` + массивы роста | коллекции без capacity | задать capacity, переиспользовать |

**Пример — логирование, которое аллоцирует даже при выключенном уровне:**

```csharp
// строка форматируется и аллоцируется всегда
_logger.LogDebug($"Order {order.Id} processed in {sw.ElapsedMilliseconds} ms");

// source generator: проверка IsEnabled, без боксинга и params-массива
[LoggerMessage(Level = LogLevel.Debug, Message = "Order {OrderId} processed in {Elapsed} ms")]
static partial void LogProcessed(ILogger logger, int orderId, long elapsed);
```

**Шаг 4 — проверить эффект изолированно:**

```csharp
[MemoryDiagnoser]
public class HotPathBench
{
    [Benchmark(Baseline = true)] public int Before() => OldImpl(_data);
    [Benchmark]                  public int After()  => NewImpl(_data);
}
```

Колонка `Allocated` должна упасть до ожидаемого значения — в идеале до `0 B`. В интеграционных тестах можно зафиксировать бюджет через `GC.GetAllocatedBytesForCurrentThread()`.

**Шаг 5 — снова снять метрики под нагрузкой.** Цель — не ноль аллокаций, а снижение `time-in-gc` и p99. Иногда хватает убрать два-три главных источника из верхушки трассы.

**Если убрать аллокации нельзя:**

- сократить время жизни объектов — чтобы они умирали в Gen 0, а не доживали до Gen 1/2, где сборка дороже;
- проверить режим GC: Server GC с большим бюджетом Gen 0 собирает реже;
- на .NET 9+ помнить, что DATAS может держать меньше куч и меньший бюджет — при упоре в throughput стоит сравнить с выключенным DATAS.

**Типичная ошибка** — оптимизировать то, что кажется дорогим, без трассы. Самые крупные источники почти всегда неожиданные: сериализатор, логирование, middleware, `ToString()` в ключе словаря.

**Что спрашивают дальше:** чем `AllocationTick` отличается от точного трекинга, почему Gen 0 почти бесплатен, а Gen 1 уже нет, как `ValueTask` экономит аллокации и когда его нельзя использовать.

## Почему Span<T> нельзя сохранить в поле класса и как обойти это ограничение?

```yaml
category: clr-gc
level: senior
difficulty: 4
slug: advanced-csharp-pochemu-span-t-nelzya-sohranit-v-pole-klassa-i-kak-oboiti-eto-ogranich
tags: span, memory
```

`Span<T>` — `ref struct`, то есть тип, который может жить только на стеке. Внутри у него managed-указатель (`ref T`) на начало данных и длина, а такие указатели GC умеет отслеживать только в стеке и регистрах. Кроме того, span может указывать на `stackalloc`-буфер, и если бы его можно было положить в объект в куче, он пережил бы кадр стека, на который ссылается. Обходят ограничение, храня не span, а то, из чего его можно получить: `Memory<T>`, массив с offset/length или ref struct-обёртку.

**Три причины запрета:**

1. **Время жизни.** `Span<byte> s = stackalloc byte[64]` указывает в кадр текущего метода. Поле класса живёт сколько угодно — после выхода из метода span указывал бы в мусор на стеке.
2. **Interior pointers в куче.** `ref T` может указывать в середину объекта (элемент массива, поле). GC поддерживает такие ссылки только на стеке; хранить их в куче он не умеет — пришлось бы усложнять и замедлять каждую сборку.
3. **Разрыв (tearing).** Span — два поля: указатель и длина. Если бы он лежал в куче и два потока писали его одновременно, другой поток мог бы прочитать указатель от одного span'а и длину от другого — выход за границы без всякого `unsafe`. На стеке span принадлежит одному потоку.

**Что компилятор из этого запрещает:**

```csharp
class Parser
{
    private Span<byte> _buffer;        // CS8345: поле ref struct-типа в классе
}

object o = span;                       // нельзя упаковать
Func<int> f = () => span.Length;       // нельзя захватить в лямбду
List<Span<byte>> list;                 // нельзя как обычный generic-аргумент
```

В `async`-методах и итераторах span нельзя держать через `await`/`yield`: локальные переменные таких методов переезжают в state machine в куче. С C# 13 локальные ref struct в `async`-методе разрешены, если их использование не пересекает `await`. Там же появилось анти-ограничение `where T : allows ref struct`, позволяющее generic-коду принимать span как аргумент типа.

**Как обойти:**

- **`Memory<T>` / `ReadOnlyMemory<T>`** — обычная структура (объект + индекс + длина), её можно хранить в поле, передавать через `await`. Span получают в момент работы:

  ```csharp
  class Parser
  {
      private readonly ReadOnlyMemory<byte> _data;
      public Parser(ReadOnlyMemory<byte> data) => _data = data;

      public int CountLines()
      {
          ReadOnlySpan<byte> span = _data.Span;   // span живёт только в этом методе
          return span.Count((byte)'\n');
      }
  }
  ```

- **Массив + смещение + длина** (или `ArraySegment<T>`) — самый дешёвый вариант, если данные всегда в массиве.
- **Ref struct вместо класса.** С C# 11 ref struct может содержать поля `Span<T>` и `ref`-поля. Так устроены `Utf8JsonReader`, `SpanReader`-подобные парсеры: вся обёртка живёт на стеке.

  ```csharp
  ref struct Tokenizer
  {
      private ReadOnlySpan<char> _rest;
      public Tokenizer(ReadOnlySpan<char> text) => _rest = text;
      public bool TryNext(out ReadOnlySpan<char> token) { /* ... */ }
  }
  ```

- **Индексы вместо срезов.** Хранить в классе не `Span`, а `Range`/`(start, length)` и нарезать исходный массив при каждом использовании.

**Цена обхода.** `Memory<T>.Span` — не бесплатное свойство: проверка, что внутри (массив, строка или `MemoryManager<T>`), и создание span'а. Его получают один раз в начале синхронного участка, а не в каждой итерации цикла.

**Что спрашивают дальше:** чем `Memory<T>` отличается от `Span<T>` по устройству, что такое `scoped` и escape rules для ref struct, почему `Utf8JsonReader` — ref struct и как с ним работать в async-коде.

## Когда Memory<T> оправдан вместо Span<T>, и какова цена этого перехода?

```yaml
category: clr-gc
level: senior
difficulty: 4
slug: advanced-csharp-kogda-memory-t-opravdan-vmesto-span-t-i-kakova-cena-etogo-perehoda
tags: span, async
```

`Memory<T>` нужен там, где кусок памяти должен пережить текущий синхронный вызов: пересечь `await`, лечь в поле, уйти в очередь или другой поток. Для всего остального — `Span<T>`. Цена перехода: чуть более тяжёлая структура, косвенность при каждом получении `.Span`, отсутствие поддержки стековой памяти и, главное, вопрос владения — кто и когда вернёт буфер.

**Устройство и отличие:**

| | `Span<T>` | `Memory<T>` |
| --- | --- | --- |
| Тип | `ref struct` | обычная `readonly struct` |
| Внутри | `ref T` + длина | `object` (массив / строка / `MemoryManager<T>`) + индекс + длина |
| Где живёт | только стек | где угодно: поле, куча, state machine |
| `await`, лямбды, generic | нет | да |
| `stackalloc`, native-указатель | да | native — только через `MemoryManager<T>`, стек — нет |
| Доступ к элементам | напрямую | через `.Span` |

**Когда `Memory<T>` оправдан:**

- асинхронный I/O: `Stream.ReadAsync(Memory<byte>)`, `Socket.ReceiveAsync`, `PipeReader` — буфер должен жить, пока операция не завершится;
- хранение среза в поле: парсер, который держит входные данные, кэш сообщений, элемент `Channel<T>`;
- передача владения буфером между компонентами — через `IMemoryOwner<T>`;
- API, которое принимает данные разной природы (массив, строка, pinned native-память) единообразно.

**Правильный паттерн — `Memory` на границах, `Span` внутри:**

```csharp
public async ValueTask<int> ProcessAsync(Stream stream, CancellationToken ct)
{
    byte[] rented = ArrayPool<byte>.Shared.Rent(4096);
    try
    {
        Memory<byte> buffer = rented;
        int read = await stream.ReadAsync(buffer, ct);   // Memory пересекает await
        return Parse(buffer.Span[..read]);               // дальше — синхронный Span
    }
    finally { ArrayPool<byte>.Shared.Return(rented); }
}

static int Parse(ReadOnlySpan<byte> data) { /* горячий цикл по span */ return data.Length; }
```

**Из чего складывается цена:**

- **`.Span` не бесплатен.** Он проверяет, что лежит внутри (массив, строка или `MemoryManager<T>`), и валидирует границы. В цикле `memory.Span[i]` это делается на каждой итерации — span нужно взять один раз.
- **Размер.** `Memory<T>` на x64 — 16 байт (ссылка + два `int`), копируется при передаче по значению; мелочь, но в структурах данных с миллионами элементов заметно.
- **Нет стековых буферов.** Всё, что уходит в `Memory<T>`, живёт в куче или в native-памяти — `stackalloc` не подходит.
- **Владение и use-after-free.** `Span` живёт не дольше метода, и ошибиться со временем жизни почти невозможно. `Memory<T>` над арендованным массивом можно сохранить и прочитать после `Return` — данные уже принадлежат другому запросу. Компилятор тут не помогает.

```csharp
IMemoryOwner<byte> owner = MemoryPool<byte>.Shared.Rent(1024);
_pending.Enqueue(owner.Memory);   // сохранили Memory
owner.Dispose();                  // вернули в пул — _pending теперь указывает на чужой буфер
```

Правило: кто держит `IMemoryOwner<T>`, тот и отвечает за `Dispose`; передавать дальше лучше владельца, а не голый `Memory<T>`.

- **Pinning.** Для передачи в native-код `Memory<T>.Pin()` возвращает `MemoryHandle`, который надо освободить; забытый handle держит массив закреплённым.

**Когда не нужен:** синхронный парсинг, форматирование, работа с буфером внутри одного метода — там `Memory<T>` только добавляет косвенность. Переписывать `Span`-API на `Memory` «на всякий случай» не стоит: сигнатура с `Span` принимает больше источников (включая стек) и быстрее.

**Что спрашивают дальше:** что такое `MemoryManager<T>` и когда его писать, как устроен `ReadOnlySequence<T>` в `System.IO.Pipelines`, почему `IMemoryOwner<T>` лучше, чем передавать массив из пула напрямую.

## Как устроен ArrayPool<T> и какие ошибки при его использовании приводят к утечкам?

```yaml
category: clr-gc
level: senior
difficulty: 4
slug: advanced-csharp-kak-ustroen-arraypool-t-i-kakie-oshibki-pri-ego-ispolzovanii-privodyat
tags: allocations, memory
```

`ArrayPool<T>` — пул переиспользуемых массивов: `Rent(n)` выдаёт массив длиной **не меньше** `n`, `Return` кладёт его обратно. `ArrayPool<T>.Shared` раскладывает массивы по корзинам размеров-степеней двойки и хранит их в потоковом кэше и в стеках на каждое ядро, поэтому аренда почти не конкурирует за блокировки. Утечки и порча данных возникают от нарушения контракта: не вернули, вернули дважды, пользуются после возврата, держат аренду слишком долго.

**Устройство `Shared`:**

- **Корзины по размеру:** 16, 32, 64, … до 2³⁰ элементов. `Rent(100)` вернёт массив длиной 128. Запрос больше максимума просто создаёт новый массив, а при `Return` он отбрасывается.
- **Двухуровневое хранение:** сначала слот в thread-local кэше текущего потока (по одному массиву на корзину), затем небольшие стеки под блокировкой для каждого ядра, затем — попытка взять у соседних ядер. Если везде пусто, выделяется новый массив.
- **Самоочистка.** Пул подписан на Gen 2 GC и при сборках выбрасывает массивы, которые давно не использовались, — агрессивнее при высокой нагрузке на память.
- **Нет отслеживания.** Пул не знает, сколько массивов выдал. Невозвращённый массив — просто объект, который соберёт GC.

`ArrayPool<T>.Create(maxArrayLength, maxArraysPerBucket)` создаёт отдельный пул с фиксированными лимитами и блокировками — имеет смысл для изоляции подсистемы, но обычно достаточно `Shared`.

**Правильное использование:**

```csharp
byte[] buffer = ArrayPool<byte>.Shared.Rent(size);
try
{
    Span<byte> data = buffer.AsSpan(0, size);   // работать только с запрошенной длиной
    Fill(data);
    Send(data);
}
finally
{
    ArrayPool<byte>.Shared.Return(buffer);       // ровно один раз
}
```

**Ошибки и к чему они приводят:**

| Ошибка | Последствие |
| --- | --- |
| Не вызвали `Return` (исключение без `finally`, ранний `return`) | утечки в строгом смысле нет, но пул не работает: каждый `Rent` — новая аллокация, большие буферы уходят в LOH |
| Двойной `Return` | один массив попадает в пул дважды, два потребителя получают его одновременно — данные одного запроса перемешиваются с другим |
| Использование после `Return` (массив сохранили в поле, в замыкании, в `Memory<T>`, в незавершённой async-операции) | чтение и запись в буфер, который уже выдан кому-то другому, — тихая порча данных |
| Работа с `buffer.Length` вместо запрошенного `size` | обработка «хвоста» с чужими данными; утечка содержимого наружу (в ответ, в файл) |
| Возврат массива, который не из пула | `Shared` бросит `ArgumentException`, если длина не совпадает с размером корзины |
| Секреты в буфере без очистки | следующий арендатор видит пароль или токен: по умолчанию `Return` не обнуляет массив |
| Аренда огромных буферов и долгое удержание | пул держит мегабайтные массивы в потоковых кэшах, память процесса не падает после пика — выглядит как утечка |

Для секретов — `Return(buffer, clearArray: true)` или `CryptographicOperations.ZeroMemory`.

**Почему «похоже на утечку», хотя её нет.** После пика нагрузки пул хранит арендованные тогда массивы, пока очистка на Gen 2 их не выбросит. Если Gen 2 случаются редко, `gc-heap-size` остаётся высоким. Это нормальное поведение кэша; настоящая утечка — когда кто-то держит ссылки на объекты, в которых лежат арендованные массивы.

**Как защититься от use-after-free:**

- возвращать буфер в том же методе, который его арендовал, в `finally`;
- при передаче владения — `IMemoryOwner<T>` (`MemoryPool<T>.Shared`) и явный `Dispose` у последнего владельца;
- после `Return` обнулять локальную ссылку, если метод длинный;
- не возвращать буфер, пока не завершилась `async`-операция, которая в него пишет.

**Что спрашивают дальше:** чем `ArrayPool` отличается от `ObjectPool<T>` и `RecyclableMemoryStream`, почему пул массивов снижает давление на LOH, как пул ведёт себя в Server GC с большим числом ядер.

## Что такое stackalloc и как не получить переполнение стека при его использовании?

```yaml
category: clr-gc
level: senior
difficulty: 4
slug: advanced-csharp-chto-takoe-stackalloc-i-kak-ne-poluchit-perepolnenie-steka-pri-ego-isp
tags: span, memory
```

`stackalloc` выделяет блок памяти прямо в кадре стека текущего метода: без кучи и GC, освобождается автоматически при выходе из метода. Переполнения избегают тремя правилами: размер маленький и ограничен константой, никогда не зависит напрямую от внешнего ввода, и `stackalloc` не вызывается в цикле. Для всего крупнее порога — fallback на `ArrayPool<T>`.

**Современная форма — без `unsafe`:**

```csharp
Span<byte> buffer = stackalloc byte[128];   // безопасно: Span с проверкой границ
byte* p = stackalloc byte[128];             // старая форма: указатель, нужен unsafe
```

**Почему переполнение так опасно.** Стек потока маленький: на Windows по умолчанию 1 МБ, на Linux размер зависит от настроек (у потоков, созданных рантаймом, обычно порядка 1,5 МБ). `StackOverflowException` в .NET нельзя перехватить: процесс просто завершается, без `catch`, без `finally`, часто без внятного лога. Для сервиса это падение всего pod'а из-за одного запроса.

**Главные ошибки:**

```csharp
// 1. Размер от пользователя — готовый DoS
Span<char> buf = stackalloc char[request.Name.Length];

// 2. stackalloc в цикле — память не освобождается до выхода из метода
for (int i = 0; i < items.Count; i++)
{
    Span<byte> tmp = stackalloc byte[256];   // 256 × items.Count байт на стеке
}

// 3. Большой буфер «потому что быстро»
Span<byte> big = stackalloc byte[512 * 1024]; // половина стека одним махом
```

Вторую ошибку компилятор не ловит, анализаторы (CA2014) — ловят: `stackalloc` нужно выносить из цикла.

Отдельно — рекурсия и глубокие стеки вызовов: 1 КБ `stackalloc` в методе, который вызывается рекурсивно на глубину тысячи, — уже мегабайт.

**Правильный паттерн — порог + пул:**

```csharp
const int StackLimit = 256;

byte[]? rented = null;
Span<byte> buffer = length <= StackLimit
    ? stackalloc byte[StackLimit]                                   // константный размер
    : (rented = ArrayPool<byte>.Shared.Rent(length));
try
{
    buffer = buffer[..length];
    Process(buffer);
}
finally
{
    if (rented is not null) ArrayPool<byte>.Shared.Return(rented);
}
```

Выделение константы, а не `length`, — частый приём: JIT генерирует более простой код для фиксированного размера, а пик использования стека известен заранее.

**Какой порог.** Типичные значения в BCL и библиотеках — от 256 байт до 1 КБ. Больше пары килобайт — повод задуматься: выигрыш по сравнению с пулом уже мал, а риск растёт, особенно в коде, который может оказаться глубоко в стеке вызовов (middleware, рекурсивный парсер, колбэк).

**Про обнуление.** По умолчанию память `stackalloc` обнуляется (флаг `localsinit`). Атрибут `[SkipLocalsInit]` (требует `AllowUnsafeBlocks`) убирает обнуление — ощутимо для больших буферов, но тогда в буфере мусор из прошлых кадров, и читать его до записи нельзя.

**Если глубина стека заранее неизвестна** — `RuntimeHelpers.TryEnsureSufficientExecutionStack()` проверяет, что до конца стека осталось достаточно места, и позволяет уйти в безопасную ветку вместо падения.

**Что спрашивают дальше:** почему `Span<T>` из `stackalloc` нельзя вернуть из метода (escape rules), чем `stackalloc` отличается от `InlineArray` и fixed-size буферов в структурах, почему нельзя использовать `stackalloc` в `async`-методе через `await`.

## Когда unsafe-код действительно оправдан и какие гарантии рантайма он снимает?

```yaml
category: clr-gc
level: senior
difficulty: 5
slug: advanced-csharp-kogda-unsafe-kod-deistvitelno-opravdan-i-kakie-garantii-rantaima-on-sn
tags: unsafe, memory
```

`unsafe` оправдан в двух случаях: interop с native-кодом, где указатели — часть контракта, и измеренный горячий путь, где безопасные средства (`Span<T>`, `MemoryMarshal`, векторные API) не дают JIT'у сгенерировать нужный код. Он снимает проверку границ, типобезопасность и отслеживание ссылок со стороны GC — ответственность за корректность памяти переходит на разработчика, а ошибки проявляются как порча кучи или падение процесса далеко от места бага.

**Какие гарантии пропадают:**

| Гарантия | В безопасном коде | С указателями |
| --- | --- | --- |
| Проверка границ | `IndexOutOfRangeException` | запись за пределы буфера в соседний объект |
| Типобезопасность | `InvalidCastException` | `*(long*)p` читает что угодно как что угодно |
| Отслеживание GC | ссылки обновляются при уплотнении | сырой указатель GC не видит: объект может переехать или быть собран |
| Время жизни | объект жив, пока на него есть ссылка | указатель на стек или освобождённую память остаётся «валидным» |
| Инициализация | память обнулена | `NativeMemory.Alloc`, `SkipLocalsInit` — мусор |

Важное отличие от C++: GC продолжает работать и двигать объекты. Указатель на managed-объект безопасен только внутри `fixed`, через `GCHandle` pinned или для объектов в POH.

**Как выглядят последствия.** Не исключение в месте ошибки, а:

- `AccessViolationException` — в .NET Core его нельзя перехватить, процесс падает;
- «Fatal error. Internal CLR error» или падение внутри GC на следующей сборке — вы испортили заголовок соседнего объекта, а обнаружилось это через минуту в другом потоке;
- тихо неверные данные.

Поэтому unsafe-баги — одни из самых дорогих в отладке.

**Когда оправдан:**

- **Interop:** вызов native-API, которые принимают указатели на структуры и буферы; работа с памятью, выделенной native-библиотекой; `function pointers` (`delegate* unmanaged<...>`) для колбэков без аллокации делегата.
- **Низкоуровневые библиотеки:** сериализаторы, парсеры, кодеки, сетевые протоколы — после профилирования, когда bounds checks или копирования реально видны в трассе.
- **Работа с native-памятью** больших объёмов вне GC (`NativeMemory.Alloc`), чтобы не нагружать кучу.

**Когда не нужен — почти всегда есть безопасная альтернатива:**

- `Span<T>` + `stackalloc` вместо `byte*` и `stackalloc` с указателем;
- `MemoryMarshal.Cast<TFrom, TTo>`, `MemoryMarshal.Read<T>` вместо приведения указателей;
- `BinaryPrimitives` для чтения чисел с нужным порядком байт;
- `Vector128<T>` / `Vector<T>` для SIMD — работают со span'ами и `ref`;
- `LibraryImport` source generator для P/Invoke вместо ручного маршалинга.

JIT хорошо убирает проверки границ в типичных циклах `for (int i = 0; i < span.Length; i++)`, так что выигрыш от указателей часто оказывается нулевым.

**Серая зона — `Unsafe` и `MemoryMarshal` без ключевого слова.** `Unsafe.Add(ref r, i)`, `Unsafe.As<T>`, `MemoryMarshal.GetArrayDataReference` не требуют `AllowUnsafeBlocks`, но так же отключают проверки. Плюс по сравнению с указателями: `ref` отслеживается GC, pinning не нужен. Минус: ошибки те же — выход за границы и нарушение типов.

**Как ограничить ущерб:**

- изолировать unsafe в маленьком, хорошо протестированном типе с безопасным API наружу;
- проверять аргументы на входе (длины, выравнивание) до входа в unsafe-участок;
- гонять тесты под нагрузкой с частыми сборками (например, с фоновым потоком, который вызывает `GC.Collect()`) — баги с pinning проявляются только тогда, когда GC действительно двигает объекты;
- писать бенчмарк рядом: если unsafe-версия не быстрее безопасной, её удаляют.

**Что спрашивают дальше:** что делает `fixed` и почему без него указатель опасен, зачем `GC.KeepAlive`, чем `ref`-указатель отличается от `T*` для GC, почему `AccessViolationException` не перехватывается.

## Что делает GC.KeepAlive и fixed, и почему без них unsafe-код может читать перемещённую память?

```yaml
category: clr-gc
level: senior
difficulty: 5
slug: advanced-csharp-chto-delaet-gc-keepalive-i-fixed-i-pochemu-bez-nih-unsafe-kod-mozhet-c
tags: unsafe, memory
```

Они решают две разные проблемы. `fixed` закрепляет объект на время блока, чтобы GC не **переместил** его при уплотнении, и даёт на него указатель. `GC.KeepAlive(obj)` ничего не закрепляет — он лишь продлевает **жизнь** объекта до этой точки, чтобы GC не собрал его (и не запустил финализатор), пока native-код ещё работает с его ресурсом. Сырой указатель GC не отслеживает, поэтому без этих средств объект может переехать или умереть посреди операции.

### fixed — защита от перемещения

Уплотняющий GC сдвигает живые объекты и обновляет все managed-ссылки. Сырой `byte*` к ним не относится: после сдвига он указывает туда, где объекта уже нет, — на свободное место или в соседний объект.

```csharp
unsafe void Hash(byte[] data)
{
    fixed (byte* p = data)          // data закреплён до конца блока
    {
        NativeHash(p, data.Length); // GC может случиться в любой момент — массив не сдвинется
    }
    // здесь закрепление снято, p использовать нельзя
}
```

`fixed` работает с массивами, строками, полями объектов и любым типом с `GetPinnableReference()` — включая `Span<T>`. Реализация дешёвая: локальная переменная помечается как pinned в GC info, и GC учитывает это только если сборка случилась внутри блока.

**Как обойти `fixed` и выстрелить себе в ногу:**

```csharp
byte* p = (byte*)Unsafe.AsPointer(ref MemoryMarshal.GetArrayDataReference(data));
Thread.Sleep(10);           // в это время случился GC с уплотнением
*p = 42;                    // запись в чужую память
```

Или вынести указатель из блока `fixed` в поле и использовать позже. Компилятор в обоих случаях не возражает. Правило: указатель на managed-объект живёт не дольше закрепления. Для долгих операций — `GCHandle.Alloc(obj, GCHandleType.Pinned)` или буфер в POH.

### GC.KeepAlive — защита от преждевременной сборки

В оптимизированном коде JIT сообщает GC, что локальная переменная (включая `this`) жива только до **последнего использования**, а не до конца метода. Если после извлечения native-хэндла объект больше не нужен managed-коду, он может быть собран прямо во время native-вызова.

```csharp
class NativeImage
{
    private IntPtr _handle = CreateImage();
    ~NativeImage() => DestroyImage(_handle);

    public void Blur()
    {
        BlurNative(_handle);   // после чтения _handle `this` больше не используется;
                               // GC может собрать объект, финализатор вызовет DestroyImage,
                               // пока BlurNative ещё работает с этим хэндлом
        GC.KeepAlive(this);    // держит `this` живым до этой строки
    }
}
```

`GC.KeepAlive` — пустой метод с `NoInlining`, смысл которого только в том, что JIT обязан считать аргумент живым до вызова. Ставить его нужно **после** последней операции, которая зависит от объекта.

Баг почти не воспроизводится в Debug (там переменные живут до конца метода) и под отладчиком, и проявляется в проде под нагрузкой — классический «раз в неделю падает».

**Правильное решение вместо KeepAlive — `SafeHandle`.** Маршалер P/Invoke увеличивает счётчик ссылок `SafeHandle` на время вызова и уменьшает после, поэтому хэндл не освободится посреди native-операции, даже если владелец стал недостижим. Плюс критическая финализация и защита от повторного освобождения.

```csharp
[LibraryImport("imaging")]
private static partial void BlurNative(ImageSafeHandle handle);
```

### Чем они не являются

| | `fixed` / pinned | `GC.KeepAlive` |
| --- | --- | --- |
| Не даёт переместить | да | **нет** |
| Не даёт собрать | да, на время блока (закреплённая локальная — корень) | да, до точки вызова |
| Где нужен | указатель на managed-память | объект с финализатором и native-ресурсом, `WeakReference`-сценарии |

**Что спрашивают дальше:** почему в Debug баг не воспроизводится, чем `SafeHandle` лучше `IntPtr`, что такое POH и `GC.AllocateArray(pinned: true)`, как P/Invoke закрепляет массивы автоматически.

## Чем Workstation GC отличается от Server GC под реальной нагрузкой и как выбрать режим?

```yaml
category: clr-gc
level: senior
difficulty: 4
slug: advanced-csharp-chem-workstation-gc-otlichaetsya-ot-server-gc-pod-realnoi-nagruzkoi-i
tags: gc, performance
```

Под нагрузкой Server GC собирает реже и быстрее за счёт параллельной работы нескольких потоков GC и больших бюджетов Gen 0, поэтому даёт выше throughput и обычно ниже частоту пауз. Платит за это памятью (в разы больше, чем Workstation) и всплесками CPU на все ядра во время сборки. Workstation экономен по памяти и CPU, но на многоядерной машине с высокой скоростью аллокаций начинает чаще собирать и проседает по throughput. Выбирают замером трёх величин под реалистичной нагрузкой: RPS, p99 latency и RSS.

**Что реально меняется:**

| Аспект | Workstation | Server |
| --- | --- | --- |
| Частота Gen 0 | высокая: бюджет маленький | низкая: бюджет на каждую кучу, зависит от размера кэша CPU |
| Кто выполняет сборку | поток, на котором кончился бюджет | N выделенных потоков, по одному на кучу |
| Аллокации из разных потоков | в одну кучу | каждый поток преимущественно в «свою» кучу, меньше конкуренции |
| Пауза одной сборки | зависит от объёма живых объектов, работает одним потоком | тот же объём делится между потоками |
| Память процесса | минимальная | больше: у каждой кучи свой Gen 0 и свой запас |
| CPU во время GC | одно ядро | все ядра, отданные под кучи |

**Где Server GC вредит:**

- **Много процессов на одной машине.** Десять сервисов с Server GC на 16-ядерной ноде — это 160 куч и 160 потоков GC, которые одновременно конкурируют за CPU и память.
- **Маленький лимит памяти.** Большие бюджеты Gen 0 плохо сочетаются с pod'ом на 256–512 МБ.
- **Приложения с низкой нагрузкой.** Сервис, обрабатывающий пару запросов в секунду, держит память под 16 куч без всякой пользы.
- **Контейнер с лимитом CPU.** Параллельная сборка съедает квоту CFS, и потоки приложения ждут следующего периода.

**DATAS меняет картину (.NET 9+).** С включённым по умолчанию DATAS Server GC стартует с одной кучи и добавляет их, только когда видит, что сборки занимают заметную долю времени. Память при небольшой нагрузке близка к Workstation, при высокой — растёт вместе с числом куч. Цена — немного ниже пиковый throughput и период адаптации при резком росте нагрузки. Для сервиса, который всегда под максимальной нагрузкой и не ограничен по памяти, имеет смысл сравнить с `GarbageCollectionAdaptationMode=0`.

**Промежуточные настройки:**

```xml
<PropertyGroup>
  <ServerGarbageCollection>true</ServerGarbageCollection>
  <GarbageCollectionAdaptationMode>1</GarbageCollectionAdaptationMode> <!-- DATAS явно -->
</PropertyGroup>
```

```json
// runtimeconfig.template.json
{
  "configProperties": {
    "System.GC.HeapCount": 4,          // ограничить число куч без DATAS
    "System.GC.NoAffinitize": true,    // не привязывать потоки GC к ядрам
    "System.GC.ConserveMemory": 5      // 0–9: чаще уплотнять ради меньшей памяти
  }
}
```

`GCHeapCount` полезен, когда на машине несколько процессов: 4 кучи вместо 32 дают большую часть выгоды Server GC с меньшей памятью. `NoAffinitize` — когда потоки GC конкурируют с другими процессами за одни и те же ядра.

**Как выбирать на практике:**

1. Нагрузочный тест с реалистичным профилем запросов, а не микробенчмарк.
2. Сравнить конфигурации: Workstation, Server + DATAS, Server без DATAS, Server с ограниченным `HeapCount`.
3. Смотреть не только средний RPS, но и p99/p999, `time-in-gc`, частоту Gen 2, RSS, CPU throttling в контейнере.
4. Проверять `GC.GetGCMemoryInfo().PauseDurations` и события GC в трассе: где паузы длиннее — в Gen 0/1 или в blocking Gen 2.

**Ориентиры по умолчанию:** API с высоким RPS на выделенных ядрах — Server (+ DATAS на .NET 9+). Воркеры с низкой нагрузкой, много сервисов на ноде, маленькие pod'ы — Workstation или Server с `HeapCount` 1–4. Desktop и CLI — Workstation.

**Что спрашивают дальше:** почему бюджет Gen 0 у Server GC больше, как DATAS решает, сколько куч держать, что происходит с Server GC при лимите CPU в Kubernetes.

## Что такое Background GC и почему пауза Gen 2 всё равно может быть заметной?

```yaml
category: clr-gc
level: senior
difficulty: 5
slug: advanced-csharp-chto-takoe-background-gc-i-pochemu-pauza-gen-2-vse-ravno-mozhet-byt-za
tags: gc, performance
```

Background GC — режим, в котором полная сборка (Gen 2) выполняется отдельным потоком параллельно с работой приложения: пометка живых объектов и sweep идут, пока потоки приложения продолжают выполняться и аллоцировать. Паузы всё равно есть: BGC останавливает потоки в начале и в конце, во время него проходят обычные блокирующие Gen 0/1, а при фрагментации или нехватке памяти GC вообще выбирает блокирующую уплотняющую Gen 2 вместо фоновой.

**Как устроен цикл BGC:**

1. **Начальная пауза.** Потоки приостанавливаются, GC фиксирует корни и запускает фоновую пометку.
2. **Конкурентная пометка.** Приложение работает; изменения ссылок отслеживаются через write watch (какие страницы памяти были записаны).
3. **Финальная пауза.** Снова остановка: повторно просматриваются изменённые за время пометки участки, чтобы ничего не потерять.
4. **Конкурентный sweep.** Мёртвые объекты превращаются в free list. Уплотнения нет.

Пока идёт BGC, потоки приложения могут вызывать **foreground GC** — обычные эфемерные сборки Gen 0/1. Они блокирующие, как всегда.

**Почему пауза всё равно заметна:**

- **Время остановки потоков (time to suspend).** Чтобы начать любую паузу, рантайм ждёт, пока все потоки дойдут до safe point. Поток в долгом цикле без вызовов или в native-коде особого режима задерживает всех. В трассе это разница между `GCSuspendEEBegin` и `GCSuspendEEEnd` — иногда она длиннее самой сборки.
- **Финальная пауза пропорциональна изменениям.** Если приложение активно переписывает ссылки в старых объектах (большие кэши, словари), к концу пометки «грязных» страниц много, и их повторный просмотр занимает время.
- **Блокирующая Gen 2 вместо фоновой.** GC переходит на неё, когда фоновая не справляется: фрагментация Gen 2 высокая и нужно уплотнение (BGC не уплотняет), высокая нагрузка на память, приближение к `GCHeapHardLimit`, аллокации обгоняют фоновую пометку. Такая сборка останавливает всё на время обхода всей кучи.
- **Эфемерные сборки на большом Gen 1.** Foreground GC во время BGC и сами по себе Gen 1 с большим количеством выживших — это копирование и обновление ссылок.
- **Торможение аллокаций LOH.** Во время BGC выделение больших объектов может замедляться: GC регулирует его, чтобы не отставать.
- **Конкуренция за CPU.** Даже без пауз фоновый поток GC съедает ядро. В контейнере с малым лимитом CPU это прямое замедление обработки запросов и CFS throttling.
- **Большое количество корней.** Тысячи потоков с глубокими стеками, миллионы GC handles — сканирование корней во время пауз занимает время.

**Как понять, какая пауза и откуда:**

```csharp
var bg   = GC.GetGCMemoryInfo(GCKind.Background);
var full = GC.GetGCMemoryInfo(GCKind.FullBlocking);

Console.WriteLine($"BGC #{bg.Index}: паузы {string.Join(", ", bg.PauseDurations.ToArray())}");
Console.WriteLine($"Blocking Gen2 #{full.Index}: пауза {full.PauseDurations[0]}, compacted={full.Compacted}");
Console.WriteLine($"Pause time %: {full.PauseTimePercentage}");
```

Подробно — `dotnet-trace collect --profile gc-verbose` и отчёт GCStats в PerfView: для каждой сборки видны тип (`Background`, `Blocking`, `Foreground`), причина, длительность паузы и время приостановки потоков.

**Что можно сделать:**

- Уменьшить долю объектов, доживающих до Gen 2, — меньше работы и для BGC, и для блокирующих сборок.
- Снизить фрагментацию (пулы, меньше pinning) — тогда GC реже вынужден уплотнять блокирующе.
- Убрать долгие циклы без safe points в горячих местах (обычно JIT вставляет GC poll, но бывают исключения с native-кодом).
- `GCSettings.LatencyMode = GCLatencyMode.SustainedLowLatency` на время чувствительной фазы — GC избегает блокирующих Gen 2, пока это возможно.
- Для коротких критичных участков — `GC.TryStartNoGCRegion`.
- Проверить, не отключён ли concurrent GC (`<ConcurrentGarbageCollection>false`) — тогда все Gen 2 блокирующие.

**Что спрашивают дальше:** почему BGC не уплотняет, чем foreground GC отличается от background, что такое safe point и GC poll, как `SustainedLowLatency` меняет поведение GC.

## Как влияет ServerGarbageCollection и ConcurrentGC на latency в контейнере с лимитом CPU?

```yaml
category: clr-gc
level: senior
difficulty: 5
slug: advanced-csharp-kak-vliyaet-servergarbagecollection-i-concurrentgc-na-latency-v-kontei
tags: gc, devops
```

Рантайм видит лимит CPU контейнера и по нему считает `Environment.ProcessorCount`, а Server GC создаёт по куче и потоку GC на каждый такой процессор. При жёстком лимите параллельная сборка быстро выедает квоту CFS, и контейнер «замораживается» до следующего периода планировщика — p99 растёт на десятки миллисекунд, хотя сама пауза GC короткая. Concurrent (background) GC добавляет ещё один фоновый поток, который тоже тратит ту же квоту. Поэтому в контейнерах с малым лимитом CPU Server GC часто хуже Workstation или требует ограничения числа куч.

**Как рантайм видит CPU:**

- `resources.limits.cpu: 2` → cgroup-квота 200 мс на период 100 мс → `Environment.ProcessorCount == 2` → Server GC создаёт 2 кучи.
- Дробный лимит округляется вверх: `1.5` → 2.
- **Без лимита** (только `requests`) рантайм видит все ядра ноды: на 64-ядерной ноде Server GC заведёт 64 кучи (или DATAS начнёт с одной и будет расти), хотя по `requests` pod рассчитан на 1–2 ядра.
- Переопределить вручную — `DOTNET_PROCESSOR_COUNT`, либо ограничить только GC через `GCHeapCount`.

**Что происходит при throttling:**

```text
limit: 1.5 → квота 150 мс CPU на период 100 мс, ProcessorCount = 2 → 2 кучи

 0–50 мс   запросы на 2 ядрах          100 мс квоты
50–75 мс   GC: 2 потока × 25 мс         50 мс квоты  → квота исчерпана на 75 мс
75–100 мс  все потоки процесса ждут следующего периода
```

Сама пауза GC — 25 мс, но запрос, пришедший на 75-й миллисекунде, ждёт ещё 25 мс просто потому, что квота кончилась. Чем больше потоков GC одновременно жгут CPU относительно квоты, тем резче этот эффект. В метриках это `container_cpu_cfs_throttled_periods_total` / `throttled_seconds` в cAdvisor. Средняя загрузка CPU при этом может выглядеть умеренной.

**Роль каждой настройки:**

| Настройка | Влияние на latency в контейнере |
| --- | --- |
| Server GC | меньше сборок и короче паузы при достаточном CPU; при малом лимите — всплески потребления квоты, больше памяти |
| Workstation GC | одна куча, сборка на потоке приложения; пауз больше, но они дешевле по CPU и памяти |
| Concurrent GC включён | Gen 2 почти без пауз, но фоновый поток конкурирует с запросами за ту же квоту |
| Concurrent GC выключен | все Gen 2 блокирующие; экономит поток и немного памяти, приемлемо для маленьких воркеров без требований к latency |
| DATAS (.NET 9+) | число куч подстраивается под нагрузку, в недогруженном pod'е Server GC ведёт себя почти как Workstation по памяти |

**Практические рекомендации:**

- **Лимит 1 CPU и меньше** — Workstation GC, concurrent оставить включённым, если важна latency. При `ProcessorCount == 1` Server GC и так недоступен.
- **2–4 CPU** — сравнить Workstation и Server + DATAS нагрузочным тестом, глядя на p99 и throttling, а не только на RPS.
- **Много CPU на pod'е, высокий RPS** — Server GC.
- **Нет CPU-лимита** — обязательно `GCHeapCount` или `DOTNET_PROCESSOR_COUNT`, иначе число куч определяется размером ноды, а не pod'а.
- `GCNoAffinitize=true`, если потоки GC привязаны к ядрам, которые делят несколько контейнеров: привязка по умолчанию рассчитана на выделенную машину.

```yaml
# фрагмент Deployment
env:
  - name: DOTNET_gcServer
    value: "1"
  - name: DOTNET_GCHeapCount
    value: "2"          # число в hex; 2 == 0x2
resources:
  limits:
    cpu: "2"
    memory: "1Gi"
```

Числовые значения в переменных `DOTNET_GC*` рантайм читает как шестнадцатеричные: `DOTNET_GCHeapCount=10` — это 16 куч. Классическая ошибка.

**Проверить, что получилось:** `GCSettings.IsServerGC`, `Environment.ProcessorCount` и `GC.GetGCMemoryInfo().TotalAvailableMemoryBytes` в логе старта; события GC в `dotnet-trace` показывают число куч.

**Что спрашивают дальше:** почему `requests` без `limits` опасен для .NET, что такое CFS throttling и как его увидеть, как DATAS решает, сколько куч держать.

## Почему LOH фрагментируется и как с этим бороться без ручного GC.Collect?

```yaml
category: clr-gc
level: senior
difficulty: 5
slug: advanced-csharp-pochemu-loh-fragmentiruetsya-i-kak-s-etim-borotsya-bez-ruchnogo-gc-col
tags: gc, memory
```

LOH по умолчанию не уплотняется: после сборки мёртвые большие объекты превращаются в свободные блоки free list, а живые остаются на местах. Новые объекты разного размера не всегда влезают в эти дыры, и куча растёт, хотя суммарно свободно много. Бороться нужно в первую очередь изменением паттерна аллокаций — пулы, одинаковые размеры, стриминг, — а уплотнение LOH можно разрешить конфигурацией GC, без ручных вызовов `GC.Collect`.

**Почему именно LOH:**

- **Нет compaction по умолчанию.** Копировать мегабайтные объекты дорого, поэтому GC ограничивается sweep'ом.
- **Разнообразие размеров.** Ответ на 120 КБ, буфер на 1 МБ, `List<T>` на 300 КБ после удвоения — дыра от освободившегося 1 МБ занимается 300 КБ объектом, остаток 700 КБ ждёт объект подходящего размера.
- **Разные времена жизни.** Долгоживущий кэш-массив посреди короткоживущих буферов делит свободное пространство на куски, которые не сливаются.
- **Собирается только в Gen 2.** Мёртвые буферы долго занимают место, пока не случится полная сборка, а новые аллокации в это время идут в конец кучи.
- **Pinning.** Большие закреплённые буферы (I/O, interop) не сдвинет даже уплотнение.

**Как увидеть:**

```csharp
var info = GC.GetGCMemoryInfo();
var loh  = info.GenerationInfo[3];            // 0–2 SOH, 3 LOH, 4 POH
double frag = (double)loh.FragmentationAfterBytes / loh.SizeAfterBytes;
Console.WriteLine($"LOH: {loh.SizeAfterBytes >> 20} MB, fragmentation {frag:P0}");
```

В `dotnet-dump` — `eeheap -gc` и `dumpheap -stat` с крупными блоками `Free` в LOH; в трассе PerfView GCStats показывает фрагментацию по поколениям после каждой сборки.

**1. Не создавать проблему — главное средство:**

- **`ArrayPool<T>.Shared`** — размеры округляются до степени двойки, и один и тот же массив переиспользуется: новых больших объектов почти не появляется.
- **`RecyclableMemoryStream`** (Microsoft.IO) вместо `MemoryStream`: данные хранятся в пуле блоков фиксированного размера меньше порога LOH, а не в одном растущем массиве.
- **Стриминг** — `System.Text.Json` с `Stream`, `PipeReader`, `CopyToAsync`, чтение файлов кусками, вместо `ReadAllBytes` и `ReadAsStringAsync`.
- **Chunking** — большие коллекции как список сегментов меньше 85 000 байт.
- **Capacity заранее** у `List<T>`, `StringBuilder`, `MemoryStream` — без промежуточных копий при удвоении.
- **Долгоживущие большие буферы** выделить один раз при старте, закреплённые — в POH (`GC.AllocateArray<T>(n, pinned: true)`).

**2. Разрешить GC уплотнять LOH — без ручного Collect:**

- **`GCSettings.LargeObjectHeapCompactionMode = CompactOnce`** — флаг применяется на следующей **естественной** блокирующей Gen 2 сборке, вызывать `GC.Collect` для этого не обязательно. Удобно выставлять периодически или по метрике фрагментации.
- **`GCConserveMemory` (0–9)** — GC начинает учитывать фрагментацию и при её превышении уплотняет LOH сам; больше значение — агрессивнее, ценой более частых и длинных сборок.

  ```xml
  <ItemGroup>
    <RuntimeHostConfigurationOption Include="System.GC.ConserveMemory" Value="5" />
  </ItemGroup>
  ```

- **`GCHeapHardLimit`** — при заданном жёстком лимите кучи (а в контейнере с memory limit он задан по умолчанию) GC рассматривает уплотнение LOH, когда упирается в лимит.

**3. Сдвинуть порог:** `GCLOHThreshold` (`System.GC.LOHThreshold`) поднимает границу LOH. Объекты среднего размера уходят в SOH, где уплотняются. Цена — их копирование при сборках и больший Gen 0/1; помогает, если основная масса «больших» объектов — 85–200 КБ.

**4. Регионы (.NET 7+)** смягчают последствия: LOH состоит из регионов, и полностью освободившийся регион возвращается в общий пул и может быть отдан ОС. Фрагментация внутри частично занятых регионов остаётся.

**Почему не `GC.Collect()` по таймеру:** полная блокирующая сборка с уплотнением LOH — одна из самых длинных пауз, а без изменения паттерна аллокаций фрагментация вернётся за минуты.

**Что спрашивают дальше:** как устроен free list LOH, почему `ArrayPool` решает проблему лучше, чем уплотнение, что такое POH и почему он отделён от LOH, как `GCConserveMemory` влияет на паузы.

## Что такое GC pressure и по каким метрикам вы поймёте, что он стал узким местом?

```yaml
category: clr-gc
level: senior
difficulty: 4
slug: advanced-csharp-chto-takoe-gc-pressure-i-po-kakim-metrikam-vy-poimete-chto-on-stal-uzk
tags: gc, observability
```

GC pressure — нагрузка, которую приложение создаёт на сборщик мусора: скорость аллокаций, объём выживающих объектов и размер кучи, которую приходится обходить. Узким местом он становится, когда время в GC и паузы начинают заметно влиять на CPU и latency. Понять это можно по доле времени в GC, частоте и длительности пауз (особенно Gen 2), скорости аллокаций и их корреляции с p99 запросов.

**Из чего складывается давление:**

- **Скорость аллокаций** — чем больше байт в секунду, тем чаще исчерпывается бюджет Gen 0 и тем чаще сборки.
- **Выживаемость** — дорого не выделение, а объекты, которые переживают сборку: их нужно пометить, скопировать и продвинуть в старшее поколение. Много «средне живущих» объектов (кэш на минуту, буферы долгих запросов) — самый плохой случай: они доживают до Gen 2 и умирают там.
- **Размер Gen 2 и LOH** — полная сборка обходит всю живую кучу, её стоимость растёт с числом объектов и ссылок.
- **Финализация и handles** — объекты с финализаторами проживают минимум одну лишнюю сборку, pinned-handles мешают уплотнению.

**Метрики и пороги-ориентиры:**

| Метрика (`dotnet-counters`) | Метрика OpenTelemetry (.NET 9+) | Когда тревожно |
| --- | --- | --- |
| `time-in-gc` | `dotnet.gc.pause.time` (сумма пауз) | стабильно выше ~5–10% времени |
| `alloc-rate` | `dotnet.gc.heap.total_allocated` (rate) | сотни МБ/с и растёт вместе с RPS непропорционально |
| `gen-0/1/2-gc-count` | `dotnet.gc.collections` с тегом `gc.heap.generation` | счётчик Gen 2 растёт почти так же быстро, как Gen 1: объекты массово доживают до старости |
| `gc-heap-size`, `gc-committed` | `dotnet.gc.last_collection.heap.size`, `...memory.committed_size` | рост после полных сборок, приближение к лимиту контейнера |
| `gc-fragmentation` | `dotnet.gc.last_collection.heap.fragmentation.size` | высокая доля фрагментации — GC уплотняет блокирующе |
| `loh-size` | — | быстрый рост → частые Gen 2 из-за бюджета LOH |
| — | `dotnet.process.cpu.time` | CPU растёт, а полезный RPS — нет |

Пороги — ориентиры, а не правила: 10% времени в GC для batch-процесса может быть нормой, а для API с SLA в 50 мс — нет.

**Главный признак — корреляция.** Сами по себе числа мало что говорят. Проблема подтверждается, когда всплески p99/p999 совпадают по времени с паузами GC, а throughput упирается в CPU, значимая часть которого уходит в потоки GC. На дашборде рядом: latency запросов, `dotnet.gc.pause.time`, `dotnet.gc.collections` по поколениям, CPU и throttling контейнера.

**Точные данные о паузах — из рантайма и трассы:**

```csharp
var info = GC.GetGCMemoryInfo();
Console.WriteLine($"Pause %: {info.PauseTimePercentage:F1}");
Console.WriteLine($"Last GC gen{info.Generation}, pause {info.PauseDurations[0].TotalMilliseconds} ms");
Console.WriteLine($"Promoted: {info.PromotedBytes >> 20} MB");
```

`dotnet-trace collect --profile gc-collect` (или `gc-verbose` со стеками аллокаций) → PerfView GCStats: для каждой сборки поколение, причина (`AllocSmall`, `AllocLarge`, `Induced`, `LowMemory`), длительность паузы, сколько байт продвинуто. `Induced` в списке причин — кто-то вызывает `GC.Collect()`.

**Что делать, когда давление подтверждено:**

1. Трасса аллокаций → убрать топ источников (пулы, `Span`, отказ от LINQ и замыканий в горячем пути).
2. Сократить выживаемость: не держать объекты чуть дольше, чем нужно; кэши — с ограничением размера и без мелких объектов на каждую запись.
3. Разобраться с LOH: пулы для больших буферов, стриминг.
4. Проверить конфигурацию GC: Server vs Workstation, DATAS, concurrent GC, лимиты контейнера.

**Не путать с `GC.AddMemoryPressure`.** Это API, которым сообщают GC, что маленький managed-объект держит много native-памяти (например, bitmap): GC учитывает это и собирает раньше. Если такой объект забывают освобождать, native-память растёт, а GC о ней не знает.

**Что спрашивают дальше:** почему средне живущие объекты хуже всего, как отличить GC pressure от утечки, какие причины сборок бывают и что означает `Induced`.

## Как ограничение памяти в Kubernetes влияет на поведение GC и почему pod получает OOMKilled?

```yaml
category: clr-gc
level: senior
difficulty: 5
slug: advanced-csharp-kak-ogranichenie-pamyati-v-kubernetes-vliyaet-na-povedenie-gc-i-pochem
tags: gc, devops
```

.NET читает memory limit из cgroup и считает его всей доступной памятью: по нему вычисляется нагрузка на память, а жёсткий лимит managed-кучи по умолчанию ставится в 75% от лимита контейнера. GC становится агрессивнее по мере приближения к нему. Но GC управляет только своей кучей, а OOM killer ядра смотрит на всю память cgroup: native-аллокации, стеки потоков, код JIT, page cache и tmpfs. Pod получает OOMKilled, когда сумма всего этого превышает лимит, — чаще всего из-за памяти вне managed-кучи или из-за отсутствия лимита, при котором рантайм ориентируется на память всей ноды.

**Что рантайм делает с лимитом:**

| Что | Значение по умолчанию при заданном memory limit |
| --- | --- |
| `TotalAvailableMemoryBytes` | memory limit контейнера |
| `GCHeapHardLimit` | 75% от лимита (но не меньше 20 МБ) |
| Порог «высокой нагрузки на память» | около 90% (`GCHighMemPercent`) — GC начинает собирать и уплотнять агрессивнее |
| `Environment.ProcessorCount` | по CPU limit — от него зависит число куч Server GC, а значит, и базовый расход памяти |

```csharp
var info = GC.GetGCMemoryInfo();
Console.WriteLine($"Available:  {info.TotalAvailableMemoryBytes >> 20} MB");   // лимит контейнера
Console.WriteLine($"High load:  {info.HighMemoryLoadThresholdBytes >> 20} MB");
Console.WriteLine($"Committed:  {info.TotalCommittedBytes >> 20} MB");
```

**Два разных «out of memory»:**

- **`OutOfMemoryException`** — managed-куча упёрлась в `GCHeapHardLimit`, и даже полная уплотняющая сборка не освободила места. Процесс жив, исключение можно залогировать, это управляемая ситуация.
- **OOMKilled (exit code 137)** — ядро убило процесс, потому что cgroup превысила memory limit. Никаких исключений, `finally`, логов — SIGKILL.

Если pod убивают, а `OutOfMemoryException` в логах нет, значит, managed-куча в свои 75% уложилась, а оставшиеся 25% съело что-то ещё.

**Что лежит за пределами GC-лимита:**

- native-библиотеки: драйверы БД, SkiaSharp/ImageSharp-подобная обработка изображений, gRPC/HTTP-стек с native-зависимостями, ML-рантаймы;
- `Marshal.AllocHGlobal`, `NativeMemory.Alloc`, memory-mapped files;
- стеки потоков: сотни потоков из-за sync-over-async — сотни мегабайт резерва и заметная часть коммита;
- JIT-код, метаданные типов, loader heaps — растут при динамической генерации кода (`Reflection.Emit`, неправильно кэшируемые `XmlSerializer`, `Expression.Compile` в цикле);
- фрагментация native-аллокатора (glibc malloc с множеством arenas);
- `emptyDir` с `medium: Memory` и файлы в `/dev/shm` — это tmpfs, он учитывается в памяти контейнера.

Page cache от чтения и записи файлов тоже учитывается в cgroup, но чистые страницы ядро вытесняет перед тем, как убивать, — обычно это не причина OOMKill, хотя сбивает с толку метрику `container_memory_usage_bytes` (смотрите `working_set`).

**Типичные сценарии OOMKilled:**

1. **Нет `limits.memory`** — рантайм видит память ноды (например, 64 ГБ), heap спокойно растёт до гигабайт, а pod убивает kubelet при давлении на ноду или eviction.
2. **Маленький лимит + много native** — pod на 512 МБ: 384 МБ отдано куче, на всё остальное 128 МБ; библиотека обработки изображений берёт 200 МБ.
3. **Server GC без DATAS на маленьком pod'е** — много куч с большими бюджетами Gen 0, heap быстро доходит до лимита, частые полные сборки и итоговое убийство по native-части.
4. **Всплеск нагрузки** — очереди, буферы ответов и кэши заполняются быстрее, чем GC успевает, плюс native-память растёт вместе с числом соединений.

**Что настраивать:**

```yaml
resources:
  requests: { memory: "1Gi" }
  limits:   { memory: "1Gi" }        # requests = limits: предсказуемый QoS
env:
  - name: DOTNET_GCHeapHardLimitPercent
    value: "0x3C"                    # 60% в hex — оставить больше под native
  - name: DOTNET_GCConserveMemory
    value: "5"                       # компактнее ценой более частых сборок
```

- `GCHeapHardLimit` / `GCHeapHardLimitPercent` — уменьшить долю кучи, если native-часть большая, или увеличить, если её почти нет;
- Workstation GC или Server с DATAS (.NET 9+) для небольших pod'ов;
- `GCConserveMemory` — если процесс держит много фрагментированной памяти;
- метрики `dotnet.gc.last_collection.memory.committed_size` и `dotnet.process.memory.working_set` рядом с лимитом на дашборде: разница между ними — native-часть, которую GC не контролирует.

**Как разбирать инцидент:** сравнить `working_set` и committed-память GC перед падением; если разница растёт — искать native (см. вопрос про 8 ГБ против 1 ГБ heap); если растёт heap — снять `dotnet-gcdump` до достижения лимита и искать удерживаемые объекты.

**Что спрашивают дальше:** почему лимит кучи 75%, а не 100%, чем OOMKilled отличается от eviction, как .NET определяет лимит в cgroup v1 и v2, зачем задавать `requests` равным `limits`.

## Приложение потребляет 8 ГБ, но dotnet-counters показывает heap 1 ГБ. Куда ушла память?

```yaml
category: clr-gc
level: senior
difficulty: 5
slug: advanced-csharp-prilozhenie-potreblyaet-8-gb-no-dotnet-counters-pokazyvaet-heap-1-gb-k
tags: memory, profiling
```

`gc-heap-size` показывает только объём объектов в managed-куче после последней сборки. Всё остальное — это память, которую GC держит закоммиченной про запас, native-аллокации (библиотеки, `Marshal.AllocHGlobal`, аллокатор ОС), стеки потоков, JIT-код и метаданные, memory-mapped файлы. Сначала нужно понять, какие «8 ГБ» имеются в виду (виртуальная память, working set, private bytes), а потом разложить память процесса по категориям и найти ту, что растёт.

**Шаг 0 — какая именно метрика 8 ГБ:**

| Метрика | Что это | Нормально ли, что она огромная |
| --- | --- | --- |
| Virtual size (VSZ, Virtual Bytes) | зарезервированное адресное пространство | да: GC с регионами резервирует большой диапазон (по умолчанию 256 ГБ), это не память |
| Working set / RSS | страницы, реально лежащие в RAM | нет, это то, что считает OOM killer |
| Private bytes / commit | закоммиченная приватная память | нет |

Если 8 ГБ — это виртуальная память, проблемы нет. Дальше речь о RSS/private.

**Шаг 1 — сравнить managed-часть с процессом:**

```bash
dotnet-counters monitor -p <pid> --counters System.Runtime
```

- `gc-heap-size` — живые объекты + фрагментация после последнего GC;
- `gc-committed` — сколько памяти GC закоммитил у ОС; может быть заметно больше heap size;
- `working-set` — вся резидентная память процесса.

`working-set − gc-committed` — native-часть, которую GC не видит. Если большая разница между committed и heap size — GC держит память про запас (Server GC с большими бюджетами, пик нагрузки в прошлом, фрагментация).

**Шаг 2 — разложить память процесса по категориям:**

```bash
dotnet-dump collect -p <pid>
dotnet-dump analyze core_xxx
> maddress -summary        # регионы памяти по типам: GC, stacks, loader heaps, native heap, image...
> eeheap                   # GC-куча и loader heaps рантайма
> threads                  # сколько потоков
```

На Linux — `/proc/<pid>/smaps` или `pmap -x <pid>` (крупные анонимные регионы — native heap); на Windows — VMMap. Для поиска конкретного виновника native-аллокаций — heaptrack или `valgrind massif` на Linux, WPR/WPA с heap-трассировкой на Windows.

**Частые находки:**

- **Native-библиотеки.** Обработка изображений и PDF, драйверы БД, ML-рантаймы (ONNX Runtime, TorchSharp), компрессия. Управляемая обёртка весит байты, native-буфер — мегабайты; без `Dispose` он живёт до финализации.
- **Забытые `Dispose` у обёрток над native-ресурсами.** `Bitmap`, `SqliteConnection`, `ZLibStream`: пока финализатор не отработал, native-память не освобождена, а GC давления не чувствует — managed-куча маленькая, повода собирать нет.
- **Фрагментация glibc malloc.** Много потоков → много malloc arenas, каждая удерживает освобождённую память. Характерная картина: RSS растёт ступеньками и не падает после пика. Помогает `MALLOC_ARENA_MAX=2` (или другое небольшое значение) в переменных окружения.
- **Потоки.** Тысячи потоков из-за блокирующих вызовов в пуле (sync-over-async) — каждый со своим стеком; `threads` в дампе и `dotnet.thread_pool.thread.count` в метриках это покажут.
- **Динамическая генерация кода.** `XmlSerializer` с нестандартным конструктором создаёт новую сборку при каждом вызове, `Reflection.Emit` с новыми (не collectible) сборками, `Expression.Compile` на каждый вызов без кэширования. Растут loader heaps и JIT-код — видно в `eeheap -loader` и метрике `dotnet.jit.compiled_methods`.
- **Memory-mapped files** и большие файлы, прочитанные через `MemoryMappedFile`, — учитываются в RSS как file-backed страницы.
- **GC держит committed-память.** После пика GC не обязан сразу отдавать память ОС. Для Server GC без DATAS это может быть сильно больше живой кучи. Проверяется сравнением `gc-committed` и `gc-heap-size`; лечится DATAS, `GCConserveMemory`, `GCHeapHardLimit`, иногда Workstation GC.
- **Pinned буферы сокетов** и POH — видны в `poh-size`, но это уже часть GC-статистики.

**Как отличить растущее от стабильного.** Одна точка ничего не говорит — нужны два снимка через интервал под нагрузкой: какие категории `maddress -summary` выросли, как изменились `gc-committed` и `working-set`. Растёт native heap при стабильном GC — ищем native-источник; растёт committed при стабильном heap size — настройки GC и фрагментация.

**Что спрашивают дальше:** почему GC не возвращает память ОС сразу, как работает `MALLOC_ARENA_MAX`, чем `gc-heap-size` отличается от `gc-committed`, как найти, какой managed-объект держит native-ресурс (финализируемые объекты в `finalizequeue`).
