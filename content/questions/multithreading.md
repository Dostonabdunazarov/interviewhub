## Что такое thread?

```yaml
category: multithreading
level: middle
difficulty: 2
slug: multithreading-chto-takoe-thread
tags: threading
```

Поток (thread) — это единица выполнения внутри процесса: собственный указатель инструкций, регистры и стек, но общая с другими потоками процесса память (куча, статические поля, открытые дескрипторы). Планировщик ОС распределяет потоки по ядрам CPU, поэтому несколько потоков одного процесса могут выполняться действительно одновременно.

**Что есть у каждого потока своё, а что общее:**

| Своё у потока | Общее для процесса |
| --- | --- |
| стек (в Windows по умолчанию 1 МБ адресного пространства, на других ОС размер зависит от платформы) | управляемая куча и все объекты в ней |
| регистры, instruction pointer | статические поля (кроме `[ThreadStatic]`) |
| thread-local storage (`ThreadLocal<T>`, `[ThreadStatic]`) | загруженные сборки, дескрипторы файлов и сокетов |

**В .NET** `System.Threading.Thread` — обёртка над потоком ОС (один управляемый поток = один нативный). Создать его напрямую можно, но в прикладном коде это делают редко:

```csharp
var t = new Thread(() => Console.WriteLine("работаю"))
{
    IsBackground = true,   // не держит процесс при завершении Main
    Name = "worker"
};
t.Start();
t.Join();                  // дождаться завершения
```

**Foreground и background.** Процесс живёт, пока жив хотя бы один foreground-поток. Background-потоки (в том числе все потоки `ThreadPool`) обрываются при выходе из процесса без выполнения `finally`.

**Почему потоки дорогие.** Создание потока — системный вызов, резервирование стека, регистрация в CLR. Переключение контекста между потоками стоит микросекунды и выбивает кэши. Тысяча потоков, большинство из которых ждёт I/O, — это расход памяти и времени планировщика впустую. Поэтому в .NET работу обычно отдают в `ThreadPool` через `Task`, а ожидание I/O делают через `async/await`, не занимая поток вовсе.

**Когда `new Thread` всё же оправдан:** долгоживущий цикл, который блокируется (например, чтение из нативного API), нужен особый приоритет, STA-апартамент для COM или имя потока для диагностики. Для «долгой задачи» есть и `Task.Factory.StartNew(..., TaskCreationOptions.LongRunning)` — он тоже создаёт отдельный поток вне пула.

**Что спросят дальше:** чем поток отличается от процесса и от `Task`, что такое context switch, почему `Thread.Abort` больше не поддерживается (в .NET Core/5+ бросает `PlatformNotSupportedException` — остановка делается кооперативно через `CancellationToken`).

## Что такое ThreadPool?

```yaml
category: multithreading
level: middle
difficulty: 2
slug: multithreading-chto-takoe-threadpool
tags: threading
```

`ThreadPool` — это общий для процесса пул заранее созданных рабочих потоков, которые берут короткие задачи из очереди и выполняют их. Он избавляет от затрат на создание потока под каждую операцию и сам регулирует число потоков под нагрузку.

**Кто им пользуется.** Почти всё асинхронное в .NET работает поверх пула: `Task.Run`, продолжения после `await` (когда нет `SynchronizationContext`), таймеры `System.Threading.Timer`, обработка запросов в ASP.NET Core, `Parallel.For`/`ForEach`, PLINQ.

```csharp
// Классический API
ThreadPool.QueueUserWorkItem(_ => DoWork());

// Современный способ — через Task, с результатом и исключениями
int result = await Task.Run(() => Compute());
```

**Свойства потоков пула:**

- все они **background** — не удерживают процесс;
- переиспользуются: после задачи поток возвращается за следующей, поэтому `[ThreadStatic]`-данные «переживают» задачу — это источник багов;
- число потоков динамическое: минимум по умолчанию равен числу логических процессоров, дальше пул добавляет потоки, если видит, что очередь не разбирается.

**Главное правило: пул — для коротких неблокирующих задач.** Если занять потоки пула синхронным ожиданием (`.Result`, `Thread.Sleep`, синхронный I/O), свободных потоков не останется, новые добавляются постепенно, и приложение «зависает» при почти нулевой загрузке CPU. Это называется ThreadPool starvation.

| Сценарий | Что использовать |
| --- | --- |
| короткое CPU-вычисление | `Task.Run` (пул) |
| ожидание I/O | `async/await` — поток не нужен вовсе |
| бесконечный блокирующий цикл | отдельный поток (`new Thread` или `TaskCreationOptions.LongRunning`) |

**Настройка.** `ThreadPool.SetMinThreads` позволяет поднять порог, до которого пул создаёт потоки без задержки. Это аварийная мера на время исправления блокирующего кода, а не решение.

**Что спросят дальше:** как пул решает добавить поток (hill climbing, starvation-детектор), что такое локальные очереди и work stealing, как увидеть starvation в метриках (`dotnet-counters`: `threadpool-queue-length`, `threadpool-thread-count`).

## Как работает ThreadPool в .NET?

```yaml
category: multithreading
level: middle
difficulty: 3
slug: multithreading-kak-rabotaet-threadpool-v-net
tags: threading
```

Пул состоит из рабочих потоков, одной глобальной очереди и локальной очереди у каждого рабочего потока. Поток сначала берёт работу из своей локальной очереди, затем из глобальной, затем пытается «украсть» задачу у соседа. Количеством потоков управляет алгоритм hill climbing плюс отдельный механизм борьбы с голоданием.

**Очереди и work stealing:**

```text
Глобальная очередь (FIFO)  ←  QueueUserWorkItem, Task.Run из не-пулового потока
      │
 ┌────┴─────┬───────────┐
Worker 1   Worker 2   Worker 3
[локальная][локальная][локальная]   ← Task, созданные внутри worker'а
 LIFO для владельца, FIFO для «ворующих»
```

- Задача, запланированная **из потока пула** (например, `Task.Run` внутри другой задачи), попадает в локальную очередь этого потока, если не указан `TaskCreationOptions.PreferFairness`.
- Владелец берёт из своей очереди с «горячего» конца (LIFO) — свежие данные ещё в кэше CPU. Остальные крадут с противоположного конца, чтобы меньше конфликтовать с владельцем.
- Задачи из внешних потоков идут в глобальную очередь.

**Сколько потоков.** Минимум (`ThreadPool.GetMinThreads`) по умолчанию равен числу логических процессоров. До минимума потоки создаются сразу по требованию. Выше минимума работают два механизма:

1. **Hill climbing** — пул периодически меняет число потоков и смотрит на пропускную способность (завершённые задачи в единицу времени). Если стало лучше — продолжает в том же направлении, хуже — откатывает.
2. **Starvation detection** — если очередь не пуста, а задачи не завершаются, пул добавляет поток примерно раз в полсекунды. Именно поэтому при массовой блокировке потоков приложение «оживает» очень медленно.

В современных версиях пул дополнительно быстрее добавляет потоки, когда поток пула блокируется на `Task.Wait`/`.Result`, — но это смягчение симптомов, а не лечение sync-over-async.

**Реализация.** Начиная с .NET 6 используется управляемая (portable) реализация пула на C# на всех платформах вместо нативной из CoreCLR. Ожидание I/O не занимает рабочие потоки: завершения приходят через IOCP (Windows) или epoll/kqueue (Unix), и в пул ставится только продолжение.

**`LongRunning`.** `Task.Factory.StartNew(work, TaskCreationOptions.LongRunning)` создаёт отдельный поток вне пула — для долгой блокирующей работы, чтобы не отнимать рабочие потоки. С async-делегатом это бессмысленно: поток освободится на первом `await`.

**Практические выводы:**

- не блокируйте потоки пула — hill climbing рассчитан на короткие CPU-задачи;
- `SetMinThreads` маскирует проблему, поднимая порог мгновенного создания потоков;
- если задача, поставленная из рабочего потока, ждёт другую задачу из той же локальной очереди, её может выполнить сам ожидающий поток (task inlining) — поэтому не любой `Wait` приводит к взаимоблокировке.

**Что спросят дальше:** как проявляется starvation в метриках, чем IO-потоки отличаются от worker-потоков, почему `Parallel.For` внутри ASP.NET-запроса — плохая идея.

## Чем процесс отличается от потока?

```yaml
category: multithreading
level: middle
difficulty: 3
slug: multithreading-chem-process-otlichaetsya-ot-potoka
tags: threading
```

Процесс — это контейнер ресурсов с изолированным адресным пространством; поток — единица выполнения внутри процесса. Потоки одного процесса разделяют память и могут напрямую читать и портить данные друг друга; процессы изолированы ОС и общаются только через IPC.

| | Процесс | Поток |
| --- | --- | --- |
| Адресное пространство | своё, изолированное | общее с другими потоками процесса |
| Ресурсы | дескрипторы, память, токен безопасности | использует ресурсы процесса |
| Стоимость создания | высокая (загрузка образа, runtime, JIT) | ниже (стек + структуры ядра) |
| Переключение | дороже: смена таблиц страниц, сброс TLB | дешевле: адресное пространство то же |
| Обмен данными | pipes, сокеты, shared memory, файлы | общие объекты в памяти + синхронизация |
| Падение | не затрагивает другие процессы | необработанное исключение в любом потоке роняет весь процесс |

**Изоляция в .NET.** Необработанное исключение в любом потоке (включая потоки пула) завершает процесс. Исключение в `Task` без наблюдения не роняет процесс, но и не всплывает — только через `TaskScheduler.UnobservedTaskException`. Отсюда правило: процесс — граница отказа, поток — нет. Если нужно изолировать ненадёжный код (плагины, нативные библиотеки), его выносят в отдельный процесс.

**AppDomain.** В .NET Framework внутри процесса были AppDomain — логическая изоляция без отдельного процесса. В .NET Core/5+ создать дополнительный AppDomain нельзя; для выгрузки кода есть `AssemblyLoadContext`, но он не даёт изоляции безопасности или падений.

**Память.** У каждого потока свой стек (в Windows по умолчанию 1 МБ зарезервированного адресного пространства), а куча общая. Поэтому локальные переменные метода принадлежат потоку, а объект, на который ссылаются из двух потоков, требует синхронизации.

**Практика:**

- масштабирование внутри машины — потоки/задачи; масштабирование и изоляция отказов — процессы и контейнеры;
- `Process.Start` для запуска дочернего процесса, для общения — `System.IO.Pipes`, сокеты или `MemoryMappedFile`;
- в Kubernetes одна реплика = обычно один процесс, и «многопроцессность» достигается числом подов, а не форками.

**Что спросят дальше:** что такое context switch и почему он дороже между процессами, как потоки делят CPU, что происходит с потоками при завершении процесса (background-потоки обрываются без `finally`).

## Что такое concurrency и parallelism?

```yaml
category: multithreading
level: middle
difficulty: 2
slug: multithreading-chto-takoe-concurrency-i-parallelism
tags: threading
```

Concurrency (конкурентность) — это структура программы, в которой несколько задач находятся «в процессе» одновременно и их выполнение перемежается. Parallelism (параллелизм) — это физически одновременное выполнение нескольких вычислений на разных ядрах. Конкурентность возможна и на одном ядре; параллелизм — нет.

**Короткая формулировка (Роб Пайк):** concurrency — про то, как *иметь дело* со многими вещами сразу; parallelism — про то, как *делать* много вещей сразу.

| | Concurrency | Parallelism |
| --- | --- | --- |
| Цель | отзывчивость, обработка многих независимых операций | ускорение вычислений |
| Типичная нагрузка | I/O-bound: запросы, сокеты, БД | CPU-bound: расчёты, обработка данных |
| Нужны ли несколько ядер | нет | да |
| Инструменты .NET | `async/await`, `Task.WhenAll`, `Channel<T>` | `Parallel.For`, PLINQ, `Task.Run` над кусками данных |

```csharp
// Конкурентность: три запроса «в полёте», потоки не заняты ожиданием
var results = await Task.WhenAll(
    http.GetStringAsync(a), http.GetStringAsync(b), http.GetStringAsync(c));

// Параллелизм: вычисление режется на куски и идёт на всех ядрах
Parallel.For(0, data.Length, i => data[i] = Heavy(data[i]));
```

**Почему путают.** Веб-сервер одновременно конкурентный и параллельный: тысячи запросов перемежаются (concurrency), а продолжения выполняются на нескольких потоках пула на разных ядрах (parallelism). Но `async/await` сам по себе не делает код параллельным — он просто не держит поток во время ожидания.

**Практические следствия:**

- ускорить I/O-bound код через `Parallel.ForEach` не получится — он будет блокировать потоки на ожидании; нужен асинхронный код;
- ускорить CPU-bound код через `async` не получится — вычисление всё равно выполняется на одном потоке;
- проблемы гонок появляются, как только есть конкурентность с общим состоянием, даже на одном ядре: поток может быть вытеснен посреди `count++`.

**Что спросят дальше:** закон Амдала (ускорение ограничено долей последовательного кода), как ограничить степень параллелизма (`MaxDegreeOfParallelism`), почему `Task` — это не поток.

## Что такое race condition?

```yaml
category: multithreading
level: middle
difficulty: 2
slug: multithreading-chto-takoe-race-condition
tags: threading
```

Race condition (состояние гонки) — ошибка, при которой результат зависит от того, в каком порядке и с каким перекрытием выполнились операции нескольких потоков. Классический пример — неатомарное «прочитать-изменить-записать» над общей переменной.

```csharp
int counter = 0;
Parallel.For(0, 1_000_000, _ => counter++);
Console.WriteLine(counter); // почти всегда меньше 1 000 000
```

**Почему теряются инкременты.** `counter++` — это три шага: прочитать значение в регистр, прибавить единицу, записать обратно. Два потока читают одно и то же `42`, оба пишут `43` — один инкремент потерян.

```text
Поток A: read 42 ─ add ─────────── write 43
Поток B:      read 42 ─ add ─ write 43
```

**Виды гонок, которые встречаются на практике:**

- **read-modify-write** — `count++`, `total += x`, `list.Add` в обычный `List<T>`;
- **check-then-act** — проверка и действие разнесены: `if (!dict.ContainsKey(k)) dict.Add(k, v);` или «ленивая» инициализация синглтона без синхронизации;
- **гонки на публикации** — объект передан другому потоку до того, как полностью сконструирован, или флаг выставлен раньше данных (зависит от модели памяти).

**Data race vs race condition.** Data race — одновременный доступ к одной ячейке памяти без синхронизации, хотя бы один доступ на запись. Race condition — более широкое понятие логической ошибки порядка: даже если каждая операция по отдельности атомарна (`ConcurrentDictionary`), комбинация «проверил — добавил» всё равно может гоняться.

**Как исправлять:**

| Ситуация | Решение |
| --- | --- |
| один счётчик или ссылка | `Interlocked.Increment`, `Interlocked.CompareExchange` |
| несколько связанных полей | `lock` |
| check-then-act в словаре | атомарные методы `ConcurrentDictionary`: `GetOrAdd`, `AddOrUpdate`, `TryAdd` |
| ленивая инициализация | `Lazy<T>`, `LazyInitializer` |
| общее состояние вообще не нужно | локальные данные на поток + объединение в конце, неизменяемые объекты |

**Почему это коварно.** Гонка может не проявляться годами: на машине разработчика мало ядер, в Debug другие тайминги, а в продакшене под нагрузкой баг вылезает раз в сутки. Тесты «запустил 10 раз — прошло» ничего не доказывают.

**Что спросят дальше:** как найти гонку (стресс-тесты, логирование, Coyote), чем гонка отличается от deadlock, почему `volatile` не спасает `count++`.

## Что такое thread safety?

```yaml
category: multithreading
level: middle
difficulty: 2
slug: multithreading-chto-takoe-thread-safety
tags: threading
```

Код или тип потокобезопасен (thread-safe), если он сохраняет корректность при одновременном вызове из нескольких потоков без дополнительной синхронизации со стороны вызывающего. Важная оговорка: потокобезопасность всегда относится к определённому контракту — какие операции и в каком сочетании гарантированно безопасны.

**Способы добиться потокобезопасности (от простого к сложному):**

1. **Не делить состояние.** Локальные переменные, данные на запрос, `ThreadLocal<T>` — нечего защищать.
2. **Неизменяемость.** Объект, который не меняется после конструирования (`record` с `init`, `ImmutableArray<T>`, `string`), можно читать из любых потоков. Изменение = новый объект.
3. **Взаимное исключение.** `lock`, `SemaphoreSlim` — в каждый момент с состоянием работает один поток.
4. **Атомарные операции.** `Interlocked` для одиночных переменных.
5. **Готовые потокобезопасные типы.** `ConcurrentDictionary`, `ConcurrentQueue`, `Channel<T>`.

**Уровни гарантий** — полезная классификация для собеседования:

| Уровень | Пример |
| --- | --- |
| immutable | `string`, `ImmutableList<T>` |
| thread-safe (каждая операция атомарна) | `ConcurrentDictionary<TKey, TValue>` |
| безопасно только чтение | `Dictionary<TKey, TValue>` без записей, `List<T>` |
| не потокобезопасен | `List<T>` при записи, `StringBuilder` |

**Главная ловушка — композиция.** Потокобезопасные операции по отдельности не дают потокобезопасной комбинации:

```csharp
// Каждая операция ConcurrentDictionary атомарна, но вместе — гонка
if (!cache.ContainsKey(key))
    cache[key] = Load(key);        // два потока загрузят и перезапишут

// Правильно — одна атомарная операция
var value = cache.GetOrAdd(key, Load);
```

Аналогично `if (queue.Count > 0) queue.Dequeue()` — между проверкой и действием другой поток мог забрать элемент; нужен `TryDequeue`.

**Что говорит документация .NET.** В разделе «Thread Safety» большинства BCL-типов написано: публичные статические члены потокобезопасны, экземплярные — нет. `Dictionary<K,V>` и `List<T>` допускают одновременное чтение из нескольких потоков, если никто не пишет.

**Цена.** Синхронизация стоит производительности и добавляет риски (deadlock, contention). Поэтому BCL-коллекции по умолчанию не потокобезопасны: платить за блокировки должен только тот, кому это нужно.

**Что спросят дальше:** какие есть concurrent-коллекции, почему `lock(this)` плох, чем thread-safe отличается от reentrant.

## Что такое critical section?

```yaml
category: multithreading
level: middle
difficulty: 2
slug: multithreading-chto-takoe-critical-section
tags: synchronization
```

Критическая секция — это участок кода, который обращается к общему ресурсу и поэтому в каждый момент времени должен выполняться не более чем одним потоком. Задача синхронизации — обеспечить взаимное исключение (mutual exclusion) при входе в такие участки.

```csharp
private readonly Lock _gate = new();   // .NET 9+; в более ранних — private readonly object
private decimal _balance;

public void Withdraw(decimal amount)
{
    lock (_gate)                        // вход в критическую секцию
    {
        if (_balance < amount) throw new InvalidOperationException();
        _balance -= amount;             // проверка и изменение — одно целое
    }                                   // выход
}
```

Без `lock` два потока могли бы одновременно пройти проверку и увести баланс в минус.

**Требования к корректной критической секции (классическая формулировка):**

- **взаимное исключение** — внутри не больше одного потока;
- **прогресс** — если секция свободна, желающий войти не ждёт бесконечно;
- **ограниченное ожидание** — ни один поток не голодает вечно.

**Правила хорошей критической секции:**

- **короткая** — внутри только работа с общим состоянием; вычисления, логирование, I/O — снаружи;
- **без вызова чужого кода** — событие, колбэк, виртуальный метод под блокировкой могут взять другую блокировку и привести к deadlock;
- **один объект блокировки на один инвариант** — все пути доступа к `_balance` должны идти через тот же `_gate`, иначе защиты нет;
- **закрытый объект блокировки** — не `this`, не `typeof(T)`, не строка: их может заблокировать посторонний код.

**Термин в Windows.** В Win32 `CRITICAL_SECTION` — это конкретный примитив: блокировка внутри процесса, которая сначала крутится в user mode и только при конкуренции уходит в ядро. `Monitor` в .NET устроен похоже. На собеседовании обычно спрашивают про понятие, а не про Win32 API, но упоминание показывает кругозор.

**Какие примитивы реализуют критическую секцию в .NET:** `lock`/`Monitor`, `System.Threading.Lock` (.NET 9), `SpinLock`, `Mutex` (межпроцессный), `SemaphoreSlim(1, 1)` (если внутри нужен `await`).

**Что спросят дальше:** что будет, если внутри секции бросится исключение (`lock` освобождает блокировку в `finally`), чем критическая секция отличается от семафора (он пускает N потоков), что такое lock contention.

## Что делает `lock`?

```yaml
category: multithreading
level: middle
difficulty: 2
slug: multithreading-chto-delaet-lock
tags: synchronization
```

`lock` — оператор C#, который обеспечивает взаимное исключение: блок кода выполняет не более одного потока одновременно для одного и того же объекта блокировки. Для обычного объекта компилятор разворачивает его в `Monitor.Enter`/`Monitor.Exit` в `try/finally`, поэтому блокировка освобождается даже при исключении.

```csharp
lock (_sync)
{
    _items.Add(item);
}

// Во что компилируется для object (C# 4+)
bool lockTaken = false;
try
{
    Monitor.Enter(_sync, ref lockTaken);
    _items.Add(item);
}
finally
{
    if (lockTaken) Monitor.Exit(_sync);
}
```

**`System.Threading.Lock` в .NET 9 / C# 13.** Появился отдельный тип блокировки. Если выражение в `lock` имеет тип `Lock`, компилятор генерирует не `Monitor`, а `using (_gate.EnterScope()) { ... }`. Это легче: не используется заголовок объекта и sync block, API явнее. Для нового кода рекомендуют именно его:

```csharp
private readonly Lock _gate = new();
lock (_gate) { ... }   // → _gate.EnterScope()
```

Осторожно: если привести `Lock` к `object` и передать в `lock`, компилятор вернётся к `Monitor` (и выдаст предупреждение) — это уже другая, несовместимая блокировка.

**Свойства `lock`:**

- **реентерабельный** — поток, уже держащий блокировку, может войти повторно (счётчик рекурсии);
- **привязан к потоку** — освободить может только владелец;
- **гарантирует видимость** — вход и выход работают как барьеры памяти, изменения внутри видны следующему владельцу;
- **не имеет таймаута** — для этого `Monitor.TryEnter(obj, timeout)` или `Lock.TryEnter`.

**Что можно блокировать.** Только reference type (value type компилятор не пропустит). Правило — закрытое `readonly`-поле:

- не `this` — его может заблокировать внешний код;
- не `typeof(Foo)` — общий на весь процесс;
- не строку — интернированные строки общие для всех.

**Ограничения:**

- **`await` внутри `lock` запрещён** компилятором (ошибка CS1996): продолжение может выполниться на другом потоке, а `Monitor` освобождается только владельцем. Для асинхронного кода — `SemaphoreSlim.WaitAsync`.
- `lock` работает только внутри процесса. Между процессами — `Mutex`, между машинами — распределённые блокировки.

**Что спросят дальше:** как `Monitor` устроен внутри (thin lock, sync block), что такое `Wait`/`Pulse`, чем `lock` отличается от `Mutex` и `SemaphoreSlim`.

## Как работает `Monitor`?

```yaml
category: multithreading
level: middle
difficulty: 3
slug: multithreading-kak-rabotaet-monitor
tags: synchronization, observability
```

`Monitor` — статический класс CLR, реализующий блокировку на любом reference-объекте: `Enter`/`Exit` для взаимного исключения и `Wait`/`Pulse`/`PulseAll` для ожидания условия. Он реентерабельный, привязан к потоку-владельцу и сначала пытается захватить блокировку без обращения к ядру ОС.

**Где хранится состояние блокировки.** У каждого объекта в куче есть заголовок (object header). При захвате без конкуренции CLR записывает в него ID потока-владельца и счётчик рекурсии — это **thin lock**, операция сводится к одному CAS. Если возникает конкуренция (или заголовок уже занят, например, хеш-кодом), блокировка «раздувается»: создаётся **sync block** — запись в таблице sync blocks, а в заголовок пишется её индекс. В sync block лежит полноценная структура с очередью ожидающих и событием ядра.

**Путь захвата при конкуренции:**

1. несколько коротких итераций spin-wait — вдруг владелец сейчас освободит;
2. если не освободил — поток встаёт в очередь и блокируется на объекте ядра (переход в kernel mode, context switch);
3. при `Exit` владелец будит одного ожидающего.

Поэтому короткие критические секции под `Monitor` дешёвые, а длинные с высокой конкуренцией дорогие: потоки засыпают и просыпаются.

**Wait/Pulse — условные переменные:**

```csharp
private readonly object _sync = new();
private readonly Queue<Job> _queue = new();

public void Produce(Job job)
{
    lock (_sync)
    {
        _queue.Enqueue(job);
        Monitor.Pulse(_sync);            // разбудить одного ждущего
    }
}

public Job Consume()
{
    lock (_sync)
    {
        while (_queue.Count == 0)        // while, а не if
            Monitor.Wait(_sync);         // отпускает блокировку и ждёт Pulse
        return _queue.Dequeue();
    }
}
```

- `Wait` атомарно освобождает блокировку и засыпает; после пробуждения снова захватывает её, прежде чем вернуться.
- `Pulse` переносит одного ждущего в очередь на захват; реально он продолжит, только когда текущий владелец выйдет.
- Условие проверяют в цикле `while`: между `Pulse` и повторным захватом состояние мог изменить другой поток.
- `Wait`/`Pulse` без владения блокировкой бросают `SynchronizationLockException`.

**Полезные члены:** `TryEnter(obj, timeout)` — захват с таймаутом; `IsEntered(obj)` — держит ли текущий поток; `Monitor.LockContentionCount` — сколько раз с начала процесса была конкуренция (есть и счётчик `monitor-lock-contention-count` в `dotnet-counters`), полезно для диагностики.

**Ограничения:** работает только внутри процесса; освободить может только владелец, поэтому несовместим с `await`; блокировать value type бессмысленно — каждый вызов упаковал бы новый объект.

**Что спросят дальше:** почему в .NET 9 появился `System.Threading.Lock` (он не использует заголовок объекта и sync block), как увидеть contention, почему условие `Wait` проверяют в `while`. Сегодня producer-consumer обычно пишут на `Channel<T>` или `BlockingCollection<T>`, а не на `Wait`/`Pulse`.

## Чем `lock` отличается от `Monitor`?

```yaml
category: multithreading
level: middle
difficulty: 3
slug: multithreading-chem-lock-otlichaetsya-ot-monitor
tags: synchronization, observability
```

`lock` — это синтаксис C#, а `Monitor` — механизм CLR, на который он опирается (для обычного объекта). `lock` покрывает самый частый сценарий «захватить — выполнить — гарантированно освободить», а `Monitor` даёт полный набор: захват с таймаутом, ожидание условия, проверку владения.

| | `lock (obj)` | `Monitor` напрямую |
| --- | --- | --- |
| Освобождение при исключении | автоматически (`try/finally`) | вручную, легко забыть |
| Таймаут захвата | нет | `Monitor.TryEnter(obj, timeout)` |
| Ожидание условия | нет | `Wait`, `Pulse`, `PulseAll` |
| Проверка владения | нет | `Monitor.IsEntered(obj)` |
| Для `System.Threading.Lock` (.NET 9) | компилируется в `EnterScope()`, не в `Monitor` | не применим к `Lock` |

**Во что превращается `lock`.** Начиная с C# 4 — в `Monitor.Enter(obj, ref lockTaken)` внутри `try` и `Monitor.Exit` в `finally` при `lockTaken == true`. Перегрузка с `ref bool` нужна, чтобы исключение, возникшее прямо во время захвата (исторически — `ThreadAbortException`), не оставило блокировку захваченной или не привело к лишнему `Exit`.

**Когда нужен `Monitor` явно:**

```csharp
// Захват с таймаутом — чтобы не висеть вечно при подозрении на deadlock
bool taken = false;
try
{
    Monitor.TryEnter(_sync, TimeSpan.FromSeconds(2), ref taken);
    if (!taken) throw new TimeoutException("lock busy");
    Update();
}
finally
{
    if (taken) Monitor.Exit(_sync);
}
```

Второй сценарий — условные переменные через `Wait`/`Pulse`, при этом их всё равно вызывают внутри `lock`: `Monitor.Wait(_sync)` требует, чтобы блокировка уже была захвачена.

**Типичные ошибки при ручном `Monitor`:**

- `Exit` не в `finally` — исключение оставляет блокировку захваченной навсегда;
- `Monitor.Enter` на value type — каждый вызов упаковывает новый объект, `Exit` получает другой объект и бросает `SynchronizationLockException`; `lock` такое не скомпилирует;
- `Exit` из другого потока — тоже `SynchronizationLockException`.

**Про .NET 9.** Для поля типа `System.Threading.Lock` таймаут и проверка владения есть прямо на типе: `TryEnter(timeout)`, `IsHeldByCurrentThread`. `Wait`/`Pulse` у `Lock` нет — если нужны условные переменные, остаются `Monitor` на обычном объекте или более высокоуровневые примитивы (`SemaphoreSlim`, `Channel<T>`).

**Что спросят дальше:** почему в `lock` нельзя `await`, как устроен thin lock и sync block, чем `Monitor` отличается от `Mutex`.

## Что такое `Mutex`?

```yaml
category: multithreading
level: middle
difficulty: 2
slug: multithreading-chto-takoe-mutex
tags: synchronization
```

`Mutex` — примитив взаимного исключения на основе объекта ядра ОС. Главное его отличие от `lock` — он может быть **именованным** и тогда работает между процессами: например, чтобы запустить только один экземпляр приложения.

```csharp
using var mutex = new Mutex(initiallyOwned: false, name: @"Global\MyApp.SingleInstance");

if (!mutex.WaitOne(TimeSpan.Zero))
{
    Console.WriteLine("Уже запущено");
    return;
}
try
{
    RunApp();
}
finally
{
    mutex.ReleaseMutex();
}
```

**Свойства:**

- **привязан к потоку** — освободить (`ReleaseMutex`) может только поток-владелец, иначе `ApplicationException`;
- **реентерабельный** — владелец может захватить повторно, но и освободить нужно столько же раз;
- **наследник `WaitHandle`** — можно ждать вместе с другими хендлами через `WaitHandle.WaitAny`/`WaitAll`;
- **abandoned mutex** — если поток-владелец завершился, не освободив мьютекс, следующий `WaitOne` получит владение, но бросит `AbandonedMutexException`. Это сигнал, что защищаемые данные могли остаться в неконсистентном состоянии.

**Имена.** В Windows префикс `Global\` делает мьютекс видимым во всех сессиях (службы и пользователь), `Local\` (по умолчанию) — только в текущей сессии. В .NET Core/5+ именованные мьютексы поддерживаются и на Linux/macOS (реализованы runtime'ом поверх файлов в временном каталоге), но видимы только процессам .NET.

**Стоимость.** Каждый `WaitOne`/`ReleaseMutex` — системный вызов, даже без конкуренции. Это на порядки медленнее незаспоренного `lock`, который обходится одним атомарным CAS в user mode.

**Когда использовать:**

- единственный экземпляр приложения или утилиты;
- защита общего файла/ресурса несколькими процессами на одной машине.

Когда **не** использовать: синхронизация внутри процесса (берите `lock`), асинхронный код (привязка к потоку ломается после `await`), несколько машин (нужна распределённая блокировка — Redis, БД, ZooKeeper).

**Что спросят дальше:** чем мьютекс отличается от семафора с одним слотом (семафор не привязан к владельцу), что такое abandoned mutex, почему `Mutex` нельзя держать через `await`.

## Чем `Mutex` отличается от `lock`?

```yaml
category: multithreading
level: middle
difficulty: 3
slug: multithreading-chem-mutex-otlichaetsya-ot-lock
tags: synchronization
```

`lock` — лёгкая блокировка внутри процесса, реализованная в CLR в пользовательском режиме; `Mutex` — объект ядра ОС, который может быть именованным и синхронизировать разные процессы. Цена этой возможности — системный вызов на каждый захват и освобождение.

| | `lock` / `Monitor` / `Lock` | `Mutex` |
| --- | --- | --- |
| Область действия | один процесс | процесс или вся машина (именованный) |
| Реализация | user mode, CAS + spin, ядро только при конкуренции | объект ядра, системный вызов всегда |
| Цена без конкуренции | десятки наносекунд | порядок микросекунды |
| Привязка к потоку | да | да |
| Реентерабельность | да | да |
| Таймаут | `Monitor.TryEnter`, `Lock.TryEnter` | `WaitOne(timeout)` |
| Ожидание нескольких | нет | `WaitHandle.WaitAny/WaitAll` |
| Если владелец умер | блокировка остаётся захваченной (поток мёртв — процесс, скорее всего, тоже) | `AbandonedMutexException` у следующего |
| `await` внутри | запрещён компилятором (CS1996) | компилируется, но сломается: освобождать нужно в том же потоке |
| Нужно `Dispose` | нет | да, это `IDisposable`-хендл |

**Почему `lock` быстрее.** Незаспоренный `lock` — это атомарная запись ID потока в заголовок объекта (или поле `Lock`). Переход в ядро происходит только тогда, когда поток реально должен ждать. `Mutex.WaitOne` каждый раз проходит через ОС, поэтому использовать его как внутрипроцессную блокировку «на всякий случай» — пустая трата производительности.

**Одинаковое ограничение с async.** Оба примитива привязаны к потоку-владельцу. После `await` продолжение обычно выполняется на другом потоке пула, и `ReleaseMutex` там бросит исключение. Для асинхронного кода внутри процесса — `SemaphoreSlim(1, 1)` с `WaitAsync`; для межпроцессной синхронизации в async-коде можно вынести работу с мьютексом в выделенный поток или использовать файловую блокировку (`FileShare.None`).

**Практический выбор:**

- защитить поле или коллекцию в своём сервисе — `lock` (в .NET 9+ на `System.Threading.Lock`);
- не дать запуститься второму экземпляру утилиты или двум процессам писать в один файл — именованный `Mutex`;
- несколько подов в Kubernetes — ни то ни другое, нужна распределённая блокировка или уникальный констрейнт в БД.

**Что спросят дальше:** что такое abandoned mutex, чем `Mutex` отличается от `Semaphore`, как сделать single-instance приложение.

## Что такое `Semaphore`?

```yaml
category: multithreading
level: middle
difficulty: 2
slug: multithreading-chto-takoe-semaphore
tags: synchronization
```

Семафор — примитив синхронизации, который пропускает в защищённый участок не более N потоков одновременно. Внутри у него счётчик свободных «слотов»: `Wait` уменьшает его (или ждёт, если он равен нулю), `Release` увеличивает. Мьютекс пускает одного, семафор — N.

```csharp
// Не больше 3 одновременных обращений к медленному ресурсу
private static readonly SemaphoreSlim _slots = new(initialCount: 3, maxCount: 3);

public async Task<string> CallAsync(string url, CancellationToken ct)
{
    await _slots.WaitAsync(ct);
    try
    {
        return await _http.GetStringAsync(url, ct);
    }
    finally
    {
        _slots.Release();
    }
}
```

**Два класса в .NET:**

- `Semaphore` — обёртка над объектом ядра ОС, может быть именованным (межпроцессным; именованные семафоры поддерживаются только в Windows), наследник `WaitHandle`.
- `SemaphoreSlim` — лёгкий внутрипроцессный семафор с `WaitAsync`. В прикладном коде почти всегда нужен он.

**Ключевое свойство — нет владельца.** В отличие от `lock` и `Mutex`, семафор не привязан к потоку: `Release` может вызвать любой поток, в том числе продолжение после `await` на другом потоке. Именно поэтому `SemaphoreSlim(1, 1)` — стандартная асинхронная замена `lock`. Обратная сторона — нет реентерабельности: повторный `Wait` в том же потоке при счётчике 0 приведёт к самоблокировке.

**Типичные применения:**

- ограничение параллелизма — не больше N запросов к внешнему API или БД;
- пул ресурсов — N соединений, N лицензий;
- асинхронный мьютекс — `SemaphoreSlim(1, 1)`.

**Типичные ошибки:**

- `Release` не в `finally` — при исключении слот «утекает», и со временем семафор блокирует всех;
- `Release` больше раз, чем было `Wait`, — счётчик растёт выше задуманного; если задан `maxCount`, бросится `SemaphoreFullException`, если нет — ограничение тихо перестанет работать;
- `WaitAsync` без `CancellationToken` и таймаута — запросы копятся в очереди ожидания бесконечно.

**Что спросят дальше:** чем `Semaphore` отличается от `SemaphoreSlim`, почему `WaitAsync` лучше `Wait` под нагрузкой, как ограничить concurrency при работе с внешним сервисом.

## Чем `Semaphore` отличается от `SemaphoreSlim`?

```yaml
category: multithreading
level: middle
difficulty: 3
slug: multithreading-chem-semaphore-otlichaetsya-ot-semaphoreslim
tags: synchronization
```

`Semaphore` — обёртка над семафором ядра ОС: поддерживает именованные межпроцессные семафоры, но каждое ожидание — системный вызов. `SemaphoreSlim` — лёгкая реализация внутри CLR для одного процесса: крутится в user mode, уходит в ядро только при долгом ожидании и, главное, умеет `WaitAsync`.

| | `Semaphore` | `SemaphoreSlim` |
| --- | --- | --- |
| Реализация | объект ядра ОС | управляемый код (Monitor + spin) |
| Межпроцессный | да, если именованный (только Windows) | нет |
| Асинхронное ожидание | нет | `WaitAsync(timeout, ct)` |
| Отмена | нет | `CancellationToken` в `Wait`/`WaitAsync` |
| Базовый тип | `WaitHandle` → `WaitAny/WaitAll` | свой; есть `AvailableWaitHandle` при необходимости |
| Цена без конкуренции | системный вызов | атомарная операция в user mode |
| Текущий счётчик | не узнать без `Release` | `CurrentCount` |
| Привязка к потоку | нет | нет |

**Почему `WaitAsync` решает.** Синхронный `Wait` держит поток заблокированным всё время ожидания. На сервере это прямой путь к ThreadPool starvation: сотня запросов ждёт слота — сотня потоков пула стоит без дела. `WaitAsync` возвращает `Task`, который завершится, когда слот освободится, а поток тем временем обслуживает другие запросы.

```csharp
private readonly SemaphoreSlim _gate = new(1, 1);

public async Task SaveAsync(Data d, CancellationToken ct)
{
    if (!await _gate.WaitAsync(TimeSpan.FromSeconds(5), ct))
        throw new TimeoutException();
    try { await _repo.WriteAsync(d, ct); }
    finally { _gate.Release(); }
}
```

**Нюансы `SemaphoreSlim`:**

- очередь асинхронных ожидающих в текущей реализации обслуживается в порядке поступления, но документация не обещает строгой справедливости между синхронными и асинхронными ожидающими — не стройте на этом логику;
- `Dispose` освобождает только внутренний `WaitHandle`, если он создавался; вызывать `Dispose`, пока кто-то ждёт, нельзя;
- `Release` не проверяет, что этот же код делал `Wait`: лишний вызов тихо увеличит число слотов (если не задан `maxCount`).

**Когда нужен именно `Semaphore`:** ограничить число одновременно работающих процессов на машине (например, не больше двух экземпляров тяжёлой утилиты). На Linux/macOS именованные семафоры не поддерживаются — конструктор с именем бросит `PlatformNotSupportedException`; там межпроцессно поддерживается только именованный `Mutex`.

**Что спросят дальше:** как ограничить concurrency к внешнему сервису, чем семафор отличается от мьютекса, что будет при лишнем `Release`.

## Что такое `ReaderWriterLockSlim`?

```yaml
category: multithreading
level: middle
difficulty: 2
slug: multithreading-chto-takoe-readerwriterlockslim
```

`ReaderWriterLockSlim` — блокировка, которая разрешает много одновременных читателей или одного писателя. Она полезна, когда данные читаются гораздо чаще, чем изменяются, и чтение занимает заметное время: читатели перестают мешать друг другу.

```csharp
private readonly ReaderWriterLockSlim _rw = new();
private readonly Dictionary<string, Config> _map = new();

public Config? Get(string key)
{
    _rw.EnterReadLock();
    try { return _map.GetValueOrDefault(key); }
    finally { _rw.ExitReadLock(); }
}

public void Set(string key, Config value)
{
    _rw.EnterWriteLock();
    try { _map[key] = value; }
    finally { _rw.ExitWriteLock(); }
}
```

**Три режима:**

| Режим | Совместим с | Назначение |
| --- | --- | --- |
| Read | другими Read и одним Upgradeable | только чтение |
| Upgradeable read | Read, но не с другим Upgradeable | прочитать и, возможно, перейти в Write |
| Write | ни с чем | изменение |

Upgradeable-режим нужен для сценария «проверил — при необходимости изменил» без отпускания блокировки. Одновременно upgradeable может держать только один поток: если бы двое повышались до записи одновременно, они бы заблокировали друг друга.

**Писатели не голодают.** Когда писатель ждёт, новые читатели не допускаются, пока он не отработает.

**Рекурсия.** По умолчанию `LockRecursionPolicy.NoRecursion`: повторный вход тем же потоком бросает `LockRecursionException`. Это сознательное решение — рекурсия в reader-writer блокировках легко приводит к deadlock.

**Когда `lock` лучше.** `ReaderWriterLockSlim` дороже простого `lock` на каждую операцию. Если критическая секция короткая (чтение из словаря — десятки наносекунд), выигрыш от параллельного чтения не окупает накладные расходы, и обычный `lock` оказывается быстрее. Выигрыш появляется при длинных чтениях и высоком соотношении чтений к записям. Решение принимают по бенчмарку, а не «по названию».

**Альтернативы, которые часто лучше:**

- `ConcurrentDictionary` — чтение без блокировок;
- неизменяемый снимок + замена ссылки: читатели берут текущий `FrozenDictionary`/`ImmutableDictionary`, писатель строит новый и публикует через `Volatile.Write`/`Interlocked.Exchange`. Идеально для редко меняющейся конфигурации.

**Ограничения:** привязан к потоку, с `await` внутри не работает; реализует `IDisposable`. Старый `ReaderWriterLock` (без Slim) медленнее и имеет известные проблемы — в новом коде не используется.

**Что спросят дальше:** почему upgradeable только один, чем плох `ReaderWriterLockSlim` для коротких секций, как сделать read-mostly кэш без блокировок.

## Что такое `Interlocked`?

```yaml
category: multithreading
level: middle
difficulty: 2
slug: multithreading-chto-takoe-interlocked
tags: synchronization
```

`Interlocked` — статический класс с атомарными операциями над одной переменной: инкремент, сложение, обмен, сравнение с обменом. Каждая операция выполняется как единое неделимое действие на уровне процессора и одновременно работает как полный барьер памяти.

```csharp
private long _requests;

public void OnRequest() => Interlocked.Increment(ref _requests);
public long Snapshot()   => Interlocked.Read(ref _requests);
```

**Основные методы:**

| Метод | Что делает |
| --- | --- |
| `Increment` / `Decrement` | атомарно ±1, возвращает новое значение |
| `Add` | атомарно прибавляет, возвращает новое значение |
| `Exchange` | записывает новое значение, возвращает старое |
| `CompareExchange(ref x, value, comparand)` | записывает `value`, только если `x == comparand`; возвращает старое значение |
| `Read(ref long)` | атомарное чтение 64-битного значения (важно в 32-битных процессах) |
| `And` / `Or` (.NET 5+) | атомарные побитовые операции |
| `MemoryBarrier` | полный барьер без операции над данными |

**Как это работает.** На x86/x64 операции компилируются в инструкции с префиксом `lock` (`lock xadd`, `lock cmpxchg`, `xchg`). На ARM64 — в атомарные инструкции LSE (`ldadd`, `cas`) или в цикл LL/SC (`ldaxr`/`stlxr`) на процессорах без LSE. В любом случае процессор гарантирует, что никакой другой поток не вклинится между чтением и записью.

**`CompareExchange` — основа lock-free кода.** Любую операцию над одной переменной можно сделать атомарной через цикл «прочитал — вычислил — попытался записать, если никто не изменил»:

```csharp
// атомарный максимум
static void UpdateMax(ref int target, int value)
{
    int current = Volatile.Read(ref target);
    while (value > current)
    {
        int seen = Interlocked.CompareExchange(ref target, value, current);
        if (seen == current) break;   // успех
        current = seen;               // кто-то изменил — повторяем
    }
}
```

**Ограничения:**

- работает только с одной переменной — два связанных поля атомарно не обновить (для этого `lock` или неизменяемый объект + `Exchange` ссылки);
- атомарность стоит денег: при частых обновлениях одной переменной из многих ядер кэш-линия «прыгает» между ядрами, и счётчик становится узким местом;
- обычное чтение переменной, которую меняют через `Interlocked`, может быть «устаревшим» — читать надо через `Volatile.Read` или `Interlocked.Read`.

**Что спросят дальше:** когда `Interlocked`, а когда `lock`; что такое ABA-проблема; почему `volatile` не делает `count++` атомарным.

## Что такое `volatile`?

```yaml
category: multithreading
level: middle
difficulty: 2
slug: multithreading-chto-takoe-volatile
tags: synchronization
```

`volatile` — модификатор поля в C#, который запрещает компилятору и JIT кэшировать значение в регистре и переставлять обращения к полю определённым образом: чтение volatile-поля имеет семантику **acquire**, запись — **release**. Атомарности составных операций и полного барьера он не даёт.

**Классическая проблема, которую он решает:**

```csharp
private bool _stop;            // без volatile

void Worker()
{
    while (!_stop) { DoWork(); }   // JIT вправе один раз прочитать _stop в регистр
}                                  // и крутиться вечно
```

JIT видит, что внутри цикла `_stop` не меняется, и может вынести чтение из цикла (особенно в Release-сборке, когда `DoWork` заинлайнен). С `private volatile bool _stop;` каждое обращение будет реальным чтением из памяти.

**Что именно гарантирует volatile:**

- **acquire при чтении** — последующие чтения и записи не будут переставлены *до* этого чтения;
- **release при записи** — предыдущие чтения и записи не будут переставлены *после* этой записи;
- этого достаточно для паттерна «записал данные, затем выставил флаг» — читатель, увидевший флаг, увидит и данные.

**Чего volatile не гарантирует:**

- **атомарности** `count++` — это по-прежнему чтение и запись, между которыми вклинится другой поток;
- **порядка «запись, затем чтение другой переменной»** (store → load): volatile-запись и следующее volatile-чтение другого поля могут переставиться, поэтому алгоритмы вроде Dekker/Peterson на одном `volatile` не работают — нужен `Interlocked` или `Thread.MemoryBarrier`;
- **«свежести»** в бытовом смысле — это про порядок, а не про мгновенную доставку значения.

**Ограничения по типам.** `volatile` применим к ссылочным типам, `bool`, `char`, `byte`, `sbyte`, `short`, `ushort`, `int`, `uint`, `float`, `nint`/`nuint`, enum на их основе и параметрам-типам, известным как reference type. `long` и `double` нельзя — в 32-битном процессе их запись неатомарна. Для них — `Volatile.Read/Write` или `Interlocked`.

**Архитектура имеет значение.** На x86/x64 обычные загрузки и сохранения уже обладают семантикой acquire/release, поэтому там `volatile` в основном ограничивает оптимизации JIT. На ARM64 JIT генерирует для volatile-обращений специальные инструкции (`ldar`/`stlr`) или барьеры — без них код, «работающий» на x86, может ломаться.

**Современная рекомендация.** Вместо модификатора поля чаще используют явные `Volatile.Read(ref x)` / `Volatile.Write(ref x, v)` — видно, какое именно обращение требует семантики. А для флагов остановки — `CancellationToken`.

**Что спросят дальше:** чем volatile отличается от `Interlocked` и `lock`, что такое memory barrier, почему код ломается на ARM.

## Когда использовать `Interlocked`, а когда `lock`?

```yaml
category: multithreading
level: middle
difficulty: 3
slug: multithreading-kogda-ispolzovat-interlocked-a-kogda-lock
tags: synchronization
```

`Interlocked` — когда инвариант умещается в **одну переменную** и операция над ней выражается одной атомарной инструкцией или коротким CAS-циклом: счётчики, флаги, замена ссылки. `lock` — когда нужно согласованно изменить **несколько** значений, выполнить проверку и действие как единое целое или когда логика внутри нетривиальна.

| Задача | Выбор | Почему |
| --- | --- | --- |
| счётчик запросов, метрика | `Interlocked.Increment/Add` | одна переменная, одна инструкция |
| флаг «запущено один раз» | `Interlocked.CompareExchange(ref _state, 1, 0)` | атомарный переход состояния |
| публикация нового снимка конфигурации | `Interlocked.Exchange` / `Volatile.Write` ссылки | неизменяемый объект целиком заменяется |
| перевод денег между двумя счетами | `lock` | два поля должны меняться вместе |
| «если нет в словаре — добавить и увеличить счётчик» | `lock` (или атомарные методы concurrent-коллекции) | check-then-act над несколькими структурами |
| сложная структура данных (очередь, дерево) | `lock` или готовая concurrent-коллекция | самописный lock-free — источник тонких багов |

**Почему нельзя просто везде `Interlocked`:**

```csharp
// Каждая операция атомарна, но вместе — нет
Interlocked.Add(ref _total, amount);
Interlocked.Increment(ref _count);
// Между ними другой поток может прочитать _total и _count
// и посчитать среднее по несогласованной паре
```

Инвариант «`_total` и `_count` согласованы» охватывает две переменные — его защищает только `lock` (или упаковка обоих значений в неизменяемый объект, заменяемый одним `Exchange`).

**Производительность — не всегда в пользу `Interlocked`:**

- без конкуренции `Interlocked` быстрее (одна атомарная инструкция против захвата и освобождения), но незаспоренный `lock` тоже стоит порядка десятков наносекунд;
- при сильной конкуренции за одну переменную оба варианта упираются в одно и то же — кэш-линию, которую ядра отбирают друг у друга. CAS-цикл при этом ещё и тратит CPU на повторы;
- если счётчик обновляется очень часто из многих потоков, помогает не выбор примитива, а шардирование: счётчик на ядро/поток и суммирование при чтении.

**Практическое правило.** Начинайте с `lock` — он проще проверяется на корректность. Переходите на `Interlocked`, если состояние естественно сводится к одной переменной или профилирование показало contention на блокировке. Самописные lock-free алгоритмы над несколькими переменными оставьте авторам BCL.

**Что спросят дальше:** как реализовать CAS-цикл, что такое ABA, почему `volatile` не заменяет ни то ни другое.

## Что такое `ConcurrentDictionary`?

```yaml
category: multithreading
level: middle
difficulty: 2
slug: multithreading-chto-takoe-concurrentdictionary
tags: collections, threading
```

`ConcurrentDictionary<TKey, TValue>` — потокобезопасный хеш-словарь из `System.Collections.Concurrent`. Его можно одновременно читать и изменять из многих потоков без внешнего `lock`, а атомарные методы вроде `GetOrAdd` и `AddOrUpdate` закрывают типичные сценарии «проверить и добавить».

```csharp
private readonly ConcurrentDictionary<string, int> _hits = new();

public void Hit(string page) =>
    _hits.AddOrUpdate(page, addValue: 1, updateValueFactory: (_, old) => old + 1);

public int Get(string page) =>
    _hits.TryGetValue(page, out var n) ? n : 0;
```

**Как устроен внутри:**

- **чтение без блокировок** — `TryGetValue`, индексатор на чтение и `ContainsKey` не берут lock; писатели публикуют изменения так, чтобы читатель без блокировки всегда видел целостный узел (значение, которое нельзя записать атомарно, заменяется вместе с узлом);
- **запись с lock striping** — массив блокировок, каждая защищает свою группу корзин; два потока, пишущие в разные группы, не мешают друг другу. Число блокировок по умолчанию связано с числом процессоров (`concurrencyLevel`);
- **ресайз** — захватывает все блокировки, поэтому редкий, но дорогой.

**Основные атомарные методы:**

| Метод | Назначение |
| --- | --- |
| `TryAdd`, `TryRemove`, `TryUpdate` | атомарные операции с результатом `bool` |
| `GetOrAdd(key, factory)` | вернуть существующее или добавить новое |
| `AddOrUpdate(key, add, update)` | добавить или обновить существующее |
| `TryRemove(KeyValuePair)` (.NET 5+) | удалить, только если значение совпадает |

**Важные нюансы:**

- **фабрики вызываются вне блокировки** — `GetOrAdd` и `AddOrUpdate` могут вызвать делегат несколько раз при гонке, хотя в словарь попадёт только один результат. Фабрика должна быть без побочных эффектов; для «строго один раз» — `ConcurrentDictionary<K, Lazy<V>>`;
- **`Count`, `Keys`, `Values`, `ToArray`** захватывают все блокировки — в горячем пути это дорого;
- **перечисление не снимок** — `foreach` не бросает исключение при параллельных изменениях, но может увидеть часть из них; для снимка — `ToArray()`;
- комбинация `ContainsKey` + индексатор — гонка, используйте атомарные методы.

**Когда брать:** общий кэш или реестр, к которому обращаются многие потоки с заметной долей записей. Если данные почти не меняются — `FrozenDictionary` (.NET 8) с атомарной заменой снимка быстрее на чтении. Если словарь принадлежит одному потоку или защищён уже существующим `lock` — обычный `Dictionary`.

**Что спросят дальше:** чем отличается от `Dictionary` под `lock`, почему `GetOrAdd` может вызвать фабрику дважды, что делать, если словарь стал узким местом.

## Чем `ConcurrentDictionary` отличается от обычного `Dictionary`?

```yaml
category: multithreading
level: middle
difficulty: 3
slug: multithreading-chem-concurrentdictionary-otlichaetsya-ot-obychnogo-dictionary
tags: collections, threading
```

`Dictionary<TKey, TValue>` не потокобезопасен при записи: параллельные изменения могут повредить внутренние структуры. `ConcurrentDictionary` рассчитан на одновременный доступ: чтение без блокировок, запись под мелкими блокировками на группы корзин, плюс атомарные составные операции. Цена — больше памяти и медленнее однопоточный доступ.

| | `Dictionary` | `ConcurrentDictionary` |
| --- | --- | --- |
| Параллельное чтение без записей | безопасно | безопасно |
| Параллельная запись | повреждение данных, исключения, зацикливание | безопасно |
| Составные операции | нет | `GetOrAdd`, `AddOrUpdate`, `TryUpdate`, `TryRemove` |
| Перечисление при изменении | `InvalidOperationException` | не бросает, но не снимок |
| `Count` | O(1) | берёт все блокировки |
| Память | массив корзин + массив entries (struct) | отдельный объект-узел на каждую запись + массив блокировок |
| Однопоточная скорость | выше | ниже, особенно на добавлении |

**Что бывает с `Dictionary` при гонке.** Одновременные `Add` из двух потоков могут испортить цепочки корзин. Исторически это приводило к бесконечному циклу в `FindEntry` — поток навсегда застревал на 100 % CPU. Современные версии .NET в ряде таких случаев обнаруживают повреждение и бросают `InvalidOperationException` о параллельной операции, но полагаться на это нельзя: поведение не определено.

**Почему нельзя «просто взять `Dictionary` под `lock`»?** Можно — и это нормальное решение, если:

- записей мало и конкуренция низкая;
- нужно атомарно изменить словарь вместе с другими полями — тогда `lock` всё равно нужен, и `ConcurrentDictionary` ничего не добавит.

`ConcurrentDictionary` выигрывает, когда много потоков читают и пишут одновременно: читатели вообще не блокируются, а писатели в разные группы корзин не мешают друг другу.

**Ловушки миграции с `Dictionary`:**

```csharp
// Было — корректно в однопоточном коде, гонка в многопоточном
if (!dict.TryGetValue(key, out var v))
{
    v = Create(key);
    dict[key] = v;
}

// Стало
var v = dict.GetOrAdd(key, Create);   // Create может вызваться больше одного раза!
```

- фабрики в `GetOrAdd`/`AddOrUpdate` выполняются вне блокировки и могут сработать несколько раз;
- `AddOrUpdate` с мутацией существующего объекта (`(_, list) => { list.Add(x); return list; }`) не потокобезопасна — сам `list` не защищён;
- LINQ по словарю (`dict.Count()`, `.ToList()`) работает через перечисление и видит «плавающее» состояние.

**Выбор:** один поток или данные не меняются после построения — `Dictionary` или `FrozenDictionary`; редкие записи с согласованностью нескольких полей — `Dictionary` + `lock`; много параллельных читателей и писателей — `ConcurrentDictionary`.

**Что спросят дальше:** как устроены lock striping и чтение без блокировок, почему фабрика вызывается дважды, чем `ImmutableDictionary` отличается от обоих.

## Какие существуют thread-safe коллекции?

```yaml
category: multithreading
level: middle
difficulty: 2
slug: multithreading-kakie-suschestvuyut-thread-safe-kollekcii
tags: collections, threading
```

Основные потокобезопасные коллекции живут в `System.Collections.Concurrent`: `ConcurrentDictionary`, `ConcurrentQueue`, `ConcurrentStack`, `ConcurrentBag`, `BlockingCollection`. К ним добавляются `Channel<T>` для асинхронного producer-consumer и неизменяемые коллекции из `System.Collections.Immutable` и `System.Collections.Frozen`, которые безопасны для чтения из любых потоков.

| Коллекция | Модель | Когда использовать |
| --- | --- | --- |
| `ConcurrentDictionary<K,V>` | ключ-значение, чтение без блокировок | общий кэш, реестр |
| `ConcurrentQueue<T>` | FIFO, lock-free | очередь задач, буфер сообщений |
| `ConcurrentStack<T>` | LIFO, lock-free | пул объектов, где важен LIFO |
| `ConcurrentBag<T>` | неупорядоченная, локальные списки на поток | один и тот же поток и кладёт, и забирает |
| `BlockingCollection<T>` | обёртка над `IProducerConsumerCollection<T>` с ограничением и блокирующим ожиданием | синхронный producer-consumer |
| `Channel<T>` | асинхронная очередь с bounded/unbounded режимом | producer-consumer в async-коде |
| `ImmutableList<T>`, `ImmutableDictionary<K,V>` | изменение возвращает новую коллекцию | снимки, которые передаются между потоками |
| `FrozenDictionary<K,V>`, `FrozenSet<T>` (.NET 8) | неизменяемые, оптимизированы под чтение | справочники, созданные один раз |

**Общий стиль API — `Try*`.** Методы `TryDequeue`, `TryPop`, `TryTake`, `TryAdd` объединяют проверку и действие в одну атомарную операцию. Проверка `Count > 0` перед извлечением бессмысленна: к моменту извлечения элемента может уже не быть.

```csharp
var queue = new ConcurrentQueue<Job>();
queue.Enqueue(job);

while (queue.TryDequeue(out var next))
    Process(next);
```

**Нюансы, о которых спрашивают:**

- `ConcurrentBag<T>` быстр только когда поток забирает свои же элементы; при сценарии «одни пишут, другие читают» он заметно медленнее `ConcurrentQueue` из-за кражи из чужих локальных списков;
- `BlockingCollection<T>` блокирует потоки на `Take`/`Add` — в async-коде вместо неё `Channel<T>`;
- `Count` и перечисление у concurrent-коллекций — «моментальный снимок в прошлом»; у `ConcurrentDictionary` `Count` к тому же берёт все блокировки;
- неизменяемые коллекции потокобезопасны на чтение, но переменная, которая хранит «текущую версию», — нет: её заменяют через `Interlocked.Exchange`/`ImmutableInterlocked` или под `lock`.

**Чего нет в BCL:** потокобезопасного `List<T>` с индексами (операции по индексу плохо сочетаются с конкурентными изменениями). `SynchronizedCollection<T>` существует только как наследие WCF, а устаревшие `ArrayList.Synchronized`/`Hashtable.Synchronized` дают лишь поштучную синхронизацию методов, не спасая от check-then-act.

**Что спросят дальше:** чем `ConcurrentDictionary` отличается от `Dictionary` под `lock`, когда `Channel<T>` лучше `BlockingCollection`, что такое backpressure.

## Что такое deadlock?

```yaml
category: multithreading
level: middle
difficulty: 2
slug: multithreading-chto-takoe-deadlock
tags: deadlock, synchronization
```

Deadlock (взаимная блокировка) — ситуация, когда два или более потока бесконечно ждут друг друга: каждый держит ресурс, нужный другому, и ждёт ресурс, который держит другой. Ни один не может продолжить, и без внешнего вмешательства это не разрешится.

```csharp
object a = new(), b = new();

// Поток 1
lock (a) { Thread.Sleep(10); lock (b) { /* ... */ } }

// Поток 2
lock (b) { Thread.Sleep(10); lock (a) { /* ... */ } }
```

Поток 1 держит `a` и ждёт `b`, поток 2 держит `b` и ждёт `a` — навсегда.

**Как выглядит в продакшене:**

- запросы перестают завершаться, но процесс жив;
- CPU почти нулевой — потоки спят, а не работают (этим deadlock отличается от livelock и бесконечного цикла);
- число потоков пула растёт, если заблокированы именно они, — пул пытается компенсировать.

**Самые частые источники в .NET:**

1. **Разный порядок захвата блокировок** — как в примере выше.
2. **Sync-over-async** — `.Result` или `.Wait()` в потоке с однопоточным `SynchronizationContext` (UI, классический ASP.NET): продолжение `await` ждёт освобождения этого потока, а поток ждёт продолжения.
3. **Вызов чужого кода под блокировкой** — событие или колбэк, который берёт другую блокировку или синхронно ждёт того, кто ждёт вас.
4. **Блокировка в БД** — две транзакции обновляют строки в разном порядке; СУБД обнаружит это и откатит одну (в SQL Server — ошибка 1205, в PostgreSQL — `deadlock detected`).

**Почему CLR не спасает.** В отличие от СУБД, CLR не ищет циклы ожидания и не разрывает их: `lock` будет ждать вечно. Защита только в дизайне кода: единый порядок захвата, короткие секции без внешних вызовов, таймауты (`Monitor.TryEnter`, `SemaphoreSlim.WaitAsync(timeout)`), отсутствие блокирующего ожидания асинхронного кода.

**Как найти.** Снять дамп (`dotnet-dump collect`), затем `dotnet-dump analyze` и команды `clrstack -all` / `syncblk`: видно, какой поток держит какую блокировку и на чём стоят остальные. В Visual Studio — окно Parallel Stacks, которое прямо подсвечивает deadlock.

**Что спросят дальше:** какие условия необходимы для deadlock (условия Коффмана), как его избежать, почему `.Result` в ASP.NET Core «работает», а в WinForms — нет.

## Как возникает deadlock?

```yaml
category: multithreading
level: middle
difficulty: 3
slug: multithreading-kak-voznikaet-deadlock
tags: deadlock, synchronization
```

Deadlock возникает, когда одновременно выполнены четыре условия Коффмана: взаимное исключение, удержание с ожиданием, отсутствие принудительного отъёма ресурса и циклическое ожидание. Если разрушить хотя бы одно, взаимная блокировка невозможна — на этом строятся все способы защиты.

| Условие | Смысл | Как выглядит в .NET |
| --- | --- | --- |
| Mutual exclusion | ресурсом владеет один | `lock`, `Mutex`, `SemaphoreSlim(1,1)`, строка в БД под `UPDATE` |
| Hold and wait | держу один ресурс и жду другой | вложенные `lock` |
| No preemption | ресурс нельзя отобрать | `lock` не освобождается, пока владелец сам не выйдет |
| Circular wait | цикл в графе ожиданий | A ждёт B, B ждёт A |

**Сценарий 1 — разный порядок захвата.** Метод `Transfer(from, to)` блокирует сначала `from`, затем `to`. Два одновременных перевода A→B и B→A захватят первые блокировки и будут ждать друг друга.

```csharp
void Transfer(Account from, Account to, decimal amount)
{
    lock (from.Sync)
    lock (to.Sync)          // при встречных переводах — цикл
    {
        from.Balance -= amount;
        to.Balance += amount;
    }
}
```

**Сценарий 2 — sync-over-async с контекстом.** В UI-потоке вызывается `GetAsync().Result`. Внутри `await` захватил `SynchronizationContext` и хочет продолжить в UI-потоке. UI-поток заблокирован на `.Result`. Здесь «ресурс» — единственный поток контекста, а цикл: поток ждёт задачу, задача ждёт поток.

**Сценарий 3 — скрытая блокировка под lock.** Под своей блокировкой код поднимает событие; обработчик синхронно вызывает метод другого компонента, который берёт свою блокировку и в другом потоке ждёт первую. Порядок захвата никто явно не нарушал — он «размазан» по компонентам.

**Сценарий 4 — голодание пула, похожее на deadlock.** Все потоки пула синхронно ждут задач, которые стоят в очереди того же пула и не могут начаться, потому что свободных потоков нет. Формально это не вечный deadlock: пул медленно добавит потоки. Но при постоянной нагрузке система так и не выходит из этого состояния.

**Сценарий 5 — ресурсы вне процесса.** Две транзакции обновляют строки в разном порядке; либо код держит `lock` в памяти и ждёт строку в БД, которую держит другой экземпляр сервиса, ожидающий этот же `lock`. СУБД обнаружит только цикл внутри себя, смешанный цикл «память + БД» не обнаружит никто.

**Почему он проявляется редко.** Для deadlock нужно, чтобы оба потока успели захватить первый ресурс до второго — узкое окно по времени. Под нагрузкой и на большем числе ядер окно «попадается» чаще, поэтому баг всплывает в продакшене.

**Что спросят дальше:** как разрушить каждое из условий на практике, как диагностировать по дампу, чем deadlock отличается от livelock и starvation.

## Как избежать deadlock?

```yaml
category: multithreading
level: middle
difficulty: 4
slug: multithreading-kak-izbezhat-deadlock
tags: deadlock, synchronization
```

Надёжный способ — сделать цикл ожидания невозможным по построению: захватывать блокировки в едином глобальном порядке, не держать блокировку при вызове чужого кода и не ждать синхронно асинхронные операции. Таймауты и детекторы — второй рубеж: они превращают вечное зависание в ошибку, которую видно.

**1. Единый порядок захвата (разрушаем circular wait).**

```csharp
void Transfer(Account from, Account to, decimal amount)
{
    var (first, second) = from.Id < to.Id ? (from, to) : (to, from);
    lock (first.Sync)
    lock (second.Sync)
    {
        from.Balance -= amount;
        to.Balance += amount;
    }
}
```

Порядок может задаваться идентификатором, уровнем в иерархии («сначала репозиторий, потом кэш»), но он должен соблюдаться везде. Тот же приём работает в БД: обновлять строки в порядке первичного ключа.

**2. Одна блокировка вместо нескольких (разрушаем hold and wait).** Часто достаточно одной, более крупной блокировки: чуть больше contention, зато deadlock невозможен. Мелкозернистые блокировки вводят только тогда, когда профилирование показало узкое место.

**3. Не вызывать чужой код под блокировкой.** События, колбэки, виртуальные методы, логгеры с синхронными sink'ами — всё это может взять свою блокировку. Шаблон: под `lock` скопировать нужное состояние, выйти, затем вызвать обработчики.

```csharp
EventHandler? handler;
lock (_sync) { _state = newState; handler = Changed; }
handler?.Invoke(this, EventArgs.Empty);   // уже без блокировки
```

**4. Не блокироваться на async-коде.** Никаких `.Result`, `.Wait()`, `GetAwaiter().GetResult()` над асинхронными методами — «async all the way». В библиотеках `ConfigureAwait(false)` снижает риск для вызывающих, у которых есть `SynchronizationContext`, но не заменяет отказ от sync-over-async.

**5. Таймауты (разрушаем no preemption «мягко»).** `Monitor.TryEnter(obj, timeout)`, `Lock.TryEnter(timeout)`, `SemaphoreSlim.WaitAsync(timeout, ct)`. При неудаче — отпустить уже захваченное, залогировать и повторить с backoff или вернуть ошибку. Это не исправляет дизайн, но делает проблему наблюдаемой.

**6. Меньше разделяемого состояния.** Актор или один поток-владелец данных, общение через `Channel<T>`; неизменяемые снимки вместо изменяемых структур; атомарные операции concurrent-коллекций вместо самописной синхронизации. Нет блокировок — нет deadlock.

**7. Асинхронные блокировки тоже блокируют.** `SemaphoreSlim` не реентерабелен: если метод под `await _gate.WaitAsync()` вызывает другой метод, который ждёт тот же `_gate`, получится самоблокировка. Внутренние методы, вызываемые под блокировкой, не должны брать её снова.

**Проверка и диагностика:**

- код-ревью на вложенные блокировки и вызовы наружу из-под `lock`;
- стресс-тесты с таймаутом на весь тест: зависание = упавший тест;
- в продакшене — дамп и `dotnet-dump analyze` → `syncblk`, `clrstack -all`; в Visual Studio окно Parallel Stacks;
- для БД — включённое логирование deadlock'ов и повтор транзакции при ошибке deadlock (для СУБД это штатная ситуация).

**Чего не делать:** не лечить deadlock увеличением `ThreadPool.SetMinThreads` или `Thread.Sleep` «чтобы успело» — это меняет тайминги и прячет проблему до следующего всплеска нагрузки.

**Что спросят дальше:** условия Коффмана, почему `.Result` зависает в UI и не зависает в ASP.NET Core, чем помогает `Channel<T>` в архитектуре без блокировок.

## Что такое livelock?

```yaml
category: multithreading
level: middle
difficulty: 2
slug: multithreading-chto-takoe-livelock
tags: synchronization
```

Livelock — ситуация, когда потоки не заблокированы и активно работают, но не продвигаются: они постоянно реагируют на действия друг друга и откатывают свои. В отличие от deadlock, CPU при livelock загружен, а полезной работы нет.

**Бытовая аналогия.** Двое в узком коридоре одновременно шагают в одну сторону, чтобы уступить дорогу, потом одновременно в другую — и так бесконечно.

**Пример в коде** — «вежливый» захват двух блокировок с откатом:

```csharp
void DoWork(object first, object second)
{
    while (true)
    {
        lock (first)
        {
            if (Monitor.TryEnter(second))
            {
                try { Work(); return; }
                finally { Monitor.Exit(second); }
            }
        }
        // не удалось — отпускаем first и сразу пробуем снова
    }
}
// Поток 1: DoWork(a, b); Поток 2: DoWork(b, a)
```

Оба потока захватывают свою первую блокировку, не получают вторую, отпускают, повторяют — синхронно, в одном ритме. Deadlock мы убрали (никто не ждёт вечно), но получили livelock.

**Где встречается на практике:**

- **CAS-циклы под высокой конкуренцией** — потоки постоянно перезаписывают значение друг у друга, и у каждого `CompareExchange` чаще проваливается, чем проходит; в крайнем случае прогресс надолго останавливается у отдельных потоков;
- **ретраи без jitter** — сотни клиентов получили ошибку в один момент и повторяют запрос через одинаковое время, снова перегружая сервис;
- **оптимистичные транзакции** — конфликтующие обновления бесконечно откатывают друг друга;
- **сообщения, которые возвращаются в очередь** — обработчик падает, сообщение снова в начале очереди, обработчик снова падает.

**Как лечить:**

- **случайная задержка (jitter) и экспоненциальный backoff** — разбивает синхронный ритм; в .NET есть `SpinWait` для коротких ожиданий, Polly для ретраев с jitter;
- **единый порядок захвата** — тогда откат вообще не нужен;
- **ограничение числа попыток** — после N неудач перейти на пессимистичную блокировку или вернуть ошибку;
- **dead-letter queue** для «отравленных» сообщений.

**Как отличить в диагностике:** при deadlock потоки стоят в `Monitor.Enter`/`WaitOne`, CPU около нуля; при livelock стеки постоянно меняются, CPU высокий, а счётчики завершённых операций не растут.

**Что спросят дальше:** чем livelock отличается от starvation, почему наивный CAS-цикл может не завершиться, зачем jitter в retry-политиках.

## Что такое starvation?

```yaml
category: multithreading
level: middle
difficulty: 2
slug: multithreading-chto-takoe-starvation
tags: threading
```

Starvation (голодание) — ситуация, когда поток или задача долго или бесконечно не получает нужный ресурс, хотя система в целом работает и другие потоки прогрессируют. Причина — несправедливое распределение: ресурс постоянно достаётся кому-то другому.

**Отличие от соседних проблем:**

| | Кто страдает | Прогресс системы | CPU |
| --- | --- | --- | --- |
| Deadlock | участники цикла, навсегда | нет у участников | около нуля |
| Livelock | участники, крутятся без толку | нет | высокий |
| Starvation | отдельные потоки/задачи | есть у остальных | любой |

**Типичные источники:**

- **Несправедливые блокировки.** `lock`/`Monitor` не гарантирует FIFO: поток, только что освободивший блокировку, часто сразу же захватывает её снова, пока разбуженный ожидающий ещё просыпается. При плотном цикле захватов отдельные потоки могут ждать очень долго.
- **Писатели в reader-writer блокировке.** Если читатели идут непрерывным потоком, писатель может никогда не дождаться момента без читателей. `ReaderWriterLockSlim` это смягчает: ожидающий писатель блокирует допуск новых читателей.
- **Приоритеты потоков.** Высокоприоритетные потоки вытесняют низкоприоритетные. ОС применяют динамическое повышение приоритета, но менять `Thread.Priority` в серверном коде без веской причины не стоит.
- **ThreadPool starvation** — самый частый случай в .NET: потоки пула заняты блокирующим ожиданием, новые задачи (включая продолжения `await`) стоят в очереди, а пул добавляет потоки медленно. Проявляется как рост задержек и `threadpool-queue-length` при низкой загрузке CPU.
- **Долгие задачи в общей очереди.** Тяжёлые операции, поставленные в тот же пул или ту же очередь `Channel<T>`, задерживают короткие.

**Как бороться:**

- не блокировать потоки пула: async all the way, долгую блокирующую работу — в выделенный поток (`TaskCreationOptions.LongRunning`);
- справедливые очереди: `SemaphoreSlim.WaitAsync` обслуживает асинхронных ожидающих по очереди; для строгой очерёдности — `Channel<T>` с одним потребителем;
- разделение нагрузки: отдельные очереди или лимиты (bulkhead) для тяжёлых и лёгких операций, чтобы одни не вытесняли другие;
- короткие критические секции — меньше времени удержания, меньше шансов, что кто-то «проиграет» много раз подряд.

**Что спросят дальше:** как распознать ThreadPool starvation в метриках, чем голодание отличается от нехватки CPU, почему `lock` в .NET не FIFO.

## Что такое lock contention?

```yaml
category: multithreading
level: middle
difficulty: 2
slug: multithreading-chto-takoe-lock-contention
tags: synchronization, threading
```

Lock contention (конкуренция за блокировку) — ситуация, когда несколько потоков одновременно пытаются захватить одну и ту же блокировку, и часть из них вынуждена ждать. Небольшая конкуренция нормальна; высокая превращает блокировку в узкое место, через которое работа проходит последовательно, сколько бы ядер ни было.

**Почему это дорого.** Незаспоренный `lock` — один атомарный CAS, десятки наносекунд. Заспоренный:

1. поток крутится в spin-wait, сжигая CPU в надежде, что владелец скоро выйдет;
2. не дождавшись — засыпает на объекте ядра: системный вызов и context switch;
3. при освобождении его нужно разбудить — ещё один переход через ядро, и поток ещё какое-то время ждёт своей очереди на CPU;
4. кэш-линия с состоянием блокировки постоянно перемещается между ядрами.

В итоге критическая секция, которая сама длится 100 нс, под конкуренцией обходится в микросекунды на вход.

**Признаки:**

- пропускная способность перестаёт расти (или падает) при добавлении ядер и потоков;
- CPU загружен не полностью, а задержки растут;
- счётчик `monitor-lock-contention-count` в `dotnet-counters` быстро растёт;
- в профилировщике много времени в `Monitor.Enter`/`Lock.Enter`, `SpinWait`, `WaitHandle.Wait`.

```bash
dotnet-counters monitor -p <pid> --counters System.Runtime
# смотреть на Monitor Lock Contention Count (в секунду) и ThreadPool Queue Length
```

**Как снижать:**

| Приём | Идея |
| --- | --- |
| укоротить критическую секцию | вычисления, I/O, логирование, аллокации — вне `lock` |
| разделить блокировку (lock striping) | несколько блокировок на разные части данных, как в `ConcurrentDictionary` |
| шардирование состояния | счётчик на поток/ядро, суммирование при чтении |
| read-mostly данные | неизменяемый снимок + атомарная замена ссылки, читатели без блокировок |
| атомарные операции | `Interlocked` вместо `lock` для одиночной переменной |
| готовые concurrent-коллекции | вместо `Dictionary`/`Queue` под общим `lock` |
| батчинг | собирать изменения локально и применять пачкой под одним захватом |

**Важно не перепутать.** Высокий contention часто — симптом, а не причина: например, под `lock` делается синхронный сетевой вызов. Тогда правильное решение — убрать I/O из-под блокировки, а не менять примитив.

**Что спросят дальше:** какие метрики и инструменты показывают contention, что такое lock convoy, когда lock-free реально помогает.

## Что такое atomic operation?

```yaml
category: multithreading
level: middle
difficulty: 2
slug: multithreading-chto-takoe-atomic-operation
tags: threading
```

Атомарная операция — это операция, которая для других потоков выглядит неделимой: они видят либо состояние до неё, либо после, но никогда промежуточное. Если операция не атомарна, другой поток может вклиниться между её шагами и увидеть или испортить «половину» результата.

**Что атомарно в .NET само по себе.** Спецификация CLI (ECMA-335) гарантирует атомарность чтения и записи для правильно выровненных значений не больше размера указателя:

| Операция | Атомарна? |
| --- | --- |
| чтение/запись `int`, `bool`, `char`, `float`, ссылки | да |
| чтение/запись `long`, `double` в 64-битном процессе | на практике да (выровнены, размер = указатель) |
| чтение/запись `long`, `double` в 32-битном процессе | **нет** — может быть «разорванное» значение |
| чтение/запись `decimal`, `Guid`, большой `struct` | **нет** |
| `x++`, `x += y`, `x = x * 2` | **нет** — чтение + изменение + запись |
| `if (x == null) x = new()` | **нет** — проверка и действие разделены |

**Torn read.** Если структура из двух полей копируется в одном потоке, а читается в другом, читатель может получить первое поле из нового значения, а второе из старого.

```csharp
struct Range { public long Start, End; }
private Range _range;          // запись _range не атомарна

// Поток A: _range = new Range { Start = 10, End = 20 };
// Поток B может увидеть Start = 10, End = 0
```

**Как получить атомарность составных операций:**

- `Interlocked` — `Increment`, `Add`, `Exchange`, `CompareExchange` для одной переменной;
- `Interlocked.Read(ref long)` — атомарное чтение 64-битного значения в 32-битном процессе;
- замена ссылки на неизменяемый объект — сама запись ссылки атомарна, поэтому `_range = new RangeObj(10, 20)` для `class`/`record` безопасна (при корректной публикации через `Volatile.Write`);
- `lock` — для всего остального, где инвариант охватывает несколько полей.

**Атомарность ≠ видимость ≠ порядок.** Атомарная запись `int` гарантирует, что никто не увидит «половину» числа, но не гарантирует, что другой поток увидит новое значение сразу или в нужном порядке относительно других записей. Для этого нужны барьеры: `Volatile.Read/Write`, `Interlocked` (полный барьер) или `lock`.

**Как это делает процессор.** На x86 атомарные read-modify-write — инструкции с префиксом `lock` (`lock xadd`, `lock cmpxchg`); на ARM64 — атомарные инструкции LSE или пара load-exclusive/store-exclusive. Процессор удерживает кэш-линию в эксклюзивном состоянии на время операции.

**Что спросят дальше:** почему `volatile int` не делает `++` атомарным, как устроен CAS, почему `long` в 32-битном процессе опасен.

## Что такое memory barrier?

```yaml
category: multithreading
level: middle
difficulty: 2
slug: multithreading-chto-takoe-memory-barrier
tags: synchronization
```

Барьер памяти (memory barrier, fence) — инструкция, которая запрещает компилятору и процессору переставлять обращения к памяти через определённую точку. Он нужен потому, что ради производительности и JIT, и CPU меняют порядок чтений и записей, и другой поток может наблюдать их не в том порядке, в котором они написаны в коде.

**Откуда перестановки:**

- **JIT/компилятор** — выносит чтение из цикла, держит значение в регистре, меняет порядок независимых операций;
- **процессор** — буфер записи (store buffer) задерживает записи, спекулятивно выполняет чтения раньше; на ARM модель памяти слабая и допускает почти любые перестановки независимых операций.

**Виды барьеров:**

| Барьер | Что запрещает | В .NET |
| --- | --- | --- |
| acquire (при чтении) | переносить последующие операции до чтения | `Volatile.Read`, чтение `volatile`-поля |
| release (при записи) | переносить предыдущие операции после записи | `Volatile.Write`, запись `volatile`-поля |
| full fence | любые перестановки через точку | `Interlocked.*`, `Thread.MemoryBarrier()`, вход/выход из `lock` |

**Классический пример — публикация данных через флаг:**

```csharp
private int _data;
private bool _ready;

// Поток A
_data = 42;
Volatile.Write(ref _ready, true);   // release: _data запишется раньше флага

// Поток B
if (Volatile.Read(ref _ready))      // acquire: _data прочитается после флага
    Console.WriteLine(_data);       // гарантированно 42
```

Без барьеров на ARM поток B может увидеть `_ready == true` и старое `_data == 0`. На x86 процессор сам не переставляет запись-запись и чтение-чтение, но JIT всё равно вправе переставить или закэшировать обращения — поэтому барьер нужен и там.

**Где барьеры уже есть без вашего участия:**

- `lock`/`Monitor.Enter`/`Exit`, `System.Threading.Lock`;
- все методы `Interlocked`;
- `Task`: запуск, завершение и `await` устанавливают happens-before между кодом до и после;
- `SemaphoreSlim`, `ManualResetEventSlim`, concurrent-коллекции.

Поэтому в обычном коде, который синхронизируется через эти примитивы, ручные барьеры не нужны. Они появляются в низкоуровневом lock-free коде.

**Чего барьер не делает:** не делает операции атомарными и не «сбрасывает кэши» — кэши CPU когерентны аппаратно. Барьер управляет только порядком, в котором операции текущего потока становятся видимыми и выполняются.

**Что спросят дальше:** чем `volatile` отличается от полного барьера, почему код, корректный на x86, ломается на ARM, что гарантирует модель памяти .NET.

## Что такое false sharing?

```yaml
category: multithreading
level: middle
difficulty: 2
slug: multithreading-chto-takoe-false-sharing
tags: threading
```

False sharing — ситуация, когда потоки на разных ядрах пишут в **разные** переменные, но эти переменные лежат в **одной кэш-линии** (обычно 64 байта). Логически данные не общие, а для процессора — общие: линия постоянно перескакивает между ядрами, и код, который должен масштабироваться линейно, замедляется в разы.

**Почему так происходит.** Когерентность кэшей (протокол MESI и его варианты) работает с целыми кэш-линиями, а не с отдельными байтами. Чтобы записать в линию, ядро должно получить её в эксклюзивное владение и инвалидировать копии у остальных. Если два ядра по очереди пишут в соседние поля, каждая запись — это промах и пересылка линии через межъядерную шину.

```csharp
// Каждый поток пишет только в свой элемент — гонок нет,
// но 8 long подряд занимают одну 64-байтную линию
var counters = new long[Environment.ProcessorCount];

Parallel.For(0, counters.Length, i =>
{
    for (int n = 0; n < 100_000_000; n++)
        counters[i]++;          // линия «пинг-понгом» ходит между ядрами
});
```

**Как исправить:**

- **разнести данные** по разным линиям — паддинг до 64, а лучше 128 байт (соседние линии часто подкачиваются парами, а на Apple M-series линия и так 128 байт):

```csharp
[StructLayout(LayoutKind.Explicit, Size = 128)]
struct PaddedLong { [FieldOffset(0)] public long Value; }

var counters = new PaddedLong[Environment.ProcessorCount];
```

- **копить локально и сливать один раз** — локальная переменная в цикле, а в общий массив запись в конце; `Parallel.For` с `localInit`/`localFinally` ровно для этого;
- **не хранить рядом горячие поля**, которые пишут разные потоки, — например, индексы головы и хвоста очереди.

**Где это встречается на практике:** массивы per-thread счётчиков, поля `_head`/`_tail` в самописных очередях, соседние объекты, выделенные подряд (аллокатор .NET кладёт их рядом в памяти). BCL сама борется с этим: `ConcurrentQueue<T>` разносит индексы сегмента через внутренние padding-структуры.

**Чего не путать:** false sharing — не баг корректности, результат будет правильным. Это чисто проблема производительности, и она не видна в коде — только в профилировщике или бенчмарке, где добавление потоков не ускоряет, а замедляет работу.

**Что спросят дальше:** как обнаружить false sharing в реальном приложении, что такое true sharing и почему шардирование счётчика помогает.

## Как правильно синхронизировать доступ к общему состоянию?

```yaml
category: multithreading
level: middle
difficulty: 3
slug: multithreading-kak-pravilno-sinhronizirovat-dostup-k-obschemu-sostoyaniyu
tags: synchronization
```

Лучшая синхронизация — та, которой нет: сначала попытаться **убрать общее изменяемое состояние** (неизменяемость, владение одним потоком, передача сообщений), и только потом защищать его — одним механизмом на один инвариант, с минимальной критической секцией.

**Порядок выбора, от простого к сложному:**

| Подход | Когда подходит |
| --- | --- |
| не делить состояние | данные локальны для запроса/задачи, результаты сливаются в конце |
| неизменяемые объекты + замена ссылки | конфигурация, кэш «читают все, меняют редко» |
| одна переменная — `Interlocked` | счётчики, флаги, CAS-переход состояния |
| готовая concurrent-коллекция | словарь, очередь, bag с независимыми операциями |
| `lock` / `System.Threading.Lock` | несколько полей образуют один инвариант |
| `SemaphoreSlim.WaitAsync` | внутри критической секции нужен `await` |
| `Channel<T>` / один поток-владелец | сложное состояние, которое проще сериализовать через очередь |

**Правила, которые делают `lock` корректным:**

- **все** обращения к защищаемым данным — и записи, и чтения — идут под одной и той же блокировкой; «читаю без lock, это же просто чтение» ломает инвариант;
- объект блокировки приватный и `readonly`; в .NET 9+ — `private readonly Lock _lock = new();`;
- внутри — только работа с состоянием: без I/O, без вызова чужого кода (колбэков, событий, виртуальных методов), без `await`;
- check-then-act делается целиком внутри одной секции.

```csharp
public sealed class Account
{
    private readonly Lock _lock = new();
    private decimal _balance;

    public bool TryWithdraw(decimal amount)
    {
        lock (_lock)
        {
            if (_balance < amount) return false;   // проверка и действие
            _balance -= amount;                    // под одной блокировкой
            return true;
        }
    }

    public decimal Balance { get { lock (_lock) return _balance; } }
}
```

**Типичные ошибки:**

- `lock (this)`, `lock (typeof(X))`, `lock ("строка")` — объект доступен снаружи, кто угодно может захватить его и устроить deadlock;
- concurrent-коллекция считается «потокобезопасной целиком»: `if (!dict.ContainsKey(k)) dict[k] = ...` — всё равно гонка, нужны атомарные `GetOrAdd`/`TryAdd`;
- наружу отдаётся ссылка на внутренний `List<T>` — после этого lock ничего не защищает; возвращайте копию или неизменяемый снимок;
- несколько блокировок без фиксированного порядка захвата — прямая дорога к deadlock.

**Инкапсуляция — главное.** Синхронизация должна жить внутри класса, который владеет состоянием, а не размазываться по вызывающему коду. Тогда корректность проверяется чтением одного файла.

**Что спросят дальше:** когда `Interlocked`, а когда `lock`; чем плох `lock (this)`; как быть, если внутри нужен `await`.

## Можно ли использовать `lock` с `async/await`?

```yaml
category: multithreading
level: middle
difficulty: 3
slug: multithreading-mozhno-li-ispolzovat-lock-s-async-await
tags: async, synchronization
```

В одном методе — да, но `await` **внутри** тела `lock` запрещён: компилятор выдаёт ошибку CS1996 «Cannot await in the body of a lock statement». Можно брать `lock` до или после `await`, если критическая секция целиком синхронная.

```csharp
public async Task UpdateAsync()
{
    var data = await LoadAsync();      // await — снаружи lock

    lock (_lock)
    {
        _cache = data;                 // короткая синхронная секция — нормально
    }

    await SaveAsync(data);             // и снова снаружи
}
```

Это вполне рабочий и частый паттерн: асинхронный I/O выполняется без блокировки, а под `lock` — только быстрая работа с общим состоянием в памяти.

**Почему компилятор запрещает `await` внутри.** `Monitor` привязан к потоку-владельцу: `Exit` должен вызвать тот же поток, что вызвал `Enter`. После `await` продолжение может выполниться на другом потоке пула — и освобождать блокировку будет уже не её владелец. Подробности — в соседнем вопросе.

**Обходы, которые не работают:**

- `Monitor.Enter` / `Monitor.Exit` вручную вокруг `await` — компилируется, но на `Exit` в другом потоке получите `SynchronizationLockException`, а блокировка останется захваченной навсегда;
- `System.Threading.Lock` (.NET 9) не решает проблему: `lock` по нему запрещает `await` так же, а `Lock.Scope` — `ref struct`, его нельзя пронести через `await`;
- `.Wait()` / `.Result` внутри `lock`, чтобы «сделать синхронно», — держит блокировку и поток всё время I/O и рискует deadlock.

**Если асинхронная операция действительно должна быть в критической секции** (например, «проверить кэш, если нет — сходить в БД и положить»), используйте асинхронный примитив — `SemaphoreSlim(1, 1)` с `WaitAsync`:

```csharp
private readonly SemaphoreSlim _gate = new(1, 1);

await _gate.WaitAsync(ct);
try   { _cache ??= await LoadAsync(ct); }
finally { _gate.Release(); }
```

**Что проверить в коде ревью:** нет ли вызова async-метода внутри `lock` через `.GetAwaiter().GetResult()`, не освобождается ли семафор вне `finally`, не держится ли блокировка на время сетевого вызова, когда можно сначала загрузить данные, а потом коротко обновить состояние.

**Что спросят дальше:** почему именно `await` в `lock` опасен, чем заменить `lock` для асинхронного кода, реентерабелен ли `SemaphoreSlim`.

## Почему нельзя делать `await` внутри обычного `lock`?

```yaml
category: multithreading
level: middle
difficulty: 4
slug: multithreading-pochemu-nelzya-delat-await-vnutri-obychnogo-lock
tags: async, synchronization
```

Потому что `lock` (`Monitor`) — блокировка с **потоковой привязкой**: владелец запоминается как конкретный поток, и освободить её может только он. Асинхронный метод после `await` может продолжиться на любом другом потоке, и тогда `Monitor.Exit` вызовет не владелец. Компилятор это знает и запрещает конструкцию (CS1996).

**Во что разворачивается `lock`:**

```csharp
bool taken = false;
try
{
    Monitor.Enter(_obj, ref taken);   // владелец = текущий поток (ID в thin lock / sync block)
    // тело
}
finally
{
    if (taken) Monitor.Exit(_obj);    // проверяет, что вызывает владелец
}
```

А async-метод компилятор превращает в state machine: код до `await` выполняется в одном вызове `MoveNext`, код после — в другом, который планировщик запустит на свободном потоке пула (если нет `SynchronizationContext`).

**Что пошло бы не так, если бы это было разрешено:**

1. **Освобождение не тем потоком.** `Monitor.Exit` из другого потока бросает `SynchronizationLockException`. Блокировка при этом остаётся захваченной исходным потоком — все остальные ждут вечно.
2. **Если продолжение попало на тот же поток**, ещё хуже: поток за время `await` вернулся в пул, выполнял чужие work items, и `Monitor` реентерабелен — любой код на этом потоке, дошедший до того же `lock`, свободно войдёт внутрь, хотя «логический» владелец ещё не закончил. Взаимное исключение нарушено незаметно.
3. **Удержание блокировки на время I/O.** Даже в идеальном мире `lock` на сотни миллисекунд сетевого вызова означает, что все потоки, пришедшие к этой секции, блокируются — это прямой путь к ThreadPool starvation.
4. **Deadlock при захвате в контексте.** С однопоточным `SynchronizationContext` (UI) продолжение ждёт освобождения потока, который ждёт... блокировку, удерживаемую этим же продолжением.

**Ключевая идея для собеседования:** `lock` защищает *поток*, а в асинхронном коде единица работы — *логическая операция*, которая кочует между потоками. Нужен примитив, у которого нет понятия «поток-владелец»: `SemaphoreSlim` считает разрешения, а не владельцев, поэтому `Release` можно вызвать с любого потока.

**Та же проблема у других потоко-привязанных примитивов:** `Mutex` (`ApplicationException`/отказ при освобождении не владельцем), `ReaderWriterLockSlim` (`SynchronizationLockException`), `System.Threading.Lock`. `SpinLock` с включённым отслеживанием владельца тоже проверяет поток.

**Что спросят дальше:** как сделать асинхронную блокировку, почему `SemaphoreSlim` не реентерабелен, как `ConfigureAwait(false)` влияет на поток продолжения.

## Что использовать вместо `lock`, если нужна асинхронная блокировка?

```yaml
category: multithreading
level: middle
difficulty: 3
slug: multithreading-chto-ispolzovat-vmesto-lock-esli-nuzhna-asinhronnaya-blokirovka
tags: synchronization, locking
```

Стандартный ответ — `SemaphoreSlim(1, 1)` с `await WaitAsync()` и `Release()` в `finally`. Но часто лучше вообще не держать блокировку через `await`: вынести I/O за пределы секции, сериализовать работу через `Channel<T>` или использовать `Lazy<Task<T>>` для однократной инициализации.

**Базовый вариант:**

```csharp
private readonly SemaphoreSlim _gate = new(1, 1);

public async Task<Token> GetTokenAsync(CancellationToken ct)
{
    await _gate.WaitAsync(ct);          // не блокирует поток — ждущие висят как задачи
    try
    {
        if (_token is { IsExpired: false }) return _token;
        _token = await _auth.RefreshAsync(ct);
        return _token;
    }
    finally
    {
        _gate.Release();
    }
}
```

**Какой инструмент под какую задачу:**

| Задача | Инструмент |
| --- | --- |
| взаимное исключение вокруг async-кода | `SemaphoreSlim(1, 1)` |
| ограничить параллелизм до N | `SemaphoreSlim(N, N)` или `ConcurrencyLimiter` из `System.Threading.RateLimiting` |
| один раз асинхронно инициализировать | `Lazy<Task<T>>` / `AsyncLazy` |
| блокировка по ключу (на пользователя, на файл) | словарь семафоров с подсчётом ссылок или библиотека (`AsyncKeyedLock`) |
| сложное состояние с разными операциями | один consumer, читающий команды из `Channel<T>` — блокировка не нужна |
| reader/writer в async | `AsyncReaderWriterLock` из Nito.AsyncEx или Microsoft.VisualStudio.Threading |

**Особенности `SemaphoreSlim`, о которых спрашивают:**

- **не реентерабелен** — повторный `WaitAsync` из той же логической операции ждёт сам себя; рекурсию придётся убрать или передавать «я уже внутри»;
- **нет владельца** — `Release` может вызвать кто угодно, лишний `Release` увеличит счётчик выше 1 (для `new(1, 1)` бросит `SemaphoreFullException` — ещё один повод задавать максимум);
- **FIFO не гарантирован** — порядок пробуждения ждущих не обещан документацией;
- `Dispose` обычно не нужен, если не использовался `AvailableWaitHandle`.

**Частая ошибка — `WaitAsync` внутри `try`:**

```csharp
try
{
    await _gate.WaitAsync(ct);   // если отменили до захвата —
    ...
}
finally { _gate.Release(); }     // Release без захвата ломает счётчик
```

`WaitAsync` должен стоять **до** `try`.

**Что спросят дальше:** как сделать блокировку по ключу без утечки семафоров, чем `WaitAsync` лучше `Wait` под нагрузкой, почему Channel иногда проще любой блокировки.

## Что такое `Channel<T>`?

```yaml
category: multithreading
level: middle
difficulty: 2
slug: multithreading-chto-takoe-channel-t
```

`Channel<T>` (пространство имён `System.Threading.Channels`, встроено в .NET Core 3.0+) — потокобезопасная асинхронная очередь для схемы producer/consumer. Писатель кладёт элементы через `ChannelWriter<T>`, читатель забирает через `ChannelReader<T>`, и обе стороны умеют **асинхронно ждать**: читатель — появления данных, писатель — свободного места.

```csharp
var channel = Channel.CreateBounded<Order>(new BoundedChannelOptions(1000)
{
    FullMode = BoundedChannelFullMode.Wait,   // писатель ждёт, если очередь полна
    SingleReader = true
});

// Producer
await channel.Writer.WriteAsync(order, ct);
channel.Writer.Complete();                    // «больше данных не будет»

// Consumer
await foreach (var item in channel.Reader.ReadAllAsync(ct))
    await ProcessAsync(item, ct);             // цикл завершится после Complete и опустошения
```

**Два вида каналов:**

- `Channel.CreateUnbounded<T>()` — без ограничения размера, `WriteAsync` завершается сразу; риск — неограниченный рост памяти, если читатель не успевает;
- `Channel.CreateBounded<T>(capacity)` — с ёмкостью и политикой при переполнении (`FullMode`): `Wait` — ждать места, `DropOldest`, `DropNewest`, `DropWrite` — выбросить элемент.

**Основные API:**

| Сторона | Методы |
| --- | --- |
| writer | `WriteAsync`, `TryWrite` (без ожидания), `WaitToWriteAsync`, `Complete(exception?)` / `TryComplete` |
| reader | `ReadAsync`, `TryRead`, `WaitToReadAsync`, `ReadAllAsync`, `Completion` (задача, завершающаяся, когда канал закрыт и пуст) |

**Чем лучше `BlockingCollection<T>` и `ConcurrentQueue<T>`:**

- `BlockingCollection` ждёт, **блокируя поток**; `Channel` ждёт через `ValueTask`, поток свободен — это важно в async-коде и под нагрузкой;
- `ConcurrentQueue` не умеет ждать вообще — пришлось бы опрашивать в цикле или городить сигналы;
- у канала есть понятие завершения (`Complete`) с передачей ошибки читателю — не нужен отдельный флаг «producer закончил».

**Опции-подсказки для производительности:** `SingleReader`/`SingleWriter = true` позволяют выбрать более дешёвую внутреннюю реализацию; `AllowSynchronousContinuations = true` разрешает выполнять продолжение читателя прямо в потоке писателя — быстрее, но писатель может неожиданно «застрять» в чужом коде.

**Разделение ролей.** Отдавайте потребителю только `ChannelReader<T>`, а производителю — только `ChannelWriter<T>`: так тип явно фиксирует, кто может писать и кто закрывает канал.

**Что спросят дальше:** когда выбирать bounded, как реализовать backpressure, чем канал отличается от очереди сообщений вроде RabbitMQ (он живёт в памяти одного процесса и теряет данные при падении).

## Когда использовать `Channel<T>`?

```yaml
category: multithreading
level: middle
difficulty: 3
slug: multithreading-kogda-ispolzovat-channel-t
```

`Channel<T>` уместен, когда нужно **развязать производителя и потребителя внутри одного процесса**: они работают с разной скоростью, в разных задачах, и между ними нужна асинхронная очередь с ожиданием и, желательно, ограничением размера.

**Типичные сценарии:**

- **фоновая обработка из HTTP-запроса** — контроллер кладёт задание в канал и сразу отвечает `202 Accepted`, `BackgroundService` читает и выполняет;
- **конвейер (pipeline)** — чтение → парсинг → обогащение → запись в БД, каждая стадия в своей задаче, между стадиями bounded-канал;
- **сериализация доступа к состоянию** — один consumer владеет состоянием и обрабатывает команды по очереди, вместо того чтобы защищать состояние блокировкой (модель актора «на минималках»);
- **батчинг** — накопить элементы и писать пачками (`TryRead` в цикле после `WaitToReadAsync`);
- **fan-out / fan-in** — несколько потребителей читают из одного канала, чтобы параллелить обработку с фиксированным числом воркеров.

```csharp
// N воркеров из одного канала — ограниченный параллелизм без семафора
var workers = Enumerable.Range(0, 4).Select(async _ =>
{
    await foreach (var job in channel.Reader.ReadAllAsync(ct))
        await HandleAsync(job, ct);
});
await Task.WhenAll(workers);
```

**Когда Channel — не лучший выбор:**

| Ситуация | Лучше |
| --- | --- |
| задания нельзя терять при падении/рестарте | внешний брокер (RabbitMQ, Kafka, SQS) или outbox в БД |
| нужно распределить работу между несколькими инстансами | тот же брокер — канал живёт в памяти одного процесса |
| просто обработать готовую коллекцию параллельно | `Parallel.ForEachAsync` |
| потокобезопасный буфер без ожидания | `ConcurrentQueue<T>` |
| сложная маршрутизация, join, окна по времени | TPL Dataflow или Rx |

**На что обратить внимание при использовании:**

- почти всегда выбирайте **bounded** — unbounded канал превращает всплеск нагрузки в рост памяти вплоть до OOM;
- решите, что происходит с элементами в канале при остановке приложения: дочитать (с таймаутом) или сознательно потерять;
- исключение в цикле потребителя убивает его — оборачивайте обработку одного элемента в `try/catch`, иначе канал заполнится, и все писатели встанут;
- закрывайте канал (`Writer.Complete()`), когда производитель закончил, иначе `ReadAllAsync` будет ждать вечно.

**Что спросят дальше:** как устроен bounded-канал внутри, что делать с `FullMode`, как корректно остановить consumer в `BackgroundService`.

## Чем `Parallel.ForEach` отличается от обычного `foreach`?

```yaml
category: multithreading
level: middle
difficulty: 3
slug: multithreading-chem-parallel-foreach-otlichaetsya-ot-obychnogo-foreach
tags: threading
```

`foreach` обрабатывает элементы последовательно в текущем потоке. `Parallel.ForEach` разбивает коллекцию на части и обрабатывает их **одновременно** на нескольких потоках пула (плюс вызывающий поток), блокируя вызывающего до завершения всех итераций. Это инструмент для **CPU-bound** работы, а не для I/O.

```csharp
Parallel.ForEach(images, new ParallelOptions { MaxDegreeOfParallelism = Environment.ProcessorCount },
    image => Resize(image));          // CPU-тяжёлая работа — хороший кандидат
```

**Ключевые отличия:**

| | `foreach` | `Parallel.ForEach` |
| --- | --- | --- |
| порядок | строго по порядку | не гарантирован |
| потоки | текущий | текущий + потоки ThreadPool |
| доступ к общему состоянию | безопасен | нужна синхронизация |
| исключения | первое прерывает цикл | собираются в `AggregateException` |
| досрочный выход | `break` | `ParallelLoopState.Stop()` / `Break()` |
| накладные расходы | нет | разбиение, планирование, делегаты |

**Как он работает.** Коллекция делится партиционером: для массивов и `IList<T>` — диапазонами, для произвольного `IEnumerable<T>` — чанками растущего размера под блокировкой перечислителя. Количество потоков по умолчанию не ограничено (`MaxDegreeOfParallelism = -1`), им управляет ThreadPool.

**Подводные камни:**

- **общее состояние** — `list.Add(x)` внутри тела даст гонку; используйте перегрузку с `localInit`/`localFinally`, чтобы копить результат в локальной переменной потока и сливать один раз:

```csharp
long total = 0;
Parallel.ForEach(items,
    () => 0L,                                   // localInit
    (item, _, local) => local + Weight(item),   // тело без синхронизации
    local => Interlocked.Add(ref total, local)); // localFinally
```

- **маленькая работа на итерацию** — накладные расходы перекрывают выигрыш; для мелких операций используйте `Partitioner.Create(0, n, rangeSize)` или обычный цикл;
- **async-лямбда** — `Parallel.ForEach(items, async x => await ...)` компилируется в `async void`: цикл «завершается» сразу, исключения роняют процесс. Для асинхронного кода — `Parallel.ForEachAsync`;
- **I/O внутри** — потоки блокируются на ожидании, пул раздувается, возможен starvation;
- **вызов из ASP.NET Core запроса** — один запрос занимает много потоков пула, отнимая их у остальных запросов.

**Когда выигрыш реален:** независимые CPU-bound итерации заметного размера (от сотен микросекунд), количество элементов больше числа ядер, отсутствие общего изменяемого состояния. Проверяйте бенчмарком — параллельная версия легко оказывается медленнее из-за false sharing или contention.

**Что спросят дальше:** чем отличается от `Parallel.ForEachAsync` и PLINQ, как ограничить параллелизм, что делают `Stop` и `Break`.

## Чем `Parallel.ForEachAsync` отличается от `Task.WhenAll`?

```yaml
category: multithreading
level: middle
difficulty: 3
slug: multithreading-chem-parallel-foreachasync-otlichaetsya-ot-task-whenall
tags: async, threading
```

`Task.WhenAll` просто ждёт уже **запущенные** задачи — если создать их через `Select`, стартуют все сразу, без ограничения. `Parallel.ForEachAsync` (.NET 6+) сам запускает обработку элементов с **ограниченным параллелизмом** (по умолчанию `Environment.ProcessorCount`), берёт следующий элемент, как только освобождается слот, и прекращает выдачу новых элементов при первой ошибке или отмене.

```csharp
// WhenAll: 10 000 HTTP-запросов одновременно
await Task.WhenAll(urls.Select(u => http.GetStringAsync(u)));

// ForEachAsync: не больше 20 одновременно
await Parallel.ForEachAsync(urls,
    new ParallelOptions { MaxDegreeOfParallelism = 20, CancellationToken = ct },
    async (url, token) => await http.GetStringAsync(url, token));
```

**Сравнение:**

| | `Task.WhenAll` | `Parallel.ForEachAsync` |
| --- | --- | --- |
| ограничение параллелизма | нет (только вручную через `SemaphoreSlim`) | `MaxDegreeOfParallelism` |
| когда стартует работа | в момент создания задач | по мере освобождения слотов |
| результаты | `Task<T[]>` в порядке исходных задач | не возвращает — собирать самим (`ConcurrentBag`, массив по индексу) |
| поведение при ошибке | ждёт **все** задачи, затем падает | перестаёт брать новые элементы, отменяет токен тела, ждёт уже запущенные |
| исключения | `await` бросает первое, все — в `task.Exception` | так же: `await` — первое, все — в `AggregateException` задачи |
| источник | готовый набор задач | `IEnumerable<T>` или `IAsyncEnumerable<T>` |

**Когда что использовать:**

- **`Task.WhenAll`** — небольшое известное число независимых операций: «параллельно загрузить профиль, заказы и настройки». Ограничение не нужно, результаты нужны все и по порядку;
- **`Parallel.ForEachAsync`** — большой или потоковый набор однотипных элементов, и внешняя система (БД, API) не выдержит всех запросов сразу.

**Подводные камни:**

- **значение по умолчанию** `ProcessorCount` рассчитано на CPU-bound работу; для I/O его почти всегда нужно выставить осознанно, исходя из лимитов внешнего сервиса;
- **сбор результатов** — `List<T>.Add` из тела даёт гонку; проще заранее выделить массив и писать по индексу (`Select((x, i) => (x, i))`);
- **«fail fast» не мгновенный** — уже запущенные тела доработают, если не проверяют переданный `token`;
- в `Task.WhenAll` по-прежнему можно ограничить параллелизм через `SemaphoreSlim`, но тогда все задачи всё равно создаются заранее и висят в памяти, ожидая семафор.

**.NET 9** добавил перегрузки `Task.WhenAll`/`WhenAny` с `ReadOnlySpan<Task>` (меньше аллокаций), а для обработки задач по мере завершения — `Task.WhenEach`, возвращающий `IAsyncEnumerable<Task>`.

**Что спросят дальше:** как ограничить параллелизм без `ForEachAsync`, что будет с исключениями, почему `Parallel.ForEach` с async-лямбдой — ошибка.

## Как диагностировать проблемы многопоточности?

```yaml
category: multithreading
level: middle
difficulty: 4
slug: multithreading-kak-diagnostirovat-problemy-mnogopotochnosti
```

Сначала классифицировать симптом — **зависание** (deadlock, starvation), **деградация под нагрузкой** (contention, starvation), **неверный результат** (race condition), — а затем снять данные с живого процесса: дамп со стеками всех потоков для зависаний, счётчики и трассировку для производительности, стресс-тест и логи для гонок.

**Инструменты .NET:**

| Инструмент | Что даёт |
| --- | --- |
| `dotnet-counters monitor -p <pid>` | живые метрики: потоки пула, длина очереди, lock contention, CPU |
| `dotnet-dump collect` + `dotnet-dump analyze` | снимок процесса: стеки потоков, блокировки, async-задачи |
| `dotnet-stack report -p <pid>` | быстро напечатать стеки всех управляемых потоков без полного дампа |
| `dotnet-trace` / PerfView | события рантайма (contention, thread pool), CPU-сэмплы, wait-анализ |
| Visual Studio: Parallel Stacks, Tasks, Threads | то же на машине разработчика, с визуализацией графа ожиданий |

**Зависание — дамп и команды SOS:**

```text
dotnet-dump collect -p 1234
dotnet-dump analyze dump_xxx.dmp
> clrstack -all        # стеки всех управляемых потоков
> syncblk              # кто владеет Monitor и сколько потоков ждут
> dumpasync            # цепочки незавершённых async-операций
> threadpool           # загрузка пула и очередь
```

Признаки:

- два потока в `Monitor.Enter`/`Wait`, каждый владеет тем, что ждёт другой, — **deadlock**;
- сотни потоков пула со стеком в `Task.Wait`/`.Result`/`GetResult`, а очередь растёт — **sync-over-async и starvation**;
- потоки ничего не ждут, но `dumpasync` показывает задачи, ожидающие `TaskCompletionSource`, который никто не завершает, — **потерянный сигнал**.

**Производительность — счётчики:**

- `monitor-lock-contention-count` растёт вместе с нагрузкой, а CPU не выбран — **lock contention**;
- `threadpool-thread-count` медленно ползёт вверх, `threadpool-queue-length` > 0 постоянно, CPU низкий — **ThreadPool starvation**;
- CPU 100% на всех ядрах, пропускная способность не растёт с потоками — spin, CAS-повторы, false sharing (нужен CPU-профиль).

С .NET 8/9 те же показатели доступны как метрики `System.Runtime` через OpenTelemetry — их можно выводить в Grafana и ловить проблему до того, как понадобится дамп.

**Race condition — самое трудное:**

- гонку почти никогда не видно в дампе; нужны **воспроизведение под стрессом** (много потоков, `Barrier` для одновременного старта, запуск тысяч итераций, другая архитектура — ARM), логи с идентификатором потока и корреляцией;
- систематическое тестирование — Microsoft Coyote перебирает чередования потоков детерминированно;
- ревью кода по признакам: общее изменяемое поле без синхронизации, check-then-act, чтение вне `lock`, `static` мутабельное состояние, небезопасные коллекции.

**Правило для продакшена:** заранее настройте возможность снять дамп (права, место на диске, `DOTNET_DbgEnableMiniDump` для дампа при падении) и экспорт метрик рантайма — во время инцидента на это не будет времени.

**Что спросят дальше:** как отличить starvation от нехватки CPU, какие метрики покажут contention, как тестировать редкую гонку.

## Что гарантирует модель памяти .NET и почему без volatile или барьера чтение может вернуть устаревшее значение?

```yaml
category: multithreading
level: senior
difficulty: 5
slug: advanced-csharp-chto-garantiruet-model-pamyati-net-i-pochemu-bez-volatile-ili-barera-c
tags: memory-model, clr
```

Модель памяти .NET гарантирует немного: **атомарность** выровненных обращений до размера указателя, **согласованность в пределах одного потока** (поток видит свои операции в программном порядке) и **acquire/release** для volatile-обращений, плюс полный барьер у `Interlocked` и блокировок. Всё остальное — порядок и момент, когда обычная запись одного потока станет видна другому, — не гарантировано. Поэтому обычное чтение может вернуть старое значение: JIT вправе его закэшировать, а процессор — переставить.

**Где это описано.** ECMA-335 (раздел I.12.6) задаёт слабую базовую модель. CoreCLR даёт более сильные гарантии, и с .NET 7 они зафиксированы в документе `docs/design/specs/Memory-model.md` репозитория dotnet/runtime. На собеседовании полезно сказать, что опираться нужно на документированные гарантии, а не на «на моём x64 работает».

**Что гарантировано:**

- **атомарность** — чтение и запись выровненных примитивов не больше `IntPtr.Size` и ссылок никогда не «рвутся». `long`/`double` в 32-битном процессе атомарны не обязаны; структуры больше указателя — никогда;
- **однопоточная согласованность** — любые оптимизации не должны менять результат с точки зрения самого потока;
- **volatile-чтение = acquire**, **volatile-запись = release** (поле `volatile`, `Volatile.Read/Write`);
- **полный барьер** — `Interlocked.*`, `Thread.MemoryBarrier`, вход/выход `lock`; запуск потока и задачи, завершение `Task` и `await` тоже создают отношение happens-before;
- **упорядоченность зависимых по данным чтений** — если прочитали ссылку, а затем поле через неё, второе чтение не «обгонит» первое;
- CoreCLR дополнительно обещает, что запись ссылки на объект в кучу публикует его безопасно (release-семантика), поэтому читатель не увидит объект с неинициализированным заголовком или незаполненными в конструкторе полями. ECMA-335 такого не требует;
- **запрет спекулятивных записей** — JIT не может записать в общую память значение, которого не было бы в исходном коде.

**Что разрешено — и откуда берётся «устаревшее» значение:**

1. **JIT объединяет и выносит чтения.** Соседние обычные чтения одного места можно слить в одно, а чтение из цикла без побочных эффектов — вынести наружу:

```csharp
while (!_stop) { _iterations++; }
// JIT вправе превратить в:
if (!_stop) while (true) { _iterations++; }   // поток никогда не увидит _stop = true
```

Это единственный механизм, который даёт «вечно устаревшее» значение, и он чисто программный — от него защищает `volatile`/`Volatile.Read`, запрещающие такое объединение.

2. **Процессор переставляет независимые операции.** Кэши когерентны, поэтому запись *в конце концов* станет видна всем ядрам. Но пока она сидит в store buffer, ядро уже выполняет следующие инструкции, а другое ядро может увидеть записи в ином порядке. На x86 так переставляется только «запись → последующее чтение другого адреса»; на ARM64 — почти любые пары независимых операций.

3. **Итог** — поток B может увидеть флаг «данные готовы», но старые данные, или никогда не заметить флаг. «Устаревание» в .NET — это не про кэш, который «забыли сбросить», а про порядок и про оптимизации JIT.

**Как правильно рассуждать о коде.** Не про «свежесть», а про пары синхронизации: запись с release в одном потоке и чтение с acquire того же места в другом. Если чтение увидело значение, записанное release-записью, то всё, что поток-писатель сделал до неё, видно читателю после.

```csharp
// Писатель                           // Читатель
_result = Compute();                  if (Volatile.Read(ref _done))
Volatile.Write(ref _done, true);          Use(_result);   // гарантированно новое
```

**Что `volatile` не лечит:** store→load перестановку (нужен полный барьер), атомарность составных операций и согласованность нескольких переменных — для этого `Interlocked` или `lock`.

**Практический вывод.** В прикладном коде синхронизируйтесь через `lock`, `Interlocked`, concurrent-коллекции, `Task`/`await` — они дают все нужные барьеры. Ручные `Volatile.*` оправданы только в низкоуровневом коде, и тогда каждое обращение должно быть осмысленной парой release/acquire.

**Что спросят дальше:** почему код, работающий на x86, ломается на ARM; чем volatile отличается от полного барьера; безопасна ли double-checked locking в .NET.

## Чем отличаются гарантии volatile, Interlocked и Volatile.Read/Write, и когда каждого из них недостаточно?

```yaml
category: multithreading
level: senior
difficulty: 5
slug: advanced-csharp-chem-otlichayutsya-garantii-volatile-interlocked-i-volatile-read-write
tags: memory-model, synchronization
```

Модификатор `volatile` и методы `Volatile.Read/Write` дают **одно и то же**: acquire при чтении, release при записи, без атомарности составных операций. Разница только в том, что модификатор применяется ко всем обращениям к полю, а методы — точечно. `Interlocked` даёт больше: **атомарный read-modify-write** и **полный барьер**. Недостаточно первого — когда нужен порядок store→load или атомарность; второго — когда инвариант охватывает несколько переменных.

**Сравнение:**

| | `volatile` поле | `Volatile.Read/Write` | `Interlocked.*` |
| --- | --- | --- | --- |
| атомарность простого чтения/записи | да (для допустимых типов) | да, включая `long`/`double` даже в 32-битном процессе | да |
| атомарный RMW (`++`, CAS, обмен) | нет | нет | да |
| порядок | acquire / release | acquire / release | полный барьер |
| store → load | не упорядочен | не упорядочен | упорядочен |
| типы | ограниченный список, без `long`/`double` | все примитивы, ссылки, `T : class` | `int`, `long`, `uint`, `ulong`, `nint`, ссылки, `float`/`double` для `Exchange`/`CompareExchange`; с .NET 9 — также `byte`/`short` и enum-типы для `Exchange`/`CompareExchange` |
| видимость в коде | неявна, на каждое обращение | явна в месте вызова | явна |

**Когда `volatile`/`Volatile` недостаточно:**

1. **Составные операции.** `volatile int _count; _count++;` — всё ещё чтение и запись, между ними вклинивается другой поток. Нужен `Interlocked.Increment`.
2. **Store → load (Dekker-подобные протоколы).**

```csharp
// Поток A                          // Поток B
Volatile.Write(ref _a, 1);          Volatile.Write(ref _b, 1);
if (Volatile.Read(ref _b) == 0)     if (Volatile.Read(ref _a) == 0)
    EnterCritical();                    EnterCritical();   // оба могут войти!
```

Release-запись и последующее acquire-чтение **другой** переменной переставлять разрешено (и x86 это реально делает через store buffer). Нужен `Interlocked.Exchange(ref _a, 1)` или `Thread.MemoryBarrier()` между записью и чтением.

3. **Паттерн «чтение → проверка → запись»**: `if (Volatile.Read(ref _state) == Idle) Volatile.Write(ref _state, Running);` — два потока пройдут проверку одновременно. Нужен `Interlocked.CompareExchange`.

**Когда недостаточно `Interlocked`:**

- **несколько переменных**: каждая операция атомарна, но пара `Interlocked.Add(ref _sum, x); Interlocked.Increment(ref _count);` может быть прочитана в промежуточном состоянии. Решение — `lock` или неизменяемый объект со всеми полями, заменяемый одним `CompareExchange` ссылки;
- **чтение без `Interlocked`/`Volatile`**: если писатель использует `Interlocked`, а читатель обычное чтение в цикле, JIT по-прежнему вправе закэшировать значение. Читать нужно через `Volatile.Read` (или `Interlocked.Read` для `long` в 32-битном коде);
- **под высокой конкуренцией** `Interlocked` на одной переменной упирается в пересылку кэш-линии — корректность есть, масштабируемости нет; помогает шардирование.

**Стоимость на практике:**

- на x64 volatile-чтение и -запись компилируются в обычные `mov` — цена только в запрещённых JIT-оптимизациях;
- на ARM64 — `ldar`/`stlr` (или барьеры `dmb`), дешевле полного барьера, но не бесплатно;
- `Interlocked` — `lock`-инструкция на x64 (десятки тактов при владении линией, сотни при её пересылке), атомики LSE или LL/SC-цикл на ARM64.

**Рекомендация.** Предпочитайте `Volatile.Read/Write` модификатору `volatile`: намерение видно в точке обращения, и нет соблазна написать `_count++` по volatile-полю, думая, что оно атомарно.

**Что спросят дальше:** как реализовать CAS-счётчик, почему Dekker не работает на volatile, что именно делает `Thread.MemoryBarrier` на x86 и ARM.

## Когда lock-free структура реально быстрее блокировки, а когда только усложняет код?

```yaml
category: multithreading
level: senior
difficulty: 5
slug: advanced-concurrency-kogda-lock-free-struktura-realno-bystree-blokirovki-a-kogda-tolko-uslo
tags: lock-free, performance
```

Lock-free выигрывает, когда операция **очень короткая** (одна-две атомарные инструкции), конкуренция **умеренная**, а стоимость блокировки — прежде всего риск, что поток-владелец будет вытеснен или заблокирован, — сопоставима с самой работой. Во всех остальных случаях — длинная критическая секция, согласованное изменение нескольких полей, сильная конкуренция за одну ячейку — lock-free не ускоряет, а только добавляет тонкие баги.

**Почему lock-free не «бесплатный»:**

- атомарная инструкция (`lock cmpxchg`, `ldaxr/stlxr`) стоит столько же, сколько незаспоренный захват `lock`, — а `lock` это и есть одна-две такие инструкции на входе и выходе;
- при сильной конкуренции все CAS бьют в одну кэш-линию: пересылка линии между ядрами (порядка 100 нс на многосокетных машинах) одинаково тормозит и блокировку, и CAS-цикл. CAS-цикл ещё и сжигает CPU на неудачных попытках;
- сложные lock-free структуры (очередь Майкла–Скотта, списки) требуют больше атомарных операций на одну вставку, чем версия с блокировкой.

**Где lock-free действительно лучше:**

| Сценарий | Почему |
| --- | --- |
| счётчики, флаги, однократная инициализация | одна инструкция вместо захвата + освобождения |
| публикация неизменяемого снимка (copy-on-write) | читатели не синхронизируются вовсе, пишущий редкий |
| горячий путь чтения при редких записях | чтения без барьеров сильнее полного, никакого contention |
| SPSC-очередь (один писатель, один читатель) | можно обойтись acquire/release без CAS |
| код, где нельзя блокироваться (обработчики с жёсткой латентностью) | нет риска, что вытесненный владелец задержит всех (lock convoy, priority inversion) |

**Главное преимущество — гарантия прогресса, а не скорость.** В lock-free алгоритме остановка или вытеснение одного потока не останавливает остальных. В блокировке поток, вытесненный планировщиком ОС с захваченным lock, заставляет всех ждать целый квант времени. Это заметно в хвостах латентности (p99.9), а не в средних.

**Когда только усложняет:**

- инвариант охватывает несколько полей — приходится упаковывать их в неизменяемый объект и копировать на каждое изменение (аллокации, нагрузка на GC);
- структура самописная — ABA, проблемы освобождения памяти, ошибки упорядочивания, которые проявляются раз в сутки и только на ARM;
- критическая секция делает что-то нетривиальное — lock-free там невозможен, остаётся только спин-ожидание, то есть та же блокировка, но хуже;
- реальная проблема — не стоимость блокировки, а **объём общего состояния**: шардирование, локальные буферы и `Channel` дают больше, чем смена примитива.

**Как принимать решение:**

1. Начать с `lock` (в .NET 9+ — `System.Threading.Lock`) или готовой коллекции BCL — `ConcurrentQueue`, `ConcurrentDictionary`, `ImmutableInterlocked` уже содержат выверенные lock-free алгоритмы.
2. Измерить: `dotnet-counters` (lock contention), BenchmarkDotNet с реалистичным числом потоков, профиль на целевой архитектуре.
3. Если contention подтверждён — сперва уменьшить общее состояние (шардирование, per-core данные), и лишь потом переходить к lock-free.

**Что спросят дальше:** что такое ABA, как написать CAS-цикл, почему незаспоренный `lock` в .NET дешёвый (thin lock, spinning перед переходом в ядро).

## Как реализовать потокобезопасный счётчик через CAS и почему наивный цикл может не завершиться?

```yaml
category: multithreading
level: senior
difficulty: 5
slug: advanced-concurrency-kak-realizovat-potokobezopasnyi-schetchik-cherez-cas-i-pochemu-naivnyi
tags: lock-free, cas
```

CAS-счётчик — цикл «прочитать текущее значение → вычислить новое → `Interlocked.CompareExchange`; если за это время кто-то изменил значение, повторить». Наивная версия может не завершиться по двум причинам: **ошибка реализации** (не перечитывается актуальное значение или чтение закэшировано JIT) и **отсутствие гарантии прогресса для конкретного потока** — lock-free обещает, что прогресс сделает *кто-то*, а не что конкретный поток когда-нибудь выиграет.

**Правильная реализация:**

```csharp
private long _value;

public long AddClamped(long delta, long max)
{
    long current = Volatile.Read(ref _value);
    while (true)
    {
        long next = Math.Min(current + delta, max);
        long observed = Interlocked.CompareExchange(ref _value, next, current);
        if (observed == current)
            return next;            // успех: значение не менялось между чтением и записью
        current = observed;         // проигрыш: берём значение, которое вернул CAS
    }
}
```

Ключевые детали: `CompareExchange` возвращает **фактическое** значение ячейки, его и надо использовать для следующей попытки — лишнее чтение не нужно. Для простого инкремента CAS не нужен вовсе: `Interlocked.Increment`/`Add` компилируются в одну инструкцию (`lock xadd` на x64, `ldadd` на ARM64 с LSE) и не требуют повторов.

**Почему наивный цикл зависает:**

1. **Не обновляется ожидаемое значение:**

```csharp
long current = _value;                                   // прочитали один раз
while (Interlocked.CompareExchange(ref _value, current + 1, current) != current)
{ }                                                      // current устарел навсегда — бесконечный цикл
```

2. **Спин-ожидание перед CAS на обычном поле** — `while (_value == Locked) { }` без `Volatile.Read`: в таком цикле нет ни одного барьера, JIT вправе прочитать поле один раз, и поток крутится вечно. Сам `CompareExchange` — полный барьер, поэтому внутри корректного CAS-цикла эта проблема не возникает; она появляется в «подготовительных» циклах вокруг него.

3. **Livelock/starvation под сильной конкуренцией.** Если 32 потока долбят одну ячейку, а вычисление `next` не мгновенное, окно между чтением и CAS велико, и конкретный поток может проигрывать неограниченно долго. Алгоритм остаётся lock-free (система в целом прогрессирует), но не wait-free. В проде это выглядит как высокие хвосты латентности и 100% CPU.

4. **Дорогое или побочное вычисление внутри цикла.** Аллокация, логирование, обращение к внешнему ресурсу в теле цикла увеличивают окно гонки и повторяются на каждой неудаче.

**Как смягчить конкуренцию:**

- держать вычисление между чтением и CAS минимальным;
- при неудаче делать backoff — `SpinWait` (`spinner.SpinOnce()`), который сначала крутится, а потом уступает поток;
- **шардировать** счётчик: ячейка на ядро или поток с паддингом от false sharing, суммирование при чтении. Именно так устроены высоконагруженные метрики;
- если логика сложнее одной переменной — вернуться к `lock`.

```csharp
var spinner = new SpinWait();
while (Interlocked.CompareExchange(ref _value, next, current) != current)
{
    spinner.SpinOnce();
    current = Volatile.Read(ref _value);
    next = Compute(current);
}
```

**Что спросят дальше:** что такое ABA и затрагивает ли она счётчик (нет — для чисел значение и есть вся информация), чем lock-free отличается от wait-free, как шардировать счётчик без false sharing.

## Что такое ABA-проблема и какими способами её решают?

```yaml
category: multithreading
level: senior
difficulty: 5
slug: advanced-concurrency-chto-takoe-aba-problema-i-kakimi-sposobami-ee-reshayut
tags: lock-free, cas
```

ABA — ошибка CAS-алгоритмов: поток прочитал значение **A**, другой поток за это время поменял его на **B** и обратно на **A**, и CAS первого потока успешно проходит, хотя состояние структуры уже другое. CAS сравнивает только значение ячейки, а не «историю» — одинаковое значение не означает, что ничего не изменилось.

**Классический пример — lock-free стек (Treiber stack):**

```text
Стек: top → A → B → C

Поток 1: читает top = A, next = B, собирается сделать CAS(top, A → B), вытеснен.
Поток 2: pop A, pop B, push A (тот же узел A переиспользован).
         Стек: top → A → C,  а B уже освобождён/в пуле.
Поток 1: CAS(top, A → B) — успех, ведь top снова A.
         Стек: top → B → ???   — висящий узел, структура сломана.
```

**Когда ABA реальна:**

- в нативном коде, где память узла освобождается и выделяется снова по тому же адресу;
- в любом коде, где **значения переиспользуются**: индексы в массиве/пуле, объекты из `ObjectPool`, числовые состояния, которые ходят по кругу;
- для чистого счётчика ABA не проблема — число и есть всё состояние.

**Почему в .NET её меньше.** Для ссылок GC фактически решает ABA: пока поток 1 держит ссылку на узел A, узел не может быть собран и повторно выделен по тому же адресу, а новый объект получит другую ссылку. Поэтому наивный Treiber stack с `Interlocked.CompareExchange` для ссылок в .NET корректен — **если узлы не переиспользуются через пул**. Стоит начать экономить аллокации пулингом — ABA возвращается.

**Способы решения:**

| Способ | Идея | Замечания в .NET |
| --- | --- | --- |
| не переиспользовать узлы | каждый push — новый объект | полагаемся на GC; цена — аллокации |
| версионирование (tagged pointer) | рядом со значением хранить счётчик изменений и сравнивать пару | для 32-битного индекса + 32-битной версии — один CAS по `long`; двойного CAS на 128 бит в публичном API `Interlocked` нет |
| неизменяемая обёртка | CAS по ссылке на новый неизменяемый объект-снимок | каждый снимок — новая ссылка, совпасть по ссылке может только тот же объект |
| hazard pointers / epoch-based reclamation | не освобождать узел, пока другие потоки могут его читать | нужны в нативном коде; в .NET их роль играет GC |
| LL/SC | load-linked/store-conditional срывается при *любой* записи в линию | аппаратный механизм ARM; из C# напрямую недоступен |
| блокировка | нет CAS — нет ABA | часто лучший ответ |

**Пример версионирования для индексов:**

```csharp
// старшие 32 бита — версия, младшие — индекс головы в массиве узлов
long state = Volatile.Read(ref _head);
int index = (int)state;
int version = (int)(state >> 32);
long next = ((long)(version + 1) << 32) | (uint)_nodes[index].Next;
if (Interlocked.CompareExchange(ref _head, next, state) == state) { /* pop удался */ }
```

Даже если индекс вернулся к прежнему, версия уже другая, и CAS провалится. Версия может переполниться и пройти круг, но для этого нужно 2³² изменений за время одного вытеснения — на практике недостижимо.

**Что сказать на собеседовании.** ABA — повод не писать самописные lock-free структуры: `ConcurrentStack<T>` и `ConcurrentQueue<T>` в BCL уже решают эти проблемы (стек — новыми узлами без пула, очередь — сегментами с порядковыми номерами слотов).

**Что спросят дальше:** почему GC защищает от ABA для ссылок, что такое LL/SC, чем wait-free отличается от lock-free.

## Зачем нужны барьеры памяти и почему корректный на x86 код ломается на ARM?

```yaml
category: multithreading
level: senior
difficulty: 5
slug: advanced-concurrency-zachem-nuzhny-barery-pamyati-i-pochemu-korrektnyi-na-x86-kod-lomaetsya
tags: memory-model, memory-barriers
```

Барьеры нужны, чтобы задать **порядок**, в котором записи одного потока становятся видны другим: и JIT, и процессор переставляют независимые обращения к памяти. Код без барьеров «работает» на x86 потому, что x86 (модель TSO) сам почти ничего не переставляет, а ARM64 — слабоупорядоченная архитектура и переставляет почти всё. Такой код корректен не по модели памяти .NET, а по случайности железа.

**Какие перестановки разрешает каждое железо:**

| Пара операций (разные адреса) | x86/x64 (TSO) | ARM64 |
| --- | --- | --- |
| load → load | не переставляются | переставляются |
| store → store | не переставляются | переставляются |
| load → store | не переставляются | переставляются |
| store → load | **переставляются** (store buffer) | переставляются |
| зависимые по адресу чтения | упорядочены | упорядочены |

На x86 каждая обычная загрузка уже имеет семантику acquire, а сохранение — release. Поэтому паттерн «записал данные, выставил флаг» работает без барьеров на уровне CPU (если JIT ничего не переставил). На ARM64 те же инструкции `ldr`/`str` никакого порядка не дают.

**Пример, ломающийся на ARM:**

```csharp
private int _data;
private bool _ready;       // без volatile

// Поток A
_data = 42;
_ready = true;             // ARM вправе сделать эту запись видимой раньше _data

// Поток B
if (_ready)
    Console.WriteLine(_data);   // на ARM64 может напечатать 0
```

На ARM ломаются обе стороны: писатель может «выпустить» запись флага раньше данных, а читатель — выполнить чтение `_data` спекулятивно до чтения `_ready`. Исправление — `Volatile.Write(ref _ready, true)` и `Volatile.Read(ref _ready)`: JIT выдаст `stlr` и `ldar` (на новых ядрах — `ldapr`), которые и есть release и acquire.

**Что ломается даже на x86** — store→load. Протокол «записал свой флаг, проверил чужой» (Dekker, Peterson, некоторые схемы «wake-up без потерь»):

```csharp
_myFlag = 1;                 // уходит в store buffer
if (_otherFlag == 0) { ... } // чтение выполняется раньше, чем запись видна другому ядру
```

Оба потока могут прочитать 0. `volatile` тут не помогает — нужен полный барьер: `Interlocked.Exchange(ref _myFlag, 1)` или `Thread.MemoryBarrier()` (на x64 это `lock or` / `mfence`, на ARM64 — `dmb ish`).

**Почему код ещё и ломается при смене JIT/рантайма.** Даже на x86 JIT вправе переставить или закэшировать обычные обращения. Код, «проверенный годами», может перестать работать после включения tiered PGO, более агрессивного инлайнинга или перехода с .NET Framework на .NET 8. Барьер — это контракт и для JIT, и для CPU.

**Где это стало актуально:** серверы на Graviton/Ampere, Apple Silicon у разработчиков, Windows on ARM. Типичные жертвы при переезде — самописные флаги остановки, «ленивая» инициализация без `Volatile`/`Lazy<T>`, самописные кольцевые буферы, spin-ожидания на обычном поле.

**Как писать переносимо:**

- синхронизироваться через `lock`, `Interlocked`, `Task`, concurrent-коллекции — у них барьеры для всех архитектур;
- если нужен флаг или публикация — `Volatile.Read/Write` в каждой точке обращения;
- для store→load — только полный барьер;
- тестировать низкоуровневый код на ARM64: сильная модель x86 скрывает до половины ошибок упорядочивания.

**Что спросят дальше:** что гарантирует модель памяти .NET, почему `volatile` не спасает Dekker, во что компилируется `Volatile.Read` на ARM64.

## Как diagnose lock contention и какие метрики покажут, что блокировка стала узким местом?

```yaml
category: multithreading
level: senior
difficulty: 5
slug: advanced-concurrency-kak-diagnose-lock-contention-i-kakie-metriki-pokazhut-chto-blokirovka
tags: contention, profiling
```

Lock contention видно по трём признакам одновременно: **счётчик конфликтов блокировок растёт** пропорционально нагрузке, **пропускная способность перестаёт расти** при добавлении потоков или реплик-ядер, а **CPU недогружен** (потоки ждут, а не работают). Затем через трассировку событий contention находят конкретную блокировку и стек, откуда её берут.

**Шаг 1 — метрики рантайма:**

| Метрика | Где | Что значит |
| --- | --- | --- |
| `monitor-lock-contention-count` | `dotnet-counters`, EventCounters `System.Runtime` | сколько раз `Monitor.Enter` не смог захватить блокировку сразу |
| `dotnet.monitor.lock_contentions` | Meter `System.Runtime` (.NET 9+), OpenTelemetry | то же в виде OTel-метрики для Grafana/Prometheus |
| `Monitor.LockContentionCount` | в коде | то же значение, можно логировать самому |
| `threadpool-thread-count` / `dotnet.thread_pool.thread.count` | там же | рост потоков пула при низком CPU — потоки блокируются |
| CPU процесса | `dotnet-counters`, мониторинг | низкий при высокой латентности — ждём, а не считаем |

```text
dotnet-counters monitor -p 1234 --counters System.Runtime
```

Абсолютное число конфликтов мало что говорит — важна **динамика**: если при удвоении RPS конфликты растут в 4 раза, а латентность p99 ползёт вверх, блокировка сериализует запросы.

**Шаг 2 — найти, какая именно блокировка:**

- **трассировка событий contention** (keyword `Contention`, `0x4000` провайдера `Microsoft-Windows-DotNETRuntime`):

```text
dotnet-trace collect -p 1234 --providers Microsoft-Windows-DotNETRuntime:0x4000:4
```

  События `ContentionStart`/`ContentionStop` со стеками показывают, где потоки ждали; в новых версиях .NET `ContentionStop` содержит длительность ожидания. Трассу открывают в PerfView (группировка по стеку) или в Visual Studio;

- **wait-анализ / Thread Time** в PerfView или Concurrency-профиле Visual Studio — сколько времени потоки провели в блокировке и на каком объекте;
- **дамп под нагрузкой**: `dotnet-dump analyze` → `syncblk` показывает объект, поток-владелец и число ждущих; `clrstack -all` — что делает владелец. Два-три дампа с интервалом в секунду сразу показывают «горячую» блокировку.

**Шаг 3 — понять природу конфликта:**

- **длинная критическая секция** — внутри I/O, логирование, сериализация, вызов чужого кода. Лечение: вынести тяжёлую работу за пределы `lock`;
- **короткая секция, но очень частая** — одна глобальная блокировка на весь сервис (кэш, пул, счётчик). Лечение: шардирование, lock striping, per-core данные, `ConcurrentDictionary`, неизменяемые снимки для чтения;
- **lock convoy** — владелец вытесняется ОС, пока держит блокировку, и очередь ждущих растёт. Видно по большому разбросу длительности ожидания;
- **скрытые блокировки** — внутри библиотек: синхронные логгеры, `lock` в самописном пуле, `static` кэши с общей блокировкой. Стек из трассы их выдаёт.

**Нюансы, которые спрашивают:**

- `Monitor` сначала крутит spin-ожидание и только потом переходит в ядро — короткие конфликты стоят CPU, а не контекстных переключений, и в CPU-профиле видны как `AwareLock::Contention`/spin;
- `SemaphoreSlim`, `ReaderWriterLockSlim`, `SpinLock` в `monitor-lock-contention-count` не попадают — их ожидание видно только в CPU/wait-профиле и стеках;
- в async-коде ожидание `SemaphoreSlim.WaitAsync` не блокирует потоки, поэтому «contention» проявляется как рост латентности и числа висящих задач (`dumpasync`), а не рост потоков.

**Как подтвердить исправление:** нагрузочный тест с тем же профилем трафика; после правки конфликты должны расти линейно или не расти, а RPS — масштабироваться с ядрами.

**Что спросят дальше:** что такое lock convoy, чем помогает lock striping, как устроен thin lock и sync block.

## Что такое ThreadPool starvation, как он проявляется в метриках и чем отличается от нехватки CPU?

```yaml
category: multithreading
level: senior
difficulty: 5
slug: advanced-concurrency-chto-takoe-threadpool-starvation-kak-on-proyavlyaetsya-v-metrikah-i-ch
tags: threadpool, async
```

ThreadPool starvation — состояние, когда все потоки пула **заняты ожиданием** (заблокированы в `.Result`, `Wait`, синхронном I/O, `Thread.Sleep`), а очередь работ растёт, и новые задачи — включая продолжения тех самых async-операций, которые ждут заблокированные потоки, — не могут выполниться. Главное отличие от нехватки CPU: **процессор простаивает**, а приложение не отвечает.

**Почему это происходит.** Пул не создаёт потоки мгновенно. До `ThreadPool.GetMinThreads()` (по умолчанию — число ядер) потоки создаются по требованию, выше — пул добавляет их медленно: hill climbing и детектор starvation выпускают примерно по одному потоку каждые пару сотен миллисекунд — секунду. При всплеске из 500 запросов, каждый из которых блокирует поток, пул «догоняет» нагрузку минутами.

```csharp
// Каждый запрос блокирует поток пула, ожидая продолжение,
// которому для выполнения тоже нужен поток пула
app.MapGet("/data", () => httpClient.GetStringAsync(url).Result);
```

**Как проявляется в метриках:**

| Метрика | Starvation | Нехватка CPU |
| --- | --- | --- |
| CPU процесса | низкий/средний | около 100% |
| `threadpool-thread-count` | **растёт ступенькой** и продолжает расти | стабилен, около числа ядер |
| `threadpool-queue-length` | стабильно больше нуля, растёт | может быть > 0 |
| `threadpool-completed-items-count` (скорость) | падает | высокая, упирается в потолок |
| латентность | резкие скачки до таймаутов, даже на лёгких эндпоинтах | растёт плавно, пропорционально нагрузке |
| health checks | падают (им тоже нужен поток) | обычно отвечают, но медленно |

В .NET 9+ те же показатели есть в Meter `System.Runtime` (`dotnet.thread_pool.thread.count`, `dotnet.thread_pool.queue.length`, `dotnet.thread_pool.work_item.count`). В трассе рантайма видны события `ThreadPoolWorkerThreadAdjustment` с причиной Starvation.

**Характерная картина.** После рестарта сервис работает, при всплеске нагрузки латентность за секунды уходит в таймауты, CPU 10–20%, число потоков растёт по 1–2 в секунду, а когда нагрузка спадает — всё «само проходит». В дампе сотни потоков со стеками в `Task.Wait`, `TaskAwaiter.GetResult`, `ManualResetEventSlim.Wait`, `Monitor.Wait`.

**Как подтвердить:**

```text
dotnet-counters monitor -p 1234 --counters System.Runtime
dotnet-dump collect -p 1234
dotnet-dump analyze <dump>  →  threadpool, clrstack -all
```

Если большинство стеков потоков пула заканчиваются в синхронном ожидании — это starvation.

**Как лечить:**

- **убрать блокирующие ожидания** — async до конца: `await` вместо `.Result`/`.Wait()`/`GetAwaiter().GetResult()`, асинхронные API для БД, файлов, HTTP;
- найти **синхронный I/O**, скрытый в библиотеках (синхронные логгеры, `Stream.Read` в сериализаторе, старые драйверы);
- долгие блокирующие операции — на выделенный поток (`TaskCreationOptions.LongRunning`, отдельный `Thread`), а не в пул;
- `ThreadPool.SetMinThreads` — временный пластырь: даёт больше потоков сразу, но маскирует причину и увеличивает потребление памяти и переключения контекста.

.NET 6+ быстрее добавляет потоки, когда поток пула блокируется именно в ожидании задачи (`Task.Wait`/`Result`), — это смягчает симптомы sync-over-async, но не отменяет проблему.

**Нехватка CPU лечится иначе:** профилированием горячих путей, уменьшением работы на запрос, масштабированием. Добавление потоков при 100% CPU только ухудшает ситуацию.

**Что спросят дальше:** почему sync-over-async приводит к starvation без `SynchronizationContext`, как работает hill climbing, чем опасен `SetMinThreads` в больших значениях.

## Почему синхронное ожидание async-метода приводит к deadlock и почему в ASP.NET Core это иногда «работает»?

```yaml
category: multithreading
level: senior
difficulty: 4
slug: advanced-concurrency-pochemu-sinhronnoe-ozhidanie-async-metoda-privodit-k-deadlock-i-pochem
tags: async, deadlock
```

Deadlock возникает, когда есть **однопоточный `SynchronizationContext`** (UI-поток WinForms/WPF, классический ASP.NET): вызывающий поток блокируется в `.Result`, а продолжение async-метода после `await` пытается вернуться именно в этот контекст — то есть в заблокированный поток. Каждый ждёт другого. В ASP.NET Core `SynchronizationContext` нет, продолжение выполняется на любом потоке пула, поэтому классического deadlock нет — но поток всё равно заблокирован, и под нагрузкой это превращается в ThreadPool starvation.

**Механизм deadlock:**

```csharp
// WPF, обработчик кнопки на UI-потоке
private void Button_Click(object s, RoutedEventArgs e)
{
    var text = LoadAsync().Result;        // 1. UI-поток блокируется
}

private async Task<string> LoadAsync()
{
    var r = await http.GetStringAsync(url);  // 2. await захватил UI-контекст
    return r.ToUpper();                      // 3. продолжение ждёт UI-поток — он занят в .Result
}
```

1. `await` видит незавершённую задачу, сохраняет `SynchronizationContext.Current` и регистрирует продолжение через `context.Post`.
2. HTTP-ответ пришёл, продолжение поставлено в очередь UI-потока.
3. UI-поток стоит в `.Result` и очередь не обрабатывает. Задача не завершится, пока не выполнится продолжение; продолжение не выполнится, пока не освободится поток.

В классическом ASP.NET (`AspNetSynchronizationContext`) картина та же: контекст запроса допускает только одно выполнение в момент времени.

**Почему в ASP.NET Core «работает»:**

- `SynchronizationContext.Current == null`, `await` не захватывает ничего, продолжение идёт в пул;
- блокированный поток ждёт, другой поток пула выполняет продолжение и завершает задачу — ожидание отпускает;
- на малой нагрузке это незаметно — лишь один поток «впустую» висит во время I/O.

**Почему это всё равно плохо:**

- каждое синхронное ожидание **занимает поток пула на всё время I/O**. При сотнях одновременных запросов потоки кончаются, продолжениям не на чем выполниться, и приложение встаёт так же, как при deadlock, — только «плавает»: то работает, то нет;
- код переносим не везде: та же библиотека, вызванная из WPF, xUnit с однопоточным контекстом или Blazor, зависнет по-настоящему;
- `.Result`/`.Wait()` заворачивают исключение в `AggregateException`, `GetAwaiter().GetResult()` — нет, но проблема блокировки одинакова.

**`ConfigureAwait(false)` — частичная защита:**

```csharp
var r = await http.GetStringAsync(url).ConfigureAwait(false);
```

Продолжение не возвращается в контекст, и deadlock в UI не случится — **если** `ConfigureAwait(false)` стоит на каждом `await` по всей цепочке, включая сторонние библиотеки. Один пропущенный — и deadlock возвращается. Поэтому это практика для библиотечного кода, а не способ «починить» sync-over-async.

**Правильные решения:**

- async до самого верха: `async Task` в контроллерах, `async void` только для обработчиков событий UI;
- если синхронный вызов неизбежен (конструктор, старый интерфейс, `Main` без async) — перестроить API, использовать асинхронную инициализацию/фабрику; `Task.Run(() => LoadAsync()).GetAwaiter().GetResult()` убирает deadlock в UI, потому что внутри `Task.Run` нет контекста, но всё равно блокирует поток — это компромисс, не решение;
- в библиотеках — `ConfigureAwait(false)` и отсутствие синхронных обёрток над async-методами.

**Что спросят дальше:** что делает `ConfigureAwait(false)`, как sync-over-async вызывает starvation, почему `async void` опасен, есть ли `SynchronizationContext` в консольном приложении (нет) и в xUnit (зависит от версии и настроек).

## Как ограничить concurrency при обращении к внешнему сервису, допускающему 500 одновременных запросов?

```yaml
category: multithreading
level: senior
difficulty: 5
slug: advanced-concurrency-kak-ogranichit-concurrency-pri-obraschenii-k-vneshnemu-servisu-dopuska
tags: throttling, resilience
```

Нужен **асинхронный ограничитель параллелизма** вокруг каждого вызова — `SemaphoreSlim(N)` или `ConcurrencyLimiter` из `System.Threading.RateLimiting` (в том числе через resilience-пайплайн `HttpClient`), — с ограниченной очередью ожидания, таймаутами и лимитом с запасом ниже 500. И не забыть, что лимит **глобальный**: если сервис развёрнут в нескольких экземплярах, 500 делится между ними.

**Базовый вариант — `DelegatingHandler` с семафором:**

```csharp
public sealed class ConcurrencyLimitHandler(int limit) : DelegatingHandler
{
    private readonly SemaphoreSlim _gate = new(limit, limit);

    protected override async Task<HttpResponseMessage> SendAsync(
        HttpRequestMessage request, CancellationToken ct)
    {
        await _gate.WaitAsync(ct);
        try   { return await base.SendAsync(request, ct); }
        finally { _gate.Release(); }
    }
}
```

Handler живёт в пайплайне типизированного или именованного `HttpClient` — лимит централизован, вызывающему коду о нём знать не нужно. Важно, чтобы экземпляр handler'а (а значит, семафор) был один на процесс, — `IHttpClientFactory` пересоздаёт handler-цепочки при ротации, поэтому семафор лучше хранить в singleton-сервисе и передавать в handler.

**Готовый вариант — `Microsoft.Extensions.Http.Resilience` (Polly v8):**

```csharp
services.AddHttpClient<PartnerClient>()
    .AddResilienceHandler("partner", b => b
        .AddConcurrencyLimiter(new ConcurrencyLimiterOptions
        {
            PermitLimit = 450,          // запас ниже 500
            QueueLimit = 1000           // сколько запросов может ждать слот
        })
        .AddTimeout(TimeSpan.FromSeconds(5)));
```

При переполнении очереди лимитер сразу отказывает (`RateLimiterRejectedException`) — это лучше, чем бесконечное накопление ожидающих.

**Что учесть, кроме самого ограничителя:**

- **несколько инстансов.** 10 подов × 500 = 5000 запросов. Варианты: статически делить лимит (`500 / replicas` с запасом), распределённый лимитер на Redis, или вынести вызовы в отдельный воркер/очередь с одним потребителем. Статическое деление проще и надёжнее, но плохо переживает автоскейлинг;
- **запас.** Лимит партнёра считается по его стороне: запросы, которые клиент уже отменил по таймауту, для партнёра могут ещё выполняться. Ставьте 80–90% от лимита;
- **таймауты.** Без таймаута «зависший» запрос держит слот вечно, и лимитер постепенно вырождается в ноль доступных слотов;
- **ретраи внутри лимита.** Повторная попытка тоже занимает слот; иначе при сбоях ретраи умножат нагрузку. В resilience-пайплайне порядок стратегий определяет, что считается одним вызовом;
- **ограниченная очередь.** Если ждать слот могут бесконечно многие, всплеск превращается в рост памяти и латентности; лучше быстро отказать и дать вызывающему деградировать;
- **пул соединений.** `SocketsHttpHandler.MaxConnectionsPerServer` (по умолчанию не ограничен) ограничивает соединения, а не запросы: для HTTP/1.1 это почти одно и то же, для HTTP/2 — нет, запросы мультиплексируются. Как самостоятельный лимитер он неудобен — ожидание соединения не видно в метриках и не управляется очередью;
- **обратная связь.** Обрабатывайте `429`/`503` и `Retry-After` — лимит на стороне партнёра может меняться.

**Метрики, которые нужны:** текущее число занятых слотов, длина очереди ожидания, время ожидания слота, число отказов лимитера. Без них невозможно понять, упираетесь ли вы в лимит или в латентность партнёра.

**Что спросят дальше:** почему `WaitAsync`, а не `Wait`; чем concurrency limit отличается от rate limit (одновременные запросы против запросов в секунду); как реализовать bulkhead.

## Чем SemaphoreSlim.WaitAsync лучше блокирующего Wait при высокой нагрузке?

```yaml
category: multithreading
level: senior
difficulty: 4
slug: advanced-concurrency-chem-semaphoreslim-waitasync-luchshe-blokiruyuschego-wait-pri-vysokoi
tags: throttling, async
```

`Wait()` **блокирует поток** на всё время ожидания слота, а `WaitAsync()` возвращает задачу и отпускает поток обратно в пул. При 1000 ожидающих запросов `Wait` держит 1000 заблокированных потоков пула — прямой путь к ThreadPool starvation, — а `WaitAsync` держит 1000 небольших объектов в очереди семафора и ноль потоков.

**Что происходит внутри:**

- `Wait()` сначала коротко крутит spin-ожидание, затем засыпает на `Monitor.Wait` внутреннего объекта. Поток занят, его стек (1 МБ зарезервированной памяти) и место в пуле — тоже;
- `WaitAsync()` при свободном слоте завершается синхронно (возвращает уже завершённую задачу, без аллокации). Если слотов нет — создаёт внутренний объект-задачу, кладёт его в связный список ожидающих и возвращает. `Release()` берёт первого ожидающего и завершает его задачу; продолжение выполняется в пуле.

```csharp
// Плохо под нагрузкой: 500 запросов ждут — 500 потоков пула заблокированы
_gate.Wait();
try { await CallAsync(); } finally { _gate.Release(); }

// Хорошо: ждущие — это задачи, а не потоки
await _gate.WaitAsync(ct);
try { await CallAsync(); } finally { _gate.Release(); }
```

**Сравнение под нагрузкой:**

| | `Wait()` | `WaitAsync()` |
| --- | --- | --- |
| стоимость одного ожидающего | поток пула + стек | объект задачи (~100 байт) |
| влияние на пул | блокирует потоки, пул вынужден создавать новые | нет |
| поток после освобождения | тот же, что ждал | любой поток пула |
| отмена | `Wait(ct)` — да | `WaitAsync(ct)` — да, без удержания потока |
| таймаут | `Wait(TimeSpan)` | `WaitAsync(TimeSpan)` |
| латентность при свободном слоте | минимальная | почти такая же — синхронный быстрый путь |

**Почему это критично именно при высокой нагрузке.** Пока ожидающих мало, разница не видна. Но семафор часто ставят как раз перед узким местом (БД, внешний API), где при деградации очередь ожидающих растёт. С `Wait` рост очереди = рост заблокированных потоков = starvation всего процесса, включая эндпоинты, которые с этим ресурсом вообще не работают. С `WaitAsync` деградирует только путь, который обращается к ресурсу.

**Когда `Wait` уместен:** в чисто синхронном коде на выделенном потоке (не в пуле) или в консольной утилите — там смешивать `WaitAsync` с блокировкой ещё хуже. Смешивать `Wait` и `WaitAsync` на одном семафоре можно, но это обычно признак sync-over-async.

**Подводные камни `WaitAsync`:**

- `WaitAsync` должен стоять **до** `try`, а `Release` — в `finally`, иначе при отмене во время ожидания `Release` вернёт слот, которого не брали;
- отменённое ожидание бросает `OperationCanceledException` — это нормально, но его нужно учитывать в логике повторов;
- ожидающие никак не ограничены — при длительной деградации очередь задач растёт неограниченно. Если это проблема, используйте таймаут (`WaitAsync(TimeSpan, ct)` возвращает `bool`) или `ConcurrencyLimiter` с `QueueLimit`;
- `SemaphoreSlim` не реентерабелен и не гарантирует FIFO.

**Что спросят дальше:** как ограничить длину очереди ожидающих, что такое ThreadPool starvation, почему `SemaphoreSlim` подходит как асинхронная блокировка, а `lock` — нет.

## Как устроен Channel<T> и когда bounded-канал предпочтительнее unbounded?

```yaml
category: multithreading
level: senior
difficulty: 4
slug: advanced-concurrency-kak-ustroen-channel-t-i-kogda-bounded-kanal-predpochtitelnee-unbounded
tags: channels, backpressure
```

Канал — это буфер элементов плюс очереди **ожидающих операций** (читателей, ждущих данных, и писателей, ждущих места), реализованные на переиспользуемых `IValueTaskSource`, поэтому ожидание не блокирует потоки и в устойчивом режиме почти не аллоцирует. Bounded-канал предпочтителен почти всегда, когда производитель может обогнать потребителя: он ограничивает память и передаёт давление обратно производителю. Unbounded оправдан, только если скорость записи ограничена извне и заведомо ниже скорости чтения.

**Что внутри (реализация `System.Threading.Channels`):**

- **unbounded** — элементы лежат в lock-free `ConcurrentQueue<T>`, блокировка берётся только для работы со списком ожидающих читателей. Для `SingleReader = true` используется отдельная, более дешёвая реализация;
- **bounded** — элементы в деке (кольцевом буфере) под одной блокировкой канала, плюс очереди заблокированных писателей и читателей. Когда писатель кладёт элемент, а читатель уже ждёт, элемент передаётся ему напрямую, минуя буфер;
- **ожидание** — `ReadAsync`/`WriteAsync` возвращают `ValueTask`. Если данные или место есть, операция завершается синхронно без аллокаций. Если нет — регистрируется объект-операция (`IValueTaskSource`); при `SingleReader` этот объект у читателя один и переиспользуется;
- **продолжения** по умолчанию запускаются асинхронно в пуле, чтобы писатель не выполнял код читателя в своём потоке; `AllowSynchronousContinuations = true` меняет это ради латентности;
- **завершение** — `Writer.Complete(ex)` помечает канал закрытым; читатели дочитывают оставшееся, после чего `ReadAsync` бросает `ChannelClosedException` (переданное в `Complete` исключение — в `InnerException`), а `WaitToReadAsync` возвращает `false`.

**Режимы переполнения bounded-канала (`FullMode`):**

| Режим | Поведение при полном буфере | Когда |
| --- | --- | --- |
| `Wait` | `WriteAsync` ждёт места, `TryWrite` возвращает `false` | задания нельзя терять — backpressure на производителя |
| `DropOldest` | выбрасывается самый старый элемент | телеметрия, «важно последнее состояние» |
| `DropNewest` | выбрасывается самый новый элемент в буфере | редко: сохранить историю, пожертвовав свежими |
| `DropWrite` | записываемый элемент отбрасывается, запись «успешна» | мягкое отбрасывание всплеска |

Для режимов с отбрасыванием есть перегрузка `Channel.CreateBounded(options, itemDropped)` — колбэк, куда можно сообщить в метрики или освободить ресурсы элемента.

**Когда bounded, когда unbounded:**

- **bounded** — источник внешний и неконтролируемый (HTTP, очередь сообщений, файл), потребитель медленнее (БД, внешний API), элементы тяжёлые. Ёмкость подбирают как «сколько элементов допустимо потерять при падении и сколько памяти не жалко», а не «побольше на всякий случай»;
- **unbounded** — производитель сам ограничен (например, таймер раз в секунду или ответы на ограниченное число запросов), нужна гарантированная неблокирующая запись из синхронного кода (`TryWrite` всегда успешен), или канал служит внутренним «почтовым ящиком» актора с небольшим трафиком.

**Цена bounded:** одна блокировка на весь канал, поэтому при очень большом количестве производителей и потребителей он заметно медленнее unbounded. Это редко важно — канал почти никогда не бывает узким местом по сравнению с работой потребителя.

**Частые ошибки:**

- unbounded «потому что проще», а потом OOM при всплеске;
- `Wait`-режим в канале, куда пишет HTTP-обработчик, без таймаута или отмены — запросы висят вместо быстрого отказа;
- ёмкость в элементах при сильно разном размере элементов — тогда контролируют байты отдельно (семафор или счётчик);
- отсутствие `Complete` — потребитель никогда не узнает, что работы больше не будет.

В .NET 9 появился `Channel.CreateUnboundedPrioritized` — unbounded-канал, отдающий элементы по приоритету через `IComparer<T>`.

**Что спросят дальше:** как реализовать backpressure до внешнего клиента, как корректно остановить потребителя, чем канал отличается от TPL Dataflow `BufferBlock`.

## Как реализовать backpressure, чтобы очередь не съела всю память при всплеске нагрузки?

```yaml
category: multithreading
level: senior
difficulty: 5
slug: advanced-concurrency-kak-realizovat-backpressure-chtoby-ochered-ne-sela-vsyu-pamyat-pri-vsp
tags: backpressure, scalability
```

Backpressure — это **обратная связь от медленного потребителя к быстрому производителю**: каждая очередь в системе ограничена, и когда она заполнена, производитель либо замедляется (ждёт), либо получает быстрый отказ, либо данные сознательно отбрасываются. Неограниченная очередь не устраняет перегрузку — она превращает её в рост памяти и латентности, пока процесс не упадёт.

**Три стратегии, и выбор зависит от того, можно ли замедлить источник:**

| Стратегия | Как | Когда |
| --- | --- | --- |
| **замедлить** производителя | bounded-канал с `FullMode.Wait`, ограниченный prefetch у брокера | источник под вашим контролем: внутренний конвейер, консьюмер очереди |
| **отказать** (load shedding) | `TryWrite` → `503`/`429` с `Retry-After` | внешний клиент, которого нельзя «притормозить» |
| **отбросить/сжать** | `DropOldest`, семплирование, объединение событий | телеметрия, метрики, «важно последнее значение» |

**Внутренний конвейер — давление распространяется само:**

```csharp
var parsed = Channel.CreateBounded<Record>(new BoundedChannelOptions(500)
    { FullMode = BoundedChannelFullMode.Wait, SingleWriter = true });

// Стадия 1: чтение. Если БД тормозит, WriteAsync ждёт — чтение файла замедляется
await foreach (var line in ReadLinesAsync(file, ct))
    await parsed.Writer.WriteAsync(Parse(line), ct);
parsed.Writer.Complete();

// Стадия 2: запись в БД батчами до 100 элементов
var batch = new List<Record>(100);
while (await parsed.Reader.WaitToReadAsync(ct))
{
    while (batch.Count < 100 && parsed.Reader.TryRead(out var r)) batch.Add(r);
    await db.BulkInsertAsync(batch, ct);
    batch.Clear();
}
```

Память ограничена сверху: 500 элементов в канале плюс один батч.

**HTTP-вход — отказывать быстро:**

```csharp
app.MapPost("/events", (Event e, ChannelWriter<Event> writer) =>
    writer.TryWrite(e)
        ? Results.Accepted()
        : Results.StatusCode(StatusCodes.Status503ServiceUnavailable));
```

Ждать в обработчике (`WriteAsync` без таймаута) плохо: запросы накапливаются в Kestrel, держат соединения и память, клиент всё равно отвалится по таймауту — и, скорее всего, повторит запрос. Дополнительно на входе: rate limiting middleware (`AddRateLimiter` с `ConcurrencyLimiter`/`TokenBucket` и ограниченной очередью), лимиты Kestrel (`MaxConcurrentConnections`, `MaxRequestBodySize`).

**Консьюмер брокера — не забирать больше, чем обработаешь:**

- RabbitMQ — `prefetch` (QoS) ограничивает количество неподтверждённых сообщений;
- Kafka — ограничение `max.poll.records`, пауза партиций (`Pause`/`Resume`), когда внутренний канал полон;
- подтверждать сообщение после обработки, а не при получении, — иначе локальная очередь снова становится неограниченной.

**Что ограничивать — элементы или байты.** Если размеры элементов сильно разнятся (от 1 КБ до 10 МБ), лимит «1000 элементов» не защищает память. Тогда вводят бюджет в байтах: `SemaphoreSlim` с разрешениями на килобайты или счётчик через `Interlocked`, проверяемый перед записью. Для потоковых байтов готовое решение — `System.IO.Pipelines` с `PauseWriterThreshold`/`ResumeWriterThreshold`.

**Скрытые неограниченные очереди, которые ломают backpressure:**

- `Task.Run`/`ThreadPool.QueueUserWorkItem` на каждый элемент — очередь пула не ограничена;
- `Task.WhenAll` по всем элементам сразу;
- `ConcurrentQueue` или `List` как буфер между стадиями;
- `SemaphoreSlim.WaitAsync` без таймаута — ожидающие задачи тоже копятся;
- ретраи с бесконечной очередью повторов.

**Метрики:** заполненность каждой очереди (`Reader.Count` у bounded-канала доступен), время ожидания записи, число отказов/отброшенных элементов. Постоянно полная очередь — сигнал масштабировать потребителя, а не увеличивать ёмкость.

**Что спросят дальше:** какой `FullMode` выбрать для телеметрии, как сделать backpressure в распределённой системе, чем pull-модель (`IAsyncEnumerable`) естественно поддерживает backpressure.

## Что делать, если ConcurrentDictionary стал узким местом под нагрузкой?

```yaml
category: multithreading
level: senior
difficulty: 5
slug: advanced-concurrency-chto-delat-esli-concurrentdictionary-stal-uzkim-mestom-pod-nagruzkoi
tags: collections, contention
```

Сначала выяснить, **что именно** тормозит: обычно это не сами чтения (они lock-free), а операции, берущие **все** блокировки (`Count`, `Keys`, `Values`, `ToArray`, ресайз), запись в один «горячий» ключ, дорогие фабрики в `AddOrUpdate`, или GC-нагрузка от миллионов узлов. Лечение зависит от причины: убрать глобальные операции, заранее задать ёмкость, держать изменяемое значение вместо перезаписи ключа, шардировать, или заменить структуру на снимки для чтения.

**Как устроен `ConcurrentDictionary`:**

- **чтения** (`TryGetValue`, `ContainsKey`, перечисление) — без блокировок, через volatile-чтения таблицы бакетов;
- **записи** — блокировка одного из массива «полос» (lock striping): ключ → бакет → блокировка. Количество блокировок по умолчанию равно числу ядер и растёт вместе с таблицей до предела;
- **ресайз таблицы** и ряд операций над всей коллекцией **захватывают все блокировки**;
- каждый элемент — отдельный объект-узел в куче.

**Типичные причины и решения:**

| Симптом | Причина | Что сделать |
| --- | --- | --- |
| всплески латентности при росте | ресайз с захватом всех блокировок | задать `capacity` (и `concurrencyLevel`) в конструкторе |
| тормозит «везде», CPU в `AcquireAllLocks` | `Count`, `Keys`, `Values`, `ToArray` в горячем пути | вести отдельный счётчик через `Interlocked`; перечислять словарь напрямую |
| contention на одном ключе | тысячи записей в один ключ (`AddOrUpdate` счётчика) | изменяемое значение: `dict.GetOrAdd(key, _ => new Counter())` и `Interlocked` по полю объекта |
| `AddOrUpdate` жжёт CPU | фабрика обновления дорогая и повторяется при конфликтах | дешёвые фабрики; вычислять заранее; изменяемое значение |
| gen2 GC, большие паузы | миллионы узлов и ключей-строк | меньше элементов (агрегация), структуры-значения, другая структура данных |
| много чтений, редкие изменения | даже lock-free чтения платят за volatile и индирекцию | `FrozenDictionary`/`ImmutableDictionary` снимок + замена ссылки |

**Изменяемое значение вместо перезаписи ключа:**

```csharp
sealed class Counter { public long Value; }

var counters = new ConcurrentDictionary<string, Counter>();

// Запись в словарь — только при первом появлении ключа;
// дальше — атомарная операция над полем, без блокировки полосы
Interlocked.Increment(ref counters.GetOrAdd(key, static _ => new Counter()).Value);
```

**Шардирование:** N независимых словарей, выбор по `hash(key) % N`, — помогает, когда нужно ещё меньше конфликтов или операции над «всей коллекцией» можно делать по шардам. Для агрегатов (метрики, счётчики) ещё лучше **локальная агрегация**: каждый поток/запрос копит в свой словарь и периодически сливает в общий.

**Снимки для read-mostly данных:**

```csharp
private volatile FrozenDictionary<string, Route> _routes = FrozenDictionary<string, Route>.Empty;

public void Reload(IEnumerable<Route> routes) =>
    _routes = routes.ToFrozenDictionary(r => r.Key);   // публикация новой версии

public Route? Find(string key) => _routes.GetValueOrDefault(key);
```

Чтения из `FrozenDictionary` (.NET 8+) заметно быстрее, построение — дороже; подходит, если обновления — редкие события.

**Мелочи, которые дают проценты:** дешёвый `IEqualityComparer` (например, `StringComparer.Ordinal` вместо культурного сравнения), отсутствие аллокации ключа при поиске (`GetAlternateLookup<ReadOnlySpan<char>>` в .NET 9+ позволяет искать строковый ключ по span), `GetOrAdd(key, factory, arg)` со `static`-лямбдой — без замыкания на каждый вызов.

**Как подтвердить диагноз:** CPU-профиль (`dotnet-trace`, PerfView) — видно, сидит ли время в `AcquireAllLocks`, `GrowTable`, `Monitor.Enter` внутри `TryAddInternal` или в фабриках; BenchmarkDotNet с реальным числом потоков и распределением ключей.

**Что спросят дальше:** почему `GetOrAdd` может вызвать фабрику дважды, чем lock striping лучше одной блокировки, когда `FrozenDictionary` хуже `ConcurrentDictionary`.

## Как GetOrAdd в ConcurrentDictionary может вызвать фабрику дважды и чем это опасно?

```yaml
category: multithreading
level: senior
difficulty: 4
slug: advanced-concurrency-kak-getoradd-v-concurrentdictionary-mozhet-vyzvat-fabriku-dvazhdy-i-ch
tags: collections, concurrency
```

`GetOrAdd(key, factory)` вызывает фабрику **вне блокировки**: если два потока одновременно не нашли ключ, оба вызовут фабрику, но в словарь попадёт только одно значение, и оба потока получат именно его. Второе созданное значение просто выбрасывается. Это опасно, когда фабрика дорогая, имеет побочные эффекты или создаёт ресурс, требующий освобождения.

**Почему так сделано.** Если вызывать пользовательскую фабрику под блокировкой полосы, медленная фабрика заблокирует все ключи этой полосы, а фабрика, обращающаяся к тому же словарю, может устроить deadlock. Поэтому алгоритм такой:

```text
1. TryGetValue(key) — нет
2. value = factory(key)           ← без блокировки, может выполняться в нескольких потоках
3. TryAddInternal(key, value)     ← под блокировкой: если ключ уже есть, вернуть существующее
```

**Чем опасно:**

- **утечка ресурсов** — фабрика открывает соединение, создаёт `HttpClient`, `Timer`, подписку; проигравший экземпляр никто не освободит;
- **дублирование побочных эффектов** — запись в БД, отправка сообщения, инкремент метрик, логирование «создан объект»;
- **cache stampede** — при холодном кэше сотни запросов одновременно выполняют тяжёлый запрос к БД за одним и тем же ключом;
- **неверные допущения** — код полагается на то, что фабрика вызвана ровно один раз (например, регистрирует объект в другом реестре).

То же относится к `AddOrUpdate`: `updateValueFactory` при конфликте вызывается повторно, поэтому она должна быть чистой функцией.

**Решение — `Lazy<T>` как значение:**

```csharp
private readonly ConcurrentDictionary<string, Lazy<Connection>> _connections = new();

public Connection Get(string name) =>
    _connections.GetOrAdd(name,
        static n => new Lazy<Connection>(() => Connection.Open(n),
                                         LazyThreadSafetyMode.ExecutionAndPublication))
        .Value;
```

Создать лишний `Lazy` дёшево и безопасно — он ничего не делает до обращения к `Value`. В словарь попадает один `Lazy`, и благодаря `ExecutionAndPublication` фабрика внутри выполнится ровно один раз, остальные потоки дождутся результата.

**Нюансы `Lazy`-решения:**

- **исключения кэшируются** — если `Connection.Open` упал, `Lazy` будет бросать это исключение вечно. Нужно удалять элемент при ошибке:

```csharp
var lazy = _connections.GetOrAdd(name, factory);
try { return lazy.Value; }
catch
{
    _connections.TryRemove(new KeyValuePair<string, Lazy<Connection>>(name, lazy)); // удалить именно этот экземпляр
    throw;
}
```

- **async-фабрика** — `Lazy<Task<T>>`: в словаре одна задача, все ждут её. Упавшую задачу так же удаляют, иначе ошибка закэшируется;
- **гарантия одного вызова — только в пределах процесса.** Для нескольких инстансов нужен распределённый механизм (блокировка в Redis/БД или идемпотентность самой операции).

**Альтернативы:**

- `IMemoryCache.GetOrCreateAsync` **тоже не защищает** от параллельного вызова фабрики — нужна та же обёртка;
- `HybridCache` (.NET 9, `Microsoft.Extensions.Caching.Hybrid`) из коробки защищает от stampede: параллельные запросы одного ключа ждут одно выполнение фабрики;
- если фабрика дешёвая и чистая (например, `new object()`, вычисление из ключа) — ничего делать не нужно, двойной вызов безвреден.

**Что спросят дальше:** почему фабрика не вызывается под блокировкой, как защититься от cache stampede в распределённой системе, какие режимы есть у `LazyThreadSafetyMode`.

## Чем AsyncLocal отличается от ThreadLocal и где это критично?

```yaml
category: multithreading
level: senior
difficulty: 4
slug: advanced-concurrency-chem-asynclocal-otlichaetsya-ot-threadlocal-i-gde-eto-kritichno
tags: async, context
```

`ThreadLocal<T>` (и `[ThreadStatic]`) хранит значение **на OS-поток**; `AsyncLocal<T>` — на **логический поток выполнения**: значение хранится в `ExecutionContext` и «течёт» вместе с `await`, `Task.Run`, таймерами и `ThreadPool.QueueUserWorkItem`, независимо от того, на каком потоке продолжится код. В async-коде `ThreadLocal` практически всегда ошибка: после `await` вы можете оказаться на другом потоке и прочитать чужое значение.

```csharp
static readonly ThreadLocal<string?> Tl = new();
static readonly AsyncLocal<string?> Al = new();

async Task HandleAsync(string user)
{
    Tl.Value = user;
    Al.Value = user;
    await Task.Delay(10);           // продолжение — на другом потоке пула
    Console.WriteLine(Tl.Value);    // null или значение ДРУГОГО запроса
    Console.WriteLine(Al.Value);    // user
}
```

**Как работает `AsyncLocal`:**

- `ExecutionContext` — неизменяемый словарь значений AsyncLocal. Установка значения создаёт новый контекст (copy-on-write);
- при `await`, `Task.Run`, постановке в пул текущий контекст **захватывается** и восстанавливается там, где продолжается выполнение;
- **изменения текут только вниз**: значение, установленное внутри вызванного async-метода, не видно вызывающему после возврата — при выходе из async-метода контекст восстанавливается. Дочерние задачи получают копию на момент запуска.

```csharp
async Task Outer()
{
    Al.Value = "outer";
    await Inner();
    Console.WriteLine(Al.Value);   // "outer", а не "inner"
}
async Task Inner() { Al.Value = "inner"; await Task.Yield(); }
```

**Где разница критична:**

| Сценарий | Правильный выбор | Почему |
| --- | --- | --- |
| контекст запроса: пользователь, tenant, correlation id | `AsyncLocal` | запрос кочует между потоками |
| `IHttpContextAccessor`, `Activity.Current`, logging scopes | уже на `AsyncLocal` | трассировка должна пережить `await` |
| `TransactionScope` в async-коде | `TransactionScopeAsyncFlowOption.Enabled` | иначе транзакция привязана к потоку и теряется после `await` |
| per-thread кэш буферов, `StringBuilder`, генератор | `ThreadLocal`/`[ThreadStatic]` | нужна изоляция по физическому потоку, чтобы не синхронизироваться |
| CPU-bound `Parallel.For` с локальным состоянием | `localInit` или `ThreadLocal` | итерации одного потока используют один объект |

**Подводные камни `AsyncLocal`:**

- **утечка во фоновые задачи.** `Task.Run` или таймер, запущенный внутри запроса, унаследует его контекст — и будет держать `HttpContext`, пользователя, `Activity` после завершения запроса. Долгоживущие фоновые циклы запускайте под `ExecutionContext.SuppressFlow()` или вне контекста запроса;
- **«ошибки» обратного распространения.** Установить значение в методе инициализации и ожидать увидеть его у вызывающего — не работает, если метод async. Для передачи наверх храните в AsyncLocal изменяемый объект-холдер и меняйте его поле (так делает `HttpContextAccessor`);
- **стоимость.** Каждая установка аллоцирует новый контекст; десятки AsyncLocal-переменных, меняющихся в горячем цикле, заметны в профиле.

**Подводные камни `ThreadLocal`:**

- значения живут, пока жив поток; потоки пула живут долго — забытое значение одного запроса «доживёт» до следующего, попавшего на этот поток;
- `ThreadLocal<T>` — `IDisposable`; при `trackAllValues: true` можно получить все значения (`Values`) для агрегации;
- `[ThreadStatic]` быстрее `ThreadLocal<T>`, но инициализатор поля выполнится только для первого потока — в остальных будет `default`.

**Что спросят дальше:** как `ExecutionContext` отличается от `SynchronizationContext`, что делает `SuppressFlow`, как устроен `IHttpContextAccessor` и почему он небезопасен вне запроса.

## Как правильно реализовать асинхронную блокировку и почему lock тут не подходит?

```yaml
category: multithreading
level: senior
difficulty: 4
slug: advanced-concurrency-kak-pravilno-realizovat-asinhronnuyu-blokirovku-i-pochemu-lock-tut-ne
tags: synchronization, async
```

`lock` не подходит, потому что `Monitor` привязан к потоку-владельцу, а асинхронная операция после `await` продолжается на другом потоке — компилятор запрещает `await` внутри `lock`. Правильная асинхронная блокировка строится на примитиве **без владельца**, ожидание в котором — это задача, а не заблокированный поток: на практике — обёртка над `SemaphoreSlim(1, 1)` с `using`-освобождением, а для блокировки по ключу — словарь семафоров с подсчётом ссылок.

**Минимальная корректная реализация:**

```csharp
public sealed class AsyncLock
{
    private readonly SemaphoreSlim _semaphore = new(1, 1);

    public async ValueTask<Releaser> LockAsync(CancellationToken ct = default)
    {
        await _semaphore.WaitAsync(ct).ConfigureAwait(false);
        return new Releaser(_semaphore);
    }

    public readonly struct Releaser(SemaphoreSlim semaphore) : IDisposable
    {
        public void Dispose() => semaphore?.Release();
    }
}

// Использование
using (await _lock.LockAsync(ct))
{
    await RefreshCacheAsync(ct);
}
```

Что здесь важно:

- захват происходит **до** входа в `using`: если ожидание отменено, `Releaser` не создан и лишнего `Release` не будет;
- `SemaphoreSlim.WaitAsync` уже имеет быстрый синхронный путь — при свободной блокировке нет аллокации задачи;
- `ConfigureAwait(false)` — блокировку можно использовать из кода с `SynchronizationContext` без риска deadlock на её собственном продолжении.

**Ограничения, которые надо осознавать:**

- **нет реентерабельности.** Повторный `LockAsync` из той же логической операции ждёт сам себя — вечный deadlock. «Узнать владельца» нельзя: потока-владельца нет, а `AsyncLocal`-флаг «я уже внутри» течёт и в дочерние задачи, превращая реентерабельность в дыру во взаимном исключении. Правильно — не вызывать публичные методы с блокировкой изнутри, а выделить внутренние методы, предполагающие, что блокировка уже взята;
- **двойной `Dispose`** освободит семафор дважды (для `new(1, 1)` — `SemaphoreFullException`, для большего максимума — тихая порча). Если это риск, делайте `Releaser` классом с флагом через `Interlocked.Exchange`;
- **порядок ожидающих** не гарантирован как строгий FIFO;
- **только в пределах процесса.** Между инстансами нужна распределённая блокировка (Redis с lease, advisory lock в PostgreSQL) — и она требует таймаутов и fencing token, а не просто «взять и отпустить».

**Блокировка по ключу** (например, «одна операция на пользователя»):

```csharp
public sealed class KeyedAsyncLock<TKey> where TKey : notnull
{
    private readonly Dictionary<TKey, (SemaphoreSlim Sem, int Refs)> _map = new();

    public async ValueTask<IDisposable> LockAsync(TKey key, CancellationToken ct)
    {
        SemaphoreSlim sem;
        lock (_map)
        {
            var e = _map.TryGetValue(key, out var x) ? x : (new SemaphoreSlim(1, 1), 0);
            _map[key] = (e.Item1, e.Item2 + 1);
            sem = e.Item1;
        }
        try { await sem.WaitAsync(ct).ConfigureAwait(false); }
        catch { Release(key, releaseSemaphore: false); throw; }
        return new Handle(this, key);
    }

    private void Release(TKey key, bool releaseSemaphore)
    {
        lock (_map)
        {
            var (sem, refs) = _map[key];
            if (releaseSemaphore) sem.Release();
            if (refs == 1) _map.Remove(key); else _map[key] = (sem, refs - 1);
        }
    }

    private sealed class Handle(KeyedAsyncLock<TKey> owner, TKey key) : IDisposable
    {
        private int _disposed;
        public void Dispose()
        {
            if (Interlocked.Exchange(ref _disposed, 1) == 0) owner.Release(key, releaseSemaphore: true);
        }
    }
}
```

Счётчик ссылок нужен, чтобы удалять семафор, когда он никому не нужен, — иначе словарь растёт бесконечно (по семафору на каждого пользователя за всё время жизни процесса). Удалять семафор из `ConcurrentDictionary` без счётчика опасно: другой поток может как раз ожидать удаляемый экземпляр, а новый пришедший создаст второй — и взаимное исключение нарушено. Короткий синхронный `lock` над словарём здесь уместен — внутри нет `await`.

**Если пишете свою блокировку на `TaskCompletionSource`,** создавайте его с `TaskCreationOptions.RunContinuationsAsynchronously`. Иначе `SetResult` в `Release` выполнит продолжение следующего ожидающего синхронно — внутри вызова `Release` в чужом потоке, что даёт неожиданную реентерабельность и глубокие стеки.

**Часто лучше обойтись без блокировки:** один consumer над `Channel<T>` сериализует операции без явных блокировок, а `Lazy<Task<T>>` решает задачу «инициализировать один раз».

**Что спросят дальше:** почему асинхронная блокировка не может быть реентерабельной, как сделать распределённую блокировку корректной (lease, fencing), чем `RunContinuationsAsynchronously` защищает от deadlock.

## Как протестировать код на race condition, если баг воспроизводится раз в сутки?

```yaml
category: multithreading
level: senior
difficulty: 5
slug: advanced-concurrency-kak-protestirovat-kod-na-race-condition-esli-bag-vosproizvoditsya-raz
tags: testing, concurrency
```

Цель — превратить «раз в сутки» в «раз в минуту», а затем в «каждый прогон»: **увеличить вероятность** опасного чередования (стресс, одновременный старт, инъекция задержек в подозрительные точки), **систематически перебрать** чередования инструментом вроде Microsoft Coyote и параллельно **собрать улики в проде** — инварианты, которые фиксируют нарушение в момент возникновения, а не через час по последствиям.

**1. Сузить подозреваемых по коду.** Гонки почти всегда там, где есть: общее изменяемое поле без синхронизации, check-then-act (`if (!dict.ContainsKey) dict.Add`), ленивая инициализация, чтение вне `lock`, `static` мутабельное состояние, `async void`, события и колбэки из разных потоков, неправильно оформленный `CancellationTokenSource`/`Timer`. Логи с идентификатором потока и корреляцией обычно указывают на пару конкурирующих операций.

**2. Стресс-тест, который реально создаёт конкуренцию:**

```csharp
[Fact]
public async Task Withdraw_is_atomic_under_contention()
{
    for (int run = 0; run < 1_000; run++)
    {
        var account = new Account(balance: 100);
        using var start = new Barrier(participantCount: 8);

        var tasks = Enumerable.Range(0, 8).Select(_ => Task.Factory.StartNew(() =>
        {
            start.SignalAndWait();                 // все стартуют одновременно
            account.TryWithdraw(100);
        }, TaskCreationOptions.LongRunning));      // отдельные потоки, а не очередь пула

        await Task.WhenAll(tasks);
        Assert.True(account.Balance >= 0, $"run {run}: {account.Balance}");
    }
}
```

Ключевые приёмы: `Barrier`/`ManualResetEventSlim` для одновременного старта (без него потоки часто выполняются по очереди), тысячи итераций, число потоков больше числа ядер, запуск в Release (JIT-оптимизации меняют картину), прогон на **ARM64** — слабая модель памяти проявляет ошибки упорядочивания, скрытые на x86.

**3. Расширить окно гонки.** Вставить задержку между «проверкой» и «действием» через тестовый шов — `Thread.Yield()`/`Task.Delay` в mock-зависимости, хук, срабатывающий только в тестах. Когда окно расширено до миллисекунд, редкая гонка воспроизводится почти всегда, и это же становится регрессионным тестом.

**4. Систематическое тестирование — Microsoft Coyote.** Coyote переписывает сборки и берёт планирование задач под свой контроль: вместо случайных чередований ОС он **детерминированно перебирает** их по стратегиям поиска, а найденный баг воспроизводится повторно по сохранённому seed-трейсу. Это самый эффективный способ для async-кода, где вариантов чередований слишком много для «удачного» стресс-теста.

**5. Детерминированное время.** Если гонка связана с таймерами и таймаутами, внедрите `TimeProvider` (.NET 8+) и в тестах используйте `FakeTimeProvider` из `Microsoft.Extensions.TimeProvider.Testing` — порядок срабатываний станет управляемым.

**6. Ловить в проде по инварианту, а не по последствиям:**

- проверки инвариантов в коде (`Debug.Assert` в тестовых сборках, счётчик нарушений и подробный лог в проде) там, где гонка портит состояние;
- при нарушении — снять дамп (`dotnet-dump` через триггер, `DOTNET_DbgEnableMiniDump` при падении) и лог последних событий из кольцевого буфера;
- метрика «число нарушений инварианта» с алертом — видно, помогает ли исправление.

**7. Исправить и доказать.** Сначала добиться стабильного воспроизведения, затем исправить (чаще всего — сделать операцию атомарной под одной блокировкой или через атомарный API коллекции), и оставить воспроизводящий тест в CI. Исправление «на глаз» без воспроизведения — лотерея: частота бага просто уменьшится.

**Чего нет в .NET:** аналога ThreadSanitizer для управляемого кода, который бы находил гонки данных автоматически. Поэтому вес ложится на дизайн (неизменяемость, владение, каналы), ревью и перечисленные техники.

**Что спросят дальше:** как работает Coyote, почему гонка чаще воспроизводится на ARM, как избежать flaky-тестов при стресс-тестировании (отдельная категория тестов, бюджет времени, стабильный seed).

## Что такое false sharing и как его обнаружить в реальном коде?

```yaml
category: multithreading
level: senior
difficulty: 5
slug: advanced-concurrency-chto-takoe-false-sharing-i-kak-ego-obnaruzhit-v-realnom-kode
tags: performance, cpu-cache
```

False sharing — деградация производительности, когда потоки на разных ядрах пишут в **разные** данные, попавшие в **одну кэш-линию**: протокол когерентности гоняет линию между ядрами на каждой записи. В реальном коде его обнаруживают по **аномалии масштабирования** (больше потоков — не быстрее или медленнее, при этом нет блокировок), подтверждают **аппаратными счётчиками** (HITM-события, `perf c2c`, VTune) и окончательно — экспериментом с паддингом.

**Признаки в профиле:**

- CPU 100%, lock contention нулевой, но пропускная способность не растёт с потоками или падает;
- CPU-профиль показывает время на простых инструкциях — инкременте поля, записи в массив, — которые «не должны» быть горячими;
- метрики IPC (инструкций за такт) резко падают при переходе от одного потока к нескольким;
- проблема исчезает при привязке всех потоков к одному ядру или при их сокращении до одного.

**Инструменты:**

| Инструмент | Что показывает |
| --- | --- |
| `perf c2c record` / `perf c2c report` (Linux) | кэш-линии с наибольшим числом HITM (загрузки, попавшие в модифицированную линию другого ядра), смещения внутри линии и адреса инструкций |
| Intel VTune (Memory Access, Microarchitecture Exploration) | contested accesses, false sharing по линиям и функциям |
| AMD uProf | аналогичные счётчики для AMD |
| BenchmarkDotNet + `[HardwareCounters]` | cache misses и др. PMC-счётчики в бенчмарке (Windows, права администратора) |
| эксперимент | добавить паддинг и сравнить — самый надёжный финальный тест |

Для JIT-кода `perf` нужен с картой символов (`DOTNET_PerfMapEnabled=1`), чтобы адреса инструкций превращались в имена методов .NET.

**Где искать в .NET-коде:**

- массивы счётчиков/накопителей, индексируемые номером потока или воркера (`long[] perWorker`);
- массив структур, где каждый поток пишет в свой элемент (`Stats[] { long Hits; long Misses; }`);
- **поля одного объекта**, которые пишут разные потоки: `_head` и `_tail` очереди, `_produced` и `_consumed`, флаг состояния рядом с часто читаемым полем;
- **соседние маленькие объекты**, выделенные подряд — аллокатор .NET кладёт их рядом, и GC при сжатии тоже может уплотнить их вплотную;
- «горячее» поле, которое часто читают все, в одной линии с полем, которое часто пишет один поток — это тоже false sharing (читатели постоянно промахиваются).

**Минимальный эксперимент:**

```csharp
[StructLayout(LayoutKind.Explicit, Size = 128)]
struct PaddedCounter { [FieldOffset(64)] public long Value; }   // поле в середине блока

// Было: long[] counters — 8 счётчиков в одной линии
// Стало: PaddedCounter[] counters — каждый в своей паре линий
```

Если время работы падает в разы при неизменной логике — это был false sharing. Размер 128 байт выбирают потому, что пространственный префетчер Intel подкачивает линии парами, а на Apple M-series и ряде ARM-серверов сама линия — 128 байт.

**Как исправлять в реальном коде (а не только паддингом):**

- **не делить линию** — локальное накопление в потоке с одним слиянием в конце;
- **шардировать** с паддингом — счётчик на ядро, индекс через `Thread.GetCurrentProcessorId()` (дёшево, но поток может мигрировать — значит, шард всё равно обновляется атомарно);
- **раскладывать поля** по частоте записи: поля, которые пишут разные потоки, — в разные объекты или с паддингом между ними;
- помнить про цену: паддинг увеличивает память в разы, применять его стоит только к доказанно горячим структурам.

**Как BCL решает это внутри:** `ConcurrentQueue<T>` разносит индексы головы и хвоста сегмента паддингом, пул потоков и `ArrayPool.Shared` держат per-core/per-thread данные. Атрибута вида «выровнять по кэш-линии» в .NET нет — только ручная раскладка через `StructLayout`.

**Что спросят дальше:** что такое HITM, почему `Interlocked` на общем счётчике — это true sharing, а не false, как шардировать счётчик при миграции потоков между ядрами.

## Почему CancellationToken может не остановить операцию и как сделать отмену надёжной?

```yaml
category: multithreading
level: senior
difficulty: 4
slug: advanced-concurrency-pochemu-cancellationtoken-mozhet-ne-ostanovit-operaciyu-i-kak-sdelat-o
tags: cancellation, async
```

Потому что отмена в .NET **кооперативная**: `CancellationToken` — лишь флаг и список колбэков, он ничего не прерывает сам. Операция остановится, только если токен дошёл до неё и она его проверяет. Надёжная отмена — это токен, протянутый через **весь** стек вызовов, проверки в долгих циклах, `Register` для API, которые токен не принимают, и таймауты на каждом уровне.

**Почему отмена не срабатывает:**

1. **Токен не передан.** Один вызов в цепочке без `ct` — и всё, что ниже, не отменяется:

```csharp
public async Task ProcessAsync(CancellationToken ct)
{
    var data = await _repo.LoadAsync();        // забыли ct
    await _http.PostAsync(url, content);        // и здесь
}
```

2. **Токен проверяется только на старте.** `Task.Run(work, ct)` лишь не запустит делегат, если отмена уже произошла; начавшийся делегат работает до конца.
3. **CPU-bound цикл без проверок.** Цикл на минуту вычислений не узнает об отмене, пока сам не спросит.
4. **Синхронные блокирующие вызовы.** `Thread.Sleep`, синхронный `Stream.Read`, `Monitor.Enter`, `Task.Wait()` без токена, старые драйверы — не реагируют на токен вовсе.
5. **API игнорирует токен или частично поддерживает.** Некоторые библиотеки принимают токен, но проверяют его только до начала I/O; отмена SQL-запроса — best-effort запрос на сервер, который может прийти, когда запрос уже выполнился.
6. **Проглоченное исключение.** `catch (Exception) { log; continue; }` ловит `OperationCanceledException`, и цикл продолжается.
7. **`WaitAsync(ct)` отменяет ожидание, а не операцию.** Метод вернёт управление, но исходная задача продолжит работать в фоне.
8. **Не тот токен.** Отменяется `CancellationTokenSource`, а в операцию передан другой — например, `CancellationToken.None` по умолчанию или токен из другого scope.

**Как сделать отмену надёжной:**

- **передавать токен везде**, последним параметром; включить анализатор CA2016 (предупреждает о непереданном токене);
- **проверять в долгих циклах**: `ct.ThrowIfCancellationRequested()` раз в итерацию или раз в N итераций;
- **API без токена** — прервать через ресурс:

```csharp
using var reg = ct.Register(static s => ((Socket)s!).Dispose(), socket);
int n = socket.Receive(buffer);   // Dispose сокета прервёт блокирующий вызов исключением
```

- **таймауты через связанные токены** — отмена может прийти и сверху, и по собственному таймауту операции:

```csharp
using var cts = CancellationTokenSource.CreateLinkedTokenSource(ct);
cts.CancelAfter(TimeSpan.FromSeconds(10));
try
{
    await _client.CallAsync(cts.Token);
}
catch (OperationCanceledException) when (!ct.IsCancellationRequested)
{
    throw new TimeoutException("Partner API did not respond in 10s");   // отличаем таймаут от отмены вызывающим
}
```

- **не глотать OCE**: `catch (OperationCanceledException) when (ct.IsCancellationRequested) { throw; }` перед общим `catch`, или фильтр `catch (Exception ex) when (ex is not OperationCanceledException)`;
- **изолировать неотменяемое**: если операцию нельзя прервать (сторонний синхронный код), вынесите её в отдельный процесс или хотя бы на отдельный поток, чтобы можно было перестать ждать и освободить ресурсы.

**Отмена ≠ откат.** Отмена может прийти после того, как побочный эффект уже произошёл (запрос ушёл, запись в БД сделана). Операции должны быть идемпотентны или иметь компенсацию. И наоборот: код очистки (commit/rollback, освобождение блокировки, запись статуса «прервано») не должен получать отменяемый токен — ему нужен `CancellationToken.None` или отдельный короткий таймаут.

**Колбэки `Register`** выполняются синхронно в потоке, вызвавшем `Cancel()`, — они должны быть короткими и не бросать исключений, иначе `Cancel` соберёт их в `AggregateException`.

**Что спросят дальше:** как отличить таймаут от отмены клиентом, почему `CancellationTokenSource` с `CancelAfter` нужно освобождать, что происходит с `HttpContext.RequestAborted` при обрыве соединения.

## Как правильно завершить долгий background-обработчик при остановке приложения?

```yaml
category: multithreading
level: senior
difficulty: 4
slug: advanced-concurrency-kak-pravilno-zavershit-dolgii-background-obrabotchik-pri-ostanovke-pri
tags: hosting, cancellation
```

Правильное завершение — это реакция на `stoppingToken`: перестать брать новую работу, **довести или корректно прервать текущую** за отведённое время, сохранить состояние и выйти из `ExecuteAsync`. Хост ждёт это не дольше `HostOptions.ShutdownTimeout` (по умолчанию 30 секунд с .NET 6), после чего продолжает остановку, и незавершённая работа просто обрывается вместе с процессом.

**Как устроена остановка:**

1. Хост получает сигнал (SIGTERM от Kubernetes/Docker, Ctrl+C, `IHostApplicationLifetime.StopApplication()`).
2. Срабатывает `ApplicationStopping`; для каждого hosted-сервиса вызывается `StopAsync` (по умолчанию последовательно, в обратном порядке регистрации).
3. `BackgroundService.StopAsync` отменяет `stoppingToken` и ждёт завершения задачи `ExecuteAsync` — или истечения токена самого `StopAsync`, который отменяется по `ShutdownTimeout`.
4. По таймауту хост перестаёт ждать и завершает процесс.

**Каркас обработчика:**

```csharp
public sealed class OrderWorker(Channel<Order> queue, ILogger<OrderWorker> log) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        try
        {
            await foreach (var order in queue.Reader.ReadAllAsync(stoppingToken))
            {
                try
                {
                    await ProcessAsync(order, stoppingToken);
                }
                catch (OperationCanceledException) when (stoppingToken.IsCancellationRequested)
                {
                    await ReturnToQueueAsync(order);   // не потерять начатый элемент
                    throw;
                }
                catch (Exception ex)
                {
                    log.LogError(ex, "Order {Id} failed", order.Id);   // один элемент не валит воркер
                }
            }
        }
        catch (OperationCanceledException) when (stoppingToken.IsCancellationRequested)
        {
            log.LogInformation("Worker stopping");
        }
    }
}
```

**Решения, которые нужно принять осознанно:**

- **дочитывать или бросать очередь.** In-memory `Channel` при остановке теряет всё, что не обработано. Либо дочитывать (закрыть writer, обработать остаток с собственным таймаутом меньше `ShutdownTimeout`), либо не держать в памяти то, что нельзя терять, — работать с брокером и подтверждать сообщение только после обработки;
- **прерывать текущую операцию или дать ей закончиться.** Передавать `stoppingToken` во всё подряд — значит прерывать транзакции на середине. Часто лучше: новые элементы не брать сразу, а текущему дать завершиться со своим таймаутом (связанный токен с `CancelAfter`);
- **идемпотентность.** Процесс может быть убит в любой момент (OOM, `SIGKILL` после grace period), поэтому повторная обработка элемента после рестарта должна быть безопасной.

**Настройки таймаутов должны быть согласованы:**

```csharp
builder.Services.Configure<HostOptions>(o => o.ShutdownTimeout = TimeSpan.FromSeconds(25));
```

В Kubernetes `terminationGracePeriodSeconds` по умолчанию 30 с, и он включает `preStop`-хук. `ShutdownTimeout` должен быть меньше grace period, иначе под убьют `SIGKILL` раньше, чем хост закончит. Для ASP.NET Core добавьте время на то, чтобы балансировщик перестал слать трафик (обычно `preStop` со sleep на несколько секунд).

**Подводные камни:**

- **синхронный код в начале `ExecuteAsync`** до первого `await` исторически выполнялся внутри `StartAsync` и блокировал старт хоста; в .NET 10 `BackgroundService` запускает весь `ExecuteAsync` в фоне, но в более ранних версиях начинайте с `await Task.Yield()` или асинхронной операции;
- **необработанное исключение** в `ExecuteAsync` с .NET 6 по умолчанию останавливает весь хост (`BackgroundServiceExceptionBehavior.StopHost`); это правильно, но воркер должен ловить ошибки отдельных элементов сам;
- **`StopAsync` не вызовется** при аварийном завершении — надеяться на него для сохранения критичных данных нельзя;
- **несколько сервисов** останавливаются последовательно и делят общий таймаут; с .NET 8 есть `HostOptions.ServicesStopConcurrently`, а `IHostedLifecycleService` даёт хуки `StoppingAsync`/`StoppedAsync`;
- **scoped-зависимости** (DbContext) создавайте через `IServiceScopeFactory` на каждую единицу работы, а не один раз на всё время жизни воркера.

**Что спросят дальше:** что будет с элементами в канале при рестарте, как сделать graceful shutdown в Kubernetes, чем `IHostedService` отличается от `BackgroundService`.

## Как реализовать периодическую задачу, устойчивую к перекрытию запусков и падениям?

```yaml
category: multithreading
level: senior
difficulty: 4
slug: advanced-concurrency-kak-realizovat-periodicheskuyu-zadachu-ustoichivuyu-k-perekrytiyu-zapu
tags: hosting, resilience
```

В пределах одного процесса — цикл на `PeriodicTimer` в `BackgroundService`: следующий запуск физически не начнётся, пока не закончился предыдущий, а `try/catch` вокруг одной итерации не даёт одному падению убить расписание. Если сервис запущен в нескольких экземплярах, этого мало — нужна **распределённая** защита от перекрытия (lease/блокировка в БД или Redis, либо планировщик вроде Quartz.NET в кластерном режиме), плюс идемпотентность задачи.

**Базовая реализация:**

```csharp
public sealed class CleanupJob(IServiceScopeFactory scopes, ILogger<CleanupJob> log, TimeProvider time)
    : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        using var timer = new PeriodicTimer(TimeSpan.FromMinutes(5), time);
        do
        {
            using var runCts = CancellationTokenSource.CreateLinkedTokenSource(stoppingToken);
            runCts.CancelAfter(TimeSpan.FromMinutes(4));        // запуск не длиннее периода
            try
            {
                await using var scope = scopes.CreateAsyncScope();
                await scope.ServiceProvider.GetRequiredService<Cleaner>().RunAsync(runCts.Token);
            }
            catch (OperationCanceledException) when (stoppingToken.IsCancellationRequested)
            {
                break;
            }
            catch (Exception ex)
            {
                log.LogError(ex, "Cleanup failed");             // упала итерация, а не расписание
            }
        }
        while (await timer.WaitForNextTickAsync(stoppingToken));
    }
}
```

**Почему `PeriodicTimer`, а не `System.Threading.Timer`:**

| | `System.Threading.Timer` | `PeriodicTimer` (.NET 6+) |
| --- | --- | --- |
| перекрытие | колбэк вызывается по расписанию, даже если предыдущий ещё работает | тики ждут в цикле — перекрытие невозможно |
| async | колбэк синхронный, `async` лямбда превращается в `async void` | `await` естественно |
| исключения | необработанное исключение в колбэке роняет процесс | обычный `try/catch` в цикле |
| пропущенные тики | накапливаются как параллельные вызовы | если работа длиннее периода, следующий `WaitForNextTickAsync` завершится сразу — один раз, тики не копятся |
| тестируемость | — | конструктор с `TimeProvider` (.NET 8+) и `FakeTimeProvider` в тестах |

**Устойчивость к падениям:**

- **итерация** — `try/catch` внутри цикла; иначе исключение завершит `ExecuteAsync`, а с .NET 6 по умолчанию — и весь хост;
- **таймаут запуска** — связанный токен с `CancelAfter`, чтобы зависшая итерация не отменила все последующие;
- **процесс** — после рестарта расписание начинается заново. Если важно не пропускать запуски, храните время последнего **успешного** выполнения в БД и при старте решайте, нужно ли догнать пропущенное;
- **повторные ошибки** — метрика «время последнего успешного запуска» и алерт, если оно старше N периодов; иначе задача может молча падать неделями;
- **перезапуски после ошибки** — при частых сбоях полезен backoff, чтобы не долбить упавшую зависимость каждые 5 минут всеми репликами одновременно.

**Несколько экземпляров сервиса:**

```sql
-- lease в БД: запуск берёт тот, кто успел продлить аренду
UPDATE job_leases
SET owner = @instance, expires_at = now() + interval '10 minutes'
WHERE job = 'cleanup' AND (expires_at < now() OR owner = @instance);
-- затронута 1 строка — мы владелец, выполняем; 0 — пропускаем тик
```

- срок аренды больше максимальной длительности запуска, иначе при долгой итерации её перехватит другой экземпляр;
- альтернативы: `pg_try_advisory_lock` в PostgreSQL, Redis `SET key value NX PX`, Quartz.NET с clustered job store (`[DisallowConcurrentExecution]`), Hangfire с recurring jobs, Kubernetes `CronJob` с `concurrencyPolicy: Forbid`;
- **идемпотентность** всё равно обязательна: аренда может истечь посреди работы (GC-пауза, сетевой сбой), и два экземпляра на короткое время будут работать одновременно.

**Jitter.** Если десяток сервисов запускает задачу ровно в :00, они синхронно нагружают БД. Небольшая случайная задержка перед первым тиком размазывает нагрузку.

**Что спросят дальше:** что делать, если запуск дольше периода; как тестировать расписание с `FakeTimeProvider`; когда лучше вынести задачу в отдельный `CronJob`, чем держать внутри веб-приложения.
