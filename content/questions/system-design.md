## Что такое System Design?

```yaml
category: system-design
level: middle
difficulty: 2
slug: system-design-chto-takoe-system-design
```

System Design — это проектирование архитектуры системы: из каких компонентов она состоит, как они общаются, где и как хранятся данные и как всё это ведёт себя под нагрузкой и при отказах. Результат — не код, а набор решений с обоснованием: почему PostgreSQL, а не Cassandra, зачем здесь очередь, что будет при падении узла.

**Что входит в предмет:**

- **Компоненты и границы** — API, сервисы, базы, кэши, брокеры, CDN, балансировщики.
- **Данные** — модель, выбор хранилища, репликация, шардирование, консистентность.
- **Нефункциональные свойства** — масштабируемость, доступность, latency, стоимость, безопасность.
- **Поведение при сбоях** — что деградирует, что теряется, как система восстанавливается.

**Уровни.** High-level design (HLD) — блоки и потоки данных на уровне «клиент → LB → API → БД/кэш/очередь». Low-level design (LLD) — схема таблиц, контракты API, классы и алгоритмы внутри сервиса. На собеседовании обычно спрашивают HLD с погружением в 1–2 узких места.

**Почему это не про «правильный ответ».** Любое решение — компромисс: strong consistency стоит latency и доступности, кэш даёт скорость ценой устаревших данных, микросервисы дают независимый деплой ценой сетевых сбоев и распределённых транзакций. Интервьюер оценивает, умеете ли вы:

1. уточнить требования вместо того, чтобы сразу рисовать;
2. прикинуть масштаб цифрами (RPS, объём данных);
3. предложить простую рабочую схему и только потом усложнять;
4. назвать узкие места и честно проговорить trade-offs.

**Типичная ошибка** — начинать с Kafka, Kubernetes и шардирования для системы на 50 RPS. Хороший дизайн — самый простой, который выдерживает заявленные требования с запасом.

## Как начать проектирование системы?

```yaml
category: system-design
level: middle
difficulty: 4
slug: system-design-kak-nachat-proektirovanie-sistemy
```

Начинать нужно не с диаграммы, а с вопросов: что система делает, для кого и в каком масштабе. Дальше — оценка нагрузки цифрами, простая схема, и только потом углубление в узкие места. Типичный порядок на 45-минутном интервью укладывается в пять шагов.

**1. Требования (5–7 минут).**

- Функциональные: 3–5 ключевых сценариев. Для URL shortener — «создать короткую ссылку», «редирект», «статистика кликов». Всё остальное явно выносим за скоуп.
- Нефункциональные: сколько пользователей, соотношение чтения и записи, допустимая latency (p99), доступность (99.9% или 99.99%), нужна ли строгая консистентность, геораспределение.

**2. Оценка масштаба (3–5 минут).** Прикидываем порядки:

```text
100M DAU × 10 запросов/день = 1B запросов/день
1B / 86 400 с ≈ 11 600 RPS в среднем, пик ×2–3 ≈ 30 000 RPS
запись 1% → ~120 RPS, 500 байт на запись → 60 KB/s ≈ 5 GB/день ≈ 1.8 TB/год
```

Цифры определяют архитектуру: 30k RPS чтения — нужен кэш; 1.8 TB/год — одна PostgreSQL ещё справится, но через 3–5 лет нужен план партиционирования.

**3. API и модель данных.** Несколько эндпоинтов с входом и выходом, основные сущности и ключи доступа. Именно паттерн доступа (по какому ключу читаем, какие запросы горячие) выбирает хранилище.

**4. High-level схема.** Клиент → CDN/LB → stateless API → кэш → БД, плюс асинхронная часть через очередь, если есть тяжёлая или отложенная работа. Сначала рисуем минимальную рабочую версию и проходим по ней один запрос end-to-end.

**5. Углубление и масштабирование.** Находим, что сломается первым при росте в 10 раз: БД на запись, горячий ключ в кэше, fan-out, внешний провайдер. Для каждого узкого места — решение и его цена: реплики чтения (лаг репликации), шардирование (кросс-шардовые запросы), очередь (eventual consistency).

**Чего избегать:**

- молча рисовать, не проговаривая допущения;
- переусложнять с первой минуты;
- называть технологии без причины («возьмём MongoDB, потому что быстро»);
- забывать про отказы: что будет, если упадёт БД, брокер, внешний API.

Хороший сигнал для интервьюера — фраза вида «я выбираю X, потому что у нас read-heavy нагрузка 100:1; цена — eventual consistency на 1–2 секунды, для ленты это приемлемо».

## Какие требования нужно собрать перед проектированием?

```yaml
category: system-design
level: middle
difficulty: 4
slug: system-design-kakie-trebovaniya-nuzhno-sobrat-pered-proektirovaniem
```

Нужны две группы требований: что система делает (функциональные) и с какими характеристиками (нефункциональные), плюс ограничения среды. Без них невозможно выбрать ни хранилище, ни степень избыточности — любое решение будет угадыванием.

**Функциональные — сценарии и границы:**

- ключевые use case: кто пользователь, какие действия, что он видит в ответ;
- что явно не делаем в этой версии (out of scope);
- синхронные и асинхронные операции: что должно быть сделано «сейчас», а что можно доделать в фоне;
- интеграции: платёжный провайдер, SMS-шлюз, внешние API.

**Нефункциональные — цифры, а не прилагательные:**

| Требование | Вопрос | Пример ответа |
| --- | --- | --- |
| Масштаб | DAU, запросы на пользователя, рост | 5M DAU, ×2 в год |
| Профиль нагрузки | read/write ratio, пики | 50:1, пик ×5 в распродажу |
| Latency | p50/p99 на ключевых операциях | p99 < 200 ms на чтение |
| Доступность | SLA | 99.95% (~22 минуты простоя в месяц) |
| Консистентность | можно ли показать устаревшие данные | лента — да, баланс — нет |
| Durability | допустима ли потеря данных | заказы — нет, метрики — да |
| Хранение | объём, срок, архив | 3 года, потом холодное хранилище |
| Безопасность | ПДн, PCI DSS, аудит | карты не храним, токенизация |

**Ограничения:**

- команда и её стек (.NET + PostgreSQL — не повод брать Cassandra без причины);
- инфраструктура: облако, on-prem, Kubernetes;
- бюджет и сроки;
- регуляторика: локализация данных (152-ФЗ, GDPR), требования аудита.

**Как спрашивать на интервью.** Коротко и с предложением по умолчанию: «Предполагаю 10M DAU, чтение преобладает, для ленты допустима задержка в пару секунд — ок?». Интервьюер либо согласится, либо даст другое ограничение, и оба варианта полезны.

**Почему это важно.** Одна и та же задача «сервис заказов» при 100 заказах в день — это монолит на одной PostgreSQL, а при 10 000 заказах в секунду в пике — шардирование, очереди и отдельный сервис резервирования остатков. Разницу определяют только требования.

## Functional vs non-functional requirements?

```yaml
category: system-design
level: middle
difficulty: 3
slug: system-design-functional-vs-non-functional-requirements
```

Functional requirements описывают, **что** система делает: операции, бизнес-правила, данные на входе и выходе. Non-functional — **как хорошо** она это делает: скорость, доступность, масштаб, надёжность, безопасность. Первые определяют API и модель данных, вторые — архитектуру.

**Functional — примеры для сервиса заказов:**

- пользователь создаёт заказ из корзины;
- заказ проходит статусы `Created → Paid → Shipped → Delivered`;
- пользователь видит историю заказов;
- при отмене деньги возвращаются.

Проверяются тестами на поведение: «после оплаты статус — Paid».

**Non-functional — те же заказы:**

- p99 создания заказа < 300 ms;
- доступность 99.95%;
- 2 000 заказов/с в пике распродажи;
- ни один оплаченный заказ не теряется (RPO = 0 для заказов);
- данные хранятся 5 лет.

Проверяются нагрузочными тестами, мониторингом SLO, chaos-тестами.

**Почему NFR важнее для архитектуры.** Функционально «создать заказ» одинаково при 10 и при 10 000 заказах в секунду. Но во втором случае появляются очереди, шардирование, идемпотентность, резервирование остатков через отдельный сервис. Архитектурные решения почти всегда продиктованы NFR.

**NFR конфликтуют друг с другом:**

| Конфликт | Пример |
| --- | --- |
| Consistency vs availability | при сетевом разделе либо отказываем, либо показываем устаревший баланс |
| Latency vs durability | синхронная репликация в другой регион добавляет десятки мс |
| Стоимость vs доступность | 99.99% требует multi-AZ и резервов, это ×2–3 к инфраструктуре |

Поэтому NFR нужно формулировать измеримо: не «быстро», а «p99 < 200 ms при 5 000 RPS»; не «надёжно», а «SLA 99.9%, RPO 1 минута, RTO 15 минут». Неизмеримое требование нельзя ни спроектировать, ни проверить.

## Как оценить нагрузку системы?

```yaml
category: system-design
level: middle
difficulty: 4
slug: system-design-kak-ocenit-nagruzku-sistemy
tags: scalability
```

Нагрузку оценивают «от пользователя»: DAU × действия на пользователя в день → запросы в день → средний RPS → пиковый RPS, отдельно для чтения и записи. Точность нужна на уровне порядка — цель понять, хватит ли одного сервера или нужно шардирование.

**Базовая формула:**

```text
RPS_avg  = DAU × запросов_на_пользователя / 86 400
RPS_peak = RPS_avg × пиковый коэффициент (обычно 2–5, для распродаж 10+)
```

Полезное округление: в сутках 86 400 с ≈ 10^5 с. Значит 1M запросов в день ≈ 12 RPS, 100M в день ≈ 1 200 RPS.

**Пример: соцсеть с лентой.**

```text
DAU                      = 20M
открытий ленты / день    = 20   → 400M чтений/день
публикаций / день        = 0.5  → 10M записей/день

чтение: 400M / 86 400 ≈ 4 600 RPS, пик ×3 ≈ 14 000 RPS
запись: 10M / 86 400  ≈ 115 RPS,   пик ×3 ≈ 350 RPS
read/write ≈ 40:1
```

**Что учитывать помимо среднего:**

1. **Суточный профиль.** Трафик неравномерен: вечерний пик в 2–3 раза выше среднего, ночью — в разы ниже. Если пользователи в одном часовом поясе, пик острее.
2. **Всплески.** Распродажи, push-рассылки, матчи: за минуту нагрузка может вырасти в 10 раз.
3. **Амплификация.** Один пользовательский запрос порождает несколько внутренних: запрос ленты = 1 вызов API + 5 запросов в кэш + 1 в БД. Для БД считать нужно именно внутренние запросы.
4. **Фоновая нагрузка.** Джобы, реиндексация, аналитика, ретраи.

**Сопоставление с мощностью.** Грубые ориентиры одного узла: stateless API на .NET — 5–20k RPS простых запросов на 8 ядер; PostgreSQL — тысячи-десятки тысяч простых запросов по индексу в секунду, но сотни-тысячи транзакций на запись с fsync; Redis — ~100k операций/с на ядро. Разделив пиковую нагрузку на мощность узла и добавив запас 30–50%, получаем количество инстансов.

**Проверка.** Оценку подтверждают нагрузочным тестом (k6, NBomber для .NET) и затем метриками из продакшена — реальный профиль почти всегда отличается от предположений.

## Что такое RPS/QPS?

```yaml
category: system-design
level: middle
difficulty: 2
slug: system-design-chto-takoe-rps-qps
tags: scalability
```

RPS (requests per second) — число запросов, которые система обрабатывает за секунду; QPS (queries per second) — то же самое, но обычно о запросах к базе или поисковому движку. Это основная метрика пропускной способности, от которой считают количество серверов, соединений и размер кэша.

**Как считать:**

```text
10M запросов в день / 86 400 с ≈ 116 RPS в среднем
```

Среднее почти бесполезно само по себе — проектируют под пик. Пиковый коэффициент 2–3 для обычного продукта, 10+ для распродаж и событий.

**RPS и latency связаны через закон Литтла:**

```text
одновременных запросов = RPS × среднее время ответа
2 000 RPS × 0.05 с = 100 запросов в полёте
```

Отсюда размер пулов: если каждый запрос держит соединение с БД 20 ms, то при 2 000 RPS нужно ~40 соединений, а не 1 000.

**Важные нюансы:**

- **RPS ≠ пользователи.** Одна загрузка страницы — это 1 HTML + десятки запросов к API и статике. Считать нужно на том уровне, который проектируется.
- **Внешний и внутренний RPS различаются.** 1 000 RPS на API могут дать 5 000 QPS в Redis и 500 QPS в PostgreSQL.
- **Разные запросы — разная цена.** 10k RPS на чтение по ключу из кэша и 10k RPS на запись с транзакцией — несравнимые нагрузки. Поэтому RPS указывают отдельно для чтения и записи.
- **Throughput без latency не имеет смысла.** «Сервис держит 50k RPS» при p99 = 3 с — это не рабочая мощность. Корректная формулировка: «20k RPS при p99 < 100 ms».

Родственные метрики: TPS (транзакции в секунду) для БД и платёжных систем, events/s или messages/s для брокеров.

## Как оценить количество пользователей?

```yaml
category: system-design
level: middle
difficulty: 4
slug: system-design-kak-ocenit-kolichestvo-polzovatelei
```

Количество пользователей оценивают от известного рынка или бизнес-цели к MAU, затем к DAU и к пиковому числу одновременных пользователей. Для архитектуры важен не «общий размер базы», а DAU и concurrency — именно они дают нагрузку.

**Воронка метрик:**

```text
Зарегистрированные → MAU → DAU → пиковый concurrency
```

- **Registered** — определяет объём хранения профилей, почти не влияет на нагрузку.
- **MAU** — активные за месяц.
- **DAU** — активные за день. Типичное отношение DAU/MAU («stickiness»): 10–20% для e-commerce, 50%+ для мессенджеров и соцсетей.
- **Concurrent users** — одновременно онлайн в пиковый момент. Важен для WebSocket-соединений, сессий, чатов.

**Оценка «сверху вниз» — от рынка:**

```text
Интернет-магазин в стране с 40M интернет-пользователей
Доля рынка 5%                 → 2M MAU
DAU/MAU 15%                   → 300k DAU
Средняя сессия 10 минут, 70% трафика в 8 вечерних часов
```

**Concurrency из DAU:**

```text
Средний онлайн  = DAU × длительность_сессий_в_день / 86 400
300k × 600 с / 86 400 ≈ 2 100 одновременно в среднем
В пиковые часы плотность ×2–3        → ~5 000–6 000 одновременно
```

**Оценка «снизу вверх» — от бизнес-цели:** «хотим 10 000 заказов в день при конверсии 2%» → 500k сессий в день → при 1.5 сессии на пользователя ~330k DAU.

**Что проверить на интервью:**

1. Географию: один часовой пояс даёт острый пик, глобальная аудитория — сглаженный профиль, но нужна multi-region.
2. Рост: заложить горизонт 1–2 года, а не текущее значение.
3. Разные типы пользователей: покупатели, продавцы, курьеры, внутренние сотрудники дают разный профиль.
4. Ботов и интеграции: партнёрские API и краулеры могут давать больше трафика, чем люди.

Результат оценки — не одно число, а DAU, пиковый concurrency и запросов на пользователя; из них уже считают RPS, storage и bandwidth.

## Как оценить storage requirements?

```yaml
category: system-design
level: middle
difficulty: 4
slug: system-design-kak-ocenit-storage-requirements
```

Объём хранения считают как «количество новых записей в день × размер записи × срок хранения», затем умножают на коэффициент репликации и накладные расходы на индексы. Отдельно считают метаданные (строки в БД) и бинарные данные (файлы в S3) — они живут в разных хранилищах и растут с разной скоростью.

**Базовая формула:**

```text
Storage = записей_в_день × размер × 365 × лет × репликация × overhead
```

- **overhead** на индексы, служебные поля, bloat в PostgreSQL — обычно ×1.5–2 к «сырым» данным;
- **репликация** — ×2–3 (primary + реплики, или RF=3 в Kafka/Cassandra/S3).

**Пример: мессенджер.**

```text
50M DAU × 40 сообщений = 2B сообщений/день
Сообщение: id 8 + chat_id 8 + sender 8 + ts 8 + текст ~100 + служебное ~50 ≈ 200 байт
2B × 200 B = 400 GB/день
× 365 = 146 TB/год
× 1.5 индексы ≈ 220 TB/год
× 3 реплики ≈ 660 TB/год
```

Вывод: это не одна PostgreSQL — нужен шардированный или wide-column store (Cassandra/ScyllaDB), партиционирование по `chat_id` и политика TTL/архива.

**Медиа считаются отдельно:**

```text
5% сообщений с фото по 200 KB: 100M × 200 KB = 20 TB/день ≈ 7.3 PB/год
```

Медиа на порядки тяжелее текста, поэтому они всегда уходят в объектное хранилище, а в БД лежит только ключ объекта.

**Что ещё учесть:**

1. **Рост** — не текущая скорость, а прогноз на 2–3 года.
2. **Retention** — сколько хранить горячо, когда переносить в холодный tier (S3 Glacier-класс дешевле в разы) или удалять.
3. **Логи, метрики, бэкапы** — бэкапы с PITR легко удваивают объём; логи на 1 000 RPS по 1 KB — это ~86 GB/день.
4. **Kafka** — `входной_поток × retention × RF`: 50 MB/s × 7 дней × 3 ≈ 90 TB.

**Ориентиры по хранилищам:** одна PostgreSQL комфортна до единиц терабайт (дальше — боль с VACUUM, бэкапами и восстановлением); десятки TB — шардирование или распределённые СУБД; петабайты — только объектное хранилище.

## Как оценить network bandwidth?

```yaml

level: middle
difficulty: 4

tags: scalability
```

Bandwidth считают как «RPS × средний размер ответа» отдельно для входящего (ingress) и исходящего (egress) трафика, для среднего и пикового значения. Результат переводят в биты в секунду, потому что пропускная способность сетей и тарифы указываются в Gbps.

**Формула и единицы:**

```text
Bandwidth = RPS × размер_payload
1 байт = 8 бит; 1 GB/s = 8 Gbps
```

Путаница байтов и битов — самая частая ошибка в оценках: разница в 8 раз.

**Пример: видеохостинг.**

```text
Загрузка:  100k видео/день × 100 MB = 10 TB/день
           10 TB / 86 400 с ≈ 116 MB/s ≈ 0.93 Gbps ingress

Просмотры: 10M просмотров/день × 5 минут × 5 Mbps
           Средний concurrency = 10M × 300 с / 86 400 ≈ 34 700 зрителей
           34 700 × 5 Mbps ≈ 174 Gbps egress в среднем, пик ×3 ≈ 520 Gbps
```

Вывод: egress в сотни Gbps невозможно отдавать из своих серверов — нужен CDN, а origin отдаёт только промахи кэша (при hit ratio 95% это ~26 Gbps в пике).

**Пример: обычный API.**

```text
5 000 RPS × 5 KB ответа = 25 MB/s = 200 Mbps
```

Для API bandwidth редко становится узким местом — сначала упрётесь в CPU или БД. Сеть важна для медиа, файлов, стриминга, репликации и бэкапов.

**Что ещё учесть:**

1. **Внутренний трафик.** Репликация БД, Kafka с RF=3 (каждый байт записи уходит ещё на 2 брокера), fan-out между микросервисами. Внутри дата-центра он может превышать внешний.
2. **Межзональный и межрегиональный трафик** в облаке платный — репликация между регионами на 100 MB/s даёт ~260 TB в месяц.
3. **Сжатие.** gzip/brotli уменьшают JSON в 5–10 раз, но не помогают медиа, которое уже сжато.
4. **Заголовки и TLS.** Для мелких запросов накладные расходы HTTP сравнимы с полезной нагрузкой.
5. **Пропускная способность NIC.** Сервер с 10 Gbps интерфейсом реально отдаёт ~8–9 Gbps; это ограничение на один узел.

Итог оценки — пиковый ingress и egress в Gbps, из которых следуют решения: CDN, прямая загрузка в S3 по presigned URL, сжатие, размещение реплик.

## Что такое bottleneck?

```yaml
category: system-design
level: middle
difficulty: 2
slug: system-design-chto-takoe-bottleneck
tags: scalability
```

Bottleneck (узкое место) — компонент, который первым достигает предела и ограничивает пропускную способность или latency всей системы. Сколько бы вы ни масштабировали остальное, система не станет быстрее, пока не расширено именно это место.

**Как выглядит:** API масштабировали с 4 до 20 подов, а RPS вырос на 10%, зато выросло время ответа — потому что все поды упираются в одну PostgreSQL на запись или в пул из 100 соединений.

**Типичные узкие места:**

| Ресурс | Симптом |
| --- | --- |
| CPU | загрузка > 80%, растёт latency, очередь в thread pool |
| Память | GC-паузы, swap, OOM kill |
| Диск I/O | высокий iowait, медленные fsync, рост времени commit |
| Сеть | насыщение NIC, потери пакетов |
| БД | блокировки, долгие запросы, исчерпан connection pool |
| Горячий ключ/партиция | один шард Redis или Kafka-партиция загружены при простое остальных |
| Внешний сервис | лимиты API, медленный платёжный провайдер |
| Синхронизация | lock contention, один глобальный мьютекс, последовательная обработка |

**Свойства, которые важно понимать:**

1. **Узкое место всегда есть.** Устранив одно, вы находите следующее — это нормально.
2. **Оно проявляется нелинейно.** До 70–80% загрузки ресурса latency почти не растёт, дальше очередь растёт лавинообразно (теория очередей: при утилизации ρ среднее время ожидания пропорционально ρ/(1−ρ)).
3. **Оно может сместиться.** Добавили кэш — БД разгрузилась, но теперь упираемся в сеть или в CPU на сериализации.

**Как проектировать с учётом bottleneck:** заранее прикинуть, какой компонент первым не выдержит роста в 10 раз, и сделать его масштабируемым или изолированным — stateless-сервисы, реплики чтения, шардирование, асинхронная обработка через очередь, кэширование горячих данных.

## Как спроектировать REST API?

```yaml
category: system-design
level: middle
difficulty: 4
slug: system-design-kak-sproektirovat-rest-api
tags: api-design, architecture
```

REST API проектируют от ресурсов и сценариев клиента: существительные в URL, семантика через HTTP-методы и коды ответа, предсказуемые форматы ошибок, пагинация, версионирование и идемпотентность для небезопасных операций. Хороший API легко использовать правильно и трудно — неправильно.

**1. Ресурсы и URL.**

```text
GET    /api/v1/orders?status=paid&cursor=abc&limit=50   список
GET    /api/v1/orders/{id}                              один заказ
POST   /api/v1/orders                                   создать
PATCH  /api/v1/orders/{id}                              частичное изменение
DELETE /api/v1/orders/{id}                              удалить/отменить
POST   /api/v1/orders/{id}/cancel                       действие, не укладывающееся в CRUD
GET    /api/v1/customers/{id}/orders                    вложенный ресурс
```

Существительные во множественном числе, без глаголов (`/getOrders` — плохо), вложенность не глубже 2 уровней.

**2. Методы и их свойства.**

| Метод | Safe | Idempotent | Назначение |
| --- | --- | --- | --- |
| GET | да | да | чтение |
| PUT | нет | да | полная замена |
| PATCH | нет | не гарантирован | частичное изменение |
| POST | нет | нет | создание, действия |
| DELETE | нет | да | удаление |

Для POST идемпотентность обеспечивают заголовком `Idempotency-Key`: сервер хранит ключ и результат первого выполнения и на повтор возвращает тот же ответ.

**3. Коды ответа.** `200/201/204` — успех (201 с `Location`), `400` — невалидный запрос, `401/403` — аутентификация/авторизация, `404`, `409` — конфликт состояния или версии, `422` — бизнес-валидация, `429` — rate limit с `Retry-After`, `5xx` — ошибка сервера. Ошибки — в едином формате RFC 7807 (`ProblemDetails` в ASP.NET Core): `type`, `title`, `status`, `detail`, `traceId`.

**4. Пагинация.** Offset (`?page=100`) на больших таблицах медленный — `OFFSET 100000` заставляет БД прочитать и отбросить строки — и нестабилен при вставках. Для лент и больших списков — cursor/keyset: `WHERE (created_at, id) < (@ts, @id) ORDER BY created_at DESC, id DESC LIMIT 50`, курсор отдаётся клиенту непрозрачной строкой.

**5. Конкурентные изменения.** Optimistic concurrency через `ETag` + `If-Match`: при несовпадении версии — `412 Precondition Failed`. В PostgreSQL версией может служить `xmin` или отдельная колонка `version`.

**6. Версионирование.** В URL (`/v1/`) — просто и явно; в заголовке — чище, но сложнее кэшировать и отлаживать. Правило: аддитивные изменения (новое необязательное поле) не ломают клиентов; удаление или переименование — только в новой версии с периодом deprecation.

**7. Нефункциональное:**

- rate limiting по клиенту/ключу, ответ 429;
- `Cache-Control` и `ETag` для кэшируемых GET;
- аутентификация через OAuth2/JWT, авторизация на уровне ресурса (не только роли — проверка владельца);
- ограничение размера запроса и `limit` на списки;
- контракт в OpenAPI, генерация клиентов.

**Когда REST — не лучший выбор:** внутренние высоконагруженные вызовы между сервисами (gRPC — бинарный протокол, HTTP/2, строгий контракт), сложные агрегирующие экраны (GraphQL или BFF), real-time (WebSocket/SSE).

## Как выбрать database?

```yaml
category: system-design
level: middle
difficulty: 4
slug: system-design-kak-vybrat-database
tags: architecture
```

Базу выбирают по паттерну доступа к данным и требованиям к консистентности, а не по популярности. По умолчанию для транзакционных данных — PostgreSQL; другое хранилище оправдано, когда есть конкретная причина: масштаб записи, специфичный тип запросов или модель данных.

**Вопросы, которые определяют выбор:**

1. **Модель данных.** Связанные сущности с инвариантами (заказ, позиции, оплата) — реляционная. Документы с переменной структурой — документная или JSONB. Граф связей с обходом на много шагов — графовая.
2. **Паттерн запросов.** Доступ по ключу, диапазонные сканы по времени, произвольные фильтры и JOIN, полнотекстовый поиск, агрегации по миллиардам строк.
3. **Нагрузка.** Соотношение чтения и записи, пиковый RPS записи, объём данных и скорость роста.
4. **Консистентность.** Нужны ли ACID-транзакции через несколько сущностей, допустима ли eventual consistency.
5. **Операционные требования.** Кто будет поддерживать, есть ли managed-вариант, бэкапы, экспертиза в команде.

**Ориентиры:**

| Задача | Выбор | Почему |
| --- | --- | --- |
| Заказы, платежи, пользователи | PostgreSQL | ACID, ограничения целостности, богатый SQL |
| Кэш, сессии, счётчики, rate limit | Redis | in-memory, sub-ms latency, атомарные операции |
| Высокая запись по ключу, TB+ данных (сообщения, события) | Cassandra / ScyllaDB | линейное масштабирование записи, партиционирование по ключу |
| Полнотекстовый поиск, фасеты | Elasticsearch / OpenSearch | инвертированный индекс, релевантность |
| Аналитика по миллиардам строк | ClickHouse | колоночное хранение, сжатие, быстрые агрегации |
| Метрики и временные ряды | Prometheus, TimescaleDB, ClickHouse | компрессия по времени, downsampling |
| Файлы, медиа, бэкапы | S3-совместимое хранилище | дёшево, практически бесконечно, durability 11 девяток |
| Журнал событий | Kafka | упорядоченный лог с retention и повторным чтением |

**Почему PostgreSQL как дефолт.** Он закрывает большинство задач среднего масштаба: транзакции, JSONB для полуструктурированных данных, полнотекстовый поиск на базовом уровне, партиционирование, расширения (PostGIS, pgvector). Одна хорошо настроенная инстанция с репликами выдерживает десятки тысяч чтений в секунду и тысячи записей.

**Polyglot persistence** — нормальная практика: PostgreSQL как источник истины, Elasticsearch для поиска, ClickHouse для аналитики, Redis для кэша. Цена — синхронизация: данные в производные хранилища доставляются через CDC (Debezium) или outbox + Kafka, и они консистентны только в конечном счёте.

**Анти-паттерны:** выбирать NoSQL «на вырост» при 100 RPS; брать MongoDB, чтобы «не думать о схеме» (схема всё равно есть, только в коде); держать всё в одной БД, включая логи и аналитику, которые убивают OLTP-нагрузку.

## SQL vs NoSQL?

```yaml
category: system-design
level: middle
difficulty: 3
slug: system-design-sql-vs-nosql
tags: architecture
```

SQL-базы дают строгую схему, JOIN и ACID-транзакции через несколько таблиц, а масштабируются в основном вертикально и репликами чтения. NoSQL-системы жертвуют частью этих гарантий ради горизонтального масштабирования, гибкой модели или специфичного паттерна доступа. Выбор определяется запросами и требованиями к консистентности.

**Сравнение:**

| | SQL (PostgreSQL, MySQL) | NoSQL |
| --- | --- | --- |
| Модель | таблицы, связи, нормализация | ключ-значение, документы, wide-column, граф |
| Схема | строгая, миграции | гибкая, но фактически живёт в коде |
| Запросы | произвольные, JOIN, агрегаты | по заранее спроектированному ключу доступа |
| Транзакции | ACID через много строк и таблиц | обычно на уровне одной записи/партиции |
| Консистентность | strong по умолчанию | часто настраиваемая или eventual |
| Масштаб записи | один primary, дальше — шардирование вручную или Citus | встроенное шардирование, линейный рост |

**Виды NoSQL — это разные инструменты:**

- **Key-value** (Redis, DynamoDB) — доступ по ключу, минимальная latency.
- **Document** (MongoDB) — вложенные документы, выборка по полям.
- **Wide-column** (Cassandra, ScyllaDB) — огромная запись, данные партиционированы по ключу и отсортированы внутри партиции. Модель строится «от запроса»: под каждый запрос своя таблица.
- **Graph** (Neo4j) — обходы связей на много шагов.

**Когда SQL:**

- важна целостность: деньги, остатки, заказы;
- запросы заранее неизвестны или меняются (отчёты, админка);
- нужны транзакции через несколько сущностей;
- данные помещаются в единицы TB — это подавляющее большинство систем.

**Когда NoSQL:**

- запись в десятки-сотни тысяч операций в секунду, которую один primary не вытянет;
- объём в десятки-сотни TB с простым доступом по ключу (сообщения, события, телеметрия);
- явно нужна multi-region запись с высокой доступностью;
- кэш и эфемерные данные (Redis).

**Граница размыта.** PostgreSQL умеет JSONB с GIN-индексами и частично заменяет документную БД. MongoDB поддерживает многодокументные транзакции. Распределённые SQL (CockroachDB, YugabyteDB, Citus) дают SQL с горизонтальным масштабированием ценой latency на распределённые транзакции.

**Практический ответ:** начинаем с PostgreSQL, пока нет измеримой причины уйти. NoSQL добавляется точечно под конкретную нагрузку, а не заменяет реляционную базу целиком.

## Когда нужен Redis?

```yaml
category: system-design
level: middle
difficulty: 4
slug: system-design-kogda-nuzhen-redis
tags: caching, architecture
```

Redis нужен, когда требуется очень быстрый (sub-ms) доступ к небольшим данным по ключу или атомарные операции над общим состоянием нескольких инстансов приложения: кэш, сессии, счётчики, rate limiting, распределённые блокировки, лидерборды. Источником истины для важных данных он обычно не является.

**Типичные сценарии:**

| Задача | Структура Redis | Пример |
| --- | --- | --- |
| Кэш запросов к БД | String/Hash + TTL | `product:123` → JSON, TTL 5 минут |
| Сессии, токены | String/Hash + TTL | серверная сессия, blacklist отозванных JWT |
| Rate limiting | `INCR` + `EXPIRE` или Lua | 100 запросов в минуту на API-ключ |
| Счётчики | `INCR`, `HINCRBY` | просмотры, лайки с периодическим сбросом в БД |
| Лидерборды | Sorted Set | `ZADD`, `ZREVRANGE` топ-100 за O(log N + M) |
| Уникальные значения | Set, HyperLogLog | уникальные посетители: HLL ~12 KB на ключ с ошибкой ~0.8% |
| Распределённая блокировка | `SET key val NX PX 30000` | одна джоба на кластер |
| Очереди, pub/sub | List, Streams, Pub/Sub | лёгкая очередь задач, real-time уведомления |
| Гео-поиск | GEO | ближайшие курьеры в радиусе |

**Почему он быстрый.** Данные в памяти, однопоточная обработка команд (нет блокировок), простой протокол. Один инстанс — порядка 100k+ простых операций в секунду, latency внутри дата-центра — сотни микросекунд.

**Ограничения, которые надо учитывать:**

1. **Память.** Все данные в RAM — дорого на больших объёмах. Нужны TTL и политика вытеснения (`maxmemory-policy allkeys-lru` для кэша).
2. **Durability.** RDB-снапшоты и AOF с `appendfsync everysec` — можно потерять до секунды данных. Асинхронная репликация — при failover возможна потеря последних записей.
3. **Однопоточность.** Одна тяжёлая команда (`KEYS *`, большой `SMEMBERS`, огромный ключ) блокирует всех. Нужно избегать больших ключей и O(N)-команд на горячем пути.
4. **Блокировки не абсолютны.** Lock с TTL может истечь во время долгой операции — для критичных случаев нужен fencing token или блокировка в БД.

**Когда Redis не нужен:** нагрузка небольшая и PostgreSQL справляется с запросами за миллисекунды; кэш нужен только внутри одного процесса (тогда `IMemoryCache` без сетевого хопа); данные требуют транзакционной целостности. Добавление Redis — это ещё один компонент, который может упасть, и проблема инвалидации кэша.

В .NET: `StackExchange.Redis` (один `ConnectionMultiplexer` на приложение), `IDistributedCache`, или `HybridCache` (.NET 9) — двухуровневый кэш L1 in-memory + L2 Redis с защитой от stampede.

## Когда нужен Kafka?

```yaml
category: system-design
level: middle
difficulty: 4
slug: system-design-kogda-nuzhen-kafka
tags: kafka, architecture
```

Kafka нужна, когда требуется надёжный, упорядоченный и повторно читаемый поток событий с высокой пропускной способностью: event-driven интеграция сервисов, CDC, event sourcing, стриминг аналитики и логов. Если нужна просто очередь задач с подтверждением каждого сообщения, RabbitMQ часто проще.

**Модель Kafka.** Топик разбит на партиции; каждая партиция — append-only лог с offset. Порядок гарантирован только внутри партиции, партиция выбирается по ключу сообщения (`hash(key) % partitions`). Консьюмеры объединены в consumer group: каждая партиция читается ровно одним консьюмером группы, поэтому параллелизм ограничен числом партиций. Сообщения не удаляются после чтения — они живут по retention (часы, дни, бесконечно для compacted-топиков).

**Когда Kafka — правильный выбор:**

1. **Несколько независимых потребителей одного события.** `OrderCreated` читают биллинг, склад, аналитика, уведомления — каждый своей группой, в своём темпе, без знания друг о друге.
2. **Replay.** Новый сервис может прочитать историю с начала; после бага можно перечитать события с нужного offset.
3. **Высокий поток.** Сотни тысяч и миллионы сообщений в секунду на кластер благодаря последовательной записи на диск, батчингу и zero-copy.
4. **Порядок по ключу.** Все события одного заказа (ключ `orderId`) обрабатываются по порядку.
5. **CDC и интеграция данных.** Debezium читает WAL PostgreSQL и публикует изменения в Kafka, откуда их забирают Elasticsearch, ClickHouse, кэш.
6. **Буфер при пиках.** Производитель пишет быстро, потребители разгребают с доступной скоростью.

**Когда Kafka избыточна:**

- десятки сообщений в секунду и одна очередь задач — хватит RabbitMQ, SQS или даже таблицы в PostgreSQL с `FOR UPDATE SKIP LOCKED`;
- нужны отложенные сообщения, приоритеты, маршрутизация по сложным правилам — это сильные стороны RabbitMQ;
- нужен request-reply с низкой latency — это задача gRPC/HTTP.

**Что нужно проектировать осознанно:**

- **Ключ партиционирования** — определяет порядок и равномерность; горячий ключ перегружает одну партицию.
- **Число партиций** — с запасом на рост консьюмеров; увеличить можно, но это меняет маппинг ключей.
- **Надёжность записи** — `acks=all`, `min.insync.replicas=2` при RF=3, идемпотентный producer.
- **Семантика доставки** — по умолчанию at-least-once, поэтому консьюмеры должны быть идемпотентными.
- **Атомарность с БД** — запись в БД и публикация в Kafka не атомарны; решается transactional outbox.

В .NET — `Confluent.Kafka` напрямую или через MassTransit/KafkaFlow.

## Когда нужен message broker?

```yaml
category: system-design
level: middle
difficulty: 4
slug: system-design-kogda-nuzhen-message-broker
tags: kafka, architecture
```

Message broker нужен, когда отправителю не нужно ждать результата обработки: чтобы развязать сервисы по времени и доступности, сгладить пики нагрузки, раздать одно событие нескольким получателям или надёжно выполнить фоновую работу с ретраями. Если вызывающему нужен ответ прямо сейчас, брокер добавляет сложность без пользы.

**Признаки, что брокер нужен:**

1. **Долгая или ненадёжная работа.** Генерация PDF, отправка email, вызов медленного внешнего API — пользователь получает `202 Accepted`, работа идёт в фоне.
2. **Пиковая нагрузка.** Во время распродажи 5 000 заказов/с, а склад обрабатывает 1 000/с — очередь поглощает пик, backlog разбирается за минуты.
3. **Временная развязка.** Сервис уведомлений упал на 10 минут — сообщения накопились и будут обработаны после восстановления, заказы при этом создаются.
4. **Fan-out.** Одно событие `PaymentCompleted` нужно биллингу, складу и аналитике. Без брокера платёжный сервис знал бы обо всех получателях.
5. **Распределённые процессы.** Саги и хореография между сервисами строятся на событиях.

**Два класса брокеров:**

| | Очередь (RabbitMQ, SQS) | Лог (Kafka, Pulsar) |
| --- | --- | --- |
| После обработки | сообщение удаляется | остаётся до retention |
| Потребители | конкурирующие за сообщения | группы с собственным offset |
| Сильные стороны | маршрутизация, приоритеты, TTL, DLQ, отложенная доставка | throughput, порядок по ключу, replay |
| Типичная задача | фоновые задачи, команды | поток событий, интеграция, CDC |

**Что брокер привносит — и что нужно решить:**

- **At-least-once доставка** → дубликаты неизбежны, обработчики должны быть идемпотентными (таблица обработанных `message_id`).
- **Атомарность с БД** → transactional outbox: событие пишется в таблицу в той же транзакции, отдельный процесс публикует его в брокер.
- **Ядовитые сообщения** → ограниченные ретраи с backoff и dead letter queue.
- **Eventual consistency** → UI должен уметь показывать «заказ обрабатывается».
- **Порядок** → гарантируется только внутри партиции/очереди.
- **Наблюдаемость** → consumer lag и размер DLQ как ключевые метрики; trace context передаётся в заголовках сообщения.

**Когда не нужен:** синхронный сценарий с ответом пользователю («проверить остаток», «получить профиль»), маленькая система, где фоновые задачи можно выполнять через таблицу-очередь в PostgreSQL или `BackgroundService` с `Channel<T>` (если потеря при рестарте допустима). Брокер — это ещё один критичный компонент, который надо мониторить, обновлять и резервировать.

## Как масштабировать API?

```yaml
category: system-design
level: middle
difficulty: 4
slug: system-design-kak-masshtabirovat-api
tags: scalability, architecture
```

API масштабируют горизонтально: делают сервис stateless, ставят несколько инстансов за балансировщик и добавляют их по метрикам. Дальше снимают нагрузку с самого API и его зависимостей — кэшированием, асинхронной обработкой и защитой от перегрузки. Обычно первым узким местом оказывается не API, а база за ним.

**1. Stateless.** Никакого состояния в памяти инстанса, которое нужно следующему запросу: сессии — в Redis или в JWT, файлы — в S3, фоновые задачи — в очереди. Тогда любой запрос может обработать любой под, и поды можно добавлять и убивать свободно.

**2. Балансировка и автоскейлинг.** L7-балансировщик (ingress в Kubernetes, Envoy, NGINX) распределяет запросы, health checks убирают больные инстансы. HPA масштабирует по CPU или по RPS/latency. Важно: readiness probe не должна пускать трафик до прогрева, graceful shutdown должен дорабатывать текущие запросы.

**3. Разгрузка зависимостей.**

- **Кэш:** HTTP-кэш и CDN для публичных GET, Redis для горячих данных, in-memory кэш для справочников.
- **Реплики чтения** для запросов, допускающих небольшой лаг.
- **Асинхронность:** тяжёлая работа уходит в очередь, API отвечает `202`.
- **Connection pooling:** 50 подов × пул 100 = 5 000 соединений убьют PostgreSQL — нужен PgBouncer в transaction mode и разумный `Maximum Pool Size`.

**4. Эффективность одного инстанса.** Асинхронный I/O без блокировок потоков (`async` до конца, никаких `.Result`), пагинация и ограничения на размер ответа, устранение N+1 запросов, сжатие ответов, `System.Text.Json` с source generators для горячих путей. Удвоение производительности инстанса — это вдвое меньше железа.

**5. Защита от перегрузки.**

- rate limiting по клиенту (`Microsoft.AspNetCore.RateLimiting` локально, Redis — глобально);
- таймауты на все исходящие вызовы и circuit breaker (Polly / `Microsoft.Extensions.Http.Resilience`);
- load shedding: при переполнении очереди отдавать 503 быстро, а не копить запросы;
- bulkhead — отдельные пулы для разных зависимостей, чтобы медленный сервис не съел все потоки.

**6. Разделение по нагрузке.** Если один эндпоинт (поиск, экспорт) потребляет непропорционально много ресурсов, его выносят в отдельный деплоймент, чтобы масштабировать независимо и изолировать сбои.

**7. Географическое масштабирование.** CDN и edge для статики и кэшируемых ответов, затем — развёртывание в нескольких регионах с GeoDNS/anycast.

**Порядок действий на практике:** измерить (где тратится время по трейсам), убрать очевидную неэффективность, добавить кэш, масштабировать горизонтально, и только затем думать о шардировании данных.

## Как масштабировать database?

```yaml
category: system-design
level: middle
difficulty: 4
slug: system-design-kak-masshtabirovat-database
tags: scalability, architecture
```

Базу масштабируют по нарастающей сложности: сначала оптимизация запросов и вертикальное масштабирование, затем кэш и реплики чтения для read-нагрузки, потом партиционирование и вынос данных, и в последнюю очередь — шардирование для масштабирования записи. Каждый шаг дороже предыдущего в разработке и эксплуатации.

**Шаг 0. Оптимизация.** Индексы по реальным запросам (`pg_stat_statements`, `EXPLAIN ANALYZE`), устранение N+1 и `SELECT *`, keyset-пагинация вместо `OFFSET`, короткие транзакции, PgBouncer для пула соединений. Часто это даёт ×10 без изменения архитектуры.

**Шаг 1. Vertical scaling.** Больше CPU, RAM (рабочий набор данных в `shared_buffers` + page cache), быстрые NVMe. Современный сервер на 64+ ядра и 512 GB RAM вытягивает очень много. Потолок — размер машины и время восстановления.

**Шаг 2. Кэширование.** Redis перед БД для горячих данных с высоким hit ratio снимает большую часть чтений. Цена — инвалидация и устаревшие данные.

**Шаг 3. Read replicas.** Потоковая репликация на 2–5 реплик, чтения распределяются, запись идёт в primary.

- лаг репликации — от миллисекунд до секунд под нагрузкой, поэтому read-your-writes нужно обеспечивать отдельно (читать из primary после собственной записи);
- на запись не помогает вообще.

**Шаг 4. Партиционирование в пределах инстанса.** Декларативное партиционирование PostgreSQL по времени или хэшу: маленькие индексы, быстрый `DROP PARTITION` вместо `DELETE` миллионов строк, partition pruning в запросах.

**Шаг 5. Функциональное разделение.** Разные домены в разные базы: заказы, каталог, пользователи. Аналитика — в ClickHouse через CDC, поиск — в Elasticsearch, логи и события — не в OLTP-базу.

**Шаг 6. Шардирование.** Данные делятся по ключу (`tenant_id`, `user_id`) между независимыми primary. Масштабирует запись и объём линейно, но:

- кросс-шардовые запросы и транзакции становятся сложными или невозможными;
- выбор ключа практически необратим, решардинг — отдельный проект;
- растёт операционная сложность: N бэкапов, N failover, миграции схемы на всех шардах.

Инструменты: Citus для PostgreSQL, Vitess для MySQL, шардирование на уровне приложения, либо переход на распределённую СУБД (CockroachDB, YugabyteDB) или wide-column store для данных с простым доступом по ключу.

**Ориентиры:** реплики нужны, когда чтение упирается в CPU primary; шардирование — когда запись или объём (обычно единицы-десятки TB) не помещаются в самый большой разумный сервер. До этого момента шардирование — преждевременная сложность.

## Что такое load balancer?

```yaml
category: system-design
level: middle
difficulty: 2
slug: system-design-chto-takoe-load-balancer
tags: scalability, architecture
```

Load balancer — компонент, который распределяет входящие запросы между несколькими экземплярами сервиса и перестаёт отправлять трафик на неработающие. Он делает возможным горизонтальное масштабирование и устраняет единичную точку отказа на уровне серверов приложения.

**L4 vs L7:**

| | L4 (транспортный) | L7 (прикладной) |
| --- | --- | --- |
| Что видит | IP, порт, TCP/UDP | HTTP: путь, заголовки, cookie |
| Возможности | быстрое проксирование соединений | маршрутизация по URL, TLS termination, retries, rate limiting |
| Примеры | AWS NLB, IPVS, MetalLB | NGINX, Envoy, HAProxy, AWS ALB, Kubernetes Ingress |

**Алгоритмы распределения:**

- **Round robin** — по кругу; хорошо для однородных запросов.
- **Weighted round robin** — с весами для машин разной мощности или канареечных релизов.
- **Least connections / least requests** — выбирать наименее загруженный; лучше при разной длительности запросов.
- **Power of two choices** — выбрать два случайных и взять менее загруженный; почти так же хорошо, как least connections, без глобального состояния (используется в Envoy).
- **Hash-based / consistent hashing** — один ключ (клиент, сессия) всегда попадает на один бэкенд; нужно для sticky sessions и шардированных кэшей.

**Health checks.** Активные (периодический запрос на `/health`) и пассивные (outlier detection: бэкенд с серией 5xx временно выключается). В ASP.NET Core — `MapHealthChecks` с отдельными liveness и readiness.

**Что ещё обычно делает L7-балансировщик:** TLS termination, HTTP/2 и gRPC, сжатие, rate limiting, добавление `X-Forwarded-For`, connection draining при деплое.

**Сам балансировщик тоже не должен быть единой точкой отказа:** пара в active-passive с общим VIP (keepalived/VRRP), managed-балансировщики облака, либо DNS/anycast перед несколькими балансировщиками.

**Sticky sessions** — привязка клиента к серверу. Упрощают stateful-приложения, но ломают равномерность и failover, поэтому предпочтительнее stateless-сервисы с состоянием в Redis.

## Что такое horizontal scaling?

```yaml
category: system-design
level: middle
difficulty: 2
slug: system-design-chto-takoe-horizontal-scaling
tags: scalability, architecture
```

Horizontal scaling (scale out) — увеличение мощности системы добавлением новых машин или инстансов, а не усилением существующих. Нагрузка распределяется между узлами, поэтому потолок роста определяется архитектурой, а не размером самого большого сервера.

**Что даёт:**

- **Почти неограниченный рост** — 10 подов → 100 подов.
- **Отказоустойчивость** — падение одного узла из 20 снижает мощность на 5%, а не до нуля.
- **Эластичность** — автоскейлинг под суточный профиль: днём 30 подов, ночью 5.
- **Стоимость** — много стандартных машин обычно дешевле одной огромной.

**Что требуется от системы:**

1. **Stateless-сервисы.** Состояние запроса не должно жить в памяти конкретного инстанса: сессии в Redis/JWT, файлы в S3, задачи в очереди.
2. **Балансировка** — балансировщик и health checks.
3. **Распределённые данные** — для stateful-компонентов нужны репликация и шардирование, и это самая сложная часть.
4. **Координация** — фоновые задачи не должны выполняться на всех инстансах одновременно (распределённая блокировка, лидер-выборы или отдельный воркер с одной репликой).

**Сложности:**

- сетевые задержки и частичные отказы между узлами;
- консистентность данных между репликами и шардами (CAP);
- in-memory кэши на каждом инстансе расходятся — нужна инвалидация через pub/sub или короткий TTL;
- больше соединений к БД: N инстансов × размер пула;
- сложнее отладка — нужны распределённые трейсы и централизованные логи.

**Stateless vs stateful.** Для API горизонтальное масштабирование почти бесплатно — добавить реплики в Deployment. Для БД это означает шардирование, где каждое добавление узла требует перераспределения данных; поэтому базы часто масштабируют сначала вертикально.

**Пример.** В Kubernetes: HPA по CPU 70% добавляет поды API с 4 до 40 за несколько минут; перед этим нужно проверить, что PostgreSQL выдержит 10-кратный рост соединений (PgBouncer) и запросов (кэш, реплики).

## Что такое vertical scaling?

```yaml
category: system-design
level: middle
difficulty: 2
slug: system-design-chto-takoe-vertical-scaling
tags: scalability, architecture
```

Vertical scaling (scale up) — увеличение мощности одного узла: больше CPU, памяти, более быстрые диски и сеть. Приложение менять не нужно, поэтому это самый быстрый и дешёвый по усилиям способ получить запас производительности, но у него есть физический и экономический потолок.

**Плюсы:**

- **Нет изменений в коде** — та же архитектура, та же консистентность.
- **Нет распределённых проблем** — транзакции, JOIN и блокировки работают как раньше.
- **Эффективно для БД.** Больше RAM — больше рабочего набора в кэше и меньше чтений с диска; NVMe вместо сетевого диска кратно снижает latency fsync.

**Минусы:**

- **Потолок.** Самый большой сервер ограничен (в облаке — сотни vCPU и единицы TB RAM), и цена растёт быстрее мощности.
- **Единая точка отказа.** Большой узел — это всё ещё один узел; нужна реплика для failover.
- **Простой при изменении.** Смена размера VM обычно требует рестарта — для БД это failover на реплику или окно обслуживания.
- **Не всегда линейно.** Приложение с lock contention или однопоточным узким местом (Redis, один consumer) не ускорится от дополнительных ядер.
- **Дольше восстановление.** Бэкап и восстановление 10-терабайтной базы занимает часы.

**Когда уместно:**

1. Базы данных до того, как понадобится шардирование — это часто самый рациональный путь на годы вперёд.
2. Быстрое решение проблемы, пока готовится горизонтальное масштабирование.
3. Компоненты, которые плохо распределяются: primary БД, однопоточные процессы.

**Сочетание подходов** — норма: stateless-сервисы масштабируют горизонтально, primary PostgreSQL — вертикально плюс реплики для чтения. Прежде чем покупать машину больше, стоит проверить, что ресурс действительно исчерпан: часто «нужно больше CPU» на деле означает отсутствующий индекс.

## Что такое caching layer?

```yaml
category: system-design
level: middle
difficulty: 2
slug: system-design-chto-takoe-caching-layer
tags: architecture
```

Caching layer — промежуточный слой быстрого хранилища между потребителем и медленным или дорогим источником данных. Он отдаёт частые результаты без обращения к источнику, снижая latency и нагрузку, ценой того, что данные могут быть устаревшими.

**Уровни кэширования от клиента к данным:**

| Уровень | Что кэширует | Инструмент |
| --- | --- | --- |
| Браузер/клиент | статику, ответы API | `Cache-Control`, `ETag` |
| CDN | статику, медиа, публичные ответы | CloudFront, Cloudflare, Akamai |
| Reverse proxy | ответы HTTP | NGINX, Varnish, Output Caching в ASP.NET Core |
| Приложение (in-process) | справочники, конфигурацию | `IMemoryCache` |
| Распределённый кэш | сущности, результаты запросов, сессии | Redis, Memcached |
| БД | страницы данных, планы | `shared_buffers`, page cache ОС |

**Стратегии работы:**

- **Cache-aside** — приложение читает из кэша, при промахе идёт в БД и кладёт результат в кэш. Самый распространённый вариант.
- **Read-through** — кэш сам загружает данные из источника.
- **Write-through** — запись одновременно в кэш и в БД; кэш свежий, запись медленнее.
- **Write-behind** — запись в кэш, в БД асинхронно; быстро, но риск потери.

**Ключевые вопросы при проектировании:**

1. **Что кэшировать.** Данные с высоким соотношением чтения к записи и допустимой устарелостью: каталог, профили, результаты тяжёлых запросов. Не кэшируют баланс перед списанием.
2. **Инвалидация.** TTL, удаление ключа при изменении, события через Kafka/CDC. Обычно комбинация: удаление при записи плюс TTL как страховка.
3. **Hit ratio.** Кэш с 50% попаданий мало полезен; цель — 90%+. Если данные не повторяются, кэш не поможет.
4. **Вытеснение.** LRU/LFU и лимит памяти.
5. **Сбой кэша.** При падении Redis вся нагрузка идёт в БД — нужно, чтобы БД это пережила или была деградация (circuit breaker, локальный кэш).
6. **Cache stampede.** Одновременный промах по горячему ключу — защита через блокировку на пересчёт или раннее обновление.

**Эффект в цифрах:** при 10 000 RPS и hit ratio 95% до БД доходит 500 RPS. При падении hit ratio до 80% — уже 2 000 RPS, в четыре раза больше. Поэтому hit ratio — одна из главных метрик системы с кэшем.

## Как организовать CDN?

```yaml
category: system-design
level: middle
difficulty: 4
slug: system-design-kak-organizovat-cdn
tags: scalability, architecture
```

CDN — сеть edge-серверов, которые кэшируют контент ближе к пользователю и отдают его без обращения к origin. Организация CDN сводится к трём решениям: что кэшировать и как долго, как инвалидировать изменённый контент и как защитить origin от промахов и всплесков.

**Как работает запрос:**

```text
Пользователь → DNS/anycast → ближайший PoP (edge)
  hit  → ответ из кэша edge (единицы-десятки мс)
  miss → (shield / mid-tier) → origin (S3 или API) → кэшируется на edge → ответ
```

**Что отдавать через CDN:**

- статику фронтенда (JS, CSS, шрифты) — идеальный случай;
- изображения и видео, включая HLS/DASH-сегменты;
- публичные и одинаковые для всех ответы API: каталог, цены, конфигурации — с коротким TTL;
- загрузки файлов по подписанным URL (signed URL/cookie) для приватного контента.

Персональные ответы (`/me`, корзина) через CDN не кэшируются — только проксируются, если нужен TLS termination и WAF на edge.

**Стратегия кэширования:**

1. **Immutable-ассеты с хэшем в имени** (`app.3f9a1c.js`) и `Cache-Control: public, max-age=31536000, immutable`. Новая версия — новое имя, инвалидация не нужна.
2. **HTML и точки входа** — короткий TTL или `no-cache` с `ETag`, чтобы быстро подхватывать новые релизы.
3. **API-ответы** — `s-maxage=60, stale-while-revalidate=300`: CDN отдаёт устаревшее, пока в фоне обновляет.
4. **Cache key** — только значимые параметры. Лишние query-параметры (utm-метки) и заголовки в ключе убивают hit ratio.

**Инвалидация.** Purge по URL или тегу (surrogate keys) при изменении контента; но основной механизм — версионирование URL, потому что purge по всей сети занимает от секунд до минут и обычно лимитирован.

**Защита origin:**

- **Origin shield** — промежуточный слой кэша: все edge-серверы ходят за промахами в один shield, а не напрямую в origin. Без него 200 PoP могут дать 200 одновременных промахов на один объект.
- **Request collapsing** — одновременные запросы к одному отсутствующему объекту объединяются в один запрос к origin.
- **Origin — S3-бакет** для статики, доступный только CDN (origin access control), а не открытый в интернет.

**Эффект в цифрах.** Сайт отдаёт 40 Gbps статики; при hit ratio 95% origin обслуживает 2 Gbps. Падение hit ratio до 80% — уже 8 Gbps, в четыре раза больше. Поэтому hit ratio и egress origin — главные метрики.

**Дополнительно:** TLS на edge и HTTP/2–3, сжатие brotli, оптимизация изображений на лету (resize, WebP/AVIF), WAF и защита от DDoS, multi-CDN для доступности и цены при очень больших объёмах.

## Как обеспечить high availability?

```yaml
category: system-design
level: middle
difficulty: 4
slug: system-design-kak-obespechit-high-availability
tags: resilience, architecture
```

High availability — способность системы продолжать обслуживать запросы при отказе отдельных компонентов. Достигается устранением единичных точек отказа: каждый критичный компонент дублирован, отказ обнаруживается автоматически, а трафик переключается на здоровые экземпляры без участия человека.

**Сначала — цель в цифрах:**

| SLA | Простой в год | Простой в месяц |
| --- | --- | --- |
| 99% | ~3.65 дня | ~7.2 часа |
| 99.9% | ~8.8 часа | ~43 минуты |
| 99.95% | ~4.4 часа | ~22 минуты |
| 99.99% | ~53 минуты | ~4.3 минуты |

Каждая «девятка» стоит заметно дороже. 99.99% означает, что ручное восстановление невозможно в принципе — только автоматика.

**Доступность последовательных зависимостей перемножается:** API (99.95%) → Redis (99.9%) → PostgreSQL (99.95%) ≈ 99.8%. Поэтому критичный путь должен быть коротким, а некритичные зависимости — необязательными.

**Уровни резервирования:**

1. **Сервисы.** Минимум 2–3 реплики stateless-сервиса, разнесённые по зонам доступности (topology spread constraints, pod anti-affinity), `PodDisruptionBudget`, чтобы обновление узлов не убило все поды.
2. **Балансировщики** — managed LB или пара с VIP.
3. **PostgreSQL** — primary + синхронная реплика в другой зоне и автоматический failover (Patroni, CloudNativePG, managed-сервис). Приложение подключается через стабильный endpoint.
4. **Redis** — Sentinel или Redis Cluster с репликами.
5. **Kafka** — RF=3, `min.insync.replicas=2`, брокеры в трёх зонах.
6. **Зоны доступности** — вся система переживает потерю одной зоны. Multi-region — следующий уровень, нужен для 99.99%+ или требований DR.

**Обнаружение и переключение:** health checks (liveness/readiness), outlier detection на балансировщике, таймауты и circuit breakers в клиентах, автоматический failover с защитой от split-brain (кворум, fencing).

**Graceful degradation.** Не все функции одинаково важны: при падении сервиса рекомендаций главная страница показывает популярные товары, при недоступности поиска работает каталог. Некритичная зависимость не должна ронять критичный сценарий.

**Процессы важны не меньше архитектуры.** Большая часть инцидентов — от изменений: canary и blue-green деплои, feature flags, быстрый rollback, миграции БД в режиме expand/contract. Плюс мониторинг SLO с алертами по burn rate и регулярные учения по failover — непроверенный резерв часто не работает в нужный момент.

## Что такое failover?

```yaml
category: system-design
level: middle
difficulty: 2
slug: system-design-chto-takoe-failover
tags: resilience, architecture
```

Failover — автоматическое или ручное переключение работы с отказавшего компонента на резервный. Цель — сократить простой до секунд или минут без потери данных, насколько позволяет выбранная схема репликации.

**Схемы:**

- **Active-passive.** Резерв (standby) получает данные, но не обслуживает трафик. При отказе primary он повышается до primary. Типично для PostgreSQL.
- **Active-active.** Все узлы обслуживают трафик; при отказе одного остальные забирают его долю. Типично для stateless-сервисов, для БД требует разрешения конфликтов записи.

**Этапы failover для БД:**

1. **Обнаружение.** Health check не отвечает N раз подряд — например, 3 проверки по 5 секунд. Слишком чувствительный детектор вызывает ложные переключения, слишком медленный — долгий простой.
2. **Решение.** Кворум (etcd/Consul у Patroni, Sentinel у Redis) подтверждает, что primary действительно недоступен, а не просто отрезан от одного наблюдателя.
3. **Промоушен.** Самая свежая реплика становится primary.
4. **Fencing.** Старый primary должен быть гарантированно выключен или лишён права записи — иначе split-brain: два primary принимают разные записи.
5. **Переключение клиентов.** Через DNS, VIP, прокси (HAProxy, PgBouncer) или service endpoint в Kubernetes. Клиенты должны уметь переподключаться и повторять запросы.

**Потеря данных зависит от репликации:**

| Репликация | Потери при failover | Цена |
| --- | --- | --- |
| Асинхронная | последние транзакции, не дошедшие до реплики | минимальная latency записи |
| Синхронная | 0 подтверждённых транзакций | +RTT до реплики на каждый commit |

**Подводные камни:**

- кэш DNS у клиентов с большим TTL продлевает простой;
- старые TCP-соединения висят до таймаута — нужны разумные keepalive и connection timeout;
- после failover реплик становится меньше — нужно быстро восстановить избыточность;
- failback (возврат на исходный узел) — отдельная операция, часто её не делают;
- непроверенный failover ломается в реальной аварии, поэтому его нужно регулярно отрабатывать.

Типичное время автоматического failover PostgreSQL с Patroni — 10–30 секунд; Redis Sentinel — порядка десятков секунд в зависимости от `down-after-milliseconds`.

## Что такое replication?

```yaml
category: system-design
level: middle
difficulty: 2
slug: system-design-chto-takoe-replication
tags: replication, architecture
```

Replication — хранение копий одних и тех же данных на нескольких узлах. Она решает три задачи: отказоустойчивость (есть куда переключиться), масштабирование чтения (читать с реплик) и снижение latency (копия ближе к пользователю). Цена — задержка или сложность согласования копий.

**Топологии:**

- **Leader-follower (primary-replica).** Все записи идут в лидер, он передаёт изменения репликам. Простая модель без конфликтов записи. PostgreSQL streaming replication, MySQL, Redis, Kafka (на уровне партиции).
- **Multi-leader.** Запись принимается в нескольких узлах (обычно по одному на регион), изменения обмениваются асинхронно. Нужна стратегия разрешения конфликтов.
- **Leaderless.** Клиент пишет в N узлов и читает с нескольких, согласованность через кворум: при `W + R > N` чтение пересекается с последней записью. Cassandra, DynamoDB.

**Синхронная vs асинхронная:**

| | Синхронная | Асинхронная |
| --- | --- | --- |
| Commit подтверждается | после записи на реплике | сразу на лидере |
| Потеря при отказе лидера | нет | последние транзакции |
| Latency записи | + RTT до реплики | минимальная |
| Если реплика недоступна | запись блокируется (или деградирует в async) | не влияет |

На практике часто используют полусинхронную схему: одна синхронная реплика в соседней зоне, остальные асинхронные. В PostgreSQL — `synchronous_standby_names = 'ANY 1 (r1, r2)'`.

**Лаг репликации и его последствия:**

- **Read-your-writes:** пользователь сохранил профиль, а следующий запрос ушёл на отстающую реплику и показал старые данные. Решение — читать из лидера какое-то время после записи или до достижения нужной позиции WAL/LSN.
- **Monotonic reads:** последовательные запросы попадают на разные реплики и видят данные «прыгающими назад». Решение — привязка пользователя к одной реплике.
- Под тяжёлой нагрузкой или при долгих запросах на реплике лаг вырастает до секунд и минут — его нужно мониторить.

**Чего репликация не заменяет:** бэкап. Ошибочный `DELETE` или повреждение данных реплицируется на все копии мгновенно. Нужны бэкапы с point-in-time recovery.

## Что такое sharding?

```yaml
category: system-design
level: middle
difficulty: 2
slug: system-design-chto-takoe-sharding
tags: partitioning, architecture
```

Sharding — горизонтальное разделение данных между несколькими независимыми узлами БД: каждый шард хранит часть строк и обслуживает их чтение и запись. Это единственный способ масштабировать запись и объём за пределы одного сервера, но он усложняет запросы, транзакции и эксплуатацию.

**Стратегии распределения:**

| Стратегия | Как | Плюсы | Минусы |
| --- | --- | --- | --- |
| Hash | `hash(user_id) % N` | равномерное распределение | range-запросы идут во все шарды; смена N перемещает почти все ключи |
| Consistent hashing / фиксированные слоты | ключ → один из 1 024 слотов → слот на шард | при добавлении шарда переезжает только часть слотов | нужна таблица маппинга |
| Range | `user_id` 1–1M → шард 1 | эффективные диапазонные запросы | горячие диапазоны, например новые записи |
| Directory (lookup) | таблица «ключ → шард» | гибкость, можно перемещать отдельных клиентов | ещё один сервис и точка отказа |
| Geo | по региону пользователя | локальность, требования к хранению данных | неравномерная нагрузка |

**Выбор ключа — главное решение.** Хороший ключ:

- присутствует почти во всех запросах, чтобы запрос шёл в один шард;
- группирует данные, которые изменяются вместе в одной транзакции (заказ и его позиции — по `customer_id` или `tenant_id`);
- даёт равномерное распределение без горячих точек.

Для SaaS естественный ключ — `tenant_id`; для соцсети — `user_id`; для мессенджера — `chat_id`.

**Что становится сложным:**

1. **Кросс-шардовые запросы** — scatter-gather по всем шардам с объединением результатов; медленно и дорого.
2. **Транзакции между шардами** — 2PC или саги; обычно их избегают дизайном ключа.
3. **Глобальные уникальные ID** — не автоинкремент, а Snowflake-подобные ID или UUIDv7.
4. **Горячие шарды** — крупный клиент перегружает свой шард; решается выделением отдельного шарда.
5. **Решардинг** — перенос данных при росте; нужно планировать заранее (много логических шардов на малом числе физических).
6. **Эксплуатация** — миграции схемы, бэкапы и мониторинг на каждом шарде.

**Инструменты:** Citus для PostgreSQL, Vitess для MySQL, встроенное шардирование MongoDB и Cassandra, либо маршрутизация на уровне приложения. Шардировать стоит, когда реплики, партиционирование и вертикальное масштабирование исчерпаны, — не раньше.

## Что такое partitioning?

```yaml
category: system-design
level: middle
difficulty: 2
slug: system-design-chto-takoe-partitioning
tags: partitioning, architecture
```

Partitioning — разделение большой таблицы или набора данных на части по какому-то признаку. В узком смысле (PostgreSQL) — деление таблицы на партиции внутри одного сервера; в широком смысле термин включает и шардирование, когда части живут на разных узлах. Цель — сделать данные управляемыми: меньше индексы, быстрее запросы, дешевле удаление.

**Горизонтальное vs вертикальное:**

- **Горизонтальное** — разные строки в разных партициях (по дате, по хэшу ключа).
- **Вертикальное** — разные колонки в разных таблицах: редко используемые большие поля (описание, JSON) отделяются от горячих узких колонок.

**Декларативное партиционирование в PostgreSQL:**

```sql
CREATE TABLE events (
    id         bigint      NOT NULL,
    created_at timestamptz NOT NULL,
    payload    jsonb,
    PRIMARY KEY (id, created_at)
) PARTITION BY RANGE (created_at);

CREATE TABLE events_2026_09 PARTITION OF events
    FOR VALUES FROM ('2026-09-01') TO ('2026-10-01');
```

Типы: `RANGE` (время — самый частый случай), `LIST` (регион, тип), `HASH` (равномерное распределение по ключу).

**Что даёт:**

1. **Partition pruning** — запрос `WHERE created_at >= now() - interval '1 day'` читает только текущую партицию.
2. **Дешёвое удаление старых данных** — `DETACH`/`DROP PARTITION` мгновенно вместо `DELETE` миллионов строк с последующим VACUUM.
3. **Меньше индексы** — индекс каждой партиции помещается в память.
4. **Раздельное обслуживание** — VACUUM и перестроение индексов по частям; старые партиции можно вынести на дешёвое хранилище.

**Ограничения:**

- ключ партиционирования должен входить в первичный ключ и уникальные ограничения;
- запросы без ключа партиционирования сканируют все партиции;
- тысячи партиций замедляют планирование запросов — разумно десятки-сотни;
- партиции нужно создавать заранее (`pg_partman` или джоба).

**Отличие от шардирования.** Партиционирование в пределах одного сервера не масштабирует CPU и запись — оно облегчает работу с объёмом. Шардирование переносит партиции на разные серверы и масштабирует всё, но добавляет распределённые проблемы. В Kafka термин «partition» означает единицу параллелизма и порядка в топике — это уже горизонтальное распределение по брокерам.

## Как обеспечить data consistency?

```yaml
category: system-design
level: middle
difficulty: 4
slug: system-design-kak-obespechit-data-consistency
tags: architecture
```

Консистентность обеспечивают на двух уровнях: внутри одной базы — транзакциями и ограничениями целостности, между сервисами и хранилищами — паттернами, которые дают eventual consistency с гарантиями: transactional outbox, идемпотентные консьюмеры, саги с компенсациями. Главное решение — какой уровень консистентности нужен каждой конкретной операции.

**1. Внутри одной БД — пользуйтесь ей.**

- ACID-транзакции для изменений, которые должны произойти вместе;
- `UNIQUE`, `FOREIGN KEY`, `CHECK` — инварианты, которые нельзя обойти багом в коде;
- правильный уровень изоляции: `READ COMMITTED` по умолчанию, `SERIALIZABLE` или явные блокировки для check-then-act;
- optimistic concurrency через колонку `version`: `UPDATE ... SET version = version + 1 WHERE id = @id AND version = @v`, 0 строк — конфликт.

Пример атомарного списания без гонки:

```sql
UPDATE stock SET qty = qty - @n
WHERE product_id = @id AND qty >= @n;   -- 0 строк = недостаточно товара
```

**2. БД + брокер — transactional outbox.** Нельзя атомарно записать в PostgreSQL и опубликовать в Kafka. Решение: в той же транзакции записать событие в таблицу `outbox`, отдельный процесс (или Debezium через CDC) публикует его в брокер. Событие гарантированно уйдёт хотя бы один раз.

**3. Получатель — идемпотентность.** Доставка at-least-once означает дубликаты. Консьюмер хранит `message_id` обработанных сообщений в той же транзакции, что и изменение данных (inbox), или делает операции идемпотентными по смыслу (upsert, установка статуса вместо инкремента).

**4. Между сервисами — саги.** Бизнес-процесс «заказ → резерв → оплата → доставка» разбивается на локальные транзакции с компенсациями: оплата не прошла — снять резерв, отменить заказ. Оркестрация (координатор с состоянием, например MassTransit state machine) проще в отладке, хореография (сервисы реагируют на события друг друга) — слабее связность.

**5. Кэш и производные хранилища.** Инвалидация после commit, TTL как страховка, CDC для поиска и аналитики. Принять, что они отстают на секунды.

**Какой уровень выбрать:**

| Данные | Требование |
| --- | --- |
| Баланс, списание денег, остаток при покупке | strong, в одной транзакции |
| Статус заказа между сервисами | eventual с гарантированной доставкой |
| Счётчик просмотров, лента, рекомендации | eventual, допустимы потери и задержки |

**Чего избегать:** распределённых транзакций 2PC между микросервисами (блокировки, зависимость от координатора), dual write «сначала в БД, потом в Kafka» без outbox, и попыток сделать всё strongly consistent — это убивает доступность и производительность.

**Проверка.** Периодическая сверка (reconciliation) между системами — например, заказы против платежей у провайдера — ловит расхождения, которые неизбежно возникнут из-за багов.

## Как обеспечить fault tolerance?

```yaml
category: system-design
level: middle
difficulty: 4
slug: system-design-kak-obespechit-fault-tolerance
tags: resilience, architecture
```

Fault tolerance — способность системы продолжать корректно работать при отказе части компонентов. Её обеспечивают три вещи: избыточность (есть чем заменить отказавшее), изоляция (сбой не распространяется) и корректная обработка ошибок на каждом вызове (таймауты, ретраи, идемпотентность, деградация).

**1. Избыточность.**

- несколько реплик каждого сервиса в разных зонах доступности;
- репликация данных: PostgreSQL с автоматическим failover, Kafka с RF=3, Redis с репликами;
- запас мощности N+1: потеря одной зоны из трёх не должна перегружать оставшиеся (нужно ~50% запаса на каждую).

**2. Таймауты на всё.** Вызов без таймаута при зависании зависимости держит поток, соединение и память, пока не исчерпаются все ресурсы. Таймаут должен быть меньше таймаута вызывающей стороны: если клиент ждёт 2 с, внутренние вызовы — не более 500–800 ms.

**3. Ретраи — осторожно.** Только для идемпотентных операций и временных ошибок (таймаут, 503, 429); экспоненциальный backoff с jitter; ограниченное число попыток и retry budget, чтобы не устроить лавину.

**4. Circuit breaker.** Если зависимость отвечает ошибками, перестать её вызывать на время и сразу возвращать fallback. В .NET — Polly или `Microsoft.Extensions.Http.Resilience` (`AddStandardResilienceHandler`: таймаут, ретраи, circuit breaker, hedging).

**5. Bulkhead.** Отдельные пулы соединений и лимиты конкурентности на каждую зависимость: медленный сервис рекомендаций не должен съесть все соединения, нужные для оформления заказа.

**6. Асинхронность и буферы.** Критичные записи — через очередь с повторной обработкой; если обработчик упал, сообщение не потеряно. DLQ для сообщений, которые не удаётся обработать.

**7. Graceful degradation.** Для каждой зависимости заранее решить, что будет без неё:

| Зависимость упала | Поведение |
| --- | --- |
| Рекомендации | показать популярное из кэша |
| Redis | идти в БД с ограничением конкурентности |
| Сервис уведомлений | заказ создаётся, письмо уйдёт позже |
| Платёжный провайдер | переключение на резервного или отложенная оплата |

**8. Защита от перегрузки.** Rate limiting, load shedding (отказ быстрым 503 вместо очереди до таймаута), приоритизация критичного трафика.

**9. Проверка.** Chaos engineering (убить под, внести задержку в сеть, отключить зону на стенде или в проде с ограниченным blast radius), game days, регулярная проверка восстановления из бэкапа. Отказоустойчивость, которую никто не проверял, — гипотеза.

## Спроектировать сервис заказов.

```yaml
category: system-design
level: middle
difficulty: 4
slug: system-design-sproektirovat-servis-zakazov
tags: practice
```

Сервис заказов — это владелец жизненного цикла заказа: создание из корзины, фиксация цен, машина состояний (создан → оплачен → собран → доставлен / отменён) и публикация событий для оплаты, склада и доставки. Ядро — PostgreSQL с транзакционной записью заказа и outbox, всё остальное взаимодействует с ним асинхронно через Kafka.

**Требования.**

- функциональные: создать заказ из корзины, получить заказ и историю заказов пользователя, отменить, менять статус по событиям оплаты/склада/доставки;
- нефункциональные: заказ не теряется и не дублируется при повторном клике, создание < 300 ms p99, доступность 99.95%, история статусов для поддержки и аудита.

**Оценка.** 1 млн заказов в день ≈ 12 заказов/с в среднем, пик ×10 — ~120 записей/с. Чтение истории в 10–20 раз чаще — ~2k RPS. Заказ с позициями ~2 КБ → 2 ГБ в день, ~730 ГБ в год. Одна PostgreSQL с репликами справляется годами, шардирование не нужно.

**Компоненты.**

```text
Client → API Gateway → Order API ──► PostgreSQL (orders, order_items, order_status_history, outbox)
                           │                    │
                           ▼                    ▼ outbox relay / Debezium
                  Cart, Pricing (sync)        Kafka: order-events
                                                │
                              Payment, Inventory, Delivery, Notifications
```

**Модель данных.**

```sql
orders(id uuid pk, user_id, status, total_amount, currency,
       idempotency_key unique, version int, created_at, updated_at)
order_items(order_id, product_id, qty, unit_price)   -- цена фиксируется на момент заказа
order_status_history(order_id, from_status, to_status, reason, at)
outbox(id, aggregate_id, type, payload jsonb, created_at, published_at)
```

Индекс `(user_id, created_at desc)` для истории. Цены копируются в `order_items`, а не берутся из каталога при чтении — иначе старый заказ «подорожает».

**Ключевые решения.**

1. **Идемпотентность создания.** Клиент шлёт `Idempotency-Key`; уникальный индекс не даст создать второй заказ при повторе, повтор возвращает уже созданный.
2. **Машина состояний.** Разрешённые переходы описаны в коде, переход — `UPDATE ... WHERE id = @id AND status = @expected`. Событие «оплачено» для отменённого заказа не применяется, а запускает возврат.
3. **Сага оформления.** Заказ создаётся в статусе `pending`, дальше резерв склада и оплата по событиям; при ошибке — компенсации (снять резерв, отменить). Оркестратор удобно сделать на MassTransit state machine.
4. **Outbox.** Запись заказа и события — одна транзакция, публикацию в Kafka делает отдельный процесс; ключ партиции — `order_id`, чтобы события одного заказа шли по порядку.

**Масштабирование и узкие места.** Чтение истории — с реплик и из кэша последних заказов; «мои заказы» не требует строгой свежести. Таблица растёт — партиционирование `orders` по `created_at` по месяцам, старые партиции в архив. При росте на порядки — шардирование по `user_id`, но это не первый шаг.

**Компромиссы.** Асинхронная сага означает, что пользователь сначала видит «заказ принят, ожидает оплаты», а не мгновенный финальный статус — зато падение склада или провайдера оплаты не ломает приём заказов. Синхронно при создании вызываются только проверки, без которых заказ бессмыслен (актуальная цена, наличие).

## Спроектировать сервис корзины.

```yaml
category: system-design
level: middle
difficulty: 4
slug: system-design-sproektirovat-servis-korziny
tags: practice
```

Корзина — это часто изменяемое, небольшое, per-user состояние с высоким чтением и низкой ценой потери отдельной операции. Поэтому основное хранилище — быстрый key-value (Redis с persistence или PostgreSQL с простой схемой), а цены и наличие не хранятся, а подтягиваются при отображении.

**Требования.**

- функциональные: добавить/удалить/изменить количество, посмотреть корзину с актуальными ценами, корзина гостя и слияние при логине, переход в оформление заказа;
- нефункциональные: операции < 100 ms p99, корзина переживает перезапуск и живёт недели, при недоступности каталога корзина всё равно открывается.

**Оценка.** 10 млн DAU, 20% активно работают с корзиной → 2 млн пользователей × ~10 операций = 20 млн операций в день ≈ 230 RPS, пик ×10 — ~2.5k RPS, из них 70–80% чтения. Корзина ~20 позиций × 50 байт ≈ 1 КБ; 30 млн активных корзин ≈ 30 ГБ — влезает в память одного Redis-кластера с запасом.

**Компоненты.**

```text
Client → Cart API ──► Redis (hash cart:{userId} → productId: qty)   TTL 30 дней
            │    └──► PostgreSQL (опционально: долгоживущие корзины, аналитика)
            ├──► Catalog/Pricing API (цены, названия — батчем, с кэшем)
            └──► Inventory API (наличие — только при показе и чекауте)
```

**Модель данных.** Redis hash: `HSET cart:{userId} {productId} {qty}`, отдельный ключ для метаданных (промокод, версия). Добавление — `HINCRBY`, атомарно без гонок между вкладками. Для гостя ключ по `anonymousId` из cookie; при логине слить гостевую корзину в пользовательскую (Lua-скрипт или транзакция `MULTI`), конфликт по количеству — брать максимум.

Если потеря корзины неприемлема или нужен анализ брошенных корзин, источник истины — PostgreSQL (`cart_items(user_id, product_id, qty, added_at)`, PK `(user_id, product_id)`, upsert через `ON CONFLICT`), а Redis — кэш. Выбор зависит от бизнеса: для большинства магазинов Redis с AOF и репликой достаточно.

**Цены и наличие.** В корзине хранится только `product_id` и количество. Цены при отображении запрашиваются батчем у pricing-сервиса; если цена изменилась с момента добавления, показать пометку. Финальная цена и резерв фиксируются только при создании заказа — корзина ничего не гарантирует.

**Узкие места и масштабирование.**

- Cart API stateless, горизонтально масштабируется;
- Redis Cluster шардирует по ключу — корзина одного пользователя в одном слоте, горячих ключей нет;
- основная задержка — вызовы каталога: кэш цен с коротким TTL, таймаут и fallback «цена уточняется»;
- лимиты: не более N позиций и M единиц товара, чтобы боты не создавали гигантские корзины.

**Компромиссы.** Хранение цены в корзине ускорило бы чтение, но создало бы проблему устаревших цен и лишнюю синхронизацию. Redis как единственное хранилище даёт простоту и скорость ценой риска потерять секунды изменений при падении — для корзины это приемлемо, для заказа нет.

## Спроектировать сервис доставки.

```yaml
category: system-design
level: middle
difficulty: 4
slug: system-design-sproektirovat-servis-dostavki
tags: practice
```

Сервис доставки отвечает за всё, что происходит с заказом после оплаты: расчёт стоимости и сроков, выбор способа (курьер, пункт выдачи, внешний перевозчик), создание отправления у перевозчика и ведение его статуса. Это интеграционный сервис: собственная логика простая, а основная сложность — ненадёжные внешние API перевозчиков, поэтому всё общение с ними асинхронное, через очередь задач с ретраями.

**Требования.**

- функциональные: рассчитать варианты доставки для корзины (цена, срок), создать отправление после оплаты заказа, выбрать слот курьера, получать статусы от перевозчиков, отменить/изменить адрес;
- нефункциональные: расчёт < 300 ms p99 (он на странице оформления), отправление создаётся гарантированно, даже если перевозчик лежит час; статусы не теряются и не дублируются.

**Оценка.** 1 млн заказов в день ≈ 12 отправлений/с, пик ×10 — ~120/с. Расчёт стоимости вызывается на каждом открытии чекаута: ~5 расчётов на заказ → 5 млн в день ≈ 60 RPS, пик ~600 RPS. Отправление со статусами ~3 КБ → 3 ГБ в день, ~1 ТБ в год — PostgreSQL с партиционированием по месяцам.

**Компоненты.**

```text
Checkout ──► Delivery API ── quote ──► тарифы/зоны (PostgreSQL + кэш в памяти)
                  │
Kafka: order-paid ──► Shipment Worker ──► Carrier Adapters (СДЭК, Boxberry, свои курьеры)
                  │                              │
                  ▼                              ▼ webhooks / polling
             PostgreSQL (shipments, events, outbox) ──► Kafka: shipment-events ──► Order, Notifications
```

**Модель данных.**

```sql
shipments(id, order_id unique, carrier, carrier_tracking_no, status,
          address jsonb, slot_from, slot_to, cost, version, created_at)
shipment_events(shipment_id, status, carrier_event_id, occurred_at,
                unique (carrier, carrier_event_id))
delivery_tariffs(carrier, zone_id, weight_from, weight_to, price, days_min, days_max)
```

`unique(order_id)` защищает от двойного создания отправления при повторной доставке события `order-paid`. Уникальность `carrier_event_id` делает приём вебхуков идемпотентным.

**Ключевые решения.**

1. **Расчёт стоимости — локально.** Тарифы перевозчиков синхронизируются в свою таблицу раз в сутки и кэшируются в памяти; онлайн-вызов перевозчика на чекауте даёт и латентность, и зависимость от его доступности. Онлайн-расчёт — только если тариф динамический, с таймаутом 1 с и fallback на табличный.
2. **Создание отправления — через outbox и воркер.** Событие оплаты → запись `shipment(status=pending)` → воркер вызывает API перевозчика с ретраями и backoff. Перевозчик лежит — заказ ждёт в `pending`, алерт при возрасте > 30 минут.
3. **Адаптеры перевозчиков.** Общий интерфейс `ICarrier` (Quote, CreateShipment, Cancel, MapStatus), свои статусы перевозчика маппятся на внутренние. Новый перевозчик — новый адаптер, остальная система не меняется.
4. **Статусы.** Вебхуки принимаются тонким эндпоинтом, кладутся в Kafka и сразу возвращают 200; для перевозчиков без вебхуков — polling активных отправлений. Переходы монотонны: «доставлено» нельзя перезаписать опоздавшим «в пути».
5. **Слоты курьеров.** Ёмкость слота — счётчик в PostgreSQL, бронирование `UPDATE slots SET booked = booked + 1 WHERE id = @id AND booked < capacity`.

**Узкие места.** Rate limits перевозчиков — отдельная очередь и лимит конкурентности на каждого (bulkhead), чтобы медленный СДЭК не тормозил остальных. Polling тысяч отправлений — батчами и только для незавершённых.

**Компромиссы.** Табличный расчёт может разойтись с реальной ценой перевозчика на несколько процентов — это цена независимости чекаута от внешних API; расхождения ловит ежедневная сверка счетов перевозчика.

## Спроектировать notification service.

```yaml
category: system-design
level: middle
difficulty: 4
slug: system-design-sproektirovat-notification-service
tags: practice
```

Notification service принимает от других сервисов запрос «уведомить пользователя о событии X», сам решает канал (push, email, SMS, in-app) по настройкам пользователя, рендерит шаблон и отправляет через внешних провайдеров. Архитектура — асинхронный конвейер на очередях: приём быстрый и надёжный, отправка с ретраями и лимитами на каждого провайдера.

**Требования.**

- функциональные: API/событие «отправить уведомление», шаблоны с локализацией, пользовательские настройки (каналы, отписки, тихие часы), история отправок, in-app лента;
- нефункциональные: уведомление не теряется, не дублируется при ретраях (повторное SMS стоит денег и раздражает), транзакционные (код входа) — секунды, маркетинговые — минуты.

**Оценка.** 10 млн DAU × 5 уведомлений = 50 млн в день ≈ 580/с, пик ×5 — ~3k/с. Каждое уведомление с логом доставки ~1 КБ → 50 ГБ в день; история нужна 90 дней → ~4.5 ТБ, это уже повод хранить лог не в основной PostgreSQL (партиции по дням с drop старых или ClickHouse/Cassandra).

**Компоненты.**

```text
Сервисы ──► Kafka: notification-requests
                 │
                 ▼
         Dispatcher: настройки пользователя, дедупликация, шаблон, выбор каналов
                 │
     ┌───────────┼────────────┬──────────────┐
     ▼           ▼            ▼              ▼
  push-queue  email-queue  sms-queue     in-app (PostgreSQL / Redis)
     │           │            │
  Push Worker  Email Worker  SMS Worker ──► FCM/APNs, SMTP-провайдер, SMS-шлюз
                                    │
                         delivery_log + статусы от провайдеров (webhooks)
```

**Модель данных.**

- `notification_requests(id, idempotency_key unique, user_id, type, payload, created_at)`;
- `deliveries(request_id, channel, status, provider_message_id, attempts, sent_at)`;
- `user_preferences(user_id, type, channel, enabled)`, `device_tokens(user_id, token, platform)`;
- `templates(type, channel, locale, body, version)`.

**Ключевые решения.**

1. **Отдельная очередь на канал.** Упавший SMS-шлюз не блокирует email и push; у каждого канала свои ретраи и лимиты скорости провайдера.
2. **Идемпотентность.** Продюсер передаёт `idempotency_key` (например, `order-123:shipped`), дубликат отбрасывается. Перед вызовом провайдера проверяется статус доставки — повторно уже отправленное не шлётся.
3. **Ретраи.** Экспоненциальный backoff, после N попыток — DLQ и, если уместно, fallback на другой канал (push не дошёл → email).
4. **Настройки и тихие часы** проверяются в dispatcher до разбиения на каналы; отложенные уведомления — в delay-очередь или таблицу запланированных.
5. **Невалидные токены** (ответ FCM `UNREGISTERED`) сразу удаляются, иначе растут бесполезные ретраи.

**Узкие места.** Лимиты внешних провайдеров (SMS-шлюз 100 сообщений/с) — token bucket на воркере. Массовая рассылка не должна задерживать код подтверждения — транзакционные и маркетинговые уведомления в разных топиках.

**Компромиссы.** At-least-once в очередях плюс дедупликация дают «почти exactly-once»: при падении воркера между вызовом провайдера и записью статуса дубль всё же возможен. Для SMS с кодами это приемлемо, полностью исключить его без поддержки идемпотентности у провайдера нельзя.

## Спроектировать URL shortener.

```yaml
category: system-design
level: middle
difficulty: 4
slug: system-design-sproektirovat-url-shortener
tags: practice
```

URL shortener — это key-value хранилище «короткий код → длинный URL» с крайне перекошенной нагрузкой: чтений (редиректов) в сотни раз больше, чем записей. Ключевые решения — как генерировать уникальные короткие коды без коллизий и как отдавать редиректы из кэша за миллисекунды.

**Требования.**

- функциональные: создать короткую ссылку (опционально — свой alias и срок жизни), редирект по ней, статистика переходов;
- нефункциональные: редирект < 20 ms p99, доступность выше, чем у создания (сломанные ссылки в рассылках хуже, чем временная невозможность создать новую), коды не угадываются перебором подряд.

**Оценка.**

- 100 млн новых ссылок в месяц ≈ 3.3 млн в день ≈ 40 записей/с;
- чтение:запись = 100:1 → ~4k редиректов/с, пик ×5 — 20k RPS;
- за 5 лет: 100 млн × 60 = 6 млрд ссылок × ~500 байт = 3 ТБ;
- длина кода: base62, 7 символов = 62⁷ ≈ 3.5 трлн комбинаций — запас в сотни раз над 6 млрд.

**Генерация кода — главный вопрос.**

| Способ | Плюсы | Минусы |
| --- | --- | --- |
| Хэш URL (MD5 → первые 7 символов base62) | одинаковые URL дают одинаковый код | коллизии, нужна проверка и повтор |
| Счётчик + base62 | без коллизий, коротко | коды идут подряд и перебираются; единый счётчик — точка синхронизации |
| Диапазоны ID: каждый инстанс берёт блок по 10 000 из PostgreSQL-sequence | без коллизий, без координации на каждый запрос | при рестарте теряется остаток блока (не страшно) |
| Случайные 7–8 символов + `INSERT` с уникальным ключом | неугадываемо, просто | редкие коллизии → повтор вставки |

Практичный выбор — случайный код с повтором при конфликте уникального индекса (при заполненности < 0.1% вероятность коллизии ничтожна) или диапазоны ID с перемешиванием (например, обратимое шифрование числа), если нужна гарантия без повторов.

**Компоненты.**

```text
Client ──► LB ──► Redirect API ──► Redis (code → url, LRU) ──miss──► хранилище
                       │
                       └─► Kafka: click-events ──► аналитика (ClickHouse)

Client ──► Create API ──► хранилище (urls)
```

**Хранилище.** Схема тривиальная: `urls(code pk, long_url, user_id, expires_at, created_at)`. 3 ТБ и 20k RPS чтения при кэше с hit rate 90%+ спокойно держит PostgreSQL с репликами, партиционированный по hash кода; при больших объёмах естественно ложится на Cassandra/DynamoDB — доступ только по ключу, транзакции не нужны.

**Редирект.** `301` кэшируется браузером навсегда — меньше нагрузки, но теряется статистика и возможность изменить ссылку; `302` — каждый переход идёт через сервис. Обычно выбирают 302, если важна аналитика.

**Узкие места.**

- популярные ссылки — кэш в Redis и локальный in-memory кэш на инстансе, можно отдавать редирект с CDN edge;
- запись статистики синхронно удвоила бы латентность — клики уходят в Kafka асинхронно, агрегируются батчами;
- злоупотребления: rate limit на создание, проверка URL по спискам фишинга.

**Компромиссы.** Пользовательские alias ломают равномерность и требуют проверки занятости, но решаются тем же уникальным индексом. Удаление истёкших ссылок — фоновая чистка, а не проверка на каждом чтении.

## Спроектировать file storage service.

```yaml
category: system-design
level: middle
difficulty: 4
slug: system-design-sproektirovat-file-storage-service
tags: practice
```

File storage service разделяет две вещи: метаданные (кто владелец, имя, папка, права, версии) лежат в PostgreSQL, а сами байты — в S3-совместимом объектном хранилище. Сервис почти никогда не пропускает содержимое файлов через себя: клиент загружает и скачивает напрямую из хранилища по presigned URL, а API только выдаёт разрешения и ведёт учёт.

**Требования.**

- функциональные: загрузка (в том числе больших файлов с докачкой), скачивание, папки, шаринг по ссылке и пользователям, версии, удаление в корзину;
- нефункциональные: файл, получивший подтверждение загрузки, не теряется; файлы до 5 ГБ; скачивание без ограничения скоростью API-серверов.

**Оценка.** 1 млн DAU × 2 загрузки × 500 КБ в среднем = 1 ТБ в день, ~365 ТБ в год. 2 млн загрузок в день ≈ 23/с, скачиваний ×5 — ~115/с. Трафик скачивания 5 ТБ/день ≈ 58 МБ/с ≈ 460 Мбит/с в среднем, пик ×3 ~1.4 Гбит/с — именно поэтому байты не должны идти через API. Метаданные: ~1 КБ на файл × 730 млн файлов в год ≈ 730 ГБ — одна PostgreSQL с партиционированием.

**Компоненты.**

```text
Client ──1. init upload──► File API ──► PostgreSQL (files status=pending)
   │                          └── presigned PUT / multipart URLs
   ├──2. PUT parts──────────────────────────────────► S3
   └──3. complete──────────► File API ──► S3 CompleteMultipartUpload, status=ready
                                  │
                                  └─► Kafka: file-uploaded ──► антивирус, превью, индексация

Скачивание: File API проверяет права ──► presigned GET (или подписанный CDN URL)
```

**Модель данных.**

```sql
files(id, owner_id, folder_id, name, size, content_type, sha256,
      storage_key, status, current_version, deleted_at, created_at)
file_versions(file_id, version, storage_key, size, created_at)
shares(file_id, grantee_id null, token unique null, permission, expires_at)
```

`storage_key` — сгенерированный путь вида `{tenant}/{yyyy}/{mm}/{uuid}`, а не пользовательское имя: переименование и перемещение меняют только метаданные.

**Ключевые решения.**

1. **Multipart upload.** Файл режется на части по 8–64 МБ, каждая грузится отдельно и повторяется при обрыве; после `complete` S3 собирает объект. Незавершённые загрузки удаляет lifecycle-правило через сутки.
2. **Статус `pending` → `ready`.** Файл виден пользователю только после подтверждения; фоновая задача чистит `pending` старше суток, чтобы не было «сирот» в S3 без записи в БД и наоборот.
3. **Обработка после загрузки** асинхронна: проверка антивирусом, превью, извлечение текста. До проверки файл можно не раздавать по публичной ссылке.
4. **Удаление** — сначала soft delete (корзина 30 дней), физическое удаление объекта — фоновой задачей.

**Масштабирование.** API stateless; S3 масштабируется сам; горячие публичные файлы — через CDN. Метаданные при росте шардируются по `owner_id`, поскольку почти все запросы — в пределах одного пользователя.

**Компромиссы.** Presigned URL нельзя отозвать до истечения — поэтому срок короткий (минуты). Дедупликация по `sha256` экономит место, но усложняет удаление (нужен подсчёт ссылок) и раскрывает факт наличия файла у других — для пользовательских данных её часто не делают.

## Спроектировать систему обработки платежей.

```yaml
category: system-design
level: middle
difficulty: 4
slug: system-design-sproektirovat-sistemu-obrabotki-platezhei
tags: practice
```

Платёжный сервис — это прослойка между заказами и внешними платёжными провайдерами (эквайрингом): он создаёт платёж, ведёт его через машину состояний, принимает результаты от провайдера и записывает каждое движение денег в журнал. Нагрузка обычно небольшая, а главное — корректность: ни одного двойного списания, ни одного «потерянного» платежа и регулярная сверка с провайдером.

**Требования.**

- функциональные: оплатить заказ (карта, СБП, кошелёк), 3-D Secure, возврат полный и частичный, статус платежа, несколько провайдеров;
- нефункциональные: идемпотентность на всех уровнях, аудит каждого изменения, данные карт не хранятся у нас (PCI DSS выносится на провайдера через токенизацию или платёжную форму), доступность 99.95%.

**Оценка.** 1 млн платежей в день ≈ 12/с, пик распродажи ×20 — ~250/с. Платёж с историей событий ~2 КБ → 2 ГБ в день, ~730 ГБ в год. Узкое место не объём, а латентность провайдера (1–5 с на авторизацию) и его доступность.

**Компоненты.**

```text
Order Service ──► Payment API ──► PostgreSQL (payments, payment_events, ledger, outbox)
                       │
                       ├──► Provider Adapter A / B ──► эквайринг
                       │           ▲
                       │           └── webhooks (результат 3DS, асинхронные статусы)
                       └──► Kafka: payment-events ──► Order, Notifications, Accounting

Reconciliation job: ежедневный реестр провайдера ⇄ наши записи
```

**Модель данных.**

```sql
payments(id, order_id, amount, currency, status, provider, provider_payment_id,
         idempotency_key unique, version, created_at)
payment_events(payment_id, type, provider_event_id unique, raw jsonb, at)
ledger_entries(id, payment_id, account, debit, credit, at)
```

Суммы — в минимальных единицах (`bigint` копеек) или `numeric`, никогда не `float`.

**Машина состояний.**

```text
created ──► pending (ушёл к провайдеру) ──► requires_action (3DS) ──► authorized ──► captured
   │                 │                                                   │
   └──► failed ◄─────┘                                         refunded / partially_refunded
```

Переход — `UPDATE ... WHERE id = @id AND status = @expected`; недопустимые переходы (вебхук «успех» для уже отменённого платежа) не применяются, а уходят в ручной разбор или автоматический возврат.

**Ключевые решения.**

1. **Идемпотентность.** `Idempotency-Key` от Order Service на создание; провайдеру передаётся наш `payment_id` как его ключ идемпотентности; вебхуки дедуплицируются по `provider_event_id`.
2. **Неизвестный исход.** Таймаут от провайдера — это не ошибка: платёж остаётся `pending`, фоновая задача запрашивает его статус у провайдера, пока не получит финальный.
3. **Двухфазная оплата.** Authorize при заказе, capture при отгрузке — деньги заморожены, но списываются, только когда товар есть.
4. **Ledger.** Неизменяемый журнал двойной записи; баланс и отчёты считаются из него, ошибки исправляются сторнирующими записями.
5. **Сверка.** Ежедневно сравнить реестр провайдера с нашими платежами: расхождения (у нас failed, у провайдера списано) автоматически корректируются или идут на ручной разбор.

**Масштабирование.** Нагрузка небольшая — одна PostgreSQL с синхронной репликой. Важнее изоляция: отдельные пулы соединений и circuit breaker на каждого провайдера, переключение на резервного провайдера при деградации основного.

**Компромиссы.** Асинхронность платежей усложняет UX («платёж обрабатывается»), но синхронное ожидание провайдера в HTTP-запросе клиента при его сбоях приводит к повторным нажатиям и дублям.

## Спроектировать систему рекомендаций.

```yaml
category: system-design
level: middle
difficulty: 4
slug: system-design-sproektirovat-sistemu-rekomendacii
tags: practice
```

Система рекомендаций почти всегда двухконтурная: тяжёлые модели обучаются и считают кандидатов офлайн (раз в час–сутки), а онлайн-сервис за десятки миллисекунд достаёт готовые кандидаты, отфильтровывает лишнее и переранжирует с учётом свежих действий пользователя. Задача бэкенда — не сама ML-модель, а конвейер данных, хранение предрасчётов и быстрая отдача с fallback.

**Требования.**

- функциональные: «рекомендуем вам» на главной, «похожие товары» на карточке, «с этим покупают» в корзине; учёт недавних действий; исключение купленного и отсутствующего;
- нефункциональные: ответ < 100 ms p99; страница не ломается, если рекомендации недоступны; свежие действия учитываются за минуты, а не за сутки.

**Оценка.** 10 млн DAU × 20 показов блоков = 200 млн запросов в день ≈ 2.3k RPS, пик ×4 — ~10k RPS. Предрасчёт: 100 товаров на пользователя × 8 байт ID ≈ 800 байт; 50 млн пользователей ≈ 40 ГБ — помещается в Redis-кластер. «Похожие товары»: 1 млн товаров × 50 соседей ≈ 400 МБ.

**Компоненты.**

```text
Клиенты ──► события (просмотр, клик, покупка) ──► Kafka: user-events
                                                    │
                    ┌───────────────────────────────┼───────────────────────┐
                    ▼                               ▼                       ▼
             Data lake (S3, Parquet)       Stream job: недавние       ClickHouse
                    │                       действия → Redis           (метрики CTR)
                    ▼
       Offline training + batch scoring (Spark/Python, раз в сутки)
                    │
                    ▼
       Redis: rec:{userId} → [itemIds], similar:{itemId} → [itemIds]
                    │
Client ──► Recommendation API (.NET): кандидаты → фильтры → лёгкое переранжирование → ответ
```

**Конвейер ответа.**

1. **Candidate generation** — объединить несколько источников: персональный предрасчёт, похожие на недавно просмотренные, популярное в категории.
2. **Фильтрация** — убрать купленное, нет в наличии, скрытое пользователем (наличие — из кэша склада).
3. **Ранжирование** — лёгкая модель или правила поверх признаков (свежесть, маржа, разнообразие категорий); тяжёлая нейросеть онлайн нужна не всегда.
4. **Логирование показов** с `request_id` — без этого не посчитать CTR и не обучить следующую модель.

**Ключевые решения.**

- Алгоритмы начального уровня: item-to-item collaborative filtering («купившие X купили Y»), матричная факторизация (ALS), для холодного старта — популярное и контентная похожесть по атрибутам.
- Холодный старт пользователя: популярное в регионе плюс быстрый учёт первых кликов из потокового контура.
- A/B-тесты обязательны: изменение модели оценивается по CTR и конверсии, а не офлайн-метрикам.

**Узкие места и деградация.** Если Redis или API недоступны — отдать заранее посчитанный список популярного из локального кэша, блок на странице не должен падать. Таймаут вызова рекомендаций со страницы — 100–150 ms.

**Компромиссы.** Офлайн-предрасчёт дешёв и быстр, но устаревает; потоковый контур добавляет свежесть ценой сложности. Начинать стоит с batch + простого потокового учёта последних просмотров — это даёт большую часть эффекта.

## Спроектировать сервис отслеживания посылок.

```yaml
category: system-design
level: middle
difficulty: 4
slug: system-design-sproektirovat-servis-otslezhivaniya-posylok
tags: practice
```

Сервис отслеживания собирает события о посылке из разных источников (сканеры на складах, курьерские приложения, внешние перевозчики), нормализует их в единый формат, хранит историю и отдаёт клиенту текущий статус и хронологию по трек-номеру. Это append-only поток событий с простым чтением по ключу — записи независимы, поэтому система хорошо масштабируется.

**Требования.**

- функциональные: приём событий (API, вебхуки, файлы от перевозчиков), страница трекинга по номеру, история статусов, уведомления о смене статуса;
- нефункциональные: событие не теряется, дубликаты не создают лишних записей и уведомлений, статус на странице обновляется в течение минуты, порядок событий корректен даже при опоздавших данных.

**Оценка.** 500 тыс. посылок в день × 8 событий = 4 млн событий в день ≈ 46/с, пик ×5 — ~250/с. Событие ~300 байт → 1.2 ГБ в день, ~440 ГБ в год. Чтение: каждую посылку проверяют ~10 раз → 5 млн запросов в день ≈ 60 RPS, пик ~500 RPS. Это нагрузка для одной PostgreSQL.

**Компоненты.**

```text
Сканеры / курьеры ──► Ingest API ─┐
Перевозчики (webhooks, polling) ──┼──► Kafka: tracking-raw (key = tracking_no)
Файлы реестров (SFTP) ──► parser ─┘              │
                                                 ▼
                              Normalizer: маппинг статусов, дедупликация
                                                 │
                         ┌───────────────────────┼─────────────────────┐
                         ▼                       ▼                     ▼
               PostgreSQL: events,      Redis: текущий статус    Kafka: status-changed
               parcels(current_status)   (кэш страницы)                │
                                                                 Notifications
Client ──► Tracking API ──► Redis ──miss──► PostgreSQL
```

**Модель данных.**

```sql
parcels(tracking_no pk, order_id, carrier, current_status, current_status_at, eta)
tracking_events(id, tracking_no, status, location, occurred_at, received_at,
                source, source_event_id, unique (source, source_event_id))
```

Индекс `(tracking_no, occurred_at)` для истории. Таблица событий — партиции по месяцу `received_at`.

**Ключевые решения.**

1. **Ключ партиции Kafka — трек-номер.** Все события одной посылки обрабатывает один консьюмер по порядку, без гонок при обновлении текущего статуса.
2. **Дедупликация** — уникальный индекс по `(source, source_event_id)`; у источников без ID — хэш от `(tracking_no, status, occurred_at)`.
3. **Опоздавшие события.** Хронология сортируется по `occurred_at` (когда случилось), а не по времени получения. Текущий статус обновляется, только если событие новее текущего: `UPDATE parcels SET ... WHERE tracking_no = @n AND current_status_at < @occurredAt`.
4. **Нормализация.** У каждого перевозчика десятки своих кодов — таблица маппинга на 8–10 внутренних статусов; неизвестный код сохраняется как сырой и попадает в алерт.

**Узкие места.** Перевозчики без вебхуков требуют polling — опрашивать только незавершённые посылки, с частотой по стадии (в пути — раз в час, на выдаче — чаще). Всплески после выгрузки реестров перевозчиком сглаживает Kafka.

**Компромиссы.** Хранение текущего статуса отдельно от истории — денормализация, но она делает чтение страницы одним запросом по ключу. Секундная свежесть не нужна: обновление через кэш с TTL 30–60 с снижает нагрузку в разы.

## Спроектировать систему массовой рассылки.

```yaml
category: system-design
level: middle
difficulty: 4
slug: system-design-sproektirovat-sistemu-massovoi-rassylki
tags: practice
```

Массовая рассылка — это пакетная задача «отправить сообщение N миллионам получателей» с ограничениями, которых нет у транзакционных уведомлений: лимиты скорости провайдеров, репутация домена отправителя, обязательная проверка отписок и возможность остановить кампанию на полпути. Архитектура: кампания режется на батчи, батчи идут через очередь к воркерам с контролем скорости, каждая отправка учитывается, чтобы рестарт не отправил письмо дважды.

**Требования.**

- функциональные: кампания (шаблон, сегмент аудитории, время старта), персонализация, пауза/отмена, учёт отписок, статистика (доставлено, открыто, клики, отказы);
- нефункциональные: 10 млн писем за 2 часа, никто не получает письмо дважды, отписавшийся — ни одного, транзакционные письма не тормозят из-за рассылки.

**Оценка.** 10 млн за 2 часа = 10 000 000 / 7200 ≈ 1 400 писем/с. Письмо после рендеринга ~30 КБ → 1 400 × 30 КБ ≈ 42 МБ/с исходящего трафика к SMTP-провайдеру. Учёт отправок: 10 млн строк × 100 байт = 1 ГБ на кампанию.

**Компоненты.**

```text
Admin UI ──► Campaign API ──► PostgreSQL (campaigns, campaign_recipients)
                                   │
                Planner: выборка сегмента курсором, батчи по 1 000
                                   │
                         Kafka / RabbitMQ: send-batches
                                   │
               Send Workers: отписки → рендер → rate limiter → ESP/SMTP
                                   │
           Webhooks провайдера (bounce, complaint, open, click) ──► статистика, suppression list
```

**Ключевые решения.**

1. **Материализация аудитории.** Перед стартом сегмент фиксируется в `campaign_recipients(campaign_id, user_id, status)` с PK `(campaign_id, user_id)` — это и гарантия «не больше одного письма на человека», и точка возобновления после сбоя.
2. **Идемпотентная отправка.** Воркер переводит строку `pending → sending` атомарным `UPDATE ... WHERE status = 'pending'` и пишет `sent` после ответа провайдера. Строки, зависшие в `sending`, после рестарта проверяются отдельно, а не отправляются вслепую.
3. **Rate limiting.** Общий лимит провайдера и лимиты на домены получателей (Gmail, Mail.ru по-разному режут всплески) — token bucket в Redis. Новый IP/домен требует прогрева: объём наращивается за дни.
4. **Suppression list.** Отписки, hard bounce и жалобы на спам проверяются непосредственно перед отправкой, а не только при построении сегмента — человек мог отписаться час назад.
5. **Пауза и отмена.** Воркер перед каждым батчем проверяет статус кампании (кэш с TTL несколько секунд) — остановка срабатывает почти мгновенно.
6. **Изоляция.** Отдельные очереди, воркеры и, желательно, отдельные IP/субдомены для маркетинга и транзакционных писем: жалобы на рассылку не должны ронять доставку кодов подтверждения.

**Узкие места.** Выборка сегмента из 10 млн — курсором по PK батчами, а не `OFFSET`; рендер шаблонов — CPU, масштабируется числом воркеров; провайдер — реальный предел скорости.

**Компромиссы.** Отправка «как можно быстрее» упирается в репутацию: письма уходят в спам. Растянуть кампанию на несколько часов с равномерной скоростью обычно выгоднее, чем выиграть 30 минут.

## Спроектировать систему обработки 10 000+ RPS.

```yaml
category: system-design
level: middle
difficulty: 4
slug: system-design-sproektirovat-sistemu-obrabotki-10-000-rps
tags: scalability, practice
```

10 000 RPS — это нагрузка, которую выдерживает обычная архитектура «stateless API за балансировщиком + кэш + PostgreSQL с репликами», если не делать глупостей: не ходить в БД на каждый запрос, держать пулы соединений под контролем и выносить тяжёлое в асинхронную обработку. Начинать нужно с уточнения, что это за запросы: 10k чтений и 10k записей в секунду — разные задачи.

**Уточнить требования.** Пусть 10k RPS в пике, 90% чтение (каталог, профиль, статусы), 10% запись (≈1k RPS), латентность p99 < 200 ms, доступность 99.9%.

**Оценка.**

- .NET-сервис на Kestrel с запросом «кэш + иногда БД» держит 1–3k RPS на под с 2 vCPU. Нужно ~5–10 подов; закладываем 15 — для запаса на потерю зоны и всплесков.
- При hit rate кэша 90% в БД доходит 9k × 0.1 = 900 чтений/с + 1k записей/с — комфортно для PostgreSQL на хорошем железе (одна запись — миллисекунды, без тяжёлых JOIN).
- Трафик: 10k × 5 КБ ответа = 50 МБ/с ≈ 400 Мбит/с — без проблем для балансировщика.

**Архитектура.**

```text
Clients ──► CDN (статика, публичные GET) ──► L7 LB / Ingress
                                                │
                                   API pods (stateless, HPA по CPU/RPS)
                         ┌──────────────┬───────┴──────┬──────────────────┐
                         ▼              ▼              ▼                  ▼
               in-memory cache   Redis cluster   PgBouncer ──► PostgreSQL   Kafka ──► workers
               (горячие ключи)   (общий кэш)        primary + 2 replicas    (тяжёлая обработка)
```

**Что важно сделать.**

1. **Кэширование в два уровня.** Локальный `IMemoryCache` на секунды для самых горячих ключей + Redis для общего кэша. Публичные GET — `Cache-Control` и CDN, такие запросы вообще не доходят до API.
2. **Пул соединений.** 15 подов × пул 100 = 1500 соединений — больше, чем стоит держать в PostgreSQL. PgBouncer в transaction mode сводит их к ~100 реальным.
3. **Чтение с реплик** для запросов, терпящих задержку репликации в доли секунды.
4. **Асинхронная запись тяжёлого.** Запрос пишет минимально необходимое и публикует событие; пересчёты, письма, интеграции — воркеры из Kafka. Ответ API не ждёт побочных эффектов.
5. **Эффективный код.** `async` везде, без sync-over-async, проекции вместо загрузки целых сущностей, `AsNoTracking`, индексы под реальные запросы, пагинация курсором.
6. **Защита.** Rate limiting по клиенту, таймауты на все вызовы, circuit breaker на внешние зависимости, лимит конкурентности — лишние запросы получают быстрый 429/503.

**Вероятные узкие места** — в порядке появления: медленные запросы к БД (видно в `pg_stat_statements`), исчерпание соединений, горячий ключ в Redis, GC-паузы при больших аллокациях, внешняя зависимость без таймаута.

**Проверка.** Нагрузочный тест (k6, NBomber) на 1.5–2× от целевой нагрузки с реалистичным профилем запросов, мониторинг p99 и насыщения ресурсов. Цифры «держит 2k RPS на под» нужно получить замером, а не предполагать.

**Компромиссы.** Кэш даёт кратный выигрыш ценой устаревания данных и проблем инвалидации. Шардирование БД на 10k RPS обычно преждевременно — оно добавляет сложность, а реплики и кэш закрывают нагрузку.

## Спроектировать сервис с Kafka.

```yaml
category: system-design
level: middle
difficulty: 4
slug: system-design-sproektirovat-servis-s-kafka
tags: kafka, practice
```

Проектирование сервиса с Kafka сводится к нескольким решениям: какие топики и события, какой ключ партиционирования (он определяет порядок и параллелизм), сколько партиций, как продюсер надёжно публикует (outbox), как консьюмер обрабатывает без потерь и дублей (commit после обработки + идемпотентность) и что делать с «ядовитыми» сообщениями (retry-топики и DLQ).

**Пример.** Сервис заказов публикует события, сервисы склада, оплаты и уведомлений их потребляют.

**1. Топики и события.**

- топик на агрегат: `orders.events` с типами `OrderCreated`, `OrderPaid`, `OrderCancelled`;
- события — факты в прошедшем времени с `event_id`, `occurred_at`, `order_id`, версией схемы;
- схема — Avro/Protobuf со Schema Registry или JSON с контрактными тестами; изменения только обратно совместимые (добавлять необязательные поля).

**2. Ключ и партиции.** Ключ = `order_id`: все события одного заказа в одной партиции, порядок гарантирован. Число партиций = параллелизм консьюмеров. Оценка: пик 2k событий/с, консьюмер обрабатывает ~200/с на партицию (есть запрос в БД) → минимум 10 партиций, берём 24–32 с запасом на рост — увеличить потом можно, но это сломает соответствие ключ → партиция.

**3. Надёжная публикация.** Запись заказа и события — в одной транзакции PostgreSQL через таблицу `outbox`; relay (фоновый `BackgroundService` или Debezium) публикует в Kafka. Продюсер: `acks=all`, `enable.idempotence=true`; топик: `replication.factor=3`, `min.insync.replicas=2`.

**4. Консьюмер.**

```text
poll ─► обработать ─► (в одной транзакции БД: изменение данных + запись event_id в inbox) ─► commit offset
```

- `enable.auto.commit=false`, коммит после успешной обработки — at-least-once;
- дубликаты отсекаются таблицей `inbox(event_id pk)` или идемпотентной операцией (upsert, переход статуса с проверкой текущего);
- обработка внутри партиции последовательная; для параллелизма — больше партиций и инстансов в consumer group, а не потоки внутри без учёта ключа.

**5. Ошибки.**

| Тип ошибки | Действие |
| --- | --- |
| временная (БД, сеть) | ретрай с backoff на месте, не коммитя offset |
| постоянная после N попыток | отправить в `orders.events.retry.5m` / `.retry.1h`, потом в `orders.events.dlq` |
| невалидное сообщение | сразу в DLQ с причиной в заголовках |

Ретраи в отдельных топиках не блокируют партицию, но нарушают порядок для этого ключа — для событий одного заказа это приходится учитывать (например, проверкой версии).

**6. Эксплуатация.** Метрики consumer lag по группе и партиции (алерт на рост), размер DLQ, время обработки. Retention топика — 7 дней, чтобы можно было перечитать после бага, сдвинув offset.

**В .NET** — `Confluent.Kafka` напрямую или MassTransit/KafkaFlow поверх, которые дают retry, DLQ и сериализацию из коробки.

**Компромиссы.** Exactly-once у Kafka есть только в цепочке Kafka → Kafka (транзакции); с внешней БД реальная гарантия — at-least-once + идемпотентность. Больше партиций — больше параллелизма, но дольше ребалансировка и больше нагрузки на брокеры.

## Спроектировать систему с PostgreSQL + Redis + Kafka.

```yaml
category: system-design
level: middle
difficulty: 4
slug: system-design-sproektirovat-sistemu-s-postgresql-redis-kafka
tags: kafka, caching, practice
```

В такой системе у каждого компонента одна чёткая роль: PostgreSQL — источник истины и транзакции, Redis — быстрый производный слой (кэш, счётчики, лимиты, блокировки), Kafka — надёжная доставка изменений другим сервисам и асинхронная обработка. Главная сложность — не сами технологии, а согласованность между ними: данные в Redis и событиях Kafka всегда производные от PostgreSQL и должны выводиться из него, а не писаться параллельно.

**Пример.** Маркетплейс: каталог товаров и заказы. 5k RPS чтения карточек, 200 RPS записей (заказы, изменения цен).

**Распределение ролей.**

| Компонент | Что хранит / делает | Что НЕ делает |
| --- | --- | --- |
| PostgreSQL | товары, цены, остатки, заказы, outbox | не обслуживает каждое чтение карточки |
| Redis | кэш карточек, сессии, rate limit, распределённые блокировки, счётчики просмотров | не единственное хранилище важных данных |
| Kafka | события `product-changed`, `order-created`, поток в поиск и аналитику | не используется как БД для запросов «дай заказ по ID» |

**Поток записи.**

```text
API ──BEGIN──► UPDATE products ...; INSERT INTO outbox ... ──COMMIT──► PostgreSQL
                                                                         │
                                       outbox relay / Debezium (CDC) ────┘
                                                   ▼
                                       Kafka: product-changed (key = product_id)
                                 ┌─────────────────┼──────────────────────┐
                                 ▼                 ▼                      ▼
                       cache invalidator   search indexer (OpenSearch)   analytics
                       DEL product:{id}
```

Запись в Kafka напрямую из API после коммита — это dual write: упал процесс между коммитом и публикацией — событие потеряно. Outbox делает публикацию гарантированной.

**Поток чтения — cache-aside.**

```text
GET /products/42 ─► Redis GET product:42 ─hit─► ответ
                          └─miss─► PostgreSQL (реплика) ─► SET product:42 EX 600 ─► ответ
```

Инвалидация — удаление ключа по событию из Kafka плюс TTL как страховка, если событие задержалось или потерялось. Удалять, а не перезаписывать: два параллельных обновления могут записать в кэш значения в неправильном порядке.

**Где Redis — не кэш.**

- rate limiting (`INCR` + `EXPIRE`) — потеря данных при падении означает лишь сброс лимитов;
- счётчики просмотров — копятся в Redis, раз в минуту сбрасываются в PostgreSQL батчем;
- блокировки для фоновых задач — с TTL и fencing token, если важна корректность (иначе только как оптимизация).

**Отказы.**

| Упал | Что происходит | Поведение системы |
| --- | --- | --- |
| Redis | промахи кэша | чтение из PostgreSQL с лимитом конкурентности, rate limit временно in-memory |
| Kafka | события не уходят | outbox копит записи, после восстановления relay догоняет; запись заказов продолжается |
| PostgreSQL | нет записи | чтение карточек из кэша, запись — 503; это единственная действительно критичная зависимость |

**Масштабирование.** Чтения — Redis и реплики; записи — PostgreSQL вертикально, затем партиционирование; консьюмеры — партиции Kafka. Каждый компонент масштабируется независимо.

**Компромиссы.** Три технологии — три кластера в эксплуатации, мониторинге и бэкапах. Для 200 RPS можно начать с одной PostgreSQL: `LISTEN/NOTIFY` или outbox с polling вместо Kafka, `IMemoryCache` вместо Redis. Добавлять компоненты стоит, когда появляется конкретная нагрузка или потребитель.

## Что произойдёт, если PostgreSQL станет недоступен?

```yaml
category: system-design
level: middle
difficulty: 4
slug: system-design-chto-proizoidet-esli-postgresql-stanet-nedostupen
tags: practice
```

Без подготовки — каскадный отказ: запросы висят до таймаута соединения, пулы потоков и соединений исчерпываются, ретраи умножают нагрузку, health checks начинают перезапускать поды, и падают даже эндпоинты, которым база не нужна. С подготовкой — кратковременная ошибка записи на 10–60 секунд, пока кластер переключается на реплику, а чтение частично продолжает работать из кэша.

**Что происходит по шагам без защиты.**

1. Новые соединения не устанавливаются, `NpgsqlConnection.Open` ждёт `Timeout` (по умолчанию 15 с), запросы — `CommandTimeout` (30 с).
2. Каждый висящий запрос держит соединение из пула, память и слот Kestrel; пул (по умолчанию `Max Pool Size=100`) заканчивается, новые запросы ждут уже пула.
3. Клиенты и upstream-сервисы получают таймауты и ретраят — нагрузка растёт в разы.
4. Если liveness probe проверяет БД, Kubernetes перезапускает все поды — теперь не работают и кэшированные эндпоинты.
5. После восстановления БД все поды одновременно открывают соединения и выполняют накопившиеся ретраи — база падает снова.

**Как это должно работать.**

**1. Автоматический failover.** PostgreSQL в HA-конфигурации: Patroni (или облачный managed — RDS, Cloud SQL) с репликой в другой зоне. При падении primary реплика повышается за 10–30 секунд. Приложение подключается через стабильную точку: Kubernetes Service/HAProxy, указывающие на текущего лидера, или multi-host строку Npgsql с `Target Session Attributes=primary`.

**2. Короткие таймауты.** `Timeout=3` на подключение, `CommandTimeout` под конкретный запрос (обычно 2–5 с). Лучше быстро вернуть 503, чем держать ресурсы 30 секунд.

**3. Ретраи с умом.** `EnableRetryOnFailure` в EF Core или Polly — ограниченное число попыток с backoff и jitter, только для транзиентных ошибок. Ретраить нужно также всю транзакцию целиком, а не одну команду.

**4. Circuit breaker.** После серии ошибок перестать дёргать БД на несколько секунд и сразу возвращать fallback — это защищает и приложение, и восстанавливающуюся базу.

**5. Правильные health checks.** Liveness — только «процесс жив». Readiness можно сделать зависимым от БД, но аккуратно: если все поды станут not ready, перестанут работать и эндпоинты без БД.

**6. Деградация.**

- чтение — из Redis, в том числе устаревших данных (stale-while-error);
- чтение с реплики, если упал только primary;
- некритичные записи (лайки, просмотры, аналитика) — в очередь, применятся позже;
- критичные (оформление заказа, оплата) — честная ошибка «попробуйте через минуту».

**Потеря данных при failover.** При асинхронной репликации транзакции, подтверждённые клиенту, но не дошедшие до реплики, теряются (обычно доли секунды). Если это недопустимо — синхронная реплика (`synchronous_commit = on` + `synchronous_standby_names`) ценой латентности каждой записи.

**Проверка.** Регулярно устраивать failover на стенде, а затем в проде в окно низкой нагрузки (`patronictl switchover`) и смотреть, сколько длится ошибка и восстанавливаются ли пулы соединений без перезапуска подов.

## Что произойдёт, если Kafka станет недоступна?

```yaml
category: system-design
level: middle
difficulty: 4
slug: system-design-chto-proizoidet-esli-kafka-stanet-nedostupna
tags: kafka, practice
```

Зависит от того, как с Kafka работают продюсеры. Если событие публикуется прямо в HTTP-запросе и запрос ждёт подтверждения — пользовательские операции начинают висеть и падать. Если используется outbox — бизнес-операции продолжаются, события копятся в таблице и уйдут после восстановления; консьюмеры просто стоят, а потом догоняют накопленный lag. Хорошо спроектированная система переживает недоступность Kafka как задержку, а не как аварию.

**Сторона продюсера.**

- `Confluent.Kafka` складывает сообщения во внутренний буфер и ретраит отправку до `message.timeout.ms` (по умолчанию 300 000 ms — 5 минут), после чего delivery report возвращает ошибку.
- `await producer.ProduceAsync(...)` в обработчике запроса ждёт этого подтверждения — запросы висят до таймаута, потоки и соединения копятся.
- Fire-and-forget `Produce` без проверки результата — события теряются молча при переполнении буфера или рестарте пода: буфер живёт только в памяти процесса.

**Защита — transactional outbox.** Событие записывается в таблицу `outbox` в той же транзакции, что и бизнес-данные. Relay публикует его и помечает отправленным. Kafka недоступна — relay ретраит с backoff, таблица растёт, пользователь ничего не замечает. Нужно мониторить размер outbox и возраст самой старой неотправленной записи, а также иметь план на случай многочасового простоя (рост таблицы, autovacuum).

**Сторона консьюмера.**

- консьюмеры перестают получать сообщения, зависящие от них процессы (уведомления, синхронизация поиска, начисление бонусов) останавливаются;
- после восстановления — всплеск: lag обрабатывается на максимальной скорости, это нагрузка на БД консьюмеров; нужен лимит параллелизма;
- закоммиченные offset хранятся в самой Kafka, так что обработка продолжится с места остановки, но сообщения, обработанные и не закоммиченные, придут повторно — консьюмеры должны быть идемпотентны.

**Частичная недоступность — более частый случай.**

| Ситуация | Эффект |
| --- | --- |
| Упал один брокер из трёх, RF=3 | лидерство его партиций переходит к репликам за секунды, клиенты переподключаются сами |
| В ISR меньше реплик, чем `min.insync.replicas` | продюсеры с `acks=all` получают `NotEnoughReplicas` — запись в эти партиции отклоняется, чтение работает |
| Нет ни одной in-sync реплики | партиция offline; `unclean.leader.election.enable=false` (по умолчанию) не позволит выбрать отстающую реплику ценой потери данных |
| Потерян кворум контроллеров (KRaft/ZooKeeper) | нельзя менять метаданные, выбирать лидеров; существующие лидеры продолжают работать |

**Что заложить заранее.**

1. Outbox для всех событий, потеря которых недопустима; для телеметрии — допустить потерю.
2. Ни один синхронный пользовательский путь не ждёт Kafka.
3. Кластер из 3+ брокеров в разных зонах, RF=3, `min.insync.replicas=2`.
4. Алерты: недоступность брокеров, under-replicated partitions, размер outbox, consumer lag.
5. Идемпотентные консьюмеры и ограничение скорости догоняющей обработки.

**Вывод для собеседования.** Kafka — это буфер между сервисами; её недоступность должна превращаться в задержку побочных эффектов, а не в отказ основных операций.

## Что делать при росте нагрузки в 10 раз?

```yaml
category: system-design
level: middle
difficulty: 4
slug: system-design-chto-delat-pri-roste-nagruzki-v-10-raz
tags: scalability, practice
```

Не масштабировать всё подряд, а найти, что сломается первым. Порядок: измерить текущее потребление ресурсов на запрос и экстраполировать ×10, определить, какой компонент упрётся в предел первым, снять самые дешёвые ограничения (горизонтальное масштабирование stateless-слоя, кэш, индексы, пулы), и только потом идти в архитектурные изменения (реплики, асинхронность, шардирование).

**1. Понять, что такое «×10».** Рост RPS равномерный или пиковый (распродажа)? Растёт чтение или запись? Новые пользователи или новые данные? 10× чтений решается кэшем, 10× записей — совсем другой разговор.

**2. Посчитать запас каждого компонента.**

| Компонент | Сейчас | ×10 | Предел | Вывод |
| --- | --- | --- | --- | --- |
| API поды | 40% CPU на 6 подах | 24 пода | HPA до 30 | ок, поднять лимит |
| PostgreSQL CPU | 35% | 350% | 100% | узкое место №1 |
| Соединения к БД | 200 | 2000 | `max_connections=500` | нужен PgBouncer |
| Redis | 15k ops/s | 150k ops/s | ~100k+ на шард | шардирование/реплики |
| Внешний API | 50 RPS | 500 RPS | лимит 200 RPS | кэш/батчинг/договор |

Практически всегда первым упирается база данных или внешняя зависимость с лимитами, а не stateless-код.

**3. Дешёвые шаги (дни).**

- горизонтально масштабировать API и воркеры, проверить, что они действительно stateless;
- кэшировать горячие чтения (Redis, CDN для публичного), увеличить TTL там, где можно;
- `pg_stat_statements`: топ запросов по суммарному времени — индексы, переписать N+1, убрать лишние колонки;
- PgBouncer для соединений, чтение с реплик;
- вынести тяжёлое из синхронного пути в очередь.

**4. Архитектурные шаги (недели–месяцы).**

- read replicas и CQRS-модели для тяжёлых чтений;
- партиционирование больших таблиц, архивирование старых данных;
- разделение БД по сервисам/доменам;
- шардирование — только когда запись не помещается в один primary даже после оптимизаций.

**5. Защитить систему, пока не готово.** Rate limiting по клиентам, приоритизация критичных операций (оформление заказа важнее рекомендаций), feature flags для отключения тяжёлых функций, load shedding — быстрый 503 лучше, чем таймауты у всех.

**6. Проверить.** Нагрузочный тест на ×10 (лучше ×15) на стенде с продовым объёмом данных — 10× на пустой БД ничего не доказывает. Смотреть p99, а не среднее, и насыщение ресурсов.

**Типичные ошибки:**

- сразу предлагать микросервисы или шардирование, не померив;
- масштабировать поды, не учтя, что каждый новый под открывает соединения к БД;
- забыть о стоимости: ×10 нагрузки не обязано означать ×10 денег, если узкое место — неэффективный запрос.

## Как обеспечить idempotency в распределённой системе?

```yaml
category: system-design
level: middle
difficulty: 4
slug: system-design-kak-obespechit-idempotency-v-raspredelennoi-sisteme
tags: idempotency, practice
```

Идемпотентность — свойство операции давать тот же результат при повторном выполнении. В распределённой системе она обязательна, потому что сеть не даёт exactly-once доставки: клиент не знает, дошёл ли запрос, на который не пришёл ответ, и повторяет его; брокер доставляет сообщения at-least-once. Обеспечивается она уникальным ключом операции и хранением результата, который проверяется атомарно с самим изменением.

**Где возникают повторы.**

- пользователь дважды нажал «Оплатить», мобильный клиент ретраит после обрыва связи;
- Polly/HTTP-клиент повторяет запрос после таймаута, хотя сервер его выполнил;
- консьюмер Kafka упал после обработки, но до коммита offset;
- вебхук провайдера пришёл дважды.

**1. Естественно идемпотентные операции.** Лучший вариант — проектировать операции так, чтобы повтор был безвреден:

- `PUT /users/1 {name}` и `SET status = 'shipped'` идемпотентны, `UPDATE balance = balance + 100` — нет;
- upsert `INSERT ... ON CONFLICT DO NOTHING/UPDATE`;
- переход состояния с проверкой: `UPDATE orders SET status = 'paid' WHERE id = @id AND status = 'pending'`.

**2. Idempotency key для API.** Клиент генерирует UUID на одно намерение пользователя и передаёт его в заголовке `Idempotency-Key`; повторы этого намерения идут с тем же ключом.

```sql
idempotency_keys(key text, client_id, request_hash, status, response_code,
                 response_body jsonb, created_at, primary key (client_id, key))
```

Алгоритм на сервере:

1. `INSERT` ключа со статусом `processing` — если конфликт, запрос повторный;
2. повтор с `completed` → вернуть сохранённый ответ; с `processing` → `409`/`425` «ещё выполняется»; другой `request_hash` с тем же ключом → `422`;
3. выполнить операцию и сохранить ответ **в той же транзакции**, что и бизнес-изменение — иначе падение между ними оставит ключ без результата или результат без ключа;
4. ключи хранить ограниченное время (24 ч – 7 дней), чистить фоновой задачей.

**3. Консьюмеры сообщений — inbox.** В транзакции обработки записать `message_id` в `inbox(message_id pk)`; конфликт — сообщение уже обработано, коммитим offset и идём дальше.

**4. Вызовы внешних систем.** Передавать свой идентификатор операции во внешний API (у платёжных провайдеров обычно есть параметр idempotency key). Если внешняя система ключ не поддерживает — перед повтором запросить у неё статус операции по нашему ID, а не повторять вслепую.

**5. Цепочки.** Ключ передаётся дальше по цепочке или из него детерминированно выводятся ключи дочерних операций (`{key}:reserve`, `{key}:charge`) — тогда повтор всей саги не дублирует шаги.

**Ошибки, которые часто делают:**

- проверить «был ли ключ» отдельным `SELECT`, а потом выполнить операцию — гонка двух одновременных повторов, нужен уникальный индекс или блокировка;
- хранить ключи только в Redis без персистентности для денежных операций;
- генерировать ключ на сервере — тогда повтор клиента получает новый ключ и смысл теряется.

**Компромиссы.** Хранение ключей и ответов — дополнительная запись на каждую операцию и рост таблицы; для чтений и естественно идемпотентных операций это не нужно. Применять ключи стоит там, где повтор стоит денег или создаёт сущность.

## Как реализовать retry без создания лавины запросов?

```yaml
category: system-design
level: middle
difficulty: 4
slug: system-design-kak-realizovat-retry-bez-sozdaniya-laviny-zaprosov
tags: resilience, practice
```

Ретраи полезны против кратковременных сбоев и опасны при перегрузке: если зависимость отвечает медленно, потому что перегружена, каждый ретрай добавляет ей нагрузки, и система добивает сама себя (retry storm). Защита — ретраить только то, что имеет смысл, с экспоненциальным backoff и jitter, ограничивать общий объём ретраев (retry budget), ретраить на одном уровне стека и выключать вызовы совсем через circuit breaker.

**Почему возникает лавина.** Цепочка Gateway → A → B → DB, на каждом уровне 3 попытки. Если DB тормозит, на один пользовательский запрос приходится до 3 × 3 × 3 = 27 запросов к БД. Добавьте пользователей, нажимающих F5, — нагрузка на больную зависимость растёт на порядок именно в момент, когда ей хуже всего.

**Правила.**

**1. Ретраить только транзиентные ошибки и только идемпотентные операции.** Да: таймаут соединения, 503, 429 (с учётом `Retry-After`), deadlock/serialization failure в БД. Нет: 400, 401, 404, 409, ошибки валидации. POST без idempotency key — не ретраить.

**2. Экспоненциальный backoff с jitter.** Задержка `base × 2^attempt`, ограниченная сверху, плюс случайность. Без jitter тысячи клиентов, получивших ошибку одновременно, придут повторно тоже одновременно — синхронные волны. Full jitter: `delay = random(0, min(cap, base × 2^attempt))`.

**3. Ограниченное число попыток и общий дедлайн.** 2–3 попытки, а суммарное время не превышает таймаут вызывающей стороны: если клиент ждёт 2 с, бессмысленно делать третью попытку на 2.5-й секунде.

**4. Ретраи на одном уровне.** Обычно — ближе к краю (клиент или gateway) или ближе к источнику ошибки, но не на всех уровнях сразу. Внутренние сервисы могут сигнализировать «не ретраить» специальным заголовком или кодом.

**5. Retry budget.** Ретраи не должны превышать, например, 10–20% от основного трафика: счётчик в скользящем окне, при превышении новые ретраи не выполняются. Так при массовом сбое нагрузка вырастает максимум на 20%, а не в 3 раза.

**6. Circuit breaker.** При доле ошибок выше порога вызовы зависимости прекращаются на время, затем пробные запросы (half-open). Ретраи внутри открытого breaker не выполняются.

**7. Сервер тоже защищается.** Rate limiting, лимит конкурентности, load shedding с `503` + `Retry-After` — сервер говорит клиентам, когда приходить.

**В .NET** всё это даёт `Microsoft.Extensions.Http.Resilience`:

```csharp
builder.Services.AddHttpClient<InventoryClient>()
    .AddResilienceHandler("inventory", b =>
    {
        b.AddTimeout(TimeSpan.FromSeconds(2));
        b.AddRetry(new HttpRetryStrategyOptions
        {
            MaxRetryAttempts = 2,
            BackoffType = DelayBackoffType.Exponential,
            UseJitter = true,
            Delay = TimeSpan.FromMilliseconds(200)
        });
        b.AddCircuitBreaker(new HttpCircuitBreakerStrategyOptions
        {
            FailureRatio = 0.5,
            MinimumThroughput = 20,
            BreakDuration = TimeSpan.FromSeconds(15)
        });
        b.AddTimeout(TimeSpan.FromMilliseconds(700));
    });
```

Внешний таймаут ограничивает всю операцию с ретраями, внутренний — каждую попытку.

**Асинхронные ретраи.** Для очередей — отложенные повторы через retry-топики или delayed-сообщения с растущей задержкой и DLQ после N попыток, а не немедленный повтор в цикле, который блокирует партицию и долбит упавшую зависимость.

**Мониторинг.** Метрика доли ретраев и состояния circuit breaker: рост ретраев — ранний сигнал деградации зависимости.

## Как обеспечить observability?

```yaml
category: system-design
level: middle
difficulty: 4
slug: system-design-kak-obespechit-observability
tags: observability, practice
```

Observability — способность по внешним сигналам системы понять, что происходит внутри, в том числе в ситуации, которую заранее не предусмотрели. Строится на трёх типах телеметрии — метриках, логах и трейсах, связанных общим `trace_id`, — плюс алертах по симптомам, которые видит пользователь, и SLO, задающих, что считается «работает нормально».

**1. Метрики — «что происходит».** Дешёвые агрегаты для дашбордов и алертов.

- для каждого сервиса — RED: Rate (RPS), Errors (доля ошибок), Duration (p50/p95/p99 латентности) по эндпоинтам;
- для ресурсов — USE: Utilization, Saturation, Errors (CPU, память, пул соединений, очереди, диск);
- бизнес-метрики: заказы в минуту, успешные оплаты, — часто первыми показывают сбой, который технические метрики пропускают;
- специфичные: consumer lag Kafka, размер outbox, hit rate кэша, GC и thread pool queue в .NET.

Prometheus + Grafana; осторожно с кардинальностью: `user_id` или полный URL в метке создают миллионы рядов.

**2. Логи — «что именно случилось».**

- структурированные (JSON) через Serilog или `ILogger` с параметрами шаблона, а не интерполяцией строк;
- в каждой записи `trace_id`, `span_id`, сервис, версия, ключевые бизнес-идентификаторы (`order_id`);
- уровни осмысленно: ошибки — то, что требует внимания, а не каждый 404;
- никаких паролей, токенов, номеров карт и лишних персональных данных;
- хранилище — Loki, Elasticsearch/OpenSearch; retention по стоимости, для отладки обычно хватает 7–30 дней.

**3. Трейсы — «где именно тормозит».** Distributed tracing показывает путь запроса через сервисы, БД, Kafka с длительностью каждого шага. Контекст передаётся в заголовке W3C `traceparent` по HTTP и в заголовках сообщений Kafka. Сэмплирование: хранить 1–10% обычных запросов и 100% ошибочных и медленных (tail-based sampling в OpenTelemetry Collector).

**4. Стандарт — OpenTelemetry.** В .NET:

```csharp
builder.Services.AddOpenTelemetry()
    .WithTracing(t => t
        .AddAspNetCoreInstrumentation()
        .AddHttpClientInstrumentation()
        .AddNpgsql()
        .AddOtlpExporter())
    .WithMetrics(m => m
        .AddAspNetCoreInstrumentation()
        .AddRuntimeInstrumentation()
        .AddOtlpExporter());
```

Данные идут в OTel Collector, оттуда — в Prometheus/Tempo/Jaeger/Loki или в коммерческий бэкенд; смена бэкенда не требует менять код.

**5. SLO и алерты.**

- SLO: «99.9% запросов к API оформления заказа успешны и быстрее 500 ms за 30 дней»;
- алертить по симптомам и скорости расходования error budget (burn rate), а не по «CPU > 80%» — высокий CPU без влияния на пользователей не повод будить дежурного;
- каждый алерт должен быть actionable и ссылаться на runbook.

**6. Связность.** Из графика ошибок — переход к трейсам этого интервала (exemplars), из трейса — к логам по `trace_id`. Без этого во время инцидента сигналы есть, но связать их невозможно.

**7. Healthchecks и синтетика.** `/health/live` и `/health/ready` для оркестратора, синтетические проверки ключевых сценариев извне — узнать о проблеме раньше пользователей.

**Компромиссы.** Телеметрия стоит денег: логи и трейсы легко начинают стоить как сама система. Сэмплирование, уровни логирования и контроль кардинальности — часть дизайна, а не оптимизация на потом.

## Как обнаружить и устранить bottleneck?

```yaml
category: system-design
level: middle
difficulty: 4
slug: system-design-kak-obnaruzhit-i-ustranit-bottleneck
tags: scalability, practice
```

Узкое место ищут сверху вниз: сначала по метрикам определить, какой компонент насыщен (где растёт очередь и время ожидания), затем трейсом найти, на каком шаге запрос проводит время, затем профилированием или анализом запросов найти конкретную причину. Устраняют его самым дешёвым способом, после чего измеряют снова — узкое место переезжает в следующий компонент.

**1. Локализовать по симптому.** Признак узкого места — насыщение: очередь растёт, латентность растёт нелинейно при небольшом росте нагрузки, throughput перестаёт расти при добавлении ресурсов.

| Где смотреть | Признак |
| --- | --- |
| API | p99 растёт, CPU ~100% или, наоборот, CPU низкий, а латентность высокая (ожидание чего-то) |
| .NET runtime | рост `ThreadPool.QueueLength`, частые Gen2 GC, `lock contention` |
| Пул соединений к БД | время ожидания соединения, исчерпание пула |
| PostgreSQL | CPU, `wait_event` в `pg_stat_activity` (Lock, IO, LWLock), рост длительности запросов |
| Очереди | растущий consumer lag |
| Внешний сервис | его латентность в трейсах, 429 |

Низкий CPU при высокой латентности почти всегда означает ожидание: блокировки, пул соединений, синхронный I/O, внешний вызов.

**2. Найти шаг по трейсу.** Distributed tracing показывает, что из 800 ms запроса 650 — это 40 последовательных запросов к БД (N+1) или один вызов внешнего API.

**3. Найти конкретную причину.**

- БД: `pg_stat_statements` — топ по `total_exec_time`, затем `EXPLAIN (ANALYZE, BUFFERS)` для плохих планов (Seq Scan на большой таблице, неверная оценка строк);
- код: `dotnet-counters` для живой картины, `dotnet-trace` и профилировщик для CPU и аллокаций, `dotnet-dump` при зависаниях (стеки всех потоков покажут, где все ждут);
- блокировки в БД: `pg_locks` + `pg_blocking_pids()`;
- сеть: размеры ответов, количество round-trip.

**4. Воспроизвести.** Нагрузочный тест с реалистичным профилем и объёмом данных подтверждает гипотезу и позволяет измерить эффект исправления.

**5. Устранить — от дешёвого к дорогому.**

1. исправить неэффективность: индекс, устранить N+1, батчинг, убрать sync-over-async, уменьшить аллокации;
2. кэшировать результат;
3. убрать работу из синхронного пути — в очередь;
4. добавить ресурсов: горизонтально для stateless, вертикально для БД;
5. изменить архитектуру: реплики, партиционирование, шардирование, денормализация.

**Типичные находки на практике:**

- отсутствующий индекс или функция в `WHERE`, не дающая его использовать;
- EF Core загружает весь граф сущностей или делает запрос в цикле;
- `.Result`/`.Wait()` приводят к голоданию пула потоков;
- `HttpClient` создаётся на каждый запрос — исчерпание сокетов;
- один горячий ключ в Redis или горячая строка в БД (счётчик), на которой все ждут блокировку;
- маленький `Max Pool Size` при большом числе параллельных запросов.

**6. Проверить и повторить.** После исправления — снова нагрузочный тест. Закон Амдала: ускорение шага, занимающего 10% времени, даёт максимум 10% выигрыша — поэтому сначала оптимизируют то, что доминирует в профиле.

## Спроектируйте систему на 100 000 RPS: с чего начнёте и что станет узким местом?

```yaml
category: system-design
level: senior
difficulty: 5
slug: system-design-senior-sproektiruite-sistemu-na-100-000-rps-s-chego-nachnete-i-chto-stanet-uz
tags: scalability, architecture
```

Начинать надо не с компонентов, а с профиля нагрузки: какая доля чтений и записей, насколько данные персональны, какие требования к свежести и латентности. 100k RPS чтения публичных данных — это задача CDN и кэша; 100k RPS записей — задача партиционирования хранилища. Узким местом почти никогда не оказывается stateless-код: первыми упираются хранилище записей, горячие ключи, пулы соединений, сеть и сама телеметрия.

**1. Уточнить нагрузку.** Допустим: 100k RPS в пике, 90% чтения (персонализированные, кэшируемые на секунды), 10% записи (10k/с), p99 < 150 ms, 99.95%.

**2. Оценки.**

- 100k RPS ≈ 8.6 млрд запросов в сутки при постоянной нагрузке; реально средняя ниже пика в 2–3 раза;
- API: при ~2k RPS на под (2 vCPU, замерить!) нужно 50 подов, с запасом N+1 по зонам (потеря одной из трёх) — ~75–80;
- трафик: 100k × 10 КБ = 1 ГБ/с ≈ 8 Гбит/с — сетевой бюджет балансировщиков и межзонального трафика (который ещё и платный в облаке);
- логи: 100k × 1 КБ лог на запрос = 100 МБ/с ≈ 8.6 ТБ/сутки — логирование каждого запроса становится одной из самых дорогих частей;
- записи: 10k/с × 1 КБ = 10 МБ/с, ~860 ГБ/сутки — это уже не «одна PostgreSQL навсегда».

**3. Архитектура.**

```text
DNS/GeoDNS ──► CDN/edge (статика, публичные GET, WAF)
                 │
             L4 LB (NLB) ──► L7 (Envoy/ingress, 10+ инстансов) ──► API pods (3 AZ)
                                                                     │
          ┌─────────────────────┬─────────────────────┬──────────────┴───────────┐
          ▼                     ▼                     ▼                          ▼
  локальный кэш          Redis Cluster         Kafka (запись как лог)       шардированное
  (секунды, горячие)     (12+ шардов, реплики)       │                      хранилище: PostgreSQL
                                                     ▼                      по ключу (Citus/свои
                                              воркеры: агрегаты,            шарды) или Cassandra/
                                              проекции для чтения           ScyllaDB
```

**4. Что станет узким местом — по порядку вероятности.**

1. **Хранилище записей.** 10k транзакций/с один primary PostgreSQL ещё может выдержать на мощном железе, но с индексами, репликацией, autovacuum и ростом объёма запас быстро кончается. Решение: шардирование по ключу владельца данных, или приём записей в Kafka и пакетная запись в хранилище (если допустима асинхронность), или хранилище с горизонтальной записью.
2. **Горячие ключи.** Одна популярная сущность (товар распродажи, звезда соцсети) — 20% трафика на один шард Redis. Решения: локальный кэш на секунды перед Redis, репликация ключа (`key#1..N`), request coalescing.
3. **Соединения.** 80 подов × пул 50 = 4000 соединений к БД и тысячи к Redis — нужны PgBouncer и мультиплексирование.
4. **Балансировка и TLS.** Терминация TLS на 100k RPS — заметный CPU; keep-alive и HTTP/2 между слоями, иначе handshake съест ресурсы.
5. **Fan-out и хвостовая латентность.** Если запрос вызывает 10 зависимостей параллельно, его p99 определяется p99.9 худшей из них. Меньше синхронных вызовов, hedging для критичных чтений, жёсткие таймауты.
6. **Внешние зависимости** с лимитами — кэш, батчинг, асинхронность.
7. **Наблюдаемость.** Сэмплирование трейсов 1%, логи по ошибкам и медленным запросам, метрики без высокой кардинальности.

**5. Чтение.** Целевой hit rate кэша — 95%+: тогда в хранилище идёт 5k чтений/с, что держат реплики. Публичное — на CDN с `stale-while-revalidate`. Персонализированное — материализованные проекции (CQRS), обновляемые из событий, чтобы чтение было одним запросом по ключу.

**6. Устойчивость к перегрузке.** Rate limiting на edge, лимит конкурентности на подах, load shedding по приоритету, автоскейлинг с упреждением (новые поды прогреваются десятки секунд), запас ~30–50%.

**7. Проверка.** Нагрузочный тест на 150k RPS в отдельном окружении с продовым объёмом данных и распределением ключей (Zipf, а не равномерное — иначе горячие ключи не проявятся).

**Компромиссы.** Асинхронная запись через Kafka и проекции для чтения дают масштаб, но вводят eventual consistency — нужен read-your-writes для автора изменения (читать свою запись с primary или из кэша сессии). Шардирование — необратимое усложнение, поэтому сначала исчерпать кэш, реплики и оптимизацию запросов.

## Спроектируйте обработку миллиона событий в секунду с гарантией отсутствия потерь

```yaml
category: system-design
level: senior
difficulty: 5
slug: system-design-senior-sproektiruite-obrabotku-milliona-sobytii-v-sekundu-s-garantiei-otsutst
tags: throughput, architecture
```

Миллион событий в секунду — это задача распределённого лога: Kafka (или совместимый Redpanda) с сотнями партиций как надёжный буфер, батчинг на каждом шаге и горизонтально масштабируемые консьюмеры. «Без потерь» — это сквозное свойство цепочки: событие подтверждается источнику только после записи на несколько реплик в разных зонах, консьюмер коммитит позицию только после записи в приёмник, а приёмник идемпотентен к повторам. Гарантия, которую реально можно дать, — at-least-once с дедупликацией, то есть effectively-once.

**Оценки.**

- 1M событий/с × 1 КБ = 1 ГБ/с сырых данных; с zstd/lz4-сжатием батчей ×4 → ~250 МБ/с на диск;
- RF=3 → ~750 МБ/с записи по кластеру плюс 500 МБ/с межброкерной репликации;
- retention 24 ч: 250 МБ/с × 86 400 с ≈ 21.6 ТБ × 3 реплики ≈ 65 ТБ; дольше — tiered storage в S3;
- брокеры: при устойчивых ~100–150 МБ/с входящих на брокер с учётом репликации — порядка 9–12 брокеров с NVMe и 25 Гбит сетью, плюс запас;
- партиции: если консьюмер обрабатывает ~5–10k событий/с на партицию, нужно 100–200 партиций; берём 256–512 — партиции определяют максимальный параллелизм.

**Архитектура.**

```text
Источники ──► Ingest gateway (stateless, .NET/Go) ──► Kafka (3 AZ, RF=3, min.insync=2)
  │ локальный буфер     │ батчинг, валидация                    │
  │ + retry по event_id │ ответ 200 только после acks=all       │
                                                                ├──► stream processing (агрегаты, обогащение)
                                                                ├──► sink → S3/Iceberg (сырые данные, долгое хранение)
                                                                └──► sink → ClickHouse / OLTP-хранилище
```

**Звенья цепочки «без потерь».**

**1. Источник.** Если источник — мобильный клиент или устройство, он хранит события локально и удаляет только после подтверждения; каждое событие имеет уникальный `event_id` и, желательно, монотонный sequence number источника — по пропускам в sequence можно доказать потерю.

**2. Ingest.** Ответ 2xx только после того, как Kafka подтвердила запись. Продюсер: `acks=all`, `enable.idempotence=true` (без дублей при внутренних ретраях), `linger.ms` 5–20 и `batch.size` 256 КБ–1 МБ для пропускной способности. Если Kafka недоступна — ingest отдаёт 503, источник ретраит; буферизовать в памяти gateway нельзя — это точка потери.

**3. Kafka.** RF=3, `min.insync.replicas=2`, rack awareness по зонам, `unclean.leader.election.enable=false`. Важная деталь: Kafka подтверждает запись после попадания в page cache реплик, а не после fsync — защита от потери опирается на то, что три реплики в трёх зонах не теряют питание одновременно.

**4. Консьюмер.** Ручной commit offset после успешной записи в приёмник. Запись батчами (10–50k событий), чтобы приёмник выдержал миллион строк в секунду.

**5. Приёмник — идемпотентный.**

- Kafka → Kafka: транзакции Kafka (exactly-once в пределах кластера, Kafka Streams / Flink);
- ClickHouse: `ReplacingMergeTree` по `event_id` или дедупликация вставок по токену батча;
- S3: детерминированные имена файлов от `(topic, partition, start_offset)` — повтор перезаписывает тот же файл;
- OLTP: `INSERT ... ON CONFLICT (event_id) DO NOTHING`.

**6. Ошибочные события** не блокируют партицию и не выбрасываются: после N попыток — в DLQ-топик с причиной, с алертом и инструментом переобработки.

**Backpressure.** Kafka — буфер на часы: при отставании консьюмеров события копятся, а не теряются. Мониторить consumer lag в секундах, а не в сообщениях, и держать retention заметно больше максимально допустимого отставания.

**Узкие места.** Горячие ключи (одно устройство или тенант даёт 10% потока) перегружают одну партицию — ключ с солью или отдельный топик для крупных тенантов. Ребалансировка consumer group на сотнях партиций — cooperative sticky assignor и static membership, чтобы рестарт пода не останавливал всю группу.

**Контроль.** Сквозная сверка: счётчики событий по источнику и часу на входе и в каждом приёмнике, алерт на расхождение. Без измерения «без потерь» — только обещание.

**Компромиссы.** `acks=all` и межзональная репликация добавляют латентность (единицы–десятки ms) и стоимость трафика; батчинг повышает пропускную способность ценой задержки. Строгий порядок только в пределах ключа — глобальный порядок на миллионе событий в секунду недостижим без потери масштабируемости.

## Как спроектировать geo-распределённую систему для пользователей на разных континентах?

```yaml
category: system-design
level: senior
difficulty: 5
slug: system-design-senior-kak-sproektirovat-geo-raspredelennuyu-sistemu-dlya-polzovatelei-na-raz
tags: geo-distribution, architecture
```

Главное ограничение — скорость света: свет в оптоволокне проходит ~200 км за миллисекунду, поэтому RTT Европа — восточное побережье США ~70–90 ms, Европа — Австралия ~250–300 ms, и никакая оптимизация кода этого не уберёт. Отсюда принципы: приблизить к пользователю всё, что можно (edge, кэш, вычисления), разместить данные пользователя в его «домашнем» регионе, не делать синхронных межрегиональных вызовов на пути запроса и заранее решить, какие данные глобальные, а какие локальные.

**1. Требования, которые определяют архитектуру.**

- целевая латентность для каждого континента (например, p95 < 200 ms);
- требования к размещению данных: GDPR, 152-ФЗ о локализации персональных данных россиян, отраслевые требования — они иногда диктуют архитектуру сильнее, чем латентность;
- что должно работать при потере региона и с какими RPO/RTO;
- характер данных: доля глобально общих (каталог, справочники) и пользовательских.

**2. Слои архитектуры.**

```text
Пользователь ──► Anycast / GeoDNS ──► ближайший edge (CDN, WAF, TLS-терминация)
                                          │
                       ┌──────────────────┼───────────────────┐
                       ▼                  ▼                   ▼
                  EU region           US region           APAC region
              (API, кэш, БД:       (API, кэш, БД:        (API, кэш, БД:
               EU-пользователи)     US-пользователи)      APAC-пользователи)
                       ▲                  ▲                   ▲
                       └──── асинхронная репликация глобальных данных ────┘
                             (каталог, конфигурация) из региона-владельца
```

**3. Edge.** TLS-handshake требует нескольких round-trip; терминация на ближайшей точке присутствия и переиспользование соединений до origin экономят сотни миллисекунд для далёких пользователей. Статика и публичные ответы — из кэша CDN.

**4. Размещение данных — ключевое решение.**

| Тип данных | Стратегия |
| --- | --- |
| Профиль, заказы, файлы пользователя | home region: пишется и читается в регионе пользователя |
| Каталог, справочники, контент | один регион-источник, асинхронные read-only копии во всех регионах |
| Глобально уникальные значения (логин, email) | глобальный сервис с консенсусом или разбиение пространства имён |
| Сессии, кэш | только локально, не реплицируются |

Home region назначается при регистрации (по стране или выбору), хранится в глобальном каталоге маршрутизации `user_id → region` и в токене пользователя — так любой edge знает, куда направить запрос.

**5. Маршрутизация.** Запрос попадает в ближайший регион; если пользователь «чужой» (путешествует), есть два варианта: проксировать в home region (дополнительная латентность только для путешественников) или переносить home region при длительном пребывании. Межрегиональный вызов на пути запроса допустим только как исключение.

**6. Хранилища.** PostgreSQL в каждом регионе со своими данными + физические/логические реплики для DR в соседнем регионе. Если нужна глобальная запись с сильной консистентностью — распределённые SQL (CockroachDB, YugabyteDB, Spanner) с привязкой строк к регионам; каждая межрегиональная транзакция платит RTT кворума. Kafka — кластер на регион, межрегиональная репликация топиков MirrorMaker 2 или аналогами.

**7. Эксплуатация.** Одинаковые регионы из одного IaC, деплой по регионам поэтапно (сначала наименьший), мониторинг латентности по регионам из реальных точек пользователей, глобальная наблюдаемость с данными, не выходящими за границу юрисдикции, если это требуется.

**Компромиссы.**

- Home region даёт локальную латентность и простую консистентность, но межрегиональные сценарии (перевод между пользователями разных регионов) становятся распределёнными — через саги и асинхронные события.
- Глобальная БД с консенсусом проще для разработчиков, но каждая запись медленнее и дороже, а сеть между регионами становится частью критического пути.
- Каждый новый регион — это кратное увеличение стоимости эксплуатации; часто достаточно одного региона + CDN + edge, а второй регион добавляется ради DR.

## Как обеспечить консистентность данных в multi-region архитектуре?

```yaml
category: system-design
level: senior
difficulty: 5
slug: system-design-senior-kak-obespechit-konsistentnost-dannyh-v-multi-region-arhitekture
tags: geo-distribution, consistency
```

Сильная консистентность между регионами стоит межрегионального RTT на каждую запись, поэтому её применяют точечно. Основной приём — у каждого фрагмента данных один регион-владелец (single writer): внутри него обычная ACID-консистентность, в остальные регионы изменения уходят асинхронно. Глобальный консенсус — только для того, где нарушение недопустимо (уникальность, деньги), конфликтующие одновременные записи в нескольких регионах — только для данных, которые умеют сливаться.

**Спектр вариантов.**

| Модель | Как устроено | Цена записи | Где применять |
| --- | --- | --- | --- |
| Single writer per entity | home region владеет записью, асинхронная репликация | локальная | большинство пользовательских данных |
| Глобальный консенсус | Raft/Paxos-кворум через регионы (Spanner, CockroachDB, YugabyteDB) | +RTT кворума, 50–150 ms | балансы, уникальные имена, инвентарь с жёстким лимитом |
| Multi-writer + разрешение конфликтов | запись в любом регионе, LWW или CRDT | локальная | корзина, счётчики, настройки, совместное редактирование |
| Синхронная репликация в соседний регион | commit ждёт подтверждения реплики | +RTT до соседа | RPO=0 для критичных данных при DR |

**1. Single writer.** Пользователь (тенант, заказ) принадлежит региону; все записи — там. Чтение в других регионах — из асинхронной копии с отставанием от сотен миллисекунд до секунд. Ошибки начинаются, когда об этом забывают: сервис в регионе B пишет в свою копию — получается незамеченный multi-writer.

**2. Сессионные гарантии поверх eventual consistency.** Пользователю важнее всего не видеть «откат» своих же действий:

- read-your-writes: после записи клиент получает версию (LSN, timestamp, номер события); чтение в другом регионе ждёт, пока реплика догонит эту версию, или проксируется в регион-владелец;
- monotonic reads: привязка сессии к одному региону/реплике или передача максимальной увиденной версии в токене;
- в PostgreSQL версию даёт `pg_current_wal_lsn()` на primary и `pg_last_wal_replay_lsn()` на реплике.

**3. Инварианты, требующие координации.** «Логин уникален глобально», «нельзя продать больше, чем есть», «баланс не уходит в минус» — либо выполнять в регионе-владельце этого ресурса (склад принадлежит региону), либо через глобальную консенсусную БД, либо разбить ресурс на квоты по регионам (каждый регион продаёт свои 100 из 300 билетов, перераспределение — фоновое). Квоты — классический способ получить локальную скорость без нарушения инварианта.

**4. Межрегиональные бизнес-операции** (перевод между пользователями разных регионов) — сага: списание в регионе A, событие через межрегиональную репликацию Kafka, зачисление в регионе B, идемпотентность и компенсации, как в межсервисном взаимодействии.

**5. Конфликтующие записи.** Если данные всё же пишутся в нескольких регионах, конфликты неизбежны и их стратегия выбирается заранее: LWW по гибридным часам, CRDT, слияние на уровне домена (подробнее — в вопросе про active-active).

**6. Проверка расхождений.** Асинхронная репликация может тихо сломаться (остановившийся слот репликации, ошибка применения). Нужны метрики отставания по каждому направлению и периодическая сверка контрольных сумм по диапазонам ключей.

**Что ответить про CAP и PACELC.** При сетевом разделении между регионами нужно выбрать: отказывать в записи данным, чей владелец недоступен (C), или принимать их с последующим разрешением конфликтов (A). Даже без разделения действует компромисс латентность/консистентность (PACELC) — именно он и определяет выбор в 99.9% времени.

**Компромиссы.** Single writer прост и быстр, но при потере региона-владельца его данные недоступны на запись до failover и теряется отставание асинхронной репликации (RPO > 0). Глобальный консенсус устраняет это, но делает каждую запись медленнее и зависимой от межрегиональной сети.

## Как спроектировать active-active в двух регионах и как решать конфликты записи?

```yaml
category: system-design
level: senior
difficulty: 5
slug: system-design-senior-kak-sproektirovat-active-active-v-dvuh-regionah-i-kak-reshat-konflikty
tags: geo-distribution, consistency
```

Active-active — оба региона одновременно обслуживают трафик, включая запись. Самый надёжный вариант — избегать конфликтов, а не разрешать их: каждая запись по ключу идёт в регион-владелец (партиционирование владения), а «active-active» достигается тем, что разные пользователи принадлежат разным регионам. Если же один и тот же объект пишется в обоих регионах, нужна заранее выбранная стратегия разрешения: LWW, CRDT или доменное слияние, — и отказ от неё для данных с жёсткими инвариантами.

**Схема.**

```text
             Global LB (GeoDNS / anycast, health-based)
                 │                              │
            Region A                         Region B
     API ─ Redis ─ PostgreSQL A        API ─ Redis ─ PostgreSQL B
                 │        ▲                 ▲        │
                 └── двусторонняя репликация изменений ──┘
                     (logical replication / CDC через Kafka + MirrorMaker 2)
```

**Требования к ёмкости.** Каждый регион должен выдержать 100% трафика: при 50/50 нагрузке после потери соседа нагрузка удваивается. Значит, либо держать запас 2×, либо иметь проверенный быстрый автоскейлинг и деградацию на время его работы.

**Вариант 1. Партиционирование владения (рекомендуемый).**

- у каждого пользователя/тенанта home region; GLB или edge направляет запросы по нему;
- запись всегда в регион-владелец, другой регион хранит копию для чтения и DR;
- конфликтов нет по построению, при отказе региона владение переносится (fencing: старый регион должен перестать принимать запись по этим ключам до переноса, иначе получится split brain).

**Вариант 2. Запись в любом регионе — нужны правила слияния.**

**Обнаружение конфликта.** Каждая запись несёт версию: номер ревизии + регион, vector clock или hybrid logical clock (HLC). Если входящее изменение не потомок локальной версии — конфликт.

**Стратегии разрешения:**

| Стратегия | Как работает | Риски | Подходит для |
| --- | --- | --- | --- |
| Last-writer-wins | побеждает больший timestamp (HLC + ID региона для детерминизма) | тихая потеря одной из записей; дрейф часов | профиль, настройки, статусы «последнее состояние» |
| CRDT | структуры, математически сходящиеся при любом порядке: G-counter, PN-counter, OR-set, LWW-register | не все операции выразимы, рост метаданных | счётчики лайков, корзина (OR-set), теги, присутствие |
| Слияние по полям | конфликт только если оба изменили одно поле | сложнее схема | документы с независимыми полями |
| Доменное правило | бизнес-логика: статус заказа идёт по максимальному этапу, «отменён» побеждает | нужно для каждой сущности | машины состояний |
| Сохранить обе версии | пользователь или оператор решает | UX | документы, заметки |

**Пример CRDT-корзины.** OR-set: добавление элемента генерирует уникальный тег, удаление удаляет только увиденные теги. Одновременное добавление товара в A и удаление в B даёт «товар есть» — добавление не теряется. Количество — PN-counter на позицию.

**Чего нельзя делать в multi-writer режиме.**

- денежные балансы и остатки с жёсткими ограничениями — LWW потеряет списание, а два региона независимо пропустят «последний товар». Такие сущности — только single writer или глобальный консенсус;
- уникальные ограничения (email) — каждая БД проверяет только локально; нужен глобальный сервис резервирования или детерминированный регион-владелец по хэшу значения;
- автоинкрементные ID — заменить на UUIDv7/Snowflake с ID региона.

**Технологии.** PostgreSQL сам по себе multi-master не поддерживает; есть расширения и форки (pgactive, BDR в EDB, pgEdge) с LWW по умолчанию. Распределённые SQL-базы (CockroachDB, YugabyteDB) решают консенсусом, но тогда запись стоит межрегионального RTT. Часто практичнее собственная репликация доменных событий через Kafka с явной логикой слияния в консьюмере.

**Операционные вопросы.**

- предотвращение циклов репликации: каждое изменение помечено регионом-источником, повторно не пересылается;
- мониторинг отставания репликации в обе стороны и счётчиков конфликтов;
- регулярная проверка переключения всего трафика в один регион.

**Компромиссы.** Active-active даёт минимальную латентность и почти нулевой RTO, но сложность растёт кратно; active-passive с быстрым failover проще и для большинства систем достаточен. Выбор active-active оправдан, когда нужна локальная запись на нескольких континентах или RTO в секундах.

## Как спланировать disaster recovery и что должно произойти при потере региона?

```yaml
category: system-design
level: senior
difficulty: 5
slug: system-design-senior-kak-splanirovat-disaster-recovery-i-chto-dolzhno-proizoiti-pri-potere
tags: disaster-recovery, resilience
```

Disaster recovery планируют от бизнеса к технике: классифицировать сервисы по критичности, для каждого класса согласовать RTO и RPO, выбрать соответствующую стратегию (бэкапы, pilot light, warm standby, active-active), расписать пошаговый runbook с владельцами и регулярно его проверять. При потере региона должен сработать заранее отрепетированный сценарий: решение о переключении, fencing старого региона, повышение реплик данных, перенаправление трафика, запуск в деградированном режиме и последующий возврат.

**1. Классификация.**

| Класс | Примеры | RTO | RPO |
| --- | --- | --- | --- |
| Tier 0 | оплата, оформление заказа, вход | минуты | ~0–секунды |
| Tier 1 | каталог, личный кабинет | < 1 ч | минуты |
| Tier 2 | отчёты, рекомендации, аналитика | часы–сутки | часы |

Тиринг экономит деньги: держать весь стек горячим во втором регионе дорого и не нужно.

**2. Стратегии.**

| Стратегия | Что во втором регионе | RTO | Стоимость |
| --- | --- | --- | --- |
| Backup & restore | только бэкапы и образы | часы | минимальная |
| Pilot light | реплики БД, инфраструктура описана, приложения выключены | десятки минут | низкая |
| Warm standby | всё развёрнуто в уменьшенном масштабе | минуты | средняя |
| Active-active | полная мощность, принимает трафик | секунды | максимальная |

**3. Что подготовить заранее.**

- **Данные:** асинхронные реплики PostgreSQL в DR-регионе (или синхронные для RPO=0 ценой латентности), репликация топиков Kafka (MirrorMaker 2 — offset консьюмеров переводятся через checkpoint'ы, не один в один), репликация бакетов S3, бэкапы в третьем месте с защитой от удаления (immutable/object lock — защита и от ransomware, и от `DROP` по ошибке).
- **Инфраструктура как код:** DR-регион поднимается из тех же Terraform/Helm-манифестов, образы контейнеров уже в его registry.
- **Секреты, сертификаты, DNS:** ключи доступны в DR-регионе, TTL DNS-записей низкий (30–60 с), либо глобальный балансировщик.
- **Зависимости:** внешние провайдеры, IdP, лицензии, whitelists IP у партнёров — классические причины, по которым «всё поднялось, но не работает».
- **Ёмкость:** квоты облака в DR-регионе заранее увеличены — во время региональной аварии ресурсы в соседних регионах резко дефицитны.

**4. Сценарий потери региона.**

1. **Обнаружение и решение (0–10 мин).** Алерты от внешней синтетики, не только из пострадавшего региона. Решение о failover принимает дежурный руководитель инцидента по заранее заданным критериям — автоматический межрегиональный failover опасен ложными срабатываниями.
2. **Fencing.** Гарантировать, что старый primary не принимает запись, даже если вернётся: отключить трафик, отозвать роль в оркестраторе БД. Иначе split brain и две расходящиеся истории.
3. **Повышение данных.** Promote реплик PostgreSQL, Redis — с нуля или из реплики (это кэш), консьюмеры Kafka стартуют с переведённых offset'ов и обязаны быть идемпотентными — часть событий придёт повторно.
4. **Масштабирование и переключение трафика.** Поднять приложения до полной мощности, переключить GLB/DNS.
5. **Деградированный режим.** Отключить Tier 2-функции флагами, чтобы освободить ресурсы.
6. **Коммуникация.** Статус-страница, поддержка, партнёры.
7. **Учёт потерь.** Транзакции, попавшие в окно RPO, — сверка с внешними системами (платёжный провайдер знает о платеже, которого у нас нет).

**5. Возврат (failback).** Отдельный, часто более сложный этап: бывший primary нужно пересоздать как реплику нового (данные разошлись), догнать, затем плановое переключение в окно низкой нагрузки. Его тоже надо репетировать.

**6. Проверка.** План, который не проверяли, не работает: регулярные учения с измерением реального RTO/RPO, восстановление из бэкапов в изолированном окружении, актуализация runbook после каждого изменения архитектуры.

**Компромиссы.** Каждая ступень вверх по стратегиям сокращает RTO/RPO ценой постоянных затрат на простаивающие ресурсы и сложности. Правильный ответ на собеседовании — не «сделаем active-active», а «зависит от стоимости простоя для каждого класса сервисов».

## Что такое RTO и RPO, и как выбранные значения меняют архитектуру?

```yaml
category: system-design
level: senior
difficulty: 5
slug: system-design-senior-chto-takoe-rto-i-rpo-i-kak-vybrannye-znacheniya-menyayut-arhitekturu
tags: disaster-recovery, architecture
```

RTO (Recovery Time Objective) — сколько времени сервис может быть недоступен после аварии, прежде чем ущерб станет неприемлемым. RPO (Recovery Point Objective) — за какой период данные могут быть потеряны, то есть насколько свежей должна быть точка восстановления. RPO определяет, как реплицируются и бэкапятся данные, RTO — насколько готова к работе резервная инфраструктура. Каждый шаг к нулю по любому из них дорожает нелинейно.

```text
       последняя точка              авария                      сервис снова работает
       восстановления                 │                                   │
 ───────────┼─────────────────────────┼───────────────────────────────────┼──────►
            │◄──────── RPO ──────────►│◄─────────────── RTO ─────────────►│
              данные, которые потеряем     обнаружение + решение + восстановление
```

**Как RPO меняет архитектуру данных.**

| RPO | Механизм для PostgreSQL | Цена |
| --- | --- | --- |
| 24 ч | ежедневный `pg_dump` / снапшот диска | дёшево, но восстановление больших БД — часы |
| 5–15 мин | base backup + архивация WAL (pgBackRest, WAL-G), `archive_timeout` | недорого, даёт PITR |
| секунды | асинхронная потоковая реплика (в другой зоне или регионе) | реплика = ещё один сервер |
| 0 в пределах региона | синхронная реплика в другой зоне (`synchronous_commit = on`, кворум `ANY 1 (...)`) | +1–2 ms на каждый commit, запись зависит от реплики |
| 0 при потере региона | синхронная репликация в другой регион или консенсусная БД | +десятки ms на каждый commit |

RPO — это свойство всей системы, а не только основной БД: Kafka (межрегиональная репликация асинхронна), S3 (кросс-региональная репликация — минуты), очереди в памяти, файлы на локальных дисках подов. Достигнутый RPO равен худшему из компонентов, хранящих важные данные.

**Два разных вида аварий.**

- Отказ инфраструктуры (умер сервер, зона, регион) — защищает репликация.
- Логическое повреждение (баг удалил данные, `UPDATE` без `WHERE`, ransomware) — репликация мгновенно копирует повреждение на все реплики. Защищает только PITR: восстановление на момент до ошибки, отложенная реплика (`recovery_min_apply_delay = '1h'`), неизменяемые бэкапы. Для этого класса RPO обычно в минутах, а RTO — часы.

**Как RTO меняет архитектуру вычислений.**

| RTO | Что нужно |
| --- | --- |
| сутки | бэкапы + инфраструктура как код, поднять с нуля |
| часы | pilot light: данные реплицируются, приложения развёртываются по runbook |
| 10–30 мин | warm standby: всё запущено в малом масштабе, переключение DNS/GLB |
| < 1 мин | автоматический failover внутри региона (Patroni, несколько AZ), active-active между регионами |

RTO складывается из времени обнаружения, принятия решения, восстановления данных, запуска и прогрева (кэш, JIT, пулы соединений), переключения трафика с учётом TTL DNS. Часто восстановление занимает минуты, а решение о переключении — полчаса: это тоже нужно планировать.

**Восстановление большого бэкапа — частая ловушка.** База 5 ТБ при скорости восстановления 500 МБ/с поднимается ~3 часа (5 000 000 МБ / 500 МБ/с = 10 000 с), плюс проигрывание WAL. Если RTO = 1 час, бэкапов недостаточно — нужна горячая реплика или более мелкие базы.

**Как выбирать значения.** Из стоимости простоя и потерь: если час недоступности стоит X, а потеря минуты заказов — Y, то стратегия оправдана, пока её годовая стоимость меньше ожидаемого ущерба. Значения разные для разных сервисов: оплате нужен RPO ≈ 0, рекомендациям — RPO «пересчитаем за ночь».

**Что сказать на собеседовании.** RTO/RPO — это договорённость с бизнесом, записанная и проверяемая учениями; архитектура выводится из них, а не наоборот. И заявленные значения ничего не стоят, если реальное время восстановления никогда не измерялось.

## Как проверить, что план восстановления работает, не устроив аварию в проде?

```yaml
category: system-design
level: senior
difficulty: 5
slug: system-design-senior-kak-proverit-chto-plan-vosstanovleniya-rabotaet-ne-ustroiv-avariyu-v-p
tags: disaster-recovery, testing
```

Проверять постепенно, наращивая реалистичность и ограничивая радиус поражения: автоматическое восстановление бэкапов в изолированной среде, учения на стенде, штабные «бумажные» прогоны, затем контролируемые эксперименты в проде на малой доле — и только после этого плановое переключение целого региона в окно низкой нагрузки с заранее подготовленным откатом. Цель каждого шага — измерить реальные RTO/RPO и найти шаги runbook, которые не работают.

**1. Бэкапы — проверка восстановлением, а не наличием.**

- ежедневная автоматическая задача: взять последний бэкап, восстановить в изолированном окружении, применить WAL до заданного момента (PITR), прогнать проверки — количество строк, контрольные суммы ключевых таблиц, smoke-запросы приложения;
- метрики: время восстановления (это и есть нижняя граница RTO) и возраст последней восстановимой точки (реальный RPO);
- алерт, если проверка не прошла, — бэкап, который не восстанавливается, хуже отсутствующего, потому что создаёт ложное спокойствие.

**2. Tabletop exercise.** Команда проходит сценарий «потерян регион A» по runbook без реальных действий: кто принимает решение, где доступы, какие команды, что делать, если упал и инструмент мониторинга. Дёшево и находит организационные дыры: секреты в недоступном регионе, единственный человек с правами, устаревшие ссылки.

**3. Учения на стенде.** Полная копия архитектуры в масштабе (тот же IaC, та же топология регионов, синтетическая нагрузка): реальное отключение региона, failover БД, переключение трафика, измерение RTO и потерь. Затем — failback.

**4. Chaos engineering в проде с ограниченным радиусом.** Принципы:

- гипотеза устойчивого состояния: «при убийстве пода error rate не превышает 0.1%, p99 < 300 ms»;
- начинать с малого: один под → одна нода → одна зона;
- автоматический стоп-кран: эксперимент прерывается, если SLO-метрики выходят за пороги;
- время — рабочие часы, когда все на месте, а не ночь;
- инструменты: Chaos Mesh / LitmusChaos в Kubernetes, AWS Fault Injection Service, Toxiproxy для задержек и обрывов соединений.

**5. Плановый switchover вместо аварийного failover.** Переключение PostgreSQL на реплику (`patronictl switchover`) в проде проверяет почти всё то же, что и авария, но контролируемо: без потери данных и с возможностью вернуться. Делать регулярно, например ежемесячно, — так failover становится рутинной операцией.

**6. Проверка DR-региона без переключения.**

- синтетические транзакции, постоянно выполняемые против DR-региона (read-only или на тестовых аккаунтах);
- зеркалирование доли читающего трафика в DR-регион (shadow traffic) без отдачи ответов пользователям;
- регулярный перевод части реального трафика (1–5%, затем 50%) в DR-регион, если архитектура это позволяет, — лучший способ убедиться, что там всё работает под нагрузкой.

**7. Game day — полное переключение.** После всех предыдущих шагов — плановое перемещение всего трафика из основного региона, объявленное заранее, с готовым планом отката и критериями прерывания. Многие компании делают это ежеквартально.

**Что измерять и фиксировать.** Фактические RTO и RPO против целевых, время до обнаружения, время до решения, шаги, потребовавшие ручного вмешательства или импровизации. Итог — blameless postmortem и задачи на исправление runbook и автоматизации.

**Типичные находки учений:** сертификаты или секреты не реплицированы, TTL DNS на деле 24 часа, квот в DR-регионе не хватает, консьюмеры Kafka в DR-регионе стартуют с начала топика, фоновые задачи запускаются в обоих регионах одновременно, мониторинг жил только в упавшем регионе.

## Как выбрать схему шардирования и что делать при необходимости решардинга?

```yaml
category: system-design
level: senior
difficulty: 5
slug: system-design-senior-kak-vybrat-shemu-shardirovaniya-i-chto-delat-pri-neobhodimosti-reshard
tags: sharding, data
```

Схему выбирают от запросов, а не от данных: ключ шардирования должен присутствовать почти в каждом горячем запросе и объединять всё, что меняется в одной транзакции. Способ распределения почти всегда стоит выбирать так, чтобы решардинг был операцией перемещения целых логических единиц, а не перехэшированием каждой строки: много логических шардов (слотов) на небольшом числе физических плюс таблица маршрутизации. Тогда рост — это перенос слотов, а не перестройка всей системы.

**1. Анализ доступа перед выбором.**

- выписать топ-20 запросов по частоте и по нагрузке (`pg_stat_statements`), для каждого — по каким полям фильтр;
- найти «естественного владельца» данных: `tenant_id` в B2B SaaS, `user_id` в B2C, `chat_id` в мессенджере, `merchant_id` в платежах;
- проверить транзакционные границы: заказ, его позиции и платежи должны оказаться на одном шарде;
- оценить распределение: есть ли тенант, который в 1000 раз больше медианы (кит), и как растёт объём во времени.

**2. Критерии хорошего ключа.**

| Критерий | Плохой пример | Почему |
| --- | --- | --- |
| Высокая кардинальность | `country` | 5 стран = максимум 5 шардов, неравномерно |
| Нет монотонности при range | `created_at` | вся запись в последний шард |
| Есть в запросах | `order_id`, когда ищут по `user_id` | каждый запрос — scatter-gather |
| Не меняется | `region` пользователя | смена значения = перенос данных |
| Нет доминирующего значения | `tenant_id` при одном гигантском тенанте | горячий шард |

**3. Механизм распределения.** Рекомендуемая схема:

```text
key ──hash──► slot (0..4095) ──routing table──► physical shard (db-01..db-08)
```

- число слотов фиксировано и с большим запасом (в 100–1000 раз больше текущего числа шардов) — его нельзя менять дёшево;
- таблица `slot → shard` маленькая, хранится в конфигурации/etcd/БД и кэшируется в приложении;
- для китов — directory-оверрайд: `tenant_id → dedicated shard`, проверяется перед хэшем.

Так устроены Redis Cluster (16 384 слота), Citus (шарды-таблицы, перемещаемые между узлами), Vitess (keyspace ranges, которые можно делить), Cassandra (vnodes на кольце consistent hashing).

**4. Что делать с запросами не по ключу.**

- глобальные вторичные индексы: отдельная таблица/сервис `email → user_id`, шардированная по своему ключу и обновляемая асинхронно из CDC;
- аналитика и поиск — не по шардам, а в отдельной системе (ClickHouse, OpenSearch), наполняемой потоком изменений;
- справочники — реплицируются на все шарды (reference tables в Citus).

**5. Когда нужен решардинг.** Сигналы: шард приближается к пределу по диску, CPU или IOPS; горячий слот или тенант; ожидаемый рост за горизонт планирования (6–12 месяцев). Решардинг надо начинать заранее — при 50–60% утилизации, потому что сам перенос нагружает исходный шард.

**6. Варианты решардинга.**

| Ситуация | Действие |
| --- | --- |
| Слоты есть, нужны новые узлы | перенос части слотов на новые шарды (самый дешёвый случай) |
| Схема `hash % N` без слотов | переход на слоты — фактически полная миграция всех данных |
| Горячий тенант | вынести в выделенный шард через directory |
| Горячий ключ внутри тенанта | менять модель данных: дробить ключ (`counter#0..15`), агрегировать асинхронно |
| Ошибся ключом шардирования | новая схема рядом, двойная запись/CDC, постепенный перевод чтения — по сути новая БД |

Процедура переноса без простоя (копирование, догоняющая репликация, переключение) — отдельная тема, но для её возможности важно, чтобы маршрутизация шла через таблицу, а не через формулу в коде.

**7. Если можно не шардировать — не шардируйте.** Сначала вертикальное масштабирование (современный сервер с 1–2 ТБ RAM и NVMe держит очень многое), реплики для чтения, партиционирование, архивирование холодных данных, разделение БД по доменам. Шардирование ломает JOIN, внешние ключи, глобальные уникальные индексы и транзакции — эту цену платят навсегда.

**Компромиссы.** Hash-слоты дают равномерность, но убивают range-запросы по ключу; range-шардирование сохраняет их, но требует постоянного деления горячих диапазонов. Directory даёт максимальную гибкость ценой дополнительного поиска и ещё одной критичной системы.

## Как перешардировать данные без простоя?

```yaml
category: system-design
level: senior
difficulty: 5
slug: system-design-senior-kak-pereshardirovat-dannye-bez-prostoya
tags: sharding, migration
```

Переносить данные небольшими единицами (слот, тенант, диапазон ключей) по схеме «копия + догоняющая репликация + короткое переключение»: сначала снять снапшот и скопировать в новый шард, затем непрерывно применять изменения через CDC, сверить данные, на секунды заблокировать запись по переносимой единице, дождаться нулевого отставания, переключить маршрутизацию и разблокировать. Пользователи видят в худшем случае короткую паузу записи по малой части ключей, а не простой системы.

**Предпосылка.** Маршрутизация через таблицу `slot/tenant → shard`, которую приложение читает и умеет быстро обновлять. Если шард вычисляется формулой `hash % N` в коде, сначала нужно ввести слой маршрутизации — без него переносить можно только всё и сразу.

**Процедура для одной единицы (например, слота 1234 с shard-03 на shard-09).**

```text
1. snapshot+copy     shard-03 ──(COPY по slot=1234, консистентный снапшот)──► shard-09
2. catch-up          shard-03 ──(logical replication / Debezium, фильтр slot=1234)──► shard-09
3. verify            сравнить количество строк и checksums по диапазонам ключей
4. freeze            routing: slot 1234 = migrating → запись отклоняется/ждёт (секунды)
5. drain             дождаться lag = 0 по LSN
6. switch            routing: slot 1234 → shard-09, версия таблицы маршрутизации ++
7. unfreeze          запись идёт в shard-09
8. cleanup           через N дней удалить данные слота на shard-03
```

**Детали, на которых всё ломается.**

**1. Консистентная точка старта.** Копирование и начало CDC должны быть согласованы: в PostgreSQL — создать слот логической репликации с экспортом снапшота и копировать данные в этом снапшоте, тогда CDC продолжит ровно с той же точки. Debezium делает это сам (initial snapshot + streaming).

**2. Применение изменений — идемпотентно.** Upsert по первичному ключу и удаление по ключу: повторное применение события не портит данные.

**3. Freeze и устаревшая маршрутизация.** У сотен подов может быть закэширована старая таблица. Варианты:

- версия маршрутизации в каждом запросе к БД, а на старом шарде — проверка «слот больше не мой» (флаг в таблице слотов на самом шарде) с ошибкой, по которой клиент обновляет маршруты и повторяет — это fencing;
- запись на время freeze ставится в ожидание на сотни миллисекунд, а не отклоняется, — клиенты видят задержку, а не ошибку.

**4. Транзакции через границу слота.** Если транзакция трогает ключи из двух слотов на одном шарде, после переноса она становится межшардовой. Ключ шардирования должен быть выбран так, чтобы этого не происходило; иначе такие операции на время миграции блокируются.

**5. Последовательности и уникальные ограничения.** Автоинкрементные ID на разных шардах конфликтуют — нужны глобальные ID (UUIDv7, Snowflake). Глобальная уникальность (email) не может проверяться на шарде.

**6. Нагрузка.** Копирование и CDC нагружают исходный шард, который и так перегружен — поэтому решардинг начинают заранее, копирование троттлят и делают в часы низкой нагрузки, переносят слоты по одному или небольшими партиями.

**7. Откат.** До cleanup старые данные на месте. Если после переключения что-то не так — переключить обратно, но изменения, сделанные на новом шарде, должны вернуться: обратная CDC-репликация с нового шарда на старый на период наблюдения делает откат безопасным.

**Альтернатива — dual write.** Приложение пишет в старый и новый шард, фоновый процесс докопирует историю, затем чтение переводится на новый. Проще в инфраструктуре, но опаснее: нет атомарности двух записей, расхождения при сбоях, и нужна сверка. CDC-подход предпочтительнее, потому что источник истины один до самого переключения.

**Готовые инструменты.** Citus (`citus_move_shard_placement` с логической репликацией и короткой блокировкой записи в конце), Vitess (`MoveTables`/`Reshard` с VReplication и `SwitchTraffic`), Redis Cluster (`MIGRATE` слотов с перенаправлением `ASK`/`MOVED`), MongoDB balancer. Если они подходят, лучше использовать их, чем писать свою миграцию.

**Наблюдаемость процесса.** Прогресс копирования, отставание CDC, результаты сверки, длительность freeze, ошибки маршрутизации — с автоматической остановкой миграции при росте латентности продового трафика.

## Как спроектировать кэш на десятки терабайт и что делать при потере кластера?

```yaml
category: system-design
level: senior
difficulty: 5
slug: system-design-senior-kak-sproektirovat-kesh-na-desyatki-terabait-i-chto-delat-pri-potere-kl
tags: caching, scalability
```

Кэш на десятки терабайт держать целиком в RAM дорого и операционно тяжело, поэтому его строят многоуровневым: горячее подмножество — в памяти, остальное — на NVMe (flash-кэш), шардирование по ключу на сотни узлов с репликами в разных зонах. Потеря кластера при таком размере — главная угроза: бэкенд, рассчитанный на 5% промахов, внезапно получает 100% трафика. Поэтому дизайн обязан включать защиту источника и процедуру прогрева, а не только саму топологию.

**1. Сначала проверить, кэш ли это.** Если данные нельзя потерять или их невозможно пересчитать за разумное время, это хранилище (Cassandra, ScyllaDB, DynamoDB), а не кэш. Дальше — допущение, что источник истины существует и всё можно восстановить.

**2. Оценки для 30 ТБ.**

- Redis на узел практично держать 25–50 ГБ: больше — медленнее full resync реплики и fork при снапшотах. 30 ТБ / 50 ГБ = 600 мастеров, с репликами — 1200 процессов. Redis Cluster рекомендован примерно до 1000 узлов — упираемся в предел;
- распределение доступа почти всегда степенное: часто 5–10% ключей дают 90% обращений. 3 ТБ горячего в RAM + 27 ТБ на NVMe закрывают ту же нагрузку в разы дешевле;
- восстановление с нуля из источника на скорости 1 ГБ/с: 30 000 ГБ / 1 ГБ/с = 30 000 с ≈ 8.3 часа. Это и есть горизонт, на который систему нужно защищать после потери кэша.

**3. Топология.**

```text
App pods ──► L1: in-process (HybridCache / MemoryCache), секунды, самые горячие ключи
   │
   └──► роутер (клиентское consistent hashing / mcrouter / Envoy)
            │
            ├──► пул A (зона 1): RAM-уровень + flash-уровень, N шардов
            ├──► пул B (зона 2): реплика пула A
            └──► пул C (зона 3): реплика
```

Варианты технологий: Memcached с extstore (значения на NVMe, ключи в RAM), CacheLib-подобные гибридные кэши, Aerospike, Redis Enterprise с tiering. Выбор диктуют размер значений и требования к структурам данных: для простых blob по ключу хватает Memcached-класса.

**4. Шардирование и отказ узла.** Consistent hashing с виртуальными нодами: потеря одного узла из 600 делает промахами ~1/600 ключей, нагрузка на источник растёт незаметно. Facebook в своей архитектуре memcache использовал «gutter pool» — небольшой резервный пул, принимающий ключи упавших серверов с коротким TTL, чтобы не перераспределять их по кольцу и не смещать нагрузку.

**5. Потеря целого кластера — сценарий и защита.**

- **Не один кластер.** Независимые реплики в разных зонах; клиент при недоступности основного пула читает из другого. Потеря зоны превращается в увеличение латентности, а не в холодный кэш.
- **Защита источника — до восстановления, а не после.** Лимит конкурентности и rate limit на запросы к БД при промахах, приоритет критичных запросов, request coalescing (один запрос в БД на ключ), отдача устаревших данных из L1, где допустимо. Без этого БД падает за секунды.
- **Прогрев из соседнего кластера (cold cluster warmup).** Новый кластер при промахе сначала читает из тёплого кластера-соседа, а не из БД; трафик переводится постепенно — 1%, 5%, 25%, 100% — по мере роста hit rate.
- **Снапшоты.** Периодические снапшоты на диск/S3 (RDB для Redis, persistent flash для гибридных кэшей) позволяют поднять кэш тёплым за минуты вместо часов; при рестарте узла flash-кэш переживает перезагрузку процесса.
- **Прогрев по журналу доступа.** Список топ-N ключей за последний час выгружается и подгружается в новый кластер до переключения трафика.
- **Деградация функциональности** флагами: отключить тяжёлые некритичные страницы, пока hit rate не восстановится.

**6. Консистентность.** На таком размере инвалидация — через поток изменений (CDC → Kafka → удаление ключей), TTL как страховка. Удалять, а не перезаписывать, чтобы не получить гонку старого и нового значения.

**7. Наблюдаемость.** Hit rate по пулам и префиксам ключей, eviction rate, доля горячих ключей, латентность p99 на уровне клиента, нагрузка на источник при промахах. Алерт на падение hit rate важнее алерта на падение узла.

**Компромиссы.** Flash-уровень — латентность сотни микросекунд вместо десятков и меньшая пропускная способность на узел, зато цена за гигабайт в разы ниже. Несколько реплик кэша удваивают-утраивают стоимость, но превращают самую опасную аварию — холодный старт — в штатную ситуацию.

## Как предотвратить cache stampede при инвалидации популярного ключа?

```yaml
category: system-design
level: senior
difficulty: 5
slug: system-design-senior-kak-predotvratit-cache-stampede-pri-invalidacii-populyarnogo-klyucha
tags: caching, resilience
```

Cache stampede (dogpile, thundering herd) — когда ключ, который читают тысячи раз в секунду, исчезает из кэша, и все эти запросы одновременно идут пересчитывать значение в БД. Защита строится на трёх идеях: пересчитывает один (request coalescing / lease), остальные получают устаревшее значение, пока идёт пересчёт (stale-while-revalidate), и популярные ключи вообще не должны «умирать» — их обновляют заранее или в фоне, а инвалидация заменяет значение, а не удаляет его.

**Масштаб проблемы.** Ключ читают 20k RPS, пересчёт занимает 200 ms. За время пересчёта в БД придут 20 000 × 0.2 = 4 000 одинаковых тяжёлых запросов. Они замедляют БД, пересчёт идёт дольше, приходят новые — положительная обратная связь.

**1. Request coalescing внутри процесса.** Сотни одновременных запросов на одном поде ждут одну задачу. В .NET 9+ `HybridCache.GetOrCreateAsync` делает это из коробки; вручную — `ConcurrentDictionary<string, Lazy<Task<T>>>`. Это снижает нагрузку с «число запросов» до «число подов» — при 100 подах всё ещё 100 запросов в БД.

**2. Распределённый lease.** Только получивший lease пересчитывает значение, остальные ждут или берут устаревшее:

```csharp
var token = Guid.NewGuid().ToString();
if (await db.StringSetAsync($"lock:{key}", token, TimeSpan.FromSeconds(5), When.NotExists))
{
    try
    {
        var fresh = await LoadFromDatabaseAsync(id);
        await db.StringSetAsync(key, Serialize(fresh), TimeSpan.FromMinutes(10));
        return fresh;
    }
    finally
    {
        await db.ScriptEvaluateAsync(
            "if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) end return 0",
            new RedisKey[] { $"lock:{key}" }, new RedisValue[] { token });
    }
}
return await WaitForValueOrStaleAsync(key);
```

TTL у lease обязателен (пересчитывающий может упасть), удаление — только своего токена. Facebook решал ту же задачу механизмом leases в memcache: при промахе сервер выдаёт токен только одному клиенту, остальные ненадолго ждут.

**3. Stale-while-revalidate — soft и hard TTL.** Хранить значение дольше, чем оно считается свежим:

```text
value + fresh_until (soft, 60 с) ; TTL ключа в Redis (hard, 10 мин)
now < fresh_until        → отдать
fresh_until ≤ now < hard → отдать устаревшее + один фоновый пересчёт (под lease)
ключа нет                → синхронный пересчёт под lease
```

Пользователи почти никогда не ждут пересчёта, а БД получает один запрос на ключ.

**4. Вероятностное раннее обновление (XFetch).** Каждый запрос с небольшой вероятностью, растущей к моменту истечения, пересчитывает значение заранее: обновить, если `now − Δ·β·ln(rand()) ≥ expiry`, где Δ — время пересчёта, β ≈ 1. Без блокировок и координации: в среднем ключ обновляет один запрос незадолго до истечения.

**5. Инвалидация обновлением, а не удалением.** Когда изменение популярного объекта приходит из CDC/события, консьюмер не делает `DEL`, а пересчитывает и записывает новое значение (или помечает текущее как устаревшее, сдвигая `fresh_until` в прошлое — тогда сработает схема из п. 3). Ключ не исчезает ни на миг.

**6. Jitter TTL.** Значения, записанные одновременно (прогрев, деплой), не должны истекать одновременно: `TTL = base × random(0.9, 1.1)`.

**7. Защита источника последним рубежом.** Лимит конкурентности на пересчёты конкретного типа (bulkhead), circuit breaker к БД, отдача устаревшего при ошибке пересчёта (stale-if-error).

**Что выбрать.**

| Ситуация | Решение |
| --- | --- |
| Умеренная нагрузка, один-два пода | coalescing внутри процесса |
| Горячие ключи, много подов | soft/hard TTL + распределённый lease |
| Нельзя отдавать устаревшее | lease + ожидание результата с таймаутом |
| Известные топ-ключи | фоновое обновление по расписанию, ключ без истечения |

**Компромиссы.** Stale-while-revalidate означает, что пользователи короткое время видят старые данные — для цены в момент оплаты это недопустимо (её берут из БД), для карточки товара — нормально. Lease добавляет круг к Redis и сложность на случай падения держателя lease.

## Как решать конфликт между consistency и availability в оплате заказа?

```yaml
category: system-design
level: senior
difficulty: 5
slug: system-design-senior-kak-reshat-konflikt-mezhdu-consistency-i-availability-v-oplate-zakaza
tags: consistency, architecture
```

Не выбирать одну букву для всей системы, а разделить процесс оплаты на шаги и для каждого решить, что дороже — отказать клиенту или допустить временную несогласованность, которую потом можно исправить. Само движение денег (списание, возврат) всегда консистентно: лучше отказать, чем списать дважды или списать без заказа. А всё вокруг (приём заказа, резерв, проверки, уведомления) можно делать доступным, если есть механизм компенсации и сверки, который приводит систему в согласованное состояние позже.

**Шаги и выбор для каждого.**

| Шаг | Что важнее | Почему | Поведение при сбое |
| --- | --- | --- | --- |
| Приём заказа | A | потерянная продажа — прямые деньги | заказ создаётся в `pending_payment`, даже если склад или антифрод медленные |
| Резерв товара | зависит от товара | оверселл одного из 10 000 vs отказ всем | для массового товара — принять и компенсировать, для уникального (билет на место) — C |
| Антифрод | A с ограничением риска | лежащий антифрод не должен останавливать продажи | fallback-правила: малые суммы пропускать, крупные — отложить |
| Авторизация/списание | C | двойное списание и списание без учёта — регуляторный и репутационный ущерб | при неизвестном исходе — ждать и выяснять, а не повторять |
| Обновление статуса заказа | eventual | может отставать на секунды | события через outbox, идемпотентные консьюмеры |
| Уведомления | A, eventual | вторичны | ретраи позже |

**Ключевые приёмы.**

**1. Неизвестный исход — отдельное состояние.** Таймаут ответа провайдера — это не «ошибка», а `unknown`. Ответ клиенту: «платёж обрабатывается», фоновая задача запрашивает статус у провайдера по нашему ID. Повторная попытка списания с новым ключом в этот момент — классический путь к двойному списанию.

**2. Авторизация вместо списания.** Холд денег при оформлении, списание (capture) — когда склад подтвердил резерв. Если резерв не удался — отмена холда, а не возврат денег: дешевле и быстрее для клиента. Это позволяет делать резерв асинхронным (A), не рискуя деньгами клиента.

**3. Компенсация вместо блокировки.** Если допустили оверселл — автоматический возврат и извинение с бонусом. Бизнес считает: стоимость редкой компенсации обычно меньше потерь от отказов при каждой задержке склада.

**4. Квоты для инвариантов.** Если нужна жёсткая граница (не продать больше 1000 билетов) при высокой доступности — разбить остаток на квоты по узлам/регионам: каждый продаёт свою часть локально, без глобальной координации.

**5. Переключение провайдера — только после определённого отказа.** При деградации основного эквайринга новый платёж можно направить к резервному, но платёж в состоянии `unknown` у первого — нельзя: сначала выяснить статус, иначе два списания у двух провайдеров.

**6. Когда недоступна наша БД.** Деньги не списываются: без записи о платеже списание нельзя ни учесть, ни вернуть автоматически. Корректный ответ — честный отказ с предложением повторить, а не «спишем, а потом запишем».

**7. Страховочная сетка — сверка.** Ежедневно и почти в реальном времени сравнивать наши платежи с реестром провайдера: списано у провайдера, но нет у нас → привязать или вернуть; у нас успех, у провайдера нет → разобраться до отгрузки.

**CAP и сетевое разделение.** Если сервис оплаты отрезан от своей БД или от провайдера, он выбирает C: не проводит денежные операции. Если сервис заказов отрезан от сервиса оплаты — выбирает A: принимает заказ, оплата пройдёт, когда связь вернётся, или заказ отменится по таймауту.

**Что показать интервьюеру.** Что выбор — бизнес-решение с денежной оценкой обеих ошибок, что есть механизм возврата к консистентности (идемпотентность, саги, компенсации, сверка), и что граница «здесь — только C» проведена по движению денег, а не по всей системе.

## Спроектируйте систему обработки платежей с гарантией однократного списания

```yaml
category: system-design
level: senior
difficulty: 5
slug: system-design-senior-sproektiruite-sistemu-obrabotki-platezhei-s-garantiei-odnokratnogo-spi
tags: idempotency, architecture
```

Гарантию «списали ровно один раз» нельзя получить от сети — только от дизайна: один платёжный объект на одно намерение оплатить (уникальное ограничение в БД), один ключ идемпотентности на всю жизнь этого объекта, передаваемый провайдеру, машина состояний с явным состоянием «исход неизвестен», в котором запрещено повторять списание вслепую, и сверка с провайдером, которая находит и автоматически возвращает дубль, если все предыдущие уровни всё же пропустили его. На практике это at-least-once попытки + идемпотентность на каждом шаге + детекция.

**Где возникают дубли.**

```text
Клиент ──(двойной клик, ретрай)──► Order ──(ретрай HTTP)──► Payment ──(ретрай, таймаут)──► PSP
                                                               ▲
                     вебхуки PSP (повторная доставка) ─────────┤
                     воркер восстановления (повтор «зависших») ┤
                     переключение на резервного провайдера ────┘
```

Каждая стрелка — место, где один и тот же запрос может прийти дважды.

**1. Уровень намерения: один платёж на заказ.**

```sql
create table payments (
  id uuid primary key,
  order_id uuid not null,
  attempt int not null,
  amount bigint not null,
  currency char(3) not null,
  status text not null,
  provider text not null,
  provider_payment_id text,
  idempotency_key text not null unique,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);
create unique index payments_one_active_per_order
  on payments(order_id) where status not in ('failed', 'canceled');
```

Частичный уникальный индекс не даёт создать второй активный платёж на заказ, сколько бы раз ни пришёл запрос. Новая попытка (`attempt + 1`) возможна только после того, как предыдущая окончательно `failed` — например, банк отклонил карту.

**2. Уровень API: idempotency key.** Order Service передаёт ключ `order:{id}:attempt:{n}`; Payment API сохраняет ключ и ответ атомарно с созданием платежа и на повтор возвращает тот же ответ.

**3. Уровень провайдера.** Наш `idempotency_key` передаётся провайдеру в его механизм идемпотентности (у Stripe — заголовок `Idempotency-Key`, у ЮKassa — `Idempotence-Key`). Повтор с тем же ключом провайдер не исполнит второй раз, а вернёт результат первой попытки. Важно знать срок хранения ключей у провайдера (у Stripe — не менее 24 часов) и не ретраить дольше.

**4. Машина состояний с `unknown`.**

```text
created ─► sending ─► authorized ─► captured ─► (refunded)
              │
              ├─► declined  (определённый отказ → можно новую попытку)
              └─► unknown   (таймаут/5xx/обрыв) ─► опрос статуса у PSP ─► authorized | declined
```

Правила:

- переход в `sending` фиксируется в БД **до** вызова провайдера — после падения процесса мы знаем, что вызов мог состояться;
- из `sending`/`unknown` разрешено только выяснение статуса (`GET payment by our id`) или повтор **с тем же ключом**, никогда не новый ключ;
- переходы — условным `UPDATE ... WHERE status = @expected`, конкурирующие воркер восстановления и вебхук не перезапишут друг друга.

**5. Вебхуки и события.** Дедупликация по `provider_event_id` (уникальный индекс в `payment_events`), обработка — идемпотентный переход состояния; публикация в Kafka через outbox, консьюмеры с inbox.

**6. Переключение провайдера.** Разрешено для новой попытки только из определённого состояния `declined`/`failed` или после того, как опрос подтвердил, что первый провайдер платёж не провёл. Платёж в `unknown` у провайдера A никогда не отправляется провайдеру B.

**7. Двухфазное списание.** Авторизация при оформлении, capture при отгрузке — capture тоже идемпотентен (ключ `capture:{payment_id}`), а частичный capture считается по сумме, уже зафиксированной в ledger.

**8. Ledger.** Неизменяемый журнал двойной записи с уникальностью по `(payment_id, operation)`: даже если код дважды попытается записать списание, вторая проводка не пройдёт.

**9. Сверка — последний рубеж.** Регулярно (реестры провайдера ежедневно, API — почти в реальном времени) сравнивать операции провайдера с нашими: два списания на один заказ → автоматический возврат лишнего и алерт; списание без платежа у нас → привязать к заказу или вернуть.

**Нагрузка и надёжность.** Объёмы обычно небольшие (сотни платежей в секунду в пике) — одна PostgreSQL с синхронной репликой в другой зоне (RPO = 0: потеря записи о вызове провайдера опасна). Отдельные пулы и circuit breaker на каждого провайдера.

**Что сказать о гарантиях честно.** Exactly-once по сети недостижим; достижимо «эффект ровно один раз» при условии идемпотентности провайдера, а там, где её нет, — минимальное окно риска плюс автоматическое обнаружение и возврат дублей. Интервьюер обычно ждёт именно этого разграничения.

## Спроектируйте систему отслеживания посылок на 10 миллионов событий в день

```yaml
category: system-design
level: senior
difficulty: 5
slug: system-design-senior-sproektiruite-sistemu-otslezhivaniya-posylok-na-10-millionov-sobytii-v
tags: architecture, throughput
```

10 миллионов событий в день — это в среднем всего ~116 событий в секунду, так что сложность не в объёме, а в характере потока: десятки разнородных источников, события приходят пачками, с опозданием, не по порядку и дважды, а читают их и люди, и B2B-клиенты, которые опрашивают API миллионами запросов. Архитектура: приём в Kafka без обработки, нормализация и дедупликация по ключу посылки, event log + материализованное текущее состояние, раздача через кэш и push (вебхуки, уведомления) вместо опроса.

**Оценки.**

- 10 млн / 86 400 ≈ 116 событий/с; но реестры перевозчиков выгружаются пачками по сотни тысяч строк, сканирование на сортировочных центрах — волнами по сменам. Проектируем приём на пик ×20 — ~2.5k/с — и буфер на всплески до миллиона событий;
- ~8 событий на посылку → ~1.25 млн новых посылок в день, активных одновременно (в пути 3–7 дней) — ~5–8 млн;
- событие ~500 байт → 5 ГБ/день, ~1.8 ТБ/год, с индексами ~3.5 ТБ; горячие данные — последние 90 дней, ~1 ТБ;
- чтение: ~10 проверок посылки людьми → 12.5 млн/день ≈ 145 RPS, вечерний пик ×5 ≈ 700 RPS; B2B-клиенты при опросе каждые 15 мин по всем активным посылкам дали бы 6 млн × 96 = 576 млн запросов/день ≈ 6.7k RPS — опрос нужно заменить вебхуками.

**Архитектура.**

```text
Источники:  сканеры/ТСД ─► Ingest API ─┐
            курьерские приложения ─────┤   (офлайн-буфер на устройстве)
            перевозчики: webhooks ─────┼──► Kafka: tracking.raw (key = tracking_no)
            перевозчики: polling ──────┤
            реестры (SFTP/S3) ─► parser┘
                                        │
                     Normalizer: маппинг кодов, дедупликация, валидация
                                        │
                              Kafka: tracking.events (нормализованные)
               ┌────────────────────────┼─────────────────────┬────────────────────┐
               ▼                        ▼                     ▼                    ▼
     State builder:             Event store              Subscriptions:        ETA / аналитика
     parcels(current state)     (PostgreSQL партиции     webhooks B2B,         (ClickHouse)
     PostgreSQL + Redis          по месяцам; архив S3)    push/SMS людям
               │
     Tracking API ◄── CDN/кэш (TTL 30–60 с) ◄── клиенты
```

**Ключевые решения.**

**1. Приём — тонкий и надёжный.** Ingest только валидирует формат и пишет в Kafka (`acks=all`), отвечает 202. Сырой поток хранится отдельно (topic retention 7 дней + S3) — при ошибке маппинга события можно переобработать.

**2. Порядок и конкурентность.** Ключ партиции — трек-номер: состояние посылки обновляет один консьюмер последовательно, без блокировок в БД. 24–48 партиций с запасом для параллелизма.

**3. Дедупликация.** У источников с ID — уникальность `(source, source_event_id)`; без ID — детерминированный хэш `(tracking_no, status_code, location, occurred_at)`. Окно дедупликации — в БД, а не в памяти консьюмера, чтобы переживать рестарты.

**4. Опоздавшие и неупорядоченные события.** Хронология строится по `occurred_at`; текущий статус — вычисляемая функция от всех событий с приоритетом этапов: опоздавшее «принято на сортировке» не откатывает «вручено». Статусы финальные (вручено, возвращено) — терминальны, после них допускаются только корректирующие события с ручным подтверждением.

**5. Хранение.**

```sql
tracking_events(tracking_no, occurred_at, status, location, source, source_event_id, raw jsonb)
  partition by range (received_at)
parcels(tracking_no pk, carrier, merchant_id, status, status_at, eta, last_event_at, version)
```

10 млн строк в день — комфортно для PostgreSQL с месячными партициями; старые партиции отсоединяются и выгружаются в Parquet на S3. Cassandra/ScyllaDB (partition key = трек-номер, clustering по времени) стоит рассматривать при росте на порядок или когда нужна многорегиональная запись.

**6. Раздача.** Страница трекинга — один запрос по ключу к `parcels` + последние события, кэш на 30–60 с (публичный ответ можно кэшировать на CDN по трек-номеру). B2B — подписка на вебхуки по `merchant_id` с ретраями, подписью HMAC и DLQ на клиента; опрос API — с жёстким rate limit.

**7. Уведомления.** Только на значимые переходы (передан курьеру, ожидает в пункте), с дедупликацией по `(tracking_no, status)` — дубли событий не должны давать дубли SMS.

**8. Неизвестные коды и мусорные данные.** Неизвестный код перевозчика — событие сохраняется как сырое, статус не меняется, алерт на рост доли нераспознанных. Посылка без событий дольше нормы для этапа — проактивный алерт «потерялась».

**Надёжность.** Kafka поглощает всплески и недоступность БД; State builder можно пересобрать из event log (replay), если сломался маппинг. Multi-AZ для Kafka и PostgreSQL; RPO по событиям ~0 благодаря `acks=all` и сырому архиву.

**Компромиссы.** Материализованное состояние — денормализация, требующая аккуратного порядка обработки, но делающая чтение тривиальным. Свежесть 30–60 секунд вместо реального времени снижает нагрузку на порядок и для трекинга посылок незаметна.

## Спроектируйте отказоустойчивый сервис уведомлений с приоритетами

```yaml
category: system-design
level: senior
difficulty: 5
slug: system-design-senior-sproektiruite-otkazoustoichivyi-servis-uvedomlenii-s-prioritetami
tags: architecture, resilience
```

Приоритеты в уведомлениях — это изоляция ресурсов, а не сортировка одной очереди: отдельные топики, пулы воркеров и квоты у провайдеров для каждого класса, чтобы маркетинговая рассылка на 10 миллионов адресов физически не могла задержать код входа. Отказоустойчивость — это несколько провайдеров на каждый критичный канал с автоматическим переключением, fallback на другой канал и сроки жизни сообщений: код подтверждения, доставленный через 10 минут, бесполезен.

**Классы приоритета.**

| Класс | Примеры | SLO доставки | При перегрузке |
| --- | --- | --- | --- |
| P0 | OTP, вход с нового устройства, сброс пароля | p99 < 5 с | никогда не задерживается, резерв мощности |
| P1 | заказ оплачен, курьер в пути | p99 < 1 мин | задерживается, но не теряется |
| P2 | маркетинг, дайджесты | часы | ставится на паузу первым |

**Оценки.** 100 млн уведомлений в день: P0 — 2 млн (~23/с, пик ~200/с), P1 — 30 млн (~350/с, пик ~2k/с), P2 — 70 млн, но кампаниями: 10 млн за час ≈ 2.8k/с. Суммарный пик ~5k/с. SMS-провайдер обычно даёт 100–500 сообщений/с на аккаунт — это главное ограничение, и именно здесь приоритеты решают.

**Архитектура.**

```text
Сервисы ──► Notification API (валидация, idempotency key, класс) ──► PostgreSQL outbox
                                                                          │
                              Kafka: notif.p0 | notif.p1 | notif.p2  ◄────┘
                                    │          │          │
                       Dispatcher P0  Dispatcher P1  Dispatcher P2   (отдельные consumer groups и пулы)
                       (настройки, шаблон, выбор канала, дедупликация)
                                    │
                  Kafka: send.{channel}.{priority}  (sms.p0, sms.p1, email.p2, push.p0 ...)
                                    │
           Channel senders: priority-aware rate limiter (Redis) ──► провайдеры A / B / C
                                    │
                    Delivery tracker: статусы, webhooks провайдеров, fallback, DLQ
```

**Почему не одна очередь с приоритетами.** Kafka не умеет приоритеты внутри топика; RabbitMQ умеет (`x-max-priority`), но если воркеры заняты долгими вызовами провайдера по P2, P0 всё равно ждёт свободного воркера. Отдельные топики + отдельные пулы воркеров + зарезервированная часть лимитов провайдера дают изоляцию гарантированно.

**Ключевые решения.**

**1. Квоты провайдера с резервом.** Лимит SMS-аккаунта 300/с делится: P0 гарантированно до 100/с, P1 — до 200/с, P2 — только остаток. Реализация — иерархический token bucket в Redis: P0 может брать и из общих токенов, P2 — только если остаток выше порога. P2 часто уходит на отдельный аккаунт или провайдера, чтобы не делить репутацию и лимиты.

**2. Мультипровайдерность и failover.** На каждый критичный канал — минимум два провайдера. Health score по доле ошибок и латентности в скользящем окне; circuit breaker переключает трафик на резервного. Для P0 допустим hedging: если провайдер не подтвердил приём за 3 с, отправить через второго — ценой редкого дубля OTP, что для кода приемлемо.

**3. Fallback по каналам.** Push не доставлен (нет токена, устройство офлайн) → SMS для P0; email-провайдер лёг → для P1 подождать и повторить, а не слать SMS (дорого).

**4. TTL сообщений.** У каждого уведомления `expires_at`: OTP — 5 минут, «курьер подъезжает» — 30 минут. Просроченные выбрасываются при отправке, а не доставляются через час после восстановления провайдера — иначе после аварии пользователи получат лавину бессмысленных сообщений.

**5. Идемпотентность.** Ключ от продюсера (`login:{sessionId}:otp`), дедупликация в dispatcher; перед вызовом провайдера проверяется статус доставки; статус `sending` фиксируется до вызова.

**6. Backpressure и load shedding.** При росте lag P1 автоматически ставятся на паузу кампании P2; при критической перегрузке P2 откладывается целиком. Решение принимается по метрикам lag в секундах для каждого класса.

**7. Надёжность приёма.** API пишет в PostgreSQL outbox и сразу отвечает; при недоступности Kafka заявки не теряются. Kafka и воркеры — в трёх зонах; P0-путь масштабируется с запасом ×3 от пика, потому что его объём мал.

**8. Наблюдаемость.** Время от запроса до подтверждения провайдером по классам и каналам, доля доставленных (по delivery reports), стоимость по провайдерам. SLO P0 — с алертом по burn rate; синтетическая отправка OTP на тестовые номера раз в минуту через каждого провайдера — так узнают о проблеме провайдера до пользователей.

**Компромиссы.** Резервирование мощности и квот под P0 означает, что часть ресурсов простаивает, а маркетинг идёт медленнее. Hedging и fallback повышают доставляемость критичных сообщений ценой редких дублей и стоимости — для P0 это правильный обмен, для P2 нет.

## Как спроектировать хранение и раздачу пользовательских файлов на петабайты?

```yaml
category: system-design
level: senior
difficulty: 5
slug: system-design-senior-kak-sproektirovat-hranenie-i-razdachu-polzovatelskih-failov-na-petabai
tags: storage, scalability
```

На петабайтах задача распадается на три независимо масштабируемые части: объектное хранилище для байтов (S3 или собственный Ceph/MinIO с erasure coding), шардированное хранилище метаданных для миллиардов записей о файлах и CDN для раздачи. Главными становятся не архитектурные схемы, а экономика (стоимость гигабайта в месяц и исходящего трафика), долговечность данных и жизненный цикл: файлы стареют и должны автоматически уходить на дешёвые уровни хранения.

**Оценки (пример).**

- хранится 5 ПБ, прирост 2 ПБ в год → 2 000 ТБ / 365 ≈ 5.5 ТБ/день ≈ 63 МБ/с входящих в среднем;
- средний файл 2 МБ → 5.5 ТБ / 2 МБ ≈ 2.75 млн загрузок в день ≈ 32/с, пик ×5 — ~160/с;
- объектов: 5 ПБ / 2 МБ = 2.5 млрд; метаданные по ~1 КБ → 2.5 ТБ — больше, чем удобно держать в одном PostgreSQL;
- раздача: если скачивают в 10 раз больше, чем загружают, — 55 ТБ/день ≈ 640 МБ/с ≈ 5 Гбит/с в среднем, пик ×3 ~15 Гбит/с. Это работа CDN, origin должен видеть малую долю.

**Архитектура.**

```text
Upload:   Client ─► API (auth, квоты, presigned multipart) ─► Object storage (hot tier)
                         │                                       │ событие ObjectCreated
                         ▼                                       ▼
                 Metadata store (шарды по owner_id)      Kafka ─► обработка: антивирус, превью,
                                                                  хэш, перекодирование видео
Download: Client ─► CDN (signed URL/cookie) ─miss─► origin shield ─► Object storage
Lifecycle: hot (SSD/Standard) ─30 дней─► warm (Infrequent Access) ─180 дней─► cold (архив)
```

**1. Хранилище байтов: облако или своё.**

| | Облачный S3 | Свой Ceph RGW / MinIO |
| --- | --- | --- |
| Стоимость | порядка десятков долларов за ТБ в месяц в стандартном классе + плата за egress | железо, ЦОД, команда; дешевле на масштабе ПБ при стабильном росте |
| Долговечность | заявлены «одиннадцать девяток» | зависит от конфигурации и эксплуатации |
| Эксплуатация | нет | дежурства, замена дисков, ребалансировка |

На своём железе — erasure coding вместо тройной репликации: схема 8+3 переживает потерю 3 дисков/узлов при избыточности 11/8 ≈ 1.375×, против 3× у репликации. Для 5 ПБ это ~6.9 ПБ сырой ёмкости вместо 15 ПБ. Ценой — больше CPU и сетевого трафика при восстановлении, поэтому горячие маленькие объекты иногда хранят с репликацией.

**2. Метаданные.** 2.5 млрд записей и десятки тысяч запросов в секунду — шардированный PostgreSQL (Citus или шардирование в приложении) по `owner_id`: почти все запросы — «файлы этого пользователя/папки». Объектный ключ генерируется (`{shard}/{uuid}`), не зависит от имени — переименование и перемещение не трогают байты. Альтернативы при ещё большем масштабе — FoundationDB, Cassandra.

**3. Дедупликация.** Content-addressed хранение (ключ = SHA-256 содержимого, или чанков по 4–8 МБ) экономит место на одинаковых файлах и делает докачку тривиальной. Цена: подсчёт ссылок для удаления, сложности с шифрованием per-user и риск утечки факта существования файла. Обычно делают в пределах одного пользователя/тенанта.

**4. Раздача.** Только через CDN с подписанными URL или cookies с коротким сроком; origin shield — промежуточный уровень кэша, чтобы промахи сотен PoP не били в хранилище. Range-запросы для видео и больших файлов. Превью и варианты изображений — генерация при первом запросе с кэшированием, а не заранее во всех размерах.

**5. Жизненный цикл и стоимость.** Обычно 80–90% обращений приходится на файлы младше месяца. Lifecycle-правила переводят старые объекты в более дешёвые классы, но у холодных классов есть плата за извлечение и минимальный срок хранения — переводить нужно по статистике доступа, а не «всё старше 30 дней». Отдельно — удаление незавершённых multipart и версий.

**6. Долговечность и целостность.** Хэш при загрузке, сверяемый хранилищем; фоновая проверка (scrubbing) в собственном хранилище; репликация критичных бакетов в другой регион; защита от удаления (versioning, object lock) от ошибок и атак; регулярная сверка метаданных и объектов — «сироты» в хранилище стоят денег, записи без объектов ломают UX.

**7. Удаление по требованию (GDPR и аналоги).** Удаление должно доходить до всех копий: версий, реплик, кэша CDN (purge), бэкапов метаданных. При дедупликации — только после обнуления счётчика ссылок. Распространённый приём — crypto-shredding: каждый пользователь шифруется своим ключом, удаление ключа делает все копии нечитаемыми.

**Компромиссы.** Облако избавляет от эксплуатации, но на петабайтах egress и хранение становятся главной статьёй расходов; собственное хранилище дешевле, но требует команды и зрелых процессов. Дедупликация и холодные классы снижают стоимость ценой сложности и латентности доступа к старым файлам.

## Как построить систему, переживающую недоступность PostgreSQL в течение 10 минут?

```yaml
category: system-design
level: senior
difficulty: 5
slug: system-design-senior-kak-postroit-sistemu-perezhivayuschuyu-nedostupnost-postgresql-v-teche
tags: resilience, architecture
```

Десять минут — дольше, чем любой ретрай и автоматический failover, поэтому «переждать» не получится: система должна уметь работать без основной БД. Для этого операции делятся на классы: чтения обслуживаются из независимых копий (кэш, read-модели, реплики), записи, которые можно применить позже, принимаются в надёжный журнал (Kafka) и применяются после восстановления, а операции, требующие немедленной консистентности (деньги, уникальные ресурсы), честно отклоняются. Плюс аккуратное восстановление, чтобы накопленная очередь и ретраи не уронили базу повторно.

**Когда это реально случается.** Автоматический failover не сработал или сработал неверно и нужен ручной разбор; повреждение данных и PITR; мажорное обновление PostgreSQL; исчерпание диска или transaction ID wraparound; сетевое разделение.

**1. Инвентаризация зависимостей.** Пройти по всем эндпоинтам и фоновым процессам и записать, что из PostgreSQL каждому нужно. Скрытые зависимости ломают всё сильнее явных: аутентификация (сессии в БД), feature flags и конфигурация, справочники, rate limits, миграции при старте пода.

**2. Классификация операций.**

| Класс | Примеры | Поведение без БД |
| --- | --- | --- |
| Чтение, терпящее устаревание | каталог, профиль, история заказов | Redis, read-модели в другом хранилище, асинхронная реплика (если упал только primary) |
| Запись, применимая позже | лайки, просмотры, отзывы, изменение настроек, создание заказа без оплаты | принять в Kafka с idempotency key, ответ «принято», применить после |
| Запись с немедленной проверкой | оплата, бронирование последнего места, регистрация уникального логина | 503 с понятным сообщением и `Retry-After` |
| Фоновые задачи | рассылки, отчёты, пересчёты | пауза по circuit breaker |

**3. Чтение без PostgreSQL.**

- кэш с `stale-if-error`: при ошибке БД отдавать устаревшее значение дольше обычного TTL;
- read-модели для ключевых экранов (OpenSearch, Redis, отдельная БД), наполняемые из CDC — они не зависят от доступности primary;
- аутентификация — JWT, проверяемый по публичному ключу без похода в БД; отзыв токенов — короткий срок жизни + denylist в Redis;
- конфигурация и флаги — локальный кэш в поде с последним известным значением.

**4. Запись без PostgreSQL — журнал намерений.**

```text
обычный путь:      API ─► PostgreSQL (данные + outbox) ─► Kafka
деградированный:   API ─► Kafka: deferred-commands (idempotency key, полная команда) ─► 202 Accepted
восстановление:    Replayer ─► PostgreSQL (идемпотентно, с ограничением скорости)
```

Порядок применения — по ключу сущности (партиционирование по ключу). При применении часть команд может не пройти валидацию (товар закончился, конфликт версии) — значит, нужна компенсация и уведомление пользователя. UX должен честно говорить «заказ принят, подтвердим в течение нескольких минут».

Объём: 10 минут × 500 записей/с = 300 000 команд — для Kafka это ничто, для PostgreSQL при восстановлении — несколько минут нагрузки, если не ограничивать скорость.

**5. Переключение режима.** Circuit breaker на уровне доступа к БД переводит приложение в деградированный режим автоматически; дополнительно — ручной флаг, чтобы дежурный мог включить режим заранее (плановые работы). Liveness-пробы не зависят от БД, поэтому поды не перезапускаются.

**6. Восстановление — самая опасная фаза.**

- поды открывают соединения постепенно (PgBouncer с ограничением `default_pool_size`), а не все сразу;
- replayer применяет накопленное с ограниченной скоростью, оставляя ресурсы живому трафику;
- выход из деградации по half-open: сначала доля запросов, затем весь трафик;
- кэш не сбрасывать — он сейчас главная защита БД.

**7. Сократить сами 10 минут.** Patroni с репликами в разных зонах, синхронная реплика для RPO=0, регулярные switchover-учения, мониторинг disk space и wraparound — большинство длительных простоев начинаются с давно видимых симптомов.

**8. Проверка.** Game day: отключить БД на стенде на 10 минут под нагрузкой, затем в проде в окно низкой нагрузки для отдельных сервисов. Измерить: долю успешных запросов, корректность применения отложенных команд, время возврата в нормальный режим.

**Компромиссы.** Деградированный путь — второй путь записи, который нужно тестировать и поддерживать; ошибки в нём проявляются только в аварию. Поэтому его ограничивают самыми ценными для бизнеса операциями, а всё остальное честно отклоняют.

## Что произойдёт при недоступности Redis и как заранее спроектировать деградацию?

```yaml
category: system-design
level: senior
difficulty: 5
slug: system-design-senior-chto-proizoidet-pri-nedostupnosti-redis-i-kak-zaranee-sproektirovat-de
tags: resilience, caching
```

Последствия зависят от того, для чего используется Redis, — и обычно он используется для большего, чем «просто кэш»: сессии, rate limiting, распределённые блокировки, idempotency keys, очереди, pub/sub. Без подготовки потеря Redis превращается в отказ всей системы: запросы висят на таймаутах клиента, а БД, внезапно получив весь трафик промахов кэша, падает следом. Деградацию проектируют заранее: для каждой роли Redis решить поведение без него, ограничить таймауты, защитить БД и сделать так, чтобы Redis не был источником истины ни для чего важного.

**Что происходит в первые секунды.**

1. `StackExchange.Redis` ждёт ответа до `syncTimeout`/`asyncTimeout` (по умолчанию 5 с) — каждый запрос, ходящий в кэш, становится на 5 секунд медленнее; при 2k RPS на под это тысячи висящих операций.
2. Промахи кэша идут в PostgreSQL: при hit rate 95% нагрузка на БД вырастает в 20 раз — БД насыщается за секунды.
3. Если пул потоков забит sync-over-async вызовами Redis, падают даже эндпоинты без Redis.
4. После возвращения Redis кэш пуст — второй удар по БД (cold start).

**Инвентаризация ролей и поведение без Redis.**

| Роль | Без Redis | Стратегия |
| --- | --- | --- |
| Кэш чтения | промахи → БД | L1 in-memory кэш (HybridCache), лимит конкурентности на БД, stale из L1, деградация тяжёлых страниц |
| Сессии | все разлогинены | JWT/подписанные cookie без серверного состояния, либо сессии в БД с L1-кэшем |
| Rate limiting | лимиты не работают | fail-open с локальным in-memory лимитером на под (лимит / число подов); для защиты логина от перебора — fail-closed или локальный строгий лимит |
| Распределённые блокировки | фоновые задачи не могут взять lock | пауза задач; корректность не должна зависеть от Redis-lock — уникальные ограничения и условные UPDATE в БД |
| Idempotency keys | риск дублей | для денежных операций ключи только в БД; Redis — лишь ускоряющий слой |
| Очереди / Streams | задачи не ставятся | важные задачи — в Kafka/outbox; Redis — только для эфемерных |
| Pub/Sub (инвалидация, websockets) | сообщения теряются | короткий TTL локального кэша как страховка, переподключение клиентов |
| Счётчики (просмотры) | теряются приращения | копить в памяти пода, сбросить позже; допустимая потеря |

**Технические меры.**

- **Короткие таймауты:** для кэша — 50–200 ms; ожидание кэша дольше, чем запрос в БД, бессмысленно. `abortConnect=false`, чтобы приложение стартовало без Redis.
- **Circuit breaker на Redis:** после серии ошибок сразу идти по fallback-пути без ожидания таймаута, периодически пробовать восстановить.
- **Защита БД:** семафор/bulkhead на запросы, которые обычно покрываются кэшем, request coalescing по ключу, приоритет критичных эндпоинтов; часть некритичных запросов отклонять, если БД насыщена.
- **L1 в процессе:** даже 5–10 секунд локального кэша для горячих ключей снимают основную нагрузку при отсутствии L2.
- **Health checks:** Redis не должен входить в liveness; в readiness — только если сервис без него бесполезен.

**Высокая доступность самого Redis.** Redis Cluster или Sentinel с репликами в разных зонах. Автоматический failover занимает секунды — порог определяется `cluster-node-timeout` (по умолчанию 15 с) или `down-after-milliseconds` у Sentinel (по умолчанию 30 с) плюс выборы; эти секунды приложение тоже должно переживать. Асинхронная репликация означает потерю последних записей при failover — ещё одна причина не хранить в Redis данные, которые нельзя потерять. Managed-сервисы (ElastiCache, Memorystore) упрощают эксплуатацию, но не отменяют деградационный дизайн.

**Восстановление.** Прогрев горячих ключей до возврата трафика (топ-N из журнала доступа или RDB-снапшот), постепенное закрытие circuit breaker, TTL с jitter, чтобы прогретые ключи не истекли одновременно.

**Проверка.** Регулярный тест «выключить Redis» на стенде под нагрузкой и замер: error rate, p99, нагрузка на БД, время восстановления. Ожидаемый результат — рост латентности и отключение второстепенных функций, но не отказ ключевых сценариев.

**Главный принцип.** Redis — ускоритель и координатор с допустимой потерей состояния. Всё, что должно пережить его потерю, имеет источник истины в другом месте.

## Как система должна вести себя при десятикратном росте нагрузки за час?


Система должна оставаться предсказуемой: stateless-слой автоматически масштабируется, а то, что не успевает или не умеет масштабироваться за час (БД, Kafka-партиции, внешние лимиты), защищено admission control — лишняя нагрузка отклоняется быстро и по приоритетам, а не превращается в таймауты для всех. Цель — продолжать обслуживать максимум, на который способна система, с полной скоростью для критичных сценариев, деградируя второстепенное, вместо того чтобы при перегрузке упасть до нуля.

**Арифметика роста.** 10× за 60 минут — это удвоение примерно каждые 18 минут (log₂10 ≈ 3.32; 60 / 3.32 ≈ 18). Скорость реакции компонентов:

| Компонент | Время реакции |
| --- | --- |
| HPA (метрики раз в 15 с) | десятки секунд на решение |
| Новый под .NET: pull образа, старт, прогрев | 30–90 с |
| Новая нода (Cluster Autoscaler / Karpenter) | 1–5 мин |
| Реплика PostgreSQL | десятки минут–часы (копирование данных) |
| Вертикальное увеличение БД | рестарт/failover, минуты простоя записи |
| Новые партиции Kafka, шарды Redis | ручная операция с ребалансировкой |
| Лимиты внешнего провайдера | дни, договор |

Вывод: за час автоматически масштабируется только stateless-слой. Stateful-компоненты должны иметь запас заранее, иначе они станут потолком.

**Поведение по уровням.**

**1. Поглощение запасом (первые минуты).** Нормальная утилизация 40–60% даёт ×1.5–2 без действий. Горячий кэш и CDN абсорбируют рост чтений.

**2. Автомасштабирование stateless.**

- HPA по RPS или concurrency на под (KEDA для консьюмеров — по lag), а не только по CPU: CPU растёт с задержкой и плохо отражает I/O-bound нагрузку;
- агрессивный scale-up (разрешить удвоение за период), медленный scale-down;
- запас нод (overprovisioning — низкоприоритетные placeholder-поды, которые вытесняются реальными), чтобы не ждать новые ноды;
- быстрый старт: ReadyToRun/Native AOT, прогрев в readiness probe (пулы соединений, кэши), маленькие образы.

**3. Защита stateful-компонентов — admission control.**

- лимит конкурентности на запросы к БД на каждом поде (общий бюджет соединений через PgBouncer не растёт с числом подов — иначе новые поды убьют БД);
- adaptive concurrency limits: сервис снижает допустимый параллелизм при росте латентности зависимостей;
- асинхронная запись через очередь (queue-based load leveling): API принимает, воркеры применяют с той скоростью, которую выдерживает БД; очередь растёт — пользователи получают «обрабатывается»;
- rate limiting по клиентам и API-ключам: один клиент не должен съесть ёмкость, нужную остальным.

**4. Приоритизация и деградация.**

- классы трафика: оформление заказа и оплата > каталог > поиск > рекомендации > аналитика;
- load shedding при насыщении — сначала отбрасывается низкий приоритет, быстрый `503` с `Retry-After`;
- feature flags отключают тяжёлые функции (персонализация, сложные фильтры, real-time счётчики);
- для предсказуемых всплесков (распродажа, продажа билетов) — виртуальная очередь (waiting room): пользователи входят с той скоростью, которую выдерживает система.

**5. Отличить рост от атаки.** 10× за час — это может быть успешная рекламная кампания, бот-скрапинг или DDoS. WAF, анализ распределения по клиентам и IP, bot management: масштабировать под атаку — дорого и бесполезно.

**6. Наблюдаемость и действия людей.** Алерт по скорости роста (а не только по абсолютному порогу) даёт дежурным время: заранее увеличить реплики консьюмеров, включить деградационные флаги, предупредить владельцев внешних интеграций. Runbook «пиковая нагрузка» с готовыми командами.

**7. Что заложить заранее.**

- нагрузочный тест с профилем роста ×10 за час (не только плато) — проверяет именно динамику автоскейлинга;
- запас по stateful-компонентам на ожидаемый пик + 30–50%;
- предварительное масштабирование перед известными событиями (pre-scaling по расписанию);
- лимиты квот облака и внешних провайдеров, согласованные заранее.

**Признак хорошего дизайна.** График «успешные запросы» растёт вместе с нагрузкой до потолка ёмкости и дальше остаётся на этом потолке (goodput стабилен), а не падает до нуля из-за каскадных таймаутов и ретраев.
