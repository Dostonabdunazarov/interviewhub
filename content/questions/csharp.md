## Чем `class` отличается от `struct`?

```yaml
category: csharp
level: middle
difficulty: 3
slug: csharp-chem-class-otlichaetsya-ot-struct
tags: value-types
```

`class` — ссылочный тип: переменная хранит ссылку на объект в управляемой куче, присваивание копирует ссылку. `struct` — значимый тип: переменная содержит сами данные, присваивание и передача в метод копируют их целиком. Из этого вытекают все остальные различия.

| | `class` | `struct` |
| --- | --- | --- |
| Семантика | ссылочная | значимая (копирование) |
| Размещение | отдельный объект в куче | там, где объявлена переменная или поле |
| Наследование | есть (кроме `sealed`) | нет, неявно `sealed`, базовый — `ValueType` |
| Интерфейсы | да | да (приведение к интерфейсу — boxing) |
| `null` | допустим | только через `Nullable<T>` |
| Конструктор без параметров | да | да с C# 10; `default(T)` всё равно даёт нули, минуя его |
| Финализатор | можно | нельзя |
| `Equals` по умолчанию | по ссылке | по полям (`ValueType.Equals`, медленно) |
| Оператор `==` | по ссылке | не определён, пока не перегружен |

```csharp
struct Counter { public int Value; public void Inc() => Value++; }

var list = new List<Counter> { new() };
// list[0].Inc();        // индексатор вернул копию — изменение потеряется
var c = list[0];         // копия
c.Inc();                 // list[0].Value всё ещё 0
```

**Цена копирования.** Большая структура, которая передаётся по значению, копируется на каждом вызове и возврате. Для крупных структур используют `in`/`ref readonly`, но лучше не делать их крупными: ориентир — до ~16–24 байт.

**Defensive copy.** Если у `readonly`-поля или `in`-параметра вызвать метод не-`readonly` структуры, компилятор сделает скрытую копию, чтобы не нарушить неизменяемость. Лечится `readonly struct` или `readonly`-методами.

**Когда выбирать `struct`:**

- тип маленький, логически одно значение (координата, `Money`, строго типизированный `OrderId`);
- неизменяемый — `readonly struct` или `readonly record struct`;
- создаётся в больших количествах, и аллокации в куче реально мешают (массив структур лежит одним непрерывным блоком без заголовков объектов).

Во всех остальных случаях — `class`. Изменяемая структура почти всегда ошибка дизайна: она ведёт себя «неожиданно» при копировании через свойства, индексаторы и `foreach`.

**Что спрашивают дальше:** где физически живёт структура (не «всегда в стеке»), когда она упаковывается, почему нужен `IEquatable<T>` для структур, что такое `ref struct` (`Span<T>`) — структура, которая гарантированно не попадёт в кучу.

## Что такое value type и reference type?

```yaml
category: csharp
level: middle
difficulty: 2
slug: csharp-chto-takoe-value-type-i-reference-type
tags: value-types
```

Это две категории типов CLR, которые различаются тем, что хранит переменная. У value type переменная содержит само значение, у reference type — ссылку на объект, живущий в управляемой куче.

**Какие типы к чему относятся:**

- **value types** — все примитивы (`int`, `double`, `bool`, `char`, `decimal`), `enum`, любые `struct` (`DateTime`, `Guid`, `TimeSpan`, `Nullable<T>`, `ValueTuple`), `record struct`;
- **reference types** — `class`, `record` (он же `record class`), `interface`, делегаты, массивы (даже `int[]`), `string`, `object`.

**Главное следствие — семантика присваивания.**

```csharp
DateTime a = DateTime.Now;
DateTime b = a;             // независимая копия

int[] x = { 1, 2, 3 };
int[] y = x;                // та же самая коллекция
y[0] = 42;                  // x[0] == 42
```

Передача в метод работает так же: value type копируется (если нет `ref`/`in`/`out`), для reference type копируется ссылка. Поэтому метод может изменить содержимое переданного объекта, но не может заменить сам объект у вызывающего — для этого нужен `ref`.

**Устройство в памяти.** Объект reference type в куче имеет заголовок (object header, используется для `lock` и хеша) и указатель на таблицу методов — на x64 это 16 байт накладных расходов плюс поля. Экземпляр value type — это только поля, без заголовка. Поэтому массив из миллиона `struct Point { int X, Y; }` — один объект размером ~8 МБ, а массив из миллиона `class Point` — массив ссылок плюс миллион отдельных объектов, которые GC должен обходить.

**Где появляются сюрпризы:**

- **boxing** — когда value type приводится к `object` или интерфейсу, в куче создаётся копия-обёртка;
- **изменение копии** — `list[0].X = 5` для списка структур не компилируется именно потому, что индексатор возвращает копию;
- **`null`** — value type не бывает `null`, для этого есть `Nullable<T>` (`int?`), который сам является структурой с флагом `HasValue`;
- **равенство** — у reference type по умолчанию сравниваются ссылки, у value type — содержимое.

**Частая ошибка на собеседовании** — отвечать «value type в стеке, reference type в куче». Место хранения — деталь реализации: поле-структура внутри класса лежит в куче, а локальная переменная, захваченная лямбдой, переезжает в класс-замыкание. Определяющее отличие — семантика копирования, а не стек.

## Где хранятся value types и reference types — в stack или heap?

```yaml
category: csharp
level: middle
difficulty: 3
slug: csharp-gde-hranyatsya-value-types-i-reference-types-v-stack-ili-heap
tags: value-types, data-structures
```

Объекты reference types всегда размещаются в управляемой куче (с редким исключением — escape analysis в новых версиях JIT). Value types хранятся там, где объявлены: локальная переменная — в стеке или регистре, поле класса — внутри объекта в куче, элемент массива — внутри массива в куче. Формула «value type в стеке» верна только для локальных переменных, и то не всегда.

**Где на самом деле лежит значение:**

| Где объявлено | Где хранится |
| --- | --- |
| Локальная переменная / параметр value type | стек кадра метода или регистр CPU |
| Поле value type внутри `class` | в куче, внутри объекта-владельца |
| Поле value type внутри `struct` | там же, где сама внешняя структура |
| Элемент `int[]`, `Point[]` | в куче, внутри массива, без отдельных объектов |
| Упакованный value type | отдельный объект в куче |
| Локальная, захваченная лямбдой | поле класса-замыкания в куче |
| Локальная в `async`-методе или итераторе, живущая через `await`/`yield` | поле state machine; после первого реального ожидания — в куче |
| Ссылка на объект (сама переменная) | как value type: в стеке, регистре или поле |

```csharp
class Order
{
    public decimal Total;          // лежит в куче внутри Order
}

void Handle()
{
    int count = 0;                 // стек/регистр
    var order = new Order();       // ссылка — в стеке, объект — в куче
    Action inc = () => count++;    // count переехал в класс-замыкание в куче
}
```

**Почему так устроено.** Стек — это память кадра вызова, она освобождается при выходе из метода. Всё, что может пережить метод (объект, на который можно сохранить ссылку; переменная, захваченная делегатом; состояние async-метода), обязано жить в куче, где время жизни определяет GC.

**`ref struct`** — единственный способ гарантировать, что значение не попадёт в кучу. `Span<T>` и `ReadOnlySpan<T>` не могут быть полями классов, не упаковываются и (до C# 13) не могут использоваться в `async`-методах. Компилятор это проверяет.

**Про escape analysis.** Начиная с .NET 9/10 JIT умеет в некоторых случаях размещать в стеке объекты, которые не покидают метод (например, упаковку или небольшой объект, не утекающий наружу). Это оптимизация, на которую нельзя рассчитывать при проектировании, но она показывает, что «класс всегда в куче» — тоже модель, а не закон.

**Что из этого важно на практике:** не место хранения само по себе, а количество аллокаций в куче — они дают нагрузку на GC. Поэтому на вопрос «где хранится» хороший ответ заканчивается фразой: определяет не тип, а контекст объявления и время жизни.

## Что такое boxing и unboxing?

```yaml
category: csharp
level: middle
difficulty: 2
slug: csharp-chto-takoe-boxing-i-unboxing
tags: boxing
```

Boxing (упаковка) — преобразование value type в `object` или интерфейс: CLR создаёт в куче объект-обёртку и копирует в него значение. Unboxing (распаковка) — обратная операция: проверка типа и копирование значения из обёртки обратно в переменную value type.

```csharp
int n = 42;
object o = n;        // box: аллокация ~24 байта на x64, копия значения
n = 100;             // o по-прежнему содержит 42
int m = (int)o;      // unbox: проверка типа + копирование
long l = (long)o;    // InvalidCastException: упакован int, а не long
long ok = (int)o;    // так правильно: сначала распаковать, потом привести
```

**Что происходит внутри.** В IL упаковка — инструкция `box`, распаковка — `unbox.any` (или `unbox`, который даёт указатель на данные внутри обёртки). Упакованный объект — полноценный объект кучи: заголовок, указатель на method table типа `Int32`, затем само значение.

**Правила распаковки строгие:** распаковать можно только в точно тот же тип (или его `Nullable<T>`, или для enum — в underlying type). Никаких неявных числовых преобразований при распаковке нет — отсюда ошибка с `(long)o` выше.

**`Nullable<T>` упаковывается особым образом:** `int?` со значением упаковывается в обычный boxed `int`, а `int?` без значения превращается в `null`, а не в объект. Поэтому `object o = (int?)null; o == null` — `true`.

**Почему это важно:**

- **аллокация** на каждую упаковку и давление на GC в горячем коде;
- **копирование** — изменения в упакованной структуре не видны оригиналу и наоборот. Особенно коварно для изменяемых структур, приведённых к интерфейсу: метод через интерфейс изменит копию в обёртке;
- **тип теряется** — `object` нужно распаковывать с правильным типом, ошибка обнаружится только в runtime.

**Как избегать:** дженерики вместо `object` (`List<int>` вместо `ArrayList`), `IEquatable<T>` у структур, generic-методы с ограничением `where T : IInterface` вместо параметра типа интерфейса. Увидеть упаковку можно в IL (SharpLab, ILSpy) или в профилировщике аллокаций как множество мелких `System.Int32`.

**Мера.** Одна упаковка — десятки наносекунд. В обычном коде, который ходит в БД и сеть, это незаметно; бороться с ней стоит в горячих циклах, сериализации и библиотечном коде, и только после измерения.

## Когда происходит boxing?

```yaml
category: csharp
level: middle
difficulty: 3
slug: csharp-kogda-proishodit-boxing
tags: boxing
```

Boxing происходит всякий раз, когда value type нужно представить как ссылку: при приведении к `object`, `ValueType`, `Enum` или к интерфейсу, который реализует структура. Явное `object o = 42` встречается редко — проблема в неявных местах.

**Типичные неявные случаи:**

```csharp
// 1. Необобщённые коллекции и API на object
var list = new ArrayList(); list.Add(1);            // box
var table = new Hashtable(); table[1] = "x";        // box ключа

// 2. params object[] — форматирование, логирование
string.Format("{0}/{1}", done, total);              // два box
logger.LogInformation("Took {Ms} ms", elapsed);     // box: args — params object?[]

// 3. Приведение структуры к интерфейсу
IComparable<int> c = 5;                             // box
void Print(IFormattable f) { }  Print(3.14);        // box при вызове

// 4. Equals(object) у структуры без IEquatable<T>
struct Point { public int X, Y; }
new Point().Equals(new Point());                    // box аргумента (и this)

// 5. Вызов унаследованных от object/ValueType методов, не переопределённых в структуре
new Point().GetHashCode();                          // box: реализация в ValueType
new Point().ToString();                             // box

// 6. foreach по value-type коллекции через интерфейс
IEnumerable<int> seq = new List<int>();
foreach (var x in seq) { }                          // enumerator-структура List<T> упаковывается
```

**Где boxing нет, хотя кажется, что будет:**

- **generic с ограничением.** `void M<T>(T x) where T : IComparable<T>` — JIT специализирует код для каждого value type, вызов `x.CompareTo` идёт напрямую. В IL стоит `constrained.` префикс, который убирает `box`;
- **строковая интерполяция в C# 10+** — `$"{count}"` идёт через `DefaultInterpolatedStringHandler.AppendFormatted<T>`, без упаковки для типов, реализующих `ISpanFormattable`;
- **`foreach` по конкретному `List<T>`** — используется struct-энумератор без упаковки;
- **вызов переопределённого в структуре метода** (`ToString`, `GetHashCode`, если вы их override) — упаковки нет.

**Нюанс с JIT.** Некоторые случаи оптимизатор убирает сам. `Enum.HasFlag` раньше упаковывал всегда; современный JIT распознаёт его как intrinsic, но только в оптимизированном коде — на Tier0 и в Debug аллокация остаётся. В .NET 10 escape analysis может убрать упаковку энумератора в `foreach` по `IEnumerable<T>`, если после tier-up и PGO вызовы девиртуализированы. Рассчитывать на это в дизайне не стоит — надёжнее побитовая проверка `(flags & F.W) != 0` и работа с конкретными типами.

**Как находить:** инструкция `box` в IL (SharpLab), анализаторы аллокаций в IDE, `dotnet-counters`/профилировщик — множество мелких объектов `System.Int32`, `System.DateTime` в Gen0. Бенчмарк с `[MemoryDiagnoser]` покажет байты на операцию.

**Что стоит сказать в конце:** в обычном бизнес-коде boxing несущественен; устранять его имеет смысл в горячих путях, где профилировщик показал давление на GC.

## Что будет при сравнении двух `struct`?

```yaml
category: csharp
level: middle
difficulty: 3
slug: csharp-chto-budet-pri-sravnenii-dvuh-struct
tags: value-types
```

Зависит от того, как сравнивать. Оператор `==` для пользовательской структуры не компилируется, пока вы его не перегрузите. `Equals` работает сразу и сравнивает структуры по значению всех полей, но реализация по умолчанию (`ValueType.Equals`) медленная и упаковывает аргументы.

```csharp
struct Point { public int X, Y; }

var a = new Point { X = 1, Y = 2 };
var b = new Point { X = 1, Y = 2 };

// a == b;          // CS0019: оператор == не определён для Point
a.Equals(b);        // true — сравнение по полям
object.ReferenceEquals(a, b); // false — каждая сторона упакована в свой объект
```

**Как устроен `ValueType.Equals(object)`:**

1. аргумент приходит как `object` — значит, `b` упаковывается (и `a` тоже, если метод не переопределён — вызов идёт на базовой реализации);
2. проверяется, что типы совпадают;
3. если в структуре нет ссылочных полей и она плотно упакована, runtime сравнивает память побайтно — быстрый путь;
4. иначе поля перебираются **через reflection** и для каждого вызывается `Equals`.

Быстрый путь тоже с подвохом: побайтное сравнение неверно для типов, у которых разные битовые представления считаются равными. Например, `double` `0.0` и `-0.0` равны по `==`, но различаются битами. Современный runtime для полей с плавающей точкой уходит на медленный путь, но сам пример хорошо показывает, почему на поведение по умолчанию полагаться неприятно.

**Цена.** Замер на .NET 10: вызов `Equals` у структуры из двух `int` без переопределения аллоцирует 48 байт (две упаковки), у структуры с полем `string` — больше 150 байт и reflection на каждом вызове. В `HashSet<Point>` или как ключ `Dictionary` это превращается в заметный поток мусора.

**Как делать правильно:**

```csharp
readonly record struct Point(int X, int Y);   // Equals, GetHashCode, ==, != сгенерированы

// или вручную
readonly struct Point2 : IEquatable<Point2>
{
    public int X { get; init; }
    public int Y { get; init; }
    public bool Equals(Point2 o) => X == o.X && Y == o.Y;
    public override bool Equals(object? obj) => obj is Point2 p && Equals(p);
    public override int GetHashCode() => HashCode.Combine(X, Y);
    public static bool operator ==(Point2 l, Point2 r) => l.Equals(r);
    public static bool operator !=(Point2 l, Point2 r) => !l.Equals(r);
}
```

`IEquatable<T>` важен не только для скорости: `EqualityComparer<T>.Default`, который используют `Dictionary`, `HashSet`, `List.Contains`, `Distinct`, выбирает типизированный `Equals(T)`, если тип его реализует, — и упаковки нет вовсе.

**Что проверяют этим вопросом:** знаете ли вы, что `==` для структур не «бесплатный», что `Equals` по умолчанию сравнивает поля через reflection, и что правильный ответ — `record struct` или `IEquatable<T>` + `GetHashCode` + операторы вместе.

## Чем отличаются `Equals()`, `ReferenceEquals()` и `==`?

```yaml
category: csharp
level: middle
difficulty: 3
slug: csharp-chem-otlichayutsya-equals-referenceequals-i
```

`ReferenceEquals` всегда проверяет, что две ссылки указывают на один объект, и его нельзя переопределить. `Equals` — виртуальный метод, который тип может переопределить под логическое равенство. `==` — оператор, который выбирается **статически** по типам переменных на этапе компиляции: для классов по умолчанию сравнивает ссылки, но может быть перегружен.

| | `ReferenceEquals(a, b)` | `a.Equals(b)` | `a == b` |
| --- | --- | --- | --- |
| Что сравнивает по умолчанию | идентичность | идентичность (класс) / поля (struct) | идентичность (класс), значения (примитивы) |
| Можно изменить | нет | `override` | перегрузка оператора |
| Выбор реализации | — | в runtime (virtual) | при компиляции по статическому типу |
| `a == null` | без ошибки | `NullReferenceException` | без ошибки |

**Главная ловушка — статическое связывание `==`:**

```csharp
string s1 = "hello";
string s2 = new string("hello".ToCharArray());

s1 == s2;                    // true  — string перегружает ==
s1.Equals(s2);               // true
ReferenceEquals(s1, s2);     // false — разные объекты

object o1 = s1, o2 = s2;
o1 == o2;                    // false! выбран object.==, сравнение ссылок
o1.Equals(o2);               // true  — виртуальный вызов string.Equals
```

Оператор — это статический метод, полиморфизма у него нет. Как только переменные имеют тип `object` или обобщённый `T` без ограничений, перегрузка `==` не видна. В generic-коде `==` для `T` вообще не компилируется без ограничения `class` (тогда это сравнение ссылок) — правильно использовать `EqualityComparer<T>.Default.Equals(a, b)`.

**Для value types:** `ReferenceEquals` бессмысленен — оба аргумента упакуются в разные объекты, результат всегда `false`. `==` у примитивов сравнивает значения, у пользовательских структур не определён.

**Для `record`:** компилятор генерирует `Equals` по значениям свойств и операторы `==`/`!=`, которые вызывают его, так что для записей все три способа, кроме `ReferenceEquals`, дают равенство по значению.

**Правила при переопределении:**

- переопределили `Equals` — обязательно переопределите `GetHashCode`, иначе объект сломается в `Dictionary` и `HashSet`;
- реализуйте `IEquatable<T>`, чтобы избежать приведения и упаковки;
- перегружаете `==` — перегрузите и `!=`, и сделайте их согласованными с `Equals`;
- `Equals` должен быть рефлексивным, симметричным, транзитивным и возвращать `false` для `null`.

**Проверка на `null`:** современная идиома — `x is null` / `x is not null`. Она не вызывает пользовательский `==` и всегда сравнивает ссылку с `null`, поэтому не ломается на типах с кривой перегрузкой оператора.

## Для чего нужен `GetHashCode()`?

```yaml
category: csharp
level: middle
difficulty: 3
slug: csharp-dlya-chego-nuzhen-gethashcode
```

`GetHashCode()` возвращает `int`, по которому хеш-структуры — `Dictionary<TKey, TValue>`, `HashSet<T>`, `ConcurrentDictionary`, `Lookup` в LINQ, `GroupBy`, `Distinct` — выбирают корзину для объекта. Хеш позволяет найти элемент за O(1) в среднем, сравнивая через `Equals` только кандидатов из одной корзины, а не всю коллекцию.

**Контракт, который обязан соблюдаться:**

1. если `a.Equals(b)`, то `a.GetHashCode() == b.GetHashCode()` — **обязательно**;
2. обратное не требуется: равные хеши у разных объектов — это коллизия, она допустима;
3. хеш не должен меняться, пока объект лежит в хеш-коллекции;
4. хеш не обязан быть стабильным между запусками процесса — и для `string` в .NET Core он **действительно разный** в каждом процессе (рандомизированный seed против hash flooding). Поэтому хеш нельзя сохранять в БД или передавать по сети.

**Что будет при нарушении пункта 1:**

```csharp
class User
{
    public string Email { get; init; } = "";
    public override bool Equals(object? o) => o is User u && u.Email == Email;
    // GetHashCode не переопределён — используется хеш по идентичности объекта
}

var set = new HashSet<User> { new() { Email = "a@b.c" } };
set.Contains(new User { Email = "a@b.c" });   // false — ищем не в той корзине
```

Компилятор предупреждает об этом (CS0659), но не запрещает.

**Как писать:**

```csharp
public override int GetHashCode() => HashCode.Combine(Email, TenantId);
```

`System.HashCode` правильно перемешивает биты и учитывает `null`. Используйте в хеше **те же поля**, что и в `Equals`, и только неизменяемые. Для строк без учёта регистра — `StringComparer.OrdinalIgnoreCase.GetHashCode(s)`, иначе равные по `Equals` строки получат разные хеши.

**Реализации по умолчанию:**

- `object.GetHashCode()` — хеш идентичности, привязанный к конкретному экземпляру и стабильный на всё время его жизни;
- `ValueType.GetHashCode()` — вычисляется из полей, медленно (может через reflection), упаковывает, и в ряде случаев опирается только на часть полей, давая плохое распределение. Для структур-ключей переопределяйте всегда;
- `record` генерирует хеш из всех полей автоматически.

**Качество хеша влияет на производительность.** Если все объекты возвращают одно и то же число (`return 0;`), корректность сохраняется, но `Dictionary` вырождается в список: поиск становится O(n). Плохое распределение — частая причина «медленного словаря».

**Что спрашивают дальше:** почему нельзя менять ключ в словаре, как устроен `Dictionary` внутри, как реализовать свой `IEqualityComparer<T>`.

## Почему нельзя изменять объект, пока он используется как ключ `Dictionary`?

```yaml
category: csharp
level: middle
difficulty: 4
slug: csharp-pochemu-nelzya-izmenyat-obekt-poka-on-ispolzuetsya-kak-klyuch-dictiona
tags: collections
```

Потому что `Dictionary` запоминает положение ключа по хешу, вычисленному один раз — в момент вставки. Если после этого изменить поля, участвующие в `GetHashCode`/`Equals`, новый хеш укажет на другую корзину, и словарь больше не найдёт запись, хотя она физически в нём лежит.

**Что происходит по шагам:**

```csharp
class Key
{
    public int Id;
    public override bool Equals(object? o) => o is Key k && k.Id == Id;
    public override int GetHashCode() => Id;
}

var key = new Key { Id = 1 };
var dict = new Dictionary<Key, string> { [key] = "value" };

key.Id = 2;                              // мутация ключа

dict.ContainsKey(key);                   // false: ищем в корзине хеша 2
dict.ContainsKey(new Key { Id = 1 });    // false: корзина верная, но Equals не совпадает
dict.Count;                              // 1 — запись есть
dict.Keys.First() == key;                // true — тот же объект
dict[key] = "new";                       // добавится ВТОРАЯ запись с тем же объектом
```

Внутри `Dictionary` хранит в каждом entry сохранённый `hashCode` ключа и индекс в массиве `buckets` (`hash % buckets.Length`). При поиске он вычисляет хеш заново, идёт в соответствующую корзину и в цепочке сравнивает сначала сохранённый хеш, потом `Equals`. После мутации совпасть не может ни одно, ни другое — запись становится «зомби»: её нельзя найти и удалить по ключу, но она занимает память и видна при перечислении. Удалить её получится только пересозданием словаря или `Clear()`.

**Почему это опасно на практике:** ошибка не падает с исключением, а проявляется как «пропавшие» данные, дубли и утечки памяти в кэшах. Обнаружить её сложно, потому что при отладке ключ выглядит корректным.

**Та же проблема касается:** `HashSet<T>` (элемент не находится и не удаляется), `ConcurrentDictionary`, `ToLookup`/`GroupBy`, а также `SortedDictionary`/`SortedSet` — там ломается порядок в дереве при изменении полей, участвующих в сравнении.

**Как избежать:**

- делать ключи **неизменяемыми**: `record`/`readonly record struct` с `init`-свойствами, строки, `Guid`, примитивы;
- строить `Equals`/`GetHashCode` только на неизменяемых полях (например, на `Id`, который задаётся в конструкторе);
- если объект по природе изменяемый (Entity в EF Core), использовать в качестве ключа его идентификатор, а не сам объект;
- если нужно «переименовать» ключ — удалить запись со старым ключом, изменить, вставить заново.

**Нюанс для сущностей с хешем по `Id`:** у новой сущности EF Core `Id` может быть `0` до `SaveChanges`, а потом получить значение из базы. Если такая сущность успела попасть в `HashSet`, она станет ненаходимой — классический баг именно этого вида.

## Что такое immutable object и зачем он нужен?

```yaml
category: csharp
level: middle
difficulty: 2
slug: csharp-chto-takoe-immutable-object-i-zachem-on-nuzhen
tags: value-types
```

Immutable object — объект, состояние которого нельзя изменить после создания. Любая «модификация» возвращает новый экземпляр, а старый остаётся прежним. Классические примеры в .NET — `string`, `DateTime`, `TimeSpan`, `Guid`, `Uri`, коллекции из `System.Collections.Immutable`.

**Зачем это нужно:**

- **потокобезопасность без блокировок** — объект, который никто не может изменить, безопасно читать из любого числа потоков;
- **предсказуемость** — передали объект в метод и уверены, что он вернётся тем же; нет эффекта «кто-то где-то поменял»;
- **безопасные ключи** — неизменяемый объект можно класть в `Dictionary`/`HashSet`, его хеш не «уплывёт»;
- **кэширование и переиспользование** — один экземпляр можно раздать всем (так работает интернирование строк);
- **проще рассуждать** — инварианты проверяются один раз в конструкторе и больше не нарушаются.

**Как сделать в современном C#:**

```csharp
// record с позиционными параметрами: init-свойства, with-выражение
public record Money(decimal Amount, string Currency);

var price = new Money(100, "USD");
var discounted = price with { Amount = 90 };   // новый объект, price не изменился

// вручную: readonly-поля / get-only или init-свойства, валидация в конструкторе
public sealed class Email
{
    public string Value { get; }
    public Email(string value) =>
        Value = value.Contains('@') ? value : throw new ArgumentException(nameof(value));
}

// структура
public readonly record struct Point(int X, int Y);
```

**Подводный камень — поверхностная неизменяемость.** `readonly` и `init` защищают только ссылку, а не содержимое объекта, на который она указывает:

```csharp
public record Order(string Id, List<string> Items);

var o = new Order("1", new() { "a" });
o.Items.Add("b");          // компилируется: список изменяемый
```

Для настоящей неизменяемости поля тоже должны быть неизменяемыми: `ImmutableArray<T>`, `IReadOnlyList<T>` поверх копии, `FrozenDictionary` для справочников. Причём `IReadOnlyList<T>` — это только интерфейс-«вид»: если снаружи остался доступ к исходному `List<T>`, данные можно изменить.

**Цена:** каждое изменение — новая аллокация. Для строк это решается `StringBuilder`, для коллекций — builder'ами (`ImmutableList.CreateBuilder<T>()`) или сборкой в изменяемой коллекции с последующей «заморозкой». Immutable-коллекции основаны на деревьях и медленнее обычных при доступе, а `FrozenDictionary`/`FrozenSet` (.NET 8) наоборот медленнее создаются, но оптимизированы для чтения.

**Где применять:** value objects в DDD, DTO и сообщения, конфигурация, ключи словарей, данные, разделяемые между потоками. Сущности с жизненным циклом (EF Core entities) обычно остаются изменяемыми.

## Чем отличаются `IEnumerable`, `ICollection` и `IList`?

```yaml
category: csharp
level: middle
difficulty: 3
slug: csharp-chem-otlichayutsya-ienumerable-icollection-i-ilist
tags: linq, collections
```

Это иерархия интерфейсов, где каждый следующий добавляет возможности к предыдущему: `IEnumerable<T>` умеет только перечисляться, `ICollection<T>` добавляет размер и изменение, `IList<T>` — доступ по индексу.

```text
IEnumerable<T>
   └── ICollection<T>
          └── IList<T>
```

| | `IEnumerable<T>` | `ICollection<T>` | `IList<T>` |
| --- | --- | --- | --- |
| Перечисление `foreach` | да | да | да |
| `Count` | нет (только LINQ `Count()`) | да, свойство | да |
| `Add`, `Remove`, `Clear`, `Contains` | нет | да | да |
| `IsReadOnly` | нет | да | да |
| Индексатор `[i]`, `IndexOf`, `Insert`, `RemoveAt` | нет | нет | да |
| Может быть ленивой/бесконечной | да | нет | нет |
| Типичные реализации | итераторы `yield`, LINQ-запросы | `HashSet<T>`, `LinkedList<T>`, `Dictionary` (как коллекция пар) | `List<T>`, `T[]`, `Collection<T>` |

**`IEnumerable<T>` — самый слабый контракт.** Он не обещает, что данные уже в памяти, что их можно перечислить дважды или что перечисление конечно. Это может быть LINQ-запрос, чтение файла построчно, генератор через `yield`. Поэтому повторный `foreach` или `Count()` может заново выполнить всю работу (предупреждение «possible multiple enumeration» в Rider/ReSharper).

**`ICollection<T>`** гарантирует материализованный набор с известным размером: `Count` — O(1) у стандартных реализаций. LINQ этим пользуется: `Enumerable.Count()` и `ToList()` проверяют, не является ли источник `ICollection<T>`, и берут `Count`/`CopyTo` вместо перебора.

**`IList<T>`** добавляет порядок и позиционный доступ. Массив тоже реализует `IList<T>`, но `Add` на нём бросит `NotSupportedException` — `IsReadOnly` для массива `true`, хотя элементы менять можно. Это пример того, что интерфейс не гарантирует поддержку всех операций.

**Отдельная ветка read-only интерфейсов:** `IReadOnlyCollection<T>` (перечисление + `Count`) и `IReadOnlyList<T>` (+ индексатор). Они не наследуются от `ICollection<T>`/`IList<T>`, это параллельная иерархия, которую реализуют `List<T>` и массивы.

**Как выбирать тип в сигнатурах:**

- **параметр** — принимайте самый общий интерфейс, которого достаточно: `IEnumerable<T>`, если нужен только проход; `IReadOnlyCollection<T>`, если нужен размер; `IReadOnlyList<T>`, если нужен индекс;
- **возвращаемое значение** — отдавайте конкретику, которую вы гарантируете: `IReadOnlyList<T>` для готового списка, чтобы вызывающий не материализовал его повторно и не мог изменить; `IEnumerable<T>` — только для действительно ленивых последовательностей;
- **не принимайте `IList<T>`**, если метод не меняет список: это лишнее требование к вызывающему.

**Что спрашивают дальше:** в чём опасность многократного перечисления `IEnumerable<T>`, чем `IEnumerable` отличается от `IQueryable`, почему `IReadOnlyList<T>` не делает данные неизменяемыми (под ним может лежать изменяемый `List<T>`).

## Чем отличаются `IEnumerable` и `IQueryable`?

```yaml
category: csharp
level: middle
difficulty: 3
slug: csharp-chem-otlichayutsya-ienumerable-i-iqueryable
tags: linq
```

`IEnumerable<T>` выполняет LINQ-операторы в памяти процесса: методы принимают делегаты (`Func<T, bool>`) и вызывают их на каждом элементе. `IQueryable<T>` принимает expression trees (`Expression<Func<T, bool>>`), накапливает их в дерево запроса, и провайдер (EF Core, например) транслирует это дерево в SQL или другой язык источника данных.

| | `IEnumerable<T>` | `IQueryable<T>` |
| --- | --- | --- |
| Методы LINQ | `System.Linq.Enumerable` | `System.Linq.Queryable` |
| Что принимают | `Func<...>` — скомпилированный код | `Expression<Func<...>>` — данные о коде |
| Где выполняется фильтр | в процессе, по уже полученным объектам | на стороне источника (БД) |
| Кто исполняет | сам .NET | `IQueryProvider` |
| Ограничения | любой C#-код | только то, что провайдер умеет транслировать |

```csharp
// IQueryable: WHERE и TOP попадут в SQL, из БД придут 10 строк
var q = db.Orders.Where(o => o.Total > 1000).OrderBy(o => o.Id).Take(10);

// IEnumerable: AsEnumerable «переключает» на LINQ to Objects
var e = db.Orders.AsEnumerable().Where(o => o.Total > 1000).Take(10);
// SELECT * FROM Orders — вся таблица едет в память, фильтр в C#
```

**Главная ловушка — потеря `IQueryable` через тип.** Если метод репозитория возвращает `IEnumerable<Order>`, любой `.Where()` поверх него выполнится в памяти, даже если под ним `DbSet`. Статический тип переменной определяет, какой `Where` вызовется: `Enumerable.Where` или `Queryable.Where`.

```csharp
IEnumerable<Order> GetOrders() => db.Orders;          // тип стёрт до IEnumerable
var big = GetOrders().Where(o => o.Total > 1000);     // Enumerable.Where → вся таблица
```

**Что не транслируется.** Вызов своего C#-метода внутри `Where` у `IQueryable` провайдер перевести в SQL не сможет. EF Core в таком случае бросает `InvalidOperationException` ("could not be translated"), за исключением финального `Select`, где допускается клиентская оценка проекции. Раньше, в EF Core 2.x, была тихая клиентская оценка всего запроса — отсюда много унаследованных проблем с производительностью.

**Когда осознанно переходить на `IEnumerable`:** когда нужно применить логику, которую нельзя выразить в SQL, **после** того как данные уже отфильтрованы на стороне БД: сначала `Where`/`Select`/`Take` в `IQueryable`, затем `AsEnumerable()` или `ToListAsync()`, и уже потом C#-логика.

**Общее у обоих:** отложенное выполнение. Ни один из них ничего не делает, пока не начато перечисление (`foreach`, `ToList`, `First`, `Count`). У `IQueryable` каждое перечисление — новый запрос в БД.

**Что проверяют этим вопросом:** понимаете ли вы, где выполняется фильтрация, и видите ли по коду ситуацию, в которой вся таблица загружается в память. Хороший ответ — с примером `AsEnumerable()` и стёртого типа в репозитории.

## Что такое deferred execution?

```yaml
category: csharp
level: middle
difficulty: 2
slug: csharp-chto-takoe-deferred-execution
tags: linq
```

Deferred execution (отложенное выполнение) — LINQ-запрос не выполняется в момент объявления. Вызов `Where`, `Select`, `OrderBy` только строит описание запроса (цепочку итераторов или expression tree); реальная работа происходит, когда результат начинают перечислять.

```csharp
var numbers = new List<int> { 1, 2, 3 };
var query = numbers.Where(n => { Console.WriteLine($"check {n}"); return n > 1; });

Console.WriteLine("до перечисления");   // ничего не проверено
numbers.Add(4);                          // запрос увидит и этот элемент
foreach (var n in query) { }             // check 1, check 2, check 3, check 4
```

**Что запускает выполнение:**

- `foreach` и любой код, вызывающий `GetEnumerator()`;
- материализация: `ToList`, `ToArray`, `ToDictionary`, `ToHashSet`;
- агрегаты и получение одного элемента: `Count`, `Sum`, `Max`, `Any`, `First`, `Single`, `ElementAt`;
- для EF Core — асинхронные аналоги `ToListAsync`, `FirstOrDefaultAsync` и т. п.

**Потоковые и буферизующие операторы.** Даже внутри отложенного запроса операторы ведут себя по-разному:

| Streaming (элемент за элементом) | Buffering (читают весь источник перед первым результатом) |
| --- | --- |
| `Where`, `Select`, `Take`, `Skip`, `Concat`, `Zip`, `Distinct` (отдаёт по мере чтения, но копит множество увиденных) | `OrderBy`, `GroupBy`, `Reverse`, `ToLookup` |

Поэтому `source.Where(...).First()` может остановиться на первом элементе, а `source.OrderBy(...).First()` всегда прочитает всё.

**Главные ловушки:**

- **повторное выполнение** — каждый `foreach` или `Count()` по запросу выполняет его заново. Для LINQ to Objects это лишняя работа, для EF Core — лишний запрос в базу, для итератора, читающего файл, — повторное чтение;
- **изменение источника** — запрос видит состояние данных на момент перечисления, а не объявления;
- **замыкание на переменную** — лямбда захватывает переменную, а не её значение:

```csharp
int min = 1;
var q = numbers.Where(n => n > min);
min = 10;
q.Count();   // фильтр с min = 10
```

- **исключения позже, чем ожидаешь** — ошибка внутри лямбды вылетит в месте перечисления, а не в строке с `Where`; аналогично `ObjectDisposedException`, если `DbContext` уже уничтожен к моменту перечисления запроса, возвращённого из метода.

**Практическое правило:** материализуйте (`ToList()`) результат, если собираетесь использовать его несколько раз, возвращаете за пределы времени жизни источника (`DbContext`, `using` на файле) или хотите «зафиксировать» снимок данных. Оставляйте ленивым, если результат читается один раз и может быть большим — ленивость экономит память и позволяет раньше остановиться.

## Что делает `yield return`?

```yaml
category: csharp
level: middle
difficulty: 2
slug: csharp-chto-delaet-yield-return
tags: linq
```

`yield return` превращает метод в итератор: метод возвращает `IEnumerable<T>` (или `IEnumerator<T>`, `IAsyncEnumerable<T>`), а значения отдаются по одному по мере перечисления. Между вызовами `MoveNext()` выполнение метода «замораживается» на строке с `yield return` и продолжается с неё же при следующем запросе элемента.

```csharp
IEnumerable<int> Evens(int max)
{
    Console.WriteLine("start");
    for (var i = 0; i <= max; i += 2)
        yield return i;          // отдаём значение и приостанавливаемся
    Console.WriteLine("end");
}

var seq = Evens(4);              // ничего не выведено: тело не запущено
foreach (var x in seq.Take(2))   // start, 0, 2 — "end" не выведется никогда
    Console.WriteLine(x);
```

**Как это устроено.** Компилятор переписывает метод в скрытый класс — state machine, который реализует `IEnumerable<T>` и `IEnumerator<T>`. Локальные переменные становятся его полями, а поле `state` хранит, до какой точки дошло выполнение. `MoveNext()` — это `switch` по состоянию: выполнить код до следующего `yield return`, записать `Current`, вернуть `true`. `yield break` или конец метода — вернуть `false`.

**Ключевые следствия:**

- **ленивость** — тело не выполняется при вызове метода, только при первом `MoveNext()`. Отсюда ловушка с валидацией аргументов:

```csharp
IEnumerable<string> ReadLines(string path)
{
    ArgumentNullException.ThrowIfNull(path);   // бросит только при перечислении!
    foreach (var line in File.ReadLines(path)) yield return line;
}
```

Правильный приём — обычный метод-обёртка с проверкой, который возвращает результат приватного итератора (или локальной функции-итератора);

- **повторное перечисление запускает метод заново** — каждый `GetEnumerator()` даёт новый экземпляр state machine;
- **`finally` и `using` работают** — при досрочном выходе из `foreach` (`break`, `Take`, исключение) вызывается `Dispose()` энумератора, который выполняет блоки `finally`. Поэтому ресурсы, открытые в итераторе, закрываются корректно, если потребитель использует `foreach`;
- **ограничения**: нельзя `yield return` внутри `try` с `catch` (внутри `try/finally` — можно), нельзя в анонимных методах и лямбдах, итератор не может иметь `ref`/`out` параметры.

**Где полезно:**

- генерация последовательностей без материализации в памяти (чтение больших файлов, постраничная выборка, бесконечные последовательности);
- собственные LINQ-подобные операторы;
- `async` + `yield return` = `IAsyncEnumerable<T>` для стриминга из БД или API.

**Цена.** Один объект state machine на перечисление и интерфейсные вызовы `MoveNext`/`Current` на каждый элемент. Для горячего кода массив или `List<T>` с `for` быстрее, но в обычном коде эта разница несущественна.

## Как работает `Dictionary`?

```yaml
category: csharp
level: middle
difficulty: 3
slug: csharp-kak-rabotaet-dictionary
tags: collections
```

`Dictionary<TKey, TValue>` — хеш-таблица с разрешением коллизий через цепочки. По хешу ключа вычисляется номер корзины, внутри корзины кандидаты сравниваются через `Equals`. Поиск, вставка и удаление — O(1) в среднем и O(n) в худшем случае, если хеши плохо распределены.

**Внутреннее устройство** — два массива:

- `int[] buckets` — для каждой корзины индекс первого элемента цепочки (со смещением на 1, чтобы 0 значил «пусто»);
- `Entry[] entries` — сами записи. `Entry` — структура: `hashCode`, `next` (индекс следующего элемента в цепочке), `key`, `value`.

Цепочки — это не связанный список объектов, а индексы внутри одного массива структур. Поэтому словарь не создаёт аллокаций на каждую вставку, пока не нужен resize.

**Поиск ключа:**

1. `hash = comparer.GetHashCode(key)`;
2. `bucket = hash % buckets.Length` (размер — простое число; на 64-битных платформах остаток считается через быстрый алгоритм с умножением);
3. идём по цепочке `entries[i]`, `i = entries[i].next`, пока не найдём запись, у которой совпал **сохранённый хеш** и `Equals` вернул `true`.

Сравнение хешей перед `Equals` отсекает большинство кандидатов дёшево.

**Вставка и рост.** Новая запись кладётся в следующий свободный слот `entries` (или в слот из списка удалённых — freelist) и становится головой цепочки своей корзины. Когда `entries` заполнен, словарь увеличивается примерно в два раза до ближайшего простого числа и перераспределяет все записи по новым корзинам — это O(n), но амортизированно вставка остаётся O(1). Если известен размер, передайте `capacity` в конструктор или вызовите `EnsureCapacity`.

**Удаление** помечает слот свободным и включает его во freelist; массив не сжимается (для этого есть `TrimExcess`).

**Важные практические детали:**

- **порядок перечисления не гарантирован**. Без удалений он совпадает с порядком вставки, но это деталь реализации — опираться нельзя;
- **ключ `null` запрещён** (`ArgumentNullException`), значение — можно;
- **`TryGetValue` вместо `ContainsKey` + индексатор** — один поиск вместо двух. Для «получить или добавить» — `CollectionsMarshal.GetValueRefOrAddDefault`;
- **не потокобезопасен** на запись. Одновременная запись из нескольких потоков может повредить внутренние цепочки (в старых версиях — вплоть до бесконечного цикла). Для конкурентного доступа — `ConcurrentDictionary`, для неизменяемых справочников — `FrozenDictionary`;
- **изменение коллекции во время `foreach`** бросает `InvalidOperationException` (кроме `Remove` и `Clear`, которые с .NET Core 3.0 это не ломают);
- **ключи должны быть неизменяемыми** и иметь корректные `GetHashCode`/`Equals`; для строк можно передать `StringComparer.OrdinalIgnoreCase`.

**Защита от атак.** Для ключей `string` с компаратором по умолчанию словарь сначала использует быстрый нерандомизированный хеш и переключается на рандомизированный, если цепочки становятся слишком длинными (признак hash flooding).

## Как работает `HashSet`?

```yaml
category: csharp
level: middle
difficulty: 3
slug: csharp-kak-rabotaet-hashset
tags: collections
```

`HashSet<T>` — хеш-таблица только из ключей, без значений. Устроена так же, как `Dictionary<TKey, TValue>`: массив корзин и массив записей с цепочками по индексам. Проверка `Contains`, `Add`, `Remove` — O(1) в среднем за счёт того, что по хешу сразу вычисляется корзина.

**Алгоритм `Add(item)`:**

1. `hash = comparer.GetHashCode(item)`;
2. корзина `hash % buckets.Length`;
3. проход по цепочке: если нашли элемент с тем же хешем и `Equals` — возвращаем `false`, дубликат не добавляется;
4. иначе кладём запись `{ hashCode, next, value }` в свободный слот и делаем её головой цепочки; при заполнении массив растёт примерно вдвое до простого числа с перехешированием всех элементов.

```csharp
var seen = new HashSet<string>(StringComparer.OrdinalIgnoreCase);
seen.Add("Admin");    // true
seen.Add("admin");    // false — по этому компаратору это тот же элемент
```

**Чем отличается от `List<T>.Contains`:** `List<T>` проверяет наличие линейным перебором — O(n). На 10 элементах разницы нет, на 100 000 — это разница между микросекундами и миллисекундами на каждую проверку. Классическая оптимизация: `items.Where(x => ids.Contains(x.Id))`, где `ids` — `List`, превращается в O(n·m); с `HashSet` — O(n).

**Операции над множествами** — главное, ради чего `HashSet` выбирают помимо уникальности:

| Метод | Что делает |
| --- | --- |
| `UnionWith` | объединение (добавляет элементы из другой коллекции) |
| `IntersectWith` | оставляет только общие |
| `ExceptWith` | удаляет элементы другой коллекции |
| `SymmetricExceptWith` | элементы, которые есть ровно в одной из коллекций |
| `IsSubsetOf`, `IsSupersetOf`, `Overlaps`, `SetEquals` | проверки отношений |

Эти методы изменяют текущее множество на месте, в отличие от LINQ `Union`/`Intersect`/`Except`, которые возвращают новую ленивую последовательность (и внутри тоже строят `HashSet`).

**Особенности:**

- **порядок не гарантирован** — нужен порядок, используйте `SortedSet<T>` (красно-чёрное дерево, O(log n)) или отдельный список;
- **нет индекса** — получить «i-й элемент» нельзя, `ElementAt` будет перебором;
- **`null` допустим** как элемент (в отличие от ключа `Dictionary`);
- **`TryGetValue(equalValue, out actualValue)`** возвращает уже хранящийся экземпляр — полезно для интернирования объектов;
- **корректность зависит от `GetHashCode`/`Equals`** элемента. Изменение полей элемента после добавления делает его ненаходимым;
- **не потокобезопасен.** Потокобезопасного `ConcurrentHashSet` в BCL нет — обычно используют `ConcurrentDictionary<T, byte>` или блокировку; для read-only сценариев — `FrozenSet<T>` (.NET 8).

**Память:** на элемент приходится запись с хешем, индексом `next` и значением плюс слот в массиве корзин — заметно больше, чем у `List<T>`. Если нужна только уникальность маленького набора, список может оказаться и компактнее, и не медленнее.

## Чем `List<T>` отличается от `LinkedList<T>`?

```yaml
category: csharp
level: middle
difficulty: 3
slug: csharp-chem-list-t-otlichaetsya-ot-linkedlist-t
tags: collections
```

`List<T>` — динамический массив: элементы лежат в одном непрерывном `T[]`, который пересоздаётся с удвоением при заполнении. `LinkedList<T>` — двусвязный список: каждый элемент — отдельный объект `LinkedListNode<T>` в куче со ссылками на соседей.

| Операция | `List<T>` | `LinkedList<T>` |
| --- | --- | --- |
| Доступ по индексу | O(1) | нет индексатора, O(n) перебором |
| Добавление в конец | O(1) амортизированно | O(1) |
| Добавление/удаление в начале | O(n) — сдвиг всех элементов | O(1) |
| Вставка/удаление в середине | O(n) сдвиг | O(1), **если узел уже на руках** |
| Поиск значения | O(n) | O(n) |
| Память на элемент | размер `T` (+ запас ёмкости) | `T` + объект узла: заголовок, 3 ссылки (`next`, `prev`, `list`) |
| Кэш CPU | отлично — данные подряд | плохо — узлы разбросаны по куче |
| Аллокации | редкие, при росте массива | на каждый `Add` |

**Почему на практике почти всегда выигрывает `List<T>`.** Асимптотика O(1) у `LinkedList` для вставки в середину обманчива: чтобы найти место вставки, нужно пройти по узлам — это O(n), причём каждый шаг — промах кэша. Сдвиг элементов в `List<T>` — это один `memmove` по непрерывной памяти, и процессор делает его очень быстро. В реальных бенчмарках `List<T>` обычно быстрее даже на вставках в середину для коллекций в тысячи элементов, не говоря о переборе.

```csharp
var list = new List<int>(capacity: 10_000);   // capacity избавляет от переаллокаций
list.Insert(0, 42);                            // O(n), но быстрый memmove

var linked = new LinkedList<int>();
var node = linked.AddLast(1);
linked.AddAfter(node, 2);                      // O(1) — узел уже есть
```

**Когда `LinkedList<T>` действительно оправдан:**

- вы храните ссылки на узлы и часто вставляете/удаляете рядом с ними — классический пример LRU-кэш: `Dictionary<TKey, LinkedListNode<T>>` + `LinkedList<T>`, где перемещение в начало и удаление — O(1);
- нужно гарантированно O(1) без пиков, которые даёт переаллокация массива у `List<T>`;
- элементы огромные и дорого копируются (редкость — обычно храним ссылки).

**Для очередей и деков** лучше не `LinkedList`, а `Queue<T>`/`Stack<T>` (кольцевой буфер на массиве) — они дают O(1) на обоих концах без аллокации на элемент.

**Про `List<T>` стоит знать:** `Capacity` против `Count`, рост удвоением, `RemoveAt(0)` в цикле — O(n²), удаление по условию делать через `RemoveAll`, а не в цикле. `CollectionsMarshal.AsSpan(list)` даёт `Span<T>` на внутренний массив для горячего кода (нельзя менять размер списка, пока используете span).

## Чем `Array` отличается от `List<T>`?

```yaml
category: csharp
level: middle
difficulty: 3
slug: csharp-chem-array-otlichaetsya-ot-list-t
tags: collections
```

Массив `T[]` — непрерывный блок фиксированной длины, поддерживаемый напрямую CLR. `List<T>` — обёртка над массивом, которая умеет расти: хранит внутри `T[] _items` и `_size`, а при нехватке места создаёт массив вдвое больше и копирует элементы.

| | `T[]` | `List<T>` |
| --- | --- | --- |
| Размер | фиксирован при создании | динамический (`Count` ≤ `Capacity`) |
| Добавление/удаление | нет (только новый массив, `Array.Resize` — это копия) | `Add`, `Insert`, `Remove`, `RemoveAll` |
| Доступ по индексу | прямой, JIT может убрать проверку границ в `for` | через индексатор с проверкой `_size` и границ |
| Индексатор возвращает | ссылку на элемент (`ref`) | копию элемента |
| Накладные расходы | заголовок массива | объект `List` + массив с запасом ёмкости |
| Многомерность | `T[,]`, зубчатые `T[][]` | нет |
| Ковариантность | есть для ссылочных типов (`string[]` → `object[]`) | нет |

**Индексатор — важное практическое отличие для структур:**

```csharp
var arr = new Point[1];
arr[0].X = 5;          // OK: изменяем элемент на месте

var list = new List<Point> { new() };
// list[0].X = 5;      // CS1612: индексатор вернул копию
var p = list[0]; p.X = 5; list[0] = p;   // так
```

**Ковариантность массивов — исторический дефект:**

```csharp
object[] objs = new string[1];
objs[0] = 42;          // ArrayTypeMismatchException в runtime
```

Из-за этого каждая запись в массив ссылочного типа сопровождается проверкой типа. У `List<T>` такой проблемы нет, он инвариантен.

**Производительность.** Разница в чтении по индексу в современном .NET минимальна: индексатор `List<T>` инлайнится. Массив выигрывает в самых горячих циклах за счёт устранения проверок границ и того, что с ним напрямую работают `Span<T>`, `Array.Sort`, SIMD-API. `List<T>` проигрывает на росте: без заданной `capacity` добавление миллиона элементов вызовет около 18 переаллокаций и копирований, а также оставит мусор в LOH для больших массивов.

**Когда что выбирать:**

- **массив** — размер известен и не меняется: буферы, результаты с фиксированным числом элементов, lookup-таблицы, низкоуровневый код, `stackalloc`/`ArrayPool<T>.Shared.Rent`;
- **`List<T>`** — размер заранее неизвестен или коллекция меняется. Если примерный размер известен — `new List<T>(capacity)`;
- **в публичном API** возвращайте `IReadOnlyList<T>` — это скрывает выбор реализации и не даёт вызывающему менять коллекцию (правда, только на уровне интерфейса).

**Мелкие, но частые вопросы:** `Array.Empty<T>()` и `[]` (collection expressions, C# 12) для пустых коллекций без аллокации; `ToArray()` у `List<T>` всегда копирует; `CollectionsMarshal.AsSpan(list)` отдаёт `Span<T>` на внутренний массив без копирования.

## Чем отличаются `First`, `FirstOrDefault`, `Single` и `SingleOrDefault`?

```yaml
category: csharp
level: middle
difficulty: 3
slug: csharp-chem-otlichayutsya-first-firstordefault-single-i-singleordefault
```

Все четыре возвращают один элемент последовательности, но по-разному реагируют на пустой результат и на наличие нескольких подходящих элементов.

| Метод | 0 элементов | 1 элемент | больше 1 |
| --- | --- | --- | --- |
| `First()` | `InvalidOperationException` | элемент | первый |
| `FirstOrDefault()` | `default(T)` | элемент | первый |
| `Single()` | `InvalidOperationException` | элемент | `InvalidOperationException` |
| `SingleOrDefault()` | `default(T)` | элемент | `InvalidOperationException` |

**Смысл выбора — выразить ожидание в коде:**

- `First` — «элементов может быть много, нужен первый, и хотя бы один обязан быть»;
- `FirstOrDefault` — «нужен первый, если есть»;
- `Single` — «ровно один, иначе это ошибка данных» (выборка по уникальному ключу, настройка, которая должна существовать);
- `SingleOrDefault` — «ноль или один, два — ошибка».

`Single` служит проверкой инварианта: если в таблице по «уникальному» полю вдруг оказалось два пользователя, лучше упасть с исключением, чем молча взять случайного.

**Цена `Single`.** Чтобы убедиться, что элемент единственный, `Single` должен продолжить перебор после найденного элемента — в LINQ to Objects до конца последовательности (или до второго совпадения). `First` останавливается на первом. В EF Core это видно в SQL:

```sql
-- First / FirstOrDefault
SELECT ... FROM Users WHERE Email = @p LIMIT 1
-- Single / SingleOrDefault
SELECT ... FROM Users WHERE Email = @p LIMIT 2   -- второй нужен для проверки
```

**Ловушки:**

- **`default(T)` для value types — не `null`.** `new[] { 1, 2 }.FirstOrDefault(x => x > 5)` вернёт `0`, и его не отличить от реального нуля. Решения: `.Cast<int?>().FirstOrDefault()`, перегрузка с явным значением по умолчанию `FirstOrDefault(-1)` (есть с .NET 6), или `TryGetValue`-подобный код;
- **`First` без `OrderBy` в EF Core** — порядок строк в SQL без `ORDER BY` не определён, «первый» будет случайным;
- **`FirstOrDefault` как «на всякий случай»** — скрывает ошибки данных, после него часто следует `NullReferenceException` в другом месте. Если элемент обязан быть — используйте `First`/`Single` и получите понятное исключение сразу;
- **поиск по первичному ключу в EF Core** — лучше `FindAsync`: он сначала проверяет change tracker и не идёт в базу, если сущность уже загружена.

**Родственные методы:** `Last`/`LastOrDefault` (для `IList<T>` работают за O(1), иначе перебор всей последовательности; в EF Core требуют `OrderBy`), `ElementAt`/`ElementAtOrDefault`, `Any` — если нужно только проверить наличие, а не получить элемент.

## Что такое LINQ и как он выполняется?

```yaml
category: csharp
level: middle
difficulty: 2
slug: csharp-chto-takoe-linq-i-kak-on-vypolnyaetsya
tags: linq
```

LINQ (Language Integrated Query) — набор методов-расширений и синтаксиса запросов для фильтрации, проекции, сортировки и агрегации данных единым способом, независимо от источника: коллекции в памяти, база данных, XML. Выполняется лениво — в момент перечисления результата — и по-разному в зависимости от того, работает ли он с `IEnumerable<T>` или `IQueryable<T>`.

**Два синтаксиса — один результат.** Query syntax компилятор переписывает в вызовы методов:

```csharp
var q1 = from o in orders
         where o.Total > 100
         orderby o.Date
         select o.Id;

var q2 = orders.Where(o => o.Total > 100).OrderBy(o => o.Date).Select(o => o.Id);
```

Никакой магии: `where` — это вызов метода `Where`, который найдётся по обычным правилам, в том числе как extension method.

**Как выполняется LINQ to Objects (`IEnumerable<T>`).** Каждый оператор — это итератор, обёрнутый вокруг предыдущего. Цепочка `Where → Select` строит объекты-декораторы, но ничего не перебирает. Когда `foreach` вызывает `MoveNext()` у последнего, тот запрашивает элемент у предыдущего, и так до источника — элементы «протягиваются» через конвейер по одному (pull-модель).

```text
foreach ─► Select.MoveNext ─► Where.MoveNext ─► List.MoveNext
                 ◄── o.Id ◄──── o (если прошёл фильтр) ◄──
```

Операторы вроде `OrderBy` и `GroupBy` так не умеют: им нужен весь вход, поэтому они буферизуют источник при первом `MoveNext`. Внутри BCL много оптимизаций: объединённые итераторы `Where+Select`, быстрые пути для массивов и `List<T>`, векторизованные `Sum`/`Min`/`Max` для примитивов.

**Как выполняется LINQ to Entities (`IQueryable<T>`).** Лямбды компилируются не в делегаты, а в expression trees. Методы `Queryable` ничего не выполняют — они добавляют узел в дерево. При перечислении `IQueryProvider` (EF Core) обходит дерево, транслирует его в SQL, выполняет запрос и материализует строки в объекты.

**Что важно знать на практике:**

- **отложенное выполнение** — запрос выполняется при `foreach`, `ToList`, `First`, `Count` и т. п., и выполняется заново при каждом перечислении;
- **замыкания** — лямбды захватывают переменные, а не значения;
- **где идёт фильтрация** — `AsEnumerable()` или тип `IEnumerable<T>` в сигнатуре переводит остаток запроса в память;
- **цена в горячем коде** — делегаты, итераторы и замыкания дают аллокации и интерфейсные вызовы; для критичных циклов обычный `for` быстрее, но в прикладном коде читаемость LINQ обычно важнее.

**Что спрашивают дальше:** разница `IEnumerable`/`IQueryable`, deferred execution, `Select` против `SelectMany`, `First` против `Single`, почему `Count()` на `IEnumerable` может перебрать всё, а на `List<T>` — нет.

## Что такое SOLID?

```yaml
category: csharp
level: middle
difficulty: 2
slug: csharp-chto-takoe-solid
tags: oop
```

SOLID — пять принципов объектно-ориентированного дизайна, которые сформулировал Роберт Мартин. Все они про одно: как устроить зависимости между классами так, чтобы изменение в одном месте не расползалось по всей системе.

| Буква | Принцип | Суть |
| --- | --- | --- |
| **S** | Single Responsibility | у класса одна причина для изменения |
| **O** | Open/Closed | расширяем поведение новым кодом, а не правкой старого |
| **L** | Liskov Substitution | наследник подставляется вместо базового без сюрпризов |
| **I** | Interface Segregation | много узких интерфейсов лучше одного «толстого» |
| **D** | Dependency Inversion | модули зависят от абстракций, а не от конкретных реализаций |

**SRP** — это не «один метод на класс», а «одна причина меняться» — точнее, один стейкхолдер. `InvoiceService`, который считает сумму, генерирует PDF и шлёт письмо, будут менять бухгалтерия, дизайнеры и админы почты независимо друг от друга.

**OCP** на практике — полиморфизм вместо `switch` по типу:

```csharp
public interface IDiscountRule { decimal Apply(Order order); }

public sealed class PriceCalculator(IEnumerable<IDiscountRule> rules)
{
    public decimal Total(Order o) => rules.Aggregate(o.Subtotal, (sum, r) => sum - r.Apply(o));
}
// новая скидка = новый класс + регистрация в DI, калькулятор не трогаем
```

**LSP** — самый «хитрый» принцип. Классический контрпример — `Square : Rectangle`: установка `Width` у квадрата меняет и `Height`, и код, рассчитанный на прямоугольник, ломается. В BCL есть свой пример: массив реализует `IList<T>`, но `Add` бросает `NotSupportedException`. Нарушение LSP — это усиление предусловий, ослабление постусловий или новые исключения в наследнике.

**ISP** — клиент не должен зависеть от методов, которыми не пользуется. Поэтому в .NET есть `IReadOnlyList<T>` рядом с `IList<T>`, а репозиторий часто делят на чтение и запись.

**DIP** не равно DI-контейнеру. Принцип говорит, что высокоуровневая логика (`OrderService`) владеет абстракцией (`IPaymentGateway`), а инфраструктура её реализует. Контейнер — лишь способ собрать граф объектов.

**Что проверяют на собеседовании:**

- умеете ли привести пример нарушения из реального кода, а не только расшифровать аббревиатуру;
- понимаете ли цену: слепое следование SOLID даёт интерфейс на каждый класс и десять слоёв абстракций (over-engineering). Принципы — эвристики, а не законы;
- связь с тестируемостью: DIP и ISP позволяют подменять зависимости в тестах;
- чем DIP отличается от IoC и DI.

## Что такое инкапсуляция, наследование, полиморфизм и абстракция?

```yaml
category: csharp
level: middle
difficulty: 2
slug: csharp-chto-takoe-inkapsulyaciya-nasledovanie-polimorfizm-i-abstrakciya
tags: oop
```

Это четыре базовых принципа ООП. Инкапсуляция скрывает состояние и защищает инварианты, наследование переиспользует и расширяет поведение базового типа, полиморфизм позволяет работать с разными типами через общий контракт, абстракция выделяет существенное и прячет детали реализации.

**Инкапсуляция** — не просто «поля private», а гарантия, что объект нельзя привести в некорректное состояние снаружи:

```csharp
public sealed class Account
{
    private readonly List<Transaction> _history = [];
    public decimal Balance { get; private set; }
    public IReadOnlyList<Transaction> History => _history;

    public void Withdraw(decimal amount)
    {
        if (amount <= 0 || amount > Balance) throw new InvalidOperationException();
        Balance -= amount;
        _history.Add(new Transaction(-amount));
    }
}
```

Свойство с публичным сеттером у каждого поля — формально инкапсуляция, по сути её отсутствие (anemic model).

**Наследование** в C# — одиночное для классов (`class B : A`) и множественное для интерфейсов. Структуры не наследуются. Наследование создаёт самую сильную связь между типами: наследник зависит от деталей базового класса (проблема «хрупкого базового класса»). Отсюда совет «composition over inheritance» — наследуйтесь, когда есть настоящее отношение «является» и выполняется LSP.

**Полиморфизм** бывает нескольких видов:

- **подтипов** (runtime) — `virtual`/`override` и интерфейсы, метод выбирается по фактическому типу объекта через таблицу виртуальных методов;
- **параметрический** — generics: `List<T>` работает с любым `T`;
- **ad hoc** — перегрузка методов и операторов, выбор на этапе компиляции.

```csharp
Shape[] shapes = [new Circle(1), new Square(2)];
var total = shapes.Sum(s => s.Area());   // вызовется Area конкретного типа
```

**Абстракция** — моделирование через контракт: `abstract class`, `interface`. Код, принимающий `Stream`, не знает, файл это, сеть или память. Абстракцию часто путают с инкапсуляцией: абстракция отвечает на вопрос «что объект делает», инкапсуляция — «как защищено его устройство».

**Что спрашивают дальше:** чем интерфейс отличается от абстрактного класса, `virtual`/`override`/`new`, почему `sealed` по умолчанию — хорошая практика (и небольшой бонус к производительности: JIT может девиртуализировать вызовы), пример нарушения LSP.

## Чем `interface` отличается от `abstract class`?

```yaml
category: csharp
level: middle
difficulty: 3
slug: csharp-chem-interface-otlichaetsya-ot-abstract-class
tags: oop
```

Интерфейс — контракт «что тип умеет», без состояния; класс может реализовать сколько угодно интерфейсов, и их могут реализовывать структуры. Абстрактный класс — частично реализованный базовый тип с состоянием, конструкторами и защищёнными членами; наследоваться можно только от одного. С C# 8 интерфейсы получили реализации по умолчанию, поэтому грань стала тоньше, но главное различие — состояние и одиночное наследование — осталось.

| | `interface` | `abstract class` |
| --- | --- | --- |
| Множественность | сколько угодно | один базовый класс |
| Поля экземпляра | нет | да |
| Конструкторы | нет | да |
| Модификаторы доступа членов | с C# 8 можно, по умолчанию `public` | любые, включая `protected` |
| Реализация методов | default interface methods (C# 8+) | обычные и `virtual` методы |
| Статические абстрактные члены | да, `static abstract` (C# 11) | нет |
| Реализуют структуры | да | нет |
| Отношение | «умеет» (can-do) | «является» (is-a) |

```csharp
public interface IClock { DateTimeOffset Now { get; } }

public abstract class Repository<T>(DbContext db) where T : class
{
    protected DbContext Db { get; } = db;                  // общее состояние
    public virtual Task<T?> FindAsync(int id) => Db.FindAsync<T>(id).AsTask();
    public abstract IQueryable<T> Query();                  // обязать наследника
}
```

**Default interface methods — не замена абстрактному классу.** Их придумали для эволюции API: добавить метод в опубликованный интерфейс, не сломав существующих реализаторов. Подвох: метод по умолчанию доступен только через ссылку типа интерфейса.

```csharp
public interface ILogger { void Log(string m); void Info(string m) => Log("INFO " + m); }
class ConsoleLogger : ILogger { public void Log(string m) => Console.WriteLine(m); }

new ConsoleLogger().Info("x");          // ошибка компиляции
((ILogger)new ConsoleLogger()).Info("x"); // работает
```

**Static abstract members** открыли generic math: `INumber<T>` требует от типа статические операторы, и можно написать `T Sum<T>(T[] xs) where T : INumber<T>`.

**Как выбирать:**

- интерфейс — по умолчанию для зависимостей (DI, моки в тестах), для возможностей, которые комбинируются (`IDisposable`, `IComparable<T>`), и для структур;
- абстрактный класс — когда у семейства типов есть общее состояние и общий алгоритм (паттерн Template Method), а наследники переопределяют шаги;
- часто их комбинируют: интерфейс как контракт + абстрактный базовый класс как удобная частичная реализация (`IList<T>` и `Collection<T>`).

**Что спрашивают дальше:** явная реализация интерфейса (`void IDisposable.Dispose()`), что будет при конфликте двух интерфейсов с одинаковыми методами, боксинг структуры при приведении к интерфейсу и как его избегают через generic-ограничения (`where T : IComparable<T>`).

## Что делают `virtual`, `override` и `new`?

```yaml
category: csharp
level: middle
difficulty: 3
slug: csharp-chto-delayut-virtual-override-i-new
tags: oop
```

`virtual` разрешает наследникам переопределить метод, `override` переопределяет его — и вызов через ссылку базового типа попадёт в реализацию наследника. `new` не переопределяет, а скрывает член базового класса: какой метод вызовется, решает статический тип переменной, а не фактический тип объекта.

```csharp
class Base
{
    public virtual string Who() => "Base";
    public string Hello() => "Base.Hello";
}

class Derived : Base
{
    public override string Who() => "Derived";
    public new string Hello() => "Derived.Hello";
}

Base b = new Derived();
b.Who();                  // "Derived"     — виртуальный вызов по типу объекта
b.Hello();                // "Base.Hello"  — решено компилятором по типу переменной
((Derived)b).Hello();     // "Derived.Hello"
```

**Механизм.** У каждого типа есть таблица виртуальных методов (vtable в MethodTable). `override` записывает свою реализацию в тот же слот, что и базовый `virtual`, поэтому вызов `callvirt` через любую ссылку находит новую версию. `new` (или `new virtual`) создаёт новый слот; старый слот остаётся с базовой реализацией, и ссылка типа `Base` продолжает смотреть в него.

**Правила и детали:**

- в C# методы по умолчанию **невиртуальные** (в отличие от Java) — это осознанное решение ради версионирования и производительности;
- без `new` при совпадении сигнатуры компилятор выдаст предупреждение CS0108 и всё равно скроет метод — `new` лишь делает намерение явным;
- `sealed override` запрещает дальнейшее переопределение в наследниках;
- `abstract` — неявно `virtual` без реализации, наследник обязан сделать `override`;
- сигнатура и доступность `override` должны совпадать с базовой; с C# 9 разрешены ковариантные возвращаемые типы (`override Derived Clone()` вместо `Base Clone()`);
- `base.Who()` вызывает реализацию родителя невиртуально.

**Ловушка — виртуальный вызов в конструкторе.** Конструктор базового класса, вызвавший `virtual`-метод, попадёт в `override` наследника до того, как отработал конструктор наследника, — поля наследника ещё не инициализированы:

```csharp
class A { public A() => Init(); protected virtual void Init() { } }
class B : A
{
    private readonly List<int> _items = [];   // инициализаторы полей идут до base-ctor, тут безопасно
    private string _name;
    public B() => _name = "b";
    protected override void Init() => Console.WriteLine(_name.Length); // NRE: _name ещё null
}
```

**Когда `new` оправдан:** почти никогда в собственном коде. Обычно он нужен, когда базовый класс из чужой библиотеки в новой версии добавил член с тем же именем, или чтобы сузить возвращаемый тип невиртуального члена. Скрытие — источник багов: поведение зависит от того, через какую ссылку вызвали.

**Производительность.** Виртуальный вызов — косвенный переход через таблицу, JIT не может его заинлайнить. Для `sealed`-классов и при известном точном типе JIT делает девиртуализацию, а в .NET 8+ динамическая PGO девиртуализирует и «горячие» мономорфные вызовы с guarded-проверкой типа.

## Чем отличаются `const`, `readonly` и `static readonly`?

```yaml
category: csharp
level: middle
difficulty: 3
slug: csharp-chem-otlichayutsya-const-readonly-i-static-readonly
```

`const` — константа времени компиляции: значение вшивается прямо в IL каждого места использования. `readonly` — поле экземпляра, которое можно присвоить только при объявлении или в конструкторе. `static readonly` — то же, но одно на тип, присваивается в статическом конструкторе и вычисляется во время выполнения.

| | `const` | `readonly` | `static readonly` |
| --- | --- | --- | --- |
| Когда известно значение | при компиляции | в runtime, в конструкторе | в runtime, в статическом конструкторе |
| Принадлежит | типу (неявно static) | экземпляру | типу |
| Допустимые типы | примитивы, `decimal`, `string`, enum, `null` для ссылок | любые | любые |
| Где хранится | литерал в IL вызывающего кода | поле объекта | статическое поле |
| Можно использовать в `case`, атрибутах, default-параметрах | да | нет | нет |

```csharp
public class Config
{
    public const int MaxRetries = 3;
    public static readonly TimeSpan Timeout = TimeSpan.FromSeconds(30);  // const нельзя: не литерал
    private readonly ILogger _logger;

    public Config(ILogger logger) => _logger = logger;   // readonly присваиваем тут
}
```

**Главная ловушка `const` — версионирование.** Значение подставляется в сборку-потребителя при компиляции. Если библиотека A объявила `public const int Version = 1`, а сборка B её использует, после обновления A до `Version = 2` без перекомпиляции B продолжит видеть `1`. Поэтому публичные значения, которые могут измениться, объявляют `static readonly`, а `const` оставляют для действительно вечных вещей (`Math.PI`, коды протокола) и для `private`/`internal`.

**`readonly` защищает ссылку, а не объект.** `readonly List<int> _items` нельзя переприсвоить, но можно сделать `_items.Add(1)`. Для структур иначе: у `readonly`-поля типа struct нельзя менять поля, а вызов не-`readonly` метода породит defensive copy.

**Производительность.** `static readonly` поля примитивов после инициализации типа JIT (с tiered compilation) рассматривает как константы и может сворачивать ветки: `if (Config.FeatureEnabled)` в оптимизированном коде превращается в безусловный код или исчезает. Поэтому разница с `const` в скорости обычно пренебрежима.

**Смежное:**

- `readonly struct` и `readonly`-методы структур — гарантия, что метод не меняет состояние;
- `ref readonly` параметры и возвращаемые значения;
- с C# 10 `const string` можно собирать интерполяцией из других констант: `const string Url = $"{Base}/api";`;
- `static readonly` инициализируется при первом обращении к типу — исключение там превратится в `TypeInitializationException`, и тип станет непригодным до конца жизни процесса.

## Что делают `ref`, `out` и `in`?

```yaml
category: csharp
level: middle
difficulty: 3
slug: csharp-chto-delayut-ref-out-i-in
```

Все три передают аргумент по ссылке — метод получает адрес переменной, а не копию. Отличаются контрактом: `ref` — читать и писать, переменная должна быть инициализирована до вызова; `out` — метод обязан присвоить значение, на входе оно не требуется; `in` — только чтение, передаётся по ссылке ради того, чтобы не копировать большую структуру.

| | До вызова инициализирована | Метод может читать | Метод может писать | Метод обязан присвоить |
| --- | --- | --- | --- | --- |
| `ref` | да | да | да | нет |
| `out` | нет | только после присваивания | да | да |
| `in` | да | да | нет | нет |

```csharp
static void Swap<T>(ref T a, ref T b) => (a, b) = (b, a);

if (int.TryParse("42", out var n)) Console.WriteLine(n);   // out var — C# 7

static double Length(in Vector3 v) => Math.Sqrt(v.X * v.X + v.Y * v.Y + v.Z * v.Z);
```

**Для ссылочных типов** `ref` означает ссылку на ссылку: без `ref` метод может менять содержимое объекта, но присваивание параметру `list = new List<int>()` не видно снаружи; с `ref` — видно.

**Подводные камни `in`:**

- если структура не `readonly`, вызов её метода через `in`-параметр делает defensive copy — выигрыш от передачи по ссылке пропадает. `in` имеет смысл с `readonly struct`;
- для маленьких структур (`int`, `DateTime`) `in` медленнее, чем передача по значению: лишняя косвенность;
- в месте вызова `in` можно не писать, и тогда компилятор при необходимости создаст временную копию (например, для литерала). С C# 12 есть `ref readonly`-параметры — то же, но вызывающий обязан передать именно переменную (lvalue).

**Ограничения:** параметры `ref`/`out`/`in` нельзя объявлять у `async`-методов и итераторов (`yield`), и их нельзя захватить в лямбду (C# 13 разрешил `ref`-локальные переменные в async-методах, но только если они не живут через `await`). Причина — ссылка может указывать на стек, а тело async-метода и лямбды переживает кадр стека. Перегрузки, отличающиеся только `ref` против `out`, запрещены — в IL это одно и то же (managed pointer, `&`), `out` — лишь атрибут.

**Родственные возможности:** `ref`-локальные переменные и `ref`-возвраты (`ref int Find(int[] arr)` возвращает ссылку на элемент массива), `ref struct` (`Span<T>`), `scoped` (C# 11) для ограничения времени жизни ссылки. На практике `out` чаще всего встречается в паттерне `TryXxx`, а `ref` — в высокопроизводительном коде; в прикладном коде вместо нескольких `out` лучше вернуть кортеж или record.

## Чем отличаются `record`, `class` и `struct`?

```yaml
category: csharp
level: middle
difficulty: 3
slug: csharp-chem-otlichayutsya-record-class-i-struct
tags: value-types
```

Различия лежат на двух независимых осях. Первая — семантика передачи: `class` и `record` (он же `record class`) ссылочные, `struct` и `record struct` копируются по значению. Вторая — семантика равенства: `class` сравнивается по ссылке, а `record` и `record struct` получают от компилятора сравнение по значению всех полей. `record` — не новый вид типа в CLR, а обычный класс или структура с набором сгенерированных членов.

| | `class` | `record` | `struct` | `record struct` |
| --- | --- | --- | --- | --- |
| Вид типа | ссылочный | ссылочный | значимый | значимый |
| `Equals` по умолчанию | по ссылке | по полям, сгенерирован | по полям: побитово или через reflection (медленно) | по полям, сгенерирован |
| `==` | по ссылке | по значению | не определён | по значению |
| `with` | нет | да | да (C# 10) | да |
| `ToString` | имя типа | `Person { Name = ... }` | имя типа | как у record |
| Позиционные свойства | — | `get; init;` | — | `get; set;` (`readonly record struct` — `init`) |
| Наследование | да | только от record | нет | нет |

**Что генерирует компилятор для `record`:** конструктор и `Deconstruct` для позиционных параметров, `Equals(object)`, `Equals(Person)` (`IEquatable<T>`), `GetHashCode`, операторы `==`/`!=`, `ToString` через `PrintMembers`, метод клонирования для `with` и защищённое свойство `EqualityContract`, из-за которого `Person` и наследник `Employee` с теми же полями не равны.

```csharp
public record Person(string Name, int Age);

var a = new Person("Ann", 30);
var b = new Person("Ann", 30);
a == b;                          // true
ReferenceEquals(a, b);           // false
var older = a with { Age = 31 }; // поверхностная копия с изменением
```

**Подводные камни record:**

- **равенство не глубокое:** поле `List<string>` сравнивается по ссылке, два record с одинаковыми списками не равны;
- **`with` копирует поверхностно** — копия и оригинал делят один и тот же список;
- **неизменяемость тоже поверхностная**, а `record struct` без `readonly` вообще изменяем;
- **не для EF Core-сущностей:** сущность идентифицируется ключом, а не всеми полями; сравнение по значению ломает change tracking и коллекции навигаций;
- **`GetHashCode` зависит от всех полей** — изменяемый record в `HashSet` «теряется» после изменения.

**Как выбирать:**

- `class` — сущности с идентичностью и жизненным циклом, сервисы, всё с поведением;
- `record` — DTO, сообщения, команды и события, value objects, результаты запросов — данные, которые сравниваются по содержимому;
- `readonly record struct` — маленькие value objects без аллокаций: `Money`, строго типизированные `OrderId`;
- `struct` — низкоуровневые типы, где нужен полный контроль над layout и равенством (обычно с ручной реализацией `IEquatable<T>`).

**Что спрашивают дальше:** как переопределить равенство в record (объявить свой `Equals(Person? other)` — компилятор его не сгенерирует), почему у `struct` нужен `IEquatable<T>`, как record ведёт себя при наследовании, чем `init` отличается от `set`.

## Что такое `init` accessor?

```yaml
category: csharp
level: middle
difficulty: 2
slug: csharp-chto-takoe-init-accessor
```

`init` (C# 9) — аксессор свойства, который разрешает присваивание только на этапе создания объекта: в конструкторе, в инициализаторе объекта `{ ... }` и в выражении `with`. После этого свойство становится доступным только для чтения. Это позволяет делать неизменяемые типы без громоздких конструкторов со всеми параметрами.

```csharp
public class User
{
    public string Name { get; init; } = "";
    public string? Email { get; init; }
}

var u = new User { Name = "Ann", Email = "a@x.io" };   // можно
u.Name = "Bob";                                        // CS8852: только при инициализации
var u2 = u with { Name = "Bob" };                      // ошибка: with — только для record, struct и анонимных типов
```

**Чем отличается от соседей:**

| | Где можно присвоить |
| --- | --- |
| `{ get; }` | только в конструкторе (и инициализаторе свойства) |
| `{ get; init; }` | конструктор + инициализатор объекта + `with` |
| `{ get; private set; }` | где угодно внутри класса, в любой момент |
| `{ get; set; }` | где угодно |

**Как это устроено.** В IL `init` — обычный метод `set_Name`, но его возвращаемый тип помечен модификатором `modreq(IsExternalInit)`. Компилятор C# 9+ знает правило и разрешает вызов только в контексте инициализации. Старые компиляторы и другие языки, не понимающие `modreq`, не могут вызвать такой сеттер вовсе. Из-за этого для `netstandard2.0` нужно вручную объявить класс `System.Runtime.CompilerServices.IsExternalInit` (или подключить polyfill-пакет).

**Важно: это проверка компилятора, а не рантайма.** Reflection (`PropertyInfo.SetValue`) и сериализаторы спокойно меняют `init`-свойства после создания — так `System.Text.Json` и EF Core и заполняют такие объекты.

**`init` не делает свойство обязательным.** Если его не указать в инициализаторе, останется значение по умолчанию. Для обязательности есть `required` (C# 11):

```csharp
public class User
{
    public required string Name { get; init; }
}

var u = new User();              // CS9035: не задано обязательное свойство Name
var ok = new User { Name = "Ann" };
```

Конструктор с атрибутом `[SetsRequiredMembers]` снимает это требование для вызывающего кода.

**Где используется:**

- позиционные `record` генерируют свойства `{ get; init; }`;
- DTO и опции конфигурации — читаемый инициализатор объекта вместо конструктора с десятью параметрами;
- `init` бывает только у свойств и индексаторов (для полей есть `readonly`), в том числе в `readonly struct`.

**Ловушка поверхностной неизменяемости** та же, что у `readonly`: `init`-свойство типа `List<T>` нельзя переприсвоить, но содержимое списка менять можно.

## Что такое covariance и contravariance?

```yaml
category: csharp
level: middle
difficulty: 2
slug: csharp-chto-takoe-covariance-i-contravariance
```

Вариантность определяет, можно ли подставить generic-тип с одним аргументом вместо того же generic-типа с другим, если аргументы связаны наследованием. Ковариантность (`out T`) сохраняет направление: `IEnumerable<string>` можно использовать как `IEnumerable<object>`. Контравариантность (`in T`) разворачивает его: `Action<object>` можно использовать как `Action<string>`.

```csharp
IEnumerable<string> strings = ["a", "b"];
IEnumerable<object> objects = strings;          // ковариантность: out T

Action<object> printAny = o => Console.WriteLine(o);
Action<string> printString = printAny;          // контравариантность: in T

IComparer<Animal> byWeight = ...;
IComparer<Cat> catComparer = byWeight;          // сравнивающий животных сравнит и котов
```

**Почему именно так.** Ковариантность безопасна, когда `T` только **выходит** из типа: кто ждёт `object`, получив `string`, не пострадает. Контравариантность безопасна, когда `T` только **входит**: метод, умеющий принять любой `object`, справится и со `string`. Отсюда ключевые слова `out` и `in` — компилятор проверяет, что `T` в `out`-позиции не встречается как параметр метода, и наоборот.

**Почему `List<T>` инвариантен:**

```csharp
List<string> s = [];
List<object> o = s;     // не компилируется — и правильно:
o.Add(42);              // иначе в список строк попало бы число
```

`T` в `List<T>` и входит (`Add`), и выходит (индексатор), поэтому ни одно направление небезопасно. Вариантным может быть только интерфейс только на чтение: `IReadOnlyList<out T>`, `IEnumerable<out T>`.

**Ограничения:**

- вариантность объявляется только у **интерфейсов и делегатов**, не у классов и структур;
- работает только для **ссылочных** аргументов: `IEnumerable<int>` нельзя привести к `IEnumerable<object>` — это потребовало бы боксинга каждого элемента, а вариантность — это переиспользование той же ссылки без преобразования;
- в BCL: `out` — `IEnumerable<T>`, `IEnumerator<T>`, `IReadOnlyList<T>`, `IReadOnlyCollection<T>`, `Func<..., TResult>`; `in` — `IComparer<T>`, `IEqualityComparer<T>`, `Action<T>`, параметры `Func<T, ...>`.

**Исторический «дефект» — ковариантность массивов.** Массивы ссылочных типов ковариантны с C# 1.0, но небезопасно:

```csharp
object[] arr = new string[1];
arr[0] = 42;            // ArrayTypeMismatchException в runtime
```

Из-за этого запись в массив ссылочного типа сопровождается проверкой типа в runtime (JIT может её опустить, например, когда тип элемента `sealed`). Generic-вариантность интерфейсов таких проверок не требует — она безопасна статически.

**Где это встречается на практике:** передача `List<Derived>` в метод, принимающий `IEnumerable<Base>`; компараторы и обработчики базового типа для производных; DI с generic-обработчиками (`INotificationHandler<in T>` в MediatR). Для ковариантных возвращаемых типов в `override` есть отдельная фича C# 9 — covariant return types, к generic-вариантности она отношения не имеет.

## Что такое delegates?

```yaml
category: csharp
level: middle
difficulty: 2
slug: csharp-chto-takoe-delegates
```

Делегат — типобезопасная ссылка на метод: объект, который хранит, какой метод вызвать и (для экземплярного метода) на каком объекте. Объявление `delegate` описывает сигнатуру, а любой метод с совместимой сигнатурой можно превратить в экземпляр делегата, передать как значение и вызвать позже. Это основа колбэков, событий, LINQ и лямбд.

```csharp
public delegate bool Filter(int value);

static bool IsEven(int x) => x % 2 == 0;

Filter f = IsEven;                 // method group → делегат
Filter g = x => x > 10;            // лямбда → делегат
f(4);                              // true, то же что f.Invoke(4)

int[] Apply(int[] xs, Filter filter) => xs.Where(x => filter(x)).ToArray();
```

**Что это в рантайме.** `delegate` компилируется в `sealed`-класс, унаследованный от `System.MulticastDelegate`, с методами `Invoke`, `BeginInvoke`/`EndInvoke` (в .NET Core не поддерживаются, бросают `PlatformNotSupportedException`). Экземпляр хранит `_target` (объект или `null` для статического метода) и указатель на метод. Делегат — ссылочный тип, создание — аллокация в куче.

**Многоадресность.** Любой делегат может содержать список вызовов:

```csharp
Action log = () => Console.WriteLine("A");
log += () => Console.WriteLine("B");
log();              // A, затем B
// log -= handler;  удаляет последнее вхождение того же метода с тем же target;
//                  анонимную лямбду так не отписать — новая лямбда = другой делегат
```

Делегаты неизменяемы: `+=` создаёт новый экземпляр с новым списком. У многоадресного делегата с возвращаемым значением вызывающий получит результат только последнего метода, а исключение в одном обработчике прервёт вызов остальных.

**Встроенные типы.** Свои `delegate` сегодня объявляют редко — есть `Action<...>`, `Func<..., TResult>`, `Predicate<T>`. Свой тип оправдан, когда нужны `ref`/`out`-параметры, осмысленное имя в публичном API или `params`.

**Совместимость.** Два делегатных типа с одинаковой сигнатурой — разные типы, `Filter` нельзя присвоить `Predicate<int>` напрямую. Но делегаты вариантны: метод, возвращающий `string`, подходит для `Func<object>`.

**Подводные камни:**

- **захват переменных в лямбде** создаёт класс-замыкание — лишняя аллокация и продление жизни захваченных объектов;
- **утечки памяти:** делегат держит ссылку на `_target`, поэтому подписка короткоживущего объекта на долгоживущий источник не даёт первому умереть;
- **method group в горячем цикле:** до C# 11 `list.Where(IsEven)` создавал новый делегат при каждом вызове, с C# 11 компилятор кэширует делегат для статических method group, как и для лямбд без захвата;
- **вызов `null`-делегата** — `NullReferenceException`, поэтому `handler?.Invoke(...)`.

**Что спрашивают дальше:** как делегаты связаны с событиями, чем `Func` отличается от `Expression<Func>`, во что компилируется замыкание, почему многоадресный делегат медленнее одиночного.

## Что такое events?

```yaml
category: csharp
level: middle
difficulty: 2
slug: csharp-chto-takoe-events
```

Событие (`event`) — член класса, который даёт внешнему коду только подписаться (`+=`) и отписаться (`-=`) от делегата, а вызывать его может только владелец. Это обёртка над делегатом, реализующая паттерн «наблюдатель» с инкапсуляцией: подписчики не могут вызвать событие за издателя, обнулить чужие подписки или прочитать список обработчиков.

```csharp
public sealed class OrderService
{
    public event EventHandler<OrderPlacedEventArgs>? OrderPlaced;

    public void Place(Order order)
    {
        // ... сохранили заказ
        OrderPlaced?.Invoke(this, new OrderPlacedEventArgs(order.Id));
    }
}

public sealed record OrderPlacedEventArgs(int OrderId);   // наследовать EventArgs не обязательно (с .NET Framework 4.5)

var svc = new OrderService();
svc.OrderPlaced += (sender, e) => Console.WriteLine($"Order {e.OrderId}");
// svc.OrderPlaced = null;     // ошибка: снаружи только += и -=
// svc.OrderPlaced(...);       // ошибка: вызвать может только OrderService
```

**Чем событие отличается от публичного поля-делегата.** С полем `public Action? OrderPlaced` любой может написать `OrderPlaced = handler` (стерев всех остальных подписчиков) или вызвать его сам. `event` закрывает обе дыры — снаружи видны только методы `add`/`remove`.

**Во что компилируется.** Field-like event разворачивается в приватное поле-делегат и пару аксессоров `add_OrderPlaced`/`remove_OrderPlaced`. Сгенерированные аксессоры потокобезопасны: используют цикл с `Interlocked.CompareExchange`. Аксессоры можно написать вручную — например, чтобы хранить обработчики в `EventHandlerList` (так делает WinForms, где у контрола сотни событий, а подписываются на единицы) или проксировать подписку на внутренний объект.

**Потокобезопасный вызов.** `OrderPlaced?.Invoke(...)` читает поле один раз, поэтому отписка из другого потока между проверкой и вызовом не приведёт к `NullReferenceException`. Старый паттерн `if (OrderPlaced != null) OrderPlaced(...)` этим страдал. Но обработчик всё равно может вызваться сразу после отписки — это нормальная гонка, её надо учитывать.

**Главная ловушка — утечки памяти.** Издатель держит ссылку на подписчика через `_target` делегата. Если долгоживущий объект (синглтон, статическое событие) имеет подписчика с коротким жизненным циклом (страница, ViewModel, scoped-сервис), подписчик не будет собран, пока не отпишется. Лечится явной отпиской в `Dispose` или weak events (`WeakEventManager` в WPF).

**Другие особенности:**

- обработчики вызываются синхронно и последовательно в потоке издателя; исключение в одном прерывает остальные;
- `async void`-обработчик — единственное легитимное место для `async void`, но его исключение нельзя поймать у издателя;
- соглашение .NET — сигнатура `(object? sender, TEventArgs e)` и метод `protected virtual void OnOrderPlaced(...)` для наследников.

**Когда событий не хватает:** для асинхронной обработки, гарантированной доставки или межсервисного взаимодействия используют `Channel<T>`, `IObservable<T>` (Rx) или брокер сообщений. Внутри одного процесса в прикладном коде часто берут mediator-нотификации — они не держат ссылок на подписчиков.

## Чем отличаются `Action`, `Func` и `Predicate`?

```yaml
category: csharp
level: middle
difficulty: 3
slug: csharp-chem-otlichayutsya-action-func-i-predicate
```

Это готовые generic-делегаты из BCL, чтобы не объявлять свои. `Action<T1..T16>` — метод, который ничего не возвращает (`void`). `Func<T1..T16, TResult>` — метод, возвращающий значение, последний параметр типа — всегда результат. `Predicate<T>` — частный случай «принимает `T`, возвращает `bool`», появился ещё в .NET 2.0, до `Func`.

| Делегат | Сигнатура | Пример |
| --- | --- | --- |
| `Action` | `void ()` | `Action tick = () => counter++;` |
| `Action<T>` | `void (T)` | `Action<string> log = Console.WriteLine;` |
| `Func<TResult>` | `TResult ()` | `Func<DateTime> now = () => DateTime.UtcNow;` |
| `Func<T, TResult>` | `TResult (T)` | `Func<int, string> fmt = x => x.ToString("N0");` |
| `Predicate<T>` | `bool (T)` | `Predicate<int> isEven = x => x % 2 == 0;` |

**`Predicate<T>` и `Func<T, bool>` — разные типы.** Сигнатура одинаковая, но делегатные типы не совместимы по присваиванию:

```csharp
Predicate<int> p = x => x > 0;
Func<int, bool> f = p;              // ошибка компиляции
Func<int, bool> f2 = x => p(x);     // обёртка
Func<int, bool> f3 = p.Invoke;      // или method group — новый делегат
```

Исторически `Predicate<T>` используют методы `List<T>` и `Array` (`FindAll`, `RemoveAll`, `Exists`, `Array.Find`), а LINQ, появившийся в .NET 3.5, — `Func<T, bool>` (`Where`, `Any`, `First`). Лямбда подходит и туда, и туда, поэтому разница заметна только когда делегат хранят в переменной. В новом коде принято `Func<T, bool>`.

**Вариантность.** Входные параметры объявлены `in`, результат `Func` — `out`:

```csharp
Func<string> getS = () => "x";
Func<object> getO = getS;           // ковариантность результата
Action<object> any = Console.WriteLine;
Action<string> str = any;           // контравариантность аргумента
```

**Когда объявлять свой делегат вместо `Action`/`Func`:**

- нужны `ref`, `out`, `in` или `params` — generic-параметр не может быть `ref`, и `Func<ref int>` не бывает;
- нужен `ref struct` в параметре (`Span<T>`) — до C# 13 и `allows ref struct` у `Func`/`Action` это было невозможно, в .NET 9 BCL-делегаты получили это разрешение;
- делегат — часть публичного API, и осмысленное имя (`RequestDelegate` в ASP.NET Core, `ValidationCallback`) документирует назначение лучше, чем `Func<HttpContext, Task>`.

**Асинхронные варианты** — просто `Func<Task>` и `Func<T, Task<TResult>>`. Классическая ошибка — передать async-лямбду туда, где ожидается `Action`: она превращается в `async void`, вызывающий не дождётся завершения, а исключение уронит процесс.

```csharp
list.ForEach(async x => await SaveAsync(x));   // async void — fire-and-forget
```

**Натуральный тип лямбды (C# 10).** `var f = (int x) => x * 2;` компилятор выведет как `Func<int, int>`; лямбда с `ref`-параметром получит синтезированный делегатный тип.

## Что такое lambda expression?

```yaml
category: csharp
level: middle
difficulty: 2
slug: csharp-chto-takoe-lambda-expression
```

Лямбда-выражение — анонимная функция, записанная прямо в месте использования: `x => x * 2`. Сама по себе она не имеет типа «функция» — компилятор превращает её либо в **делегат** (`Func<int, int>`), либо в **дерево выражений** (`Expression<Func<int, int>>`), в зависимости от того, какой тип ожидается. Лямбда может захватывать внешние переменные — тогда образуется замыкание.

```csharp
Func<int, int> square = x => x * x;                   // expression lambda
Func<int, int, int> add = (a, b) => { return a + b; }; // statement lambda
Action hello = () => Console.WriteLine("hi");

var parse = (string s) => int.Parse(s);               // C# 10: натуральный тип Func<string, int>
var inc = (int x = 1) => x + 1;                       // C# 12: параметры по умолчанию
Func<int, int> ignore = _ => 42;                      // discard-параметр
```

**Во что компилируется.** Зависит от того, что лямбда захватывает:

- **ничего** — статический метод в скрытом классе `<>c`, делегат создаётся один раз и кэшируется в статическом поле; повторные вызовы без аллокаций;
- **только `this`** — экземплярный метод текущего класса, делегат создаётся при каждом выполнении выражения;
- **локальные переменные или параметры** — компилятор создаёт класс-замыкание (`<>c__DisplayClass`), переносит захваченные переменные в его поля и делает лямбду его методом. Аллокация класса-замыкания и делегата.

```csharp
int threshold = 10;
Func<int, bool> big = x => x > threshold;   // threshold теперь поле объекта-замыкания
threshold = 100;
big(50);                                    // false: захвачена переменная, а не значение
```

**Ловушки:**

- **захват переменной, а не значения** — изменение после создания лямбды видно внутри; классика — `for (int i...)` с захватом `i` (все делегаты увидят финальное значение). У `foreach` с C# 5 переменная своя на каждой итерации;
- **продление жизни** — захваченный большой объект живёт, пока жив делегат;
- **общее замыкание** — две лямбды в одном методе, захватывающие разные переменные, могут делить один объект-замыкание, и короткоживущая лямбда удержит данные длинной;
- **скрытые аллокации в горячем коде** — `static`-лямбда (C# 9) запрещает захват и гарантирует отсутствие замыкания: `list.Where(static x => x > 0)`;
- **async-лямбда в `Action`** превращается в `async void`.

**Лямбда как дерево выражений.** Если параметр метода — `Expression<Func<T, bool>>` (как у `IQueryable.Where`), компилятор не генерирует IL тела, а строит объектную модель выражения. Её можно разобрать и транслировать в SQL — так работает EF Core. Statement-лямбды (с `{ }`) в дерево выражений не конвертируются.

**Лямбда vs локальная функция.** Локальная функция (`int Square(int x) => x * x;` внутри метода) не требует делегата, если её просто вызывают, и захватывает переменные в структуру, а не в класс — без аллокации. Поддерживает `yield`, рекурсию и generic-параметры естественным образом. Если делегат не нужен, локальная функция обычно эффективнее.

## Что такое extension methods?

```yaml
category: csharp
level: middle
difficulty: 2
slug: csharp-chto-takoe-extension-methods
```

Extension method — статический метод статического класса, первый параметр которого помечен `this`. Его можно вызывать так, будто это метод экземпляра расширяемого типа: `text.IsBlank()` вместо `StringExtensions.IsBlank(text)`. Это синтаксический сахар — тип не меняется, доступа к приватным членам нет, компилятор просто переписывает вызов в статический.

```csharp
public static class StringExtensions
{
    public static bool IsBlank(this string? s) => string.IsNullOrWhiteSpace(s);

    public static string Truncate(this string s, int max) =>
        s.Length <= max ? s : s[..max] + "…";
}

"  ".IsBlank();                 // true
string? name = null;
name.IsBlank();                 // true — вызов на null не падает, это статический метод
```

**Как компилятор выбирает метод.** Сначала ищутся экземплярные методы типа; extension-методы рассматриваются, только если подходящего экземплярного нет. Поиск идёт по пространствам имён, подключённым через `using`, начиная с ближайшего. Отсюда следствия:

- экземплярный метод с той же сигнатурой всегда побеждает — если в новой версии библиотеки у типа появится свой `Truncate`, ваш extension молча перестанет вызываться;
- без нужного `using` метод «исчезает» — поэтому пакеты кладут расширения DI в namespace `Microsoft.Extensions.DependencyInjection`, чтобы они были видны сразу;
- два extension-метода с одинаковой сигнатурой из разных namespace дают ошибку неоднозначности.

**Где это используется в .NET:**

- **весь LINQ** — `Where`, `Select` и т. д. это расширения `IEnumerable<T>` и `IQueryable<T>` в классах `Enumerable` и `Queryable`;
- **регистрация сервисов** — `services.AddDbContext<T>()`, `app.UseAuthentication()`;
- **расширение интерфейсов** — метод для всех реализаций `IEnumerable<T>` сразу, без базового класса;
- **fluent API и builder'ы**.

**Особенности:**

- `this ref` для структур (C# 7.2) позволяет расширению менять значение без копии: `public static void Inc(this ref Counter c)`;
- расширения работают с generic-ограничениями: `public static T Clamp<T>(this T v, T min, T max) where T : IComparable<T>`;
- их нельзя вызывать через `dynamic` — это привязка на этапе компиляции;
- полиморфизма нет: метод выбирается по статическому типу выражения, а не по фактическому.

**C# 14 — extension members.** Новый синтаксис `extension` блоков позволяет объявлять не только методы, но и extension-свойства и статические члены расширяемого типа:

```csharp
public static class EnumerableExtensions
{
    extension<T>(IEnumerable<T> source)
    {
        public bool IsEmpty => !source.Any();         // extension-свойство
    }
}
```

Старые `this`-методы продолжают работать и совместимы с новым синтаксисом.

**Когда не стоит:** если нужен доступ к состоянию объекта или полиморфизм — это метод класса. Засорять `object` или `string` десятками расширений на «удобство» — плохая практика: они появляются в IntelliSense у всего кода, подключившего namespace.

## Что такое pattern matching в C#?

```yaml
category: csharp
level: middle
difficulty: 2
slug: csharp-chto-takoe-pattern-matching-v-c
```

Pattern matching — способ проверить значение на соответствие «форме» (тип, константа, диапазон, значения свойств, структура списка) и одновременно извлечь из него данные. Работает в `is`, в `switch`-операторе и в `switch`-выражении. Появился в C# 7 с type pattern и с каждой версией расширялся — до C# 11 со списковыми шаблонами.

```csharp
if (obj is string { Length: > 0 } s)          // тип + свойство + переменная
    Console.WriteLine(s.ToUpper());

decimal Discount(Order o) => o switch
{
    { Total: > 1000, Customer.IsVip: true } => 0.15m,   // extended property pattern (C# 10)
    { Total: > 1000 }                      => 0.10m,
    { Items.Count: 0 }                     => throw new InvalidOperationException(),
    _                                      => 0m,
};
```

**Виды шаблонов:**

| Шаблон | Пример | Версия |
| --- | --- | --- |
| type / declaration | `x is int n` | C# 7 |
| constant | `x is null`, `case 42` | C# 7 |
| var | `x is var v` | C# 7 |
| property | `p is { Age: >= 18 }` | C# 8 |
| positional | `point is (0, 0)` — через `Deconstruct` | C# 8 |
| tuple | `(a, b) switch { (true, false) => ... }` | C# 8 |
| relational | `> 0`, `<= 100` | C# 9 |
| logical | `and`, `or`, `not` | C# 9 |
| list | `[1, 2, ..]`, `[var first, .., var last]` | C# 11 |

```csharp
string Classify(int[] xs) => xs switch
{
    []                  => "пусто",
    [var single]        => $"один: {single}",
    [0, ..]             => "начинается с нуля",
    [.., var last]      => $"последний: {last}",
};

bool IsLetter(char c) => c is >= 'a' and <= 'z' or >= 'A' and <= 'Z';
```

**Почему `is null` лучше `== null`.** Оператор `==` может быть перегружен, и `x == null` вызовет пользовательский код. `is null` и `is not null` всегда проверяют ссылку напрямую.

**Что даёт компилятор:**

- **проверка полноты** — `switch`-выражение без `_` над enum или иерархией выдаст предупреждение CS8509, если покрыты не все случаи, а в runtime бросит `SwitchExpressionException`;
- **недостижимые ветки** — ветка, полностью покрытая предыдущими, — ошибка компиляции, поэтому порядок важен: частное выше общего;
- **эффективный код** — компилятор строит дерево решений и не проверяет одно и то же свойство повторно.

**Ограничения и подвохи:**

- шаблоны сравнивают только с **константами**: `x is someVariable` не скомпилируется, для этого есть `when`: `case var n when n == limit`;
- полнота для enum не гарантирована — в enum можно положить любое число, поэтому для enum всегда нужна ветка `_`;
- property pattern вызывает геттеры — если геттер тяжёлый или с побочными эффектами, это заметно;
- positional pattern требует `Deconstruct` (у record и кортежей он есть);
- list pattern работает с типами, у которых есть индексатор и `Length`/`Count`; срез `..var rest` требует поддержки диапазонов.

**Где уместно:** разбор иерархий команд/событий, state machines, маппинг ошибок в HTTP-коды, валидация входных данных. Замена длинных цепочек `if/else if` на `switch`-выражение — частый вопрос на ревью; но замена полиморфизма на `switch` по типам — уже вопрос дизайна (OCP).

## Что такое nullable reference types?

```yaml
category: csharp
level: middle
difficulty: 2
slug: csharp-chto-takoe-nullable-reference-types
tags: value-types, sql
```

Nullable reference types (NRT, C# 8) — режим компилятора, в котором ссылочный тип без `?` считается «не может быть `null`», а `string?` — «может». Компилятор делает статический анализ потока и предупреждает о возможном разыменовании `null` и о присваивании `null` туда, где его не ждут. Это только аннотации и предупреждения: в runtime `string` и `string?` — один и тот же тип, никаких проверок не добавляется.

```csharp
#nullable enable
string name = null;          // CS8600/CS8625: null в non-nullable
string? maybe = GetName();
Console.WriteLine(maybe.Length);   // CS8602: возможное разыменование null

if (maybe is not null)
    Console.WriteLine(maybe.Length);   // ок: анализ потока знает, что тут не null
```

**Включение.** В новых шаблонах проектов `<Nullable>enable</Nullable>` в `.csproj` стоит по умолчанию. Для постепенной миграции есть директивы `#nullable enable|disable|restore` на уровне файла или участка кода. Чтобы предупреждения реально работали, их стоит сделать ошибками: `<WarningsAsErrors>nullable</WarningsAsErrors>`.

**Чем отличается от `Nullable<T>`:**

| | `int?` | `string?` |
| --- | --- | --- |
| Что это | другой тип — `Nullable<int>`, структура с `HasValue` | тот же `string` с аннотацией |
| Runtime | да, отдельное представление | нет, только метаданные `[Nullable]` |
| Проверка | `.Value` бросит исключение | никаких проверок, только предупреждения |

В generic-коде это различие всплывает: `T?` без ограничения означает «`default(T)` может быть», а для `where T : struct` — `Nullable<T>`.

**Инструменты для точного анализа:**

- **`!` (null-forgiving)** — «я знаю, что здесь не `null`», подавляет предупреждение. Злоупотребление им — главный способ сделать NRT бесполезным;
- **атрибуты** из `System.Diagnostics.CodeAnalysis`: `[NotNullWhen(true)]` для `TryGet`-паттерна, `[MaybeNull]`, `[NotNull]`, `[MemberNotNull]` для методов инициализации, `[AllowNull]`, `[DoesNotReturn]`;

```csharp
public bool TryFind(int id, [NotNullWhen(true)] out User? user) { ... }

if (TryFind(1, out var u)) Console.WriteLine(u.Name);   // без предупреждения
```

- **`required`-свойства** (C# 11) — решают проблему «non-nullable свойство DTO не инициализировано в конструкторе» (CS8618) без `= null!`.

**Где анализ не спасает:**

- данные извне — десериализация JSON, reflection, EF Core материализация — могут положить `null` в non-nullable свойство, компилятор этого не видит; проверять входные данные всё равно нужно (`ArgumentNullException.ThrowIfNull`);
- массивы: `new string[10]` содержит десять `null`, хотя тип `string[]`;
- `default` у структур с ссылочными полями;
- код без NRT (старые библиотеки) — его API «oblivious», предупреждений не будет.

**Связь с EF Core:** при включённом NRT EF Core выводит обязательность колонки из аннотации: `string Name` → `NOT NULL`, `string? Middle` → `NULL`. Включение NRT на существующем проекте может сгенерировать миграцию, меняющую nullability колонок, — это частый сюрприз.

## Чем отличаются `string` и `StringBuilder`?

```yaml
category: csharp
level: middle
difficulty: 3
slug: csharp-chem-otlichayutsya-string-i-stringbuilder
```

`string` неизменяем: каждая «модификация» (`+`, `Replace`, `Substring`) создаёт новую строку в куче. `StringBuilder` — изменяемый буфер символов: `Append` дописывает в уже выделенную память и расширяет её при нехватке, а итоговая строка создаётся один раз в `ToString()`. Поэтому для многократной сборки строки в цикле нужен `StringBuilder`, а для нескольких фиксированных частей — обычная конкатенация или интерполяция.

```csharp
// O(n²): на каждой итерации копируется вся накопленная строка
string s = "";
foreach (var item in items) s += item + ",";

// O(n): дописываем в буфер
var sb = new StringBuilder(capacity: items.Count * 8);
foreach (var item in items) sb.Append(item).Append(',');
string result = sb.ToString();
```

**Почему конкатенация в цикле квадратична.** Строка из 10 000 шагов по 10 символов: на каждом шаге копируется вся предыдущая строка — суммарно порядка 500 млн символов копирования и 10 000 мусорных объектов, крупные из которых попадают в LOH (от 85 000 байт, то есть примерно от 42 500 символов).

**Как устроен `StringBuilder`.** Внутри — связный список чанков (`char[]`). При переполнении он не копирует старые данные, а добавляет новый чанк (размер растёт, но ограничен ~8000 символов на чанк), поэтому `Append` амортизированно O(1). Цена — `Insert`, `Remove` и индексатор `sb[i]` в середине могут требовать обхода чанков. Указание `capacity` заранее уменьшает число чанков.

**Когда `StringBuilder` не нужен:**

- **фиксированное число частей** — `a + b + c` компилятор превращает в один `string.Concat(a, b, c)` с одной аллокацией;
- **интерполяция** — с C# 10 `$"{id}: {name}"` компилируется в `DefaultInterpolatedStringHandler`, который пишет в арендованный буфер без боксинга аргументов; это быстрее, чем `string.Format`, и обычно не хуже `StringBuilder`;
- **склейка коллекции** — `string.Join(",", items)` проще и быстрее ручного цикла;
- **строка известной длины** — `string.Create(length, state, (span, st) => ...)` пишет прямо в память итоговой строки, без промежуточного буфера.

**Ловушки:**

- `sb.Append(a + b)` — конкатенация внутри `Append` создаёт промежуточную строку; правильно `sb.Append(a).Append(b)`;
- `sb.Append($"{x}")` — с C# 10 есть перегрузка `Append(ref AppendInterpolatedStringHandler)`, интерполяция пишется прямо в builder; в старых версиях создавалась строка;
- `StringBuilder` не потокобезопасен;
- в горячем коде сами билдеры можно переиспользовать через пул (`ObjectPool<StringBuilder>` из `Microsoft.Extensions.ObjectPool`) — ASP.NET Core делает так внутри.

**Ориентир:** порог «когда становится выгодно» — несколько (грубо 5–10) операций в цикле; для 2–4 частей разница незаметна, а читаемость важнее. Если спорный случай в горячем пути — меряйте BenchmarkDotNet с `[MemoryDiagnoser]`.

## Почему `string` immutable?

```yaml
category: csharp
level: middle
difficulty: 3
slug: csharp-pochemu-string-immutable
tags: value-types
```

Потому что строка — ссылочный тип, который повсеместно используется как значение: ключ словаря, имя файла, SQL-параметр, токен. Неизменяемость даёт `string` семантику значения при ссылочной передаче: строку можно раздать куда угодно, и никто не изменит её «из-под» другого владельца. Из этого же следуют потокобезопасность, стабильный хеш-код, интернирование и безопасность проверок.

**Конкретные причины:**

- **безопасность** — проверили путь или права (`if (IsAllowed(path)) Open(path)`), и между проверкой и использованием никто не подменит содержимое (защита от TOCTOU внутри процесса);
- **ключи хеш-таблиц** — `GetHashCode` строки зависит от содержимого; изменяемая строка-ключ «потерялась» бы в `Dictionary`;
- **потокобезопасность** — чтение неизменяемого объекта из многих потоков не требует синхронизации;
- **интернирование и общий пул литералов** — все одинаковые литералы в процессе ссылаются на один объект (`string.Intern`, `string.IsInterned`); это возможно только если объект никто не может изменить;
- **дешёвое «копирование»** — присваивание и передача копируют ссылку, защитные копии не нужны.

```csharp
string a = "hello";
string b = a;
a += " world";            // создан новый объект, a указывает на него
Console.WriteLine(b);     // "hello" — b не изменился

object.ReferenceEquals("abc", "abc");   // true: литералы интернированы
```

**Как устроена строка в памяти.** Объект `string` — заголовок, длина (`int`) и символы UTF-16 одним блоком, плюс завершающий `\0` для interop. Размер фиксируется при создании, поэтому «дописать» в строку физически некуда — любая операция создаёт новый объект.

**Цена неизменяемости** — аллокации при каждой модификации. Её снижают:

- `StringBuilder` для пошаговой сборки;
- `string.Create` и `DefaultInterpolatedStringHandler` — запись сразу в итоговый буфер;
- `ReadOnlySpan<char>` / `AsSpan()` для разбора без `Substring`: `line.AsSpan(0, 5)` не выделяет память;
- `string.Concat`/`string.Join` с одной аллокацией на результат.

**Неизменяемость можно нарушить — и нельзя.** Через `unsafe`/`fixed`, `MemoryMarshal` или reflection можно записать в память строки. Это ломает интернированные литералы во всём процессе (изменив `"abc"`, вы измените его везде) и кэшированные хеши, поэтому считается undefined behavior. Единственное легитимное место — `string.Create`, где запись разрешена до того, как строка стала видна кому-либо.

**Связанные вопросы:** почему `string` — не value type (переменный размер, дешёвая передача большой строки по ссылке), чем `==` у строк отличается от `ReferenceEquals` (перегружен и сравнивает содержимое), почему для паролей раньше рекомендовали `SecureString` (строку нельзя затереть, и она живёт в памяти до GC; сейчас `SecureString` не рекомендован для новых разработок).

## Что такое `Span<T>` и `Memory<T>`?

```yaml
category: csharp
level: middle
difficulty: 2
slug: csharp-chto-takoe-span-t-i-memory-t
tags: span
```

`Span<T>` — «окно» на непрерывный участок памяти: массив, часть массива, строку, память на стеке (`stackalloc`) или неуправляемый буфер. Он позволяет читать и писать данные без копирования и без аллокаций. `Span<T>` — `ref struct`, поэтому живёт только на стеке. `Memory<T>` — то же окно, но обычная структура: её можно хранить в полях, передавать в `async`-методы и лямбды, а для работы с данными из неё получают `Span` через `.Span`.

```csharp
string line = "2026-09-29;ORDER;42";

// без Span: Split создаёт массив и три строки
// со Span: ноль аллокаций
ReadOnlySpan<char> s = line;
int i = s.IndexOf(';');
var date = DateOnly.Parse(s[..i]);
int id = int.Parse(s[(s.LastIndexOf(';') + 1)..]);

Span<byte> buffer = stackalloc byte[256];     // память на стеке, без GC
int written = Encoding.UTF8.GetBytes("hello", buffer);
```

**Как устроен `Span<T>`.** Это пара «управляемая ссылка на первый элемент (`ref T`) + длина». Ссылка может указывать внутрь объекта в куче, в стек или в неуправляемую память — поэтому один API работает со всеми источниками. Индексация проверяет границы и по скорости сопоставима с массивом.

**Почему `ref struct` и какие ограничения.** Внутренняя ссылка может указывать на стек текущего метода. Если бы `Span` попал в кучу, он пережил бы этот кадр стека и указывал бы на мусор. Поэтому `Span<T>` нельзя:

- хранить в полях классов и обычных структур (только в `ref struct`);
- боксить, приводить к `object` или интерфейсу;
- использовать через `await` и `yield` (C# 13 разрешил `ref struct`-локальные в async-методах и итераторах, но только на участках без `await`/`yield`);
- захватывать в лямбду.

**`Memory<T>` снимает эти ограничения** ценой небольшого оверхеда: хранит ссылку на объект-владелец (массив, строку или `MemoryManager<T>`), смещение и длину. Не может указывать на стек.

```csharp
async Task<int> ReadAsync(Stream stream, Memory<byte> buffer)
{
    int n = await stream.ReadAsync(buffer);    // Span сюда нельзя, Memory — можно
    return Checksum(buffer.Span[..n]);         // в синхронном коде берём Span
}
```

| | `Span<T>` / `ReadOnlySpan<T>` | `Memory<T>` / `ReadOnlyMemory<T>` |
| --- | --- | --- |
| Вид | `ref struct` | `struct` |
| Где живёт | только стек | где угодно |
| `stackalloc`, неуправляемая память | да | нет (кроме своего `MemoryManager`) |
| `async`, поля, лямбды | нет | да |
| Скорость доступа | максимальная | через `.Span`, чуть дороже |

**Правило выбора:** синхронные методы принимают `Span<T>`/`ReadOnlySpan<T>`, асинхронные и хранящие буфер — `Memory<T>`. Параметры, которые только читаются, — `ReadOnly`-варианты: в них неявно конвертируются и `string`, и массивы.

**Где это в BCL и практике:** перегрузки `int.Parse(ReadOnlySpan<char>)`, `Stream.ReadAsync(Memory<byte>)`, `Utf8JsonReader`, `System.IO.Pipelines`, `string.Create`, `MemoryExtensions` (`Split` в .NET 9 для `ReadOnlySpan<char>` без аллокаций). Большие буферы берут из `ArrayPool<T>.Shared` и работают с ними через `Span`.

**Подводные камни:** `stackalloc` большого размера — риск `StackOverflowException` (ориентир — до ~1 КБ, иначе пул); `Memory<T>` поверх арендованного массива после `Return` в пул указывает на чужие данные — для владения есть `IMemoryOwner<T>`; `span.ToArray()` и `ToString()` снова аллоцируют.

## Что такое `IAsyncEnumerable<T>`?

```yaml
category: csharp
level: middle
difficulty: 2
slug: csharp-chto-takoe-iasyncenumerable-t
tags: async
```

`IAsyncEnumerable<T>` (C# 8, .NET Core 3.0) — асинхронная последовательность: элементы приходят по одному, и ожидание следующего элемента не блокирует поток. Это `IEnumerable<T>`, у которого `MoveNext` стал `MoveNextAsync()` и возвращает `ValueTask<bool>`. Потребляется через `await foreach`, создаётся async-итератором — методом с `async` и `yield return`.

```csharp
public async IAsyncEnumerable<Order> ReadOrdersAsync(
    [EnumeratorCancellation] CancellationToken ct = default)
{
    int page = 0;
    while (true)
    {
        var batch = await _api.GetPageAsync(page++, ct);
        if (batch.Count == 0) yield break;
        foreach (var o in batch) yield return o;
    }
}

await foreach (var order in ReadOrdersAsync().WithCancellation(ct))
    Process(order);
```

**Зачем, если есть `Task<List<T>>`.** `Task<List<T>>` ждёт, пока загрузится всё, и держит весь результат в памяти. `IAsyncEnumerable<T>` отдаёт элементы по мере поступления: первый обрабатывается, пока следующие ещё читаются из сети или базы, память — O(1) от размера результата. А `IEnumerable<Task<T>>` не подходит, потому что заранее неизвестно, сколько будет элементов — само «есть ли следующий» требует ожидания.

**Как устроено.** Компилятор генерирует класс, который одновременно является state machine async-метода и итератора, реализует `IAsyncEnumerator<T>` и `IAsyncDisposable`. `await foreach` разворачивается в `try/finally` с `await DisposeAsync()` — поэтому `finally` и `using` внутри итератора выполнятся, даже если потребитель вышел из цикла через `break`.

**Отмена — главный подводный камень.** Токен можно передать двумя способами: параметром метода и через `.WithCancellation(ct)`. Чтобы второй способ работал, параметр должен быть помечен `[EnumeratorCancellation]` — тогда компилятор объединит оба токена. Без атрибута `WithCancellation` тихо ничего не отменит (есть предупреждение CS8425).

**Где встречается:**

- **EF Core** — `query.AsAsyncEnumerable()` стримит строки из `DbDataReader` без буферизации всего результата;
- **ASP.NET Core** — контроллер или minimal API может вернуть `IAsyncEnumerable<T>`, `System.Text.Json` сериализует элементы в ответ по мере получения, не собирая список;
- **gRPC server streaming**, `ChannelReader<T>.ReadAllAsync()`, SignalR-стримы, пагинация внешних API;
- **LINQ** — с .NET 10 операторы `Where`, `Select` и др. для `IAsyncEnumerable<T>` есть в самой BCL (`System.Linq.AsyncEnumerable`), раньше для этого подключали пакет `System.Linq.Async`.

**Ловушки:**

- последовательность ленивая, как обычный итератор: ничего не выполняется до `await foreach`, и повторное перечисление запускает работу заново;
- `ConfigureAwait(false)` для `await foreach` пишется как `.ConfigureAwait(false)` на самой последовательности;
- долгий `await foreach` по EF Core держит открытым соединение и reader — внутри нельзя запускать другие запросы на том же `DbContext`;
- для параллельной обработки элементов подходит `Parallel.ForEachAsync`, который принимает `IAsyncEnumerable<T>`.

## Почему reflection дорог и какие способы его ускорить существуют?

```yaml
category: csharp
level: senior
difficulty: 4
slug: advanced-csharp-pochemu-reflection-dorog-i-kakie-sposoby-ego-uskorit-suschestvuyut
tags: reflection, performance
```

Reflection дорог по двум причинам: **поиск** членов идёт по метаданным и строкам в runtime, а **вызов** через `MethodInfo.Invoke` проходит универсальный путь — массив `object[]` аргументов, боксинг value types, проверки типов и числа параметров, обёртка исключений в `TargetInvocationException`, и никакого инлайнинга. Ускоряют его, превращая «динамический» вызов в обычный: кэшированием метаданных, созданием типизированного делегата, генерацией IL или переносом работы на этап компиляции (source generators, `UnsafeAccessor`).

**Из чего складывается цена:**

- **`GetMethod("Name")`, `GetProperties()`** — поиск по строке в метаданных, фильтрация по `BindingFlags`, создание объектов `MethodInfo`/`PropertyInfo`, аллокация массивов на каждый вызов `GetProperties()`. У runtime есть внутренний кэш, но сам вызов всё равно не бесплатен;
- **`Invoke`** — аргументы упаковываются в `object[]`, каждый value type боксится, результат тоже возвращается как `object`; runtime проверяет типы аргументов и приводит их;
- **нет оптимизаций JIT** — вызов через reflection непрозрачен: ни инлайнинга, ни девиртуализации, ни устранения проверок;
- **`Activator.CreateInstance(type)`** и `GetCustomAttributes()` — последний каждый раз создаёт новые экземпляры атрибутов.

**Что изменилось в новых .NET.** В .NET 7 `MethodInfo.Invoke` после первых вызовов переключается на сгенерированный IL-стаб вместо интерпретации, и стал в разы быстрее. В .NET 8 появились `MethodInvoker` и `ConstructorInvoker` — однократно созданный «вызыватель» с перегрузками без массива аргументов:

```csharp
var mi = typeof(Calc).GetMethod(nameof(Calc.Add))!;
MethodInvoker invoker = MethodInvoker.Create(mi);   // создать один раз и кэшировать
object? r = invoker.Invoke(calc, 2, 3);             // без object[], но боксинг остаётся
```

**Способы ускорения — от простого к радикальному:**

**1. Кэшировать метаданные.** `PropertyInfo[]` для типа достаточно получить один раз — в `ConcurrentDictionary<Type, ...>` или в generic static-классе, который JIT-ит отдельную копию на каждый `T` и не требует поиска по словарю:

```csharp
static class PropsCache<T> { public static readonly PropertyInfo[] Props = typeof(T).GetProperties(); }
```

**2. Типизированный делегат.** `CreateDelegate` связывает `MethodInfo` с делегатом один раз, дальше вызов стоит как обычный вызов делегата — без боксинга и проверок:

```csharp
var getter = prop.GetMethod!.CreateDelegate<Func<User, string>>();
string name = getter(user);
```

Ограничение — нужно знать типы на этапе компиляции. Если не знаете, помогают generic-«мостики» или деревья выражений.

**3. Скомпилированные expression trees** — строят лямбду вида `(object o) => (object)((User)o).Name`, компилируют в делегат `Func<object, object>`. Работает для неизвестных типов, но компиляция стоит сотни микросекунд, её обязательно кэшируют.

**4. `DynamicMethod` + `ILGenerator`** — ручная генерация IL: максимальная гибкость и скорость, так делали Dapper и старые сериализаторы. Сложно писать и отлаживать.

**5. `[UnsafeAccessor]` (.NET 8)** — доступ к приватным полям, методам и конструкторам без reflection вообще: JIT генерирует прямой доступ, цена как у обычного вызова, совместимо с Native AOT.

```csharp
[UnsafeAccessor(UnsafeAccessorKind.Field, Name = "_items")]
static extern ref int[] Items(MyList list);
```

**6. Source generators** — перенести всю работу на этап компиляции: `System.Text.Json` source generation, `[LoggerMessage]`, `[GeneratedRegex]`, Mapperly вместо AutoMapper. Reflection в runtime не остаётся совсем.

**Native AOT и trimming.** Reflection по строкам несовместим с trimming: линкер не видит, что `GetMethod("Foo")` использует `Foo`, и может его вырезать. Нужны атрибуты `[DynamicallyAccessedMembers]`, а `Reflection.Emit` и компиляция expression trees в AOT недоступны (деревья выражений там только интерпретируются). Это ещё один аргумент за source generators.

**На собеседовании** обычно ждут: сравнения порядков (прямой вызов — единицы наносекунд, `CreateDelegate` — близко к нему, `Invoke` — на порядок и более медленнее, `GetMethod` без кэша — ещё хуже; точные цифры зависят от версии .NET — меряйте BenchmarkDotNet), понимания, что главное — не вызывать поиск метаданных в горячем пути, и знания, как это решают реальные библиотеки.

## Как source generators решают проблемы reflection и какие ограничения у них есть?

```yaml
category: csharp
level: senior
difficulty: 4
slug: advanced-csharp-kak-source-generators-reshayut-problemy-reflection-i-kakie-ogranicheni
tags: source-generators, performance
```

Source generator — плагин компилятора Roslyn, который во время сборки анализирует код проекта (синтаксис и семантическую модель) и добавляет в компиляцию новые C#-файлы. Всё, что reflection выяснял в runtime — какие у типа свойства, какие атрибуты, какие методы, — генератор выясняет при компиляции и выписывает обычный код. В итоге в runtime нет поиска метаданных, боксинга и `Invoke`, код совместим с trimming и Native AOT, ошибки видны при сборке. Главное ограничение — генератор может только **добавлять** код и видит только то, что известно при компиляции.

**Пример — `System.Text.Json`:**

```csharp
[JsonSerializable(typeof(Order))]
internal partial class AppJsonContext : JsonSerializerContext { }

var json = JsonSerializer.Serialize(order, AppJsonContext.Default.Order);
```

Генератор создаёт для `Order` метаданные и код записи свойств напрямую (`writer.WriteNumber("id", value.Id)`), без reflection при старте и без генерации IL в runtime.

**Какие проблемы reflection это снимает:**

| Проблема reflection | Решение генератором |
| --- | --- |
| медленный первый вызов, «прогрев» кэшей | код уже скомпилирован, быстрый старт (важно для serverless и AOT) |
| боксинг и `object[]` в `Invoke` | прямые типизированные вызовы, JIT может инлайнить |
| trimming вырезает члены, используемые по строке | линкер видит обычные ссылки в коде |
| `Reflection.Emit` недоступен в Native AOT | эмитить нечего, всё сгенерировано заранее |
| ошибки конфигурации — в runtime | диагностики (`Diagnostic`) и ошибки компиляции |
| «магия», которую сложно отладить | сгенерированный код можно открыть и пройти отладчиком |

**Где уже используется в .NET:** `[GeneratedRegex]` (регулярка компилируется в C#), `[LoggerMessage]` (логирование без боксинга и парсинга шаблона), `[LibraryImport]` (P/Invoke маршалинг), `System.Text.Json`, биндер конфигурации и Request Delegate Generator для minimal API в AOT-сценариях; из сторонних — Mapperly, Refit, MediatR-альтернативы, StronglyTypedId.

**Как пишется.** Современный API — `IIncrementalGenerator`: генератор описывает конвейер (`ForAttributeWithMetadataName` → трансформация в модель → `RegisterSourceOutput`), а Roslyn кэширует промежуточные результаты и перезапускает только изменившиеся шаги. Старый `ISourceGenerator` устарел: он выполнялся на каждое нажатие клавиши в IDE и тормозил редактор.

**Ограничения:**

- **только добавление кода.** Изменить или удалить существующий код нельзя, поэтому пользовательские типы и методы должны быть `partial`, а генератор дописывает вторую половину (с C# 13 можно `partial`-свойства и индексаторы). Подменить вызов в существующем коде позволяют только interceptors — отдельная, более узкая фича;
- **только compile-time знание.** Типы из плагинов, загружаемых в runtime, `object`-полиморфизм, данные из БД генератор не видит. Для STJ полиморфизм надо объявлять явно (`[JsonDerivedType]`), а generic-типы — перечислять в `[JsonSerializable]`;
- **генераторы не видят вывод друг друга** — все запускаются над исходной компиляцией, цепочки невозможны;
- **сборка генератора** таргетирует `netstandard2.0` и подключается как analyzer (`OutputItemType="Analyzer"`); зависимости генератора нужно упаковывать особым образом;
- **производительность IDE.** Плохо написанный генератор (модели без value-equality, хранение `ISymbol`/`SyntaxNode` в конвейере) ломает кэширование и тормозит каждый пересчёт;
- **отладка и тестирование** сложнее: `Debugger.Launch()` или тесты через `CSharpGeneratorDriver` и snapshot-тестирование (Verify);
- **не всегда быстрее reflection с кэшем.** Для редких вызовов выигрыш — в старте и совместимости с AOT, а не в пропускной способности; зато растёт размер сборки.

**Что спрашивают дальше:** чем генератор отличается от анализатора (анализатор только сообщает, генератор добавляет код), от T4-шаблонов (T4 не видит семантическую модель и запускается отдельно), от IL weaving вроде Fody (тот переписывает готовый IL и может менять существующий код), как посмотреть сгенерированное (`<EmitCompilerGeneratedFiles>true</EmitCompilerGeneratedFiles>`).

## Когда expression trees предпочтительнее скомпилированных делегатов и наоборот?

```yaml
category: csharp
level: senior
difficulty: 4
slug: advanced-csharp-kogda-expression-trees-predpochtitelnee-skompilirovannyh-delegatov-i-n
tags: expression-trees, performance
```

Делегат — это исполняемый код: его можно только вызвать. Expression tree — это код в виде данных: дерево объектов `Expression`, которое можно разобрать, преобразовать, транслировать в другой язык или скомпилировать в делегат в runtime. Деревья выражений выбирают, когда нужно **анализировать** код (ORM, построение запросов, получение имени члена) или **сгенерировать** код в runtime для типов, неизвестных при компиляции. Во всех остальных случаях — когда код просто надо выполнить — нужен обычный делегат.

```csharp
Func<User, bool>             f = u => u.Age > 18;   // IL-метод + делегат
Expression<Func<User, bool>> e = u => u.Age > 18;   // Lambda(GreaterThan(Property(u, Age), Constant(18)))

users.Where(f);      // IEnumerable: фильтрация в памяти
db.Users.Where(e);   // IQueryable: EF Core читает дерево и строит WHERE "Age" > 18
```

**Когда нужны деревья выражений:**

- **трансляция в другой язык** — EF Core, LINQ-провайдеры для MongoDB, OData: провайдер обходит дерево (`ExpressionVisitor`) и строит SQL. Делегат для этого бесполезен — из IL нельзя надёжно восстановить намерение;
- **динамическое построение запросов** — фильтры из UI, комбинирование предикатов (`And`/`Or` через `Expression.AndAlso` с заменой параметров), `PredicateBuilder`;
- **метаданные вместо строк** — `x => x.Name` в FluentValidation, `HasKey(x => x.Id)` в EF Core, `nameof`-подобные API до `CallerArgumentExpression`;
- **генерация быстрых аксессоров** — построить `(object o) => (object)((T)o).Prop` для неизвестного при компиляции `T` и один раз скомпилировать. Это один из способов ускорить reflection.

**Цена `Expression.Compile()`.** Компиляция дерева — это генерация `DynamicMethod` и его JIT: десятки–сотни микросекунд и аллокации, на порядки дороже самого вызова. Поэтому скомпилированный делегат **обязательно кэшируют**. Типичная ошибка:

```csharp
// каждый вызов компилирует заново — катастрофа в горячем пути
public object Get(object o) => BuildGetter(o.GetType()).Compile()(o);

// правильно: компиляция один раз на тип
static readonly ConcurrentDictionary<Type, Func<object, object?>> Cache = new();
public object? Get(object o) => Cache.GetOrAdd(o.GetType(), t => BuildGetter(t).Compile())(o);
```

После компиляции вызов стоит примерно как вызов обычного делегата — с поправкой на то, что делегат, полученный через `Compile()`, вызывается через closure-объект и иногда чуть медленнее делегата на статический метод.

**Когда предпочтительнее обычный делегат:**

- код известен при компиляции — лямбда, method group, `CreateDelegate`: нулевая цена построения, полная оптимизация JIT (включая инлайнинг в вызывающий метод через PGO-девиртуализацию);
- LINQ to Objects — `IEnumerable.Where` принимает `Func`, передавать туда `Expression` и компилировать бессмысленно;
- код с `ref`/`out`, `async`/`await`, statement-блоками, присваиванием, `?.`, интерполяцией — компилятор C# не умеет превращать такие лямбды в дерево (API `System.Linq.Expressions` умеет больше, но строить руками тяжело);
- **Native AOT** — там нет JIT, `Compile()` переключается на интерпретатор деревьев и становится очень медленным. Для AOT альтернатива — source generators;
- для одноразовой операции — построение дерева дороже, чем reflection-вызов.

**Промежуточные варианты.** `Compile(preferInterpretation: true)` использует интерпретатор: дешёвое построение, медленное выполнение — подходит для редко вызываемых выражений. `LambdaExpression.CompileToMethod` в .NET Core отсутствует. Если выражение нужно и анализировать, и выполнять — храните `Expression` и лениво закэшированный `Func`.

**Подводный камень EF Core:** если метод принимает `Func<T, bool>` вместо `Expression<Func<T, bool>>`, вызов `db.Users.Where(predicate)` выберет `Enumerable.Where` — вся таблица загрузится в память и отфильтруется там. Компилятор не предупредит.

**Что спрашивают дальше:** как объединить два `Expression<Func<T,bool>>` (нужен `ExpressionVisitor`, заменяющий параметр), почему захваченная переменная в дереве становится `MemberExpression` к полю closure-класса (и поэтому EF Core параметризует её в SQL, а константу — нет), чем `Expression.Compile` отличается от `DynamicMethod`.

## Как устроен вызов делегата и почему многоадресный делегат дороже одиночного?

```yaml
category: csharp
level: senior
difficulty: 4
slug: advanced-csharp-kak-ustroen-vyzov-delegata-i-pochemu-mnogoadresnyi-delegat-dorozhe-odi
tags: delegates, performance
```

Одиночный делегат — объект с двумя главными полями: `_target` (объект, на котором вызывать метод) и `_methodPtr` (адрес кода). Вызов `d(x)` JIT превращает в несколько инструкций: загрузить `_target`, подставить его как `this` и сделать косвенный `call` по `_methodPtr` — это чуть дороже виртуального вызова. Многоадресный делегат вместо одной цели хранит массив делегатов, и его `_methodPtr` указывает на заглушку, которая перебирает этот массив в цикле. Отсюда цена: цикл, отдельный косвенный вызов на каждого подписчика, аллокации при `+=`/`-=` и невозможность оптимизаций вроде девиртуализации.

**Устройство объекта.** Каждый делегатный тип — `sealed`-наследник `MulticastDelegate`. В CoreCLR у экземпляра есть поля:

| Поле | Назначение |
| --- | --- |
| `_target` | `this` для экземплярного метода |
| `_methodPtr` | точка входа, которую вызывает `Invoke` |
| `_methodPtrAux` | реальный метод для статических делегатов (через thunk) |
| `_invocationList` | `object[]` делегатов у многоадресного; у одиночного обычно `null` |
| `_invocationCount` | число элементов в списке |

Метод `Invoke` не имеет IL-тела — его реализует runtime, и JIT генерирует вызов напрямую, без обращения к reflection.

**Нюанс: статический метод дороже экземплярного.** Вызов делегата устроен под соглашение «первый аргумент — `this`». Для статического метода `this` лишний, поэтому `_methodPtr` указывает на shuffle thunk — заглушку, сдвигающую аргументы, — а настоящий адрес хранится в `_methodPtrAux`. Именно поэтому компилятор C# превращает лямбду без захвата не в статический метод, а в экземплярный метод синглтона `<>c.<>9`: вызов такого делегата быстрее.

```csharp
Func<int, int> sq = x => x * x;   // компилируется в <>c.<>9.<Main>b__0_0 — экземплярный метод
```

**Как вызывается многоадресный делегат.** При `a += b` вызывается `Delegate.Combine`: делегаты неизменяемы, поэтому создаётся новый объект, у которого `_invocationList` содержит всех подписчиков, а `_methodPtr` указывает на multicast-заглушку. При вызове заглушка идёт по массиву и вызывает каждый элемент как обычный одиночный делегат:

```csharp
// логически эквивалентно
foreach (Delegate d in invocationList)
    result = ((Func<int>)d)();        // возвращается только результат последнего
```

**Почему это дороже одиночного:**

- **N косвенных вызовов + цикл** вместо одного вызова — очевидно;
- **нет девиртуализации.** В .NET 8+ динамическая PGO умеет для «горячего» одиночного делегата вставить проверку `if (d._methodPtr == ожидаемый) прямой вызов` и даже заинлайнить цель. Через multicast-заглушку это невозможно;
- **аллокации при подписке и отписке.** `+=` создаёт новый объект делегата и, как правило, новый массив; `-=` ищет совпадение с конца списка (O(n)) и снова создаёт новый делегат. Частая подписка/отписка в горячем коде нагружает GC;
- **`GetInvocationList()`** каждый раз аллоцирует копию массива. Его используют, когда нужно вызывать обработчики по отдельности — чтобы собрать все результаты, изолировать исключения или вызвать их асинхронно;
- **хуже локальность** — делегаты-подписчики и их `_target` разбросаны по куче.

**Семантические последствия, о которых спрашивают:**

- у `Func<T>` с несколькими подписчиками результаты всех, кроме последнего, теряются;
- исключение в одном обработчике прерывает вызов оставшихся;
- порядок вызова — порядок подписки, но полагаться на него в событиях — плохая идея;
- `-=` для лямбды, которая не сохранена в переменную, ничего не удаляет: новая лямбда — другой делегат (равенство делегатов — по `_target` и методу, а для многоадресных — по всему списку).

**Практические выводы:**

- для горячего пути с одним обработчиком одиночный делегат, закэшированный в поле, почти бесплатен; ещё быстрее — generic-параметр со struct-реализацией интерфейса (`where TOp : struct, IOperation`) или указатель на функцию `delegate*<int, int>` (C# 9, `unsafe`) — без объекта делегата вообще;
- если подписчиков много и они часто меняются — хранить `List<Action>` или `ImmutableArray<Action>` и перебирать вручную: контроль над исключениями и аллокациями;
- кэшировать делегаты для method group: с C# 11 компилятор делает это сам для статических методов, для экземплярных — каждое `obj.Method` в месте использования создаёт новый объект.
