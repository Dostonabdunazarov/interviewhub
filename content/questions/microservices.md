## Что такое микросервисная архитектура?

```yaml
category: microservices
level: middle
difficulty: 2
slug: microservices-chto-takoe-mikroservisnaya-arhitektura
tags: microservices
```

Микросервисная архитектура — это способ построить систему как набор небольших, независимо развёртываемых сервисов, каждый из которых отвечает за одну бизнес-возможность, владеет своими данными и общается с остальными только по сети через явные контракты (HTTP/gRPC API, сообщения).

**Ключевые признаки** (именно они отличают микросервисы от «монолита, порезанного на проекты»):

- **Независимый деплой.** Сервис можно выпустить, не пересобирая и не выкатывая соседей. Если для релиза нужно синхронно обновить пять сервисов — это распределённый монолит.
- **Своя база данных.** Другие сервисы не лезут в чужие таблицы, а получают данные через API или события.
- **Граница по бизнесу, а не по техническому слою.** Сервис `Orders`, а не `DataAccessService`.
- **Автономная команда.** Одна команда владеет сервисом целиком: код, деплой, мониторинг, дежурства (закон Конвея работает в обе стороны).
- **Технологическая свобода** — возможна, но на практике её ограничивают, чтобы не плодить зоопарк.

**Что это даёт:**

- независимое масштабирование горячих частей (например, только каталог в распродажу);
- изоляцию отказов — падение рекомендаций не должно ронять оформление заказа;
- параллельную работу многих команд без очереди на общий релиз.

**Чем за это платят:**

- сетевые вызовы вместо вызовов методов: задержки, таймауты, частичные отказы;
- нет общей ACID-транзакции — нужны Saga, Outbox, eventual consistency;
- обязательная инфраструктура: CI/CD на каждый сервис, service discovery, централизованные логи, трассировка, метрики;
- сложнее отладка и локальный запуск.

**Типичный стек в .NET:** ASP.NET Core minimal API или gRPC, брокер (RabbitMQ/Kafka) через MassTransit, OpenTelemetry для трассировки, контейнеры в Kubernetes, иногда .NET Aspire для локальной оркестрации.

На собеседовании обычно следом спрашивают «когда микросервисы не нужны» — правильный ответ показывает, что вы понимаете: это решение организационной проблемы масштабирования команд, а не способ «сделать код чище».

## Монолит vs микросервисы?

```yaml
category: microservices
level: middle
difficulty: 3
slug: microservices-monolit-vs-mikroservisy
tags: microservices
```

Монолит — одно развёртываемое приложение с общей кодовой базой и обычно общей БД; микросервисы — много независимо развёртываемых сервисов со своими данными. Ни один подход не лучше в общем случае: монолит проще и дешевле, микросервисы окупаются, когда много команд и частей системы с разными требованиями к масштабу и релизам.

| | Монолит | Микросервисы |
| --- | --- | --- |
| Деплой | один артефакт, всё выкатывается вместе | каждый сервис отдельно |
| Вызовы между модулями | in-process, наносекунды | сеть, миллисекунды, могут упасть |
| Транзакции | обычная ACID-транзакция БД | Saga, Outbox, eventual consistency |
| Масштабирование | всё приложение целиком | каждый сервис по своей нагрузке |
| Изоляция отказов | утечка памяти в одном модуле роняет всё | отказ локализуется (если есть timeout/circuit breaker) |
| Рефакторинг границ | переименовал класс — IDE всё поправила | меняются контракты, нужна версионность |
| Отладка | один процесс, один стек вызовов | distributed tracing, корреляция логов |
| Инфраструктура | минимальная | CI/CD × N, discovery, мониторинг, брокер |
| Командная работа | конфликты при росте до десятков разработчиков | команды автономны |

**Промежуточный вариант — модульный монолит.** Один деплой, но код разбит на модули с жёсткими границами: у каждого свои сущности и схема БД, общение через публичные интерфейсы или in-process события, запрет прямых ссылок проверяется архитектурными тестами (например, NetArchTest). Это даёт большую часть пользы от правильных границ без сетевой сложности, а модуль потом можно выделить в сервис.

**Частая ошибка — распределённый монолит:** сервисы есть, но они делят базу, выкатываются только вместе и синхронно вызывают друг друга цепочками. Получаются недостатки обоих миров.

**Как аргументировать выбор на интервью:**

- размер и число команд (одна команда из 6 человек — почти всегда монолит);
- разные профили нагрузки или требований к доступности у частей системы;
- зрелость DevOps: без автоматического деплоя и наблюдаемости микросервисы превращаются в боль;
- стабильность домена: пока границы не понятны, их дешевле двигать внутри монолита.

## Когда микросервисы не нужны?

```yaml
category: microservices
level: middle
difficulty: 3
slug: microservices-kogda-mikroservisy-ne-nuzhny
tags: microservices
```

Микросервисы не нужны, когда у вас нет проблемы, которую они решают: одна-две команды, неустоявшийся домен, умеренная нагрузка, нет зрелой инфраструктуры для деплоя и наблюдаемости. В этих случаях модульный монолит быстрее в разработке, дешевле в эксплуатации и проще в отладке.

**Конкретные признаки, что рано:**

- **Маленькая команда.** Если 5–8 человек поддерживают 15 сервисов, большая часть времени уходит на инфраструктуру, а не на фичи. Микросервисы в первую очередь масштабируют *организацию*.
- **Стартап / MVP.** Домен ещё меняется каждые пару месяцев. Неверно проведённую границу внутри монолита поправить — рефакторинг на день, между сервисами — миграция данных и контрактов на месяцы.
- **Нет CI/CD, контейнеров, централизованных логов и трассировки.** Без этого инциденты расследуются по SSH на десять машин.
- **Сильно связанные данные.** Если почти каждая операция требует консистентного изменения данных нескольких «сервисов», вы получите Saga на каждый чих или распределённые транзакции.
- **Жёсткие требования к latency.** Цепочка из 5 сетевых вызовов по 5–10 мс заметна, внутрипроцессный вызов — нет.
- **Нагрузка равномерная.** Если всё приложение масштабируется одинаково, отдельное масштабирование частей ничего не даёт — достаточно нескольких реплик монолита за балансировщиком.

**Скрытые издержки, которые недооценивают:**

- eventual consistency, которую нужно объяснять бизнесу и обрабатывать в UI;
- версионирование контрактов и обратная совместимость;
- интеграционное тестирование и локальный запуск всей системы;
- стоимость облака: у каждого сервиса свои реплики, БД, запас по ресурсам.

**Что делать вместо этого.** Модульный монолит с чёткими границами модулей и отдельными схемами БД. Когда появится реальная причина — отдельная команда, модуль с особой нагрузкой, другой цикл релизов, требования к изоляции (например, PCI DSS для платежей), — модуль выделяется в сервис с помощью Strangler Fig.

Хороший ответ на интервью: «Начал бы с модульного монолита и выделял сервисы по конкретным драйверам, а не заранее».

## Как определить границы микросервисов?

```yaml
category: microservices
level: middle
difficulty: 3
slug: microservices-kak-opredelit-granicy-mikroservisov
tags: microservices
```

Границы сервисов проводят по бизнес-возможностям и bounded context'ам из DDD, а не по техническим слоям или таблицам. Хорошая граница — та, при которой типичное изменение требований затрагивает один сервис, а сервис может выполнить свою основную работу, не делая синхронных вызовов к соседям.

**Инструменты поиска границ:**

- **Event Storming.** С бизнесом выписывают доменные события («Заказ оформлен», «Оплата получена», «Товар отгружен»), команды и агрегаты. Кластеры событий с общим языком — кандидаты в контексты.
- **Ubiquitous language.** Где одно слово начинает значить разное («Клиент» у продаж и у доставки), там граница.
- **Бизнес-возможности.** Каталог, корзина, заказы, платежи, доставка — то, что организация «умеет делать».
- **Структура команд.** Сервис должен принадлежать одной команде; если два сервиса постоянно меняют вместе — границу провели неверно.

**Критерии хорошей границы:**

- **высокая связность внутри** — данные и правила, меняющиеся вместе, лежат вместе;
- **слабая связанность снаружи** — мало вызовов через границу, контракты стабильны;
- **владение данными** — у каждой сущности один источник истины, остальные держат копии или ссылки по ID;
- **транзакционная граница** — инварианты, которые надо проверять атомарно, должны быть внутри одного сервиса.

**Анти-признаки неверной границы:**

- фича требует синхронного релиза нескольких сервисов;
- «болтливое» (chatty) взаимодействие: на один запрос — десятки вызовов соседа;
- сервисы читают таблицы друг друга;
- CRUD-сервисы на сущность (`CustomerService`, `ProductService`) без поведения, а логика размазана по «оркестраторам»;
- нужна распределённая транзакция для обычного сценария.

**Практический совет:** начинайте с крупных сервисов. Разрезать крупный сервис позже проще, чем склеивать мелкие, которые успели обрасти своими БД и контрактами.

## Что такое bounded context?

```yaml
category: microservices
level: middle
difficulty: 2
slug: microservices-chto-takoe-bounded-context
tags: microservices
```

Bounded context (ограниченный контекст) — понятие из DDD: явная граница, внутри которой доменная модель и термины имеют одно точное значение. За границей то же слово может означать другое, и это нормально — у каждого контекста своя модель.

**Пример.** «Товар» в разных контекстах интернет-магазина:

| Контекст | Что важно о товаре |
| --- | --- |
| Каталог | название, описание, фото, характеристики |
| Склад | SKU, остатки, ячейка хранения, вес |
| Ценообразование | цена, скидки, акции |
| Доставка | габариты, хрупкость |

Попытка сделать одну «универсальную» сущность `Product` со всеми полями приводит к классу, который все боятся трогать, и к связанности всех команд через него.

**Связь с микросервисами.** Bounded context — естественный кандидат на границу сервиса (или группы сервисов). Один сервис не должен охватывать несколько контекстов, иначе модели смешиваются. Обратное допустимо: один контекст может быть реализован парой сервисов.

**Как контексты общаются** — описывается context map:

- **Shared ID** — общим обычно остаётся только идентификатор (`ProductId`);
- **Anti-Corruption Layer** — слой-переводчик, который защищает вашу модель от чужой (например, от модели legacy-системы);
- **Published Language** — стабильный публичный контракт или событие, отдельный от внутренней модели;
- **Customer/Supplier, Conformist** — отношения между командами: кто под кого подстраивается.

**Что важно понимать:** контекст — это граница *модели и языка*, а не просто папка в проекте. Внутри контекста термины однозначны, код говорит языком бизнеса, а внутренние классы не утекают наружу через API.

## Как микросервисы взаимодействуют между собой?

```yaml
category: microservices
level: middle
difficulty: 3
slug: microservices-kak-mikroservisy-vzaimodeistvuyut-mezhdu-soboi
tags: microservices
```

Сервисы взаимодействуют двумя способами: **синхронно** — запрос-ответ по сети (REST/HTTP, gRPC), и **асинхронно** — через брокер сообщений (RabbitMQ, Kafka, Azure Service Bus), где отправитель не ждёт получателя. Обычно в системе есть оба, и выбор делается под конкретный сценарий.

**Синхронное взаимодействие:**

- **REST/JSON** — универсально, удобно для внешних API и отладки;
- **gRPC** — бинарный Protobuf поверх HTTP/2, строгий контракт, стриминг; хорош для внутренних вызовов с высокой частотой;
- **GraphQL** — чаще на границе с фронтом (BFF), а не между сервисами.

Нужны: service discovery, таймауты, retry, circuit breaker. Минус — временная связанность: если вызываемый сервис лежит, вызывающий тоже не может ответить.

**Асинхронное взаимодействие:**

- **команды** (`ReserveStock`) — адресованы конкретному получателю, обычно через очередь;
- **события** (`OrderPlaced`) — факт, который произошёл; издатель не знает подписчиков (pub/sub);
- **асинхронный request/reply** — запрос в очередь, ответ в reply-очередь по correlation ID.

Плюсы — развязка по времени, буферизация пиков, естественная расширяемость (новый подписчик без изменения издателя). Минусы — eventual consistency, дубликаты и порядок сообщений, сложнее трассировка.

**Как выбирать:**

| Сценарий | Способ |
| --- | --- |
| Нужен ответ прямо сейчас для пользователя (получить цену, проверить права) | синхронно |
| Уведомить других о факте (заказ создан) | событие |
| Длительный процесс, несколько участников | асинхронно + Saga |
| Сгладить пиковую нагрузку | очередь |

**Способы уменьшить синхронные вызовы:** держать локальную копию нужных чужих данных, обновляемую событиями (например, сервис заказов хранит имена и цены товаров на момент заказа).

**Инфраструктура в .NET:** `HttpClient` через `IHttpClientFactory` с resilience-хендлерами, `Grpc.Net.Client`, MassTransit или NServiceBus поверх брокера, OpenTelemetry для сквозной трассировки обоих типов вызовов.

## REST vs gRPC?

```yaml
category: microservices
level: middle
difficulty: 3
slug: microservices-rest-vs-grpc
tags: api-design, microservices
```

REST — архитектурный стиль поверх HTTP, обычно с JSON, ресурсами и HTTP-методами; gRPC — RPC-фреймворк с контрактом в `.proto`, бинарной сериализацией Protobuf и транспортом HTTP/2. REST универсальнее и лучше для публичных API и браузеров, gRPC — быстрее и строже для внутренних вызовов между сервисами.

| | REST (JSON) | gRPC |
| --- | --- | --- |
| Контракт | OpenAPI, часто опционален | `.proto`, обязателен, генерация клиента и сервера |
| Формат | текстовый JSON | бинарный Protobuf, компактнее и быстрее парсится |
| Транспорт | HTTP/1.1 или HTTP/2 | HTTP/2 (мультиплексирование, одно соединение) |
| Стриминг | нет встроенного (SSE, WebSocket отдельно) | unary, server, client, bidirectional streaming |
| Браузер | нативно | только через gRPC-Web или JSON transcoding |
| Отладка | curl, браузер, человекочитаемо | нужны grpcurl, Postman; payload бинарный |
| Кэширование | HTTP-кэш, CDN, ETag | фактически нет |
| Эволюция | договорённости и версии в URL | правила Protobuf: номера полей, не переиспользовать удалённые |
| Ошибки | HTTP-статусы, ProblemDetails | статус-коды gRPC (`NotFound`, `Unavailable`, `DeadlineExceeded`) |

**gRPC в .NET:**

```protobuf
service Inventory {
  rpc Reserve (ReserveRequest) returns (ReserveReply);
}
message ReserveRequest { string sku = 1; int32 qty = 2; }
message ReserveReply { bool ok = 1; }
```

Пакет `Grpc.AspNetCore` генерирует базовый класс сервера и клиент; клиент регистрируется через `AddGrpcClient<T>()` и интегрируется с `IHttpClientFactory`. Есть **deadline** — таймаут, который передаётся по цепочке вызовов.

**Подводные камни gRPC:**

- HTTP/2 держит долгоживущие соединения, поэтому L4-балансировщик прибивает весь трафик к одному поду — нужна L7-балансировка (Envoy, service mesh) или клиентская балансировка;
- нужен TLS или явная настройка для HTTP/2 без шифрования (h2c);
- поддержка на прокси и API gateway не везде полная.

**Практичный компромисс:** снаружи REST (через gateway), внутри gRPC для высоконагруженных синхронных вызовов; ASP.NET Core умеет JSON transcoding, отдавая один gRPC-сервис и как REST.

## Synchronous vs asynchronous communication?

```yaml
category: microservices
level: middle
difficulty: 3
slug: microservices-synchronous-vs-asynchronous-communication
tags: async, synchronization
```

При синхронном взаимодействии вызывающий отправляет запрос и ждёт ответа (HTTP, gRPC); при асинхронном — кладёт сообщение в брокер и продолжает работу, а получатель обработает его, когда сможет. Главное различие — временная связанность: синхронно оба сервиса должны быть доступны одновременно, асинхронно — нет.

Важно не путать с `async/await` в C#: асинхронный `await httpClient.GetAsync()` не блокирует поток, но архитектурно это всё ещё синхронное взаимодействие — вы ждёте ответа.

| | Синхронно | Асинхронно (сообщения) |
| --- | --- | --- |
| Доступность | отказ вызываемого = отказ вызывающего | получатель может быть недоступен, сообщения подождут в очереди |
| Latency | суммируется по цепочке | для пользователя быстро, результат — позже |
| Консистентность | ответ сразу, можно прочитать свежие данные | eventual consistency |
| Нагрузка | пики передаются напрямую вниз | очередь сглаживает пики (load leveling) |
| Сложность | простая модель, понятная отладка | дубликаты, порядок, DLQ, идемпотентность |
| Связанность | вызывающий знает адрес и API | издатель может не знать подписчиков |

**Проблема цепочек.** Если запрос проходит A → B → C → D и у каждого доступность 99,9%, итоговая — примерно 99,6%, а latency — сумма всех. Длинные синхронные цепочки — признак неверных границ.

**Когда синхронно:** нужен немедленный ответ пользователю, запрос-чтение, валидация (проверить остаток перед показом кнопки).

**Когда асинхронно:** оповещение о факте (событие), долгие операции (генерация отчёта), взаимодействие нескольких сервисов в бизнес-процессе, интеграция с медленными внешними системами.

**Типичный гибрид:** API принимает команду синхронно, сохраняет её, возвращает `202 Accepted` с идентификатором, дальнейшая обработка идёт через события, а клиент узнаёт результат через polling, webhook или SignalR.

**Что спросят дальше:** как гарантировать доставку (Outbox), как бороться с дубликатами (идемпотентные обработчики, Inbox), что делать с «ядовитыми» сообщениями (DLQ).

## Что такое API Gateway?

```yaml
category: microservices
level: middle
difficulty: 2
slug: microservices-chto-takoe-api-gateway
tags: microservices
```

API Gateway — единая точка входа для внешних клиентов, которая принимает запросы и маршрутизирует их к нужным внутренним сервисам, попутно решая сквозные задачи: аутентификацию, rate limiting, TLS-терминацию, логирование. Клиент видит один адрес, а не десятки сервисов.

**Что обычно делает gateway:**

- **маршрутизация** — `/api/orders/*` → сервис заказов, `/api/catalog/*` → каталог;
- **аутентификация** — проверка JWT, после чего внутрь передаются claims или внутренний токен;
- **rate limiting и квоты** на клиента или API-ключ;
- **TLS-терминация, CORS, сжатие**;
- **агрегация** — один запрос клиента собирает ответ из нескольких сервисов (осторожно, см. ниже);
- **трансляция протоколов** — REST снаружи, gRPC внутри;
- **наблюдаемость** — единое место для access-логов и метрик входящего трафика.

**Варианты в .NET-мире:**

- **YARP** (Yet Another Reverse Proxy) — библиотека Microsoft для построения прокси на ASP.NET Core, настраивается через конфиг или код;
- **Ocelot** — популярный open-source gateway для .NET;
- облачные: Azure API Management, AWS API Gateway; инфраструктурные: NGINX, Envoy, Kong.

```json
"ReverseProxy": {
  "Routes": {
    "orders": { "ClusterId": "orders", "Match": { "Path": "/api/orders/{**rest}" } }
  },
  "Clusters": {
    "orders": { "Destinations": { "d1": { "Address": "http://orders:8080/" } } }
  }
}
```

**Паттерн Backend for Frontend (BFF)** — отдельный gateway под каждый тип клиента (веб, мобильное приложение), со своими агрегациями и форматом.

**Риски:**

- **единая точка отказа** — нужно несколько реплик и отсутствие состояния;
- **бутылочное горлышко по релизам**, если gateway принадлежит одной команде и все изменения идут через неё;
- **утечка бизнес-логики** в gateway — он должен оставаться «тонким»;
- дополнительный сетевой хоп и latency.

## Что такое Service Discovery?

```yaml
category: microservices
level: middle
difficulty: 2
slug: microservices-chto-takoe-service-discovery
tags: microservices
```

Service discovery — механизм, с помощью которого сервис находит сетевой адрес другого сервиса по логическому имени. В облаке и контейнерах экземпляры постоянно создаются, умирают и меняют IP, поэтому адреса нельзя хранить в конфиге — их нужно получать из реестра, который знает актуальный список здоровых экземпляров.

**Как это устроено:**

1. Экземпляр при старте регистрируется в реестре (сам или его регистрирует платформа).
2. Реестр проверяет здоровье экземпляров через health check и удаляет мёртвые.
3. Клиент запрашивает адреса по имени сервиса и выбирает, куда отправить запрос.

**Два варианта обнаружения:**

| | Client-side discovery | Server-side discovery |
| --- | --- | --- |
| Кто выбирает экземпляр | клиент получает список и сам балансирует | клиент идёт на балансировщик/прокси, тот выбирает |
| Примеры | Consul + клиентская библиотека, Eureka, gRPC client-side LB | Kubernetes Service, AWS ALB, service mesh |
| Плюсы | нет лишнего хопа, гибкая балансировка | клиент простой, логика в инфраструктуре |
| Минусы | библиотека нужна в каждом языке | дополнительный компонент на пути запроса |

**В Kubernetes** discovery встроен: `Service` получает стабильное DNS-имя (`orders.default.svc.cluster.local`) и виртуальный IP, kube-proxy распределяет трафик по подам, которые прошли readiness probe. Поэтому в k8s отдельный Consul обычно не нужен.

**В .NET** есть `Microsoft.Extensions.ServiceDiscovery` (используется в .NET Aspire): в `HttpClient` указывается логическое имя вида `https+http://catalog`, а адрес резолвится из конфигурации или DNS.

```csharp
builder.Services.AddServiceDiscovery();
builder.Services.AddHttpClient<CatalogClient>(c =>
        c.BaseAddress = new("https+http://catalog"))
    .AddServiceDiscovery();
```

**Нюансы:** DNS-кэширование может отдавать устаревшие адреса; клиентам всё равно нужны retry и таймауты, потому что реестр отстаёт от реальности на секунды; для gRPC с долгими соединениями важно, чтобы балансировка учитывала появление новых экземпляров.

## Что такое Circuit Breaker?

```yaml
category: microservices
level: middle
difficulty: 2
slug: microservices-chto-takoe-circuit-breaker
tags: resilience
```

Circuit breaker («автоматический выключатель») — паттерн, который перестаёт отправлять запросы к зависимости, если она массово отвечает ошибками, и сразу возвращает отказ вызывающему. Это защищает и упавший сервис (ему дают восстановиться), и вызывающий (он не тратит потоки и соединения на заведомо бесполезные ожидания).

**Три состояния:**

| Состояние | Поведение |
| --- | --- |
| **Closed** | запросы идут как обычно, breaker считает ошибки |
| **Open** | порог ошибок превышен — запросы сразу отклоняются (в Polly — `BrokenCircuitException`), вызова по сети нет |
| **Half-Open** | после паузы (break duration) пропускается пробный запрос; успех → Closed, ошибка → снова Open |

**Пример на Microsoft.Extensions.Http.Resilience (Polly v8):**

```csharp
builder.Services.AddHttpClient<PaymentsClient>()
    .AddResilienceHandler("payments", b => b
        .AddCircuitBreaker(new HttpCircuitBreakerStrategyOptions
        {
            FailureRatio = 0.5,                      // 50% ошибок
            MinimumThroughput = 20,                  // но не меньше 20 запросов
            SamplingDuration = TimeSpan.FromSeconds(30),
            BreakDuration = TimeSpan.FromSeconds(15)
        }));
```

Считается доля ошибок за окно, а не просто «N ошибок подряд»; `MinimumThroughput` не даёт размыкаться из-за двух неудачных запросов ночью.

**Что считать ошибкой.** Обычно — 5xx, 408, 429, таймауты и сетевые исключения. Ответ `400` или `404` — это ошибка клиента, а не нездоровье зависимости, их учитывать нельзя.

**Что делать, когда breaker открыт:** вернуть fallback (кэшированные данные, значение по умолчанию, деградированный ответ — «рекомендации недоступны»), быстро ответить `503`, поставить операцию в очередь.

**Нюансы:**

- breaker локален для экземпляра: у каждого пода своё состояние, и это обычно нормально;
- один breaker на зависимость (или на эндпоинт), а не один на всё приложение;
- состояния breaker'а стоит выводить в метрики и алерты — это ранний сигнал проблем.

## Что такое Retry?

```yaml
category: microservices
level: middle
difficulty: 2
slug: microservices-chto-takoe-retry
tags: resilience
```

Retry — повторная попытка операции после временного (transient) сбоя: сетевой ошибки, таймаута, ответа `503` или `429`. Многие сбои в распределённой системе кратковременны — перезапуск пода, переключение соединения, короткая перегрузка, — и второй запрос через сотни миллисекунд проходит успешно.

**Ключевые параметры:**

- **что повторять** — только transient-ошибки: `HttpRequestException`, таймауты, 5xx, 408, 429. Никогда — `400`, `401`, `404`, ошибки валидации: повтор даст тот же результат;
- **сколько раз** — обычно 2–3 попытки, не больше;
- **задержка** — exponential backoff (200 мс, 400 мс, 800 мс…) плюс **jitter** (случайный разброс), чтобы клиенты не повторяли синхронно;
- **общий бюджет времени** — повторы не должны выходить за таймаут, который ждёт вызывающий.

```csharp
builder.Services.AddHttpClient<CatalogClient>()
    .AddResilienceHandler("catalog", b => b
        .AddRetry(new HttpRetryStrategyOptions
        {
            MaxRetryAttempts = 3,
            BackoffType = DelayBackoffType.Exponential,
            UseJitter = true,
            Delay = TimeSpan.FromMilliseconds(200)
        }));
```

`HttpRetryStrategyOptions` по умолчанию уже обрабатывает типичные transient-ответы и учитывает заголовок `Retry-After`. Для большинства клиентов достаточно `AddStandardResilienceHandler()`, который включает retry, circuit breaker и таймауты с разумными значениями.

**Главное условие безопасности — идемпотентность.** `GET` повторять безопасно. `POST /payments` без idempotency key может списать деньги дважды: первый запрос выполнился, но ответ потерялся по дороге, и клиент повторил.

**Где ещё встречается retry:**

- EF Core: `EnableRetryOnFailure()` для SQL Server/PostgreSQL (тогда пользовательские транзакции нужно оборачивать в execution strategy);
- брокеры: повторная доставка сообщения, redelivery в MassTransit, после исчерпания — DLQ.

Retry без ограничений — один из самых частых источников каскадных отказов, поэтому в связке с ним почти всегда нужен circuit breaker.

## Почему retry может быть опасен?

```yaml
category: microservices
level: middle
difficulty: 4
slug: microservices-pochemu-retry-mozhet-byt-opasen
tags: resilience
```

Retry опасен тем, что умножает нагрузку ровно в тот момент, когда зависимость и так перегружена, и может повторить неидемпотентную операцию. Неаккуратные повторы превращают локальный сбой в каскадный отказ всей системы (retry storm).

**1. Усиление нагрузки по цепочке (retry amplification).** Если A → B → C → D и каждый уровень делает 3 попытки, при отказе D он получит до 3 × 3 × 3 = 27 запросов на один пользовательский. Правило: повторять на одном уровне (обычно ближе к краю или непосредственно у вызова), а внутренние уровни пусть падают быстро.

**2. Retry storm и thundering herd.** Зависимость притормозила → все клиенты одновременно получили таймаут → все одновременно повторили → нагрузка выросла в разы → сервис окончательно лёг. Без jitter повторы синхронизируются волнами.

**3. Дубли неидемпотентных операций.** Таймаут не означает, что операция не выполнилась. Запрос мог дойти, списание прошло, а ответ потерялся. Повтор `POST` без idempotency key — двойное списание, два заказа, два письма.

**4. Повтор неповторяемых ошибок.** `400`, `401`, `409`, ошибка валидации — повтор бессмысленен и только тратит ресурсы и время пользователя.

**5. Рост latency и нарушение таймаутов.** Три попытки по 10 секунд — это 30+ секунд, а вызывающий ждёт 5. Он уже отвалился, а вы продолжаете нагружать зависимость ради ответа, который никому не нужен.

**6. Удержание ресурсов.** Во время повторов держатся потоки, соединения, блокировки в БД, пользовательская транзакция.

**Как делать безопасно:**

- повторять только transient-ошибки и только идемпотентные операции (или с idempotency key);
- exponential backoff + jitter, 2–3 попытки;
- **retry budget** — ограничивать долю повторов от общего трафика (например, не больше 10–20%), чтобы при массовом сбое повторы не удваивали нагрузку;
- circuit breaker снаружи повторов — при открытом breaker'е повторы не идут;
- общий таймаут на всю операцию и per-attempt таймаут на каждую попытку;
- уважать `Retry-After` и `429`;
- передавать deadline по цепочке (в gRPC это встроено), чтобы нижние сервисы не работали после того, как верхний сдался.

**Пример вопроса на интервью:** «Сервис лёг на 30 секунд, а восстанавливался 20 минут — почему?» Ответ: после перезапуска его сразу добили накопленные повторы от всех клиентов без jitter и без circuit breaker'а.

## Что такое Timeout?

```yaml
category: microservices
level: middle
difficulty: 2
slug: microservices-chto-takoe-timeout
tags: resilience
```

Timeout — максимальное время, которое вызывающий готов ждать ответа от зависимости, после чего он прерывает ожидание и считает вызов неудачным. Без таймаута один медленный сервис заставляет висеть потоки, соединения и запросы всех, кто от него зависит, и медленность распространяется по системе.

**Почему «медленно» хуже, чем «упал».** Упавший сервис быстро возвращает ошибку соединения. Зависший держит запросы открытыми: пул соединений исчерпывается, запросы копятся в очереди, память растёт — и начинает деградировать уже вызывающий.

**Виды таймаутов:**

- **connect timeout** — на установку TCP/TLS-соединения, короткий;
- **per-attempt timeout** — на одну попытку запроса;
- **total timeout** — на всю операцию, включая все повторы;
- **таймауты БД** — `CommandTimeout` в EF Core/ADO.NET;
- **deadline** — абсолютный момент, к которому ответ должен быть получен, и который передаётся дальше по цепочке (gRPC deadline).

**В .NET:**

```csharp
// HttpClient.Timeout — по умолчанию 100 секунд, для межсервисных вызовов слишком много
builder.Services.AddHttpClient<CatalogClient>()
    .AddResilienceHandler("catalog", b => b
        .AddTimeout(TimeSpan.FromSeconds(2)));

// сквозная отмена
await client.GetAsync(url, cancellationToken);
```

Таймаут работает через `CancellationToken`, поэтому токен нужно пробрасывать во все асинхронные вызовы — иначе операция внутри продолжит выполняться. В ASP.NET Core `HttpContext.RequestAborted` отменяется, когда клиент отключился.

**Как выбрать значение.** От реальной latency зависимости: обычно немного выше p99 (например, p99 = 300 мс → таймаут 1 с), и обязательно меньше таймаута вызывающего уровня. Таймауты должны уменьшаться вниз по цепочке: gateway 10 с → сервис 5 с → его зависимость 2 с.

**Подводный камень:** таймаут не отменяет операцию на стороне сервера. Запрос мог выполниться, поэтому повтор после таймаута безопасен только для идемпотентных операций.

## Что такое Bulkhead pattern?

```yaml
category: microservices
level: middle
difficulty: 2
slug: microservices-chto-takoe-bulkhead-pattern
tags: resilience
```

Bulkhead («переборка», как в отсеках корабля) — паттерн изоляции ресурсов: для разных зависимостей или типов нагрузки выделяются отдельные ограниченные пулы (потоков, соединений, слотов конкурентности), чтобы проблема в одной части не истощила ресурсы для всех остальных.

**Проблема, которую он решает.** Сервис вызывает платежи, рекомендации и склад. Рекомендации начали отвечать по 30 секунд. Без изоляции все входящие запросы застревают в ожидании рекомендаций, пул соединений и потоки заканчиваются — и перестаёт работать даже оформление заказа, которому рекомендации вообще не нужны.

**Уровни, на которых применяется:**

- **внутри процесса** — ограничение одновременных вызовов к каждой зависимости. В Polly v8 это concurrency limiter (на базе `System.Threading.RateLimiting`), который заменил старую Bulkhead policy;
- **пулы соединений** — отдельный `HttpClient` с ограничением `MaxConnectionsPerServer` на каждую зависимость;
- **на уровне развёртывания** — разные реплики или пулы подов для разных клиентов (например, отдельные экземпляры под пакетную обработку и под интерактивный трафик);
- **на уровне данных** — отдельные очереди и консьюмеры для разных типов сообщений, чтобы поток медленных задач не блокировал быстрые;
- **ресурсы Kubernetes** — limits на CPU/память, чтобы один контейнер не съел весь узел.

```csharp
builder.Services.AddHttpClient<RecommendationsClient>()
    .AddResilienceHandler("recs", b => b
        .AddConcurrencyLimiter(permitLimit: 20, queueLimit: 10)
        .AddTimeout(TimeSpan.FromSeconds(1)));
```

Когда лимит и очередь заполнены, новые вызовы сразу отклоняются, и их можно обработать fallback'ом.

**Trade-off:** жёсткое разделение снижает утилизацию — выделенный пул может простаивать, пока другой переполнен. Лимиты подбираются по реальной конкурентности и latency (закон Литтла: конкурентность ≈ RPS × среднее время ответа).

Bulkhead обычно сочетают с таймаутом (чтобы слоты не занимались бесконечно) и circuit breaker'ом.

## Что такое idempotency?

```yaml
category: microservices
level: middle
difficulty: 2
slug: microservices-chto-takoe-idempotency
tags: idempotency
```

Идемпотентность — свойство операции давать один и тот же результат и одинаковый эффект на систему, сколько бы раз её ни выполнили с теми же входными данными. В распределённых системах это критично, потому что повторы неизбежны: retry после таймаута, повторная доставка сообщения брокером, двойной клик пользователя.

**Почему повторы неизбежны.** Если клиент не получил ответ, он не может знать, выполнилась ли операция: запрос потерялся, упал сервер или потерялся ответ. Брокеры с гарантией at-least-once тоже по определению иногда доставляют сообщение повторно. Exactly-once доставки «из коробки» по сети не бывает — есть только at-least-once + идемпотентная обработка.

**Идемпотентность HTTP-методов (по спецификации):**

| Метод | Идемпотентен | Комментарий |
| --- | --- | --- |
| `GET`, `HEAD` | да | и безопасен (не меняет состояние) |
| `PUT` | да | «установить ресурс в такое состояние» |
| `DELETE` | да | повторное удаление ничего не меняет (статус ответа может отличаться — 404) |
| `POST` | нет | каждый вызов создаёт новый ресурс |
| `PATCH` | не гарантированно | зависит от операции |

**Примеры:**

- `SET balance = 100` — идемпотентно; `balance = balance + 10` — нет;
- «отметить заказ оплаченным» — идемпотентно; «добавить позицию в заказ» — нет;
- отправка письма — нет, если не проверять, было ли оно уже отправлено.

**Важное различие:** идемпотентность — про *эффект*, а не про идентичность ответа. Повторный `DELETE` может вернуть `404`, повторный запрос с idempotency key — сохранённый ответ первого, но состояние системы не должно меняться повторно.

**Как добиваются:** естественно идемпотентный дизайн операций (установка состояния вместо инкремента), idempotency key на запросах, дедупликация сообщений по ID (Inbox), уникальные ограничения в БД, оптимистичная блокировка по версии.

## Как сделать API idempotent?

```yaml
category: microservices
level: middle
difficulty: 3
slug: microservices-kak-sdelat-api-idempotent
tags: idempotency
```

Основной способ — **idempotency key**: клиент генерирует уникальный ключ на логическую операцию и передаёт его в заголовке, сервер сохраняет результат первой обработки по этому ключу и на повторы возвращает сохранённый ответ, не выполняя операцию заново. Дополнительно помогают естественная идемпотентность операций и уникальные ограничения в БД.

**Схема с idempotency key:**

1. Клиент генерирует `Idempotency-Key: 5f1c...` (GUID) и использует один и тот же ключ во всех повторах этой операции.
2. Сервер в транзакции пытается вставить запись `(key, status = processing, request_hash)`.
3. Если вставка прошла — выполняет операцию, сохраняет ответ (статус-код и тело) рядом с ключом.
4. Если ключ уже есть и статус `completed` — возвращает сохранённый ответ.
5. Если ключ есть, но `processing` — возвращает `409 Conflict` (или просит повторить позже), чтобы не обрабатывать параллельно.
6. Если тот же ключ пришёл с другим телом — `422`/`409`: это ошибка клиента.

```csharp
app.MapPost("/payments", async (PaymentRequest req,
    [FromHeader(Name = "Idempotency-Key")] Guid key, AppDb db) =>
{
    var existing = await db.IdempotencyKeys.FindAsync(key);
    if (existing is { Status: "completed" })
        return Results.Json(existing.Response, statusCode: existing.StatusCode);

    await using var tx = await db.Database.BeginTransactionAsync();
    db.IdempotencyKeys.Add(new IdempotencyRecord(key, "processing")); // PK по key
    await db.SaveChangesAsync();          // конкурентный дубль упадёт на уникальности
    var payment = await ChargeAsync(req, db);
    // ... сохранить ответ в записи, Status = "completed"
    await db.SaveChangesAsync();
    await tx.CommitAsync();
    return Results.Created($"/payments/{payment.Id}", payment);
});
```

Ключевое — запись ключа и бизнес-изменение должны фиксироваться **в одной транзакции**, иначе возможна ситуация «операция выполнена, ключ не сохранён».

**Другие приёмы:**

- **PUT с клиентским ID** вместо `POST`: `PUT /orders/{orderId}` — клиент сам задаёт ID, повтор перезаписывает то же самое;
- **уникальные ограничения**: `UNIQUE(external_payment_id)` — второй раз вставить не получится;
- **установка состояния вместо инкремента**: `status = 'paid'`, а не `count + 1`;
- **условные обновления**: `UPDATE ... WHERE version = @expected` или `If-Match` с ETag.

**Практические детали:** ключи хранят ограниченное время (у Stripe — 24 часа), ключ связывают с пользователем, чтобы чужой ключ не вернул чужой ответ. Если операция вызывает внешнюю систему, ключ нужно пробросить и туда, иначе идемпотентность ломается на следующем звене.

## Что такое distributed transaction?

```yaml
category: microservices
level: middle
difficulty: 2
slug: microservices-chto-takoe-distributed-transaction
tags: transactions, consistency
```

Распределённая транзакция — транзакция, которая должна атомарно изменить данные в нескольких независимых ресурсах: разных базах данных, базе и брокере сообщений, нескольких сервисах. Либо все изменения применяются, либо ни одно — как у обычной ACID-транзакции, но через сеть.

**Классическая реализация — two-phase commit (2PC):**

1. **Prepare.** Координатор спрашивает всех участников: «Готовы зафиксировать?» Каждый выполняет изменения, пишет их в журнал, удерживает блокировки и отвечает «да» или «нет».
2. **Commit/Rollback.** Если все ответили «да» — координатор рассылает commit, иначе — rollback.

Протокол стандартизирован как XA; в Windows его реализует MSDTC, в .NET — `TransactionScope` с эскалацией до распределённой транзакции (в .NET 7+ поддержка распределённых транзакций на Windows вернулась, но только на Windows).

**Почему в микросервисах 2PC почти не используют:**

- участники блокируют данные, пока ждут решения координатора — падает пропускная способность;
- при падении координатора между фазами участники зависают в неопределённом состоянии;
- многие ресурсы XA не поддерживают: Kafka, большинство облачных БД, HTTP-API других сервисов;
- синхронная связанность: все участники должны быть доступны одновременно.

**Чем заменяют:**

- **Saga** — последовательность локальных транзакций с компенсирующими действиями при ошибке;
- **Transactional Outbox** — атомарно сохранить изменение и событие в одной локальной БД, а доставить событие позже;
- **Inbox / идемпотентные обработчики** — безопасная обработка повторов;
- **пересмотр границ** — если операция требует атомарности между сервисами постоянно, данные, возможно, должны жить в одном сервисе.

Итог: в микросервисах вместо атомарности «всё или ничего» принимают **eventual consistency** и проектируют процесс так, чтобы из любого промежуточного состояния можно было дойти до согласованного.

## Почему distributed transactions сложны?

```yaml
category: microservices
level: middle
difficulty: 4
slug: microservices-pochemu-distributed-transactions-slozhny
tags: transactions, consistency
```

Распределённые транзакции сложны, потому что участники общаются через ненадёжную сеть и падают независимо, а значит, невозможно одновременно гарантировать атомарность, доступность и приемлемую производительность. Протоколы вроде 2PC дают атомарность ценой блокировок, зависаний и жёсткой связанности, а отказ от них — ценой временной несогласованности.

**Фундаментальные причины:**

- **Частичные отказы.** В одном процессе вызов либо выполнился, либо бросил исключение. По сети есть третий исход — «неизвестно»: таймаут не говорит, дошёл ли запрос и выполнился ли он.
- **Невозможность консенсуса без допущений.** Задача двух генералов: по ненадёжному каналу две стороны не могут гарантированно договориться о совместном действии за конечное число сообщений. FLP-результат: в асинхронной системе с возможным падением даже одного узла детерминированный консенсус не гарантирован.
- **CAP.** При сетевом разделе приходится выбирать между согласованностью и доступностью.

**Конкретные проблемы 2PC:**

| Проблема | Суть |
| --- | --- |
| Блокирующий протокол | после `prepare` участник держит блокировки, пока не узнает решение; если координатор упал — держит неопределённо долго |
| Координатор — SPOF | его журнал становится критичным, восстановление требует ручного вмешательства (in-doubt транзакции) |
| Latency | минимум два сетевых раунда + fsync журналов на каждом участнике |
| Доступность | транзакция успешна, только если живы все участники: доступности перемножаются |
| Поддержка | Kafka, RabbitMQ, облачные сервисы, внешние REST API не участвуют в XA |
| Связанность | сервисы вынуждены делить транзакционного координатора и технологии |

**Проблема dual write.** Даже без 2PC типичная ошибка — «сохранить в БД, потом отправить в брокер». Если процесс упал между этими шагами, событие потеряно; если поменять местами — событие ушло, а данные не сохранились. Именно для этого придуман Outbox.

**Что делают на практике:**

- **Saga** с компенсациями вместо отката;
- **Outbox** для атомарности «данные + событие»;
- **идемпотентность и Inbox** для безопасных повторов;
- **семантические блокировки** (статусы `Pending`) вместо блокировок БД;
- **сверка (reconciliation)** — фоновые задачи, находящие и исправляющие расхождения;
- проектирование границ так, чтобы жёсткие инварианты оставались внутри одного сервиса.

**Что проверяют на интервью:** понимание, что «просто обернуть в `TransactionScope`» не работает между сервисами, и умение объяснить, какую изоляцию теряет Saga (нет изоляции — другие видят промежуточное состояние).

## Что такое Saga Pattern?

```yaml
category: microservices
level: middle
difficulty: 2
slug: microservices-chto-takoe-saga-pattern
tags: consistency
```

Saga — паттерн управления бизнес-транзакцией, охватывающей несколько сервисов, как последовательностью локальных транзакций. Каждый шаг фиксирует изменения в своей базе и публикует событие или команду для следующего шага; если какой-то шаг не удался, выполняются **компенсирующие транзакции**, которые семантически отменяют уже сделанные шаги.

**Пример — оформление заказа:**

| Шаг | Действие | Компенсация |
| --- | --- | --- |
| 1. Orders | создать заказ в статусе `Pending` | отменить заказ |
| 2. Inventory | зарезервировать товар | снять резерв |
| 3. Payments | списать деньги | вернуть деньги |
| 4. Orders | перевести заказ в `Confirmed` | — |

Если платёж отклонён, выполняются компенсации в обратном порядке: снять резерв → отменить заказ.

**Два способа координации:**

- **хореография** — сервисы реагируют на события друг друга, центрального управляющего нет;
- **оркестрация** — отдельный оркестратор (state machine) отправляет команды участникам и решает, что дальше.

**Важные свойства:**

- **нет изоляции (I из ACID).** Промежуточные состояния видны другим: заказ `Pending`, товар зарезервирован, но деньги ещё не списаны. Поэтому используют семантические статусы и проверяют их в бизнес-логике;
- **компенсация ≠ rollback.** Это новая бизнес-операция (возврат денег, письмо с извинениями), и она сама может упасть — её повторяют;
- **идемпотентность шагов обязательна** — сообщения могут прийти повторно;
- **надёжная публикация** событий — через Outbox, иначе saga зависнет между шагами.

**Инструменты в .NET:** MassTransit (state machine sagas на `MassTransitStateMachine<T>`, хранение состояния в EF Core/MongoDB/Redis), NServiceBus Sagas, для долгих процессов — Temporal, Azure Durable Functions.

Saga подходит для бизнес-процессов, которые естественно можно разбить на шаги с понятной отменой. Если отменить шаг нельзя, его ставят последним (pivot transaction).

## Choreography vs Orchestration?

```yaml
category: microservices
level: middle
difficulty: 3
slug: microservices-choreography-vs-orchestration
tags: consistency
```

Это два способа координировать шаги Saga или любого бизнес-процесса между сервисами. В **хореографии** сервисы реагируют на события друг друга и сами решают, что делать, — центра нет. В **оркестрации** есть оркестратор, который явно отправляет команды участникам и хранит состояние процесса.

**Хореография (заказ):**

```text
Orders   --OrderCreated-->    Inventory
Inventory --StockReserved-->  Payments
Payments --PaymentFailed-->   Inventory (снять резерв), Orders (отменить)
```

**Оркестрация (тот же процесс):**

```text
OrderSaga -> Inventory: ReserveStock
Inventory -> OrderSaga: StockReserved
OrderSaga -> Payments:  ChargePayment
Payments  -> OrderSaga: PaymentFailed
OrderSaga -> Inventory: ReleaseStock
OrderSaga -> Orders:    CancelOrder
```

| | Хореография | Оркестрация |
| --- | --- | --- |
| Где логика процесса | размазана по участникам | в одном месте — оркестраторе |
| Связанность | слабая: издатель не знает подписчиков | участники не знают друг о друге, но оркестратор знает всех |
| Видимость процесса | «где сейчас заказ?» — нужно собирать по логам и трассам | состояние хранится явно, легко посмотреть и отладить |
| Добавить шаг | новый подписчик, издатель не меняется | правка оркестратора |
| Риск | циклические зависимости событий, «никто не понимает весь процесс» | оркестратор превращается в «божественный» сервис с бизнес-логикой |
| Таймауты и зависания | сложно: кто заметит, что ответ не пришёл? | оркестратор ставит таймаут и запускает компенсацию |
| Подходит | 2–4 шага, простые реакции на события | много шагов, ветвления, компенсации, SLA процесса |

**Практическое правило.** Для простых реакций («заказ создан → отправить письмо, начислить баллы») — хореография: издателю не нужно знать о подписчиках. Для процесса с компенсациями и таймаутами — оркестрация, потому что отладка хореографии из шести сервисов превращается в археологию.

**В .NET:** хореография — обычные консьюмеры MassTransit/NServiceBus; оркестрация — MassTransit state machine saga или NServiceBus Saga с хранением состояния в БД, либо движки вроде Temporal.

Чаще всего в реальной системе оба подхода сосуществуют: процессы внутри одного домена оркестрируются, а между доменами общаются публикацией событий.

## Что такое Outbox Pattern?

```yaml
category: microservices
level: middle
difficulty: 2
slug: microservices-chto-takoe-outbox-pattern
tags: consistency
```

Transactional Outbox — паттерн надёжной публикации событий: вместо прямой отправки в брокер сервис записывает событие в таблицу `outbox` **в той же локальной транзакции**, что и бизнес-изменения, а отдельный фоновый процесс читает эту таблицу и публикует события в брокер. Так изменение данных и факт «событие нужно отправить» фиксируются атомарно.

**Проблема dual write, которую он решает:**

```csharp
await db.SaveChangesAsync();          // 1. заказ сохранён
await bus.Publish(new OrderPlaced()); // 2. процесс упал здесь — событие потеряно
```

Поменять порядок не помогает: событие уйдёт, а сохранение упадёт — подписчики узнают о несуществующем заказе. Распределённой транзакции между БД и брокером нет.

**Как работает:**

1. В транзакции: `INSERT INTO orders ...` и `INSERT INTO outbox (id, type, payload, created_at)`.
2. Commit — оба изменения либо есть, либо нет.
3. Relay (фоновый `BackgroundService` или CDC) выбирает неотправленные записи, публикует их в брокер.
4. После подтверждения брокера помечает запись отправленной или удаляет.

**Гарантия — at-least-once.** Если relay опубликовал событие, но упал до пометки записи, после перезапуска событие уйдёт повторно. Поэтому консьюмеры должны быть идемпотентными (или использовать Inbox).

**Варианты relay:**

- **polling** — периодический `SELECT ... WHERE sent_at IS NULL ORDER BY id LIMIT 100`; при нескольких экземплярах — `FOR UPDATE SKIP LOCKED`, чтобы не отправлять одно и то же параллельно;
- **CDC (Change Data Capture)** — Debezium читает журнал транзакций БД (WAL/binlog) и публикует новые строки outbox в Kafka без нагрузки опросами.

**Готовые реализации в .NET:** MassTransit Transactional Outbox для EF Core (`AddEntityFrameworkOutbox<TDbContext>`), NServiceBus Outbox, Wolverine, CAP.

**На что обратить внимание:** порядок событий (в пределах агрегата публиковать по порядку), очистку старых записей, мониторинг «возраста» самой старой неотправленной записи — это главный индикатор проблем.

## Что такое Inbox Pattern?

```yaml
category: microservices
level: middle
difficulty: 2
slug: microservices-chto-takoe-inbox-pattern
tags: consistency
```

Inbox — паттерн на стороне получателя: перед обработкой сообщения его идентификатор записывается в таблицу `inbox` в той же транзакции, что и бизнес-изменения. Если сообщение с таким ID уже есть — оно было обработано, и дубликат пропускается. Это превращает доставку at-least-once в эффективно однократную обработку.

**Зачем он нужен.** Брокеры и Outbox гарантируют «хотя бы один раз»: сообщение может прийти повторно, если консьюмер упал до `ack`, брокер сделал redelivery или Outbox-relay отправил событие дважды. Если обработчик не идемпотентен сам по себе (начисление бонусов, списание остатка), повтор испортит данные.

**Как работает:**

1. Пришло сообщение с `MessageId`.
2. Открывается транзакция БД.
3. `INSERT INTO inbox (message_id, consumer, processed_at)` — с уникальным ключом `(message_id, consumer)`.
4. Если вставка нарушила уникальность — это дубль: commit/rollback и `ack` без обработки.
5. Иначе — выполняется бизнес-логика, commit.
6. `ack` брокеру.

Если процесс упал после commit, но до `ack`, сообщение придёт снова, но запись в inbox уже есть — повторной обработки не будет.

**Детали реализации:**

- ключ — ID сообщения, заданный **отправителем** (например, ID записи outbox), а не генерируемый брокером при каждой доставке;
- ключ учитывает имя консьюмера, если одно сообщение обрабатывают несколько обработчиков в одном сервисе;
- таблицу нужно чистить по TTL, окно хранения должно превышать максимально возможную задержку повторной доставки;
- Inbox работает, только если бизнес-изменения лежат в той же БД, что и таблица inbox.

**Альтернативы:** естественная идемпотентность обработчика (установка статуса, upsert по ключу), проверка версии агрегата.

**В .NET:** в MassTransit Transactional Outbox для EF Core включает и inbox-часть (дедупликацию входящих сообщений), в NServiceBus дедупликацию обеспечивает его Outbox.

## Что такое eventual consistency?

```yaml
category: microservices
level: middle
difficulty: 2
slug: microservices-chto-takoe-eventual-consistency
tags: consistency
```

Eventual consistency (согласованность в конечном счёте) — модель, при которой данные в разных частях системы могут временно расходиться, но при отсутствии новых изменений со временем приходят к одному согласованному состоянию. Это цена за доступность и независимость сервисов, которые не делят одну транзакцию.

**Как это выглядит на практике.** Пользователь оформил заказ, сервис заказов его сохранил и опубликовал `OrderPlaced`. Через 200 мс сервис склада снял остаток, через секунду сервис аналитики обновил отчёт. В эти мгновения разные сервисы «видят» разный мир.

**Где возникает:**

- обмен событиями между микросервисами;
- CQRS: read-модель отстаёт от write-модели;
- репликация БД (чтение с реплики);
- кэши и CDN;
- геораспределённые хранилища.

**Как с этим жить:**

- **проектировать UX** под задержку: «Заказ принят, подтверждение придёт на почту», оптимистичное обновление интерфейса;
- **read-your-writes** для автора изменения: вернуть данные из ответа команды или читать с мастера сразу после записи;
- **явные статусы** (`Pending`, `Processing`) вместо притворства, что всё уже готово;
- **версии и порядок** событий, чтобы старое событие не перезаписало новое;
- **идемпотентные обработчики** — повторы при синхронизации неизбежны;
- **reconciliation** — периодическая сверка и исправление расхождений;
- **мониторинг лага** — насколько отстаёт подписчик от издателя.

**Когда eventual consistency неприемлема.** Инварианты, которые нельзя нарушать даже на миг: не уйти в минус по счёту, не продать одно место дважды. Такие проверки нужно держать внутри одного сервиса и одной транзакции (или резервировать ресурс заранее).

**Частое заблуждение:** «eventual» не означает «когда-нибудь и без гарантий». В нормально работающей системе задержка — миллисекунды или секунды, и её можно и нужно измерять.

## Как обеспечить консистентность между сервисами?

```yaml
category: microservices
level: middle
difficulty: 4
slug: microservices-kak-obespechit-konsistentnost-mezhdu-servisami
tags: consistency
```

Строгой ACID-консистентности между сервисами без распределённых транзакций нет, поэтому её обеспечивают комбинацией: правильные границы (жёсткие инварианты — внутри одного сервиса), надёжная доставка изменений (Outbox), безопасная обработка повторов (идемпотентность/Inbox), координация процессов (Saga) и сверка расхождений (reconciliation). Результат — eventual consistency с контролируемыми гарантиями.

**1. Начать с границ.** Если два куска данных должны меняться атомарно всегда — скорее всего, они принадлежат одному агрегату и одному сервису. Большинство «проблем консистентности» — это неверно проведённые границы.

**2. Надёжная публикация изменений.** Transactional Outbox или CDC: изменение и событие фиксируются атомарно, потеря события невозможна.

**3. Надёжная и идемпотентная обработка.**

- at-least-once доставка + Inbox или естественно идемпотентные операции;
- DLQ для сообщений, которые не удаётся обработать, с алертами;
- учёт порядка: версия агрегата в событии, игнорирование устаревших версий.

**4. Бизнес-процессы через Saga.** Шаги с компенсациями, оркестратор с таймаутами для длинных процессов, семантические блокировки (статусы `Pending`, резервирование) вместо блокировок БД.

**5. Резервирование вместо проверки.** Не «проверить остаток, потом списать» через сеть, а «зарезервировать остаток» как атомарную операцию в сервисе-владельце, с истечением резерва по таймауту.

**6. Защита от гонок.** Оптимистичная конкуренция (`rowversion`, `xmin` в PostgreSQL, ETag), уникальные ограничения, условные обновления.

**7. Сверка и исправление.**

- фоновые задачи, сравнивающие данные сервисов (например, заказы и платежи за сутки);
- обработка «зависших» саг по таймауту;
- возможность переотправить события или перестроить проекции.

**Как выбрать уровень гарантий:**

| Требование | Решение |
| --- | --- |
| Жёсткий инвариант (баланс ≥ 0) | внутри одного сервиса, локальная транзакция |
| Процесс из нескольких шагов с отменой | Saga + Outbox + идемпотентность |
| Распространение справочных данных | события + локальные копии |
| Отчёты, аналитика | асинхронные проекции, лаг приемлем |

**Что не работает:** dual write («сохранил в БД, отправил в брокер»), синхронные цепочки вызовов в надежде, что «все будут доступны», общая база для нескольких сервисов как «решение» консистентности — это возвращает связанность монолита без его транзакций.

## Что такое distributed lock?

```yaml
category: microservices
level: middle
difficulty: 2
slug: microservices-chto-takoe-distributed-lock
tags: synchronization
```

Distributed lock (распределённая блокировка) — механизм взаимного исключения между несколькими процессами или машинами: в каждый момент только один держатель блокировки выполняет критическую секцию. Обычный `lock` или `SemaphoreSlim` работает только внутри одного процесса, а при нескольких репликах сервиса нужен общий арбитр.

**На чём реализуют:**

| Хранилище | Механизм |
| --- | --- |
| Redis | `SET key token NX PX 30000` — установить, если нет, с TTL; снятие — Lua-скрипт с проверкой токена |
| PostgreSQL | advisory locks: `pg_try_advisory_lock(key)` / `pg_advisory_xact_lock` |
| SQL Server | `sp_getapplock` |
| ZooKeeper / etcd | эфемерные узлы, lease с TTL, ревизии для fencing token |
| Azure Blob Storage | blob lease |

**Обязательные свойства корректной блокировки:**

- **взаимное исключение** — два клиента не держат блокировку одновременно;
- **TTL/lease** — если держатель упал, блокировка сама освободится, иначе будет deadlock навсегда;
- **снятие только владельцем** — при захвате сохраняется уникальный токен, освобождение проверяет его (иначе можно снять чужую блокировку, взятую после истечения твоей);
- **fencing token** — монотонный номер, который защищённый ресурс проверяет, чтобы отклонить запись от «опоздавшего» держателя.

**Пример снятия в Redis:**

```lua
if redis.call("get", KEYS[1]) == ARGV[1] then
  return redis.call("del", KEYS[1])
else
  return 0
end
```

**В .NET** удобна библиотека `DistributedLock` (Medallion) с одинаковым API поверх Redis, PostgreSQL, SQL Server, ZooKeeper и других.

**Главное ограничение.** Блокировка с TTL не даёт абсолютной гарантии: процесс может «заснуть» (GC-пауза, свап, сетевые задержки) дольше TTL и продолжить работу, считая, что всё ещё владеет блокировкой. Поэтому для корректности, а не только для эффективности, нужны fencing tokens или идемпотентные операции.

## Когда нужен distributed lock?

```yaml
category: microservices
level: middle
difficulty: 3
slug: microservices-kogda-nuzhen-distributed-lock
tags: synchronization
```

Distributed lock нужен, когда несколько экземпляров сервиса могут одновременно выполнить действие, которое должно выполняться строго одним, и эту гарантию нельзя получить средствами самого хранилища данных. Во многих случаях лучше обойтись без него: уникальные ограничения, оптимистичная конкуренция и партиционирование проще и надёжнее.

**Две категории задач (разделение Мартина Клеппмана):**

- **Эффективность** — блокировка избегает лишней работы. Если изредка её возьмут двое, ничего страшного: отчёт посчитают дважды, письмо-напоминание уйдёт повторно. Здесь хватит простой блокировки в Redis.
- **Корректность** — двойное выполнение портит данные или деньги. Здесь блокировки с TTL недостаточно: нужны fencing tokens, а часто — вообще другой механизм.

**Типичные законные сценарии:**

- **singleton-задачи** в кластере: cron-джоба, миграции БД при старте, очистка outbox — должны выполняться на одной реплике (альтернативы — отдельный Job в Kubernetes, leader election);
- **защита дорогого пересчёта** от параллельного запуска (например, при прогреве кэша — против cache stampede);
- **работа с внешним ресурсом**, который не поддерживает конкурентность и сам не умеет блокировки (FTP-файл, legacy API);
- **последовательная обработка по ключу**, когда нельзя гарантировать партиционирование сообщений.

**Когда лучше без него:**

| Задача | Альтернатива |
| --- | --- |
| Не создать дубль записи | `UNIQUE`-ограничение в БД |
| Не потерять конкурентное обновление | оптимистичная блокировка (`rowversion`, `If-Match`) |
| Обработать сообщения одного агрегата по порядку | партиционирование по ключу в Kafka, sessions в Azure Service Bus |
| Разобрать очередь задач несколькими воркерами | `SELECT ... FOR UPDATE SKIP LOCKED` |
| Списание баланса | атомарный `UPDATE ... SET balance = balance - @x WHERE balance >= @x` |
| Одна запущенная джоба | Kubernetes CronJob с `concurrencyPolicy: Forbid`, Hangfire/Quartz с кластерными блокировками |

**Подводные камни:** выбор TTL (слишком короткий — блокировка истечёт посреди работы, слишком длинный — долгое ожидание после падения), продление блокировки (watchdog) при долгих операциях, недоступность хранилища блокировок — что делать тогда: ждать, отказывать или работать без неё.

## Redis как distributed lock — какие проблемы?

```yaml
category: microservices
level: middle
difficulty: 3
slug: microservices-redis-kak-distributed-lock-kakie-problemy
tags: synchronization, caching
```

Redis подходит для распределённых блокировок ради эффективности, но плохо — ради строгой корректности. Основные проблемы: блокировка может истечь, пока держатель ещё работает; при асинхронной репликации блокировка теряется при failover; Redis сам по себе не выдаёт fencing tokens, а Redlock опирается на предположения о времени, которые в реальных системах нарушаются.

**Базовая реализация и её частые ошибки:**

```text
SET lock:order:42 <uuid> NX PX 30000
```

- `SETNX` + отдельный `EXPIRE` — не атомарно: упал между командами → вечная блокировка. Нужен один `SET ... NX PX`;
- снятие через простой `DEL` — можно удалить чужую блокировку, если твоя уже истекла и её взял другой. Снимать нужно Lua-скриптом, сверяя токен;
- без TTL — упавший клиент держит блокировку вечно.

**1. Истечение TTL во время работы.** Держатель ушёл в долгую GC-паузу, завис на сетевом вызове или его процесс был приостановлен на 40 секунд при TTL 30. Блокировку забрал второй клиент, первый «просыпается» и продолжает писать — два писателя одновременно. Продление (watchdog) уменьшает риск, но не устраняет: пауза может случиться между проверкой и записью.

**2. Failover и асинхронная репликация.** Клиент взял блокировку на мастере, мастер упал до репликации ключа, реплика стала мастером — блокировки нет, её берёт второй клиент.

**3. Redlock.** Алгоритм захвата большинства из N независимых узлов Redis предлагается против проблемы failover. Критика (Клеппман, «How to do distributed locking»): он зависит от ограниченных задержек сети, пауз процессов и дрейфа часов; при перезапуске узла без fsync блокировка может «исчезнуть». Автор Redis (antirez) с частью критики не согласен — это до сих пор спорная тема, но консенсус такой: для корректности Redlock недостаточен.

**4. Нет fencing tokens.** Надёжная схема: при захвате выдаётся монотонно растущий номер, а защищаемый ресурс отклоняет запись с номером меньше последнего виденного. `INCR` в Redis может дать номер, но проверять его должен сам ресурс (БД: `UPDATE ... WHERE last_token < @token`).

**5. Операционные моменты:** Redis недоступен — все, кто ждёт блокировку, стоят; eviction-политика (`allkeys-lru`) может вытеснить ключ блокировки при нехватке памяти.

**Рекомендации:**

- для «не делать лишнюю работу дважды» — Redis `SET NX PX` + Lua-снятие + watchdog, этого достаточно;
- для корректности — fencing tokens, проверяемые хранилищем, либо координатор с консенсусом (etcd, ZooKeeper), либо блокировки прямо в БД, которую вы и так защищаете (advisory lock, `SELECT ... FOR UPDATE`);
- ещё лучше — сделать операции идемпотентными и условными, чтобы двойное выполнение было безопасным.

## Где использовать cache?

```yaml
category: microservices
level: middle
difficulty: 3
slug: microservices-gde-ispolzovat-cache
tags: caching
```

Кэш стоит использовать там, где данные читаются гораздо чаще, чем меняются, их получение дорого (медленный запрос, внешний API, сложный расчёт), а небольшая устарелость допустима. Кэшируют на нескольких уровнях — от браузера до БД, — и на каждом свои правила инвалидации.

**Уровни кэширования:**

| Уровень | Примеры | Что кэшировать |
| --- | --- | --- |
| Клиент/браузер | HTTP `Cache-Control`, `ETag` | статику, редко меняющиеся ответы API |
| CDN | Cloudflare, Azure Front Door | статику, публичные страницы, медиа |
| API Gateway / reverse proxy | output caching | публичные ответы GET |
| Приложение, in-memory | `IMemoryCache`, `HybridCache` L1 | справочники, настройки, горячие ключи |
| Распределённый | Redis, `IDistributedCache` | сессии, результаты запросов, общие для реплик данные |
| БД | buffer pool, материализованные представления | агрегаты, отчёты |

**Хорошие кандидаты:**

- справочники и конфигурация (страны, валюты, фича-флаги);
- каталог товаров, контент;
- результаты дорогих вычислений и агрегатов;
- ответы внешних медленных или платных API;
- данные чужих сервисов, чтобы не делать синхронный вызов на каждый запрос;
- токены и ключи (JWKS для валидации JWT).

**Плохие кандидаты:**

- данные, которые должны быть строго актуальными (баланс при списании, остатки при резервировании) — читайте из источника истины;
- данные с высокой частотой изменений и низкой частотой чтения;
- уникальные запросы с низким hit rate — кэш только тратит память;
- персональные данные без понимания, кто и где их может прочитать.

**In-memory vs распределённый.** Локальный кэш быстрее (наносекунды против сетевого запроса), но у каждой реплики своя копия, и они могут расходиться. Распределённый общий для всех, переживает рестарт подов, но требует сети и сериализации. В .NET 9 появился `HybridCache`, объединяющий оба уровня и защищающий от stampede.

**Что обязательно продумать:** стратегию инвалидации и TTL, поведение при недоступности кэша (система должна работать, хоть и медленнее), метрики hit rate, защиту от stampede и холодного старта.

## Cache-aside pattern?

```yaml
category: microservices
level: middle
difficulty: 3
slug: microservices-cache-aside-pattern
tags: caching
```

Cache-aside (lazy loading) — самый распространённый паттерн кэширования: приложение сначала ищет данные в кэше; при промахе читает из БД, кладёт результат в кэш и возвращает. При изменении данных приложение пишет в БД и удаляет (инвалидирует) запись в кэше. Кэш ничего не знает о БД — всей логикой управляет приложение.

**Чтение:**

```csharp
public async Task<Product?> GetAsync(int id, CancellationToken ct)
{
    var key = $"product:{id}";
    var cached = await _cache.GetStringAsync(key, ct);
    if (cached is not null)
        return JsonSerializer.Deserialize<Product>(cached);

    var product = await _db.Products.FindAsync([id], ct);
    if (product is not null)
        await _cache.SetStringAsync(key, JsonSerializer.Serialize(product),
            new DistributedCacheEntryOptions
            {
                AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(10)
            }, ct);
    return product;
}
```

**Запись:** обновить БД → удалить ключ (`_cache.RemoveAsync(key)`). Удалять, а не обновлять значение, обычно надёжнее: при двух конкурентных записях обновление кэша может записать устаревшее значение последним.

**Плюсы:**

- в кэше только реально запрашиваемые данные;
- отказ кэша не ломает систему — запросы идут в БД;
- просто реализовать, работает с любым хранилищем.

**Минусы и подводные камни:**

- **первый запрос всегда медленный** (cold cache), после деплоя или сброса — всплеск нагрузки на БД;
- **cache stampede** — при истечении горячего ключа сотни запросов одновременно идут в БД;
- **гонка при записи**: читатель прочитал старое значение из БД, писатель обновил БД и удалил ключ, читатель записал в кэш старое значение — кэш неверен до истечения TTL. Поэтому TTL обязателен как страховка;
- **кэширование отсутствия**: если объекта нет, без кэширования «пустого» результата (negative caching) каждый запрос несуществующего ID идёт в БД.

**В .NET 9+** `HybridCache.GetOrCreateAsync` реализует cache-aside с двухуровневым хранением и защитой от stampede: конкурентные запросы одного ключа ждут одну фабрику.

```csharp
var product = await hybridCache.GetOrCreateAsync($"product:{id}",
    async ct => await db.Products.FindAsync([id], ct), cancellationToken: ct);
```

## Write-through vs Write-behind cache?

```yaml
category: microservices
level: middle
difficulty: 3
slug: microservices-write-through-vs-write-behind-cache
tags: caching
```

Оба паттерна описывают запись через кэш. При **write-through** запись синхронно идёт в кэш и в БД, и операция считается успешной, только когда обновлены оба. При **write-behind (write-back)** запись сразу подтверждается после обновления кэша, а в БД изменения сбрасываются асинхронно, часто пачками.

| | Write-through | Write-behind |
| --- | --- | --- |
| Latency записи | выше: кэш + БД | низкая: только кэш |
| Консистентность кэш/БД | кэш всегда актуален | БД отстаёт от кэша |
| Риск потери данных | нет (БД — источник истины) | есть: кэш упал до сброса — изменения потеряны |
| Нагрузка на БД | каждая запись | запись батчами, можно схлопывать повторные изменения одного ключа |
| Сложность | умеренная | высокая: очередь сброса, повторы, порядок, конфликты |
| Типичное применение | данные, которые сразу же читают | счётчики, метрики, лайки, телеметрия, игровое состояние |

**Write-through** обычно сочетают с read-through: кэш выступает фасадом над БД, приложение работает только с ним. Недостаток — в кэш попадает всё записанное, даже то, что никто не будет читать; поэтому нужен TTL.

**Write-behind** выгоден при высокой частоте записи в одни и те же ключи: 1000 инкрементов счётчика за секунду превращаются в один `UPDATE`. Но нужно решить: что делать при падении узла кэша (персистентность Redis — AOF/RDB — снижает, но не исключает потери), как сохранить порядок, как обрабатывать ошибки БД при отложенной записи.

**Сравнение с cache-aside.** В микросервисах чаще всего используют cache-aside: приложение пишет в БД и инвалидирует кэш. Он проще, отказ кэша не ведёт к потере данных, а Redis/`IDistributedCache` не умеют сами синхронизироваться с БД — read/write-through в чистом виде требует либо кэша с поддержкой загрузчиков (NCache, Hazelcast, Apache Ignite), либо обёртки в коде приложения.

**На интервью** часто уточняют: «Что будет, если write-through записал в БД, а в кэш — нет?» Нужна чёткая последовательность (сначала БД, потом кэш) и TTL как страховка, иначе кэш и БД разойдутся.

## Что такое cache stampede?

```yaml
category: microservices
level: middle
difficulty: 2
slug: microservices-chto-takoe-cache-stampede
tags: caching
```

Cache stampede (dog-piling, thundering herd) — ситуация, когда популярный ключ в кэше истекает или удаляется, и множество параллельных запросов одновременно получают промах и все идут пересчитывать значение в БД. Вместо одного запроса к БД — сотни одинаковых, и база может не выдержать.

**Сценарий:** главная страница кэшируется на 60 секунд, её запрашивают 2000 RPS, построение занимает 500 мс. В момент истечения ключа за эти 500 мс около тысячи запросов увидят промах и запустят тот же тяжёлый запрос.

**Способы защиты:**

**1. Single-flight / request coalescing.** В пределах процесса только один запрос вычисляет значение, остальные ждут его результат. В .NET 9+ это делает `HybridCache.GetOrCreateAsync` из коробки. Вручную — `SemaphoreSlim` на ключ или `Lazy<Task<T>>` в `ConcurrentDictionary`.

```csharp
var page = await hybridCache.GetOrCreateAsync("home-page",
    async ct => await BuildHomePageAsync(ct),
    new HybridCacheEntryOptions { Expiration = TimeSpan.FromMinutes(1) });
```

Важно: `IMemoryCache.GetOrCreateAsync` защиты не даёт — фабрика может выполниться несколько раз параллельно.

**2. Распределённая блокировка на пересчёт.** Если реплик много, один экземпляр берёт блокировку (`SET lock:key NX PX`), остальные либо ждут, либо отдают устаревшее значение.

**3. Stale-while-revalidate.** Хранить значение дольше логического TTL: после «мягкого» истечения отдавать старое значение и в фоне обновлять его одним запросом.

**4. Probabilistic early expiration (XFetch).** Каждый запрос с небольшой вероятностью, растущей по мере приближения к истечению, обновляет значение заранее — пересчёт размазывается во времени.

**5. Jitter в TTL.** Если тысячи ключей закэшированы одновременно (например, после деплоя) с одинаковым TTL, они и истекут одновременно. Случайный разброс ±10–20% размазывает истечение.

**6. Прогрев кэша** перед переключением трафика и фоновое обновление самых горячих ключей.

**Родственные проблемы:** cache penetration (запросы несуществующих ключей, которые никогда не попадают в кэш — лечится negative caching или Bloom-фильтром) и cache avalanche (массовое одновременное истечение или падение всего кэша).

## Что такое cache invalidation?

```yaml
category: microservices
level: middle
difficulty: 2
slug: microservices-chto-takoe-cache-invalidation
tags: caching
```

Cache invalidation — удаление или обновление устаревших данных в кэше, когда меняется источник истины. Задача считается одной из самых сложных («There are only two hard things in Computer Science: cache invalidation and naming things»), потому что между изменением данных и обновлением кэша всегда есть окно, а в распределённой системе — ещё и гонки, потери сообщений и несколько копий кэша.

**Основные стратегии:**

| Стратегия | Как работает | Плюсы / минусы |
| --- | --- | --- |
| **TTL** | запись живёт фиксированное время | просто и надёжно; данные устаревают до TTL |
| **Явная инвалидация** | при записи в БД приложение удаляет ключ | свежие данные; легко забыть место, где данные меняются |
| **Событийная** | сервис-владелец публикует `ProductUpdated`, подписчики удаляют ключи | работает между сервисами; событие может задержаться или потеряться |
| **Версионирование ключей** | `product:42:v7` — при изменении версия растёт, старый ключ просто не читают | нет гонок удаления; нужно где-то хранить текущую версию |
| **CDC** | Debezium читает журнал БД и инвалидирует кэш | ловит все изменения, даже прямые SQL-правки; дополнительная инфраструктура |

**Удалять или обновлять?** Обычно удалять: при конкурентных записях обновление кэша может перетереть новое значение старым, а удаление приведёт к перечитыванию из БД при следующем запросе.

**Типичные проблемы:**

- **гонка чтения и записи** в cache-aside: читатель загрузил старое значение до записи, а положил в кэш после инвалидации. Смягчают коротким TTL, отложенным повторным удалением (delayed double delete) или версионированием;
- **многоуровневый кэш**: удалили в Redis, но в `IMemoryCache` каждой реплики значение осталось. Нужна рассылка инвалидации (Redis pub/sub, backplane) или короткий L1 TTL. `HybridCache` поддерживает инвалидацию по тегам (`RemoveByTagAsync`);
- **зависимые ключи**: товар изменился — нужно сбросить и карточку, и списки категорий, и поисковую выдачу. Помогают теги;
- **CDN и HTTP-кэш** — `Cache-Control: max-age` не отозвать: нужны purge API или версии в URL (`app.3f9a.js`).

**Практическое правило:** всегда ставить TTL как страховку, даже при явной инвалидации, и выбирать его исходя из того, насколько бизнес готов видеть устаревшие данные.

## Как масштабировать микросервис?

```yaml
category: microservices
level: middle
difficulty: 4
slug: microservices-kak-masshtabirovat-mikroservis
tags: scalability, microservices
```

Основной способ — горизонтальное масштабирование: сделать сервис stateless и запускать нужное количество реплик за балансировщиком, автоматически меняя их число по нагрузке. Но реплики помогают только до тех пор, пока узким местом не станет что-то общее — база данных, кэш, брокер или внешняя зависимость, — поэтому масштабирование всегда начинается с поиска bottleneck'а.

**1. Найти узкое место.** Метрики: CPU, память, latency p95/p99, длина очередей, пул соединений БД, GC-паузы. Добавлять реплики к сервису, который ждёт медленный SQL-запрос, бесполезно — вы только увеличите нагрузку на БД.

**2. Сделать сервис stateless:**

- сессии и кэш — во внешнем хранилище (Redis) или в токене;
- файлы — в объектном хранилище (S3/Blob), а не на локальном диске;
- фоновые задачи с блокировками или leader election, чтобы не выполнялись N раз;
- data protection keys ASP.NET Core — в общем хранилище, иначе куки одной реплики не расшифруются другой;
- SignalR — backplane (Redis) или Azure SignalR Service.

**3. Автоскейлинг:**

- **Kubernetes HPA** — по CPU, памяти или кастомным метрикам (RPS, latency);
- **KEDA** — по длине очереди RabbitMQ, лагу консьюмеров Kafka, в том числе до нуля реплик;
- важны корректные `requests`/`limits`, быстрый старт и readiness probe, чтобы новая реплика не получала трафик раньше готовности.

**4. Масштабирование данных:**

- read-реплики для чтения;
- кэширование горячих данных;
- CQRS — отдельные оптимизированные read-модели;
- шардирование/партиционирование по ключу (tenant, пользователь);
- пул соединений: 50 реплик × 100 соединений могут исчерпать `max_connections` PostgreSQL — нужен PgBouncer.

**5. Асинхронность.** Тяжёлую работу вынести в очередь и воркеры, масштабируемые отдельно; очередь сглаживает пики.

**6. Масштабирование консьюмеров.** В Kafka параллелизм ограничен числом партиций в топике: консьюмеров в группе больше, чем партиций, — лишние простаивают. В RabbitMQ competing consumers масштабируются проще, но ценой порядка.

**7. Оптимизация самого сервиса** — иногда дешевле: убрать N+1, добавить индекс, уменьшить аллокации, включить Server GC, использовать пулы.

**Шкала куба (Scale Cube, книга «The Art of Scalability»):** X — клонирование реплик, Y — функциональное разделение на сервисы, Z — партиционирование данных. Хорошие ответы упоминают все три оси.

## Horizontal vs vertical scaling?

```yaml
category: microservices
level: middle
difficulty: 3
slug: microservices-horizontal-vs-vertical-scaling
tags: scalability
```

Вертикальное масштабирование (scale up) — дать одной машине больше ресурсов: CPU, памяти, более быстрый диск. Горизонтальное (scale out) — добавить больше машин или экземпляров и распределить нагрузку между ними. Вертикальное проще, но ограничено потолком железа и не даёт отказоустойчивости; горизонтальное масштабируется почти неограниченно, но требует stateless-дизайна и распределения данных.

| | Вертикальное | Горизонтальное |
| --- | --- | --- |
| Как | больше CPU/RAM на узле | больше узлов/реплик |
| Изменения в коде | обычно не нужны | stateless, внешние сессии, балансировка |
| Предел | максимальный размер машины | практически нет (упирается в общие ресурсы) |
| Отказоустойчивость | одна машина — SPOF | отказ одной реплики не критичен |
| Стоимость | большие машины дорожают нелинейно | много дешёвых узлов, но растут накладные расходы |
| Простой при изменении | часто нужен рестарт/миграция | добавление реплик без простоя |
| Консистентность данных | проще: одна база, один процесс | сложнее: репликация, шардирование, распределённые кэши |

**Когда вертикальное уместно:**

- базы данных — масштабировать PostgreSQL вертикально часто разумнее, чем шардировать;
- быстрое решение текущей проблемы, пока готовится архитектурное;
- stateful-компоненты, которые трудно распределить;
- рабочие нагрузки, требующие много памяти в одном процессе (большие in-memory вычисления).

**Когда горизонтальное:**

- stateless веб-сервисы и API — это основной способ масштабирования микросервисов;
- переменная нагрузка с автоскейлингом;
- требования к высокой доступности (минимум 2–3 реплики в разных зонах).

**Нюансы:**

- горизонтальное масштабирование приложения переносит нагрузку на общие компоненты: БД, пул соединений, кэш;
- закон Амдала: если часть работы последовательна (глобальная блокировка, один лидер), добавление узлов даёт убывающую отдачу;
- в Kubernetes оба вида есть в автоматическом варианте: HPA добавляет поды, VPA подбирает `requests`/`limits`.

На практике комбинируют: подбирают разумный размер реплики (правильно выставленные ресурсы) и масштабируют количество.

## Как обнаруживать падение сервиса?

```yaml
category: microservices
level: middle
difficulty: 3
slug: microservices-kak-obnaruzhivat-padenie-servisa
```

Падение сервиса обнаруживают на нескольких уровнях: платформа проверяет каждый экземпляр через health checks и перезапускает или исключает его из балансировки; мониторинг отслеживает метрики «золотых сигналов» и алертит по SLO; синтетические проверки имитируют пользователя снаружи; клиенты замечают отказы по таймаутам и ошибкам и реагируют через circuit breaker.

**1. Health checks экземпляров.** Kubernetes liveness/readiness probes, health check балансировщика. Экземпляр, не прошедший readiness, убирается из `Service`; не прошедший liveness — перезапускается. Это самовосстановление без участия человека.

**2. Метрики и алерты (golden signals из Google SRE):**

| Сигнал | Пример алерта |
| --- | --- |
| Latency | p99 > 1 с в течение 5 минут |
| Traffic | RPS упал до нуля (сервис «молчит» — тоже отказ) |
| Errors | доля 5xx > 2% |
| Saturation | CPU > 90%, очередь растёт, пул соединений исчерпан |

Лучше алертить по симптомам, влияющим на пользователя (error rate, latency, burn rate SLO), а не по каждой причине («CPU 80%»), — иначе будет шум.

**3. Внешний мониторинг (black-box).** Синтетические запросы извне кластера: проверка ключевых сценариев (логин, поиск, оформление) из нескольких регионов. Ловит то, что внутренние метрики не видят: DNS, сертификаты, сетевые проблемы, недоступный gateway.

**4. Отказы с точки зрения клиентов.** Circuit breaker'ы в вызывающих сервисах, метрики ошибок исходящих вызовов, распределённая трассировка — помогают быстро понять, кто в цепочке виноват.

**5. Мониторинг асинхронных компонентов.** Консьюмер может «быть живым», но не обрабатывать сообщения: алерты по lag'у консьюмеров Kafka, возрасту самого старого сообщения, росту DLQ, возрасту записей outbox.

**6. Heartbeat для фоновых задач.** Cron-джоба не вызывается снаружи — пусть она отправляет «я отработала» в мониторинг (dead man's switch), алерт, если сигнала нет.

**Частые ошибки:**

- health check проверяет только «процесс отвечает», а сервис при этом не может работать;
- алерт только на полный отказ, а частичная деградация (10% ошибок) остаётся незамеченной;
- мониторинг живёт в том же кластере и падает вместе с ним.

## Что такое health check?

```yaml
category: microservices
level: middle
difficulty: 2
slug: microservices-chto-takoe-health-check
tags: observability
```

Health check — эндпоинт или проверка, по которой внешняя система (оркестратор, балансировщик, мониторинг) узнаёт, может ли экземпляр сервиса нормально работать. По результату экземпляр перезапускают, выводят из балансировки или поднимают алерт.

**В ASP.NET Core** есть встроенный механизм health checks:

```csharp
builder.Services.AddHealthChecks()
    .AddCheck("self", () => HealthCheckResult.Healthy(), tags: ["live"])
    .AddNpgSql(connectionString, tags: ["ready"])      // пакет AspNetCore.HealthChecks.NpgSql
    .AddRedis(redisConnection, tags: ["ready"]);

app.MapHealthChecks("/health/live", new HealthCheckOptions
{
    Predicate = c => c.Tags.Contains("live")
});
app.MapHealthChecks("/health/ready", new HealthCheckOptions
{
    Predicate = c => c.Tags.Contains("ready")
});
```

Результат — `Healthy`, `Degraded` или `Unhealthy`; по умолчанию `Unhealthy` возвращает HTTP 503. Проверки для PostgreSQL, Redis, RabbitMQ, Kafka и т. д. есть в open-source пакетах `AspNetCore.HealthChecks.*`, свою проверку пишут, реализовав `IHealthCheck`.

**Что проверять:**

- сам процесс отвечает (liveness);
- обязательные зависимости доступны: БД, брокер (readiness);
- внутреннее состояние: прогрет ли кэш, прошли ли миграции, не застрял ли фоновый обработчик.

**Правила хорошего health check:**

- **быстрый и дешёвый** — вызывается каждые несколько секунд у каждой реплики; не делать тяжёлых запросов (достаточно `SELECT 1`), использовать таймаут;
- **не проверять транзитивно** соседние микросервисы в liveness: если сервис B лёг, перезапуск всех реплик A не поможет, а только усугубит ситуацию;
- **разделять liveness и readiness** — у них разный смысл и разная реакция;
- **не отдавать наружу подробности** (строки подключения, версии) — эндпоинт закрыть от публичного доступа или отдавать детали только внутренним клиентам;
- для графической панели есть `AspNetCore.HealthChecks.UI`, а результаты можно публиковать в метрики через `IHealthCheckPublisher`.

**Частая ошибка:** health check, который возвращает `200` всегда, пока процесс жив, — оркестратор отправляет трафик в экземпляр, который не может достучаться до БД.

## Liveness vs readiness?

```yaml
category: microservices
level: middle
difficulty: 3
slug: microservices-liveness-vs-readiness
tags: observability
```

Liveness отвечает на вопрос «жив ли процесс или его нужно перезапустить», readiness — «готов ли экземпляр принимать трафик прямо сейчас». В Kubernetes провал liveness приводит к перезапуску контейнера, провал readiness — к исключению пода из балансировки без перезапуска. Есть ещё startup probe — «закончил ли сервис запускаться».

| | Liveness | Readiness | Startup |
| --- | --- | --- | --- |
| Вопрос | процесс не завис? | можно слать запросы? | запуск завершён? |
| При провале | рестарт контейнера | под убирается из endpoints `Service` | рестарт после исчерпания попыток |
| Что проверять | только сам процесс: отвечает ли HTTP-стек, нет ли deadlock | зависимости, без которых сервис бесполезен, прогрев | то же, что liveness, но с большим бюджетом времени |
| Проверка внешних зависимостей | нет | да (осторожно) | нет |

**Пример для Kubernetes:**

```yaml
startupProbe:
  httpGet: { path: /health/live, port: 8080 }
  failureThreshold: 30
  periodSeconds: 2          # до 60 секунд на старт
livenessProbe:
  httpGet: { path: /health/live, port: 8080 }
  periodSeconds: 10
  failureThreshold: 3
readinessProbe:
  httpGet: { path: /health/ready, port: 8080 }
  periodSeconds: 5
  failureThreshold: 2
```

Пока startup probe не прошла, liveness и readiness не выполняются — это защищает медленно стартующие сервисы от преждевременного рестарта.

**Главная ошибка — проверять БД в liveness.** База недоступна → liveness всех реплик падает → Kubernetes перезапускает все поды → они стартуют, снова не видят БД, снова перезапускаются. Отказ БД превращается в отказ всего сервиса и шторм рестартов. Проблема не лечится перезапуском — значит, её не место в liveness.

**Осторожно и с readiness.** Если все реплики зависят от одной общей зависимости и она недоступна, все поды становятся not ready, и сервис перестаёт отвечать даже понятной ошибкой — клиенты получают отказ соединения. Иногда лучше остаться ready и возвращать быструю `503` или деградированный ответ. Проверять в readiness стоит то, что специфично для этого экземпляра.

**Graceful shutdown:** при остановке пода сервис должен перестать быть ready, дождаться завершения текущих запросов и только потом выйти. В ASP.NET Core это `HostOptions.ShutdownTimeout` и обработка `IHostApplicationLifetime.ApplicationStopping`; в k8s — согласовать с `terminationGracePeriodSeconds` и иногда добавить `preStop`-задержку, чтобы endpoints успели обновиться.

## Что такое observability?

```yaml
category: microservices
level: middle
difficulty: 2
slug: microservices-chto-takoe-observability
tags: observability
```

Observability (наблюдаемость) — свойство системы, позволяющее по её внешним сигналам понять, что происходит внутри, и ответить на вопросы, которые вы не предусмотрели заранее: «почему у клиентов из Казахстана медленно оформляется заказ с 14:05?». В микросервисах без неё отладка практически невозможна, потому что один запрос проходит через десяток процессов.

**Мониторинг vs observability.** Мониторинг отвечает на заранее известные вопросы (дашборды и алерты: «error rate выше 2%»). Observability — возможность исследовать неизвестные проблемы, комбинируя и детализируя данные по произвольным измерениям (эндпоинт, тенант, версия, регион).

**Три основных сигнала (three pillars):**

- **метрики** — агрегированные числа во времени: RPS, latency, ошибки, загрузка ресурсов;
- **логи** — события с контекстом: что произошло, с какими параметрами;
- **трассы** — путь конкретного запроса через все сервисы с временем каждого шага.

Иногда добавляют профилирование (continuous profiling) и события.

**Ключевое — корреляция.** Сигналы ценны, когда связаны: по всплеску latency на графике перейти к медленным трассам (exemplars), из трассы — к логам этого запроса по `TraceId`. Для этого все сигналы должны нести общий контекст.

**OpenTelemetry** — стандарт де-факто: единый API, SDK и протокол (OTLP) для метрик, логов и трасс, без привязки к вендору. В .NET:

```csharp
builder.Services.AddOpenTelemetry()
    .ConfigureResource(r => r.AddService("orders-api"))
    .WithTracing(t => t
        .AddAspNetCoreInstrumentation()
        .AddHttpClientInstrumentation()
        .AddOtlpExporter())
    .WithMetrics(m => m
        .AddAspNetCoreInstrumentation()
        .AddRuntimeInstrumentation()
        .AddOtlpExporter());
builder.Logging.AddOpenTelemetry(o => o.AddOtlpExporter());
```

.NET нативно использует `System.Diagnostics.Activity` для трасс и `System.Diagnostics.Metrics.Meter` для метрик — OpenTelemetry SDK просто собирает их и экспортирует.

**Бэкенды:** Prometheus + Grafana, Jaeger/Tempo, Loki/Elasticsearch, облачные (Azure Monitor/Application Insights), коммерческие APM (Datadog, New Relic).

**Практические вопросы:** стоимость хранения (сэмплирование трасс, retention логов), кардинальность меток в метриках (нельзя класть `userId` в label), единые имена сервисов и атрибутов (semantic conventions OpenTelemetry).

## Logs vs metrics vs traces?

```yaml
category: microservices
level: middle
difficulty: 3
slug: microservices-logs-vs-metrics-vs-traces
tags: observability
```

Это три вида телеметрии с разным назначением. **Метрики** — дешёвые агрегированные числа во времени, чтобы увидеть, *что* что-то не так, и алертить. **Трассы** показывают, *где* в цепочке сервисов проблема для конкретного запроса. **Логи** объясняют, *почему* — детальные события с контекстом.

| | Метрики | Логи | Трассы |
| --- | --- | --- | --- |
| Что это | числовые ряды: counter, gauge, histogram | дискретные события с сообщением и полями | дерево span'ов одного запроса через сервисы |
| Пример | `http_server_request_duration_seconds` p99 = 1,2 с | `Payment declined for order 42: insufficient funds` | запрос 1,2 с: gateway 5 мс → orders 40 мс → payments 1,1 с |
| Стоимость хранения | низкая, не зависит от трафика | высокая, растёт с трафиком | высокая, обычно сэмплируют |
| Кардинальность | должна быть низкой (метки: эндпоинт, статус) | произвольная | произвольная |
| Для чего | дашборды, алерты, SLO, тренды | расследование, аудит, ошибки | поиск узкого места, зависимостей, причины latency |
| Инструменты | Prometheus, Grafana, Azure Monitor | Loki, Elasticsearch/Kibana, Seq | Jaeger, Tempo, Zipkin, Application Insights |

**Типичный сценарий расследования:**

1. Алерт по метрике: error rate `/checkout` вырос до 8%.
2. Трассы проблемных запросов: ошибка возникает в вызове `payments → bank-gateway`, таймаут.
3. Логи `payments` по `TraceId` этих запросов: `SocketException: Connection refused` к новому адресу банка после изменения конфига.

**Метрики в .NET** — через `System.Diagnostics.Metrics`:

```csharp
var meter = new Meter("Orders");
var placed = meter.CreateCounter<long>("orders.placed");
placed.Add(1, new KeyValuePair<string, object?>("channel", "web"));
```

**Логи** должны быть структурированными (`ILogger` с шаблонами сообщений, а не интерполяцией), чтобы по полям можно было искать:

```csharp
logger.LogWarning("Payment declined for order {OrderId}: {Reason}", orderId, reason);
```

**Трассы** в .NET — `ActivitySource` и `Activity`; ASP.NET Core, `HttpClient`, gRPC, многие драйверы БД и MassTransit создают span'ы автоматически.

**Частые ошибки:**

- высокая кардинальность меток метрик (`userId`, `orderId` в label) — взрывной рост числа рядов;
- считать метрики по логам — дорого и неточно;
- логировать всё на уровне `Information` в горячем пути;
- отсутствие `TraceId` в логах — нельзя связать их с трассами (при использовании OpenTelemetry-логгера связывание происходит автоматически).

## Что такое distributed tracing?

```yaml
category: microservices
level: middle
difficulty: 2
slug: microservices-chto-takoe-distributed-tracing
```

Distributed tracing — это запись пути одного запроса через все сервисы в виде дерева span'ов: у каждого span'а есть имя операции, время начала и длительность, атрибуты и ссылка на родителя. Все span'ы одного запроса объединены общим `TraceId`, поэтому по нему видно, какой сервис и какой вызов съел время или вернул ошибку.

**Основные понятия:**

- **trace** — вся цепочка обработки одного внешнего запроса;
- **span** — одна операция внутри неё: входящий HTTP-запрос, вызов `HttpClient`, SQL-запрос, публикация сообщения;
- **span context** — `TraceId` + `SpanId` + флаги сэмплирования, то, что передаётся между процессами;
- **propagation** — передача контекста через границы процессов: в HTTP/gRPC-заголовках, в заголовках сообщений брокера.

**Как контекст едет по сети.** Стандарт — W3C Trace Context:

```text
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             версия-trace-id (16 байт)---------parent span id--флаги (01 = sampled)
```

Сервис-получатель читает заголовок, создаёт свой span с тем же `TraceId` и родителем из заголовка, а при исходящих вызовах пишет уже свой `SpanId`.

**В .NET** трассировка встроена в платформу: span — это `System.Diagnostics.Activity`, источник — `ActivitySource`. ASP.NET Core, `HttpClient`, gRPC, EF Core/Npgsql, MassTransit создают Activity сами; OpenTelemetry SDK их собирает и экспортирует по OTLP в Jaeger, Tempo, Zipkin или Application Insights. Свой span для бизнес-операции:

```csharp
private static readonly ActivitySource Source = new("Orders");

using var activity = Source.StartActivity("ReserveStock");
activity?.SetTag("order.id", orderId);
// ... если слушателя нет, activity == null, накладные расходы минимальны
```

Источник нужно зарегистрировать: `.WithTracing(t => t.AddSource("Orders"))`.

**Что даёт на практике:**

- видно критический путь запроса и последовательные вызовы, которые можно распараллелить;
- видно N+1 по сети (40 одинаковых вызовов `catalog` в одном запросе);
- автоматически строится карта зависимостей сервисов;
- из span'а можно перейти к логам этого запроса по `TraceId`.

**Сэмплирование.** Хранить все трассы дорого, поэтому сэмплируют: **head-based** — решение принимается в начале запроса (например, 10%) и передаётся дальше флагом в `traceparent`; **tail-based** — в OpenTelemetry Collector после завершения трассы, что позволяет сохранять все ошибочные и медленные трассы. Важно, чтобы сервисы уважали решение родителя (`ParentBased`-сэмплер), иначе трассы будут «дырявыми».

## Как передавать correlation ID между сервисами?

```yaml
category: microservices
level: middle
difficulty: 3
slug: microservices-kak-peredavat-correlation-id-mezhdu-servisami
tags: observability
```

Correlation ID — идентификатор, который присваивается запросу на входе в систему и передаётся во все последующие вызовы и сообщения, чтобы по нему найти все связанные логи. Сегодня базовый вариант — использовать `TraceId` из W3C `traceparent`: .NET и OpenTelemetry передают его автоматически. Отдельный заголовок вроде `X-Correlation-ID` нужен, когда ID должен жить дольше одной трассы или быть виден клиенту.

**Схема работы:**

1. Gateway или первый сервис берёт ID из входящего заголовка, а если его нет — генерирует.
2. ID кладётся в контекст запроса и в scope логгера — все логи получают поле `CorrelationId`.
3. Все исходящие HTTP/gRPC-вызовы добавляют заголовок.
4. Все публикуемые сообщения несут ID в своих заголовках; консьюмер восстанавливает его в свой контекст.
5. ID возвращается клиенту в ответе — поддержка может найти запрос по номеру из жалобы.

**Входящая сторона — middleware:**

```csharp
app.Use(async (ctx, next) =>
{
    var id = ctx.Request.Headers["X-Correlation-ID"].FirstOrDefault()
             ?? Activity.Current?.TraceId.ToString()
             ?? Guid.NewGuid().ToString("N");

    ctx.Response.Headers["X-Correlation-ID"] = id;
    using (logger.BeginScope(new Dictionary<string, object> { ["CorrelationId"] = id }))
        await next();
});
```

**Исходящие HTTP-вызовы** — пакет `Microsoft.AspNetCore.HeaderPropagation` копирует заголовки входящего запроса в исходящие:

```csharp
builder.Services.AddHeaderPropagation(o => o.Headers.Add("X-Correlation-ID"));
builder.Services.AddHttpClient<PaymentsClient>().AddHeaderPropagation();
app.UseHeaderPropagation();
```

Он работает только внутри HTTP-запроса. Для фоновых задач пишут свой `DelegatingHandler`, который берёт ID из `AsyncLocal`-контекста.

**Сообщения.** В MassTransit у сообщения есть `CorrelationId`, `ConversationId` (общий для всей цепочки сообщений, порождённых одним исходным) и `InitiatorId`; плюс он сам передаёт trace context. Для «голого» Kafka/RabbitMQ-клиента ID и `traceparent` нужно явно писать в заголовки сообщения и читать в консьюмере.

**Типичные ошибки:**

- ID теряется на асинхронной границе: запрос положил задачу в `Channel`/очередь, фоновый обработчик пишет логи без контекста — нужно сохранять ID вместе с задачей;
- каждый сервис генерирует свой ID вместо того, чтобы брать входящий;
- доверие к внешнему заголовку без валидации — ограничьте длину и формат, иначе в логи можно положить что угодно;
- дублирование двух систем: если есть OpenTelemetry, проще логировать `TraceId`/`SpanId` (OpenTelemetry-логгер и многие sink'и делают это автоматически) и не заводить отдельный ID без реальной причины.

**Correlation ID vs TraceId.** TraceId привязан к одной трассе; бизнес-процесс, растянутый на часы (Saga, повторные попытки из DLQ), может породить несколько трасс. Тогда полезен бизнесовый correlation ID (например, `OrderId`) или span links между трассами.

## Как обрабатывать повторные сообщения?

```yaml
category: microservices
level: middle
difficulty: 3
slug: microservices-kak-obrabatyvat-povtornye-soobscheniya
```

Повторные сообщения неизбежны: почти все брокеры и Outbox дают доставку at-least-once, поэтому задача не в том, чтобы дубли исключить, а в том, чтобы их обработка не меняла результат. Для этого консьюмер делают идемпотентным — естественно (операция сама по себе повторяемая), через дедупликацию по ID сообщения или через проверку версии/состояния.

**Откуда берутся дубли:**

- консьюмер обработал сообщение, но упал до `ack` — брокер доставит его снова;
- истёк visibility timeout / lock (SQS, Azure Service Bus), пока обработка ещё шла, — сообщение получил второй экземпляр;
- Outbox-relay опубликовал событие и упал до пометки «отправлено»;
- ребаланс consumer group в Kafka до коммита offset'а;
- продюсер повторил публикацию после таймаута подтверждения.

**Стратегии — от простой к сложной:**

| Стратегия | Как | Когда подходит |
| --- | --- | --- |
| Естественная идемпотентность | `SET status = 'Paid'`, upsert по ключу, «удалить, если есть» | операция описывает итоговое состояние, а не приращение |
| Уникальный бизнес-ключ | уникальный индекс на `payment_id`, `INSERT ... ON CONFLICT DO NOTHING` | сообщение создаёт сущность |
| Дедупликация по MessageId (Inbox) | таблица обработанных ID в той же транзакции | приращения: начислить бонус, списать остаток |
| Проверка версии | событие несёт версию агрегата, применять только `version = current + 1` | проекции и read-модели, где важен порядок |

**Пример естественной идемпотентности вместо приращения:**

```csharp
// плохо: повтор удвоит бонус
customer.Bonus += msg.Amount;

// хорошо: начисление — отдельная запись с уникальным ключом
db.BonusAccruals.Add(new BonusAccrual(msg.OrderId, customer.Id, msg.Amount));
await db.SaveChangesAsync(); // дубль упадёт на unique (OrderId) — ловим и считаем обработанным
```

**Побочные эффекты вне БД.** Отправку письма или вызов внешнего API нельзя включить в транзакцию. Варианты: передавать внешнему API idempotency key, производный от ID сообщения; фиксировать факт отправки до/после вызова и принять, что в редких случаях письмо уйдёт дважды.

**Смежные вещи, о которых спросят:**

- **retry и poison messages** — сообщение, которое падает всегда, после N попыток уходит в DLQ (в MassTransit — `_error`-очередь), иначе оно блокирует очередь;
- **порядок** — дубль может прийти после более нового сообщения; проверка версии или «последняя запись по времени события» защищает от отката состояния;
- **exactly-once в Kafka** работает только в пределах Kafka (транзакционный продюсер + read_committed); как только обработчик пишет во внешнюю БД, снова нужна идемпотентность.

## Как проектировать API между микросервисами?

```yaml
category: microservices
level: middle
difficulty: 3
slug: microservices-kak-proektirovat-api-mezhdu-mikroservisami
tags: microservices
```

Внутреннее API проектируют как публичный контракт: оно описывает бизнес-возможности сервиса, а не его таблицы, меняется только обратно совместимо и не требует от клиента знания внутренней модели. Главные цели — слабая связанность, предсказуемое поведение при сбоях и возможность деплоить сервисы независимо.

**Принципы:**

- **Контракт от потребителя, а не от схемы БД.** `POST /orders/{id}/cancel` лучше, чем `PATCH /orders/{id}` с `{ "status": 5 }`: сервис сохраняет инварианты у себя, клиенту не нужно знать допустимые переходы.
- **Не отдавать внутренние сущности.** Отдельные DTO; добавление колонки в таблицу не должно менять контракт.
- **Coarse-grained операции.** Если для одного экрана нужно 10 вызовов к одному сервису — API слишком «болтливое», каждая сетевая поездка добавляет задержку и точку отказа.
- **Идемпотентность.** Операции с побочными эффектами принимают idempotency key, чтобы клиент мог безопасно повторять.
- **Явная модель ошибок.** Единый формат (`ProblemDetails`, RFC 9457), различимые коды: 400/409/422 — не повторять, 503/429 — можно повторить.
- **Пагинация и лимиты** на всех списках — внутренний клиент тоже может запросить миллион строк.
- **Обратная совместимость** — поля только добавляются, клиенты игнорируют незнакомые (tolerant reader), обязательность новых полей не вводится.

**Синхронно или асинхронно.** Запрос-ответ (REST/gRPC) — когда вызывающему нужен результат прямо сейчас. Если сервис просто сообщает «что-то произошло», лучше событие: издатель не знает подписчиков, и отказ подписчика не ломает издателя. Цепочки синхронных вызовов `A → B → C → D` складывают задержки и перемножают вероятность отказа.

**REST или gRPC для внутреннего трафика:**

- gRPC — строгий контракт в `.proto`, генерация клиентов, бинарный формат, стриминг; хорошо для внутреннего «сервис-сервис»;
- REST + OpenAPI — проще отлаживать, лучше совместим с gateway и сторонними клиентами.

**Контракт как артефакт.** `.proto`-файлы или OpenAPI-спецификация лежат в репозитории, изменения проходят ревью и проверку на breaking changes (для protobuf — `buf breaking`, для OpenAPI — сравнение спецификаций в CI), а совместимость с реальными потребителями проверяют contract-тестами.

**Не забыть о нефункциональном:** таймауты и дедлайны (в gRPC дедлайн передаётся по цепочке), аутентификация сервис-сервис (mTLS или токены client credentials), rate limiting, корреляция и трассировка.

**Анти-паттерны:** общая NuGet-библиотека с доменными моделями для всех сервисов (скрытая связанность и синхронные релизы), «CRUD поверх таблиц», синхронный вызов в соседний сервис в каждом запросе ради данных, которые можно держать локальной копией по событиям.

## Как версионировать API?

```yaml
category: microservices
level: middle
difficulty: 3
slug: microservices-kak-versionirovat-api
```

Лучшая стратегия версионирования — как можно реже выпускать новую версию: большинство изменений делают обратно совместимыми (только добавление полей и эндпоинтов), а мажорную версию вводят лишь для настоящих breaking changes и какое-то время поддерживают старую и новую параллельно. Способ указания версии (URL, заголовок, query) вторичен — важнее правила совместимости и процесс вывода старых версий.

**Что ломает клиентов, а что нет:**

| Совместимо | Breaking change |
| --- | --- |
| новое необязательное поле в ответе | удаление или переименование поля |
| новый эндпоинт | смена типа поля (`int` → `string`) |
| новый необязательный параметр запроса | новое обязательное поле в запросе |
| новое значение enum — *если клиенты к этому готовы* | изменение смысла поля или кода ответа |

Совместимость держится на двух сторонах: сервер не удаляет и не меняет существующее, клиент игнорирует незнакомые поля (tolerant reader) и не падает на неизвестном значении enum.

**Способы передать версию:**

- **в URL** — `/api/v2/orders`: наглядно, легко маршрутизировать на gateway и кэшировать; самый распространённый вариант;
- **в заголовке** — `api-version: 2.0` или media type `application/vnd.shop.v2+json`: URL ресурса стабилен, но сложнее отлаживать из браузера;
- **в query** — `?api-version=2.0`: так делает Azure REST API.

**В ASP.NET Core** — пакеты `Asp.Versioning.Http` (minimal API) и `Asp.Versioning.Mvc`:

```csharp
builder.Services.AddApiVersioning(o =>
{
    o.DefaultApiVersion = new ApiVersion(1, 0);
    o.AssumeDefaultVersionWhenUnspecified = true;
    o.ReportApiVersions = true;   // заголовки api-supported-versions / api-deprecated-versions
    o.ApiVersionReader = ApiVersionReader.Combine(
        new UrlSegmentApiVersionReader(),
        new HeaderApiVersionReader("api-version"));
});
```

**gRPC/protobuf** версионируют иначе: поля идентифицируются номерами, поэтому добавление поля совместимо, удалённый номер помечают `reserved` и никогда не переиспользуют. Для несовместимых изменений заводят новый пакет: `shop.orders.v2`.

**Жизненный цикл версии:**

1. Выпустить v2 рядом с v1; v1 внутри по возможности реализовать как адаптер над v2, чтобы не дублировать логику.
2. Объявить v1 устаревшей: документация, заголовки `Deprecation`/`Sunset`.
3. Смотреть метрики: кто ещё вызывает v1 (по client id / имени сервиса).
4. Помочь последним потребителям мигрировать и удалить v1.

Для внутренних API между микросервисами последний шаг — самый важный: без метрик использования старые версии живут годами.

**Что спросят дальше:** как версионировать события (там нет «параллельного эндпоинта», сообщения лежат в очереди и в истории) и как ловить breaking changes до релиза — contract testing и автоматическая проверка спецификаций в CI.

## Как мигрировать монолит на микросервисы?

```yaml
category: microservices
level: middle
difficulty: 4
slug: microservices-kak-migrirovat-monolit-na-mikroservisy
tags: microservices
```

Монолит мигрируют постепенно, а не переписыванием с нуля: сервисы выделяют по одному вдоль бизнес-границ, трафик переключают на новый код через фасад (Strangler Fig), а монолит продолжает работать, пока из него не уйдёт последняя функция. Сначала стоит ответить на вопрос «зачем» — если проблема не в масштабировании команд или нагрузки, миграция может не окупиться.

**Порядок действий:**

1. **Сформулировать цель.** «Команды мешают друг другу в релизах», «каталог надо масштабировать отдельно», «модуль платежей требует отдельного compliance». Цель определяет, что выделять первым и как измерять успех.
2. **Подготовить инфраструктуру.** CI/CD на отдельный сервис, контейнеры, централизованные логи, трассировка, метрики, брокер сообщений. Без этого первый же сервис станет источником инцидентов.
3. **Навести границы внутри монолита.** Разложить код на модули по bounded context'ам, убрать прямые обращения к чужим таблицам и классам — получить модульный монолит. Этот шаг часто даёт большую часть пользы сам по себе.
4. **Выбрать первый сервис.** Слабо связанный, с понятной границей, не самый критичный: уведомления, поиск, отчёты. На нём команда отрабатывает деплой, мониторинг и интеграцию.
5. **Выделить сервис.** Новый код с собственной БД; монолит обращается к нему через API или события; перед монолитом ставится маршрутизатор (gateway, reverse proxy — например, YARP), который переводит нужные маршруты на новый сервис.
6. **Разделить данные.** Самая трудная часть: синхронизация через события или CDC на переходный период, затем отключение старых таблиц.
7. **Удалить старый код из монолита.** Без этого шага получается две реализации одной функции.
8. Повторить для следующего контекста.

**Почему не переписать всё сразу (big bang):** долгие месяцы без ценности для бизнеса, старая система продолжает меняться, новая догоняет «движущуюся цель», а переключение в один день — огромный риск. Пошаговая миграция поставляет результат после каждого сервиса и позволяет остановиться, когда цель достигнута.

**Типичные ошибки:**

- резать по техническим слоям (`UserService`, `DataService`) вместо бизнес-возможностей;
- оставить общую БД — сервисы формально отдельные, но любая миграция схемы ломает всех;
- синхронные цепочки вызовов вместо событий — распределённый монолит с сетевыми задержками;
- слишком мелкие сервисы в начале: границы ещё не устоялись, а переносить код между сервисами намного дороже, чем между модулями.

**Критерий успеха** — не число сервисов, а метрики: частота и независимость деплоев, lead time изменений, количество инцидентов.

## Что такое Strangler Fig Pattern?

```yaml
category: microservices
level: middle
difficulty: 2
slug: microservices-chto-takoe-strangler-fig-pattern
tags: microservices
```

Strangler Fig («фикус-душитель») — паттерн постепенной замены старой системы: перед ней ставится фасад, который принимает весь трафик, а функции по одной переносятся в новые сервисы, и фасад переключает соответствующие запросы на них. Старая система «усыхает», пока её не останется, и её можно выключить. Название — от тропического растения, которое обвивает дерево-хозяина и со временем полностью его заменяет (метафора Мартина Фаулера).

**Как это выглядит:**

```text
клиенты ──► фасад (gateway / reverse proxy)
              ├── /catalog/*     → catalog-service (новый)
              ├── /search/*      → search-service  (новый)
              └── всё остальное  → legacy-монолит
```

**Шаги для одной функции:**

1. Поставить фасад перед монолитом, пока ничего не меняя (весь трафик идёт в legacy).
2. Реализовать функцию в новом сервисе.
3. Переключить маршрут на новый сервис — сначала для части трафика или внутренних пользователей.
4. Убедиться, что всё работает (метрики, ошибки, сравнение результатов), и перевести 100%.
5. Удалить старую реализацию из монолита.

**Почему это работает:**

- риск маленький: каждое переключение обратимо — достаточно вернуть маршрут;
- ценность поставляется постепенно, а не через год;
- монолит продолжает работать и принимать правки, пока миграция идёт.

**Где разместить фасад.** Для HTTP — API Gateway или reverse proxy (в .NET — YARP, также nginx, Envoy, облачный gateway). Для внутренних вызовов — интерфейс внутри монолита, за которым прячут либо старый код, либо HTTP-клиент к новому сервису (branch by abstraction). Для событийных интеграций — перехват сообщений.

**Сложности:**

- **данные** — новому сервису нужны данные, которые ещё пишет монолит; обычно их синхронизируют событиями или CDC до тех пор, пока владение не перейдёт полностью;
- **общие сценарии** — одна пользовательская операция может затрагивать и старую, и новую часть; нужна интеграция между ними;
- **незавершённая миграция** — самая частая проблема: «последние 20%» не переносят годами, и приходится поддерживать обе системы.

Паттерн применим не только к микросервисам: так же заменяют старый фронтенд (по страницам) или legacy-API (по эндпоинтам).

## Как тестировать микросервисы?

```yaml
category: microservices
level: middle
difficulty: 3
slug: microservices-kak-testirovat-mikroservisy
tags: microservices
```

Микросервисы тестируют слоями: основная масса проверок — быстрые тесты внутри одного сервиса (unit и компонентные с реальной БД в контейнере), совместимость между сервисами проверяют contract-тестами, а дорогих end-to-end тестов через всю систему держат минимум — только для критичных пользовательских сценариев. Классическая пирамида сохраняется, но в середине появляется слой контрактов.

**Слои:**

| Уровень | Что проверяет | Инструменты в .NET |
| --- | --- | --- |
| Unit | доменная логика, агрегаты, расчёты | xUnit/NUnit, без инфраструктуры |
| Интеграционные / компонентные | сервис целиком: HTTP → логика → реальная БД/брокер; внешние сервисы заменены стабами | `WebApplicationFactory`, Testcontainers, WireMock.Net, MassTransit test harness |
| Contract | запросы потребителя совпадают с тем, что поддерживает провайдер | PactNet, проверка схем OpenAPI/protobuf в CI |
| End-to-end | ключевой сценарий через несколько реальных сервисов | стенд или .NET Aspire, Playwright |

**Компонентный тест — основная рабочая лошадка:**

```csharp
public class OrdersApiTests(OrdersApiFactory factory) : IClassFixture<OrdersApiFactory>
{
    [Fact]
    public async Task Place_order_returns_201()
    {
        var client = factory.CreateClient();
        var resp = await client.PostAsJsonAsync("/orders", new { ProductId = 1, Qty = 2 });
        Assert.Equal(HttpStatusCode.Created, resp.StatusCode);
    }
}

// OrdersApiFactory : WebApplicationFactory<Program>, IAsyncLifetime —
// поднимает PostgreSQL через Testcontainers и подменяет connection string,
// HTTP-клиент к Payments направляет на WireMock-заглушку.
```

Такой тест ловит ошибки маппинга, миграций, сериализации и конфигурации DI — то, что unit-тесты с моками пропускают. Реальная БД в контейнере вместо in-memory провайдера важна: EF Core InMemory не проверяет транзакции, ограничения и SQL-специфику.

**Почему e2e должно быть мало:** они медленные, нестабильные (любой сервис на стенде может быть сломан или в другой версии), сложно понять, кто виноват, и они возвращают связанность релизов — «нельзя выкатить, пока e2e не зелёные у всех».

**Что ещё тестируют в распределённой системе:**

- **асинхронные сценарии** — публикуется ли нужное событие, идемпотентен ли консьюмер на повторе (MassTransit `ITestHarness` позволяет проверить `Published<T>()` и `Consumed<T>()`);
- **отказы** — поведение при таймауте или 503 зависимости: WireMock с задержкой, fault injection; в проде — chaos engineering;
- **миграции** БД на копии реальной схемы;
- **после деплоя** — smoke-тесты и синтетические проверки, canary-релизы с автоматическим откатом по метрикам.

**Частый вопрос интервьюера:** «как проверить, что изменение в сервисе A не сломало B, не поднимая всю систему?» — ответ: contract testing плюс обратная совместимость контрактов.

## Что такое contract testing?

```yaml
category: microservices
level: middle
difficulty: 2
slug: microservices-chto-takoe-contract-testing
```

Contract testing — проверка того, что два сервиса понимают друг друга, без их совместного запуска: потребитель фиксирует, какие запросы он отправляет и какие поля ответа ему нужны, а провайдер в своём CI проверяет, что он этот контракт выполняет. Это заменяет большую часть хрупких end-to-end тестов для проверки совместимости.

**Consumer-driven contracts (подход Pact):**

1. **Потребитель** пишет тест против mock-сервера Pact: «на `GET /orders/42` я жду `200` и JSON с полями `id` и `status`». Тест проверяет клиентский код, а побочным продуктом получается pact-файл (JSON с описанием взаимодействий).
2. Pact-файл публикуется в **Pact Broker** (или PactFlow).
3. **Провайдер** в CI поднимает свой реальный сервис и прогоняет против него все запросы из контрактов своих потребителей, сравнивая ответы.
4. Перед деплоем `can-i-deploy` проверяет, совместима ли выкатываемая версия с версиями соседей, которые сейчас в этом окружении.

```csharp
// сторона потребителя (PactNet)
var pact = Pact.V3("basket-service", "orders-service", new PactConfig()).WithHttpInteractions();

pact.UponReceiving("get order")
    .Given("order 42 exists")                 // provider state
    .WithRequest(HttpMethod.Get, "/orders/42")
    .WillRespond()
    .WithStatus(HttpStatusCode.OK)
    .WithJsonBody(new { id = Match.Type(42), status = Match.Type("Paid") });

await pact.VerifyAsync(async ctx =>
{
    var client = new OrdersClient(new HttpClient { BaseAddress = ctx.MockServerUri });
    var order = await client.GetAsync(42);
    Assert.Equal("Paid", order.Status);
});
```

`Match.Type` означает «любое значение этого типа» — контракт не должен требовать конкретных данных, иначе он хрупкий. `Given(...)` — provider state: провайдер перед проверкой готовит нужные данные.

**Главная ценность:** провайдер точно знает, какие поля реально используют потребители. Поле, которое никто не читает, можно удалить; поле из контракта — нельзя, CI провайдера упадёт до релиза, а не в проде.

**Чем не является:** это не функциональный тест провайдера (бизнес-логику проверяют его собственные тесты) и не проверка производительности. Контракт проверяет форму и смысл взаимодействия.

**Альтернативы и дополнения:**

- **provider-driven / schema-based** — провайдер публикует OpenAPI или `.proto`, а CI проверяет изменения на обратную совместимость (`buf breaking`, сравнение OpenAPI-спецификаций);
- **контракты сообщений** — Pact поддерживает message pacts для асинхронных взаимодействий; альтернатива — schema registry (Avro/Protobuf/JSON Schema) с правилами совместимости.

**Ограничения:** нужен процесс — потребители должны писать тесты, провайдер обязан их проверять, брокер нужно поддерживать. При 2–3 сервисах одной команды это может быть избыточно.

## Как обеспечить отказоустойчивость микросервисной системы?

```yaml
category: microservices
level: middle
difficulty: 4
slug: microservices-kak-obespechit-otkazoustoichivost-mikroservisnoi-sistemy
tags: resilience, microservices
```

Отказоустойчивость строится из предположения, что любая зависимость может в любой момент тормозить или падать. Задача — не допустить каскада: локализовать отказ (таймауты, bulkhead, circuit breaker), корректно повторять временные сбои (retry с идемпотентностью), деградировать вместо полного отказа (fallback, асинхронность) и иметь избыточность на уровне инфраструктуры (несколько реплик, зон, автоматический перезапуск).

**Уровень вызова (код сервиса):**

- **таймаут на каждом сетевом вызове** — зависание хуже ошибки: оно держит потоки, соединения и память;
- **retry** только для transient-ошибок, с backoff и jitter, в пределах общего бюджета времени;
- **circuit breaker** — перестать бить в упавшую зависимость и сразу отдавать отказ/fallback;
- **bulkhead / ограничение конкурентности** — медленная зависимость не должна забрать все ресурсы сервиса;
- **идемпотентность** операций — без неё retry небезопасен.

В .NET всё это даёт `Microsoft.Extensions.Http.Resilience`:

```csharp
builder.Services.AddHttpClient<InventoryClient>()
    .AddStandardResilienceHandler(); // rate limiter, total timeout, retry, circuit breaker, attempt timeout
```

**Уровень архитектуры:**

- **асинхронность там, где можно.** Заказ принимается и сохраняется, а уведомление, начисление бонусов, аналитика идут через брокер — их отказ не мешает оформлению;
- **graceful degradation** — без рекомендаций страница товара работает, без сервиса отзывов — показывается «отзывы временно недоступны»; нужно заранее решить, какие зависимости критичны;
- **локальные копии данных** — сервис хранит нужные справочники по событиям, а не запрашивает их синхронно в каждом запросе;
- **нет общих точек отказа** — общая БД, единый Redis «на всех», один брокер без кластера;
- **load shedding и rate limiting** — при перегрузке лучше быстро отказать части запросов (`429`/`503`), чем медленно обслуживать всех.

**Уровень инфраструктуры:**

- несколько реплик каждого сервиса в разных зонах доступности, `PodDisruptionBudget`;
- health checks: liveness для перезапуска зависших, readiness для вывода из балансировки;
- автомасштабирование, резерв мощности;
- кластер брокера и реплики БД с автоматическим failover;
- безопасные релизы: rolling/canary, быстрый откат, feature flags.

**Проверка и эксплуатация:**

- SLO и алерты по пользовательским симптомам (ошибки и latency), а не только по CPU;
- chaos engineering и game days — намеренно убивать поды, вносить задержки, проверять, что деградация идёт по плану;
- runbook'и и постмортемы.

**Типичные ловушки:** retry на каждом уровне цепочки (усиление нагрузки в разы — retry storm), таймауты вызывающего короче, чем у вызываемого, «вечные» очереди без DLQ, fallback, который сам ходит в ту же упавшую зависимость.

## Как определить границы сервисов через DDD и какие признаки говорят об ошибке?

```yaml
category: microservices
level: senior
difficulty: 5
slug: microservices-advanced-kak-opredelit-granicy-servisov-cherez-ddd-i-kakie-priznaki-govoryat-ob
tags: ddd, architecture
```

Через DDD границы ищут сверху вниз: сначала разбивают домен на поддомены (что делает бизнес), затем находят bounded context'ы (где у модели и языка одно значение), внутри них — агрегаты (где проходят транзакционные инварианты). Сервис обычно равен одному bounded context'у или его части, но никогда не пересекает несколько контекстов. Об ошибке говорят не диаграммы, а поведение системы: изменения, релизы и транзакции, которые постоянно пересекают границу.

**Три уровня и что каждый решает:**

| Уровень | Вопрос | Влияние на сервисы |
| --- | --- | --- |
| Поддомен (core / supporting / generic) | куда вкладываться | core — своими силами и тщательно; generic (биллинг, auth, email) — купить или взять готовое, не писать свой сервис |
| Bounded context | где модель однозначна | кандидат на границу сервиса и владения данными |
| Агрегат | что должно меняться атомарно | не может быть разрезан между сервисами |

Поддомен — это пространство задачи, контекст — пространство решения. Они часто совпадают, но не обязаны: один legacy-контекст может покрывать несколько поддоменов, и это само по себе подсказка, где резать.

**Как находить на практике:**

- **Event Storming** — выписать доменные события на временной линии и найти *pivotal events* («Заказ оформлен», «Отгружено»): вокруг них часто меняется язык, ответственные люди и данные — там граница.
- **Язык** — где эксперты начинают спорить о значении термина или используют разные слова для одного, там стык контекстов.
- **Инварианты** — «сумма резервов не больше остатка» должна проверяться атомарно, значит, резерв и остаток в одном агрегате и одном сервисе. Инвариант между сервисами — это Saga и eventual consistency; если бизнес на это не согласен, граница неверна.
- **Автономия решений** — хорошая граница позволяет сервису принять решение по своим данным, не спрашивая соседей синхронно.
- **Команды** — один контекст принадлежит одной команде; контекст, который делят три команды, не станет независимым сервисом.

**Признаки ошибочной границы (измеримые):**

- **change coupling** — анализ истории git: сервисы A и B меняются в одних и тех же PR/релизах в большинстве случаев;
- **deployment coupling** — релиз требует координированного выката нескольких сервисов в определённом порядке;
- **chatty-взаимодействие** — один пользовательский запрос порождает десятки синхронных вызовов соседа; сервис бесполезен, если сосед недоступен;
- **распределённые транзакции в обычных сценариях** — компенсации нужны не для редких бизнес-исключений, а в каждом втором потоке;
- **общая таблица или общая доменная библиотека** — модели обоих сервисов на самом деле одна модель;
- **anemic entity services** — `CustomerService` с CRUD, а правила живут в «оркестраторах» над ним; поведение отделено от данных;
- **события-репликация** — `CustomerUpdated` с полным снимком из 60 полей, который все копируют: сервисы делят модель, а не обмениваются фактами;
- **сервис-«бог»** — все обращаются к нему, и он меняется в каждой фиче.

**Что делать при ошибке.** Склеить сервисы обратно — нормальное решение, а не поражение: объединение двух сильно связанных сервисов обычно дешевле, чем бесконечная координация. Поэтому стартуют с крупных контекстов (или модульного монолита) и режут дальше, только когда граница подтверждена данными о реальных изменениях.

**Что спросят дальше:** как быть с сущностью, которая нужна всем (`Customer`, `Product`) — ответ: у каждого контекста своя модель, общим остаётся идентификатор, а владелец публикует события о значимых фактах.

## Что такое bounded context и почему одна сущность может по-разному выглядеть в разных сервисах?

```yaml
category: microservices
level: senior
difficulty: 4
slug: microservices-advanced-chto-takoe-bounded-context-i-pochemu-odna-suschnost-mozhet-po-raznomu
tags: ddd, architecture
```

Bounded context — граница, внутри которой модель и язык однозначны. Одна «сущность» выглядит в разных сервисах по-разному, потому что модель — это не описание реального мира, а инструмент для решения конкретной задачи: у продаж, склада и бухгалтерии разные задачи, значит, им нужны разные атрибуты, правила и жизненные циклы. Общим у представлений остаётся только идентичность — один и тот же `CustomerId`.

**Пример: «Клиент».**

```csharp
// Sales: кто и на каких условиях покупает
public class Customer
{
    public CustomerId Id { get; }
    public CustomerTier Tier { get; private set; }
    public Money CreditLimit { get; private set; }
    public void Upgrade(...) { ... }            // правила продаж
}

// Shipping: куда и как доставлять — здесь это «Получатель»
public record Recipient(CustomerId Id, string Name, Address Address, string Phone);

// Billing: кому выставлять счета — «Плательщик»
public class Payer
{
    public CustomerId Id { get; }
    public string TaxId { get; }
    public PaymentTerms Terms { get; }
}
```

Названия тоже могут различаться: язык каждого контекста остаётся точным, и слово «клиент» не приходится уточнять в каждой фразе.

**Почему единая модель хуже:**

- класс `Customer` на 80 полей, у которого у каждой команды свои правила валидации и свой смысл полей — любое изменение требует согласования всех;
- инварианты конфликтуют: для продаж клиент без адреса валиден, для доставки нет;
- жизненные циклы разные: заблокированный в продажах клиент всё ещё должен получить уже оплаченный заказ;
- «канонические модели данных» в масштабе предприятия исторически проваливаются по тем же причинам.

**Как контексты согласуются:**

- **один владелец факта.** Имя и контакты меняются в контексте «Профиль», адрес доставки — там, где его вводят. Остальные хранят копии нужных им полей, обновляемые событиями;
- **события несут бизнес-смысл, а не снимок таблицы:** `CustomerRelocated { CustomerId, NewAddress }` вместо `CustomerUpdated` со всеми полями — подписчик сам решает, что ему из этого нужно;
- **Anti-Corruption Layer** — переводчик на входе, чтобы чужая модель не проникала в свою:

```csharp
public sealed class CrmCustomerTranslator
{
    public Recipient ToRecipient(CrmContactDto dto) =>
        new(new CustomerId(dto.ExternalId),
            $"{dto.FirstName} {dto.LastName}".Trim(),
            Address.Parse(dto.DeliveryAddr ?? dto.LegalAddr),
            PhoneNumber.Normalize(dto.Phones.FirstOrDefault()));
}
```

- **Shared Kernel** — небольшая общая часть модели (например, `Money`, `CustomerId`), которую сознательно делят две команды; допустимо, но это прямая связанность, её держат минимальной.

**Частые ошибки:**

- «сервис сущности» `CustomerService`, в который все ходят синхронно за любым полем — единая модель, просто по сети;
- общая NuGet-библиотека с доменными классами для всех сервисов;
- путать bounded context с микросервисом: контекст — граница модели; внутри него может быть несколько деплойных единиц, но одна единица не должна смешивать несколько контекстов.

**На что смотрит интервьюер:** понимаете ли вы, что дублирование данных между контекстами — это нормальная цена автономии, и можете ли назвать владельца каждого атрибута и механизм, которым изменение доходит до остальных.

## Как реализовать Saga и в чём практическая разница между хореографией и оркестрацией?

```yaml
category: microservices
level: senior
difficulty: 5
slug: microservices-advanced-kak-realizovat-saga-i-v-chem-prakticheskaya-raznica-mezhdu-horeografie
tags: saga, consistency
```

Saga реализуют как последовательность локальных транзакций, каждая из которых атомарно меняет данные своего сервиса и публикует событие через Outbox; при отказе на шаге выполняются компенсации уже сделанных шагов. Практическая разница между хореографией и оркестрацией проявляется не на схеме, а в эксплуатации: где хранится состояние процесса, кто замечает зависание, как меняется процесс, пока в нём «висят» тысячи экземпляров, и как отвечать на вопрос «почему заказ 42 застрял».

**Обязательный фундамент для любого варианта:**

- каждый шаг — локальная транзакция + Outbox (иначе событие теряется и saga зависает);
- каждый обработчик идемпотентен (Inbox или естественная идемпотентность);
- у каждого экземпляра есть correlation ID (обычно `OrderId`);
- шаги классифицируются: **compensatable** (можно отменить), **pivot** (точка невозврата — после неё только вперёд), **retriable** (после pivot, должны гарантированно завершиться повторами). Хороший дизайн ставит рискованные и необратимые шаги как можно позже.

**Оркестрация на MassTransit (state machine):**

```csharp
public class OrderStateMachine : MassTransitStateMachine<OrderState>
{
    public State Reserving { get; private set; } = null!;
    public State Charging  { get; private set; } = null!;
    public Event<OrderSubmitted> Submitted { get; private set; } = null!;
    public Event<StockReserved>  Reserved  { get; private set; } = null!;
    public Event<PaymentFailed>  Failed    { get; private set; } = null!;
    public Event<PaymentCaptured> Captured { get; private set; } = null!;

    public OrderStateMachine()
    {
        InstanceState(x => x.CurrentState);
        Event(() => Submitted, e => e.CorrelateById(m => m.Message.OrderId));
        // ... корреляция остальных событий по OrderId

        Initially(When(Submitted)
            .Publish(ctx => new ReserveStock(ctx.Saga.CorrelationId))
            .TransitionTo(Reserving));

        During(Reserving, When(Reserved)
            .Publish(ctx => new CapturePayment(ctx.Saga.CorrelationId))
            .TransitionTo(Charging));

        During(Charging,
            When(Captured).Finalize(),
            When(Failed)
                .Publish(ctx => new ReleaseStock(ctx.Saga.CorrelationId))
                .Publish(ctx => new CancelOrder(ctx.Saga.CorrelationId))
                .Finalize());
    }
}
```

Состояние хранится в БД (`EntityFrameworkRepository` с optimistic concurrency — два события одного заказа могут прийти параллельно). Таймауты — через `Schedule(...)`: если `PaymentCaptured` не пришёл за 15 минут, оркестратор сам запускает компенсацию. Для процессов на дни и недели с сложной логикой повторов рассматривают workflow-движки (Temporal, Azure Durable Functions).

**Хореография** — обычные консьюмеры: Inventory слушает `OrderSubmitted` и публикует `StockReserved`, Payments слушает `StockReserved` и т. д. Кода меньше, центральной точки нет, но состояние процесса нигде явно не хранится.

**Практические различия:**

| Вопрос | Хореография | Оркестрация |
| --- | --- | --- |
| «Где застрял заказ 42?» | собирать по трассам и логам нескольких сервисов | одна строка в таблице состояния saga |
| Кто замечает, что ответа нет | никто, если специально не сделать «сторожа» | таймаут в state machine |
| Изменение процесса | правка нескольких сервисов разных команд, согласованный релиз | правка одного оркестратора |
| Экземпляры «в полёте» при изменении | события старого формата должны обрабатываться новыми подписчиками | новая версия машины должна уметь продолжить старые состояния; иногда держат обе версии до завершения старых экземпляров |
| Тестирование | только интеграционно, процесс нигде не описан целиком | state machine тестируется изолированно (MassTransit test harness) |
| Связанность | через события, издатель не знает подписчиков | оркестратор знает всех участников и их команды |
| Циклы событий | реальный риск | исключены конструкцией |

**Отсутствие изоляции** — главный скрытый риск любой saga. Контрмеры: *semantic lock* (статус `Pending` блокирует конфликтующие операции над заказом), коммутативные операции (резерв/снятие резерва в любом порядке дают верный остаток), перечитывание значения перед pivot-шагом, версионирование.

**Мониторинг:** число экземпляров в каждом состоянии, возраст самых старых незавершённых, доля компенсаций — рост последней часто первым сигнализирует о проблеме у участника.

**Рекомендация на собеседовании:** хореография — для коротких реакций на события между доменами; оркестрация — когда процесс имеет бизнес-владельца, SLA, ветвления и компенсации.

## Как проектировать компенсирующие транзакции, если откат физически невозможен?

```yaml
category: microservices
level: senior
difficulty: 5
slug: microservices-advanced-kak-proektirovat-kompensiruyuschie-tranzakcii-esli-otkat-fizicheski-ne
tags: saga, consistency
```

Компенсация — это не откат, а новая бизнес-операция, которая семантически отменяет эффект: письмо нельзя «отозвать», но можно отправить уточнение; списание с карты нельзя «откатить», но можно сделать refund. Поэтому компенсации проектируют вместе с бизнесом как часть процесса, а необратимые шаги переносят как можно ближе к концу saga — после них остаются только шаги, которые гарантированно доводятся повторами.

**Классификация шагов — с неё начинается дизайн:**

| Тип шага | Пример | Как обращаться |
| --- | --- | --- |
| Compensatable | резерв товара, hold денег на карте | есть явная обратная операция: release, void |
| Pivot (точка невозврата) | capture платежа, отгрузка со склада | после него saga только идёт вперёд |
| Retriable | начисление бонусов, отправка уведомления | должен завершиться, повторяется до успеха |
| Необратимый побочный эффект | email, SMS, вызов партнёра без отмены | выполняется последним или компенсируется «корректирующим» действием |

**Приёмы, когда прямой отмены нет:**

- **Двухфазность в домене.** Вместо «списать» — «заблокировать» (authorize/hold), а списание (capture) делать только после успеха всех рискованных шагов. Так же со складом: резерв вместо списания, отгрузка в самом конце.
- **Перенос необратимого в конец.** Письмо «заказ оформлен» отправляется по событию `OrderConfirmed`, а не после первого шага.
- **Семантическая компенсация.** Refund вместо отмены платежа, сторнирующая проводка вместо удаления записи в бухгалтерии, письмо «заказ отменён» вместо «отзыва» первого письма.
- **Компенсация с потерями.** Отмену авиабилета партнёр делает со штрафом — это нормальный исход, его фиксируют и показывают пользователю, а не прячут.
- **Ручная обработка.** Если автоматическая компенсация невозможна или не удалась, saga переходит в состояние `RequiresAttention` и создаёт задачу оператору. Это тоже часть дизайна, а не авария.

**Требования к самой компенсации:**

- **идемпотентна** — команда `RefundPayment` может прийти дважды; ключ идемпотентности — `PaymentId` или `SagaId + Step`;
- **коммутативна с прямым шагом** — компенсация может прийти раньше, чем сам шаг (сообщения перемешались или шаг ещё ретраится). Участник должен запомнить «отменено» и отклонить запоздалый прямой шаг:

```csharp
public async Task Handle(ReleaseStock cmd)
{
    var r = await db.Reservations.FindAsync(cmd.OrderId);
    if (r is null)
    {
        db.Reservations.Add(Reservation.Cancelled(cmd.OrderId));
    }
    else
    {
        r.Cancel();
    }
    await db.SaveChangesAsync();
}

public async Task Handle(ReserveStock cmd)
{
    var r = await db.Reservations.FindAsync(cmd.OrderId);
    if (r is { Status: ReservationStatus.Cancelled })
        return;
    ...
}
```

- **не может «упасть окончательно»** — ретраится с backoff, а после исчерпания попыток уходит в ручную обработку, не в тишину;
- **работает с текущим состоянием**, а не с «откатом к снимку»: за время saga данные могли поменять другие операции (отсутствие изоляции), поэтому компенсация резерва — `+N` к остатку, а не «вернуть остаток к прежнему значению».

**Что важно для пользователя и аудита.** Компенсация видна: в истории заказа остаются и списание, и возврат. Это нормальная модель для финансов и логистики — бухгалтерия так работает веками.

**Что спрашивают дальше:** где хранить информацию о том, какие шаги уже выполнены (в состоянии оркестратора), что делать, если компенсация сама требует подтверждения внешней системы (это отдельная мини-saga с таймаутом), и как объяснить бизнесу состояние «отменено частично».

## Как работает Outbox и почему без него возможна потеря события?

```yaml
category: microservices
level: senior
difficulty: 4
slug: microservices-advanced-kak-rabotaet-outbox-i-pochemu-bez-nego-vozmozhna-poterya-sobytiya
tags: outbox, consistency
```

Outbox решает проблему двойной записи: сервис должен и изменить свою БД, и опубликовать событие в брокер, а общей транзакции у них нет. Событие записывается в таблицу `outbox` той же локальной транзакцией, что и бизнес-данные, а отдельный процесс (relay) потом читает таблицу и публикует события в брокер. Либо сохраняется всё, либо ничего, а доставка становится at-least-once.

**Почему без Outbox событие теряется:**

```csharp
await db.SaveChangesAsync();
await bus.Publish(new OrderPlaced(order.Id));
```

- процесс упал, pod убили при деплое или брокер недоступен между двумя строками — заказ есть, события нет, saga никогда не стартует;
- поменять порядок не помогает: опубликовали, а `SaveChanges` упал на constraint — подписчики обрабатывают заказ, которого не существует;
- retry вокруг `Publish` не спасает от падения процесса, а Kafka-транзакции не включают в себя БД.

**Как устроено:**

1. В транзакции: `INSERT INTO orders ...` + `INSERT INTO outbox (id, aggregate_id, type, payload, created_at)`.
2. Relay забирает неотправленные записи по порядку, публикует, помечает отправленными (или удаляет).
3. Если relay упал после публикации, но до пометки, событие уйдёт повторно — поэтому консьюмеры обязаны быть идемпотентными (Inbox).

**Два способа доставки из таблицы:**

| | Polling publisher | CDC (Debezium) |
| --- | --- | --- |
| Механизм | фоновая задача читает `outbox` раз в N мс | чтение WAL/binlog, Outbox Event Router |
| Задержка | интервал опроса | доли секунды |
| Нагрузка на БД | постоянные запросы, блокировки, очистка таблицы | чтение лога репликации |
| Инфраструктура | ничего нового | Kafka Connect, replication slot, его мониторинг |

**В .NET** обычно не пишут вручную — MassTransit транзакционный outbox для EF Core:

```csharp
services.AddMassTransit(x =>
{
    x.AddEntityFrameworkOutbox<OrdersDbContext>(o =>
    {
        o.UsePostgres();
        o.UseBusOutbox();
    });
    x.UsingRabbitMq((ctx, cfg) => cfg.ConfigureEndpoints(ctx));
});
```

После этого `IPublishEndpoint.Publish` внутри scope с `DbContext` пишет сообщение в таблицы outbox, и оно сохраняется тем же `SaveChangesAsync`, а фоновый delivery service отправляет его в брокер.

**Подводные камни:**

- **Порядок.** Несколько экземпляров relay с `FOR UPDATE SKIP LOCKED` масштабируются, но могут перемешать события одного агрегата. Если порядок важен — один активный relay (leader election) или распределение по `aggregate_id`; в Kafka ключом сообщения делают `aggregate_id`.
- **Рост таблицы.** Отправленные записи нужно чистить, иначе опрос деградирует; для PostgreSQL помогают частичный индекс по неотправленным и партиционирование по времени.
- **Задержка ≠ 0.** Событие появляется в брокере позже коммита; read-your-writes через события не получится.
- **«Ядовитое» событие** (не сериализуется, превышает лимит размера) блокирует очередь relay — нужен счётчик попыток и отдельный статус.
- **Схема payload.** В таблице лежит уже сериализованный контракт — его версия должна быть зафиксирована в момент записи.

**Что спрашивают дальше:** чем Outbox отличается от Inbox (тот защищает приём), как гарантировать порядок при нескольких relay, почему CDC прямо из бизнес-таблиц хуже, чем из outbox (наружу утекает внутренняя схема БД вместо контракта).

## Зачем нужен Inbox и как он защищает от повторной обработки?

```yaml
category: microservices
level: senior
difficulty: 4
slug: microservices-advanced-zachem-nuzhen-inbox-i-kak-on-zaschischaet-ot-povtornoi-obrabotki
tags: inbox, idempotency
```

Брокеры и Outbox дают at-least-once: одно и то же сообщение может прийти повторно — после падения consumer'а между обработкой и ack, после rebalance в Kafka, после повторной отправки relay'ем. Inbox делает обработку идемпотентной: ID сообщения записывается в таблицу `inbox` в той же транзакции, что и бизнес-изменения, и повтор с тем же ID распознаётся и пропускается. В сочетании с Outbox это даёт эффективно exactly-once обработку в пределах БД сервиса.

**Механизм:**

```sql
CREATE TABLE inbox (
    message_id  uuid        NOT NULL,
    consumer    text        NOT NULL,
    processed_at timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (message_id, consumer)
);
```

```csharp
public async Task Handle(PaymentCaptured msg, Guid messageId, CancellationToken ct)
{
    await using var tx = await db.Database.BeginTransactionAsync(ct);

    var inserted = await db.Database.ExecuteSqlInterpolatedAsync($"""
        INSERT INTO inbox (message_id, consumer)
        VALUES ({messageId}, 'billing.payment-captured')
        ON CONFLICT DO NOTHING
        """, ct);

    if (inserted == 0)
        return;

    var order = await db.Orders.FindAsync([msg.OrderId], ct);
    order!.MarkPaid(msg.Amount);
    await db.SaveChangesAsync(ct);
    await tx.CommitAsync(ct);
}
```

Если два экземпляра одновременно получили один и тот же ID, второй `INSERT` ждёт на блокировке уникального индекса до коммита первого и получает 0 строк. Если обработка упала — откатывается и запись в inbox, повтор пройдёт заново.

**Ключевые условия:**

- **Одна транзакция** с бизнес-данными. Inbox в Redis, а данные в PostgreSQL — снова двойная запись: отметка есть, изменений нет, или наоборот.
- **Стабильный ID** от отправителя — ID записи outbox или явный `MessageId`, а не GUID, сгенерированный при получении. Offset Kafka подходит только пока сообщение не переложено в retry-топик или другой топик.
- **Колонка `consumer`** нужна, если несколько обработчиков в одном сервисе получают одно и то же событие.
- **Очистка.** Записи хранят дольше максимального окна повторной доставки (retention топика, время жизни DLQ, ручной replay), потом удаляют фоновой задачей.

**Чего Inbox не покрывает:**

- **внешние побочные эффекты** — HTTP-вызов платёжки или отправка email внутри обработчика не откатятся вместе с транзакцией. Их выносят в Outbox (команда «отправить письмо» как сообщение) или передают внешней системе idempotency key;
- **порядок** — Inbox отсекает дубли, но не переупорядочивание; для этого нужна версия агрегата;
- **replay** — при осознанной переобработке истории inbox придётся очистить или использовать другое имя consumer'а.

**Альтернатива — естественная идемпотентность.** Если операция по природе повторяема (`UPSERT` по ключу, «установить статус Paid, если версия меньше N»), отдельная таблица не нужна. Inbox нужен, когда операция не идемпотентна: «прибавить к балансу», «создать запись».

**В MassTransit** транзакционный outbox для EF Core включает и inbox: при `UseEntityFrameworkOutbox<TDbContext>(context)` на receive endpoint состояние полученных сообщений хранится в таблице `InboxState`, а дубликаты в пределах `DuplicateDetectionWindow` отбрасываются.

**Что спрашивают дальше:** почему нельзя проверить «был ли ID» отдельным `SELECT` до обработки (гонка между двумя экземплярами), как быть с консьюмером, который пишет в несколько БД, и чем Inbox отличается от идемпотентного producer'а Kafka (тот защищает от дублей только при записи в лог).

## Когда CQRS оправдан и какую сложность он приносит?

```yaml
category: microservices
level: senior
difficulty: 5
slug: microservices-advanced-kogda-cqrs-opravdan-i-kakuyu-slozhnost-on-prinosit
tags: cqrs, architecture
```

CQRS оправдан, когда модели записи и чтения действительно расходятся: сложные инварианты на запись и совершенно другие по форме запросы на чтение (поиск, агрегаты, денормализованные экраны), или нагрузка на чтение на порядки выше и требует отдельного хранилища. Цена — две модели вместо одной, механизм синхронизации и eventual consistency, которую видит пользователь. Для CRUD-сервиса это чистый overhead.

**Уровни CQRS — путают постоянно:**

| Уровень | Что разделено | Сложность |
| --- | --- | --- |
| Разделение кода | команды и запросы — разные обработчики (MediatR-стиль), одна БД, одна схема | почти бесплатно |
| Разные модели, одна БД | запись через агрегаты EF Core, чтение — Dapper/SQL по view или денормализованным таблицам, обновляемым в той же транзакции | умеренная, консистентность сильная |
| Отдельное хранилище чтения | PostgreSQL для записи, Elasticsearch/Redis/отдельная реплика для чтения, синхронизация событиями | высокая, eventual consistency |
| CQRS + Event Sourcing | запись — поток событий, чтение — проекции | максимальная |

Большинству систем хватает первых двух уровней. Когда на собеседовании говорят «внедрили CQRS», полезно уточнить, какой именно.

**Когда оправдан (особенно третий уровень):**

- чтение на порядки чаще записи и требует другой формы данных: каталог с полнотекстовым поиском и фасетами, ленты, дашборды;
- запрос собирает данные из нескольких агрегатов или сервисов — проекция заранее собирает их в одну таблицу вместо join'ов по сети;
- модель записи богатая (инварианты, состояние), а экраны требуют плоских DTO — одна модель тянется в обе стороны и портится;
- разные требования к масштабированию и доступности: чтение должно жить, даже если запись деградировала.

**Какую сложность приносит:**

- **Задержка синхронизации.** Пользователь сохранил и не видит изменения в списке — нужно проектировать UX и read-your-writes.
- **Инфраструктура синхронизации.** Outbox, брокер, обработчики проекций, их идемпотентность и порядок.
- **Перестройка проекций.** Новое поле в read-модели требует пересчёта из истории — нужен источник (event log или полная выгрузка) и процедура rebuild без простоя.
- **Расхождения.** Потерянное или неправильно обработанное событие оставляет read-модель неверной навсегда — нужны сверка и инструмент повторной синхронизации.
- **Больше кода и тестов:** каждый сценарий — команда, событие, проекция, запрос.
- **Отладка:** «почему в списке старая цена» требует смотреть в несколько хранилищ.

**Признаки ненужного CQRS:** read-модель — копия таблицы записи один в один; на каждую команду ровно один экран с теми же полями; команд и запросов несколько десятков, а нагрузка — сотни RPS, с которыми справляется одна БД с индексами.

**Практичный путь:** начинать с разделения кода и оптимизированных запросов к той же БД (view, read replica), выносить отдельную read-модель для конкретного тяжёлого сценария, когда метрики показывают проблему, а не для всего сервиса сразу.

**Что спрашивают дальше:** как бороться с задержкой read-модели, нужен ли Event Sourcing для CQRS (нет — это независимые паттерны), и как перестроить проекцию на живой системе.

## Как бороться с задержкой синхронизации read-модели в CQRS?

```yaml
category: microservices
level: senior
difficulty: 5
slug: microservices-advanced-kak-borotsya-s-zaderzhkoi-sinhronizacii-read-modeli-v-cqrs
tags: cqrs, consistency
```

Задержку нельзя убрать полностью — её делают маленькой и измеримой, а там, где пользователь должен сразу видеть свои изменения, обходят на уровне API и UI: возвращают результат прямо из команды, ждут нужную версию проекции или читают из модели записи. Сначала решают, где задержка вообще проблема: обычно это только «я сам что-то изменил и сразу смотрю», а не чужие изменения.

**1. Уменьшить и измерить задержку:**

- публиковать события быстро (CDC вместо опроса outbox раз в секунды);
- обрабатывать проекции пачками, параллелить по ключу агрегата;
- метрика `projection_lag` = now − timestamp последнего применённого события и/или lag consumer group; алерт по SLO (например, p99 < 2 с).

**2. Read-your-writes без ожидания проекции:**

- **Ответ команды.** Команда возвращает созданный/изменённый объект или его версию, UI обновляет список локально (optimistic UI) — самый дешёвый и частый способ.
- **Ожидание версии.** Команда возвращает версию агрегата, клиент передаёт её в запрос, read-сторона ждёт до таймаута, пока проекция не догонит:

```csharp
app.MapGet("/orders/{id}", async (Guid id, long? minVersion, OrdersReadDb db, CancellationToken ct) =>
{
    var deadline = DateTime.UtcNow.AddSeconds(2);
    while (true)
    {
        var view = await db.Orders.AsNoTracking().FirstOrDefaultAsync(o => o.Id == id, ct);
        if (view is not null && (minVersion is null || view.Version >= minVersion))
            return Results.Ok(view);
        if (DateTime.UtcNow > deadline)
            return Results.Ok(view);
        await Task.Delay(100, ct);
    }
});
```

Вместо 200 со старыми данными по таймауту можно вернуть 202/заголовок «данные обновляются» — главное, чтобы клиент знал.

- **Чтение из модели записи** для экранов «только что изменённого объекта» (карточка заказа после оформления), а списки и поиск — из read-модели.
- **Синхронная проекция.** Критичную read-модель обновлять в той же транзакции, что и запись (одна БД), остальные — асинхронно. Marten, например, поддерживает inline-проекции наряду с асинхронными.

**3. Push вместо опроса.** После применения события проекция уведомляет клиента (SignalR, WebSocket): «заказ 42 обновлён» — UI перечитывает данные. Пользователь видит изменение, как только оно готово, без поллинга.

**4. Сделать задержку частью продукта.** Статусы «обрабатывается», «платёж в обработке», явное время обновления на дашбордах. Для многих сценариев (отчёты, аналитика, рекомендации) секунды и даже минуты бизнес устраивают — это надо выяснить, а не предполагать.

**Чего не делать:**

- `Thread.Sleep(1000)` перед редиректом — задержка непостоянна, при нагрузке её не хватит;
- читать из read-модели внутри команды для проверки инвариантов — проверки идут только против модели записи;
- синхронно обновлять все проекции во всех хранилищах — это возврат к распределённой транзакции.

**Отдельная проблема — расхождение, а не задержка.** Если проекция пропустила событие, данные неверны навсегда. Защита: идемпотентные обработчики с проверкой версии (событие с версией не `current + 1` — сигнал пропуска), периодическая сверка и возможность пересобрать проекцию из истории.

**Что спрашивают дальше:** как обеспечить порядок событий одного агрегата в проекции, что делать, если проекция отстала на часы (rebuild в параллельную таблицу и переключение), и как это выглядит в UI мобильного клиента.

## Когда Event Sourcing действительно нужен и почему его часто внедряют напрасно?

```yaml
category: microservices
level: senior
difficulty: 5
slug: microservices-advanced-kogda-event-sourcing-deistvitelno-nuzhen-i-pochemu-ego-chasto-vnedryay
tags: event-sourcing, architecture
```

Event Sourcing нужен, когда история изменений — сама ценность для бизнеса: нужно знать не только текущее состояние, но и как и почему к нему пришли, восстанавливать состояние на любой момент и строить из той же истории новые представления. Типичные области — финансы и учёт, страхование, логистика со сложными жизненными циклами. Напрасно его внедряют, когда хотят «аудит» или «интеграцию через события» — эти задачи решаются гораздо дешевле, а сложность ES остаётся навсегда.

**Суть:** состояние агрегата не хранится, а вычисляется сверткой событий:

```csharp
public sealed class Account
{
    public decimal Balance { get; private set; }
    public long Version { get; private set; }

    public void Apply(MoneyDeposited e) { Balance += e.Amount; Version++; }
    public void Apply(MoneyWithdrawn e) { Balance -= e.Amount; Version++; }
}
```

Запись — append в поток агрегата с проверкой ожидаемой версии (optimistic concurrency). Чтение — через проекции.

**Когда действительно оправдан:**

- бизнес мыслит событиями и задаёт вопросы к истории: «какой был лимит на момент сделки», «почему изменилась премия», «сколько заказов отменили после смены адреса»;
- нужен temporal query — состояние на произвольную дату с юридической значимостью;
- регулярно появляются новые представления данных, которые нужно построить по всей истории (новая аналитика, новый расчёт);
- сложная доменная модель, где явные события делают поведение понятнее, чем мутации полей;
- append-only хранение — требование (аудит, неизменяемость записей).

**Почему внедряют напрасно:**

| Мотивация | Что дешевле |
| --- | --- |
| «Нужен аудит» | таблица истории изменений, temporal tables, CDC в хранилище логов |
| «Нужно публиковать события другим сервисам» | обычное состояние + Outbox; доменные события ≠ интеграционные |
| «Хотим CQRS» | CQRS работает и без ES |
| «Модно, масштабируется» | ES не ускоряет систему сам по себе, часто наоборот |

**Сложность, которая остаётся навсегда:**

- **Версионирование событий.** История неизменяема, а модель меняется: upcasting, несколько версий обработчиков, слабая схема.
- **Проекции везде.** Любой запрос «найти заказы по статусу» — через read-модель с eventual consistency, её rebuild и мониторинг.
- **Исправление ошибок.** Нельзя `UPDATE` неправильное значение — нужно корректирующее событие и, возможно, пересборка проекций.
- **Длинные потоки.** Агрегаты с тысячами событий требуют snapshot'ов или пересмотра границ.
- **Удаление персональных данных** (GDPR) конфликтует с неизменяемостью — crypto-shredding или хранение PII вне событий.
- **Команда.** Нужны люди, понимающие паттерн; ошибки моделирования событий исправлять дорого.

**Частые ошибки внедрения:**

- ES во всей системе, хотя он нужен в одном bounded context (например, только в «Счетах»);
- события вида `OrderUpdated { все поля }` — это CRUD в форме событий, история бесполезна;
- публикация внутренних событий потока наружу как контракта — любое изменение модели ломает подписчиков.

**Инструменты в .NET:** Marten (поверх PostgreSQL), EventStoreDB/KurrentDB, собственная таблица событий в PostgreSQL для простых случаев.

**Что спрашивают дальше:** как менять схему событий, как делать snapshot'ы, как обеспечить уникальность (например, email) без запроса к проекции, и как ES сочетается с GDPR.

## Как менять схему события в Event Sourcing, если история неизменяема?

```yaml
category: microservices
level: senior
difficulty: 5
slug: microservices-advanced-kak-menyat-shemu-sobytiya-v-event-sourcing-esli-istoriya-neizmenyaema
tags: event-sourcing, schema
```

Сохранённые события не переписывают — меняют то, как их читают. Основные инструменты по возрастанию цены: слабая схема (новые поля опциональны, неизвестные игнорируются), upcasting (старое событие преобразуется в новую форму при чтении), новый тип события рядом со старым, и только в крайнем случае — копирование истории в новый store с преобразованием. Цель — чтобы код агрегата и проекций знал одну актуальную форму, а «зоопарк» версий жил в одном слое десериализации.

**1. Слабая схема — для аддитивных изменений.** Новое поле добавляется с разумным значением по умолчанию:

```csharp
public sealed record OrderPlaced(
    Guid OrderId,
    Guid CustomerId,
    decimal Total,
    string Currency = "RUB");
```

Старые события без `Currency` десериализуются с default. Удалять поля, менять тип или смысл так нельзя: `Total` не может «тихо» начать означать сумму без НДС.

**2. Upcasting — для структурных изменений.** Между хранилищем и агрегатом стоит преобразователь, который превращает старую версию в новую:

```csharp
public sealed record OrderPlacedV1(Guid OrderId, Guid CustomerId, decimal Total);
public sealed record OrderPlaced(Guid OrderId, Guid CustomerId, Money Total, string Channel);

public static class OrderUpcasters
{
    public static object Upcast(object e) => e switch
    {
        OrderPlacedV1 v1 => new OrderPlaced(v1.OrderId, v1.CustomerId,
                                            new Money(v1.Total, "RUB"), Channel: "web"),
        _ => e
    };
}
```

Upcaster'ы цепочкой: V1 → V2 → V3, каждый знает только шаг к следующей версии. Тип события в хранилище фиксируется строкой (`order-placed.v1`), а не именем CLR-класса — иначе рефакторинг namespace'а сломает чтение истории. Marten и EventStoreDB-клиенты имеют свои точки расширения для upcasting.

**3. Новый тип события.** Если изменился смысл, а не форма — например, `OrderPlaced` раньше означал «оформлен и оплачен», а теперь оплата отдельна, — заводят новые события (`OrderPlaced`, `OrderPaid`), а старое событие продолжает обрабатываться как два факта сразу. Это честнее, чем подделывать историю upcaster'ом.

**4. Copy-and-transform.** Если накопилось много версий или нужно изменить границы потоков (разделить агрегат), историю один раз читают, преобразуют и пишут в новый store, затем переключают сервис. Делается как миграция без простоя: новый store догоняет старый, потом запись переключается. Дорого, но очищает код от легаси-версий.

**Чего не делать:** `UPDATE` событий в таблице. Это разрушает главное свойство — историю, которой можно доверять; ломает уже построенные проекции и копии у подписчиков, если события публиковались.

**Отдельно — snapshot'ы и проекции:**

- snapshot сериализует текущее состояние агрегата; при изменении формы состояния snapshot проще выбросить и пересоздать из событий, чем мигрировать;
- проекции при изменении логики пересобираются с нуля в новую таблицу (blue/green), потом чтение переключается.

**Внешние подписчики.** Если события потока публикуются наружу, upcasting у себя их не спасёт — поэтому наружу отдают отдельные интеграционные события со своим версионированием, а внутренние меняют свободно.

**Что спрашивают дальше:** как тестировать (набор сериализованных событий всех версий как фикстуры, тест «каждую версию можно прочитать»), что делать с GDPR-удалением (crypto-shredding), и когда пора делать copy-and-transform вместо очередного upcaster'а.

## Что должен и чего не должен делать API Gateway?

```yaml
category: microservices
level: senior
difficulty: 4
slug: microservices-advanced-chto-dolzhen-i-chego-ne-dolzhen-delat-api-gateway
tags: gateway, architecture
```

API Gateway должен решать сквозные задачи на входе в систему: маршрутизацию, TLS, аутентификацию, rate limiting, базовую наблюдаемость. Он не должен содержать бизнес-логику, знать доменные правила или оркестрировать бизнес-процессы. Как только gateway начинает «немного проверять заказ» или собирать ответ из пяти сервисов по доменным правилам, он превращается в распределённый монолит, который правят все команды и который не может релизиться независимо.

**Что делать gateway:**

| Задача | Детали |
| --- | --- |
| Маршрутизация | по пути, хосту, заголовку; canary/weighted routing; маршрутизация версий API |
| TLS termination | сертификаты в одном месте, внутри — mTLS или сеть кластера |
| Аутентификация | валидация JWT (подпись, срок, audience), отсев анонимных запросов |
| Грубая авторизация | «маршрут `/admin/*` только для роли admin»; решения на уровне объекта — в сервисе |
| Защита | rate limiting, лимиты размера запроса, таймауты, IP allow/deny, CORS |
| Наблюдаемость | access-логи, метрики по маршрутам, старт трассы и `traceparent` |
| Протоколы | gRPC-JSON transcoding, WebSocket proxying |

**В .NET** это обычно YARP — reverse proxy как обычное ASP.NET Core приложение, к которому подключаются стандартные middleware:

```csharp
builder.Services.AddReverseProxy()
    .LoadFromConfig(builder.Configuration.GetSection("ReverseProxy"));
builder.Services.AddAuthentication().AddJwtBearer();
builder.Services.AddAuthorization(o =>
    o.AddPolicy("customers", p => p.RequireAuthenticatedUser()));
builder.Services.AddRateLimiter(o =>
    o.AddFixedWindowLimiter("per-client", w => { w.PermitLimit = 100; w.Window = TimeSpan.FromSeconds(1); }));

var app = builder.Build();
app.UseAuthentication();
app.UseAuthorization();
app.UseRateLimiter();
app.MapReverseProxy();
```

Политики (`AuthorizationPolicy`, `RateLimiterPolicy`) привязываются к маршрутам в конфигурации YARP. Альтернативы — managed-шлюзы облаков, Kong, Envoy-based ingress.

**Чего не делать:**

- **Бизнес-логика и валидация домена** — «нельзя заказать больше 10 единиц» живёт в сервисе заказов, иначе правило дублируется или обходится внутренними вызовами.
- **Оркестрация процессов** — последовательные вызовы сервисов с компенсациями в gateway — это saga без состояния и без надёжности.
- **Детальная авторизация** — «пользователь видит только свои заказы» требует данных, которые есть только у сервиса.
- **Своя БД с доменными данными** и кэширование ответов, зависящих от пользователя, без понимания инвалидации.
- **Retry неидемпотентных запросов** — повтор POST на уровне proxy может создать два заказа.
- **Один gateway на всё и одна команда-владелец** — каждый новый endpoint ждёт их релиза.

**Агрегация — отдельный вопрос.** Если мобильному клиенту нужен один экран из трёх сервисов, это делает BFF (Backend for Frontend) — отдельный сервис под конкретного клиента, которым владеет команда этого клиента. Gateway остаётся тонким, BFF содержит логику представления, но не доменную.

**Риски самого gateway:**

- единая точка отказа — несколько экземпляров, health checks, отдельный rate limiting на каждый маршрут, чтобы один тяжёлый маршрут не занимал весь пул;
- дополнительный hop — обычно единицы миллисекунд, но таймауты gateway должны быть больше таймаутов сервиса за ним, иначе клиент получит 504, а операция выполнится;
- доверие к заголовкам — сервисы за gateway не должны слепо верить `X-User-Id`, если до них можно достучаться в обход; надёжнее пробрасывать проверенный токен.

**Что спрашивают дальше:** чем gateway отличается от service mesh (north-south против east-west трафика), BFF против общего gateway, и где проверять права доступа.

## Какие задачи решает service mesh и когда его сложность не оправдана?

```yaml
category: microservices
level: senior
difficulty: 5
slug: microservices-advanced-kakie-zadachi-reshaet-service-mesh-i-kogda-ego-slozhnost-ne-opravdana
tags: service-mesh, devops
```

Service mesh выносит сетевые задачи межсервисного (east-west) трафика из кода в инфраструктуру: mTLS и идентичность сервисов, управление трафиком (canary, retries, timeouts), единые L7-метрики и политики доступа — одинаково для всех сервисов на любом языке. Он оправдан при десятках сервисов, нескольких стеках и требованиях zero trust; при паре десятков .NET-сервисов одной команды его сложность обычно больше, чем выгода.

**Как устроен:** data plane — прокси (Envoy-sidecar в каждом pod'е у Istio, свой прокси у Linkerd, или node-level прокси в ambient-режиме Istio) перехватывает весь трафик; control plane раздаёт прокси конфигурацию, сертификаты и политики.

**Задачи, которые он решает:**

| Задача | Без mesh | С mesh |
| --- | --- | --- |
| Шифрование и аутентификация сервисов | сертификаты в каждом сервисе, ротация вручную | автоматический mTLS, ротация сертификатов, SPIFFE-идентичность |
| Авторизация «кто кого может вызывать» | NetworkPolicy (L3/L4) + проверки в коде | L7-политики: сервис A может `GET /orders`, но не `DELETE` |
| Canary, traffic shifting, mirroring | на уровне ingress или в коде | веса между версиями для внутренних вызовов |
| Retries, timeouts, outlier detection | Polly в каждом клиенте | единая конфигурация, в том числе для чужих сервисов на других языках |
| Метрики и трассировка вызовов | инструментирование каждого сервиса | golden signals для всех вызовов без изменений кода (но контекст трассы всё равно пробрасывает приложение) |

**Цена:**

- **Ресурсы и задержка:** sidecar на каждый pod — десятки МБ памяти и CPU, плюс миллисекунды на hop; на тысячах pod'ов это заметные деньги. Ambient-режим уменьшает накладные расходы, но добавляет свои компоненты.
- **Эксплуатация:** обновления control plane, совместимость версий, CRD, сертификаты — нужен кто-то, кто глубоко понимает mesh. При его сбое страдает весь трафик.
- **Отладка:** «запрос не дошёл» — это теперь ещё и конфигурация прокси, политики, mTLS-режим; 503 от Envoy с флагами вроде `UF`/`URX` нужно уметь читать.
- **Дублирование resilience:** retry в mesh и retry в Polly перемножаются — 3 × 3 = 9 попыток на каждый вызов; нужно договориться, где живут retries.
- **Жизненный цикл pod'а:** порядок старта и остановки sidecar'а и приложения (job'ы, которые не завершаются; запросы до готовности прокси).

**Когда не оправдан:**

- немного сервисов на одном стеке — Polly/`Microsoft.Extensions.Http.Resilience`, OpenTelemetry и NetworkPolicy дают 80% пользы;
- нет требования шифровать внутренний трафик или аудитор устраивает шифрование на уровне сети/CNI;
- нет людей, готовых владеть mesh'ем;
- основная проблема — не сеть, а границы сервисов или данные.

**Промежуточные варианты:** Linkerd (проще и легче Istio), Cilium с mTLS и L7-политиками на уровне CNI, Istio ambient только для L4 mTLS без waypoint-прокси.

**Что спрашивают дальше:** чем mesh отличается от API Gateway, кто отвечает за retries при наличии mesh, и как постепенно внедрять mesh (permissive mTLS, потом strict, по одному namespace).

## Как комбинировать circuit breaker, retry и timeout, чтобы они не конфликтовали?

```yaml
category: microservices
level: senior
difficulty: 5
slug: microservices-advanced-kak-kombinirovat-circuit-breaker-retry-i-timeout-chtoby-oni-ne-konflik
tags: resilience, patterns
```

Порядок снаружи внутрь: общий таймаут на всю операцию → retry → circuit breaker → таймаут одной попытки. Тогда общий таймаут ограничивает суммарное время с учётом всех повторов, каждая попытка отдельно ограничена своим таймаутом и учитывается breaker'ом как отказ, а открытый breaker мгновенно отклоняет попытку, и retry не тратит время на заведомо мёртвый сервис. Плюс согласованные числа: таймауты, задержки и окно breaker'а должны быть связаны между собой.

**Так это выглядит в Polly v8** (стратегии, добавленные раньше, — внешние):

```csharp
services.AddHttpClient<InventoryClient>(c => c.BaseAddress = new("http://inventory"))
    .AddResilienceHandler("inventory", b => b
        .AddTimeout(TimeSpan.FromSeconds(3))
        .AddRetry(new HttpRetryStrategyOptions
        {
            MaxRetryAttempts = 2,
            BackoffType = DelayBackoffType.Exponential,
            UseJitter = true,
            Delay = TimeSpan.FromMilliseconds(200)
        })
        .AddCircuitBreaker(new HttpCircuitBreakerStrategyOptions
        {
            FailureRatio = 0.5,
            MinimumThroughput = 20,
            SamplingDuration = TimeSpan.FromSeconds(30),
            BreakDuration = TimeSpan.FromSeconds(15)
        })
        .AddTimeout(TimeSpan.FromMilliseconds(800)));
```

`AddStandardResilienceHandler()` собирает ту же цепочку: rate limiter → total timeout → retry → circuit breaker → attempt timeout — и проверяет согласованность параметров при старте (например, окно sampling breaker'а должно быть хотя бы вдвое больше таймаута попытки).

**Типичные конфликты:**

| Ошибка | Что происходит |
| --- | --- |
| Только общий таймаут, без таймаута попытки | первая попытка «висит» до общего таймаута, retry не успевает сработать |
| Таймаут попытки × число попыток + задержки > общего таймаута | последние попытки никогда не выполняются, конфигурация вводит в заблуждение |
| Breaker снаружи retry | одна логическая операция с тремя неудачными попытками считается одним отказом, breaker открывается слишком поздно |
| Retry на `BrokenCircuitException` без паузы | серия мгновенных отказов; пока breaker открыт, повторять бессмысленно |
| Таймаут попытки не считается отказом | breaker не видит «тормозящий» сервис — `HttpCircuitBreakerStrategyOptions` по умолчанию учитывает `TimeoutRejectedException`, а самописные предикаты `ShouldHandle` часто забывают |
| `HttpClient.Timeout` меньше общего таймаута pipeline | клиент обрывает запрос раньше, политики не отрабатывают как задумано (по умолчанию 100 с) |

**Согласованность с соседями по цепочке:**

- **Бюджет по всей цепочке.** Если gateway ждёт 5 с, сервис A не может тратить 3 × 3 с на вызовы B. Таймауты уменьшаются от края системы внутрь; в gRPC дедлайн входящего вызова можно передать дальше автоматически (`EnableCallContextPropagation()` в gRPC client factory).
- **Retry только на одном уровне.** Gateway, mesh, сервис A и сервис B с тремя попытками каждый дают 3⁴ = 81 запрос к последнему сервису на один пользовательский — retry storm. Ретраят там, где известна идемпотентность операции, обычно ближе к вызывающему коду.
- **Retry только идемпотентных операций** — POST без idempotency key не повторяют, иначе таймаут попытки превращается в дубль заказа.
- **429 и `Retry-After`** — уважать задержку сервера, а не долбить его по своему расписанию (`HttpRetryStrategyOptions` по умолчанию учитывает `Retry-After`).

**Что ещё помогает:** hedging (параллельная попытка после задержки) для чтений с жёстким latency SLO вместо последовательного retry; bulkhead/rate limiter, чтобы медленный сервис не съел все соединения; fallback — кэш или деградированный ответ при открытом breaker'е.

**Что спрашивают дальше:** как подобрать сами пороги, как это тестировать (fault injection, chaos-стратегии Polly v8 — бывший Simmy), и как быть с retry при асинхронном обмене сообщениями.

## Как выбрать порог для circuit breaker и что произойдёт при неверной настройке?

```yaml
category: microservices
level: senior
difficulty: 5
slug: microservices-advanced-kak-vybrat-porog-dlya-circuit-breaker-i-chto-proizoidet-pri-nevernoi-n
tags: resilience, patterns
```

Порог выбирают от данных, а не «на глаз»: нормальный уровень ошибок зависимости, трафик на один экземпляр клиента и то, сколько времени вы готовы ждать перед реакцией. Breaker должен открываться, когда ошибок явно больше фона, и не открываться от единичных всплесков. Слишком чувствительный breaker сам устраивает outage, отключая живой сервис; слишком вялый не срабатывает, и медленная зависимость съедает потоки и соединения, вызывая каскадный отказ.

**Параметры Polly v8 и их смысл:**

| Параметр | Default Polly | Как выбирать |
| --- | --- | --- |
| `FailureRatio` | 0.1 | заметно выше нормального фона ошибок: при фоне 1% — 0.2–0.5 |
| `MinimumThroughput` | 100 | чтобы решение принималось на статистически значимом числе вызовов |
| `SamplingDuration` | 30 с | окно наблюдения; короче — быстрее реакция и больше шума |
| `BreakDuration` | 5 с | сколько дать зависимости на восстановление до пробного запроса |
| `ShouldHandle` | исключения, кроме отмены | что считать отказом |

**Пошаговый расчёт:**

1. **Фон ошибок** из метрик за неделю: p99 уровня 5xx/таймаутов у зависимости. Если в норме 2% — `FailureRatio = 0.1` уже близко к опасной зоне на пиках.
2. **Трафик на экземпляр.** Breaker живёт в каждом процессе отдельно. 600 RPS к сервису на 10 pod'ов — 60 RPS на pod, за 30 с — 1800 вызовов, `MinimumThroughput = 100` достигается за 2 с. А при 1 RPS на pod — 30 вызовов за окно, и breaker с порогом 100 не откроется никогда.
3. **Время реакции.** Хотим отключиться за ~10 с после начала деградации — окно 10–15 с при достаточном трафике.
4. **BreakDuration** — от характера сбоев: перезапуск pod'а — секунды, отказ БД — минуты. Для долгих сбоев используют `BreakDurationGenerator` с растущей длительностью.
5. **Что считать отказом:** 5xx, 408, 429, таймауты, ошибки соединения — да; 400/404/409 — нет, это ошибки запроса, а не здоровья сервиса. `HttpCircuitBreakerStrategyOptions` по умолчанию так и настроен.

**Что происходит при неверной настройке:**

| Ошибка | Симптом |
| --- | --- |
| `FailureRatio` близко к фону | breaker хлопает (open/close) на обычных пиках, пользователи получают ошибки при живой зависимости |
| `MinimumThroughput` больше трафика за окно | breaker не открывается вообще, видимой защиты нет |
| Слишком маленький `MinimumThroughput` | 3 ошибки из 5 вызовов ночью открывают breaker |
| `BreakDuration` слишком короткий | зависимость, которая поднимается после рестарта, тут же получает поток запросов и падает снова |
| `BreakDuration` слишком длинный | сервис давно жив, а клиент ещё минуту отдаёт fallback |
| Один breaker на весь хост | падение одного тяжёлого endpoint'а отключает все остальные |
| 4xx считаются отказом | баг клиента или атака с невалидными запросами «отключает» здоровый сервис |
| Таймауты не считаются отказом | зависший сервис не открывает breaker, потоки ждут |

**Гранулярность.** Стандартный handler создаёт pipeline на именованный клиент; `SelectPipelineByAuthority()` даёт отдельный breaker на каждый хост — важно, если один клиент ходит в несколько адресов. Для разных по критичности операций — разные клиенты/pipeline.

**Эксплуатация:**

- метрики состояния breaker'а (Polly публикует события и метрики через telemetry) и алерт на открытие;
- `CircuitBreakerStateProvider` — показать состояние в health check, `CircuitBreakerManualControl` — открыть вручную при плановых работах;
- fallback для открытого состояния — иначе breaker просто превращает медленную ошибку в быструю, что лучше, но не идеально;
- проверить настройки под нагрузкой с fault injection, а не в проде.

**Что спрашивают дальше:** что такое half-open и почему пробный запрос один, как breaker взаимодействует с retry и балансировщиком (один плохой экземпляр из пяти даёт 20% ошибок — breaker по хосту отключит всех, outlier detection на уровне балансировщика уберёт только его), и почему breaker на стороне клиента не заменяет rate limiting на стороне сервера.

## Как спланировать распил монолита и с чего начать в первую очередь?

```yaml
category: microservices
level: senior
difficulty: 5
slug: microservices-advanced-kak-splanirovat-raspil-monolita-i-s-chego-nachat-v-pervuyu-ochered
tags: migration, architecture
```

Начинать не с выделения сервиса, а с ответа «какую проблему решаем»: независимые релизы команд, масштабирование конкретной части, изоляция отказов, смена технологии. Потом — подготовка монолита (модульные границы внутри, CI/CD, наблюдаемость), и только после этого первый сервис: небольшой, слабо связанный по данным, но реально полезный, чтобы на нём отработать инфраструктуру. Распил — многомесячный инкрементальный процесс через Strangler Fig, а не переписывание с нуля.

**Шаг 0. Цель и метрики.** «Перейти на микросервисы» — не цель. Цель — «команда платежей релизится независимо, сейчас ждёт общий релиз раз в две недели» или «каталог выдерживает распродажу без масштабирования всего монолита». Метрики (lead time, частота релизов, MTTR, стоимость инфраструктуры) нужны, чтобы понять, что распил помогает, и вовремя остановиться.

**Шаг 1. Карта домена и связей:**

- bounded contexts через event storming с бизнесом;
- реальные зависимости в коде (граф namespace'ов/проектов, NDepend, анализ вызовов);
- кто какие таблицы пишет и читает — связанность по данным обычно сильнее, чем по коду;
- hotspots: какие части меняются чаще всего и какими командами (история git).

**Шаг 2. Модульный монолит.** Навести границы внутри: отдельные проекты-модули, публичные интерфейсы между ними, запрет прямого доступа к чужим таблицам, архитектурные тесты (NetArchTest/ArchUnitNET). Если границы не получается удержать внутри одного процесса, в сети они станут только хуже. Часто на этом шаге половина проблем уже решена.

**Шаг 3. Платформа.** До первого сервиса: автоматический деплой, централизованные логи, метрики, трассировка (OpenTelemetry), service discovery, шаблон сервиса, брокер сообщений, подход к контрактам. Иначе каждый сервис изобретает это сам.

**Шаг 4. Выбор первого кандидата:**

| Хороший первый кандидат | Плохой первый кандидат |
| --- | --- |
| мало входящих зависимостей, своих данных, чёткий контракт | ядро домена, от которого зависит всё (Заказы, Пользователи) |
| отдельная команда, которая будет им владеть | «общий» модуль без владельца |
| отдельная причина масштабирования или частые изменения | редко меняющийся код без проблем |
| уведомления, поиск, генерация документов, интеграция с внешним партнёром | функционал с распределёнными транзакциями с ядром |

Выделение «края» системы даёт быструю победу и опыт, а ядро разбирают позже, когда инфраструктура и практики отлажены.

**Шаг 5. Итерация для каждого сервиса:**

1. Фасад/прокси перед монолитом (YARP), чтобы можно было переключать маршруты.
2. Новый сервис реализует функцию; трафик переводится постепенно (по маршруту, проценту, тенанту).
3. Данные: сначала сервис читает через API монолита или синхронизирует копию, затем становится владельцем, монолит переходит на его API или события.
4. Старый код удаляется — без этого шага получается два источника правды.

**Типичные ошибки:**

- big bang rewrite с заморозкой фич — бизнес не ждёт год;
- нарезка по техническим слоям (сервис «данных», сервис «валидации»);
- выделение сервиса без выделения данных — общая БД, распределённый монолит;
- слишком мелкие сервисы на старте: 30 сервисов на 8 разработчиков;
- отсутствие критерия остановки — часть монолита разумно оставить монолитом навсегда.

**Что спрашивают дальше:** как разделить общую БД, как маршрутизировать трафик во время миграции, как сохранить консистентность между монолитом и новым сервисом в переходный период.

## Как работает Strangler Fig на практике и как маршрутизировать трафик во время миграции?

```yaml
category: microservices
level: senior
difficulty: 5
slug: microservices-advanced-kak-rabotaet-strangler-fig-na-praktike-i-kak-marshrutizirovat-trafik-v
tags: migration, architecture
```

Перед монолитом ставят маршрутизирующий слой (reverse proxy вроде YARP, ingress или gateway), через который идёт весь трафик. Функции по одной переписываются в новых сервисах, и маршрут для них переключается с монолита на сервис — сначала для части запросов, потом для всех; старый код удаляется. Ключевое свойство — любой шаг обратим переключением маршрута, а монолит продолжает работать всё время миграции.

**Последовательность для одной функции:**

1. **Перехват.** Весь трафик уже идёт через прокси, который пока всё отправляет в монолит. Этот шаг делают один раз и заранее.
2. **Новая реализация** рядом, с теми же контрактами API (или с адаптером в прокси).
3. **Теневой режим (для чтений).** Запросы зеркалируются в новый сервис, ответы сравниваются с монолитом, но пользователю отдаётся ответ монолита.
4. **Постепенное переключение:** внутренние пользователи → тенант-пилот → 5% → 50% → 100%.
5. **Перенос владения данными** — новый сервис становится источником правды, монолит читает у него.
6. **Удаление кода** из монолита — без этого «душение» не закончено.

**Маршрутизация в YARP:**

```json
{
  "ReverseProxy": {
    "Routes": {
      "invoices-new": {
        "ClusterId": "invoices",
        "Order": 1,
        "Match": {
          "Path": "/api/invoices/{**rest}",
          "Headers": [ { "Name": "X-Tenant", "Values": [ "pilot-1", "pilot-2" ] } ]
        }
      },
      "invoices-legacy": {
        "ClusterId": "monolith",
        "Order": 2,
        "Match": { "Path": "/api/invoices/{**rest}" }
      },
      "catch-all": {
        "ClusterId": "monolith",
        "Order": 100,
        "Match": { "Path": "{**catch-all}" }
      }
    },
    "Clusters": {
      "invoices": { "Destinations": { "d1": { "Address": "http://invoices/" } } },
      "monolith": { "Destinations": { "d1": { "Address": "http://legacy/" } } }
    }
  }
}
```

Способы выбрать, кто идёт в новый сервис:

| Критерий | Когда |
| --- | --- |
| Путь/метод (`GET /invoices` — новый, `POST` — пока монолит) | чтение переносят раньше записи |
| Тенант/пользователь (заголовок, claim) | пилотные клиенты, консистентный опыт для одного пользователя |
| Процент трафика | stateless-чтения; в YARP — своим middleware или на уровне ingress/mesh с весами |
| Feature flag | переключение без перевыкладки конфигурации прокси |

Для записи важна «липкость»: один и тот же пользователь или сущность всегда должны попадать в одну реализацию, иначе данные разъедутся между двумя хранилищами.

**Что, кроме HTTP:**

- **Внутренние вызовы в монолите** — branch by abstraction: интерфейс `IInvoiceService`, за которым реализация либо локальная, либо HTTP-клиент к новому сервису, переключается флагом.
- **Фоновые задачи и события** — перехват на уровне сообщений: новый сервис подписывается на события монолита (через Outbox/CDC), а задача в монолите отключается флагом.
- **UI** — страница за страницей через тот же прокси или micro-frontends.

**Данные в переходный период** — самая сложная часть: синхронизация через CDC из таблиц монолита в БД сервиса, затем смена направления, когда владельцем становится сервис. Двойная запись из кода без Outbox даёт расхождения.

**Подводные камни:**

- прокси становится критичной точкой — несколько экземпляров, минимум логики, отдельные таймауты на маршрут;
- сессии и аутентификация монолита (cookie, server-side session) должны быть понятны новому сервису — обычно переход на токены выполняют до распила;
- метрики сравнения: ошибки и latency новой реализации против старой на тех же запросах — критерий для каждого шага;
- «вечная миграция»: 80% перенесено, остаток никто не трогает, поддерживаются обе системы.

**Что спрашивают дальше:** как откатываться после переноса данных (обратная синхронизация на время стабилизации), как делить общую БД, и чем Strangler Fig отличается от параллельного запуска (parallel run), где результаты обеих систем сравнивают долго и систематически.

## Как разделить общую базу данных при выделении сервиса из монолита?

```yaml
category: microservices
level: senior
difficulty: 5
slug: microservices-advanced-kak-razdelit-obschuyu-bazu-dannyh-pri-vydelenii-servisa-iz-monolita
tags: migration, data
```

Делят поэтапно, каждый шаг обратим: сначала определяют, какие таблицы принадлежат новому сервису и кто ещё к ним обращается; затем изолируют доступ (все обращения к этим таблицам — только через код будущего сервиса), потом физически переносят данные с синхронизацией в переходный период и последним шагом рвут чужие join'ы и foreign keys, заменяя их вызовами API или локальными копиями по событиям. Самая частая ошибка — вынести код, а БД оставить общей.

**Шаг 1. Инвентаризация.** Кто читает и пишет каждую таблицу: поиск по коду, `pg_stat_statements`, логи запросов, отчёты и ETL, которые ходят напрямую в БД (их часто забывают). Таблицы делятся на: принадлежащие сервису, принадлежащие монолиту и «общие» — с ними сложнее всего.

**Шаг 2. Изоляция внутри монолита.** Таблицы будущего сервиса выносятся в отдельную схему (`invoicing.*`), доступ к ним — только через модуль и его интерфейс. Чужой SQL с join'ом на `invoices` переписывается на вызов модуля. Отдельный пользователь БД с правами только на свою схему делает нарушения видимыми сразу.

**Шаг 3. Разделение данных.** Варианты по возрастанию риска:

| Подход | Как | Когда |
| --- | --- | --- |
| Отдельная схема в той же БД | сервис владеет схемой, никто больше не имеет прав | промежуточный шаг, дёшево |
| Синхронизация через CDC | Debezium/логическая репликация копирует таблицы в БД сервиса, сервис сначала только читает | перенос с проверкой на реальных данных |
| Смена владельца | сервис начинает писать сам, монолит получает изменения событиями или ходит в API | после стабилизации чтения |

Перенос записи — критичный момент. Безопасная последовательность: сервис пишет в свою БД и публикует события через Outbox → монолит подписывается и обновляет свою копию (для старого кода, который ещё читает напрямую) → когда прямых чтений не осталось, копия в монолите удаляется.

**Шаг 4. Разрыв связей между таблицами:**

- **Foreign key** на таблицу другого сервиса удаляют; ссылочная целостность обеспечивается приложением и событиями (`CustomerDeleted` → обработка у подписчика).
- **Join'ы** заменяют на: API-вызов (для единичных объектов), локальную read-only копию нужных полей по событиям (для списков и фильтрации), API composition на уровне BFF.
- **Транзакции через границу** превращаются в saga с компенсациями — это нужно увидеть на шаге инвентаризации, потому что меняет бизнес-процесс.
- **Отчёты** — отдельное аналитическое хранилище, куда данные из всех сервисов приходят через CDC/события, а не прямые запросы к БД сервисов.

**Общие таблицы** (справочники, «пользователи», настройки):

- справочник с одним владельцем — владелец публикует изменения, остальные хранят кэш;
- таблица, которую пишут несколько модулей, обычно означает, что в ней смешаны разные понятия — её разделяют по bounded contexts (`customers` → профиль, кредитные условия, адреса доставки);
- статичные справочники (страны, валюты) допустимо дублировать как конфигурацию.

**Перенос без простоя:**

1. Начальная выгрузка + CDC догоняет изменения.
2. Сверка: количество строк, контрольные суммы по диапазонам.
3. Переключение чтения, затем записи; на время стабилизации — обратная синхронизация для отката.
4. Удаление таблиц в монолите только после периода, за который убедились, что к ним никто не обращается (аудит доступа).

**Что спрашивают дальше:** как быть с ID (генерация на стороне сервиса, UUID вместо sequence, чтобы не конфликтовать при двусторонней синхронизации), как обеспечить консистентность в переходный период и что делать с отчётами, которые делали join через всю БД.

## Как согласовывать контракты между сервисами и что даёт contract testing?

```yaml
category: microservices
level: senior
difficulty: 4
slug: microservices-advanced-kak-soglasovyvat-kontrakty-mezhdu-servisami-i-chto-daet-contract-testi
tags: contracts, testing
```

Контракт — это то, что потребители реально используют из API или события, а не всё, что провайдер отдаёт. Согласование держится на трёх вещах: явная машиночитаемая схема (OpenAPI, protobuf, Avro/JSON Schema в реестре), правила эволюции (только обратно совместимые изменения, ломающие — через новую версию) и автоматическая проверка в CI. Contract testing даёт эту проверку без поднятия всей системы: провайдер узнаёт, что сломает конкретного потребителя, до деплоя, а не на интеграционном стенде.

**Два подхода к контрактам:**

| | Provider-first (schema-first) | Consumer-driven contracts |
| --- | --- | --- |
| Источник правды | схема провайдера (OpenAPI, `.proto`) | ожидания каждого потребителя |
| Проверка | diff схем на breaking changes (`oasdiff`, `buf breaking`, Schema Registry compatibility) | провайдер прогоняет контракты всех потребителей |
| Что ловит | удаление поля, смену типа, новое обязательное поле | всё это плюс семантику: формат, статус-коды, поведение в конкретных состояниях |
| Знает ли провайдер, кто что использует | нет | да — можно удалить поле, которое никто не читает |

На практике их сочетают: схема и проверка совместимости в CI для всех API, consumer-driven контракты — для критичных связей между командами.

**Как работает consumer-driven (Pact):**

1. Потребитель пишет тест против mock-сервера Pact, описывая запросы и минимально нужный ответ. Результат — pact-файл (JSON-контракт).
2. Pact-файл публикуется в Pact Broker с версией и веткой потребителя.
3. Провайдер в своём CI поднимает себя (без внешних зависимостей), получает из брокера контракты всех потребителей и проигрывает их против себя. Состояния (`order 42 exists`) готовит через provider state endpoint.
4. Перед деплоем — `can-i-deploy`: брокер отвечает, совместима ли эта версия с версиями соседей, которые сейчас в целевом окружении.

```csharp
var pact = Pact.V4("orders-web", "orders-api", new PactConfig()).WithHttpInteractions();

pact.UponReceiving("a request for an existing order")
    .Given("order 42 exists")
    .WithRequest(HttpMethod.Get, "/orders/42")
    .WillRespond()
    .WithStatus(HttpStatusCode.OK)
    .WithJsonBody(new
    {
        id = Match.Type(42),
        status = Match.Regex("Paid", "^(New|Paid|Cancelled)$")
    });

await pact.VerifyAsync(async ctx =>
{
    var client = new OrdersClient(new HttpClient { BaseAddress = ctx.MockServerUri });
    var order = await client.GetAsync(42);
    Assert.Equal(42, order.Id);
});
```

Matchers (`Match.Type`, `Match.Regex`) делают контракт устойчивым: проверяется форма и тип, а не конкретные значения. Для событий Pact поддерживает message pacts — тот же подход для асинхронных контрактов.

**Что contract testing не заменяет:**

- функциональные тесты провайдера — контракт проверяет форму взаимодействия, а не правильность бизнес-логики;
- немного end-to-end тестов на критичные сценарии;
- нефункциональное: таймауты, производительность, порядок событий.

**Типичные ошибки:**

- контракт описывает весь ответ провайдера, а не то, что потребитель читает, — любое изменение ломает тест, и команда его отключает;
- точные значения вместо matchers;
- контракты есть, но `can-i-deploy` не встроен в пайплайн — никто не смотрит;
- общая клиентская NuGet-библиотека провайдера как «контракт» — связывает релизы и не показывает, какие поля реально используются;
- провайдер тестирует контракты с замоканной бизнес-логикой так глубоко, что проверяется уже не он.

**Организационная часть:** изменение контракта — это разговор команд. Правило «провайдер не ломает существующих потребителей; ломающее изменение = новая версия + период поддержки обеих + список потребителей, которые перешли» работает лучше любого инструмента.

**Что спрашивают дальше:** как версионировать API и события, как проверять контракты событий в Kafka (Schema Registry + compatibility mode), и как поступать с внешними потребителями, которых нельзя попросить написать pact.

## Как версионировать события, чтобы не ломать подписчиков?

```yaml
category: microservices
level: senior
difficulty: 5
slug: microservices-advanced-kak-versionirovat-sobytiya-chtoby-ne-lomat-podpischikov
tags: schema, contracts
```

Базовое правило: в рамках одной версии события допускаются только обратно совместимые изменения — новые опциональные поля, новые значения, которые подписчики умеют игнорировать. Удаление, переименование, смена типа или смысла поля — это новая версия события, которую публикуют параллельно со старой, пока все подписчики не перейдут. Подписчики со своей стороны пишутся как tolerant reader: игнорируют неизвестные поля и не падают на отсутствии необязательных.

**Что совместимо, а что нет:**

| Изменение | Совместимо? |
| --- | --- |
| Новое опциональное поле | да |
| Новое значение enum | только если подписчики обрабатывают неизвестные значения (default-ветка, а не исключение) |
| Удаление поля | нет, пока хоть один подписчик его читает |
| Переименование, смена типа (`int` → `string`, сумма в копейках → в рублях) | нет |
| Поле стало обязательным | нет для старых событий в топике |
| Смена смысла при той же форме | нет, и это самое опасное — схема проверку пройдёт |

**Как обозначить версию:**

- в типе события: `OrderPlaced.v2` / CloudEvents `type: com.shop.order.placed.v2`;
- в заголовке сообщения (`event-version: 2`) при том же топике;
- в отдельном топике (`orders.v2`) — для крупных ломающих изменений;
- Schema Registry с режимом совместимости проверяет совместимые изменения автоматически при регистрации схемы и не даёт случайно зарегистрировать несовместимую в ту же subject.

**Процесс ломающего изменения:**

1. Провайдер начинает публиковать v2 рядом с v1 (обе версии пишутся в Outbox одной транзакцией, либо v1 генерируется адаптером из v2).
2. Подписчики по одному переходят на v2; провайдер отслеживает, кто ещё на v1 (lag consumer group, реестр потребителей, contract tests).
3. Когда v1 никто не читает — публикация v1 прекращается, а через retention удаляется топик/схема.

**Tolerant reader в .NET:**

```csharp
public sealed record OrderPlaced(
    Guid OrderId,
    decimal Total,
    string? Currency,
    OrderChannel Channel = OrderChannel.Unknown);

var options = new JsonSerializerOptions(JsonSerializerDefaults.Web)
{
    UnmappedMemberHandling = JsonUnmappedMemberHandling.Skip,
    Converters = { new JsonStringEnumConverter() }
};
```

`Skip` — поведение по умолчанию в System.Text.Json; важно не включать `Disallow` и не валидировать входящие события строже, чем нужно. Неизвестные строковые значения enum `JsonStringEnumConverter` не простит — для enum, которые будут расширяться, надёжнее строковое поле и маппинг с default.

**Проектирование, которое упрощает эволюцию:**

- события несут бизнес-факт с ограниченным набором полей (`OrderShipped { OrderId, ShippedAt, Carrier }`), а не снимок всей сущности — меньше поверхность контракта;
- денежные суммы — сразу с валютой, даты — с часовым поясом (UTC), идентификаторы — строками/UUID: типичные причины ломающих изменений устраняются заранее;
- интеграционные события отделены от внутренних доменных — внутреннюю модель можно менять, наружу публикуется стабильный контракт;
- в каждом событии `eventId`, `occurredAt`, `version` — для идемпотентности и диагностики.

**Подводные камни:**

- в топике лежат старые события — новая версия подписчика должна читать и их (replay, retry-очереди, DLQ);
- при параллельной публикации v1/v2 подписчик, читающий оба, обработает факт дважды — подписываться нужно на одну версию;
- «тихая» смена семантики (сумма теперь без НДС) не ловится ни одной схемой — только процессом ревью и явным новым полем (`TotalExclVat`).

**Что спрашивают дальше:** как это делается в Kafka с Schema Registry (режимы BACKWARD/FORWARD/FULL и порядок деплоя), как узнать всех подписчиков события, и чем версионирование событий отличается от версионирования REST API (подписчиков не видно в логах запросов).

## Как организовать распределённую трассировку и что делать, если контекст теряется?

```yaml
category: microservices
level: senior
difficulty: 4
slug: microservices-advanced-kak-organizovat-raspredelennuyu-trassirovku-i-chto-delat-esli-kontekst
tags: tracing, observability
```

Трассировка строится на OpenTelemetry: каждый сервис создаёт span'ы для входящих и исходящих операций, контекст трассы (`trace-id`, `span-id`) передаётся между сервисами по стандарту W3C Trace Context в заголовке `traceparent`, а span'ы отправляются через OTLP в Collector и дальше в бэкенд (Jaeger, Tempo, Zipkin и т. п.). Контекст теряется там, где автоматическая инструментация его не переносит — в брокерах без поддержки, фоновых очередях внутри процесса, прокси, режущих заголовки, — и это чинят явной передачей контекста.

**Базовая настройка в .NET:**

```csharp
builder.Services.AddOpenTelemetry()
    .ConfigureResource(r => r.AddService("orders-api"))
    .WithTracing(t => t
        .AddAspNetCoreInstrumentation()
        .AddHttpClientInstrumentation()
        .AddSource("MassTransit")
        .AddSource("Orders")
        .AddOtlpExporter());
```

В .NET span — это `System.Diagnostics.Activity`, текущий хранится в `Activity.Current` (через `AsyncLocal`) и автоматически течёт через `await`. ASP.NET Core извлекает `traceparent` из входящего запроса, `HttpClient` добавляет его в исходящие (gRPC-клиент в .NET работает поверх `HttpClient`, поэтому тоже). MassTransit сам создаёт span'ы и передаёт контекст в заголовках сообщений.

**Где контекст теряется и что делать:**

| Место | Причина | Решение |
| --- | --- | --- |
| Kafka через Confluent.Kafka | клиент не инструментирован | инжектить `traceparent` в headers при produce и извлекать при consume |
| Фоновая обработка через `Channel`/очередь в памяти | `Activity.Current` в воркере свой | сохранять `ActivityContext` вместе с элементом очереди и стартовать span с ним как родителем |
| `ExecutionContext.SuppressFlow`, `UnsafeQueueUserWorkItem`, свои потоки | контекст не копируется | не использовать без нужды или передавать контекст явно |
| Gateway, nginx, legacy-прокси | заголовок не пробрасывается или перезаписывается | проверить конфигурацию, включить OTel в прокси |
| Неинструментированный сервис в середине | разрыв цепочки | минимум — пробросить заголовки как есть |
| Разное sampling-решение у сервисов | часть span'ов отброшена | `ParentBased` sampler: решение принимает корень, остальные следуют |
| Batch-consumer | у пачки много родителей | span обработки пачки с links на контексты сообщений |

**Явная передача через Kafka:**

```csharp
private static readonly ActivitySource Source = new("Orders");
private static readonly TextMapPropagator Propagator = Propagators.DefaultTextMapPropagator;

public Task PublishAsync(Message<string, string> msg)
{
    using var activity = Source.StartActivity("orders publish", ActivityKind.Producer);
    msg.Headers ??= new Headers();
    Propagator.Inject(new PropagationContext(activity?.Context ?? default, Baggage.Current),
        msg.Headers, (h, key, value) => h.Add(key, Encoding.UTF8.GetBytes(value)));
    return producer.ProduceAsync("orders", msg);
}

public void Handle(ConsumeResult<string, string> r)
{
    var parent = Propagator.Extract(default, r.Message.Headers,
        (h, key) => h.TryGetLastBytes(key, out var b)
            ? new[] { Encoding.UTF8.GetString(b) }
            : Array.Empty<string>());
    Baggage.Current = parent.Baggage;
    using var activity = Source.StartActivity("orders process", ActivityKind.Consumer, parent.ActivityContext);
    ...
}
```

**Связь с логами и метриками:** при включённом OpenTelemetry-логгинге или scope'ах `ILogger` в записи логов попадают `TraceId`/`SpanId` — по ним из трассы переходят в логи. Exemplars связывают точки метрик с трассами.

**Объём и стоимость:**

- head sampling (например, 10% через `TraceIdRatioBased` внутри `ParentBased`) — дёшево, но редкие ошибки теряются;
- tail sampling в OpenTelemetry Collector — решение после завершения трассы: сохранить все ошибки и медленные запросы, остальное — выборочно;
- не делать span на каждую мелкую операцию и не класть в атрибуты PII и тела запросов.

**Как искать разрывы:** трассы, где корневой span — consumer или фоновая задача, а не HTTP-вход; сервисы с аномально большим числом корневых трасс; span'ы без родителя при наличии `traceparent` в логах на входе.

**Что спрашивают дальше:** чем trace-id отличается от correlation-id (можно использовать trace-id как correlation-id), что такое baggage и почему в него нельзя класть много данных (передаётся в каждом запросе), и как трассировать асинхронный процесс, растянутый на часы (links вместо одного огромного дерева).
