# Факты: PostgreSQL

## Один NULL в подзапросе — и NOT IN возвращает пустоту

```yaml
slug: not-in-s-null
category: postgresql
```

`x NOT IN (1, 2, NULL)` раскрывается в `x <> 1 AND x <> 2 AND x <> NULL`. Сравнение с `NULL` даёт `NULL`, а не `true`, поэтому условие никогда не выполняется, и запрос молча возвращает ноль строк.

```sql
SELECT * FROM users u
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id);
```

Самое коварное: запрос годами работает, пока в колонке не появится первый `NULL`. Для анти-джойна используйте `NOT EXISTS` — он с `NULL` ведёт себя предсказуемо и обычно не медленнее.

## count(1) не быстрее count(*)

```yaml
slug: count-zvezdochka-vs-count-1
category: postgresql
```

Миф родом из других СУБД. В PostgreSQL `count(*)` — отдельная форма агрегата без аргумента, она просто считает строки. `count(1)` формально вычисляет выражение и проверяет его на `NULL`, так что, если разница и есть, она в пользу `count(*)`.

А вот `count(column)` — это уже другая семантика: он считает только строки, где колонка не `NULL`. Медленный `count(*)` на большой таблице лечится не синтаксисом, а приблизительной оценкой из `pg_class.reltuples` или отдельным счётчиком.

## UPDATE не меняет строку, а создаёт новую

```yaml
slug: mvcc-vacuum-razduvanie
category: postgresql
```

Из-за MVCC каждый `UPDATE` пишет новую версию строки, а старая остаётся мёртвым кортежем, пока её не уберёт `VACUUM`. Таблица-очередь со статусами, которую постоянно обновляют, может весить в десятки раз больше живых данных.

Обычный `VACUUM` помечает место для повторного использования, но почти не возвращает его ОС. Хуже всего — долгая транзакция или сессия `idle in transaction`: пока она жива, автовакуум не может удалить версии, которые она теоретически видит. `VACUUM FULL` сжимает таблицу, но берёт эксклюзивную блокировку на всё время работы.

## CREATE INDEX без CONCURRENTLY останавливает запись

```yaml
slug: create-index-concurrently
category: postgresql
```

Обычный `CREATE INDEX` берёт блокировку `SHARE`: читать таблицу можно, а `INSERT`, `UPDATE` и `DELETE` ждут, пока индекс не построится. На большой таблице это минуты простоя записи.

`CREATE INDEX CONCURRENTLY` пишет не блокируя, но строится дольше, не работает внутри транзакции (а многие инструменты миграций оборачивают их в транзакцию) и при ошибке оставляет индекс в состоянии `INVALID`. Такой индекс нужно удалить и создать заново.

## Быстрый ALTER TABLE может положить всю таблицу

```yaml
slug: alter-table-ochered-blokirovok
category: postgresql
```

С PostgreSQL 11 `ADD COLUMN ... DEFAULT` с неволатильным значением выполняется мгновенно, без перезаписи таблицы. Но любой `ALTER TABLE` всё равно берёт `ACCESS EXCLUSIVE` блокировку, пусть и на миг.

Если в этот момент идёт долгий `SELECT`, миграция встаёт в очередь, а все новые запросы к таблице встают в очередь уже за ней. Сервис лежит, хотя сама операция мгновенная. Ставьте перед миграцией `SET lock_timeout = '5s'` и повторяйте попытку.

```sql
SET lock_timeout = '5s';
ALTER TABLE orders ADD COLUMN source text DEFAULT 'web';
```

## UNIQUE пропускает сколько угодно NULL

```yaml
slug: unique-i-null
category: postgresql
```

По стандарту SQL `NULL` не равен другому `NULL`, поэтому уникальный индекс по `email` спокойно примет десять строк с `email IS NULL`. Для составного ключа ловушка ещё злее: `(tenant_id, external_id)` с `NULL` во втором поле перестаёт защищать от дублей.

С PostgreSQL 15 это настраивается: `UNIQUE NULLS NOT DISTINCT` считает все `NULL` одинаковыми. На более старых версиях выручает частичный уникальный индекс `WHERE external_id IS NULL` по оставшимся колонкам.
