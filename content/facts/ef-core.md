# Факты: EF Core

## Отслеживание сущностей стоит памяти, даже если вы ничего не меняете

```yaml
slug: asnotracking-i-pamyat
category: ef-core
```

По умолчанию каждая загруженная сущность регистрируется в Change Tracker: контекст хранит ссылку на неё и снимок исходных значений для поиска изменений. Отчёт на 100 тысяч строк держит в памяти заметно больше, чем сами данные, а `SaveChanges` потом проверяет их все.

Для чтения используйте `AsNoTracking()` или сразу проекцию через `Select` в DTO — проекции вообще не отслеживаются. Если контекст только читает, можно выставить `QueryTrackingBehavior.NoTracking` на весь контекст.

## Include нескольких коллекций умножает строки

```yaml
slug: include-dekartov-vzryv
category: ef-core
```

`Include(o => o.Items).Include(o => o.Payments)` превращается в один SQL с двумя `LEFT JOIN`. Для заказа со 100 позициями и 10 платежами база вернёт 1000 строк, и в каждой продублированы все колонки заказа. Это cartesian explosion: запрос тормозит, трафик растёт в разы.

`AsSplitQuery()` разбивает загрузку на отдельные запросы по каждой коллекции. Цена — несколько обращений к БД и отсутствие единого снимка данных без транзакции. Включайте точечно, а не глобально.

## Find может не пойти в базу

```yaml
slug: find-lokalnyy-kesh
category: ef-core
```

`DbSet.Find(id)` сначала ищет сущность среди уже отслеживаемых контекстом и, если находит, возвращает её без SQL-запроса. Удобно, но значит и то, что вы получите версию из памяти, а не свежую из базы.

`FirstOrDefault(x => x.Id == id)` всегда выполняет запрос, но при включённом отслеживании вернёт тот же экземпляр из трекера: значения из базы не перезапишут то, что уже лежит в памяти. Хотите гарантированно свежие данные — `AsNoTracking()` или новый контекст.

## Один DbContext нельзя использовать из двух потоков

```yaml
slug: dbcontext-ne-potokobezopasen
category: ef-core
```

`DbContext` не потокобезопасен и держит одно соединение. Если запустить два запроса через один контекст параллельно, например через `Task.WhenAll`, EF бросит `InvalidOperationException: A second operation was started on this context instance before a previous operation completed`.

Для параллельных запросов создавайте отдельные контексты через `IDbContextFactory<T>`. И не забывайте `await` у каждого асинхронного вызова: незавершённый запрос тоже ломает следующий.

## ExecuteUpdate проходит мимо Change Tracker

```yaml
slug: executeupdate-mimo-change-tracker
category: ef-core
```

`ExecuteUpdate` и `ExecuteDelete` (EF Core 7+) сразу шлют `UPDATE`/`DELETE` в базу, не загружая сущности. Это быстро, но уже отслеживаемые объекты об изменении не узнают: в памяти остаются старые значения, а если эти же свойства были изменены в коде, следующий `SaveChanges` затрёт массовое обновление.

Ещё нюанс: эти методы выполняются сразу, а не при `SaveChanges`, и не входят в его транзакцию. Нужна атомарность вместе с остальными изменениями — открывайте транзакцию явно.
