# Факты: CLR и GC

## 85 000 байт — и объект уже в куче больших объектов

```yaml
slug: loh-85000-bait
category: clr-gc
```

Объект размером от 85 000 байт попадает в Large Object Heap. Считается полный размер с заголовком, поэтому `new byte[84976]` уже в LOH, а `new byte[84975]` — ещё нет. LOH логически относится ко второму поколению: `GC.GetGeneration` вернёт 2 сразу после создания.

LOH собирается только при полной сборке и по умолчанию не уплотняется, так что частые большие временные буферы дают и долгие паузы, и фрагментацию. Лечится переиспользованием: `ArrayPool<T>.Shared`, `RecyclableMemoryStream`.

## GC.Collect() не уплотняет LOH

```yaml
slug: gc-collect-ne-uplotnyaet-loh
category: clr-gc
```

Даже принудительная полная сборка освобождает мёртвые объекты в LOH, но не двигает живые: дыры между ними остаются. При фрагментации процесс может держать сотни мегабайт, а очередной большой массив всё равно не влезет ни в одну дыру.

Уплотнение LOH нужно попросить явно, и действует просьба на одну сборку:

```csharp
GCSettings.LargeObjectHeapCompactionMode = GCLargeObjectHeapCompactionMode.CompactOnce;
GC.Collect();
```

Это дорогая пауза, а не регулярная практика. Лучше не плодить большие временные объекты.

## ASP.NET Core по умолчанию работает на Server GC

```yaml
slug: server-gc-po-umolchaniyu
category: clr-gc
```

Консольное приложение стартует с Workstation GC, а шаблон веб-проекта включает Server GC. Классический Server GC заводит кучу на каждое логическое ядро и собирает реже, поэтому один и тот же сервис на машине с 32 ядрами «весит» заметно больше, чем на ноутбуке.

С .NET 9 вместе с Server GC по умолчанию включён режим DATAS: число куч подстраивается под нагрузку, и потребление памяти в контейнерах стало скромнее. Если сервис всё равно раздувается, смотрите `GCHeapHardLimit`, `GCConserveMemory` или переключайтесь на Workstation GC.

## Финализатор продлевает объекту жизнь

```yaml
slug: finalizator-prodlevaet-zhizn
category: clr-gc
```

Объект с финализатором нельзя просто выбросить: при первой сборке GC переносит его в очередь финализации, и объект вместе со всем, на что ссылается, переживает сборку и повышается в поколении. Память освободится только после того, как отработает поток финализации, и следующей сборки.

Поэтому класс с `~Finalizer()` должен реализовать `IDisposable` и вызывать `GC.SuppressFinalize(this)` в `Dispose`. А для неуправляемых хэндлов вместо своего финализатора лучше взять готовый `SafeHandle`.
