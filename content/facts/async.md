# Факты: async/await

## async void роняет процесс

```yaml
slug: async-void-ronyaet-process
category: async
```

У `async void` метода нет `Task`, в который можно положить исключение. Поэтому исключение после первого `await` выбрасывается прямо в пул потоков, и процесс падает целиком. `try/catch` вокруг вызова не поможет: к моменту ошибки вызов уже вернул управление.

```csharp
try { Boom(); } catch { }
static async void Boom() { await Task.Yield(); throw new Exception(); }
```

`async void` допустим только в обработчиках событий UI. Во всех остальных случаях возвращайте `Task`.

## ConfigureAwait(false) в коде ASP.NET Core почти ничего не делает

```yaml
slug: configureawait-v-aspnet-core
category: async
```

`ConfigureAwait(false)` говорит: «не возвращайся в исходный `SynchronizationContext`». В классическом ASP.NET и WPF такой контекст был, и без этой настройки ловили дедлоки на `.Result`. В ASP.NET Core контекста синхронизации нет вообще, продолжения и так выполняются в пуле потоков.

В коде приложения можно не писать его на каждом `await`. В библиотеках, которые могут попасть в WinForms, WPF или старый ASP.NET, — по-прежнему стоит.

## Task.Run в контроллере не ускоряет I/O

```yaml
slug: task-run-v-aspnet-core
category: async
```

`await Task.Run(() => repo.Load())` в экшене выглядит асинхронно, но на деле запрос просто перекладывается с одного потока пула на другой. Поток пула занят ожиданием I/O точно так же, плюс накладные расходы на переключение.

Для I/O нужны настоящие асинхронные API: `ToListAsync`, `ReadAsync`, `SendAsync`. `Task.Run` имеет смысл только чтобы вынести тяжёлую CPU-работу из потока, который нельзя блокировать, а в веб-сервере таких потоков нет.

## .Result в ASP.NET Core не дедлочит, а душит пул потоков

```yaml
slug: sync-over-async-thread-pool-starvation
category: async
```

Без контекста синхронизации `.Result` и `.Wait()` в ASP.NET Core не приводят к классическому дедлоку. Зато каждый такой вызов держит поток пула заблокированным. Под нагрузкой свободные потоки заканчиваются, а новые пул добавляет постепенно, с задержкой, и не успевает за входящими запросами.

Симптом узнаваемый: CPU почти не загружен, а латентность растёт до секунд, и в дампе сотни потоков стоят в `Wait`. Лечится только одним: асинхронность по всей цепочке вызовов.

## await Task.WhenAll показывает только первое исключение

```yaml
slug: whenall-pervoe-isklyuchenie
category: async
```

Если упали несколько задач, `await Task.WhenAll(...)` бросит только первое исключение из `AggregateException`. Остальные не теряются: они лежат в свойстве `Exception` самой задачи.

```csharp
var all = Task.WhenAll(t1, t2);
try { await all; }
catch { foreach (var ex in all.Exception!.InnerExceptions) log.LogError(ex, "fail"); }
```

Если нужно логировать все ошибки параллельных вызовов, сохраняйте задачу `WhenAll` в переменную.

## ValueTask нельзя ожидать дважды

```yaml
slug: valuetask-odin-raz
category: async
```

`ValueTask` может оборачивать переиспользуемый объект `IValueTaskSource`. После первого `await` источник возвращается в пул и может уже обслуживать другую операцию, поэтому повторный `await`, `.Result` до завершения или одновременное ожидание из двух мест дают неопределённое поведение.

Правило простое: `ValueTask` ожидается ровно один раз. Нужно больше — вызовите `.AsTask()` и работайте с обычной `Task`.
